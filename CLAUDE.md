# Канон проекта

Загружается в каждую сессию Claude Code: роль репо, роутер слоёв и принципы,
которые действуют всегда. Каноны форм — в README слоёв; карта документации,
связи между слоями и handoff-контракт — `docs/README.md`; путь форка —
`docs/getting-started.md`.

## Роль репо и флоу

Этот репозиторий — **шаблон бизнес-стратегии**. Его форк `<org>/strategy` —
design-time источник истины: бизнес заказчика (профиль, реестр проблем,
стейкхолдеры), AJTBD, SWOT, Карта гипотез, а когда стратегия требует
продукта — проектирование продуктов (vision и поверхности, интерфейс, экраны,
FSD-карта, диалоги бота, мобильное приложение, сервисы и домены) и
ИТ-периметр бизнеса. Кода здесь нет: stable-артефакты read-only читают
код-репо (`docs/README.md § Что docs отдаёт соседям`).

Экосистема — 7 шаблонов `stit-core/*`; форки одной орги лежат рядом
sibling-checkout'ами (`../<name>`):

| шаблон → форк | роль |
|---|---|
| `business-strategy-template` → `<org>/strategy` | **этот**: стратегия и проектирование продукта |
| `project-infra-template-compose` → `<org>/infra` | runtime проекта (docker-compose на VPS) и операционный хаб |
| `go-backend-template` → `<org>/backend` | Go-сервис |
| `spa-frontend-template` → `<org>/frontend` | React SPA (кабинет, всё за логином) |
| `ssr-frontend-template` → `<org>/site` | Astro SSR-сайт (индексируемый контент) |
| `telegram-bot-template` → `<org>/<bot>` | Telegram-бот |
| `mobile-template` → `<org>/mobile` | KMP-приложение Android + iOS |

Библиотеки: `golibinfra` (Go-киты) и `pylibinfra` (Python-киты).

Флоу проекта:

1. **Старт — здесь.** Аналитик входит через `/entrypoint`, клиент — через
   `/entrypoint-for-business` (§7); до кода проектируется всё, что можно.
2. **Продукт спроектирован → хаб `<org>/infra`.** Там `/init-project` читает
   strategy и поднимает инфру, сквозная задача ведётся
   программой в `.claude/plans/` инфры, и оттуда агенты уходят в сиблинги работать обвязкой того репо.
3. **Дизайн меняется по ходу** — агент из хаба приходит сюда (`../strategy`)
   и работает скиллами этого репо через те же входы. Прямой заход сюда без
   хаба — такой же нормальный режим.

Канон карты и флоу — `docs/reference/ecosystem.md` хаба `<org>/infra`.

## 1. Forward-only

Всё, что пишется в репо, — артефакты, документация, state скиллов, описания
коммитов и PR — говорит о текущем состоянии и о том, куда идём: без журналов
прошлого, «было/стало», дат и следов отменённых решений. Факт, который вынесла
эволюция, удаляется вместе со ссылками на него; история — в `git log`.
Критерии чистой правки — `.claude/rules/forward-only.md`.

## 2. Слои и роутер

Поток сверху вниз: бизнес (профиль, реестр проблем `business-problem`,
стейкхолдеры) → AJTBD → SWOT → Карта гипотез; терминал стратегии — задача
(`task`). Продукт — опциональный исход: под него заводится папка
`docs/projects/<slug>/`, внутри которой ось — поверхность (реестр
`surface.md`); ИТ-периметр один на бизнес. Входы во все слои — оркестраторы
`/entrypoint` (аналитик) и `/entrypoint-for-business` (клиент): они
раскладывают сырьё по слоям и маршрутизируют к исполнителям; прямой вызов
исполнителя тоже допустим.

| слой (канон — README по ссылке) | вопрос | исполнитель | узкий аудит |
|---|---|---|---|
| [`docs/business/`](docs/business/README.md) | кто этот бизнес, какие его проблемы решаем, кто в нём принимает решения | `/business-deep-dive` | — (`/cross-audit`) |
| [`docs/ajtbd/`](docs/ajtbd/README.md) | кто наш сегмент по работам, его граф работ и трения | `/segment-deep-dive` · `/job-graph-deep-dive` · `/jtbd-interview` | `/ajtbd-audit` |
| [`docs/swot/`](docs/swot/README.md) | за счёт чего возможен следующий шаг | `/swot-deep-dive` | `/swot-audit` |
| [`docs/hypothesis-map/`](docs/hypothesis-map/README.md) | под какие метрики целимся | `/hypothesis-map-deep-dive` | `/hypothesis-map-audit` |
| [`projects/<slug>/`](docs/projects/_template/project/README.md) | зачем продукт и для кого (vision, поверхности, возможности) | `/project-deep-dive <slug>` | `/project-audit <slug>` |
| [`…/interface/<surface>/`](docs/projects/_template/interface/README.md) | как пользователь взаимодействует | `/interface-deep-dive <slug> [<surface>]` | `/interface-audit <slug>` |
| [`…/screens/<surface>/`](docs/projects/_template/screens/README.md) | как компонуются экраны | `/screen-deep-dive <slug> [<surface>]` | `/screen-audit <slug>` |
| [`…/fsd/<surface>/`](docs/projects/_template/fsd/README.md) | как фронт нарезан по слоям FSD (фронтовые поверхности: `web` · `admin` · `desktop` · `embed`) | `/fsd-deep-dive <slug> [<surface>]` | `/fsd-audit <slug>` |
| [`…/telegram-bot-flow/<surface>/`](docs/projects/_template/telegram-bot-flow/README.md) | как бот ведёт диалог | `/telegram-bot-flow-deep-dive <slug> [<surface>]` | `/telegram-bot-flow-audit <slug>` |
| [`…/mobile/<surface>/`](docs/projects/_template/mobile/README.md) | как устроено мобильное приложение | `/mobile-deep-dive <slug> [<surface>]` | `/mobile-audit <slug>` |
| [`…/services/`](docs/projects/_template/services/README.md) | из каких сервисов состоит бэкенд | `/service-deep-dive <slug>` | `/service-audit <slug>` |
| `…/services/<svc>/domains/<ctx>/` | какой бизнес-код у бэкенда (по bounded-context) | `/domain-deep-dive <slug> <ctx>` | `/service-audit <slug>` |
| [`projects/infrastructure/`](docs/projects/infrastructure/README.md) | где всё это физически живёт | `/infrastructure-deep-dive` | `/infrastructure-audit` |
| [`projects/project-map.md`](docs/projects/project-map.md) | как продукты бизнеса стыкуются | авторская сторона — `integration` (`/project-deep-dive`) | `/cross-audit` |

`…` — `docs/projects/<slug>`. Сквозную консистентность всех слоёв сверяет
`/cross-audit`; связи между слоями семантические и авторятся снизу вверх —
их карта в `docs/README.md § Связи между слоями`. Канон формы продуктовых
слоёв живёт один раз в `docs/projects/_template/`, данные — в папках
проектов. Скиллы проектных слоёв берут `<project-slug>` первым аргументом,
слои по поверхности — `[<surface>]` вторым; без аргументов — пикеры по
человекочитаемым именам (`docs/projects/README.md`, `.claude/rules/naming.md`).

## 3. Экспертиза — священна на всех слоях

Содержательные формулировки артефактов агент не пишет из своей головы:
артефакты — источник истины, по которому бизнес принимает решения, а код-репо
пишут код, поэтому выдуманная формулировка становится ложным фактом у всех
потребителей. Формулировку даёт её владелец (таблица ниже) — через
`AskUserQuestion`; факты о бизнесе берутся из материалов клиента,
подтверждённого research и транскриптов интервью. Anti-patterns агент может
предлагать как варианты ответа, сами тексты — нет. Неоднозначность вне
покрытия — вопрос человеку, не угадывание.

| область | что не пишется из головы | владелец |
|---|---|---|
| **Бизнес-проблемная** (business · swot · hypothesis-map) | профиль и текущие числа бизнеса, факторы и ставки SWOT, цель, метрика (формула, источник истины, атрибуция, критерий приёмки), субъект и его мотивация, гипотезы | бизнес, аналитик |
| **Стейкхолдерская** (business) | имена и кресла, роль в сделке, власть и интерес, стойка, личные драйверы, страхи и win, связи между людьми, путь вовлечения; психографику не выдумывать — «не отбить ROI» пишется страхом CFO, только если так сказал клиент | материалы клиента, интервью |
| **AJTBD** (ajtbd) | сегменты, работы (когда / хочу / чтобы), нанятые решения, трения, драйверы и барьеры, мотивации; работа доказывается прошлым поведением (затратами времени и денег), не гипотетикой | аналитик, подтверждённый research, транскрипты интервью |
| **Продуктовая** (project) | vision, jobs, pains, value, why, source | бизнес, аналитик |
| **UX-доменная** (interface) | goal, action, when, using-what | аналитик |
| **Мобильная** (mobile) | состав экранов и фич, фразы голосовых команд, тексты обоснований разрешений (`rationale`), обещания свежести виджета и точности напоминаний, поведение без сети и без разрешений (`fallback`); линза платформы задаёт вопросы, но не отвечает за аналитика — «нужно ли продукту», включая «не нужно», решает он | аналитик |
| **Бизнес-домен** (домены сервисов) | инварианты, preconditions, business rules | архитектор |
| **Архитектурная** (services) | разбиение на сервисы, владелец данных, sync или брокер, технология ресурса (postgres / redis / nats), нужен ли gateway | архитектор |
| **Инфраструктурная** (infrastructure) | провайдеры и ёмкость серверов, kubernetes или compose, раскладка юнитов по рантаймам, общие ресурсы бизнеса | архитектор, бизнес |

Метрика — совместный с бизнесом best-effort таргет, **не гарантия**:
гарантируем доставку проекта по scope, а граница «гарантируем / целимся / вне
контроля» живёт в строке `docs/business/business-problem.md`. Облик (craft:
цвет, типографика, пространство, движение) в артефакты не пишется: wireframe
и hi-fi автор макета собирает вручную, модель craft не выдумывает.

## 4. Авто-память отключена

Автопамять Claude Code выключена (`autoMemoryEnabled: false` в
`.claude/settings.json`), поэтому «сохранить в память» не предлагается. То,
что должно пережить сессию, живёт в репо и коммитится вместе с ним — это
общая память проекта: `CLAUDE.md`, `.claude/rules/<topic>.md` и единый state
оркестраторов — `.claude/skills/entrypoint/state/` (аналитик) и
`.claude/skills/entrypoint-for-business/state/` (клиент); исполнители пишут в
свои ветки этого дерева.

## 5. Авторизация правок и коммит

Правки артефактов делаются свободно. Спросить человека стоит перед правкой,
которая может сломать накопленную продуктовую модель (vision · user ·
capability — основа остальных слоёв) или несовместимо раскатиться вширь
(контракт артефактов всех слоёв).

Перед коммитом — узкий аудит каждого тронутого слоя (колонка «узкий аудит» в
§2); тронули несколько слоёв — ещё `/cross-audit`. Коммит и push — решение
человека: без явной просьбы агент не коммитит и не пушит.

## 6. Зоны правок

- Артефакты слоя правит его исполнитель из таблицы §2 по канону формы из
  README слоя; аналитический оркестратор маршрутизирует и в `docs/` сам не
  пишет. В клиент-режиме все темы ведёт клиентский оркестратор (§7).
- `docs/projects/_template/` — образец формы: данные проекта в него не
  пишутся, а канон не копируется в папки проектов.
- Sweep'ы (терминология, чистка): один агент — одна непересекающаяся зона.

## 7. Клиент-режим (`entrypoint-for-business`)

Когда сессию ведёт клиент, основатель или PO, а не аналитик, вход один —
`/entrypoint-for-business`. Он ведёт все темы сам, через свои призмы в
бизнес-языке, и read-only сверяется с методичками аналитических скиллов;
аналитические скиллы в этом режиме не активируются. Суть режима:

- **бизнес-язык** — клиент не видит `slug`, `kind`, `draft`, `stable`, имён
  файлов и скиллов; только «закрыто / в работе»;
- **метрика — совместная цель, не гарантия** (§3); строгую измеримость
  (атрибуция, критерий приёмки) клиент-режим оставляет аналитику;
- **эскалация и передача** — застрявшее помечается `**жду аналитика**`;
  наработанное уезжает в единую ветку `client` только с явного согласия
  клиента; `--no-verify` не используется — упавший хук обсуждается с клиентом;
- **единый контекст** — любой скилл read-only видит оба дома state
  (аналитический и клиентский), проектные ветки — только текущего продукта; в
  чужой дом и чужую ветку никто не пишет. Прочитанное из кухни аналитика
  клиенту не зачитывается, а переводится в бизнес-язык (anti-leak).

Детали — призмы тем, упаковка передачи, доступ к репозиторию, форматы
`client-handoff/` — в скилле `entrypoint-for-business` и его `references/`.

## 8. Язык

Ответы — на русском. Проза артефактов, пояснения и человекочитаемые поля —
по-русски, без полу-калек («пропсы», «варианты-проперти»); каноны терминов —
в README слоёв. Английский в backticks — для устоявшегося канона (FSD-слои,
DDD-термины `aggregate` · `value object` · `use-case` · `event` · `policy` ·
`bounded-context`, `a11y`) и для структурных идентификаторов, которые читают
код-репо: имена H2-секций и поле-метки доменных шаблонов (`<org>/backend`),
идентификаторы слоя telegram-bot-flow (`<org>/<bot>`) и слоя mobile
(`<org>/mobile`). Эти идентификаторы не переименовываются — они часть
handoff-контракта; полный перечень — в разделах о языке контракта README
этих слоёв. Технические идентификаторы (имена файлов, функций, переменных,
команд, флагов) и содержимое коммитов и PR не переводятся; комментарии в
коде — на языке окружающего кода.
