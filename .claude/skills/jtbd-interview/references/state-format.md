# Формат памяти `state/`

Рабочее состояние процесса интервью. **Не** артефакты `docs/ajtbd/` — это
**сырьё** для соседних скилов. Forward-only, не журнал.

## Расположение

```
.claude/skills/jtbd-interview/state/
├── prep.md                                        (подготовка: сегмент-цель, гипотезы, критерии, рынок, объём)
├── channels.md                                    (каналы рекрута + находки роя + делегирование)
├── <тема>-script.md                               (опц. собранный скрипт под задачу)
├── transcripts/<YYYY-MM-DD>--<HH-MM>--<тема>.md   (человекочитаемый лог интервью)
└── candidates/<тема>-<UTC-ts>.md                  (выжатые кандидаты: работы / решения / трения)
```

Каталоги создаются по требованию. **Транскрипты и кандидаты не удаляются
авто** — это сырьё для intake соседей и для повторного захода.

## `prep.md`

```markdown
---
phase: prep
---

## Цель интервью
- Задача: поиск сегмента | поиск продукта
- Рынок: b2b | b2c
- Сегмент-цель / широкая гипотеза работы: <…> (откуда: соседний state / аналитик)

## Гипотезы работ (чек «есть / нет»)
- <гипотеза работы 1>
- <гипотеза работы 2>

## Критерии рекрута
- Роль: <…> (B2B — ЛПР напрямую)
- Подтверждённая оплата работы: <как проверяем, что человек уже платит>
- Квалифицирующие признаки: <…>

## Объём и план волн
- Норматив: <30+/20+ навигация | 10–12/8–10 сегмент | 8+ продукт>
- Волны: итерации по 6–8; стоп — 2 волны подряд без новых работ
- Дыра: размер сегмента — количественник/кабинетная аналитика (не интервью) → /segment-deep-dive
```

## `channels.md`

```markdown
---
phase: channels
---

## Каналы рекрута (по убыванию конверсии)
| канал | кого там найти | формат сообщения |
|---|---|---|
| <…> | <…> | <…> |

## Находки роя
- <конкретный чат / сообщество / панель / конференция> — <ссылка> — <кого>

## Тексты сообщений
- <канал>: <каркас месседжа — наполняет аналитик/клиент>

## Делегирование
- Бриф админу: <критерии · где · что писать · анкета · сколько · как назначать · куда складывать>
```

## `candidates/<тема>-<ts>.md`

```markdown
---
source: state/transcripts/2026-06-05--14-30--dacha-gear.md
segment-hypothesis: dacha-owner
---

## Кандидаты-работы
- <name> · когда «…» · хочу «…» · чтобы «…» · level=core? · type=последовательная?
  · важность 7/10 · частота 3–4/сезон · доказана: <какие затраты> · уточнить: <что>

## Кандидаты-решения
- <name> · нанято на «…» · kind=substitute · satisfaction 3/10 (N=1) · цена 1500₽
  · цена↔ценность 6/10 · уточнить: <что>

## Кандидаты-трения
- <name> · пара (решение «…» + работа «…») · сила 7/10 · драйверы «…» · барьеры «…»
```

## Секции (служебные — опциональны, forward-only)

В `prep.md` / `channels.md` можно держать:
- `## Открытые вопросы` — `**жду решения аналитика**` блокирует переход
  фазы; закрытый — удалить;
- `## Что копать дальше` — следующие шаги; выполненные удалять.

## Жизненный цикл

- Создаётся, когда есть что записать.
- Перезаписывается свободно (`prep`/`channels`/`script`).
- Транскрипты и кандидаты — **накапливаются**, авто не чистятся (сырьё).
- Не аккумулировать журнал прошлого — история в `git log`.

## Единый контекст (read-only)

Скилл **read-only** смотрит соседние `state/` и **в чужой не пишет**:

- `../segment-deep-dive*/state/` — под какой сегмент целиться, какие
  гипотезы работ-stub и отбраковки НЕ-сегментов уже есть;
- `../job-graph-deep-dive*/state/` — какие дыры графа (работы / решения /
  трения, дыры research) проверить интервью.

Наоборот: `/segment-deep-dive` и `/job-graph-deep-dive` **read-only**
читают наши `transcripts/` и `candidates/` как сырьё для intake (режим B).
Промотируют в `docs/ajtbd/` они, через `AskUserQuestion`.

## Клиент-эскалация

Если процесс ведёт клиент: state всё равно здесь. Передача аналитику — через
intake-механизм соседей. В чате — бизнес-язык (без `slug`/`kind`/`draft`),
метрика не подаётся как гарантия. Push в единую ветку `client` — по тем же
правилам клиент-режима репозитория (с явного согласия).
