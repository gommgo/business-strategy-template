# jtbd-interview

**Отдельный тяжёлый опциональный процесс** живых JTBD-интервью по
методологии **Advanced JTBD** (Иван Замесин). В контексте `docs/`
интервью **не обязательны** — основной источник истины слоя `docs/ajtbd/`
это рой web-research. Но когда research не вычерпал реальность, нет
подтверждённых работ / решений / трений, не из чего собрать Score или
нужно проверить гипотезы работ «есть / нет» — запускается этот скилл.
Запуск **только по явному запросу** (аналитика или эскалации клиента).

## Контракт I/O (главное)

Скилл **НЕ пишет напрямую в артефакты `docs/ajtbd/`**. Он **собирает
сырьё** в ветку `_interview/` единого дерева state оркестратора
(`../entrypoint/state/ajtbd/_interview/`):

- **Транскрипты** (человекочитаемые) →
  `../entrypoint/state/ajtbd/_interview/transcripts/<YYYY-MM-DD>--<HH-MM>--<тема>.md`;
- **Кандидатов** (работы / решения / трения, выжатые из конспекта) →
  `../entrypoint/state/ajtbd/_interview/candidates/<тема>-<ts>.md`.

Это сырьё затем разбирают через **intake (режим B)** скилы
`/segment-deep-dive` (кандидаты в сегменты) и `/job-graph-deep-dive`
(кандидаты в работы / решения / трения). Промотируют в `docs/ajtbd/`
**они**, через `AskUserQuestion`. Этот скилл — поставщик сырья, не
владелец артефактов.

## Разведочная рамка (держать всю сессию)

Работа живёт в психике, напрямую не видна. Единственная зацепка —
**действия** (затраты времени / денег / энергии), **не мнения и не
гипотетика**. Поэтому:

- Спрашиваем **только про прошлое**. «Что бы вы сделали, если…» — данных
  не даёт; люди катастрофически плохо прогнозируют своё поведение.
- Три сущности **не смешиваются**: работа ⟂ решение ⟂ проблема. Трение —
  следствие конкретного решения, нанятого на работу.
- Интервьюер **никогда не выдумывает ответы респондента** и не подсказывает.
  Экспертиза сегмента — священна (`CLAUDE.md` §3): её добывают из живого
  человека, не из головы модели. Скилл помогает **держать скрипт,
  фиксировать сказанное и интерпретировать**, но содержание ответов — от
  респондента.

## Точки входа

| вызов | поведение |
|---|---|
| `/jtbd-interview` | сводка по фазам процесса + следующий шаг |
| `/jtbd-interview prep` | определить сегмент/гипотезы, критерии рекрута, рынок, объём |
| `/jtbd-interview channels` | рой web-research по каналам рекрута + единый список каналов |
| `/jtbd-interview script` | собрать скрипт под задачу (сегмент / продукт; B2B / B2C) |
| `/jtbd-interview conduct` | вести живое интервью по скрипту (держать, фиксировать, напоминать правила) |
| `/jtbd-interview interpret` | конспект → кандидаты + transcript в `_interview/` |
| `/jtbd-interview <свободный текст / конспект>` | сырьё конспекта → фаза interpret |

`phase` ∈ {`prep`, `channels`, `script`, `conduct`, `interpret`}.

## Что делать сразу при запуске

1. Прочитать `docs/ajtbd/README.md` + 5 kind-файлов
   (`segment.md`, `job.md`, `solution.md`, `segment-problem.md`,
   `job-graph.md`) — **какой результат нужен на выходе** интервью (шаблон
   работы когда/хочу/чтобы; решение + satisfaction/цена; трение + сила/
   драйверы/барьеры). Интервью существует, чтобы наполнить эти формы.
2. Прочитать `references/phases.md` — карту 5 фаз.
3. Read-only подтянуть единое дерево state оркестратора
   (`../entrypoint/state/`, см. «Единый контекст») — под какой сегмент уже
   целятся `/segment-deep-dive` и `/job-graph-deep-dive` (ветка
   `../entrypoint/state/ajtbd/`), какие гипотезы работ / дыры research они
   оставили.
4. Если args = конспект интервью / текст — фаза `interpret`
   (`references/interpret.md`).
5. Если args пустые — сводка по фазам + `AskUserQuestion` со следующим
   шагом.
6. Если `<phase>` — открыть соответствующий reference.

## Сводка состояния (без args)

1. Прочитать ветку `_interview/` (`prep.md`, `channels.md`,
   `transcripts/`, `candidates/`) в дереве оркестратора + read-only
   остальное дерево.
2. Определить **текущую фазу**:
   - нет `../entrypoint/state/ajtbd/_interview/prep.md` (не определены
     сегмент/гипотезы/критерии) → `prep`;
   - prep есть, нет списка каналов в
     `../entrypoint/state/ajtbd/_interview/channels.md` → `channels`;
   - каналы есть, нет собранного скрипта → `script`;
   - скрипт есть, нет ни одного транскрипта → `conduct`;
   - есть транскрипты без выжатых кандидатов → `interpret`;
   - объём интервью не добран по нормативу → назад в `conduct`.
3. Вывести карту фаз и где мы. Через `AskUserQuestion` предложить
   следующий шаг.

## Фазы процесса

Полная карта — `references/phases.md`. Процесс **длительный** и идёт
итерациями (волны интервью), не водопадом.

| фаза | цель | reference | сырьё на выход |
|---|---|---|---|
| `prep` | под какой сегмент / гипотезы работ интервью; критерии рекрута (роль, опыт, **подтверждённая оплата** работы); рынок B2B/B2C; объём по нормативам | `phases.md` | `_interview/prep.md` |
| `channels` | где искать респондентов: СВОЙ рой web-research по каналам рекрута; единый список «канал → кого там найти → формат сообщения»; делегирование админу | `recruit-channels.md`, `recruit-delegation.md` | `_interview/channels.md` |
| `script` | собрать скрипт под задачу: B2B/B2C поиск сегмента ИЛИ B2C/B2B поиск продукта; дословные блоки вопросов | `scripts.md` | `_interview/<тема>-script.md` (опц.) |
| `conduct` | вести живое интервью: держать скрипт, помогать фиксировать ответы, напоминать правила | `scripts.md`, `transcripts.md` | `_interview/transcripts/<…>.md` |
| `interpret` | конспект → кандидаты: шаблон работы, нанятые решения, трения; записать transcript + кандидатов | `interpret.md`, `transcripts.md` | `_interview/candidates/<…>.md` |

## Объём по нормативам (фиксировать в prep)

Из базы знаний AJTBD. Интервью идут **итерациями**, объём — ориентир, не
догма:

| задача | B2C | B2B |
|---|---|---|
| навигация — найти полноту сегментов | 30+ | 20+ |
| детально один сегмент | 10–12 | 8–10 |
| JTBD для продукта на выбранный сегмент | 8+ | 8+ |
| итерация поиска (один цикл) | 6–8 | 6–8 |
| сигнал полноты | 2 итерации подряд без новых работ | то же |

Размер сегмента качественными интервью **не определяется** — нужен
количественник / кабинетная аналитика (это уже не интервью, отметить как
дыру для `/segment-deep-dive`).

## Свой рой web-research по каналам (фаза channels)

См. `references/recruit-channels.md`. Это **отдельный** рой от
research-волн `/segment-deep-dive` / `/job-graph-deep-dive`: те ищут
работы/решения/трения, **этот** — каналы, **где живёт** нужный сегмент и
**как с ним заговорить**. Запуск только по решению аналитика через
`AskUserQuestion` (дефолт 5 углов: LinkedIn / телеграм-чаты и сообщества /
панели рекрута / текущая база и нетворк / конференции и реклама / тест
через лендинг). Параллельные подагенты в одном message-блоке (инструмент
**Agent**), не Workflow. Находки → `../entrypoint/state/ajtbd/_interview/channels.md`. Принцип:
**сообщение важнее канала**; рекрутим **только тех, кто уже платил за
выполнение работы**.

## Стиль вопросов (к аналитику/клиенту)

- **Всегда `AskUserQuestion`**, до 4 вопросов в раунде.
- **Опции** — для: enum (рынок `b2b`/`b2c`; задача интервью «поиск
  сегмента» / «поиск продукта»; выбор каналов; выбор блоков скрипта);
  выбор существующего сегмента-цели из ветки `../entrypoint/state/ajtbd/`;
  проверочного вопроса на ложную работу.
- **Other (значения)** — гипотезы работ, критерии рекрута, тексты
  сообщений для рекрута, формулировки кандидатов из конспекта. Содержание
  интервью **не выдумывать** — оно от респондента / аналитика.

Внутри **самого интервью** (фаза conduct) скилл держит **дословные блоки
вопросов** из `references/scripts.md` и **правила** из `references/conduct.md` —
но ответы вписывает только те, что назвал респондент.

## Память: ветка `_interview/`

Сырьё интервью живёт в ветке `_interview/` единого дерева state
оркестратора: `../entrypoint/state/ajtbd/_interview/`. Своего `state/` у
скилла нет. Канон формы заметок (per-kind заметка) и состав ветки
`_interview/` — `../entrypoint/references/state-model.md`. Состав:

```
../entrypoint/state/ajtbd/_interview/
├── prep.md                                   (сегмент-цель, гипотезы работ, критерии рекрута, рынок, объём)
├── channels.md                               (каналы рекрута: канал → кого → сообщение; находки роя)
├── transcripts/<YYYY-MM-DD>--<HH-MM>--<тема>.md   (человекочитаемый лог интервью)
└── candidates/<тема>-<UTC-ts>.md             (выжатые кандидаты: job / solution / segment-problem)
```

Транскрипты и кандидаты — **сырьё для соседей**, не удаляются авто.
Forward-only, пустые служебные секции удаляются.

**Единый контекст (read-only):** скилл read-only смотрит всё дерево
`../entrypoint/state/` и **в чужие ветки не пишет** (своя — только
`_interview/`). В первую очередь — ветку `../entrypoint/state/ajtbd/`
(`/segment-deep-dive`, `/job-graph-deep-dive`): под какой сегмент целиться,
какие гипотезы работ / дыры research проверить интервью. Наоборот — эти
скилы read-only читают наши транскрипты для intake. См.
`../entrypoint/references/state-model.md`.

## Клиент-эскалация

Скилл запускается и по эскалации клиента, который хочет интервью. Тогда:
бизнес-язык в чате (без `slug`/`kind`/`draft`), метрика — не гарантия,
строгую измеримость откладываем аналитику. Сырьё всё равно ложится в
ветку `_interview/`; передача аналитику — через тот же intake-механизм
(`/segment-deep-dive`, `/job-graph-deep-dive`). Скилл их **не вызывает** —
предлагает аналитику.

## Завершение сессии

1. Перечислить, что наработано (фаза, сколько транскриптов, сколько
   кандидатов).
2. Назвать текущую фазу и следующий шаг (продолжить интервью до норматива
   / выжать конспекты / передать сырьё).
3. Через `AskUserQuestion` предложить:
   - продолжить набор интервью (если объём не добран);
   - выжать накопленные конспекты (фаза `interpret`);
   - **передать сырьё** на разбор: `/segment-deep-dive` (кандидаты в
     сегменты) или `/job-graph-deep-dive` (кандидаты в работы / решения /
     трения) через их **intake (режим B)** — указать пути транскриптов и
     `../entrypoint/state/ajtbd/_interview/candidates/`.

Скилл **сам не вызывает** другие скилы — называет следующий шаг, запускает
аналитик.

## Запреты

- Не писать напрямую в `docs/ajtbd/` — только собирать сырьё в ветку
  `_interview/`.
- Не выдумывать ответы респондента, работы, решения, трения, оценки.
  Содержание интервью — от живого человека, не из головы модели.
- Не выдавать **гипотетику** за работу — работа доказывается прошлым
  поведением (затраты времени/денег/энергии).
- Не задавать вопросы про будущее, не подсказывать ответ, не задавать по
  3–4 вопроса сразу, не перебивать паузы (правила conduct).
- Не рекрутить тех, кто **не платил** за выполнение работы (нет затрат —
  нет доказанной работы).
- Не запускать рой каналов через Workflow — только параллельные подагенты
  (Agent) в одном message-блоке; и только по решению аналитика.
- Не аккумулировать журнал в ветке `_interview/` — forward-only.
- Не писать в чужие ветки дерева `../entrypoint/state/` — только
  read-only (своя — `_interview/`).
- Не пушить и не коммитить. Не вызывать другие скилы — предлагать
  следующий шаг аналитику.
