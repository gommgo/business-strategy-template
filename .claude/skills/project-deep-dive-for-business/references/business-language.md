# Словарь перевода жаргон → язык бизнеса

Скилл общается с клиентом **только** в правой колонке. Левая —
внутренняя терминология, видимая аналитику.

## Главное

| жаргон | бизнес |
|---|---|
| artifact / запись | «то, что мы описываем» / «карточка» |
| slug | не упоминается; внутри подбирается автоматически |
| kind | не упоминается |
| draft | «в работе» / «черновик» |
| stable | «закрыто» / «готово» |
| status | «состояние» |
| vision | «общая идея продукта» / «зачем продукт и для кого» |
| user | «пользователь» / «тип пользователей» |
| capability | «умение продукта» / «что продукт делает» |
| boundary | «граница продукта» / «что НЕ делаем» |
| surface | «где продукт работает» (web/мобильный/...) |
| integration | «общение с внешним сервисом» |
| constraint | «обязательное правило» / «закон» / «контрактное обязательство» |
| market | «конкуренты и аналоги» |

## Поля

| жаргон | бизнес |
|---|---|
| description | «короткое описание в одно предложение» |
| context | «где это происходит, в каком процессе» |
| jobs (jobs-to-be-done) | «что они хотят получить от продукта» |
| pains | «что их сейчас раздражает» |
| value | «какую пользу это приносит пользователю» |
| direction | «в какую сторону идут данные» |
| owner | «кто начинает общение» |
| payload | «что именно передаём/получаем» |
| kind (у constraint) | «какого типа правило — закон / контракт / SLA» |
| source | «ссылка на документ / закон / договор» |
| sources (у market) | «откуда вы это узнали» / «ссылки на статьи и сайты» |
| url | «основная ссылка» |
| type (у surface) | «формат» (web / мобильный / API / админка / бот) |
| lives-at | «где это конкретно — какой домен, какой магазин приложений» |
| why (у boundary) | «почему отказ — правильный, а не временный» |
| audience | «для кого продукт — для других компаний (b2b), для людей (b2c), для сотрудников внутри (internal), для государства (gov)» |
| intent | «это новая услуга или улучшение существующей; решаем свою задачу или задачу клиента» |
| market-maturity | «вы уже работаете на этом рынке или это разведка нового, где вас ещё нет» |
| lifecycle | «на какой стадии продукт — идея / в сборке / MVP / бета / работает / дорабатываем» (видно как простая стадия, без жаргона status) |

## Процедуры

| жаргон | бизнес |
|---|---|
| project / project-slug / папка проекта | «продукт» (по человекочитаемому названию; slug и папка не показываются) |
| Project picker | «какой продукт обсуждаем?» |
| addresses-problem | «какую бизнес-задачу продукт решает» |
| Phase / фаза | «блок» / «тема» |
| Workflow | «как мы будем работать» |
| AskUserQuestion | (просто вопрос с кнопками — не упоминается) |
| Stub | (не упоминается; внутри создаётся автоматически) |
| Promote draft → stable | «закроем этот блок?» |
| Cascade delete | «давайте уберём это и всё связанное — вот что затронется» |
| Audit | «проверка консистентности» (если уж зашло — но обычно эскалируем к аналитику) |
| Cross-audit | (никогда не упоминаем — внутренний инструмент) |
| Mirror / зеркало | «связь» |
| Research / рой агентов | (не упоминаем; если клиент просит — эскалируем) |
| Escalation | «передать аналитику» |
| State / state-заметка | «наши заметки» / «мои заметки про продукт» |
| Branch | «отдельная папка для аналитика» (если уж зашло) |
| Push | «отправить» |
| Commit | «зафиксировать» |
| Frontmatter / YAML | (никогда не показываем) |

## Чего никогда не говорить

- «Это draft / stable» — клиент не отличает.
- «По канону записи …» — клиент не знает канона.
- «Slug нужен в kebab-case» — клиент не должен это видеть.
- «Папка `docs/projects/<slug>/`» — продукт называем по-человечески, не
  именем папки и не slug.
- «Spawn agent / Web research roy» — не упоминаем.
- «Cross-layer консистентность» — это аналитический слой.

## Как формулировать критерии и anti-patterns

Вместо:
> «User не должна нарушать критерий 2 (контекст устойчивый).»

Скилл говорит:
> «Похоже, тут не хватает контекста — где этот пользователь находится,
> в каком процессе. Можете дописать?»

Вместо:
> «Это anti-pattern — capability как фича из бэклога.»

Скилл говорит:
> «Заметил, что это звучит как пункт из плана разработки. Обычно в
> таких случаях лучше переформулировать в "что пользователь получает".
> Попробуем?»

## Если клиент использует жаргон

Если клиент сам говорит «давайте про user» — скилл подхватывает его
язык и не «переучивает». Но **не** уходит в гипертерминологию: остаётся
на пол-шаге проще, чем клиент.
