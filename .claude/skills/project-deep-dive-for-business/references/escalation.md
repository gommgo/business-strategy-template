# Эскалация и передача аналитику

Два формата эскалации:

1. **Мягкая** — клиент застрял на конкретном вопросе. Скилл фиксирует
   `**жду аналитика**` в state-заметке. Клиент продолжает работу
   дальше. При следующем `--share` это поедет аналитику вместе с
   остальным.

2. **Полная** (`--share`) — клиент решает передать аналитику весь
   накопленный материал и переключиться на ожидание. Это происходит:
   - по явному жесту клиента (`--share` или «передай аналитику»);
   - по подсказке скилла, когда клиент явно застрял или закончил блок.

## Мягкая эскалация (`**жду аналитика**`)

### Когда

Скилл видит сигнал «клиент не может ответить»:

- три раза Other без сходящегося ответа;
- явное «не знаю / надо спросить»;
- клиент попросил «давай это пропустим»;
- вопрос требует специальной дисциплины (классификация регуляторики,
  рынок).

### Что делает

1. `AskUserQuestion`:

   > «Вижу, что тут лучше дождаться аналитика — у него есть
   > инструменты, чтобы это прояснить. Можем зафиксировать вопрос для
   > него и пойти дальше?»

   - «Да, отложим до аналитика»;
   - «Нет, давайте ещё попробуем»;
   - «Лучше передам сразу» (`--share`).

2. По «да» — записать в state-заметку:

   ```markdown
   ## Открытые вопросы
   - (**жду аналитика**) <конкретный вопрос в языке клиента>
   ```

3. Сообщить клиенту: «Записал. Когда отправим, аналитик увидит и
   ответит. Пойдём дальше?»

### Что **не делает**

- Не пытается «угадать» ответ за клиента.
- Не блокирует дальнейшую работу. Клиент может работать с другими
  блоками, пока этот ждёт.
- Не отправляет в этот момент ничего наружу. Эскалация копится
  локально до `--share`.

## Полная передача (`--share`)

### Когда

Триггеры:

- Клиент явно сказал «передай аналитику» / `--share`.
- Закрыл логичный блок (например, дописал vision до stable, или
  заполнил всех users), и скилл предлагает.
- Накопилось 3+ `**жду аналитика**` — скилл предлагает не копить
  дальше.

### Подтверждение через `AskUserQuestion`

**Обязательный шаг**. Без явного «да» от клиента ничего не уезжает.

> «Я подготовлю для аналитика:
>   — что вы заполнили в проекте (черновики ваших блоков);
>   — наши заметки и открытые вопросы;
>   — короткий пересказ что сделали и где остановились;
>   — полный текст нашей сессии (мои вопросы и ваши ответы — чтобы
>     аналитик видел контекст).
>
> Всё это поедет в **отдельную папку проекта**, чтобы аналитик мог
> посмотреть, не трогая основную работу. Отправляем?»

Опции:

- «Да, отправляем сейчас».
- «Хочу сначала посмотреть, что именно поедет» — `--share --preview`,
  скилл показывает содержимое summary и список файлов (transcript
  показывать не нужно — клиент уже видел эти диалоги в чате).
- «Нет, отменим».

### Что упаковывается

Файлы, которые попадают в commit (только по **выбранному продукту**):

1. **Изменения в `docs/projects/<project-slug>/`** — то, что клиент
   заполнил по продукту в этой сессии.
2. **Изменения в `state/<project-slug>/`** — заметки, открытые вопросы,
   в т.ч. все `**жду аналитика**`.
3. **`client-handoff/summary.md`** — живой срез: что сделал, где
   остановился, на что ждёт ответа. Бизнес-языком, без жаргона; держится
   актуальным (перезаписывается, без мусора).
4. **`client-handoff/transcripts/<YYYY-MM-DD>--<HH-MM>--<тема>.md`** —
   человекочитаемое имя; полный лог сессии: каждый вопрос, **варианты,
   которые скилл предлагал**, и выбранный ответ.

### Что **не** упаковывается

- ❌ `state/<project-slug>/_session-log/` — это служебный буфер, его
  содержимое уже перенесено в transcripts.
- ❌ Папки **других** продуктов — упаковываем только текущий
  `docs/projects/<project-slug>/`.
- ❌ Файлы вне `docs/projects/<project-slug>/`,
  `.claude/skills/project-deep-dive-for-business/state/<project-slug>/`,
  `client-handoff/`.
- ❌ `.env`, `.runtime/`, ключи. Их в проектном репо быть не должно,
  но на всякий случай — `git add` адресный, не `-A`.

### Настройка доступа к репозиторию (один раз)

Push требует логин/пароль — но клиента спрашиваем **ровно один раз на
устройстве**, дальше git помнит сам. Перед первым push проверить, сохранён
ли уже доступ:

```bash
host=$(git remote get-url origin | sed -E 's#https?://([^/@]*@)?([^/]+)/.*#\2#')
[ "$(git config --global credential.helper)" = "store" ] \
  && grep -q "@$host" ~/.git-credentials 2>/dev/null && echo ДОСТУП-ЕСТЬ
```

- Печатает `ДОСТУП-ЕСТЬ` → доступ уже сохранён: ничего не спрашиваем, сразу
  к Git-механике.
- Иначе — **один раз** запросить логин и пароль (или токен доступа, если
  выдали) через `AskUserQuestion` бизнес-языком: «Чтобы отправлять без
  повторных вопросов, нужно один раз ввести доступ к репозиторию — логин и
  пароль (или токен). Сохраню локально на вашем компьютере, больше не
  спрошу.» Логин и пароль клиент вводит через Other (два поля). Затем
  сохранить стандартным механизмом git (не редактировать файл руками):

  ```bash
  git config --global credential.helper store
  printf 'protocol=https\nhost=%s\nusername=%s\npassword=%s\n' \
    "$host" "<логин>" "<пароль>" | git credential approve
  ```

  После этого push идёт молча — и сейчас, и во всех будущих сессиях.

**Логин и пароль клиента — секрет.** Никогда не писать их в transcript,
summary, state, commit или в обычный текст чата после ввода. Этот шаг в лог
сессии не попадает.

### Синхронизация с main (старт и перед push)

`main` — канон аналитика, он уходит вперёд (аналитик мёржит черновики,
дописывает анализ). Чтобы клиент всегда работал поверх свежей аналитики,
ветку `client` держим перебазированной на `main` — и на старте сессии, и
перед каждым push.

**На старте сессии (до работы):**

1. `git fetch origin` — узнать, ушёл ли `main` вперёд (всегда безопасно).
2. Рабочее дерево чистое (нет несохранённых черновиков)?
   - Да → лечь поверх свежего `main`:
     ```bash
     git switch client 2>/dev/null || git switch -c client origin/main
     git pull --rebase origin client 2>/dev/null   # свои коммиты с другого устройства
     git rebase origin/main
     ```
     Клиенту бизнес-языком: «Подтянул свежие обновления, можно работать».
   - Нет (есть несохранённые черновики) → дерево **не трогать**; сказать,
     что обновления подтянутся при отправке, и работать дальше (rebase на
     `main` всё равно случится в Git-механике после коммита).

**Конфликт rebase** — не угадывать. Через `AskUserQuestion` бизнес-языком:
«Свежие правки пересеклись с вашими черновиками — это лучше развести
аккуратно. Поставлю на паузу для аналитика?» → зафиксировать
`**жду аналитика**`, дерево не ломать. Конфликты разруливает аналитик.

### Git-механика

1. Доступ настроен (см. «Настройка доступа»).
2. Встать на единую ветку `client` — одна на все сессии, новые не плодим:
   `git switch client 2>/dev/null || git switch -c client origin/main`.
3. Перезаписать `client-handoff/summary.md` под актуальное состояние
   (живой срез, без мусора — см. формат ниже).
4. Записать `client-handoff/transcripts/<YYYY-MM-DD>--<HH-MM>--<тема>.md` (с
   предложенными вариантами — см. формат ниже).
5. `git add` адресно — перечислить только нужные пути выбранного
   продукта (`docs/projects/<project-slug>/`,
   `.claude/skills/project-deep-dive-for-business/state/<project-slug>/`,
   `client-handoff/`).
6. `git commit -m "client-handoff: <UTC-ts>"` — пройти git-hook
   commit-msg, который проверяет Conventional Commits. Если формат
   ломается — сообщение должно быть `docs(handoff): client session
   <UTC-ts>` или подобное.
7. Лечь поверх свежего `main` и запушить: `git fetch origin && git rebase
   origin/main`. Первый push — `git push -u origin client`; последующие
   (rebase переписал историю) — `git push --force-with-lease origin client`
   (безопасный force: откажется, если на remote есть чужие коммиты).
   Remote-ветка ушла вперёд (другое устройство) → `git pull --rebase origin
   client`, снова `git rebase origin/main`, повторить push.
8. Удалить локально `state/<project-slug>/_session-log/<этой-ts>.md` —
   он уже уехал в transcripts.

### Если git-hook падает

Скилл **не** идёт по пути `--no-verify`. Вместо этого:

1. Поймать сообщение хука.
2. Через `AskUserQuestion`:

   > «При отправке возникла техническая загвоздка: <текст ошибки в
   > бизнес-форме>. Я попробую исправить и переотправить, или
   > сделайте паузу — аналитик разберётся.»

   - «Подожди, я свяжусь с аналитиком сам».
   - «Попробуй автоматически».
   - «Откатить и не отправлять».

3. По «попробуй» — починить корректным способом (например,
   переформатировать commit message по Conventional Commits) и
   повторить.

### После успешного push

1. Обновить state-заметки клиента: к каждой записи с `**жду
   аналитика**` добавить `**отправлено в ветку client (<UTC-ts>)**`.
2. Удалить `state/<project-slug>/_session-log/<этой-ts>.md`.
3. Сгенерировать текст для клиента — короткий, бизнес-языком:

   > «Готово. Аналитику передан черновик в ветке
   > `client`. Чтобы он быстрее включился, перешлите ему:
   >
   > ---
   > <готовый текст для мессенджера, 3-5 строк: что обсуждали, на
   > каких блоках застряли, что нужно от аналитика>
   > ---
   >
   > Можем продолжить или закончим на сегодня?»

## Формат `client-handoff/summary.md`

`summary.md` — **живой срез** для аналитика, не журнал. На каждом `--share`
**перезаписывается** под текущее состояние: закрытые вопросы уходят из
«Открытых», устаревшее «где остановились» заменяется, решённое не копится.
Forward-only — без «было/стало» и следов прошлых сессий. Цель: аналитик с
одного взгляда видит актуальную картину по продукту, без мусора.

```markdown
# Передача аналитику — продукт <название>

Обновлено: <YYYY-MM-DD> · Ветка: `client`

## Что обсудили

- <бизнес-формулировка, 1-2 строки на каждую тему>
- <…>

## Что заполнили / уточнили

- <бизнес-формулировка изменений, без slug — только актуальное>
- <…>

## Где остановились

- <текущая тема, что осталось>

## Открытые вопросы для аналитика

- <вопрос 1 — в бизнес-форме; только ещё не закрытые>
- <…>

## Где смотреть

- Заполнено в `docs/projects/<project-slug>/`:
  - <bullet с указанием файла + бизнес-описание изменения>
- Заметки клиента: `.claude/skills/project-deep-dive-for-business/state/<project-slug>/`
- Логи сессий: `client-handoff/transcripts/`
```

## Формат `client-handoff/transcripts/<YYYY-MM-DD>--<HH-MM>--<тема>.md`

Имя файла — **человекочитаемое**: дата, время и тема разделены **двойным
тире** `--` для читаемости (внутри части — одинарный дефис), напр.
`2026-06-04--14-25--produkt-onboarding.md`. Время в имени через дефис
(`14-25`, `:` запрещён в именах на Windows), в заголовке транскрипта — через
двоеточие (`14:25`). Дата-время делают имя уникальным.

Транскрипт — **верный лог сессии**: пишется последовательно, не
редактируется (в отличие от summary). Каждый блок несёт и **варианты,
которые скилл предлагал** (клиент их обычно теряет — а аналитику ценно
видеть, из чего выбирали), и итоговый ответ:

```markdown
# Сессия <YYYY-MM-DD> <HH:MM> · продукт <название> · <тема>

## <фаза / тема блока>
**Вопрос:** <текст вопроса, как был показан клиенту>
**Что предлагал:**
- <вариант 1>
- <вариант 2>
- <вариант 3>
- свой ответ
**Выбрано:** <вариант или свой текст клиента> — <пояснение, если было>

## <следующий блок>
…
```

Варианты берутся из буфера `_session-log` (там они уже записаны как
`### Опции`). Последовательно, forward-only.

## Текст для клиента (для пересылки аналитику)

Скилл генерит, чтобы клиент скопировал в мессенджер / email. Шаблон:

```
Привет! Я сегодня поработал над описанием продукта.

В репозитории <repo-name> есть ветка `client`, там черновики и
краткий пересказ.

Главное:
- разобрали <темы>;
- остановился на <теме>;
- нужна твоя помощь по <вопросам>.

Глянь когда сможешь.
```

Скилл подставляет реальные темы и вопросы. Без приветствия от имени
скилла («Я Claude…»). Текст должен звучать как от самого клиента —
он же его и копирует.
