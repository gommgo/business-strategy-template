# Формат заметок клиента

Память скилла-для-клиента — аналогична аналитической, но с двумя
дополнениями.

## Расположение

State **скоупится по продукту** — у каждого `<project-slug>` своя ветка,
чтобы разные продукты не сталкивались:

```
.claude/skills/project-deep-dive-for-business/state/<project-slug>/
├── vision.md
├── user/<slug>.md
├── capability/<slug>.md
├── boundary/<slug>.md
├── surface/<slug>.md
├── integration/<slug>.md
├── constraint/<slug>.md
├── market/<slug>.md
└── _session-log/
    └── <UTC-ts>.md
```

`_session-log/` — служебный буфер для накопления вопросов-ответов
сессии по этому продукту. Уезжает в
`client-handoff/transcripts/<YYYY-MM-DD>--<HH-MM>--<тема>.md` при `--share` и
удаляется локально.

## Шаблон kind-заметки

```markdown
---
kind: user
slug: nurse-partner
ref: docs/projects/<project-slug>/user.md#nurse-partner
---

## Открытые вопросы
- В скольких клиниках одновременно работает?
- (**жду аналитика**) Какие именно регуляторные документы применимы
  — нужна юридическая консультация.

## Что я имел в виду
- Когда я сказал «передать без переспросов» — имел в виду, что
  сейчас тратится 20 минут на согласование формата по телефону, не
  факт отправки.

## Что копать дальше
- После звонка с клиникой — уточнить, есть ли SMS-нотификации в их
  МИС.
```

## Frontmatter

Тот же, что у аналитического скилла:

| ключ | значение |
|---|---|
| `kind` | один из 8 |
| `slug` | равен slug в таблице |
| `ref` | путь к артефакту |

## Секции

### `## Открытые вопросы`

Те же правила, что в `../../project-deep-dive/references/state-format.md`,
плюс новый маркер:

- `**blocker**` — переход draft → stable заблокирован. Используется
  редко, в основном на самопроверке.
- `**жду аналитика**` — клиент сам не отвечает, ждёт аналитика. Это
  **специфика клиентского скилла**. При `--share` всё с этим
  маркером оказывается в summary как «открытые вопросы для аналитика».

### `## Что я имел в виду`

Уникальная для клиентского скилла. Сюда падают **переформулировки
самого клиента**: «когда я сказал X, я имел в виду Y». Это очень
ценный материал для аналитика — даёт авторский контекст без
интерпретации скилла.

Формат: маркированный список. Одна строка = одно уточнение.

### `## Доменные решения`

Та же секция, что у аналитического скилла. Используется реже —
клиент обычно не формулирует «решения» в их явной форме. Если возник
момент, когда клиент сказал «А, ясно, давайте сделаем как Y» —
скилл фиксирует здесь.

### `## Что копать дальше`

Та же секция. Локальные «следующие шаги», известные клиенту.

## `_session-log/<UTC-ts>.md`

Накопительный буфер текущей сессии. Формат:

```markdown
# Сессия <UTC-ts>

## Вопрос (скилл, фаза: <phase>)
<текст AskUserQuestion-вопроса>

### Опции, которые были показаны
- <опция 1>
- <опция 2>
- Other

### Ответ
<выбранная опция или Other-текст>

## Вопрос (скилл, фаза: <phase>)
<…>

### Ответ
<…>
```

Этот файл **служебный** — не редактируется руками. Каждый раунд
`AskUserQuestion` дописывает блок (вопрос + показанные опции + ответ).
При `--share` содержимое уезжает в
`client-handoff/transcripts/<YYYY-MM-DD>--<HH-MM>--<тема>.md` и файл удаляется.

Если `--share` не происходит, лог накапливается. При следующей сессии
— новый `<UTC-ts>.md`, старый продолжает лежать. Скилл это не чистит:
все логи уедут разом при следующем `--share`.

## Единый контекст (read-only)

Чтобы картина была единой, скилл read-only подтягивает соседние `state/`:
аналитика того же продукта (`../project-deep-dive/state/<project-slug>/`)
и верхнеуровневые слои — клиентский и аналитический режим
(`../business-deep-dive-for-business/state/`, `../business-deep-dive/state/`,
`../business-problem-deep-dive-for-business/state/`,
`../business-problem-deep-dive/state/`). Проектный слой — только по
текущему продукту (`<project-slug>`); чужие продукты не читаются (изоляция
продуктов). В чужой state **не пишет**. Аналитический скилл симметрично
read-only видит state клиента по этому продукту.

**Anti-leak (клиент-режим).** Прочитанное из кухни аналитика — тихий
контекст: открытые вопросы аналитика, доменные решения, что он считает
подозрительным, `slug/draft/stable` клиенту **не зачитываются**, только
переводятся в бизнес-язык. Клиенту по-прежнему видно лишь «закрыто / в
работе».

## Правила жизненного цикла

- **Создаётся** только когда есть что записать.
- **Перезаписывается** свободно.
- **Удаляется** (kind-заметки):
  - Все секции пустые → удалить файл.
  - Запись в артефакте удалена (каскад) → удалить файл.
- **`_session-log/<ts>.md`** — удаляется автоматически при `--share`
  (содержимое переезжает в transcripts).
- **Не аккумулировать** журнал «было/стало», даты, истории.
- Forward-only.

## Что НЕ хранить в заметке

- Историю изменений (git).
- Дубликаты содержимого таблицы.
- Личные данные клиента (контакты, e-mail, телефоны) — кроме случаев,
  когда это прямо относится к артефакту (например, контакт
  партнёра-интеграции).
- Внутренние термины и формулировки от модели «на всякий случай».
- Маркетинговую копию.
