# Фазы и режимы ведения сеанса

Скилл проактивно ведёт архитектора по фазам: смотрит, где в слое дыра, и
идёт туда. Здесь — детальные маршруты фаз и трёх режимов входа. Каждый шаг —
раунд `AskUserQuestion` (≤4 вопросов) → `Edit` → следующий раунд.

`<P>` = `docs/projects/<project-slug>`,
`TPL` = `docs/projects/_template/services`.

## bootstrap — слоя ещё нет

**Сигнал**: каталога `<P>/services/` не существует.

1. Скопировать формы из канона:

   ```
   mkdir -p <P>/services
   cp $TPL/service.md      <P>/services/service.md
   cp $TPL/platform.md     <P>/services/platform.md
   cp $TPL/architecture.md <P>/services/architecture.md
   ```

2. Раунд 1 `AskUserQuestion` — **«монолит или несколько сервисов?»**:
   - опция «Монолит — один `api`-сервис с несколькими контекстами» (норма,
     не упрощение; канон прямо это говорит);
   - опция «Несколько сервисов — границы уже понятны»;
   - опция «Не знаю — давай по контекстам/нагрузке разберём» (тогда
     стартуем с монолита, разбиение — осознанным решением позже);
   - Other.
   Ответ ложится первым пунктом в `architecture.md § Decisions`
   (формулировка обоснования — словами архитектора, через Other).
3. Если в `<P>` уже существуют доменные артефакты (папки
   `domains/<ctx>/` где-либо в проекте) — следующая фаза **partition**:
   каждому контексту нужен сервис-владелец
   (`services/<svc>/domains/<ctx>/`). Контекст вне сервиса — находка
   `/service-audit`, не валидное состояние.
4. Иначе — фаза **registry**: завести первый сервис (минимум один —
   инвариант слоя).

## registry — реестр `service.md`

По каждому заводимому сервису — раунд:

- **name** (Other) — человекочитаемое имя; `slug` скилл выводит сам
  (транслит, kebab-case, показ одной строкой «завожу как `<slug>`» — см.
  `.claude/rules/naming.md`).
- **description** (Other) — одно предложение, какую часть продукта несёт.
- **type** — опции по enum: `api` / `worker` / `gateway` / `edge` / `bot`
  (с подсказкой смысла из формы `service.md § Типы сервисов`; scheduled-джоба
  — `worker`, монолит — `api`).
- **surfaces** — множественный выбор из slug'ов `<P>/surface.md` + опция
  `—` (для `worker`/`gateway` обычно `—`). Поверхности, которой нет в
  реестре, отсюда не завести — `**blocker**` + `/project-deep-dive`.

После строки реестра — папка и паспорт:

```
mkdir -p <P>/services/<svc>
cp $TPL/_templates/service-readme.md <P>/services/<svc>/README.md
```

Заголовок и вводную фразу паспорта заполнить из name/description, остальные
секции оставить шаблонными → фаза passports.

Тест-критерий перед фиксацией строки (опции ✅/❌ из формы
`service.md § Тест-критерий`): «можно ли задеплоить и сломать его, не
трогая соседей?» — Postgres под заказы и Traefik на входе сервисами не
становятся.

## passports — паспорт каждого сервиса

Порядок секций запомнен, у архитектора не спрашивается; по каждой — свой
раунд (или несколько):

1. **Purpose** — «что делаем» / «чего не делаем» (оба — Other; «чего не
   делаем» — граница с соседним сервисом или платформой).
2. **Exposes** — бизнес-каталог функций наружу (sync):
   - есть ли функции вообще? Для `worker` норма `_N/A (worker — живёт на
     событиях и расписаниях)_;
   - на функцию: `name`/`description` (Other), `audience` — множественный
     выбор `` `surface:<slug>` `` (из `surface.md`) / `` `service:<slug>` ``
     (из реестра) / `` `integration:<slug>` `` (inbound, из
     `integration.md`); `backed-by` — выбор из существующих use-case'ов
     `domains/*/use-cases/` этого сервиса (`` `use-case:<ctx>.<Operation>` ``)
     либо `—`; нет нужного use-case'а — `**blocker**` +
     `/domain-deep-dive`.
   - Без протоколов и endpoint'ов — транспорт-детали в `Exposes` —
     anti-pattern.
3. **Owned Contexts** — какие контексты живут в сервисе:
   - выбор из существующих неприкаянных/чужих контекстов (тогда это
     partition/миграция — см. ниже) + «новый контекст» (Other → имя; папку
     и артефакты заводит `/domain-deep-dive`, здесь — строка таблицы +
     `**blocker**` «контекст объявлен — спроектировать»);
   - для `gateway`/`edge`/`bot` — `_N/A (no domains)_` (папка `domains/` у
     этих типов — anti-pattern).
4. **Dependencies** — что нужно от окружения; на каждое ребро:
   - вид ref'а — опции: «другой сервис проекта» (выбор из реестра) /
     «платформенный ресурс» (выбор из `platform.md` + «нужен новый» →
     фаза platform) / «внешняя система или сосед» (выбор из
     `integration.md`);
   - `nature` (Other) — зачем зависимость, бизнес-смыслом;
   - anti-pattern-проверка: sync-цепочка `service → service → service` в
     одном сценарии — опции «да, осознанно (обосную в Decisions)» /
     «переведём на события» (Other).
5. **Resources** — собственные ресурсы, «потребность + технология»:
   - `resource`-имя (Other), `type` — опции enum (`database` / `cache` /
     `search-index` / `vector-store` / `object-storage` / `other`),
     `technology` — Other (выбор архитектора: `postgres`, `redis`, …),
     `purpose` (Other);
   - stateless-сервис — `_нет (stateless service)_`;
   - **без операционки**: размер/версия/retention в ответе — подсветить и
     не записывать (runtime-механика — `<org>/infra`);
   - имя ресурса, совпадающее с ресурсом другого сервиса, — раунд
     anti-pattern «shared database?».
6. **Messaging** — асинхронный обмен:
   - на строку: `direction` — опции `produces` / `consumes`; `broker` —
     выбор из `platform.md` `type: message-broker` (+ «нужен брокер» →
     фаза platform); `topic` (Other); `event` — для `produces` выбор из
     `domains/<ctx>/events/` **этого** сервиса (produces пишет только
     владелец контекста события), для `consumes` — выбор из существующих
     `produces` соседей (та же пара `broker`+`topic`); `purpose` (Other);
   - не ходит в брокер — `_N/A_`.
7. **Workers** — фоновые воркеры внутри сервиса (процессы того же
   деплой-юнита): по каждому — `trigger` (`topic:<t>` — обязана быть парная
   строка `consumes` в `Messaging`; schedule — смысл словами, не cron) и
   `backed-by` (доменный use-case — опции из `domains/*/use-cases/`).
   Развилка через AskUserQuestion: «это воркер внутри сервиса или отдельный
   деплой-юнит?» — отдельный целиком на событиях/расписании → сервис
   `type: worker` в реестре, не строка Workers.
8. **Fronts** — только для `type: gateway`: `Integration` — выбор из
   `integration.md`; `Client` — ссылка на
   `_shared/integrations/<slug>/` (клиента авторит `/domain-deep-dive`;
   нет — `**blocker**`); `Normalizes` (Other). У остальных типов — `_N/A_`.
9. **Notes** — особенности, не влезшие в таблицы (Other), или `_нет_`.

После каждой секции — чек-лист `references/draft-stable.md`; все ✅ —
предложить промоушн паспорта.

## platform — реестр `platform.md`

Заводится **только под потребность паспортов**: ресурс, который не требует
ни один паспорт (`Dependencies` / `Messaging.broker`), — сирота. На запись:

- **name** (Other; `slug` выводит скилл), **description** (Other — зачем
  проекту, бизнес-смыслом);
- **type** — опции enum: `message-broker` / `api-gateway` / `cdn` /
  `object-storage` / `idp` / `other`;
- **technology** — Other (осознанный выбор архитектора: `nats` / `kafka` /
  `traefik` / `minio` / …);
- **provided-by** — опции: `own` (свой ресурс проекта; размещение потом —
  `infrastructure/placement.md`) / по опции на каждую существующую запись
  `docs/projects/infrastructure/shared-platform.md`
  (`` `shared:<slug>` ``) / «нужен общий ресурс бизнеса, которого ещё нет» —
  тогда `**blocker**`-вопрос в state + эскалация в
  `/infrastructure-deep-dive` (запись `shared-platform.md` — его
  территория), а здесь временно `own` или пусто по решению архитектора.

Тест-критерий (опции ✅/❌ из `platform.md § Тест-критерий`): «если убрать —
сломается обмен у нескольких сервисов, при том что проектировать в нём
нечего?» Как только в «гейтвее» появляется наша логика — это сервис
`type: edge`, раунд переквалификации.

## partition — контексты по сервисам

Два сценария:

**Раздача неприкаянных контекстов** (после bootstrap, когда домены уже
существуют): на каждый контекст — раунд «кто владелец?» с опциями по
`api`/`worker`-сервисам реестра + «нужен новый сервис» (→ registry).
Перенос папки + строка в `Owned Contexts`.

**Миграция** (перенос контекста из сервиса A в сервис B) — каскад:

1. Подтвердить операцию: «контекст `<ctx>` переезжает `<A>` → `<B>`?»
   (рефы `use-case:<ctx>.<Operation>` / `event:<ctx>.<Event>`
   сервисо-агностичны — доменные артефакты и внешние ссылки на них правок
   не требуют, владелец выводится из пути).
2. Перенести папку целиком:
   `<P>/services/<A>/domains/<ctx>/` → `<P>/services/<B>/domains/<ctx>/`.
3. Каскад по паспортам **обоих**:
   - `Owned Contexts`: строка уходит из A, появляется в B;
   - `Messaging`: `produces` событий контекста — только у владельца →
     строки переезжают из A в B; `consumes` A на собственные события
     `<ctx>` превращаются в честные consumes чужого (или удаляются —
     спросить);
   - `Exposes`: функции с `backed-by: use-case:<ctx>.*` переезжают в B
     (или остаются фасадом A с новым ребром `service:<B>` — спросить).
4. Каскад по **соседям**: каждый паспорт с `service:<A>` в `Dependencies`,
   потреблявший функции контекста, — раунд «перевесить на `service:<B>`?»;
   in-process reader'ы `<ctx>` внутри A теперь ходят в чужой сервис —
   `**blocker**` для `/domain-deep-dive` (in-process через границу сервиса
   запрещён).
5. Пересвести `architecture.md § Topology`; спросить про новую строку
   `Decisions` (почему переехал — словами архитектора).
6. Прогнать чек-лист по обоим паспортам; предложить `/service-audit`.

## architecture — свод

1. Прочитать все паспорта и реестры; **вывести** диаграмму `Topology`
   (mermaid `flowchart LR`): subgraph поверхностей → входной api-gateway
   (`platform.md`) → сервисы; сервисы ↔ брокер (пунктир, подписи —
   topic'и); gateway-сервисы → внешние интеграции. Узлы — только slug'и
   из `service.md` / `platform.md` / `surface.md` / `integration.md`;
   сплошная стрелка = sync (`Dependencies`), пунктирная = async
   (`Messaging`). Ребро, которого нет в паспортах, в диаграмму не попадает.
2. Показать диаграмму архитектору, раунд: «свод соответствует замыслу?»
   Расхождение = дыра в паспортах → вернуться в passports, не дорисовать.
3. **Decisions** — единственное, что здесь авторится: по решению на раунд
   (Other; falsifiable-формулировка: чем подтверждается, что станет
   сигналом пересмотра). Минимум: почему такие границы сервисов / почему
   монолит; каждая осознанная sync-связь; выбор своего/общего брокера.
4. **Flows** — опционально, 3–7 строк-иллюстраций или `_нет_`.

## cohesion — целостность слоя

1. Прогнать инварианты канона по слою: минимум один сервис; контекст ровно
   в одном сервисе и слаги контекстов уникальны в проекте; ресурс ровно у
   одного владельца; каждый `consumes` имеет продюсера; папки = реестр;
   deployment-agnostic.
2. По каждой дыре — раунд: чинить сейчас / `**blocker**` в state.
3. Добить промоушены `draft → stable` по чек-листу (по подтверждению).
4. Предложить `/service-audit <project-slug>`; при затронутых
   контекстах/интеграциях/размещении — `/cross-audit`; неразмещённые
   юниты — `/infrastructure-deep-dive`.

## Режимы

### A. Новая сущность

**Сигнал**: args = несуществующий `<service-slug>`, либо выбор «завести»
из сводки.

Маршрут: registry (строка + папка + паспорт из шаблона) → passports по
этому сервису → при появлении нужд — platform → чек-лист. Для записи
`platform.md` — фаза platform напрямую.

### B. Сырьё

**Сигнал**: args = свободный текст / приложение (транскрипт обсуждения
архитектуры, диаграмма, набросок, заметки).

1. Прочитать материал внимательно.
2. Извлечь кандидатов: сервисы (deploy-юниты), платформенные ресурсы,
   sync-рёбра, события/topic'и, ресурсы сервисов. Фильтр — anti-patterns
   канона (трафик-роутер без нашего кода → `platform.md`, не сервис;
   «общая БД» → разнести; наносервис на контекст → кандидат в монолит).
3. Показать план в чат:

   ```
   Из материала вижу:
   - 2 сервиса-кандидата: `orders` (api), `notifications` (worker);
   - 1 платформенный ресурс: брокер (nats?);
   - 1 кандидат НЕ-сервис: «traefik на входе» → platform (api-gateway);
   - 2 ребра: orders -. order-events .-> notifications; web → orders.
   Так?
   ```

4. Раунд `AskUserQuestion` — подтвердить план / корректировка через Other
   по каждой группе.
5. По подтверждению — stub'ы (строки реестров `status: draft`, паспорта из
   шаблона) + state-заметки «извлечено из сырья — уточнить <что>»
   (`**blocker**` там, где материал противоречил канону).
6. Выбрать через `AskUserQuestion`, что углубить первым → режим C.

Не объявлять извлечённое зафиксированным; не достраивать топологию,
которой в материале нет, «потому что обычно так делают».

### C. Углубление

**Сигнал**: args = существующий `<service-slug>` / `architecture` /
`platform`, либо выбор из сводки.

1. Прочитать артефакт целиком + state-заметку + соседей по рёбрам
   (паспорта из `Dependencies`, ресурсы из `platform.md`, события из
   `domains/*/events/`).
2. Найти: пустые/шаблонные секции; anti-pattern-подозрения (runtime-механика
   в Resources, транспорт в Exposes, shared database, sync-цепочка,
   `domains/` у gateway/edge/bot); битые рёбра; consumes без продюсера.
3. Раунд (≤4 вопросов) точечно по найденному: дыры — Other;
   anti-patterns — опции «да, переразбиваю» / «нет, вот почему» (Other);
   битые рёбра — «исправить на <варианты>» / «удалить» / «stub-сосед».
4. Применить через `Edit`; обновить state; зеркала соседей
   (produces ↔ consumes; Exposes провайдера ↔ Dependencies потребителя)
   — по подтверждению.
5. Чек-лист `references/draft-stable.md`; все ✅ — предложить промоушн;
   осталась дыра — следующий раунд; неотвечаемый `**blocker**` —
   зафиксировать, выйти, предложить другого кандидата.
