# swot-deep-dive

Формализация **LinkedSWOT** заказчика: `factor` (сильные/слабые стороны,
тренды/угрозы) → `bet` (стратегические ставки). Канон —
`docs/swot/README.md`. Между картиной бизнеса (`docs/business/`) и Картой
гипотез (`docs/hypothesis-map/`): факторы вырастают из профиля и
конкурентов, ставки дотягиваются (`promoted-to`) до цели или гипотезы.

Слой **многопроблемный**: реестр проблем — `docs/business/business-problem.md`
(одна строка = одна проблема), а каждая запись `factor`/`bet` несёт колонку
`business-problem` — массив slug-рефов на строки реестра (M:N: один фактор бизнеса
часто общий для нескольких проблем). **Проблема — первичное измерение
группировки**: заводя фактор или ставку, скилл всегда тегирует её
проблемой(ами). Все методологические инварианты считаются **в пределах
одной проблемы**.

Скилл ведёт сеанс через 3 фазы, структурированные вопросы
(`AskUserQuestion`), фиксирует контекст в своей ветке единого дерева
state оркестратора (`../entrypoint/state/swot/`), **не выдумывает
бизнес-формулировки**. Глубинная логика LinkedSWOT —
`references/methodology.md`.

## Доказательная база факторов — разведка AJTBD (read-only)

Факторы **не берутся из головы**: сильное трение клиента
(`ajtbd/segment-problem`, `strength` высок при низкой удовлетворённости
нанятым решением) — прямое evidence для `weakness`/`threat`; высокий
`segment.score` и работы без хорошего решения — для `strength`/`trend`.
Скилл может **read-only** читать `docs/ajtbd/*` (segment · segment-problem
· job · solution) и state соседних ajtbd-скилов как контекст. **Трения и
сегменты не выдумывает**; перенос их смысла в фактор — через
`AskUserQuestion`, как обычный promotion. Автозалива нет.

Трение клиента (`ajtbd/segment-problem`) ≠ проблема бизнеса
(`business/business-problem`): первое **питает доказательством** факторы и
строку реестра проблем, не подменяет её.

## Стейкхолдеры — evidence факторов и сверка стратегии (read-only)

Люди-решатели внутри заказчика (`docs/business/stakeholder.md`) часто **и
есть внутренние факторы SWOT**, а их стратегические взгляды задают рамку
ставок. Скилл **read-only** читает `stakeholder.md` (+ `stakeholder-map.md`)
и держит в голове два моста:

- **Человек-как-фактор.** Властный `champion` (`power: high`,
  `attitude: champion`) — кандидат в `strength` (сильный внутренний
  союзник); властный `blocker`/`skeptic` (`power: high`) — кандидат в
  `weakness`/`threat` (внутреннее сопротивление). При заведении фактора, у
  которого за спиной стоит конкретное лицо, предложить это **опцией** в
  `AskUserQuestion`, не выдумывая стойку.
- **Ставка не против ключевого лица.** Заводя `bet`, сверь её со
  `strategic-stance` властных стейкхолдеров: ставка, **противоречащая**
  стойке того, кто будет её санкционировать/финансировать (`power: high`),
  — стратегический риск (мертва на старте). Подними как подозрение, предложи
  переформулировать или явно отметить риск; не «причёсывай» молча.

**Стейкхолдеров и их стойку не выдумывает** — берёт из `business`-слоя
(заводятся через `/business-deep-dive`, фаза `stakeholders`). Сквозную
сверку роем делает `/cross-audit` (углы `stakeholder-factor` ·
`stakeholder-strategy`).

## Точки входа

| вызов | поведение |
|---|---|
| `/swot-deep-dive` | сводка по фазам + предложение следующего шага |
| `/swot-deep-dive <kind>` | завести новую сущность типа kind (режим A) |
| `/swot-deep-dive <kind>:<slug>` | углубить существующую запись (режим C) |
| `/swot-deep-dive <slug>` | найти slug; одиночный → C; конфликт kind → переспросить |
| `/swot-deep-dive <свободный текст / транскрипт>` | сырьё → разбор (режим B) |
| `/swot-deep-dive --phase <name>` | принудительно работать в фазе |

`kind` ∈ {`factor`, `bet`}.

`phase` ∈ {`factors`, `bets`, `cohesion`}.

## Что делать сразу при запуске

1. Прочитать `docs/swot/README.md` — освежить канон 2 kinds и
   методологические инварианты LinkedSWOT.
2. Прочитать `references/methodology.md` — устройство LinkedSWOT
   (квадранты, баланс факторов, изоморфизм ставки и зародыша гипотезы).
3. Прочитать `references/phases.md` — карту 3 фаз.
4. **Прочитать реестр проблем** `docs/business/business-problem.md` —
   строки-проблемы, по которым скоупятся факторы и ставки. Нет ни одной
   проблемы → подсказать завести через `/business-deep-dive business-problem`.
5. Если args пустые — **сводка по фазам** + `AskUserQuestion` с выбором
   следующего шага.
6. Если args указывают на сущность — определить kind и режим (A/B/C) по
   `references/workflow-patterns.md`.

## Сводка состояния (без args)

1. Прочитать `factor.md` + `bet.md` + реестр проблем
   `docs/business/business-problem.md`.
2. Перечислить **проблемы** (строки реестра); подсчитать `draft`/`stable`
   по `factor`/`bet`, разложив записи по `business-problem` (массив-реф).
3. Прочитать свою ветку `../entrypoint/state/swot/` и read-only остальное
   дерево (см. «Единый контекст») — собрать `**blocker**`-вопросы.
4. **Фазы считаются в пределах проблемы.** Если проблем несколько —
   сначала выбрать, по какой идём (`AskUserQuestion`), затем определить
   текущую фазу по записям, чей `business-problem` содержит выбранную:
   - нет факторов с этой проблемой → `factors`;
   - есть факторы, нет ставок → `bets`;
   - всё заполнено, есть draft/blocker → `cohesion`.
5. Вывести карту фаз (как в `references/phases.md`, раздел «Сводка фаз») —
   по выбранной проблеме; для остальных — краткая сводка «закрыта/в работе».
6. Через `AskUserQuestion` предложить: продолжить фазу / переключиться на
   другую проблему / перепрыгнуть фазу / разобрать сырьё.

## Фазы проработки

Скилл **проактивно** ведёт через 3 фазы. Полная карта — `references/phases.md`.
Фазы считаются **в пределах одной проблемы**; каждая заводимая запись
тегируется проблемой(ами) через `business-problem`:

| фаза | цель | артефакты |
|---|---|---|
| `factors` | факторы LinkedSWOT по 4 квадрантам, с опорой на трения AJTBD | `factor.md` |
| `bets` | стратегические ставки из пар факторов (≥1 внутр. + ≥1 внеш.), доведённые до карты | `bet.md` |
| `cohesion` | целостность SWOT проблемы + повышение draft → stable | оба |

Строится **набегающей волной** (неточно → уточняем), не водопадом.

## Три режима

См. `references/workflow-patterns.md`; обязательные поля и порядок
заполнения по kind — `references/field-checklists.md` (открыть в раундах
по слотам):

- **A. Новая сущность.** Args = `<kind>` или `<kind>:<новый-slug>`.
  Батч `AskUserQuestion` по `Критерии <kind>` из `docs/swot/<kind>.md`;
  опции — anti-patterns из `Что <kind> НЕ` того же файла и `Anti-patterns`
  README слоя; значения — через Other. Всегда спросить **к какой
  проблеме(ам) относится** (`business-problem` — массив строк реестра;
  опции — существующие проблемы + «новая, завести через `/business-deep-dive`»).
- **B. Сырьё.** Args = транскрипт / заметки. Извлечь кандидатов
  (factor/bet), определить, **о какой проблеме(ах)** материал, показать
  план, по подтверждению завести stub-строки с `business-problem`, углубить через C.
- **C. Углубление.** Args = `<kind>:<slug>`. Точечные вопросы по дырам и
  методологическим подозрениям (всё — в пределах проблем записи); чек-лист
  `draft → stable`.

## Стиль вопросов

См. `references/workflow-patterns.md`. Краткий канон:

- **Всегда через `AskUserQuestion`**, до 4 вопросов в раунде.
- **Опции** — для: anti-patterns; enum (`factor.area`); выбора
  существующего slug соседа (фактор для `bet.factors`, цель/гипотеза для
  `bet.promoted-to`); **выбора проблемы(ам)** для `business-problem` (существующие
  строки реестра + «новая проблема»).
- **Свободная форма (Other)** — для значений: `name`, `description`, текст
  фактора по шаблону квадранта, ставки «⟨действие⟩, чтобы ⟨ценность⟩».
- Бизнес-формулировки (текст фактора и ставки) даёт аналитик: это
  экспертиза бизнеса (`CLAUDE.md` §3), и догаданная формулировка стала бы
  ложным основанием стратегии. Anti-patterns как опции — да; сами тексты —
  нет.

## Память — своя ветка единого дерева

Весь аналитический state — **одно дерево** у оркестратора. Скилл своего
`state/` не держит: per-kind заметки пишет в **свою ветку**
`../entrypoint/state/swot/<kind>/<slug>.md` (`factor` · `bet`). Формат —
канон `../entrypoint/references/state-model.md`. Три опциональные секции:
`## Открытые вопросы` (опц. `**blocker**` — блокирует `draft → stable`),
`## Доменные решения`, `## Что копать дальше`. Forward-only. Файл/ветка
создаются по требованию; пустые секции — удалить.

**Единый контекст (read-only).** Скилл видит **всё дерево**
`../entrypoint/state/` — бизнес-слой (`business/` — профиль, конкуренты,
реестр проблем, стейкхолдеры — властные champion/blocker как evidence
факторов и стойка как рамка ставок), разведку AJTBD (`ajtbd/` — трения и
сегменты как evidence), Карту гипотез (`hypothesis-map/` — куда доводятся
ставки), срез
оркестратора (`index.md`/`threads/`) — плюс клиентский дом
`../entrypoint-for-business/state/` (правила — `cross-read.md`). **Своя
ветка — rw, чужое — read-only; в чужое не пишет.**

## Методологические инварианты (семантические, не slug-grep)

Связи **не валидируются slug-целостностью** — они семантические. Все
инварианты считаются **в пределах одной проблемы** (`business-problem`).
Методологические инварианты ловит рой `/swot-audit`. Скилл **в процессе**
держит их в голове и поднимает при углублении и cohesion:

- каждая запись `factor`/`bet` несёт непустой `business-problem` (массив строк
  реестра проблем);
- `bet.factors` балансирует ≥1 внутренний (`strength`/`weakness`) +
  ≥1 внешний (`trend`/`threat`);
- `bet.promoted-to` доведена до `goal`/`hypothesis` (`docs/hypothesis-map/`);
- ставка по форме «⟨действие⟩, чтобы ⟨ценность⟩» (есть «чтобы»/ценность);
- `factor`, не вошедший ни в одну `bet` (ни по одной из своих проблем), —
  повод поднять;
- правильный квадрант (`strength`/`weakness` — про устройство бизнеса;
  `trend`/`threat` — про мир; действие = это уже `bet`, не factor).

Сам скилл — **не аудитор**; в конце сессии предложит `/swot-audit` или
`/cross-audit`.

## Контракт `draft → stable`

См. `references/draft-stable.md`. Чек-лист после каждой правки: обязательные
слоты заполнены · `Критерии <kind>` подтверждены аналитиком · `Anti-patterns`
не нарушены · нет `**blocker**` в state. Все ✅ → предложить повышение через
`AskUserQuestion`. Скилл **не повышает сам**.

## Stub-сущности

Если копаемая сущность ссылается на ещё не существующий slug (ставка
доводится до цели, которой нет): завести stub-строку (для `bet.promoted-to`
— это сущность чужого слоя `docs/hypothesis-map/`, её заводит
`/hypothesis-map-deep-dive`; здесь — записать state-заметку «ставка
ждёт цель/гипотезу — завести в Карте гипотез», вернуться к исходной). Для
своего слоя (фактор, на который ссылается ставка) — завести stub-фактор
(`slug + name + description + business-problem + area + status=draft`, прочее `—`).

## Удаление сущности (каскад)

1. Прочитать `factor.md` + `bet.md` + свою ветку `../entrypoint/state/swot/`
   — найти семантические упоминания slug (особенно `bet.factors`).
2. Показать каскад. Через `AskUserQuestion` по каждому месту: «заменить на
   другой slug» / «удалить упоминание» / «оставить».
3. Применить пакетом. Удалить запись из файла и
   `../entrypoint/state/swot/<kind>/<slug>.md`.
4. Если удалён единственный внутренний/внешний фактор ставки — спросить,
   не нарушился ли баланс. Если удалена строка реестра проблем (это
   сущность чужого слоя `docs/business/`) — у записей, чей `business-problem`
   ссылался только на неё, спросить, к какой проблеме переотнести или
   удалить (запись без проблемы запрещена).

## Завершение сессии

1. Перечислить затронутые сущности (заведены/углублены/удалены/повышены).
2. Перечислить нерешённые `**blocker**`-вопросы.
3. Назвать текущую фазу и логичный следующий шаг.
4. Через `AskUserQuestion` предложить: `/swot-audit` (инварианты
   LinkedSWOT роем, по каждой проблеме) / `/hypothesis-map-deep-dive`
   (довести ставки до целей, метрик и гипотез) / `/cross-audit` (стыки с
   business — в т.ч. стейкхолдеры: `stakeholder-factor`/`stakeholder-strategy`
   — ajtbd и продуктами).
5. Если факторам не хватает доказательной базы (трений клиента) —
   подсказать, что трения и сегменты собираются в `docs/ajtbd/` через
   `/segment-deep-dive` и `/job-graph-deep-dive`.

Скилл **сам не вызывает** другие скилы — аналитик запускает.

## Границы

- Цели, метрики и гипотезы живут в `docs/hypothesis-map/`
  (`/hypothesis-map-deep-dive`), строки реестра проблем — в
  `docs/business/` (`/business-deep-dive business-problem`); здесь на них
  только ссылаются `bet.promoted-to` и колонка `business-problem`.
- Статус записи меняет аналитик: `draft → stable` — по его подтверждению,
  `stable → draft` скилл только подсвечивает.
- Пишет скилл в `docs/swot/` и свою ветку `../entrypoint/state/swot/`;
  остальное дерево state и клиентский дом — только чтение.
