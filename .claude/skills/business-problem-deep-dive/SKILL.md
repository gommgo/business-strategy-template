# business-problem-deep-dive

Формализация **бизнес-проблем** заказчика по строгой методологии:
**LinkedSWOT** (`factor` → `bet`) → **Карта гипотез** (`goal` · `metric`
· `subject` · `hypothesis` · `task`). Канон — `docs/business-problem/README.md`.
Между слоем «кто этот бизнес» (`docs/business/`) и «зачем продукт»
(`docs/projects/<slug>/`).

Слой **многопроблемный**: `frame.md` — **таблица проблем** (одна строка =
одна проблема), а каждая запись 7 kind несёт колонку `problem` — массив
slug-рефов на строки `frame` (M:N: фактор/субъект/метрика и т.п. часто
общие для нескольких проблем). **Проблема — первичное измерение
группировки**: заводя SWOT- или гипотезо-картовую запись, скилл всегда
тегирует её проблемой(ами). Все методологические инварианты считаются **в
пределах одной проблемы**. Связь с продуктом тоже M:N и ведётся авторски
на стороне продукта (`projects/<slug>/vision.addresses-problem`).

Скилл ведёт сеанс через 8 фаз, структурированные вопросы
(`AskUserQuestion`), фиксирует контекст в `state/`, **не выдумывает
бизнес-логику**. Глубинная логика обеих методологий — `references/methodology.md`;
дисциплина метрик-обязательств — `references/metric-spine.md`.

## Проблема бизнеса ≠ проблема клиента (не путать)

`frame` (строка) — это проблема **бизнеса заказчика** (его боль в
деньгах/времени/риске). Её **не** надо смешивать с `ajtbd/segment-problem`
— трением **клиента** заказчика с конкретным нанятым решением. Это две
разные сущности из двух соседних слоёв, и слово «проблема» в них значит
разное. Связь односторонняя: разведка AJTBD **питает** этот слой —
`segment-problem` (трение клиента) служит **доказательством** проблемы
бизнеса и SWOT-фактора, `segment` (группа клиентов по работам)
проявляется как `subject` (чьё поведение меняем). Заводя строку `frame`
или фактор, держи это различие: «проблема бизнеса» формулируется в его
терминах, трения клиента — лишь evidence под неё.

Скилл может **read-only** читать `docs/ajtbd/*` (segment · segment-problem
· job · solution) и state соседних ajtbd-скилов как контекст. **Трения и
сегменты не выдумывает**; перенос их смысла в свои артефакты (фактор,
строку `frame`, субъекта) — через `AskUserQuestion`, как обычный
promotion. Автозалива из `docs/ajtbd/` нет.

## Юридическая рамка (держать в голове всю сессию)

Мы гарантируем **доставку проекта на 100% по scope** — твёрдо. Метрики —
**совместный с бизнесом best-effort таргет**, не гарантия исхода. Поэтому
строгость метрик — ради **общей ясности и честного измерения**, не ради
суда. Граница «гарантируем / целимся / вне контроля» живёт в `frame.md`.
Скилл **никогда** не подаёт метрику как гарантию.

## Точки входа

| вызов | поведение |
|---|---|
| `/business-problem-deep-dive` | сводка по фазам + предложение следующего шага |
| `/business-problem-deep-dive <kind>` | завести новую сущность типа kind (режим A) |
| `/business-problem-deep-dive <kind>:<slug>` | углубить существующую запись (режим C) |
| `/business-problem-deep-dive <slug>` | найти slug; одиночный → C; конфликт kind → переспросить |
| `/business-problem-deep-dive <свободный текст / транскрипт>` | сырьё → разбор (режим B) |
| `/business-problem-deep-dive --phase <name>` | принудительно работать в фазе |

`kind` ∈ {`frame`, `factor`, `bet`, `goal`, `metric`, `subject`,
`hypothesis`, `task`}.

`phase` ∈ {`swot`, `bets`, `goal`, `metric`, `subject`, `hypothesis`,
`task`, `cohesion`}.

## Что делать сразу при запуске

1. Прочитать `docs/business-problem/README.md` — освежить канон 8 kinds,
   юр-рамку и методологические инварианты.
2. Прочитать `references/phases.md` — карту 8 фаз.
3. При работе с `factor`/`bet` — открыть `references/methodology.md`
   (LinkedSWOT). При работе с `goal`..`task` — тот же файл (Карта
   гипотез). При работе с `metric` — `references/metric-spine.md`.
4. Если args пустые — **сводка по фазам** (см. ниже) + `AskUserQuestion`
   с выбором следующего шага.
5. Если args указывают на сущность — определить kind и режим (A/B/C) по
   `references/workflow-patterns.md`.
6. Если `--phase` — открыть карту фазы.

## Сводка состояния (без args)

Скилл всегда даёт аналитику **карту, где он в методологии**, не просто
список draft-записей.

1. Прочитать `frame.md` (таблица проблем) + все 7 табличных файлов.
2. Перечислить **проблемы** (строки `frame`); подсчитать `draft`/`stable`
   по каждому kind, разложив записи по `problem` (массив-реф).
3. Прочитать `state/` (своё + read-only из
   `../business-problem-deep-dive-for-business/state/` и соседних слоёв,
   если есть — см. «Единый контекст») — собрать `**blocker**`-вопросы.
4. **Фазы считаются в пределах проблемы.** Если проблем несколько —
   сначала выбрать, по какой проблеме идём (`AskUserQuestion` «над какой
   проблемой работаем»), затем определить её текущую фазу по дереву (на
   записях, чей `problem` содержит выбранную):
   - `frame` пуст или у проблемы статус draft → рамка (часть фазы `swot`);
   - нет факторов с этой проблемой → `swot`;
   - нет ставок → `bets`;
   - нет целей → `goal`;
   - нет метрик → `metric`;
   - нет субъектов → `subject`;
   - нет гипотез → `hypothesis`;
   - нет задач → `task`;
   - всё заполнено, но есть draft/blocker → `cohesion`.
5. Вывести карту фаз (как в `references/phases.md`, раздел «Сводка фаз») —
   по выбранной проблеме; для остальных проблем дать краткую сводку
   «закрыта/в работе».
6. Через `AskUserQuestion` предложить: продолжить фазу выбранной проблемы /
   переключиться на другую проблему / завести новую проблему /
   перепрыгнуть фазу / разобрать сырьё.

## Фазы проработки

Скилл **проактивно** ведёт через 8 фаз. Полная карта — `references/phases.md`.
Кратко, по порядку методологии (SWOT → Карта гипотез):

Фазы считаются **в пределах одной проблемы** (строки `frame`); каждая
заводимая запись тегируется проблемой(ами) через `problem`:

| фаза | цель | артефакты |
|---|---|---|
| `swot` | строка проблемы в `frame` + факторы LinkedSWOT | `frame.md`, `factor.md` |
| `bets` | стратегические ставки из пар факторов | `bet.md` |
| `goal` | цели карты (критерий успеха без цифр) | `goal.md` |
| `metric` | измеримые метрики цели (baseline/target/атрибуция/приёмка) | `metric.md` |
| `subject` | субъекты влияния + мотивация | `subject.md` |
| `hypothesis` | гипотезы (если·то·потому что·тогда) | `hypothesis.md` |
| `task` | задачи проверки гипотез | `task.md` |
| `cohesion` | целостность карты проблемы + повышение draft → stable | все |

**SWOT — рекомендуемый, но не обязательный вход.** Если бизнес принёс
ясную цель, можно начать с `goal`; скилл через `AskUserQuestion`
спросит «почему сейчас?» и предложит до-насытить SWOT позже (см.
`references/phases.md`, «Перепрыгивание»). Строится **набегающей волной**
(неточно → уточняем), не водопадом.

## Три режима

См. `references/workflow-patterns.md`. Зеркалит project-deep-dive:

- **A. Новая сущность.** Args = `<kind>` или `<kind>:<новый-slug>`.
  Батч `AskUserQuestion` по `Критерии <kind>` из md-файла; опции —
  anti-patterns из `Что <kind> НЕ`; значения — через Other. Для kind ≠
  `frame` всегда спросить **к какой проблеме(ам) относится** (`problem` —
  массив строк `frame`; опции — существующие проблемы + «новая»).
- **B. Сырьё.** Args = транскрипт интервью / заметки. Извлечь
  кандидатов по слоям (factor/bet/goal/metric/subject/hypothesis/task),
  определить, **о какой проблеме(ах)** материал, показать план, по
  подтверждению завести stub-строки с `problem`, углубить через C.
- **C. Углубление.** Args = `<kind>:<slug>`. Точечные вопросы по дырам и
  методологическим подозрениям (всё — в пределах проблем записи); чек-лист
  `draft → stable`.

## Стиль вопросов

См. `references/workflow-patterns.md`. Краткий канон:

- **Всегда через `AskUserQuestion`**, до 4 вопросов в раунде.
- **Опции** — для: anti-patterns из `Что <kind> НЕ`; enum (`factor.area`,
  `metric.kind`, `metric.direction`, `subject.kind`); выбора
  существующего slug соседа; **выбора проблемы(ам)** для `problem`
  (существующие строки `frame` + «новая проблема»); теста-критерия (✅/❌).
- **Свободная форма (Other)** — для значений: `name`, `description`, текст
  фактора, ставки, цели, частей гипотезы (`if`/`then`/`because`/`so`),
  мотивации субъекта, полей метрики (`source`/`attribution`/`acceptance`).
- **Никогда** не выдумывать бизнес-формулировки. Anti-patterns как опции
  — да; сами тексты — нет. Это **священная экспертиза бизнеса** (см.
  `CLAUDE.md` §3).

## Память `state/<kind>/<slug>.md`

Заметки лежат **рядом со скиллом**:
`.claude/skills/business-problem-deep-dive/state/<kind>/<slug>.md`.
`frame` — табличный, поэтому и его заметки по проблеме лежат как
`state/frame/<problem-slug>.md`. См. `references/state-format.md`.
Три опциональные секции: `## Открытые вопросы` (опц. `**blocker**`),
`## Доменные решения`, `## Что копать дальше`. Forward-only. Пустые —
удалить.

Скилл может **read-only** смотреть
`../business-problem-deep-dive-for-business/state/` — что наработал
клиент — и state соседних ajtbd-скилов
(`../segment-deep-dive*/state/`, `../job-graph-deep-dive*/state/`) как
контекст по трениям и сегментам клиента. **Не пишет туда.**

## Методологические инварианты (семантические, не slug-grep)

В отличие от interface/screen, связи **не валидируются slug-целостностью**
— они семантические, как в project. Все инварианты считаются **в пределах
одной проблемы** (`problem`): запись с проблемой P замыкается на записи
той же P. Методологические инварианты ловит рой `/business-problem-audit`.
Скилл **в процессе** держит их в голове и поднимает при углублении и
cohesion:

- у каждой проблемы (строки `frame`) есть ≥1 `goal` — иначе она повисла;
- каждая запись 7 kind несёт непустой `problem` (массив строк `frame`);
- задача-сирота (`task` без `hypothesis`) запрещена;
- `hypothesis.so` бьёт в конкретную `metric` той же проблемы; `because`
  опирается на `subject.motivation`; «если» — наше воздействие-принцип,
  «то» — поведение субъекта;
- целевая `metric` без влияющей гипотезы (в пределах её проблемы) —
  мёртвая; у каждой целевой есть ≥1 `balancing` в той же проблеме;
- `bet.promoted-to` доведена до `goal`/`hypothesis`; `bet.factors`
  балансирует ≥1 внутренний + ≥1 внешний;
- `factor`, не вошедший ни в одну `bet` (ни по одной из своих проблем), —
  повод поднять.

Сам скилл — **не аудитор**; в конце сессии предложит `/business-problem-audit`
или `/cross-audit`.

## Контракт `draft → stable`

См. `references/draft-stable.md`. Чек-лист после каждой правки: обязательные
слоты заполнены · `Критерии <kind>` подтверждены аналитиком · `Что <kind>
НЕ` не нарушены · `Тест-критерий` ✅ · нет `**blocker**` в state. Все 5 ✅
→ предложить повышение через `AskUserQuestion`. Скилл **не повышает сам**.

## Stub-сущности

Если копаемая сущность ссылается на ещё не существующий slug (гипотеза
упомянула метрику, которой нет): завести stub-строку (`slug + name +
description/части + problem + status=draft`, прочее `—`; `problem` обычно
наследует проблему(ы) сущности-инициатора), записать state-заметку
«заведён как stub в контексте `<откуда>` — докопать в фазе `<phase>`»,
вернуться к исходной. См. SKILL project-deep-dive как образец механики.

## Удаление сущности (каскад)

1. Прочитать все 8 файлов + `state/` — найти семантические упоминания
   slug (особенно `bet.factors`, `bet.promoted-to`, `metric.goal`,
   `hypothesis.subject`/`metric`, `task.hypothesis`, а также любую запись,
   у которой удаляемый slug стоит в `problem`).
2. Показать каскад. Через `AskUserQuestion` по каждому месту: «заменить
   на другой slug» / «удалить упоминание» / «оставить».
3. Применить пакетом. Удалить запись из файла и `state/<kind>/<slug>.md`.
4. Если удалена единственная метрика цели — спросить, не пора ли
   пересмотреть `goal`. Если удалена строка `frame` — у записей, чей
   `problem` ссылался только на неё, спросить, к какой другой проблеме их
   переотнести или удалить (запись без проблемы запрещена).

## Завершение сессии

1. Перечислить затронутые сущности (заведены/углублены/удалены/повышены).
2. Перечислить нерешённые `**blocker**`-вопросы.
3. Назвать текущую фазу и логичный следующий шаг.
4. Через `AskUserQuestion` предложить: `/business-problem-audit`
   (инварианты методологии роем, по каждой проблеме) / `/cross-audit`
   (стыки с business, `docs/ajtbd/` и проектами `docs/projects/<slug>/`) /
   передать клиенту через `/business-problem-deep-dive-for-business`.
5. Если SWOT-факторам или строкам `frame` не хватает доказательной базы
   (трений клиента) или субъект не опёрт на сегмент — подсказать, что
   трения и сегменты собираются в `docs/ajtbd/` через `/segment-deep-dive`
   и `/job-graph-deep-dive` (запускает аналитик руками).

Скилл **сам не вызывает** другие скилы — аналитик запускает.

## Запреты

- Не редактировать таблицы (включая `frame.md` — таблицу проблем)
  вслепую — всегда сначала `Read`.
- Не выдумывать бизнес-формулировки (текст фактора, ставки, цели, частей
  гипотезы, мотивации, полей метрики). Anti-patterns как опции — да.
- **Не подавать метрику как гарантию.** Она best-effort таргет.
- Не повышать `draft → stable` без явного подтверждения аналитика; не
  понижать сам.
- Не аккумулировать историю в `state/` — forward-only.
- Не писать в `state/` соседнего (клиентского) скилла — только read-only.
- Не пушить и не коммитить. Коммит/push — гейт аналитика.
- Не вызывать другие скилы — предложить аналитику запустить руками.
