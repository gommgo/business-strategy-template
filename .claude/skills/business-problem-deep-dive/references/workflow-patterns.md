# Три режима ведения сеанса

Скилл выбирает режим по виду args. Зеркалит project-deep-dive.

## A. Новая сущность

**Сигнал:** args = `<kind>` или `<kind>:<новый-slug>`.

1. Прочитать `docs/business-problem/<kind>.md` целиком (`Критерии`,
   `Что НЕ`, `Тест-критерий`). Для factor/bet/goal..task — освежить
   `methodology.md`; для metric — `metric-spine.md`.
2. Раунд 1 `AskUserQuestion` — фундамент: `slug` (Other), `name` (Other),
   `description` (Other; для hypothesis вместо него — четыре части). Для
   kind ≠ `frame` — здесь же спросить `problem` (к какой проблеме(ам)
   относится; опции — существующие строки `frame` + «новая проблема»;
   M:N, можно несколько). Без `frame`-строки сначала завести проблему.
3. Записать строку со `status=draft`, `problem` проставлен, прочее `—`.
   Для `frame` — новая строка таблицы проблем.
4. Раунд 2+ — батч по доменным слотам kind (см. `field-checklists.md`).
   До 4 вопросов. Перемежать опции (anti-patterns / enum / выбор
   проблемы / соседи) и Other (значения).
5. Ссылка на несуществующий slug → **stub** (см. SKILL.md), продолжить.
6. Раунд по `Тест-критерий` (✅/❌ из примеров).
7. Чек-лист `draft-stable.md`. Все 5 ✅ → предложить stable.
8. Записать `state/<kind>/<slug>.md`, если есть что.
9. Предложить следующий шаг по `phases.md`.

## B. Сырьё

**Сигнал:** args = транскрипт интервью / заметки бизнеса.

1. Прочитать материал внимательно.
2. Определить, **о какой проблеме(ах)** материал — если в реестре
   `frame` подходящей строки нет, предложить завести проблему первой.
3. Извлечь кандидатов **только то, что прямо названо** (не угадывать),
   проставив каждому `problem`:
   - factor — что названо как сила/слабость/тренд/угроза;
   - bet — что предложено как «сделать X ради Y»;
   - goal — какой результат/успех назван;
   - metric — какие числа/KPI упомянуты;
   - subject — чьё поведение хотят изменить;
   - hypothesis — какая причинная идея «если/то» прозвучала;
   - task — какие проверки/эксперименты названы.
4. Показать план в чате, `AskUserQuestion` — подтвердить/поправить
   (в том числе привязку к проблеме).
5. Завести **stub'ы** с `problem`, создать state-заметки «извлечено из
   сырья — уточнить ⟨что⟩».
6. `AskUserQuestion` — какую углубить первой (по логике фаз) → режим C.

### Что НЕ делать в B

- Не объявлять извлечённое «зафиксированным» (это кандидаты).
- Не угадывать `motivation`, части гипотезы, поля метрики — только
  `name`/`description` близко к языку аналитика/бизнеса.
- Не выдумывать кандидатов, которых в материале нет.
- Не оставлять кандидата без `problem` — если проблема неясна, спросить,
  а не угадывать.

## C. Углубление

**Сигнал:** args = `<kind>:<slug>` существующей записи.

1. Прочитать строку + `state/<kind>/<slug>.md`. Отметить её `problem` —
   все проверки соседей идут в пределах этих проблем.
2. Прочитать соседей семантически **в пределах проблем записи** (для
   hypothesis — её subject и metric той же проблемы; для bet — её
   factors; для metric — её goal и какие гипотезы той же проблемы бьют).
3. Найти: пустой/невалидный `problem`; пустые обязательные слоты;
   подозрения по anti-patterns; методологические тупики в пределах
   проблемы (метрика без влияния, ставка-висяк, задача без гипотезы,
   «тогда» без метрики той же проблемы).
4. Раунд `AskUserQuestion` (до 4): дыры → Other; anti-pattern → «да/нет
   почему»; тупик → «связать с ⟨варианты⟩ / оставить, потому что Other».
5. Применить ответы; обновить state.
6. Чек-лист `draft-stable.md`. Все 5 ✅ → предложить stable.
7. Осталась дыра/подозрение → следующий раунд.

## Стиль вопросов

### Когда давать опции

| ситуация | формат |
|---|---|
| anti-pattern из `Что <kind> НЕ` | две опции «соответствует / не соответствует (Other почему)» |
| enum (`factor.area`, `metric.kind`, `metric.direction`, `subject.kind`) | по опции на значение |
| привязка к проблеме (`problem`) | по опции на каждую строку `frame` (можно несколько) + «новая проблема» (Other) |
| тест-критерий | опции из примеров ✅/❌ |
| выбор существующего slug соседа | по опции на каждого + «нужен новый» (Other) |
| метод атрибуции метрики | опции из списка `metric-spine.md` |
| перепрыгивание фазы | две-три опции «потому что X/Y/Other» |

### Когда только Other (значения)

`name`, `description`, текст фактора, ставки «⟨действие⟩, чтобы ⟨ценность⟩»,
цели, четыре части гипотезы, `motivation` субъекта, поля метрики
`source`/`attribution`/`acceptance`/`evidence`, любой ещё не существующий
slug. **Это священная экспертиза бизнеса — не выдумывать.**

### Чего не делать

- Не предлагать «образцы» доменных формулировок от себя. Примеры в md —
  иллюстрация канона, не варианты для текущего проекта.
- Не более 4 вопросов в раунде.
- Не закрывать сессию без чек-листа хотя бы по одной правленой сущности.
