# 8 фаз формализации бизнес-проблемы

Скилл ведёт аналитика по фазам как по карте: всегда видно, где мы, что
закрыто. **Порядок — рекомендация, не закон.** Порядок следует методологии:
LinkedSWOT (`swot` → `bets`) → Карта гипотез (`goal` → `task`) → `cohesion`.
Строим **набегающей волной** — неточно, потом уточняем.

Слой **многопроблемный**: `frame` — таблица проблем. Фазы 2-8 считаются
**в пределах одной проблемы** (строки `frame`): сначала выбираем, по какой
проблеме идём, потом смотрим её дерево. Каждая заводимая запись тегируется
проблемой(ами) через `problem` (массив строк `frame`, M:N).

## Карта фаз

### 1. `swot` — строка проблемы + факторы

**Триггер:** проблемы (строки `frame`) ещё нет или у выбранной статус
draft, либо нет факторов с её `problem`.

**Цель:** завести строку проблемы в таблице `frame` — границу
«гарантируем/целимся/вне контроля» — затем собрать факторы LinkedSWOT из
картины бизнеса (`docs/business/`), тегируя каждый фактор проблемой(ами).

**Что копать:**
- Проблема в терминах бизнеса (деньги/время/риск), не решения. Если
  проблем несколько — каждая отдельная строка `frame`.
- Факторы по 4 областям: сильные/слабые (про устройство бизнеса),
  тренды/угрозы (про мир). Формулировка по шаблону квадранта. К какой
  проблеме(ам) фактор относится (`problem`) — один фактор бизнеса часто
  общий для нескольких проблем.

**Подтянуть доказательства из AJTBD (read-only).** Прежде чем спрашивать
факторы и формулировать строку проблемы, заглянуть в `docs/ajtbd/` (read-only):
- `segment-problem` — трения клиента с нанятыми решениями (`strength`
  1–10). Сильное трение при низкой `satisfaction`/`price-value-fit`
  соответствующего `solution` — это **доказательство** SWOT-фактора
  (часто `weakness`/`threat`) и опора строки `frame`. Агрегированные
  трения по проблеме — её evidence.
- Это **не** проблема бизнеса (`frame`), а трение **клиента** (см.
  «Проблема бизнеса ≠ проблема клиента» в SKILL.md). Перенос смысла
  трения в фактор/строку `frame` — через `AskUserQuestion`, не автозаливом.
  Трения не выдумывать: нет данных AJTBD — спросить аналитика, а при
  углублении подсказать `/segment-deep-dive` / `/job-graph-deep-dive`.

**Анти-паттерны:** проблема в терминах фич; действие в формулировке
фактора (это `bet`); слабость в графе угроз; метрика-как-гарантия в frame;
фактор без `problem`; фактор/строка `frame` без опоры на трения клиента,
когда AJTBD-данные есть; подмена проблемы бизнеса трением клиента.

**Переходы после:** `bets` — перебрать пары факторов проблемы в ставки.

### 2. `bets` — стратегические ставки

**Триггер:** есть факторы, нет ставок.

**Цель:** из пар факторов (≥1 внутренний + ≥1 внешний) родить ставки
«⟨действие⟩, чтобы ⟨ценность⟩».

**Что копать:** приём «если сила A, а тренд B — как A раскрыть в условиях
B». Баланс лево/право. Куда ставка доводится (`promoted-to`).

**Анти-паттерны:** ставка без опоры на факторы; только внутренние/только
внешние; ставка-фича без «чтобы».

**Переходы после:** `goal` — приоритетную ставку довести до цели.

### 3. `goal` — цели карты

**Триггер:** есть ставки, нет целей.

**Цель:** критерий успеха **без цифр**, выросший из приоритетной ставки.

**Что копать:** «по каким критериям поймём, что достигли?» + шатание
(утрировать, отбросить часть, щупать границу, «зачем вам этот результат?»).

**Анти-паттерны:** цифра внутри цели; задача вместо цели; цель без метрики.

**Переходы после:** `metric` — навесить измеримость.

### 4. `metric` — метрики цели

**Триггер:** есть цель, нет метрик. Ядро слоя — см. `metric-spine.md`.

**Цель:** метрики, однозначно показывающие достижение цели: baseline +
target, источник истины, атрибуция, критерий приёмки, guardrail. `problem`
метрики обычно совпадает с проблемой её цели.

**Что копать:** «какие метрики однозначно покажут достижение? текущее/
желаемое? опережающая/запаздывающая? что НЕ ухудшить (balancing)?
откуда число? как докажем наш вклад? что считаем приёмкой?».
`current` берётся из `business/current-metric.md`.

**Анти-паттерны:** бинарная; без baseline; без источника; без guardrail
(в пределах проблемы); **метрика как гарантия**.

**Переходы после:** `subject` — через чьё поведение двигаем.

### 5. `subject` — субъекты влияния

**Триггер:** есть метрики, нужно понять, чьё поведение их двигает.

**Цель:** субъекты (носители самодвижения) + мотивация (боли/желания).
Негативный субъект — если есть противодействие.

**Что копать:** «чьё поведение изменить, чтобы двинулась метрика?» (не
исполнитель). «Какие боли/желания?» + пять «ну и что?» до корневой.

**Связь с AJTBD-сегментом (read-only).** Субъект влияния семантически
вырастает из `ajtbd/segment` — группы клиентов по бандлу работ. Заводя
или углубляя субъект, заглянуть в `docs/ajtbd/segment.md` (read-only) и
через `AskUserQuestion` предложить связать субъект с конкретным сегментом
(опции — существующие сегменты + «другой/без сегмента»); мотивация
субъекта опирается на success-criteria сегмента и его трения
(`segment-problem.drivers`/`barriers`), не выдумывается. Нет сегментов —
подсказать `/segment-deep-dive` (запускает аналитик). Сегмент ≠ субъект:
сегмент — рынок/клиент, субъект — чьё поведение мы двигаем под метрику.

**Анти-паттерны:** исполнитель вместо субъекта; субъект без мотивации;
система без воли; субъект, оторванный от сегмента, когда AJTBD-данные есть.

**Переходы после:** `hypothesis` — на каждую боль/желание гипотеза.

### 6. `hypothesis` — гипотезы

**Триггер:** есть субъект с мотивацией, нет гипотез.

**Цель:** гипотезы в 4 частях (если·то·потому что·тогда→metric).

**Что копать:** «„если“ — принцип или уже задача? „то“ — поведение
субъекта? „потому что“ на его боли? „тогда“ — на какую метрику и как?».

**Анти-паттерны:** конкретная задача в «если»; «тогда» не о метрике;
пустое «потому что»; запрос на анализ вместо гипотезы.

**Переходы после:** `task` — под приоритетные гипотезы задачи.

### 7. `task` — задачи проверки

**Триггер:** есть гипотезы, нет задач.

**Цель:** активности, которыми проверяем гипотезы. Каждая привязана к
гипотезе (сирота запрещена).

**Что копать:** «чем проверим эту гипотезу? эксперимент/замер/пилот? к
какой гипотезе крепится?».

**Анти-паттерны:** задача-сирота; инженерный тикет реализации; задача как
цель.

**Переходы после:** `cohesion`.

### 8. `cohesion` — целостность

**Триггер:** все kinds выбранной проблемы имеют записи, фокус —
целостность её карты.

**Цель:** проверить инварианты методологии **в пределах проблемы** (см.
README слоя), повысить проходящие чек-лист записи `draft → stable`,
подсветить подозрения (проблема без цели, метрика без влияния, фактор без
ставки, ставка-висяк, запись без `problem`), предложить
`/business-problem-audit` и `/cross-audit`, передать цель/метрику/субъект
в проект(ы) `docs/projects/<slug>/` (связь проблема↔проект — M:N,
авторски на стороне продукта через `vision.addresses-problem`).

**Анти-паттерны:** принудительный stable у незрелых; «красный путь»
брошен на полпути (детализировали зелёную цепочку); проблема, оставшаяся
без единой цели.

## Сводка фаз для UI

Сводка — **по выбранной проблеме**; для остальных проблем даём строку
«закрыта / в работе».

```
Проблема: paid-outflow (1 из 2)
Фазы:
  ✅ swot        — строка frame stable, 6 факторов
  ✅ bets        — 3 ставки
  🔄 goal        — 1 draft (текущая)
  ⏳ metric
  ⏳ subject
  ⏳ hypothesis
  ⏳ task
  ⏳ cohesion

Прочие проблемы:
  🔄 slow-onboarding — в работе (фаза bets)
```

✅ — закрыта (≥1 stable, нет blocker); 🔄 — текущая; ⏳ — не начата.

## Перепрыгивание

SWOT — рекомендуемый, не обязательный вход. Если бизнес принёс ясную
цель — `AskUserQuestion`: «Перепрыгнуть в `goal`, минуя SWOT — почему
сейчас?» (опции: «бизнес уже дал ясную цель», «срочное решение», «SWOT
до-насытим позже», Other). Даже при перепрыгивании строка проблемы в
`frame` нужна — цель и метрика тегируются её `problem`. Ответ →
`state/goal/_phase-jump.md` как доменное решение. Скилл напоминает: без
SWOT ставка может оказаться необоснованной — стоит вернуться и до-насытить.
