# Лучи проверки business-problem-audit

Каждый луч — отдельный угол семантической проверки инварианта
методологии. Один луч = один агент. Запускаются параллельно. Структура:
**Файлы** · **Применим если** · **Что искать** · **Промпт-добавка**.

Слой **многопроблемный**: `frame.md` — таблица проблем (одна строка =
одна проблема), каждая запись 7 kind несёт колонку `problem` (массив
строк `frame`, M:N). **Все лучи считают инвариант в пределах одной
проблемы**: запись с проблемой P учитывается вместе с записями той же P,
а нарушение помечается полем `problem`. Луч проходит по каждой строке
`frame` отдельно (или по одной, если задан scope).

## problem-goal

**Файлы:** `frame.md`, `goal.md`.
**Применим если:** в `frame` есть хотя бы одна строка (проблема).

**Что искать:**
- `error`: строка `frame` (проблема), на которую не ссылается ни одна
  `goal` через `problem`. Проблема без цели — повисла, её нечего
  раскрывать в метрики.

**Промпт-добавка:**
```
frame.md — таблица проблем. Для КАЖДОЙ строки frame проверь: есть ли хотя
бы одна goal, чей массив problem содержит этот problem-slug? Нет → error
«проблема без цели», в finding укажи problem = этот slug.
```

## problem-tag

**Файлы:** все 7 табличных (`factor`, `bet`, `goal`, `metric`, `subject`,
`hypothesis`, `task`), `frame.md`.
**Применим если:** есть хотя бы одна запись 7 kind.

**Что искать:**
- `error`: запись 7 kind с пустым `problem` (`—`) — вне реестра, непонятно,
  какой проблемы касается.
- `error`: запись, чей `problem` ссылается на slug, которого нет в таблице
  `frame` (несуществующая проблема).

**Промпт-добавка:**
```
У каждой записи factor/bet/goal/metric/subject/hypothesis/task колонка
problem — непустой массив slug-рефов на существующие строки frame. Найди
записи с пустым problem (error) или ссылкой на отсутствующую в frame
проблему (error). В finding укажи refs на запись.
```

## task-orphan

**Файлы:** `task.md`, `hypothesis.md`.
**Применим если:** есть задачи.

**Что искать:**
- `error`: задача без привязки к гипотезе (`task.hypothesis = —` или
  ссылается на несуществующую/несоответствующую по смыслу гипотезу).
  Задача-сирота запрещена методологией (ресурсный фильтр).

**Промпт-добавка:**
```
Каждая задача (task) обязана проверять конкретную гипотезу. Для каждой
task: есть ли гипотеза, которую она по смыслу проверяет? Нет → error.
Также: задача, похожая на инженерный тикет реализации (а не на проверку
гипотезы), → warning. В finding укажи problem(ы) задачи.
```

## hypothesis-shape

**Файлы:** `hypothesis.md`, `subject.md`, `metric.md`.
**Применим если:** есть гипотезы.

**Что искать:**
- `error`: «тогда» (`so`/`metric`) не ссылается на существующую метрику
  цели **той же проблемы** — нечем оценить.
- `error`: «если» описывает действие **субъекта**, а не наше воздействие;
  или «то» не про поведение субъекта.
- `warning`: «потому что» (`because`) не опирается на `subject.motivation`
  (нет корреляции с болями/желаниями).
- `warning`: «если» — конкретная задача, а не принцип (преждевременная
  конкретизация).
- `error`: запрос на анализ вместо гипотезы («нужно собрать данные»).

**Промпт-добавка:**
```
Формат гипотезы: ЕСЛИ <наше воздействие-принцип> ТО <поведение субъекта>
ПОТОМУ ЧТО <на мотивации субъекта> ТОГДА <метрика цели>. Проверь каждую
часть семантически против subject.motivation и metric. «Тогда» должно
бить в метрику ТОЙ ЖЕ проблемы, что у гипотезы. Перечисли конкретные
нарушения, в каждом finding укажи problem гипотезы.
```

## metric-influence

**Файлы:** `metric.md`, `hypothesis.md`, `goal.md`.
**Применим если:** есть метрики.

**Что искать:**
- `error`: целевая метрика (`kind` ≠ balancing), в которую не бьёт ни
  одна гипотеза **той же проблемы** («тогда» ни одной гипотезы её не
  упоминает) — мёртвая.
- `error`: бинарная метрика как результат; метрика без `current`
  (baseline) или без `source`.
- `warning`: метрика-цель без привязки к существующей `goal`.

**Промпт-добавка:**
```
Для каждой целевой метрики: какие гипотезы ТОЙ ЖЕ проблемы на неё влияют
(через «тогда»)? Ни одной → error «метрика без влияния». Проверь baseline
(current), источник истины (source), небинарность. Балансирующие
(kind=balancing) влияния не требуют — их удерживают. В finding укажи
problem метрики.
```

## guardrail

**Файлы:** `metric.md`, `goal.md`.
**Применим если:** есть целевые метрики.

**Что искать:**
- `warning`: целевая метрика без хотя бы одной балансирующей
  (`kind=balancing`) **в той же проблеме** — можно «улучшить одно,
  сломать другое».

**Промпт-добавка:**
```
У каждой целевой метрики (kind=leading/lagging, direction=up/down) должна
быть ≥1 балансирующая (kind=balancing, direction=hold) В ТОЙ ЖЕ проблеме,
закрывающая очевидный способ «сжульничать». Нет → warning, назови, какой
способ обхода открыт, и укажи problem.
```

## bet-promotion

**Файлы:** `bet.md`, `factor.md`, `goal.md`, `hypothesis.md`.
**Применим если:** есть ставки.

**Что искать:**
- `warning`: ставка не доведена до карты (`promoted-to = —`) — мёртвый
  мост.
- `warning`: ставка без баланса факторов (нет ≥1 внутреннего +
  ≥1 внешнего в `factors`).
- `error`: формат ставки не «⟨действие⟩, чтобы ⟨ценность⟩» (нет «чтобы»/
  ценности).

**Промпт-добавка:**
```
Ставка — мост SWOT→карта. Проверь: доведена ли до goal/hypothesis
(promoted-to); балансирует ли факторы (≥1 внутренний strength/weakness +
≥1 внешний trend/threat); есть ли «чтобы» (ценность). Перечисли нарушения,
в каждом finding укажи problem(ы) ставки.
```

## factor-usage

**Файлы:** `factor.md`, `bet.md`.
**Применим если:** есть факторы.

**Что искать:**
- `hint`: фактор, не вошедший ни в одну ставку (`bet.factors`) **ни по
  одной из своих проблем**.
- `warning`: фактор в неправильном квадранте — действие в формулировке
  (это `bet`), слабость в `threat`, угроза как внутренний дефект.

**Промпт-добавка:**
```
Стороны (strength/weakness) — про устройство бизнеса; тренды/угрозы — про
мир; любое действие — это уже bet. Проверь квадрант каждого фактора по
смыслу. Фактор может работать на несколько проблем (массив problem):
проверь, использован ли он хотя бы в одной ставке (по любой из своих
проблем); если нет вовсе — hint. В finding укажи problem(ы) фактора.
```

## goal-shape

**Файлы:** `goal.md`, `metric.md`, `task.md`.
**Применим если:** есть цели.

**Что искать:**
- `warning`: цель с цифрой внутри (цифра должна быть в `metric`).
- `warning`: задача вместо цели («внедрить X» — активность).
- `error`: цель без единой метрики (нет `metric`, ссылающейся на цель).

**Промпт-добавка:**
```
Цель — критерий успеха без цифр, состояние мира (не активность). Проверь:
нет ли цифр в формулировке (должны быть в metric); не активность ли это
(тогда задача); есть ли ≥1 метрика на цель. В finding укажи problem(ы)
цели.
```

## frame-guarantee

**Файлы:** `frame.md` (таблица проблем), `metric.md`.
**Применим если:** в `frame` есть хотя бы одна строка.

**Что искать:** для каждой строки `frame` (проблемы):
- `error`: метрика подана как **гарантия** (в колонке `target`/`guarantee`
  строки или формулировке метрики этой проблемы) — нарушение юр-рамки
  (метрика = best-effort таргет).
- `warning`: в строке смешаны `guarantee` (доставка по scope) и `target`
  (метрики best-effort); пустая колонка `out-of-control`.

**Промпт-добавка:**
```
frame.md — таблица проблем, колонки slug·name·problem·guarantee·target·
out-of-control·scope·status. Юр-рамка: гарантируем доставку проекта по
scope (guarantee); метрики (target) — best-effort, НЕ гарантия. Для
КАЖДОЙ строки: найди, где метрика обещана как гарантия результата; проверь,
что guarantee и target не смешаны и out-of-control заполнен. В finding
укажи problem = slug строки.
```

## subject-selfmotion

**Файлы:** `subject.md`, `hypothesis.md`.
**Применим если:** есть субъекты.

**Что искать:**
- `error`: исполнитель/сотрудник как субъект (не носитель самодвижения —
  тот, кто делает задачу, а не тот, чьё поведение меняем).
- `warning`: субъект без `motivation` (нечем питать «потому что» гипотез).

**Промпт-добавка:**
```
Субъект — носитель собственной воли, чьё поведение меняем; не исполнитель
задачи. Проверь каждого: это тот, чьё поведение двигает метрику, или
исполнитель? Есть ли мотивация (боли/желания)? В finding укажи problem(ы)
субъекта.
```

## Порядок лучей

Полный прогон: `problem-tag` → `frame-guarantee` → `problem-goal` →
`factor-usage` → `bet-promotion` → `goal-shape` → `metric-influence` →
`guardrail` → `subject-selfmotion` → `hypothesis-shape` → `task-orphan`
(сначала валидность привязки к проблемам и рамка, затем вниз по причинной
цепи карты — всё per-problem). `--quick` — `problem-goal`, `task-orphan`,
`hypothesis-shape`, `metric-influence`.
