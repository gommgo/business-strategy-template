# Чек-лист `draft → stable`

После каждой правки — пункты ниже. Все ✅ → предложить повышение через
`AskUserQuestion`. **Скилл не повышает сам.**

1. **Обязательные слоты заполнены** (см. `field-checklists.md`).
   Опциональные — `—`.
2. **`Критерии segment` подтверждены** аналитиком через `AskUserQuestion`
   (бандл: ровно одна Big Job + ≥1 Core Job; общие критерии успеха;
   различимый признак).
3. **«Что segment НЕ» не нарушены** — anti-patterns проверены, ❌
   (демография; одна работа/должность/индустрия сама по себе; персона
   продукта; «все клиенты»; ноль/несколько Big Job).
4. **`Тест-критерий` ✅.**
5. **Score вычислим** — есть все четыре компонента (важность ·
   частотность · размер · удовлетворённость), прослежены к
   research/интервью; `score` записан с обоснованием.
6. **Факт прослежен до источника** — бандл, критерии и компоненты Score
   прослеживаются до research-отчёта или транскрипта интервью. Нет
   `**blocker**` в state.

Все ✅ → `AskUserQuestion`: «Повышаем `segment:<slug>` в stable?» По «да»
— `status: draft → stable`.

## Особое для этого слоя

- Сегмент не stable без **вычислимого Score** (все компоненты) — это ядро
  методологии приоритизации.
- Сегмент не stable, если **размер** не подтверждён количественником /
  кабинетной аналитикой (качественные интервью размер не дают) — оставить
  `**blocker**`.
- Запись на основе **неподтверждённого** web-research остаётся `draft`,
  пока аналитик не подтвердил факт.
- Бандл (`core-jobs` + `big-job`) на этом слое — гипотезы-stub'ы в
  `job.md`; их **полная** проработка (рёбра, CPR, типы) идёт в
  `/job-graph-deep-dive` и не блокирует stable сегмента, но Big Job и ≥1
  Core Job должны быть названы.

## Понижение

Скилл сам не понижает — подсвечивает и предлагает через `AskUserQuestion`.

## Когда нельзя пройти — нормально

Нужен ещё research / количественник на размер / живые интервью
(`/jtbd-interview`) → закрыть `draft`, оставить `**blocker**`, предложить
следующий шаг.
