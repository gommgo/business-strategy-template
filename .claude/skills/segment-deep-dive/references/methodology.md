# Методология AJTBD: сегмент (держать в голове)

Глубинная логика, которую скилл держит **в голове** в процессе и
поднимает при кластеризации и cohesion (как `hypothesis-map-deep-dive`
держит инварианты методологии своего слоя). Скилл — **не аудитор**;
инварианты слоя ловит рой `/ajtbd-audit`.

## Что такое сегмент

> Сегмент = люди или компании, объединённые **общей работой** (не
> демографией, не болью, не решением).

Держится на трёх опорах:
- **бандл работ** — 1–4 **Core Jobs** + ровно **одна Big Job**;
- **общие критерии успеха** — по чему судит «достаточно хорошо» (быстро /
  дёшево / безопасно / статус / низкий шум);
- **различимый воспроизводимый признак** — можно сказать, кто в сегменте,
  по контексту и работам.

Одна и та же Core Job при **разных** критериях успеха — это **разные**
сегменты (студент и предприниматель про «добраться из A в B» хотят
разного).

**Главная ошибка** — галлюцинировать, что знаем сегменты. Поиск сегмента
— поиск *known unknown*. Всегда стартуем с позиции «сегментов может не
быть». Антипаттерн «влюбиться в фичу/гипотезу» — мозг саботирует разведку.

## Уровни и типы работ (для гипотез)

На этом слое работы — **гипотезы** (stub'ы в `job.md`); полный граф
строит `/job-graph-deep-dive`. Но уровень и тип важны уже для бандла:

- **`big`** — верхняя мотивация, не меняется десятилетиями («комфортно
  проводить выходные»). Ровно одна на сегмент.
- **`core`** — то, за что платят, что решение завершает целиком («купить
  экипировку»). Здесь покупка. 1–4 на сегмент.
- **`low`** — низкоуровневые шаги; для сегментации не нужны (важны для
  UX/графа).

Типы (определяют будущую стратегию, размечаются в графе): разовые ·
последовательные · частотные (двигатель LTV) · виральные · налоговые
(издержки, можно «убить») · **ложные** (85 lvl — проверочный вопрос «а
что вы уже делали для этого?»; «похудеть к лету» часто ложная).

## Формула Score

```
Score = важность × частотность × размер × (10 − удовлетворённость решением)
```

| компонент | что это | откуда |
|---|---|---|
| **важность** | субъективный приоритет работы (X/10) | интервью/research |
| **частотность** | как часто выполняется (раз/период) | интервью/research |
| **размер** | сколько людей/компаний имеют работу | количественная валидация / кабинетная аналитика |
| **10 − удовлетворённость** | насколько текущее решение НЕ удовлетворяет | вопрос «насколько решение даёт ожидаемый результат?» (1–10) |

Чем хуже текущее решение — тем проще конкурировать (люди активнее ищут
альтернативы, ниже барьеры перехода). Компоненты **прослеживаются к
research/интервью**, не выдуманы. Размер качественными интервью не
определяется — нужен количественник / кабинетная аналитика.

**Поле `segment.score`** — число + обоснование (например
«8×6×средний×(10−4)»). Без всех компонентов Score не вычислим → сегмент
остаётся `draft`.

## Стратегия выбора сегмента

После Score — внутренние фильтры (можем ли сделать значимо ценнее ·
стоимость · стратегия/интересы) и выбор:

| | стартап | корпорация |
|---|---|---|
| главный приоритет | **низкая удовлетворённость** (быстрый трекшн) | **большой размер** |
| логика | мало ресурсов; неудовлетворённый сегмент купит даже слабый MVP | стабильные инвестиции; важны масштаб и маржа |

Из 5–10 гипотез обычно остаётся 2–4, выбираем **1–2** для углубления
(передача в `/job-graph-deep-dive`).

## Кластеризация и отбраковка

После каждой волны/intake:
1. Сгруппировать находки по **похожести бандла работ + критериев успеха**.
2. **Дифференцировать** сегменты между собой (чем отличим один от
   соседнего — бандлом или критериями).
3. **Отбраковать НЕ-сегменты** с фиксацией **почему** в `state/`
   (критично для фильтрации следующих волн). Типичные НЕ-сегменты:
   демография без бандла; «все клиенты»; одна работа/должность/индустрия
   сама по себе; группа без Big Job или с несколькими.
4. Решить: добирать полноту (ещё волна) или углубляться в выбранный
   сегмент.

## B2B vs B2C ветвление (`segment.kind`)

**`b2c`** — бандл работ одного человека; критерии успеха личные.

**`b2b`** — есть **роли сделки**, у каждой свои работы и мотивации:
бизнес-заказчик → ЛПР → держатель бюджета → ЛВР (IT, безопасник) →
рекомендатель → саботажник → чемпион → end-user.

Ключевой инсайт B2B: **90% мотивации ЛПРа — личные эмоциональные
работы** (job security, статус, рост позиции, рутина, поддержка), а
бизнес-KPI — лишь «река»-контекст, по которой плывёт «лодочка» личных
целей. B2B-работа = бизнес-работа («конвой») + личные работы сотрудника.
Score и бандл B2B-сегмента учитывают обе части; нельзя игнорировать ни
ту, ни другую. Нужно знать работы и возражения **всех** ролей, способных
заблокировать сделку.

При гипотезах и кластеризации скилл сначала спрашивает `kind`, затем
ведёт по нужной ветке (промпты роя — в `research-waves.md`).

## Инварианты, которые скилл поднимает (не grep, смыслом)

- сегмент держится на бандле: ровно одна `big-job` + ≥1 `core-job`;
- Score вычислим: есть все четыре компонента, прослежены к источнику;
- бандл — не демография: различимый признак по контексту и работам;
- разные критерии успеха при той же Core Job → разные сегменты;
- отбракованный НЕ-сегмент имеет зафиксированное «почему»;
- работы сегмента заведены как гипотезы-stub'ы в `job.md` с `segment`.

Полную проверку слоя (включая solution/segment-problem/job-graph) делает
`/ajtbd-audit`; стыки с соседними слоями — `/cross-audit`.
