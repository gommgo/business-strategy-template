# segment-deep-dive

Поиск, кластеризация и скоринг **сегментов** — строгий **разведочный**
слой AJTBD между «кто этот бизнес» (`docs/business/`) и графом работ
(`job-graph-deep-dive`). Канон — `docs/ajtbd/README.md` и
`docs/ajtbd/segment.md`. Источник истины — **многоволновой рой
web-research** и опционально **JTBD-интервью**, не проекция аналитика.

Скилл владеет файлом `docs/ajtbd/segment.md`. Гипотезы работ заводит как
stub-записи в `docs/ajtbd/job.md` (полноценный граф работ строит уже
`/job-graph-deep-dive`).

Слой **один на бизнес** (как `business`/`business-problem`), не
per-project. Питает обоих соседей: вверх — `business-problem` (трения
сегмента доказывают проблему бизнеса), вниз — `docs/projects/<slug>/`
(механики ценности из графа подсказывают возможности продукта).

## Ядро методологии (держать в голове всю сессию)

- **Сегмент = люди, объединённые общей работой**, не демографией. Один
  сегмент держится на **бандле Core Jobs** + ровно **одной Big Job** +
  общих **критериях успеха**. «Женщины 25–35», «SMB» — НЕ сегмент.
- **Главная ошибка — галлюцинировать, что знаем сегменты.** Поиск
  сегмента — это поиск *known unknown*. Всегда стартуем с позиции
  «сегментов может не быть».
- **Score** = важность × частотность × размер × (10 − удовлетворённость
  текущим решением). Чем хуже текущее решение — тем проще принести
  ценность. Из 5–10 гипотез обычно остаётся 2–4, выбираем 1–2.
- **Норматив полноты** — итерации, пока **две волны подряд не принесли ни
  одной новой работы/сегмента**.
- `segment.core-jobs` и `big-job` на этом слое — **гипотезы работ**
  (stub'ы в `job.md`), а не готовый граф.
- **Экспертиза священна** (`CLAUDE.md` §3): формулировки сегментов,
  работ, критериев успеха, оценки компонентов Score — **только** от
  аналитика через `AskUserQuestion` или из research/транскриптов.
  Anti-patterns как опции — да; сами тексты — нет.

Глубинная логика метода — `references/methodology.md`.

## Точки входа

| вызов | поведение |
|---|---|
| `/segment-deep-dive` | сводка по фазам + предложение следующего шага |
| `/segment-deep-dive <slug>` | углубить запись сегмента (режим C) |
| `/segment-deep-dive segment:<slug>` | то же явно (режим C) |
| `/segment-deep-dive segment` | завести новый сегмент руками (режим A) |
| `/segment-deep-dive <свободный текст / ссылка / путь к материалу / транскрипт>` | сырьё → разбор (режим B / intake) |
| `/segment-deep-dive --research <тема>` | запустить многоволновой рой |
| `/segment-deep-dive --phase <name>` | работать в указанной фазе |

`phase` ∈ {`intake`, `hypotheses`, `research`, `cluster`, `score`,
`cohesion`}.

## Что делать сразу при запуске

1. Прочитать `docs/ajtbd/README.md` и `docs/ajtbd/segment.md` — освежить
   канон полей сегмента, инварианты и anti-patterns.
2. Прочитать `references/phases.md` — карту фаз.
3. При гипотезах/кластеризации/скоринге — открыть
   `references/methodology.md` (Score, бандл работ, B2B/B2C).
4. Если args = ссылка/путь/материал/транскрипт — режим intake (см.
   `references/intake.md`).
5. Если args пустые — **сводка по фазам** (см. ниже) + `AskUserQuestion`.
6. Если `--research` — многоволновой рой (`references/research-waves.md`).
7. Если `--phase` — открыть карту фазы.

## Сводка состояния (без args)

Скилл всегда даёт аналитику **карту, где он в методологии**, не просто
список draft-записей.

1. Прочитать `docs/ajtbd/segment.md` + `state/` (своё + read-only из
   соседних — см. «Единый контекст») + `state/research/`-отчёты.
2. Подсчитать сегменты: всего, `draft`/`stable`; отметить, у каких Score
   вычислим (есть все компоненты), у каких нет.
3. Собрать `**blocker**`-вопросы из `state/`.
4. Определить **текущую фазу**:
   - нет материалов и нет гипотез → `intake`;
   - материалы есть, нет 7–10 гипотез сегментов → `hypotheses`;
   - гипотезы есть, рой не отработал до полноты → `research`;
   - находки роя есть, не кластеризованы в сегменты → `cluster`;
   - сегменты есть, у части не вычислен Score → `score`;
   - есть выбранные сегменты с Score, есть draft → `cohesion`.
5. Вывести карту фаз (как в `references/phases.md`, «Сводка фаз»). Через
   `AskUserQuestion` предложить следующий шаг.

## Фазы проработки

Скилл **проактивно** ведёт через фазы (как `business-deep-dive` ведёт
свои), строится **набегающей волной**. Полная карта — `references/phases.md`.

| фаза | цель | артефакты |
|---|---|---|
| `intake` | принять сырьё (материалы клиента / транскрипты `jtbd-interview`) | `state/`, stub'ы |
| `hypotheses` | 7–10 широких высокоуровневых гипотез сегментов по бандлам работ | `state/`, stub'ы `segment`/`job` |
| `research` | многоволновой рой web-research до нормы полноты | `state/research/` |
| `cluster` | кластеризация находок в сегменты, дифференциация, отбраковка НЕ-сегментов с «почему» | `segment.md` |
| `score` | Score сегментов, выбор 1–2 для углубления | `segment.md` |
| `cohesion` | целостность, draft → stable, передача в `job-graph-deep-dive` | `segment.md` |

**Вход сверху** — из `/business-deep-dive` (профиль готов): профиль и
конкуренты бизнеса дают контекст гипотезам. Можно начать сразу с
`hypotheses`, если профиль уже есть.

## Три режима

См. `references/workflow-patterns.md`:

- **A. Новая сущность.** Args = `segment` или `segment:<новый-slug>`.
  Батч `AskUserQuestion` по `Критерии segment` из `segment.md`; опции —
  anti-patterns из «Что segment НЕ»; значения — через Other. Всегда
  спросить `kind` (`b2b`/`b2c`) — от него ветвится разбор.
- **B / intake. Сырьё.** Args = материалы клиента (текст/ссылка/файл)
  или транскрипты из `jtbd-interview` (лежат в `state/`). Извлечь
  кандидатов в сегменты/работы — **только прямо названное**, показать
  план, по подтверждению завести stub'ы. См. `references/intake.md`.
- **C. Углубление.** Args = `<slug>` или `segment:<slug>`. Точечные
  вопросы по дырам и методологическим подозрениям; чек-лист
  `draft → stable`.

## Стиль вопросов

См. `references/workflow-patterns.md`. Краткий канон:

- **Всегда через `AskUserQuestion`**, до 4 вопросов в раунде.
- **Опции** — для: anti-patterns из «Что segment НЕ»; enum (`segment.kind`
  `b2b`/`b2c`); выбора существующего slug соседа; теста-критерия (✅/❌);
  promotion кандидата из research; запуска/остановки волны роя.
- **Свободная форма (Other)** — для значений: `name`, `description`,
  `who-context`, `success-criteria`, тексты гипотез работ, оценки
  компонентов Score (важность · частотность · размер · удовлетворённость),
  `sizing`.
- **Никогда** не выдумывать формулировки сегментов, работ, критериев
  успеха, оценки Score. Anti-patterns как опции — да; сами тексты — нет.
  Это **священная экспертиза** (`CLAUDE.md` §3). Неоднозначность вне
  покрытия → вопрос человеку, не угадывание.

## B2B vs B2C ветвление

`segment.kind` определяет разбор (`references/methodology.md`):

- **`b2c`** — бандл работ одного человека; критерии успеха — личные.
- **`b2b`** — есть **роли сделки** (бизнес-заказчик · ЛПР · держатель
  бюджета · ЛВР · рекомендатель · саботажник · чемпион · end-user). Score
  и работы учитывают, что **90% мотивации ЛПРа — личные работы**
  (job security, статус, рост позиции), а KPI — лишь контекст-«река».
  Сегмент B2B держится на бизнес-работе + личных работах сотрудника.

При гипотезах и кластеризации скилл сначала спрашивает `kind`, затем
ведёт по соответствующей ветке (промпты роя — B2B / B2C — в
`references/research-waves.md`).

## Многоволновой web-research через рой агентов

**Ключевая особенность слоя.** См. `references/research-waves.md`. Рой
5–10 агентов в **одной волне** → кластеризация находок → **следующая
волна засевается дырами и новыми зацепками предыдущей** → стоп, когда
**две волны подряд не дали новых сегментов/работ** (норматив полноты
AJTBD). Реализация — **внутри-скиловый рой через инструмент Agent**
(параллельные вызовы в одном message-блоке), не через Workflow.

Запуск — только по решению аналитика через `AskUserQuestion` (дефолт 5
углов на волну). Кандидаты падают в `state/research/<тема>-<UTC-ts>.md`.
**Авто-залив в `segment.md` запрещён** — promotion только через
`AskUserQuestion`. После каждой волны — `AskUserQuestion`: «гонять ещё
волну (есть дыры)» / «полнота достигнута, в кластеризацию».

## Память `state/`

Заметки лежат **рядом со скиллом**:
`.claude/skills/segment-deep-dive/state/segment/<slug>.md` (+
`state/hypotheses.md` для широких гипотез до кластеризации,
`state/research/<тема>-<ts>.md`). Формат — `references/state-format.md`.
Три опциональные секции: `## Открытые вопросы` (опц. `**blocker**`),
`## Доменные решения`, `## Что копать дальше`. Forward-only. Пустые
секции/заметки — удалить.

**Единый контекст (read-only):** скилл подтягивает соседние `state/`,
чтобы картина была общей — клиентский режим
(`../segment-deep-dive-for-business/state/`) и соседние слои
(`../business-deep-dive*/state/`, `../job-graph-deep-dive*/state/`). В
чужой state **никто не пишет**.

## Контракт `draft → stable`

См. `references/draft-stable.md`. Чек-лист после каждой правки:
обязательные слоты заполнены · `Критерии segment` подтверждены аналитиком
· «Что segment НЕ» не нарушены · тест-критерий ✅ · Score вычислим (есть
все компоненты) · факт прослежен до research или транскрипта интервью ·
нет `**blocker**` в state. Все ✅ → предложить повышение через
`AskUserQuestion`. **Скилл не повышает сам**; не понижает сам.

## Stub-гипотезы работ

`core-jobs`/`big-job` сегмента на этом слое — **гипотезы**. Когда сегмент
ссылается на ещё не существующую работу: завести stub-строку в
`docs/ajtbd/job.md` (`slug + name + when/want/so-that как гипотеза +
segment + level + status=draft`, прочее `—`), записать state-заметку
«заведена как гипотеза-stub в контексте `segment:<slug>` — граф достроит
`/job-graph-deep-dive`», вернуться к сегменту. Полноценный граф работ
(рёбра, CPR, типы, механики) — не здесь.

## Удаление сегмента (каскад)

1. Прочитать `segment.md` + `job.md` + `state/` — найти семантические
   упоминания slug (`job.segment`, stub-работы сегмента, заметки).
2. Показать каскад. Через `AskUserQuestion` по каждому месту: «заменить
   на другой slug» / «удалить упоминание» / «оставить».
3. Применить пакетом. Удалить запись из `segment.md` и
   `state/segment/<slug>.md`.
4. Если у сегмента были stub-работы, ни на что больше не завязанные, —
   спросить, удалить их из `job.md` или переотнести.

## Завершение сессии

1. Перечислить затронутые сущности (заведены/углублены/удалены/повышены).
2. Перечислить нерешённые `**blocker**`-вопросы и оставшиеся дыры
   полноты.
3. Назвать текущую фазу и логичный следующий шаг.
4. Через `AskUserQuestion` предложить:
   - `/jtbd-interview` — если нужны живые интервью (кладёт транскрипты +
     кандидатов в state, которые этот скилл разберёт через intake);
   - `/job-graph-deep-dive` — собрать граф работ выбранного по Score
     сегмента;
   - `/ajtbd-audit` — рой: методологические инварианты слоя;
   - `/cross-audit` — стыки с business / business-problem / projects.

Скилл **сам не вызывает** другие скилы — аналитик запускает руками.

## Запреты

- Не редактировать `segment.md` (и `job.md`) вслепую — всегда сначала
  `Read`.
- Не выдумывать формулировки сегментов, работ, критериев успеха, оценки
  компонентов Score. Anti-patterns как опции — да.
- **Демография — не сегмент.** Не заводить сегмент по возрасту/полу/
  размеру компании без бандла работ и критериев успеха.
- Не авто-вписывать research/транскрипты в артефакты — promotion только
  через `AskUserQuestion`.
- Не строить полноценный граф работ — здесь только гипотезы-stub'ы; граф
  делает `/job-graph-deep-dive`.
- Не повышать `draft → stable` без подтверждения аналитика; не понижать
  сам.
- Не путать `ajtbd/segment` (клиент/рынок) с `projects/<slug>/persona`
  (пользователь нашего решения) — соседние слои.
- Не аккумулировать историю в `state/` — forward-only.
- Не писать в `state/` соседнего (клиентского) скилла — только read-only.
- Не пушить и не коммитить. Коммит/push — гейт аналитика.
- Не вызывать другие скилы — предложить аналитику запустить руками.
