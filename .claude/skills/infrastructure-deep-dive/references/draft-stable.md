# Контракт `draft → stable` (ИТ-периметр)

Запись становится `stable`, когда **все 5 пунктов одновременно** ✅.
Скилл проверяет, архитектор подтверждает, скилл применяет правку
`status:`. Источник инвариантов —
`docs/projects/infrastructure/README.md § Инварианты слоя`.

## Чек-лист

### 1. Обязательные колонки заполнены

По реестру kind'а, без placeholder'ов (`<…>`, `_TBD_`) и пустых ячеек:

| kind | обязательно при stable |
|---|---|
| `server` | `slug`, `name`, `provider`, `location`, `capacity`, `purpose` |
| `runtime` | `slug`, `name`, `type` (`kubernetes` \| `compose`), `environment` (`prod` \| `staging` \| `dev`), `servers` (≥1 slug) |
| `shared-platform` | `slug`, `name`, `description`, `type` (enum реестра), `technology` |
| `job` | `slug`, `name`, `trigger`, `target` (≥1 реф) — плюс чек-лист `§ job` ниже |
| `placement` | `unit`, `runtime` |

Для `runtime` дополнительно: `type: compose` несёт ровно один сервер в
`servers` (сплит на compose = несколько compose-рантаймов).

### 2. Рефы резолвятся

- `runtime.servers` — каждый slug существует строкой `server.md`.
- `placement.runtime` — slug существует строкой `runtime.md`.
- `placement.unit` резолвится по префиксу:
  - `service:<project>/<svc>` → строка реестра
    `docs/projects/<project>/services/service.md`;
  - `platform:<project>/<slug>` → строка
    `docs/projects/<project>/services/platform.md` **с
    `provided-by: own`** (ресурс с `shared:` размещается как
    `shared-platform:<slug>`, не от имени проекта);
  - `shared-platform:<slug>` → строка `shared-platform.md`;
  - `job:<slug>` → строка реестра `job.md`.
- Для `shared-platform` — ресурс потребляет ≥1 проект
  (`provided-by: shared:<slug>` в чьём-то `services/platform.md`); сирота
  stable не становится без явного решения архитектора в state («заведён
  на вырост, потребители — …»).

Чужие реестры читаются read-only; битый реф **не чинится правкой чужого
файла** — либо правится своя запись, либо state-заметка «ждёт записи в
`service.md`/`platform.md` проекта» (`**blocker**`).

### 3. У юнита есть prod-размещение

Для записей, отвечающих за живой юнит:

- placement сервиса: у `service:<project>/<svc>` есть хотя бы одна строка
  с рантаймом `environment: prod` — иначе сервис «живёт нигде»;
- `shared-platform`-ресурс, которого потребляет ≥1 проект, и
  `own`-ресурс проекта — размещены (есть строка `placement.md`).

Не-prod строка placement (dev/staging) может быть stable и без
prod-парной — но скилл подсвечивает дыру в coverage-сводке.

### 4. Нет IP / секретов / runtime-механики

В тексте записи (и её state-заметке) нет:

- IP-адресов, hostname, доменов доступа, имён ОС, SSH/паролей/токенов;
- runtime-механики: реплики, версии k8s/helm, CNI, ingress-контроллер,
  retention, affinity, размеры подов.

Это контракт слоя: чувствительное и летучее живёт в `<org>/infra`.
Найдено — убрать **до** stable (и вообще сразу).

### 5. State чист по `**blocker**`-вопросам

`../entrypoint/state/infrastructure/<kind>/<slug>.md`: секции
`## Открытые вопросы` нет, либо в ней нет пометок `**blocker**`.
Не-blocker вопросы при stable допустимы («хорошо бы узнать», не «смысл
сломан»). `## Доменные решения` stable не мешает — это накопленный
контекст («почему два `own`, а не общий»).

### job

- строка реестра `job.md` имеет файл `jobs/<slug>.md` и наоборот;
- обязательные H2 файла заполнены: `Trigger`, `Does`, `Target`,
  `Retention`, `Verify`, `On failure`, `Notes` (пустое — явный `_N/A_`);
- `Trigger` — смысл словами или `topic:<t>`, **не** cron-выражение;
- `Verify` непуст содержательно: названо, как узнаём, что джоба работает
  (restore-тест, свежесть результата) — «никак» блокирует stable;
- каждый реф `Target` резолвится (сервер / рантайм / общий ресурс / сервис
  проекта);
- есть строка `placement.md` с `unit: job:<slug>`;
- это уход за периметром, не продуктовый воркер (тест-критерий `job.md`
  подтверждён).

## Тест-критерий по kind

Перед повышением скилл предъявляет через `AskUserQuestion` ✅/❌-примеры
(конкретику подставляет из самой записи), архитектор соотносит свою.

### server

> «Платит ли бизнес за это как за отдельную машину, и можно ли её
> выключить, не выключая другую?»

- ✅ `srv-prod-1` — VPS у hetzner, 8 vCPU / 16 GB, prod-ядро.
- ❌ «managed Postgres у Selectel» — машина провайдера, не наша строка:
  это технология ресурса (`Resources` паспорта / `shared-platform.md`).

### runtime

> «Можно ли сказать юниту „живи здесь“ — и инфра-репо поймёт, как это
> материализовать (helm в кластер / блок в compose-файле этого хоста)?»

- ✅ `main-cluster` · `kubernetes` · `prod` · `[srv-prod-1, srv-prod-2]`.
- ❌ «staging» без серверов — окружение как абстракция; пока нет машин и
  строки, окружения нет.

### shared-platform

> «Если ресурс упадёт — затронет ли это больше одного проекта, при том
> что проектировать в нём нечего?»

- ✅ единый NATS, через который ходят события CRM-проекта и магазина.
- ❌ Postgres под заказы одного магазина — ресурс сервиса `orders`.
- ❌ «шлюз» с нашей логикой агрегации — это сервис какого-то проекта
  (`type: edge`/`gateway`), не ресурс.

### placement

> «Прочитав строку, инфра-репо однозначно понимает: этот юнит
> материализуется в этом рантайме?»

- ✅ `service:crm/orders` · `main-cluster`.
- ❌ «orders живёт на srv-prod-1» — мимо рантайма, прямо на сервер:
  размещаем в **рантайм**, сервера читаются через `runtime.servers`.
- ❌ строка для «Postgres сервиса orders» — ресурсы сервиса едут вместе
  с ним, отдельная строка не нужна.

## Алгоритм проверки скиллом

После любой правки записи:

1. `Read` реестр записи (+ реестры, на которые она ссылается).
2. `Read` state-заметку записи, если есть.
3. Сверить пункты 1, 2, 3, 4, 5 вручную (committed-валидатора в репо
   нет).
4. Все ✅ → раунд `AskUserQuestion` по тест-критерию kind'а (✅/❌-примеры
   + Other).
5. Подтверждено → раунд `AskUserQuestion`: «Готов к stable, повышаем?» —
   «Да, повысить» / «Нет, ещё не уверен» (Other — что смущает).
6. По «Да» — `Edit`'ом `status: draft → stable`. Что-то не держится →
   откатить status, вернуться к проблемным колонкам.

## Что НЕ делать

- **Не повышать сам**, без подтверждения архитектора — даже при всех ✅.
- **Не понижать `stable → draft` сам** — только подсветить и предложить.
- **Не чинить рефы правкой чужих файлов** (`service.md` / `platform.md`
  проектов — зона `/service-deep-dive`).
- **Не считать тест-критерий пройденным «по умолчанию»** — это отдельное
  смысловое подтверждение в текущей сессии.
- **Не пропускать пункт 4**: запись с IP/секретом не «почти stable» —
  это нарушение контракта слоя, чистится немедленно.
