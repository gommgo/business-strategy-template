# infrastructure-deep-dive

Проработка **ИТ-периметра бизнеса** — физической стороны всех продуктов:
сервера (`server.md`) → рантаймы на них (`runtime.md`) → общие
платформенные ресурсы (`shared-platform.md`) → джобы периметра (`job.md`)
→ размещение юнитов
(`placement.md`). Канон слоя — `docs/projects/infrastructure/README.md`;
скилл его не дублирует, а исполняет.

Слой **один на бизнес** и межпроектный (как `project-map.md`): аргумента
проекта у скилла нет. Канон формы и данные живут в одних файлах — в
`_template/` слой не шаблонируется. Цепочка смысла:

```
projects/<slug>/services/service.md   что мы строим (deployment-agnostic)
projects/<slug>/services/platform.md  что проекту нужно от платформы
                 │ provided-by: own | shared:<slug>
infrastructure/shared-platform.md     общие ресурсы бизнеса
infrastructure/placement.md           кто где живёт (unit → runtime)
infrastructure/runtime.md             среды исполнения (k8s / compose)
infrastructure/server.md              железо/VPS
```

Этот слой — design-time SoT размещения и **завершается на
stable-записи**. Что с ней делает `<org>/infra` (провижининг, манифесты,
helm, compose-файлы) — забота того репо, не этого скилла. Здесь — смысл и
ёмкость; IP, hostname, доступы и runtime-механика живут в `<org>/infra`.

## Главный ритм: AskUserQuestion

Скилл — интервьюер архитектора, не редактор. Партнёр по диалогу —
архитектор или бизнес (тот, кто платит за сервера и решает топологию):
провайдер и ёмкость сервера, выбор kubernetes или compose, общий или свой
ресурс, раскладка юнитов по рантаймам — его экспертиза (`CLAUDE.md` §3,
«Инфраструктурная»), поэтому решения ложатся в реестры его словами, а
скилл их не сочиняет. Шаг сеанса — раунд `AskUserQuestion` → ответ →
запись в реестр через `Edit` → следующий раунд:

- в раунде до 4 вопросов — это лимит инструмента; больше вопросов —
  следующим раундом;
- ответ записывается сразу после раунда: отложенное «до конца фазы»
  теряется при `/clear`;
- выбор «как обычно делают» (k8s по умолчанию) и молча досочинённые
  ёмкость или провайдер — догадка, а не решение архитектора; при сомнении
  нужен ещё один раунд вопросов;
- anti-patterns канона слоя скилл даёт опциями, а значения полей — только
  через свободную форму (Other).

## Точки входа

Аргумента слоя нет — слой один. Опциональный аргумент — тема или сырьё:

| вызов | поведение |
|---|---|
| `/infrastructure-deep-dive` | сводка по фазам + coverage + ходы на выбор |
| `/infrastructure-deep-dive <kind>` | завести новую запись типа kind (режим **A**) |
| `/infrastructure-deep-dive <kind>:<slug>` | углубить существующую запись (режим **C**) |
| `/infrastructure-deep-dive <свободный текст / приложение>` | сырьё → разбор (режим **B**): список VPS, набросок раскладки, выгрузка биллинга провайдера |
| `/infrastructure-deep-dive --phase <name>` | принудительно работать в фазе |

`kind` ∈ {`server`, `runtime`, `shared-platform`, `job`, `placement`}.

`phase` ∈ {`servers`, `runtimes`, `shared-platform`, `jobs`,
`placement`, `cohesion`}.

Для `placement` записи идентифицируются по `unit`
(`service:<project>/<svc>` | `platform:<project>/<slug>` |
`shared-platform:<slug>` | `job:<slug>`), не по slug.

## Что делать сразу при запуске

1. Прочитать `docs/projects/infrastructure/README.md` — освежить канон
   слоя и его инварианты.
2. Прочитать `references/phases.md` — карту 6 фаз.
3. Прочитать 5 реестров слоя: `server.md`, `runtime.md`, `job.md`,
   `shared-platform.md`, `placement.md`.
4. Собрать **межпроектный контекст** (read-only):
   - реестры сервисов всех проектов — `docs/projects/*/services/service.md`
     (исключая `_template` и `infrastructure`) — юниты для размещения;
   - платформенные потребности — `docs/projects/*/services/platform.md`:
     строки `provided-by: shared:<slug>` (потребители общих ресурсов) и
     `provided-by: own` (ресурсы, требующие собственного placement);
   - для фазы `jobs` — из паспортов `services/*/README.md` **только**
     секции `## Resources` (stateful-ресурсы под coverage бэкапов) и
     `## Messaging` (продюсеры topic-триггеров).
5. Прочитать свою ветку state
   (`../entrypoint/state/infrastructure/`, если есть) — секции
   `## Открытые вопросы`; пометки `**blocker**` приоритетны.
6. Если args пустые — **сводка состояния** (см. ниже) + `AskUserQuestion`
   с выбором хода.
7. Если args указывают на сущность/сырьё — определить kind и режим
   (A/B/C), идти по нему.

Как говорить о ходе, словах и вариантах — `.claude/rules/guiding.md`;
условия работы, названные человеком, читаются до первого вопроса.

## Сводка состояния (без args)

1. Подсчитать `draft`/`stable` по каждому из 5 реестров.
2. Построить **coverage-сводку** (таблицей в чат, не prose):

   ```
   ## Покрытие размещения

   | юнит | тип | placement (prod) | placement (прочие) |
   |---|---|---|---|
   | service:crm/orders | сервис | main-cluster | dev-box |
   | service:crm/ai-gateway | сервис | — ⚠ | dev-box |
   | platform:crm/cache (own) | ресурс проекта | — ⚠ | — |
   | shared-platform:nats | общий ресурс | main-cluster | — |

   Потребности без ответа периметра:
   | проект | потребность | provided-by | запись shared-platform |
   |---|---|---|---|
   | crm | events-broker | shared:nats | ✅ |
   | shop | media-storage | shared:minio | — ⚠ |
   ```

3. Определить текущую фазу по триггерам из `references/phases.md`
   (нет серверов → `servers`; сервера без рантаймов → `runtimes`; есть
   неотвеченные `shared:` потребности → `shared-platform`; есть дыры
   coverage → `placement`; всё заполнено, есть draft/blocker → `cohesion`).
4. Вывести карту фаз (формат — `references/phases.md § Сводка фаз`).
5. Через `AskUserQuestion` предложить: продолжить фазу / закрыть конкретную
   дыру coverage / перепрыгнуть фазу / разобрать сырьё.

## Фазы проработки

Скилл **проактивно** ведёт через 6 фаз. Полная карта (триггеры, что
копать, анти-паттерны, переходы) — `references/phases.md`:

| фаза | цель | артефакт |
|---|---|---|
| `servers` | учёт железа/VPS: провайдер, локация, ёмкость одной колонкой, назначение | `server.md` |
| `runtimes` | среды исполнения: k8s-кластер на нескольких серверах / compose-хост на одном; `environment` prod\|staging\|dev | `runtime.md` |
| `shared-platform` | общие ресурсы бизнеса из intake потребностей проектов (`provided-by: shared:<slug>`) | `shared-platform.md` |
| `jobs` | обслуживающие джобы периметра: триггер смыслом (не cron), `target` — что обслуживают, проверка успеха | `job.md` + `jobs/<slug>.md` |
| `placement` | каждый сервис, каждый размещаемый ресурс и каждая джоба получают рантайм; coverage-сводка | `placement.md` |
| `cohesion` | инварианты слоя из README + повышение draft → stable + гейт аудита | все |

Порядок — рекомендация, не закон: строим набегающей волной (неточно →
уточняем); при перепрыгивании скилл называет цену пропуска одной фразой,
пишет долг в state и работает, вопрос «почему сейчас?» — только когда
пропуск задевает обязательный артефакт маршрута
(`references/phases.md § Перепрыгивание`).

## Три режима

- **A. Новая запись.** Args = `<kind>` или `<kind>:<новый-slug>`. Раунд
  `AskUserQuestion` по «Критерии <kind>» и «Тест-критерий» из реестра слоя;
  опции — anti-patterns из «Что <kind> НЕ» и enum-поля; значения —
  через Other. `slug` скилл выводит из `name` сам (`.claude/rules/naming.md`);
  для `placement` вместо slug — выбор `unit` из непокрытых юнитов
  coverage-сводки (пикер по именам). Завести строку → погрузиться в C.
- **B. Сырьё.** Args = свободный текст / приложение: список VPS из
  биллинга, набросок раскладки на салфетке, выгрузка «что где крутится».
  Извлечь кандидатов (сервера / рантаймы / общие ресурсы / размещения),
  показать план разбора, по подтверждению — завести stub-строки со
  state-заметками и пройти C по каждой. Чувствительное из сырья (IP,
  hostname, ключи) **в реестры не переносить** — отметить архитектору, что
  это уезжает в `<org>/infra`.
- **C. Углубление.** Args = `<kind>:<slug>` существующей записи либо выбор
  из сводки. Точечные вопросы по дырам и подозрениям (рантайм без
  серверов, юнит без prod, ресурс-сирота); чек-лист `draft → stable`
  после каждой правки.

## Стиль вопросов

- Вопросы — через `AskUserQuestion`, до 4 в раунде; запись в реестр после
  каждого раунда.
- **Опции** — для:
  - enum-полей (`runtime.type` `kubernetes`|`compose`,
    `runtime.environment` `prod`|`staging`|`dev`, `shared-platform.type`);
  - anti-patterns слоя как вариантов («это managed-сервис без сервера —
    не строка `server.md`?», «двум проектам нужен брокер — общий
    `shared:` или осознанно два `own`?»);
  - выбора существующего соседа (сервера для `runtime.servers`, рантайм
    для `placement.runtime`, юнит из coverage-сводки);
  - тест-критериев kind'а с примерами ✅/❌
    (`references/draft-stable.md`).
- **Свободная форма (Other)** — для значений: `name`, `provider`,
  `location`, `capacity`, `purpose`, `description`, `technology`.
- Конкретику — провайдера, ёмкость, локацию, выбор k8s или compose,
  раскладку, решение «общий или свой» — называет архитектор; скилл
  подсказывает только anti-patterns.

## Память: своя ветка единого дерева state

Скилл своего `state/` не держит. Per-kind заметки — в **свою ветку**
единого дерева state оркестратора:

```
../entrypoint/state/infrastructure/<kind>/<slug>.md
```

`kind` ∈ {`server`, `runtime`, `shared-platform`, `job`, `placement`}; для
`placement` ключ заметки — нормализованный `unit`
(`:` и `/` → `--`, например `service--crm--orders.md`). Формат — канон
`../entrypoint/references/state-model.md`: frontmatter (`kind` · `slug` ·
`ref`) + три опциональные секции `## Открытые вопросы` (опц. `**blocker**`
— блокирует `draft → stable`), `## Доменные решения` (например, «почему
два `own`-Postgres, а не общий»), `## Что копать дальше`. Файл существует,
пока есть хоть одна непустая секция. **Forward-only**: без «было/стало»,
дат и журналов (`.claude/rules/forward-only.md`).

**Единый контекст (read-only).** Скилл видит всё дерево
`../entrypoint/state/` (срез `index.md`, нити `threads/`, ветки слоёв) и
клиентский дом `../entrypoint-for-business/state/`. Проектные ветки
читает по тем проектам, чьи сервисы размещает (слой межпроектный —
изоляция продуктов здесь не сужает чтение, но **писать** можно только в
свою ветку `infrastructure/`). Маркер `**жду аналитика**` из клиентского
дома — blocker-кандидат.

## Контракт `draft → stable`

См. `references/draft-stable.md`. Чек-лист после каждой правки (все
пункты одновременно ✅ → предложить повышение через `AskUserQuestion`):

1. **Обязательные колонки заполнены** (по реестру kind'а), без
   placeholder'ов.
2. **Рефы резолвятся**: `runtime.servers` → строки `server.md`;
   `placement.unit` → реестры `service.md`/`platform.md` проектов
   (для `platform:` — строка с `provided-by: own`),
   `shared-platform.md` или `job.md`; `placement.runtime` → строка
   `runtime.md`.
3. **У юнита есть prod-размещение** — для записей, отвечающих за юнит
   (placement сервиса; shared-ресурс, который потребляют).
4. **Нет IP / hostname / секретов / runtime-механики** в тексте записи.
5. **State чист по `**blocker**`-вопросам.**

Повышение — только с явного подтверждения архитектора; скилл не повышает
сам и не понижает `stable → draft` (максимум подсветить и предложить).

## Удаление записи (каскад)

1. Прочитать 5 реестров слоя + `services/platform.md` проектов + свою
   ветку state — найти все ссылки на удаляемый slug (`runtime.servers`,
   `placement.runtime`, `placement.unit`, `provided-by: shared:<slug>`).
2. Показать каскад: «ссылаются X, Y — вот что повиснет» (удаление сервера
   обескровливает рантайм; удаление рантайма — размещения; удаление
   shared-ресурса — потребности проектов).
3. Через `AskUserQuestion` по каждому месту: «заменить на другой slug» /
   «удалить строку» / «оставить (станет битой → state-заметка)». Правки в
   `services/platform.md` проектов — зона `/service-deep-dive`: здесь
   только state-заметка «потребность проекта осталась без ответа».
4. Применить пакетом через `Edit`; удалить строку и state-заметку.

## Завершение сессии

1. Перечислить затронутые записи (заведены / углублены / повышены /
   удалены) и свежий срез coverage («не размещены: …»).
2. Перечислить нерешённые `**blocker**`-вопросы из своей ветки state.
3. Назвать текущую фазу и ходы дальше — два-три, один рекомендован.
4. Через `AskUserQuestion` предложить: `/infrastructure-audit` (узкий
   аудит слоя — рефы, дубли, enum, сироты, coverage) / `/cross-audit`
   (углы `service-placement` · `platform-shared`), если в сессии трогались
   и проектные слои / вернуться к незакрытой фазе.

Скилл **сам не вызывает** другие скилы — архитектор запускает.

Как говорить о ходе, словах и вариантах — `.claude/rules/guiding.md`:
итог сессии, ходы дальше и строка «как продолжить» идут по нему.

## Границы

- **Проектная топология — только читать.** Сервисы, паспорта,
  `architecture.md`, `platform.md` проектов (включая саму колонку
  `provided-by`) — зона `/service-deep-dive <slug>`. Здесь они читаются
  как intake; несоответствие — state-заметка или подсказка запустить
  соседний скилл.
- **Runtime-механика — в `<org>/infra`.** Реплики, версии k8s, CNI,
  helm-values, retention, манифесты в реестры слоя не пишутся; принёс
  архитектор — вежливо отклонить с пометкой «это инфра-репо».
- **Секреты и адресация не пишутся** ни в реестры, ни в state, даже
  временно: IP, hostname, ОС, SSH, пароли, токены. Всё, что попало в
  реестр, уезжает в git-историю, поэтому из сырья (режим B) они не
  переносятся.

Итог ключевого: значения полей приходят от архитектора; в stable запись
поднимается только по его подтверждению; писать можно только в свою ветку
state, а другие скиллы — только предлагать.
