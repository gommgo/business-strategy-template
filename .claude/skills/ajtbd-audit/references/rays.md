# Лучи проверки ajtbd-audit

Каждый луч — отдельный угол семантической проверки инварианта методологии
Advanced JTBD. Один луч = один агент. Запускаются параллельно. Структура:
**Файлы** · **Применим если** · **Что искать** · **Промпт-добавка**.

Источник списка инвариантов — `docs/ajtbd/README.md` § «Связи и
методологические инварианты». Слой **разведочный, но строгий**: связи
**не валидируются slug-целостностью**, они семантические — поэтому лучи
ищут смысл, а не grep.

Слой держится на **сегментах**: `segment.md` — таблица сегментов (одна
строка = один сегмент), у каждого свой бандл работ (Core Jobs + одна Big
Job). **Граф работ собирается внутри одного сегмента.** Поэтому
большинство лучей считают инвариант **в пределах одного сегмента**:
работа / решение / трение / граф с сегментом S замыкаются на сущности
того же S. Луч проходит по каждой строке `segment` отдельно (или по
одной, если задан scope `<segment-slug>`). Нарушение помечается полем
`segment`.

## segment-bundle

**Файлы:** `segment.md`, `job.md`.
**Применим если:** в `segment` есть хотя бы одна строка.

**Что искать:**
- `error`: сегмент без `big-job` или с **несколькими** Big Job — не
  сегмент (ровно одна Big Job на сегмент).
- `error`: сегмент без `core-jobs` (нет ни одной Core Job) — бандла нет.
- `warning`: `big-job`/`core-jobs` ссылаются на работу, чей `level` не
  соответствует (big-job указывает на `core`, core-job на `big`/`low`).
- `hint`: сегмент описан **демографией**, а не бандлом работ
  («женщины 25–35», «SMB») — не бандл.

**Промпт-добавка:**
```
Сегмент держится на бандле: ровно одна big-job + ≥1 core-job + общие
критерии успеха. Для каждого сегмента проверь: одна ли big-job (ноль или
несколько → error); есть ли ≥1 core-job (нет → error); совпадает ли level
работ с ролью (big-job → job.level=big, core-jobs → core); не подменён ли
бандл демографией (hint). В finding укажи segment = slug сегмента.
```

## so-that-chain

**Файлы:** `job.md`, `segment.md`.
**Применим если:** есть работы.

**Что искать:**
- `error`: разрыв непрерывности «чтобы» — `job.so-that` нижней работы по
  смыслу ≠ `want` работы её `parent-job` (нарушение принципа «5 почему»).
- `error`: цепочка `core`/`low`-работы не доходит вверх по `parent-job`
  до `big`-работы своего сегмента (повисает / уходит не туда).
- `warning`: `parent-job` ссылается на работу другого сегмента (цепочка
  пересекает границу сегмента).

**Промпт-добавка:**
```
Непрерывность «чтобы»: so-that нижней работы = want работы parent-job (как
5 почему), цепочка core/low ведёт вверх до big-работы своего сегмента. Для
каждой работы пройди по parent-job вверх: совпадает ли so-that с want
родителя по смыслу (не строкой)? доходит ли цепочка до big-job сегмента?
не уводит ли в чужой сегмент? Разрыв смысла или недоход до big → error. В
finding укажи segment работы.
```

## job-segment

**Файлы:** `job.md`, `segment.md`.
**Применим если:** есть работы.

**Что искать:**
- `error`: работа без `segment` (`—`) — вне реестра, непонятно, чьего
  спроса касается.
- `error`: `job.segment` ссылается на сегмент, которого нет в `segment.md`.

**Промпт-добавка:**
```
Каждая работа тегирована сегментом (job.segment — непустой реф на
существующую строку segment.md). Найди работы с пустым segment (error) или
ссылкой на отсутствующий сегмент (error). В finding укажи segment работы
(или "—", если пуст/невалиден).
```

## core-solution

**Файлы:** `job.md`, `solution.md`, `segment.md`.
**Применим если:** есть Core-работы.

**Что искать:**
- `error`: `core`-работа без хотя бы одного `solution` (нет `solution`,
  чей `hired-for` содержит эту работу) — Score сегмента не вычислить.
- `error`: на Core-работу нанято решение, но без оценок `satisfaction`
  и/или `price-value-fit` — нет входа в Score (низкая удовлетворённость =
  сигнал ценности).
- `warning`: оценки решения стоят «на глаз» — не прослежены к
  research/интервью (по тексту/state видно, что не подтверждены).

**Промпт-добавка:**
```
У целевой (core) работы должно быть ≥1 нанятое решение (solution, чей
hired-for содержит эту работу) с оценками satisfaction и price-value-fit —
иначе Score сегмента (важность × частотность × размер × (10 −
удовлетворённость)) не вычислить. Для каждой core-работы: есть ли решение?
есть ли у него обе оценки? подтверждены ли они research/интервью? Нет
решения или нет оценок → error. В finding укажи segment работы.
```

## problem-pair

**Файлы:** `segment-problem.md`, `solution.md`, `job.md`.
**Применим если:** есть трения (segment-problem).

**Что искать:**
- `error`: `segment-problem` без `solution` и/или без `job` (`—`) —
  нарушение ядра «проблема — следствие решения, нанятого на работу».
- `error`: `solution`/`job` трения ссылаются на несуществующую сущность,
  или пара несогласована (это решение не нанято на эту работу — `solution.hired-for`
  не содержит `job` трения).
- `warning`: `strength` трения без обоснования из research/интервью.

**Промпт-добавка:**
```
Ядро AJTBD: проблема не существует сама по себе — она следствие
пары solution + job. Для каждого segment-problem: заполнены ли solution И
job? существуют ли они? нанято ли это решение на эту работу (solution.hired-for
содержит job трения)? обоснована ли strength research/интервью? Пустой/
несогласованный/несуществующий solution или job → error. В finding укажи
segment трения.
```

## score-computable

**Файлы:** `segment.md`, `solution.md`, `job.md`.
**Применим если:** есть сегменты со `status: stable`.

**Что искать:**
- `error`: `stable`-сегмент, чей `score` не вычислим — нет одного из
  компонентов (важность / частотность / размер / удовлетворённость),
  прослеживаемых к Core-работам и их решениям.
- `warning`: `score` записан числом, но компоненты-обоснование (`<число +
  обоснование>`) отсутствуют — непонятно, откуда взято.

**Промпт-добавка:**
```
Score сегмента = важность × частотность × размер × (10 − удовлетворённость
текущим решением). У stable-сегмента все компоненты должны быть
прослеживаемы: важность/частотность — из core-работ (importance, frequency),
размер — sizing, удовлетворённость — из solution.satisfaction нанятых на
core-работы решений. Для каждого stable-сегмента: вычислим ли Score (все
4 компонента есть и обоснованы)? Нет компонента → error; голое число без
обоснования → warning. В finding укажи segment.
```

## graph-cpr

**Файлы:** `job-graph.md`, `job.md`, `segment.md`.
**Применим если:** есть графы (job-graph).

**Что искать:**
- `error`: `job-graph` без `cpr` (нет критического пути результатов).
- `error`: разрыв CPR — соседние шаги `cpr` не связаны как
  последовательность (`prev-jobs`/`parent-job` не подтверждают порядок),
  или `cpr` не ведёт к Big Job сегмента.
- `error`: работы графа без разметки `type` (`job-types` не покрывает
  работы CPR; у работ `job.type` пуст).
- `warning`: `cpr` ссылается на работу не из этого сегмента.

**Промпт-добавка:**
```
job-graph: CPR (cpr) — упорядоченный must-do путь работ к Big Job сегмента;
разрыв CPR убивает результат. Работы графа размечены по type (job-types и/
или job.type). Для каждого графа: есть ли cpr? непрерывен ли он по смыслу
(шаги связаны как последовательность, ведут к big-job)? размечены ли типы
всех работ графа? нет cpr / разрыв / непроставленные type → error;
чужой сегмент в cpr → warning. В finding укажи segment графа.
```

## false-job

**Файлы:** `job.md`, `job-graph.md`.
**Применим если:** есть работы.

**Что искать:**
- `warning`: подозрение на **ложную работу** (85 lvl) — работа,
  сформулированная как реальная, но не двигающая к ценности (по смыслу —
  «надо», навязанная, ритуальная), не проверенная вопросом и **не
  помеченная** `type: ложная`.
- `hint`: работа выглядит как задача/шаг интерфейса/наш будущий продукт,
  а не как цель + желаемое состояние («нажать кнопку», «открыть
  приложение»).

**Промпт-добавка:**
```
Ложная работа (85 lvl) — выглядит как работа, но не двигает к ценности;
требует проверочного вопроса «двигает ли она к ценности?» и пометки
type=ложная. Для каждой работы: есть ли подозрение на ложность (ритуал/
«надо»/навязано) при отсутствии пометки type=ложная → warning. Работа,
похожая на задачу/фичу/шаг интерфейса/наш продукт, а не на цель + желаемое
состояние → hint. В finding укажи segment работы.
```

## orphan-refs

**Файлы:** все 5 (`segment`, `job`, `job-graph`, `solution`,
`segment-problem`).
**Применим если:** есть хотя бы одна запись.

**Что искать:**
- `error`: работа-сирота — `job`, которая не входит ни в один граф
  (`job-graph.cpr`/`target-job`) и не упомянута бандлом сегмента
  (`segment.core-jobs`/`big-job`) и не имеет потомков по `parent-job`/`prev-jobs`.
- `error`: `solution`/`segment-problem`/`job-graph`, ссылающиеся на
  несуществующую сущность (`hired-for`, `by-segment`, `segment`,
  `target-job`, `cpr`, `maps-to` на отсутствующий competitor/offering).
- `warning`: запись ссылается сама на себя / цикл `parent-job`.

**Промпт-добавка:**
```
Найди сущности, повисшие или бьющие в пустоту. Работа-сирота: job, не
входящая ни в граф (cpr/target-job), ни в бандл сегмента (core-jobs/big-job),
ни в чьи-то parent-job/prev-jobs → error. Решение/трение/граф со ссылками
(hired-for, by-segment, segment, target-job, cpr, solution, job, maps-to)
на несуществующую сущность → error. Цикл parent-job → warning. В finding
укажи segment затронутой сущности (или "—").
```

## layer-mixup

**Файлы:** `segment-problem.md`, `solution.md`, `job.md`,
`docs/business/business-problem.md` (read-only, для контраста).
**Применим если:** есть трения (segment-problem) или решения.

**Что искать:**
- `error`: `segment-problem` подан как проблема **бизнеса** (формулировка
  про KPI/отток/выручку заказчика, а не про трение **клиента** с нанятым
  решением) — путаница слоёв; должен питать `business/business-problem`, а
  не подменять.
- `warning`: `segment-problem` использует слово «pain»/«боль» вместо
  недостижимого результата + негативной эмоции.
- `warning`: `solution` описан как **наш будущий продукт**/фича, а не как
  то, что сегмент нанимает **сейчас** (это `project`, не solution).

**Промпт-добавка:**
```
Слои разные. segment-problem = трение клиента с нанятым решением на
работе; business/business-problem = проблема бизнеса заказчика (первое
питает второе, не подменяет). solution = что сегмент нанимает сейчас, не
наш будущий продукт. Найди: segment-problem, сформулированный как проблема
бизнеса (KPI/отток/выручка заказчика) → error; «pain»/«боль» вместо
недостижимого результата → warning; solution как наш будущий продукт/фича
→ warning. business-problem.md читай только для контраста, не как источник
findings. В finding укажи segment.
```

## Порядок лучей

Полный прогон: `job-segment` → `segment-bundle` → `so-that-chain` →
`graph-cpr` → `core-solution` → `problem-pair` → `score-computable` →
`false-job` → `orphan-refs` → `layer-mixup` (сначала валидность привязки
к сегменту и устройство бандла, затем непрерывность графа вверх,
решения/трения/Score, далее — ложные работы, сироты и путаница слоёв).
`--quick` — `segment-bundle`, `so-that-chain`, `problem-pair`,
`graph-cpr`.
