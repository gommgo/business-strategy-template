# project-audit

Аудит консистентности продуктового слоя **одного проекта** в `docs/projects/<project-slug>/`:

- **1 singleton** `vision.md`;
- **реестр-хребет** `surface.md` — поверхности продукта; их slug'и — ключи партиционирования, `type` и род `web-kind`
  решают, какие слои получит поверхность;
- **папка возможностей** — по файлу `capability/<surface>.md` на поверхность: реестр, паспорта, урезание;
- **7 плоских кросс-поверхностных таблиц** — `user.md` (с постурой), `object.md` (с атрибутами и представлениями),
  `action.md`, `integration.md`, `boundary.md`, `constraint.md`, `market.md`.

Канон формы — `docs/projects/_template/project/README.md` и формы kind рядом с ним. Аудит **читает и сообщает**, ничего
не правит: правки идут через `/project-deep-dive <project-slug>`.

Проверяется слой изнутри: форма записей, ссылки ядра, хребет поверхностей, покрытие возможностей вниз по ситуациям и
сценариям той же папки проекта и матрица «пользователь × объект × действие». Смысл связей с соседними слоями —
пользователи против участников (who), продукт против `addresses-problem`, трасса вверх — сверяет `/cross-audit`.

## Мультипроект: выбор проекта

Аудит скоупится в один проект. Первый позиционный аргумент — `<project-slug>`. Без него — пикер `AskUserQuestion` по
именам проектов (подкаталоги `docs/projects/`, исключая `_template` и `infrastructure` — образец формы и ИТ-периметр, не проекты; текст опции — имя из
vision, slug — деталью). Один прогон — один проект.

## Точки входа

| вызов | поведение |
|---|---|
| `/project-audit` | пикер проекта → полный прогон |
| `/project-audit <project-slug>` | полный прогон всех файлов проекта и матрица |
| `/project-audit <project-slug> <kind>` | прогон одного kind и ссылающихся соседей |
| `/project-audit <project-slug> capability` | все файлы возможностей и соседи |
| `/project-audit <project-slug> capability:<surface>` | один файл `capability/<surface>.md` |
| `/project-audit <project-slug> <kind>:<slug>` | одна запись и её соседи на один шаг |

`kind` ∈ {`vision`, `surface`, `user`, `object`, `action`, `capability`, `integration`, `boundary`, `constraint`,
`market`}. `capability` без уточнения берёт все файлы возможностей; `capability:<surface>` сужает до одной поверхности;
`capability:<slug>` (slug записи) тоже работает — аудит находит файл, где лежит запись. Матрица собирается при полном
прогоне и при прогоне `object`, `action`, `capability`.

Первый аргумент совпал с папкой `docs/projects/` (кроме `_template` и `infrastructure`) — это `<project-slug>`; иначе — пикер.

## Что делать при запуске

1. **Проект.** Разобрать первый аргумент; не задан или не совпал с папкой — пикер по именам. Зафиксировать проект на
   прогон.
2. Прочитать `docs/projects/_template/project/README.md` и формы kind из scope — канон, по которому идёт сверка.
3. Прочитать `references/rules.md` — реестр правил с тяжестью и нормой.
4. Прочитать файлы проекта из scope:
   - корневые — `vision.md`, `surface.md`, `user.md`, `object.md`, `action.md`, `integration.md`, `boundary.md`,
     `constraint.md`, `market.md`;
   - все файлы возможностей — листингом папки возможностей проекта, а не угадыванием имён: имя каждого файла должно быть
     slug'ом поверхности реестра (R-STRUCT-007).
5. Определить набор vision и маршруты поверхностей по `surface.md` — от них зависят правила R-STRUCT-004, R-VS-*,
   R-RL-001, R-CAP-006 (`references/rules.md § Состав слоя`, словарь правил).
6. Прочитать то, что называют правила, за пределами слоя — только чтением: листинг папок слоёв проекта; колонку
   `capabilities` и имена ситуаций, сценарии, имена зон и блоков в `interface/<surface>/`; раздел «Решения»
   `screens/<surface>/map.md`; наличие профилей голоса уровня продукта.
7. Прочитать ветку state проекта `../entrypoint/state/projects/<project-slug>/project/` — для правил о blocker'ах,
   заметках и решениях поверхностей.
8. Прогнать правила, собрать матрицу, собрать находки.
9. Сгруппировать по записи, внутри — по тяжести; вывести отчёт в чат.
10. Перезаписать `audit-state/<project-slug>/last-report.md` с reasoning-trace.

## Уровни тяжести

| severity | смысл | пример |
|---|---|---|
| `error` | Структурное нарушение, ломает модель | дубль slug; значение вне перечня; пустой обязательный слот у stable; vision без раздела своего набора; `web` без рода у stable; папка слоя не по роду поверхности; ядро возможности в пустоту; хаб без паспорта или без сценария; необратимое без защиты; объект без создателя |
| `warning` | Семантическое подозрение | успех без сигнала; принцип без проверки; допущение вне `Assumptions` у stable; сводка vision разошлась с реестром; две постуры без решения о разделении; синоним в имени; имя возможности не «глагол + объект»; слова интерфейса; граница-отсрочка; ограничение без источника |
| `hint` | Покрытие и стиль, не ломает | поверхность без файла возможностей; interface поверхности не начат; stable со ссылкой на draft; формальная матрица; короткое описание |

Реестр с нормой каждого правила — `references/rules.md`.

## Формат отчёта

Отчёт читает человек, который правила аудита не писал, поэтому в чат он идёт словами (`.claude/rules/guiding.md` §4, §5):

- **Итог — первым.** Одна-две фразы: что в порядке, что держит работу, что можно отложить; затем два-три хода дальше,
  один рекомендован.
- **Находка — три части:** что нарушено → чем грозит → как исправить (кто и каким шагом). Уровень — словом («ошибка»,
  «предупреждение», «подсказка»); код правила и уровень латиницей — в скобках в конце. Запись названа словами, её адрес
  — в скобках: по нему находят файл и вызывают команду. «Чем грозит» берётся из нормы правила (`references/rules.md`),
  а не сочиняется.
- **Дефект проверки — не вопрос человеку.** Находку, в которой аудит видит дефект самой проверки, а не слоя (правило
  сработало мимо своей нормы), он записывает с причиной в reasoning-trace `audit-state/<project-slug>/last-report.md` и
  называет одной строкой отчёта; вопросом выносится только то, где у человека есть выбор.
- **Группировка** — по записи; внутри — ошибки, предупреждения, подсказки; матрица — отдельным разделом в конце.

Пример — иллюстрация формы на вымышленных данных:

```
Проверка продуктового слоя проекта «Сеть направлений» (/project-audit <project-slug>).

Итог. Пользователи, объекты и границы продукта в порядке. Работу держат четыре ошибки: в vision нет раздела об
устройствах, у главной возможности кабинета партнёра нет сценария, у поверхности «Промо» не назван род, у одного
действия два имени. Предупреждение о пустой строке матрицы и подсказку о боте можно отложить.

Дальше можно:
1) закрыть четыре ошибки — рекомендую: без рода у «Промо» нет маршрута, без сценария не начать экраны кабинета;
   /project-deep-dive <project-slug>, от вас — четыре решения;
2) начать с одной — имени действия: выбрать слово из «Изменить / Редактировать», пока оно не ушло в экраны;
3) идти в interface, не правя, — ошибки останутся и повторятся в следующем прогоне.

Ошибка. В vision нет раздела «Устройства и доступность» (Devices and accessibility), а набор разделов у продукта полный.
  Чем грозит: vision — основа остальных слоёв; без раздела своего набора его не закрыть.
  Как исправить: аналитик добавляет раздел — /project-deep-dive <project-slug> --phase discovery (R-STRUCT-004, error).

Ошибка. У главной возможности (hub) кабинета партнёра «Отправить направление»
  (capability/web-partner.md:send-referral) нет сценария.
  Чем грозит: сценарии главных возможностей идут первыми — без них не стартуют ни бриф на вид кабинета, ни экраны.
  Как исправить: аналитик пишет сценарий — /interface-deep-dive <project-slug> web-partner scenario (R-CAP-006, error).

Ошибка. У веб-поверхности «Промо» (surface:promo) не назван род, а запись закрыта (stable).
  Чем грозит: род выбирает маршрут и репозиторий кода — без него неизвестно, какой слой проектирует поверхность.
  Как исправить: аналитик называет род — лендинг, сайт или кабинет (landing · site · app) —
  /project-deep-dive <project-slug> surface:promo (R-STRUCT-009, error).

Ошибка. У действия «Изменить» (action:edit) два имени: «Изменить / Редактировать».
  Чем грозит: одно действие получит два слова в интерфейсе — пользователь прочтёт их как два разных.
  Как исправить: аналитик выбирает слово, второе уходит в запрещённые синонимы (banned) —
  /project-deep-dive <project-slug> action:edit (R-GL-003, error).

Подсказка. У поверхности «Бот» (surface:tg-bot) нет файла возможностей.
  Чем грозит: не названо, что бот умеет, — сценариям и диалогам не на что опереться.
  Как исправить: аналитик заводит возможности — /project-deep-dive <project-slug> capability:tg-bot — или проверяет,
  нужна ли поверхность (R-STRUCT-008, hint).

Матрица «пользователь × объект × действие»
| пользователь | Направление (referral) | Исследование (study) |
|---|---|---|
| Медсестра партнёра (nurse-partner) | создаёт; отправляет свои (send, own) | смотрит свои (own) |
| Врач (doctor) | принимает в команде (accept, team); удаляет | — |
| Аудитор (auditor) | — | — |

Предупреждение. У пользователя «Аудитор» (user:auditor) строка матрицы пуста: ни объектов, ни действий.
  Чем грозит: пользователь заведён, а делать в продукте ему нечего.
  Как исправить: аналитик называет его возможности или проверяет, нужен ли он продукту, —
  /project-deep-dive <project-slug> (R-MX-003, warning).

Счёт: 4 ошибки, 1 предупреждение, 1 подсказка.
```

## `audit-state/<project-slug>/last-report.md`

Отчёт лежит рядом со скиллом и скоупится по проекту:

```
.claude/skills/project-audit/audit-state/<project-slug>/last-report.md
```

После каждого прогона файл перезаписывается reasoning-trace: какие правила запускал, какие записи проверил, что нашёл и
почему, как отнёс действия к видам матрицы. Это не журнал — следующий прогон перезаписывает его; отчёты разных проектов
не сталкиваются. Файл в git, чтобы команда могла читать.

```markdown
---
project: <project-slug>
ran-on: <all | kind | kind:slug | capability:surface>
files-read: <9 корневых + M файлов возможностей + соседи по правилам>
records-checked: N
vision-set: <full | minimum>
totals: { error: X, warning: Y, hint: Z }
---
```

## Границы

- **Только отчёт.** Артефакты правит `/project-deep-dive <project-slug>`, запускает его аналитик по выводу аудита.
  `stable → draft` аудит не понижает: сообщает «обязательный слот пуст при stable», понижает аналитик. Такие находки у
  проекта, чьи файлы разошлись с формой слоя, — список работ приведения к канону.
- **Один проект за прогон.** `_template/` — образец формы, не данные; чужой проект — отдельный прогон.
- **Находка — только по сработавшему правилу** `references/rules.md`; «возможно, тут что-то не так» без правила в отчёт
  не идёт. Правило, требующее суждения, помечено «чтением» и приводит цитату.
- **Соседние слои — только то, что называют правила:** листинг папок, колонки и имена interface той же поверхности,
  раздел «Решения» карты экранов. Их содержимое проверяют их аудиты, смысл межслойных связей — `/cross-audit`.
- **Без suppressions.** Правила проверяют форму записей — слот пуст или нет, ссылка есть или нет, маркер есть или нет, —
  поэтому находка повторяется, пока запись не поправлена. Эвристику, которая не подходит к случаю, аналитик разбирает по
  отчёту.
- **Инструмент аналитика.** В клиент-режиме (`entrypoint-for-business`) `/project-audit` клиенту не предлагается.
