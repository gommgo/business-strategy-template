# Чек-листы полей по kind

По разделу на каждый из 4 kind screens (flow · screen · block · shell) и
на два файла поверхности — свод `map.md` и реестр текстов `texts.md`. В
каждом разделе:

- **Поля** — что во frontmatter, что обязательно, что опционально.
- **Тело** — нужно ли yaml-дерево и какие узлы обязательны.
- **Ссылается на** — какие соседи (screens + interface).
- **Кто ссылается на это** — обратные связи.
- **Главные anti-patterns** — короткий список из README'а kind.
- **Порядок копания** — последовательность вопросов в режиме A/C.

Полные критерии — в каноне
`docs/projects/_template/screens/_template/<kind>.md` (форма-образец, общая
для всех проектов и поверхностей) и в каноне слоя
`docs/projects/_template/screens/README.md` (нотация, состояния, контракты
блоков, тексты, доступность и узкий экран). Данные поверхности проекта
живут в
`docs/projects/<project-slug>/screens/<surface>/<kind>/<slug>/index.md`,
`map.md` и `texts.md` — в корне папки поверхности. Здесь — выжимка для
скилла. Формулировки значений — маршрут, причины, правила полей, вопросы
плиток, тексты — дают владельцы (`CLAUDE.md` §3): аналитик, бизнес, для
утверждения текстов — владелец продукта.

Дальше `…/screens/` и `…/interface/` — это слои **текущей поверхности
текущего проекта**:
`docs/projects/<project-slug>/screens/<surface>/` и
`docs/projects/<project-slug>/interface/<surface>/` соответственно. Все
ссылки — в пределах одной поверхности.

## flow

**Frontmatter**: `slug`, `name`, `description`, `desktop`, `mobile`,
`transitions`, `who`, `assets`, `status`.

**Обязательные**: `slug`, `name`, `description`, `desktop` (непустой
массив), `mobile` (непустой массив, обычно ≥2), `status`.
**Опциональные**: `transitions`, `who`, `assets`.

**Тело**: yaml-дерева нет. Тело — markdown-прозa с пояснением, что
именно объединяет flow.

**Ссылается на**:
- `desktop` / `mobile` → `…/screens/<surface>/screens/<slug>/` (screens);
- `transitions[].{from,to}` → screens той же mobile-серии;
- `who` → `…/interface/<surface>/who.md` (interface).
**Кто ссылается**: `screen.mobile-of` (для screen, входящих в
mobile-серию потока).

**Anti-patterns**:
- screen / shell / situation / route / state — не путать с flow;
- шаги, ветвления и ошибки задачи — это сценарий (scenario) interface,
  поток лишь раскладывает экраны задачи по вьюпортам;
- пустой `desktop` или пустой `mobile`;
- один screen-slug в обоих списках (это разные viewport → должны быть
  разные screen);
- transitions между desktop- и mobile-screen;
- flow с одним screen и в `desktop`, и в `mobile` (это просто screen
  с `viewport: any`);
- экран `type: master-detail` без мобильной серии из двух и больше
  экранов.

**Ширины приёмки** — по вьюпорту: экраны списка `desktop` принимают на
ширинах от первого брейкпоинта дизайн-системы, списка `mobile` — ниже
него (`kb/common/acceptance-widths.yaml`, ключ `by_viewport`); поток их не
пишет, но вьюпорт экрана и его место в потоке должны совпадать.

**Порядок копания**:

1. `slug`, `name`, `description` (Other).
2. `desktop`: мультивыбор существующих screens с `viewport: desktop`
   или «нужен новый» (Other → A в screen).
3. `mobile`: мультивыбор существующих screens с `viewport: mobile`
   или «нужен новый» (Other → A в screen). Минимум 2 в режиме
   flow — иначе anti-pattern; у `master-detail` — список и детали.
4. `transitions` (опц): для каждой пары `from→to` в mobile-серии
   собрать `{from, to, trigger}`. Триггер — действие словаря
   `action.md` (опции) или событие словами (Other).
5. `who` (опц): мультивыбор из `…/interface/<surface>/who.md` + «нужен
   новый» (Other → запустить
   `interface-deep-dive <project-slug> <surface> who`).
6. `assets` (опц): см. `assets-policy.md`.
7. Anti-patterns раундом: «Это просто screen?» / «Это
   sidebar→drawer?» (бинарные опции + Other).
8. Тест-критерий: «Это объединение N screen-slug разных viewport
   вокруг одной задачи?» — варианты ✅/❌ из README.

## screen

**Frontmatter**: `slug`, `name`, `description`, `type`, `object`,
`main-task`, `key-action`, `zone`, `shell`, `blocks`, `situations`,
`who`, `route`, `params`, `access`, `url-state`, `indexed`, `viewport`,
`entrypoint`, `transitions-to-screen`, `mobile-of`, `role`, `assets`,
`status`.

**Обязательные**: `slug`, `name`, `description`, `type`, `object`,
`main-task`, `key-action`, `zone`, `shell`, `blocks`, `situations`,
`who`, `route`, `params`, `access`, `viewport`, `status`; `url-state` — у
`list` и `master-detail`. `—` допустим по правилам формы: у `service` —
`main-task`, `key-action`, `zone`; `object: —` — только с решением в
разделе «Решения» `map.md`; `key-action: —` — у экрана только для
чтения; `params: —` — у маршрута без параметров.
**Опциональные**: `indexed` (по умолчанию `false`), `entrypoint`,
`transitions-to-screen`, `mobile-of`, `role`, `assets`.

**Тело**: yaml `slot-fills` + `states`; необязательный раздел
`## Доступность` — отступления экрана от конвенций поверхности.
- `slot-fills`: каждый слот из shell заполнен (`block:<slug>`, либо
  дерево, либо `—` если опционален).
- `states`: ключи словаря состояний экрана (канон слоя, «Состояния
  экрана»: `empty-first-run` … `generating`); значение — дельта слотов
  относительно `slot-fills` или `'не применимо: причина'`. Идеальное
  состояние — сам `slot-fills`, без ключа.
- **Обязательный набор** — объединение условий канона («Обязательный
  набор»): по полям экрана (строка `type` и строка «Экран или маршрут
  целиком» таблицы типов; `params` с объектом — `not-found`;
  `access: roles` — `no-permission`), по блокам (коллекция —
  `empty-first-run`, `partial-few`; поиск или фильтр — `empty-filtered`;
  типы с ключом `screen_states` словаря компонентов), по ситуациям
  (`refusals`), по возможности (`duration: background` —
  `in-progress-background`), по решениям поверхности (работа без сети —
  `offline`, живые данные — `stale`). Набор скилл собирает сам и
  показывает списком «ключ — почему обязателен»; сборку набора делает
  утилита `states` раздела `project` скилла дизайна, пока её файла нет —
  скилл собирает набор по этому списку. Каждое обязательное состояние —
  дельта или «не применимо» с причиной; прочие ключи словаря — по
  решению аналитика.

**Ссылается на**:
- `shell` → `…/screens/<surface>/shells/<slug>/`;
- `blocks` → `…/screens/<surface>/blocks/<slug>/`;
- `situations` → `…/interface/<surface>/situation.md` (их `refusals` —
  в обязательный набор);
- `who` → `…/interface/<surface>/who.md`;
- `zone` → `…/interface/<surface>/zone.md`;
- `object`, объектный тип в `params` → `object.md` проекта;
- `main-task` → `capability/<surface>.md` той же поверхности;
- `key-action`, атрибут `action=` в дереве, `trigger` перехода →
  `action.md` проекта;
- `transitions-to-screen[].to` → screens;
- `mobile-of` → flow;
- `block:<slug>` внутри `slot-fills`/`states` → screens-blocks;
- `data:<slug>` внутри деревьев → `…/interface/<surface>/data-items.md`,
  `data:<slug>.<атрибут>` — атрибут объекта `data-items.object`;
- `text:<key>` → строка `…/screens/<surface>/texts.md`;
- `ui:<Тип>` → словарь компонентов или расширение проекта
  (`tree-notation.md`).
**Кто ссылается**: `flow.desktop`, `flow.mobile`,
`block.used-by-screens` (зеркало), `screen.transitions-to-screen`
(другие screens), свод `map.md` (строки «Карты экранов» и «Маршрутов»),
`tiles[].link` блоков, `pages.screen` FSD-карты поверхности (путь — её
`route`, охрана — её `access`).

**Anti-patterns**:
- block / shell / flow / route / data-слой — не путать;
- экран без объекта и роли («главная», «обзор») без решения в
  `map.md`;
- облик в `slot-fills` (цвета, пиксели, шрифты, `variant`, `size`);
- оси контекста приложения (тема, бренд, плотность, направление
  письма) как атрибуты узлов;
- breakpoints в `slot-fills`;
- FSD-имена (`widget`, `feature`) в дереве или frontmatter;
- `state` без явного override (пустая секция); обязательное состояние без
  дельты и без «не применимо: причина»;
- ключ `states` вне словаря; `not-found` вместо `archived-deleted` у
  архивного объекта; состояния приложения на экране вместо раздела
  каркаса;
- литерал текста в дереве `stable`-экрана;
- маршрут вне реестра `map.md`;
- расхождение `screen.blocks` и реально использованных `block:` в
  `slot-fills`/`states`;
- `screen.situations`, не покрывающий ситуации, чьи ux-substrates
  есть на этом экране (через `block.ux-substrates`).

**Порядок копания** (порядок этапа «экраны» — `SKILL.md`, «Сводка
состояния»):

1. `name`, `description` (Other); `slug` скилл выводит из `name`.
2. `type`: десять опций закрытого списка канона («Экран: тип, карта и
   маршрут»), в описании опции — каркас и строка обязательных состояний
   типа. При четырёх и больше экранах поверхности скилл показывает,
   если типы все одинаковы: это признак шаблона вместо проектирования.
3. `object`: опции — объекты `object.md` + `—` («экрана без объекта» —
   решение: скилл спрашивает почему и пишет строку раздела «Решения»
   `map.md`).
4. `main-task`: опции — возможности `capability/<surface>.md` (у
   `service` — `—`).
5. `key-action`: опции — действия `action.md`, чьи `objects` включают
   объект экрана + `—` (экран только для чтения, `service`).
6. `zone`: опции — зоны `…/interface/<surface>/zone.md` (у `service` —
   `—`).
7. `shell`: опции = существующие shell-slug'и + «нужен новый»
   (Other → A в shell).
8. `viewport`: три опции enum `desktop` / `mobile` / `any`.
9. `route`: Other (URL `/foo/:id` или именованный view
   `modal:archive-confirm`); маршрут входит в закрытый реестр
   поверхности. `params` скилл выводит из `route` (`:id` → параметр, тип
   — объект глоссария) и показывает одной строкой для контроля.
10. `access`: опции `public` / `authenticated` / `roles` (`roles` — роли
    `who` этого экрана).
11. `url-state`: мультивыбор `tab` / `page` / `filters` / `sort` /
    `view` / `panel` или `—`; у `list` и `master-detail` обязателен. В
    адресе нет несохранённого ввода и секретов.
12. `who`: мультивыбор из `…/interface/<surface>/who.md` + «нужен новый»
    (Other → запустить
    `interface-deep-dive <project-slug> <surface> who`).
13. `situations`: мультивыбор из `…/interface/<surface>/situation.md` +
    «нужна новая» (Other → запустить
    `interface-deep-dive <project-slug> <surface> situation`).
14. `blocks`: мультивыбор из существующих screens-blocks + «новый»
    (Other → A в block). Должен включать всё, что появится в
    `slot-fills`/`states`.
15. `indexed`, `entrypoint` (опц): опции `true` / `false`.
16. `mobile-of` (опц): если `viewport: mobile` — выбор flow, в
    который входит. Иначе `—`.
17. `role` (опц): для участников flow — `master` / `detail` /
    `filters` / Other.
18. `transitions-to-screen` (опц): по переходу — `to` (опции
    экранов), `trigger` (действие словаря — опции, событие — Other),
    `keeps` (опции — строки раздела «Переход» `map.md` + Other), `back`
    (как вернуться — Other, или опция `irreversible`).
19. **Тело — `slot-fills`** (раунд за раундом, по одному слоту):
    - для каждого слота shell из соседнего файла:
      - опции: «`block:<slug>` из существующих» / «дерево» (Other) /
        «оставить `—`» (если слот опционален в shell);
      - если дерево — углубление по узлам по `tree-notation.md` (типы
        словаря, `layout:`-узлы, ключи текстов).
20. **Тело — `states`** — по обязательному набору, ключ за ключом:
    опции — «дельта» (узлы по `tree-notation.md`) / «не применимо»
    (причина — Other, слова аналитика). Затем — прочие ключи словаря по
    желанию аналитика. Тексты состояний — строки реестра с ролями канона
    («Частные правила»: пустые — `empty` и `action`; `error-load` —
    `error`, `inline-message` или `banner`; `loading-initial`,
    `generating` — `status`; `no-permission`, `not-found` — `title`,
    `body`, `action`).
21. **`## Доступность`** (опц): у узла с перетаскиванием (например
    `ui:FileUpload`) — путь одним указателем и с клавиатуры; особая
    фокусировка экрана (Other — слова аналитика).
22. `assets` (опц): см. `assets-policy.md`.
23. Anti-patterns раундом.
24. Тест-критерий: «Одна точка маршрута с типом, объектом и главной
    задачей, с заполненными слотами shell и описанными состояниями
    обязательного набора?» — варианты ✅/❌ из формы.

**После правки** — пересчитать `screen.blocks` (все `block:<slug>` из
слотов и `states`); пересобрать строки экрана в своде `map.md`; у нового
ключа `text:` — строка реестра `texts.md` черновиком (`assumed`).

## block

**Frontmatter**: `slug`, `name`, `description`, `interface-block`,
`ux-substrates`, `data`, `slots`, `source`, `form`, `collection`,
`tiles`, `used-by-screens`, `assets`, `status`.

**Обязательные**: `slug`, `name`, `description`, `interface-block`,
`ux-substrates` (непустой), `status`; контракты — по составу дерева:
`form` — у блока с субстратом `ввод` или `выбор`; `collection` — у блока
с `ui:Table`, `ui:List`, `ui:TreeView` или повторяемой `ui:Card`;
`tiles` — у блока с `ui:KpiTile`.
**Опциональные**: `data`, `slots`, `source` (по умолчанию `screen`),
`used-by-screens`, `assets`.

**Тело**: yaml `tree` с внутренними областями (`block-header`,
`block-body`, `block-footer`, `block-aside`). Минимум — `block-body`. У
блока со своим источником (`source: own`) — ещё раздел `states`: ключи
`loading-initial`, `error-load`, у коллекции — `empty-first-run`,
`empty-filtered`, `partial-few`; значение — дельта внутренних областей
или `'не применимо: причина'`.

**Ссылается на**:
- `interface-block` → `…/interface/<surface>/block.md` (тот же slug,
  ровно один);
- `ux-substrates` → `…/interface/<surface>/ux-substrate.md` (зеркало
  `interface/<surface>/block.md.ux-substrates`);
- `data: { <param>: data:<slug> }` →
  `…/interface/<surface>/data-items.md`;
- `used-by-screens` → screens (зеркало; источник — реальные ссылки
  `block:<slug>` в screens);
- `block:<slug>` внутри `tree` через `slots` → другие screens-
  blocks (если блок-контейнер);
- `data:<slug>` внутри `tree`, `form.field`, `tiles.value` →
  `…/interface/<surface>/data-items.md` (атрибут — через
  `data-items.object`);
- `collection.filters`, `collection.sort` → атрибуты объекта
  (`object.md`, «Атрибуты»); `collection.bulk`, `tiles.action`, атрибут
  `action=` → `action.md`;
- `form.error`, `tiles.no-data`, `text:<key>` в дереве → `texts.md`;
- `tiles.link` → screens.
**Кто ссылается**: `screen.blocks`, `screen.slot-fills`,
`screen.states`.

**Anti-patterns**:
- screen / shell / один компонент / data-слой / FSD-узел — не путать;
- расхождение `ux-substrates` с зеркалом в `interface/<surface>/block.md`;
- дерево без `block-body`;
- облик в дереве (цвет, тень, шрифт, пиксели, `variant`, `size`);
- оси контекста приложения (тема, бренд, плотность, направление
  письма) как атрибуты узлов;
- breakpoints в дереве;
- один и тот же `data:<slug>` под разными именованными слотами;
- индикаторы и состояния в `tree` блока: у блока со своим источником —
  его раздел `states`, у остальных — `states` экрана;
- форма без `form`, коллекция без `volume`, плитка без базы сравнения;
- тип, длины или перечень поля в `form` вместо ссылки на атрибут
  объекта.

**Порядок копания**:

1. `name`, `description` (Other); `slug` — совпадает с interface-блоком.
2. `interface-block`: опции = существующие interface-block-slug'и
   (читать из `…/interface/<surface>/block.md`) + «нужен новый» (Other →
   предложить запустить
   `interface-deep-dive <project-slug> <surface> block:<slug>`).
   **По канону slug в screens совпадает с slug в interface.**
3. `ux-substrates`: автоматически предложить весь список
   `ux-substrates` выбранного interface-block по умолчанию (для
   зеркала). Аналитик может скорректировать; при несовпадении —
   обработать через политику зеркал (см. SKILL.md).
4. `data` (опц): мультивыбор data-items из interface + Other для
   нового; формат `{ <param>: data:<slug> }`. Anti-pattern: один
   data: под разными `<param>`.
5. `slots` (опц): нужны ли именованные слоты под вложение `block:`
   (контейнер блок). Опции «нет» / «да» (Other → перечислить имена).
6. `used-by-screens` (опц): зеркало; в режиме A заполняется по мере
   того, как screens начинают на него ссылаться. Скилл предлагает
   текущий список (выводимо из screens), аналитик подтверждает.
7. **Тело — `tree`** (раунд за раундом, по областям):
   - Начать с `block-body` (обязательная) — по узлу на каждый
     объявленный субстрат: тип `ui:` из словаря по потребности
     (`tree-notation.md`), раскладка — `layout:`-узлы, атрибуты — из
     закрытого списка.
   - Затем `block-header` (опц): обычно `layout:row` с поиском
     (`ui:SearchInput`) и кнопками.
   - Затем `block-footer` (опц): обычно пагинация (`ui:Pagination`) /
     `layout:row` с действиями.
   - Затем `block-aside` (опц): для боковых дорожек блока.
   - Проверка покрытия: каждый объявленный `ux-substrate` должен
     быть представлен узлом дерева (по типу и назначению узла).
8. `source` (опц): опции `screen` / `own` — блок грузит данные сам,
   отдельно от экрана (плитка дашборда, панель с другим источником). При
   `own` — раздел `states` блока по набору из «Тела».
9. **Контракты** — по составу дерева (форма `block.md`, канон слоя
   «Контракты блоков»):
   - `form` — запись на поле: `field` (опции — атрибуты объекта через
     `data:`), `control` (тип узла поля в дереве; выбор по числу
     вариантов и выборов — ux 04/06 §1), `required` (`—` / `true` /
     `false`), `format` (Other или `—`), `validation` (правило словами и
     момент проверки — Other; правило-инвариант домена — ссылкой на него,
     формулирует архитектор), `error` (ключ `text:` роли `error`),
     `default` (значение или «нет: причина»), `autocomplete` (токен или
     «нет: причина»). Тип, длины и перечень не повторяются — они у
     атрибута объекта.
   - `collection` — `task` (опции `find` / `compare` / `one-record` /
     `act`), `volume` (`typical`, `max` — числа от аналитика), `filters`
     (атрибуты объекта или `—`), `sort` (атрибут и направление), `bulk`
     (действия словаря или `—`), `narrow` (пять опций способа на узком
     экране — ux 09/03 §2.2). По `volume.max` скилл называет, что
     требуют пороги ux 04/01 §2 — пагинация, поиск или фильтр, управление
     колонками, `url-state` экрана, массовые действия и экспорт, — и
     сверяет с деревом.
   - `tiles` — запись на плитку: `value` (`data:`), `question` (вопрос
     роли — формулирует бизнес или аналитик), `precision`, `baseline`,
     `good` (опции `up` / `down` / `target`), `thresholds`, `delta`,
     `period`, `link` (экран), `action` (действие или `—`), `no-data`
     (ключ `text:`). Незаполненное поле — решение «показатель не
     выводить»: скилл спрашивает, а не заполняет.
10. `assets` (опц): см. `assets-policy.md`.
11. Anti-patterns раундом.
12. Тест-критерий: «Раскрытие одного interface-block в композицию
    компонентов — не экран, не каркас, не один компонент?» —
    варианты ✅/❌ из формы.

**После правки `ux-substrates`** — сравнить с
`…/interface/<surface>/block.md`; при расхождении — политика зеркал (см.
SKILL.md).

## shell

**Frontmatter**: `slug`, `name`, `description`, `slots`, `responsive`,
`assets`, `status`.

**Обязательные**: `slug`, `name`, `description`, `slots` (непустой
объект; у каждого слота — `required`, `accepts`, `landmark`), `status`.
**Опциональные**: `responsive`, `assets`.

**Тело**: yaml `tree` — каркас (шапка, навигация, side / main / detail /
overlay и т.п.) с атрибутом `fills=$<slot>` на узле каждого слота из
`slots`; слотовые узлы пусты. Своё содержимое у каркаса — навигация
(`ui:Sidebar items=nav`, `ui:TopBar`, `ui:BottomNav` — пункты из раздела
«Навигация» `map.md`), поиск по приложению, один узел помощи, меню
пользователя. У основного каркаса — раздел `## Состояния приложения`.

**Ссылается на**: `map.md` (пункты навигации); ключи `text:` → `texts.md`.
**Кто ссылается**: `screen.shell`.

**Anti-patterns**:
- screen / block / узел раскладки / карта экранов — не путать;
- содержимое экранов в shell-tree (конкретный блок, текст экрана);
- оси контекста приложения (тема, бренд, плотность, направление
  письма) как атрибуты узлов shell;
- пиксели / raw-CSS в `tree` или `responsive`;
- слот без `accepts`, `required` или `landmark`; ни одного или два
  слота с `landmark: main`;
- `responsive`-behaviour, не покрытое допустимыми значениями; `hidden`
  у слота, чьи функции больше нигде не доступны;
- структурный адаптив через `responsive` (когда меняется число
  экранов, а не облик слота) — это `flow`;
- навигация как слот, который заполняет экран; боковая панель экрана
  как навигация приложения;
- два узла помощи; состояния приложения на экранах вместо раздела
  каркаса;
- shell без `slots`.

**Порядок копания**:

1. `name`, `description` (Other); `slug` скилл выводит. Каркасов
   несколько: основной (рабочие экраны), входа, полноэкранный (мастер,
   полотно).
2. `slots` (раунд за раундом, по одному слоту):
   - имя слота (Other, kebab-case);
   - `required`: опции `true` / `false`;
   - `accepts`: опции `block` / `tree` / `block | tree` /
     `block (modal/drawer)`;
   - `landmark`: опции `main` / `navigation` / `complementary` /
     `region` / `—`; ровно один слот — `main`;
   - повторять до «всё, больше слотов нет» (Other).
3. `responsive` (опц): по каждому диапазону (`xs` / `sm` / `md` / `lg` /
   `xl` — имена диапазонов, границы — токены `breakpoint.*`
   дизайн-системы, таблица — канон слоя) — поведения слотов из enum
   (`visible` / `drawer-via-burger` / `overlay` / `stacked` / `hidden` /
   `fullscreen` / `bottom-sheet`). Спросить: «Меняется ли что-то на этом
   диапазоне?» Оверлей на узкой ширине — `fullscreen` или
   `bottom-sheet`; планшетная ширина — диапазон `sm`: поведение слотов
   на нём или «не применимо» с причиной в теле каркаса. `hidden` —
   только когда функции слота доступны иначе.
4. **Тело — `tree`**: каркас из `layout:`-узлов (`layout:stack` /
   `layout:row` / `layout:layer`) и типов словаря. Навигация — узел
   основного каркаса: вариант (боковая панель, верхняя панель, нижняя
   панель вкладок) — по числу разделов, типу приложения и частоте
   переключений (ux 02/02 §1.6); пункты — корневые зоны interface по
   `order`. Узел помощи — один. Каждый узел, обёртывающий слот, получает
   `fills=$<slot>`; **слотовые узлы — пустые**.
5. **`## Состояния приложения`** (основной каркас): строка на
   `service-unavailable`, `maintenance`, `session-expiry`,
   `connection-lost`, `demo-mode` — где видно, форма (строки развилки
   ux 04/08 §2.2), ключи текстов; состояния нет у продукта — «не
   применимо: причина». Нужен ли сценарий истечения сессии — раздел
   `MVP` vision: нет решения — вопрос в заметке, а не догадка.
6. `assets` (опц): см. `assets-policy.md`.
7. Anti-patterns раундом.
8. Тест-критерий: «Объявление набора слотов, навигации и поведения на
   ширинах — не сам route с контентом, не блок и не узел раскладки?» —
   варианты ✅/❌ из формы.

## map.md

Singleton папки поверхности `…/screens/<surface>/map.md`, форма —
`docs/projects/_template/screens/_template/map.md`.

**Frontmatter**: `surface`, `status`.

**Разделы**: свод — `## Карта экранов`, `## Маршруты`, `## Навигация`
(собирается из полей экранов, зон interface и дерева основного каркаса;
руками по смыслу не авторится); решения поверхности — `## Переход`,
`## События`, `## Конвенции`, `## Узкий экран`, `## Решения`.

**Ссылается на**: экраны поверхности (свод), зоны
`…/interface/<surface>/zone.md` и основной каркас (навигация),
`action.md` (строки «Событий»), vision (`MVP`, `Devices and
accessibility`).
**Кто ссылается**: `screen.transitions-to-screen[].keeps` (обещание
«Перехода»), `screen.object: —` (строка «Решений»), контракт генерации
макета (карта экранов и закрытый список маршрутов), `/screen-audit`.

**Anti-patterns**: маршрут или экран в своде, которого нет в полях
экранов; ручная правка свода вместо правки экрана; порядок и состав по
впечатлению о продукте; облик (цвет статуса, вид баннера); шаги задачи
вместо того, что переживает переход.

**Порядок копания** (место в этапе «экраны» — `SKILL.md`, «Сводка
состояния»):

1. **`## Переход` — первым, до экранов** (ux 13/04 §13): что переживает
   переход (фильтры, сортировка, страница, выделение, прокрутка,
   вкладка, черновик формы, шаг мастера — перечень ux 05/05 §9), где
   живёт, срок, что переживает, как проверить. Строки — слова аналитика;
   скилл предлагает перечень вопросом, не ответом.
2. **`## Решения`** — по мере решений: разделение приложений (число «да»
   по вопросам ux 13/04 §17 — из заметки поверхности), вариант навигации
   (ux 02/02 §1.6), способ реализации мобильного (адаптив, отдельная
   мобильная версия, PWA, нативное; отвергнутые — с причиной; ux 09/01
   §2), работа без сети, экраны без объекта. У строки — почему и кто
   теряет; формулирует аналитик или бизнес.
3. **Свод** — пересобрать после каждой правки экранов: строка «Карты
   экранов» и «Маршрутов» на экран, служебные экраны — своими строками,
   строка-запрет «маршрутов вне списка нет»; «Навигация» — уровни и
   пункты из зон, видимость — из `who` и `access` экранов. Сборка свода
   — утилита `screen_map` раздела `project` скилла дизайна; пока её
   файла нет — по форме, раздел «Свод» `screens/_template/map.md`.
4. **`## События`** — строка на каждое действие `action=` деревьев
   экранов и на событие системы: форма сообщения (семь форм ux 04/08
   §2.1 или «ничего: результат виден на экране»), «почему» — строка
   развилки ux 04/08 §2.2; одно событие — одна форма, ошибка тостом не
   показывается.
5. **`## Конвенции`** — решения «одно на продукт», которые исполняет
   дизайн-система (позиции — `kb/ux/README.md`, «Реестр разрешённых
   противоречий»), и строки «Доступность»: фокус при открытии и
   закрытии оверлея, удалении строки, смене маршрута и ошибке формы;
   объявления; помощь в одном месте; повторный ввод и вставка в поля
   входа; лимит времени сессии.
6. **`## Узкий экран`** — строка на каждый тип экрана поверхности и
   строка каркаса: пять вопросов ux 09/01 §4.2; что оставить — по рангам
   атрибутов объекта; сценарий, которого на узкой ширине сознательно
   нет, — строка урезания с основанием и сроком пересмотра. Vision
   записал «только десктоп» — раздел не заполняется.

**Для stable**: авторские разделы полны (у строки — основание и, где
нужно, проверка), свод совпадает с полями экранов, у каждого действия
экранов есть строка «Событий».

## texts.md

Реестр текстов интерфейса поверхности `…/screens/<surface>/texts.md`,
форма — `docs/projects/_template/screens/_template/texts.md`. Ведёт его
этап «тексты интерфейса» (`SKILL.md`).

**Колонки**: `key` · `role` · `text` · `maxlen` · `action` · `object` ·
`group` · `context` · `status`; второй язык — колонка `text-<locale>`
(список языков — у FSD-карты поверхности, `shared-lib.md`).

**Обязательные**: `key`, `role`, `text`, `status`; `maxlen` — для
`checked`; `context` — у омонимов, строк с подстановкой и строк с
ограничением длины.

**Ссылается на**: `action.md` (`action`), `object.md` (`object`).
**Кто ссылается**: `text:<key>` деревьев экранов, блоков и каркасов,
`form.error`, `tiles.no-data`, ключи текстов раздела «Состояния
приложения» каркаса; ключи строк локализации FSD-карты поверхности.

**Anti-patterns**: ключ по значению, а не по месту (`list.button1`);
роль строки не совпала с ролью части компонента; синонимы из `aliases`
объекта или `banned` действия; число, имя или дата литералом вместо
данных и ICU; тексты страниц сайта, юридические тексты, данные ячеек и
полей; облик текста; заглушки.

**Порядок работы** (этап «тексты интерфейса»):

1. Ключи деревьев без строки — завести строки: `key` из дерева; `role` —
   из раздела `text_roles` словаря компонентов по части, под которой
   стоит узел (текст вне компонента — по месту: заголовок экрана —
   `title`); `object`, `action` — из узла и экрана; `group` — строки
   одного меню или набора статусов объекта.
2. `text` — черновик агента «допущением», статус `assumed`: из
   глоссария объектов (`name`, без `aliases`), словаря действий (`verb`,
   `past`, без `banned`), голоса продукта и правил ux 07/02. Голоса
   продукта нет — долг и предложение `/design-deep-dive <project-slug>`
   (уровень продукта).
3. `maxlen` — ширина компонента дизайн-системы (после первого входа
   дизайна кабинета) или ориентиры ux 07/05 §4.6.
4. Проверка — `checked`: словарь запретов ux 07/06 по роли строки,
   межстрочные проверки ux 07/06 §7.3, `maxlen` как ворота. Линтер
   `copy_lint.py` берёт роль строки входом; где у него нет профиля жанра
   интерфейса, строку сверяют со словарём запретов глазами.
5. `approved` — только словом владельца продукта (`CLAUDE.md` §3); скилл
   предлагает, не утверждает. Правка текста возвращает строку в
   `assumed`.
