# Три режима ведения сеанса

`screen-deep-dive` поддерживает три явно различающихся сценария входа.
Скилл выбирает режим по виду args при запуске и далее ведёт сеанс,
комбинируя точечные шаги. Отдельные сценарии — этап «тексты интерфейса»
(раздел «Тексты интерфейса») и папка поверхности, чьи файлы разошлись с
формой слоя (раздел «Привести к канону»).

## A. Новая сущность

**Сигнал**: args = `<kind>` или `<kind>:<новый-slug>` (когда папка
`docs/projects/<project-slug>/screens/<surface>/<kind>/<slug>/` ещё не
существует).

### Шаги

1. Прочитать канон README.md соответствующего kind в
   `docs/projects/_template/screens/_template/<kind>.md`: секции `Критерии`,
   `Что НЕ`, `Тест-критерий`, `Форма frontmatter`, anti-patterns.
2. Раунд 1 `AskUserQuestion` — фундамент:
   - `name` (Other) — человекочитаемое; `slug` скилл выводит из имени и
     показывает одной строкой для контроля (`.claude/rules/naming.md`);
   - `description` (Other) — одна-две строки.
3. Создать папку
   `docs/projects/<project-slug>/screens/<surface>/<kind>/<slug>/` и
   записать `<slug>/index.md` с заполненными
   `slug + name + description + status=draft` и обязательными полями,
   где значение уже известно. Поля, где прочерк — решение аналитика
   (`object`, `main-task`, `key-action`, `zone` экрана), остаются пустыми
   до его ответа; ссылочные массивы без значения — пустыми.
4. Раунд 2+ `AskUserQuestion` — батч по доменным слотам kind в
   порядке `field-checklists.md`. До 4 вопросов в раунде; перемежать
   опции (anti-patterns, enum'ы, существующие slug-и) и Other
   (значения).
5. По мере заполнения — если в поле нужна ссылка на ещё не
   существующую сущность screens, отработать **stub** (см. SKILL.md):
   создать stub-папку, записать state-заметку с открытым вопросом,
   продолжить. Если ссылка — в interface, **stub не заводить**:
   предложить аналитику запустить `interface-deep-dive`, оставить
   `**blocker**` в state.
6. После frontmatter — переход к дереву (только для screen / block /
   shell; flow не имеет yaml-тела). Раунд за раундом по слотам и
   внутренним областям с опциями по `tree-notation.md` (типы словаря по
   потребности, `layout:`-узлы, атрибуты закрытого списка); тексты —
   ключами `text:<key>` со строкой реестра черновиком. У экрана затем —
   `states` по обязательному набору, у блока — контракты по составу
   дерева (`field-checklists.md`).
7. После всех слотов — раунд `AskUserQuestion` по `Тест-критерий`:
   ✅/❌ варианты как опции. Аналитик подтверждает.
8. Применить чек-лист `draft-stable.md`. Если все 6 ✅ — предложить
   повышение в stable. После правки экрана — пересобрать свод `map.md`.
9. Записать
   `../entrypoint/state/projects/<project-slug>/screens/<surface>/<kind>/<slug>.md`,
   если есть что (открытые вопросы, доменные решения, что копать
   дальше).

### Пример раунда (screen, после фундамента)

Иллюстрация формы вопросов, не образец ответов. Скилл предлагает четыре
вопроса разом:

- **type** — три-четыре типа закрытого списка, ближайших по сценарию и
  блокам экрана (в описании опции — каркас и обязательные состояния
  типа), остальные — через Other.
- **object** — объекты `object.md`, которые называют ситуации экрана, +
  `—` («экран без объекта» — тогда вопрос «почему» и строка «Решений»
  `map.md`).
- **main-task** — возможности `capability/<surface>.md`, которые
  реализуют ситуации экрана.
- **route** — Other (свободная форма): URL вида `/studies/:id` или
  именованный view `modal:archive-confirm`; `params` скилл выводит из
  маршрута и показывает строкой для контроля.

### Пример раунда (block, после фундамента)

- **interface-block** — выбрать из существующих interface-block-slug'ов
  (читается из
  `docs/projects/<project-slug>/interface/<surface>/block.md`); если
  нет — Other с предложением
  `interface-deep-dive <project-slug> <surface> block:<slug>`. По канону
  slug блока в screens совпадает с slug interface-блока.
- **ux-substrates** — мультивыбор; скилл показывает список субстратов
  выбранного interface-блока и предлагает их все по умолчанию (чтобы
  совпадало с зеркалом).
- **source** — опции `screen` / `own`: «грузит ли блок данные сам,
  отдельно от экрана?» (при `own` — раздел `states` блока).
- Anti-pattern check — «Это, случайно, не один компонент
  (`ui:Button`)? Не весь экран?» — опции бинарные.

Следующим раундом — контракт по составу дерева: у коллекции — `task`
(четыре опции) и `volume` (числа — Other), у формы — поле за полем, у
плиток — вопрос, база и пороги (формулирует бизнес или аналитик).

## B. Сырьё

**Сигнал**: args = свободный текст, скриншот UI, URL, выгрузка из
Figma, описание макета словами, либо комбинация. См. `raw-input.md`.

### Шаги

1. Изучить материал внимательно. Картинки — посмотреть содержательно
   (что за макет, какие зоны, что в них, есть ли master/detail,
   модалки, тулбары). URL — `WebFetch` для получения текста страницы /
   описания. Текст — прочитать.
2. Извлечь кандидатов на сущности:
   - **shell** — каркас (шапка, навигация, side / main / detail /
     overlay); один материал может намекать на один shell;
   - **screen** — конкретный route/view (что в каких слотах shell) и его
     тип по закрытому списку канона;
   - **block** — выделяемые единицы внутри слотов (панель действий с
     таблицей, панель фильтров, превью, …);
   - **flow** — если в материале есть и desktop, и mobile-разрезы
     одного сценария;
   - **строки `map.md`** — если материал говорит, что переживает
     переход, как сообщается событие или как экран живёт на телефоне.
3. Фильтр — anti-patterns из README'ев kind (канон
   `docs/projects/_template/screens/_template/<kind>.md`): «один компонент»
   — не block, «sidebar→drawer» — не flow, «route с контентом» —
   screen (не shell), и т.п.
4. Через чат показать план:
   ```
   Из материала вижу:
   - 1 shell-кандидат: <slug>
   - 2 screen-кандидата: <slug>, <slug>
   - 4 block-кандидата: <slug>, <slug>, <slug>, <slug>
   - flow: похоже на desktop-only, не нужен
   Сохранить картинку как <surface>/assets/screen/<slug>/<имя>.png? (y/n)
   Так?
   ```
5. Раунд `AskUserQuestion` — подтвердить план / попросить корректировку
   через Other / решить про сохранение ассета.
6. По подтверждению:
   - сохранить картинку как `<surface>/assets/<kind>/<slug>/<имя>.png`
     (см. `assets-policy.md`);
   - завести **stub-папки** в
     `docs/projects/<project-slug>/screens/<surface>/<kind>/<slug>/`
     (минимум `slug + name + description + status=draft`,
     `assets: ['<имя>.png']` где применимо);
   - создать state-заметки с открытыми вопросами «извлечено из сырья
     — уточнить <что>».
7. Через `AskUserQuestion` — выбрать, какую сущность углубить первой.
   Естественный порядок: раздел «Переход» `map.md` → shell → screen →
   block (`raw-input.md`).
8. Перейти в режим C на выбранной. Повторить для остальных.

### Что НЕ делать в режиме B

- Не объявлять извлечённое «зафиксированным». Это кандидаты до
  подтверждения аналитика.
- Не угадывать `route`, текст label кнопок, точное число слотов по
  скриншоту — только структуру; компонент называется типом словаря по
  потребности, а не подписью со скриншота.
- Не выдумывать кандидатов, которых в материале нет, «потому что
  обычно бывают» (типа «наверное, нужен footer»).
- Не лазить в web без явной просьбы. Если аналитик показывает скрин
  конкурента и просит «найди ещё похожие» — тогда WebSearch (см.
  `assets-policy.md`).
- Не сохранять картинку в репо без согласия аналитика.

## C. Углубление

**Сигнал**: args = `<kind>:<slug>` существующей записи, либо аналитик
выбрал из сводки.

### Шаги

1. Прочитать
   `docs/projects/<project-slug>/screens/<surface>/<kind>/<slug>/index.md`
   целиком (frontmatter + yaml-дерево в теле).
2. Прочитать
   `../entrypoint/state/projects/<project-slug>/screens/<surface>/<kind>/<slug>.md`,
   если есть.
3. Прочитать соседей (interface-файлы — из той же поверхности того же
   проекта, `docs/projects/<project-slug>/interface/<surface>/`):
   - для `screen` — соответствующий `shell`, ссылающиеся `block`-и,
     `interface/<surface>/situation.md` для перечисленных ситуаций (их
     частота и отказы), `interface/<surface>/who.md` для участников,
     `zone.md`; в продуктовом слое — `object.md`, `action.md`,
     `capability/<surface>.md` (паспорт главной задачи: `duration`);
     `map.md` и строки `texts.md` его ключей;
   - для `block` — `interface/<surface>/block.md` (зеркало
     `ux-substrates`), `interface/<surface>/ux-substrate.md` для
     перечисленных субстратов, screens, которые ссылаются на этот блок
     (для `used-by-screens`);
   - для `shell` — все screens, которые на него ссылаются;
   - для `flow` — все его desktop/mobile screens.
4. Применить канон README соответствующего kind
   (`docs/projects/_template/screens/_template/<kind>.md`): секции
   `Критерии`, `Что НЕ`, `Тест-критерий`. Найти:
   - пустые обязательные слоты frontmatter;
   - подозрения по anti-patterns (облик в дереве, breakpoints в
     `slot-fills`, FSD-имена, и т.п.);
   - рассинхрон зеркал (`block.ux-substrates` ↔ interface,
     `screen.blocks` ↔ реально использованные `block:` в дереве,
     `block.used-by-screens` ↔ ссылки в screens);
   - битые ссылки на screens / interface / продуктовый слой / assets;
   - дыры в дереве (нет обязательной внутренней области, субстрат без
     узла, `ui:` вне словаря, атрибут вне списка, литерал текста);
   - непокрытый обязательный набор состояний; контракт блока, которого
     требует состав дерева (`form`, `collection`, `tiles`); ключ `text:`
     без строки реестра; свод `map.md`, разошедшийся с экранами.
5. Раунд `AskUserQuestion` (до 4 вопросов) — точечно по найденному:
   - дыры frontmatter — заполняем через Other / выбор существующих;
   - дыры дерева — выбор типа словаря / `layout:`-узла по
     `tree-notation.md`, значения атрибутов — из закрытого списка;
   - дыры набора состояний — по ключу: «дельта» / «не применимо»
     (причина — Other);
   - anti-pattern-подозрения — опции «да, anti-pattern» / «нет,
     вот почему» (через Other);
   - битые ссылки screens — опции «исправить на <варианты>» /
     «удалить» (если поле допускает) / «оставить stub»;
   - битые ссылки interface — опции «запустить
     `interface-deep-dive <project-slug> <surface> <kind>:<slug>`, я
     подожду» / «удалить ссылку» / «заменить на существующий
     interface-slug»;
   - рассинхрон зеркала `block.ux-substrates` — опции «брать
     screens-вариант» (предложить запустить interface-deep-dive) /
     «брать interface-вариант» (правка screens) / «расхождение
     смысловое» (state-blocker).
6. Применить ответы: правка файла записи, обновление state-заметки,
   пересчёт зеркал где применимо (например, `screen.blocks` ↔
   `slot-fills` пересчитывается автоматически), пересборка свода
   `map.md` после правки экрана.
7. После раунда — повторно прогнать чек-лист `draft-stable.md`.
   Если все 6 ✅ — предложить повышение в stable.
8. Если осталась хотя бы одна дыра или подозрение — следующий раунд.

### Когда переходить от C к завершению

- Все 6 пунктов чек-листа ✅ → предложить stable, по подтверждению
  поменять status.
- Остался `**blocker**`-вопрос, на который аналитик сейчас ответить не
  может → зафиксировать в state-заметке, оставить `status: draft`,
  выйти из углубления этой сущности; предложить другую или сводку.

## Стиль вопросов: правила

### Когда давать опции

| ситуация | формат |
|---|---|
| anti-pattern из `Что <kind> НЕ` | две опции: «соответствует anti-pattern» / «не соответствует» (объяснить почему через Other) |
| перечисление канона (`type`, `viewport`, `access`, `url-state`, `entrypoint`, `indexed`, `accepts`, `landmark`, `behaviour`, `source`, `level`, `collection.task`, `collection.narrow`, `tiles.good`) | значения перечня опциями; в вопросе — до четырёх опций (лимит инструмента): у длинного перечня — самые вероятные по контексту, остальные — через Other |
| тест-критерий из `Тест-критерий` | опции из примеров ✅/❌, аналитик соотносит свой случай |
| выбор существующего slug соседа, объекта, действия, возможности | по опции на каждый существующий + «нужен новый» (Other) |
| выбор `ui:` для узла дерева | опции — типы словаря из группы, чья потребность (`purpose`) ближе к словам аналитика; имя не выводится из слов (`tree-notation.md`) |
| выбор `block:<slug>` для слота screen | опции — существующие блоки + «новый» (Other → A в block) |
| обязательное состояние набора | «дельта» / «не применимо» (причина — Other) |
| зеркало `block.ux-substrates` расходится с interface | три опции: «брать screens» / «брать interface» / «расхождение смысловое — blocker» |

### Когда не давать опции, только Other

| поле | почему |
|---|---|
| `name` | человекочитаемое имя — формулировка аналитика |
| `description` | смысл записи — слова аналитика |
| `route` | URL/именованный view — доменная семантика, не угадывать |
| причина «не применимо», правило поля `validation`, вопрос, база и пороги плитки, `volume` коллекции | решения и числа владельцев (`CLAUDE.md` §3) |
| строки «Перехода», «Событий», «Решений» `map.md` | решения поверхности — слова аналитика; перечень ux — вопросом, не ответом |
| структура сетки (`columns: [...]`, `areas`) | конкретика — выбор аналитика |
| `assets` (имя файла-референса) | имя выбирает аналитик; скилл предлагает kebab-case по умолчанию |

Тексты интерфейса — отдельный путь: черновик строки пишет агент
«допущением», утверждает владелец продукта (раздел «Тексты
интерфейса»). Идентификаторы — `slug`, ключ `text:`, `params` — выводит
скилл и показывает одной строкой для контроля.

### Чего не делать

- Не предлагать «образцы» вроде «может быть, route такой-то?» — это
  выдумывание домена. Черновик текста интерфейса — исключение с
  пометкой: строка `assumed`, пока её не утвердил владелец продукта.
- Не упоминать «правильные» формулировки из README как опции в виде
  готовых текстов значений. Примеры в README — это иллюстрация
  канона, не варианты для текущего проекта.
- Не задавать больше 4 вопросов в одном `AskUserQuestion`. Если
  нужно больше — следующий раунд.
- Не закрывать сессию без чек-листа `draft-stable.md` хотя бы по
  одной правленой сущности.
- Не предлагать конкретные FSD-имена (`StudiesListWidget`) — карта
  слайсов ведётся в `fsd/<surface>/` (`/fsd-deep-dive`), не в screens.

## Тексты интерфейса

Этап `ui-texts` маршрута кабинета идёт после экранов: ключ строки
строится по месту на экране, а предел длины — по ширине компонента
дизайн-системы, поэтому реестр без экранов стал бы вторым источником
(контракт этапа — `../design-deep-dive/references/phases.md § 4`). Порядок
работы по колонкам — `field-checklists.md`, раздел `texts.md`.

- **Когда.** У экранов поверхности есть ключи `text:` (экраны `draft` или
  `stable`). Stable-экрану нужны строки не ниже `checked`; `approved`
  нужен до чистового макета и передачи в код.
- **Вход.** Ключи деревьев; глоссарий объектов (`name`, `aliases`) и
  словарь действий (`verb`, `past`, `banned`); профиль голоса продукта;
  ширины компонентов дизайн-системы для `maxlen` — после первого входа
  дизайна кабинета, до него — ориентиры ux 07/05 §4.6.
- **Цикл строки.** Черновик агента «допущением» — `assumed`; словарь
  запретов, межстрочные проверки и `maxlen` — `checked` (линтер
  `copy_lint.py texts.md`, 0 error — `field-checklists.md`, раздел
  `texts.md`); слово владельца продукта — `approved`. Правка текста
  возвращает строку в `assumed`: утверждение относится к конкретной
  формулировке.
- **Правка текста с холста кабинета.** Заказчик поправил текст
  интерфейса на холсте — исполнитель дизайна в реестр не пишет: он
  оставляет блокер в заметке холста и предлагает этот скилл. Правка
  входит в этап с середины: строка получает формулировку заказчика со
  статусом `assumed`, проходит проверки — `checked`, и `approved` — словом
  заказчика как владельца продукта; утверждённую строку холст получает
  следующей сборкой входа
  (`../design-deep-dive/references/claude-design.md § 5`). Ошибка
  проверки — заказчику с причиной, до его решения на холсте остаётся
  утверждённый текст.

Чего не делать: не утверждать строку за владельца; не заводить строку без
ключа в дереве; не писать в строку чисел, имён и дат — они приходят из
данных, подстановки — ICU (ux 07/05 §4.4); не брать синонимы из
`aliases` объекта и `banned` действия.

## Привести к канону

Файлы папки поверхности расходятся с формой слоя — например, форк
обновил шаблон поверх заполненного проекта. Тогда папка приводится к
канону `docs/projects/_template/screens/`: нотация дерева, ключи и наборы
состояний, типы `ui:` и атрибуты, тексты в реестре, поля экрана,
контракты блоков, `map.md`. Цель — чтобы FSD-карта, слой дизайна и аудиты
читали экраны по одной форме, не потеряв ни одной формулировки аналитика.

**Когда.** При запуске скилл сверяет папку с формой: деревья парсятся по
грамматике; ключи `states` — из словаря; `ui:` — типы словаря; атрибуты —
из закрытого списка; у экранов есть поля `type`, `object`, `main-task`,
`key-action`, `zone`, `params`, `access`, `url-state`; переходы — записи
`{to, trigger, keeps, back}`; в деревьях — ключи текстов, а не литералы;
есть `map.md` и `texts.md`. Расхождения видит и `/screen-audit`. Их мало
— правятся по ходу, в режиме C; много — скилл первым пунктом сводки
предлагает пакет.

**Сначала продукт и interface.** Поля экрана ссылаются на объекты,
действия и возможности продукта (`/project-deep-dive`), а зоны, ситуации с
отказами и данные с объектами — на interface (`/interface-deep-dive`). Их
нет — скилл называет соседа первым шагом, а в заметке пропусков пишет
долг.

**Механические правки** делает утилита `normalize` раздела `project`
скилла дизайна (`../design-deep-dive/scripts/README.md § project`):
`normalize check <project-slug> [<surface>]` показывает дифф и список
смысловых полей владельцу, `normalize build … --write` после одного
подтверждения правит файлы по месту, свод `map.md` пересобирает
`screen_map build`. Когда окружения нет — скилл сам, после одного
подтверждения и показав различие по каждому файлу:

- дерево — в компактную форму грамматики (`tree-notation.md`): узел с
  детьми кончается двоеточием, слот каркаса — `fills=$<slot>` в голове
  узла;
- имя компонента из `aka` — тип словаря, у которого это имя в `aka`;
- атрибут вне закрытого списка снимается: вид и размер компонента решает
  дизайн-система; если атрибут выражал уровень действия — вопрос
  аналитику про `level`;
- ключ `states` вне словаря — ближайший ключ словаря по таблице
  соответствия ключей мобильного слоя
  (`docs/projects/_template/mobile/README.md § Состояния экрана и
  словарь`); ключ, за которым стоят несколько состояний словаря, —
  вопрос аналитику;
- литерал текста в дереве — ключ `text:<key>` по месту и роли и строка
  `texts.md` со статусом `assumed`;
- переход, записанный одним slug экрана, — запись `{to: <slug>}`;
- недостающие `map.md` и `texts.md` — из формы; свод `map.md` —
  пересобрать по экранам.

**Пустое — не прочерк.** Новые поля, где прочерк — решение владельца
(`object`, `main-task`, `key-action`, `zone` экрана; «не применимо» в
наборе состояний; `trigger`, `keeps`, `back` перехода), остаются пустыми
до ответа аналитика: пустое поле аудит видит как пробел, а прочерк за
аналитика — молчаливый ответ за него.

**Смысловые правки** — аналитику (`CLAUDE.md` §3), раундами режима C: тип,
объект, главная задача и ключевое действие экрана; доступ и состояние в
адресе; обязательные наборы состояний; контракты форм, коллекций и
плиток; разделы «Переход», «События», «Конвенции», «Узкий экран» и
«Решения» `map.md`; `maxlen` строк — по ширинам компонентов
дизайн-системы.

**Статусы.** Stable-записи скилл не понижает — понижение делает только
аналитик (канон слоя, «Статус записи»). Пустой обязательный слот
stable-записи — находка `/screen-audit`, и список этих находок — список
работ перевода.

**Порядок — по зависимостям.** Продукт (`/project-deep-dive`) → interface
(`/interface-deep-dive`) → экраны (этот скилл) → FSD-карта
(`/fsd-deep-dive`: путь и охрана страниц, типы `shared-ui`, сценарии
данных, ключи локализации) → стыки мобильного приложения и бота. В конце
скилл называет следующего исполнителя. Заметки держат открытые вопросы
перевода, а не его историю.
