# Режим B: разбор сырья

«Сырьё» — любая входящая форма, по которой нужно понять, какие
сущности заводить:

- **картинка** (скриншот макета, фрейм Figma, скрин конкурента,
  фото эскиза на бумаге);
- **URL** (страница конкурента, статья с UI-паттерном, Figma-share-
  link, gist с разметкой);
- **текст** (описание макета словами, транскрипт интервью с
  дизайнером, заметки по итогам встречи);
- **комбинация** — типично: «вот скрин и описание к нему».

Скилл переходит в режим B, когда:

- args содержат свободный текст без kind/slug-сигналов;
- в сообщении пользователя есть приложение (картинка или файл
  отдельным content-блоком);
- args начинаются с URL.

## Алгоритм разбора

### Шаг 1. Изучить материал

**Картинка**: посмотреть содержательно. Что за макет — одностраничный,
master/detail, дашборд, форма, модалка? Какие зоны видны
(header, sidebar, main, detail, footer, overlay)? Сколько блоков
внутри (toolbar, list, preview, filters)? Mobile или desktop?

**URL**: `WebFetch` — получить текст страницы или метаданные. Если
URL — картинка, посмотреть её.

**Текст**: прочитать. Выделить сущности, упомянутые явно («экран
исследований», «фильтры слева», «карточка справа»), и сущности
выводимые («раз фильтры слева — наверное, master-detail-shell»).

### Шаг 2. Извлечь кандидатов

Применить фильтр по `Что НЕ` из README каждого kind (канон
`docs/projects/_template/screens/_template/<kind>.md`). Кандидаты —
только то, что прошло фильтр.

| вижу в материале | kind-кандидат |
|---|---|
| каркас приложения (header + sidebar + main) без конкретного контента | shell |
| конкретный route с заполненными зонами | screen |
| выделяемая часть слота (toolbar+table, фильтр-панель, preview-карточка) | block |
| desktop-макет + 2+ mobile-макета одной задачи | flow |
| sidebar становится drawer на mobile | НЕ flow (это `shell.responsive`) |
| один компонент (`ui:Button`) | НЕ block (это props компонента) |
| state экрана (loading, empty) | НЕ screen и НЕ block (это `screen.states`) |
| маршрут как поле | НЕ flow (это `screen.route`) |

### Шаг 3. Показать план

Через чат:

```
Из материала вижу:

shell-кандидаты:
  - app-shell-v2 — header + sidebar (collapsible) + main + detail + footer

screen-кандидаты:
  - studies-workspace — desktop, route /studies, slots: side/main/detail
  - studies-list-m — mobile, route /studies, slot main только

block-кандидаты:
  - filters-panel — slug, чекбоксы + диапазон дат + кнопка применить
  - studies-list — slug, sticky toolbar + таблица + pagination
  - study-preview — slug, header + scroll-body с инфо-блоками

flow-кандидаты:
  - studies-browse — объединяет studies-workspace (desktop) и
    studies-list-m (mobile)

Картинка → сохранить как <surface>/assets/screen/studies-workspace/
master-detail-figma.png? (y/n)

Так?
```

### Шаг 4. Подтвердить через AskUserQuestion

Раунд до 4 вопросов:

- «Кандидаты shell/screen/block/flow корректные?» (опции: «да, все
  правильные» / «убрать какие-то» (Other) / «добавить какие-то»
  (Other));
- «Сохранить картинку как ассет?» (по политике
  `assets-policy.md`);
- «Какую сущность углубить первой?» (опции: по одной на каждый
  кандидат + «другую» (Other));
- (если URL) «WebFetch посмотреть страницу для дополнительного
  контекста?» (опции: «да» / «нет, в материале хватает»).

### Шаг 5. Завести stub'ы

Для каждого подтверждённого кандидата:

1. Создать папку
   `docs/projects/<project-slug>/screens/<surface>/<kind>/<slug>/`.
2. Записать `index.md` с минимальным frontmatter:
   - `slug`, `name` (из описания / содержимого материала), `description`
     (краткая фраза о сущности), `status: draft`;
   - обязательные слоты — где есть значение, поставить; где нет, —
     `—` или пустые массивы;
   - `assets: [<имя-сохранённого-файла>]` если сохранили.
3. Тело — пустое (или минимальный yaml-`tree`/`slot-fills` со
   значимыми узлами из материала).
4. Создать `state/<project-slug>/screens/<surface>/<kind>/<slug>.md` с
   секцией `## Открытые вопросы`:
   - «извлечено из сырья — уточнить <конкретно что>»;
   - **blocker**'ы по ключевым неопределённостям (например, если из
     материала непонятно, какой shell соответствует — `**blocker**:
     не определён shell`).

### Шаг 6. Углубить выбранную через C

См. `workflow-patterns.md` C-режим.

## Естественный порядок углубления

shell → screen → block. Объясняется так:

- screen ссылается на shell — пустой shell ломает screen;
- screen.slot-fills ссылается на block — пустой block ломает
  screen;
- block.interface-block ссылается на interface — если в interface
  нет, надо туда сходить **до** углубления block.

flow углубляется в самом конце — это «обзорная» сущность по уже
существующим screens.

## Anti-patterns режима B

- ❌ Заводить кандидата, который не подтверждён аналитиком —
  кандидаты до подтверждения это **гипотезы**, не сущности.
- ❌ Угадывать `route`, текст label, точное число слотов по
  скриншоту — только структуру.
- ❌ «Это, наверное, master-detail-shell» — нет, спросить.
- ❌ Сохранять картинку без согласия (см. `assets-policy.md`).
- ❌ Лезть в web без явной просьбы (см. `assets-policy.md`).
- ❌ Заводить interface-сущности из сырья — это домен
  `interface-deep-dive`. Если из материала видны новые
  ситуации/блоки-аналитики/субстраты — предложить аналитику
  запустить `interface-deep-dive` параллельно.
