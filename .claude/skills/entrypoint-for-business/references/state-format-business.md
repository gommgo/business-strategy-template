# Единый state клиентской стороны (клиентский дом)

Весь state клиентской стороны живёт в **одном дереве** —
`entrypoint-for-business/state/`. Его ведёт **сам клиентский оркестратор**
(он ведёт все темы) — отдельных клиентских под-скилов нет. Аналитическая
сторона симметрично живёт в `entrypoint/state/` (свой канон —
`../../entrypoint/references/state-model.md`).

Forward-only: закрытое **удаляется**. Не хранить персональные данные
клиента (кроме прямо относящихся к артефакту). Дерево создаётся **по
требованию**.

## Владение по секциям дерева

```
.claude/skills/entrypoint-for-business/state/
├── index.md                 ← оркестратор: срез «где мы» по темам (бизнес-язык)
├── threads/<slug>.md        ← оркестратор: открытая тема-нить
├── swot-hm/<slug>.md        ← оркестратор: SWOT/Карту гипотез ведёт сам
├── business/...             ← тема «профиль бизнеса»
├── ajtbd/                   ← темы «типы клиентов» + «работы клиентов»
│   └── <kind|segment-slug>/<slug>.md
├── projects/<project-slug>/ ← тема «продукт» (изоляция по продукту)
└── _session-log/<UTC-ts>.md (буфер вопросов-ответов → transcript при --share)
```

Всё дерево ведёт **сам оркестратор** (он ведёт все темы): `index.md` +
`threads/` — срез и маршрут; `swot-hm/` — SWOT/Карта гипотез; ветки
`business/` · `ajtbd/` · `projects/<slug>/` — черновики по соответствующим
темам. Проектные ветки изолированы по продукту. Read-only сверяется с
аналитическим домом `../../entrypoint/state/` (anti-leak), туда не пишет.

## `index.md` — срез по темам (оркестратор)

Singleton-карта «где мы» в бизнес-формулировках, с маркером «закрыто / в
работе / не трогали». Ссылается на ветки тем, не дублирует их.

```markdown
# Где мы

## Про ваш бизнес
- в работе · детально: `business/`

## Про ваших клиентов
- одна группа разобрана, есть ещё · детально: `ajtbd/`

## Сильные/слабые стороны, идеи, цель, число (ведём сами)
- задача «возврат клиентов»: стороны разобрали, цель в работе
- детально: `swot-hm/`

## Про продукт
- не трогали
```

## `threads/<slug>.md` — открытая тема-нить (оркестратор)

Незавершённый разбор рассказа или тема через несколько направлений: что
обсуждаем и что **ждёт**. Закрытое — убирается; нить без открытого —
удаляется.

```markdown
---
slug: vozvrat-klientov
opened-from: рассказ клиента про задачу «возврат платных», 2026-06-06
---

## О чём (ждёт разбора)
- к чему стремимся (цель) — в работе
- по какому числу поймём — ждёт (метрика — возможно к аналитику)

## Что я имел в виду
- «отток» — про платных пациентов, не всех

## Что дальше
- закрыть цель словами, потом число
```

## Per-kind заметка (ветки тем и `swot-hm/`)

Оркестратор пишет в ветку темы рабочее состояние по одной сущности.
Зеркалит аналитический формат (`../../entrypoint/references/state-model.md`),
с двумя клиентскими дополнениями: маркер `**жду аналитика**` и секция «Что
я имел в виду».

```markdown
---
kind: user
slug: nurse-partner
ref: docs/projects/<project-slug>/user.md#nurse-partner
---

## Открытые вопросы
- В скольких клиниках одновременно работает?
- (**жду аналитика**) Какие именно регуляторные документы применимы
  — нужна юридическая консультация.

## Что я имел в виду
- Когда я сказал «передать без переспросов» — имел в виду, что сейчас
  тратится 20 минут на согласование формата по телефону, не факт отправки.

## Что копать дальше
- После звонка с клиникой — уточнить, есть ли SMS-нотификации в их МИС.
```

Frontmatter: `kind` (имя kind слоя; для `swot-hm/` — `блок` SWOT/Карты
гипотез), `slug` (= slug в таблице), `ref` (путь к артефакту). Заметка
`swot-hm/` дополнительно несёт привязку `задача:` — клиенту слово не
показывается.

### Секции

- **`## Открытые вопросы`** — как в аналитическом доме, плюс маркер
  `**жду аналитика**` (клиент сам не отвечает, ждёт аналитика; при
  `--share` всё с ним → в summary как «открытые вопросы для аналитика»).
  `**blocker**` используется редко, в основном на самопроверке.
- **`## Что я имел в виду`** — переформулировки самого клиента «когда
  сказал X, имел в виду Y». Ценный авторский контекст без интерпретации
  скилла. Маркированный список, одна строка = одно уточнение.
- **`## Доменные решения`** — как в аналитическом доме; у клиента реже.
- **`## Что копать дальше`** — локальные следующие шаги, известные клиенту.

## `_session-log/<UTC-ts>.md`

Накопительный буфер сессии. Блоки `## Вопрос (тема: <бизнес-название>)` →
`### Опции, которые были показаны` → `### Ответ`. **Служебный**, не
редактируется руками — каждый раунд `AskUserQuestion` дописывает блок. При
`--share` содержимое уезжает в
`client-handoff/transcripts/<YYYY-MM-DD>--<HH-MM>--<тема>.md` и файл
удаляется. Без `--share` логи накапливаются (новый `<UTC-ts>.md` на
сессию), уезжают разом при следующем `--share`.

## Единый контекст (read-only)

Чтобы картина была единой, клиентская сторона read-only подтягивает:

- **свой дом** — чужие ветки клиентского дерева (для общей картины);
- **аналитический дом** — `../../entrypoint/state/` целиком (кухня
  аналитика).

Проектные ветки — только по текущему продукту (изоляция продуктов). В
аналитический дом **не пишет**.

**Anti-leak (клиент-режим).** Прочитанное из кухни аналитика — **тихий
контекст**: сырые открытые вопросы, черновые гипотезы, доменные решения,
`slug/draft/stable` клиенту **не зачитываются**, только переводятся в
бизнес-язык. Клиенту по-прежнему видно лишь «закрыто / в работе».

## Жизненный цикл

Создаётся при наличии содержимого; перезаписывается свободно;
заметка/нить удаляется при пустых секциях/каскаде; `_session-log` — при
`--share`. Forward-only, без истории «было/стало».
