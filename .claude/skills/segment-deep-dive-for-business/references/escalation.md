# Эскалация и передача аналитику

Два формата: **мягкая** (застрял на вопросе — фиксируем, идём дальше) и
**полная** (`--share` — материал уезжает аналитику в ветку).

**Частый повод эскалации в этом слое** — глубокий разбор клиентов: найти
неочевидные типы клиентов, собрать **граф работ** (как клиент идёт к своей
цели и что нанимает на каждом шаге), точно оценить, **насколько таких
клиентов много** (размер рынка), и расставить приоритеты — это работа
аналитика (рой помощников по интернету + интервью + инструменты). Клиент
даёт первичную картину «как вижу», аналитик углубляет.

## Мягкая эскалация (`**жду аналитика**`)

Сигнал: 3× «не знаю»; «надо посмотреть / спросить»; просьба пропустить;
вопрос требует разбора рынка, точной оценки размера или приоритизации.

1. `AskUserQuestion`: «Похоже, это лучше дождаться аналитика — у него есть
   инструменты, чтобы это прояснить. Зафиксируем и пойдём дальше?» — «Да,
   отложим» / «Ещё попробуем» / «Передам сразу».
2. По «да» — в state: `## Открытые вопросы` → `- (**жду аналитика**)
   <вопрос в языке клиента>`.
3. «Записал. Когда отправим, аналитик увидит и ответит. Идём дальше?»

Не угадывает, не блокирует другие типы клиентов, не отправляет наружу
(копится до `--share`).

## Полная передача (`--share`)

Когда: явное «передай»; собрали один-два типа клиентов; накопилось 3+
`**жду аналитика**`.

### Подтверждение (обязательно)

> «Я подготовлю для аналитика:
>   — портреты клиентов, которые вы описали (черновики);
>   — наши заметки и открытые вопросы;
>   — короткий пересказ что собрали и где остановились;
>   — полный текст нашей сессии.
>
> Всё поедет в **отдельную папку проекта**, чтобы аналитик посмотрел, не
> трогая основную работу. Отправляем?»

Опции: «Да, отправляем» / «Сначала покажи, что поедет» (`--share
--preview`) / «Нет, отменим».

### Что упаковывается

1. `docs/ajtbd/segment.md` (черновики клиента — портреты клиентов).
2. `state/` (заметки, `**жду аналитика**`, `## Что я имел в виду`).
3. `client-handoff/summary.md` (живой срез, держится актуальным).
4. `client-handoff/transcripts/<YYYY-MM-DD>--<HH-MM>--<тема>.md`
   (человекочитаемое имя; полный лог сессии с предложенными вариантами).

**Не** упаковывается: `state/_session-log/` (уже в transcripts); файлы вне
перечисленного; ключи/.env (`git add` адресный, не `-A`).

### Настройка доступа к репозиторию (один раз)

Push требует логин/пароль — но клиента спрашиваем **ровно один раз на
устройстве**, дальше git помнит сам. Перед первым push проверить, сохранён
ли уже доступ:

```bash
host=$(git remote get-url origin | sed -E 's#https?://([^/@]*@)?([^/]+)/.*#\2#')
[ "$(git config --global credential.helper)" = "store" ] \
  && grep -q "@$host" ~/.git-credentials 2>/dev/null && echo ДОСТУП-ЕСТЬ
```

- Печатает `ДОСТУП-ЕСТЬ` → доступ уже сохранён: ничего не спрашиваем, сразу
  к Git-механике.
- Иначе — **один раз** запросить логин и пароль (или токен доступа, если
  выдали) через `AskUserQuestion` бизнес-языком: «Чтобы отправлять без
  повторных вопросов, нужно один раз ввести доступ к репозиторию — логин и
  пароль (или токен). Сохраню локально на вашем компьютере, больше не
  спрошу.» Логин и пароль клиент вводит через Other (два поля). Затем
  сохранить стандартным механизмом git (не редактировать файл руками):

  ```bash
  git config --global credential.helper store
  printf 'protocol=https\nhost=%s\nusername=%s\npassword=%s\n' \
    "$host" "<логин>" "<пароль>" | git credential approve
  ```

  После этого push идёт молча — и сейчас, и во всех будущих сессиях.

**Логин и пароль клиента — секрет.** Никогда не писать их в transcript,
summary, state, commit или в обычный текст чата после ввода. Этот шаг в лог
сессии не попадает.

### Синхронизация с main (старт и перед push)

`main` — канон аналитика, он уходит вперёд (аналитик мёржит черновики,
дописывает разбор клиентов и граф работ). Чтобы клиент всегда работал
поверх свежей аналитики, ветку `client` держим перебазированной на `main`
— и на старте сессии, и перед каждым push.

**На старте сессии (до работы):**

1. `git fetch origin` — узнать, ушёл ли `main` вперёд (всегда безопасно).
2. Рабочее дерево чистое (нет несохранённых черновиков)?
   - Да → лечь поверх свежего `main`:
     ```bash
     git switch client 2>/dev/null || git switch -c client origin/main
     git pull --rebase origin client 2>/dev/null   # свои коммиты с другого устройства
     git rebase origin/main
     ```
     Клиенту бизнес-языком: «Подтянул свежие обновления, можно работать».
   - Нет (есть несохранённые черновики) → дерево **не трогать**; сказать,
     что обновления подтянутся при отправке, и работать дальше (rebase на
     `main` всё равно случится в Git-механике после коммита).

**Конфликт rebase** — не угадывать. Через `AskUserQuestion` бизнес-языком:
«Свежие правки пересеклись с вашими черновиками — это лучше развести
аккуратно. Поставлю на паузу для аналитика?» → зафиксировать
`**жду аналитика**`, дерево не ломать. Конфликты разруливает аналитик.

### Git-механика

1. Доступ настроен (см. «Настройка доступа»).
2. Встать на единую ветку `client` — одна на все сессии, новые не плодим:
   `git switch client 2>/dev/null || git switch -c client origin/main`.
3. Перезаписать `client-handoff/summary.md` под актуальное состояние
   (живой срез, без мусора) и записать
   `client-handoff/transcripts/<YYYY-MM-DD>--<HH-MM>--<тема>.md` (с
   предложенными вариантами) — форматы ниже.
4. `git add` адресно (`docs/ajtbd/segment.md`,
   `.claude/skills/segment-deep-dive-for-business/state/`,
   `client-handoff/`).
5. `git commit -m "docs(handoff): segment client session <UTC-ts>"`
   (Conventional Commits — пройти хук).
6. Лечь поверх свежего `main` и запушить: `git fetch origin && git rebase
   origin/main`. Первый push — `git push -u origin client`; последующие
   (rebase переписал историю) — `git push --force-with-lease origin client`
   (безопасный force: откажется, если на remote есть чужие коммиты).
   Remote-ветка ушла вперёд (другое устройство) → `git pull --rebase origin
   client`, снова `git rebase origin/main`, повторить push.
7. Удалить локально `state/_session-log/<этой-ts>.md`.

### Если git-hook падает

**Не** `--no-verify`. Поймать сообщение, через `AskUserQuestion`:
«Возникла техническая загвоздка: <текст>. Попробовать исправить, или
пауза — аналитик разберётся?» — «свяжусь с аналитиком» / «попробуй
автоматически» / «откатить». По «попробуй» — починить корректно
(переформатировать commit message) и повторить.

### После push

1. К каждой `**жду аналитика**` добавить `**отправлено в ветку client
   (<UTC-ts>)**`.
2. Удалить `_session-log/<ts>.md`.
3. Дать клиенту текст для пересылки (3-5 строк, бизнес-языком, от его
   лица): кого из клиентов описали, где остановились, что нужно от
   аналитика (часто — «помоги глубже разобрать клиентов и понять, на кого
   делать ставку»).

## Формат `client-handoff/summary.md`

`summary.md` — **живой срез** для аналитика, не журнал. На каждом `--share`
**перезаписывается** под текущее состояние: закрытые вопросы уходят из
«Открытых», устаревшее «где остановились» заменяется, решённое не копится.
Forward-only — без «было/стало» и следов прошлых сессий. Цель: аналитик с
одного взгляда видит актуальную картину клиентов, без мусора.

```markdown
# Передача аналитику — клиенты (кого обслуживаем)

Обновлено: <YYYY-MM-DD> · Ветка: `client`

## Типы клиентов
- <по каждому: краткий портрет — за что платят, что для них «хорошо»;
  закрыт / в работе>

## Что собрали
- <как часто платят, насколько довольны тем, чем пользуются — текущая
  картина, с опорой если назвали>

## Где остановились
- <текущий тип клиента, что осталось — только актуальное>

## Открытые вопросы для аналитика
- <глубокий разбор клиентов / граф работ / точная оценка размера /
  приоритизация — только ещё не закрытые>

## Где смотреть
- `docs/ajtbd/segment.md` — черновики (портреты клиентов)
- заметки: `.claude/skills/segment-deep-dive-for-business/state/`
- логи сессий: `client-handoff/transcripts/`
```

## Формат transcript

Имя файла — **человекочитаемое**: `transcripts/<YYYY-MM-DD>--<HH-MM>--<тема>.md`
(напр. `2026-06-05--14-25--klienty-dachniki.md`). Три части — дата, время,
тема — разделены **двойным тире** `--` для читаемости; внутри части —
одинарный дефис. Время в имени через дефис (`14-25`, `:` запрещён в именах
на Windows), в заголовке транскрипта — через двоеточие (`14:25`). Тема —
короткий слаг того, что обсуждали (тип клиента); дата-время делают имя
уникальным.

Транскрипт — **верный лог сессии**: пишется последовательно, не
редактируется (в отличие от summary). Каждый блок несёт и **варианты,
которые скилл предлагал** (клиент их обычно теряет — а аналитику ценно
видеть, из чего выбирали), и итоговый ответ:

```markdown
# Сессия <YYYY-MM-DD> <HH:MM> · <тема>

## <бизнес-название блока>
**Вопрос:** <текст вопроса>
**Что предлагал:**
- <вариант 1>
- <вариант 2>
- <вариант 3>
- свой ответ
**Выбрано:** <вариант или свой текст клиента> — <пояснение, если было>

## <следующий блок>
…
```

Варианты берутся из буфера `_session-log` (там они уже записаны как
`### Опции`). Последовательно, forward-only.
