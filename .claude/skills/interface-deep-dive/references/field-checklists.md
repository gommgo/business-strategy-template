# Чек-листы полей по kind

По разделу на каждый из 7 артефактов. В каждом разделе:

- **Поля** — что в таблице, что обязательно, что опционально.
- **Ссылается на** — какие соседи.
- **Кто ссылается на это** — обратные связи.
- **Главные anti-patterns** — короткий список из `Что <kind> НЕ`.
- **Порядок копания** — последовательность вопросов в режиме A/C.

Полные критерии — в каноне `docs/projects/_canon/interface/<kind>.md`
(форма-образец, общая для всех проектов). Данные проекта живут в
`docs/projects/<project-slug>/interface/<kind>.md`. Здесь — выжимка для
скилла.

---

## who

**Поля**: `slug`, `name`, `description`, `users`, `status`.
`slug`/`name`/`description`/`status` обязательны; `users` — опционально.

**Ссылается на**: `users` (опц.) — `projects/<slug>/user` (если роль
сводится к пользователю(ям) продукта; системные акторы обычно `—`).
Мягкая связь снизу-вверх (interface → project), ловит `/cross-audit`.
Опции — существующие `user` того же проекта (см. `project-context.md`),
не выдумывать.
**Кто ссылается**: `situation.who`, `block.who`.

**Anti-patterns**: конкретное лицо · уровень прав / ACL · пассивный
объект · организация как юрлицо · устройство / канал / UI · «система по
инерции».

**Порядок копания**:

1. `slug` (Other).
2. `name` (Other) — человекочитаемое.
3. `description` (Other) — кто это в проекте.
4. Раунд anti-patterns: «Это лицо?» / «Это объект, над которым
   действуют?» / «Это организация как юрлицо?» / «Это устройство?» —
   опции бинарные + Other.
5. Тест-критерий: «Кто здесь делает шаг — роль/тип, а не лицо?» через
   `AskUserQuestion` с примерами ✅/❌ из md.

## stage

**Поля**: `slug`, `name`, `description`, `status`.
Все обязательные.

**Особенность**: **порядок строк в таблице = порядок этапов процесса**.
При добавлении строки её место в файле важно. При правке порядка —
проверять связность.

**Ссылается на**: ничего.
**Кто ссылается**: `situation.stage`.

**Anti-patterns**: экран / зона / блок · действие или ситуация · чистый
срок ожидания · граница ответственности сама по себе.

**Порядок копания**:

1. `slug`, `name`, `description` (Other).
2. **Место в порядке**: показать существующие этапы в порядке файла,
   спросить через `AskUserQuestion`: «Между какими этапами вставить?»
   (опции — каждая позиция).
3. Anti-patterns.
4. Тест-критерий: «Содержательная фаза процесса со своим местом в
   порядке?».

## situation

**Поля**: `slug`, `name`, `description`, `stage`, `who`, `when`,
`action`, `goal`, `entry-data`, `exit-data`, `using-what`,
`ux-substrate` (зеркало), `block` (зеркало), `jobs`, `capabilities`,
`hypotheses`, `status`.

**Обязательные**: `slug`, `name`, `description`, `stage`, `who`,
`action`, `goal`, `using-what`, `status`.
**Опциональные** (могут быть `—`): `when`, `entry-data`, `exit-data`,
`ux-substrate`, `block`, `jobs`, `capabilities`, `hypotheses`.

**Ссылается на**: `stage`, `who`, `data-items` (entry/exit),
`ux-substrate` (зеркало), `block` (зеркало); сквозные рёбра (опц.,
авторски на ситуации) — `jobs` (`ajtbd/job`), `capabilities`
(`projects/<slug>/capability`), `hypotheses`
(`hypothesis-map/hypothesis`). Сквозные рёбра — мягкие связи снизу-вверх,
ловит `/cross-audit`; опции из существующих сущностей соседних слоёв (см.
`project-context.md`), не выдумывать.
**Кто ссылается**: `ux-substrate.situation` (M:1 — этим строится
зеркало `situation.ux-substrate`).

**Anti-patterns**: слишком крупно (=этап) · слишком мелко (=субстрат) ·
экран или состояние интерфейса · несколько целей в одном · `goal` как
предусловие следующего шага.

**Порядок копания**:

1. **Фундамент**: `slug`, `name`, `description` (Other).
2. **`stage`**: опции = существующие stage-slugs + «нужен новый» (Other
   → A-режим в stage).
3. **`who`**: опции = существующие who-slugs + «нужен новый» (Other →
   A в who).
4. **`action`** (Other) — «как именно действует». Anti-pattern:
   содержит инструмент.
5. **`goal`** (Other) — «зачем». Anti-pattern: подмена предусловием
   (опции: «отвечает на оба: зачем вообще + зачем именно так» /
   «похоже на предусловие — "чтобы продолжить работу"»).
6. **`when`** (Other) — опционально, можно `—`.
7. **`using-what`** (Other) — бизнес-средство. Anti-pattern: содержит
   облик («primary-кнопка»).
8. **`entry-data`** (опц): опции = существующие data-items + «нужен
   новый» (Other → A в data-items); можно `—`.
9. **`exit-data`** (опц) — аналогично.
10. **`ux-substrate`** — заполняется автоматически (зеркало). Скилл
    предлагает: «нужны субстраты этой ситуации, заведём?» — переход в
    A-режим для `ux-substrate` (это раскрытие using-what в атомы).
11. **`block`** — зеркало; заполняется когда субстраты собраны в
    блок (через `block.ux-substrates`).
11a. **Сквозные рёбра** (опц.): `jobs` (опции — `ajtbd/job`),
    `capabilities` (опции — `capability` того же проекта), `hypotheses`
    (опции — `hypothesis-map/hypothesis`). Предлагать как контекст-связь
    (см. `project-context.md`); прочерк допустим, не выдумывать.
12. Anti-patterns.
13. Тест-критерий: «Одна фраза who+when+action+goal — это один присест,
    одна цель?».

**Зеркала**: после правки `ux-substrate.situation` или
`block.ux-substrates` — пересчитать `situation.ux-substrate` и
`situation.block` автоматически.

## zone

**Поля**: `slug`, `name`, `description`, `parent-zone`, `status`.
**Обязательные**: `slug`, `name`, `description`, `status`.
**Опциональные**: `parent-zone` (может быть `—` для корневой).

**Ссылается на**: `parent-zone` → другая `zone` (родитель). Цикл
запрещён.
**Кто ссылается**: `block.zone`, `block.transition-from-zone`.

**Anti-patterns**: отдельный блок (даже если в зоне один блок) · экран /
маршрут приложения · этап процесса · группа по who или stage ·
пространственная раскладка.

**Порядок копания**:

1. `slug`, `name`, `description` (Other).
2. `parent-zone`: опции = существующие zones + «корневая (`—`)» +
   «новая родительская» (Other → A в zone).
3. **Проверить цикл**: пройтись по `parent-zone` от текущей зоны вверх,
   убедиться что не возвращается к себе.
4. Anti-patterns.
5. Тест-критерий: «Смысловая область из (обычно нескольких) блоков с
   неявными переходами внутри?».

## block

**Поля**: `slug`, `name`, `description`, `zone`, `who`, `ux-substrates`,
`entrypoint`, `transition-to-block`, `transition-from-zone`, `status`.

**Обязательные**: `slug`, `name`, `description`, `zone`, `who`
(непустой массив), `ux-substrates` (непустой), `entrypoint` (bool),
`status`.
**Опциональные**: `transition-to-block`, `transition-from-zone` (могут
быть `—`).

**Ссылается на**: `zone`, `who` (массив), `ux-substrate` (массив),
`block` (transition-to-block), `zone` (transition-from-zone).
**Кто ссылается**: `block.transition-to-block` (другие блоки),
`situation.block` (зеркало через `ux-substrates`).

**Anti-patterns**: зона (группа блоков) · субстрат («кнопка входа») ·
экран 1:1 · раскладка / облик · декоративный контейнер.

**Порядок копания**:

1. `slug`, `name`, `description` (Other).
2. `zone`: опции = существующие zones + «новая» (Other → A в zone).
3. `who`: множественный выбор из существующих, минимум один (для
   универсального — `[any]`).
4. `ux-substrates`: множественный выбор из существующих субстратов.
   **Непустой обязательно** — без субстратов блока не бывает. Если
   нужных субстратов нет — переход в A-режим для `ux-substrate`.
5. `entrypoint`: опции `true` / `false`. Подсказка: «глобальный вход
   системы — обычно один-два».
6. `transition-to-block` (опц): показать существующие блоки. Правило:
   **только межзонные или нестандартные внутризонные**. Опции — блоки
   из других зон, либо `—`.
7. `transition-from-zone` (опц): входящие зоны (откуда можно попасть
   в этот блок). Опции — существующие zones, либо `—`.
8. Anti-patterns.
9. Тест-критерий: «Узел навигации, собирающий субстраты ≥1 ситуации —
   не группа и не атом?».

**После правки `ux-substrates`** — пересчитать зеркала `situation.block`
у затронутых ситуаций (через join `block.ux-substrates →
ux-substrate.situation`).

## ux-substrate

**Поля**: `slug`, `name`, `description`, `type`, `situation`, `status`.
Все обязательные.

**Ссылается на**: `situation`.
**Кто ссылается**: `block.ux-substrates`, `situation.ux-substrate`
(зеркало).

**Anti-patterns**: компонент / облик («primary-кнопка md») ·
бизнес-средство целиком («Загрузчик файлов») · составная форма целиком
(«форма входа») · данные · блок или экран.

**Порядок копания**:

1. `slug`, `name`, `description` (Other).
2. `type`: 5 опций enum'а: `команда` · `ввод` · `выбор` · `инфо` ·
   `список`. С пояснением (предъявление vs управление).
3. `situation`: опции = существующие situations + «новая» (Other → A в
   situation).
4. Anti-patterns.
5. Тест-критерий: «Один акт взаимодействия (`type` + `name`) в "что /
   зачем" — не облик, не агрегат, не форма целиком, не данные?».

**После правки `situation`** — пересчитать зеркало
`situation.ux-substrate` у затронутых ситуаций (старой и новой).

## data-items

**Поля**: `slug`, `name`, `description`, `status`. Все обязательные.

**Ссылается на**: ничего.
**Кто ссылается**: `situation.entry-data`, `situation.exit-data`.

**Anti-patterns**: технические артефакты (`session token`, `JWT`,
`cookie`, `csrf`) · идентификаторы реализации (ID строк БД) · цифровая
тень вместо первоисточника («строка в таблице заказов» вместо «заказ») ·
атрибут вместо сущности · UI-состояние (скролл, фокус) ·
вспомогательное вычисляемое (кэш, индекс) · среда исполнения.

**Сквозной идентификатор**: один датум — один `slug` везде. Если в
разных ситуациях похоже выглядящий датум — это один и тот же `slug`,
не разные.

**Порядок копания**:

1. `slug`, `name`, `description` (Other).
2. Anti-patterns раундом: «Технический артефакт?» / «Цифровая тень?» /
   «Атрибут без жизненного цикла?» / «UI-состояние?».
3. Тест-критерий: «Произнёс бы это участник в разговоре про свою
   работу, и есть ли у этого свой жизненный цикл?».
4. Проверка сквозности: если name похоже на уже существующий datum —
   спросить «это тот же датум, что `<slug>`?». При «да» — не заводить,
   использовать существующий.
