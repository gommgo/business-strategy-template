# Контекст продуктового слоя проекта

`interface-deep-dive` живёт **на слой ниже** продуктового слоя **того же проекта** и работает в контексте одной
поверхности. Продуктовый слой описывает продукт — vision, реестр поверхностей `surface.md`, пользователей и их
постуры, глоссарий объектов `object.md`, словарь действий `action.md`, возможности по поверхности
`capability/<surface>.md` — и живёт в `docs/projects/<project-slug>/`; interface — UX-аналитику одной поверхности в
`docs/projects/<project-slug>/interface/<surface>/`. Продуктовый слой этот скилл читает, но не пишет: его ведёт
`/project-deep-dive`.

Связь зоны, ситуации и сценария с поверхностью **структурная**: запись лежит в папке своей поверхности. Поверхность
задана выбором папки на старте — отдельно её не спрашивать.

## Какая поверхность получает interface

Interface есть у всех поверхностей, кроме `web` рода `landing` и `site`: у сайта и лендинга на его месте слой страницы
`site/<surface>/` (`docs/projects/_template/site/README.md`). У `web` без рода маршрут не определён — сначала род через
`/project-deep-dive`. Сценарии обязательны у поверхностей маршрута приложения (`web` рода `app`, `admin`, `desktop`,
`embed`); у мобильной и бот-поверхности — по желанию.

## Маппинг

| interface | продуктовый слой | поле и как использовать | проверка ссылки |
|---|---|---|---|
| `who` (роль) | `user` — корневой `user.md`, кросс-поверхностный | `who.users` (опц., массив); системный актор — `—`. Постуру участник берёт у пользователя: строка таблицы «Постура» с этой поверхностью, а без неё — строка `surface: —` | смысловая — `/cross-audit` (`user-who`) |
| `situation` | `capability` **этой поверхности** | `situation.capabilities` (опц., массив); системное действие — `—`; частота паспорта возможности — подсказка к `frequency` | смысловая — `/cross-audit` (`capability-situation`) |
| `situation` | `job` — `docs/ajtbd/job.md` | `situation.jobs` (опц.): какие работы сегмента обслуживает шаг | смысловая |
| `situation` | `hypothesis` — `docs/hypothesis-map/hypothesis.md` | `situation.hypotheses` (опц.): какие гипотезы шаг проверяет | смысловая |
| `scenario` | `capability` **этой поверхности** | `scenario.capability` — ровно одна; у `hub` и `critical` сценарий обязателен; `reversibility` по умолчанию — у действия ядра возможности (`action.md`) | возможность есть в файле поверхности |
| `scenario` | `object` — статусы | «Что меняется»: `<object>.<status>` из колонки `statuses` глоссария | объект и статус есть в `object.md` |
| `zone` | `object` | `zone.object` — объект, вокруг которого построен раздел, или `—` | объект есть в `object.md` |
| `data-items` | `object` и его атрибуты | `data-items.object` — `<object>`, `<object>.<атрибут>` или `—`; через него резолвится `data:` дерева экрана | объект и атрибут есть в `object.md` |
| `zone` | `surface` | структурно — зона лежит в `interface/<surface>/` | — |

Ссылки на объекты глоссария и возможность сценария проверяются на существование: по ним экраны берут тип, длины и
статусы, а сценарий хаба закрывает покрытие возможности. Смысл связи — тот ли объект, та ли возможность — сверяет
`/cross-audit`. Работы и гипотезы — из глобальных слоёв `docs/ajtbd/` и `docs/hypothesis-map/`.

## Когда показывать связь

### Заведение `who`

После фундамента — раунд связи с пользователями (иллюстрация формы вопроса):

```
AskUserQuestion:
header: "Связь с пользователем"
multiSelect: true
options:
  - "user:<slug-1>" (description = name)
  - "user:<slug-2>" (description = name)
  - "Системный актор (без пользователя)"
  - Other («не из перечисленных, опишу»)
```

Выбор — в колонку `users` (массив или `—`). «Почему» — по желанию в заметку `…/interface/<surface>/who/<slug>.md`,
`## Доменные решения`; системный актор — «намеренно без пользователя: интерес системы X»; ответ Other — дословно в
заметку. У пользователя нет строки постуры — вопрос в заметку и предложение `/project-deep-dive <project-slug>
user:<slug>`.

### Заведение `situation`

После фундамента — раунды сквозных рёбер (все опциональны, несколько сразу, прочерк допустим):

```
AskUserQuestion (header: "Возможность") → situation.capabilities
options: capability:<slug-i> из capability/<surface>.md этой поверхности / «Системное действие (без возможности)» / Other

AskUserQuestion (header: "Работа сегмента") → situation.jobs
options: job:<slug-i> из docs/ajtbd/job.md / «нет» / Other

AskUserQuestion (header: "Гипотеза") → situation.hypotheses
options: hypothesis:<slug-i> из docs/hypothesis-map/hypothesis.md / «нет» / Other
```

Возможности — **только из файла этой поверхности**. У реализуемой возможности есть паспорт — его `frequency`
показывается подсказкой к частоте шага, ответ даёт аналитик.

### Заведение `scenario`

Опции возможности — возможности этой поверхности: `hub` и `critical` без сценария первыми. Действие ядра возможности
даёт обратимость по умолчанию, глоссарий — объекты и статусы для «Что меняется». У возможностей поверхности нет
приоритетов — сценарии не с чего начать: предложить `/project-deep-dive <project-slug> capability:<surface>`.

### Заведение `zone` и `data-items`

Опции объекта — строки `object.md` (у данных — ещё атрибуты `<object>.<атрибут>`) и прочерк-решение: «раздел не
вокруг объекта», «датум вне модели объектов». Нужного объекта нет — blocker в заметке и `/project-deep-dive
<project-slug> object`: глоссарий ведёт продуктовый слой, одно понятие — одно слово на все поверхности.

## Если продуктовый слой проекта пуст

Нет нужного источника — корневой `user.md` пуст, нет файла возможностей поверхности, глоссарий пуст — раунд связи
не задаётся, работа идёт дальше. У поверхности маршрута приложения это пропуск маршрута: сценарии и объектные ссылки
ждут продукта. Скилл пишет долг в заметку пропусков `…/interface/<surface>/_phase-jump.md` и при закрытии сессии
спрашивает:

> «У проекта `<project-slug>` нет продуктовых записей, на которые опирается interface: <что>. Для прототипа это
> допустимо, но interface растёт из продукта. Открыть `/project-deep-dive <project-slug>`?»

Опции: «Да, запустим» / «Нет, продолжим без продукта».

## Если связь в заметке уже другая

`who:doctor` в заметке уже связан с `user:doctor-clinic-owner`, а аналитик хочет связать с `user:doctor-employee` —
это смена контекста. Скилл не перезаписывает молча, а спрашивает: «Связан с user:X. Меняем на user:Y или роль
относится к обоим?» — и по выбору обновляет запись и заметку.

## Сквозная сверка

После сессии скилл предлагает `/cross-audit --quick`: его углы `user-who`, `capability-situation` и `surface-zone`
показывают, остались ли участники без пользователя, пользователи без участника, возможности без ситуаций **в этом
проекте**; один угол — `/cross-audit <project-slug> <lens>`. Сам `/cross-audit` скилл не запускает — это работа
аналитика.
