# Три режима ведения сеанса

`interface-deep-dive` поддерживает три явно различающихся сценария входа.
Скилл выбирает режим по виду args при запуске и далее ведёт сеанс,
комбинируя точечные шаги.

## A. Новая сущность

**Сигнал**: args = `<kind>` или `<kind>:<новый-slug>` (когда slug ещё
не существует в файле).

### Шаги

1. Прочитать канон `docs/projects/_template/interface/<kind>.md` целиком:
   секции `Критерии`, `Что НЕ`, `Тест-критерий`.
2. Раунд 1 `AskUserQuestion` — фундамент:
   - `slug` (через Other) — если ещё не дан;
   - `name` (Other) — человекочитаемое;
   - `description` (Other) — одна-две строки.
3. Записать строку в данные поверхности
   `docs/projects/<project-slug>/interface/<surface>/<kind>.md` с
   заполненными `slug + name + description + status=draft`, остальные
   ячейки `—`.
4. Раунд 2+ `AskUserQuestion` — батч по доменным слотам kind в порядке
   `field-checklists.md`. До 4 вопросов в раунде; перемежать опции
   (anti-patterns) и Other (значения).
5. По мере заполнения — если в поле нужна ссылка на ещё не
   существующую сущность **той же поверхности**, отработать **stub**
   (см. SKILL.md): создать stub-запись, записать state-заметку с открытым
   вопросом, продолжить.
6. После всех слотов — раунд `AskUserQuestion` по `Тест-критерий` из
   md: ✅/❌ варианты как опции. Аналитик подтверждает.
7. Применить чек-лист `draft-stable.md`. Если все 5 ✅ — предложить
   повышение в stable.
8. Записать `state/<project-slug>/interface/<surface>/<kind>/<slug>.md`,
   если есть что (открытые вопросы, неочевидные доменные решения).

### Пример раунда (situation, после фундамента)

Скилл предлагает четыре вопроса разом:

- **stage** — выбрать из существующих slug'ов в `stage.md` (опции) или
  «нужен новый» (Other → A-режим в stage).
- **who** — аналогично из `who.md`.
- **when** — Other (свободная форма). Подсказка из md: «опционально,
  можно `—`».
- **goal vs anti-pattern** — два варианта: «отвечает на оба вопроса
  "зачем вообще" и "зачем именно так"» / «похоже на предусловие
  следующего шага (anti-pattern)». При втором — вернуть аналитика к
  формулировке.

## B. Сырьё

**Сигнал**: args = свободный текст, или пользователь приложил
транскрипт / заметки / скрин UI.

### Шаги

1. Прочитать материал внимательно.
2. Извлечь кандидатов на сущности — что похоже на ситуацию, кто
   действующий, какие данные, какие зоны. Фильтр — секции `Что НЕ`
   из канона `docs/projects/_template/interface/<kind>.md` (отбросить,
   что заведомо не подходит: «снимок» не who, «нажать кнопку» не
   situation, и т.п.).
3. Через чат показать план: «Из материала вижу:
   - 3 ситуации: <slug-кандидаты>;
   - 2 участника: <slug>;
   - 4 данных: <slug>;
   - 1 зона + 2 блока — пока неопределённо.
   Так?»
4. Раунд `AskUserQuestion` — подтвердить план / попросить корректировку
   через Other.
5. По подтверждению — завести **stub'ы** в соответствующих файлах
   поверхности `docs/projects/<project-slug>/interface/<surface>/`
   (минимум `slug + name + description + status=draft`); создать
   state-заметки с открытыми вопросами «извлечено из сырья — уточнить
   <что>».
6. Через `AskUserQuestion` — выбрать, какую сущность углубить первой.
7. Перейти в режим C на выбранной. Повторить для остальных.

### Что НЕ делать в режиме B

- Не объявлять извлечённое «зафиксированным». Это кандидаты до
  подтверждения аналитика.
- Не угадывать `goal`, `action`, `using-what` по сырью — только
  `name` / `description` максимально близко к языку аналитика.
- Не выдумывать кандидатов, которых в материале нет, «потому что
  обычно бывают».

## C. Углубление

**Сигнал**: args = `<kind>:<slug>` существующей записи, либо
аналитик выбрал из сводки.

### Шаги

1. Прочитать строку из данных поверхности
   `docs/projects/<project-slug>/interface/<surface>/<kind>.md`.
2. Прочитать `state/<project-slug>/interface/<surface>/<kind>/<slug>.md`,
   если есть.
3. Прочитать соседей **той же поверхности**: для situation — `who`,
   `stage`, ссылки на data-items, ux-substrate (по фильтру), block (по
   join'у).
4. Применить канон `docs/projects/_template/interface/<kind>.md` секции
   `Критерии`, `Что НЕ`, `Тест-критерий` к строке. Найти:
   - пустые обязательные слоты;
   - подозрения по anti-patterns (`goal` похож на предусловие,
     `using-what` содержит облик, и т.п.);
   - рассинхрон зеркал (для situation);
   - битые ссылки.
5. Раунд `AskUserQuestion` (до 4 вопросов) — точечно по найденному:
   - дыры — заполняем через Other;
   - anti-pattern-подозрения — опции «да, anti-pattern» / «нет,
     вот почему» (через Other);
   - битые ссылки — опции «исправить на <варианты>» / «удалить»
     (если поле допускает) / «оставить stub».
6. Применить ответы: правка строки, обновление state-заметки,
   пересчёт зеркал если нужно.
7. После раунда — повторно прогнать чек-лист `draft-stable.md`.
   Если все 5 ✅ — предложить повышение в stable.
8. Если осталась хотя бы одна дыра или подозрение — следующий раунд.

### Когда переходить от C к завершению

- Все 5 пунктов чек-листа ✅ → предложить stable, по подтверждению
  поменять status.
- Остался `**blocker**`-вопрос, на который аналитик сейчас ответить не
  может → зафиксировать в state-заметке, оставить `status: draft`,
  выйти из углубления этой сущности; предложить другую или сводку.

## Стиль вопросов: правила

### Когда давать опции

| ситуация | формат |
|---|---|
| anti-pattern из `Что <kind> НЕ` | две опции: «соответствует anti-pattern» / «не соответствует» (объяснить почему через Other) |
| enum поле (`ux-substrate.type`) | по одной опции на каждое значение enum |
| тест-критерий из `Тест-критерий` | опции из примеров ✅/❌, аналитик соотносит свой случай |
| выбор существующего slug соседа | по опции на каждый существующий + «нужен новый» (Other) |
| структурный выбор (`entrypoint: true/false`) | две опции |

### Когда не давать опции, только Other

| поле | почему |
|---|---|
| `name` | человекочитаемое имя — формулировка аналитика |
| `description` | смысл записи — слова аналитика |
| `goal`, `action`, `when` | доменная семантика, не угадывать |
| `using-what` | бизнес-средство — выбор аналитика |
| любой slug, который ещё не существует | аналитик называет, не скилл |

### Чего не делать

- Не предлагать «образцы» вроде «может быть, goal такой-то?» — это
  выдумывание домена.
- Не упоминать «правильные» формулировки из md как опции в виде
  готовых текстов значений. Примеры в md — это иллюстрация канона,
  не варианты для текущего проекта.
- Не задавать больше 4 вопросов в одном `AskUserQuestion`. Если
  нужно больше — следующий раунд.
- Не закрывать сессию без чек-листа `draft-stable.md` хотя бы по
  одной правленой сущности.
