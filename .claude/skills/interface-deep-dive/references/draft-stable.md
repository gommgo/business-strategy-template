# Контракт `draft → stable`

Запись становится `stable`, когда **все 5 пунктов одновременно** ✅.
Скилл проверяет, аналитик подтверждает, скилл применяет.

## Чек-лист

### 1. Обязательные слоты заполнены

Опциональные могут быть `—`. Остальные — обязательно с непустым
значением (для slug-полей — реф; для свободного текста — фраза).

См. `field-checklists.md` — там по каждому kind: какие слоты
обязательны и какие опциональны.

### 2. Все ссылки валидны

Каждый `slug` в ячейке записи существует как `slug` строки в
соответствующем соседнем файле.

- `situation.stage` → `stage.md`
- `situation.who` → `who.md`
- `situation.entry-data` / `exit-data` → `data-items.md`
- `situation.ux-substrate` → `ux-substrate.md` (зеркало)
- `situation.block` → `block.md` (зеркало)
- `block.zone` → `zone.md`
- `block.who` → `who.md`
- `block.ux-substrates` → `ux-substrate.md`
- `block.transition-to-block` → `block.md`
- `block.transition-from-zone` → `zone.md`
- `zone.parent-zone` → `zone.md`
- `ux-substrate.situation` → `situation.md`

`stable` может ссылаться на `draft` — это допустимо. `audit` подсветит
hint, но не блокирует stable.

### 3. Зеркала консистентны (только для `situation`)

Канонические источники:

- `ux-substrate.situation` (M:1) — источник для отношения
  «субстрат принадлежит ситуации».
- `block.ux-substrates` (M:N) — источник для «блок собирает субстраты».

Производные поля у `situation`:

- `situation.ux-substrate` — должен быть равен набору всех
  `ux-substrate.slug`, где `ux-substrate.situation == <slug
  ситуации>`.
- `situation.block` — должен быть равен набору всех `block.slug`,
  где `block.ux-substrates` пересекается с
  `situation.ux-substrate`.

Скилл держит зеркала синхронными автоматически после каждой правки
канонических источников.

### 4. Тест-критерий явно подтверждён

В md-файле kind есть секция `Тест-критерий` с примерами ✅/❌. Через
`AskUserQuestion` скилл предъявляет аналитику примеры и спрашивает:
«какой из этих образцов ближе всего к вашей записи?».

Запись проходит, когда аналитик соотносит её с ✅-примером и
эксплицитно подтверждает «да, это так».

### 5. State-заметка чиста по `**blocker**`-вопросам

`state/<project-slug>/<kind>/<slug>.md`:

- Не содержит секцию `## Открытые вопросы` ИЛИ
- Содержит, но в ней нет вопросов с префиксом/суффиксом `**blocker**`.

Не-blocker открытые вопросы при stable допустимы (они описывают
«хорошо бы узнать», не «здесь смысл сломан»).

Секция `## Доменные решения` к stable не относится — она может быть.
Секция `## Что копать дальше` — обычно пуста к stable.

## Алгоритм проверки скиллом

После любой правки записи:

1. Прочитать строку из артефакта.
2. Прочитать `state/<project-slug>/<kind>/<slug>.md`, если есть.
3. Прогнать пункты 1–3, 5 (программно проверяемые).
4. Если все 4 ✅ — раунд `AskUserQuestion` по тест-критерию (пункт 4).
5. Если и пункт 4 ✅ — раунд `AskUserQuestion`: «Готов к stable,
   повышаем?» с опциями «Да, повысить» / «Нет, ещё не уверен» (через
   Other — что именно смущает).
6. При «Да» — Edit'ом поменять `status: draft → stable`.

## Что НЕ делать

- **Не повышать сам**, без подтверждения аналитика. Даже если все 5
  пунктов ✅ — спросить.
- **Не понижать `stable → draft` сам** при обнаружении проблемы — это
  смысловое решение аналитика. Можно подсветить и предложить.
- **Не считать пункт 4 пройденным «по умолчанию»**, потому что слоты
  заполнены. Тест-критерий — отдельное смысловое подтверждение.
- **Не игнорировать `**blocker**`-вопросы** — они должны быть закрыты
  или удалены (если стали неактуальны) до stable.
