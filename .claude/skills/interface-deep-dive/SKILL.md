# interface-deep-dive

Проектирование interface **одной поверхности** проекта в `docs/projects/<project-slug>/interface/<surface>/`: восемь
kind — участник (who), этап (stage), ситуация (situation), сценарий (scenario), зона (zone), блок (block), субстрат
(ux-substrate), данные (data-items). Канон формы — `docs/projects/_template/interface/README.md`. Скилл ведёт сессию
структурированными вопросами (`AskUserQuestion`), держит контекст в своей ветке единого state оркестратора
(`../entrypoint/state/projects/<project-slug>/interface/<surface>/`), домен не выдумывает, облик не пишет.

Interface — аналитика взаимодействия: кто, когда, как и зачем действует, каким путём проходит задачу, в каком разделе
навигации это живёт. Композицию экранов строит `/screen-deep-dive` той же поверхности, облик — слой дизайна `design/`.

Скилл — **единственная точка входа** в interface-слой: заведение, углубление, разбор сырья, приведение к канону, переход
`draft → stable`, удаление с каскадом.

## Какая поверхность получает interface

UX-слой **партиционируется по поверхности**: на каждую поверхность реестра `docs/projects/<project-slug>/surface.md` —
своя папка `interface/<surface>/` с восемью файлами. Interface есть у всех поверхностей, кроме `web` рода `landing` и
`site`: у сайта и лендинга на его месте слой страницы `site/<surface>/`, который ведёт `/design-deep-dive`. Сценарии
обязательны у поверхностей маршрута приложения — `web` рода `app`; `admin`, `desktop`, `embed`; у мобильной и
бот-поверхности они по желанию.

## Выбор проекта и поверхности

Аргументы позиционны — `<project-slug>` первый, `<surface>` второй:

| вызов | проект · поверхность |
|---|---|
| `/interface-deep-dive <project-slug> <surface> …` | взять `<project-slug>` и `<surface>` |
| `/interface-deep-dive <project-slug> …` | проект задан; поверхность — пикер по именам из `surface.md` |
| `/interface-deep-dive …` | пикеры по именам: сначала проект, затем поверхность |

1. **Проект.** Первый аргумент совпал с подпапкой `docs/projects/` (кроме `_template` и `infrastructure`) — это `<project-slug>`. Иначе —
   пикер «Какой проект?» по именам (исключая `_template` и `infrastructure`; заголовок vision; slug — деталью). Проектов нет — «сначала заведи проект через
   `/project-deep-dive`», выйти.
2. **Поверхность.** Прочитать `surface.md`. Следующий аргумент совпал со `slug` строки реестра — это `<surface>`; иначе
   — пикер «Какая поверхность?» по `surface.name` (slug и `type` — деталью). Пикер не предлагает `web` рода `landing` и
   `site`. Реестр пуст — «сначала заведи поверхность через `/project-deep-dive <project-slug>`», выйти. Поверхность вне
   реестра не принимается — хребет ведёт реестр.
3. **Род.** У `web` рода `landing` или `site` работы в interface нет: на его месте слой страницы — назвать
   `/design-deep-dive <project-slug> <surface>`. Папка `interface/<surface>/` у такой поверхности уже есть — показать её
   аналитику и предложить решение (`references/workflow-patterns.md § Привести к канону`, «Папка у сайта или лендинга»).
   `web` без рода — остановиться и назвать `/project-deep-dive <project-slug>`: без рода маршрут не определён.
4. **Первый заход на поверхность.** Папки `interface/<surface>/` нет — создать её копией формы
   `docs/projects/_template/interface/_template/`: восемь файлов, у таблиц — только канон-проза и заголовок таблицы без
   строк-образцов, у `scenario.md` — без образцовых секций. Каталог руками в обход скилла не создаётся.
5. Все чтения и записи скоупятся в `docs/projects/<project-slug>/interface/<surface>/` и ветку
   `../entrypoint/state/projects/<project-slug>/interface/<surface>/`.

## Точки входа

После проекта и поверхности остаток аргументов задаёт режим:

| вызов | поведение |
|---|---|
| `/interface-deep-dive <project-slug> <surface>` | сводка поверхности и первые кандидаты на работу |
| `/interface-deep-dive <project-slug> <surface> <kind>` | завести запись kind (режим A) |
| `/interface-deep-dive <project-slug> <surface> <kind>:<slug>` | углубить запись (режим C) |
| `/interface-deep-dive <project-slug> <surface> <slug>` | найти запись; одна — режим C; совпала в нескольких kind — переспросить |
| `/interface-deep-dive <project-slug> <surface> <свободный текст / приложение>` | сырьё → разбор (режим B) |

`kind` ∈ {`who`, `stage`, `situation`, `scenario`, `zone`, `block`, `ux-substrate`, `data-items`}. `kind:slug` —
ускоритель: заход без аргументов с пикером по именам есть всегда (`.claude/rules/naming.md`).

## Порядок работы на поверхности

Продукт описывается до экранов, и interface — его последний шаг перед ними
(`docs/projects/_template/project/README.md § Порядок этапов`). На поверхности маршрута приложения работа идёт так:

1. **Сценарии хабов — первыми.** Для каждой возможности `hub` и `critical` поверхности — сценарий (ux 13/04 §11); его
   шаги сразу заводят ситуации, сначала stub-строками.
2. **Остальное interface:** участники, этапы, ситуации с частотой и отказами, зоны — разделы навигации с порядком и
   объектом, блоки, субстраты, данные со ссылкой на объект.

После сценариев хабов вход готов у первого входа дизайна кабинета — бриф на вид, карточки стиля, дизайн-система
(`/design-deep-dive <project-slug> <surface>`; условия —
`.claude/skills/design-deep-dive/references/phases.md § Первый вход дизайна кабинета`): стиль не ждёт экранов. Когда
interface поверхности `stable`, следующий шаг — экраны (`/screen-deep-dive <project-slug> <surface>`); у мобильной
поверхности — `/mobile-deep-dive`, у бота — `/telegram-bot-flow-deep-dive`.

Сценарии опираются на продукт: приоритеты возможностей и глоссарий объектов ведёт `/project-deep-dive`. Их нет — скилл
называет продуктовый слой первым шагом. Начать interface раньше можно — это обычный режим (`.claude/rules/guiding.md`
§5): скилл называет цену пропуска одной фразой — сценарии и объектные ссылки ждут продукта, — пишет пропуск и долг в
заметку пропусков `…/interface/<surface>/_phase-jump.md` по форме
`../entrypoint/references/state-model.md § Особый случай: _phase-jump.md` — «Доменные решения» — что пропущено и почему,
«Что копать дальше» — долг — и работает. Вопрос «почему сейчас?» задаётся, только когда пропуск задевает обязательный
артефакт маршрута (тот же раздел `state-model.md`): в остальных случаях он стоял бы барьером.

## Что делать сразу при запуске

1. Определить проект и поверхность, проверить род; при первом заходе — завести папку.
2. Прочитать `docs/projects/_template/interface/README.md` — канон слоя: файлы, связи, информационная архитектура.
3. Прочитать продуктовый слой того же проекта — `vision.md`, `surface.md`, корневой `user.md` с постурой, `object.md`,
   `action.md`, файл возможностей поверхности `capability/<surface>.md` — и `references/project-context.md`: какие связи
   с продуктом предлагать и какие ссылки проверяются.
4. **Сверить папку поверхности с каноном:** восемь файлов, колонки `frequency` и `refusals` у ситуаций, `order` и
   `object` у зон, `object` у данных, порядок колонок. Расхождений много — первым пунктом сводки предложить пакет
   «Привести к канону» (`references/workflow-patterns.md § Привести к канону`).
5. Нет аргументов после поверхности — сводка (ниже) и выбор через `AskUserQuestion`.
6. Аргументы указывают на запись — определить kind и режим (A, B, C) и идти по `references/workflow-patterns.md`.

Как говорить о ходе, словах и вариантах — `.claude/rules/guiding.md`; условия работы, названные человеком, читаются
до первого вопроса.

## Сводка состояния

1. Прочитать восемь файлов папки поверхности.
2. Посчитать `draft` и `stable` по каждому kind.
3. Прочитать свою ветку `…/interface/<surface>/` и заметку пропусков — открытые вопросы (`**blocker**` первыми) и долг.
4. Собрать кандидатов на работу по приоритету:
   - возможности `hub` и `critical` поверхности без сценария — **первыми** на поверхности маршрута приложения;
   - черновики с `**blocker**`-вопросами;
   - ситуации без частоты, ситуации экрана без отказов, зоны без порядка и объекта, данные без объекта;
   - черновики с большим числом пустых обязательных слотов; черновики, на которые ссылаются stable-соседи.
5. Вывести сводку (пример — иллюстрация формы):

   ```
   Проект: <project-slug> · поверхность: Веб для медсестры (web-partner · web, app)
     scenario     1 draft · хабов без сценария: 1 (check-status)
     who 2 · stage 3 · situation 7 (2 stable) · zone 3 · block 4 · ux-substrate 11 · data-items 5
     без частоты: 3 ситуации · зоны без порядка: 1 · данные без объекта: 2
   Открытых blocker-вопросов: 1 · Долг: глоссарий объектов пуст — /project-deep-dive
   Дальше: сценарий check-status; после сценариев хабов — первый вход дизайна (бриф на вид)
   ```

6. Через `AskUserQuestion` — выбрать, что копать.

## Три режима

Шаги, сценарий отдельно, пример раунда, стиль вопросов и приведение к канону — `references/workflow-patterns.md`.

- **A. Новая сущность** — `<kind>` или `<kind>:<новый-slug>`: вопросы по `Критерии <kind>` формы, опции — anti-patterns
  и перечисления, значения — через Other.
- **B. Сырьё** — текст, транскрипт, скрин: кандидаты (рассказ о задаче — кандидат в сценарий), план, stub-строки по
  подтверждению, затем углубление каждой через C.
- **C. Углубление** — `<kind>:<slug>` или выбор из сводки: точечные вопросы по дырам и подозрениям, чек-лист
  `draft → stable` после каждой правки.

## Стиль вопросов

- Вопросы — через `AskUserQuestion`, до четырёх в раунде (лимит инструмента; больше — следующим раундом).
- **Опции** — anti-patterns из `Что <kind> НЕ`, примеры тест-критерия, перечисления (`ux-substrate.type`, `frequency`,
  `expertise`, `reversibility`), ключи отказов словаря состояний, позиции зоны в навигации, объекты глоссария и
  возможности поверхности, выбор существующего соседа.
- **Свободная форма** (Other) — значения: `name`, `description`, `goal`, `action`, `when`, `using-what`, шаги и
  ветвления сценария, «что дальше», утверждения приёмки.
- Формулировки UX-доменных полей даёт аналитик (`CLAUDE.md` §3): опциями идут anti-patterns и перечисления, а сами
  тексты скилл не подсказывает. Прочерк в `refusals`, `order`, `object` — решение аналитика, скилл его не ставит.

## Память: своя ветка единого state

Своей папки state у скилла нет. Заметки пишутся в ветку единого дерева state оркестратора, скоупленную по проекту и
поверхности, — не в папку interface и не в корень проекта; формат — `../entrypoint/references/state-model.md`:

- запись — `../entrypoint/state/projects/<project-slug>/interface/<surface>/<kind>/<slug>.md` (в том числе сценарий —
  `…/scenario/<slug>.md`);
- заметка пропусков поверхности — `…/interface/<surface>/_phase-jump.md`.

Заметка существует, пока в ней есть секция с содержимым: `## Открытые вопросы` (пометка `**blocker**` блокирует stable),
`## Доменные решения`, `## Что копать дальше`; frontmatter — `kind`, `slug`, `ref`. Заметка держит текущее знание о
записи, а не историю: закрытое удаляется, пустая заметка удаляется целиком.

### Единый контекст: read-only видимость дерева

Скилл читает read-only всё дерево state оркестратора — срез `…/state/index.md`, открытые нити, верхние слои `business/`,
`ajtbd/`, `swot/`, `hypothesis-map/` — и клиентский дом `../entrypoint-for-business/state/…`. Проектные ветки — только
по текущему `<project-slug>`. Своя ветка — `…/interface/<surface>/` одной поверхности — rw, остальное — read-only: в
чужое не писать. Маркер `**жду аналитика**` в клиентском доме — кандидат в blocker.

## Зеркала

`situation.ux-substrate` и `situation.block` — **производные** поля. Канонические источники — `ux-substrate.situation`
(M:1) и `block.ux-substrates` (M:N). Скилл держит зеркала синхронными **автоматически после любой правки** без
подтверждения: после правки `ux-substrate.situation` или `block.ux-substrates` пересчитывает зеркала затронутых
ситуаций.

## Контракт `draft → stable`

Чек-лист после каждой правки — `references/draft-stable.md`:

1. Обязательные слоты заполнены (у ситуации при stable — частота, у ситуации экрана — отказы; у сценария — мета и
   разделы).
2. Все ссылки валидны — внутри поверхности и на объекты глоссария и возможность сценария в продуктовом слое.
3. Зеркала консистентны (у ситуации).
4. Тест-критерий формы подтверждён аналитиком в этой сессии.
5. В заметке записи нет `**blocker**`-вопросов.

Все пять ✅ — «Готов к stable, повышаем?»; по подтверждению — `status: draft → stable`. Скилл **не повышает сам** и не
понижает: `stable → draft` делает только аналитик, скилл может лишь предложить.

## Stub-сущности

Запись ссылается на несуществующую запись **той же поверхности** (шаг сценария — на ситуацию, которой ещё нет):

1. В файле поверхности — новая строка `slug`, `name`, `description`, `status: draft`, остальные ячейки `—`, кроме ячеек,
   где прочерк — решение (`frequency`, `refusals`, `order`, `object`): они остаются пустыми.
2. В заметке stub-записи — `## Открытые вопросы`: «заведён как stub в контексте `<откуда сослались>` — докопать».
3. Возврат к исходной записи.

Нет объекта глоссария или возможности поверхности — это продуктовый слой: скилл туда не пишет, а оставляет blocker в
заметке и предлагает `/project-deep-dive <project-slug>`.

## Удаление сущности (каскад)

1. Прочитать восемь файлов поверхности и свою ветку — найти все ссылки на удаляемый slug **в этой поверхности**, в том
   числе шаги, ветвления и участников сценариев.
2. Показать каскад: «ссылаются X, Y, Z — вот что сломается».
3. По каждому месту — `AskUserQuestion`: «заменить на другой slug» / «поставить `—`, если поле допускает» / «удалить
   ссылающуюся запись»; у шага сценария — «заменить ситуацию» / «убрать шаг».
4. По подтверждению — все правки одним пакетом; затем удалить запись и её заметку, пересчитать зеркала затронутых
   ситуаций.
5. На удаляемую запись ссылаются экраны поверхности (`situations`, `zone`, `blocks`, узлы `data:`) — их ведёт
   `/screen-deep-dive`: предупредить, что ссылки повиснут.

## Завершение сессии

1. Перечислить затронутые записи: заведены, углублены, удалены, повышены.
2. Перечислить нерешённые открытые вопросы и долг заметки пропусков.
3. Назвать ходы дальше — два-три, один рекомендован; рекомендованный — по разделу «Порядок работы на поверхности»:
   сценарии хабов закрыты — первый вход дизайна кабинета; interface поверхности stable — экраны.
4. Предложить через `AskUserQuestion`: «Прогнать `/interface-audit <project-slug> <surface>`?» — полный аудит
   поверхности. По «да» — сказать «Запусти `/interface-audit <project-slug> <surface>`»: другие скиллы этот скилл сам не
   вызывает.

Как говорить о ходе, словах и вариантах — `.claude/rules/guiding.md`: итог сессии, ходы дальше и строка «как
продолжить» идут по нему.

## Границы

- Облика в interface нет: слой описывает бизнес-средство (`using-what`) и роли атомов, а не вид — цвет, типографика,
  пространство, движение, вид и размер компонентов решает слой дизайна `design/`; композицию экрана строит
  `screens/<surface>/`, а макет собирает слой дизайна `design/`.
- Ссылка из одной поверхности в запись другой не заводится: поверхности изолированы, общее — один пользователь, один
  объект, один датум на двух поверхностях — сводит `/cross-audit`.
- Продуктовый слой — vision, пользователи, объекты, действия, возможности — скилл читает, но не пишет: его ведёт
  `/project-deep-dive`.
- У `web` рода `landing` и `site` interface нет — на его месте слой страницы.

Формулировки доменных полей приходят от аналитика, в stable запись поднимается только по его подтверждению, в чужие
ветки state скилл не пишет, а другие скиллы, включая аудит, не запускает — только предлагает.
