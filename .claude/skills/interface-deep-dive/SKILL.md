# interface-deep-dive

Углублённая проработка артефактов интерфейса **одного проекта** в
`docs/projects/<project-slug>/interface/`. Канон формы —
`docs/projects/_canon/interface/README.md`. Скилл ведёт сеанс через
структурированные вопросы, фиксирует контекст в `state/<project-slug>/`,
не выдумывает домен и craft.

Использовать как **единственную точку входа** в interface-слой проекта:
заведение, углубление, разбор сырья, переход `draft → stable`,
удаление с каскадом.

Скилл всегда работает **в контексте одного проекта** (см. ниже «Выбор
проекта»). Дальше по тексту `<project-slug>` — выбранный проект, а
`docs/projects/<project-slug>/interface/` — его interface-слой.

## Выбор проекта

Скилл работает в контексте **одного** проекта. `<project-slug>` —
первый позиционный аргумент:

| вызов | проект |
|---|---|
| `/interface-deep-dive <project-slug> …` | взять `<project-slug>` |
| `/interface-deep-dive …` (без slug) | `AskUserQuestion`-пикер по папкам `docs/projects/` (исключая `_canon`) |

Алгоритм определения проекта при запуске:

1. Если первый аргумент совпадает с именем подпапки `docs/projects/`
   (кроме `_canon`) — это `<project-slug>`; остаток args — точка входа.
2. Иначе — собрать список подпапок `docs/projects/` (исключить
   `_canon`) и через `AskUserQuestion` спросить «Какой проект?». Если
   проектов нет — сказать «сначала заведи проект через
   `/project-deep-dive`», выйти.
3. Все дальнейшие чтения/записи скоупятся в выбранный проект:
   `docs/projects/<project-slug>/interface/` и
   `state/<project-slug>/`.

## Точки входа

После того как `<project-slug>` определён, остаток args задаёт режим:

| вызов | поведение |
|---|---|
| `/interface-deep-dive <project-slug>` | сводка состояния + топ-3 кандидата на углубление |
| `/interface-deep-dive <project-slug> <kind>` | завести новую сущность типа kind (режим A) |
| `/interface-deep-dive <project-slug> <kind>:<slug>` | углубить существующую запись (режим C) |
| `/interface-deep-dive <project-slug> <slug>` | найти slug; одиночный → C; конфликт kind → переспросить |
| `/interface-deep-dive <project-slug> <свободный текст / приложение>` | сырьё → разбор (режим B) |

`kind` ∈ {`who`, `stage`, `situation`, `zone`, `block`, `ux-substrate`, `data-items`}.

## Что делать сразу при запуске

1. Определить `<project-slug>` (см. «Выбор проекта»).
2. Прочитать `docs/projects/_canon/interface/README.md` — освежить
   канон формы.
3. Прочитать `docs/projects/<project-slug>/vision.md` и продуктовые
   файлы (если есть) + `references/project-context.md` — освежить связи
   с продуктовым слоем **того же проекта** (who ↔ user,
   situation ↔ capability, zone ↔ surface).
4. Если остаток args пуст — сделать сводку (см. ниже) и через
   `AskUserQuestion` предложить выбор что копать.
5. Если остаток args указывает на сущность — определить kind и режим
   (A/B/C), применить маршрут из `references/workflow-patterns.md`.

## Сводка состояния (без args)

1. Прочитать все 7 файлов в `docs/projects/<project-slug>/interface/`.
2. Подсчитать: сколько `draft` / `stable` по каждому kind.
3. Прочитать `state/` (если есть) и собрать открытые вопросы — секции
   `## Открытые вопросы`; пометки `**blocker**` приоритетны.
4. Выявить топ-3 «горячих» кандидата по приоритету:
   - draft-записи с `**blocker**`-вопросами;
   - draft-записи с большим числом пустых обязательных слотов;
   - draft-записи, на которые ссылаются stable-соседи (блокируют их
     корректность).
5. Вывести сводку в чат, предложить через `AskUserQuestion` выбрать.

## Три режима

См. `references/workflow-patterns.md` — детали сценариев и примеры
вопросов.

- **A. Новая сущность**. Args = `<kind>` или `<kind>:<новый-slug>`.
  Батч `AskUserQuestion` по `Критерии <kind>` из соответствующего
  md-файла; опции — anti-patterns из `Что <kind> НЕ`; свободная форма
  через Other для значений.
- **B. Сырьё**. Args = свободный текст или приложение. Извлечь
  кандидатов, показать план, по подтверждению завести stub-строки,
  погрузиться в каждую через режим C.
- **C. Углубление**. Args = `<kind>:<slug>` или выбран из сводки.
  Точечные вопросы по дырам и подозрениям; чек-лист `draft → stable`
  после каждой правки.

## Стиль вопросов

См. `references/workflow-patterns.md`.

- **Всегда через `AskUserQuestion`**, до 4 вопросов в одном раунде.
- **Опции** только для:
  - anti-patterns из секции `Что <kind> НЕ` («это похоже на anti-pattern
    X — согласен?»);
  - теста-критерия (бинарный выбор ✅/❌ из секции `Тест-критерий`);
  - структурного перечисления (enum типа `ux-substrate.type`).
- **Свободная форма** (через Other) — для **значения**: `name`,
  `description`, `goal`, `action`, `when`, `using-what`, имена ролей.
- **Никогда** не предлагать конкретные тексты доменных полей от себя.
  Anti-patterns — да. Сама формулировка — нет.

## Память `state/<project-slug>/<kind>/<slug>.md`

Заметки лежат **рядом со скиллом**, не в
`docs/projects/<project-slug>/interface/` и не в корне проекта, и
скоупятся по проекту:

```
.claude/skills/interface-deep-dive/state/<project-slug>/<kind>/<slug>.md
```

Дальше по тексту скилла — короткое `state/`, это сокращение того же
пути (с учётом текущего `<project-slug>`).

См. `references/state-format.md`. Кратко:

- Файл существует, пока в нём есть хоть одна секция с содержимым.
- Три возможные секции (любая может отсутствовать):
  - `## Открытые вопросы` (опц. префикс `**blocker**` у вопроса,
    блокирующего stable),
  - `## Доменные решения` (неочевидные смысловые решения, не лезущие
    в `description`),
  - `## Что копать дальше`.
- Если все три пусты — заметку удалить.
- Заметка не журнал: не аккумулировать «было/стало», только текущее
  состояние знания. Forward-only.

## Зеркала

`situation.ux-substrate` и `situation.block` — **производные** поля
(зеркала). Канонические источники: `ux-substrate.situation` (M:1) и
`block.ux-substrates` (M:N).

Скилл держит зеркала синхронными **автоматически после любой правки**
без подтверждения. После каждой правки `ux-substrate.situation` или
`block.ux-substrates` — пересчитать соответствующие зеркала в
`situation.md` и применить.

## Контракт `draft → stable`

См. `references/draft-stable.md`. Чек-лист после каждой правки:

1. Обязательные слоты заполнены (опциональные могут быть `—`).
2. Все `slug`-ссылки валидны (записи существуют в соседних файлах).
3. Зеркала консистентны (для `situation`).
4. Тест-критерий из md явно подтверждён аналитиком в этой сессии.
5. В `state/<project-slug>/<kind>/<slug>.md` нет `**blocker**`-вопросов
   (другие открытые вопросы — закрыты или явно отмечены как «не
   блокирует»).

Если все 5 ✅ — предложить через `AskUserQuestion`: «Готов к stable,
повышаем?». По подтверждению — изменить `status: draft → stable`.
Скилл **не повышает сам**.

Понижение `stable → draft` — только аналитик руками. Скилл максимум
может предложить, не делать.

## Stub-сущности

Если копаемая сущность ссылается на не существующий slug:

1. В соответствующем файле — новая строка: `slug + name + description
   + status=draft`, остальные ячейки `—`.
2. В `state/<project-slug>/<kind>/<stub-slug>.md` — секция
   `## Открытые вопросы` с записью «Заведён как stub в контексте
   `<откуда сослались>` — докопать».
3. Возврат в исходную сущность, копание продолжается.

## Удаление сущности (каскад)

1. Прочитать все 7 файлов
   `docs/projects/<project-slug>/interface/` + `state/` — найти все
   ссылки на удаляемый slug.
2. Показать каскад: «ссылаются X, Y, Z — вот что сломается».
3. Через `AskUserQuestion` по каждому месту — опции: «заменить на
   другой slug» / «поставить `—` (если поле допускает)» / «удалить
   ссылающуюся запись».
4. По подтверждению — выполнить все правки одним пакетом.
5. Удалить запись из её файла.
6. Удалить `state/<project-slug>/<kind>/<slug>.md`.
7. Пересчитать зеркала затронутых ситуаций.

## Завершение сессии

В конце:

1. Перечислить затронутые сущности (заведены / углублены / удалены).
2. Перечислить нерешённые открытые вопросы по сущностям.
3. Предложить через `AskUserQuestion`: «Прогнать `/interface-audit`?»
   — это полный аудит консистентности. По «да» сказать пользователю
   «Запусти `/interface-audit`» — сам не вызываю, это другой скилл.

## Запреты

- Не редактировать таблицы вслепую — всегда сначала `Read`.
- Не выдумывать значения доменных полей. Anti-patterns как опции — да;
  тексты `goal`, `action`, `name`, `description`, `using-what` — нет.
- Не выдумывать craft (облик, цвет, размер, варианты компонентов) —
  это библиотека `@sftbmb/ui`, не предмет скилла.
- Не повышать `draft → stable` без явного подтверждения аналитика.
- Не понижать `stable → draft` сам — только подсветить и предложить.
- Не оставлять зеркала рассинхронными.
- Не аккумулировать историю в `state/` — forward-only.
- Не создавать `state/<project-slug>/<kind>/<slug>.md`, если все
  секции были бы пустыми — заметка появляется только когда есть что
  записать.
- Не работать сразу с несколькими проектами в одной сессии — скилл
  скоупится в один `<project-slug>`.
