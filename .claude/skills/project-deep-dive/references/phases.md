# 8 фаз вижн-мейкинга

Скилл ведёт аналитика по фазам как по карте: всегда видно, где мы, что
закрыто, что осталось. **Порядок — рекомендация, не закон.** Аналитик
может перепрыгнуть; скилл напомнит про последствия.

Фазы — это режим разговора, не директива «делать только это». В любой
фазе можно завести запись из другого kind, если она всплыла естественно.
Фаза влияет на:

- **что предлагаем копать первым** в сводке состояния;
- **какие вопросы задаём** (фокус разговора);
- **какие переходы между фазами** предлагаем после артефакта.

## Карта фаз

### 1. `discovery` — vision

**Триггер:** `docs/projects/<project-slug>/vision.md` отсутствует
(только что заскаффолден из формы `_template/`) или `status: draft`.

**Цель:** довести `vision.md` до состояния, когда сторонний человек
прочитал и понял **чьей** боли касается продукт и какие границы
поставлены.

**Что копать:**

- Problem — одно-два предложения чьей жизни мы касаемся.
- Success — проверяемый исход (метрика или наблюдаемый сдвиг
  поведения).
- Non-goals — что **не делаем**, с короткими «потому что».
- Оси `audience`/`intent`/`market-maturity` и `lifecycle` — тип и зрелость
  инициативы (enum от аналитика, см. `field-checklists.md`).
- `addresses-problem` — какие строки
  `docs/business/business-problem.md` (общий реестр проблем) продукт
  закрывает (массив slug-рефов, M:N). Скилл читает реестр, показывает
  строки-проблемы как опции `AskUserQuestion`, аналитик выбирает; новые
  проблемы не выдумываются здесь (заводятся в
  `/business-deep-dive business-problem`). Без привязки vision висит в
  воздухе — `success` целит в метрики выбранных проблем.

**Анти-паттерны:**

- Vision как «платформа для X» без адресата боли.
- Vision как список фич.
- Vision как маркетинговый слоган.
- `addresses-problem` пустой при stable — продукт без проблемы.
- `market-maturity: prospective` без проспективных сущностей наверху
  (`ajtbd/segment` / `business/business-problem` с `served=prospective`).

**Логичные переходы после:**

- `user` — из Problem уже названы кандидаты в адресаты, давай
  раскроем.
- `boundary` — если Non-goals выявил несколько устойчивых границ, можно
  сразу занести их как отдельные boundary-записи.

### 2. `user` — сегменты адресатов

**Триггер:** vision стабилен, user.md пуст или мало записей.

**Цель:** очертить **тех, чьё поведение изменится**, если продукт
сработает. Заводим минимум 1, обычно 2-5.

**Что копать:**

- Кто адресат боли (контекст устойчивый).
- Jobs-to-be-done в её языке.
- Боли наблюдаемые.
- Что для **неё лично** будет «полегчало».

**Анти-паттерны:**

- Демография без боли.
- Внутренняя роль команды как user.
- «Идеальный пользователь» из методички.
- Системный актор (это `interface/<surface>/who.md`, не сюда).

**Логичные переходы после:**

- `surface` — где этих users встречаем (хребет вперёд: реестр
  поверхностей нужен, чтобы партиционировать возможности).
- если user диктует канал («медсестра — телефон, не десктоп») — это
  прямой сигнал к surface.

### 3. `surface` — поверхности (реестр-хребет)

**Триггер:** vision и user очерчены, реестр `surface.md` пуст/мал.

**Цель:** очертить **где** продукт встречает user, и **открыть
поверхностям место** в остальных слоях. `surface.md` — реестр-хребет:
его slug'и — ключи партиционирования. Каждая строка реестра получит
свой файл возможностей `capability/<surface>.md` и (ведут свои скилы)
папки `interface/<surface>/`, `screens/<surface>/`. Web / mobile / api /
admin / bot / desktop / embed / …

**Что копать:**

- Тип + конкретное «где» (домен / store / messenger).
- Какие user обслуживаются.
- Самодостаточность (user закрывает job, не выходя за пределы).

**Анти-паттерны:**

- Технологический стек как surface («React-фронт»).
- Email-рассылка без обратного действия как surface (это integration).
- Внутренний tool как surface (логи, k8s-dashboard).

**Логичные переходы после:**

- `capability` — теперь можно очертить возможности **по каждой
  поверхности** (хребет готов, есть куда партиционировать).
- `constraint` — web с PII влечёт 152-ФЗ / GDPR — провести по
  поверхностям.

### 4. `capability` — возможности (по поверхности)

**Триггер:** реестр `surface.md` непуст, но у поверхности нет файла
`capability/<surface>.md` или он пуст. **Не стартует без `surface`** —
нет поверхностей, некуда партиционировать возможности.

**Цель:** очертить **что продукт умеет** в терминах ценности для user,
**по каждой поверхности**. Не «как реализовано» — это `domain/`. Скилл
идёт по реестру поверхностей: для каждой поверхности заводит/добивает её
файл `capability/<surface>.md` (форма — `_template/project/capability.md`,
колонки те же). Одна ценность на двух поверхностях = две записи (в
разных файлах), у каждой своё воплощение.

**Что копать (в файле выбранной поверхности):**

- Глагол + объект в языке user.
- Кому ценность (одна+ user).
- Самодостаточная формулировка (без отсылки к другой capability).
- Сквозные рёбра (опц.): `hypotheses` (→ `hypothesis-map/hypothesis`),
  `jobs` (→ `ajtbd/job`).

**Анти-паттерны:**

- Фича из бэклога («v2.0 — поиск»).
- Зонтичная capability («управление пользователями»).
- Технологическая способность («OAuth»).
- Дубль одной ценности в файле **одной** поверхности (если ценность на
  двух поверхностях — это две записи в **разных** файлах, осознанно).

**Логичные переходы после:**

- `integration` — capability часто опирается на внешнюю систему.
- `market` — для самой яркой capability полезно посмотреть, кто ещё
  это умеет на рынке (запустить research роем по этому проекту).

### 5. `integration` — внешние системы и стыки с соседями

**Триггер:** есть surface и capability, нужно зафиксировать внешние
зависимости.

**Цель:** очертить, **с чем обмениваемся** и **зачем** — будь то внешняя
система или соседний проект того же бизнеса. Файл несёт **две таблицы**:
`## Провайдеры` (одна строка на систему) и `## Функции` (одна строка на
функцию интеграции, в языке бизнеса).

**Что копать (провайдеры):**

- Что за провайдер (один = одна запись).
- Direction (in / out / duplex).
- Owner (we / partner / both).
- Payload — что передаём/получаем в целом.
- `surface` — какие поверхности обслуживает интеграция (массив slug-рефов
  в реестр `surface.md`): платёжный шлюз web-чекаута → `` [`web`] ``;
  единый IDP всех точек входа → `` [`web`, `mobile`, `admin`] ``.
- `target` — `external` (обычная внешняя система: Stripe, CRM) или
  `sibling-project` (обмен с **другим продуктом того же бизнеса**).
- `sibling-project` — при `target: sibling-project` ссылается на slug
  соседнего проекта; иначе `—`. Это ребро межпроектного стыка фиксируется
  здесь (авторская сторона) и **сводится в `docs/projects/project-map.md`**.

**Что копать (функции):** для каждого провайдера — каталог его функций в
**языке бизнеса**: `slug`, `name`, `description` («списать деньги»,
«начислить баллы»), `direction` (`out` — мы зовём их функцию; `in` — они
зовут нашу). Без техники: endpoint/сигнатура — это конкретика клиента
`domains/_shared/`, не сюда. Функции — кандидаты, которые потом потребляет
use-case (колонка `functions`) и реализует клиент `_shared/integrations/<slug>/`.

**Анти-паттерны:**

- Внутренний сервис как integration (Postgres — это инфра).
- Библиотека без побочных эффектов.
- Соседний проект бизнеса как обычная внешняя `integration`
  (`target: external`) — для него `target: sibling-project` + ребро в
  `project-map.md`.
- Техническая сигнатура функции (endpoint, метод) в `## Функции` — здесь
  бизнес-описание; конкретика — в клиенте `domains/_shared/`.

**Логичные переходы после:**

- `constraint` — если payload — чувствительный (PII / финансы /
  здоровье), автоматический повод завести constraint.
- `market` — research поможет найти альтернативных провайдеров для
  той же интеграции.

### 6. `constraint` — ограничения

**Триггер:** есть surface + integration, нужно осветить «что обязаны».

**Цель:** очертить **внешние** требования, которые продукт обязан
соблюдать.

**Что копать:**

- Источник внешний (закон, контракт, SLA, RFC).
- Снимать нельзя.
- `source` ссылается на конкретный документ.

**Анти-паттерны:**

- Внутреннее правило команды.
- Best practice без обязательности.
- Технические предпочтения.

**Логичные переходы после:**

- `market` — изучить, как конкуренты соблюдают эти constraints (даёт
  ориентиры).
- `cohesion` — если constraints сложные, пройти по surface, проверить
  что покрыты.

### 7. `market` — рыночные аналоги

**Триггер:** ядро продукта очерчено, нужен внешний контекст.

**Цель:** карта **продуктовой территории** — direct / indirect /
manual / legacy аналоги. Наполняется в основном **роем агентов**
(см. `research-rays.md`).

**Что копать:**

- Кто (название, URL).
- Какую позицию занимают.
- Чем мы отличаемся (наблюдаемо).
- Источники.

**Анти-паттерны:**

- «Полный список рынка». Берём релевантных для **наших** user и
  capability.
- Маркетинговая копия их или наша.
- Без `sources`.

**Логичные переходы после:**

- `cohesion` — финальная сводка слоя.

### 8. `cohesion` — целостность

**Триггер:** vision + реестр surface + плоские kind + у каждой поверхности
реестра есть непустой `capability/<surface>.md` — есть хотя бы по записи,
фокус — целостность картины.

**Цель:**

- Заведение `boundary`-записей по каждой устойчивой границе из
  vision.non-goals.
- Повышение `draft → stable` для записей, проходящих чек-лист.
- Подсветка подозрительных мест (capability без user, surface без
  user, vision без `addresses-problem`, поверхность реестра без файла
  возможностей, `integration.surface`/`sibling-project` на несуществующую
  сущность, …).
- Предложить запустить `/project-audit <project-slug>` (внутренние тупики
  + структурный разрыв хребта) и `/cross-audit` (стыки с
  `<slug>/interface/<surface>`/`<slug>/domains`/`<slug>/screens/<surface>`,
  привязка `addresses-problem`, межпроектные стыки `project-map.md`).

**Анти-паттерны:**

- Принудительный stable у записей, которые ещё draft по делу.
- Завести boundary под backlog-задачу (boundary — устойчивое «нет»,
  не «потом»).

## Сводка фаз для UI

Скилл выводит карту фаз в чате при сводке состояния так:

```
Фазы:
  ✅ discovery   — vision stable
  ✅ user     — 3 stable, 1 draft
  ✅ surface     — 2 (web-partner, tg-bot)
  🔄 capability  — web-partner: 2 draft; tg-bot: файла ещё нет (текущая)
  ⏳ integration
  ⏳ constraint
  ⏳ market
  ⏳ cohesion
```

Где: ✅ — закрыта (≥1 stable, нет blocker), 🔄 — текущая (есть драфты),
⏳ — не начата. Для `capability` статус считается **по поверхностям**
реестра: фаза закрыта, когда у каждой поверхности есть непустой
`capability/<surface>.md`.

## Перепрыгивание

Аналитик в любой момент может сказать «давай сразу market» — скилл не
блокирует, но **спрашивает через `AskUserQuestion`**:

- «Перепрыгнуть из текущей `<current>` в `<target>` — почему сейчас?»
  — опции: «бизнес уже дал материал по этой теме», «сначала хочу
  увидеть рынок чтобы понять user», «нужно для срочного решения»,
  Other.

Ответ запоминается как «доменное решение» в ветке state проекта —
`../entrypoint/state/projects/<project-slug>/project/_phase-jump.md`. Это
не блокер, просто полезный контекст для будущих сессий по этому проекту.
