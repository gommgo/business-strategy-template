# Чек-листы полей по kind

Что заполнять при заведении и углублении каждого kind: обязательное и опциональное, кто формулирует и в каком порядке
разумно копать. Колонки, критерии, «Что НЕ» и тест-критерий — в форме `docs/projects/_template/project/<kind>.md`,
здесь — выжимка для скилла. Кто владеет формулировкой — `CLAUDE.md` §3, строка «Продуктовая»: бизнес и аналитик;
разделы vision агент может предложить «допущением».

## vision (singleton)

**Набор разделов** — по поверхностям продукта (`docs/projects/_template/project/vision.md § Разделы`):

- **полный** — двенадцать разделов: у продукта, где хоть одна поверхность идёт маршрутом приложения (`web` рода `app`,
  `admin`, `desktop`, `embed`);
- **минимум** — `Name` (с родом поверхности), `Problem`, `Users`, `Success`, `Non-goals` и `Assumptions`, если
  допущения есть: у продукта только из сайтов и лендингов, мобильного приложения или бота; остальные разделы — по
  желанию.

**Должно быть для stable** — каждый раздел своего набора заполнен; разделу, которому нечего сказать, — явное «нет» с
причиной, а не пропуск:

| раздел | что должно быть | формулирует |
|---|---|---|
| `Name` | имя продукта; сводка поверхностей (`slug` · `type` · `web-kind`) — из `surface.md`; у поверхности-приложения — тип приложения (`admin` · `client` · `mixed`) и ИИ-слой | бизнес — имя; аналитик — тип |
| `Problem` | чья боль и в какой момент; наблюдения исследований — ограничениями («пользователи бросают, когда…») | бизнес, аналитик |
| `Users` | ссылки на пользователей; сводка «пользователь × поверхность × постура» — из таблицы «Постура» `user.md` | аналитик |
| `Positioning` | класс продукта, главная альтернатива со ссылкой на запись `market`, чем продукт отличается — наблюдаемо, без оценочных слов | бизнес |
| `Experience principles` | 3–5 пар «принцип → как проверить», у каждой — адрес нормы (ux 01/04 §3) | аналитик |
| `Voice` | ссылки на `<slug>/voice.yaml` (бренд) и `<slug>/voice.product.yaml` (продукт); у продукта с интерактивной поверхностью ссылка на профиль продукта обязательна | владелец продукта |
| `Success` | строки «цель → сигнал → метрика»: метрика — запись `hypothesis-map/metric.md` или наблюдаемый сдвиг; задачи приёмки «роль · ситуация · цель без слов интерфейса · планка» | бизнес |
| `MVP` | возможности первой версии `<surface>:<slug>`; решение по каждому из двенадцати системных сценариев ux 13/04 §22 — «есть» или «не нужно, потому что…» | бизнес, аналитик |
| `Devices and accessibility` | мобильный объём — «пользователь → триггер → результат → бюджет времени» или «нет» с условием ux 09/01 §1.3; паритет по умолчанию; цель доступности (WCAG 2.2 AA по умолчанию, иная — с причиной) | бизнес, аналитик |
| `Constraints` | ссылки на записи `constraint` и «что нельзя менять» или «нет» | аналитик, архитектор |
| `Non-goals` | пункт — slug записи `boundary` и одна строка; полная запись — в `boundary.md` | бизнес |
| `Assumptions` | допущения без своего раздела и вопросы заказчику или «нет» | аналитик |

Плюс для stable:

- **`addresses-problem`** — массив slug'ов строк `docs/business/business-problem.md` (≥ 1). Привязку даёт аналитик
  опциями из реестра; проблемы здесь не заводятся.
- **Оси** — перечисления, опция на значение: `audience` (`b2b` \| `b2c` \| `b2b2c` \| `internal` \| `gov`),
  `intent` (`new-service` \| `improve-service` \| `internal-problem` \| `client-problem`), `market-maturity`
  (`prospective` — разведка нового рынка \| `served` — обслуживаемый рынок; `prospective` адресует проспективные
  `ajtbd/segment.md` и `business/business-problem.md` с `served=prospective`).
- **`lifecycle`** — `draft` → `accepted` → `build` → `mvp` → `beta-testing` → `stable` → `updating`, отдельно от
  `status` записи. Переход в `stable` запускает восходящий поток `project → business` (провенанс `from-project` у
  offering, current-metric, business-problem) — его ловит `/cross-audit`.
- **Пометки `(допущение)`** — только в `Assumptions`: подтверждённый пункт теряет пометку, неподтверждённый переезжает
  в `Assumptions`.

**Статус:** маркер `**status:**` в конце файла; рядом строки `**audience:**`, `**intent:**`, `**market-maturity:**`,
`**lifecycle:**`, `**addresses-problem:**`.

**Порядок копания:** набор разделов → `Problem` → `Users` → `Success` → `Non-goals` → `Positioning` → `Experience
principles` → `Devices and accessibility` → `Constraints` → `Voice` → `Name` (имя, тип приложения) → оси →
`lifecycle` → `addresses-problem` → `Assumptions`; в фазе `cohesion` — `MVP` и сводки `Name`, `Users`.

`Problem` задаёт всё остальное: без него `Success` — про абстракцию, а `Non-goals` — про вкусовщину. Оси и
`lifecycle` — перечисления от аналитика, не угадывать. Сводки не сочиняются: расхождение исправляют в источнике и
пересобирают сводку.

## user

Файл несёт две таблицы — «Пользователи» и «Постура».

### Пользователи

**Обязательно:** `slug`, `name`, `description`, `status`.

**Должно быть для stable:** `context` — где пользователь живёт, под каким давлением; `jobs` — работы в его языке;
`pains` — наблюдаемые боли; `success` — что для него лично «полегчало»; у пользователя поверхности маршрута
приложения — ещё и полная строка постуры.

**Опционально:** `segments` — slug'и сегментов `ajtbd/segment.md`, к которым сводится пользователь (связь авторская,
снизу вверх; обратную сторону сводит `/cross-audit`). Опции — существующие сегменты, не выдумывать.

**Порядок копания:** fundamentals → `context` → `jobs` → `pains` → `success` → `segments` → постура.

`context` идёт первым: от него зависит, как формулировать работы и боли; размытый контекст даёт абстрактные работы.

### Постура

**Строка:** `user` · `surface` · `hours` · `return` · `main-work` · `posture` · `density` · `accelerators` ·
`learning`; своего `status` у строки нет — её полноту проверяет переход пользователя в `stable`.

- Строка `surface: —` — постура пользователя на всех его поверхностях; пишется в фазе `user`, до реестра поверхностей.
  Строка `surface: <slug>` — только где постура другая; пишется в фазе `surface`.
- Опции перечислений: `return` (`daily` \| `weekly` \| `monthly` \| `rare`), `main-work` (`yes` \| `no`), `posture`
  (`sovereign` \| `transient` \| `auxiliary` \| `mixed`), `density` (`high` \| `medium` \| `low`), `learning`
  (`expected` \| `minimal` \| `excluded`). `hours` и `accelerators` — словами аналитика (Other).
- `density` — поведенческая потребность; режим плотности по умолчанию и его числа решают бриф на вид и дизайн-система.

**Порядок копания:** три вопроса — `hours`, `return`, `main-work` → `posture` → `density` → `accelerators` →
`learning`. Постуру выводят из ответов на три вопроса (ux 01/01 §5.1); вывод без ответов — anti-pattern формы.

## surface (реестр-хребет)

**Обязательно:** `slug`, `name`, `description`, `status`.

**Должно быть для stable:** `type` — `web` \| `mobile` \| `api` \| `admin` \| `bot` \| `desktop` \| `embed` \|
`other`; `lives-at` — где живёт (домен, id в магазине приложений или «личная установка», мессенджер, хост); `user` —
массив slug'ов пользователей; у `type: web` — `web-kind`.

**`web-kind`** — род веб-поверхности, опциями `landing` · `site` · `app` с тестом формы (`surface.md`, критерий 6); у
остальных типов — `—`. Род выбирает маршрут и репозиторий кода: `landing` и `site` — слой страницы и `<org>/site`,
`app` — interface, экраны, FSD-карта и `<org>/frontend`.

**Порядок копания:** fundamentals → `type` → `web-kind` (у `web`) → `lives-at` → `user`.

`type` задаёт формат `lives-at`: у `web` — домен, у `mobile` — id в магазине приложений или «личная установка», у
`bot` — мессенджер; сменился тип — `lives-at` обычно переформулируют.

Поверхность — **ось**: строка реестра открывает ей место в слоях по типу и роду — файл `capability/<surface>.md`,
папки `interface/<surface>/`, `screens/<surface>/`, `fsd/<surface>/`, `site/<surface>/`,
`telegram-bot-flow/<surface>/`, `mobile/<surface>/`, `design/<surface>/` (какие — `surface.md`, врезка формы).

Решение о разделении админки и клиентской части (семь вопросов ux 13/04 §17) пишется в заметку поверхности,
`## Доменные решения`. Для `type: mobile` уведомления, виджеты, ярлыки, голосовые команды и фоновая работа — части
той же поверхности (`mobile/<surface>/`, `/mobile-deep-dive`); внешние посредники платформы — кандидаты в
`integration`, неснимаемые свойства платформы и правила магазина — в `constraint`.

## object (глоссарий объектов)

Файл несёт три таблицы — «Объекты», «Атрибуты», «Представления».

### Объекты

**Обязательно:** `slug`, `name`, `description`, `purpose`, `statuses` (или `—` у объекта без жизненного цикла),
`status`.

**Должно быть для stable:** `examples` — два-три реальных экземпляра из материалов клиента; `creates` и `deletes` —
пользователи или `system`; атрибуты рангов 1–3.

**Опционально:** `aliases` — другие названия того же объекта; в текстах и именах записей они — запрещённые синонимы.

**Кто формулирует:** аналитик; примеры — только из материалов клиента: придуманный экземпляр стал бы ложным фактом
для экранов, текстов и демо-данных (`CLAUDE.md` §3). Нет материалов — вопрос в заметке объекта, а не пример.

**Опции:** `creates`, `deletes` — пользователи из `user.md` и `system`; anti-patterns формы — «коллекция?»,
«представление?», «роль?», «единица кода?».

**Порядок копания:** `name` (как говорит пользователь, в единственном числе) → `description` → три вопроса ux 13/04
§6 (экземпляры, атрибуты, ссылка) → `examples` → `purpose` → `statuses` (пары `` `<slug>` — <имя> `` по порядку
жизненного цикла) → `aliases` → `creates` · `deletes` → атрибуты → представления.

### Атрибуты

**Обязательно:** `object`, `slug`, `name`, `rank`, `type`, `required`; `length` — у `text`; `values` — у `enum`.

- `type` — опциями: `text` \| `number` \| `money` \| `date` \| `datetime` \| `enum` \| `bool` \| `file` \|
  `ref:<object>`; множественное значение — суффикс `[]`.
- Ранг ставят по значению для пользователя, а не по порядку колонок: атрибуты 1–3 узнают экземпляр (ux 01/03 §5.3).
- Связь объектов — атрибут `ref:<object>`; атрибут, которому негде жить, требует объекта-связки (ux 13/04 §9).

**Порядок копания:** атрибуты рангов 1–3 → остальные по убыванию значения → типы → длины и перечни.

### Представления

Только исключения из правила рангов (ux 01/03 §2.3): `object` · `context` (`row` \| `card` \| `search` \| `option` \|
`notification` \| `breadcrumb` \| `inline` \| `page`) · `attributes` · `why`. Объект без исключений в таблице не
появляется.

## action (словарь действий)

**Обязательно:** `slug`, `name`, `description`, `verb`, `past`, `banned` (непуст), `reversibility`, `objects`,
`status`.

- `verb` и `past` — две формы одного слова: кнопка, заголовок подтверждения, сообщение о результате и журнал
  называют действие одним корнем (ux 04/10 §1.4).
- `banned` — запрещённые синонимы; словарь начинают с них: перечислить все разрешённые слова нельзя, а запрет даёт
  эффект сразу.
- `reversibility` — опциями `undo` \| `soft-delete` \| `confirm` \| `irreversible` (ux 04/10 §1.1): от неё зависят
  уровень кнопки, контейнер и шаг защиты в сценарии.
- `objects` — объекты глоссария, к которым действие применимо; одно действие над разными объектами — одна строка,
  если имя и обратимость совпадают.

**Кто формулирует:** аналитик; глагол — в языке пользователя, без «ОК» и брендированных слов.

**Порядок копания:** `name` → `verb` → `past` (тот же корень) → `banned` → `reversibility` → `objects` →
`description`.

## capability (файл на поверхность, `capability/<surface>.md`)

Возможность живёт в файле своей поверхности; имя файла — slug поверхности из реестра `surface.md`. Чек-лист зрелости
считается по записи; что файл относится к поверхности реестра, ловит `/project-audit`.

### Реестр

**Обязательно:** `slug`, `name`, `description`, `status`.

**Должно быть для stable:** `value` — ценность в языке пользователя; `user` — массив пользователей (≥ 1); `object` —
ровно один объект глоссария; `action` — ровно одно действие словаря; `priority` — `hub` \| `critical` \| `regular`.

**Опционально:** `trace` — трасса вверх одним массивом: `job:<slug>` (работа сегмента `ajtbd/job.md`) и
`hypothesis:<slug>` (гипотеза `hypothesis-map/hypothesis.md`); иначе `—`. Опции — существующие работы и гипотезы, не
выдумывать; обратную сторону сводит `/cross-audit`.

**Опции:** `object` и `action` — строки `object.md` и `action.md` + «нужен новый» (stub в словаре); `priority` — три
значения с определениями формы (критерий 7).

**Порядок копания:** поверхность (файл `capability/<surface>.md`) → `name` («глагол + объект», до четырёх слов) →
`description` → `value` → `user` → `object` → `action` → `priority` → `trace` → паспорт → урезание.

Возможность не заводится без поверхности: сначала строка в `surface.md`, затем файл. Нет пользователя, объекта или
действия — stub в их файле (`workflow-patterns.md § Stub-сущности`), затем возврат. Одна ценность на двух
поверхностях — две записи в **разных** файлах, у каждой своё воплощение.

### Паспорт (`## Паспорта` → `### <slug>`)

Обязателен у `hub`, `critical` и у ИИ-функции, у `regular` — по желанию. Поле, которому нечего сказать, пишется `—`,
а не пропускается.

| поле | что | опции или форма |
|---|---|---|
| `need` | потребность за задачей: зачем человеку результат | Other |
| `trigger` | когда и откуда начинается; все точки входа | Other |
| `outcome` | какой объект появится или в какой статус перейдёт | статусы из `object.md` |
| `acceptance` | 1–3 проверяемых утверждения и задача для теста | Other |
| `frequency` | частота возможности | `hours-daily` \| `daily` \| `weekly` \| `monthly` \| `rare` \| `once` |
| `error-cost` | цена ошибки и кто платит | `low` \| `medium` \| `high` + кто платит |
| `reversibility` | обратимость; по умолчанию — у действия | `undo` \| `soft-delete` \| `confirm` \| `irreversible` |
| `scope` | над чьими экземплярами | `own` \| `team` \| `all` |
| `duration` | сколько длится действие (ux 06/02 §2.2, §5.1) | `instant` \| `short` \| `long` \| `background` |
| `posture-exception` | транзитная функция внутри суверенной постуры | Other \| `—` |
| `depends-on` | интеграции и ограничения | slug'и `integration.md`, `constraint.md` \| `—` |
| `metric` | метрика возможности | запись `hypothesis-map/metric.md` \| `—` |
| `justification` | зачем возможность, если `trace` пуст и её нет в `MVP` | Other \| `—` |
| `ai` | ИИ-функция: блок ux 13/03 §1.4 с путём без ИИ | `no` \| блок `ai` |

- `error-cost: high` требует обратимости, а `irreversible` — шага защиты в сценарии возможности.
- `duration: long` на экране — индикатор прогресса и действие остановки, `background` — состояние
  `in-progress-background` в обязательном наборе экрана.
- `scope` вместе с ядром даёт строку матрицы «пользователь × объект × действие».

### Урезание (`## Урезание`)

У мобильной поверхности — ценность другой поверхности, которой здесь сознательно нет: `slug` · `capability`
(`<surface>:<capability-slug>`) · `why` — основание, данные об аудитории · `review` — когда пересмотреть · `status`.
Паритет — по умолчанию; «нет бюджета» основанием не бывает. У мобильной ширины веба то же решение пишет карта экранов
(`screens/<surface>/map.md`, раздел «Узкий экран»).

## boundary

**Обязательно:** `slug`, `name`, `description`, `status`.

**Должно быть для stable:** `why` — почему отказ продуктово правильный.

**Порядок копания:** fundamentals → `why`.

`why` — главная проверка: в нём нет продуктового аргумента (только «нет ресурсов», «потом») — это бэклог, а не
граница. Полная запись живёт здесь; раздел `Non-goals` vision держит на границу slug и одну строку, и расхождение
правят здесь, а строку vision пересобирают.

## integration

Файл несёт две таблицы: `## Провайдеры` (строка на систему) и `## Функции` (строка на функцию интеграции).

### Провайдеры

**Обязательно:** `slug`, `name`, `description`, `status`.

**Должно быть для stable:**

- `direction` — `in` \| `out` \| `duplex`.
- `payload` — что передаём и получаем в целом, в языке бизнеса.
- `owner` — `we` \| `partner` \| `both`.
- `surface` — slug'и поверхностей реестра `surface.md`, которые интеграция обслуживает (минимум одна).
- `target` — `external` \| `sibling-project`.
- `sibling-project` — **обязателен тогда и только тогда**, когда `target: sibling-project`: slug соседнего проекта
  бизнеса; при `target: external` — `—`.

**Порядок копания:** fundamentals → `direction` → `owner` → `payload` → `surface` → `target` → `sibling-project`.

`direction` и `owner` вместе показывают, как смотреть на обмен: `out` + `we` — мы вызываем их; `in` + `partner` — они
шлют нам; `duplex` + `both` — нужна явная синхронизация. `surface` привязывает интеграцию к поверхностям реестра
(slug вне реестра ловит `/project-audit`). `target: sibling-project` — обмен с другим продуктом того же бизнеса: ребро
сводится в `docs/projects/project-map.md`.

### Функции

**Обязательно:** `slug`, `integration`, `name`, `description`, `direction`, `status`.

- `integration` — slug провайдера из таблицы выше; функция без провайдера — сирота.
- `description` — что функция делает, в языке бизнеса, без адреса и сигнатуры (они — в клиенте `services/_shared/`).
- `direction` — `out` (мы зовём их функцию) \| `in` (они зовут нашу); событие — тоже функция.

`slug` функции — её общая личность на трёх высотах: здесь (бизнес), в клиенте интеграции (конкретика) и в
`functions` use-case'а, который её вызывает. Согласованность ловит `/cross-audit`.

## constraint

**Обязательно:** `slug`, `name`, `description`, `status`.

**Должно быть для stable:** `kind` — `regulation` \| `sla` \| `contract` \| `technical` \| `other`; `source` —
документ: адрес, номер закона и статья, номер контракта и пункт.

**Порядок копания:** fundamentals → `kind` → `source`.

`source` — главная проверка: не может аналитик назвать документ — это пожелание, а не ограничение.

## market

**Обязательно:** `slug`, `name`, `description`, `status`.

**Должно быть для stable:** `url` — основной сайт продукта; `sources` — статьи, обзоры, официальные страницы.

**Опционально, в `description`:** позиция (`direct` / `indirect` / `manual` / `legacy`) и наблюдаемое отличие.

Не порядок копания, а поток: `market` в основном наполняет рой агентов (`research-rays.md`), кандидаты приходят с
`url`, `sources` и позицией, аналитик подтверждает — запись заводится. В режиме A тот же поток, только кандидатов
называет аналитик.

## Универсальные нюансы

### `description`

- Одно предложение, не абзац; в языке бизнеса и пользователя: «вход без паролей», а не «JWT-аутентификация».
- Без маркетинговой копии: «передача направления одним кликом», а не «революционная платформа».

### `slug`

- Kebab-case, английский, короткий — одно-три слова: `nurse-partner` лучше `clinic-partner-receiving-nurse`.
- Уникален в пределах файла (у атрибута — в пределах объекта).
- Выводит скилл из `name` и показывает одной строкой для контроля (`.claude/rules/naming.md`); после заведения не
  меняется — это якорь ссылок в заметках и соседних слоях.

### `name`

- Человекочитаемое, в языке проекта (русский по умолчанию); длиннее `slug`, короче `description` — как заголовок
  карточки.

### `status`

- Дефолт у новой записи — `draft`; повышение — через скилл по чек-листу `draft-stable.md`; понижение — только
  аналитик руками.
