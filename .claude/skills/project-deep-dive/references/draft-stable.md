# Чек-лист `draft → stable`

После каждой правки сущности скилл прогоняет 5 пунктов. Если все ✅ —
предлагает аналитику повысить через `AskUserQuestion`. **Не повышает
сам.**

## 5 пунктов

### 1. Обязательные слоты заполнены

Для каждого kind — свой список обязательного (см.
`field-checklists.md`). Опциональные слоты могут быть `—`.

Универсально обязательное во всех 7 табличных kinds: `slug`, `name`,
`description`, `status`.

Vision — обязательны три раздела (Problem, Success, Non-goals — даже
если Non-goals пуст, секция должна явно сказать «нет ограничений» или
«определим позже») плюс непустой `addresses-problem` (≥1 slug-реф на
строку `docs/business/business-problem.md`) и оси `audience`/`intent`/
`market-maturity`/`lifecycle`. Vision без привязки к проблеме в stable не
повышается — продукт без проблемы висит в воздухе.

### 2. `Критерии <kind>` пройдены

Каждый критерий из секции `Критерии <kind>` в форме
`docs/projects/_canon/project/<kind>.md` **явно подтверждён** аналитиком
в этой или предыдущей сессии через `AskUserQuestion`. Не «скилл уверен,
что критерий выполнен», а «аналитик нажал ✅».

Если критерий из md новый (изменился канон) — нужно переспросить.

### 3. `Что <kind> НЕ` — не нарушены

По каждому anti-pattern из секции `Что <kind> НЕ` скилл прогнал
проверку через `AskUserQuestion` — «не похоже ли на anti-pattern X?»
— и получил ❌ (= «не похоже»).

Если хотя бы один anti-pattern подтвердился (✅ = «похоже») — запись
**не может стать stable**, пока не переформулирована.

### 4. `Тест-критерий` ✅

Аналитик прошёл бинарный вопрос из секции `Тест-критерий` в md и
подтвердил конкретный пример (свой случай или близкий пример из
списка ✅). Если случай попадает в ❌-категорию — повышение
блокируется.

### 5. В `state/<project-slug>/<kind>/<slug>.md` нет `**blocker**`-вопросов

Открытые вопросы без префикса `**blocker**` — не мешают (это
обычные «копать дальше»). Блокирует только то, что явно помечено как
блокирующее.

Если все 5 ✅ — `AskUserQuestion`:

> «Запись `<kind>:<slug>` прошла все 5 пунктов. Повышаем `draft →
> stable`?»

- «Да, повышаем»
- «Нет, ещё подумаю»
- «Да, но сначала закрою вопрос: <Other>»

По «да» — поменять `status: draft` на `status: stable` в файле.
Записать пустую секцию или удалить её, если в state-заметке всё
закрыто.

## Понижение `stable → draft`

Скилл **сам не понижает**. Может:

1. Подсветить: «запись `<kind>:<slug>` помечена stable, но критерий X
   нарушен / появился `**blocker**` / соседняя запись удалена и
   ссылка повисла».
2. Через `AskUserQuestion`: «понижаем обратно в draft?» — опции «да,
   понижаем» / «нет, оставляем stable, вот почему: <Other>».

Только по «да» — `status: stable → draft`. Иначе остаётся как есть, в
state-заметке появляется доменное решение «оставлен stable несмотря на
X, потому что Y».

## Когда чек-лист **нельзя пройти**

Бывают сущности, которые **проектно** не доходят до stable в этой
сессии — нужно ещё интервью, ещё research, ещё корпоративное решение.
Это нормально. Не нужно «натягивать» stable.

Признаки:

- `**blocker**`-вопрос требует ответа от бизнеса, которого здесь нет.
- Критерий из md фундаментально не выполняется (например, capability
  не имеет ни одного user — задача под кого-то другого).
- Anti-pattern подтвердился, и аналитик пока не готов переформулировать.

В этих случаях скилл просто **закрывает запись без повышения**,
оставляя `status: draft`, и предлагает следующий шаг по `phases.md`.

## Stable записи, ссылающиеся на draft

Это **допустимо**. `stable` означает «запись прошла свои критерии»,
не «вся цепочка зрелая». `/project-audit <project-slug>` подсветит hint,
не блокирует.

Пример: `capability:send-referral` (stable) ссылается на
`user:nurse-partner` (draft) — это значит, что capability
сформулирована, user заведена, но pains/jobs ещё уточняются.
Нормально.
