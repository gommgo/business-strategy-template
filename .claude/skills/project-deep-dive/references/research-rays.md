# Web-research через рой агентов

Опциональный, но мощный механизм. Основной для `market` и `constraint`,
доступный также для `integration` (поиск провайдеров) и `surface`
(поиск аналогов поверхностей в нише). **Никогда** не запускается
автоматически — только по явному решению аналитика.

## Когда применять

| фаза | повод |
|---|---|
| `market` | основной способ наполнения. Аналитик не знает наизусть всех конкурентов в нише клиента. |
| `constraint` | какие регуляторные требования применимы к этому типу продукта (PII в RU, медицинские данные, финансы). |
| `integration` | какие провайдеры есть на рынке для нужного типа интеграции (платежи в RU/EU, IDP, нотификации). |
| `surface` | реже — какие форматы поверхностей принято в нише (например, для B2B logistics — обычно admin + API, не consumer-web). |

## Запуск

1. Аналитик попросил research, или скилл предложил после артефакта по
   `phases.md`.
2. Раунд `AskUserQuestion`:
   - **Сколько углов поиска?** опции: «3 — узкий фокус», «5 — дефолт»,
     «10 — широкая разведка», «15 — full sweep».
   - **Фокус** (через Other) — одной фразой, что копать. Скилл
     преобразует во N разных углов автоматически.
3. Скилл генерит N разных промптов под одну тему (см. ниже «Шаблоны
   углов»).
4. Спавнит N агентов **параллельно** через `Agent` tool — все вызовы в
   **одном** message-блоке. `subagent_type: general-purpose` (доступ к
   WebSearch/WebFetch).
5. Ждёт всех. Каждый агент возвращает структурированный markdown-отчёт.
6. Сводит в `state/research/<query-slug>-<ts>.md` — единый файл со
   всеми отчётами, разделёнными `## <угол>` секциями.
7. Раскладывает кандидатов по kind: в конце сводного файла секция
   `## Кандидаты` с подразделами по kind:

   ```
   ## Кандидаты
   ### market
   - `doctolib` · «Doctolib» · direct EU · https://doctolib.fr · sources: [...]
   - `klaraapp` · «Klara» · indirect US · ...

   ### constraint
   - `gdpr-art-9` · «GDPR ст. 9: special category data» · regulation · https://...
   ```

8. Раунд `AskUserQuestion` по каждому кандидату — опции:
   - **«Принять в `<kind>` как `<slug>`»** — скилл создаёт строку в
     соответствующем файле со `status: draft`;
   - **«Отбросить»** — кандидат остаётся только в `state/research/`,
     не попадает в артефакты;
   - **«Доработать через Other»** — аналитик переформулирует.

   До 4 кандидатов в раунде; остальные — следующими раундами.

## Шаблоны углов

Для одной темы (`market` поиск конкурентов «B2B markdown editor for
docs teams») 5 углов = 5 разных запросов:

1. **Direct competitors** — продукты, делающие ровно то же для того же
   сегмента.
2. **Indirect/adjacent** — продукты, закрывающие ту же job, но в
   другом сегменте или формате (например, generic markdown editor).
3. **Manual workaround** — как persona делает это **руками** без
   инструмента сейчас.
4. **Category leaders** — лидеры широкой категории, даже если не
   прямые конкуренты. Полезны для понимания позиционирования.
5. **Recent entrants** — продукты, появившиеся за последний год.
   Сигнал, куда движется рынок.

10 углов — добавить:

6. Open-source альтернативы.
7. SaaS aggregators / app-stores в нише (G2 / Capterra / ProductHunt
   topics).
8. Региональные игроки (если рынок локальный — российские/EU/APAC).
9. Корпоративные in-house решения.
10. Failed / shut-down players за 2-3 года (понять why).

15 углов — добавить:

11. Подкасты / Substack / X-аккаунты в нише.
12. Конференции / митапы.
13. Reddit / HN / форумы — что обсуждают пользователи.
14. Сравнительные обзоры («X vs Y vs Z»).
15. Job postings — кто нанимает PMa/engineer'а в нишу.

Для `constraint` углы другие:

1. Регулятор RU (152-ФЗ, отраслевые).
2. Регулятор EU (GDPR, AI Act если AI).
3. Регулятор US (HIPAA / PCI-DSS / SOC2 — по типу данных).
4. Отраслевые стандарты (ISO, ГОСТ).
5. Контрактные практики в нише (типовые SLA от провайдеров).

Аналитик может задать свои углы через Other в фокусе.

## Промпт для одного агента

Каждый агент получает:

```
Тема: <фокус аналитика>
Угол: <один из шаблонных или custom>
Слой: <market | constraint | integration | surface>
Контекст продукта (из vision.md):
  Problem: …
  Success: …

Найди 3-7 кандидатов по этому углу. Для каждого:
- short slug (kebab-case, английский);
- name;
- one-sentence description, что это и какую позицию занимает;
- url основной;
- 2-3 sources (URL статьи/обзора/официального сайта/документации);
- relevance: high | medium | low — насколько подходит к Problem/Success.

Не выдумывай. Если по углу ничего нет — верни пустой список + одно
предложение почему ничего не нашёл. Не давай маркетинговую оценку —
наблюдаемые свойства.

Ответ — markdown с табличкой и списком sources.
```

## Что НЕ делать с результатами

- ❌ Авто-вписывать в `docs/project/<kind>.md`. Promotion **только**
  через `AskUserQuestion` аналитика.
- ❌ Терять отчёты — `state/research/<query>-<ts>.md` остаётся даже
  после promotion. Forward-only не означает «удаляй полезное» — это
  файл-сырьё, как материал для режима B.
- ❌ Спавнить рой повторно по той же теме без явного решения. Если
  research дал мало — лучше задать ручные точечные вопросы, чем
  второй заход агентов.
- ❌ Запускать рой во время режима B (сырьё). B и research —
  отдельные источники сырья; смешивать опасно (запутается, что от
  бизнеса, что из веба).

## Storage

```
.claude/skills/project-deep-dive/state/research/
  ├── competitors-medreferral-20250603T143000.md
  ├── pdn-constraints-20250603T144500.md
  └── …
```

Имя: `<query-slug>-<UTC-timestamp>.md`. Timestamp — для возможности
повторного захода («в марте искали — давай повторим, что изменилось»).

Внутри файла — единый отчёт со всех агентов и финальная секция
`## Кандидаты`, как описано выше.
