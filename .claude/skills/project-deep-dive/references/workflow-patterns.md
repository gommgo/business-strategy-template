# Три режима ведения сеанса

`project-deep-dive` поддерживает три явно различающихся сценария входа.
Скилл выбирает режим по виду args при запуске и далее ведёт сеанс,
комбинируя точечные шаги. Зеркалит interface-deep-dive.

## A. Новая сущность

**Сигнал**: args = `<kind>` или `<kind>:<новый-slug>` (slug ещё не
существует в файле).

### Шаги

1. Прочитать `docs/project/<kind>.md` целиком: секции `Критерии`,
   `Что НЕ`, `Тест-критерий`.
2. Раунд 1 `AskUserQuestion` — фундамент:
   - `slug` (Other) — если не дан;
   - `name` (Other);
   - `description` (Other).
3. Записать строку в `docs/project/<kind>.md` с заполненными
   `slug + name + description + status=draft`, остальные ячейки `—`.
   Для `vision.md` — записать в раздел Problem.
4. Раунд 2+ `AskUserQuestion` — батч по доменным слотам kind. См.
   `field-checklists.md`. До 4 вопросов в раунде; перемежать опции
   (anti-patterns / enums / соседи) и Other (значения).
5. Если в поле нужна ссылка на ещё не существующую сущность — отработать
   **stub** (см. SKILL.md): создать stub-запись, записать state-заметку
   с открытым вопросом, продолжить текущую запись.
6. После всех слотов — раунд `AskUserQuestion` по `Тест-критерий`:
   варианты ✅/❌ из примеров md как опции. Аналитик подтверждает.
7. Применить чек-лист `draft-stable.md`. Если все 5 ✅ — предложить
   повышение в stable.
8. Записать `state/<kind>/<slug>.md`, если есть что (открытые вопросы,
   неочевидные доменные решения).
9. Предложить логичный следующий шаг по `phases.md`.

### Пример раунда (persona, после фундамента)

Скилл предлагает четыре вопроса разом:

- **context** — Other (свободно: «где persona живёт, под каким
  давлением»).
- **jobs** — Other (jobs-to-be-done в её языке, списком).
- **pains** — Other (наблюдаемые боли).
- **success vs vision.success** — две опции: «совпадает с vision.success»
  / «отличается, вот как» (Other).

## B. Сырьё

**Сигнал**: args = свободный текст / транскрипт интервью с бизнесом /
заметки / письмо клиента.

### Шаги

1. Прочитать материал внимательно.
2. Извлечь кандидатов по слоям. **Не** угадывать значения доменных
   полей — только то, что **прямо названо** в материале:
   - persona — кто упомянут как «пользователь / клиент / адресат»;
   - capability — что «продукт / сервис / решение умеет/будет уметь»;
   - surface — где «работаем / пользуемся / на телефоне / в админке»;
   - integration — какие внешние «системы / провайдеры / партнёры»;
   - constraint — какие «законы / договоры / обязательства»;
   - boundary — что «не делаем / не наш скоуп / отдаём наружу»;
   - market — кто упомянут как «конкурент / аналог / альтернатива».
3. Через чат показать план:

   ```
   Из материала вижу:
     persona: nurse-partner, doctor (кандидаты)
     capability: send-referral, check-status
     surface: web-partner
     integration: clinic-mis (упомянули МИС партнёра)
     boundary: no-insurance (явно сказано «страховку не считаем»)
   Так?
   ```

4. Раунд `AskUserQuestion` — подтвердить план / поправить через Other.
5. По подтверждению — завести **stub'ы** в файлах (минимум `slug + name
   + description + status=draft`); создать state-заметки с открытыми
   вопросами «извлечено из сырья — уточнить <что>».
6. Через `AskUserQuestion` — выбрать, какую сущность углубить первой
   (предложение по логике фаз).
7. Перейти в режим C на выбранной. Повторить для остальных.

### Что НЕ делать в режиме B

- Не объявлять извлечённое «зафиксированным». Это кандидаты до
  подтверждения аналитика.
- Не угадывать `jobs`, `pains`, `value`, `payload`, `source` по сырью
  — только `name` / `description` максимально близко к языку аналитика
  или клиента.
- Не выдумывать кандидатов, которых в материале нет, «потому что
  обычно бывают».
- Не запускать рой агентов автоматически. Research — отдельное
  решение аналитика.

## C. Углубление

**Сигнал**: args = `<kind>:<slug>` существующей записи, либо аналитик
выбрал из сводки.

### Шаги

1. Прочитать строку из `docs/project/<kind>.md` (для vision —
   `vision.md` целиком).
2. Прочитать `state/<kind>/<slug>.md`, если есть.
3. Прочитать соседей семантически: для `capability` — какие persona
   упомянуты, есть ли они; для `surface` — какие persona, какие
   capability у них; для `integration` — какие constraint могли бы
   быть применимы.
4. Применить `docs/project/<kind>.md` секции к строке. Найти:
   - пустые обязательные слоты;
   - подозрения по anti-patterns (capability похожа на фичу, boundary
     похож на backlog, constraint без source);
   - семантические тупики (surface без persona, market без sources).
5. Раунд `AskUserQuestion` (до 4 вопросов) — точечно по найденному:
   - дыры — заполняем через Other;
   - anti-pattern-подозрения — опции «да, anti-pattern» / «нет, вот
     почему» (через Other);
   - семантические тупики — опции «связать с <варианты>» / «оставить
     как есть, потому что <Other>».
6. Применить ответы: правка строки, обновление state-заметки.
7. После раунда — повторно прогнать чек-лист `draft-stable.md`.
   Если все 5 ✅ — предложить повышение в stable.
8. Если осталась хотя бы одна дыра или подозрение — следующий раунд.

### Когда переходить от C к завершению

- Все 5 пунктов чек-листа ✅ → предложить stable, по подтверждению
  поменять status.
- Остался `**blocker**`-вопрос, на который аналитик сейчас ответить не
  может → зафиксировать в state-заметке, оставить `status: draft`,
  выйти из углубления этой сущности; предложить другую или сводку.

## Стиль вопросов

### Когда давать опции

| ситуация | формат |
|---|---|
| anti-pattern из `Что <kind> НЕ` | две опции: «соответствует anti-pattern» / «не соответствует» (объяснить почему через Other) |
| enum поле (`surface.type`, `integration.direction`, `integration.owner`, `constraint.kind`) | по одной опции на каждое значение enum |
| тест-критерий из `Тест-критерий` | опции из примеров ✅/❌, аналитик соотносит свой случай |
| выбор существующего slug соседа | по опции на каждый существующий + «нужен новый» (Other) |
| перепрыгивание фазы | две-три опции «потому что X / Y / Other» |
| запуск research | «5 агентов» / «10 агентов» / «15 агентов» / «не запускать сейчас» |
| promotion кандидата из research в артефакт | «принять как `<kind>:<slug>`» / «отбросить» / «доработать через Other» |

### Когда не давать опции, только Other

| поле | почему |
|---|---|
| `name` | человекочитаемое имя — формулировка аналитика |
| `description` | смысл записи — слова аналитика |
| `value`, `jobs`, `pains`, `success` у persona | доменная семантика, не угадывать |
| `why` у boundary | продуктовое решение в словах аналитика |
| `payload` у integration | бизнес-контракт, формулирует аналитик |
| `source` у constraint | конкретный документ, ищет аналитик |
| любой slug, который ещё не существует | аналитик называет, не скилл |

### Чего не делать

- Не предлагать «образцы» вроде «может быть, value такой?» — это
  выдумывание домена.
- Не упоминать «правильные» формулировки из md как опции в виде
  готовых текстов значений. Примеры в md — иллюстрация канона, не
  варианты для текущего проекта.
- Не задавать больше 4 вопросов в одном `AskUserQuestion`. Если
  нужно больше — следующий раунд.
- Не закрывать сессию без чек-листа `draft-stable.md` хотя бы по одной
  правленой сущности.
