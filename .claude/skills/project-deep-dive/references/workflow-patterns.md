# Режимы сеанса и приведение к канону

`project-deep-dive` различает три сценария входа — новая сущность, сырьё, углубление — и выбирает режим по виду
аргументов, дальше комбинируя точечные шаги. Отдельный сценарий — проект, чьи файлы разошлись с формой слоя, приводится
к канону (раздел «Привести к канону»).

Все пути **скоупятся в выбранный проект**. Данные пишутся в:

- vision — `docs/projects/<project-slug>/vision.md`;
- восемь плоских таблиц — `docs/projects/<project-slug>/<kind>.md`: `surface`, `user` (с таблицей «Постура»),
  `object` (с таблицами «Атрибуты» и «Представления»), `action`, `integration`, `boundary`, `constraint`, `market`;
- возможности — **файл на поверхность** `docs/projects/<project-slug>/capability/<surface>.md` (реестр, паспорта,
  урезание).

Форму — критерии, «Что НЕ», тест-критерий — скилл читает из канона `docs/projects/_template/project/<kind>.md`; у
возможностей форма одна на все поверхности — `docs/projects/_template/project/capability.md`.

## A. Новая сущность

**Сигнал:** аргументы `<project-slug> <kind>` или `<project-slug> <kind>:<новый-slug>` (такого slug в файле нет).

### Шаги

1. Прочитать форму kind целиком: `Критерии`, `Что НЕ`, `Тест-критерий`.
2. У возможности **сначала поверхность**: из аргумента `capability:<surface>:<slug>` или пикером по реестру
   `surface.md` (по именам). Поверхности в реестре нет — предложить сперва завести её.
3. Раунд 1 `AskUserQuestion` — фундамент: `name` и `description` (Other). `slug` скилл выводит из `name` и показывает
   одной строкой для контроля (`.claude/rules/naming.md`).
4. Записать строку в файл данных — `slug`, `name`, `description`, `status: draft`, остальные ячейки `—`:
   - плоские таблицы → `<kind>.md`; атрибут объекта → таблица «Атрибуты» `object.md`; постура → таблица «Постура»
     `user.md` (своего `status` у её строки нет);
   - возможность → `capability/<surface>.md`; файла нет — завести из формы;
   - vision → его разделы; в фазе `discovery` — ещё набор разделов, оси, `lifecycle` и `addresses-problem` (опции —
     строки `docs/business/business-problem.md`).
5. Раунд 2+ — доменные слоты kind в порядке `field-checklists.md`, до четырёх вопросов в раунде, опции (anti-patterns,
   перечисления, соседи) вперемешку с Other (значения). У возможности — ядро (`object`, `action` опциями из словарей),
   `priority`, `trace`, затем паспорт у `hub`, `critical` и ИИ-функции; у интеграции — `surface`, `target` и
   `sibling-project`.
6. Нужна ссылка на ещё не существующую сущность — **stub** (раздел «Stub-сущности»), затем возврат к записи.
7. Раунд по `Тест-критерий`: примеры ✅/❌ формы опциями, аналитик соотносит свой случай.
8. Чек-лист `draft-stable.md`; все пять ✅ — предложить повышение.
9. Заметка, если есть что записать (открытые вопросы, неочевидные решения):
   `../entrypoint/state/projects/<project-slug>/project/<kind>/<slug>.md`; у возможности —
   `…/project/capability/<surface>/<slug>.md`.
10. Интеграция с `target: sibling-project` — напомнить, что ребро межпроектного стыка сводится в
    `docs/projects/project-map.md`.
11. Предложить логичный следующий шаг по `phases.md`.

### Примеры раундов (иллюстрация формы вопросов, не образец ответов)

Пользователь, после фундамента — четыре вопроса разом: `context` (Other); `jobs` (Other, списком); `pains` (Other);
«успех пользователя совпадает с `Success` vision?» — «совпадает» / «отличается, вот как» (Other).

Возможность, после фундамента: «над каким объектом?» — объекты `object.md` + «нужен новый»; «какое действие?» —
действия `action.md` + «нужно новое»; «приоритет?» — `hub` / `critical` / `regular` с определениями формы; «во что
целит вверх?» — работы сегмента и гипотезы + «нет трассы».

## B. Сырьё

**Сигнал:** аргументы `<project-slug>` + свободный текст, транскрипт интервью с бизнесом, заметки, письмо клиента.

### Шаги

1. Прочитать материал целиком.
2. Извлечь кандидатов по kind — только то, что **прямо названо** в материале:
   - `user` — кто назван пользователем, клиентом, адресатом; факты постуры — «весь день в системе», «заходит раз в
     месяц», «это его основная работа»;
   - `surface` — где «работаем, пользуемся, на телефоне, в админке»; признаки рода — «лендинг акции», «сайт
     компании», «личный кабинет»;
   - `object` — вещи с экземплярами, которые называет клиент («заявка», «направление»); названные реальные экземпляры
     — кандидаты в примеры;
   - `action` — глаголы, которыми клиент называет работу с объектами, и слова, которые он путает;
   - `capability` — что продукт «умеет или будет уметь», **с привязкой к поверхности**; поверхность неясна —
     пометить «поверхность уточнить»;
   - `integration` — внешние системы, провайдеры, партнёры; другой продукт того же бизнеса — `target:
     sibling-project`;
   - `constraint` — законы, договоры, обязательства; `boundary` — «не делаем», «не наш скоуп»; `market` —
     конкуренты, аналоги, альтернативы.
3. Показать план в чат (пример — иллюстрация):

   ```
   Из материала вижу:
     user:       nurse-partner, doctor (кандидаты); постура медсестры — «между приёмами, на телефоне»
     surface:    web-partner (кабинет → род app?), tg-bot
     object:     referral («направление»), study («исследование»)
     action:     send («отправить»; в тексте ещё «переслать», «передать»)
     capability:
       web-partner: send-referral, check-status
       tg-bot:      check-status (своё воплощение в боте)
     integration: clinic-mis (external); loyalty-app (соседний продукт → sibling-project)
     boundary:    no-insurance («страховку не считаем»)
   Так?
   ```

4. `AskUserQuestion` — подтвердить план или поправить через Other.
5. По подтверждению — **stub'ы** в файлах (`slug`, `name`, `description`, `status: draft`) и заметки с открытыми
   вопросами «извлечено из сырья — уточнить <что>»; названные экземпляры объектов — в заметку объекта кандидатами в
   примеры.
6. `AskUserQuestion` — какую запись углубить первой (предложение — по логике фаз).
7. Режим C на выбранной; повторить для остальных.

### Границы режима B

- Извлечённое — кандидаты до подтверждения аналитика, а не записи.
- По сырью заполняются только `name` и `description`, близко к языку аналитика или клиента; `jobs`, `pains`, `value`,
  постура, примеры объектов, `payload`, `source` добываются вопросами в режиме C: догадка по сырью легла бы в
  артефакт фактом.
- Кандидат появляется, только если он прямо назван в материале; «обычно так бывает» — не основание.
- Research-рой — отдельное решение аналитика; режим B его не запускает.

## C. Углубление

**Сигнал:** аргументы `<project-slug> <kind>:<slug>` существующей записи, либо аналитик выбрал запись из сводки.

### Шаги

1. Прочитать запись (vision — `vision.md` целиком; возможность — в файле поверхности из аргумента
   `capability:<surface>:<slug>` или пикером).
2. Прочитать её заметку, если есть.
3. Прочитать соседей в пределах проекта: у возможности — есть ли её пользователи, объект и действие, применимо ли
   действие к объекту (`action.objects`), есть ли паспорт у хаба; у пользователя — строка постуры; у объекта — кто
   создаёт и удаляет, атрибуты рангов 1–3; у поверхности — пользователи, род, файл возможностей; у интеграции —
   поверхности реестра и `sibling-project`, применимые ограничения.
4. Применить к записи секции формы и найти:
   - пустые обязательные слоты (`field-checklists.md`);
   - подозрения по anti-patterns: возможность-фича, два действия или две частоты в одной возможности, зонтичный
     глагол, слова интерфейса; объект-коллекция или представление; действие с двумя корнями; `web` без рода; граница
     похожа на бэклог; ограничение без источника; соседний продукт как `target: external`; у vision — принцип без
     проверки, маркетинговая лексика, пометки `(допущение)` вне `Assumptions`;
   - семантические тупики: поверхность без пользователя, рынок без источников, возможность в файле поверхности вне
     реестра, сводка vision разошлась с источником.
5. Раунд `AskUserQuestion` (до четырёх вопросов) по найденному: дыры — Other; подозрения — «да, anti-pattern» / «нет,
   потому что» (Other); тупики — «связать с <варианты>» / «оставить, потому что» (Other).
6. Применить ответы: правка записи, обновление заметки.
7. Повторить чек-лист `draft-stable.md`; все пять ✅ — предложить повышение.
8. Осталась дыра или подозрение — следующий раунд.

### Когда переходить от C к завершению

- Все пять пунктов ✅ → предложить stable; по подтверждению — сменить статус.
- Остался `**blocker**`-вопрос, на который аналитик сейчас не ответит, → записать в заметку, оставить `draft`, выйти
  из углубления записи и предложить другую или сводку.

## Стиль вопросов

### Когда давать опции

| ситуация | формат |
|---|---|
| anti-pattern из `Что <kind> НЕ` | «соответствует anti-pattern» / «не соответствует» (почему — Other) |
| перечисление: `surface.type`, `surface.web-kind`, постура (`return`, `main-work`, `posture`, `density`, `learning`), `capability.priority`, поля паспорта (`frequency`, `error-cost`, `reversibility`, `scope`, `duration`), `action.reversibility`, тип атрибута, контекст представления, `integration.direction`, `integration.owner`, `integration.target`, `constraint.kind` | опция на каждое значение, с определением из формы |
| тест-критерий | примеры ✅/❌ формы, аналитик соотносит свой случай |
| выбор существующего соседа: пользователь, объект, действие, работа сегмента, гипотеза | опция на каждую существующую запись + «нужен новый» (Other) |
| поверхность для возможности, `integration.surface` | опция на каждую поверхность реестра (по именам) + «нужна новая» |
| `integration.sibling-project` | опция на каждый проект `docs/projects/` (кроме текущего и `_template`) + «нужен новый проект» |
| пункт раздела vision «допущением» | предложение агента с пометкой `(допущение)` / «переформулирую сам» (Other) / «в `Assumptions`» |
| запрещённые синонимы действия (`banned`) | кандидаты-синонимы глагола опциями, аналитик отмечает запрещённые + Other |
| перепрыгивание фазы | «потому что X / Y» / Other |
| запуск research | «5 агентов» / «10 агентов» / «15 агентов» / «не запускать сейчас» |
| кандидат из research в артефакт | «принять как `<kind>:<slug>`» / «отбросить» / «доработать» (Other) |

### Когда не давать опции, только Other

| поле | почему |
|---|---|
| `name`, `description` | имя и смысл записи — слова аналитика |
| `value`, `jobs`, `pains`, `success` | доменная семантика, не угадывать |
| примеры объектов (`examples`) | только реальные экземпляры из материалов клиента |
| `verb`, `past` действия | глагол продукта — в языке его пользователей |
| `hours`, `accelerators` постуры | наблюдение о работе пользователя |
| `why` границы, основание урезания | продуктовое решение в словах аналитика |
| `payload` интеграции, `source` ограничения | бизнес-контракт и конкретный документ называет аналитик |

`slug` новой записи не спрашивается ни опцией, ни через Other: скилл выводит его из `name`.

**«Допущение» — только для разделов vision** (`CLAUDE.md` §3): агент предлагает пункт из материалов клиента,
транскриптов и подтверждённого research и помечает его `(допущение)`; владелец подтверждает (пометка снимается) или
отклоняет. Числа, цены, сроки, имена и метрики допущением не бывают: нет источника — вопрос владельцу.

### Чего избегать

- Образцов значений от себя вне разделов vision («может быть, value такой?») и примеров формы в роли готовых опций:
  примеры в форме иллюстрируют канон, а не предлагают ответ для проекта.
- Больше четырёх вопросов в одном `AskUserQuestion` — остальное следующим раундом.
- Закрытия сессии без чек-листа `draft-stable.md` хотя бы по одной правленой записи.

## Stub-сущности

Запись ссылается на сущность, которой ещё нет (возможность назвала пользователя, объект или действие, которых нет):

1. В файле этой сущности — новая строка `slug`, `name`, `description`, `status: draft`, остальные ячейки `—`.
   Stub-объект и stub-действие ложатся в `object.md` и `action.md` (так заходят со списка функций до объектов);
   stub-возможность — в файл своей поверхности; поверхности нет в реестре — сначала stub-строка `surface`.
2. В заметке stub-записи — `## Открытые вопросы`: «заведён как stub в контексте `<откуда сослались>` — докопать в
   фазе `<phase>`» (`…/project/<kind>/<stub-slug>.md`; у возможности — `…/project/capability/<surface>/<stub-slug>.md`).
3. Возврат к исходной записи.

## Удаление сущности (каскад)

1. Прочитать продуктовый слой проекта — vision, восемь плоских таблиц, все файлы возможностей — и ветку
   `../entrypoint/state/projects/<project-slug>/project/`: найти все упоминания удаляемого slug.
2. Показать каскад: «упоминается в `<файлы>` — вот что поправить».
3. По каждому месту — `AskUserQuestion`: «заменить на другой slug» / «удалить упоминание» / «оставить как есть».
4. По подтверждению — все правки одним пакетом; затем удалить запись из её файла и её заметку.
5. Особые случаи:
   - **поверхность** — её файл возможностей и ссылки `integration.surface` повисают: решить судьбу файла (перенести
     записи на другую поверхность или удалить); строки постуры `surface: <slug>` — удалить или перенести. Папки
     `interface/`, `screens/`, `fsd/`, `site/`, `telegram-bot-flow/`, `mobile/`, `design/` этой поверхности ведут
     свои скиллы — здесь только предупредить, что они осиротеют;
   - **объект или действие** — ядро возможностей (`object`, `action`), `action.objects`, атрибуты `ref:<object>`,
     представления; ссылки соседних слоёв — зоны и данные interface, поля экранов, атрибут `action=`, реестр текстов —
     ведут их скиллы: предупредить и назвать `/interface-deep-dive` и `/screen-deep-dive`;
   - **пользователь** — строки постуры, `creates` и `deletes` объектов, `capability.user`, `surface.user`; удалён
     единственный пользователь — спросить, не пора ли пересмотреть vision.

## Привести к канону

Файлы проекта расходятся с формой слоя — например, форк обновил шаблон поверх заполненного проекта. Тогда проект
приводится к канону `docs/projects/_template/project/`: колонки, разделы и файлы — как в форме. Цель — чтобы аудиты,
соседние слои и код-репо читали продукт по одной форме, не потеряв ни одной формулировки владельцев.

**Когда.** При запуске скилл сверяет файлы проекта с формой: файлы слоя, колонки таблиц и их порядок, разделы vision,
таблицы «Постура», «Атрибуты», «Представления», разделы «Паспорта» и «Урезание». Расхождения видит и `/project-audit`.
Расхождений мало — они правятся по ходу, в режиме C; много — скилл первым пунктом сводки предлагает пакет «Привести к
канону».

**Пакет** показывается списком по файлам и делится на две части.

**Механические правки** скилл делает сам после одного подтверждения, показав различие по каждому файлу:

- недостающие файлы слоя — из формы с пустыми таблицами (`object.md`, `action.md`); недостающие разделы — каркасом
  формы: разделы vision своего набора в порядке формы (текст существующих разделов остаётся на месте), таблица
  «Постура» в `user.md`, разделы «Паспорта» и «Урезание» в файлах возможностей;
- колонки — по форме и в её порядке: недостающая колонка встаёт на своё место; значения колонок вне канона
  раскладываются по колонкам канона, где у их смысла есть место, — например, ссылки возможности на работы сегмента и
  гипотезы, записанные вне `trace`, переезжают в `trace` с префиксами `job:` и `hypothesis:`; колонку, смыслу
  которой места в форме нет, скилл не удаляет, а переносит её значения в заметки записей и спрашивает владельца;
- значения, которые однозначно следуют из других полей: `web-kind: —` у поверхности не типа `web`; сводки `Name` и
  `Users` vision — из `surface.md` и таблицы «Постура», когда источники есть;
- форма ячеек: slug'и в обратных кавычках, массивы, прочерк у пустого опционального поля
  (`docs/projects/_template/project/README.md § Форма ячеек`).

**Смысловые правки** — владельцу формулировки (`CLAUDE.md` §3); скилл спрашивает и не угадывает: новые разделы vision
(кроме сводок), постура пользователей, род каждой поверхности `web`, объекты и действия (имена, определения, примеры
из материалов клиента, статусы, кто создаёт и удаляет), ядро возможностей (`object`, `action`, `priority`), паспорта
хабов, критичных и ИИ-функций, разделение возможности с двумя действиями или двумя частотами, развёрнутые абзацы
`Non-goals` — в записи `boundary.md`. Вопросы идут раундами режима C по владельцам: бизнес, аналитик.

**Пустое — не прочерк.** Пока владелец не ответил, новая обязательная ячейка остаётся пустой. Там, где `—` — значение
(`web-kind` не веб-поверхности, `statuses` объекта без жизненного цикла, `trace` без ребра вверх), прочерк ставится,
только когда он следует из других полей: иначе он стал бы молчаливым решением за владельца, а пустую ячейку аудит
видит как пробел. Вопрос по каждой такой ячейке — в заметке записи в своей ветке state.

**Статусы.** Stable-записи скилл не понижает — понижение делает только аналитик
(`docs/projects/_template/project/README.md § Статус записи`). Пустой обязательный слот stable-записи — находка
`/project-audit`, и список этих находок — список работ перевода: аналитик добивает запись или понижает её сам.

**Порядок — по зависимостям.** Сначала продукт — vision, постура, род поверхностей, объекты и действия, возможности;
затем interface (`/interface-deep-dive`: объекты данных и зон, поля навигации зон, сценарии хабов, частота и отказы
ситуаций), экраны (`/screen-deep-dive`), FSD-карта (`/fsd-deep-dive`), стыки мобильного приложения и бота. Этот
скилл ведёт продукт и в конце называет следующего исполнителя.

**Не выдумывать.** Примеры объектов, статусы, род поверхности, приоритет и значения паспортов даёт владелец; находки
research попадают в артефакт только через `AskUserQuestion`. Заметки держат открытые вопросы перевода, а не его
историю.
