# project-deep-dive

Углублённая проработка артефактов в `docs/project/`. Канон —
`docs/project/README.md`. Скилл ведёт сеанс через 8 фаз вижн-мейкинга,
структурированные вопросы (`AskUserQuestion`), фиксирует контекст в
`state/`, не выдумывает домен и не пишет маркетинговую копию.

Использовать как **единственную точку входа** в `docs/project/` для
аналитика: заведение, углубление, разбор сырья, фаз-навигация, переход
`draft → stable`, удаление с каскадом, market/constraint research через
рой агентов.

## Точки входа

| вызов | поведение |
|---|---|
| `/project-deep-dive` | сводка состояния по фазам + предложение следующего шага |
| `/project-deep-dive <kind>` | завести новую сущность типа kind (режим A) |
| `/project-deep-dive <kind>:<slug>` | углубить существующую запись (режим C) |
| `/project-deep-dive <slug>` | найти slug; одиночный → C; конфликт kind → переспросить |
| `/project-deep-dive <свободный текст / транскрипт>` | сырьё → разбор (режим B) |
| `/project-deep-dive --phase <name>` | принудительно работать в указанной фазе |
| `/project-deep-dive --research <kind>:<query>` | запустить рой агентов на тему |

`kind` ∈ {`vision`, `persona`, `capability`, `boundary`, `surface`,
`integration`, `constraint`, `market`}.

`phase` ∈ {`discovery`, `persona`, `capability`, `surface`,
`integration`, `constraint`, `market`, `cohesion`}.

## Что делать сразу при запуске

1. Прочитать `docs/project/README.md` — освежить канон 8 kinds и связи.
2. Прочитать `references/phases.md` — карту 8 фаз.
3. Если args пустые — сделать **сводку по фазам** (см. ниже) и через
   `AskUserQuestion` предложить выбор: продолжить текущую фазу /
   перепрыгнуть / разобрать сырьё / запустить research.
4. Если args указывают на сущность — определить kind и режим (A/B/C),
   применить маршрут из `references/workflow-patterns.md`.
5. Если `--research` — перейти к `references/research-rays.md`.
6. Если `--phase` — открыть карту фазы из `references/phases.md`.

## Сводка состояния (без args)

Скилл всегда даёт аналитику **карту, где он находится в воркфлоу**, а не
просто список draft-записей. Это ключевое отличие от interface-канона.

1. Прочитать `vision.md` + все 7 табличных файлов.
2. Подсчитать: `draft` / `stable` по каждому kind, плюс существует ли
   vision (если нет — текущая фаза = `discovery`).
3. Прочитать `state/` (своё + read-only из
   `../project-deep-dive-for-business/state/`, если каталог существует)
   — собрать открытые вопросы, особенно `**blocker**`.
4. Определить **текущую фазу** по дереву:
   - vision не существует или status:draft → `discovery`;
   - persona-таблица пустая → `persona`;
   - capability-таблица пустая → `capability`;
   - surface пустая → `surface`;
   - integration пустая → `integration`;
   - constraint пустая → `constraint`;
   - market пустая → `market`;
   - все заполнены, но есть draft-записи или blocker-вопросы → `cohesion`.
5. Вывести сводку в чат:

   ```
   Текущая фаза: <name> (<n>/<N>)
   docs/project/ покрытие:
     vision      [draft]
     persona     3 stable, 1 draft
     capability  2 draft
     surface     —
     integration —
     constraint  —
     market      —
     boundary    1 stable
   Открытых blocker-вопросов: 2
   Готов клиент-черновик в ветке: client/<slug>/<ts>  (если есть)
   ```

6. Через `AskUserQuestion` (до 4 опций) предложить:
   - продолжить фазу `<name>` — что копать первым;
   - перепрыгнуть в фазу `<other>` (с обоснованием);
   - разобрать сырьё (вставит свободным текстом / транскриптом);
   - запустить research-рой по теме.

## Фазы проработки

Скилл **глубоко проактивно** ведёт через 8 фаз. Полная карта фаз —
`references/phases.md`. Кратко, по порядку:

| фаза | цель | артефакты на выходе |
|---|---|---|
| `discovery` | vision.md draft → stable; первое касание проблемы и успеха | `vision.md` |
| `persona` | сегменты пользователей/клиентов | `persona.md` |
| `capability` | бизнес-возможности верхнего уровня | `capability.md` |
| `surface` | где продукт «торчит наружу» | `surface.md` |
| `integration` | внешние системы | `integration.md` |
| `constraint` | регуляторика / SLA / контракты | `constraint.md` |
| `market` | конкуренты и аналоги (с роем агентов) | `market.md` |
| `cohesion` | boundary + сквозная проверка, что слой целостен | `boundary.md`, повышение `draft → stable` |

Порядок — рекомендация, не закон. Аналитик может перепрыгнуть. Скилл
**в начале каждой сессии напоминает**, какая фаза сейчас и почему, и
**после каждого артефакта** предлагает логичный следующий шаг с
обоснованием. См. `references/phases.md` для предложений-переходов.

## Три режима

См. `references/workflow-patterns.md` — детали сценариев и примеры
вопросов. Зеркалит interface-deep-dive:

- **A. Новая сущность**. Args = `<kind>` или `<kind>:<новый-slug>`.
  Батч `AskUserQuestion` по `Критерии <kind>` из соответствующего
  md-файла; опции — anti-patterns из `Что <kind> НЕ`; свободная форма
  через Other для значений.
- **B. Сырьё**. Args = свободный текст или транскрипт интервью с
  бизнесом. Извлечь кандидатов по слоям (persona / capability /
  surface / integration / constraint / market), показать план, по
  подтверждению завести stub-строки, погрузиться в каждую через C.
- **C. Углубление**. Args = `<kind>:<slug>` или выбран из сводки.
  Точечные вопросы по дырам и подозрениям; чек-лист `draft → stable`
  после каждой правки.

## Стиль вопросов

См. `references/workflow-patterns.md` (раздел «Стиль вопросов»). Краткий
канон:

- **Всегда через `AskUserQuestion`**, до 4 вопросов в одном раунде.
- **Опции** только для:
  - anti-patterns из секции `Что <kind> НЕ` («это похоже на anti-pattern
    X — согласен?»);
  - теста-критерия (бинарный выбор ✅/❌ из секции `Тест-критерий`);
  - структурного перечисления (enum типа `surface.type`,
    `integration.direction`, `constraint.kind`);
  - выбора существующего slug соседа («связать с persona X / Y / нужен
    новый»).
- **Свободная форма** (через Other) — для **значения**: `name`,
  `description`, `value`, `jobs`, `pains`, `why`, `payload`, `source`,
  имена ключевых ролей и систем.
- **Никогда** не предлагать конкретные тексты доменных полей от себя.
  Anti-patterns — да. Сама формулировка — нет.

## Память `state/<kind>/<slug>.md`

Заметки лежат **рядом со скиллом**:

```
.claude/skills/project-deep-dive/state/<kind>/<slug>.md
```

Для `vision` — singleton: `.claude/skills/project-deep-dive/state/vision.md`.

Дополнительный каталог `state/research/` — для отчётов роя агентов
(см. `references/research-rays.md`).

См. `references/state-format.md`. Кратко:

- Файл существует, пока в нём есть хоть одна секция с содержимым.
- Три возможные секции (любая может отсутствовать):
  - `## Открытые вопросы` (опц. префикс `**blocker**`);
  - `## Доменные решения` (неочевидные смысловые решения, не лезущие в
    `description`);
  - `## Что копать дальше`.
- Forward-only: не аккумулировать «было/стало».
- Если все три секции пустые — заметку удалить.

### Read-only видимость state соседнего скилла

Скилл может (но не обязан) **read-only смотреть**
`../project-deep-dive-for-business/state/` — чтобы видеть, что клиент
наработал в режиме «домашнее задание». **Не пишет туда**. Если клиент
прислал черновик через push в ветку `client/<slug>/<ts>` — этот state
появляется в файловой системе после merge / fetch, обычная git-механика.

## Семантические связи (без жёстких slug-валидаций)

В отличие от `docs/interface/`, project-слой **не валидирует**
slug-ссылки между записями. Связи семантические:

- `persona.slug` упоминается в `surface.persona` и `capability.persona`
  — но и без явного полей-связи запись может быть валидна;
- `capability` без persona — не ошибка, но подозрительно (повод
  поднять при cohesion);
- `surface` без persona — мёртвая, повод задать вопрос;
- `constraint` обычно привязан к surface или integration в `description`,
  не отдельным полем.

`/project-audit` ловит **внутрипроектные** тупики (пустые обязательные
слоты, draft без якоря). `/cross-audit` ловит **между-слойные**
несостыковки (persona без покрытия в interface.who и т.п.). Сам
project-deep-dive — **не аудитор**; в конце сессии предложит запустить
один из них.

## Контракт `draft → stable`

См. `references/draft-stable.md`. Чек-лист после каждой правки:

1. Обязательные слоты заполнены (опциональные могут быть `—`).
2. `Критерии <kind>` пройдены — аналитик подтвердил в этой сессии через
   `AskUserQuestion`.
3. `Что <kind> НЕ` — не нарушены (anti-patterns исключены).
4. `Тест-критерий` ✅ — аналитик явно подтвердил пример своего случая.
5. В `state/<kind>/<slug>.md` нет `**blocker**`-вопросов.

Если все 5 ✅ — предложить через `AskUserQuestion`: «Готов к stable,
повышаем?». По подтверждению — изменить `status: draft → stable`. Скилл
**не повышает сам**. Понижение `stable → draft` — только аналитик
руками.

## Web-research через рой агентов

Опциональный механизм, основная для `market` и `constraint`, доступный
и для `integration`/`surface` как помощь в разведке. См.
`references/research-rays.md`. Кратко:

1. Аналитик подтвердил запуск (через `AskUserQuestion`, дефолт = 5
   агентов; можно изменить).
2. Скилл генерит N разных углов поиска по одной теме (конкуренты в
   нише X / регуляторика в RU / провайдеры платежей в B2C / …).
3. Спавнит N агентов параллельно через `Agent` tool (subagent_type:
   general-purpose, доступ к WebSearch/WebFetch).
4. Каждый агент возвращает структурированный отчёт.
5. Скилл сводит в `state/research/<query>-<ts>.md` + раскладывает
   кандидатов по kind (`market`, `constraint`, …).
6. Аналитик проходит кандидатов через `AskUserQuestion` — какие
   принимаем в артефакты, какие отбрасываем. **Авто-promotion в
   `docs/project/` запрещён** — слишком высок риск галлюцинаций.

## Stub-сущности

Если копаемая сущность ссылается семантически на ещё не существующий
slug (например, capability упомянула persona, которой ещё нет):

1. В соответствующем файле — новая строка: `slug + name + description
   + status=draft`, остальные ячейки `—`.
2. В `state/<kind>/<stub-slug>.md` — секция `## Открытые вопросы` с
   записью «Заведён как stub в контексте `<откуда сослались>` —
   докопать в фазе `<phase>`».
3. Возврат в исходную сущность, копание продолжается.

## Удаление сущности (каскад)

1. Прочитать все 8 файлов + `state/` — найти все семантические
   упоминания удаляемого slug.
2. Показать каскад: «упоминается в `<files>` — вот что нужно поправить».
3. Через `AskUserQuestion` по каждому месту — опции: «заменить на
   другой slug» / «удалить упоминание» / «оставить как есть».
4. По подтверждению — выполнить все правки одним пакетом.
5. Удалить запись из её файла.
6. Удалить `state/<kind>/<slug>.md`.
7. Если удалена единственная persona — спросить, не пора ли
   пересмотреть vision.

## Завершение сессии

В конце:

1. Перечислить затронутые сущности (заведены / углублены / удалены /
   повышены в stable).
2. Перечислить нерешённые открытые вопросы.
3. Назвать текущую фазу и логичный следующий шаг.
4. Предложить через `AskUserQuestion`:
   - «Прогнать `/project-audit`?» (внутрипроектная консистентность);
   - «Прогнать `/cross-audit`?» (сквозная проверка с interface/domain/screen);
   - «Передать клиенту через `/project-deep-dive-for-business` блок
     <X>?» (если фаза подходит под бизнес-домашку).

Скилл **сам не вызывает** другие скилы — это разные точки входа.
Аналитик запускает.

## Запреты

- Не редактировать таблицы и vision.md вслепую — всегда сначала `Read`.
- Не выдумывать значения доменных полей. Anti-patterns как опции — да;
  тексты `description`, `value`, `jobs`, `pains`, `why`, `payload`,
  `source` — нет.
- Не писать в `docs/project/` напрямую из агентов research-роя.
  Результаты идут в `state/research/`, promotion — через
  `AskUserQuestion` аналитика.
- Не повышать `draft → stable` без явного подтверждения аналитика.
- Не понижать `stable → draft` сам — только подсветить и предложить.
- Не аккумулировать историю в `state/` — forward-only.
- Не создавать `state/<kind>/<slug>.md`, если все секции были бы
  пустыми — заметка появляется только когда есть что записать.
- Не писать в `state/` соседнего скилла (`project-deep-dive-for-business`)
  — только read-only.
- Не пушить и не коммитить ничего. Коммит/push — гейт аналитика
  (проектная конвенция, см. `CLAUDE.md`).
- Не вызывать другие скилы — предложить аналитику запустить руками.
