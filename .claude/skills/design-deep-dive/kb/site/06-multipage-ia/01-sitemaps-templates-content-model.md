## Выжимка для агента

1. **Карта сайта — таблица до макетов**: страницы, шаблоны, родители, URL, коллекции, навигация и порядок сборки пишутся
   в `site-map` до первого `page-plan`; IA документируют в таблицах, не в макетах. → §1 [консенсус: NN/g 2014; ux 02-01 §1]
2. **Карта по умолчанию — по `site_type`** (`pages.mode: by-type`), список брифа (`listed`) её только дополняет и сужает;
   обязательные страницы типа не выбрасываются без записи причины в `derived_from`. → §2 [практика] (B §2)
3. **Страница без факта не строится**: отзывы, кейсы, команда, награды, цифры — только при фактах `facts.yaml`; иначе
   `status: blocked-facts`, а не выдумка. → §2 [практика] (контракт §3 п. 10)
4. **Главная многостраничника — маршрутизатор с отдельным шаблоном**: визуально отличается от внутренних страниц и не
   служит посадочной под рекламу. → §3.1 [исследование: NN/g 2024; C 01 §3.2]
5. **Шаблон = серия однотипных страниц** (≥ 3 записей одной структуры: услуги, врачи, проекты, программы, статьи) — один
   `page-plan` с `page.template: true` и коллекция данных; уникальная страница — свой `page-plan`. → §3.2 [практика]
6. **Страницы одного шаблона делят структуру полностью**; правило «соседние страницы делят ≤ 3 из 6 осей» (Hallmark) —
   для разных проектов, не для страниц одного сайта. → §3.3 [мнение вендора] (поправка к C 01 §3.4)
7. **Раздел, у которого есть подстраницы, имеет свою страницу-хаб**; «папка без страницы» в меню и крошках — дефект.
   → §3.4 [консенсус: NN/g 2018, 2019; ux 02-01 §9]
8. **Лендинг внутри сайта — подсайт**: логотип → главная, подвал с реквизитами; для платного трафика — вариант шаблона без
   меню (`header: landing-minimal`) из тех же данных; `indexable: false` или `canonical` на основную — не оба (H 01 §2.3).
   → §3.5 [мнение: NN/g 1996/2003; C 02 §2.3]
9. **Серия «услуга × город» — только с уникальными фактами каждой страницы и местом в иерархии**; иначе одна страница
   услуги со списком зон обслуживания. → §3.6 [документация: Google spam policies «Doorway abuse», 2026-09-24]
10. **Модель контента = коллекции + поля + связи**: у каждой коллекции URL-шаблон, хаб, поля с типом и обязательностью,
    ссылки `reference` на другие коллекции и `fact-ref` на факты. → §4.1 [практика]
11. **Цена, контакт, врач, программа хранятся один раз**: прайс, карточки услуг и страницы врачей читают одно поле;
    ручные копии цен на разных страницах — дефект. → §4.2 [практика] (Google: один контент — один URL)
12. **Markdown или поля CMS — исходник, наружу — HTML**; отдельных «версий для ИИ» и для ботов нет. → §4.3
    [документация: `[V:Vkn3R6DUJ34 20:33]`, `[V:kype1JQbrks 22:36]`]
13. **Связи коллекций порождают перелинковку**: услуга ↔ врачи, проект ↔ направление, статья → программа — поля
    `reference-list`, а не ручные ссылки. → §4.4 [практика]
14. **404 — код 404, неверный URL остаётся в адресной строке**, пути на хабы, поиск (если есть), контакт; без редиректа на
    главную и без крошек. → §5.1 [исследование: NN/g 2015; документация: GOV.UK через B §5.2] [проверено]
15. **Страница результатов поиска по сайту — либо `Disallow` шаблона поиска в robots.txt (новый сайт, по умолчанию),
    либо `noindex` (страницы уже в индексе; `Disallow` — после выпадения)**: вместе не работают — за `Disallow` Google не
    видит `noindex` [V:cfIQ_ksB61U 13:18]; «ничего не найдено» устроено как 404.
    → §5.2 [документация: Google URL structure; Яндекс «Структура сайта»]
16. **У каждой формы — своя или общая «спасибо»** (`noindex`, не в меню), юридический набор — по I и в подвале каждой
    страницы. → §5.3 [документация: GOV.UK через B §5.1; стандарт: 152-ФЗ ст. 18.1 — I]
17. **HTML-карта сайта — при ≥ 2 уровнях и десятках страниц**, статичная, многоколоночная, ссылка «Карта сайта» в подвале;
    малому сайту (≤ ≈ 25 страниц) хватает подвала-карты. → §5.4 [исследование: NN/g 2008, 2019]
18. **Сборка: сначала главная** — пакет 1 строит общую шапку, подвал, DESIGN.md; дальше пакет на шаблон по трафику и
    зависимостям; коллекция собирается на 1–3 образцах. → §6 [документация: справка Kimi Websites; kimi 07/01 §2.2]
19. **Каждая ссылка меню и подвала ведёт на страницу `site-map`** — приёмка пакета 1; внутренние ссылки — `<a href>` в
    исходном HTML. → §6 [документация: Google «Link best practices»; Яндекс «Структура сайта»]
20. **Меняешь адреса — таблица редиректов 301 на равноценные страницы**, удалённое без замены — 404/410, без цепочек.
    → §3.7 [документация: Google «How to move a site»; Яндекс «Смена структуры»] [спорно] (в деталях)
21. **Глубина: страница — не глубже 3 сегментов пути** (без языкового префикса); глубже — хаб или фильтр. У 19 живых
    многостраничников с sitemap медиана глубины URL 2, p90 ≤ 3 у 15 из 19. → §2.0 [проверено] + [документация: Яндекс]

## 1. Карта сайта как артефакт конвейера

```text
site-brief (site_type, pages.mode, pages.list, languages, search.existing_site, constraints.cms)
  └─ site-map (этот файл + схема)  ── chrome: шапка, подвал, крошки, поиск — один раз на сайт
       ├─ templates[]  ── page-plan на шаблон (page.template: true) или на уникальную страницу
       ├─ collections[] ── модель контента CMS: поля → слоты page-plan, fact-ref → facts.yaml
       ├─ pages[]      ── id, тип, шаблон, URL, родитель (крошки), приоритет, источники трафика
       └─ build_order  ── пакеты исполнителя: 1 — главная + общие компоненты; дальше — шаблоны
```

- **Что пишет Claude**: `site-map` (x-fill `claude` брифа: поле `pages` — «выводит сам, показывает в Going with»,
  `../01-foundations/03-site-brief.md` §3). Заказчику показывается дерево страниц и меню, а не JSON.
- **Как связано**: `page-plan.page.id` = `pages[].id` = `brief.pages.list[].id` = `copy-deck.page_id`;
  `page-plan.refs.site_map` — путь к карте; `page-plan.navigation` выбирает вариант шапки и подвала из `site-map.chrome`
  (решение G по вопросу E: общие элементы задаются один раз — WCAG 2.2 3.2.3 Consistent Navigation и 3.2.6 Consistent Help
  требуют одинакового относительного порядка на всех страницах набора). [стандарт]
- **Режимы брифа**: `by-type` — берётся карта §2 для типа, Claude добавляет страницы по фактам и возражениям; `listed` —
  берётся список заказчика, Claude сверяет его с картой §2 и задаёт вопрос о пропущенных обязательных страницах
  (приоритет 1: контакты, юридический набор, «спасибо», 404). `intake.what_ordered: redesign` — карта строится от
  существующего сайта: инвентаризация (sitemap, меню, логи) → таблица «старый URL → новый» (§3.7). [практика]
- **Проверка карты** до сборки (J — `site_validate.py`): у каждой страницы есть шаблон и родитель; каждый пункт меню и
  подвала ведёт на страницу карты; у каждой формы — «спасибо»; у каждой индексируемой страницы ≥ 1 входящей ссылки;
  все шаблоны есть в `build_order`. Схема и перекрёстная проверка трёх примеров — 0 ошибок [проверено: 15:20, venv-A,
  jsonschema 4.26].

## 2. Карты по умолчанию по типам сайтов

### 2.0. Как читать и данные опыта

Обязательные страницы (must) — B `../02-site-types/01-site-and-page-taxonomy.md` §2; здесь — дерево, шаблоны, глубина и
хабы. Глубина — сегменты пути от главной. Опыт G/01 (`ia_probe.py`, 20 сайтов, 24.09.2026, данные у 18): медиана глубины
URL из sitemap — 2 у 12 сайтов, 1 — у 2, 3–5 — у 4 (severstal 4, designcube 5, foxford 5, thoughtworks 3); число
шаблонов пути — от 2 (brplaw, 11 URL) до 716 (artlebedev, большая часть — проекты с уникальными путями). Глубже 3 уходят
каталоги продукции и архивы, а не услуги. [проверено]

### 2.1. Корпоративный сайт (`corporate-site`, приоритет 4)

| Уровень | Страницы (шаблон) | Приоритет |
|---|---|---|
| 0 | главная (`home-multipage`, макроструктура `directory`) | must |
| 1 | направления — хаб (`services-index-page`); проекты — хаб (`case-list-page`); о компании (`about-page`); контакты; запрос расчёта (`form-page`) | must |
| 2 | направление × N (`service-page`, коллекция); проект × N (`case-page`, коллекция); подстраницы «О компании»: документы и допуски (`documents-page` (новый id)), руководство, история; новости (`blog-index-page`) и вакансии (`careers-page`) | must / should / could |
| вне | политика, согласие (`legal-page`), «спасибо», 404 | must |

- «О компании» — 4 уровня: таглайн на главной → сводка 1–2 абзаца → подстраницы (миссия, история, руководство, инвесторам,
  новости, вакансии) → ссылки в подвале; **небольшой компании подстраницы не нужны — всё на одной странице**
  [исследование: NN/g 2019, > 70 пользователей, 100 сайтов].
- Новости — только при выпуске не реже раза в квартал; раздел с последней датой двухлетней давности — вред доверию.
  [практика] (E `article-cards`)
- Пример: `../10-playbooks-contracts/examples/corporate-b2b-stalkon/site-map.yaml` (15 шаблонов, 16 страниц-образцов,
  RU + адаптация EN на 7 страницах).

### 2.2. Услуги и локальный бизнес (`services-site`, приоритет 1)

| Уровень | Страницы | Приоритет |
|---|---|---|
| 0 | главная (маршрутизатор: услуги, цены, специалисты, адрес) | must |
| 1 | услуги — хаб; цены (`pricing-page` из поля цены коллекции); специалисты (`team-page`); контакты (адрес, часы, карта); о компании (лицензия); запись (`form-page`) | must |
| 2 | категория услуг (при > ≈ 12 услуг, `services-index-page`); услуга × N (`service-page`); специалист × N (`specialist-page` (новый id)); филиал × N (`location-page` (новый id), при ≥ 2 адресах); отзывы (`reviews-page`, при фактах) | must / should |
| 3 | услуга внутри категории (`/uslugi/{категория}/{услуга}/`) | must при категориях |
| вне | посадочные под рекламу (`landing-lead-services`, `noindex`, без меню), юридический набор, «спасибо», 404 | should / must |

- Цена или «от» — на странице услуги и в прайсе из одного поля; у лидогенерации цена рано (C 01 §3.2). [проверено]
- Телефон — в шапке на всех страницах и видим на телефоне без меню: у лидогенерации РФ это канал целевого действия
  (M, `header_phone`; B §3.1). [данные: M, выборка 49 страниц]
- Город × услуга — §3.6.

### 2.3. Портфолио и студия (`portfolio-site`)

главная = работы (`portfolio-page`, макроструктура `portfolio-grid`) или `home-multipage` с работами первыми (B §7.7);
уровень 1 — работы (хаб с фильтром по отрасли и услуге, если работ > ≈ 12), услуги, о студии (команда внутри), контакты
(бриф на проект — `form-page`); уровень 2 — проект × N (`case-page`). Крошки часто не нужны: 2 уровня (NN/g правило 7);
у 3 из 3 студий G/01 (artlebedev, pentagram, designcube) крошек на страницах проектов нет у двух. [проверено]

### 2.4. Мероприятие (`event-site`)

главная события (дата, место, билеты в первом экране); программа (день × секция); спикеры (хаб) → спикер × N
(`specialist-page` (новый id)); доклад × N (при > ≈ 30 докладах); место и как добраться; билеты и цены; партнёры;
прошлые события (архив — отдельный раздел с годом в пути: `/2025/`); оферта при продаже. Серия конференций — у каждой
свой подсайт с локальной навигацией (программа, спикеры, билеты, место), общий раздел бренда сверху (smashingconf:
125 шаблонов пути на 1347 URL — города × годы). [проверено] + [практика]

### 2.5. Школа и курсы (`school-site`)

главная; каталог программ (`program-catalog-page` (новый id), фильтры по направлению, уровню, длительности — не
индексируются); направление (хаб, при ≥ 3 направлениях); программа × N (`landing-course` внутри сайта, со своей
локальной навигацией-оглавлением); преподаватели (хаб) → преподаватель × N; цены и оплата (рассрочка, вычет — факты);
отзывы; «Компаниям» (B2B — отдельный вход только при уникальном содержимом); бесплатные уроки (лид-магнит); блог;
о школе (лицензия); оферта.

### 2.6. Личный бренд (`personal-brand-site`)

главная (кто, чем помогает, главное действие); о себе (`about-page`); услуги или продукты (1–5 — одной страницей, больше —
хаб); публикации (блог или список внешних ссылок с датой); выступления (список с датами и записями); контакты;
юридический набор при сборе данных. 1–2 уровня: крошки не нужны. [практика]

### 2.7. Маркетинговый сайт SaaS (`saas-marketing-site`)

главная; продукт (хаб) → функция × N (`feature-page`); решения (хаб) → сценарий × N (`use-case-page`: отрасль, роль,
размер); тарифы; интеграции (хаб → интеграция × N при каталоге); безопасность; кейсы (хаб → кейс); ресурсы (блог,
вебинары, документация — часто отдельный хост); сравнения и «альтернативы» (серия); компания (о нас, вакансии);
запрос демо (`form-page`); вход в продукт — `log-in` в шапке, продукт — отдельный пакет с общим DESIGN.md (B §7.2).
Шапка — мега-меню «Продукт / Решения / Ресурсы» у больших, 4–6 ссылок у малых (linear: 8 пунктов, kontur: 7 с подменю;
G/01). [проверено] + [мнение вендора: Hallmark N1b, N11]

### 2.8. Кампания из нескольких страниц (`campaign-site`) и `landing-site`

`campaign-site`: 2–6 страниц-глав, линейный порядок («дальше» в конце главы), шапка — логотип, главы, призыв; крошки не
нужны (линейная структура — NN/g правило 7); «спасибо», правила акции, юридический набор. `landing-site`: лендинг +
«спасибо» + юридический набор + 404 — карта из 4–6 страниц, `chrome.header.archetype: minimal-cta`. [практика]

## 3. Шаблоны

### 3.1. Главная — отдельный шаблон

- Главная визуально и структурно отличается от внутренних страниц, чтобы посетитель узнавал точку старта; анти-пример —
  главная, похожая на страницу новости (Icahn). [исследование: NN/g 2024, принцип 1.3]
- Задача — «кто вы, что делаете, куда идти»: примеры содержимого разделов, а не только общие категории-ссылки (NN/g 2024,
  3.2); порядок секций — C 01 §3.2. Реклама на главную не ведётся (C 02 §3.1). [консенсус]

### 3.2. Шаблон или уникальная страница

| Признак | Шаблон (`instances: collection`) | Уникальная страница (`single`) |
|---|---|---|
| Число страниц одной структуры | ≥ 3 (услуги, врачи, проекты, программы, статьи, филиалы, спикеры) | 1–2 |
| Источник содержимого | записи CMS с одинаковыми полями | своя история, свой порядок секций |
| План | один `page-plan` с `page.template: true` + коллекция | свой `page-plan` |
| Пакет исполнителя | один пакет, 1–3 образца (`sample_instances`) | пакет на страницу |
| Примеры | `service-page`, `case-page`, `specialist-page`, `article-page`, `landing-course` в каталоге | главная, «О компании», контакты, тарифы |

[практика] (A 03 §7: kimi получает пакет на шаблон)

### 3.3. Единство серии и различие типов

- Страницы одного шаблона делят все оси формы (порядок секций, блоки, ритм) — это и есть шаблон; различаются данными.
- Разные типы страниц одного сайта делят систему блоков, шапку, подвал и DESIGN.md, а форму выбирают свою (главная —
  `directory`, статья — `long-document`, прайс — `pricing-first`).
- Поправка к `../03-page-structure/01-narratives-and-section-order.md §3.4` для многостраничника: правило Hallmark «no two
  should share more than three of the six axes» написано для последовательных сборок разных страниц в сессии
  (`structure.md`, «Anti-repetition»); к страницам одного шаблона оно не применяется, потому что единообразие серии
  требуют WCAG 3.2.3/3.2.4 и предсказуемость ИА (ux 02-02 §11). Визуальное единство серии — creative (контракт §2).
  [мнение вендора] + [стандарт]

### 3.4. Хаб у каждого раздела

У пункта меню с подстраницами — страница-хаб: список детей с короткими описаниями, «остановка» по пути, боковые переходы
к соседям (NN/g 2019 «3-click rule»: «landing pages or navigation hubs at key points»; Accenture). Мега-меню доступно
без скриптов именно через хаб: пункт верхнего уровня ведёт на обычную страницу со всеми пунктами панели (NN/g 2017).
Заголовок группы без страницы — только визуальная подпись, в крошки не попадает (NN/g 2018, правило 6). [исследование]

### 3.5. Лендинг внутри сайта

`page_type` лендинга, `site_type` сайта (B §7.1): логотип → главная, подвал с реквизитами и юридическими ссылками,
связь с родителем (NN/g «The Rise of the Subsite», 1996, дополнение 2003: «microsites… fragment a company's Web
presence»). Для платного трафика — второй шаблон той же коллекции с `header: landing-minimal` и одним сигналом индексации:
`canonical` на основную страницу (то же содержание) или `indexable: false` (другое), не оба (H 01 §2.3);
меню убирается по C 02 §2.3 [спорно: кейсы вендоров]. [мнение] + [практика]

### 3.6. Серии «услуга × город», «услуга × отрасль»

Google относит к doorway «несколько доменов или страниц под регионы или города, которые воронкой ведут на одну страницу»
и «существенно похожие страницы, ближе к результатам поиска, чем к ясной иерархии»; к scaled content — «много страниц
генеративным ИИ без добавленной ценности» [документация: Google spam policies, 2026-09-24]. Правило серии:

1. У страницы — уникальные факты места: адрес или зона выезда, цены региона, работы и отзывы в этом городе, сроки.
2. Страница — в иерархии: хаб города или услуги, крошки, ссылки из меню или хаба (не только из sitemap).
3. Нет фактов → одна страница услуги со списком зон обслуживания; число городов в серии = число городов с фактами.
4. Отдельная страница под сегмент — только при различии ≥ 2 признаков из 4 (C 02 §3.4).

[документация] + [практика]; у cleanon.ru (G/01) 980 URL при 43 шаблонах пути — серия «город × услуга» с общей структурой;
уникальность текстов опыт не проверял. [проверено] (частично)

### 3.7. Редизайн и смена адресов

- Адреса сохраняются, если нет причины менять (NN/g «URL as UI»: «Do not move pages around»; бриф
  `search.existing_site.keep_urls`). [мнение: NN/g 1999, механизм в силе]
- Меняешь — таблица «старый → новый» в `url_policy.redirects`: 301/308 на равноценную страницу; удалённое без замены —
  404 или 410; меню и внутренние ссылки — сразу на новые адреса; новый sitemap. [документация: Google «How to move a site»;
  Яндекс «Смена структуры и дизайна сайта»]
- Противоречие: Яндекс советует при той же тематике 301 удалённых страниц «на главную соответствующего раздела» и считает
  цепочку редиректов допустимой; Google — избегать цепочек (≤ 3, < 5) и не выдавать раздел за замену. Позиция базы: редирект
  только на страницу, которая прямо заменяет удалённую; иначе 404/410; без цепочек. [спорно]

## 4. Модель контента для CMS

### 4.1. Коллекции, поля, связи

| Тип поля (`collections[].fields[].type`) | Что хранит | Пример |
|---|---|---|
| `text`, `rich-text` | заголовок, описание, тело (Markdown или структурированный текст) | название услуги, «что входит» |
| `slug` (unique) | часть URL | `implantaciya` |
| `enum` | фасет, категория | уровень программы, специальность врача |
| `fact-ref` | ссылка на факт `facts.yaml` нужного вида | цена «от», опыт врача, клиент проекта |
| `reference`, `reference-list` | связь с другой коллекцией | услуга → врачи; статья → программа |
| `media` | реальное фото, карта, обложка (план ассетов — ai-media) | фото клиники |
| `date`, `number`, `url`, `boolean` | даты, числа, ссылки | старт потока, дата редакции документа |
| `seo-meta` | title, description, OG (тексты — text, техника — H) | — |

Правила [практика]: (1) у коллекции — `url_pattern`, `hub_page`, `sort`, `facets`; (2) поле, которое попадает в слот,
указывает `slot` (id словаря) — так copy-deck и page-plan читают данные по id; (3) числа, отзывы, люди, цены — только
`fact-ref`: факт один, страниц много; (4) дата редакции у юридических документов обязательна (I).

### 4.2. Один источник правды

Прайс, карточки услуг на главной, мега-меню услуг и страница услуги читают одну коллекцию; цена меняется в одном месте.
Страницы-копии с тем же содержимым — дубли (Google SEO Starter Guide: «each piece of content… only accessible through one
individual URL»). [документация] + [практика]

### 4.3. Исходник и выдача

Markdown или поля CMS — нормальный исходник; наружу — HTML, одна адаптивная версия на одном URL: отдельные мобильные URL
теряли контент, ссылки, `hreflang` (`[V:kype1JQbrks 22:36]`), отдельные версии «для LLM» ломаются незаметно
(`[V:Vkn3R6DUJ34 15:07]`), Markdown-исходник у Splitt — с 2012 г. (`[V:Vkn3R6DUJ34 20:33]`). [документация]

### 4.4. Связи порождают перелинковку

Правила `linking.related_rules` строятся из полей связи (`by: reference-field`), а не из ручных списков: услуга → врачи
(`team-grid`), врач → услуги (`related-links`), проект ↔ направление (`case-cards`), статья → программа (мост к продаже).
Ручная ссылка ставится в тексте (контекстная), с описательным текстом ссылки (Google). Подробно — `02` §3. [практика]

### 4.5. Платформы заказчика (`constraints.cms`)

| CMS брифа | Что учесть в карте | Метка |
|---|---|---|
| `static`, `custom` (сборка из репозитория) | коллекции — файлы данных (YAML, Markdown) рядом с шаблонами; генерация HTML и sitemap при сборке | [практика] |
| `wordpress` | коллекции — типы записей и таксономии; sitemap генерирует ядро или плагин; следить за архивами тегов и авторов (дубли, `noindex`) | [практика] |
| `1c-bitrix` | коллекции — инфоблоки; ЧПУ настраиваются шаблоном адреса раздела и элемента | [практика] |
| `tilda` | страницы собираются из блоков; серии — «Потоки» и каталог; общие шапка и подвал — отдельными страницами-блоками, проверять одинаковость на всех страницах | [практика] |

Документацию платформ этот агент не читал — строки таблицы проверить J по справкам платформ («Открытые вопросы»). Слой

## 5. Служебные страницы

### 5.1. 404

- Сервер отдаёт **код 404** (или 410) — техника H; страница: заголовок «Страница не найдена» без жаргона, что делать
  (проверить адрес), пути на хабы и главную, поиск, если он есть на сайте, контакт; без обвинения и без крошек
  (GOV.UK — через B §5.2; E `not-found`, вариант `with-routes` для многостраничника). [документация]
- **Не перенаправлять на главную**: неверный URL остаётся в адресной строке — пользователь увидит опечатку (NN/g «You Are
  Here», 2015: Telegraph — извинение, «проверьте адрес», указатель, полная навигация, статус, контакты). [исследование]
- Опыт G/01 (v1.0): честный 404 у 15 из 18 сайтов; «мягкая» 404 (ответ 200) — у linear.app (оболочка приложения без
  ссылок) и ilyabirman.ru (301 на адрес со слэшем → 200); у artlebedev.ru несуществующий адрес отвечал дольше 30 с.
  [проверено]

### 5.2. Поиск по сайту и его результаты

- Когда нужен поиск — `02` §2.4. Страница результатов: `Disallow` шаблона поиска в robots.txt или, если страницы уже в
  индексе, сначала `noindex`, а после выпадения — `Disallow` (вместе не работают — [V:cfIQ_ksB61U 13:18]) (Яндекс: «результаты поиска по
  сайту… рекомендуем запрещать индексирование»; Google: блокировать «URLs that generate search results»); «ничего не
  найдено» — как 404: подсказки, популярные разделы, контакт (NN/g 2015). [документация]
- Поле поиска не прячется в мега-меню (NN/g 2017). `WebSite` + `SearchAction` в разметке — решение H.

### 5.3. «Спасибо» и юридический набор

«Спасибо» у каждой формы: что будет дальше и когда, контакты, следующий шаг, событие цели (B §5.1, F); `noindex`, не в
меню и не в sitemap, в `linking.orphans_allowed`. Юридический набор (политика ПД, согласие отдельным документом с
01.09.2025, оферта, cookie, лицензии) — перечень I (`../08-legal-trust-a11y/`); в карте — `utility_pages.legal_set` и
ссылки в подвале каждой страницы, включая посадочные без меню. [стандарт] (I `req:LR-RU-05`, `req:LR-RU-13`)

### 5.4. HTML-карта сайта

NN/g 2008 (2 исследования × 15 пользователей, 20 сайтов): к карте обратились 7 % участников, найти смогли 67 %;
многоколоночная карта — 61 % успешных задач против 47 % у одноколоночной; называть «Карта сайта», статичная, ссылка в
подвале [исследование]. NN/g 2019: полная карта в подвале — только при ≈ 25 страницах и меньше [исследование]. Правило:
при ≥ 2 уровнях и > 25 страниц — страница «Карта сайта» (`html-sitemap-page` — id словаря v1, proposed); при ≤ 25 — подвал-карта.
Это второй способ найти страницу для WCAG 2.2 2.4.5 Multiple Ways (AA) наряду с поиском и связанными ссылками. [стандарт]

## 6. Порядок сборки серии страниц

1. **Пакет 1 — главная** (`builds_chrome: true`): общие шапка, подвал, крошки, 404-компонент, DESIGN.md и токены; все
   пункты меню и подвала — ссылки на URL карты (пока пустые страницы-заглушки со статусом `planned`). Справка «Kimi 网页»:
   сложный сайт — «сначала главная, потом постепенно подстраницы и функции» [документация: Moonshot, через kimi 06-cn/01
   §5.2]; «сайт + кабинет» — два пакета с общим DESIGN.md (kimi 07/01 §2.2).
2. **Пакеты шаблонов по трафику**: сначала шаблон главного входа (услуга, программа, направление) на 1–3 образцах, затем
   форма и «спасибо», затем хабы (хаб строится после образцов детей), затем доверие (врачи, проекты, о компании), затем
   контент (статьи), служебные и посадочные под рекламу.
3. **Каждый пакет переиспользует** компоненты пакета 1 (`depends_on`), а не генерирует шапку заново; одна страница — одна
   сессия исполнителя, после смены модели или длинной истории — новая сессия (kimi Z-report п.4). [практика]
4. **Приёмка шага**: ссылки меню и подвала ведут на страницы карты; шаблон на образцах совпадает с `page-plan`; крошки
   по `parent`; внутренние ссылки — `<a href>` в исходном HTML (Google, Яндекс); коллекция вне образцов — данными.

Проекция в kimi (предложение, файлы kimi не правим): пакет на шаблон + список маршрутов серии и пункты меню с URL в
TASK.md; приёмка «каждая ссылка навигации ведёт на маршрут карты» — аналог A1_STRUCTURE webapp (`build_package.py`
стр. 379–380); NAV_RULE заменить архетипом шапки из `site-map.chrome.header.archetype` (`02` §1.2).

## Частые ошибки

1. Карта «по шаблону генератора»: «Главная · Услуги · О нас · Блог · Контакты» у любого бизнеса, без хабов и коллекций.
2. Раздел меню без своей страницы («папка») или страница-копия прайса на каждой услуге с разными ценами.
3. Отзывы, команда, кейсы, награды «для полноты» без фактов — выдумка вместо `status: blocked-facts`.
4. Сотни страниц «услуга × город» с заменой топонима — doorway и scaled content (Google).
5. Лендинг кампании без логотипа-ссылки и подвала с реквизитами — «микросайт», оторванный от компании.
6. Меню и ссылки, которые строятся только скриптом (кнопки `onclick`, `routerLink`), — страница не находится краулером.
7. Отдельная мобильная версия или «версия для ИИ» — теряет содержимое, ссылки, `hreflang`.
8. 404 с кодом 200 или редирект всего несуществующего на главную (G/01: 2 из 19 сайтов — мягкая 404).
9. Результаты поиска по сайту в индексе и в sitemap.
10. Шаблон, пересобранный генератором для каждой страницы серии заново: у страниц одной услуги разный порядок секций.
11. Относительные адреса в sitemap.xml (G/01: ilyabirman.ru) и URL с редиректом в sitemap (G/01: linear.app) — sitemap
    должен содержать абсолютные канонические URL (Google).

## Чек-лист

- [ ] `site-map` написан до `page-plan`; режим брифа `by-type`/`listed` записан, исключения объяснены?
- [ ] Все обязательные страницы типа (B §2) есть или исключены с причиной; страницы без фактов помечены `blocked-facts`?
- [ ] У главной свой шаблон; у каждого раздела с подстраницами — хаб?
- [ ] Серии однотипных страниц — шаблоны с коллекцией, одним `page-plan` и 1–3 образцами?
- [ ] Цены, люди, адреса хранятся в одном месте (`fact-ref`, одна коллекция)?
- [ ] Серии «услуга × город» — только с уникальными фактами и местом в иерархии?
- [ ] 404 отдаёт код 404 и пути на хабы; результаты поиска — `Disallow` шаблона (новый сайт) или `noindex` (уже в индексе),
  не оба; у каждой формы «спасибо»?
- [ ] Юридический набор по I в подвале каждой страницы, включая посадочные без меню?
- [ ] HTML-карта сайта при > 25 страниц и ≥ 2 уровнях, при ≤ 25 — подвал-карта?
- [ ] `build_order` начинается с главной и общих компонентов; каждый шаблон в порядке сборки?
- [ ] Схема `site-map.schema.json` и перекрёстные ссылки проходят без ошибок?

## Открытые вопросы и противоречия

1. **Числа по глубине и шаблонам — 18 сайтов одного дня**, выборка не случайная; частоты — ориентир, не норма.
   Проверка — выборка M (`pages.csv`, шаблоны `mp-*`) и расширение G/01 до 50 сайтов (живая фаза не нужна, HTTP).
2. **Документация CMS не прочитана** (Tilda «Потоки», WordPress типы записей, 1С-Битрикс инфоблоки, Contentful, Sanity):
   таблица §4.5 — практика агента, проверить J.
3. **Страница «Отзывы» у B2B**: B рекомендует `reviews-page` для услуг; для завода отзывы заменены проектами с цитатами —
   решение по отрасли, данных нет.
4. **Редиректы удалённых страниц**: Google против Яндекса (§3.7) [спорно].
5. **Hallmark против NN/g по подвалу-карте** — `02` §1.4.
6. **Новые `page_type`** (`specialist-page`, `location-page`, `program-catalog-page`, `search-results-page`,
   `documents-page`) — ждут решения J; до решения vocab_lint даёт ошибки (ожидаемо).
