## Выжимка для агента

1. **Первое правило ARIA: если есть нативный элемент с нужной семантикой и поведением — использовать его.**
   `<button>`, `<a href>`, `<input>`, `<select>`, `<details>`, `<dialog>` уже умеют фокус, клавиатуру и состояния.
   → §1.1 `[стандарт]`
2. **Роль — это обещание.** `<div role="button">` обещает, что автор написал обработку Enter **и** Space, поставил
   `tabindex="0"` и нарисовал фокус. Не выполнил — «similar to making a "Place Order" button that abandons an order».
   → §1.2 `[APG]`
3. **Больше ARIA — больше ошибок.** На страницах с ARIA в среднем 59,1 обнаруженной ошибки против 42 без неё; ARIA
   выросла на 27 % за год и в 6 раз с 2019. → §1.4 `[исследование]`
4. **Не ставь `aria-hidden="true"` и `role="presentation"` на фокусируемый элемент и на его предка.** Это даёт
   фокус «в никуда». → §1.3 `[стандарт]`
5. **У каждого интерактивного элемента: имя, роль, значение, состояние.** Четыре вопроса к каждому элементу перед
   сдачей. → §2 `[стандарт]`
6. **Имя — 1–3 слова, начинается с самого различающего**: «Удалить заказ 12045», а не «Заказ 12045 удалить».
   Название роли в имя не входит: скринридер скажет «кнопка» сам. → §3.6 `[APG]`
7. **Предпочитай видимый текст.** `aria-label` не виден, не переводится автопереводчиками, рассинхронизируется при
   правках и **скрывает всё содержимое** элементов, которые берут имя из содержимого. → §3.2 `[APG]`
8. **Видимый текст подписи обязан входить в доступное имя** (2.5.3): иначе ломается голосовое управление. → §3.7 `[стандарт]`
9. **Весь видимый контент — внутри лендмарков**, `<main>` ровно один, у повторяющихся лендмарков уникальные метки,
   слово «навигация» в метку не пишем. → §4 `[APG]`
10. **Заголовки важнее лендмарков**: 71,6 % пользователей скринридеров ищут информацию по заголовкам и только
    3,7 % — по лендмаркам. Но нужны и те, и другие. → §5 `[исследование]`
11. **Три способа скрыть — три разных смысла**: `display:none` (нет ни для кого), `aria-hidden="true"` (есть
    визуально, нет для AT), визуально скрытый класс (нет визуально, есть для AT). Живую область нельзя прятать
    первыми двумя. → §6 `[консенсус]`
12. **`outline: none` без замены — катастрофа**; переопределённый индикатор даёт 3:1 к соседним цветам, площадь ≥
    периметра 2 px, строится на `outline` (переживает forced-colors и не двигает раскладку). → §7 `[стандарт]`
13. **Готовый универсальный индикатор**: `:focus-visible { outline: 3px solid black; box-shadow: 0 0 0 6px white; }`
    — чёрное даёт контраст на светлом, белое на тёмном. → §7.2 `[практика]`
14. **Tab/Shift+Tab — между компонентами, стрелки — внутри составного компонента.** Один tab stop на весь тулбар,
    меню, радиогруппу, тулбар, грид, дерево, tablist. → §8.1 `[APG]`
15. **`tabindex` > 0 запрещён**; порядок меняется перестановкой в DOM. → §9.1 `[APG]`
16. **Skip-ссылка — первый фокусируемый элемент страницы**, видима при фокусе, ведёт на существующий контейнер; после
    активации следующий Tab идёт в контент. → §9.3 `[консенсус]`
17. **Фокус всегда где-то есть.** Удалили строку — перевести фокус на следующую; закрыли диалог — вернуть на триггер;
    иначе фокус падает на `<body>` и пользователь теряется. → §10 `[APG]`
18. **Модалка: фокус внутрь при открытии, кольцо Tab замкнуто, Esc закрывает, фон инертен, фокус возвращается на
    вызвавший элемент.** Исключения из возврата перечислены явно. → §10.2 `[APG]`
19. **Смена маршрута в SPA: сменить `<title>`, перевести фокус на `<h1>` или контейнер контента.** Живая область тут
    хуже перевода фокуса. → §10.5 `[консенсус]`
20. **Ошибки формы: фокус на сводку ошибок вверху страницы** (GOV.UK) либо на первое ошибочное поле (W3C). Сводка
    надёжнее при нескольких ошибках. → §10.4 `[спорно]`
21. **Отключённые контролы: `disabled` убирает из фокуса, `aria-disabled` оставляет.** Оставлять фокусируемыми там,
    где важна обнаружимость (пункты меню, вкладки, кнопки тулбара); убирать там, где наличие выводится из соседей.
    → §8.10 `[APG]`
22. **Selection follows focus** допустима, только если переключение мгновенно; при сетевом запросе на каждой вкладке
    это «devastating». → §8.3 `[APG]`
23. **Одноклавишные шорткаты отключаются или требуют фокуса** (2.1.4); не занимать `Caps Lock+*`, `Insert+*`,
    `Control+Option+*` (macOS — VoiceOver), meta+клавиша, Alt+F*, любой модификатор с Tab/Enter/Space/Esc. → §11.2 `[APG]`
24. **Шорткаты дополняют навигацию, а не заменяют её**; «слишком много шорткатов» повышает когнитивную нагрузку.
    → §11.1 `[APG]`
25. **Тултип не заменяет подпись.** `title` не виден на тач и с клавиатуры; иконка без подписи обязана иметь
    доступное имя, а в свёрнутом rail — ещё и подпись при раскрытии. → §3.8, §8.13 `[консенсус]`
26. **В forced-colors системные цвета выбираются по нативной семантике, а не по ARIA**: `<div role="button">` не
    станет выглядеть кнопкой в режиме высокой контрастности. Ещё одна причина использовать `<button>`. → §1.5 `[стандарт]`
27. **Документируй два потока для каждого сложного компонента: мышью и с клавиатуры.** Это форма, которую можно
    прямо отдать в реализацию. → §8.14 `[практика]`

## 1. Правила ARIA

### 1.1 Первое правило: сначала нативное

«If you *can* use a native HTML element or attribute with the semantics and behavior you require **already built in**,
instead of re-purposing an element and adding an ARIA role, state or property to make it accessible, **then do so**» [S1].

Когда это может быть невозможно (перечислено в самом документе): фича есть в HTML, но не реализована или не
поддержана AT; **визуальные ограничения не дают стилизовать нативный элемент**; фичи в HTML нет [S1].

Что получаешь бесплатно с нативным элементом: включение в tab-последовательность, обработку Enter/Space, состояния,
`disabled` без `aria-disabled`, увеличение области нажатия через `<label>`, корректные системные цвета в
forced-colors, работу с голосовым вводом.

| Хочется собрать из `div` | Взять нативное |
|---|---|
| Кнопка | `<button type="button">` |
| Ссылка | `<a href>` |
| Чекбокс, радио | `<input type="checkbox">`, `<input type="radio">` |
| Выпадающий список из готовых значений | `<select>` |
| Раскрывающийся блок | `<details>` / `<summary>` (учитывая §8.5) |
| Модальный диалог | `<dialog>` с `showModal()` |
| Индикатор загрузки с процентом | `<progress>` |
| Числовой ввод со стрелками | `<input type="number">` (осторожно: колёсико мыши меняет значение) |
| Результат вычисления, статус | `<output>` (нативная роль `status`) |
| Группа полей с общим вопросом | `<fieldset>` + `<legend>` |
| Таблица данных | `<table>`, `<th scope>`, `<caption>` |

### 1.2 Роль — это обещание

`<div role="button">Place Order</div>` — обещание, что автор добавил JS, дающий ожидаемое клавиатурное поведение.
«Unlike HTML input elements, ARIA roles do not cause browsers to provide keyboard behaviors or styling». Роль без
выполнения обещания — «similar to making a "Place Order" button that abandons an order and empties the shopping
cart» [S2]. `[APG]`

Минимальный набор, который придётся написать руками для `role="button"` на `div`: `tabindex="0"`, обработчик `click`,
обработчик `keydown` на Enter **и** Space (с `preventDefault` для Space, иначе прокрутит страницу), стили `:hover`,
`:focus-visible`, `:active`, поддержка `aria-disabled` и исключение из порядка табуляции при отключении.

### 1.3 Второе, третье и четвёртое правила

- **Не менять нативную семантику без необходимости.** `<h2 role="tab">` — нельзя; `<div role="tab"><h2>…</h2></div>` — можно [S1].
- **Все интерактивные ARIA-контролы работают с клавиатуры.** `role="button"` обязан реагировать и на Enter, и на
  Space [S1].
- **Не ставить `role="presentation"` и `aria-hidden="true"` на фокусируемый элемент** — «will result in some users
  focusing on 'nothing'». **`aria-hidden` на предке видимой кнопки прячет и кнопку** [S1].

Тонкости четвёртого правила [S1]:
- если элемент не виден и не интерактивен, `aria-hidden` допустим **вместе с `tabindex="-1"`**;
- при `display:none` или `visibility:hidden` и `aria-hidden`, и `tabindex="-1"` не нужны — элемент уже вне дерева
  доступности и вне порядка табуляции.

**Статус документа изменился:** «Using ARIA» с 24 февраля 2026 — Discontinued Draft; четыре правила оставлены
«for historical purposes and for easier reference», за практикой W3C отправляет в APG [S1]. Формулировка «пять правил
ARIA» из старых материалов больше не соответствует живому документу.

### 1.4 ARIA и скрывает, и усиливает — и её стало слишком много

Примеры «скрывающего» действия ARIA прямо из APG [S2]:

```html
<a role="menuitem">Пользователь AT воспринимает это как пункт меню, а не ссылку.</a>
<a aria-label="Пользователь AT слышит только aria-label, не текст ссылки">Текст ссылки</a>
<table role="log"><!-- это больше не таблица для AT --></table>
<ul role="navigation">
  <li><a href="…">ссылка</a></li>  <!-- ОШИБКА: li больше не в списке -->
</ul>
```

**Данные о масштабе** [S3]: 133 ARIA-атрибута на среднюю главную страницу (рост 27 % за год, ×6 к 2019); ARIA
используют 82,7 % страниц. **Страницы с ARIA имеют в среднем 59,1 обнаруженной ошибки против 42 без неё** — на 17
барьеров больше. WebAIM оговаривается, что это не доказывает причинность (страницы с ARIA сложнее), но связь
устойчива восьмой год. `role="menu"` есть на 5,7 % страниц, и **22 % этих меню создают барьеры** из-за неполной
разметки и поведения. `aria-hidden="true"` — 23,3 на страницу, рост 250 % с 2020. `[исследование]`

**Правило для генератора интерфейсов:** ARIA добавляется **только там, где нативного эквивалента нет**, и каждая
добавленная роль сопровождается клавиатурным контрактом из §8. Практик, цитируемый в каталоге ИИ-ошибок, описывает
типичное поведение модели как «throws `aria-hidden="true"` at a wall and hopes it sticks»
(`../11-ai-generated-ui/01-failure-modes-catalog.md` F9.4).

### 1.5 Типовые ошибки применения ARIA в HTML

Из нормативного «ARIA in HTML» (W3C Recommendation 11 августа 2026) [S4]:

| Ошибка | Почему плохо |
|---|---|
| `<button role="heading">` | Нельзя переопределять интерактивный элемент неинтерактивной ролью: поведение кнопки конфликтует с ожиданиями от заголовка |
| `<button role="button">`, `<main role="main">`, `<fieldset role="group">` | Избыточно; делает разметку многословной и учит других плохой практике |
| `<summary role="button">` | Ломает передачу состояния раскрытия, форсирует роль button вместо платформенной |
| `<div role="select">` | `select` — абстрактная роль, авторам запрещена; нужен `combobox` |
| `<article role="generic">` | `generic` предназначена для реализаций браузеров; нужен `div` или `role="presentation"` |
| `<input type="checkbox" checked aria-checked="false">` | **Нативное состояние побеждает ARIA**: будет прочитано как отмеченное |
| `<p>…<div role="link">…</div>…</p>` | ARIA не меняет правила вложенности HTML: парсер вынесет `div` из `p` |

**Исключение, о котором надо знать:** `<ul role="list">` формально избыточен, **но некоторые браузеры снимают
семантику списка, если убрать маркеры через CSS** (`list-style: none`) — в этом случае явная роль оправдана [S4].
Это же описывает Скотт О'Хара в разборе поведения Safari [S5].

**Disabled-ссылка.** `<a href disabled>` невалиден; `aria-disabled="true"` на ссылке **не отключает её
функционально**. Правильный приём: убрать `href` и оставить `<a role="link" aria-disabled="true">` [S4].

**Forced-colors выбирает системные цвета по нативной семантике, а не по ARIA:** «adding `role="button"` to a `div`
will **not** cause an element's color to be forced to `ButtonText`» [S6]. То есть в режиме высокой контрастности
`<div role="button">` перестаёт выглядеть кнопкой. `[стандарт]`

## 2. Имя, роль, значение, состояние: контракт интерактивного элемента

Четыре вопроса к каждому интерактивному элементу перед приёмкой (критерий 4.1.2):

| Вопрос | Чем закрывается | Типичный провал |
|---|---|---|
| **Имя**: как назвать вслух | видимый текст; `<label for>`; `aria-label`; `aria-labelledby`; `alt` | иконка-кнопка без текста → «кнопка» |
| **Роль**: что это | нативный тег; `role` | `div` с `onclick` → не объявляется вообще |
| **Значение**: что в нём сейчас | `value`; содержимое; `aria-valuenow` + `aria-valuemin/max` + `aria-valuetext` | кастомный слайдер без `aria-valuenow` |
| **Состояние**: в каком он состоянии | см. таблицу ниже | раскрытое меню без `aria-expanded` |

**Таблица состояний по компонентам** (что именно ставить):

| Компонент | Атрибут состояния | Значения |
|---|---|---|
| Кнопка-раскрытие (меню, аккордеон, поповер, дисклоужер, комбобокс) | `aria-expanded` | `true` / `false` |
| Кнопка-тумблер (вкл/выкл функции: «жирный», «тёмная тема») | `aria-pressed` | `true` / `false` / `mixed` |
| Переключатель-switch | `aria-checked` + `role="switch"` | `true` / `false` |
| Чекбокс | `checked` (нативно) или `aria-checked` | `true` / `false` / `mixed` |
| Радио, пункт меню-радио | `aria-checked` | `true` / `false` |
| Вкладка, опция листбокса, узел дерева, ячейка грида | `aria-selected` | `true` / `false` |
| Текущий пункт навигации | `aria-current` | `page` / `step` / `location` / `date` / `time` / `true` |
| Заголовок сортируемой колонки | `aria-sort` | `ascending` / `descending` (у несортированных **атрибут убирать**) |
| Поле с ошибкой | `aria-invalid` | `true` |
| Обязательное поле | `required` (нативно) или `aria-required` | `true` |
| Отключённый элемент, остающийся в фокусе | `aria-disabled` | `true` |
| Загружающаяся область | `aria-busy` | `true` / `false` (поддержка слабая, см. файл 03 §3.6) |
| Элемент, управляющий другим | `aria-controls` | id управляемого элемента |
| Раскрытие, тип всплывающего | `aria-haspopup` | `menu` / `listbox` / `tree` / `grid` / `dialog` |

**`aria-current` vs `aria-selected`.** `aria-current="page"` — «это текущая страница в навигации»;
`aria-selected` — «эта опция выбрана внутри виджета выбора». Путать их — частая ошибка: активный пункт сайдбара
получает `aria-current="page"`, а не `aria-selected="true"`. `[консенсус]` по [S2], [S4].

## 3. Доступные имена и описания

### 3.1 Что это и как звучит

Доступное имя — «a short string, **typically 1 to 3 words**», решающее две задачи: передать назначение и **отличить
элемент от других на странице** [S7]. Описание — более длинная строка (инструкция, формат).

Порядок озвучивания: **имя → роль → состояние → описание**. Пример из APG: «Mute Conversation switch button off,
Silences alerts and notifications about activity in this conversation» [S7].

**Важное ограничение описаний:** «some screen readers do not announce descriptions by default but instead inform
users of their presence so that users can press a key» [S7]. Значит, **в описание нельзя класть то, без чего нельзя
пользоваться** — только уточнение.

### 3.2 Пять правил именования

1. **Читать предупреждения и тестировать.** «It is difficult to over emphasize the importance of testing to ensure
   that names browsers calculate match expectations» [S7].
2. **Предпочитать видимый текст.** Имя, существующее только в разметке, рассинхронизируется при правках и не
   переводится. Если у интерактивного элемента нет постоянно видимой подписи — «consider adjusting the design to
   include one» [S7].
3. **Предпочитать нативные приёмы**: `<label>`, `<legend>`, `<caption>`, `alt`.
4. **Не полагаться на браузерный fallback** (`title`, `placeholder`): «their content typically yields low quality
   accessible names that are not effective» [S7].
5. **Короткие и полезные.**

### 3.3 Приоритет вычисления имени

Браузер идёт по списку и берёт первое, что дало результат [S7]:

1. `aria-labelledby`
2. `aria-label`
3. нативное: `value` (кнопки-инпуты), `alt` (`img`, `area`, `input type=image`), `legend` (первый в `fieldset`),
   связанный `<label>` (прочие поля), `figcaption` (первый в `figure`), `caption` (первый в `table`)
4. содержимое элемента — **для ролей, которые берут имя из содержимого**
5. fallback: `title`, затем `placeholder` (для текстовых полей)

**Роли, берущие имя из содержимого** [S7]: button, cell, checkbox, columnheader, gridcell, heading, link, menuitem,
menuitemcheckbox, menuitemradio, option, radio, row, rowheader, switch, tab, tooltip, treeitem.

**Ловушка №1.** Если на такой элемент повесить `aria-label` или `aria-labelledby`, **всё его содержимое скрывается
от AT**: «content contained in the element and its descendants is hidden from assistive technology users unless the
descendant content is referenced by `aria-labelledby`» [S7]. Кнопка с `aria-label="Сохранить"`, внутри которой есть
счётчик изменений, — счётчик исчезнет.

**Ловушка №2.** `aria-label` на неинтерактивных элементах (абзац, пункт списка) **запрещён спецификацией** —
валидатор выдаст ошибку [S7].

**Ловушка №3.** `aria-labelledby` **нельзя чейнить**: если элемент, на который ссылаются, сам имеет
`aria-labelledby`, оно игнорируется [S7].

### 3.4 Что умеет `aria-labelledby` и чего не умеет `<label>`

`aria-labelledby` [S7]:
- конкатенирует несколько элементов в порядке перечисления, через пробел; повторные ссылки игнорируются;
- включает **скрытый** контент (`hidden`, `display:none`, `visibility:hidden`);
- включает **значение полей ввода**;
- может ссылаться **на сам элемент**: `<a id="more" aria-labelledby="more bees-heading">Подробнее…</a>` →
  «Подробнее... 7 способов помочь пчёлам»;
- имеет **высший приоритет** и перекрывает всё.

Чего он **не** делает: браузер **не** превращает клик по метке в активацию контрола — «that is an author
responsibility» [S7]. У нативного `<label for>` это работает и **увеличивает область нажатия**, что прямо помогает
критерию 2.5.8 Target Size.

**Явная связь надёжнее неявной:** «Some combinations of assistive technologies and browsers fail to treat the
element as having an accessible name that is specified by using implicit association» (обёртка вместо `for`/`id`) [S7].

### 3.5 Описания

`aria-describedby` работает как `aria-labelledby`, но читается последним и может ссылаться на **скрытый** элемент —
типовой приём для подсказки, раскрываемой кнопкой «?»:

```html
<label for="username">Логин</label>
<input id="username" aria-describedby="username-desc">
<button aria-expanded="false" aria-controls="username-desc" aria-label="Справка о логине">?</button>
<p id="username-desc" hidden>Логин — это имя, под которым вы входите в сервис.</p>
```

Приоритет описания: `aria-describedby` → нативное (`caption` у таблицы, если имя задано иначе; `value` у кнопок;
содержимое `summary`) → `title` [S7].

`caption` у таблицы: становится **именем**, если нет `aria-label`/`aria-labelledby`; если имя задано ими — `caption`
становится **описанием**. У `figure` так не работает: `figcaption` не станет описанием автоматически [S7].

### 3.6 Как формулировать имена

Правила APG, пригодные как прямые инструкции генератору [S7]:

- **Называть функцию, а не форму.** Иконка «X», закрывающая диалог, — «Закрыть», не «X». Навигация слева с ссылками
  на продукты — «Продукты», не «Левая».
- **Самое различающее слово — первым.** Для списка контактов: «Изменить Иван Петров», «Удалить Иван Петров»,
  «Действия для Иван Петров» лучше, чем «Иван Петров изменить». Обоснование: «screen reader users can more easily
  and quickly distinguish the buttons from one another».
- **1–3 слова**; больше — только по необходимости.
- **Не включать название роли**: «кнопка», «изображение», «навигация» — скринридер произносит роль сам, получится
  «Site Navigation Navigation».
- **Уникальные имена у элементов одной роли**, кроме случая, когда они действительно идентичны и ведут в одно место.
- **Начинать с заглавной** (помогает интонации), **точку в конце не ставить**.

Для русского языка: конструкция «Глагол + объект» («Удалить заказ 12045») работает так же, как английская; «Заказ
12045: удалить» хуже, потому что различающее слово уходит в конец. `[практика]`

### 3.7 Label in Name: видимый текст внутри доступного имени

Критерий 2.5.3 (A): доступное имя **содержит** видимый текст подписи, best practice — видимый текст **в начале** [S8].

| Разметка | Вердикт |
|---|---|
| `<button aria-label="Закрыть">Отмена</button>` | **Провал**: видимого «Отмена» нет в имени; голосовая команда «нажми Отмена» не сработает |
| `<button aria-label="Удалить заказ 12045">Удалить</button>` | Проходит: видимое «Удалить» в начале имени |
| `<a aria-label="Подробнее о тарифе Про">Подробнее</a>` | Проходит |
| `<button aria-label="Submit">Отправить</button>` | **Провал** в русском интерфейсе |

Экспериментальное правило axe `label-content-name-mismatch` ловит это частично.

### 3.8 Иконки-кнопки и свёрнутый rail

Инвентарь решений `[консенсус]` по [S2], [S7], [S12], [V:2juq00vrvl0]:

| Ситуация | Разметка | Комментарий |
|---|---|---|
| Иконка + видимый текст в кнопке | `<button><svg aria-hidden="true" focusable="false"></svg> Сохранить</button>` | Имя даёт текст; иконка декоративна |
| Только иконка | `<button aria-label="Сохранить"><svg aria-hidden="true" focusable="false"></svg></button>` | Либо визуально скрытый `<span class="visually-hidden">Сохранить</span>` внутри кнопки — надёжнее для перевода |
| Иконка + счётчик | `<button aria-labelledby="cnt lbl"><svg …></svg><span id="cnt">3</span></button>` + `<div id="lbl" role="tooltip">Уведомления</div>` | Имя станет «3 Уведомления» [S12] |
| Свёрнутый навигационный rail | Кнопка/ссылка с `aria-label`, **плюс видимая подпись при раскрытии**, плюс тултип | Тултип **не заменяет** подпись |

**Почему `aria-label` не всегда лучший выбор.** Адриан Розелли: «Experience doing localization work has taught me the
attribute is too often missed when handling strings for translation. For automated translation, while support has
gotten better, you cannot count on `aria-label` being auto translated» [S9]. Визуально скрытый текст внутри элемента
переводится как обычный. `[практика]`

**Данные о цене иконок без подписей** (агент B, файл `../01-foundations/02-myths-and-misapplied-laws.md` §9):
универсально узнаваемы лишь несколько иконок (дом, печать, лупа); «непонятная иконка = потраченная впустую функция»;
подписи должны быть видны **всегда, без взаимодействия**, потому что hover не работает на тач и с клавиатуры.
`[исследование]`

## 4. Лендмарки и регионы

### 4.1 Соответствие HTML и ролей

| HTML | Роль лендмарка |
|---|---|
| `<header>` **в контексте `<body>`** | `banner` |
| `<footer>` **в контексте `<body>`** | `contentinfo` |
| `<nav>` | `navigation` |
| `<main>` | `main` |
| `<aside>` | `complementary` |
| `<section>` **с доступным именем** | `region` |
| `<search>` | `search` |
| `<form>` **с доступным именем** | `form` |

**`<header>` и `<footer>` не становятся banner/contentinfo, если вложены в `<article>`, `<aside>`, `<main>`, `<nav>`,
`<section>`** [S10]. Практический вывод: шапка страницы (page header) внутри `<main>` — это **не** banner, и это
правильно; banner — только глобальная шапка приложения.

### 4.2 Правила проектирования

Главный принцип APG: «Including **all perceivable content** on a page in one of its landmark regions… is one of the
most effective ways of ensuring assistive technology users will not overlook information» [S10].

Три шага [S10]: выделить воспринимаемые области (то, что дизайнер разделяет выравниванием и отступами) → назначить
роли → пометить.

Правила меток [S10]:
- если роль встречается больше одного раза — **уникальная метка каждой**;
- **исключение**: два одинаковых блока пагинации над и под таблицей результатов получают **одинаковую** метку
  «Результаты поиска», потому что различать их «may be more distracting than helpful»;
- две `navigation` с идентичным набором ссылок — **одинаковая** метка;
- если область начинается с заголовка — метить `aria-labelledby` на этот заголовок;
- **не включать название роли в метку**: «Site Navigation» → «Site Navigation Navigation»; правильно «Site»;
- `region` (`<section>` с именем) **обязан** иметь метку, иначе это не лендмарк;
- `banner`, `main`, `complementary`, `contentinfo` — **верхнеуровневые**, по одному на страницу;
- **содержимое модального диалога в лендмарк не оборачивать**: «A landmark that wraps modal content cannot provide
  any benefit to users… the modal itself is a container that provides both a name and boundaries».

### 4.3 Готовая карта лендмарков для веб-приложения

Соответствует каркасу из `../02-ia-navigation/02-navigation-patterns.md` §1 и
`../03-layout-placement/01-page-anatomy-templates.md`:

```html
<a class="skip-link" href="#main">К основному содержимому</a>
<header>                                  <!-- banner: логотип, переключатель контекста, утилиты -->
  <search>…</search>                      <!-- search: глобальный поиск -->
  <nav aria-label="Утилиты">…</nav>       <!-- уведомления, помощь, профиль -->
</header>
<nav aria-label="Разделы">…</nav>         <!-- navigation: сайдбар/рельс -->
<main id="main" tabindex="-1">            <!-- main: ровно один -->
  <h1>…</h1>
  …
</main>
<aside aria-label="Свойства объекта">…</aside>  <!-- complementary: панель-инспектор -->
<footer>…</footer>                        <!-- contentinfo -->
```

Примечания:
- `tabindex="-1"` на `<main>` нужен как цель skip-ссылки и как точка возврата фокуса при смене маршрута SPA (§10.5);
- панель-инспектор справа — `complementary`, если её содержимое осмысленно отдельно от основного, иначе `region`
  с меткой;
- хлебные крошки — отдельная `<nav aria-label="Хлебные крошки">` с `aria-current="page"` на последнем элементе.

### 4.4 Реальность использования лендмарков

По опросу WebAIM [S11]: «всегда» или «часто» используют лендмарки **31,8 %** пользователей скринридеров (после
падения с 43,8 % в 2014 до 25,6 % в 2021 — отскок), но как **первый способ поиска информации** на длинной странице
— **только 3,7 %**. `[исследование]`

Значит: лендмарки нужны (они дёшевы и дают структуру), но **бюджет внимания надо тратить на заголовки** (§5).

Данные о текущем состоянии: хотя бы один лендмарк есть на 84,3 % главных страниц, но `<main>` — только на 46,1 %,
`search` — на 18,8 % [S3].

Автопроверки: axe `region` (весь контент в лендмарках), `landmark-one-main`, `landmark-no-duplicate-main/banner/contentinfo`,
`landmark-*-is-top-level`, `landmark-unique`.

## 5. Иерархия заголовков

**Правила** [S13]:
- вкладывать по рангу; **пропуск ранга вниз (`h2` → `h4`) не допускается**; пропуск вверх при закрытии секции
  (`h4` → `h2`) допустим;
- **в фиксированных секциях (сайдбар, подвал) ранги не должны меняться от содержимого основной области** —
  консистентность между страницами важнее;
- допустимы два устройства страницы: `h1` = название сайта, все структурные заголовки `h2`; или `h1` = заголовок
  контента, а навигация/сайдбар/подвал тоже `h2`.

**Для веб-приложения работает второй вариант**: `h1` — заголовок страницы объекта («Заказ №12045»), совпадающий с
шапкой страницы и с `<title>`; секции контента — `h2`; блоки внутри секции — `h3`. `[практика]`

**Почему это важнее всего остального в структуре** [S11]: способ поиска информации на длинной странице —
заголовки **71,6 %**, поиск по странице 13,6 %, чтение подряд 6,4 %, по ссылкам 4,8 %, по лендмаркам 3,7 %.
У продвинутых пользователей доля заголовков 78 %, у новичков 47 % (новички в 2,5 раза чаще пользуются Find).
Уровни заголовков полезны 88,8 % опрошенных. `[исследование]`

**Состояние в вебе** [S3]: 41,8 % страниц пропускают уровни (рост с 39 %); 18,1 % имеют больше одного `h1`;
7,5 % не имеют заголовков вообще; из страниц с `<h6>` **94,9 % пропускают уровни** — то есть заголовки там
используются как стиль.

Автопроверки: axe `heading-order`, `empty-heading`, `page-has-heading-one`; экспериментальное `p-as-heading`.

**Приём из доклада:** уровни заголовков подписываются прямо на макете отдельным компонентом-аннотацией (H1, H2, H3),
а структура контента продумывается **до** открытия макетного редактора [V:2juq00vrvl0, 36:54]. `[практика]`

## 6. Скрытие: три разных инструмента

| Способ | Видно глазом | Есть для AT | В tab-последовательности | Когда применять |
|---|---|---|---|---|
| `display: none` / `visibility: hidden` / атрибут `hidden` | нет | **нет** | нет | Контент не нужен никому: свёрнутая панель аккордеона, неактивная вкладка |
| `aria-hidden="true"` | **да** | нет | **да, если элемент фокусируем — это ошибка** | Декоративные иконки рядом с текстом; дубли контента; фон под модалкой (вместе с `inert`) |
| Визуально скрытый класс | нет | **да** | да, если элемент фокусируем | Подписи, доступные только AT; skip-ссылка до фокуса; живые области; текст внутри иконки-кнопки |
| `inert` (атрибут) | да | нет | **нет** | Фон под модальным диалогом: разом убирает и фокус, и семантику |
| `opacity: 0` / `clip-path` без правильного класса | нет | **да** | **да** | Не использовать: создаёт «фокус в никуда» |

Канонический класс визуального скрытия (из Inclusive Components) [S12]:

```css
.visually-hidden {
  clip-path: inset(100%);
  clip: rect(1px, 1px, 1px, 1px);
  height: 1px;
  overflow: hidden;
  position: absolute;
  white-space: nowrap;
  width: 1px;
}
```

**Три обязательных следствия:**
1. **Живую область нельзя скрывать через `display:none` или `aria-hidden`** — «Hidden live regions are not
   announced» [S14]. Только визуально скрытым классом.
2. **Нельзя вешать `aria-hidden` на предка фокусируемого элемента** — кнопка исчезнет для AT, оставшись в табуляции [S1].
3. Иконки внутри кнопок с видимым текстом всегда получают `aria-hidden="true"` **и** `focusable="false"` (второе —
   против старых браузеров и против озвучивания SVG как группы) [S9].

Автопроверки: axe `aria-hidden-focus`, `aria-hidden-body`, `presentation-role-conflict`.

## 7. Видимый фокус

### 7.1 Требования

Три критерия работают вместе (подробно — `01-wcag22-as-build-rules.md` §5.3, §6.3, §12.2):

| Критерий | Уровень | Что требует |
|---|---|---|
| 2.4.7 Focus Visible | AA | Индикатор **существует** |
| 1.4.11 Non-text Contrast | AA | Индикатор даёт **3:1 к соседним цветам** |
| 2.4.13 Focus Appearance | AAA | Площадь ≥ периметра 2 px и **3:1 между состояниями** |
| 2.4.11 Focus Not Obscured | AA | Компонент с фокусом не перекрыт полностью |

### 7.2 Универсальный индикатор

Готовый рецепт, покрывающий любой фон [S15]:

```css
:focus-visible {
  outline: 3px solid black;
  box-shadow: 0 0 0 6px white;   /* белый «ореол» шириной 3px поверх чёрной обводки */
}
```

Вариант «Oreo» (два чёрных контура с белым между ними), ещё заметнее:

```css
:focus-visible {
  outline: 9px double black;
  box-shadow: 0 0 0 6px white;
}
```

Если компоненты в основном тёмные — поменять чёрный и белый местами.

**Почему именно `outline`** [S15]:
- `outline` **не входит в box model** → не вызывает сдвига раскладки (в отличие от `border`);
- `outline` **сохраняется в forced-colors**, а `box-shadow`, `background-color` и `border-color` — принудительно
  переопределяются или обнуляются (§1.5, файл 04 §3.5);
- `outline` принимает форму элемента.

**`:focus-visible`, а не `:focus`** — индикатор показывается только при клавиатурном фокусе. Приём Патрика Лаука для
обратной совместимости [S15]:

```css
button:focus { /* базовые стили фокуса */ }
button:focus:not(:focus-visible) { /* отменить их, если это не клавиатурный фокус */ }
button:focus-visible { /* усиленные стили */ }
```

### 7.3 Где что мерить

Контраст «к соседним цветам» зависит от положения индикатора [S15]:

| Положение | С чем мерить 3:1 |
|---|---|
| Снаружи (outset) | Фон страницы вокруг компонента |
| Внутри | Фон компонента |
| По границе (border) | **И** фон компонента, **и** фон страницы |
| Внутренняя граница | Фон компонента и его собственная граница |

Практический приём из доклада: между тёмным кольцом фокуса и цветной кнопкой нужна **светлая прослойка**, иначе
критерий не выполняется и кольцо плохо видно глазом [V:2juq00vrvl0, 07:15]. `[практика]`

### 7.4 Фокус ≠ выделение

APG формулирует два обязательных требования [S16]:
- «The visual focus indicator must always be visible»;
- «**The selected state must be visually distinct from the focus indicator**».

Разница по смыслу: фокус — как курсор мыши, он один и отмечает точку взаимодействия; выделение (`aria-selected`)
может быть множественным и **сохраняется, когда фокус ушёл** [S16]. В таблице с чекбоксами это значит: выделенная
строка и строка в фокусе оформляются **по-разному** и могут не совпадать.

### 7.5 Что делать с дефолтом браузера

APG советует «rely on the default focus indicators provided by browsers», предупреждая при этом, что «colors and
gradients can disappear in high contrast modes» [S16]. Измерения показывают, что дефолт часто не виден: 1,4:1 на
розовой кнопке в Chrome, 2,1:1 в Safari (§5.3 файла 01) [S15].

**Правило базы:** задавать собственный индикатор по §7.2 глобально, в базовом слое CSS, **до** написания любого
компонента. Это тот случай, когда одно правило закрывает критерий на всём продукте.

## 8. Клавиатурные контракты компонентов

Все контракты ниже — по ARIA Authoring Practices Guide [S17]. APG не является нормативным документом, но на него
ориентируются Material, Fluent, Carbon, Primer, Spectrum и Polaris; отклонение от него надо обосновывать.

### 8.1 Базовое правило

**Tab и Shift+Tab перемещают фокус между компонентами; стрелки — внутри компонента**, который содержит несколько
фокусируемых элементов (составной виджет, composite widget) [S16].

Составные виджеты, у которых **один tab stop на весь компонент**: combobox, grid, listbox, menu и menubar,
radiogroup, tablist, toolbar, treegrid, tree.

Куда попадает фокус при входе в составной виджет [S16] — три конвенции:

| Конвенция | Где применяется |
|---|---|
| На элемент, который имел фокус в прошлый раз (иначе первый) | grid, treegrid |
| **На выделенный элемент** (иначе первый) | radiogroup, tabs, listbox, tree |
| **На первый элемент** | menubar, toolbar |

### 8.3 Selection follows focus: когда можно

Перемещение фокуса внутри однозначного составного виджета может автоматически менять выделение. APG [S16]:

- **Можно**, когда переключение мгновенно: панели вкладок уже в DOM. «A keyboard user who wishes to display the
  fourth of six tabs can do so with 3 quick presses of the right arrow».
- **Нельзя**, если показ панели вызывает сетевой запрос или перезагрузку: «the effect… can be **devastating** to the
  experience for keyboard and screen reader users» — каждое движение стрелки даёт задержку, а при перезагрузке фокус
  вообще теряется.

Когда выделение не следует за фокусом, выбор делается **Enter или Space**.

### 8.4 Грид: что кладётся в ячейку

APG называет **только два оптимальных сочетания** [S17]:
1. в ячейке **один** виджет, не использующий стрелки (ссылка, кнопка, кнопка меню, toggle, радио, switch, чекбокс),
   и навигация грида ставит фокус **на виджет**;
2. в ячейке текст или одна картинка, и фокус ставится **на ячейку**.

Всё остальное «add complexity for authors or users or both».

**Вход внутрь ячейки** (когда там редактирование или несколько виджетов) [S17]: **Enter** или **F2** передают
управление содержимому; **Esc** возвращает навигацию по гриду (и может отменить правку); внутри ячейки Tab ходит по
виджетам грида; ←/→ ходят по виджетам внутри ячейки, если их несколько.

**Требование, которое ломает наивные реализации:** в гриде **каждая ячейка либо фокусируема, либо содержит
фокусируемый элемент**, иначе скринридер в режиме приложения её просто не прочитает. Исключение — заголовочные
ячейки без функций (без сортировки и фильтра) [S17].

### 8.5 Аккордеон, дисклоужер и `<details>`

APG для аккордеона требует только Enter/Space; **стрелки не обязательны**, и все заголовки — обычные tab stops [S17].
Это отличает аккордеон от вкладок и упрощает реализацию.

`<details>`/`<summary>` даёт то же поведение нативно, но: не поддерживает «только одна панель открыта» без JS, и
`role="button"` на `<summary>` ставить нельзя (§1.5). Для аккордеона с одной открытой панелью проще кнопки с
`aria-expanded`.

### 8.6 Меню против навигации

**`role="menu"` — это виджет приложения (как меню в десктопной программе), а не список ссылок.** Признак правильного
применения: внутри `menuitem`, работают стрелки, Tab выходит наружу, Esc закрывает.

Признак неправильного: `role="menu"` на списке навигационных ссылок. Данные: `role="menu"` есть на 5,7 % главных
страниц, и **22 % этих меню создают барьеры** из-за неполной разметки и поведения [S3]. `[исследование]`

Правило: **навигация — это `<nav>` + `<ul>` + `<a>`**, раскрывающийся подраздел — кнопка с `aria-expanded` и обычный
список. `role="menu"` берётся только для меню действий (контекстное меню, меню «ещё» у строки таблицы).
`[консенсус]` по [S3], [S17].

### 8.7 Подменю по клику, а не по наведению

Раскрытие по `hover` недоступно с клавиатуры и на тач; APG во всех меню использует активацию. Это же правило —
в `../02-ia-navigation/02-navigation-patterns.md` §2 (п. 18 выжимки). `[консенсус]`

### 8.8 Роли и атрибуты по компонентам (справочник)

| Компонент | Роли | Обязательные атрибуты |
|---|---|---|
| Вкладки | `tablist` / `tab` / `tabpanel` | `aria-selected` на tab; `aria-controls` на tab → id панели; `aria-labelledby` на панели → id вкладки; неактивные вкладки `tabindex="-1"` |
| Аккордеон | кнопки внутри `h2`–`h3` | `aria-expanded`, `aria-controls` |

| Модалка | `dialog` | `aria-modal="true"`, `aria-labelledby` (заголовок) и по необходимости `aria-describedby` |
| Алерт-диалог | `alertdialog` | то же + текст сообщения через `aria-describedby` |
| Комбобокс | `combobox` + `listbox`/`option` | `aria-expanded`, `aria-controls`, `aria-activedescendant`, `aria-autocomplete` |
| Листбокс | `listbox` / `option` | `aria-selected`, `aria-multiselectable` при множественном выборе |
| Дерево | `tree` / `treeitem` / `group` | `aria-expanded` на родительских узлах, `aria-selected`, `aria-level` |
| Грид | `grid` / `row` / `gridcell` / `columnheader` / `rowheader` | `aria-rowcount`, `aria-colcount`, `aria-rowindex`, `aria-colindex` при виртуализации; `aria-sort` на заголовке |
| Слайдер | `slider` | `aria-valuenow`, `aria-valuemin`, `aria-valuemax`, `aria-valuetext` (если число само по себе непонятно), `aria-orientation` |

### 8.9 Два способа управлять фокусом внутри составного виджета

**Roving tabindex** [S16]: активный элемент получает `tabindex="0"`, остальные `-1`; при нажатии стрелки —
переставить и вызвать `.focus()`. Плюс: «the user agent will scroll the newly focused element into view».

**`aria-activedescendant`** [S16]: DOM-фокус остаётся на контейнере, активный потомок указывается по id. Автор сам
рисует визуальный индикатор и **сам прокручивает элемент в зону видимости**. Ограничения DOM-связи: активный элемент
— потомок фокусированного, либо связан через `aria-owns`, либо (для combobox/textbox/searchbox) через `aria-controls`.

**Обязательная оговорка, которую пропускают** [S16]: при **клике или тапе** нужно так же обновлять
`tabindex`/`aria-activedescendant`, иначе переключение мышь ↔ клавиатура даёт рассинхрон и «confusing experience».

Практический выбор: **roving tabindex по умолчанию** (браузер сам скроллит и рисует фокус); `aria-activedescendant`
— когда DOM-фокус должен остаться в поле ввода (комбобокс) или когда элементов тысячи и переставлять `tabindex`
дорого. `[практика]`

### 8.10 Отключённые контролы: фокусировать или нет

`disabled` (HTML) убирает из tab-последовательности; `aria-disabled="true"` оставляет фокусируемым [S16].

Компромисс APG [S16]:

| Убирать из фокуса (`disabled`) | Оставлять фокусируемым (`aria-disabled`) |
|---|---|
| Кнопка «Назад» при видимой «Вперёд» | Copy / Cut / Paste в тулбаре редактора |
| Кнопка «Вверх» при видимой «Вниз» | Опции листбокса |
| Наличие выводится из соседних элементов | Пункты меню |
| | Вкладки |
| | Узлы дерева |

Обоснование: «screen reader users are far less likely to discover disabled elements that are not focusable because
moving focus is one of their primary methods of discovery» [S16].

**Общее правило, выходящее за рамки APG:** отключённая кнопка без объяснения — плохой UX независимо от фокуса.
Лучше держать кнопку активной и показывать ошибку при попытке, либо рядом писать, чего не хватает (см.
`../06-feedback-states-motion/` и `../05-flows-journeys/04-errors-and-recovery.md`). `[консенсус]`

### 8.11 Прокручиваемые области

Область с `overflow: auto`, не содержащая фокусируемых элементов, недоступна с клавиатуры в части браузеров.
Решение Адриана Розелли, закрывающее сразу четыре критерия [S18]:

```html
<div role="region" aria-labelledby="cap1" tabindex="0">
  <table>…<caption id="cap1">…</caption>…</table>
</div>
```
```css
[role="region"][aria-labelledby][tabindex] { overflow: auto; }
[role="region"][aria-labelledby][tabindex]:focus { outline: .1em solid …; }
```

Разбор: `tabindex="0"` → **2.1.1**; `role` + `aria-labelledby` → **4.1.2** (всё фокусируемое обязано иметь имя и
роль); `overflow: auto` → **1.4.10 Reflow**; `outline` с контрастом 3:1 → **2.4.7** и **1.4.11**.

Селектор по атрибутам выбран намеренно: **прокрутка не появится, пока разметка не сделана доступной**. Автопроверка
частично есть: axe `scrollable-region-focusable`.

### 8.12 Компоненты, которых APG не покрывает

APG не даёт паттернов для: пагинации, тостов, drag-and-drop, бесконечной прокрутки, панелей (немодальных),
командной палитры. Правила для них собраны в `03-forms-tables-dynamic-content.md` и выведены из общих принципов.

Клавиатурный минимум для них `[практика]`:

| Компонент | Контракт |
|---|---|
| Пагинация | `<nav aria-label="Пагинация">` + список ссылок/кнопок; текущая страница — `aria-current="page"`; обычная табуляция |
| Немодальная боковая панель | Фокус **не** захватывается; Esc закрывает; при закрытии фокус возвращается на триггер; панель стоит в DOM рядом с триггером или фокус явно переводится |
| Командная палитра | Открытие по шорткату **с модификатором** (Ctrl/Cmd+K); внутри — паттерн комбобокса; Esc закрывает и возвращает фокус |
| Массовые действия в таблице | Чекбоксы строк — обычные чекбоксы; «выбрать все» — чекбокс с `aria-checked="mixed"` при частичном выборе; панель массовых действий появляется — объявляется как статус (файл 03 §3) |

### 8.13 Тултип против тоглтипа

Разведение, которое стоит закрепить [S12]:

| | **Тултип** | **Тоглтип** |
|---|---|---|
| Вызов | наведение **и фокус** | **клик/тап** |
| Что это | подпись или уточнение к контролу | кнопка «i», существующая только чтобы показать сообщение |
| Связь | `aria-labelledby` (если это имя) или `aria-describedby` (если уточнение) | **живая область**: сообщение вставляется в пустой `role="status"` после клика |
| Почему так | на фокус реагирует клавиатура | если повесить `aria-describedby`, скринридер получит текст **до** нажатия, и нажатие покажется бесполезным |
| Работает на тач | плохо (focus и active совпадают) | **да** |

Ключевая проблема `title`: «If you want to hide content from mobile and tablet users as well as assistive tech users
and keyboard only users, use the `title` attribute» (цитата TPG у Хейдона Пикеринга) [S12].

**Правило:** тултип — последнее средство, когда места действительно нет (панель инструментов редактора). «There's
always room for text if you make it» [S12]. Требования 1.4.13 (Dismissible/Hoverable/Persistent) — файл 01 §10.3.

## 9. Порядок табуляции и skip-ссылки

### 9.1 Правила порядка

- `tabindex` отсутствует → поведение по умолчанию: в tab-последовательности только формы и `<a href>`
  (**в macOS по умолчанию только формы**, расширяется системной настройкой) [S16];
- `tabindex="0"` → в последовательности по DOM-порядку;
- `tabindex="-1"` → вне последовательности, но фокусируем через `.focus()`;
- **`tabindex` > 0 — «strongly advised NOT to use»**; «The most robust method of manipulating the order of the tab
  sequence… is rearranging elements in the DOM» [S16].

Правила предсказуемости [S16]:
- порядок по направлению чтения (слева направо, сверху вниз для русского и английского);
- **пройти все элементы одной секции до перехода в другую** — в трёхколоночном экране сначала весь левый сайдбар,
  потом центр, потом правая панель;
- не делать больших прыжков «назад»: «especially for users with a narrow field of view»;
- одинаковые паттерны по всему продукту;
- **не ставить начальный фокус при загрузке страницы**, кроме двух случаев: у страницы одна основная функция, к
  которой почти все обращаются сразу (экран входа, поиск), и пользователь заходит сюда часто.

**Главная опасность CSS:** `order`, `flex-direction: row-reverse`, `grid-area` и `position: absolute` меняют
визуальный порядок, не меняя DOM. Это ломает 1.3.2 и 2.4.3 одновременно. Правило: **визуальный порядок = DOM-порядок**;
если нужно поменять — менять разметку. `[стандарт]`

### 9.2 Постоянство фокуса

«It is essential that there is always a component within the user interface that is active (`document.activeElement`
is not null or is not the body element)» [S16]. Если после закрытия диалога или удаления элемента фокус не поставлен
явно, браузер отправит его на `<body>`, и клавиатурный пользователь окажется в начале страницы.

Автопроверка, которую стоит написать самому: после каждого действия в Playwright читать `document.activeElement` и
падать, если это `body`.

### 9.3 Skip-ссылка

Требования `[консенсус]` по [S3], [S19], [V:2juq00vrvl0]:
- **первый фокусируемый элемент документа**;
- визуально скрыта до фокуса, при фокусе видна (позиционируется поверх шапки);
- ведёт на существующий контейнер с `id`, у которого есть `tabindex="-1"` (иначе в части браузеров фокус не
  переместится, только прокрутится страница);
- после активации **следующий Tab идёт в контент**, а не обратно в навигацию — NN/g: «This last step is frequently
  overlooked, but essential» [S19];
- дизайнер решает, видима ли она всегда или появляется по табу, и **рисует её вид вместе с кольцом фокуса**
  [V:2juq00vrvl0, 28:45].

Данные: skip-ссылки есть на **17,1 %** главных страниц, и **каждая десятая сломана** [S3]. Автопроверки: axe
`bypass`, `skip-link`.

Для приложения с длинной навигацией полезны **несколько skip-ссылок**: «К содержимому», «К навигации», «К поиску» —
но не больше трёх, иначе они сами становятся блоком, который хочется пропустить. `[практика]`

## 10. Управление фокусом

### 10.1 Общее правило

Фокус переводится **только как немедленный ответ на действие пользователя**. Если что-то произошло асинхронно
(пришёл тост, обновились данные), фокус **не** трогать — иначе пользователь теряет место работы
[S14]. `[консенсус]`

### 10.2 Открытие и закрытие оверлеев

**Модальный диалог** [S17]:

| Момент | Что делать |
|---|---|
| Открытие | Фокус **внутрь** диалога |
| Куда именно | Обычно первый фокусируемый элемент. **Если контент сложный** (списки, таблицы, несколько абзацев) — `tabindex="-1"` на статический элемент в начале и фокус туда (и **не вешать `aria-describedby` на контейнер**). **Если контент длинный** — на заголовок. **Если это последний шаг необратимого действия** — на **наименее разрушительное** действие. Если диалог только информирует — на самое частое действие («ОК») |
| Пока открыт | Tab и Shift+Tab **закольцованы внутри**; фон `inert` (или `aria-hidden` + перехват фокуса) |
| Esc | Закрывает |
| Закрытие | Фокус **возвращается на вызвавший элемент** |
| Исключения из возврата | (1) вызвавший элемент исчез → на элемент, дающий логичное продолжение; (2) повторный вызов маловероятен **и** задача диалога ведёт к следующему шагу. Пример APG: диалог «сколько строк добавить» → фокус в первую ячейку первой новой строки |
| Обязательный элемент | «It is strongly recommended that the tab sequence of all dialogs include a visible element with role `button` that closes the dialog» |

**Немодальная панель** (инспектор, фильтры, чат): фокус **не** захватывается; Esc закрывает; панель стоит в DOM
рядом с триггером или фокус переводится явно; при закрытии возврат на триггер. Если панель может перекрыть
фокусируемый контент — это риск 2.4.11 (файл 01 §12.1), и тогда нужен один из пяти безопасных способов раскрытия.

**Нативный `<dialog>` + `showModal()`** даёт бесплатно: захват фокуса, Esc, инертность фона, `::backdrop`.
Возврат фокуса на триггер браузер делает сам при закрытии. Это лучший вариант по правилу 1. `[практика]`

### 10.3 Удаление элемента

Если пользователь удалил строку таблицы, пункт списка, вкладку или карточку:

| Ситуация | Куда фокус |
|---|---|
| Удалена строка из середины списка | На **следующую** строку (её кнопку того же назначения) |
| Удалена последняя строка | На предыдущую |
| Удалён единственный элемент | На контейнер списка или на пустое состояние (с `tabindex="-1"`), либо на кнопку «Создать» |
| Удаление подтверждалось в диалоге | Не возвращать на исчезнувший триггер — см. исключение в §10.2 |
| Удалена вкладка | APG: на **следующую** вкладку; если её нет — на предыдущую; если удалена последняя — на элемент, дающий логичное продолжение |

Плюс объявление результата через живую область: «Заказ 12045 удалён» (файл 03 §3).

### 10.4 Ошибки формы

Два варианта, и источники расходятся:

| Подход | Источник | Когда |
|---|---|---|
| Фокус на **сводку ошибок** вверху страницы (`role="alert"`, заголовок «Есть проблема», ссылки на каждое поле) | **GOV.UK**: «move keyboard focus to the error summary (the govuk-frontend javascript will do this for you)» [S20] | **По умолчанию**, особенно при нескольких ошибках: пользователь сразу узнаёт их число и может перейти к любой |
| Фокус на **первое ошибочное поле** | **W3C WAI Tutorial**: «If the submitted data contains errors, it is convenient to set the focus to the first `<input>` element that contains an error» [S21] | Когда ошибка одна и очевидна |

**Рекомендация базы:** сводка ошибок как основной механизм (она же покрывает случай одной ошибки — GOV.UK требует
показывать её «даже если ошибка одна»), плюс «Error: » в начале `<title>`, плюс сообщения у полей с теми же
формулировками. Детали — `03-forms-tables-dynamic-content.md` §1.6. `[спорно]` — в пользу сводки два аргумента
(число ошибок и навигация), против — лишний шаг при единственной ошибке.

### 10.5 Смена маршрута в SPA

Проблема: браузер не перезагружает страницу, скринридер не объявляет новый `<title>`, а клавиатурный пользователь
остаётся в том месте оболочки, где нажал ссылку.

**Решение** `[консенсус]` по [S14], [S17]:
1. **Сменить `document.title`** — это нужно и для истории, и для вкладок, и для 2.4.2.
2. **Перевести фокус** на `<h1>` новой страницы (с `tabindex="-1"`) или на контейнер `<main>` с `tabindex="-1"`.
   Скринридер прочитает заголовок — тот же контекст, который дал бы `<title>` при перезагрузке.
3. Прокрутить страницу вверх (иначе пользователь остаётся в середине предыдущей прокрутки).

**Почему не живая область.** Sara Soueidan: «Instead of relying on a live region to announce the page change, you
could send keyboard focus to the main `<h1>`… By moving the user's focus to the heading, the screen reader announces
the heading's content… (But don't forget to change the page's `<title>` when a new page is loaded, too.)». Перевод
фокуса заодно решает задачу клавиатурного пользователя, которому иначе пришлось бы протабливать всю оболочку [S14].

**Что выбрать: `h1` или `main`.** Фокус на `h1` даёт заголовок сразу; фокус на `main` даёт возможность читать с
начала контента. Оба применяются на практике; `h1` предпочтительнее, потому что даёт больше информации одним
объявлением. `[практика]`

**Чего не делать:** не ставить фокус на первый интерактивный элемент новой страницы (пользователь не поймёт, где он)
и не объявлять «Страница загружена» — это не отвечает на вопрос «где я».

### 10.6 Загрузка контента и подгрузка

- **Кнопка «Показать ещё»**: после загрузки фокус **остаётся на кнопке** (она не исчезла), а число новых элементов
  объявляется живой областью. Если кнопка исчезла (всё загружено) — фокус на первый из добавленных элементов.
- **Бесконечная прокрутка**: см. `03-forms-tables-dynamic-content.md` §6 — для клавиатуры она враждебна, потому что
  подвал недостижим.
- **Мастер (несколько шагов)**: при переходе на следующий шаг — фокус на заголовок шага, как при смене маршрута.

### 10.7 Фокус и виртуализация

Виртуальный список (рендерятся только видимые строки) ломает фокус: элемент, на котором стоял фокус, может быть
удалён из DOM при прокрутке. Правила `[практика]`:
- держать в DOM фокусируемый элемент, даже если он вышел за пределы окна (буфер над и под);
- при удалении сфокусированного узла — перенести фокус на ближайший существующий и объявить положение;
- выставлять `aria-rowcount`/`aria-rowindex` (или `aria-setsize`/`aria-posinset`), чтобы AT знала реальный размер
  набора, а не число отрендеренных строк.

## 11. Клавиатурные ускорители

### 11.1 Когда они нужны

APG формулирует иерархию прямо [S16]:
- «keyboard shortcuts **enhance, not replace**, standard keyboard access» — всё должно быть доступно навигацией
  **без** шортката;
- «If people who rely on the keyboard have to read documentation to learn which keys are required to use an
  interface, the interface may technically meet some accessibility standards but in practice is only accessible to
  the small subset of them who have the knowledge that such documentation exists»;
- «in most well-designed user interfaces, the percentage of functionality that needs to be accessible via a keyboard
  shortcut… is not very high… **excess shortcuts create cognitive load** that make the most useful ones more
  difficult to remember».

**Три типа поведения шортката** [S16]:

| Поведение | Когда |
|---|---|
| **Переместить фокус** | Цель — сократить путь: в поле поиска, в тулбар, в составной виджет, в секцию страницы |
| **Выполнить действие, не двигая фокус** | Контекст действия — там, где фокус. Пример APG: фокус в списке, шорткат удаляет опцию — «the user can hear the next option in the list and immediately decide whether to press the delete shortcut again» |
| **Переместить и выполнить** | Кнопка, открывающая меню или диалог; чекбокс; ссылка |

### 11.2 Чего не занимать

**Конфликты ОС** [S16]: любой модификатор + Tab / Enter / Space / Escape; meta (Win/Cmd) + любая одиночная клавиша;
Alt + функциональная клавиша.

**Конфликты со скринридерами** [S16]: `Caps Lock` + что угодно; `Insert` + что угодно; `Scroll Lock` + что угодно;
**в macOS — `Control + Option` + что угодно** (это модификатор VoiceOver).

**Конфликты с браузером** [S16]: беречь адресную строку, панель уведомлений, обновление страницы, закладки и
историю, **поиск по странице**. Намеренный конфликт допустим, когда: функция приложения используется часто,
браузерная — редко, и у браузерной есть другой путь.

**Конвенции клавиш, которые надо соблюдать** [S16]:

| Функция | Windows/Linux | macOS |
|---|---|---|
| Контекстное меню | Shift+F10 | — |
| Копировать | Ctrl+C | Cmd+C |
| Вставить | Ctrl+V | Cmd+V |
| Вырезать | Ctrl+X | Cmd+X |
| Отменить | Ctrl+Z | Cmd+Z |
| Вернуть | Ctrl+Y | Cmd+Shift+Z |

### 11.3 Одноклавишные шорткаты

Критерий 2.1.4 (A): если шорткат состоит только из букв, цифр, знаков препинания или символов, должно быть верно
хотя бы одно: можно выключить; можно переназначить с модификатором; **активен только когда компонент в фокусе**.

Практика продуктов с «g i», «c», «/», «?» (GitHub, Linear, Gmail): **обязательна страница настроек с выключателем**.
Минимально достаточная реализация — глобальный флаг «Горячие клавиши: вкл/выкл» в настройках профиля.
`[стандарт]` + `[практика]`

### 11.4 Как показывать шорткаты

`[практика]`, свод правил из APG и практики продуктов:
- **на самом элементе**, а не только в документации: в пункте меню справа («Сохранить · Ctrl+S»), в тултипе кнопки,
  в подсказке командной палитры;
- **одна страница-справочник**, открываемая по `?` (и доступная из меню помощи) — со списком всех шорткатов;
- в разметке пункта меню сочетание выносится в отдельный элемент, который **не входит в доступное имя** пункта,
  либо входит целиком и читается как «Сохранить, Control S» — второй вариант лучше, потому что иначе шорткат
  недоступен скринридеру;
- показывать сочетания в нотации текущей ОС (Cmd на macOS, Ctrl на Windows) — определять по платформе;
- **не использовать шорткаты для деструктивных действий без подтверждения**.

## Частые ошибки

Ошибки нейросетей из `../11-ai-generated-ui/01-failure-modes-catalog.md`, закрываемые этим файлом:

1. **F9.4 «Hover-only взаимодействия и отсутствие фокуса»** — §7 (индикатор), §8.7 (подменю по клику), §8.13
   (тултип против тоглтипа). Автопроверка: селекторы `:hover` без парного `:focus-visible`; обработчики `mouseover`
   без `click`/`keydown`.
2. **F9.1 «Неподписанные контролы»** — §2, §3. Автопроверка: полный набор axe-правил на имена.
3. **F4.3 «Кнопки без назначения»** и **F4.4 «Не тот тип контрола»** — §1.1: `div` с `onclick` не имеет ни роли, ни
   клавиатуры; нативный элемент решает обе проблемы сразу.
4. **F11.1 (b) «No interaction» и (i) «Partial Implementation»** (кнопку можно выбрать, но нельзя снять выбор) —
   §2: состояние должно быть двусторонним (`aria-pressed`, `aria-selected`).
5. **F1.2 «Навигация меняется от экрана к экрану»** — §4.3: общий каркас лендмарков в одном layout-компоненте.
6. **F6.3 «Состояние не переживает переход между экранами»** — §10.5: при смене маршрута фокус и `<title>`
   обновляются явно, а не «как получится».

Ошибки, специфичные для этой темы:

7. **`aria-label` поверх видимого текста** — ломает 2.5.3 и скрывает содержимое (§3.3, §3.7).
8. **`role="menu"` на навигации** — 22 % таких меню создают барьеры (§8.6).
9. **`aria-hidden` на предке кнопки** — фокус «в никуда» (§1.3).
10. **`tabindex` > 0 «чтобы поправить порядок»** — ломает порядок глобально (§9.1).
11. **`outline: none` с обещанием «потом сделаем красиво»** (§7.1).
12. **Модалка на `div` без `inert`, Esc и возврата фокуса** (§10.2) — при том что `<dialog>` даёт всё это бесплатно.
13. **Фокус после удаления не переводится** — падает на `body` (§9.2, §10.3).
14. **Смена маршрута SPA без смены `<title>` и без перевода фокуса** (§10.5).
15. **Кастомный `div`-скроллер без `tabindex`** — недоступен с клавиатуры (§8.11).
16. **Одинаковые метки у разных `nav`** («Навигация», «Навигация») — вместо «Разделы», «Утилиты» (§4.2).
17. **Слово «навигация» внутри метки лендмарка** — двойное произношение (§4.2).
18. **Selection follows focus на вкладках с сетевой загрузкой** (§8.3).
19. **`aria-activedescendant` без собственной прокрутки активного элемента в зону видимости** (§8.9).
20. **Шорткат на одну букву без выключателя** — провал 2.1.4 (§11.3).

## Чек-лист

Семантика:
- [ ] Каждый интерактивный элемент — нативный тег или роль с полным клавиатурным контрактом?
- [ ] Нет `aria-hidden` и `role="presentation"` на фокусируемых элементах и их предках?
- [ ] Нет избыточных ролей (`<button role="button">`) и абстрактных ролей?
- [ ] Нативные состояния не перебиты ARIA-атрибутами?
- [ ] `role="menu"` применён только к меню действий, не к навигации?

Имена:
- [ ] У каждого интерактивного элемента есть имя, роль, значение и состояние?
- [ ] Имя — 1–3 слова, начинается с различающего, без слова-роли, уникально среди элементов той же роли?
- [ ] Видимый текст подписи входит в доступное имя?
- [ ] Иконки рядом с текстом помечены `aria-hidden="true"` и `focusable="false"`?
- [ ] У иконок-кнопок имя задано так, что переводится (визуально скрытый текст или переводимый `aria-label`)?

Структура:
- [ ] Весь видимый контент в лендмарках, `<main>` ровно один, метки уникальны и без слова-роли?
- [ ] Один `h1`, уровни не пропущены, в фиксированных секциях ранги стабильны?
- [ ] Skip-ссылка первая, видна при фокусе, цель имеет `tabindex="-1"`, после неё Tab идёт в контент?

Фокус:
- [ ] Индикатор задан глобально через `:focus-visible` + `outline` и виден на любом фоне?
- [ ] Выделение визуально отличается от фокуса?
- [ ] Нет `tabindex` > 0; визуальный порядок совпадает с DOM-порядком?
- [ ] После каждого действия `document.activeElement !== body`?
- [ ] Модалка: фокус внутрь, кольцо замкнуто, Esc, фон инертен, возврат на триггер?
- [ ] После удаления элемента фокус на соседний?
- [ ] При смене маршрута SPA меняется `<title>` и фокус уходит на `h1`?
- [ ] Ни один фокусируемый элемент не перекрыт липкой панелью?

Клавиатура:
- [ ] Каждый составной виджет — один tab stop, внутри стрелки?
- [ ] Контракт каждого компонента совпадает с таблицей §8.2?
- [ ] Выделение следует за фокусом только там, где переключение мгновенно?
- [ ] Прокручиваемые области фокусируемы и имеют имя?
- [ ] Шорткаты не конфликтуют с ОС, скринридером и ключевыми функциями браузера?
- [ ] Одноклавишные шорткаты можно выключить?
- [ ] Шорткаты показаны на самих элементах и собраны на одной странице?

## Открытые вопросы и противоречия

1. **Фокус на сводку ошибок или на первое поле** — GOV.UK и W3C WAI дают разные рекомендации (§10.4). Ни один из
   источников не приводит сравнительного теста. Кандидаты на проверку: исследования GOV.UK по паттерну validation
   (обещаны, но не опубликованы), Adam Silver «Form Design Patterns».
2. **APG не покрывает мобильные и тач.** Гайд прямо оговаривается: «this guide does not indicate which examples are
   compatible with mobile browsers or touch interfaces… some ARIA features are not supported in any mobile browser»
   [S2]. Значит, клавиатурные контракты §8 проверены для десктопа, а поведение тех же компонентов с VoiceOver и
   TalkBack надо тестировать отдельно. Это пробел, который стоит закрыть агенту F1 (мобильная адаптация, волна 3).
3. **Selection follows focus в листбоксе и дереве** — APG допускает оба поведения и не даёт критерия выбора, кроме
   «мгновенно или нет». Для таблиц с серверной фильтрацией это существенно, а данных нет.
4. **Порог «сколько шорткатов много»** нигде не назван числом. APG говорит «не очень высокий процент функций», но
   границы не даёт. Кандидаты: замеры на реальных продуктах (Linear, Superhuman, GitHub), исследования по
   запоминаемости акселераторов.
5. **Аннотация порядка фокуса на макете** (§8.14) описана только в докладе практика; методик и данных о её
   эффективности нет. Помечено `[практика]`.
6. **Виртуализация и скринридеры** (§10.7): ни APG, ни W3C не дают паттерна для виртуальных списков. Правила
   выведены из общих требований и практики, помечены `[практика]`. Кандидаты на проверку: документация
   TanStack Virtual, AG Grid accessibility, исследования по `aria-rowcount` в реальных AT.
7. **Расхождение с волной 1 не найдено.** Правила этого файла дополняют
   `../02-ia-navigation/02-navigation-patterns.md` (подменю по клику, не прятать навигацию, показывать текущее место)
   и `../03-layout-placement/04-placement-conventions-and-redundancy.md` (Esc закрывает модалку, фокус возвращается
   на триггер — там это записано в «чего нельзя нарушать никогда», здесь раскрыто).
