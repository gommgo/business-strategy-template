## Выжимка для агента

1. **У каждого поля — видимая подпись, связанная через `<label for>`.** Треть полей в вебе не подписана вообще;
   плейсхолдер подписью не является. → §1.1 `[стандарт]` + `[исследование]`
2. **Общие инструкции к форме ставь ПЕРЕД `<form>`**: внутри формы скринридеры переходят в «Forms Mode» и читают
   в основном поля, подписи и легенды. → §1.2 `[стандарт]`
3. **Подсказку к полю связывай через `aria-describedby`**, а не оставляй «рядом визуально». → §1.3 `[стандарт]`
4. **Радиогруппы и группы чекбоксов — всегда `fieldset` + `legend`.** Без этого вопрос не связан с ответами.
   → §1.4 `[стандарт]`
5. **Сводка ошибок вверху страницы обязательна, даже если ошибка одна**: `role="alert"`, заголовок, ссылка на каждое
   поле, те же формулировки, что у полей, «Ошибка:» в начале `<title>`, фокус на сводку. → §1.6 `[система]`
6. **После ошибки введённые данные не очищаются** — это 3.3.7 Redundant Entry, а не вежливость. → §1.6 `[стандарт]`
7. **Не валидируй на blur по умолчанию.** GOV.UK запрещает прямо; W3C показывает как приём. Безопасный компромисс —
   валидация по сабмиту плюс точечная инлайн-проверка там, где она дешевле ошибки. → §1.7 `[спорно]`
8. **Кастомный селект, дейтпикер и загрузка файла требуют полного клавиатурного контракта**; если его нет —
   использовать нативные `<select>`, `<input type="date">`, `<input type="file">`. → §1.8 `[консенсус]`
9. **Капча — проблема №1 у пользователей скринридеров 14 лет подряд.** Убирать: rate limiting, honeypot, WebAuthn,
   токены провайдера. Если оставлять — только узнавание объектов и всегда с альтернативой. → §1.9 `[исследование]`
10. **Таблица данных — это `<table>`, `<th scope>`, `<caption>`.** Не `div`, не CSS-grid: «some browsers break the
    semantics and a screen reader user will be stranded». → §2.1 `[консенсус]`
11. **`aria-sort` только на одной колонке, у остальных атрибут убирается**; факт сортировки объявляют не все
    скринридеры — нужна живая область. → §2.4 `[исследование]`
12. **Широкая таблица прокручивается в контейнере `role="region"` + `aria-labelledby` + `tabindex="0"`** — это
    закрывает 1.4.10, 2.1.1, 2.4.7, 4.1.2 сразу. → §2.6 `[практика]`
13. **`role="grid"` — для интерактивных гридов, а не для таблиц данных.** «Just use HTML tables for your data».
    → §2.2 `[мнение]`
14. **Живая область — последнее средство.** Сначала: состояние ARIA (`aria-expanded`, `aria-pressed`), затем
    предупреждающая подсказка заранее, затем перевод фокуса, и только потом живая область. → §3.1 `[консенсус]`
15. **Две живые области на страницу: одна `assertive`, одна `polite`**, обе в DOM с загрузки, очередь ведётся вручную.
    → §3.4 `[практика]`
16. **Живая область не передаёт разметку**: кнопки и ссылки внутри неё теряют роль и недостижимы. Уведомление с
    действием — это диалог, а не тост. → §3.3 `[стандарт]` + `[консенсус]`
17. **Фильтры: не объявляй каждое изменение — дай подсказку заранее** («Изменение фильтров меняет список») и
    объявляй итог: «Найдено 12 заказов». → §3.5 `[практика]`
18. **Пустой результат поиска объявляется `assertive`** — это исключение из правила «не шуметь». → §3.5 `[консенсус]`
19. **Модалка: `role="dialog"` + `aria-modal="true"` + имя, фокус внутрь, Esc, фон `inert`, возврат фокуса.**
    Нативный `<dialog>` даёт это бесплатно. → §4.1 `[APG]`
20. **Немодальная панель фокус не захватывает**, но если она может перекрыть фокусируемый контент — это 2.4.11.
    → §4.3 `[стандарт]`
21. **Тост: `role="status"`, без интерактива, не исчезает быстрее, чем можно прочитать; важное дублируется в
    постоянном месте.** → §5.1 `[консенсус]`
22. **Счётчик в бейдже — часть доступного имени**, а не отдельный узел: «3 уведомления». → §5.2 `[практика]`
23. **Drag-and-drop обязан иметь альтернативу кликами** (2.5.7) и **отдельно** клавиатурную (2.1.1) — это два
    разных требования. → §5.3 `[стандарт]`
24. **Бесконечная прокрутка враждебна клавиатуре**: подвал недостижим. По умолчанию — «Показать ещё» + пагинация.
    → §6 `[консенсус]`
25. **У каждого графика — текстовое резюме и таблица-эквивалент**, а не только `alt="график"`. → §7 `[консенсус]`
26. **Скелетоны: `aria-busy` поддерживается плохо** — прятать загружающуюся область `aria-hidden` и объявлять
    «Загрузка…» / «Загружено» отдельной polite-областью. → §8 `[практика]`

## 1. Формы

### 1.1 Подписи

**Иерархия способов** (от лучшего к худшему) [S1]:

| Способ | Когда |
|---|---|
| `<label for="id">` + `id` на поле | **По умолчанию всегда** |
| `<label>` обёрткой | Хуже: «Some combinations of assistive technologies and browsers fail to treat the element as having an accessible name» |
| Визуально скрытый `<label>` | Когда назначение очевидно из контекста — практически только поиск |
| `aria-label` | Когда подписи в вёрстке нет вообще (поле поиска рядом с кнопкой «Найти») |
| `aria-labelledby` | Когда подпись — существующий элемент (кнопка рядом с полем) |
| `title` | «generally less reliable and **not recommended**» |
| `placeholder` | **Не подпись** |

**Почему `<label for>` лучше `aria-label`:** браузер делает клик по метке активацией контрола, **увеличивая область
нажатия** — это прямо помогает критерию 2.5.8 Target Size [S2]; текст метки видим всем, а не только AT; он
переводится штатными средствами.

**Данные о масштабе** [S3]: 6,9 полей на среднюю главную страницу (+36 % за три года); **33,1 % полей не подписаны
никак**; отсутствие подписи поля — на 51 % страниц, и доля растёт. `[исследование]`

**Плейсхолдер.** W3C: «placeholder text is not a replacement for labels»; он исчезает при вводе, имеет низкий
контраст и мешает проверить ответы перед отправкой [S1]. Разбор практика, который редко попадает в статьи:
форма, заполненная серыми плейсхолдерами, **выглядит уже заполненной** для людей с когнитивными особенностями;
светлый плейсхолдер не проходит по контрасту, тёмный выглядит как введённое значение; исчезающий плейсхолдер уносит
подсказку формата [V:2juq00vrvl0, 51:17]. `[практика]`

**Правило базы:** плейсхолдер **не заменяет подпись и не хранит критичную информацию**; подсказка формата живёт в
`aria-describedby` под полем. Полный запрет плейсхолдеров — позиция одного автора, помечаем `[спорно]`.

**Единица подписи:** одна подпись на одно поле. axe `form-field-multiple-labels` ловит несколько `<label>` на поле;
`label-title-only` (best practice) ловит подпись только через `title`.

### 1.2 Инструкции к форме и «Forms Mode»

**Ключевой факт:** скринридеры переключаются в режим форм внутри `<form>` и в этом режиме читают в основном
`<input>`, `<select>`, `<textarea>`, `<legend>`, `<label>`. «It is critical to include form instructions in ways that
can be read aloud» [S1].

Отсюда:
- **общие инструкции ставятся ПЕРЕД `<form>`**: что обязательно, какие форматы, сколько времени займёт, где искать
  помощь;
- инструкции внутри формы — только через `<label>`, `<legend>` или `aria-describedby`.

Формулировка из доклада: «форма — как настольная игра, правила объясняют до начала, иначе никто не выиграет»
[V:2juq00vrvl0, 24:41]. `[практика]`

### 1.3 Подсказки и форматы

Три способа связать подсказку с полем [S1]:

```html
<!-- 1. В подписи — самый надёжный -->
<label for="expire">Срок действия (ММ/ГГГГ)</label>
<input id="expire">

<!-- 2. aria-describedby — читается после имени и роли -->
<label for="expire2">Срок действия</label>
<input id="expire2" aria-describedby="expire2-hint">
<span id="expire2-hint">Например 03/2028</span>

<!-- 3. aria-labelledby с двумя id — подсказка входит в ИМЯ -->
<label id="l" for="expire3">Срок действия</label>
<input id="expire3" aria-labelledby="l hint3">
<span id="hint3">ММ/ГГГГ</span>
```

Выбор: формат и пример → `aria-describedby` (не засоряет имя); часть смысла, без которой имя непонятно
(«Количество, шт.») → в подпись.

**Ограничение описаний:** часть скринридеров не читает описание автоматически, а лишь сообщает о его наличии [S2].
**В описание нельзя класть то, без чего нельзя заполнить поле.**

**Обязательность.** Помечать обязательные поля, а не необязательные, если обязательных большинство; программно —
`required` (нативно объявляется как «обязательно») либо `aria-required="true"`. Легенда «* — обязательное поле»
ставится **до** формы (§1.2).

### 1.4 Группировка

`<fieldset>` + `<legend>` — единственный способ программно связать вопрос с группой ответов: «If a question is not
programmatically associated with its answer options, assistive technology users may access the answers without being
aware of the question» [S1].

Обязательно для: радиогрупп; групп чекбоксов с общим вопросом; **групп полей с одинаковыми подписями** («Адрес
доставки» / «Адрес плательщика» — иначе два поля «Город» неразличимы); составных полей (дата из трёх полей,
диапазон «от — до»).

`<optgroup>` — группировка внутри `<select>`.

**Ограничение:** `<legend>` нельзя стилизовать произвольно во всех браузерах, и вложенные `fieldset` звучат
многословно. Для больших форм лучше секции с заголовками `h2`/`h3` плюс `fieldset` только на смысловые группы.
`[практика]`

### 1.5 Автозаполнение

`autocomplete` на полях **о самом пользователе** (1.3.5) — 53 значения из раздела 7 WCAG: `name`, `given-name`,
`family-name`, `email`, `tel`, `street-address`, `address-level2`, `postal-code`, `country-name`, `bday`,
`organization`, `cc-number`, `cc-exp`, `username`, `current-password`, `new-password`, `one-time-code`.

Тройная выгода: соответствие 1.3.5; работа менеджеров паролей (условие 3.3.8); меньше ввода для людей с моторными
нарушениями и голосовым вводом.

Автопроверка: axe `autocomplete-valid`.

### 1.6 Ошибки: полный контракт

**Что должно произойти при отправке формы с ошибками** `[консенсус]` по [S1], [S4]:

1. Страница показывается заново **с сохранёнными введёнными значениями** (3.3.7).
2. В начало `<title>` добавляется «Ошибка: ».
3. Вверху страницы, перед формой, появляется **сводка ошибок**:
   - контейнер с `role="alert"`;
   - заголовок («Есть проблема» / «There is a problem»);
   - список, где **каждый пункт — ссылка на поле** (`href="#id"`);
   - формулировки **дословно те же**, что у полей;
   - **фокус переводится на сводку**.
4. У каждого ошибочного поля: `aria-invalid="true"`, сообщение, связанное через `aria-describedby`, визуальный
   признак **не только цветом** (иконка + текст + толщина границы).

Разметка GOV.UK [S4]:

```html
<div class="govuk-error-summary" data-module="govuk-error-summary">
  <div role="alert">
    <h2 class="govuk-error-summary__title">Есть проблема</h2>
    <ul>
      <li><a href="#name">Введите полное имя</a></li>
      <li><a href="#issued">Дата выдачи паспорта должна быть в прошлом</a></li>
    </ul>
  </div>
</div>
```

**Требование «даже если ошибка одна»** — GOV.UK: «Always show an error summary when there is a validation error, even
if there's only one» [S4]. `[система]`

**Требования к тексту ошибки** (3.3.1 + 3.3.3):
- назвать **поле** («Дата выдачи»), а не «поле 3»;
- назвать **что не так** конкретно, а не «неверный формат»;
- **подсказать, как исправить**, и напомнить формат: «Введите год числом, например 2020».

**Двухуровневое документирование ошибок** [V:2juq00vrvl0, 27:43]: в дизайн-системе — общее состояние ошибки
компонента (иконка, место сообщения); на макете конкретного экрана — условие срабатывания и точный текст.
`[практика]`

### 1.7 Когда проверять: спор источников

| Позиция | Источник | Аргумент |
|---|---|---|
| **Не валидировать на blur.** Ждать нажатия «Продолжить» | GOV.UK: «Do not validate when the user moves away from a field… avoid validating the information in a field before the user has finished entering it. This sort of validation can cause problems — especially for users who type more slowly» [S4] | Медленно печатающие получают ошибку до того, как закончили |
| **Валидировать при уходе с поля** | W3C WAI Tutorial: пример с `aria-live="assertive"` на blur [S1] | Ошибка исправляется на месте, а не после сабмита |
| **Валидировать во время набора** | W3C для проверки занятости логина: `aria-live="polite"`, «the message is only read once when the user stops typing» [S1] | Дорогая проверка (уникальность), которую иначе узнаешь только после отправки |

**Рекомендация базы** `[спорно]`, в сторону GOV.UK:
- **по умолчанию — валидация по сабмиту** со сводкой ошибок;
- **инлайн-проверка во время набора — точечно**, там, где ошибка дорого обходится: занятость логина, сила пароля,
  счётчик символов, доступность домена. Всегда `polite`, всегда после паузы в наборе;
- **валидация на blur — только для «исправления», а не «обвинения»**: подсветить успешный ввод, нормализовать формат
  (пробелы в номере карты), но не показывать ошибку, пока поле не покинуто дважды или форма не отправлена;
- **повторная валидация после исправления** обязательна: сообщение снимается сразу, как только значение стало
  валидным.

GOV.UK дополнительно советует **отключать HTML5-валидацию** (`novalidate`, не ставить `required`), потому что вид и
текст браузерных сообщений нельзя привести к системе [S4]. Это **`[система]`, а не `[консенсус]`**: сам GOV.UK
пишет, что хотел бы увидеть исследования о влиянии отсутствия `required` на скринридеры. Практика базы:
**`required` ставить** (он объявляется AT), `novalidate` — ставить, если своя валидация полная.

**Прощающий ввод** (и COGA 4.5.8, и GOV.UK) [S4], [S9]: принимать разные форматы (индекс с пробелами и без, имена с
апострофами и диакритикой), игнорировать лишние символы (пробелы, дефисы, скобки, точки — «особенно вносимые
диктовкой»), нормализовать на сервере, а не отвергать.

### 1.8 Кастомные контролы

Правило: **кастомный контрол берётся, только если нативный физически не решает задачу**, и тогда он получает полный
контракт из `02-keyboard-focus-semantics.md` §8.

| Контрол | Нативный вариант | Когда нужен кастомный | Что обязательно |
|---|---|---|---|
| Выбор из списка | `<select>` | Нужен поиск, множественный выбор с тегами, богатые опции | Паттерн combobox: `role="combobox"`, `aria-expanded`, `aria-controls`, `aria-activedescendant`; Esc закрывает; Enter выбирает; печать фильтрует |
| Дата | `<input type="date">` | Нужны диапазоны, подсветка занятых дат, нестандартный календарь | **Всегда оставлять текстовый ввод даты рядом с календарём**; календарь — грид с навигацией стрелками, PageUp/PageDown по месяцам, Esc закрывает |
| Файл | `<input type="file">` | Нужен drag-and-drop | **Кнопка «Выбрать файл» обязательна помимо зоны перетаскивания** (2.5.7); после выбора — объявление имени файла и статуса загрузки живой областью |
| Множественный выбор тегами | `<select multiple>` | Почти всегда | Каждый тег — удаляемый элемент с именем «Удалить <тег>»; Backspace в поле удаляет последний тег; число выбранных объявляется |
| Числовой ввод | `<input type="number">` | Форматирование, единицы | Осторожно: колесо мыши меняет значение при фокусе — блокировать; `inputmode="decimal"` для мобильных |
| Rich text | `contenteditable` | Всегда | Тулбар — паттерн toolbar (один tab stop); шорткаты форматирования; **не перехватывать Tab** (или давать способ выйти — иначе ловушка фокуса, 2.1.2) |
| Пароль | `<input type="password">` | — | **Разрешить вставку**; кнопка «показать пароль» с `aria-pressed` |
| Код подтверждения | `<input>` | — | **Одно поле**, `autocomplete="one-time-code"`, `inputmode="numeric"`; не шесть полей с автоперескоком (§9.7 файла 01) |

**Общее требование к любому кастомному контролу:** при `prefers-reduced-motion` анимация раскрытия убирается; в
forced-colors состояние видно (§3.5 файла 04); значение доступно как текст, а не только как позиция.

### 1.9 Капча

**Данные:** в опросе WebAIM (1539 респондентов) капча — **проблема №1 с большим отрывом**, и держится на первом месте
14 лет подряд; у респондентов с инвалидностью она попадает в топ вдвое чаще [S5]. `[исследование]`

Иерархия решений `[консенсус]` по [S5], [S6]:

1. **Убрать капчу.** Альтернативы, не являющиеся когнитивным тестом: rate limiting, honeypot-поле, проверка
   поведения, токен провайдера (Turnstile, Privacy Pass), WebAuthn, подтверждение по почте.
2. Если нельзя — **распознавание объектов** («выберите картинки с машинами») разрешено на AA, запрещено на AAA;
   задание не должно выходить за пределы узнавания.
3. **Всегда давать альтернативу**, не являющуюся когнитивным тестом. Аудио-капча, которую надо расшифровать и
   напечатать, **альтернативой не считается** [S6].
4. Капча, появляющаяся только иногда (при блокировщике рекламы, после неверных попыток), **под критерий всё равно
   подпадает** [S6].

## 2. Таблицы

### 2.1 Разметка

| Случай | Что делать |
|---|---|
| Заголовки только в первой строке | `<th>` в строке; **`scope="col"` ставить всё равно** — без него часть скринридеров читает «Дата – Событие – Место» в ячейке «Место» из-за неоднозначности направления [S7] |
| Заголовки и в строке, и в колонке | `<th scope="col">` и `<th scope="row">` |
| Заголовок охватывает несколько колонок или строк | `<colgroup span>` / `<thead>`,`<tbody>`,`<tfoot>` + `scope="colgroup"` / `scope="rowgroup"` |
| Многоуровневые заголовки, которые нельзя связать линейно | `id` на `<th>` + `headers` на `<td>` |
| Название таблицы | `<caption>` — «functions like a heading for a table», основной механизм опознания в режиме таблиц |
| Описание структуры сложной таблицы | summary внутри `<caption>`, либо через `aria-describedby`, либо через `<figure>`; **не дублировать caption** |

Автопроверки: axe `th-has-data-cells`, `td-headers-attr`, `scope-attr-valid`, `empty-table-header`,
`table-duplicate-name`; экспериментальные `td-has-header` (таблица крупнее 3×3), `table-fake-caption`.

**Таблицы для раскладки не использовать**: «As a general rule, tables aren't meant to be used for layout purposes» [S7].

### 2.2 `<table>` против `role="grid"`

Категорично и однозначно [S8]: «**Avoid ARIA `grid` roles for responsive tables (and similarly, avoid using
`<div>`s). ARIA grids are interactive widgets, not data tables (though they retain some traits of data tables).
Just use HTML tables for your data.**»

Когда `role="grid"` всё-таки уместен: ячейки редактируются на месте; нужна навигация стрелками по ячейкам; нужно
выделение диапазонов; в каждой ячейке интерактив, и обычная табуляция даёт сотни остановок. Тогда — полный
контракт грида из `02-keyboard-focus-semantics.md` §8.2 и §8.4.

**Критерий выбора** `[практика]`:

| Признак | `<table>` | `role="grid"` |
|---|---|---|
| Строк на экране | любое | любое |
| Ячейки редактируются | нет | да |
| Интерактив в каждой ячейке | 0–1 элемент на строку | много |
| Выделение диапазонов | нет | да |
| Стоимость реализации | низкая | высокая, нужен полный контракт |

### 2.3 Действия строки

- Каждая кнопка действия получает **уникальное имя с объектом**: «Удалить заказ 12045», а не «Удалить» ×50
  (§3.6 файла 02). Видимый текст «Удалить» должен входить в имя (2.5.3).
- Иконки-кнопки в строке: размер и зазор по 2.5.8 — иконка 20 px в кнопке 32×32 с зазором 4 px проходит; три иконки
  20 px вплотную — нет (§12.4 файла 01).
- Действия, спрятанные под hover, — провал: они недоступны с клавиатуры и на тач. Правильно: показывать всегда
  либо раскрывать по кнопке «Ещё» (`aria-haspopup="menu"`).
- Меню действий строки — паттерн menu button; Esc возвращает фокус на кнопку.

### 2.4 Сортировка

**Разметка** [S9]: `aria-sort` **на `<th>`**, значения `ascending` / `descending` / `none` / `other`.
Практика автора: **у несортированных колонок атрибут убирать, а не ставить `none`; больше одной колонки с
`aria-sort` быть не должно**. Заголовок-кнопка внутри `<th>`, а не `onclick` на `<th>`.

**Объявляется ли факт сортировки** (проверка августа 2024) [S9]:

| Пара | Объявляет |
|---|---|
| NVDA + Firefox | да |
| JAWS + Chrome | да |
| Narrator + Edge | да |
| VoiceOver + Safari (iPadOS) | да |
| **VoiceOver + Safari (macOS)** | **нет** |
| **TalkBack + Chrome / Firefox** | **нет** |

Отсюда: нужна **живая область** с текстом вроде «Отсортировано по возрастанию», которая **очищается через ~1 секунду**
— иначе повторная сортировка в ту же сторону не даст изменения текста и не будет объявлена [S9]. Текст области брать
из системы локализации: строка, зашитая в JS, не переводится автопереводчиками [S9]. `[исследование]`

**Направление кодировать формой, а не цветом** (1.4.1): полые шевроны → залитый треугольник [S9].

**В длинных таблицах подсвечивать саму колонку** (через `<col>`; поддержка Chrome/Edge 91+, Firefox, Safari 14+),
иначе при прокрутке заголовков не видно, что отсортировано [S9].

**Как сообщить, что колонка вообще сортируема.** У несортированных колонок `aria-sort` нет, значит подсказки нет.
Пять протестированных приёмов [S9]: подсказка в `<caption>` (проще всего, звучит один раз при входе в таблицу);
скрытая часть `<caption>` + `aria-describedby`; `aria-describedby` на кнопку; `aria-labelledby`;
`aria-roledescription`. Универсального решения нет — «no one ideal way to handle this». **Рекомендация базы:**
подсказка в `<caption>` как дефолт (дёшево, звучит один раз, видна всем).

### 2.5 Выбор строк и массовые действия

`[практика]`, свод:
- чекбокс строки — нативный `<input type="checkbox">` с именем, включающим объект: «Выбрать заказ 12045»;
- чекбокс «выбрать все» — `aria-checked="mixed"` при частичном выборе (или `indeterminate` у нативного);
- число выбранных объявляется **polite**-областью: «Выбрано 12 заказов»;
- панель массовых действий, появляющаяся при выборе, — **не** забирает фокус; её появление объявляется тем же
  сообщением;
- в гриде **Shift+Space выделяет строку** и служит шорткатом к чекбоксу, когда фокус не на нём (§8.2 файла 02);
- массовое деструктивное действие подтверждается с **точным числом и перечислением первых нескольких имён**
  (`../01-foundations/01-principles-and-laws.md` §14.3).

### 2.6 Широкие таблицы и адаптив

**Прокрутка в контейнере** — минимальное решение, закрывающее четыре критерия сразу [S8]:

```html
<div role="region" aria-labelledby="cap1" tabindex="0">
  <table><caption id="cap1">Заказы за март</caption>…</table>
</div>
```
```css
[role="region"][aria-labelledby][tabindex] { overflow: auto; }
[role="region"][aria-labelledby][tabindex]:focus { outline: .1em solid …; } /* контраст 3:1 */
```

1.4.10 Reflow прямо исключает таблицы данных из требования «без прокрутки в двух измерениях», так что
горизонтальная прокрутка таблицы — законное решение, а не обход.

**Чего не делать** [S8]:
- **не переверстывать таблицу через CSS `display`** (`display: block` на строках и ячейках): «some browsers break the
  semantics and a screen reader user will be stranded (yes, even at the end of 2020 this is still true)»;
- ARIA не покрывает всё: **аналога HTML-атрибута `headers` в ARIA нет**, поэтому таблицы с объединёнными ячейками
  после переверстки чинить нечем;
- CSS scroll snap автор сознательно не применяет: в тестах пользователи хотели «оседлать» границу ячеек для
  сравнения, и при зуме и увеличении текста это ломается.

**Карточки вместо таблицы на узком экране** — допустимо, если это **другая разметка**, а не переверстанная таблица:
список `<ul>` с элементами, где каждое поле — пара «подпись: значение». Тогда семантика честная. Но теряется
сравнение по колонкам; решение о переходе — у агентов D1 и F1 (`../04-components-patterns/`, `../09-mobile/`).
`[консенсус]`

### 2.7 Виртуализация

При виртуальной прокрутке в DOM только видимые строки. Требования `[практика]`:
- `aria-rowcount` на таблице/гриде и `aria-rowindex` на строках — чтобы AT знала реальный размер набора;
- то же для колонок при горизонтальной виртуализации (`aria-colcount`, `aria-colindex`);
- фокусируемый элемент не удалять из DOM (буфер над и под видимой областью), иначе фокус падает на `body`;
- при переходе Ctrl+End учитывать, что «key events that move focus to the beginning or end of the grid… may move
  focus to the last row **in the DOM** rather than the last available row in the back-end data» [S10];
- объявлять позицию при прыжках: «Строка 240 из 1500».

## 3. Живые области и объявления

### 3.1 Лестница решений: живая область — последняя

Порядок выбора `[консенсус]` по [S11], [S12]:

| Ступень | Инструмент | Когда |
|---|---|---|
| 1 | **Состояние ARIA** | Изменение — это состояние элемента: раскрытие (`aria-expanded`), тумблер (`aria-pressed`), выбор (`aria-selected`), сортировка (`aria-sort`). **Живая область не нужна** |
| 2 | **Предупреждающая подсказка заранее** | Пользователь знает, что произойдёт, до того как нажмёт: «Изменение фильтров меняет список», «Результаты появляются по мере ввода» |
| 3 | **Перевод фокуса** | Появилось что-то, с чем надо работать: диалог, панель, заголовок результатов, новый шаг мастера |
| 4 | **Живая область** | Короткое сообщение без интерактива, которое нельзя передать иначе: «Сохранено», «Найдено 12», «Ошибка сети» |

Цитата, задающая тон [S11]: «if you can create an interface that can limit the number of live regions necessary —
**none being the ideal** — then that'd be for the better» (Scott O'Hara).

**Почему так строго.** Свойства живых областей — «only **strong suggestions** as to how you want live region
announcements to be made», их может переопределить браузер, AT или пользователь; объявления **транзитны**:
«Once an announcement is made, it disappears forever… If the user misses an announcement, they miss it» [S11].

### 3.2 Инструменты

| Способ | Неявные значения | Поддержка |
|---|---|---|
| `aria-live="polite"` | — | хорошая |
| `aria-live="assertive"` | — | хорошая |
| `role="status"` | polite + `aria-atomic="true"` | **хорошая** |
| `role="alert"` | assertive + `aria-atomic="true"` | **хорошая** |
| `role="log"` | polite | специализированная, слабее |
| `role="marquee"` | off | плохая, кандидат на удаление из спецификации |
| `role="timer"` | off | плохая, кандидат на удаление |
| `<output>` | нативно `role="status"`, принимает `<label>` | хорошая |

**Разница между `aria-live` и ролью** [S11]: роль добавляет **семантику** («это alert»), некоторые скринридеры
произносят слово «Alert» перед текстом; **роль принимает доступное имя**, а `<div aria-live>` — нет. Имя области
полезно, когда областей несколько: «Корзина, 5 товаров» вместо просто «5».

Максимальная совместимость — ставить оба: `<div role="status" aria-live="polite">` [S12].

**Конфигурация, на которую нельзя полагаться** [S11]: `aria-relevant` (по умолчанию `additions text`),
`aria-atomic` (по умолчанию `false`), `aria-busy` — «support… is currently inconsistent across browsers and screen
reader pairings».

**Когда `assertive`:** ошибка отправки формы, истечение сессии, предупреждение безопасности, **пустой результат
поиска**. Всё остальное — `polite`.

### 3.3 Чего живая область не умеет

1. **Не передаёт разметку.** «The screen reader will announce the entire contents of a live region as **one long
   string of text, without any of the structure**». Кнопка внутри объявляется как текст, без роли [S11].
2. **Фокус в неё не переходит**, и попасть в неё нечем — нет механизма навигации к живой области.
3. Отсюда: **уведомление с действием не может быть живой областью и не может быть тостом**. Спецификация ARIA:
   «authors SHOULD NOT require users to close an alert. If an author desires focus to move to a message…, the author
   SHOULD use **`alertdialog`** instead of alert» [S11].

| Тип уведомления | Правильный инструмент |
|---|---|
| «Сохранено», «Найдено 12» | `role="status"` |
| «Ошибка сети», «Сессия истекает» | `role="alert"` |
| «Удалено. **Отменить**» | Живая область объявляет факт; кнопка «Отменить» **должна быть достижима**: либо постоянный элемент в интерфейсе, либо `alertdialog` с переводом фокуса, либо шорткат Ctrl+Z с подсказкой |
| «Требуется подтверждение» с кнопками | `alertdialog` с переводом фокуса |

### 3.4 Шесть практик реализации

Из [S11], проверенный свод:

1. **Контейнер живой области — в DOM с загрузки страницы**, до первого обновления. «If you insert a live region into
   the DOM or convert a container into a live region *when you need it*, there's a high chance that it won't work».
2. **Скрывать только визуально скрытым классом.** Не `display:none`, не `aria-hidden` — «Hidden live regions are not
   announced». Чтобы пустой контейнер не занимал места: `[aria-live]:not(:empty) { … }`.
3. **Держать ровно две области: одну `assertive` и одну `polite`**, и вести очередь сообщений самому. Спецификация:
   «Items which are assertive will be presented immediately, followed by polite items. User agents… MAY choose to
   clear queued changes when an assertive change occurs» — то есть лишние области съедают сообщения друг друга.
4. **Собирать сообщение целиком и вставлять одной операцией** — иначе несколько отдельных объявлений.
5. **Короткий текст без разметки, картинок и интерактива.**
6. **Очищать область через 350–500 мс** между обновлениями — иначе повторное одинаковое сообщение не вызовет
   изменения и не будет объявлено.

**Отладка:** расширение **NerdeRegion** (вкладка в DevTools, список живых областей и лог мутаций с таймкодами) [S11].

**Ещё одно правило из Inclusive Components** [S12]: **глушить живые области в скрытых вкладках браузера** —
иначе пользователь слышит объявления со страницы, которую не видит. Реализация: слушать `visibilitychange` и
переключать `role`/`aria-live` между `status`/`polite` и `none`/`off`.

### 3.5 Что объявлять в веб-приложении

| Событие | Область | Текст |
|---|---|---|
| Сохранение | polite | «Сохранено» / «Черновик сохранён в 14:32» |
| Ошибка сохранения | assertive | «Не удалось сохранить: нет связи. Попробуйте ещё раз» |
| Применён фильтр | polite | «Найдено 12 заказов» — **и подсказка заранее**, см. ниже |
| Пустой результат | **assertive** | «Ничего не найдено» |
| Строка удалена | polite | «Заказ 12045 удалён» |
| Массовое действие завершено | polite | «Обновлено 12 заказов» |
| Выбрано N строк | polite | «Выбрано 12 заказов» |
| Загрузка начата / завершена | polite | «Загрузка…» / «Загружено 45 заказов» |
| Прогресс длинной операции | polite, **с интервалом**, а не на каждый процент | «25 процентов» каждые 25 % |
| Сессия истекает | assertive | «Сессия завершится через 2 минуты» |
| Добавлено в корзину | polite (или перевод фокуса на панель корзины) | «Товар добавлен. В корзине 3 товара» |
| Сортировка применена | polite, очищается через 1 с | «Отсортировано по дате, по убыванию» |

**Фильтры и поиск: подсказка вместо потока объявлений** [S11]. Не делать контейнер результатов живой областью —
иначе «very noisy user experience». Вместо этого:
- у группы фильтров — постоянная подсказка «Изменение фильтров меняет список ниже» (так сделан сам сайт
  WCAG Quick Reference);
- у поля поиска — `aria-describedby` «Результаты появляются по мере ввода» (так сделан a11ysupport.io);
- **итоговое число объявлять polite-областью**, отдельно от списка;
- **пустой результат — assertive**: «let someone know immediately when they have entered a query that returns no
  results… People who can see the UI are likely going to notice right away when the dynamic content dries up»
  (Scott O'Hara) [S11];
- по Enter — **перевести фокус на заголовок результатов**; Esc возвращает фокус в поле.

**Связь со слепотой к изменениям.** Изменения, которых не видно, — это не только проблема скринридеров: слепота к
изменениям срабатывает при прерывании восприятия всего в **67 мс**, и наиболее уязвимы именно сообщения об ошибках,
статусы после отправки и **результаты после применения фильтра**
(`../01-foundations/01-principles-and-laws.md` §11.5). Отсюда парное правило `[исследование]`:
**новый элемент ставится близко к точке, куда пользователь уже смотрит, и подаётся достаточно контрастно** — то есть
визуальное уведомление и живая область решают одну задачу для разных людей и проектируются вместе.

### 3.6 `aria-busy` и загрузка

`aria-busy="true"` должен говорить AT «подожди, здесь идут изменения». На практике **поддерживается плохо**:
«most screen readers (except JAWS) will read the contents of the busy region even before it's done loading» [S11].

Рабочая замена:

```html
<div aria-live="polite" class="visually-hidden">Загрузка…</div>
<section aria-hidden="true"><!-- скелетон --></section>
```
после загрузки:
```html
<div aria-live="polite" class="visually-hidden">Загружено 45 заказов</div>
<section><!-- контент --></section>
```

То есть живая область работает как **текстовая альтернатива скелетона**.

## 4. Модальные и немодальные оверлеи

### 4.1 Модальный диалог

**Разметка** [S10]:
```html
<dialog aria-labelledby="dlg-title">
  <h2 id="dlg-title">Удалить заказ?</h2>
  …
  <button>Отмена</button><button>Удалить</button>
</dialog>
```
Нативный `<dialog>` + `showModal()` даёт бесплатно: захват фокуса, Esc, инертность фона, `::backdrop`, возврат
фокуса на триггер. Это реализация первого правила ARIA.

Если диалог собирается вручную: `role="dialog"` + `aria-modal="true"` + имя через `aria-labelledby` + `inert` на
остальной странице + собственная реализация кольца Tab и Esc.

**Поведение** — полный контракт в `02-keyboard-focus-semantics.md` §10.2. Ключевое:
- фокус внутрь при открытии, выбор точки зависит от содержимого;
- **если это последний шаг необратимого действия — фокус на наименее разрушительное действие**;
- Esc закрывает; в форме с несохранёнными данными Esc спрашивает подтверждение, а не теряет ввод;
- при закрытии фокус на триггер, кроме двух названных исключений;
- в tab-последовательности диалога должна быть **видимая кнопка закрытия**.

**Чего не делать:**
- вложенные модалки (вторая поверх первой) — пользователь теряется, а кольцо фокуса ломается;
- модалка для длинной формы — лучше отдельная страница
  (`../03-layout-placement/01-page-anatomy-templates.md`: «Resist the temptation to use modals and wizards on
  complex apps… context is king»);
- **обёртывать содержимое модалки в лендмарк** — бессмысленно (§4.2 файла 02);
- прокрутка фона под открытой модалкой.

### 4.2 Alert-диалог

`role="alertdialog"` — диалог, содержащий срочное сообщение. Ведёт себя как модальный диалог, но сообщение читается
сразу. Применять там, где уведомление требует действия: «Сессия истекает. Продлить?», «Не удалось сохранить.
Повторить?».

### 4.3 Немодальные панели

Инспектор, фильтры, чат, панель уведомлений:
- фокус **не** захватывается (пользователь может уйти в основной контент);
- Esc закрывает, фокус возвращается на триггер;
- панель стоит в DOM сразу после триггера, либо фокус переводится явно при открытии;
- **если панель может перекрыть фокусируемый контент — это риск 2.4.11**, и нужен один из пяти безопасных способов
  раскрытия (`01-wcag22-as-build-rules.md` §12.1): сдвиг контента, reflow основной области, удержание кольца до
  закрытия, открытие в пустое поле, автоскрытие при уходе фокуса.

**Тонкость из Understanding 2.4.11** [S13]: вариант «раскрытие удерживает кольцо табуляции до закрытия» создаёт
неравенство между клавиатурой и мышью (мышью можно работать с фоном, клавиатурой нет) — «should be used cautiously».

### 4.4 Поповеры, меню, комбобоксы

Непостоянные раскрытия (меню, список комбобокса, календарь, тултип) под 2.4.11 не подпадают, **если закрываются при
уходе фокуса** [S13]. Значит правило: **любое всплывающее, кроме диалога и панели, закрывается при потере фокуса и
по Esc**.

Требования 1.4.13 (Dismissible / Hoverable / Persistent) — `01-wcag22-as-build-rules.md` §10.3.

## 5. Уведомления, бейджи, перетаскивание

### 5.1 Тосты

Правила `[консенсус]` по [S11], [S12]:
- `role="status"` (polite); `role="alert"` только для ошибок;
- **без интерактивных элементов** (§3.3);
- **не исчезает быстрее, чем можно прочитать**: минимум 5 секунд для короткого текста, пауза при наведении и при
  фокусе внутри страницы; критичное не исчезает само;
- **важное дублируется в постоянном месте** (центр уведомлений, статус объекта, история действий) — «Once an
  announcement is made, it disappears forever» [S11];
- одновременно не больше одного-двух тостов; очередь, а не стопка;
- тост не перекрывает фокусируемый контент (2.4.11) — ставить в поле страницы или делать так, чтобы контент
  подвинулся.

**Отмена действия.** Паттерн «Удалено. Отменить» конфликтует с правилом «без интерактива в живой области». Варианты
`[практика]`: кнопка «Отменить» в постоянной панели действий; Ctrl+Z с подсказкой, показанной в тосте текстом;
`alertdialog` для дорогих операций. Допустимый тост с действием — при трёх условиях (не исчезает сам или ≥ 10 с с
продлением при наведении и фокусе; действие продублировано в постоянном месте; фокус не захватывается) —
`../04-components-patterns/08-notifications-toasts-banners.md` §3.4.

### 5.2 Бейджи и счётчики

- Счётчик — **часть доступного имени кнопки**, а не отдельный узел: `aria-labelledby="count label"` даёт
  «3 Уведомления» [S12].
- Изменение счётчика объявлять **не надо** на каждый чих: это шум. Объявлять только по явному действию пользователя.
- Точка-индикатор без числа («есть непрочитанное») — добавить визуально скрытый текст «Есть непрочитанные».
- Цветной бейдж статуса — текст внутри, а не только цвет (1.4.1).

### 5.3 Drag-and-drop

**Три независимых требования:**

| Требование | Критерий | Что делать |
|---|---|---|
| Работает с клавиатуры | 2.1.1 (A) | Выбрать элемент (Space), перемещать стрелками, подтвердить (Space), отменить (Esc); объявлять позицию живой областью |
| Работает **одним указателем без перетаскивания** | 2.5.7 (AA) | **Кнопки «вверх»/«вниз»** у элемента; или «выбрать → меню „переместить в…“»; или поле ввода позиции |
| Цели достаточного размера | 2.5.8 (AA) | Ручка перетаскивания ≥ 24×24, лучше 44×44 |

**Ключевое:** клавиатурная реализация **не закрывает** 2.5.7 — «unless that equivalent keyboard operation also
provides controls that can be clicked or tapped with a pointer» [S14]. Нужны именно кликабельные контролы.

Готовые альтернативы для типовых случаев — `01-wcag22-as-build-rules.md` §12.3 (канбан, список, слайдер, карусель,
загрузка файлов, выделение области).

**Объявления при клавиатурном перетаскивании** `[практика]`: «Заказ 12045 взят, позиция 3 из 20» → «Позиция 2 из 20»
→ «Заказ 12045 перемещён в колонку „В работе“, позиция 2».

## 6. Бесконечная прокрутка и «показать ещё»

**Проблема для клавиатуры и AT:** при бесконечной прокрутке подвал недостижим (каждое приближение к нему подгружает
новую порцию), позиция в наборе неизвестна, вернуться к найденному элементу после перехода и возврата невозможно.

**Порядок предпочтения** `[консенсус]`:

| Вариант | Когда | Требования |
|---|---|---|
| **Пагинация** | Таблицы, результаты поиска, всё, куда возвращаются | `<nav aria-label="Пагинация">`, `aria-current="page"`, объявление «Страница 3 из 12, показаны заказы 41–60» |
| **Кнопка «Показать ещё»** | Ленты, карточки | Фокус остаётся на кнопке; число добавленных объявляется polite; когда всё загружено — кнопка исчезает, фокус на первый добавленный элемент |
| **Бесконечная прокрутка** | Только ленты без подвала и без необходимости возврата | Обязательно: `role="feed"` с `aria-busy` на время подгрузки, `aria-posinset`/`aria-setsize` на статьях, клавиши PageUp/PageDown между статьями, **дублирование ссылок подвала в шапке или сайдбаре** |

`role="feed"` — единственный паттерн APG для бесконечных лент: PageDown/PageUp — следующая/предыдущая статья;
Ctrl+End — первый фокусируемый элемент **после** ленты; Ctrl+Home — первый **перед** ней. APG предупреждает:
«Due to the lack of convention, providing easily discoverable keyboard interface documentation is especially
important» [S10].

Продуктовые аргументы за и против бесконечной прокрутки — у агента D1 (`../04-components-patterns/`).

## 7. Графики, дашборды, визуализация

Требования `[консенсус]`:

1. **Текстовое резюме** — вывод, а не описание формы: «Продажи выросли на 12 % за квартал, спад в феврале».
   Резюме видимо всем (оно полезно всем), либо связано через `aria-describedby`.
2. **Таблица-эквивалент** с теми же данными: видимая по кнопке «Показать таблицу» либо визуально скрытая. Кнопка
   переключения «график / таблица» получает явное имя: «Показать таблицу», «Показать график»
   [V:2juq00vrvl0, 38:56].
3. **Контейнер графика** — `role="img"` с `aria-label`, если внутри SVG нет доступной структуры; тогда внутренности
   `aria-hidden`.
4. **Цвет не единственный носитель** (1.4.1): прямые подписи у линий, разные маркеры, штриховка.
5. **Значимая графика — 3:1 к соседним цветам** (1.4.11): линии, точки, границы секторов.
6. **Интерактив графика доступен с клавиатуры**: если есть tooltip по наведению — есть и по фокусу; если есть
   зум перетаскиванием — есть кнопки (2.5.7).
7. **Легенда — текст**, а не только цветные квадраты; клик по легенде (скрыть серию) — кнопка с `aria-pressed`.
8. **Обновление живого дашборда** — не объявлять каждое изменение; дать кнопку паузы автообновления (2.2.2) и
   настройку частоты.

Дашборд как продуктовая тема — у агента D1; визуальные правила графиков — `../../ui/`.

## 8. Загрузка, скелетоны, оптимистичный UI

| Состояние | Что делать |
|---|---|
| Скелетон известной структуры | Загружающаяся секция `aria-hidden="true"`; отдельная visually-hidden polite-область «Загрузка…», затем «Загружено N» (§3.6) |
| Спиннер неизвестной длительности | То же; сам спиннер `aria-hidden`, текст в живой области |
| Прогресс с процентом | `<progress>` или `role="progressbar"` с `aria-valuenow`; объявлять **с шагом** (каждые 25 %), а не на каждый процент |
| Блокирующая загрузка | Фон `inert`; фокус на контейнер загрузки; по завершении — фокус туда, где работа продолжается |
| Оптимистичный UI (изменение показано до ответа сервера) | Объявлять **итог**, а не намерение; при откате — `assertive`: «Не удалось сохранить, изменения отменены» |
| Ленивая подгрузка изображений | `alt` присутствует с самого начала; не подставлять `alt` после загрузки |

Пороги времени отклика (0,1 / 1 / 10 с) и выбор индикатора — `../01-foundations/01-principles-and-laws.md` §12 и
`../06-feedback-states-motion/` (волна 2).

## Чек-лист

Формы:
- [ ] У каждого поля видимая подпись через `<label for>`?
- [ ] Общие инструкции стоят перед `<form>`?
- [ ] Подсказки формата связаны через `aria-describedby`?
- [ ] Радиогруппы и группы чекбоксов в `fieldset` с `legend`?
- [ ] Поля о пользователе имеют `autocomplete`?
- [ ] Обязательность помечена программно и объяснена до формы?
- [ ] При ошибке: сводка вверху с `role="alert"`, фокус на неё, ссылки на поля, «Ошибка:» в `<title>`?
- [ ] Формулировки в сводке и у полей совпадают дословно?
- [ ] Введённые данные сохраняются после ошибки?
- [ ] Сообщение об ошибке называет поле, проблему и способ исправления?
- [ ] Ошибка снимается сразу после исправления?
- [ ] Валидация принимает разные форматы и игнорирует лишние символы?
- [ ] Вставка в поля пароля и кода разрешена, код вводится одним полем?
- [ ] Капчи нет либо есть альтернатива без когнитивного теста?
- [ ] Кастомные контролы имеют полный клавиатурный контракт, а нативные не заменены без причины?

Таблицы:
- [ ] `<table>` + `<th scope>` + `<caption>`?
- [ ] Заголовочные ячейки со `scope` даже в простой таблице?
- [ ] Действия строки имеют уникальные имена с объектом?
- [ ] Действия строки видны без наведения?
- [ ] `aria-sort` только на одной колонке, у остальных убран?
- [ ] Факт сортировки объявляется живой областью, очищаемой через ~1 с?
- [ ] Направление сортировки кодируется формой, а не цветом?
- [ ] Широкая таблица в контейнере `role="region"` + `aria-labelledby` + `tabindex="0"` с `overflow:auto`?
- [ ] Чекбоксы строк подписаны объектом; «выбрать все» имеет состояние «частично»?
- [ ] При виртуализации выставлены `aria-rowcount`/`aria-rowindex`?

Динамика:
- [ ] Каждое изменение сначала проверено на возможность обойтись состоянием ARIA или подсказкой заранее?
- [ ] На странице ровно две живые области, обе в DOM с загрузки?
- [ ] Живые области скрыты визуально скрытым классом, а не `display:none`?
- [ ] Сообщения короткие, без разметки и интерактива?
- [ ] Область очищается между обновлениями?
- [ ] Пустой результат объявляется `assertive`?
- [ ] У фильтров и поиска есть постоянная подсказка о том, что изменится?
- [ ] Живые области глушатся в скрытых вкладках?

Оверлеи и уведомления:
- [ ] Модалка: имя, `aria-modal`, фокус внутрь, Esc, инертный фон, возврат фокуса, видимая кнопка закрытия?
- [ ] Немодальная панель не перекрывает фокусируемый контент?
- [ ] Всплывающие закрываются по Esc и при уходе фокуса?
- [ ] Тост без интерактива, живёт достаточно долго, важное продублировано в постоянном месте?
- [ ] Счётчик входит в доступное имя кнопки?

Прочее:
- [ ] У каждого перетаскивания есть и клавиатурная, и указательная альтернатива?
- [ ] Вместо бесконечной прокрутки — пагинация или «Показать ещё», либо подвал продублирован?
- [ ] У каждого графика есть текстовое резюме и таблица-эквивалент?
- [ ] Скелетоны скрыты от AT, а состояние объявлено текстом?

## Открытые вопросы и противоречия

1. **Инлайн-валидация (§1.7).** GOV.UK запрещает валидацию на blur, W3C WAI показывает её как приём. Ни одна сторона
   не приводит эксперимента. Кандидаты на проверку: Adam Silver «Form Design Patterns» (глава о валидации),
   исследования Baymard по чекауту (сайт не отдаёт текст ни одному HTTP-клиенту — нужен агент с браузером),
   внутренние исследования GOV.UK, о которых они пишут «we'd like to hear from teams».
2. **`required` и `novalidate` (§1.7).** GOV.UK советует не ставить `required` — это расходится с практикой и с
   ожиданиями AT. Помечено `[система]`. GOV.UK сам просит исследований.
3. **Полный запрет плейсхолдеров.** Позиция «я не вижу случая, где плейсхолдер не был бы проблемой»
   [V:2juq00vrvl0, 52:19] сильнее, чем позиция W3C («не замена подписи»). В базе принята мягкая формулировка;
   расхождение зафиксировано как `[спорно]`.
4. **Карточки вместо таблицы на узком экране (§2.6).** Розелли тестировал и утверждает, что вариант с горизонтальной
   прокруткой «performs better for all users», чем переверстка; но это один источник и один тест без опубликованной
   методики. Продуктовое решение остаётся за D1 и F1.
5. **Тост с действием (§5.1).** Material Design документирует тосты с интерактивом; Розелли перечисляет, какие
   критерии WCAG они нарушают; Soueidan и O'Hara рекомендуют `alertdialog`. Прямого замера потерь нет.
   Статья Розелли о тостах в этом ресёрче **не открывалась** — ссылка идёт через пересказ [S11], помечено.
6. **`aria-busy` (§3.6).** Sara Soueidan пишет, что поддерживает только JAWS; отдельной матрицы поддержки по парам
   «браузер + AT» я не нашёл. Обходной путь через `aria-hidden` — `[практика]`, не измерено.
7. **Виртуализация (§2.7).** Ни APG, ни W3C не дают паттерна. Правила выведены из общих требований. Кандидаты:
   документация AG Grid и TanStack Virtual по доступности, тесты `aria-rowcount` в NVDA и JAWS.
8. **Матрица объявления сортировки (§2.4) датирована августом 2024.** Поведение скринридеров меняется; при
   использовании стоит перепроверить на актуальных версиях.
9. **Расхождений с файлами волны 1 не найдено.** Правила дополняют
   `../03-layout-placement/04-placement-conventions-and-redundancy.md` (тост и модалка об одном событии — нельзя;
   подпись и плейсхолдер не повторяют друг друга) и `../01-foundations/01-principles-and-laws.md` §14
   (предотвращение → восстановление → сообщение).
