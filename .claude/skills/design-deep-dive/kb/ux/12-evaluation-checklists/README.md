# 12 — Оценка: протоколы, сводный чек-лист, автопроверки, метрики

Папка отвечает на вопрос «как проверить, что интерфейс хороший» тремя способами: силами агента без
пользователей, автоматикой и с людьми. Собрана агентом I (волна 3) из чек-листов и наборов автопроверок
всех остальных папок базы плюс собственный ресёрч по протоколам и метрикам.

## Выжимка папки

1. **Автопроверки — ворота, а не оценка.** «Пройдено» и «хорошо» — разные вещи; полный цикл проверок
   удваивает функциональное качество, но 42–48 % требований остаются невыполненными. `[исследование]`
2. **Один проход находит 42 % крупных и 32 % мелких проблем** (Nielsen 1992). Отсюда 3–5 независимых
   проходов; для агента — 3–5 линз, каждая отдельной сессией без результата предыдущих. `[исследование]`
3. **Список находок доминируется мелочью** (59 крупных против 152 мелких на шести интерфейсах), поэтому
   шкала серьёзности 0–4 обязательна, и собирается она отдельным прогоном: оценка одного оценщика
   ненадёжна, среднее трёх достаточно. `[исследование]`
4. **Порядок проверки — по частоте поломки и стоимости проверки.** WebAIM Million 2026: шесть типов ошибок
   дают 96 % всех нарушений (контраст 83,9 % страниц, alt 53,1 %, подписи полей 51 %, пустые ссылки 46,3 %,
   пустые кнопки 30,6 %, `lang` 13,5 %); 95,9 % страниц имеют обнаруживаемые нарушения WCAG. `[исследование]`
5. **Сценарный прогон даёт в 4–5 раз больше точности, чем критика скриншота** (+3,3 против +0,7), но роняет
   внешний вид; конфликт снимается откатом при пяти подряд ошибках и выбором лучшего шага. `[исследование]`
6. **Отбор лучшего из k по метрике безопаснее починки**: он не может внести новый дефект. Best-of-8 по axe:
   IR 0,40 → 0,14, Critical 47 → 12; починка промтом снижает IR, но добавляет Minor и Moderate.
   `[исследование]`
7. **LLM-ревью чинит обратную связь и сканируемость и почти не чинит сценарий и ясность цели экрана**
   (Feedback +0,44, Flow максимум +0,12 из 5). Сценарий задаётся во входном контракте, а не правится ревью.
   `[исследование]`
8. **Один прогон судьи — не измерение**: 13,6 % переворотов при идентичном повторе, 11 прогонов для
   устойчивого вердикта, перестановка позиций обязательна, перефразировка рубрики меняет итог в 25 % случаев.
   `[исследование]`
9. **PURE — единственный экспертный протокол, дающий сравнимое число без пользователей**: 1–3 на шаг,
   сумма по задаче, цвет по худшему шагу; корреляция с SEQ 0,5 и SUS 0,4. `[исследование]`
10. **Размеры выборок**: 5 для качественного теста (3 — для регулярных дешёвых раундов, обоснование другое),
    20 для количественного, 15 на группу для карточной сортировки, 39 для айтрекинга, 20–30 для опросников.
    Погрешность при 20 участниках ±19 %. `[исследование]`
11. **Критерий валидности проверки**: прогон, вернувший ноль находок, — неудавшийся прогон, а не чистый
    интерфейс. `[мнение]` Нильсена, подкреплено данными WebAIM.
12. **Правило «стоп»**: если после k вариантов ни один не прошёл ворота, проблема во входном контракте,
    а не в генерации; в файле 03 есть таблица «что массово провалилось → какой пункт контракта пропущен».
    `[исследование]`

## Незакрытое

- Раздел **CNS (консистентность и дизайн-система)** сводного чек-листа неполон: папка
  `../10-design-systems-consistency/` пуста (агент H волны 3 ещё пишет), а обязательные пункты готовых
  плейбуков `../13-app-types/01–04` в чек-лист не перенесены — после сдачи H появится блок «по типу
  приложения». Разделы TXT и MOB собраны по готовым файлам агентов G и F1.
- **Эффективность ручного протокола доступности не измерена** — пробел F2 закрыт частично: найдены числа
  для эвристической оценки вообще и для автоматики, но не для шести ручных проходов.
- **Корреляция пунктов чек-листа с результатом теста с людьми нигде не измерена** — главный кандидат
  на собственный эксперимент.
