# Метрики и тестирование с пользователями

Google Research, web.dev) плюс 8 дайджестов видео и файлы базы

Что измерять, какой метрикой, на какой выборке и с какой погрешностью. Чего метрики не показывают. Быстрые
методы, которые дают ответ за час. Протокол теста, пригодный к буквальному исполнению. Что из этого может
сделать агент, а что — только живые люди. Что агент-генератор обязан подготовить, чтобы тест с людьми вообще
стал возможен.

`03-automated-checks.md`.

## Выжимка для агента

1. **Числа и инсайты конфликтуют.** Лучший метод для улучшения дизайна (частые малые качественные тесты) —
   худший для получения статистики, и наоборот. Выбирать по цели, а не брать всё сразу. → §1.1, `[консенсус]`
2. **5 пользователей** для качественного теста; **20** — минимум для количественного; **15 на группу** для
   карточной сортировки; **39** для устойчивых тепловых карт айтрекинга. → §5, `[исследование]`
3. **Три теста по 5 лучше одного на 15.** Формула Нильсена–Ландауэра: найдено = N(1 − (1 − L)ⁿ), типичное
   L = 31 %. → §5.1, `[исследование]`
4. **Krug настаивает на трёх участниках**, и это не спор о факте: его основание — ёмкость команды по починке,
   а не доля находок. → §5.2, `[спорно]`, разрешено условием
5. **Погрешность количественных метрик велика**: SD времени задачи = 52 % от среднего; при 20 участниках
   доверительный интервал ±19 %; для ±10 % нужно 76 человек — «полная трата денег». → §5.3, `[исследование]`
6. **Успешность задачи — базовая метрика UX**: «если люди не могут выполнить задачу, всё остальное неважно».
   → §2.1, `[консенсус]`
7. **SUS: среднее 68 по 500 исследованиям.** 74 → 70-й процентиль (B−); **80,3 и выше — верхние 10 %**
   и точка, где люди начинают рекомендовать; ниже 51 — нижние 15 %. Балл SUS не процент. → §3.1, `[исследование]`
8. **UMUX-Lite — два утверждения** вместо десяти, корреляция с SUS r = 0,83, пересчёт в SUS с точностью ~99 %
   по опубликованной регрессии. → §3.2, `[исследование]`
9. **SEQ — одна шкала 1–7 сразу после задачи; среднее 5,3–5,6** по 400+ задачам и 10 000 пользователей.
   При оценке ниже 5 спрашивать почему. → §3.3, `[исследование]`
10. **NPS — метрика лояльности, не юзабилити**: сильно зависит от страны (в Японии −47 % даже для любимых
    компаний), легко геймится, не реагирует на локальные правки интерфейса. → §3.5, `[исследование]`
11. **Опросники требуют 20–30 респондентов.** Сообщать средний балл по пяти участникам нельзя. → §3.7,
    `[консенсус]`
12. **AUS (Accessible Usability Scale)** мерит удобство доступного опыта, а не соответствие: 10–12 задач
    своей ассистивной технологией, затем 10 вопросов, балл из 100; средний 65 по 2 100 сессиям. → §3.6,
    `[практика]`
13. **HEART: Happiness, Engagement, Adoption, Retention, Task success**, и процесс Goals → Signals → Metrics.
    Engagement может не иметь смысла в корпоративном контексте. → §4.1, `[исследование]`
14. **Провал опознать легче, чем успех**: бросание задачи, события undo, фрустрация — самые сильные сигналы.
    → §4.1, `[исследование]`
15. **Нормируй счётчики**: «сырые счётчики растут вместе с базой пользователей». → §4.1, `[исследование]`
16. **Дизайн-KPI Фридмана: 30–40 задач-формулировок, целевая планка 80–90 % успешных выполнений по каждой.**
    Единственная найденная процедура, превращающая «дизайн решает задачу» в проверяемое утверждение. → §4.2,
    `[практика]`
17. **Search quality score**: топ-100 запросов за год → от редакции 2–3 эталонных URL на запрос → сверка
    с выдачей; эталонные ссылки обязаны попадать в первую пятёрку. → §4.4, `[практика]`
18. **PURE даёт число без пользователей** и коррелирует с SEQ 0,5 и с SUS 0,4. → §4.3, `[исследование]`
19. **Метрики генеративного качества**: IR = WVS / число DOM-элементов; EXEC@k; NRS; VFS; IIS с весами
    S1/S2/S3. Нормировать на размер артефакта обязательно. → §4.5, `[исследование]`
20. **Core Web Vitals как UX-порог**: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1 по 75-му процентилю. → §6.1,
    `[стандарт]`
21. **Изучай края аудитории, а не среднего пользователя**: самых активных и совсем новичков. → §6.3,
    `[практика]`
22. **Survival-анализ находит ключевое действие**: когорта одного дня, действия первого дня, связь с
    возвращением. Разные горизонты удержания дают разные ключевые действия. → §6.4, `[исследование]`
23. **Чужая метрика не переносится**: +9 % действий у Spotify — успех, у google.com был бы провалом. → §6.5,
    `[мнение]`
24. **Задача формулируется как роль + ситуация + цель, без указания пути** и без слов из интерфейса. → §7.1,
    `[консенсус]`
25. **Тест — наблюдение за попыткой использования с мыслями вслух, а не опрос мнений.** Искать «вопросительные
    знаки над головой». → §7.2, `[практика]`
26. **Не тестировать на дизайнерах**: «designers are the worst — designers often have opinions». → §7.4,
    `[мнение]`
27. **Ритм важнее полноты**: одно утро в месяц в фиксированный день; привязка к датам поставки срывает тест
    навсегда. → §7.5, `[практика]`
28. **Отчёт — письмо на две страницы**, разбор сразу после теста. → §7.6, `[практика]`
29. **Качественное исследование не даёт процентов**: на выборке ~12 «6 из 12» в проценты не переводят. → §7.7,
    `[данные]`
30. **Симуляция пользователей LLM-агентами — отладка исследования, а не замена теста.** → §8, `[исследование]`
31. **Отсутствие жалоб ничего не значит: 67 % пользователей скринридеров никогда или редко сообщают о
    барьере.** → §10.2, `[исследование]`
32. **Удовлетворённость не растёт год к году**, потому что она есть отношение полученного к ожидаемому,
    а ожидания формируются всеми остальными сервисами. Неизменный показатель = команда сработала хорошо.
    → §10.3, `[исследование]`

## 1. Как выбирать метрику

### 1.1 Конфликт чисел и инсайтов

Прямая формулировка NN/g: **«the best usability methodology is the one least suited for generating detailed
numbers»** [S1]. Механизм конфликта:

- лучшие тесты — частые малые, с пятью участниками и мыслями вслух; как только найдена проблема, её чинят
  и тестируют заново;
- малые тесты не дают достаточно узких доверительных интервалов;
- проговаривание вслух удлиняет время задачи и загрязняет метрику времени;
- в качественных тестах между сессиями вносятся правки, поэтому метрики измеряют разные вещи.

Практический вывод: **не пытаться получить числа из качественного теста**. Если нужны числа, ставится
отдельное количественное исследование с другой выборкой и другим протоколом.

### 1.2 Карта метрик

| Что нужно узнать | Метрика | Метод | Выборка |
|---|---|---|---|
| Могут ли люди выполнить задачу | успешность задачи (§2.1) | тест с задачами | 20+ для числа, 5 для инсайтов |
| Сколько это стоит усилий | время задачи (§2.2), SEQ (§3.3) | тест с задачами | 20+ |
| Где именно они спотыкаются | наблюдение, ошибки (§2.3) | качественный тест, 5 человек | 5 |
| Как воспринимается продукт целиком | SUS (§3.1) или UMUX-Lite (§3.2) | опросник после сессии | 20–30 |
| Какая часть интерфейса проблемнее | SEQ после каждой задачи (§3.3) | опросник после задачи | 20–30 |
| Насколько тяжела работа в сложной системе | NASA-TLX (§3.4) | опросник после задачи | 20+ |
| Лояльны ли пользователи | NPS (§3.5) | опрос | сотни |
| Удобен ли доступный опыт | AUS (§3.6) | задачи + анкета на своей AT | 10+ |
| Движется ли продукт к цели | HEART (§4.1) | аналитика + опросы | вся база |
| Решает ли дизайн заявленные задачи | дизайн-KPI, 80–90 % (§4.2) | 30–40 задач | 20+ |
| Насколько трудны фундаментальные задачи | PURE (§4.3) | экспертная оценка | 3 эксперта |
| Работает ли поиск | search quality score (§4.4) | сверка топ-100 запросов | — |
| Насколько хорош сгенерированный интерфейс | IR, EXEC@k, NRS, VFS, IIS (§4.5) | автоматика + разметка | — |
| Не тормозит ли интерфейс | Core Web Vitals (§6.1) | полевые данные | 75-й процентиль |
| Что мешает в реальном использовании | rage clicks, dead clicks, воронки (§6.2) | аналитика | вся база |
| Какое действие удерживает | survival-анализ (§6.4) | когортный анализ | десятки тысяч |
| Понятны ли названия разделов | tree test (§9.2) | немодерируемый тест | 5 для инсайтов, больше для чисел |
| Замечают ли элемент навигации | click test (§9.3) | немодерируемый тест | десятки |
| Что запоминается с первого взгляда | 5-секундный тест (§9.1) | немодерируемый тест | десятки |

### 1.3 Правило комбинации

Ни одна метрика не автономна. Три независимых формулировки одного и того же:

- «Numbers alone don't usually provide the insights needed to understand *why* an effect was observed
  or how to fix a problem» [S2];
- количественные данные показывают факт, качественные — причину и цену: график скорости при падении на
  Тур де Франс фиксирует провал, а фотографии показывают кровь и сорванные пять лет подготовки
  [V:I4UIIISgl2U, 27:48];
- «фетишизм чисел» ведёт к тому, что наблюдение за поведением не считают данными; данные — не только числа
  и не обязаны иметь доверительный интервал [V:yoMq_r-tD-Y, 17:35].

**Уверенность в решении строится из суммы источников**: качественные интервью, лабораторные тесты,
поведенческая аналитика, метрики после запуска. Спор «юзабилити-тест или A/B» бессмыслен — нужно и то,
и другое [V:I4UIIISgl2U, 54:32]. `[консенсус]`

## 2. Поведенческие метрики задачи

### 2.1 Успешность задачи (task success rate)

**Определение**: доля участников, выполнивших задачу. Бинарная и грубая — ничего не говорит о том, почему
провалились и насколько хорошо справились те, кто справился. Но: «if users can't accomplish their target task,
all else is irrelevant. User success is the bottom line of usability» [S1]. `[консенсус]`

**Частичный успех.** Строгая модель — только полный успех засчитывается. Мягкая модель — уровни успеха
с частичным зачётом, в зависимости от масштаба ошибки. Выбор фиксируется до исследования и не меняется,
иначе сравнение версий невалидно [S1].

Аналог в бенчмарках генерации: WebGen-Bench считает Accuracy = (N_Yes + 0,5·N_Partial) / N_Total — то есть
частичный успех с весом 0,5 (`../11-ai-generated-ui/02-research-and-benchmarks.md` §3.3).

**Целевое значение**: универсального нет. Ориентир для дизайн-KPI — **80–90 % успешных выполнений по каждой
из 30–40 задач** (§4.2) `[практика]`.

### 2.2 Время задачи

**Разброс огромен**: анализ 1 520 замеров по 70 задачам на разных сайтах и интранетах дал
**стандартное отклонение = 52 % от среднего** [S3]. То есть при среднем времени 10 минут SD = 5,2 минуты.
`[исследование]`

Следствия:
- время задачи имеет смысл только **в сравнении** — с конкурентом, с прошлой версией, с нормой;
- выбросы (6 % пользователей) при расчёте статистики удаляются, но разбираются качественно: «найдите,
  какое «невезение» (то есть плохой дизайн) утащило их результат вниз» [S3];
- в качественном тесте с мыслями вслух время измерять нельзя: проговаривание его удлиняет [S1].

### 2.3 Ошибки

Число ошибок на задачу, число повторов одной ошибки, доля восстановившихся. Готовый порог из базы:
**три повтора одной ошибки за сессию заполнения** — сигнал, что чинить надо интерфейс, а не текст
(`../05-flows-journeys/04-errors-and-recovery.md`). `[практика]`

Отдельная измеримая величина: **события undo и erase как индикаторы проблем юзабилити** — приём, на который
ссылается работа о HEART (Akers et al., CHI 2009) [S4]. Полный текст не открывал; механизм прямой:
отмена — это след неудачного действия, и её всплеск локализует проблему.

### 2.4 Обучаемость

Разность между первым и n-м прохождением одной задачи одним человеком. Требует лонгитюдного дизайна
(несколько сессий с теми же людьми) и потому редко ставится. Дешёвая замена для агента — когнитивный проход
(`01-expert-review-protocols.md` §4), который оценивает обучаемость экспертно.

## 3. Опросники

### 3.1 SUS (System Usability Scale)

**Что**: 10 утверждений Ликерта, даётся **после сессии целиком** (post-test). Результат — балл 0–100.
Изобретён Джоном Бруком в Digital Equipment Corporation в 1980-х, многократно валидирован [S2].

**Нормы** (Sauro, 500 исследований) [S5]:

| Балл | Процентиль | Оценка |
|---|---|---|
| **68** | 50 | C — среднее |
| 74 | 70 | B− |
| **80,3** | **90** | **A** — верхние 10 %; точка, где люди начинают рекомендовать продукт |
| < 51 | < 15 | F |

**Главная ловушка**: балл SUS **не процент**. 70 из 100 — это не «70 %», а результат чуть выше среднего
(≈ 50-й процентиль). Сообщать стейкхолдерам лучше процентиль, а не сырой балл [S5].

**Условие сравнимости**: порядок и формулировки вопросов не менять, иначе нормы неприменимы [S2].

**Ограничение**: SUS сильно коррелирует с NPS; они дают разные данные, но измеряют пересекающееся [S2].

### 3.2 UMUX-Lite

**Что**: два утверждения на 5- или 7-балльной шкале [S6]:
1. «Возможности [системы] отвечают моим требованиям».
2. «[Системой] легко пользоваться».

Соответствует модели принятия технологии (TAM): полезность + удобство.

**Числа** [S6]: внутренняя надёжность α = **0,86** (у SUS 0,91); корреляция с SUS **r = 0,83**, с NPS
**r = 0,72**. Опубликованная регрессия для пересчёта в SUS:

```
SUS = 0,65 × ((Item1 + Item2 − 2) × (100/12)) + 22,9
```

Точность пересчёта — около **99 %**, подтверждена на двух независимых наборах данных (Lewis et al.,
Borsci et al.). `[исследование]`

**Когда брать вместо SUS**: когда времени в сессии мало или когда измерение удобства встраивается в более
крупный опрос. Открытый вопрос, названный самим автором: насколько можно менять формулировку первого пункта
(«capabilities» → «features» / «functions») без потери валидности.

### 3.3 SEQ (Single Ease Question)

**Что**: одна шкала 1–7 **сразу после каждой задачи**: «Насколько трудной или лёгкой была задача?»
Подписываются только края [S7].

**Числа** [S7]:
- **среднее 5,3–5,6** по 400+ задачам и 10 000 пользователей (историческое среднее обновлено в мае 2019);
- корреляция с временем задачи и успешностью около **r = 0,5** — метрики пересекаются, но не заменяют
  друг друга;
- SEQ работает не хуже более сложных SMEQ и Usability Magnitude Estimation (Sauro & Dumas, CHI 2009);
- **в ~14 % случаев** человек проваливает задачу и при этом оценивает её как очень лёгкую.

**Обязательный довесок**: при оценке ниже 5 просить кратко объяснить, почему было трудно — это даёт
диагностику ровно в тот момент, когда человек ещё помнит причину [S7].

**Ограничение**: людям трудно отделить сложность самой задачи от проблем интерфейса. Лечится сравнением
одной и той же задачи на сопоставимом продукте [S7].

### 3.4 NASA-TLX

Шесть шкал по 21 делению: mental demand, physical demand, time pressure, perceived success, effort,
frustration; плюс взвешивание категорий [S2].

**Когда**: сложные ответственные системы, где ошибка дорога — медицина, авиация, сложные финансовые
процессы; обученные работники, которые не выбирают, каким приложением пользоваться.

**Когда не**: обычные продукты и простые потоки — инструмент тяжёл, требует объяснения после каждой задачи
и ломает естественность сессии [S2].

### 3.5 NPS и его ограничения

**Что**: «Насколько вероятно, что вы порекомендуете … другу или родственнику?», шкала 0–10.
Промоутеры 9–10, пассивные 7–8, детракторы 0–6. NPS = % промоутеров − % детракторов, диапазон −100…+100.
Пассивные входят в знаменатель, но не влияют на числитель. Источник — Reichheld, HBR 2003, опрос
4 000 респондентов [S8].

**Шесть ограничений** [S8]:

1. **Это метрика лояльности, а не юзабилити.**
2. **Сильная зависимость от страны.** Qualtrics XM Institute 2021, 17 509 респондентов, 18 стран: NPS
   «любимых компаний» ≥ 60 % в Индии и Мексике, но **−47 % в Японии и −11 % в Южной Корее** — то есть
   в некоторых культурах даже про любимую компанию отвечают ниже 7. Сравнивать NPS между странами нельзя.
3. **Разрывы между «высоким» и «низким» NPS тоже различаются по странам** (максимум в Бразилии, минимум
   в Японии).
4. **Локальная правка интерфейса не двигает NPS.** Улучшили тексты или иконки — общий показатель останется
   плоским. Нужны метрики уровня задачи.
5. **Метрика легко геймится** (закон Кэмпбелла): выборочный показ опроса только довольным клиентам,
   «rating racketeering» — купон за хорошую оценку, намёк, что от оценки зависит работа сотрудника.
6. **Одна цифра не суммирует опыт.**

**Зачем всё же нужен**: понятен руководству, коррелирует с прибылью, коррелирует с SUS, собирается одним
вопросом [S8]. Позиция базы: включать в набор как контекстную метрику, **никогда не использовать как
метрику качества интерфейса и не сравнивать между странами**. `[консенсус]`

### 3.6 AUS (Accessible Usability Scale)

Метрика **удобства доступного опыта**, а не соответствия стандарту [V:xEtKkLdAnvI, 2:50:26]:

- **10–12 задач** («найди информацию», «импортируй файл»);
- человек выполняет их **своей** ассистивной технологией, и фиксируется, какой именно;
- затем **анкета из 10 вопросов**;
- на выходе балл по шкале **из 100**.

Инструмент Fable Tech Labs; **средний балл 65 по 2 100 сессиям** (проверено агентом W10). Мотивация:
«if something is compliant, doesn't mean that it's actually still usable» — типовой пример — повторы
у скринридера из-за неправильной разметки. `[практика]`

**Когда применять**: после того как формальные ворота доступности пройдены (0 Critical, 0 Serious,
IR ≤ 0,15, `03-automated-checks.md` §5.4) и нужно узнать, удобно ли на самом деле. AUS занимает ту же
позицию относительно WCAG, что SUS относительно функциональных требований.

**Ограничение**: одна коммерческая платформа, одна опубликованная норма; независимой валидации я не нашёл.

### 3.7 Общие правила для всех опросников

- **Все они — самоотчёт**, то есть ненадёжные данные; сочетать с поведенческими метриками обязательно [S2].
- **Требуется 20–30 участников**, чтобы результат обобщался. С пятью участниками средний балл сообщать
  нельзя [S2].
- **Полезный приём при малой выборке**: задать «почему вы поставили X?» и использовать ответ качественно,
  не делая из среднего вывода [S2].
- **Post-test (SUS) подвержен эффекту пика-конца**: итоговое впечатление формируют самый интенсивный момент
  и конец сессии. Post-task (SEQ) этого лишён и потому точнее локализует проблему [S2].
- **Шкала не больше 7 делений** [S2].
- **Брать стандартные опросники, а не свои**: у стандартных есть валидность, надёжность и чувствительность,
  проверенные исследованиями, и нормы для сравнения [S2].

## 4. Рамки и сводные метрики

### 4.1 HEART (Google)

Разработана в Google как ответ на недостатки бизнес-метрик PULSE (Page views, Uptime, Latency, Seven-day
active users, Earnings) [S4]. Проблема PULSE: метрики косвенные и неоднозначные — «рост просмотров функции
может означать и то, что функция популярна, и то, что запутанный интерфейс заставляет людей плутать в ней».
`[исследование]`

| Категория | Что это | Пример метрики | Когда не нужна |
|---|---|---|---|
| **Happiness** | аттитюдное: удовлетворённость, воспринимаемая простота, готовность рекомендовать | еженедельный опрос в продукте | — |
| **Engagement** | частота, интенсивность, глубина взаимодействия | доля активных, заходивших 5+ дней за неделю (пример Gmail) | **в корпоративном контексте**, где пользоваться обязаны; тогда — на уровне отдельной функции |
| **Adoption** | сколько новых начали пользоваться за период | число созданных аккаунтов за 7 дней | у зрелых продуктов стабилизируется |
| **Retention** | сколько из когорты остались | доля 7-дневных активных, остающихся активными через 3 месяца | у зрелых продуктов стабилизируется |
| **Task success** | эффективность, результативность, ошибки | доля выполненных задач, время | — |

**Правило нормировки**: Engagement сообщается **на пользователя**, а не суммарно — иначе рост означает
приток пользователей, а не рост вовлечённости [S4].

**Процесс Goals → Signals → Metrics** [S4]:

1. **Goals.** Что пользователю нужно сделать; чего добивается редизайн. Категории HEART используются как
   подсказки для формулировки («важнее привлечь новых или углубить вовлечённость существующих?»). Разногласия
   в команде о целях — не помеха, а повод довести до консенсуса. На этом шаге не думать, измеримо ли это.
2. **Signals.** Какие действия или ощущения показывают успех или провал. Сигнал должен быть **чувствительным
   и специфичным**: двигаться, когда меняется опыт, и не двигаться от посторонних причин. Важная подсказка
   авторов: **«sometimes failure is easier to identify than success»** — бросание задачи, события undo,
   фрустрация.
3. **Metrics.** Как сигнал превращается в число на дашборде. «Raw counts will go up as your user base grows,
   and need to be normalized» — отношения, проценты, средние.

**Пример разрешающей силы** [S4]: во время обвала рынка в сентябре 2008 у Google Finance выросли и просмотры,
и 7-дневные активные, но по этим числам нельзя было понять, пришли ли новые люди или паникуют старые.
Метрики Adoption и Retention разделили эти группы.

### 4.2 Дизайн-KPI (Фридман)

Единственная найденная процедура, превращающая «дизайн решает задачу» в проверяемое утверждение
[V:2hlQqMigGZg, 04:23]–[09:38]. `[практика]`

**Состав дизайн-KPI.** Ограничения: доля выполненных задач; какие задачи люди вообще делают (топ-задачи);
насколько успешно; сколько времени тратят; как быстро восстанавливаются после ошибок; минимальное воздействие
на среду (контекст госзаказчика; в общий набор переносить как опциональный). Эффекты: снижение числа обращений
в поддержку; ускорение публикации; отсутствие поломок при изменениях; повышение качества входящих данных
от пользователей.

**Процедура замера** [09:38]:
1. Таблица, где организация оценивает себя по всем осям и отслеживает их во времени.
2. Для проверки дизайна собираются тестовые конструкции.
3. Людям даются **30–40 задач** формулировками вида «узнайте о последнем законодательстве по GDPR»,
   «выясните, как подать петицию».
4. **Целевая планка — 80–90 % успешных выполнений по каждой задаче**; KPI считаются выполненными только
   при её достижении.

**Как вводить в организации** [46:44]: обойти отделы и узнать их собственные KPI и жалобы, затем
переформулировать решения их проблем как результат дизайна. Пример: отдел жаловался на долгую публикацию
через разные легаси-CMS — ответом стала не дизайн-система, а «руководства и пять-шесть готовых компонентов,
которые можно подставлять». Дальше — служба поддержки (на что чаще всего жалуются: не находят в поиске,
не находят в навигации), и только потом руководство, к которому приходят с уже согласованным набором.

**Для агента-генератора** это самая прямо применимая процедура: список из 30–40 формулировок задач
становится одновременно набором сценарных тестов (`03-automated-checks.md` §6) и набором заданий для теста
с людьми, а планка 80–90 % — порогом приёмки.

Связь с остальной базой: **успешность задачи — базовая метрика везде**; время сценария — только для структурированных
задач; число кликов — не метрика (`../01-foundations/02-myths-and-misapplied-laws.md` §1). Набор метрик для
экспертных инструментов (время до первого успеха, время исправления ошибки, ошибки конфигурации, активные
пользователи на команду, доля задач вне системы) — `../13-app-types/01-admin-backoffice-playbook.md` §13; для
клиентского сервиса — доля задач, решённых без обращения в поддержку (`../13-app-types/02-client-facing-app-playbook.md`).

### 4.3 PURE как метрика

Разбор протокола — `01-expert-review-protocols.md` §5. Здесь только метрологическая часть:

- **балл трения** без участия пользователей: сумма оценок 1–3 по шагам happy path;
- корреляция с **SEQ 0,5** (p < 0,05) и с **SUS 0,4** (p < 0,01) на том же продукте;
- межэкспертная надёжность 0,5–0,9, обычно > 0,8 после обучения панели;
- сравнивать можно одну задачу между версиями и конкурентами, нельзя — разные задачи между собой.

**Позиция в наборе**: PURE занимает место, для которого больше ничего нет, — сравнимое число без
пользователей и без разработки. Именно поэтому он годится как селектор при отборе лучшего из k вариантов.

### 4.4 Search quality score

Готовая процедура для продуктов с поиском [V:EEbpwEzB42w, 1:03:16]. `[практика]`

1. Взять **топ-100 поисковых запросов** за год.
2. Получить от редакции (или от владельца домена) по **2–3 URL**, которые должны появляться на каждый запрос.
3. Сверить с фактической выдачей.
4. **Доля совпадений и есть search quality score**; эталонные ссылки обязаны попадать в **первую пятёрку**.

Обоснование порога «первая пятёрка» из того же источника: первая тройка результатов получает около **60 %**
кликов, пятая позиция — 10–20 % вероятности клика; впечатление обо всей выдаче складывается по первым десяти
результатам, позиция 11 роли не играет [30:28], [32:31]. Операционный вывод автора: «relentlessly focus on
the quality of top three results for your top 100 queries».

### 4.5 Метрики качества сгенерированного интерфейса

Разобраны в `../11-ai-generated-ui/02-research-and-benchmarks.md`; здесь сведены как рабочий набор.

| Метрика | Формула или определение | Что меряет | Порог |
|---|---|---|---|
| **EXEC@k** | производственная сборка проходит и домашний маршрут рендерит осмысленный контент с k-й попытки | исполняемость | EXEC@1 = 100 % |
| **NRS** | доля маршрутов из карты, достижимых из home по видимой навигации | навигационная целостность | 100 %; **считается человеком** |
| **VFS** | блочное сопоставление Size / Text / Position / Color, среднее без весов | визуальное соответствие референсу | по задаче |
| **IIS** | 7 категорий взаимодействий × покрытие × результат (1 / 0,5 / 0) × scope (S1 = 1, S2 = 2, S3 = 3) | работоспособность интерактива | лучший фронтир 39,3 из 100 |
| **WVS** | 1·Minor + 2·Moderate + 3·Serious + 4·Critical | доступность, абсолютно | — |
| **IR_axe** | WVS / число DOM-элементов | доступность, нормированно | ≤ 0,15 |
| **Appearance** | рубрика 1–5 (рендер, релевантность, гармония, современность), судья | внешний вид | ≥ 3,8 |
| **Accuracy** | (N_Yes + 0,5·N_Partial) / N_Total по тест-кейсам | функциональное соответствие | лучший результат 58,2 % |

**Три правила выбора метрики** (чек-лист агента C, `../11-ai-generated-ui/02-...`):
- метрика должна быть нормирована на размер артефакта (как IR), а не наказывать длинные страницы;
- исполняемость измеряется **отдельно** от качества (несобравшимся — ноль, как в UI2App);
- у каждой метрики должен быть второй независимый инструмент для кросс-проверки.

**Главное предупреждение**: единой «лучшей модели для UI» не существует, и лидер по одной метрике проигрывает
по другой (VFS-лидер Gemini 3.1 Pro против IIS-лидера Claude Sonnet 4.6, разрыв 5,2×). Выбирать модель надо
под конкретную метрику. `[консенсус]`

## 5. Размеры выборок

### 5.1 Пять пользователей и формула

Формула Нильсена–Ландауэра [S9]: доля найденных проблем = **N(1 − (1 − L)ⁿ)**, где N — общее число проблем
в дизайне, L — доля проблем, обнаруживаемых одним пользователем. **Типичное L = 31 %** (среднее по большому
числу проектов). `[исследование]`

| n | Доля найденных проблем при L = 31 % |
|---|---|
| 0 | 0 % |
| 1 | 31 % |
| 3 | 67 % |
| **5** | **≈ 85 %** |
| 10 | ≈ 98 % |
| 15 | ≈ 99,5 % |

**Ключевой вывод не в числе 5, а в распределении бюджета**: чтобы найти все проблемы, нужно 15 пользователей;
но **три исследования по 5 человек дают больше улучшений, чем одно на 15**, потому что между ними чинят [S9].
Второе исследование проверяет, сработала ли починка, и «копает глубже» — до архитектуры, потока задач и
соответствия потребностям, которые в первом исследовании заслонены поверхностными проблемами.

**Почему не один пользователь**: риск быть введённым в заблуждение поведением одного человека; фиксированные
издержки на планирование лучше амортизировать на нескольких находках [S9].

**Несколько несхожих групп** [S9], [S10]: формула верна для сопоставимых пользователей. Если группы ведут
себя по-разному (врачи и пациенты; продавцы и покупатели), нужны представители каждой, но **не по 5 на группу,
а по 3–4** — наблюдения перекрываются. Пример NN/g: новички, средние и опытные инвесторы → 3 × 3 = 9 человек,
а не 15.

### 5.2 Три против пяти

**Krug настаивает на трёх участниках раунда** [V:VTW1yYUqBm8, 39:46]: «не пять, не семь, не восемь».
Обоснование прагматическое: рекрутинга меньше, а серьёзных проблем найдётся всё равно столько, сколько команда
способна починить, или больше.

**Это не спор о факте.** У Нильсена основание — доля найденных дефектов (формула с L = 31 %); у Круга —
ёмкость команды по починке. Позиция базы:

| Цель | Число |
|---|---|
| Регулярные дешёвые внутренние раунды («одно утро в месяц») | **3** |
| Нужна оценка полноты находок в раунде | **5** |
| Очень низкие накладные расходы (agile-процесс, тест внутри спринта) | **2** — оптимум ROI смещается вниз [S10] |
| Несколько несхожих групп | **3–4 на группу** |
| Нужны числа | **20** |

`[спорно]`, разрешено условием.

### 5.3 Количественные исследования

| Метод | Минимум | Источник |
|---|---|---|
| Количественное юзабилити-исследование (метрики) | **20** | [S10], [S3] |
| Карточная сортировка | **15 на группу** | [S10] |
| Айтрекинг (устойчивые тепловые карты) | **39** | [S10] |
| Опросники (SUS, SEQ, UMUX-Lite) | **20–30** | [S2] |

**Погрешность при 20 участниках** [S3]. SD времени задачи = 52 % от среднего; SD среднего = SD / √n.
При 20 участниках (19 после удаления одного ожидаемого выброса — 6 % пользователей выбросы) погрешность
**±19 %** при 90 % доверительном интервале. Для среднего времени 300 с интервал 243–357 с.

Чтобы сузить до **±10 %**, нужны данные от 71 участника, то есть протестировать 76. Вывод первоисточника:
«Testing 76 users is a complete waste of money for almost all practical development projects. You can get
good-enough data on 4 different designs by testing each of them with 20 users». `[исследование]`

### 5.4 Что делают на практике

Опрос 217 участников конференции NN/g: компании используют в среднем **11 участников** на раунд — вдвое
больше рекомендуемого [S10]. Разбор 83 консалтинговых проектов NN/g: корреляция между числом участников
и числом находок «очень мала».

Три причины, по которым берут больше пяти, названные самим NN/g: внутренняя убедительность для руководства;
несколько целевых аудиторий; фиксированные издержки консалтингового проекта делают выгодным чуть больший
объём. Ни одна из них не про качество находок.

## 6. Аналитические метрики и метрики продукта

### 6.1 Производительность как UX-метрика

**Core Web Vitals** [S11]: LCP ≤ **2,5 с**, INP ≤ **200 мс**, CLS ≤ **0,1**. Измеряются по **75-му
процентилю** загрузок, **раздельно для мобильных и десктопа**; страница считается прошедшей, только если
все три метрики укладываются. Подробнее о том, как их собирать, — `03-automated-checks.md` §9.

Связь с UX-правилами: пороги отклика 0,1 с / 1 с / 10 с и правила индикаторов ожидания
(`../06-feedback-states-motion/02-system-status-and-waiting.md`) описывают, что делать при превышении;
CWV говорят, превышено ли.

### 6.2 Поведенческая аналитика

| Сигнал | Что означает | Что с этим делать |
|---|---|---|
| **Rage clicks** — несколько быстрых кликов подряд в одно место | элемент выглядит интерактивным, но не реагирует, или реакция незаметна | проверить AC-FRM-07 (кнопка без обработчика) и AC-PRF-04 (реакция за 100 мс) |
| **Dead clicks** — клик по неинтерактивному элементу | ложный сигнификатор: текст выглядит ссылкой, карточка выглядит кликабельной | проверить UX-LAY-09 (вариантов контраста не больше трёх) и UX-DAT-09 (строка — настоящая ссылка) |
| **Всплеск undo и erase** | неудачные действия | локализует проблему точнее, чем опрос [S4] |
| **Отвал по шагам воронки** | конкретный шаг сценария | сравнить с картой трения (`01-expert-review-protocols.md` §8.2) |
| **Время до первой ценности** | сколько шагов между входом и ключевым действием | `../05-flows-journeys/01-onboarding-and-first-run.md` §1 |
| **Доля пропустивших тур** | тур не нужен или мешает | там же §11 |
| **Падение оценок в сторах после релиза** | доступный внешний сигнал качества крупного изменения [V:I4UIIISgl2U, 17:37] | разбирать по сегментам устройств и языков |

**Оговорка про rage clicks и dead clicks.** Термины взяты из практики продуктовой аналитики (Hotjar, FullStory
и аналогичные инструменты); **опубликованного исследования, задающего пороги** («сколько кликов подряд за
сколько миллисекунд считается rage click»), я не нашёл. Использовать как сигнал для локализации, не как
метрику с порогом. `[практика]`

### 6.3 Изучать края, а не среднего

**«Средний пользователь» — опасная конструкция**: изучать нужно края — самых активных и довольных и новичков,
которые ничего не понимают [V:I4UIIISgl2U, 27:48]. `[практика]`

Рабочий приём оттуда же [24:43]: источник гипотез — группа в «счастливом состоянии» (те, кто проводит
в продукте часы); у них спрашивают, чем они пользуются ежедневно. В разобранном кейсе таких функций оказалось
две, и обе были спрятаны.

**Но слова пользователей нельзя брать напрямую** [25:43]: люди не осознают своих смещений, не додумывают
и прямо врут (кейс Боба Мосты о паре, клявшейся «только не минивэн» и купившей минивэн). Качественные ответы
проверяются количественно: в том же кейсе 1,2 млн вступлений в сообщества в день подтвердили слова
«счастливой» группы.

Данные, которые заставляют смотреть на нижний край: **5 % пользователей — продвинутые, 69 % — слабые**,
способные лишь реагировать на показанное (OECD, развитые страны) [V:yoMq_r-tD-Y, 24:50]. Описание поведения
слабого пользователя, пригодное как тест: пролистывает ленту и нажимает «нравится», но когда элемент ушёл
за пределы экрана, не знает, как его вернуть [25:51]. `[данные]`

### 6.4 Survival-анализ: как найти ключевое действие

Метод из разбора реального проекта [V:I4UIIISgl2U, 31:27]. `[данные]`

1. Взять когорту зарегистрировавшихся в один день (в разобранном кейсе — около миллиона человек).
2. Зафиксировать все действия первого дня.
3. Проверить, какие из них связаны с возвращением.

**Результат кейса**: возвращение **на следующий день** лучше всего предсказывает подписка на коллекцию
в первый день; возвращение **через три недели** — вступление в сообщество. То есть **разные горизонты
удержания дают разные ключевые действия**, и выбор горизонта — продуктовое решение, а не техническое.

**Что было сделано с результатом** [32:57]: две найденные функции вынесли из скрытого меню в нижнюю
навигацию. Эффект: посещаемость экрана коллекций **+600 %**, число подписок **+300 %**. Новых функций не
добавляли — только сделали видимыми существующие.

Для входного контракта генерации это способ ответить на пункт UX-PRE-02 («одно ключевое действие») данными,
а не догадкой.

### 6.5 Чужие метрики не переносятся

Правило [V:I4UIIISgl2U, 18:38]: опубликованные Spotify цифры перехода с гамбургера на нижнюю навигацию —
рост использования пунктов меню на 30 % и рост числа действий на 9 %. **Для google.com рост числа действий
на 9 % был бы провалом**, потому что цель главной страницы поиска — увести человека дальше как можно быстрее.

Перед заимствованием чужого решения и чужой метрики проверять, совпадает ли целевая метрика. Копирование
вредит дважды: может ухудшить продукт и лишает аргументов при защите решения — «если единственный довод
„так делает Facebook“, вы стоите на шаткой лестнице» [19:38]. `[мнение]`

### 6.6 A/B-тесты и их смещение

**A/B-тест приспособлен к мелким изменениям и потому подталкивает к ним**: крупные изменения, дающие рост
в разы, таким способом не находятся [V:I4UIIISgl2U, 51:30]. `[мнение]`

Второе: **сильная реакция, даже злая, — признак вовлечённости; отсутствие реакции опаснее** [51:30]. При
оценке крупного изменения всплеск негатива в отзывах — не обязательно провал; разбирать надо по сегментам
(в кейсе жалобы шли с дешёвых широких Android-планшетов азиатских рынков, где на иероглифических языках
подписи в нижней панели сжались до двух символов) [49:28].

Третье: **«data driven» — опасная формулировка**; данные не принимают решений, решения принимают люди;
целиться нужно в «data informed» [53:31].

## 7. Протокол теста с пользователями

Полностью исполнимая процедура, проигранная на сцене целиком [V:VTW1yYUqBm8]. Уровень — `[практика]`:
числа даны как практические нормы без ссылок на эксперименты.

### 7.1 Задачи

**Формат задачи**: роль + ситуация + цель, **без указания пути** [V:VTW1yYUqBm8, 32:39]. Пример из доклада:
«вы гражданин США с американским паспортом, живёте и работаете в США; компания отправляет вас докладчиком
на конференцию в Новой Зеландии; вы думаете, что вам может понадобиться виза; определите по этому сайту,
нужна ли она, и если нужна — начните оформление».

Три правила формулировки [S12]:

| Правило | Плохо | Лучше |
|---|---|---|
| **Реалистичность** | «Купите оранжевые кроссовки Nike» | «Купите пару обуви дешевле 40 долларов» |
| **Действие, а не описание** | «Скажите, куда бы вы нажали» | «Найдите фильм, который хотели бы посмотреть в воскресенье днём» |
| **Без подсказок и шагов** | «Зайдите на сайт, войдите и скажите, куда нажать, чтобы получить выписку» | «Посмотрите результаты промежуточных экзаменов» |

Отдельно [S12]: **не использовать в формулировке слова из интерфейса**. Если на сайте есть кнопка
«Подписаться на рассылку», задача не может звучать «Подпишитесь на рассылку» — иначе проверяется не
понятность, а умение читать. Правильно: «Найдите способ получать информацию о предстоящих событиях
на почту».

Оговорка: **избегать подсказок — не значит быть расплывчатым**. «Запишитесь к стоматологу» хуже, чем
«Запишитесь на вторник в 10:00 к своему стоматологу, доктору Петерсену», — люди хорошо приостанавливают
неверие и выполняют задачу как свою.

**Ограничение, отсекающее обход интерфейса** [V:VTW1yYUqBm8, 32:39]: внешним поиском пользоваться нельзя,
внутренним поиском сайта можно — «так мы больше узнаем о том, как работает сайт».

### 7.2 Что такое тест и чего в нём нет

Тест — **наблюдение за тем, как человек пытается воспользоваться тем, что вы сделали**, с проговариванием
вслух [V:VTW1yYUqBm8, 23:29]. Это **не фокус-группа**: мнения, впечатления и прошлый опыт не спрашивают.

Что искать: **«вопросительные знаки, возникающие у человека над головой»** — моменты непонимания в процессе,
а не итоговую оценку [24:31].

### 7.3 Скрипт модератора (15 шагов)

Читается **дословно, по бумаге**, а не пересказывается [V:VTW1yYUqBm8, 27:34].

1. Представиться и объявить формат: «я проведу вас через эту сессию; перед началом у меня есть информация
   для вас, я прочитаю её, чтобы ничего не упустить».
2. Напомнить цель: «мы просим людей попробовать воспользоваться сайтом, над которым работаем, чтобы понять,
   работает ли он как задумано».
3. Назвать длительность.
4. **Снять ответственность**: «мы тестируем сайт, а не вас; вы не можете сделать здесь ничего неправильно;
   это, наверное, единственное место сегодня, где можно не беспокоиться об ошибках».
5. Попросить думать вслух, расшифровав через три вопроса: на что вы смотрите, что пытаетесь сделать,
   о чём думаете.
6. **Снять вежливость**: «не бойтесь задеть наши чувства; мы делаем это, чтобы улучшить сайт, поэтому нам
   нужны честные реакции».
7. Договориться о вопросах: спрашивать можно, но модератор, скорее всего, не ответит сразу — «нам интересно,
   как люди справляются, когда рядом нет помощника»; ответы после сессии.
8. Получить согласие на запись: запись экрана и разговора, только для работы над улучшением, увидят только
   участники проекта; предупредить о наблюдателях, которым виден экран, а не человек.
9. Подписать форму из двух предложений и **только после этого** включить запись.
10. Спросить, есть ли вопросы.
11. Четыре разогревающих вопроса: чем занимаетесь; сколько часов в неделю проводите в интернете; какими
    сайтами пользуетесь по работе и лично; есть ли любимые сайты.
12. **Экскурсия по главной**: «посмотрите на эту страницу и скажите, что вы о ней думаете: что бросается
    в глаза, чей это сайт, что здесь можно делать и для чего это; прокручивать можно, кликать пока нельзя».
13. Задание: прочитать вслух и выдать распечатку; проговорить ограничение; повторить просьбу думать вслух.
14. Во время выполнения **не подсказывать и не подтверждать**: на «мне сюда кликнуть?» — «делайте то,
    что делали бы».
15. Остановить по времени: «в интересах времени остановимся здесь, это было ровно то, что нужно».
    **Незавершённая задача — нормальный результат.**

### 7.4 Кого приглашать

- **Планку отбора держать предельно низкой** [V:VTW1yYUqBm8, 25:32]: критерий «пользовался браузером».
  Чем ниже планка, тем проще рекрутинг.
- **На старте целевая аудитория не нужна** [46:54]: встроенные в продукт проблемы настолько грубые, что
  на них наткнётся кто угодно; недостающие доменные знания подсказываются прямо в сессии
  («рекрутировать свободно, оценивать по кривой»).
- **Не тестировать на дизайнерах** [V:AVKz9ZYoxgo, 50:10]: «I never test with designers — designers are
  the worst… designers often have opinions». Нужны пользователи или люди, не знакомые с продуктом.
- **Подростки — одни из лучших участников** [V:xEtKkLdAnvI, 3:24:24]: «the most critical, the most honest
  and the most helpful people you can find»; разговаривать как с молодыми взрослыми, брать согласие
  родителей.
- **Если доступа к пользователям нет** [3:26:27]: брать людей внутри компании, которые понимают домен,
  но не работают над этим продуктом.
- **Участников с когнитивными особенностями** искать через профильные НКО и фонды, закладывая дорогу
  и гонорар [3:20:17].
- **Тест нельзя вести через переводчика** [V:VTW1yYUqBm8, 25:32]: слишком многое зависит от нюансов языка;
  модератор и наблюдатели обязаны понимать язык участника.
- **Для доступности**: 4–5 сотрудников с инвалидностью, час, **их собственные** ассистивные технологии
  с их настройками скорости речи и многословности; участники с разными ограничениями
  (`../08-accessibility/04-inclusive-design-and-testing.md` §5.6).

### 7.5 Ритм

**Одно утро в месяц в фиксированный день** [V:VTW1yYUqBm8, 45:51]. Пример: «третьи четверги» в одном из
агентств правительства США — в третий четверг каждого месяца приходят трое заранее набранных участников,
и тестируется то, что есть в пригодном для показа состоянии.

**Главный смысл фиксированной даты** [46:54]: отвязать тестирование от поставок. Расписание «протестируем
на той неделе, когда будет прототип» срывается вместе с прототипом, и тест не проводится никогда.

Для agile-команд автор помечает норму как другую («раз в спринт или как договоритесь»), не раскрывая.

**Что можно тестировать до появления дизайна** [43:50]: старую версию перед редизайном; продукты конкурентов
и сопоставимые продукты («они проработали законченный вариант подхода к вашей задаче и оставили ключи
в машине»); набросок на салфетке тем же приёмом, что и экскурсия по главной; прототип «garden path»,
где собран только правильный путь, а шаг в сторону открывает заглушку «эта часть прототипа не собрана».

### 7.6 Что делать с результатом

- **Разбор командой сразу после теста**, а не после написания отчёта [41:47].
- **Квота наблюдателя**: три самые серьёзные проблемы за сессию → девять после трёх участников → три
  из девяти в разбор [51:00].
- **Отчёт — письмо максимум на две страницы** списком: что тестировали (со ссылкой), какие задачи давали,
  худшие наблюдённые проблемы, что с ними делаем [41:47].
- **Чинить наименьшим изменением**, устраняющим наблюдённую проблему [51:00].
- **Смотреть всем**: общий опыт наблюдения даёт команде понимание аудитории, которого не даёт отчёт [47:55].

### 7.7 Качественное исследование не даёт процентов

Прямое правило руководителя UX-лаборатории по итогам ~50 исследований в год [V:94q-lTzInhs, 53:45]:
выборка около **12 человек**, и «6 из 12» или «8 из 12» считать в процентах бессмысленно. Формулировка
«не замечают» означает большинство, а не всех. **Если проблему поймал один из двенадцати, её дополнительно
проверяют на нескольких людях**, чтобы отличить особенность человека от дефекта интерфейса. `[данные]`

**Связка методов той же лаборатории** [1:13:17]:
1. свободное знакомство («друг прислал ссылку»), наблюдатели выходят на 10–15 минут и смотрят, что человек
   делает сам;
2. разбор впечатлений и вопросы «почему так»;
3. и только потом классический сценарный тест — сходится ли путь пользователя с задуманным дизайнером.

**Ай-трекинг как средство отличить «не увидел» от «увидел и не понял»** [1:15:19]: в разобранном кейсе
движений взгляда в поисках крестика закрытия не зафиксировано ни слева, ни справа — взгляд держался
на картинке, — значит увеличение или перенос крестика проблему не решит. Без этого данные вывод был бы
неверным.

### 7.8 Удалённые тесты

- **Модерируемый удалённый** — та же процедура; теряется только язык тела, и это некритично при хорошем
  звуке. Требование: не спикерфон, а VoIP внутри системы демонстрации экрана [V:VTW1yYUqBm8, 53:02].
- **Начинать с удалённых нельзя**: сначала 8–9 очных, чтобы процедура была отработана, потому что удалённо
  приходится следить гораздо внимательнее — неясно, молчит человек потому, что думает, или потому, что
  к нему пришла собака.
- **Немодерируемый удалённый**: отдаёшь URL, задачу и число участников, получаешь видео с мыслями вслух
  примерно через час. Годится для быстрой грубой проверки [54:04].

**Инструменты.** Названные в источниках платформы (UserTesting, Maze, Optimal Workshop, UserZoom,
Chalkmark, UsabilityHub) упомянуты в статьях NN/g и в докладе Круга как примеры; их актуальный состав
и цены я не проверял. **Российские платформы немодерируемого тестирования я проверить не смог**: поиск
по названиям, упомянутым в задании (Fabuza, UXCrowd), не дал страниц, которые я мог бы открыть и
подтвердить. Записываю как непроверенное — см. «Открытые вопросы».

## 8. Симуляция пользователей LLM-агентами

### 8.1 Что это и что оно даёт

**UXAgent** (arXiv:2502.12561v3, CHI EA '25) — LLM-агентный модуль плюс универсальный коннектор к браузеру:
автоматически порождаются тысячи симулированных пользователей для теста целевого сайта. Результаты выдаются
в трёх формах: качественной (агента можно «интервьюировать» о том, как он думал), количественной (число
действий) и видеозаписью (`../11-ai-generated-ui/02-research-and-benchmarks.md` §4.4). `[исследование]`

**Позиционирование самих авторов — ключевое**: это инструмент **отладки дизайна исследования** до реального
теста с людьми, а не замена теста. В эвристической оценке с пятью UX-исследователями участники хвалили
новизну, но высказали опасения по поводу LLM-агентных UX-исследований.

**PerceptUI** (arXiv:2606.05697) — персона-обусловленная оценка: предсказывает, как конкретный пользователь
ответит на вопросы об интерфейсе, с текстовым обоснованием. Прямая критика существующего подхода в аннотации:
MLLM-оценщики «produce surface-level critiques or a judgment that reflects the model's own biases rather
than the genuine response of a particular user».

### 8.2 Как использовать как предварительный фильтр

Рабочая схема, выводимая из этих ограничений:

| Что можно | Что нельзя |
|---|---|
| Отладить формулировки задач до теста с людьми (понятны ли, не содержат ли подсказок) | Считать долю успеха симулированных агентов оценкой юзабилити |
| Найти очевидные тупики и недостижимые состояния массовым обходом | Считать, что агент «не понял» так же, как не понял бы человек |
| Прогнать много вариантов интерфейса и отсеять заведомо сломанные | Отчитываться числами симуляции перед заказчиком |
| Проверить покрытие сценариев (все ли ветки достижимы) | Заменять тест с пользователями AT |
| Сгенерировать список гипотез для последующей проверки на людях | Считать персону агента репрезентативной |

**Главное ограничение, общее для всех симуляций**: агент, генерировавший интерфейс, и агент, его проходящий,
обучены на одних данных и имеют одинаковые слепые зоны. Эффект самопредпочтения измерен на судьях (до +25 %)
и нет оснований считать, что на симулированных пользователях его нет.

### 8.3 Что симуляция точно не закрывает

Список из `../11-ai-generated-ui/04-constraints-prompts-and-checks.md` §6 (см. также
`03-automated-checks.md` §11): уместность решения задаче; приоритет содержимого; доверие и приемлемость;
корректность словаря домена; обучающий эффект интерфейса; достижимость маршрутов через вложенные меню
и условные ссылки.

Плюс отдельно — **всё, что относится к ассистивным технологиям**: тест с пользователями скринридеров
требует их собственных AT с их настройками; симуляция здесь не работает в принципе
(`../08-accessibility/04-inclusive-design-and-testing.md` §5.6).

## 9. Быстрые методы

### 9.1 Пятисекундный тест

**Что**: участнику показывают экран на 5 секунд, затем убирают и спрашивают, что он запомнил: чей это экран,
что здесь можно сделать, что было главным.

**Что проверяет**: читается ли назначение экрана и работает ли иерархия. Это количественная версия
«экскурсии по главной» из протокола Круга (§7.3, шаг 12) и проверка того же, что squint-тест
(`01-expert-review-protocols.md` §9.5).

**Для агента**: исполним буквально — отдельная сессия, один скриншот, ограничение на объём вывода, четыре
вопроса; ответ сравнивается с заявленной задачей экрана. Ограничение симуляции: у модели нет «пяти секунд»,
и её «первое впечатление» не эквивалентно человеческому. `[практика]`

### 9.2 Tree test

**Что** [S13]: участникам показывают только **дерево названий разделов**, без интерфейса, и просят найти
конкретный ресурс. Проверяет **информационную архитектуру отдельно от навигационного интерфейса**.

**На какие вопросы отвечает**: понятны ли названия категорий; точно ли они передают содержимое;
сгруппировано ли содержимое по-пользовательски; различимы ли заголовки между собой; не слишком ли структура
широка или глубока.

**Метрики**: прямая успешность (нашёл без хождения вверх-вниз по дереву) и косвенная успешность (нашёл,
но пришлось возвращаться).

**Состав задач** [S14]: основные ресурсы; **«sleight-of-hand» задачи** — поиск не самого важного ресурса,
чтобы оценить информационный запах родительской категории; потенциально проблемные области (новые
категории, спорные результаты карточной сортировки); **разогревочная задача** в начале, которая заодно
отсеивает невнимательных в немодерируемом тесте.

**Выборка**: качественный tree test требует немногих участников (как обычный тест); **количественный
требует большей выборки** и даёт точные измерения времени и доли успеха, но не объясняет почему [S14].

**Полезная деталь** [S14]: чтобы сравнить два места для одной метки («помидоры» в «Фруктах» или «Овощах»),
не нужно два дерева — достаточно одного, и считается, куда участники пошли первыми.

### 9.3 Click test (first-click)

**Что** [S13]: участнику показывают **статическое изображение** экрана (скриншот, вайрфрейм, набросок)
и задачу; он отмечает, куда бы нажал. После клика задача считается завершённой.

**На какие вопросы отвечает**: какие навигационные компоненты используются, какие остаются незамеченными,
каких избегают.

**Результат**: тепловая карта кликов. Помогает понять, заметен ли навигационный дизайн или элементы
конфликтуют и создают шум.

**Ограничение**: тест неинтерактивен; проверять интерактивные элементы им нельзя.

**Зачем разделять tree test и click test** [S13]: они отвечают на разные вопросы и вместе локализуют
причину. Если люди не заходят в важный раздел, причина может быть в IA (название непонятно или
непривлекательно) или в UI (ссылку не замечают). Tree test проверяет первое, click test — второе.
Догадка о причине стоит дорого: «было бы обидно потратить деньги на редизайн интерфейса и обнаружить,
что проблема в архитектуре, или наоборот».

### 9.4 Партизанские тесты

Короткие тесты со случайными людьми в общественном месте или внутри компании, без рекрутинга и без
оборудования. Обоснование, которое делает их допустимыми: на ранних этапах встроенные в продукт проблемы
настолько грубые, что на них наткнётся кто угодно, и доменные знания можно подсказать прямо в сессии
[V:VTW1yYUqBm8, 46:54]. `[практика]`

Ограничение: не годятся для специализированных доменов, где задача непонятна человеку со стороны,
и для оценки эффективности опытных пользователей.

### 9.5 Сводная таблица быстрых методов

| Метод | Что проверяет | Артефакт | Фокус | Тип данных |
|---|---|---|---|---|
| 5-секундный тест | читаемость назначения экрана и иерархии | скриншот | UI | качественный + количественный |
| Tree test | понятность названий и структуру | список названий | IA | оба |
| Closed card sort | соответствие содержимого категориям | карточки + категории | IA | оба |
| Click test | заметность навигационных элементов | статическое изображение | UI | количественный |
| Юзабилити-тест | всё вместе, с причинами | работающий прототип | IA + UI | качественный (может быть количественным) |

Таблица построена по [S13]; графа «артефакт» добавлена мной.

## 10. Ловушки измерения

### 10.1 Метрика становится целью

Закон Кэмпбелла: чем важнее метрика в принятии решений, тем вероятнее её манипуляция [S8]. Примеры из
первоисточника: показывать опрос только довольным клиентам; «rating racketeering» — купон за хорошую оценку;
намёк сотрудника, что от оценки зависит его работа.

Для генеративной системы это прямое предупреждение: **метрика, по которой отбираются варианты, будет
оптимизирована** — в том числе способами, не улучшающими опыт. Поэтому селектор должен быть либо
детерминированным (число нарушений axe), либо составным (несколько метрик, каждая со своим порогом),
но не единственным субъективным баллом.

### 10.2 Отсутствие жалоб ничего не значит

**67 % пользователей скринридеров никогда или редко сообщают владельцу сайта о барьере**
(`../08-accessibility/04-inclusive-design-and-testing.md` §1.3, данные WebAIM). `[исследование]`

Это разрушает распространённый аргумент «нет обращений — нет проблемы». Общая форма ловушки: **люди,
которым интерфейс не подошёл, уходят молча**, и в данных они выглядят как отсутствие данных. То же
касается любой воронки: отвал на шаге не порождает обращения в поддержку.

### 10.3 Удовлетворённость не растёт

Лонгитюдные данные NN/g: удовлетворённость пользователей (шкала 1–7, каждая точка — тест одного сайта)
**не растёт год от года, тренда нет** [V:OtBeg5eyEHU, 31:44]. `[данные]`

Объяснение: субъективная удовлетворённость — это не качество продукта, а **отношение полученного
к ожидаемому**, а ожидания формируются совокупным опытом всех остальных сервисов. Когда улучшаются все,
планка поднимается [33:33].

**Практическое следствие для чтения метрик** [34:37]:

| Что произошло с показателем год к году | Как читать |
|---|---|
| Не изменился | команда сработала **хорошо** — удержала уровень при выросших ожиданиях |
| Вырос | исключительно хорошо |
| Упал при неизменном продукте | **норма, а не аномалия** |

Отсюда неизменное требование непрерывного улучшения: качество надо поднимать постоянно, иначе пользователи
уходят, даже если продукт не стал хуже [35:38].

### 10.4 Оценка метрики без базы сравнения

«That my hypothetical task took an average of 10 minutes means little on its own» [S3]. Десять минут —
катастрофа для подписки на рассылку (среднее по индустрии — 1 минута, удовлетворены при < 2) и отличный
результат для оформления ипотеки. **Метрику собирают, чтобы сравнить её с другой метрикой**: с конкурентом,
с прошлой версией, с нормой.

Тот же принцип в правилах базы: показатель без базы сравнения не показывается
(`../04-components-patterns/03-dashboards-and-kpi.md` §4.3).

### 10.5 Что измерять нельзя

- **Статистику на пяти участниках.** Любой средний балл по пяти респондентам не сообщается [S2].
- **Проценты на выборке 12** [V:94q-lTzInhs, 53:45].
- **Время задачи в тесте с мыслями вслух** [S1].
- **NPS между странами** [S8].
- **Баллы PURE разных задач между собой** (`01-expert-review-protocols.md` §5.2).
- **Один прогон LLM-судьи как измерение** (`03-automated-checks.md` §8.2).

## 11. Что агент-генератор обязан подготовить для теста с людьми

Тест с людьми стоит дорого, и агент может резко удешевить его, подготовив материалы. Ниже — минимальный
комплект, который сдаётся вместе с интерфейсом.

### 11.1 Артефакты

| Артефакт | Содержание | Откуда берётся |
|---|---|---|
| **Список гипотез** | что именно неясно и требует проверки на людях; каждая гипотеза сформулирована как проверяемое утверждение | находки инспекции с `confidence: low`; пункты чек-листа со способом `HUM` и `JDG` |
| **30–40 задач-формулировок** | роль + ситуация + цель, без слов из интерфейса, без указания пути | дизайн-KPI (§4.2), правила формулировки (§7.1) |
| **Ожидаемый путь для каждой задачи** | happy path, по которому считается успех | спецификации сценариев из входного контракта |
| **Критерий успеха для каждой задачи** | что считается успехом, что частичным успехом | §2.1 |
| **Набор метрик** | какие собираем: успешность, время, SEQ после каждой задачи, SUS или UMUX-Lite после сессии | §1.2 |
| **Прототип, пригодный к тесту** | все состояния реализованы, данные реалистичны, заглушек нет; при неготовности — «garden path» с заглушкой на шаг в сторону | UX-STA-*, UX-AIG-01, §7.5 |
| **Профиль участников** | сколько человек, какие группы, какие ассистивные технологии | §5, `../08-accessibility/04-...` §5.6 |
| **Список известных проблем** | что уже найдено инспекцией и автоматикой, чтобы не тратить сессии на очевидное | отчёт инспекции |
| **Базовая линия** | прошлые значения метрик или значения конкурента | §10.4 |

### 11.2 Что агент обязан убрать до показа людям

- Заполнительный текст, стоковые картинки, служебные панели прототипа — люди, отвлёкшиеся на неважное,
  теряют способность обсуждать работоспособность решения [V:99e6d2purlo, 07:17]. Формальная проверка —
  AC-TXT-01, AC-TXT-02.
- Всё, что уже найдено автоматикой: «heuristic evaluation, чтобы не тратить пользователей»
  (`01-expert-review-protocols.md` §1.3).

### 11.3 Процедура внедрения, если тестов ещё нет

Из практики внедрения доступности, переносимо на UX вообще [V:xEtKkLdAnvI, 2:42:51], [3:13:04]:

1. **Пилот на проблеме, о которой уже говорят все команды** и которая мешает всем, а не отдельной группе
   (типовые находки: слишком мелкий кегль, кнопка, не говорящая, что делает).
2. **Малые обязательства**: просить не программу исследований, а 3–5 участников и 2–3 сессии на ближайшие
   2–3 месяца.
3. **Видеоклипы вместо графиков**: короткие фрагменты сессий, где видно, как человек мучается, работают
   там, где «facts and charts and legal compliance» не работают.
4. **One-to-one со всеми, у кого есть право голоса, до большой встречи**, чтобы не получить лавину
   возражений на презентации.
5. **Артефакт на выходе** — дорожная карта с действиями, сроками, ролями и целями.
6. **Ритм** — фиксированный день раз в месяц (§7.5).

## Частые ошибки

1. **Пытаться получить числа из качественного теста.** §1.1.
2. **Сообщать средний балл опросника по пяти участникам.** §3.7.
3. **Переводить «6 из 12» в проценты.** §7.7.
4. **Читать балл SUS как процент.** 70 из 100 — это примерно среднее, а не «70 %». §3.1.
5. **Менять формулировки SUS** и сравнивать с нормами. §3.1.
6. **Сравнивать NPS между странами.** §3.5.
7. **Использовать NPS как метрику юзабилити** и ждать, что локальная правка его сдвинет. §3.5.
8. **Измерять время задачи в тесте с мыслями вслух.** §2.2.
9. **Не удалять выбросы при расчёте статистики — или удалять и забывать о них.** §2.2.
10. **Брать 11 участников «для убедительности».** Вдвое дороже без прироста находок. §5.4.
11. **Тестировать на дизайнерах.** §7.4.
12. **Давать задачу словами из интерфейса.** §7.1.
13. **Просить рассказать, куда бы нажал, вместо того чтобы нажать.** §7.1.
14. **Подсказывать во время сессии.** §7.3, шаг 14.
15. **Планировать тест «на неделе, когда будет прототип».** Он не состоится. §7.5.
16. **Начинать с удалённых тестов**, не отработав процедуру очно. §7.8.
17. **Считать симуляцию LLM-агентами заменой теста.** §8.1.
18. **Считать отсутствие жалоб отсутствием проблем.** §10.2.
19. **Читать неизменившуюся удовлетворённость как застой.** §10.3.
20. **Оценивать метрику без базы сравнения.** §10.4.
21. **Переносить чужую метрику вместе с чужим решением.** §6.5.
22. **Искать крупные улучшения A/B-тестами.** §6.6.
23. **Оптимизировать «долю прошедших онбординг» вместо «доли дошедших до ценности».**
    `../05-flows-journeys/01-onboarding-and-first-run.md` §11.
24. **Изучать «среднего пользователя» вместо краёв.** §6.3.
25. **Отдавать людям то, что находит автоматика.** §11.2.

## Чек-лист

Выбор метода и метрики:
1. Сформулировано, что именно нужно узнать, до выбора метода?
2. Выбрано, что нужно — инсайты или числа; метод соответствует?
3. Метрика имеет базу сравнения (прошлая версия, конкурент, норма)?
4. Метрика нормирована (на пользователя, на размер артефакта)?
5. Собраны и поведенческие, и аттитюдные данные, а не что-то одно?

Выборка:
6. Размер выборки соответствует цели (5 / 3–4 на группу / 20 / 15 / 39)?
7. Для количественных выводов участников не меньше 20?
8. Посчитана погрешность, и её величина названа в отчёте?
9. Выбросы удалены из статистики и разобраны качественно?

Опросники:
10. Взят стандартный опросник, а не свой?
11. Формулировки и порядок не изменены?
12. Post-task и post-test не перепутаны (SEQ после задачи, SUS после сессии)?
13. При оценке SEQ ниже 5 задан вопрос «почему»?
14. Баллы переведены в процентили там, где они будут показаны стейкхолдерам?

Задачи:
15. Задача сформулирована как роль + ситуация + цель?
16. В формулировке нет слов из интерфейса и нет описания шагов?
17. Задача требует действия, а не рассказа?
18. Для каждой задачи заранее определён критерий успеха?
19. Задач 30–40, если считаются дизайн-KPI, и планка 80–90 % объявлена?

Проведение:
20. Скрипт модератора читается дословно?
21. Участнику сказано, что тестируется сайт, а не он?
22. Модератор не подсказывает и не подтверждает?
23. Наблюдатели записали по три худшие проблемы за сессию?
24. Разбор проведён сразу после теста?
25. Отчёт укладывается в две страницы?

Подготовка к тесту силами агента:
26. Собран комплект §11.1 (гипотезы, задачи, ожидаемые пути, критерии успеха, метрики, прототип, профиль
    участников, список известных проблем, базовая линия)?
27. Из прототипа убраны заглушки и отвлекающие элементы?
28. Всё, что находит автоматика, уже починено — сессии не тратятся на очевидное?
29. Для проверки доступности запланированы участники со своими ассистивными технологиями?

## Открытые вопросы и противоречия

1. **Три против пяти участников** — разобрано в §5.2. `[спорно]`, разрешено условием, не фактом.
2. **Пороги rage clicks и dead clicks не опубликованы.** Термины индустриальные, инструменты (Hotjar,
   FullStory и аналоги) задают пороги по-своему и не раскрывают методику. Использую как сигнал без порога.
   Кандидат на проверку следующей волной: документация конкретных инструментов и любые академические
   работы о «frustration signals».
3. **Российские платформы немодерируемого тестирования не проверены.** Названия из задания (Fabuza, UXCrowd)
   я не смог подтвердить открытием страниц. Не утверждаю ни их существования, ни отсутствия. Кандидаты
   для следующей волны: агент с браузерным доступом; поиск по русскоязычным UX-сообществам; проверка
   Яндекс.Взгляда и аналогов как инструментов немодерируемого тестирования.
4. **AUS валидирован одной компанией.** Fable Tech Labs, средний 65 по 2 100 сессиям; независимой
   публикации о валидности и надёжности шкалы я не нашёл. Применять, отмечая это.
5. **Числа дизайн-KPI (30–40 задач, 80–90 %) — практика одного консультанта** [V:2hlQqMigGZg], без ссылки
   на исследование. Планка 80–90 % не обоснована ничем, кроме опыта; для сложных экспертных систем она,
   вероятно, недостижима и должна быть пересмотрена по типу продукта.
6. **Search quality score** — практика одного консультанта; порог «в первой пятёрке» выведен из данных
   о распределении кликов, но сама процедура нигде не валидирована.
7. **SEQ: 14 % случаев «провалил, но легко»** — важное число, ограничивающее доверие к самоотчёту, но
   у Сауро оно дано ссылкой на его же материал, который я не открывал отдельно. Читать как порядок величины.
8. **Данные о времени задачи (SD = 52 %)** собраны на сайтах и интранетах середины 2000-х. Для современных
   веб-приложений повторного замера я не нашёл; разброс может отличаться.
9. **Формула Нильсена–Ландауэра с L = 31 %** описывает **проблемы одного дизайна для сопоставимых
   пользователей**. Она не применима к разнородным группам (для них правило 3–4 на группу) и, строго говоря,
   не применима к линзам агента (`01-expert-review-protocols.md` §7.2, п. 4 открытых вопросов).
10. **Корреляция между прохождением чек-листа и результатом теста с людьми нигде не измерена** — это общий
    пробел, отмеченный и в `02-master-checklist.md`. Лучший кандидат на собственный эксперимент: один набор
    интерфейсов, прогон сводного чек-листа и теста с людьми, расчёт того, какие пункты предсказывают провал
    задачи.
11. **Метрики генеративного качества (IIS, NRS, VFS) требуют человеческой разметки** для NRS и IIS
    (Krippendorff α 0,72–0,84 у авторов бенчмарка). Полностью автоматического аналога не существует, и это
    ограничивает применимость их как селектора при отборе из k вариантов.
12. **HEART описан в работе 2010 года**; последующих публикаций Google о том, как фреймворк изменился
    за 15 лет, я не искал. Механизм (Goals → Signals → Metrics) от даты не зависит, конкретные примеры
    метрик устарели.

## Источники

- `[S1]` Nielsen Norman Group. Success Rate: The Simplest Usability Metric.
  https://www.nngroup.com/articles/success-rate-the-simplest-usability-metric/ — прочитано целиком.
  Конфликт чисел и инсайтов, определение успешности задачи, частичный успех, «user success is the bottom
  line of usability».
- `[S2]` Nielsen Norman Group. Beyond the NPS: Measuring Perceived Usability with the SUS, NASA-TLX, and
  the Single Ease Question. https://www.nngroup.com/articles/measuring-perceived-usability/ — прочитано
  целиком. Post-task против post-test, SUS (среднее 68, 80,3 для верхних 10 %), SEQ, NASA-TLX, требование
  20–30 участников, ограничения самоотчёта, правило «не больше 7 делений», аргумент за стандартные
  опросники.
- `[S3]` Jakob Nielsen. Quantitative Studies: How Many Users to Test?
  https://www.nngroup.com/articles/quantitative-studies-how-many-users/ — прочитано целиком.
  SD = 52 % от среднего на 1 520 замерах и 70 задачах; 20 участников → ±19 % при 90 % доверительном
  интервале; 76 участников для ±10 %; 6 % выбросов; правило «метрику собирают для сравнения».
- `[S4]` Kerry Rodden, Hilary Hutchinson, Xin Fu. Measuring the User Experience on a Large Scale:
  User-Centered Metrics for Web Applications. Proceedings of CHI 2010, ACM Press.
  PDF: https://blog.kleros.io/content/files/pub-tools-public-publication-data/pdf/36299.pdf — прочитано
  целиком. PULSE и его недостатки, пять категорий HEART, Goals → Signals → Metrics, нормировка счётчиков,
  «failure is easier to identify than success», примеры Gmail и Google Finance, ссылка на Akers et al.
  CHI 2009 об undo как индикаторе.
- `[S5]` Jeff Sauro. Measuring Usability with the System Usability Scale (SUS). MeasuringU.
  https://measuringu.com/sus/ — прочитано. Среднее 68 по 500 исследованиям; перевод в процентили и
  буквенные оценки; 80,3 = A; 74 = B−; ниже 51 = F; предупреждение «SUS не процент».
- `[S6]` Jeff Sauro. Measuring Usability: From the SUS to the UMUX-Lite. MeasuringU.
  https://measuringu.com/umux-lite/ — прочитано целиком. UMUX и его дефект (двухфакторная структура),
  UMUX-Lite из двух пунктов, α = 0,86, r = 0,83 с SUS и 0,72 с NPS, регрессия пересчёта в SUS с точностью
  ~99 %, связь с TAM, открытый вопрос о переформулировке первого пункта.
- `[S7]` Jeff Sauro. 10 Things To Know About The Single Ease Question (SEQ). MeasuringU.
  https://measuringu.com/seq10/ — прочитано целиком. Шкала 1–7 после задачи, среднее 5,3–5,6 по 400+ задачам
  и 10 000 пользователей, r ≈ 0,5 с временем и успешностью, 14 % случаев «провалил, но легко», требование
  спрашивать «почему» при оценке ниже 5, проблема отделения сложности задачи от проблем интерфейса.
- `[S8]` Nielsen Norman Group. Net Promoter Score (NPS) and UX. https://www.nngroup.com/articles/nps-ux/ —
  прочитано целиком. Определение и расчёт, Reichheld HBR 2003, различия по странам (Qualtrics XM Institute
  2021: 17 509 респондентов, 18 стран; Япония −47 %, Южная Корея −11 % даже для любимых компаний), шесть
  ограничений включая закон Кэмпбелла и «rating racketeering», три причины всё же использовать.
- `[S9]` Jakob Nielsen. Why You Only Need to Test with 5 Users.
  https://www.nngroup.com/articles/why-you-only-need-to-test-with-5-users/ — прочитано целиком. Формула
  N(1 − (1 − L)ⁿ), L = 31 %, 15 пользователей для всех проблем, три теста по 5 лучше одного на 15, почему
  не один пользователь, 3–4 на группу при нескольких аудиториях.
- `[S10]` Jakob Nielsen. How Many Test Users in a Usability Study?
  https://www.nngroup.com/articles/how-many-test-users/ — прочитано целиком. Исключения: 20 для
  количественных, 15 для карточной сортировки, 39 для айтрекинга; опрос 217 участников (в среднем 11
  участников на раунд); 83 кейса NN/g с очень малой корреляцией; 2 участника для процессов с низкими
  накладными расходами; разбор слабых аргументов за большую выборку.
- `[S11]` web.dev. Web Vitals. https://web.dev/articles/vitals — прочитано. LCP ≤ 2,5 с, INP ≤ 200 мс,
