# Сводный чек-лист экрана и сценария

Волна 3 · Агент I · 22 сентября 2026 · собран из 40 содержательных файлов базы (папки 01–09, 11, частично 13),
12 дайджестов видео и собственного ресёрча (29 источников целиком)

Машиночитаемый свод правил базы: **434 пунктов в 20 блоках** (APP — четыре подблока по типу приложения). Каждый пункт имеет идентификатор, формулировку «да/нет», серьёзность,
способ проверки и ссылку на файл-источник, где правило разобрано с доказательствами. Агент ссылается на
идентификаторы в отчётах: «нарушен UX-FRM-03» вместо «форма плохая».

Как проводить проверку — `01-expert-review-protocols.md`. Что из этого запускается скриптом и с какими
порогами — `03-automated-checks.md`. Метрики и тесты с людьми — `04-metrics-and-user-testing.md`.

## 1. Как читать и как пользоваться

### 1.1 Формат строки

```
| ID | Проверка (ответ «да» = норма) | Сер. | Способ | Источник |
```

**Серьёзность** — свёртка шкалы Нильсена 0–4 (`01-expert-review-protocols.md` §3.1) в три градации, которые
можно проставить заранее, до конкретного интерфейса:

| Код | Название | Смысл | Соответствие 0–4 |
|---|---|---|---|
| **B** | блокер | задача не выполняется, данные теряются, закон нарушается; отдавать нельзя | 4 и тяжёлые 3 |
| **S** | серьёзно | задача выполняется, но дорого: трение, ошибки, повторная работа | 3 и 2 |
| **D** | желательно | улучшает опыт, не мешает задаче; чинить при наличии бюджета | 1 |

**Уточнение серьёзности по контексту.** Базовая серьёзность в таблице — для рабочего веб-сервиса
(админка или клиентский кабинет). Она повышается на ступень, если пункт нарушен **на маршруте топ-задачи**,
и понижается на ступень на редком служебном экране. Пункты, помеченные `[спорно]` в файлах-источниках,
не могут иметь серьёзность выше **D** — позиция базы по ним является синтезом, а не установленным фактом
(перечень — §8.2).

**Способ проверки:**

| Код | Что это | Где описано |
|---|---|---|
| `DOM` | разбор DOM или статического кода одной страницы | `03-automated-checks.md` §4 |
| `LNT` | линтер по исходникам (до рендера) | `03-automated-checks.md` §3 |
| `AXE` | axe-core, Lighthouse, второй аудитор | `03-automated-checks.md` §5 |
| `SCR` | сценарий в headless-браузере (Playwright, GUI-агент) | `03-automated-checks.md` §6 |
| `IMG` | сравнение или анализ скриншота (визуальная регрессия, squint, grayscale) | `03-automated-checks.md` §7 |
| `JDG` | мультимодальный судья по рубрике, несколько прогонов | `03-automated-checks.md` §8 |
| `HUM` | только человек | `03-automated-checks.md` §11 |

Пункт может иметь несколько способов через запятую; первый — основной. **Если способ `JDG` или `HUM`,
автоматические ворота по этому пункту не ставятся** — он попадает в отчёт как наблюдение.

### 1.2 Четыре режима использования

| Режим | Что берём | Когда |
|---|---|---|
| **Перед генерацией** | блок `PRE` целиком | до первого промта; незаполненный пункт = причина не генерировать |
| **Чек-лист экрана** (screen audit) | §5 — упорядоченный проход по одному экрану | после генерации каждого экрана |
| **Чек-лист сценария** | §6 — проход по пути от начала до конца | после сборки сценария |
| **После генерации** | блок `OUT` целиком | перед отдачей человеку |

### 1.3 Порядок проверки

Сначала то, что дешевле всего проверить и чаще всего ломается. Основание для порядка — два независимых
набора данных:

1. **WebAIM Million 2026** (1 млн главных страниц, февраль 2026) [S1]: 95,9 % страниц имеют обнаруживаемые
   нарушения WCAG; **шесть типов ошибок дают 96 % всех**: низкий контраст текста 83,9 % страниц, отсутствующий
   alt 53,1 %, отсутствующая подпись поля 51 %, пустые ссылки 46,3 %, пустые кнопки 30,6 %, отсутствующий
   `lang` 13,5 %. Плюс: 41,8 % страниц с пропусками уровней заголовков, 18,1 % с несколькими `h1`,
   `<main>` только у 46,1 %, у 17,1 % есть skip-ссылка и **каждая десятая из них сломана**.
2. **Каталог дефектов нейросетей** `../11-ai-generated-ui/01-failure-modes-catalog.md` и бенчмарки
   (`../11-ai-generated-ui/02-research-and-benchmarks.md`): разрыв «выглядит правильно / работает правильно»
   измерен трижды (WebGen-Bench 52,0 против 17,1; UI2App VFS-лидер против IIS-лидера в 5,2 раза;
   FullFront: **ни одна модель не выше 0,60 по Text и Form**); cross-route state — ноль у трёх из шести
   фронтирных моделей; админки — худшая категория (средний IIS 9,4).

Итоговый порядок блоков:

```
PRE → BLD → A11 → STA → NAV → LAY → FRM → DAT → OVL → FLW → ACT → SET → FBK → ETH → TXT → MOB → CNS → APP → AIG → OUT
 │     │     │     │     └ структура, компоненты, сценарии, тексты, мобайл, консистентность, плейбуки ─┘     │     │
 │     │     │     └ состояния: самый частый пропуск генерации                                               │     │
 │     │     └ доступность: самый частый дефект веба вообще                                                  │     │
 │     └ сборка: провал делает остальное бессмысленным                                    ошибки нейросетей ─┘     │
 └ входной контракт                                                                               ворота выдачи ───┘
```

### 1.4 Что делать с результатом

- Любой невыполненный пункт **B** — стоп. Интерфейс не отдаётся; см. правила «стоп» в
  `03-automated-checks.md` §10.
- Невыполненные **S** считаются и сравниваются с бюджетом итерации.
- **D** собираются в список и чинятся при наличии бюджета, но **не вместо** B и S (правило «низко висящих
  плодов», `01-expert-review-protocols.md` §3.3).
- Отчёт: `01-expert-review-protocols.md` §6.3–6.4.

## 5. Чек-лист экрана (screen audit)

Порядок прохода по одному экрану. В скобках — идентификаторы, которые проверяются на этом шаге.

**Шаг 0. Заявка.** Записать, что этот экран должен делать: задача, роль, одно ключевое действие, ожидаемый
объём данных. Без этого проверка вырождается (UX-PRE-02, UX-PRE-14).

**Шаг 1. Экскурсия до первого действия.** Отдельная сессия, один скриншот, без DOM: чей это экран, что
здесь можно делать, для чего это, что бросается в глаза первым. Сравнить с заявкой шага 0
(`01-expert-review-protocols.md` §9.2). → UX-LAY-01, UX-NAV-01.

**Шаг 2. Дешёвая автоматика.** Сборка, линт, инвентарь, поиск заглушек, axe в двух темах.
→ UX-BLD-01…12, UX-AIG-01…03, UX-A11-01…08, UX-A11-19, UX-A11-21.

**Шаг 3. Состояния.** Замокать: пусто-новое, пусто-фильтр, загрузка 3 с, ошибка 500, нет прав, много данных,
граничные значения. Снять скриншот каждого. → UX-STA-01…18.

**Шаг 4. Структура и иерархия.** Squint-тест, grayscale, проверка одной primary-кнопки, шапки, панелей,
дублей. → UX-LAY-01…18, UX-NAV-02…13.

**Шаг 5. Компоненты по типу экрана.**
- форма → UX-FRM-01…28;
- таблица, список, фильтры, дашборд, карточка объекта → UX-DAT-01…25;
- оверлеи и уведомления на этом экране → UX-OVL-01…18;
- настройки и права → UX-SET-01…16;
- действия и меню → UX-ACT-01…18.

**Шаг 6. Клавиатура и скринридер.** Tab по экрану и обратно; открыть-закрыть каждый оверлей; проверить
`document.activeElement` после каждого действия. → UX-A11-09…12, UX-A11-15, UX-A11-16, UX-OVL-06, UX-OVL-07.

**Шаг 7. Обратная связь и движение.** Нажать на всё, что меняет состояние; замерить отклик; проверить
индикаторы и анимации. → UX-FBK-01…16.

**Шаг 8. Этика.** Если на экране есть согласия, платежи, подписки, таймеры или отказы — UX-ETH-01…14.

## 6. Чек-лист сценария

Проверяется на каждом ключевом пути от начала до конца. Экранная проверка (§5) её не заменяет: путь ломается

**Шаг 0. Спецификация.** Цель, роль, happy path, ветвления, ошибки по шагам, конечные состояния, «что дальше».

**Шаг 4. Тест переживания перехода, семь шагов.** → UX-FLW-04, UX-DAT-13, UX-DAT-14, UX-AIG-11.

**Шаг 5. Навигация назад и адресуемость.** «Назад» браузера на каждом шаге; открытие скопированного URL;
поведение оверлея при «Назад». → UX-FLW-02, UX-FLW-03.

**Шаг 8. Путь на телефоне.** 360 px, тот же сценарий, включая системный «Назад» и открытую клавиатуру.
→ UX-MOB-01…24.

**Шаг 9. Деструктивная ветка.** Если в сценарии есть удаление, отмена подписки, массовая операция —

## 7. Что взято из checklist.design и чего там нет

checklist.design — самый известный публичный набор чек-листов дизайна; снят headless-браузером 22.09.2026.
Структура: **пять разделов** — Mobile app, Web app, Website, Design system, Flows.

| Раздел | Что внутри |
|---|---|
| Web app | Dashboard, Billing, Onboarding, Pricing, Settings, Empty State, Notifications |
| Mobile app | Paywall, Onboarding, Login, Camera, Map View, Chat, Search, Profile |
| Website | Features, Blog Post, Contact Us, Pricing, 404, Team, Careers, FAQ |
| Design system | Typography, Tokens, Accordion, Banner, Radio, Tooltip, Modal, Input Field, Button, Toggle |
| Flows | Adding to cart, Uploading media, Canceling subscription, Filtering items, Resetting password, Submitting a form, Contacting support |

**Формат пункта**: название → короткое описание → иногда обоснование или антипример. У чек-листа счётчик
«0 из N» и кнопка сброса; есть экспорт «Copy as plain text» и в Confluence, Notion, Linear; в 2026 появились
Agent skill и Figma skill.

**Что полезного взято** (с указанием источника в соответствующих пунктах базы):
- различение «zero state против no-results state» и требование пути выхода из no-results — совпадает с
  UX-STA-02 и UX-STA-06; в базе это правило подтверждено независимо
  (`../06-feedback-states-motion/01-state-matrix.md`);
- отдельный вариант состояния ошибки, а не подмена его пустым состоянием — UX-STA-05;
- структура пункта «название + короткое описание + антипример» как формат подачи — использована в §3;
- набор разделов «экран / компонент / сценарий» подтверждает разделение на чек-лист экрана и чек-лист
  сценария (§5, §6).

**Чего там нет** (и потому этот файл не является его пересказом):
1. **Серьёзности** — все пункты равнозначны; невозможно отличить блокер от пожелания.
2. **Способа проверки** — не сказано, чем проверять; нет разделения «глазами / DOM / скрипт».
3. **Ссылок на источники и уровня доказательности** — ни один пункт не обоснован; часть пунктов совпадает
   с исследованными правилами, часть — вкусовые.
4. **Состояний как сквозной темы** — есть отдельный чек-лист Empty State, но нет состояний загрузки,
   частичной загрузки, отсутствия прав, офлайна; нет матрицы состояний по типам экранов.
5. **Проверок переживания перехода** — ни одного пункта про URL, «Назад», сохранение фильтров и черновиков.
   Это самый массовый измеренный дефект генерации.
6. **Ошибок нейросетей** — блока AIG нет вовсе.
7. **Порогов** — нет чисел («строк больше 50 → пагинация», «колонок больше 8 → липкая первая»).
8. **Доступности как отдельного слоя** — упоминается фрагментарно внутри компонентов; нет клавиатуры,
   фокуса, живых областей, forced-colors.
9. **Пунктов про визуальный слой чек-лист Modal даёт больше, чем про поведение**: из шести пунктов один —
   «Background change behind modal» (затемнить или размыть фон), и при этом нет ни возврата фокуса, ни Esc,
   ни ловушки фокуса.

**Вывод**: checklist.design годится как источник формулировок и как напоминание о составе экрана,
но не как источник правил — у пунктов нет обоснования, серьёзности и способа проверки. `[мнение]`

### 8.3 Что чек-лист не проверяет

Ни один пункт этого файла не отвечает на вопросы, которые остаются человеку
(`../11-ai-generated-ui/04-constraints-prompts-and-checks.md` §6):

- **уместность решения задаче** — нужен ли вообще этот экран, эта функция, этот дашборд;
- **приоритет содержимого** — метрика измерит площадь и контраст, но не знает, что здесь важнее;
- **корректность самого словаря домена** — чек-лист ловит отклонение от словаря, но не ошибку в словаре;
- **доверие и приемлемость**;
- **обучающий эффект интерфейса** — учится ли человек пользоваться продуктом.

Кроме того, **прохождение чек-листа не означает «хороший UX»**. Автопроверки и чек-листы — ворота, а не
оценка (`../11-ai-generated-ui/04-...` выжимка, п. 25). Формальный признак: WCAG-соответствие не гарантирует
удобства («WCAG does not guarantee usability»), и то же верно для любого свода правил.

## Частые ошибки

1. **Использовать чек-лист вместо задачи экрана.** Пункты проверяют форму, а не то, решает ли экран задачу.
   Заявка (§5, шаг 0) обязательна.
2. **Проверять все пункты подряд на каждом экране.** Блоки применяются по типу экрана; лишние пункты
   размывают отчёт.
3. **Считать чек-лист достаточным.** Он не находит проблем категории «чего-то не хватает» за пределами
   перечисленного и не заменяет теста с людьми.
4. **Игнорировать серьёзность** и закрывать отчёт списком пунктов D при открытых B.
5. **Проверять только «идеальное» состояние экрана.** Блок STA существует именно потому, что состояния
   систематически пропускаются.
6. **Проверять экран, не проверив путь.** Блок FLW и §6 закрывают дефекты между экранами.
7. **Отдавать судье пункты со способом DOM/LNT/SCR.** Детерминированное проверяется детерминированно.
8. **Повышать серьёзность спорных пунктов** (§8.1).
9. **Пропускать блок APP.** Общие блоки не заменяют плейбук: пункты по типу приложения (§3.18) обязательны для
   своего типа, а консистентность (§3.17) проверяется по инвентарю и автопроверкам, а не «на глаз».
10. **Заводить свои идентификаторы** вместо UX-*. Идентификаторы нужны, чтобы отчёты разных прогонов
    сравнивались между собой.

## Открытые вопросы и противоречия

1. **Разделы CNS (§3.17) и APP (§3.18) собраны в волне 4** (агент S1) по `../10-design-systems-consistency/02-consistency-rules.md`
   (семь правил, четыре случая, 22 автопроверки) и чек-листам `../13-app-types/01–04`; серьёзность назначена по той же
   шкале и не измерена; пункты, дублирующие общие блоки, не переносились. Разделы TXT (§3.15) и MOB (§3.16) собраны
   по готовым файлам агентов G и F1.
2. **Серьёзность пунктов назначена мной**, а не измерена. Основание — шкала Нильсена (частота × влияние ×
   устойчивость) плюс данные о частоте нарушения (WebAIM Million) и о частоте дефектов генерации (каталог C).
   Для части пунктов (особенно D) назначение спорно и подлежит пересмотру после первых прогонов. `[мнение]`
3. **Число пунктов (434, из них по типу приложения проверяется один подблок) велико для одного прохода.** Предполагается, что большая часть проверяется
   автоматически (`03-automated-checks.md`), а вручную остаётся 30–50. Соотношение не измерено.
4. **Нет данных о том, какие пункты чек-листов реально коррелируют с результатом теста с пользователями.**
   Ни один из прочитанных источников не публикует такой валидации; checklist.design её тоже не имеет.
   Это кандидат на собственный эксперимент: прогнать чек-лист и тест с людьми на одном наборе интерфейсов
   и посчитать, какие пункты предсказывают провал задачи.
5. **Пороговые значения D1 (200 / 1000 / 10 000 строк) — синтез одного агента** `[мнение]`; подтверждены только
   50 и 20 (Polaris) и порог колонок «> 8» (`[консенсус]`, UX-DAT-04). В UX-DAT-05 это отмечено; виртуализацию
   считать по узлам DOM (Lighthouse 800 / 1 400).
6. **Пороги приёмки доступности (IR ≤ 0,15, Lighthouse ≥ 95) откалиброваны по одному исследованию** (A11yn,
   Best-of-8), как отмечает F2. Считать предварительными.
7. **Блок ETH содержит пункты с правовой стороной** (DSA, 152-ФЗ), которая меняется. Актуальность проверяется
   по `../06-feedback-states-motion/04-dark-patterns-and-ethics.md`, где перечислены даты и статьи.
8. **Пункт UX-OUT-12 («проверка нашла хотя бы одну проблему») формально не является свойством интерфейса** —
   это свойство проверки. Он оставлен в блоке OUT сознательно: без него агент может отчитаться «всё чисто»
   и закрыть ворота на пустом прогоне.
