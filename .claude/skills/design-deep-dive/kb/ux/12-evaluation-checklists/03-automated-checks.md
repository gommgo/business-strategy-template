## Выжимка для агента

1. **Автопроверки — ворота, а не оценка UX.** «Пройдено» и «хорошо» — разные вещи; ни один набор проверок
   не говорит, что интерфейс удобен. → §1.1, `[консенсус]`
2. **Порядок по стоимости, а не по важности**: линт → инвентарь → axe → состояния → сценарии → судья →
   человек. Провал дешёвых ворот прекращает проверку. → §2, `[исследование]`
3. **Сценарный прогон даёт в 4–5 раз больше точности, чем критика скриншота** (+3,3 против +0,7 пункта на
   WebGen-Bench). Если ресурс один — вкладывать в сценарии. → §6.1, `[исследование]`
4. **Скриншот-критика чинит вид, сценарный прогон чинит функцию, и они конфликтуют.** Нужен откат при пяти
   подряд ошибках и выбор лучшего шага. → §8.3, `[исследование]`
5. **Отбор лучшего из k безопаснее починки**: он не может внести новый дефект. Best-of-8 по axe:
   IR 0,40 → 0,14, Critical 47 → 12. → §10.3, `[исследование]`
6. **Автоматика находит ~57 % дефектов доступности по объёму, но только ~32 % критериев**, и по четырнадцати
   критериям A/AA даёт ноль. → §5.2, `[исследование]`
7. **axe-core 4.13 знает ровно одно правило для WCAG 2.2** (`target-size`, «needs review»). Пять из шести
   новых критериев не проверяются автоматом вообще. → §5.3, `[исследование]`
8. **Нормируй метрику на размер артефакта**: IR = WVS / число DOM-элементов, иначе длинные страницы
   штрафуются. → §5.4, `[исследование]`
9. **Прогоняй второго аудитора**: покрытие правил у движков различается. → §5.5, `[исследование]`
10. **Гоняй axe в обеих темах и на каждом брейкпоинте** — этого требует сам стандарт (EN 301 549, 5.2.2). →
    §5.1, `[стандарт]`
11. **`AxeBuilder.analyze()` сканирует страницу в текущем состоянии.** Модалку, форму с ошибками и пустое
    состояние надо сначала открыть локаторами. → §5.6, `[система]`
12. **Проверяй соблюдение собственных ограничений, а не только объявляй их**: 50 % провалов исполняемости на
    UI2App — их нарушение. → §3.1, `[исследование]`
13. **Инвентарь интерфейса — единственный способ найти дефекты категории «в двух и более местах»**: одно
    действие с разными именами, два стиля одной кнопки, разные форматы дат. → §4.6, `[практика]`
14. **Поиск заглушек — самая дешёвая и самая результативная текстовая проверка**: словарь `lorem`,
    `Feature 1`, `Coming soon`, `TODO`, `John Doe`, `10k+`. → §4.5, `[консенсус]`
15. **Каждое число на экране сопоставляется с полем набора данных.** Ни люди, ни модели содержательных
    ошибок не замечают. → §4.5, `[исследование]`
16. **Тёмные паттерны частично автоматизируемы**: лживый таймер ловится перезагрузкой после истечения,
    асимметрия — сравнением вычисленных стилей кнопок. → §6.6, `[исследование]`
17. **Визуальная регрессия обязательна после каждой правки**, иначе правка одного экрана ломает другой. →
    §7, `[исследование]`
18. **Растровый diff «зафаззивает» именно важные дефекты** (разные размеры иконок, разные размеры пунктов
    навигации). Блочное сопоставление устойчивее. → §7.2, `[мнение]` + `[исследование]`
19. **Core Web Vitals — UX-порог**: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1 по 75-му процентилю, раздельно для
    мобильных и десктопа. → §9, `[стандарт]`
20. **Судье давай рубрику, а не «оцени»**; несколько прогонов, перестановка позиций, зафиксированный шаблон. →
    §8, `[исследование]`
21. **Правило «стоп»: если после k вариантов ни один не прошёл ворота — проблема во входном контракте,
    а не в генерации.** → §10.4, `[исследование]`
22. **Ноль находок — неудавшийся прогон, а не чистый интерфейс.** → §10.5, `[мнение]` Нильсена

## 1. Рамка

### 1.1 Ворота, а не оценка

Автоматическая проверка отвечает на вопрос «нарушено ли известное правило», и только на него. Она не отвечает
на вопросы «решает ли экран задачу», «уместен ли этот компонент здесь», «понятен ли этот термин». Смешение
этих вопросов — главная ошибка применения (`../11-ai-generated-ui/04-constraints-prompts-and-checks.md`,
выжимка п. 25). `[консенсус]`

Два подтверждения из разных областей:
- WCAG-соответствие не гарантирует удобства: «even if you meet every high-priority checkpoint, users with
  disabilities might still be completely incapable of using your site»
  (`../08-accessibility/04-inclusive-design-and-testing.md` §1.2);
- полный цикл автоматических проверок на WebGen-Bench примерно удваивает функциональное качество
  (26,4 % → 51,9 %), но **42–48 % функциональных требований остаются невыполненными**
  (`../11-ai-generated-ui/02-research-and-benchmarks.md` §3.3). `[исследование]`

### 1.2 Три роли автопроверок

| Роль | Что делает | Что с результатом |
|---|---|---|
| **Ворота** | не выпускает артефакт с нарушением жёсткого правила | провал → назад к генерации |
| **Селектор** | ранжирует k вариантов по объективной метрике | выбрать лучший, остальные отбросить |
| **Сигнал** | помечает подозрительное для человека или судьи | попадает в отчёт как наблюдение |

Одна и та же проверка может играть разные роли в зависимости от порога: «0 нарушений Critical» — ворота,
«IR_axe» — селектор, «число уникальных стилей кнопок» — сигнал.

### 1.3 Обозначения

| Столбец | Значение |
|---|---|
| **ID** | идентификатор автопроверки для ссылок в отчётах |
| **Как** | инструмент и метод |
| **Порог** | что считается нормой; «0» = ни одного нарушения |
| **Роль** | ворота / селектор / сигнал |
| **Закрывает** | пункт сводного чек-листа `02-master-checklist.md` |

## 2. Порядок запуска и стоимость

Порядок взят из `../11-ai-generated-ui/04-constraints-prompts-and-checks.md` §4.6 и дополнен уровнями,
которых там не было (визуальная регрессия, производительность, этика).

```
УРОВЕНЬ 0 — секунды, на каждой итерации генерации
  сборка → линт кода → линт токенов → инвентарь импортов и маршрутов → поиск заглушек
  ПРОВАЛ → назад к генерации. Дальше не идём.

УРОВЕНЬ 1 — десятки секунд, на каждом готовом экране
  axe-core × {светлая, тёмная} × {360, 768, 1280, 1920} → второй аудитор
  → DOM-эвристики → скриншоты состояний (пусто, загрузка 3 с, ошибка 500, нет прав, много данных)
  → проверки размеров целей и горизонтальной прокрутки

УРОВЕНЬ 2 — минуты, на каждом готовом сценарии
  Playwright: happy path → путь с ошибками → только клавиатура → телефонный вьюпорт
  → тест переживания перехода (7 шагов) → «Назад» и deep links
  → axe внутри состояний (открытая модалка, форма с ошибками)

УРОВЕНЬ 3 — минуты и деньги, перед отбором варианта
  визуальная регрессия по всем маршрутам → Core Web Vitals
  → GUI-агент по заявленным функциям → VLM-критика по рубрике (несколько прогонов)
  → отбор лучшего из k по метрике

УРОВЕНЬ 4 — только человек, перед приёмкой
  §11
```

**Почему именно так.** Вклад каждого элемента цикла измерен на WebGen-Bench
(`../11-ai-generated-ui/02-research-and-benchmarks.md` §3.3) `[исследование]`:

| Конфигурация | Точность | Внешний вид | Start Failed | Δ точности |
|---|---|---|---|---|
| Только исполнение (текст ошибки сборки) | 45,9 | 3,0 | 4,6 | — |
| + критика скриншота VLM | 46,6 | **3,6** | 2,2 | +0,7 |
| + прохождение сценариев GUI-агентом | 49,9 | 3,4 | 1,9 | **+3,3** |
| + откат при 5 подряд ошибках | 51,2 | 3,7 | 0,2 | +1,3 |
| + выбор лучшего шага в конце | 52,6 | 3,8 | 0,2 | +1,4 |

Четыре вывода: сценарии важнее скриншотов в 4–5 раз; скриншот-критика отвечает за вид; они конфликтуют
(добавление сценариев роняет вид 3,6 → 3,4); конфликт снимается откатом и выбором лучшего шага.

**Разделение моделей экономит деньги без потери качества**: для критики скриншота и оценки прогона GUI-агента
достаточно небольшой открытой VLM (в эксперименте — Qwen2.5-VL-32B); замена её на фронтирную модель «does not
notably improve the accuracy or the appearance score». Кодогенерирующую модель маленькой заменить нельзя.
`[исследование]`

**Формат словаря.** Правило — объект, а не строка: `id`, `level` (`error` / `warning`), `lang`, `pattern`,
`flags`, **`appliesTo` (роли узлов)**, `excludes`, `message`, `replacement`, `examples` (пара «до / после»),
`source`. Без роли узла словарь даёт ложные срабатывания и его выключают целиком: «Отмена» на кнопке законна,
«Отмена» как заголовок экрана — нет. Закрытый список ролей и полная структура —
`../07-ux-writing/06-banned-words-and-patterns.md` §7.1–7.2. Роли `user-content` и `help` исключаются
из большинства проверок. **Правило без `source` в конфиг не добавляется.**

**Порядок применения словарей** (`../07-ux-writing/06-...` §7.4): артефакты копипаста и заглушки (блокирующие,
первыми и всегда) → запрещённые формулировки ошибок и отказов (блокирующие) → канцелярит, маркетинг, штампы
(по ролям узлов) → длина, форматы, согласованность (анализаторы) → уровень чтения (только для развёрнутых
текстов).

**Что делает агент при срабатывании** (там же §7.5): `error` → переписать по `replacement` и `examples`,
перепроверить; если переписать нельзя без потери смысла — сообщить явно, а не глушить правило.
`warning` → проверить контекст; законный случай добавляется в конфиг продукта **как исключение с обоснованием**,
а не выключением правила целиком.

**Ограничение, названное самим источником**: регулярные выражения по русскому — приближение; правила про
указательное «данный», цепочки родительных и деепричастия дадут ложные срабатывания, и для продакшн-линтера
нужен морфологический разбор (pymorphy, Natasha).

## 5. Доступность

Полные правила — `../08-accessibility/`; здесь — инструментальная часть и пороги.

### 5.1 Матрица прогонов

axe-core прогоняется **на каждом маршруте × две темы × четыре ширины** (360, 768, 1280, 1920). Формально
этого требует сам стандарт: EN 301 549, 5.2.2, Note 3 (`../08-accessibility/04-inclusive-design-and-testing.md`
§5.7). Для приложения из 12 маршрутов это 96 прогонов; при длительности прогона в секунды это уровень 1
по стоимости. `[стандарт]`

Отдельно прогоняется axe **внутри состояний**, которых нет на «чистой» странице: открытая модалка, форма
с ошибками, пустое состояние, состояние загрузки, длинный контент (§5.6).

### 5.2 Сколько закрывает автоматика

Данные Deque: 2000+ аудитов, 13 000+ страниц, 294 958 дефектов, движок axe-core
(`../08-accessibility/04-inclusive-design-and-testing.md` §5.2). `[исследование]`

- **57,38 % дефектов найдено автоматикой** (169 242 из 294 958).
- **Покрытие по критериям — 16 из 50 (≈ 32 %)** для WCAG 2.1 AA.
- Топ-5 критериев дают 78,51 % всех дефектов; один только 1.4.3 Contrast — 30,08 %.

### 5.4 Метрика и пороги

**WVS (Weighted Violation Score)** = 1·Minor + 2·Moderate + 3·Serious + 4·Critical (веса уровней axe).
**IR (Inaccessibility Rate)** = WVS / число DOM-элементов — нормировка, чтобы длинные страницы не
штрафовались (`../11-ai-generated-ui/02-research-and-benchmarks.md` §3.4). `[исследование]`

| Ворота | Порог | Обоснование |
|---|---|---|
| Нарушения **Critical** | **0** | у лучших вариантов Best-of-8 их 12 на весь корпус из 300 заданий |
| Нарушения **Serious** | **0** на продуктовых экранах | те же данные |
| **IR_axe** | **≤ 0,15** | лучший результат Best-of-8 — 0,14; лучшая фронтирная модель без мер — 0,13 |
| **Lighthouse Accessibility** | ≥ 95 | Best-of-8 доводит базовую модель до 95,43 |
| Второй аудитор | нет новых Critical | покрытия движков различаются |
| Контраст токенов | 0 нарушений пар | линт до рендера |
| Ручной протокол | 6 из 6 проходов без блокеров | `../08-accessibility/04-...` §5.4 |
| Клавиатурный сценарий | проходится до конца | автотест Playwright |

Ориентир по разбросу: у фронтирных моделей IR_axe без специальных мер 0,13–0,45; Best-of-8 опускает до 0,14.

### 5.5 Второй аудитор

Авторы A11yn делают кросс-проверку axe + AChecker, следуя рекомендации литературы: покрытие правил и
эвристики у аудиторов различаются (`../11-ai-generated-ui/02-research-and-benchmarks.md` §3.4).

## 6. Сценарные тесты

### 6.1 Почему это главный уровень

Прохождение сценариев GUI-агентом даёт **+3,3 пункта точности** против **+0,7** у критики скриншота —
разница в 4–5 раз (§2). Если бюджет один, он идёт сюда. `[исследование]`

Два режима:
- **Playwright по заранее описанным сценариям** — когда есть спецификации из входного контракта;
- **GUI-агент с генерируемой инструкцией «обойти все заявленные функции»** — когда сценарии не описаны;
  в WebGen-Agent инструкция генерируется отдельным промтом с one-shot примером, и ручная проверка выборки
  показала, что **98,3 %** инструкций хорошо покрывают требования (`../11-ai-generated-ui/04-...` §4.4).

### 6.2а Матрица тестирования

Полная матрица — `../09-mobile/04-platform-conventions-and-browser-quirks.md` §7. Рабочий минимум:

**Ширины для скриншотов и прогонов** (CSS px): **320** (требование WCAG 1.4.10, окно 1280 при зуме 400 %),

**Браузеры** (список GOV.UK, покрывающий ~98 % их трафика, редакция февраля 2026): iOS — Safari, Chrome, Edge;

сеть (быстрая / Slow 4G / офлайн); устройство (быстрое / CPU ×4–×6); ввод (тач / тач + внешняя клавиатура);
контекст (обычный браузер / in-app браузер / установленный PWA); доступность (VoiceOver / TalkBack).

| В DevTools | Только на реальном устройстве |

без каждого жеста → axe **на каждом брейкпоинте**.

**Десятиминутный прогон одного экрана на телефоне** (`../09-mobile/04-...` §7.5, 14 шагов): 360 px без
горизонтальной прокрутки → видна ли задача экрана на первом экране → ландшафт → попадание пальцем в каждую цель
с первого раза → зум при фокусе на поле, видимость подписи и подсказки → видимость ошибки при открытой
клавиатуре → системный «Назад» → закрытие оверлея тремя способами с одинаковым результатом → свернуть браузер
на минуту и вернуться → авиарежим → VoiceOver/TalkBack по основному пути → максимальный системный размер текста
→ открытие из мессенджера (in-app браузер) → замедленный CPU.

## 7. Визуальная регрессия

### 7.1 Когда полезна

- **После каждой правки** — ловит дефект F8.4 (правка одного экрана ломает другой). Это обязательный шаг
  цикла `../11-ai-generated-ui/04-...` §4.5. `[исследование]`
- **При смене версии дизайн-системы или токенов** — вместе с `diff` линтера токенов.
- **Не полезна** на экранах с живыми данными без фиксации фикстур: дифф будет шуметь.

|---|---|---|---|---|

| AC-VIS-02 | Скриншоты всех состояний (пусто, загрузка, ошибка) сняты и сохранены как базовая линия | набор фикстур | полный набор | UX-STA-18 |
| AC-VIS-03 | Скриншоты на всех ширинах совпадают с базовой линией | дифф по ширинам | 0 неожиданных | UX-MOB-01 |
| AC-VIS-04 | Squint-тест: при понижении разрешения до ~20 px остаётся одна точка входа | преобразование скриншота + судья | 1 точка | UX-LAY-04 |
| AC-VIS-05 | Grayscale: смысл сохраняется | преобразование + судья | 0 потерь | UX-A11-13 |

### 7.2 Ограничение растрового диффа

Приём из сообщества: агент открывает страницу в размерах макета, снимает скриншот, сравнивает с макетом
через ImageMagick с порогом сходства, откатывает изменения, снижающие сходство, и останавливается после
фиксированного числа циклов. Три важные детали из первоисточника: размытие не больше 10 % (шрифты рендерятся
иначе); откат ухудшающих изменений; жёсткий лимит циклов с отчётом
(`../11-ai-generated-ui/04-...` §3.6). `[мнение]`

**Известное ограничение того же приёма**: растровый дифф «зафаззивает» именно те дефекты, которые важны, —
разные размеры пунктов навигации, разные размеры иконок, низкое разрешение изображений на HiDPI. То есть
сравнение с референсом ловит крупную геометрию и не ловит мелкую.

**Академический аналог, который устойчивее**: блочное сопоставление с разбором по Size / Text / Position /
Color (метрики Design2Code и VFS в UI2App). Оно устойчивее к различиям реализации, чем попиксельный дифф.
`[исследование]`

## 8. Мультимодальная критика

### 8.1 Как подавать

| Правило | Почему |
|---|---|
| Давать **рубрику**, а не «оцени интерфейс» | свободная оценка не воспроизводима; рубрики — `01-expert-review-protocols.md` §7.8 |
| Подавать **скриншоты по состояниям**, а не один «идеальный» | пропуски систематически теряются |
| Подавать **изображение и текст вместе** (V + T) | только визуал и только текст по отдельности дают неудовлетворительный результат; V + T стабильно лучше обеих (Interaction2Code) `[исследование]` |
| **Увеличивать область мелкого взаимодействия** | при изменении менее ~2,5 % площади воспроизведение падает до нуля; при трёхкратном увеличении CLIP и SSIM ≈ 0,8 `[исследование]` |
| **Обводить область рамкой** (Mark prompt) | Claude-3.5-Sonnet +11 % к usability против прямого промта, +8 % против CoT `[исследование]` |
| **Скрывать «красоту»**, если цель — функция | обесцвеченный скриншот или структурная схема; иначе судья оценивает вид |
| **Не отдавать содержание и числа** | слепота к содержанию измерена (коэффициент −0,354) |

### 8.3 Конфликт скриншот-критики и сценарного прогона

Измерено: добавление сценарного прогона поднимает точность на +3,3 и **роняет внешний вид на −0,2**, потому
что «modifying the codebase for functional fulfillment sometimes damages the website appearance or causes
errors». Конфликт снимается двумя механизмами `[исследование]`:

**Правило отката, готовое к переносу**: если 5 подряд шагов содержат ошибки выполнения — вернуть траекторию
и кодовую базу к лучшему предыдущему шагу. **Лучший шаг** = максимум балла сценарного теста, затем максимум
балла внешнего вида, затем самый поздний.

**Выбор лучшего шага в конце**: тем же правилом выбирается лучший шаг из всех, потому что поздние правки
не обязательно улучшают. Вместе откат и выбор дают +2,7 точности и возвращают внешний вид с 3,4 до 3,8.

### 8.4 Сравнение с референсом

Если есть эталонный макет: блочное сопоставление (Size / Text / Position / Color), а не попиксельный дифф
(§7.2). Если эталонных близнецов нет, а в наборе есть узнаваемые интерфейсы — обязательны **синтетические
близнецы** (`01-expert-review-protocols.md` §7.4).

### 10.3 Отбор вместо починки

**Отбор лучшего из k по объективной метрике безопаснее починки**, потому что не может внести новый дефект.

|---|---|---|---|---|
| Базовая модель | 0,40 | 4 479 | 47 | 90,88 |

контраста и структуры лендмарков: «post-hoc prompting remains prone to unintended regressions»; стоит
4 584 промежуточных токена на запрос. Рост k до 20 даёт убывающую отдачу.

**Обобщение**: селектором годится любая метрика, считаемая без человека — число нарушений axe, число ошибок
сборки, доля пройденных сценарных тестов, число элементов вне дизайн-системы, наличие всех обязательных
состояний, балл PURE.

### 10.4 Правило «стоп» на входном контракте

**Если после k вариантов ни один не проходит ворота — проблема во входном контракте, а не в генерации.**
Возвращаться к требованиям (какие компоненты, какие состояния, какая дизайн-система), а не запускать цикл
починки (`../08-accessibility/04-inclusive-design-and-testing.md` §5.8). `[исследование]`

Диагностика, какой именно пункт контракта пропущен:

| Что массово провалилось | Что не дано на входе |
|---|---|
| состояния (AC-LNT-15, AC-SCF-09…13) | UX-PRE-08: состояния не перечислены поимённо |
| маршруты и тупики (AC-NAV-11, AC-NAV-12) | UX-PRE-06: карта экранов не закрыта |
| переживание перехода (AC-SAV-01…07) | UX-PRE-07: не сказано, что переживает переход |
| тексты и числа (AC-TXT-01…03) | UX-PRE-10, UX-PRE-11: нет данных и глоссария |
| компоненты вне системы (AC-BLD-06) | UX-PRE-09: система подана документацией, а не кодом |
| формы (AC-FRM-*, AC-SCF-01…08) | UX-PRE-15: контракт формы не заполнен |
| доступность (§5.4) | UX-PRE-18: уровень не объявлен явно |

### 10.5 Ноль находок

**Прогон, вернувший ноль находок, считается неудавшимся прогоном, а не чистым интерфейсом**
(`01-expert-review-protocols.md` §10.1). Практическая проверка: WebAIM Million 2026 находит автоматически
обнаруживаемые нарушения WCAG на **95,9 %** главных страниц миллиона сайтов [S2]. Ноль нарушений axe на
нетривиальном приложении почти всегда означает, что axe запущен не на том, что надо (не на всех маршрутах,
не во всех темах, не в раскрытых состояниях).

## 11. Чего автоматика не находит никогда

### 11.1 Список из первоисточников

Из `../11-ai-generated-ui/04-constraints-prompts-and-checks.md` §6 и
`../08-accessibility/04-inclusive-design-and-testing.md` §5.3:

1. **Достижимость маршрутов через вложенные меню, модальную маршрутизацию и условные ссылки.** UI2App
   считает NRS человеком именно потому, что это «cannot be reliably enumerated programmatically».
2. **Соответствие реализации рубрике взаимодействия.** «Runtime probing alone cannot reliably determine
   whether different implementations satisfy the same interaction rubric».
3. **Уместность решения задаче.** «An unsolicited interactive dashboard nobody needed is a design failure
   even if it's technically flawless».
4. **Приоритет содержимого против визуального веса.** Метрика измерит площадь и контраст, но не знает,
   что здесь важнее.
5. **Доверие и приемлемость.**
6. **Корректность самого словаря домена.** Словарь ловит несоответствие словарю, но не ловит, что словарь неверен.
7. **Достаточность обучающего эффекта интерфейса.**

По текстам словарь не ловит (`../07-ux-writing/06-banned-words-and-patterns.md` §8): синтаксис элемента
(подпись чекбокса «Включена» лексически безупречна и неверна по сути); уместность тона; заголовок, обещающий
несуществующее; формально правильный и бессмысленный текст; термин, непонятный аудитории; неверный выбор слова
из законной пары («Сохранить» вместо «Готово»); trick wording и мягкие тёмные приёмы; соответствие текста
реальному поведению («Удалить» может архивировать).

По доступности автоматика не находит **никогда**: порядок фокуса; видимость фокуса; перекрытие фокуса
липкой панелью; ловушку фокуса; корректность alt по смыслу; качество доступных имён; логичность порядка
чтения; reflow; контраст границ и состояний; смысл текста ошибки; альтернативу перетаскиванию;
консистентность помощи; повторный ввод; доступность аутентификации; hover-only; правильность объявлений
живых областей; поведение при масштабировании; forced-colors.

### 11.2 Что из этого может закрыть сценарный агент

Часть «ручного» на самом деле автоматизируема сценарием, если у агента есть браузер:

| Пункт | Как закрывается сценарием | ID |
|---|---|---|
| Порядок фокуса | Tab по странице, сравнение с DOM-порядком | AC-SCF-08 |
| Видимость фокуса | скриншот сфокусированного элемента + анализ контраста | AC-A11-01 |
| Перекрытие фокуса | `elementFromPoint` | AC-A11-08 |
| Ловушка фокуса | Tab по кругу с ограничением числа шагов | AC-SCF-16 |
| Hover-only | статический анализ + сравнение DOM при hover и focus | AC-LNT-07 |
| Повторный ввод (3.3.7) | прогон до второго вопроса | AC-FLW-12 |
| Reflow | скриншоты на ширинах + горизонтальная прокрутка | AC-LAY-01 |
| forced-colors | эмуляция в DevTools | AC-A11-20 |
| Альтернатива перетаскиванию | инвентарь dnd против списка альтернатив | AC-A11-13 |

Остаются человеку: **смысл alt и доступных имён**, **логичность порядка чтения**, **смысл текста ошибки**,
**консистентность помощи по содержанию**, **уместность**, **приоритет содержимого**, **доверие**,
**корректность словаря**, **обучаемость** — и весь §11.1 пункты 3–7.

### 11.3 Симуляция пользователей не закрывает этот список

UXAgent позиционируется как инструмент **отладки дизайна исследования** до реального теста с людьми, а не
как замена теста; в его эвристической оценке с пятью UX-исследователями участники высказали опасения по
поводу LLM-агентных UX-исследований. PerceptUI прямо критикует существующие MLLM-оценки за то, что они дают
«surface-level critiques or a judgment that reflects the model's own biases rather than the genuine response
of a particular user» (`../11-ai-generated-ui/04-...` §6). Подробнее — `04-metrics-and-user-testing.md` §8.
`[исследование]`

## 12. Инструменты 2026

### 12.1 Что можно запускать локально

| Инструмент | Роль | Что даёт | Ограничение |
|---|---|---|---|
| **axe-core** (4.13) в headless-браузере | основной движок доступности | 60 правил WCAG 2.0, 2 правила 2.1, 1 правило 2.2 | не даёт ложных срабатываний, поэтому и не покрывает спорное |
| **@axe-core/playwright** | axe внутри сценарных тестов | проверка состояний, которых нет на чистой странице | сканирует состояние на момент вызова [S1] |
| **Lighthouse / Lighthouse CI** | сводный балл и тренд, CWV | удобен как порог и как история | подмножество axe плюс эвристики; не заменяет axe |
| **pa11y / pa11y-ci** | обёртка для CI | поддерживает axe и HTML_CodeSniffer как движки | то же покрытие, что у движка |
| **eslint-plugin-jsx-a11y** | линт до сборки | дёшево ловит `div` с `onClick`, `img` без alt, `a` без href, положительный `tabindex` | статически; не видит вычисленную разметку |
| **Playwright** | сценарные тесты, скриншоты, эмуляция устройств, троттлинг, forced-colors | главный инструмент уровня 2 | требует описанных сценариев или GUI-агента |
| **Storybook interaction tests** | проверка компонента в изоляции, включая состояния и клавиатуру | состояния компонента заводятся как истории и проверяются автоматически | проверяет компонент, не экран и не путь |
| **Chromatic** (или любой визуальный регресс) | базовая линия скриншотов, дифф по PR | ловит F8.4 | шумит на живых данных; нужны фикстуры |
| **Второй аудитор** (AChecker, HTML_CodeSniffer, WAVE API) | кросс-проверка | покрытия движков различаются | разные трактовки одних критериев |
| **Линтер токенов** (`@google/design.md lint` или свой) | контраст пар до рендера | ловит тёмную тему на уровне системы | не видит runtime-цвета |
| **NerdeRegion** | отладка живых областей | список областей и лог мутаций с таймкодами | ручной инструмент |
| **ImageMagick / любой растровый дифф** | сравнение с макетом | дёшево | «зафаззивает» мелкую геометрию (§7.2) |
| **Линтер текстов** (свой, по словарю `../07-ux-writing/06-banned-words-and-patterns.md` §7) | запрещённые слова и формулировки по ролям узлов | единственная проверка текстов, кроме судьи | регулярки по русскому — приближение, нужен морфоанализ |
| **Собственные DOM-скрипты** | §4 целиком | закрывают то, чего нет ни в одном движке | писать и поддерживать самому |

### 12.2 Чего нет

- **UX-линтера** в смысле «проверь, что интерфейс удобен», не существует. Все инструменты проверяют либо
  доступность, либо код, либо визуальную стабильность. Правила уровня «одна primary-кнопка», «фильтры в URL»,
  «состояние переживает переход» пишутся самостоятельно по §4 и §6.
- **Публичного бенчмарка UX админок** не существует (`../11-ai-generated-ui/02-research-and-benchmarks.md`,
  открытые вопросы). Ближайшее — UI2App (категория Admin) и WebGen-Bench (Data Management), но оба меряют
  воспроизведение и исполняемость, а не удобство.
- **Автопроверки соответствия дизайн-системе по смыслу** (тот ли компонент выбран для задачи) — только
  судья или человек.

## Частые ошибки

1. **Считать «прошло автопроверки» оценкой UX.** §1.1.
2. **Запускать дорогие проверки до дешёвых.** Сценарный прогон на несобирающемся приложении бессмысленен. §2.
3. **Вкладываться в скриншот-критику вместо сценариев.** Разница 4–5 раз. §2.
4. **Не откатываться при конфликте вида и функции.** Сценарные правки роняют вид; нужен откат и выбор
   лучшего шага. §8.3.
5. **Гонять axe только на «чистой» странице.** Модалка, форма с ошибками и пустое состояние не проверяются. §5.6.
6. **Гонять axe в одной теме и на одной ширине.** §5.1.
7. **Верить, что axe покрывает WCAG 2.2.** Одно правило из шести новых критериев. §5.3.
8. **Использовать абсолютное число нарушений вместо нормированного.** Длинные страницы штрафуются. §5.4.
9. **Чинить вместо отбора.** Починка вносит новые дефекты. §10.3.
10. **Останавливаться на k = 20.** Убывающая отдача после 8. §10.3.
11. **Запускать цикл починки, когда ни один из k вариантов не прошёл.** Проблема во входном контракте. §10.4.
12. **Считать ноль находок успехом.** §10.5.
13. **Отдавать судье то, что проверяется детерминированно** (числа, тексты, наличие элементов). §8.1.
14. **Один прогон судьи.** §8.2.
15. **Менять формулировку рубрики без перезамера.** §8.2.
16. **Растровый дифф как единственная визуальная проверка.** Мелкая геометрия теряется. §7.2.
17. **Визуальная регрессия на живых данных без фикстур.** Шум. §7.1.
18. **Проверять CWV в лаборатории и считать, что INP измерен.** Нужны полевые данные. §9.
19. **Не прогонять второго аудитора.** §5.5.
20. **Не перезапускать проверки после смены модели или промта.** §8.2, AC-JDG-09.

## Чек-лист

1. Ворота уровня 0 прогоняются на каждой итерации генерации, а не один раз в конце?
2. Провал ворот прекращает проверку и возвращает к генерации?
3. axe прогнан на каждом маршруте × две темы × четыре ширины?
4. axe прогнан внутри состояний (модалка, форма с ошибками, пусто, загрузка, ошибка)?
5. Включены принудительно best-practice-правила из §5.3?
6. Прогнан второй независимый аудитор?
7. Метрика нормирована (IR = WVS / число DOM-элементов)?
8. Прогнан линт токенов до рендера?
9. Прогнаны собственные DOM-эвристики (§4), а не только axe?
10. Собран инвентарь интерфейса (кнопки, поля, иконки, форматы дат и чисел, статусы)?
11. Прогнан поиск заглушек и сверка чисел с набором данных?
12. Прогнаны сценарные тесты: happy path, ошибки, клавиатура, телефон, тёмная тема, медленная сеть, роль без прав?
13. Прогнан тест переживания перехода из семи шагов?
14. Прогнаны проверки деструктивных действий и массовых операций?
15. Прогнаны автопроверки тёмных паттернов (§6.6)?
16. Визуальная регрессия прогнана после каждой правки, а не в конце?
17. Core Web Vitals измерены по 75-му процентилю, раздельно для мобильных и десктопа?
18. Судья прогнан нужное число раз, с перестановкой позиций, по зафиксированной рубрике?
19. Выбран лучший из k по метрике, а не по виду?
20. Все ворота §10.1 пройдены?
21. Прогон вернул хотя бы одну находку?
22. Список §11.1 явно передан человеку, а не объявлен «проверенным»?

## Открытые вопросы и противоречия

1. **Пороги доступности откалиброваны по одному исследованию.** IR ≤ 0,15 и Lighthouse ≥ 95 выведены из
   A11yn (Best-of-8). Отмечено агентом F2 и подтверждаю: считать предварительными до собственного замера.
2. **Данные о покрытии автоматики — 2021 год и WCAG 2.1.** axe с тех пор вырос (4.13 против версий 2021
   года), но публичного повторного замера нет. 57 % / 32 % — порядок величины.
3. **Как выбирать k в Best-of-N для не-доступностных метрик — неизвестно.** Для axe N = 8 разумно,
   N = 20 избыточно; для сценарной точности и для PURE данных нет.
4. **Число прогонов судьи (11)** получено на текстовых задачах двумя судьями одного провайдера; для
   мультимодальной оценки интерфейса не перепроверено.
5. **Ложные срабатывания собственных DOM-эвристик не измерены.** Например, AC-NAV-09 (одна primary-кнопка)
   будет срабатывать на экранах с несколькими независимыми секциями, если секции не размечены. Каждое
   правило §4 требует прогона на заведомо корректном корпусе до включения в ворота. `[мнение]`
6. **Порог «два дубля видны одновременно»** (агент B, `[исследование]`) не превращён в автопроверку:
   определение «видны одновременно» зависит от вьюпорта и прокрутки. AC-NAV-10 проверяет дубли в DOM,
   что строже.
7. **Проверка AC-TXT-03 (числа против набора данных) требует, чтобы набор данных был машиночитаем.**
   Если фикстуры генерируются той же моделью, проверка вырождается. Нужен независимый источник данных.
8. **AC-CNS-09 (одинаковый состав атрибутов объекта в разных представлениях)** предполагает, что известно,
   какие DOM-узлы соответствуют каким полям объекта. Без разметки `data-field` реализуема только
   эвристически.
9. **INP в лаборатории не измеряется.** Синтетический прогон взаимодействий даёт оценку, но не полевое
   значение; порог 200 мс относится к 75-му процентилю реальных пользователей.
10. **Storybook interaction tests и Chromatic** названы в задании как инструменты 2026; я прочитал
    документацию Storybook по interaction tests, но не измерял их полезность для генеративного конвейера.
    Гипотеза: они закрывают уровень компонента (девять состояний элемента, клавиатурный контракт), который
    иначе проверяется дороже, на уровне экрана. Не проверено.
11. **Проверка «оверлеи, не инициированные человеком» (AC-SCF-15)** требует различать оверлей, открытый
    действием, и оверлей, открытый таймером или условием. Реализуется через сопоставление события открытия
    с последним пользовательским событием; порог по времени (например, 500 мс) не обоснован данными.
