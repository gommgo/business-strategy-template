# UX Research — база знаний для агента-проектировщика интерфейсов

Статус: **волны 1–4 завершены (22 сентября 2026)**. Четыре волны, 27 агентов: 57 содержательных файлов + 13 README папок
(54 376 строк), 79 дайджестов видео из 84 роликов каталога, 28 отчётов агентов, кэш 1 003 страниц. Волна 4 — аудит
(`99-raw/reports/wave4-X-audit.md`) и синтез: этот README (выжимка и реестр противоречий), `00-glossary.md`,
`90-sources/` (библиография), `12-evaluation-checklists/master-checklist.yaml`, `07-ux-writing/before-after.tsv`,
`99-raw/handoff-to-ui-research.md`. Как расширять базу — `PLAN.md`, раздел «Итог».

Соседняя база: `../ui/` — визуальный слой (цвет, типографика, размеры, форма, сетка в числах, токены, атлас
дизайн-систем, стили). Здесь — UX: структура, навигация, анатомия экранов, компоненты как поведение, сценарии,
состояния, обратная связь, тексты, доступность как правила, мобильные паттерны, ошибки нейросетей в UX, оценка,
плейбуки по типам приложений. Там, где база даёт минимальное число (контраст, размер цели), точное значение берётся
из `../ui/`; все такие места собраны в `99-raw/handoff-to-ui-research.md`.

## Как пользоваться (для агента)

Единицы базы: папка → `README.md` (список файлов и выжимка папки на 10 строк) → файл → первый раздел «Выжимка для
агента» (15–60 правил с меткой уровня и ссылкой `→ §`) → тело файла → «Частые ошибки» (с номерами дефектов `F1.1–F13.4`) →
«Чек-лист» → «Открытые вопросы» → «Источники». Ссылки вида `04-components-patterns/05 §4.3` означают папку, номер файла и
раздел; `[V:<id> mm:ss]` — дайджест видео в `91-videos/digests/`. Если правило повторяется в нескольких файлах, полная
формулировка с источниками живёт в файле-каноне (перечень канонов — `99-raw/reports/wave4-X-audit.md`, раздел 2.1);
остальные места — одна строка и ссылка. Если два места базы расходятся, действует реестр противоречий ниже.

Три сценария входа:

1. **Спроектировать с нуля.** `13-app-types/04-master-procedure-brief-to-screens.md` (30 шагов, у каждого — артефакт и
   проверка) → плейбук типа продукта: `13-app-types/01` (админка), `02` (клиентский сервис), `03` (ИИ-функции) →
   объекты и язык: `01-foundations/03`, `07-ux-writing/01 §10` → сценарии по шаблону `05-flows-journeys/02 §1.4` →
   ИА и навигация `02-ia-navigation/01–02` → анатомия экранов `03-layout-placement/01` → компоненты по потребности
   (`04-components-patterns/`) → контракт состояний `06-feedback-states-motion/01 §2` → тексты `07-ux-writing/02` →
   доступность `08-accessibility/01–02` → телефон `09-mobile/01` → контракт генерации `11-ai-generated-ui/04 §1` →
   перед отдачей — сводный чек-лист `12-evaluation-checklists/02` (и его YAML). Выжимка ниже — это то, что обязано быть
   в голове на каждом шаге.
2. **Проверить готовый интерфейс.** `12-evaluation-checklists/01` (протокол: задачи → 3–5 проходов линзами →
   серьёзность отдельным проходом → отчёт из шести полей) → `12-evaluation-checklists/02` (434 пунктов `UX-<БЛОК>-<NN>`
   с серьёзностью и способом проверки; машиночитаемо — `master-checklist.yaml`) → `12-evaluation-checklists/03`
   (автопроверки `AC-*` как ворота: линт → инвентарь → axe в двух темах → состояния → сценарии → судья → человек) →
   `08-accessibility/04 §5` (ручной протокол из шести проходов) → `09-mobile/04 §7` (матрица устройств) → классификация
   находок по каталогу дефектов `11-ai-generated-ui/01`. Спорные места сверяй с реестром противоречий ниже; числа
   для приёмки — `12-evaluation-checklists/04`.
3. **Исправить сгенерированный интерфейс.** Сначала классифицируй дефект по `11-ai-generated-ui/01` (`F1.1–F13.4`:
   маршруты, состояния, формы, консистентность, доступность, тексты) → реши, чинить или перегенерировать: отбор лучшего
   из k по метрике надёжнее починки, сценарный прогон чинит функцию, скриншот-критика — вид (`11-ai-generated-ui/04 §3`)
   → правь по файлу темы дефекта (состояния — `06-feedback-states-motion/01`, формы — `04-components-patterns/05`,
   таблицы — `04-components-patterns/01`, тексты — `07-ux-writing/06` как линтер) → границы правки и стартер
   (`11-ai-generated-ui/03 §2–§3`, `10-design-systems-consistency/02 §8`) → визуальный регресс по всем маршрутам →
   ворота `12-evaluation-checklists/03 §10`.

Соседняя база `../ui/` даёт числа визуального слоя (контраст, шкала отступов, размеры контролов, токены,
стили) и свои чек-листы `../ui/13-evaluation-checklists/` (визуальный QA, рубрики VLM-критика, автопроверки
токенов); здесь эти числа не дублируются — даётся минимум по стандарту и ссылка.

## Легенда меток уровня доказательности

Девять меток (шесть из `PLAN.md` плюс три, которые фактически используются в файлах и узаконены аудитом):

| Метка | Что означает | Как читать |
|---|---|---|
| `[исследование]` | Число или утверждение из эмпирической работы с описанной методикой: айтрекинг, эксперимент, бенчмарк, опрос с известным N | Самая сильная метка; год и выборка — в файле рядом с числом |
| `[консенсус]` | Совпадение нескольких независимых авторитетных источников (NN/g, дизайн-системы, стандарты) без собственного измерения | Правило берётся по умолчанию |
| `[стандарт]` | Норма стандарта или закона: WCAG 2.2, WAI-ARIA APG, EN 301 549, ICU, CSS, DSA, FTC, 152-ФЗ | Это требование, а не эмпирика; в старых файлах — `[APG]`, `[норма]`, «`[исследование]` (норма)» |
| `[система]` | Правило одной дизайн-системы или документации продукта (Carbon, Material 3, GOV.UK, Primer, Apple HIG, GitHub, Stripe) | Норма её библиотеки, не доказательство; при выборе своей системы — держать её везде |
| `[данные]` | Первичные данные без эксперимента: собственные подсчёты агента (каталог 95 систем), отчёты вендоров (Retool), пересказ чужих замеров без методики | Порядок величины, не константа |
| `[практика]` | Устоявшийся приём индустрии либо синтез агента по механизму; источника с измерением нет | Применять, отмечая отсутствие данных |
| `[мнение]` | Позиция одного автора, в том числе авторитетного (Купер, Нильсен, Бирман, Фридман) | При цитировании называть автора; «`[мнение]` Нильсена» — эта же метка |
| `[спорно]` | Источники расходятся; позиция базы — синтез с условием | Условие — в реестре противоречий ниже |
| `[V:<id> mm:ss]` | Ссылка на дайджест видео с таймкодом | Не уровень: рядом ставится одна из меток выше |

Составные метки разрешены и не разбиваются: `[стандарт]` + `[исследование]` — норма плюс измеренная частота её
нарушения; `[исследование]` + `[спорно]` — измерение есть, но обобщение на другие задачи спорно; `[V:…]` + `[мнение]` —
позиция докладчика. Метки `[рамка проекта]` и `[решение базы]` (встречаются в `13/04`, `07/README`) — решения этой базы,
читать как `[мнение]`. В сводную выжимку ниже входят только правила с ядром не ниже `[консенсус]` (или `[стандарт]`);
детали правила могут быть `[система]` и `[практика]` — они помечены внутри строки.

**Оговорки к числам**, которые цитируют чаще всего (подробности — в «Открытых вопросах» файлов):

- Nielsen 1997 (+58 % / +47 % / +27 % / +124 %, «читают 20 %») получен на маркетинговом веб-тексте; на микрокопи
  приложений не проверялся. Числа сгиба (57 / 74 / 42 %, разница 84 %) — сайты, не приложения с постоянной навигацией.
- «10 / 20 / 30 секунд» до решения остаться — веб-страницы, а не приложения с авторизацией.
- «Бюджет подтверждений 2–3 на сессию» — числа нет ни в одном источнике; измерено только привыкание после второго
  показа предупреждения. «98 % выбирают один ответ» — иллюстрация Microsoft, не замер.
- «3–6 показателей на дашборде», «правило 5 секунд», «80 % внимания левой половине» — практика без измерения.
- Deque 57 % / 32 % / 16 из 50 — данные 2021 года по WCAG 2.1; WebAIM Million — главные страницы публичного веба, не
  админки. Один оценщик находит 42 % / 32 % — Nielsen 1992, шесть интерфейсов начала 1990-х.
- IR ≤ 0,15 и Lighthouse ≥ 95 как ворота приёмки — одно исследование (A11yn, Best-of-8). 11 прогонов судьи, 13,6 %
  переворотов — текстовые задачи, для мультимодальной оценки не перепроверено. F1 ≥ 0,8 для судьи — рекомендация NN/g.
- Retool (2 276 / 86 / 48 / 22 %) — опрос вендора; 18 правил Microsoft — 2019 год, до LLM; «~90 % точности ИИ» — не порог.
- Пороги таблиц 200 / 1 000 / 10 000 строк и 8 / 12 колонок — синтез D1 (подтверждены только 50 у Polaris и 20 у
  Primer); мобильные пороги 3–4 колонки / 20 объектов / 200–300 строк — расчёт F1.
- Отложенный показ индикатора 200–400 мс и минимум 300–500 мс — практика индустрии, первоисточника нет; тайминги
  мега-меню 0,5 / 0,1 с — эвристика NN/g без эксперимента.
- `autocomplete` «−≥30 % времени», «400 мс на переключение клавиатура ↔ мышь», «6–7 полей на шаг» — со слайдов одного
  докладчика (Фридман), первоисточники не названы.
- «Кириллица +10–15 %» — рабочее число отчётов волн 1–2; позиция базы — 10–30 %, короткие строки в 2–3 раза (W3C/IBM).
- «Статистика NN/g о 50 сгенерированных дашбордах (92 % / 78 % / 100 %)» — не существует; пример выдуманной цитаты.

## Выжимка: 60 сквозных правил

Отбор: правило повторяется в двух и более папках либо имеет измеренное число; ядро правила — уровень не ниже
`[консенсус]` (детали могут быть `[система]` или `[практика]` — так и помечены). У каждого правила: формулировка с числом
или условием · уровень · файл-канон и раздел. Правила с ядром ниже `[консенсус]` — в блоке «Практика и спорное» после
выжимки. Порядок — по этапам процедуры `13-app-types/04`.

### 1. Бриф и постура

1. **Постуру определи до первого экрана и отдельно для каждой роли.** Суверенный инструмент (ежедневная многочасовая
   работа) — плотно, консервативно по цвету, богатая немодальная обратная связь, акселераторы, расчёт на «вечного
   середняка»; транзитный — одно окно, крупные контролы, развёрнутые подписи, никаких вложенных диалогов. Класс продукта
   задаёт допущения: в экспертном инструменте документация и обучение легитимны, но дефекты не компенсируют; в клиентском
   сервисе обучение исключается из допущений вовсе. Порог «> 1 ч в день» и модель постур (Купер) — `[мнение]`.
   — `[консенсус]` / `[исследование]` — `01-foundations/01 §5.1`; `13-app-types/01 §1.2, §2`; `13-app-types/02 §2, §5`.

### 2. Объекты и язык

2. **Глоссарий объектов и словарь действий — до экранов.** Одно понятие — одно слово, одно слово — одно понятие
   («аккаунт» и «профиль» на одном экране — два разных места в голове пользователя; 14 терминов для «видео» в одном
   проекте — измеренный симптом запущенности). Имя действия не меняется по потоку: кнопка «Опубликовать» → диалог
   «Опубликовать?» → тост «Опубликовано» → статус «Опубликован». — `[консенсус]` / `[система]` —
   `07-ux-writing/01 §10.1, §10.3`; `10-design-systems-consistency/02 §3.2, §3.5`; `04-components-patterns/10 §1.4`.
3. **Объект → действие.** Сначала выбирается объект, потом действие над ним; с карточки каждого объекта достижимы все
   связанные объекты; тупиков нет — у каждого конечного состояния есть «что дальше». — `[консенсус]` —
   `01-foundations/03 §7, §11`; `05-flows-journeys/02 §5.4`.
4. **Дефолты — самый сильный рычаг.** Настройки почти не меняют: поле предзаполняется самым частым значением; в диалоге
   подтверждения дефолтной кнопки нет; предвыбор — только безопасных значений, которые не расширяют обязательства,
   сбор данных или расходы; в радиогруппе фактического вопроса предвыбора нет, у настройки с безопасным умолчанием —
   есть. — `[исследование]` / `[консенсус]` — `01-foundations/01 §10.4, §14.3`; `06-feedback-states-motion/04 §8.2`;
   `05-flows-journeys/03 §4.3`; `04-components-patterns/06 §4.4`.

### 3. Сценарии

5. **Сначала happy path целиком, потом ветвления, потом ошибки на каждом шаге, потом пустые и переходные состояния.**
   Сценарий описывается по шаблону (цель, роль, точки входа, шаги, ветвления, ошибки, конечные состояния, что меняется в
   системе) до карты экранов: ревью после генерации сценарий уже не чинит (+0,03…+0,12 из 5). — `[консенсус]` /
   `[исследование]` — `05-flows-journeys/02 §1.1, §1.4`; `01-foundations/03 §11`; `13-app-types/04 §11`.
6. **Мастер — для редких задач неподготовленных пользователей**: ≤5–7 именованных шагов, жёсткий порядок, самодостаточные
   шаги, выход «Сохранить и вернуться позже», страница проверки со ссылками «Изменить» (правка возвращает на проверку, а
   не прогоняет заново), страница подтверждения с номером и «что дальше». Свободный порядок или ветвления — список задач
   со статусами, без индикатора шагов (GOV.UK: 12-шаговый индикатор убрали без потерь); частая задача эксперта — одна
   страница с секциями («context is king»); клиентский сервис — один вопрос на экран. — `[консенсус]` / `[система]`
   (граница — `[спорно]`) — `05-flows-journeys/02 §2.2, §3, §7`; `03-layout-placement/01 §7`; `13-app-types/02 §12`;
   реестр № 6, 14.
7. **Порядок защиты: предотвращение → отмена → подтверждение.** Подтверждать только редкое и серьёзное; если один ответ
   выбирают почти всегда («98 %» — иллюстрация Microsoft), диалог удаляется; привыкание измерено — внимание падает уже
   после второго показа; ввод имени объекта — только для самых редких необратимых действий, иначе и он станет
   автоматизмом; «больше не показывать» не оправдывает ненужный диалог. — `[консенсус]` / `[исследование]` / `[система]` —
   `05-flows-journeys/03 §1, §4.2, §4.4, §4.7, §5`; `01-foundations/01 §14.3`; `04-components-patterns/07 §6`.
8. **Подтверждение конкретно и называет результат.** Имя объекта, число, последствия (и что не будет удалено); кнопки
   — «Удалить проект» / «Оставить проект», не Yes/No, не OK и не «Вы уверены?»; дефолтной кнопки нет или она безопасная;
   красный — только на финальном подтверждении; кнопки с противоположными последствиями разведены (Veeam: 20 минут
   работы в мастере и почти нажатый Cancel вместо Finish). — `[консенсус]` / `[исследование]` — `05-flows-journeys/03 §4.3,
   §10.1`; `07-ux-writing/02 §7`; `03-layout-placement/04 §5`.
9. **Отмена вместо подтверждения везде, где действие обратимо.** Отмена показывается в момент действия («Удалено.
   Отменить»), тост с отменой не исчезает сам и продублирован корзиной или журналом; мягкое удаление со сроком (30 дней
   Drive и Notion, 90 дней GitHub); симметрия отмены: отписаться, отключить, удалить аккаунт — тем же каналом и не
   длиннее подключения (FTC, DSA ст. 25(3)(c)); кто уполномочен совершить действие, тот уполномочен его отменить
   (ложная тревога на Гавайях — 38 минут). — `[консенсус]` / `[система]` / `[стандарт]` / `[исследование]` —
   `05-flows-journeys/03 §2, §3, §7.5–7.6`; `06-feedback-states-motion/04 §7.2`; `04-components-patterns/08 §3.4`.
10. **Онбординг — это первое действие, а не тур.** Руководства не читают; туры при первом запуске «dramatically
    overused» и забываются; пустое состояние — основной инструмент онбординга (причина + что здесь появится + одно
    действие); помощь — контекстная, рядом с шагом, в момент нужды; необязательную настройку откладывать. Никаких попапов
    при загрузке, сразу после входа и до получения ценности; никаких просьб об оценке, почте и разрешениях до первого
    результата; анонсы новых функций — в контексте, не при входе. — `[исследование]` / `[консенсус]` —
    `05-flows-journeys/01 §2, §4, §6, §9`; `01-foundations/01 §6.2`; `06-feedback-states-motion/04 §6.3`.
11. **Сохранение: ничего не терять и не спрашивать дважды.** Введённое сохраняется при ошибке валидации, при «Назад»,
    при обновлении страницы, при отказе сервера и при истечении сессии (WCAG 2.2.5); один и тот же вопрос в одном процессе
    не задаётся дважды (3.3.7, уровень A); лимит времени — предупреждение не позже чем за 20 с, продление не меньше
    10 раз (2.2.1). Модель сохранения выбирается по типу контрола: переключатель применяется мгновенно, чекбоксы,
    радиогруппы и текстовые поля — по кнопке, в одной форме не смешивать; явное сохранение по умолчанию, кнопка активна
    всегда, одна на страницу, названа глаголом с объектом; автосохранение — по паузе ввода и с ручным сохранением рядом;
    при уходе с несохранённым — черновик, а не «Сохранить изменения?». Состояние списка (запрос, фильтры, сортировка,
    страница, колонки, позиция) живёт в URL и восстанавливается при возврате из карточки; на пользователя запоминаются
    ширины колонок, вкладка и свёрнутые панели, а поиск, выделение и режим правки сбрасываются. — `[консенсус]` +
    `[стандарт]` / `[система]` / `[исследование]` — `08-accessibility/01 §7, §9.5`; `04-components-patterns/05 §6.1`;
    `05-flows-journeys/05 §1–§3, §8`; `04-components-patterns/06 §5`; `04-components-patterns/01 §6.4`.

### 4. Экраны: ИА, навигация, раскладка

12. **Сначала ИА, потом навигация.** Не больше трёх уровней иерархии (четыре — предел каркаса «верхняя панель + левая
    рейка»); в сайдбаре — не больше двух; плоская иерархия предпочтительнее глубокой; «7±2» к меню не применяется —
    7–9 и больше пунктов верхнего уровня нормально; категории не пересекаются, «Разное» и «Прочее» — симптом
    незаконченной ИА; разделы — существительные, действия — глаголы, порядок пунктов — по частоте и важности (алфавит —
    только когда названия известны заранее); структура проверяется карточной сортировкой (15 человек качественно,
    30–50 количественно) и tree-тестом, а не спором. — `[исследование]` / `[система]` / `[консенсус]` —
    `02-ia-navigation/01 §1, §3–§5, §7`; `02-ia-navigation/02 §2`; `12-evaluation-checklists/04 §5`.
13. **Главная навигация веб-приложения — слева, вертикально.** Верхняя панель — когда пунктов мало, подписи короткие и
    контенту нужна вся ширина; логотип слева ведёт на главную (центрированный логотип — провал возврата на главную в
    шесть раз чаще); утилиты — справа вверху; переключатель контекста — рядом с логотипом; текущее положение показано
    минимум двумя признаками; навигация одинакова на всех экранах. — `[консенсус]` / `[исследование]` / `[система]` —
    `02-ia-navigation/02 §1, §3, §7, §11`; `03-layout-placement/04 §1`.
14. **Не прятать навигацию на десктопе.** Скрытая навигация: использование 27 % против 48 %, находимость контента
    −20 %, время задачи +39 %, воспринимаемая сложность +21 %. На телефоне скрытие приемлемо (57 % против 86 %) только с
    компенсацией — нижняя панель из 3–5 ключевых пунктов или комбинированная навигация (лучшие сайты 89 % против 44 % у
    сайта со всем за иконкой); проверочный вопрос: сколько задач человек выполнит, если никогда не найдёт меню.
    — `[исследование]` — `02-ia-navigation/02 §12`; `09-mobile/02 §1.2–1.3`; `01-foundations/02 §4`.
15. **Один путь навигации к разделу.** Не дублировать пункты в верхней панели и сайдбаре, не ставить два меню с одним
    содержимым; хорошая избыточность — только несколько перекрёстных ссылок внутри контента; повтор функции — сложность,
    а не подстраховка; подменю открываются по клику (тач и клавиатура), каскад глубже одного уровня запрещён; хлебные
    крошки — от трёх уровней, не вместе с «Назад», иерархия, а не история. — `[исследование]` / `[консенсус]` —
    `02-ia-navigation/01 §8`; `02-ia-navigation/02 §2, §4, §12`; `03-layout-placement/04 §11`;
    `10-design-systems-consistency/02 §6`.
16. **Каркас одинаков на всех экранах, меняется только основная область.** У каждого экрана шапка страницы: путь назад,
    заголовок, статус, действия; заголовок списка — тип объекта во множественном числе, заголовок карточки — имя
    объекта; одна primary-кнопка на экран или на независимую секцию — справа в шапке страницы (шесть файлов, уровень
    `[система]`); действия страничной формы — внизу, выровнены по левому краю полей (айтрекинг: три лучших варианта из
    шести); в диалоге подтверждение справа, отмена слева, отмена никогда не дефолтная; один порядок кнопок на весь продукт.
    — `[консенсус]` / `[система]` / `[исследование]` (диалог — `[спорно]`) — `03-layout-placement/01 §1–§2`;
    `03-layout-placement/03 §4`; `03-layout-placement/04 §2–§4`; реестр № 1–2.
17. **Одно и то же — в одном и том же месте на всех экранах.** Порядок кнопок, положение главного действия, место
    фильтров, пагинации, тостов, ошибки у поля, пустого значения и плотность внутри типа зоны фиксируются один раз
    (WCAG 3.2.3 / 3.2.4); нарушать конвенцию — только при доказанном выигрыше и явно; намеренно отличаться нужно в
    четырёх случаях — деструктивное действие, критичное предупреждение, смена режима, смена контекста (организация,
    среда); консистентность обязательна внутри типа зоны и представления объекта, но не скрывает реальные различия
    домена и не повод для перестановок в зрелом продукте. — `[консенсус]` + `[стандарт]` — `03-layout-placement/04 §10,
    §12`; `08-accessibility/01 §2.5`; `10-design-systems-consistency/02 §3.3, §3.6, §5`; реестр № 50.
18. **Верх экрана получает непропорционально много внимания, но «всё без прокрутки» — миф.** 57 % времени просмотра —
    выше сгиба, 74 % — в первых двух экранах, 42 % — в верхних 20 % страницы (сайты, для приложений с постоянной
    навигацией не измерено); главное — вверх и влево; читают по «слоёному пирогу» заголовков и ключевых слов, F-паттерн —
    признак плохого форматирования; слепота к изменениям срабатывает при прерывании в 67 мс — новый элемент ставится
    рядом с точкой внимания. — `[исследование]` — `03-layout-placement/03 §6`; `01-foundations/01 §11`;
    `01-foundations/02 §3`.
19. **Группируй пространством, а не рамками.** Расстояние между группами заметно больше, чем внутри; одна шкала
    отступов с базовым шагом 8 и дробным 4; форма — в одну колонку; ширина поля подсказывает длину ответа; текст —
    45–75 знаков в строке (цель 60–70; 40–60 — ориентир M3 для узких экранов); всё по левому краю, числа — по правому;
    одна точка входа взгляда; движение — самый дорогой сигнал внимания, не больше одного постоянно движущегося элемента.
    — `[исследование]` / `[консенсус]` — `03-layout-placement/02 §1, §2, §4, §6`; `03-layout-placement/03 §3, §9`;
    `01-foundations/01 §9`; реестр № 44.
20. **Плотность — решение под задачу, а не вкус.** Админка эксперта плотнее, клиентский сервис воздушнее; один режим на
    продукт, плотность едина внутри типа зоны (таблицы плотные, мастер разреженный — одинаково везде); переключатель
    плотности — функция доступности (COGA), а не украшение; современные страницы скорее слишком разрежены (NN/g 2018);
    «частое видно всегда» — плотность как следствие правила. — `[консенсус]` / `[стандарт]` / `[исследование]` —
    `03-layout-placement/02 §5`; `08-accessibility/04 §3.2`; `04-components-patterns/01 §4.1`; `13-app-types/01 §5, §12`;
    реестр № 18.
21. **Иконка без подписи — только для 3–4 универсальных (дом, лупа, печать) и для очень частых действий ежедневного
    инструмента, с тултипом.** Подпись увеличивает цель клика; для навигации и нестандартных действий подпись видима
    всегда; тултипов на тач не существует, критичное в тултип не кладут. — `[исследование]` / `[консенсус]` —
    `03-layout-placement/03 §8`; `01-foundations/02 §9`; `04-components-patterns/07 §5`; `09-mobile/04 §1.5`.

### 5. Компоненты

22. **Таблица решает четыре задачи** (найти по критериям, сравнить, посмотреть или изменить одну запись, выполнить
    действия), и каждая требует своих инструментов. Первая колонка — человекочитаемый идентификатор; колонки — по
    важности; текст влево, числа вправо моноширинными цифрами, центрирование запрещено; с девятой колонки — липкий
    заголовок, липкая первая колонка и управление колонками; сортировка по умолчанию — «самое свежее» или «самое
    срочное»; страница 20 строк (25–50 в плотных админках), пагинация снизу; больше 50 объектов — пагинация и фильтр;
    около 1 000 строк — серверные сортировка и фильтрация, а виртуализацию считать по узлам DOM (Lighthouse: 800
    предупреждение, 1 400 ошибка). Пороги 200 / 1 000 / 10 000 — синтез D1 `[мнение]`. — `[исследование]` / `[консенсус]`
    / `[система]` — `04-components-patterns/01 §1–§3, §5, §6, §9.4`; `13-app-types/01 §6.1`; `09-mobile/03 §2.14`;
    реестр № 43.
23. **Модалка — не по умолчанию, а строка таблицы в модалке — никогда.** Пять измеренных издержек модалки (закрывают не
    читая); порядок контейнеров: боковая панель → раскрытие строки (только для коротких таблиц) → отдельная страница →
    модалка последней; контейнер выбирается по семи критериям (первым решает инициатор, вторым — нужен ли контекст,
    третьим — объём); модалка оправдана в четырёх случаях и запрещена в трёх; короткий самодостаточный ввод ≤5 полей без
    прокрутки — модалка допустима; не помещается в самый большой размер — это страница; инициируется пользователем, не
    при загрузке и не после входа; не больше двух действий; заголовок — подпись открывшей кнопки, глаголом; Esc
    закрывает, фокус — на первое поле, после закрытия возвращается на триггер; без вложенности, один оверлей за раз.
    — `[исследование]` / `[консенсус]` / `[стандарт]` — `04-components-patterns/07 §1, §2, §7`;
    `04-components-patterns/01 §4.4`; `03-layout-placement/01 §6`; `08-accessibility/02 §10.2`; `13-app-types/04 §19`;
    реестр № 7, 37–39.
24. **Массовые действия — ровно две сущности.** Панель над таблицей, появляющаяся при выделении (только применимые
    действия, с числом выбранных; не внизу экрана), и действия строки; «выбрать всё» означает «на странице», «все N по
    фильтру» — отдельное явное действие; перед необратимой операцией — предпросмотр с точным числом и первыми именами;
    подтверждение одно на операцию, а не на элемент; после — сообщение с отменой без перестроения таблицы и отчёт о
    частичном успехе с повтором только неудавшихся. — `[консенсус]` / `[система]` / `[практика]` —
    `04-components-patterns/01 §8.2`; `04-components-patterns/10 §3`; `05-flows-journeys/03 §6`; `13-app-types/01 §6.4`.
25. **Поиск и фильтры — один блок инструментов.** Поиск — видимое поле, не иконка, плейсхолдер называет область
    («Поиск по заказам»); подсказки примерно с третьего символа, каждая ведёт к результатам; число результатов
    показывается всегда, включая ноль; «ничего не найдено» — заметное сообщение в теле страницы с путём вперёд (запрос
    остаётся в поле, исправление, ослабление условий, сброс фильтров), без юмора; точный идентификатор находится без
    нечёткости. Фильтры: до 5 простых — строкой сверху; 6–8 — строка с раскрытием; больше 8 или многозначные фасеты —
    панель слева (Baymard: горизонтальная панель ломается после 6–8 типов); один порог на продукт; мгновенное применение —
    при отклике ≤1 с на десктопе, на телефоне и при дорогих запросах — кнопка «Применить»; чипы применённых фильтров —
    над результатами, сброс категории и глобальный; тип контрола выводится из типа данных. — `[исследование]` /
    `[система]` / `[консенсус]` — `04-components-patterns/02 §2, §3`; `06-feedback-states-motion/01 §4.4`;
    `03-layout-placement/04 §6`; `09-mobile/02 §6`; реестр № 4, 51.
26. **Дашборд — мониторинг исключений, а не анализ, и не нужен каждому приложению.** «Дашборд по умолчанию» —
    задокументированный дефект генерации: сначала список вопросов роли, главный экран роли — рабочая очередь или ответ
    «что происходит и что дальше»; 3–6 показателей вверху (число не измерено — `[консенсус]`); показатель без базы
    сравнения не показывается; период — один на экран; каждый блок ведёт вглубь минимум в два шага; величину кодируют
    только длина и 2D-позиция — круговые, кольцевые, спидометры, tree map и 3D не для дашборда; цвет кодирует категорию и
    никогда не единственный канал (до 8 % мужчин не различают цвета); данные помечаются временем обновления.
    — `[исследование]` / `[консенсус]` — `04-components-patterns/03 §1, §3, §4, §5.4, §6, §7, §8.3`;
    `03-layout-placement/01 §3`; `13-app-types/01 §4`; `13-app-types/02 §6`; реестр № 54.
27. **Форма — слабейший компонент генерации, а правила форм измеримо окупаются.** Ни одна модель в FullFront не превысила
    0,60 по формам, в WebGen-Bench операции с формами — самая массовая категория при точности 17,1 %; соблюдение
    базовых правил почти удваивает безошибочные отправки (78 % против 42 %). Контракт формы до генерации: поле → контрол
    → обязательность → формат и маска → правила → текст ошибки → состояния; одна колонка (исключение — части одного
    значения: день/месяц/год); ширина поля равна ожидаемой длине ввода (город — 19 символов); длинная форма режется по
    смысловым группам, а не «одно поле на страницу»; Tab-порядок совпадает с визуальным. — `[исследование]` /
    `[консенсус]` — `04-components-patterns/05 §0–§2, §6.2`; `11-ai-generated-ui/01 §6.1`; `13-app-types/04 §22`.
28. **Подписи над полем, плейсхолдер — не подпись.** Подпись всегда ближе к своему полю, чем к соседнему, 1–3 слова,
    существительное, без «введите» и без двоеточия; плейсхолдер — только пример значения, продублированный подсказкой
    снаружи (семь измеренных вредов, включая «поле с текстом выглядит заполненным и его пропускают»); требования к
    формату и паролю — вне поля и постоянно; обязательность видна до нажатия кнопки, помечать меньшинство, одна
    конвенция на продукт; прощающий ввод — пробелы, дефисы, ведущие нули, месяцы словом (GOV.UK: приём месяцев словом
    резко сократил ошибки); вставка не блокируется нигде, включая пароль (3.3.8); `autocomplete` — каждому полю о
    пользователе (1.3.5). — `[консенсус]` / `[исследование]` / `[стандарт]` (обязательность — `[спорно]`) —
    `04-components-patterns/05 §3`; `07-ux-writing/02 §3`; `08-accessibility/01 §9.4, §9.6`; реестр № 8, 34.
29. **Валидация — по отправке, инline — только там, где окупается; кнопку не блокировать.** По умолчанию проверка по
    отправке: сводка ошибок вверху с переводом фокуса, даже если ошибка одна, плюс сообщения у полей с теми же
    формулировками; проверка по уходу из поля — только для полей с неочевидным ответом, лимитами и масками (там +22 %
    успешности, −42 % времени, −47 % фиксаций); никогда — по мере набора до первой ошибки, уход из незаполненного поля —
    не ошибка; успех показывать только для сложных полей; серверная валидация всегда. Кнопку отправки не блокировать до
    нажатия (disabled при сбое скрипта — «гарантированные 100 % отказа», не фокусируется, низкоконтрастна); после
    нажатия — состояние «выполняется» против дубля, запрос идемпотентен; одна кнопка отправки на форму; Reset и
    «Очистить» не делать. — `[исследование]` / `[консенсус]` / `[система]` (момент — `[спорно]`) —
    `04-components-patterns/05 §4, §5`; `08-accessibility/03 §1.6–1.7`; `05-flows-journeys/04 §3.2, §3.5`;
    `05-flows-journeys/05 §1.5`; реестр № 5, 36.
30. **Сообщение об ошибке — над полем, тремя признаками, с путём вперёд.** Над полем, между подписью с подсказкой и
    полем: низ перекрывают экранная клавиатура, выпадающий список и автозаполнение («под полем» — только на десктопе в
    системах с этой конвенцией); не меньше трёх индикаторов — текст, иконка, рамка, и никогда только цвет; не в тултипе
    и не в модалке; текст — что случилось, почему, что сделать; без кода, без «неверно», без «что-то пошло не так»;
    система не обвиняет пользователя. — `[консенсус]` / `[исследование]` (место — `[данные]`) —
    `04-components-patterns/05 §4.4`; `05-flows-journeys/04 §2.3, §3.1, §7`; `09-mobile/03 §3.5`; `07-ux-writing/02 §6`;
    реестр № 22.
31. **Тип контрола выводится из числа вариантов и числа выбираемых.** До 5 вариантов и один ответ — радиокнопки; 5–15 —
    селект; больше 15 — комбобокс с автодополнением; несколько ответов — чекбоксы и никогда `<select multiple>`;
    известное человеку значение (дата рождения, страна) — поле ввода быстрее любого списка; дата — всегда текстом;
    радиокнопки и чекбоксы — вертикально, подпись кликабельна (у тумблера тоже); группа радиокнопок исчерпывающая
    («Ничего из перечисленного», «Другое»); недоступный пункт приглушается с причиной, скрывается только то, чего у роли
    нет в принципе; капча заменяется ограничением частоты, honeypot, WebAuthn и токенами провайдера — она проблема № 1 у
    пользователей скринридеров 14 лет подряд, а «простой вопрос» и слайдер нарушают 3.3.8 и 2.5.7. — `[консенсус]` /
    `[система]` / `[исследование]` — `04-components-patterns/06 §1, §4–§6, §9`; `04-components-patterns/10 §2.4`;
    `08-accessibility/03 §1.9`; реестр № 13, 32, 35.
32. **Форма сообщения выводится из типа, срочности, нужности действия и инициатора.** Результат действия человека — там,
    где он работал; событие системы — в глобальной зоне; тост не для ошибок и не для критичного (участница NN/g ждала
    5 минут, не заметив исчезнувшее сообщение); тост без действия живёт 4–10 с, с действием — не исчезает сам и действие
    продублировано в постоянном месте; один угол на продукт; стопка не больше 2–3, агрегация лучше стопки; автоисчезающий
    тост в вебе — только с инлайн-дублем; баннер — состояние системы или аккаунта, один на страницу; одно событие — одна
    форма (не тост и модалка сразу); успех показывается только там, где он не очевиден — «Документ успешно сохранён»
    шум. — `[консенсус]` / `[исследование]` / `[система]` — `04-components-patterns/08 §1, §3–§5, §7`;
    `08-accessibility/03 §5.1`; `13-app-types/04 §20`; реестр № 10–12.
33. **Настройки: разделы, одна кнопка, опасная зона внизу.** Личные настройки и настройки организации — разные экраны;
    локальное меню разделов слева, каждый со своим URL; одна кнопка сохранения на страницу либо явно независимые
    секции; опасная зона — внизу, отдельным блоком с рамкой (первоисточник — GitHub); лестница защиты — подтверждение с

### 6. Состояния и обратная связь

35. **Пять базовых состояний каждого экрана перечисляются поимённо.** Идеальное, пустое, загрузка, частичное, ошибка —
    по контракту `S01–S22`, а не словами «продумай состояния»: закрытый список — единственный подтверждённый способ
    получить их от генератора. «Пусто» — только после загрузки («нет записей» во время загрузки — самый вредный дефект:
    часть пользователей уходит, не дождавшись); три причины пустоты — три разных текста; у пустого состояния всегда
    причина и одно действие, сообщение — в теле области, крупно (мелкая серая надпись не получила ни одной фиксации),
    и оно заменяет элемент целиком, включая шапку таблицы; «нет прав», «заблокировано другим», «архивировано», «лимит
    достигнут» — отдельные состояния, не 404 и не 500; блоки экрана независимы по данным и ошибкам — отказ одного
    сервиса ломает один блок; крайние случаи данных (ноль, отрицательное, очень длинная строка, тысячи элементов)
    перечисляются поимённо. — `[консенсус]` / `[исследование]` / `[система]` — `06-feedback-states-motion/01 §1, §2,
    §4–§6`; `11-ai-generated-ui/01 §7`; `13-app-types/04 §21`; `05-flows-journeys/04 §4.5`.
36. **Отклик: 0,1 с — прямое манипулирование, 1 с — поток не рвётся, 10 с — предел внимания.** Видимая реакция на любое
    нажатие — до 100 мс, иначе нажмут ещё раз; при операции короче 1 с ничего не показывать — мелькание хуже; локальная
    предсказуемая операция — индикатор с 1 с (в 1–2 с достаточно смены состояния кнопки и блокировки повтора); дольше
    10 с — определённый прогресс, «Прервать» и возможность уйти; для сетевых и непредсказуемых операций порог показа
    ниже (M3: 0,2 / 5 с), отложенный показ 200–400 мс и минимум показа 300–500 мс — практика индустрии без
    первоисточника. — `[исследование]` / `[консенсус]` (числа отложенного показа — `[практика]`) —
    `06-feedback-states-motion/02 §2`; `01-foundations/01 §12`; реестр № 9.
37. **Скелетон — страница, спиннер — модуль, прогресс-бар — измеримый процесс; не лгать оценкой.** Скелетон повторяет
    структуру будущей страницы (без плейсхолдеров контента он «equivalent to a spinner») и не применяется к процессам;
    индикатор на блок — при разных источниках данных и видимом каркасе; определённый прогресс предпочтительнее
    неопределённого, но 90 % за пять секунд и 10 % за пять минут «can even feel deceptive» — лучше честный объём
    («обработано 340 из 12 000») и шаги вместо процентов («шаг 2 из 5: обработка файлов»); «осталось» фрустрирует
    сильнее, чем «прошло» (Tan & Nov, CHI 2026, N = 425), отсутствие таймера — самое длинное субъективное ожидание;
    индикатор двигается; долгие операции — в фон со статусом, отменой, уведомлением и результатом, который можно забрать
    позже; никогда «не нажимайте дважды»; откат оптимистичного обновления объясняется, а не молча возвращается.
    — `[консенсус]` / `[исследование]` / `[система]` — `06-feedback-states-motion/02 §3–§6`; `13-app-types/02 §6.2`;
    `07-ux-writing/02 §14`; реестр № 10, 26, 59.
38. **Core Web Vitals — UX-порог: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1 на 75-м процентиле, раздельно для мобильных и
    десктопа.** Живые данные не переставляют то, на что смотрят: новое сверху — кнопкой «Показать N новых», а не
    сдвигом; свежесть показывается рядом с данными («обновлено 12 минут назад»), устаревшее помечается явно;
    автообновляющийся контент останавливается или управляется (WCAG 2.2.2); частые прерывания ведут к усталости от
    оповещений — 56 уведомлений в день у среднего пользователя уже в 2016. — `[стандарт]` / `[консенсус]` /
    `[исследование]` / `[практика]` — `01-foundations/01 §12.3`; `09-mobile/01 §7.2`; `06-feedback-states-motion/02 §8,
    §9.3`; `12-evaluation-checklists/03 §9`.
39. **Движение оправдано четырьмя вещами**: обратная связь, смена состояния, пространственная связь, сигнификатор; всё
    остальное — декор. 100–400 мс (простая обратная связь ~100, оверлей 200–300), выход быстрее входа, старт в пределах
    0,1 с после действия, ease-out на входе и ease-in на выходе; чем чаще видят, тем короче; анимацию можно прервать;
    одна оркестрованная анимация вместо шести конкурирующих; `prefers-reduced-motion` обязателен, включать анимацию в
    `no-preference`; ничего не мигает чаще трёх раз в секунду (2.3.1); автодвижение дольше 5 с имеет паузу (2.2.2);
    анимация по взаимодействию отключаема (2.3.3). Запреты против дефолтов нейросетей: появление секций при прокрутке,
    hover-эффект на каждой карточке, бесконечные градиенты и пульсации, движение без действия. — `[исследование]` /
    `[консенсус]` / `[стандарт]` / `[система]` — `06-feedback-states-motion/03 §1–§3, §7, §8`;
    `03-layout-placement/03 §9`; `08-accessibility/01 §7`.
40. **Отказ не должен быть дороже согласия** — в действиях, экранах, заметности и каналах. Ничего не попадает в корзину,
    заказ и счёт без явного действия; согласия выключены по умолчанию и одной полярности; согласие на персональные данные
    — отдельный элемент (152-ФЗ ст. 9 с 01.09.2025); повтор просьбы после отказа запрещён (DSA ст. 25(3)(b)); отмена —
    тем же каналом, не длиннее подключения (DSA ст. 25(3)(c), FTC); таймеры и остатки — только по реальным данным (из
    393 таймеров 157 лживых; один сайт генерировал остаток случайным числом); показ сборов на последнем шаге повышает
    трату на 21 %; «Принять все» и «Отклонить все» одинаково заметны; мигающий таймер — тёмный паттерн; сгенерированное
    ИИ помечено, ассистент не выдаёт себя за человека (DSA ст. 35(1)(k)); запрет пишется в контракт генерации явно.
    — `[консенсус]` / `[стандарт]` / `[исследование]` — `06-feedback-states-motion/04 §1.4, §3, §5, §6.4, §7, §8`;
    `13-app-types/02 §7, §10, §13`; `13-app-types/03 §15`.

### 7. Тексты

41. **Читают около 20 % текста экрана, остальное сканируют.** Текст вдвое короче даёт +58 % юзабилити, сканируемость
    +47 %, объективный язык +27 %, всё вместе +124 % (Nielsen 1997, маркетинговый веб-текст — на микрокопи приложений не
    проверялось); видят примерно два слова (11 символов) каждого пункта — ключевое слово в начало (для 35 % ссылок по
    первым 11 символам назначение не угадать); предложение — до 15–20 слов, абзац — до 50; уровень чтения — 6–8 класс
    для массовой аудитории, 10–12 для экспертов, для русского английские формулы не действуют (формула Оборневой);
    эксперты предпочитают простой язык; текст пишется до макета; сокращать мусор, а не смысл. — `[исследование]` /
    `[консенсус]` — `01-foundations/01 §11.3`; `07-ux-writing/01 §3, §4, §13.1`.
42. **Кнопка = глагол + объект.** По-русски — инфинитив совершенного вида («Сохранить», не «Сохраните»), 1–3 слова, до 4
    с объектом, без точки, только первое слово с заглавной; по-английски — `{verb} + {noun}` без артиклей, sentence case,
    оксфордская запятая, одна пара на продукт (Sign in / Log in); «OK» и «Submit» — не подтверждение; ссылка называет
    назначение, не «здесь» и не «click here»; подпись поля — существительное 1–3 слова; подсказка — одно предложение;
    тост — одна строка; вкладка — 1–2 слова; заголовок экрана — группа существительного, глагол живёт на кнопке; таблица
    длин по компонентам — одна на базу. — `[консенсус]` / `[система]` — `07-ux-writing/02 §1–§3, §8`; `07-ux-writing/01
    §12`; `07-ux-writing/03 §2, §6`; `07-ux-writing/04 §1–§6`; реестр № 47.
43. **Голос один, тон меняется; система не обвиняет пользователя.** Карта тона фиксируется до экранов; эффект тона
    измерим, но мал (0,5–1 балл из 5) — бюджет ясности больше бюджета тона; нейтральный тон в админке, деньгах,
    безопасности и деструктивных действиях; «invalid», «неверно», «вы не заполнили» запрещены — «Не удалось…» вместо
    «Ошибка…»; юмор при неудаче пользователя запрещён, допустим только когда виновата система и потерь нет; короткое
    системное сообщение — без лица, «мы» — только от организации с понятным субъектом; канцелярит («осуществить»,
    «данный», «является») и слова-пустышки («успешно», «автоматически») запрещены; сообщение об ошибке отвечает: что
    случилось, почему, что сделать. — `[консенсус]` / `[исследование]` (тон в админке — `[практика]`, «мы» — `[спорно]`)
    — `07-ux-writing/01 §5.1, §6–§9`; `07-ux-writing/03 §7, §8`; `05-flows-journeys/04 §2.3`;
    `06-feedback-states-motion/01 §4.8`; реестр № 31, 41.
44. **Русский текст длиннее английского на 10–30 %, короткие строки — в 2–3 раза.** Кнопки, вкладки и колонки
    проектируются под расширение, а не под среднюю длину; плюрализация — только через ICU (`one` / `few` / `many` /
    `other`, где `other` — дробные), род — через `select`, никакой конкатенации строк; числа, даты, валюта, относительное
    время — через `Intl`; в предложении линкуется только фрагмент, называющий назначение; типографика: «ёлочки», длинное
    тире, тире как прочерк при отсутствии данных (ноль — только результат подсчёта), неразрывные пробелы между числом и
    единицей, без точки в подписях, кнопках и тостах; никаких прошедших времён и причастий с родом про пользователя;
    подставляемые значения не склоняются; текста в изображениях нет; имя человека — одно поле или «Фамилия / Имя и
    другие имена». — `[исследование]` / `[стандарт]` / `[система]` / `[консенсус]` — `07-ux-writing/03 §3–§6`;
    `07-ux-writing/05 §4–§7`; реестр № 42, 45.

### 8. Доступность

45. **Целевой уровень — WCAG 2.2 AA (55 критериев); WCAG — минимальная планка, не определение удобства.** Соответствие
    считается для страницы и процесса целиком (капчу из формы не исключить, все пять шагов чекаута), каждый брейкпоинт и
    обе темы — отдельно; всё делается с клавиатуры (2.1.1); индикатор фокуса — свой, на `outline`, не меньше 3:1 к
    соседним цветам (дефолт браузера измерен 1,4–2,8:1 на цветных кнопках); фокусируемый элемент не перекрыт липкой
    шапкой, подвалом или панелью (2.4.11, `scroll-padding`); контраст текста 4,5:1, крупного текста и значимой графики
    3:1 (точные таблицы — `../ui/01-color/`); текст масштабируется до 200 %, страница работает при 320 CSS px
    без горизонтальной прокрутки — это окно 1 280 px при зуме 400 % (таблицы исключены, но в фокусируемом контейнере);
    зум не отключать; цвет никогда не единственный носитель смысла; инструкции не опираются на форму, цвет и положение;
    WCAG 3 в правила не закладывать. — `[стандарт]` + `[исследование]` — `08-accessibility/01 §1, §3, §5, §6, §12.1,
    §14`; `08-accessibility/02 §7`; `09-mobile/04 §4.10, §6.4`.
46. **Размер цели: не меньше 24×24 CSS px или зазор, чтобы круги Ø24 px не пересекались (2.5.8, AA).** Основные и
    деструктивные действия на таче — 44×44 (Apple: 44 pt по умолчанию, 28 pt минимум с зазорами 12/24 pt; M3 — 48 dp);
    точность касания — 7 мм в центре экрана и 12 мм в углах, в неудобной позе в дальнем углу хуже 30 мм; строки у краёв —
    не ниже 9–10 мм; цель — весь контейнер (строка, карточка, кнопка), а не иконка или слово; у перетаскивания —
    альтернатива одним указателем (2.5.7) и отдельно клавиатурная (2.1.1) — два разных требования; ничего не срабатывает
    по `mousedown` и `touchstart`. — `[стандарт]` / `[исследование]` — `08-accessibility/01 §8, §12.4`;
    `09-mobile/02 §2.3–2.4`; `09-mobile/04 §2.8`; реестр № 21.
47. **Нативный элемент вместо ARIA; у каждого интерактивного элемента — имя, роль, значение, состояние.** Страницы с
    ARIA дают в среднем 59,1 ошибки против 42 без неё; `<div role="button">` — обещание обработать Enter и Space,
    `tabindex` и фокус; пустые кнопки без имени — на 30,6 % главных страниц; имя — 1–3 слова, различающее слово первым,
    видимый текст подписи входит в доступное имя (2.5.3); заголовки важнее лендмарков (по заголовкам ищут 71,6 %
    пользователей скринридеров, по лендмаркам — 3,7 %), нужны оба: один `<h1>`, `<title>` на каждый маршрут, skip-ссылка
    первой; `tabindex` > 0 запрещён; Tab — между компонентами, стрелки — внутри составного; фокус всегда где-то есть:
    удалили строку — на соседнюю, закрыли диалог — на триггер; модалка — `role="dialog"`, фокус внутрь, кольцо Tab, Esc,
    `inert`, возврат; смена маршрута в SPA — сменить `<title>` и перевести фокус на `<h1>`; в forced-colors системные
    цвета выбираются по нативной семантике, тени исчезают. — `[стандарт]` / `[исследование]` / `[консенсус]` —
    `08-accessibility/02 §1–§10`; `08-accessibility/03 §4`; `08-accessibility/04 §4.3`.
48. **Формы, таблицы и динамика для вспомогательных технологий.** Видимая подпись через `<label for>` (треть полей в вебе
    не подписана); подсказка — через `aria-describedby`; группы — `fieldset` + `legend`; сводка ошибок — `role="alert"`,
    фокус на неё, ссылки на поля, «Ошибка:» в `<title>`; таблица данных — `<table>`, `<th scope>`, `<caption>`, не `div`
    и не CSS-grid; `aria-sort` только на одной колонке; статусные сообщения объявляются без перевода фокуса (4.1.3), но
    живая область — последнее средство после состояния ARIA, подсказки заранее и перевода фокуса; две живые области на
    страницу (`polite` и `assertive`), с загрузки в DOM; живая область не передаёт разметку — уведомление с действием
    это диалог, не тост; пустой результат поиска объявляется `assertive`; бесконечная прокрутка враждебна клавиатуре —
    «Показать ещё» и пагинация; у графика — текстовое резюме и таблица-эквивалент; кастомный селект, дейтпикер и загрузка
    файла — с полным клавиатурным контрактом, иначе нативные. — `[стандарт]` / `[консенсус]` / `[практика]` —
    `08-accessibility/03 §1–§8`; `04-components-patterns/01 §6`.
49. **Автоматика находит ~57 % дефектов доступности по объёму, но лишь ~32 % критериев, по 14 критериям — ноль.** Порядок
    фокуса (2.4.3): 9 553 дефекта у Deque, 100 % найдены вручную; axe-core 4.13 знает ровно одно правило WCAG 2.2;
    данные 2021 года по WCAG 2.1 — порядок величины. Ручной протокол из шести проходов обязателен: клавиатура,
    скринридер, зум 200 % и 400 %, forced-colors и тёмная тема, reduced motion, реальные данные и края; стенд —
    NVDA + Chrome и Firefox, VoiceOver + Safari (JAWS + Chrome — самая частая пара, 24,7 %; NVDA — самый распространённый,
    65,6 %); час с пятью сотрудниками с инвалидностью на их собственных AT; 91,3 % пользователей скринридеров работают с
    телефона, а APG мобильные не покрывает; отсутствие жалоб ничего не значит — 67 % пользователей скринридеров не
    сообщают о барьере; доступность ставится на входе, а не чинится после: отбор лучшего из 8 по axe снижает IR 0,40 →
    0,14, а починка промтом вносит новые нарушения. — `[исследование]` / `[практика]` — `08-accessibility/04 §1.3, §5`;
    `08-accessibility/01 §13`; `09-mobile/04 §6`; `12-evaluation-checklists/03 §5`; реестр № 33.

### 9. Мобайл

50. **Сначала «что из продукта нужно на телефоне», потом «как сверстать».** Список мобильных сценариев — артефакт
    брифа; паритет контента и функций — цель, паритет интерфейса — нет; mobile-first — порядок приоритизации, а не вёрстки:
    перенос мобильного интерфейса на десктоп измеримо ухудшает десктоп (навигацией пользовались в 54 % задач против 77 %,
    179 участников); плотная админка — desktop-first, клиентский сервис — mobile-first; отказ от мобильной версии законен
    по данным об аудитории и пересматривается. Именованные диапазоны M3 (600 / 840 / 1 200 / 1 600 dp) — словарь правил
    перестроения, не список устройств; брейкпоинт ставится там, где ломается раскладка (элементы сталкиваются, колонка
    узка, строка длинна, лишнее место), проверка — на произвольных ширинах и у границ; ширина окна — один параметр для
    поворота, разделённого экрана и складного; перестроение недеструктивно и обратимо, функциональность от размера не
    меняется; container queries — для компонентов, брейкпоинты — для каркаса; интерфейс не делится по типу ввода, цели
    считаются по наименее точному указателю (`any-pointer: coarse`). — `[консенсус]` / `[исследование]` / `[система]`
    (выбор системы диапазонов — `[спорно]`) — `09-mobile/01 §1–§5`; `10-design-systems-consistency/02 §4.3`;
    `02-ia-navigation/02 §10`; реестр № 27, 57.
51. **Мобильная сессия — 72 секунды против 150 на десктопе, 40 % сессий короче 15 секунд: проектируй возобновление.**
    Черновик, шаг мастера, фильтры и позиция прокрутки переживают сворачивание вкладки и возврат; вкладка мобильного
    браузера выгружается без `beforeunload` — сохранять по паузе ввода и по `visibilitychange`; понимание текста на
    телефоне не хуже, только медленнее на трудных местах (276 участников, +30 мс на слово) — краткость остаётся, миф
    «мобильный пользователь торопится» — нет; проектировать под медленное устройство и плохую сеть (массовые модели в
    16–18 раз медленнее устройств проектировщиков); Core Web Vitals — отдельно для мобильных. — `[исследование]` /
    `[консенсус]` / `[данные]` — `09-mobile/01 §1.2, §6, §7`; `09-mobile/04 §4.8`; `05-flows-journeys/05 §6.3, §9`.
52. **Мобильная навигация и действия.** Паттерн — по числу разделов: 3–5 равнозначных — нижняя панель с подписями и
    фиксированным составом (пункты не прячутся и не отключаются по контексту), 6 и больше — выдвижная панель или рейка,
    одна задача за сессию — хаб; подчинённая навигация — по числу подкатегорий (меньше 6 — аккордеон, 6–15 — секционное
    меню, больше 15 — страница категории); «зона большого пальца» — миф: касаются центра экрана и двигают контент к
    центру, а главное действие — внизу или в липкой панели с проверкой на перекрытие клавиатурой; необратимое не рядом
    с рутинным («что произойдёт при промахе на 12 мм?»); отклик на касание виден вокруг пальца; «Назад» работает везде,
    включая оверлеи и аккордеоны — самая частая мобильная потеря работы; master-detail на телефоне — две страницы; жест —
    ускоритель, а не единственный путь, свайп по строке — только для деструктивного с отменой; hover-действия
    дублируются видимыми; FAB — не больше одной и не на каждом экране; обучающий оверлей — симптом, а не решение.
    — `[консенсус]` / `[система]` / `[исследование]` / `[практика]` — `09-mobile/02 §1–§5`; реестр № 15, 20.
53. **Таблица на телефоне: задача «уместить» не имеет решения — ограничение в рабочей памяти, а не в пикселях.**
    Поддерживаются два сценария — сравнить строки по одной колонке и открыть деталь одной строки; пять способов по
    возрастанию потерь: приоритетные колонки → горизонтальная прокрутка с липкой первой колонкой (единственное место,
    где NN/g её разрешает: стрелки и обрезанный элемент, контейнер `role="region"` + `tabindex="0"`) → аккордеон-строка
    → вкладки внутри таблицы → отдельный экран-деталь; больше 3–4 колонок или многословная колонка — карточки
    (легибельно помещаются только две многословные колонки); закрепление строк и колонок съедает площадь — считать
    цену; `display: block` на таблице ломает семантику в Safari — проверять скринридером; поворот телефона — последнее
    средство; управление колонками — списком имён, не перетаскиванием. — `[исследование]` / `[консенсус]` /
    `[стандарт]` — `09-mobile/03 §2`; `04-components-patterns/01 §3.3`; реестр № 19.
54. **Форма и оверлеи на телефоне.** Одна колонка всегда; поле с кеглем меньше 16 px заставляет Safari зумить — лечится
    кеглем, не отключением масштабирования; каждому полю — `type`, `inputmode`, `autocomplete`, `enterkeyhint`; ошибка над
    полем и видна при открытой клавиатуре; не заставлять печатать то, что снимается с датчиков (камера, GPS, контакты);
    длинный номер — блоками по 4; черновик сохраняется при сворачивании и потере связи; модалка превращается в
    полноэкранный диалог или нижнюю шторку (начальная высота не больше половины экрана), а не в уменьшенную модалку;
    немодальное на десктопе может стать модальным в Safari на iPhone — проверять на устройстве; `100vh` больше экрана
    (`svh`/`dvh`), `100vw` даёт горизонтальный скролл; всё у краёв — с `env(safe-area-inset-*)`; `touch-action:
    manipulation` вместо отключения зума; hover-стили только внутри `@media (hover: hover)`; DevTools не заменяют
    физическое устройство. — `[консенсус]` / `[стандарт]` / `[система]` (нативный пикер — `[спорно]`) —
    `09-mobile/03 §3, §6`; `09-mobile/04 §4, §7.4`.

### 10. Проверка и генерация

55. **Внешний вид ≠ работоспособность.** На WebGen-Bench 52 % по тестам дизайна против 17,1 % по функциональным у одной
    связки; админка — измеренно худший класс генерации (IIS 9,4 при визуальном балле 76+, у одной модели — 2,0); арены
    и попарное человеческое голосование слепы к содержательным ошибкам (текстовое сходство −0,354 при позиции 0,761):
    содержание, числа, маршруты и тексты проверяются детерминированно, а не судьёй и не «на глаз»; выдуманная
    «статистика NN/g о 50 дашбордах» не существует — цитаты проверяются. — `[исследование]` —
    `11-ai-generated-ui/01 §2.1, §3.1`; `11-ai-generated-ui/02 §2, §5, §7`; `12-evaluation-checklists/01 §7.6`.
56. **Контракт генерации задаёт то, что модель сама не сделает.** Детальность входа — единственный фактор, улучшающий
    всё сразу: объектная модель и закрытая карта экранов с реестром маршрутов (провалы навигации — ссылка на
    незарегистрированный маршрут и выдуманная страница; проверяется по `href`); состояния поимённо; реальные данные с
    граничными случаями до дизайна — никаких «lorem», «Feature 1», «Welcome back, John»; состояние, переживающее переход
    между экранами (три из шести фронтирных моделей — ровно 0,0); один источник компонентов на потребность и правило
    заземления (компонент, проп или токен без источника не используется; репозиторий > пакет > приложение > сайт
    документации); проверенный стартер — первый компонент задаёт палитру, типографику и отступы для остального;
    границы правки; словарь запретов — только для достаточно сильной модели (слабым он вредит); описывать взаимодействие
    текстом, а не только скриншотом; мелкие взаимодействия (< ~2,5 % площади) — отдельной генерацией. Порядок «каркас
    один раз → данные → экраны по одному → компоненты → тексты → состояния → проверки» — обоснованная гипотеза
    `[консенсус]`, прямо не измерена; правка одного экрана ломает соседние (F8.4) — визуальный регресс по всем маршрутам
    после каждой правки. — `[исследование]` / `[консенсус]` / `[система]` — `11-ai-generated-ui/04 §1, §2`;
    `11-ai-generated-ui/01 §4.2, §8.3, §12, §13`; `11-ai-generated-ui/03 §2, §3`; `10-design-systems-consistency/01 §2`;
    `10-design-systems-consistency/02 §8, §9`; `13-app-types/04 §14–§15, §26`.
57. **Отбор лучшего из k по метрике надёжнее починки.** Best-of-8 по axe: IR 0,40 → 0,14, Critical 47 → 12; итеративная
    починка промтом снижает до 0,32 и вносит новые дефекты; сценарный прогон агентом чинит функцию (+3,3 пункта),
    скриншот-критика — вид (+0,7), и они конфликтуют — нужны откат при серии ошибок и выбор лучшего шага; самопроверка по
    скриншоту вредит слабым моделям (Block-Match 39,7 → 30,1); для критики достаточно небольшой открытой VLM, для
    генерации кода — нет; ревью-LLM чинит обратную связь (+0,44) и почти не чинит сценарий (+0,12) — сценарий задаётся до
    генерации; правило «стоп»: если после k вариантов ни один не прошёл ворота — проблема во входном контракте, а не в
    генерации. — `[исследование]` — `11-ai-generated-ui/04 §3`; `11-ai-generated-ui/02 §3.3`;
    `12-evaluation-checklists/03 §6, §8, §10`; `08-accessibility/04 §5.7`.
58. **Судья-LLM: один прогон — шум.** 13,6 % переворотов попарных предпочтений при идентичном повторе, 11 прогонов для
    устойчивого мажоритарного вердикта (число получено на текстовых задачах); перестановка позиций обязательна (у одной
    модели 72 % большинства за первую позицию) — победа засчитывается только при совпадении в обоих порядках;
    reference-guided grading снижает долю ошибок 14/20 → 6/20 (CoT) → 3/20; формулировка рубрики версионируется как код —
    перефразировка меняет вердикт в 25 % случаев; сложный критерий разбивается на несколько судей, часть из них —
    детерминированные правила; судья другого семейства, чем генератор; калибровка против человеческой разметки (F1 ≥ 0,8)
    — `[мнение]` NN/g. — `[исследование]` / `[консенсус]` — `11-ai-generated-ui/02 §4`; `12-evaluation-checklists/01 §7.5`;
    `11-ai-generated-ui/04 §5`.
59. **Экспертная оценка: задачи, линзы, серьёзность, доказательства.** Начинать со списка ключевых задач, а не с экранов;
    один оценщик находит 42 % крупных и 32 % мелких проблем (Nielsen 1992 — порядок величины) — отсюда 3–5 независимых
    проходов разными линзами (новичок, эксперт, только клавиатура, телефон, скринридер, самый уязвимый пользователь) в
    отдельной сессии без контекста создания; когнитивный проход — четыре вопроса Lewis–Polson на каждый шаг; PURE даёт
    число без пользователей (1–3 на шаг, цвет задачи по худшему шагу, α ≥ 0,667); серьёзность 0–4 (частота × влияние ×
    устойчивость) собирается отдельным проходом, среднее трёх оценок, несколько четвёрок — релиз запрещён; каждая
    находка — что, где, какое правило нарушено, доказательство (событие или фрагмент DOM), серьёзность, наименьшая
    рекомендация; coverage gate: обход не завершён, пока не задействованы ключевые контролы; оценивать путь, а не экран
    (четыре типа трения: тупик, повторный ввод, лишнее подтверждение, потеря состояния); ноль находок — неверна проверка,
    а не идеален дизайн; экспертиза готовит тест с людьми, а не заменяет его. — `[исследование]` / `[консенсус]` /
    `[практика]` — `12-evaluation-checklists/01 §2–§8, §10`; реестр № 16, 25.
60. **Автопроверки — ворота, не оценка UX; метрики выбираются по цели.** «Пройдено» и «хорошо» — разные вещи; порядок по
    стоимости: линт токенов → инвентарь интерфейса (одно действие с разными именами, два стиля кнопки, разные форматы
    дат) → axe и Lighthouse в обеих темах, на каждом брейкпоинте и внутри состояний (модалка, форма с ошибками, пусто),
    плюс второй аудитор, метрика нормирована на размер DOM (IR = WVS / число элементов) → поиск заглушек и сверка каждого
    числа с набором данных → сценарные тесты (happy path, ошибки, клавиатура, телефон, тёмная тема, медленная сеть, роль
    без прав, возврат на предыдущий экран) → судья → человек, который один проверяет достижимость маршрутов через
    вложенные меню, уместность, приоритет и доверие; проверять соблюдение собственных ограничений, а не только объявлять
    их (50 % провалов исполняемости — их нарушение). Метрики: успешность задачи — базовая везде; число кликов и тапов —
    не метрика; время сценария — только для структурированных задач; экспертные инструменты — время до первого успеха,
    время исправления ошибки, ошибки конфигурации, активные пользователи на команду, доля задач вне системы; клиентский
    сервис — доля задач без обращения в поддержку; чужая метрика не переносится. — `[консенсус]` / `[исследование]` /
    `[стандарт]` (наборы метрик по классам — `[данные]` / `[практика]`) — `12-evaluation-checklists/03 §1–§10`;
    `11-ai-generated-ui/04 §4, §6`; `12-evaluation-checklists/04 §2.1, §4.2`; `01-foundations/02 §1`;
    `13-app-types/01 §13`; `13-app-types/02 §17`; реестр № 23.

### Практика и спорное (ядро ниже `[консенсус]` — применять, зная статус)

- **Законы объектов (OOUX)**: одинаковые объекты выглядят одинаково во всех контекстах, разные — по-разному;
  представление объекта (полное, строка, карточка, чип, превью в поиске, уведомление, крошка) выводится один раз и
  переиспользуется; порядок первых трёх атрибутов не переставляется. Повторяется в пяти папках, но везде `[мнение]`
  (Prater, Купер) — `01-foundations/03 §2`; `10-design-systems-consistency/02 §2`; `13-app-types/04 §10`;
  `04-components-patterns/04 §8`.
- **Матрицы «роль × объект × действие» (CTA, CRUD)** как минимальный артефакт прав до экранов; ограничение области
  («только свои») — в составе списков, а не в ошибке при клике — `[мнение]` — `01-foundations/03 §4, §6`;
  `13-app-types/04 §8`; `13-app-types/01 §7.1`.
- **Права и аудит**: право — действие, роль — набор прав, наименьшие привилегии, владельцев не меньше двух; аудит-лог
  отвечает на пять вопросов (кто, что, над чем, когда, откуда) и фильтруется по полям, не ищется текстом; имперсонация
  видима, ограничена, записана; контекст организации и среда (прод / песочница) видны всегда. Самый слабый по
  доказательности файл базы: правила из документации GitHub, Stripe и Microsoft Entra, ни одного измерения —
  `[система]` / `[практика]` — `04-components-patterns/09 §5, §7, §8, §11`; `13-app-types/01 §7`.
- **Порог суверенной постуры «> 1 ч в день»** и **«инструмент делается как продукт, если им пользуются больше 10
  человек или он участвует в денежном процессе»** — `[мнение]` — `01-foundations/01 §5.1`; `13-app-types/01`, ov 10.
- **«Работает → надёжно → удобно → приятно»**; для инструментов с высокой ценой ошибки целевая эмоция — собранность, а
  не восторг — `[мнение]` (Купер против NN/g) — `01-foundations/04 §3`.
- **Восемь канонических разделов настроек** (профиль, аккаунт и безопасность, уведомления, внешний вид, команда и
  доступ, биллинг, интеграции и API, опасная зона); поиск по настройкам — от ~25–30 настроек — `[практика]` / `[мнение]`
  — `04-components-patterns/09 §1.2, §2.3`.
- **Числа Фридмана со слайдов**: `autocomplete` экономит ≥30 % времени; переключение клавиатура ↔ мышь ≈400 мс, на
  форме из 8 полей табуляция втрое быстрее; не больше 6–7 полей на шаг — `[практика]` / `[мнение]` единичного
  источника — `04-components-patterns/05 §2.5, §6.2`.
- **Три величины «бейджей»**: счётчики-бейджи ≤2–3 на экран `[мнение]`; типы уникальных индикаторов на списке ≤2–3
  `[исследование]`; индикаторов статуса на экране ≤5–6 `[система]` — одно слово, три разные величины —
  `04-components-patterns/04 §2.5, §5.3`; `03-layout-placement/03 §9`.
- **Отложенный показ индикатора** 200–400 мс и минимум 300–500 мс; порог 30 с для перевода операции в фон; пять
  элементов фоновой задачи — `[практика]` — `06-feedback-states-motion/02 §2.4, §5`.
- **Ролевой онбординг** (разные первые экраны для владельца, сотрудника, клиента) и **экраны 403 / 404 / 500 внутри
  приложения** (каркас сохраняется, минимум два выхода, на 403 — «запросить доступ») — `[практика]`, источников с
  исследованиями нет — `05-flows-journeys/01 §8`; `05-flows-journeys/04 §7`; `07-ux-writing/02 §15`.
- **Командная палитра**: слой поверх видимой навигации, включена по умолчанию, с видимым триггером и подсказкой
  сочетания (без неё не используется — кейс GitHub); публичных исследований принятия нет — `[практика]` —
  `04-components-patterns/10 §4.4`; `02-ia-navigation/01 §10`; `13-app-types/01 §8`.
- **Дизайн-KPI Фридмана**: 30–40 задач-формулировок, планка 80–90 % успешных выполнений по каждой — `[практика]` одного
  консультанта — `12-evaluation-checklists/04 §4.2`.
- **ИИ-функции**: человек в цикле для действий — план → предпросмотр → подтверждение → применение → журнал → отмена;
  всегда есть путь без ИИ; потоковый вывод — состояние «идёт генерация», а не результат (признак незавершённости,
  остановка, запрет действий над недописанным); уверенность показывать не всегда, N-best лучше числа; чат — не конечная
  форма интерфейса; 18 правил Microsoft (2019) — каркас ревью — `[практика]` / `[мнение]`, исследований по UX потокового
  вывода нет — `13-app-types/03 §6, §7, §10, §12`; `06-feedback-states-motion/02 §10`.
- **Юмор и эмодзи** — измерений нет ни за, ни против; позиция базы: эмодзи в интерфейсе — нет (иконка должна быть
  частью системы), юмор — только когда виновата система и потерь нет; в админках безопаснее не шутить — `[спорно]` —
  `07-ux-writing/01 §8`; `07-ux-writing/06 §5.3`.
- **Расширение формулы Нильсена–Ландауэра на линзы агента** (пять линз ≈ 93 % крупных проблем) — гипотеза для
  собственного стенда — `[мнение]` — `12-evaluation-checklists/01 §7.2`.

### Числа для оценки и тестирования (не правила интерфейса)

Один оценщик находит 42 % крупных и 32 % мелких проблем (1992) → 3–5 проходов; серьёзность 0–4 отдельным проходом,
среднее трёх. Тест с людьми: 5 участников для качественного раунда, 20 — минимум для чисел, 3 — регулярные дешёвые
раунды по ёмкости команды на починку (Krug), 15 на группу для карточной сортировки, 39 — для устойчивых тепловых карт;
три теста по 5 лучше одного на 15 (найдено = N(1 − (1 − L)ⁿ), L ≈ 31 %). Разброс времени задачи — SD 52 % от среднего:
при 20 участниках ±19 %, для ±10 % нужны 76 человек. SUS: среднее 68, 80,3 и выше — верхние 10 %, ниже 51 — нижние 15 %;
UMUX-Lite (два утверждения) коррелирует с SUS r = 0,83; SEQ — одна шкала 1–7 сразу после задачи, среднее 5,3–5,6, ниже 5 —
спрашивать почему; NPS — лояльность, не юзабилити; опросники — от 20–30 респондентов; качественное исследование
процентов не даёт («6 из 12» в проценты не переводят); PURE коррелирует с SEQ 0,5 и с SUS 0,4; успешность задачи —
базовая метрика везде; задача формулируется как роль + ситуация + цель без слов из интерфейса; не тестировать на
дизайнерах; отчёт — две страницы, разбор сразу после теста. — `12-evaluation-checklists/01 §2–§3`;
`12-evaluation-checklists/04 §3, §5, §7`.

### Позиции, ограниченные контекстом

Русские источники трека видео (Бирман, Кочеткова, Курлаев, Умнова, Бородкин, Степанова, Романовский, Стернина,
Аляновский, UsabilityLab) дают базе правила «когда и зачем», грамматическую рамку микрокопи и антипримеры с конкретикой,
которых нет в статьях. Но часть их позиций — риторика доклада или следствие контекста (унаследованные системы, регламент
банка, переговоры с заказчиком). Такие позиции в базе записаны как развилки с условием, а не как правила (реестр № 60):

предложения — `07-ux-writing/03`), «работоспособность интерфейса» как третий слой оценки (Бюро Горбунова), позиция
«стабильность и привычка выше локальной оптимальности» (реестр № 50), организационная механика B2B (закупает менеджмент —
работает оператор; саботаж внедрения; «стать частью мозга заказчика»), реклама как часть UX-разбора, банковская тайна как
аргумент доступности, «этикет обновлений» и «хвосты» в дереве доступности, качество связи как параметр доступности.
