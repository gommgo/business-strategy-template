## Выжимка для агента

Делай:

1. **Начинай с явного сохранения.** Primer: «When designing a form, **start with an explicit saving pattern**» [S2].
   Автосохранение вводится осознанно, для конкретных типов данных, а не «чтобы было современно». → §1.1 `[система]`
2. **Не смешивай явное и автоматическое сохранение внутри одной формы** и не смешивай на одной странице без явного
   визуального разделения блоков [S2]. → §1.3 `[система]`
3. **Декларативные контролы — явное сохранение** (текстовые поля, группы чекбоксов и радиокнопок, нативные `select`,
   мультиселекты); **императивные — автосохранение** (переключатель, сегментированный контрол, одиночный не-нативный
   дропдаун) [S2]. → §1.4 `[система]`
4. **Автосохраняй по паузе, а не по таймеру.** Купер: сохранять «every single little change as soon as the user makes
   it»; критика таймера Word, который «clamps shut» посреди набора; «wait until the user stops typing for a couple of
   seconds and **then** save» [S1]. → §2.1 `[мнение]`
5. **Оставляй ручное сохранение даже при автосохранении.** «All programs should have manual save controls, but users
   should **not be required** to invoke manual saves» [S1]; NN/g: «autosave does not need to replace save: **they can
   both coexist**» [S3]. → §1.1, §2.2 `[консенсус]`
6. **Показывай состояние сохранения**, если результат не очевиден из самого интерфейса: «сохраняется» → «сохранено в
   HH:MM» → «не сохранено». → §2.2 `[спорно]` (разбор противоречия — §2.2)
7. **Держи кнопку сохранения активной всегда.** Primer: «Do not disable or hide a form's save button even if the form
   is invalid or has not been changed» — `disabled` не фокусируется Tab'ом и низкоконтрастен [S2]. → §1.5 `[система]`
8. **Одна кнопка сохранения на странице** и один активный режим редактирования одновременно [S2]. → §1.5 `[система]`
9. **Подписывай кнопку глаголом и объектом**: «Сохранить профиль», а не «Готово» [S2]. → §1.5 `[система]`
10. **Черновик вместо вопроса «вы уверены?».** Twitter при отмене написания твита предлагает «Удалить черновик» /
    «Сохранить черновик»; Instagram при уходе назад предлагает сохранить в черновик [S14][S15]. → §3.5 `[консенсус]`
11. **Выход из длинного процесса называется «Сохранить и вернуться позже»**, а не «Отмена» (формулировка GOV.UK) [S11].
    → §3.5 `[система]`
12. **Черновик должен быть находим**: отдельный список или пометка в общем списке, с датой и с кнопкой «продолжить».
    → §3.2 `[практика]`
13. **Автоматические снимки версий — сами по себе**: Figma каждые 30 минут плюс при потере связи и при падении [S7];
    Notion каждые 10 минут активной правки плюс через 2 минуты после последней правки [S10]. → §4.2 `[система]`
14. **У версии есть автор, время, описание.** Figma показывает имя версии, описание, дату и **имя и аватар основного
    автора** [S7]. → §4.3 `[система]`
15. **Оптимистичное обновление помечает элемент, а не удаляет его.** React: элемент остаётся в списке со статусом
    «удаляется» (приглушение, зачёркивание, заблокированная кнопка), при ошибке возвращается сам [S6]. → §5.2 `[система]`
16. **Предупреждай об уходе только когда есть несохранённые изменения** и снимай слушатель, когда их нет: `beforeunload`
    ломает bfcache в Firefox и вредит производительности [S5]. → §6.2 `[система]`
17. **Для автоматического сохранения состояния используй `visibilitychange`, а не `beforeunload`**: последний не
    срабатывает надёжно на мобильных [S5]. → §6.3 `[система]`
18. **Не проси ввести то, что уже вводили в этом процессе** — WCAG 2.2, 3.3.7 Redundant Entry, уровень A [S13];
    канон — `../08-accessibility/01-wcag22-as-build-rules.md` §9.5. → §9 `[стандарт]`
19. **Показывай, кто ещё работает с объектом.** «Приложение работает как внешняя память пользователя»
    [V:P1CYZ65b5SA 01:03]; видимость активности коллег — `../01-foundations/01-principles-and-laws.md` §6.13.
    → §7.1 `[практика]`
20. **Дай посмотреть, как это было настроено в прошлый раз.** Настройку резервного копирования делают раз в квартал,
    и человек хочет увидеть предыдущую конфигурацию — она показывает, как выглядит приемлемое решение
    [V:P1CYZ65b5SA 01:03]. → §4.6 `[практика]`
21. **Запоминай рабочее состояние интерфейса на пользователя**: фильтры, сортировку, набор и ширины колонок, выбранную
    вкладку, свёрнутые панели, ширину боковой панели. → §8.1 `[практика]`
22. **Держи адресуемое состояние в URL**: фильтры, вкладка, открытая запись, страница списка. Тогда «Назад», обновление
    и пересылка ссылки работают без дополнительной работы. → §8.4 `[практика]`
23. **Составь явный список того, что переживает переход между экранами** — это измеренно самое слабое место у
    генераторов интерфейсов (три из шести фронтирных моделей набирают 0.0). → §9 `[исследование]`

Не делай:

24. **Не убирай кнопку «Сохранить» ради «эффективности».** Кейс Nextdoor: форма настроек без кнопки Save выбивает
    человека из автопилота; «the reduction in the number of steps does not translate in a reduction of the interaction
    cost» [S3]. → §1.1 `[исследование]`
25. **Не спрашивай «Сохранить изменения?» при закрытии.** «A dialog box that is **always answered the same way** is a
    redundant dialog box that should be eliminated» [S1]. → §6.1 `[мнение]`
26. **Не используй «Не сохранять» как суррогат отмены** — для этого есть undo и явная команда «Отменить все изменения»
    [S1]. → §6.4 `[мнение]`
27. **Не совмещай сохранение с выбором формата или места хранения** — это свойства объекта, а не часть сохранения [S1].
    → §1.6 `[мнение]`
28. **Не создавай копию через диалог** с выбором имени и папки: «there should be no such interruption» [S1]. → §4.6 `[мнение]`
29. **Не показывай индикатор сохранения там, где его можно спутать со статусом валидации** [S2]. → §2.2 `[система]`
30. **Не обещай, что автосохранение заменяет офлайн-режим.** Figma прямо: «Autosave is a **safeguard**… it's not a
    fully-featured offline mode» [S9]. → §2.3 `[система]`
31. **Не храни критичное состояние только в браузере.** Figma перечисляет условия потери: неподдерживаемый браузер,
    очистка кэша, приватный режим, переполненная квота, расширение [S9]. → §2.4 `[система]`
32. **Не сбрасывай фильтры и выбор при возврате назад** — это дефект F6.3 каталога ИИ-дефектов. → §9 `[исследование]`
33. **Не запоминай то, что пользователь ожидает видеть чистым**: строку поиска, снятые галочки массового выделения,
    режим редактирования. → §8.2 `[практика]`

## 1. Развилка: явное сохранение, автосохранение, немедленное применение

### 1.1 Три модели

| Модель | Механика | Ментальная модель пользователя |
|---|---|---|
| **Явное сохранение** | Изменения применяются по кнопке или по Enter в поле; уход со страницы отменяет | «Пока не нажал — ничего не произошло» |
| **Автосохранение** | Изменения применяются сами, с паузой или по событию; состояние показывается | «Система пишет за мной» |
| **Немедленное применение** | Изменение контрола **есть** действие; отдельного сохранения нет | «Я щёлкнул выключателем — свет включился» |

Стартовая позиция — явное сохранение [S2] `[система]`: «When designing a form, **start with an explicit saving
pattern**.» Автосохранение и немедленное применение вводятся точечно, по типу контрола (§1.4) и по типу данных (§1.2).

**Почему нельзя просто убрать кнопку.** NN/g разбирает кейс Nextdoor (форма «Email Settings» без кнопки Save)
[S3] `[исследование]` — это наблюдение в исследовании с формулой:

> **IC = P + M** (interaction cost = physical + mental). «It's not worth reducing P by a small amount if the
> corresponding M becomes much larger.»
> «By removing the *Save* button the designers have taken users out of autopilot mode… users must now spend time
> looking around the page for the omitted *Save* button… **The reduction in the number of steps does not translate in a
> reduction of the interaction cost**.»

И главное про ментальную модель: «most users assume nothing is really changed until a *Save* or *Apply* button is
pressed, and **navigating away from the form will revert any changes** just as though they hit *Cancel*» [S3].

**Почему кнопку нельзя оставить единственным механизмом.** Купер [S1] `[мнение]`: «The program should **automatically**
save the document… At the very least, when the user is done with the document and requests the Close function, the
program will merely go ahead and write the changes out to disk without stopping to ask for confirmation.» И сразу:
«All programs should have manual save controls, but users should **not be required** to invoke manual saves.»

**Разрешение**: автосохранение и кнопка сосуществуют [S3]. Кнопка — для контроля и для ментальной модели; автосохранение
— чтобы не терять работу при сбое. Противоречие касается только **индикации** (§2.2).

### 1.2 Выбор модели по типу данных и последствий

`[практика]` — синтез [S1][S2][S3] и практики; прямого исследования по типам данных не найдено.

| Тип данных | Модель | Почему |
|---|---|---|
| **Документ, заметка, длинный текст, канвас** | Автосохранение + версии + ручная веха | Потеря дорога, откат есть, результат виден сразу |
| **Форма с внешними последствиями** (заявка, платёж, публикация, рассылка) | **Явное сохранение**, черновик отдельно | Промежуточное состояние не должно уходить наружу |
| **Настройки-переключатели** (уведомления, темы, флаги) | Немедленное применение | Результат виден; контрол императивный (§1.4) |
| **Настройки-формы** (реквизиты, политики, лимиты) | Явное сохранение | Данные связаны между собой; частичное применение опасно |
| **Правка в строке таблицы** | Явное подтверждение строки | Соседние данные не должны меняться от случайного клика |
| **Фильтры, сортировка, набор колонок** | Немедленное применение + сохранение как состояние интерфейса (§8) | Это не данные, а вид; откат — снять фильтр |
| **Массовая правка** | Явное сохранение всей операции | `03-…` §6 |
| **Черновик сообщения, комментария, письма** | Автосохранение черновика | Прерывание типично, потеря болезненна |

### 1.3 Правило «не смешивать»

`[система]` [S2] — прямое требование Primer:

> «Avoid mixing explicit and automatic save patterns on a single page with multiple forms, and **never mix save
> patterns in a single form**. For example: if I upload a profile photo in the "Public profile" form, that change
> should not be saved until I explicitly submit the whole form.»

Practical: если на странице есть и автосохраняемые переключатели, и явно сохраняемая форма, они должны быть
**визуально разделены** на отдельные блоки с собственными границами, и у формы должна быть своя кнопка
(рекомендация Primer «Separate auto-saving controls from an explicitly saved form»).

Частый антипаттерн, который это правило запрещает: страница настроек, где половина переключателей применяется сразу,
а половина ждёт кнопки внизу, без всякого визуального различия. Пользователь не может угадать, что уже применено.

### 1.4 Императивные и декларативные контролы

Самое исполнимое правило выбора модели [S2] `[система]`:

**Декларативные контролы — только явное сохранение** (иначе ломается доступность):
- текстовые поля — «Users expect to set a value and then submit. **Sensitive information could be unintentionally
  submitted**, such as a change password input»;
- группы чекбоксов — «It could be unclear whether or not the selection has been saved. Users may accidentally submit a
  selection clicked by accident»;
- группы радиокнопок — «**Screenreader users can't read the options without selecting them**, which could accidentally
  apply a selection the user didn't want»;
- нативные `<select>` — то же самое при переборе стрелками;
- мультиселекты — «Use save and cancel buttons in dropdowns that allow multiple selections».

**Императивные контролы — только автосохранение** (мгновенная обратная связь, отдельное сохранение избыточно):
- переключатель (ToggleSwitch) — «behaves like a light switch: the light just switches on and off without you having to
  confirm each time you flip the switch»;
- сегментированный контрол — «behaves like tabs: the tab changes as soon as you select it»;
- одиночный не-нативный дропдаун — «behaves like a radio dial: the station starts playing as soon as you select it».

Отдельное правило для меню [S2]: «Semantic menus should only have a list of options to select from and should not have
a save button. **As soon as additional features (search inputs, filters, tabs, etc) are added, the component should be
treated like a dialog** with a button to submit and a button to cancel.»

Аргумент про радиокнопки и скринридеры — сильнейший в этом списке: он превращает выбор модели сохранения из вопроса
вкуса в вопрос доступности.

### 1.5 Кнопка сохранения

`[система]` [S2]:

- **Подпись**: активный глагол — Create / Save / Delete / Update; при неочевидности добавлять имя объекта («Сохранить
  публичный профиль», а не «Готово»). Правило: «Add the item's name to the button text in cases where it may be unclear
  to the user what is being changed.»
- **Вид**: primary — если кнопка сохраняет всю страницу; secondary — если только сегмент; при паре с Cancel —
  primary для сохранения, secondary для отмены.
- **Состояние**: «**Do not disable or hide a form's save button even if the form is invalid or has not been changed.**
  Disabled buttons cannot be focused using the Tab key, and disabled button styles are typically low-contrast and
  difficult to read.» Согласовано с Фридманом [V:qktwIWZNFY4 51:41]: disabled сообщает о проблеме, но не ведёт к
  решению, а при сбое скрипта запирает человека.
- **Число**: «There should be **only one save button on a page**»; несколько кнопок с одинаковой подписью путают
  пользователей скринридеров и голосового управления.
- **Один режим редактирования одновременно**, если блоки правятся отдельно: «Allow only one edit mode activated at a
  time.»
- **Если все поля сохраняются сами — кнопки быть не должно**: «This makes it unclear when data is being saved.»
- **Размещение**: по умолчанию внизу слева, Cancel справа от Save; в диалогах и в комментариях — внизу справа, Cancel
  слева; при инлайн-редактировании — вплотную к полю. (Расхождение платформ по порядку кнопок разобрано в
  `../03-layout-placement/04-placement-conventions-and-redundancy.md` §4.)

### 1.6 Что не относится к сохранению

Купер отдельно разбирает функции, которые ошибочно пришивают к сохранению [S1] `[мнение]`:

- **Формат хранения**. «By tying the physical format to the act of saving, the user is confronted with additional,
  unnecessary complexity… From the user's point-of-view, the physical format of the document is a **characteristic of
  the document** rather than of the disk file.» Место — свойства объекта или отдельный экспорт.
- **Имя и размещение**. Диалог «Сохранить как» одновременно именует и размещает, но **не умеет переименовывать и
  перемещать существующий объект** — и это порождает ловушку: правил объект 20 минут, вызвал «Сохранить как» с новым
  именем → старый объект уходит на диск **без последних 20 минут**. Правильная механика: имя правится на месте
  (в заголовке), перемещение — отдельная команда.
- **Отмена изменений**. «The file system should not be called in as a surrogate for undo… The concept of going directly
  to the file system to undo changes merely **undermines the undo function**.»

Восемь целевых функций вместо тройки «Сохранить как / Сохранить изменения / Открыть» [S1] — готовый список для
проектирования работы с объектом:
1. автоматически сохранять; 2. создать копию (**Snapshot Copy**, имя «Копия X», без диалога); 3. создать веху;
4. именовать и переименовывать на месте; 5. размещать и перемещать; 6. задавать формат хранения (отдельно);
7. отменять изменения (undo); 8. **отказаться от всех изменений** (явная команда «Отменить все изменения»).

## 2. Автосохранение: механика

### 2.1 Когда именно сохранять

`[мнение]`, но правило исполнимое и единственное найденное [S1]:

- Идеал: «the program will save **every single little change as soon as the user makes it**, in other words, after each
  keystroke. For most programs, this is quite feasible.»
- Критика таймера: Word сохраняет по обратному отсчёту и «it just **clamps shut** in a very realistic and disconcerting
  imitation of a broken program… It is a very unpleasant experience.»
- Правило: «**If the algorithm would pay attention to the user instead of the clock, the problem would disappear**…
  All the program needs to do is wait until the user **stops typing for a couple of seconds** and *then* save.»

То есть: **debounce по паузе ввода (порядка 1–3 с), а не интервал по часам.** Плюс обязательные точки сохранения по
событиям `[практика]`:
- уход фокуса из поля;
- переход на другой шаг, вкладку, объект;
- сворачивание вкладки (`visibilitychange`, §6.3);
- закрытие вкладки, насколько это возможно;
- потеря соединения — Figma создаёт контрольную точку при потере связи и при падении [S7].

Отдельно: **сохранение не должно блокировать ввод.** Индикатор «сохраняется» не отбирает фокус, не блокирует поля и не
перерисовывает содержимое.

### 2.2 Индикация: противоречие и его разрешение

`[спорно]` — источники требуют противоположного.

| Источник | Требование |
|---|---|
| NN/g [S3] | Показать «Saved» рядом с каждым изменённым полем: «**visual feedback must be displayed for every process a system undertakes**»; иначе «the website is an autonomous entity that decides on its own how and when to do things» |
| Primer [S2] | «If a form field is saved automatically, it should be obvious whether or not it saved **without using text or visual indicators**. A visual indicator… **could be mistaken as a validation status**» |

Разрешение (синтез базы, требует проверки) `[практика]`:

- **Результат виден сам по себе → индикатор не нужен.** Переключатель уведомлений щёлкнул, вкладка переключилась,
  элемент списка переехал — это и есть подтверждение. Здесь прав Primer.
- **Результат не виден в области просмотра → индикатор обязателен.** Длинный документ, форма с автосохранением,
  настройки, где изменение влияет на другой экран. Здесь прав NN/g.
- **Индикатор не должен выглядеть как статус валидации**: не зелёная галочка у поля (это «значение корректно»), а
  **статус на уровне объекта**: строка в шапке области — «Все изменения сохранены · 14:32» / «Сохранение…» /
  «Не сохранено».
- **Три состояния, не два**: «сохраняется» — «сохранено (с временем)» — «не сохранено (с причиной и действием)».
  Третье состояние обязательно: без него человек не отличит «сохранено» от «не дошло».
- Визуальное исполнение индикаторов — у агента E2, `../06-feedback-states-motion/02-system-status-and-waiting.md`.

Дополнительный аргумент за индикацию: она закрывает вопрос **времени**. «Сохранено» без времени не отвечает на вопрос
«а мои последние три абзаца попали?»; «Сохранено в 14:32» отвечает.

### 2.3 Сбой автосохранения

`[система]` [S9] + `[практика]`:

- **Автосохранение — предохранитель, а не режим работы.** Figma прямо: «Autosave is a safeguard in the event that
  something goes wrong, **it's not a fully-featured offline mode**. It significantly reduces the possibility of data
  loss» — и перечисляет случаи: нестабильная связь, падение приложения, браузера или ОС, перезагрузка машины,
  отключение питания.
- **Сбой автосохранения — отдельное состояние с действием**, а не молчание: «Не удалось сохранить. Повторить» плюс
  сохранение изменений локально до восстановления связи.
- **Не терять изменения при закрытии вкладки**: Figma хранит изменения в IndexedDB браузера и применяет их при
  следующем открытии файла — «This applies even if you close the tab or browser, or shut down your device entirely»
  [S9]. Важная деталь: «**If you've closed the affected files, you will need to reopen them to sync** your offline
  changes» — то есть синхронизация не происходит сама, и об этом надо сказать пользователю.
- **Несколько вкладок и несколько людей офлайн**: Figma сохраняет ожидающие изменения в каждой вкладке и сливает их
  при возврате связи [S9]. Если ваша система так не умеет — это должно быть сказано, а не обнаружено.

### 2.4 Где живёт несохранённое

`[система]` [S9], полные предупреждения:

Figma перечисляет **условия, при которых локально сохранённые изменения будут потеряны**: неподдерживаемый браузер или
его версия; кэш очищен до переподключения; приватный режим или гостевая учётка, автоматически очищающая данные;
переполненная квота хранилища браузера; расширение браузера, помешавшее сохранению.

Отсюда правило `[практика]`: **критичное состояние не хранится только в браузере.** Локальное хранилище — второй
эшелон; первый — сервер. Если серверного эшелона нет (например, пользователь не аутентифицирован), это надо сказать
прямо: «Черновик хранится только в этом браузере».

Иерархия хранилищ для сценариев:

| Что | Где | Почему |
|---|---|---|
| Черновик объекта, за который отвечает продукт | Сервер | Переживает смену устройства; виден в списке черновиков |
| Промежуточное состояние формы до первой отправки | Локально + сервер по возможности | Сервер может ещё не знать об объекте |
| Состояние интерфейса (фильтры, колонки, панели) | Сервер (профиль) для долгоживущего, локально для сессионного | §8.3 |
| Адресуемое состояние (что открыто, что отфильтровано) | **URL** | §8.4 |
| Несохранённые изменения при обрыве связи | Локально, с последующей синхронизацией | §2.3 |

## 3. Черновики

### 3.1 Что такое черновик

`[практика]`: черновик — это **объект в состоянии «существует, но не действует»**. Отличия от смежных понятий:

- от **несохранённых изменений**: черновик сохранён, просто не опубликован и не отправлен;
- от **архива**: архив — то, что действовало и перестало быть актуальным (`03-…` §3.1);
- от **корзины**: корзина — то, что удалили.

Черновик решает три задачи: прерывание (`02-task-flows-and-wizards.md` §6), безопасное исследование (`03-…` §8) и
разделение «сделал» и «применил».

Купер формулирует потребность в черновике как **fudgeability** — способность системы принять промежуточное, ещё не
полное состояние: «В большинстве компьютеризованных систем есть только два состояния: несуществование и полное
соответствие… Разрешая много мелких временных ошибок и доверяя людям исправить их до того, как они вызовут проблемы
дальше по потоку, мы избегаем куда больших и постоянных ошибок»
(`../01-foundations/01-principles-and-laws.md` §5.5, п. 13). Практический перевод: **объект можно сохранить с
незаполненными необязательными полями и со статусом «требует уточнения»**.

### 3.2 Где черновики живут и как их находят

`[практика]` — прямых источников по интерфейсу черновиков не найдено; правила выведены из требования обнаружимости
(«если пользователь не может это найти — этого не существует», `../01-foundations/04-psychology-of-satisfaction.md` §5.5).

Три схемы размещения:

| Схема | Когда | Риск |
|---|---|---|
| **Отдельный список «Черновики»** | Черновиков много, они самостоятельны (письма, статьи, рассылки) | Про него забывают, если нет счётчика |
| **Черновики в общем списке с бейджем** | Черновиков мало, они лежат среди готовых объектов (заявки, документы) | Замусоривают список; нужен фильтр |
| **Возврат к черновику из точки создания** | Черновик один на сценарий (незавершённая настройка, недооформленный заказ) | Теряется при смене устройства, если хранится локально |

Обязательный минимум:
- **счётчик черновиков** там, где их ждут (пункт меню, вкладка);
- у черновика — **дата последнего изменения** и, если правят несколько человек, автор;
- **кнопка «Продолжить»**, ведущая **на тот шаг, где человек остановился**, а не в начало;
- если черновик привязан к длинному процессу — показать **прогресс** («заполнено 3 из 5 разделов»), как в списке задач
  GOV.UK (`02-task-flows-and-wizards.md` §4).

### 3.3 Срок хранения и уборка

`[практика]` — задокументированных сроков хранения именно черновиков я не нашёл; ориентиры берутся из сроков корзины
(30 дней Drive и Notion, 90 дней GitHub — `03-…` §3.2).

Правила:
- Если срок есть — **он показан на черновике** («будет удалён 21 октября»), а не спрятан в справку.
- **Предупредить до удаления**, а не после.
- Черновики, привязанные к процессу с дедлайном (заявка, тендер, отчётный период), удаляются по логике процесса, и об
  этом сказано в момент создания.
- Черновики **не должны занимать лимиты** видимых объектов, если они не действуют; если занимают — сказать (аналог
  честной оговорки Drive о квоте, `03-…` §3.4).

### 3.4 Черновик и валидация

`[практика]`:
- **Черновик сохраняется с ошибками валидации.** Это его смысл: человек не дозаполнил.
- Валидация «на публикацию» и валидация «на сохранение черновика» — **разные наборы правил**. Для черновика
  обязательным может быть одно поле (например, название), для публикации — двадцать.
- При попытке опубликовать неполный черновик показывается сводка недостающего со ссылками на поля
  (`04-errors-and-recovery.md` §3.5), а не отказ в сохранении.
- GOV.UK решает то же самое иначе — вопросом «Have you completed this section?» с вариантами «Yes, I've completed this
  section» / «No, I'll come back later», после чего задача помечается «Incomplete» или «In progress» [S11]. Это
  полезно, когда система сама не может определить полноту (необязательные вопросы, длинный текст, сверка с кем-то).

### 3.5 Выход с сохранением черновика

`[консенсус]`:

- **Twitter** при нажатии Cancel в черновике твита показывает выбор «Удалить черновик» / «Сохранить черновик». NN/g:
  «This choice ensures users don't accidentally lose work» [S14].
- **Instagram** при уходе назад из процесса добавления изображения в историю предлагает сохранить работу как черновик
  [S15].
- **GOV.UK** называет выход из длинного процесса **«Сохранить и вернуться позже»** — формулировка задаёт ожидание
  вместо тревоги [S11].
- **Apple** для выбора, связанного с намеренным действием, требует action sheet, а не алерт: отмена письма даёт **три**
  варианта — удалить правки или весь черновик, сохранить черновик, вернуться к редактированию
  (`03-destructive-actions-undo-confirmation.md` §4.3, источник [S3] того файла — Apple HIG «Alerts»).

Правило `[практика]`: **три варианта, а не два.** «Сохранить черновик» — «Удалить» — «Продолжить редактирование».
Вариант «Продолжить редактирование» обязателен: часто человек нажал «Выйти» случайно.

Плохой вариант этого же диалога — «Вы уверены, что хотите уйти? Изменения не сохранятся» с кнопками «Да/Нет»: он
спрашивает про намерение вместо того, чтобы предложить решение (см. запрет Microsoft подтверждать отказ от задачи,
`03-…` §4.2).

## 4. Версии и история изменений

### 4.1 Когда нужны

`[практика]`, опора — типология Купера (`03-…` §2.2) и задокументированные реализации [S7][S10]:

| Признак | Нужна история версий |
|---|---|
| Объект живёт долго и меняется многократно | Да |
| Объект правят несколько человек | Да, обязательно (иначе чужое изменение необратимо) |
| Ошибку можно заметить спустя дни | Да (стек undo не достаёт) |
| Есть регуляторные требования к аудиту | Да, плюс журнал действий (`03-…` §9.2) |
| Объект короткоживущий и одноразовый | Нет, достаточно undo и черновика |

Версии закрывают то, чего не закрывает undo: ошибка замечена позже; ошибку сделал другой; сессия давно закрыта;
нужно сравнить «как было» и «как стало».

### 4.2 Частота автоматических снимков

`[система]` — два задокументированных значения, обоснований не опубликовано:

| Продукт | Автоматический снимок | Дополнительно |
|---|---|---|
| **Figma** | **каждые 30 минут** | плюс контрольная точка **при потере соединения и при падении**; плюс при создании и слиянии ветки [S7][S8] |
| **Notion** | **каждые 10 минут** активного редактирования | плюс ещё одна версия **через 2 минуты после последней правки** [S10] |

Схема Notion точнее: она различает «идёт работа» и «работа закончилась», и второе условие гарантирует, что финальное
состояние сессии редактирования попадёт в историю. Это переносимое правило `[практика]`: **снимок по интервалу во
время активности + снимок по завершению активности**.

**Глубина хранения** — тарифицируемый параметр в обоих продуктах:
- Notion: **7 дней (Free) / 30 (Plus) / 90 (Business) / без ограничения (Enterprise)** [S10];
- Figma: **30 дней** на бесплатном тарифе, полная история на платных [S7].

Для собственного продукта `[практика]`: глубина должна быть **явно названа в интерфейсе**, а не подразумеваться, и
«истёкшие» версии должны исчезать предсказуемо, а не молча.

### 4.3 Состав записи версии

`[система]` [S7][S1]:

Обязательно: **время и дата**, **автор** (Figma показывает имя и аватар основного автора), **название или описание**.
Купер добавляет размер и заметку пользователя [S1].

Различение автоматических и ручных версий [S7]:
- автоматические группируются в таймлайне и раскрываются по клику — иначе список из сотни снимков нечитаем;
- ручная версия создаётся командой (Figma: Cmd/Ctrl+Alt+S) и получает **заголовок и описание**;
- ограничения интерфейса Figma, полезные как ориентир: **заголовок обрезается после 25 знаков**, описание видно
  целиком **до 140 знаков**; ссылки в описании не становятся кликабельными.

Права [S7]: смотреть историю — при праве «просмотр»; создавать, переименовывать, восстанавливать — только при праве
«редактирование». Это разумный дефолт: история — часть содержания, восстановление — изменение.

### 4.4 Что делать с версией

`[система]` [S7] — набор действий Figma переносится почти дословно:

- **посмотреть** (снимок открывается для просмотра, панорамирования, копирования объектов);
- **восстановить**;
- **дублировать в новый объект** — «Duplicate to share a specific version or point in time… or use as a starting point
  for further iteration». Это прямой механизм безопасного исследования (`03-…` §8.2);
- **дать ссылку на конкретную версию**;
- **назвать существующую версию** задним числом.

Важное ограничение, которое Figma честно называет: у дубликата версии **не переносятся комментарии и история**
оригинала [S7]. Любое «создание копии» обязано сообщать, что именно не скопировалось.

Правила восстановления `[практика]`:
- **Перед восстановлением создаётся точка текущего состояния** — восстановление само должно быть обратимым.
- Показать, **что изменится** при восстановлении (сколько правок будет отменено, чьи).
- Восстановление попадает в историю как отдельное событие с автором.

### 4.5 Показ различий

`[практика]` — публичной UX-документации по показу диффов в продуктовых интерфейсах я не нашёл; правила выведены из
механики ревью Figma [S8] и из требования конкретности:

- **По полям, а не по объекту целиком**: «Статус: Новая → В работе», «Срок: 12.10 → 19.10».
- **Только изменившееся** по умолчанию; всё остальное — по запросу.
- **Две формы просмотра**: рядом (side-by-side) и наложением — Figma даёт обе в ревью ветки [S8].
- Для длинных текстов — подсветка вставленного и удалённого.
- Для структурных изменений — дерево «добавлено / изменено / удалено», как в ревью ветки Figma (по страницам).

### 4.6 Прошлая конфигурация как справка

Недооценённый сценарий, зафиксированный NN/g [V:P1CYZ65b5SA 01:03] `[практика]`:

> Настройку автоматического резервного копирования серверов делают **раз в квартал**; пользователь не помнит, как
> делал прошлый раз, и хочет посмотреть предыдущую настройку — она показывает, **как выглядит приемлемое решение**, и
> избавляет от старта с нуля. «Приложение работает как внешняя память пользователя.»

Следствия для проектирования редких сценариев:
- **Показывать прошлую конфигурацию рядом** с формой новой, а не прятать её за модалку или в историю.
- **Предзаполнять из прошлого запуска.** NN/g в правилах мастеров: «Consider reusing the user's selections from previous
  use as the defaults for the next use» (`02-task-flows-and-wizards.md` §3.4).
- **Давать «повторить прошлую настройку»** одним действием.
- Купер о создании копии: **без диалога, тихо** — «Copy of X» в том же месте [S1]. Копия прошлой конфигурации — самый
  дешёвый способ начать.

## 5. Оптимистичное обновление

### 5.1 Когда безопасно

`[практика]` — синтез механики [S6] и правил обратимости:

**Безопасно**, когда одновременно выполняются три условия:
1. Вероятность отказа низка (обычная операция над своим объектом).
2. Откат **не уничтожает работу пользователя** (он ничего не вводил или ввод сохранён).
3. Пользователь **увидит** откат и поймёт его (он остался на том же экране).

**Не применять**:
- к операциям, где цена расхождения высока: деньги, бронирование ограниченного ресурса, изменение прав, отправка
  наружу;
- к действиям, после которых происходит **переход на другой экран**: человек уйдёт, а откат случится там, где его не
  видно;
- к длительным операциям (больше пары секунд) — там уместен явный прогресс, а не иллюзия мгновенности;
- когда результат операции **вычисляется сервером** и предсказать его нельзя (номер, расчёт, статус после проверки).

### 5.2 Механика и откат

`[система]` [S6] — React описывает модель, которая переносится на любой стек:

- Оптимистичное состояние **временное по построению**: оно равно реальному значению, пока нет активного действия, и
  **схлопывается в реальное**, когда действие завершилось. «There's **no extra render to "clear" the optimistic
  state**. The optimistic and real state converge in the same render when the Transition completes.»
- **Отдельный код отката не нужен.** При ошибке действие завершается, реальное значение не менялось, интерфейс сам
  возвращается в прежнее состояние. Остаётся показать сообщение об ошибке.
- **Паттерн оптимистичного удаления** (прямо из документации): элемент **не исчезает** из списка, а помечается как
  удаляемый — приглушённая прозрачность, зачёркнутый текст, кнопка заблокирована и подписана «Удаляется…». При ошибке
  элемент **сам возвращается** в обычный вид, и рядом появляется сообщение.
- **Относительные обновления вместо абсолютных**: «прибавить 1», а не «поставить 5», иначе при параллельных изменениях
  показываются устаревшие значения.
- Типовая ошибка реализации: обновление вне транзакции — «the optimistic state will **briefly appear and then
  immediately revert**» (мигание интерфейса).
- Признак «операция в процессе» вычисляется сравнением оптимистичного и реального значения либо отдельным флагом.

### 5.3 Что показывать

`[практика]`:

| Момент | Что видит человек |
|---|---|
| Сразу после действия | Результат применён **с признаком незавершённости**: приглушение, пунктир, «Удаляется…», заблокированная кнопка |
| Успех | Признак незавершённости снимается; отдельное сообщение об успехе обычно не нужно — результат виден |
| Ошибка | Состояние возвращается, появляется сообщение **рядом с элементом** с причиной и кнопкой «Повторить» |
| Долгая задержка (> 2–3 с) | Оптимистичный режим не годится: переходить к явному прогрессу |

**Нельзя** показывать оптимистичный результат как окончательный (без признака незавершённости): тогда откат
воспринимается как самопроизвольное изменение данных, а это худший из возможных сигналов о надёжности системы
(«ложь системы о своём состоянии», `../01-foundations/04-psychology-of-satisfaction.md` §5.7).

## 6. Уход со страницы и несохранённые изменения

### 6.1 Когда предупреждать

`[консенсус]` с оговорками:

- **Если работает автосохранение — не предупреждать вообще.** Купер: «A dialog box that is **always answered the same
  way** is a redundant dialog box that should be eliminated» [S1].
- **Если сохранение явное и изменения есть — предупреждать.** Primer допускает `beforeunload` именно для этого [S2].
- **Если изменений нет — не вешать слушатель** [S5] (§6.2).
- **Лучше предупреждения — черновик.** Вместо «вы потеряете изменения» предложить «Сохранить черновик» (§3.5).
- **Внутренняя навигация (внутри SPA) — не то же самое, что закрытие вкладки.** Внутри приложения вы контролируете
  диалог полностью и можете дать три варианта; при закрытии вкладки — только браузерный текст (§6.2).

### 6.2 `beforeunload` и его пределы

`[система]` [S5] — технические ограничения, определяющие, что можно обещать:

- Диалог вызывается `event.preventDefault()`; `returnValue` — легаси-совместимость.
- **Требуется sticky activation**: браузер не покажет диалог, если человек ни разу не взаимодействовал со страницей.
  Логика MDN: «If the user has never interacted with the page, then there is no user data to save, so no legitimate use
  case for the dialog.»
- **Текст задать нельзя** — показывается общая формулировка браузера. Primer фиксирует это как ограничение: «Modern
  browsers prevent developers from customizing the `alert` message, so we're limited to a generic message like "Do you
  want to leave this site? Changes you made may not be saved"» [S2]. Figma о том же: «Figma isn't able to control the
  message included in this dialog» [S9].
- **Срабатывает ненадёжно, особенно на мобильных**: типичный сценарий, где события не будет, — человек ушёл в другое
  приложение и закрыл браузер из менеджера задач.
- **В Firefox ломает bfcache**: страницы со слушателем `beforeunload` не попадают в кэш «назад/вперёд», и это вредит
  производительности.
- Итоговая рекомендация MDN: **вешать слушатель только когда есть несохранённые изменения, и снимать его, когда их
  нет.**

Практический вывод `[практика]`: `beforeunload` — **последний рубеж, а не механизм сохранения**. Полагаться на него
как на защиту данных нельзя; он лишь уменьшает вероятность случайного закрытия.

### 6.3 `visibilitychange` как правильный триггер сохранения

`[система]` [S5]: «It is recommended to use the **`visibilitychange`** event as a more reliable signal for automatic
app state saving that gets around problems like the above.»

То есть: **сохранять состояние при сворачивании вкладки и уходе в фон**, а не пытаться поймать закрытие. Это же
покрывает мобильный сценарий «переключился на другое приложение».

Практическая связка `[практика]`:
1. debounce по паузе ввода (§2.1) — основное автосохранение;
2. `visibilitychange` — сохранение при уходе в фон;
3. `beforeunload` — только предупреждение и только при наличии несохранённого.

### 6.4 Три варианта при закрытии

`[система]` — образец даёт настольное приложение Figma [S9]: при попытке закрыть вкладку, выйти из приложения или из
аккаунта с офлайн-изменениями предлагается выбор:
- **Leave / Log out** — офлайн-изменения сохраняются в браузере, файлы можно открыть позже для синхронизации;
- **Discard / Discard and log out** — «Figma will clear any offline changes it stored in the browser. **This action
  can't be undone** and you won't be able to retrieve those changes in the future».

Хороший образец по двум причинам: варианты названы результатом, и про необратимость второго сказано прямо.

Требование к такому диалогу `[практика]`: три кнопки — «Сохранить и выйти», «Выйти без сохранения», «Остаться». Кнопка
«Остаться» не должна быть спрятана: чаще всего диалог возникает от случайного нажатия.

## 7. Совместная работа

### 7.1 Присутствие и активность

`[практика]`, опора — `../01-foundations/01-principles-and-laws.md` §6.13 (видимость активности коллег как
переложение social proof на рабочие инструменты) и [S9] (Figma перечисляет многопользовательские функции: «seeing who
is active in the file, observation mode, multiplayer cursors»).

Минимум для веб-сервиса:
- **Кто сейчас смотрит объект** — аватары в шапке карточки.
- **Кто сейчас редактирует** — отдельный, более сильный сигнал, чем «смотрит».
- **Кто последний менял и когда** — на самом объекте, а не только в истории.
- **Что именно поменялось с моего прошлого захода** — если объект долгоживущий.

Важно: присутствие — это **функция, требующая связи**. Figma честно относит все многопользовательские функции к
недоступным офлайн [S9]; значит в офлайне интерфейс не должен показывать устаревшие аватары как актуальные.

### 7.2 Блокировка против слияния

`[практика]` — стратегии и их цена разобраны в `04-errors-and-recovery.md` §4.6; здесь — следствия для сохранения:

| Стратегия | Что означает для сохранения |
|---|---|
| **Блокировка** | Сохранение всегда успешно, но нужен таймаут блокировки, видимый владелец блокировки и право администратора её снять; иначе объект «залипает» за ушедшим сотрудником |
| **Обнаружение конфликта** | Сохранение может не пройти; обязательны сохранение своей версии и показ расхождения (§4.5) |
| **Слияние** | Сохранение проходит всегда, но нужны история, точка возврата до слияния и путь разрешения конфликтов (модель Figma, `03-…` §8.3) |

Заимствуемое решение Figma [S8]: **перед слиянием создаётся дополнительная контрольная точка основного объекта**, и
вся работа ветки попадает в историю одной точкой, а детали остаются в ветке. Это даёт и откат, и читаемую историю.

### 7.3 Что не сливается

Честная оговорка, которую стоит копировать [S8] `[система]`: в Figma **комментарии не переносятся** между веткой и
основным файлом ни в одну сторону, и это написано прямо.

Общее правило `[практика]`: у любого механизма копирования, ветвления и слияния должен быть **явный список того, что
не переносится** (комментарии, история, права, вложения, связи), показанный до операции.

## 8. Состояние интерфейса на пользователя

### 8.1 Что запоминать

`[практика]` — прямых исследований не найдено; список выведен из принципа пространственной памяти и из требования не
заставлять повторять работу (`../01-foundations/01-principles-and-laws.md` §6.9, §5.3).

| Что | Где хранить | Срок |
|---|---|---|
| Применённые фильтры и поисковый запрос списка | URL (адресуемо) + профиль для «последнего использованного» | Сессия; по явному действию — навсегда (сохранённое представление) |
| Сортировка | URL + профиль | Как фильтры |
| Набор, порядок и ширины колонок таблицы | Профиль пользователя | Постоянно |
| Плотность отображения | Профиль | Постоянно |
| Выбранная вкладка внутри объекта | URL | Постоянно для типа объекта |
| Свёрнутые и развёрнутые панели, ширина боковой панели | Профиль (Primer и B фиксируют, что ширина панели запоминается) | Постоянно |
| Свёрнутость навигации | Профиль | Постоянно |
| Последняя открытая организация или проект | Профиль | Постоянно |
| Позиция прокрутки в длинном списке при возврате «назад» | Память маршрутизатора | В пределах сессии |
| Шаг мастера и введённые данные | Сервер (черновик) | До завершения или истечения срока |

**Сохранённые представления** (именованные наборы фильтров, колонок и сортировки) — отдельный механизм, закрывающий
«плато эффективности» (`../01-foundations/04-psychology-of-satisfaction.md` §6.6): без акселераторов пользователь
навсегда застревает на посредственном уровне. Детали компонента — у агента D1,
`../04-components-patterns/02-search-filter-sort.md`.

### 8.2 Что сбрасывать

`[практика]`:

| Что | Почему сбрасывать |
|---|---|
| Строка поиска при возврате в раздел | Человек пришёл за новым; «залипший» запрос читается как пустой раздел |
| Массовое выделение строк | Выполнять массовое действие над забытым выделением опасно |
| Режим редактирования | Уход и возврат — естественная граница; иначе непонятно, сохранено ли |
| Открытые модальные окна и панели | При возврате по ссылке пользователь ожидает исходное состояние |
| Временные сообщения и тосты | Они привязаны к моменту |
| Пагинация после смены фильтра | Страница 8 нового набора почти наверняка не то, что нужно |

Правило Тидвелл, ограничивающее «умность» (`../01-foundations/01-principles-and-laws.md` §6.10): **не быть слишком
умным** — не закрывать «простаивающее», не вычищать «бесполезное», не сортировать и не организовывать автоматически
без просьбы.

### 8.3 Где хранить состояние интерфейса

`[практика]`:

- **URL** — всё, что должно переживать «Назад», обновление и пересылку ссылки (§8.4).
- **Профиль пользователя на сервере** — то, что должно переживать смену устройства: колонки, плотность, сохранённые
  представления, свёрнутость навигации.
- **Локальное хранилище браузера** — сессионные удобства: последняя вкладка, несохранённый черновик как второй эшелон.
  Помнить перечень условий потери (§2.4).
- **Память маршрутизатора в приложении** — позиция прокрутки и состояние экрана при возврате назад в пределах сессии.

Важно `[практика]`: **состояние интерфейса на пользователя не должно влиять на то, что видят другие**. Если фильтр
сохраняется «на объект», а не «на пользователя», коллега увидит чужой вид и решит, что данные пропали.

### 8.4 URL как состояние

`[практика]` — правило выводится из требования работоспособности «Назад»
(`02-task-flows-and-wizards.md` §5) и из практики; исследований по доле пользователей, пересылающих ссылки на
отфильтрованные виды, я не нашёл.

В URL должно быть: открытый объект; открытая вкладка объекта; страница списка; применённые фильтры и поиск; сортировка;
режим представления (таблица/карточки); открытая панель деталей, если она меняет содержание экрана.

В URL **не должно** быть: несохранённых данных формы; секретов; состояния, которое ломается при открытии другим
пользователем без прав (нужен осмысленный 403 — `04-errors-and-recovery.md` §4.1).

Проверка: **скопировать адрес, открыть в новой вкладке — экран должен выглядеть так же.** Это же проверяемое
требование для генератора (§10).

## 9. Что обязано переживать переход между экранами

Это самое слабое место генерируемых интерфейсов: в UI2App сохранение состояния между маршрутами (уровень S3) —
общий провал фронтира, **три из шести моделей набирают ровно 0.0**, лучший результат 21.6 из 100
(`../11-ai-generated-ui/01-failure-modes-catalog.md` §8.3, дефект F6.3) `[исследование]`. Поэтому список должен быть
задан на входе явно и проверяться сценарным тестом.

| Состояние | Обязано переживать | Как проверить |
|---|---|---|
| **Черновик формы** | уход на другой экран и возврат; перезагрузку; истечение сессии | Заполнить половину, уйти, вернуться — данные на месте |
| **Шаг мастера и введённое** | переход «назад», уход и возврат, закрытие вкладки | `02-task-flows-and-wizards.md` §6 |
| **Применённые фильтры и поиск** | переход в карточку объекта и возврат в список; «Назад» браузера | Отфильтровать, открыть запись, вернуться — фильтры на месте |
| **Сортировка и страница списка** | то же | То же |
| **Выделение строк** | переход в карточку и возврат **в пределах одной задачи** (например, при массовой правке); сбрасывается при смене фильтра | Выделить, открыть одну запись, вернуться |
| **Позиция прокрутки** | возврат по «Назад» | Прокрутить, открыть запись, вернуться — та же позиция |
| **Открытая вкладка объекта** | перезагрузку и пересылку ссылки | Открыть вкладку «История», обновить страницу |
| **Корзина покупок / рабочий набор** | любую навигацию, перезагрузку, повторный вход | Положить, уйти, вернуться, перезайти |
| **Выбранная организация / проект** | любую навигацию и повторный вход | Переключить, перезайти |
| **Настройки вида (колонки, плотность)** | смену устройства | Открыть на другом устройстве |
| **Ранее введённые в процессе данные** | повторный запрос в том же процессе (WCAG 3.3.7) | Дойти до шага, где то же поле спрашивают снова |

Сценарный тест (готовый к автоматизации) `[практика]`:
1. Выставить состояние (фильтр + сортировка + прокрутка + выделение).
2. Перейти на другой маршрут.
3. Вернуться **кнопкой «Назад» браузера**.
4. Вернуться **ссылкой навигации приложения**.
5. **Обновить страницу.**
6. Скопировать URL и открыть в новой вкладке.
7. Закрыть вкладку и открыть приложение заново.
Ожидания по каждому пункту задаются заранее и различаются: пункт 7 не обязан сохранять прокрутку, но обязан сохранять
черновик.

## 10. Проверяемые требования для генератора

Закрывают дефекты F6.3 (состояние не переживает переход), F5.5 (нет подтверждения успеха), F4.1 (формы без
обработки) каталога `../11-ai-generated-ui/01-failure-modes-catalog.md`.

**Во входной контракт:**

1. Для каждой формы указана модель сохранения: явная / автоматическая / немедленное применение — и она **одна на
   форму**.
2. Для каждого экрана перечислено, какое состояние переживает переход (таблица §9).
3. Для автосохранения указаны: триггер (пауза N секунд, уход фокуса, `visibilitychange`), место хранения, индикация
   трёх состояний.
4. Для каждого длинного процесса указано, где живёт черновик и как к нему вернуться.
5. Объявлено, что находится в URL (§8.4) и что — в профиле пользователя.
6. Указано, применяется ли оптимистичное обновление, и если да — к каким действиям и в какой форме признака
   незавершённости.

**Автоматические проверки:**

| Проверка | Как | Дефект |
|---|---|---|
| Кнопка сохранения не заблокирована | авто-DOM | `disabled` на кнопке отправки формы |
| Одна кнопка сохранения | авто-DOM | Больше одной на странице |
| Модели не смешаны | авто-DOM/код | В одной форме есть и автосохраняемое поле, и кнопка отправки |
| Радиокнопки и `select` не автосохраняются | авто-код | Обработчик `change` отправляет запрос без кнопки |
| Состояние в URL | авто-сценарий: применить фильтр, прочитать `location.href` | URL не изменился |
| Переживает «Назад» | авто-сценарий по §9 | Фильтры, прокрутка или выделение сброшены |
| Переживает перезагрузку | авто-сценарий | То же |
| Черновик | авто-сценарий: заполнить половину формы, уйти, вернуться | Поля пустые |
| Индикация автосохранения | авто-сценарий: изменить поле, подождать | Нет элемента со статусом сохранения |
| Предупреждение об уходе | авто-сценарий: изменить поле, попытаться уйти | Нет `beforeunload` при наличии изменений, **или** `beforeunload` висит при их отсутствии |
| Повторный ввод | авто-сценарий: пройти процесс до повторного запроса того же поля | Поле пустое и не предлагает ранее введённое (нарушение WCAG 3.3.7) |
| Оптимистичное удаление | авто-сценарий: подменить ответ на ошибку | Элемент исчез и не вернулся |

## Частые ошибки

1. **Кнопка «Сохранить» убрана ради «эффективности»** — человек не понимает, применилось ли (§1.1) [S3].
2. **Кнопка есть, но автосохранение тоже работает**, и непонятно, что она делает (§1.3).
3. **Смешение моделей внутри одной формы** [S2] (§1.3).
4. **Автосохранение на радиокнопках и нативных `select`** — пользователь скринридера применяет вариант, просто читая
   список [S2] (§1.4).
5. **Кнопка отправки заблокирована до валидности формы** [S2][V:qktwIWZNFY4] (§1.5).
6. **Несколько кнопок сохранения с одинаковой подписью** [S2] (§1.5).
7. **Автосохранение по таймеру, прерывающее ввод** [S1] (§2.1).
8. **«Сохранено» без времени** — не отвечает на вопрос «а последние правки попали?» (§2.2).
9. **Нет состояния «не сохранено»** — сбой выглядит как успех (§2.2).
10. **Индикатор сохранения перепутан со статусом валидации** [S2] (§2.2).
11. **Автосохранение подаётся как офлайн-режим** [S9] (§2.3).
12. **Черновик хранится только в браузере, и об этом не сказано** [S9] (§2.4).
13. **Черновики некуда пойти посмотреть** — их нет в списках, нет счётчика (§3.2).
14. **«Продолжить» возвращает в начало процесса**, а не на шаг остановки (§3.2).
15. **Черновик нельзя сохранить с ошибками валидации** — теряется весь смысл черновика (§3.4).
16. **«Вы уверены, что хотите уйти?» вместо «Сохранить черновик»** (§3.5).
17. **Диалог ухода с двумя кнопками** без варианта «Продолжить редактирование» (§3.5).
18. **История версий без автора** — в многопользовательской системе бесполезна (§4.3).
19. **Сотня автоматических версий без группировки** [S7] (§4.3).
20. **Восстановление версии без точки возврата** — откат отката невозможен (§4.4).
21. **Копия объекта создаётся с потерей связанных данных, и об этом не сказано** [S7][S8] (§4.4, §7.3).
22. **Оптимистичное обновление на деньгах и правах** (§5.1).
23. **Элемент исчезает мгновенно, а потом возвращается** — выглядит как сбой данных (§5.2).
24. **`beforeunload` висит всегда**, даже когда изменений нет: ломает bfcache и приучает игнорировать диалог [S5] (§6.2).
25. **Расчёт на `beforeunload` как на механизм сохранения** — на мобильных он не срабатывает [S5] (§6.2).
26. **Фильтры сбрасываются при возврате из карточки объекта** — дефект F6.3 (§9).
27. **URL не отражает состояние**: ссылку нельзя переслать, «Назад» не работает (§8.4).
28. **Запомнена строка поиска**, и раздел выглядит пустым (§8.2).
29. **Массовое выделение пережило смену фильтра** — риск действия не над тем (§8.2).
30. **Настройки вида сохранены «на объект», а не «на пользователя»** — коллега видит чужой вид (§8.3).
31. **Повторный запрос данных, уже введённых в этом процессе** — нарушение WCAG 3.3.7 [S13] (§9).

## Чек-лист

Модель сохранения:

1. Для каждой формы выбрана одна модель: явная, автоматическая или немедленное применение?
2. Не смешаны ли модели внутри одной формы? Разделены ли визуально на странице?
3. Декларативные контролы сохраняются явно, императивные — сами?
4. Активна ли кнопка сохранения всегда? Одна ли она на странице?
5. Называет ли подпись кнопки глагол и объект?
6. Отделены ли от сохранения выбор формата, имя и место объекта?

Автосохранение:

7. Срабатывает ли по паузе ввода, а не по таймеру?
8. Сохраняется ли состояние при уходе вкладки в фон (`visibilitychange`)?
9. Есть ли три состояния индикации: сохраняется / сохранено со временем / не сохранено?
10. Не путается ли индикатор со статусом валидации?
11. Что происходит при сбое автосохранения — сказано ли и есть ли повтор?
12. Сказано ли, где хранится несохранённое и при каких условиях оно пропадёт?

Черновики:

13. Можно ли сохранить черновик с незаполненными полями?
14. Есть ли место, где черновики видно, с датой и счётчиком?
15. Возвращает ли «Продолжить» на шаг остановки?
16. Назван ли выход «Сохранить и вернуться позже», а не «Отмена»?
17. Есть ли в диалоге ухода три варианта, включая «Продолжить редактирование»?
18. Показан ли срок хранения черновика, если он есть?

Версии:

19. Делаются ли автоматические снимки во время активности и по её завершении?
20. Названа ли глубина хранения в интерфейсе?
21. Есть ли у версии автор, время и описание?
22. Группируются ли автоматические версии?
23. Создаётся ли точка возврата перед восстановлением версии?
24. Показываются ли различия по полям, а не по объекту целиком?
25. Можно ли посмотреть прошлую конфигурацию при редкой повторяющейся настройке?

Оптимистичное обновление:

26. Применяется ли оно только к дешёвым и обратимым операциям?
27. Виден ли признак незавершённости?
28. Возвращается ли состояние при ошибке и видно ли сообщение рядом с элементом?
29. Не уходит ли пользователь с экрана до подтверждения результата?

Уход и несохранённое:

30. Вешается ли `beforeunload` только при наличии несохранённых изменений и снимается ли потом?
31. Есть ли сохранение по `visibilitychange` вместо расчёта на закрытие?
32. Предлагается ли черновик вместо предупреждения о потере?

Совместная работа:

33. Видно ли, кто смотрит и кто редактирует объект?
34. Видно ли, кто и когда менял в последний раз?
35. Что происходит при одновременной правке — не перезаписывается ли молча?
36. Есть ли точка возврата перед слиянием?
37. Сказано ли, что не переносится при копировании и слиянии?

Состояние интерфейса:

38. Запоминаются ли фильтры, сортировка, колонки, плотность, свёрнутые панели?
39. Сбрасываются ли поиск, выделение и режим редактирования?
40. Отражает ли URL то, что видно на экране? Открывается ли скопированная ссылка так же?
41. Разделено ли состояние «на пользователя» и «на объект»?
42. Проходит ли экран сценарный тест переживания перехода (§9, семь шагов)?

## Открытые вопросы и противоречия

1. **Индикация автосохранения** — прямое противоречие NN/g [S3] и Primer [S2] (§2.2). Разрешение через критерий
   «виден ли результат в области просмотра» — синтез базы, экспериментально не проверен.
2. **Порог debounce** для автосохранения («пара секунд» у Купера) — авторская оценка без измерений; конкретное число
   (1 с, 2 с, 3 с) нигде не обосновано.
3. **Частота снимков версий** (30 минут Figma, 10 минут Notion) — продуктовые решения без опубликованного обоснования.
   Схема Notion (интервал + завершение активности) выглядит лучше, но это вывод из механики, а не из данных.
4. **Сроки хранения черновиков** — задокументированных значений не найдено вообще; ориентиры взяты от сроков корзины.
5. **Показ различий между версиями** в продуктовых интерфейсах — публичной UX-документации нет; §4.5 выведен из
   механики ревью Figma. Кандидаты для следующей волны: документация Notion и Confluence о сравнении версий,
   исследования по восприятию диффов.
6. **Конфликты одновременной правки** — источников почти нет (общее с `04-errors-and-recovery.md` §4.6).
7. **Что именно люди ожидают увидеть запомненным** — прямых исследований не найдено; таблицы §8.1 и §8.2 выведены из
   принципов (пространственная память, «не быть слишком умным») и из практики. Это хороший кандидат на собственный
   тест: какие из перечисленных состояний пользователи ожидают сохранёнными, а какие сброшенными.
8. **Доля пользователей, пересылающих ссылки на отфильтрованные виды** — данных нет; правило «URL как состояние»
   обосновано механизмом (работа «Назад», обновление, воспроизводимость) и дефектом F6.3, а не измерением.
9. **Купер писал до эпохи веба и SPA**: его модель «единого файла» предполагает документ и файловую систему.
   Перенос на веб-сервис (черновик на сервере, URL как состояние) — мой синтез; сами правила («сохранять автоматически»,
   «не спрашивать при закрытии», «не совмещать сохранение с форматом») переносятся, метафора файла — нет.
10. **Не проверено**, как сочетать автосохранение с правами: что происходит, если человек начал править объект и
    потерял права в процессе. Сценарий не описан ни в одном источнике.
