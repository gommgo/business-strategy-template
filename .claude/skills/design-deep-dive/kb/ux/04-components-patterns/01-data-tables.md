## Выжимка для агента

1. **Таблица решает четыре задачи: найти записи по критериям, сравнить данные, посмотреть/изменить одну запись,
   выполнить действия над записями.** Каждая задача требует своих инструментов; если ни одна не заявлена — таблица
   не нужна. → §1.1 `[исследование]`
2. **Два преимущества таблицы над карточками — масштабируемость и сравнение.** «Две соседние точки данных легко
   сравнить, потому что пользователю не надо ни двигать глазами, ни держать информацию в рабочей памяти». → §1.1 `[исследование]`
3. **Сценарий «найти одну запись и изменить её» — не повод для таблицы**: это master-detail или экран объекта. → §1.2 `[практика]`
4. **Первая колонка — человекочитаемый идентификатор, а не сгенерированный ID.** Коды и автогенерированные ID
   отодвигаются вправо или убираются. → §3.1 `[исследование]`
5. **Порядок колонок = порядок важности слева направо**, связанные колонки рядом. → §3.2 `[консенсус]`
6. **С 9-й колонки обязательны липкий заголовок, липкая первая колонка и управление колонками** с видимым
   индикатором «скрыто N колонок». → §2, §3.4 `[консенсус]`
7. **Горизонтальная прокрутка — не способ «уместить», а осознанное решение**: допустима, только когда каждая
   колонка нужна по делу, первая закреплена и есть настройка колонок. → §3.3 `[спорно]`
8. **Переупорядочивание колонок не делается одним drag-and-drop**: на широкой таблице нужен список имён колонок с
   изменяемым порядком. → §3.4 `[практика]`
9. **Текст влево, количественные числа вправо и моноширинными цифрами, бейджи по центру, действия в конце строки.**
   Заголовок колонки выравнивается так же, как её содержимое. Центрирование текста запрещено. → §3.6 `[консенсус]`
10. **Дата, телефон, индекс — качественные числа, их можно оставлять слева.** → §3.6 `[практика]`
11. **Пустая ячейка таблицы — серое тире с текстовой альтернативой** («нет данных» через `aria-label` или
    visually-hidden текст): тире отличает «пусто» от «сломалось» и держит вёрстку, альтернатива снимает довод Primer
    против символа-заполнителя; ноль — только результат подсчёта; в карточке и форме — «Не указано». Слово «null»
    не показывается никогда. → §3.7; правило и таблица ситуаций — `../07-ux-writing/03-russian-interface-text.md` §6.4
    `[система]` + `[практика]`
12. **Зебра больше не дефолт**: при hover, selected, disabled она даёт пять уровней серого. Линии-разделители или
    «карточный» вид надёжнее. Подсветка строки при наведении включена всегда. → §4.2 `[спорно]`
13. **Клик по всей строке ведёт на карточку объекта**; внутри строки допустимы вторичные ссылки, но одна из них —
    первичная. → §4.3 `[система]`
14. **Модалка поверх таблицы для просмотра и правки строки запрещена**: она закрывает те записи, на которые
    пользователь опирается. Порядок предпочтения: боковая панель → раскрытие строки → отдельная страница →
    модалка (последняя). → §4.4, §7 `[исследование]`
15. **Раскрытие строки аккордеоном не бесплатно**: пользователи не закрывают раскрытое и теряют соседние записи.
    На длинной таблице предпочтительнее панель деталей, которая сдвигает контент, а не накрывает его. → §4.4 `[спорно]`
16. **Сортировка по умолчанию — не алфавит, а «самое свежее» или «самое срочное»**, если тип данных это допускает;
    состояние сортировки видно постоянно у активной колонки. → §5 `[консенсус]`
17. **Многоуровневая сортировка живёт в отдельном оверлее** со списком полей, явным направлением у каждого и
    приоритетом перетаскиванием; называется «Сортировка», а не «мультисортировка». → §5.3 `[практика]`
18. **Пагинация по умолчанию для рабочих таблиц.** Бесконечная прокрутка запрещена, когда пользователю нужно найти
    конкретное, сравнить объекты в длинном списке или посмотреть несколько верхних. → §6 `[исследование]`
19. **Пагинация снизу; сверху её не дублируют**, пока страница не длиннее 2–3 экранов. Размер страницы: 20 строк —
    рабочая отправная точка, 25–50 для плотных админок; значение запоминается. → §6.3 `[система]`
20. **«Показать ещё» обязано сообщать три числа**: всего, загружено, осталось. → §6.2 `[исследование]`
21. **Позиция в списке восстанавливается при возврате из карточки** (pogo sticking), вместе с фильтрами,
    сортировкой и страницей — всё это живёт в URL. → §6.4 `[исследование]`
22. **Номер страницы должен что-то значить**: при сортировке показывай на номерах диапазон значений колонки
    сортировки, иначе прыжок по номеру — признак того, что пользователь потерялся. → §6.5 `[практика]`
23. **Редактирование в строке работает только на узкой таблице** и обязано визуально отличаться от режима чтения:
    фон строки, поля вместо текста, смена кнопок Edit/Delete на Save/Cancel в другом месте. → §7.2 `[исследование]`
24. **1–2 частых действия строки — иконками с подписью в tooltip, остальные — в меню**; меню с менее чем тремя
    пунктами разворачивается в иконки. → §8.1 `[система]`
25. **Действия, показываемые только по наведению, недоступны с тача и с клавиатуры** — им нужен парный видимый
    путь. → §8.1 `[консенсус]`
26. **Массовые действия = ровно две сущности**: панель над таблицей, появляющаяся при выделении, и действия строки;
    в режиме массового выбора действия строки отключаются. → §8.2 `[консенсус]`
27. **«Выбрать всё» означает «всё на странице»**; «выбрать все N во всём наборе» — отдельное явное действие,
    появляющееся после первого. Чекбокс в шапке имеет три состояния. → §8.2 `[консенсус]`
28. **После массового действия — сообщение об успехе с отменой внутри него**, без резких перестроений таблицы. → §8.3 `[практика]`
29. **Четыре состояния таблицы проектируются отдельно**: загрузка (скелет строк), пусто при первом входе, пусто
    после фильтра, ошибка загрузки. Пустое состояние **заменяет таблицу вместе с заголовками колонок**. → §9 `[система]`
30. **Сначала состояние загрузки, потом пустое** — показать «нет записей» и через секунду заменить данными хуже,
    чем не показать ничего. → §9.2 `[исследование]`
31. **От ~1000 строк в DOM нужна виртуализация или серверная пагинация**, и тогда сортировка, фильтрация и
    «выбрать всё» обязаны работать на сервере, а не по видимому куску. → §9.4 `[практика]`
32. **Сохранённые виды (saved views) — это фильтры + сортировка + набор и порядок колонок + размер страницы**,
    с именем, переименованием, дублированием и удалением. → §10.2 `[система]`
33. **Экспорт — обязательная страховка** для любой таблицы, из которой нельзя получить нужный срез интерфейсом. → §10.1 `[практика]`
34. **Таблица сравнения — отдельный компонент**: варианты в колонках, атрибуты в строках, до 5 вариантов
    (типично 3–4), значения полные и в одном формате. → §1.4 `[практика]`

## 1. Когда таблица

### 1.1 Четыре задачи пользователя (NN/g)

NN/g разбирает большие рабочие таблицы (не сравнительные таблицы товаров) через четыре задачи [S1] `[исследование]`:

| Задача | Что она требует от таблицы |
|---|---|
| **Найти записи по критериям** | Человекочитаемый идентификатор в первой колонке; порядок колонок по важности; находимые, быстрые и мощные фильтры; **явный признак, что данные отфильтрованы**; прозрачный синтаксис фильтра |
| **Сравнить данные** | Липкие заголовки строк и колонок; границы/зебра/подсветка при наведении, чтобы не терять место; **скрытие и переупорядочивание колонок** с индикатором состояния; скрытие записей и сортировка |
| **Посмотреть, изменить, добавить одну запись** | Представление записи целиком: боковая панель, раскрытие строки, страница или (последним) модалка; явный режим правки |
| **Выполнить действия над записями** | Действия строки (1–2 inline, дальше меню) и массовые действия (выбор + панель) |

Айтрекинг из той же статьи: участник фиксируется туда-сюда между данными таблицы и фильтрами над ней, а внутри
таблицы ведёт **иерархический поиск** — колонка 1, колонка 2, прыжок на 4-ю и 6-ю, потом следующая строка [S1].
Отсюда два следствия: фильтры должны быть в поле зрения рядом с таблицей, и «важные колонки рядом» — это не вкус,
а экономия переводов взгляда.

Второе объяснение того же поведения: при приоритетном порядке колонок пользователь **сканирует строки вертикально**
и переводит взгляд горизонтально только тогда, когда увидел что-то требующее разбирательства [V:23AQBZzDUIo].

**Два преимущества таблицы над карточками** [S1] `[исследование]`:
1. Масштабируемость — легко растить и число строк, и число колонок.
2. Сравнение — «две соседние точки данных легко сравнить, потому что, в отличие от карточного UI, пользователю не
   надо ни двигать глазами, ни держать информацию в рабочей памяти: он видит оба элемента одновременно».

### 1.2 Таблица решений: таблица / список / карточки / master-detail / сравнение

Развилка решается по заявленной задаче экрана, а не по красоте. Критерии проверяемы до генерации.

| Критерий | Таблица | Список (строки) | Карточки | Master-detail | Таблица сравнения |
|---|---|---|---|---|---|
| Главная задача | сравнить много записей по колонкам | просмотреть и выбрать одну из однородных | ознакомиться с разнородными объектами | перебрать много объектов подряд | выбрать один из нескольких вариантов |
| Число полей на объект | 4 и больше | 2–4 | 2–5 + изображение | 2–3 в списке, всё в детали | 5–30 атрибутов |
| Однородность объектов | одинаковые | одинаковые | **разнородные** | одинаковые | одинаковые |
| Нужно сравнивать значения | **да** | иногда | **нет** | нет | **да, это и есть задача** |
| Изображение существенно | нет | нет | **да** | нет | иногда |
| Объектов в наборе | десятки–миллионы | десятки–сотни | десятки | сотни–тысячи | **до 5** |
| Типичная ошибка | превратить в свалку из 25 колонок | потерять данные, нужные для решения | применить к однородному списку вместо списка | применить к сложному объекту, которому нужна вся ширина | взять больше 5 вариантов |

Обоснования: карточки «хуже сканируются, потому что позиция элементов внутри не фиксирована и менее предсказуема
для глаза… не годятся, когда пользователь ищет конкретный элемент», и «плохой выбор, когда нужно сравнивать» [S36]
`[исследование]`; master-detail уместен, когда «я обычно ищу номер заказа и правлю по одному заказу, мне не нужно
видеть все сразу» [V:WJE3EDkiu0w]; для сравнения работает только таблица сравнения [S33].

Отдельный критерий Primer: **таблица не годится, если у колонок ячейки обычно пустые, если данные понятнее с
группировкой и иерархией, если строки и колонки — только средство раскладки, и если в ячейках длинные тексты**
[S24] `[система]`. GOV.UK формулирует это же жёстко: «Never use the table component to layout content on a page»
[S41].

Primer отдельно разводит **data table** и **data grid**: грид нужен, «если основная цель — править ячейки или иначе
взаимодействовать с ними (как в электронной таблице)» [S24]. Carbon с другой стороны: таблица не применяется
«as a replacement for a spreadsheet application» [S7]. То есть между «таблица» и «электронная таблица» есть
промежуточный компонент, и подменять их нельзя.

### 1.3 Формулировка задачи экрана (вставляется в задание генератору)

Ошибка F1.1/F3.1 каталога — модель достраивает типичный экран из обучающих данных, потому что термин не уточнён
(«profile page» стал соцсетевым профилем). Поэтому перед генерацией экрана-таблицы заполняется шаблон:

```
Объект: <имя типа объекта во множественном числе>
Роль пользователя: <кто>
Задача экрана (одна фраза, глагол + результат): <например «найти заказы, по которым просрочена отгрузка,
  и назначить им ответственного»>
Активная задача из четырёх: найти / сравнить / открыть одну / действовать над многими
Объём: <строк в наборе>, <колонок по умолчанию>, <колонок всего>
Сортировка по умолчанию: <поле, направление, причина>
Фильтры обязательные: <список>
Действия строки: <1–2 частых> + <в меню>
Массовые действия: <список> + что подтверждается, что отменяется
Что происходит по клику на строку: <куда ведёт>
Состояния: первый вход / фильтр ничего не нашёл / ошибка загрузки / частичная загрузка
```

Без заполненного шаблона таблица генерируется как «table с десятью строками и без единого инструмента работы с
данными» (F4.2).

### 1.4 Таблица сравнения — отдельный компонент

Не путать с таблицей данных. Канонический разворот: **варианты в колонках, атрибуты в строках**, подписи строк
слева, подписи колонок сверху [S33], [V:4f8Kzf3Y_l0].

Правила `[практика]` (NN/g в статье и видео совпадают):
1. **До 5 вариантов, типично 3–4.** Больше — «формат становится подавляющим»; вместо таблицы сравнения нужны
   фильтры на странице списка. Динамические таблицы «обычно принимают 3–4 варианта»; на мобильном — **не больше 2**.
2. **Предел сообщается пользователю явно**, и объект можно убрать из сравнения.
3. **В строки идут только атрибуты, влияющие на решение**: «Don't just throw every piece of metadata that you have
   into the table».
4. **Значения полные и в одном формате.** «Самая большая проблема таблиц сравнения — не дизайн, а контент»:
   пропущенные атрибуты и разный формат делают таблицу бесполезной. Антипример: в одной строке четыре разных слова
   вместо одного значения («Zip, Zero, Zilch, Nada»).
5. **Липкие заголовки колонок обязательны**, если атрибутов больше экрана.
6. **Незнакомые термины определяются в контексте**, абстрактные величины переводятся в конкретное («2.7 oz» →
   «примерно как яйцо»); либо тултип с пояснением.
7. **Дать управление**: выбор отображаемых атрибутов, сворачиваемые строки, переключатель **«показать только
   различия»** (и наоборот — скрыть строки, где все варианты совпадают).
8. Статическая таблица (предзаданный набор) — до 5 вариантов; динамическая (пользователь выбирает) — при большем
   каталоге; кнопки «Сравнить» в списке делаются **вторичными**.

Когда таблица сравнения не нужна вовсе [S33]: объекты **не взаимоисключающие** (можно купить несколько),
**простые**, **дешёвые и легко заменимые** (пользователь сатисфайсит), **уникальные и трудно сравнимые**, а также
выбираемые по эстетике.

Теоретическая опора: фильтры обслуживают **некомпенсаторное** решение («отсечь всё дороже 20 000»), таблица
сравнения — **компенсаторное** («более тяжёлый ноутбук, но лучше батарея»), к которому люди переходят обычно при
менее чем 5–7 альтернативах [S33].

## 2. Пороги: что обязано быть в таблице при каком объёме

Каталог ошибок ИИ помечает «таблицы без сортировки, фильтрации и пагинации» как **не подтверждённый отдельно**
дефект (F4.2, `[спорно]`) именно потому, что ни один источник не даёт порогов. Ниже — сводка того, что удалось
найти в дизайн-системах, плюс мой вывод там, где источника нет. Каждая строка проверяема по DOM.

### 2.1 По числу строк в наборе

| Строк в наборе | Обязательно | Основание |
|---|---|---|
| ≤ 10 | Осмысленная сортировка по умолчанию. Больше ничего | — |
| 11–50 | Сортировка по ключевым колонкам; липкий заголовок, если строк на экране больше ~20 | «Support sorting if the list can be long» [S14] |
| **> 50** | **Пагинация или «показать ещё»** + общее число объектов; **поиск или фильтр по таблице** | Polaris: «Paginate when the current list contains **more than 50 items**»; «Support filtering if the list can be long» [S14] `[система]` |
| > 200 | Фильтры как отдельный блок (не только поиск); состояние списка в URL; выбор размера страницы | вывод из [S14], [S7] `[мнение]` |
| > 1000 | Виртуализация строк или серверная пагинация; серверные сортировка, фильтрация и «выбрать все N» | вывод из ограничений браузера и из правила «выбрать все во всём наборе» [S14] `[мнение]` |
| > 10 000 | Обязательны массовые действия и экспорт: перебрать вручную невозможно | вывод `[мнение]` |

Автопроверка: в DOM больше 50 `<tr>` в `<tbody>` **и** нет элемента пагинации (`nav[aria-label*="agination"]`,
кнопка «Показать ещё») **и** нет поля поиска/фильтра в области таблицы → дефект.

### 2.2 По числу колонок

| Колонок видно | Обязательно | Основание |
|---|---|---|
| ≤ 5 | Приоритетный порядок; числовые вправо | [S1], [S17] |
| 6–8 | То же + липкий заголовок при вертикальной прокрутке | [S1] |
| **> 8** | **Липкая первая колонка** с идентификатором; **управление колонками** (скрыть, переставить) с **видимым индикатором «скрыто N колонок»** | [S1], [V:23AQBZzDUIo], [V:s7nvF1PuAWY] `[консенсус]` |
| > 12 | То же + сохранённые наборы колонок (виды) либо вкладки внутри таблицы (например, 15 колонок → 3 вкладки по 5) | [V:GCJ6k3tD50A, 1:36:56] `[практика]` |

Автопроверка: `<th>` больше 8 **и** нет контрола управления колонками → дефект; «скрыто N» отсутствует при
скрытых колонках → дефект.

### 2.3 По наличию операций

| Условие | Обязательный элемент | Основание |
|---|---|---|
| Колонка сортируема | `aria-sort` на её `<th>`, индикатор направления виден постоянно у активной | [S7] `[система]` |
| Есть массовые действия | Чекбокс в шапке слева с тремя состояниями + чекбокс в каждой строке | [V:7MjvBqlRzCY] `[практика]` |
| Выбрана хотя бы одна строка | Контекстная панель действий над таблицей, число выбранных, «снять выделение» | [S7], [V:7MjvBqlRzCY] `[консенсус]` |
| Таблица может быть пустой | Отдельная реализация пустого состояния, **заменяющая таблицу** | [S12], [S24] `[система]` |
| Загрузка дольше ~1 с | Скелет строк, не спиннер | [S7], [S31] `[консенсус]` |
| Строка кликабельна | Ссылка (а не только обработчик клика), чтобы работали открытие в новой вкладке и клавиатура | вывод `[практика]` |

## 3. Колонки

### 3.1 Первая колонка

**Правило:** первая колонка по умолчанию — **человекочитаемый идентификатор записи**, а не «mystery meat»
автогенерированный ID [S1] `[исследование]`.

Обоснования:
- «Длинные строки букв и цифр… часто выводятся на видное место первой колонкой таблицы, заставляя людей
  просматривать её насквозь, чтобы найти нужное… дайте человекочитаемую информацию как основную точку опоры и
  отодвиньте ID на менее заметную позицию» [S30].
- Короткие коды дороже, чем кажутся: «Короткий код лучше влезает в маленькую область, чем целое предложение, но
  кладёт гораздо большую когнитивную нагрузку… даже высокообученные профессионалы не помнят все коды» [S30].
  Отрасли-нарушители: медицина, CRM, бухгалтерия, enterprise.
- «Speak human»: заменяй автогенерируемые ID и коды читаемым [V:23AQBZzDUIo]. Пример: «Ship code 11» → название
  перевозчика; «11, 11, 20 11» → «NOV 11» [V:WJE3EDkiu0w].

**Условие эффективности липкой первой колонки:** в ней должен стоять уникальный идентификатор или имя, иначе
закрепление бесполезно — по нему не видно, какая строка разбирается [V:23AQBZzDUIo].

В Primer эта колонка называется **row header** и «визуально отличается от остальных ячеек строки», семантически —
`<th scope="row">` [S24], [S41].

Если технический ID всё же нужен (для поддержки, для API) — он остаётся в таблице, но **не первым** и с
копированием одним кликом (см. `04-lists-cards-and-record-view.md` §6).

### 3.2 Порядок колонок

1. **По важности слева направо**, связанные колонки рядом: «once a user has located a potential record of
   interest, don't force them to move their eyes back and forth between column 1 and column 20» [S1].
2. Порядок по умолчанию — **продуктовое решение**, а не «всё, что есть в таблице БД»: «prioritize as a product
   team which columns are the most important for the user to see upon page load» [S17].
3. Рабочий критерий отбора колонки: **нужна ли по ней сортировка или фильтрация**. Если нет — колонку можно
   склеить с соседней или убрать в раскрытие строки [V:WJE3EDkiu0w].
4. Оговорка: «важность» не одна для всех ролей. В системах с разными ролями порядок либо настраивается
   пользователем, либо задаётся ролевым пресетом (см. §10.2).

### 3.3 Сколько колонок терпимо и когда горизонтальная прокрутка

Прямого измерения нет ни в одном источнике. Что есть:

- «Minimize the number of columns. It's easier to scan many rows than it is to scan many columns» [S24].
- Полезное следствие оттуда же: **если строк заведомо будет меньше, чем колонок, поменяй их местами** [S24].
- «Горизонтальная прокрутка до сих пор затратнее вертикальной даже на современных тачпадах с жестами»
  [V:23AQBZzDUIo] — подано как факт без ссылки на исследование.
- Atlassian: «горизонтально прокручиваемые таблицы могут создавать проблемы доступности, если нет достаточного
  визуального признака прокрутки. Поэтому **мы рекомендуем сначала искать способы упростить таблицу**, и только
  потом браться за горизонтальную прокрутку» [S25].
- Balsamiq: «горизонтальная прокрутка допустима, если каждая колонка нужна по делу», при закреплённой первой
  колонке [V:WJE3EDkiu0w].

**Разрешение противоречия** (Balsamiq за прокрутку, NN/g против) — по условиям `[спорно]`:

горизонтальная прокрутка допустима, если одновременно выполнено всё:
- первая колонка закреплена и содержит идентификатор;
- заголовки колонок липкие;
- есть управление колонками (скрыть, переставить) и оно находимо;
- набор колонок по умолчанию осмыслен (частые данные видны без прокрутки);
- есть видимый признак, что таблица прокручивается вбок (тень у края, полоса прокрутки, не только жест).

Прокрутка **не** годится как способ «влезть» — тогда вместо неё скрытие колонок, вкладки внутри таблицы или
разбиение экрана.

Ключевая переформулировка задачи: «Как показать большую таблицу на ограниченном экране? Никак. Видеть таблицу
целиком редко относится к задаче пользователя. Работа дизайнера — провести анализ задач и дать инструменты под
задачу» [V:s7nvF1PuAWY]. Ограничение не в пикселях: даже на восьми 24-дюймовых мониторах найдётся слишком большая
таблица, «и у человека не хватит объёма рабочей памяти».

### 3.4 Управление колонками

Обязательный набор при более чем 8 колонках `[консенсус]`:

| Возможность | Требование |
|---|---|
| **Скрыть / показать** | Список всех колонок с чекбоксами; **видимый индикатор текущего состояния** — NN/g показывает меню, в котором прямо написано «15 columns are currently hidden» [S1] |
| **Переупорядочить** | Два пути: перетаскивание заголовков (быстрый ускоритель, но низкая находимость и плохая доступность) **и** переупорядочиваемый **список имён колонок** — на широкой таблице тащить колонку через несколько экранов невозможно [S1], [V:s7nvF1PuAWY] |
| **Закрепить** | Первая колонка (идентификатор) и, при наличии итогов, крайняя правая [S17] |
| **Изменить ширину** | Опционально. «Лучшая ситуация — когда изменение ширины не нужно, потому что у таблицы правильные отступы по умолчанию»; drag-handle на разделителе ожидается в редактируемых таблицах [S17] |
| **Сбросить** | Заметный «вернуть вид по умолчанию» — «creates in users a sense of security and trust… they can explore the page and customize it without creating unwanted permanent changes» [S17] |
| **Сохранить** | Настройка живёт в сессии браузера **или в учётной записи** [S17] |

Антипаттерн: 25 колонок по умолчанию без возможности скрыть (см. `../03-layout-placement/01-page-anatomy-templates.md` §4.4).

### 3.5 Ширины колонок

Готовая модель Primer (четыре режима) [S24] `[система]`:

| Режим | Поведение | Когда |
|---|---|---|
| `grow` (по умолчанию) | Растягивается по свободному месту, минимум — ширина самой широкой ячейки (`minmax(auto, 1fr)`); допускает min/max | Обычные текстовые колонки |
| `growCollapse` | Растягивается **и сжимается**; без min-width может схлопнуться в 0 | Колонки, которыми можно пожертвовать при сужении |
| `auto` | По самой широкой ячейке. **Не применять, когда длина содержимого сильно меняется** — будет layout shift | Статусы, короткие коды |
| Явная ширина | Точная, не растёт и не сжимается | Даты, суммы, служебные колонки |

Дополнительно: колонка действий ширину не принимает (её минимум — ширина действий); если все колонки ограничены и
строка не заполняет контейнер, разница добавляется к последней колонке [S24].

Числа ширин и отступов — `../../ui/06-components-visual/`.

### 3.6 Выравнивание и форматирование

`[консенсус]` (Primer, Pencil & Paper, GOV.UK, Polaris, Friedman совпадают):

| Тип содержимого | Выравнивание | Примечание |
|---|---|---|
| Текст, ссылки, иконки | Влево | «Всё, что состоит из букв, — влево» [S17] |
| **Количественные** числа: суммы, меры, проценты | **Вправо**, по десятичной точке | Одинаковое число знаков после запятой; **моноширинные (табличные) цифры** — иначе «$1,111.11 выглядит меньше, чем $999.99» [S17], [S24], [S14] |
| **Качественные** числа: дата, индекс, телефон, номер | Можно влево | Особенно если это первая колонка [S17] `[практика]` |
| Бейджи и статусы | По центру | [V:GCJ6k3tD50A, 1:38:00] `[мнение]` |
| Мини-графики (спарклайны) | Вправо | Чтобы сравнивались по общей базе [V:GCJ6k3tD50A] |
| Кнопки действий | В правом конце строки | [V:GCJ6k3tD50A], [S25] |
| **Заголовок колонки** | **Так же, как её содержимое** | Иначе «off putting whitespaces» и лишний визуальный шум [S17] |
| Центрирование текста | **Никогда** | «Center alignment prevents quick scanning and noticing irregularities and ultimately makes the eye jump around» [S17] |

Форматирование содержимого:
- **Одна колонка — один тип данных.** «Заголовок колонки должен точно описывать то, что лежит в её ячейках; иначе
  непонятно, по какому значению идёт сортировка» [S24].
- **Не повторять квалификатор в каждой ячейке**: «Qualified Lead / Nurturing Lead» → колонка «Тип лида», значения
  «Квалифицированный / В работе» [S17]; «Заказ №1001, Заказ №1002» → колонка «Заказ», значения «1001, 1002»
  (см. `../03-layout-placement/04-placement-conventions-and-redundancy.md` §11).
- **Точность по задаче**: «$3 848 305,93 вместо $3 848 306 или даже $3,8 млн… каждая лишняя единица информации —
  потерянное время» [S29]. В рабочей таблице точность нужна, в сводке — нет.
- **Даты**: месяц числом читается хуже буквенного сокращения («11.11.2011» против «11 ноя 2011») [V:WJE3EDkiu0w].
  Относительное время («2 часа назад») против точного — см. `04-lists-cards-and-record-view.md` §6.2.
- **Длинный текст**: перенос предпочтительнее обрезки, «потому что не прячет содержимое»; **обрезка — крайняя
  мера**, и полный текст показывается в tooltip [S24]. Заголовок колонки при переполнении переносится на две
  строки и дальше обрезается, полный — в tooltip [S7].
- **Много тегов в ячейке**: показать несколько и «+N», остальное — в раскрытии строки; не заводить колонку на
  каждый тег [V:WJE3EDkiu0w].

### 3.7 Пустые значения

Прямое расхождение источников `[спорно]`:

- **Primer:** «By default, leave empty cells blank. You may show a message to explain an absence of data. **Just
  don't use a character like "x" or "-". It creates a weird experience for assistive technologies like screen
  readers**» [S24].
- **Широкая практика админок** (и предыдущая формулировка задания) — ставить «—», чтобы отличить «пусто» от
  «сломалось».

Позиция базы (волна 4, реестр противоречий): **в таблице — серое тире «—» с текстовой альтернативой для скринридера**
(`aria-label="нет данных"` или visually-hidden текст) — это снимает довод Primer против символа-заполнителя и отличает
«пусто» от «сломалось»; **ноль — только результат подсчёта**, не «нет данных»; **в карточке и форме — «Не указано»**
текстом; одно правило на продукт (`../10-design-systems-consistency/02-consistency-rules.md` чек-лист 19). Смысл
пустоты при необходимости объясняется и вне ячейки — в подписи колонки или легенде. Тире не участвует в сортировке как
значение. Правило и таблица ситуаций (нет данных / ноль / неприменимо / нет доступа / загружается) —
`../07-ux-writing/03-russian-interface-text.md` §6.4. Чего нельзя никогда: показывать `null`,
`undefined`, `NaN`, `Invalid Date`, `0001-01-01` — это утечка модели данных в интерфейс.

Отдельно: **при сортировке пустые значения — отдельная категория**, и направление для них задаётся явно
(«пустые → заполненные») [V:GCJ6k3tD50A, 2:01:25].

## 4. Строки

### 4.1 Высота и плотность

Плотность — решение под задачу, а не константа (правило из `../03-layout-placement/02-grid-spacing-density.md`).
Ориентиры высоты строки от практиков: **condensed 40px / regular 48px / relaxed 56px** [S17]; Carbon даёт пять
размеров строк (xs, s, m, l, xl) и требует, чтобы **строка заголовка была той же высоты**, что строки данных, а
xl применялась только если ожидается две строки текста в ячейке [S7]. Числовые таблицы по системам —
`../../ui/03-spacing-sizing/`.

**Когда плотнее** `[консенсус]`:
- ежедневная работа по 4+ часа, обученные пользователи;
- задача — сравнение и сверка многих строк;
- экран узкий по высоте либо таблица — часть многопанельного рабочего места.

**Когда воздушнее**:
- редкая задача, неподготовленный пользователь, клиентский сервис;
- в ячейках многострочный текст;
- строки кликабельны и по ним часто промахиваются (цели нажатия — `../08-accessibility/`).

Противоречие источников `[спорно]`: Balsamiq требует больше воздуха и отвергает довод «больше данных выше сгиба»
(«столько данных за раз всё равно не просканировать») [V:WJE3EDkiu0w]; Friedman описывает экспертные среды, где
работают 8+ часов в день и плотность — норма, а внешний вид перестаёт иметь значение [V:GCJ6k3tD50A, 27:13].
Разрешение: **плотность — функция интенсивности использования и экспертизы**. Практическое правило: переключатель
плотности (2–3 положения) снимает спор и стоит дёшево; значение запоминается на пользователя [S17].

**Переключатель плотности — не замена продуманным умолчаниям.** По умолчанию берётся плотность, соответствующая
основной роли: админка и бэк-офис — плотная, личный кабинет — средняя.

### 4.2 Зебра, разделители, наведение

- **Подсветка строки при наведении включена всегда**, даже если строка некликабельна: «it can help the user
  visually scan the columns of data in a row» [S7] `[система]`.
- **Зебра** помогает «keep their place as they look around and compare data» [S1], но перестала быть безопасным
  дефолтом: при наличии disabled, hover, selected и их наложений получается **до пяти уровней серого**, и
  «visual continuity within the table» ломается [S17] `[спорно]`.
- Альтернативы: тонкие линии-разделители строк (цвет должен «растворяться в фоне»); «карточный» вид (если у
  приложения уже есть фоновый оттенок); полное отсутствие разделителей при неплотных данных [S17].
- **Вертикальные разделители колонок необязательны**; если есть — не толще 1px и светло-серые [S17].
- Вертикальное выравнивание в ячейке: **по центру при разбросе высоты до 3 строк, по верху при большем**;
  многострочные ячейки прижимаются к верху, «чтобы всё было видно с первого взгляда» [S17].

**Решение:** зебра включается, если одновременно (а) больше 6 колонок, (б) строки не выбираются и не отключаются,
(в) подсветка при наведении и выделение решены другими средствами (рамка, левый маркер). Иначе — линии.

### 4.3 Клик по строке

`[система]` (Polaris, Primer):
1. **Вся строка ведёт на карточку объекта.** «Have items that perform an action when clicked. The action should
   navigate to the resource's details page» [S14].
2. Внутри строки может быть несколько ссылок, но **одна из них помечена как первичная** (`data-primary-link` в
   Polaris) — именно она срабатывает при клике по пустому месту строки [S14].
3. Это должна быть **настоящая ссылка** (`<a href>`), а не обработчик на `<tr>`: иначе не работают открытие в новой
   вкладке, копирование адреса, переход с клавиатуры.
4. Клик по чекбоксу, по действию строки и по вложенной ссылке **не должен** приводить к переходу.
5. Если у объекта нет своей страницы, клик по строке открывает боковую панель деталей — и тогда выделенная строка
   получает видимое состояние «выбрана».

Свойство строки `tone` (subdued / success / warning / critical) в Polaris — фоновая подсветка **состояния записи**,
не результата действия [S14]; применять ограниченно, иначе таблица становится светофором.

### 4.4 Раскрывающиеся строки (accordion rows)

Приём: вместо модалки развернуть строку вертикально и показать детали или форму внутри [V:23AQBZzDUIo].

Ограничения, которых нет в видео, но которые есть в статье 2022 года [S1] `[исследование]`:
- «users don't tend to clean up after themselves (i.e., close accordions when they are done) and they may end up
  with cluttered displays unsuited for the other core table tasks»;
- «more important, users will have difficulty referring to records that are **not in immediate proximity** of the
  one being edited» — раскрытая строка отодвигает всё, что ниже.

Carbon добавляет `[система]` [S7]:
- раскрытие — для дополнительной информации или данных, требующих отдельного запроса;
- «when the content in the expanded area feels cramped, consider taking the user to a dedicated page, side panel,
  or data table»;
- **«раскрыть всё» по умолчанию выключено**: массовое раскрытие сводит на нет выигрыш отложенных запросов;
- при комбинации с выбором иконка раскрытия стоит **левее** чекбокса.

**Разрешение `[спорно]`:** раскрытие строки уместно при коротком списке (до ~25 строк на странице) и небольшом
объёме деталей; при длинной таблице и богатых деталях выигрывает **боковая панель, которая сдвигает колонки, а не
накрывает их** [V:GCJ6k3tD50A, 1:46:08]. Модалка не применяется ни в том, ни в другом случае (§7).

### 4.5 Вложенные строки и деревья

- Polaris даёт `rowType`: `data` / `subheader` (выглядит и ведёт себя как заголовок таблицы) / `child` (с
  отступом), плюс `selectionRange` — строка-родитель выделяет диапазон дочерних [S14] `[система]`.
- Atlassian выделяет **отдельный компонент** «Table tree» — то есть дерево в таблице не считается вариантом
  обычной таблицы [S26].
- Правило: **глубина вложенности в таблице — не больше двух уровней**. Дальше это дерево (`../02-ia-navigation/`)
  или «relationship filtering» — колонки, раскрывающиеся слева направо [V:GCJ6k3tD50A, 56:57] `[практика]`.
- При вложенности «выбрать всё» и массовые действия обязаны явно отвечать на вопрос, включают ли они потомков.

## 5. Сортировка

### 5.1 Индикаторы и поведение

`[система]` (Carbon, Primer, Atlassian совпадают):
- Заголовок сортируемой колонки — **кнопка**; сортировка по конкретным колонкам может быть отключена [S24].
- Три состояния: unsorted / ascending / descending. **Иконка показывается только у активной колонки; у
  сортируемых она появляется при наведении и фокусе** [S7].
- Семантика: `aria-sort="ascending|descending|none"` на `<th>` — это и есть автопроверяемый признак сортируемости.
- **Колонка действий заголовка не имеет** и не сортируется [S24].
- Сортировка привязана к значению, а не к отрисовке: «тип ключа влияет на результат — числовые и строковые ключи
  дают разные порядки; не используйте объекты как ключи» [S25].
- Шеврон сортировки не должен ломать выравнивание заголовка относительно содержимого [S17].

### 5.2 Сортировка по умолчанию

| Тип данных | Сортировка по умолчанию |
|---|---|
| События, заказы, обращения, логи | **Самое свежее сверху** (дата создания или изменения) |
| Очередь работы | **Самое срочное сверху** (ближайший дедлайн, наименьший остаток, наивысший приоритет) |
| Справочник, номенклатура | Алфавит по первой колонке |
| Результаты поиска | По релевантности (см. `02-search-filter-sort.md` §3) |

«In the majority of cases, default sorting shows the most recent entries at the top… **or entries most needing
action** (lowest inventory, most urgent priority)» [S17] `[практика]`. Primer формулирует мягче: «Data should be
initially rendered in an intuitive order, for example starting with the most recently created items»; алфавит по
первой колонке — фолбэк [S24] `[система]`.

**Сортировка по колонке статуса** — отдельный случай: алфавитный порядок статусов бессмыслен («Готово, Отменён,
В работе»). Статусам задаётся **явный порядок по жизненному циклу или по срочности**, и он одинаков везде, где этот
статус встречается (см. `04-lists-cards-and-record-view.md` §5). Если такого порядка нет — колонка не сортируется,
а фильтруется.

Типовой набор направлений, который пользователь ожидает увидеть: A→Я, Я→А, от старых к новым, от новых к старым,
от больших к меньшим, от меньших к большим [S17].

### 5.3 Многоуровневая сортировка

Когда нужна: когда первичный ключ даёт много одинаковых значений (сортировка по статусу, затем по дате) —
то есть почти всегда в очередях работы.

Анатомия `[практика]` (эталон Airtable, разбор [V:GCJ6k3tD50A, 2:01:25]):
- **отдельный оверлей** по кнопке «Сортировка», а не хитрый клик с Shift по заголовкам;
- список полей, добавление и удаление поля;
- **направление задаётся явно для каждого поля** словами: «A→Я», «9→1», «пустые → заполненные»;
- приоритет полей меняется перетаскиванием;
- переключатель «пересортировывать автоматически» (иначе при правке строка прыгает из-под курсора);
- подпись кнопки — «Сортировка» или «Сортировка и фильтры», **не «мультисортировка»**;
- на узком экране — список полей с чекбоксами, перетаскивание приоритета и обязательно явный переключатель
  направления.

Индикатор в заголовках при активной многоуровневой сортировке: у каждой участвующей колонки — стрелка **с номером
приоритета** [V:GCJ6k3tD50A, 1:32:45].

## 6. Пагинация, «показать ещё», бесконечная прокрутка, виртуализация

### 6.1 Таблица решений

| Критерий | Пагинация | «Показать ещё» | Бесконечная прокрутка | Виртуализация (бесконечная прокрутка с окном) |
|---|---|---|---|---|
| Пользователь ищет конкретную запись | **да** | иногда | **нет** [S6] | да |
| Пользователь сравнивает объекты в длинном списке | **да** | иногда | **нет** [S6] | да |
| Нужны только несколько верхних элементов | **да** | да | **нет** [S6] | да |
| Однородная лента без конкретной цели | нет | да | **да** [S6] | да |
| Набор очень большой (десятки тысяч) | **да** | нет | нет | **да** |
| Подгрузка дольше ~2 с | **да** [V:WJE3EDkiu0w] | да | нет | нет |
| Внизу страницы есть что-то нужное (футер, итоги) | да | **да** | **нет** [S5] | зависит |
| Клавиатурные и скринридерные пользователи значимы | **да** | да | **нет** [S6], [S41] | требует `role="feed"` |
| Нужна ссылка на конкретный кусок набора | **да** | нет | нет | нет |

**Для рабочих таблиц админки пагинация — дефолт.** Бесконечная прокрутка «работает лучше всего там, где
пользователь листает однородные элементы без конкретной задачи — развлечения, новости, соцсети» [S6], то есть не в
админке. GOV.UK дополнительно запрещает её по доступности: «Avoid using the "infinite scroll" technique… This
causes problems for keyboard users» [S41].

Известные проблемы бесконечной прокрутки [S6], [S5] `[исследование]`: трудно переискать объект (нет ориентиров);
**иллюзия полноты** (пользователь думает, что дошёл до конца, пока контент грузится ниже сгиба); недоступен футер;
клавиатурному пользователю приходится протабать всё, а скринридер видит только первый «чанк» (частично лечится
ролью ARIA `feed`, которая ещё и даёт выход за пределы ленты); растёт вес страницы; ломается штатная полоса
прокрутки — «то, что было серединой, становится верхней восьмой».

### 6.2 «Показать ещё»

Плюсы: линейное движение по списку и так преобладает; крупная кнопка проще для попадания, чем каретки и номера;
остаётся доступ к футеру; пользователь контролирует объём загружаемого (важно при плохой связи) [S5].

**Обязательный минимум** [S5] `[исследование]`:
- общее число объектов в наборе;
- сколько уже показано («Показано 40 из 333»);
- сколько осталось загрузить;
- когда грузить нечего — кнопка исчезает и остаётся общее число.

Без этих чисел «пользователи не понимают, когда дойдут до конца списка» (антипример Lowes) [S5].

### 6.3 Пагинация: состав, размер страницы, место

Состав полосы пагинации (Carbon) [S10] `[система]`: выбор числа элементов на странице; **диапазон элементов с
общим числом** («21–40 из 333»); текущая страница из общего числа страниц; кнопки «назад» и «вперёд».
Вариант с номерами страниц (`pagination nav`) — для контента и секций; многоточие **никогда не ставится в начале
или конце** ряда номеров.

**Размер страницы:**
- Primer: «эти факторы делают невозможным рекомендовать идеальный размер для всех случаев, но **20 строк — хорошая
  отправная точка**». Факторы: можно ли фильтровать строки, число колонок, визуальная сложность ячеек, сколько
  контекста нужно при просмотре [S24] `[система]`.
- Практика плотных админок: 25 или 50 при узких строках и небольшом числе колонок.
- Выбор размера — обязателен при наборе больше ~200 строк; **значение запоминается на пользователя** [S17].
- Слишком короткая страница раздражает, слишком длинная — теряет и перегружает [S24].

**Место:**
- Carbon прямо: «Do stack the pagination component below the data table. **Do not stack the pagination component
  above the data table**» [S10] `[система]`.
- Правило базы (из `../03-layout-placement/04-placement-conventions-and-redundancy.md` §7): пагинация снизу;
  дублировать сверху только при странице длиннее 2–3 экранов (ориентир — 50+ строк).
- Альтернатива дублированию — липкая полоса пагинации внизу окна; тогда сверху ничего не нужно.

**Правила GOV.UK** [S41] `[система]`:
- «Do not show pagination if there's only one page of content.»
- «Redirect users to the first page if they enter a URL of a page that no longer exists.»
- Разметка: `<nav aria-label="Pagination">`, `aria-current="page"` у текущей, `aria-label="Page N"` у каждой
  ссылки, `rel="prev"` / `rel="next"`.
- Пагинация **не применяется к линейным путям** (шаги формы): там «Продолжить» и «Назад».

### 6.4 Сохранение позиции и состояния

`[исследование]`:
- **Pogo sticking** (уйти в объект и вернуться) — массовое поведение. «Ensure that your listing pages support pogo
  sticking… это особенно частая и болезненная проблема при бесконечной прокрутке и "показать ещё"» [S5].
- Состояние списка — **фильтры, сортировка, номер страницы, размер страницы, набор колонок** — живёт в URL и
  восстанавливается при возврате (`../03-layout-placement/01-page-anatomy-templates.md` §4.2, [S7]).
- Выбор строк не сбрасывается при смене страницы без предупреждения; если сбрасывается — это сообщается
  (`../03-layout-placement/04-placement-conventions-and-redundancy.md` §7).
- Дефект F6.3 каталога («состояние не переживает переход между экранами») — сильнейший в каталоге: три из шести
  фронтирных моделей набирают ровно 0.0 на этом уровне. Значит, это первое, что проверяется автотестом.

### 6.5 Осмысленная навигация по страницам

Айтрекинг-наблюдение (одна сессия, финансовый инструмент): пользователь отфильтровал, отсортировал, **не заглянул
дальше третьей строки и прыгнул на восьмую страницу наугад** — «прыжок по номеру страницы это точка, где человек
потерялся и пытается угадать» [V:GCJ6k3tD50A, 1:28:40] `[данные]` (выборка = 1).

Два приёма оттуда же `[практика]`:
- **steps pagination** — на номерах страниц показывать значение колонки, по которой отсортировано («стр. 8:
  «М–О»», «стр. 3: 12 000–15 000 ₽»);
- **scroll bar range interval** — подписи диапазона у полосы прокрутки, показывающие, в какие значения попадёшь.

### 6.6 Виртуализация как UX-требование

Виртуализация (рендер только видимого окна строк) — не оптимизация, а условие пригодности при больших наборах.
UX-требования к ней `[практика]`:
1. Полоса прокрутки отражает **весь набор**, а не загруженный кусок (иначе повторяется дефект бесконечной
   прокрутки).
2. Липкий заголовок и липкая первая колонка не «плывут» при быстрой прокрутке.
3. Ctrl+F браузера перестаёт работать по невидимым строкам — значит, **поиск по таблице обязателен**.
4. Сортировка, фильтрация и «выбрать все N» выполняются на сервере по всему набору, а не по загруженному окну.
5. Позиция прокрутки восстанавливается при возврате.
6. Для скринридера — `aria-rowcount`/`aria-rowindex` по полному набору (детали — `../08-accessibility/`).

## 7. Редактирование

### 7.1 Таблица решений

| Критерий | Inline (в ячейке/строке) | Боковая панель | Отдельная страница | Раскрытие строки | Модалка |
|---|---|---|---|---|---|
| Ширина таблицы | **узкая** | любая | любая | любая | — |
| Полей в записи | 1–4 | 5–15 | 15+ | 3–8 | — |
| Нужен контекст соседних записей | да | **да** | нет | частично | **нет (и она его закрывает)** |
| Правки идут подряд по многим записям | **да** | **да** | нет | нет | нет |
| Цена ошибки высока | нет | да | да | **да** (трение полезно) | — |
| Нужна прямая ссылка на форму | нет | опционально | **да** | нет | нет |
| Рекомендация | быстрые правки значений | **вариант по умолчанию** | сложная запись | короткие детали | **не применять** |

Обоснования:
- Inline: «работает, только если таблица узкая» [S1].
- Модалка: «закрывает соседние записи, и пользователь не может свериться или скопировать данные похожей записи. Мы
  регулярно наблюдаем в тестах, что люди обращаются к существующим данным других записей, пока правят запись» —
  «мы вообще не рекомендуем модалки для серьёзной работы по редактированию» [S1] `[исследование]`. То же в списке
  топ-10 ошибок приложений с прямым антипримером Airtable [S30].
- Боковая панель: «закрывает часть таблицы, но оставляет доступ к данным» [S1]; «самый масштабируемый вариант,
  если нужно много места, прокрутка и вложенные вкладки» [S17].
- Намеренное трение: делать поля редактируемыми только внутри раскрытой строки или панели — «меньше места для
  ошибки, потому что надо провалиться, чтобы начать править. Полезно для высокорисковых данных» [S17].

### 7.2 Видимость режима редактирования

Обязательный сигнальный набор `[исследование]` (разбор хорошего примера в [S30]):
1. **Строка меняет фон** (например, серый), чтобы было видно область правки.
2. **Ячейки превращаются в поля ввода** — видно, что редактируемо, а что нет.
3. **Кнопки меняются**: «Изменить»/«Удалить» → «Сохранить»/«Отмена».
4. **Кнопки меняют место и цвет** — «это дополнительный важный сигнал, он снижает вероятность нажать не ту кнопку
   после правки, если пользователь действует по мышечной памяти».
5. Явно определена **область режима**: одна ячейка, одна строка или вся таблица — «приложения различаются по
   охвату режима редактирования, и пользователь должен понимать, что сейчас редактируемо» [S30].

Подтверждение правки: клик вне поля, Enter, галочка или кнопка «Сохранить»; Esc отменяет [S17].
Ячейка, доступная для правки, подсказывает это курсором и состоянием при наведении [S17].

### 7.3 Массовое редактирование

Паттерн `[практика]` [V:GCJ6k3tD50A, 1:41:01]:
1. Пользователь выбирает строки, **включая вариант «все N во всём наборе»**, а не только видимые.
2. Нажимает «Изменить выбранные».
3. Открывается **Excel-подобный вид с настраиваемым набором колонок**, где меняются значения списком.
4. Принцип: **сначала выбираешь, что менять, потом меняешь.**
5. Перед применением показывается, сколько записей будет затронуто; после — результат с числом успешных и
   неуспешных и возможностью открыть список неуспешных.

Для массовой загрузки/импорта — минимум пять стадий: подготовка (шаблон и ожидаемый формат) → загрузка файла →
сопоставление колонок → починка сопоставления → импорт; обязательная функция на стадии починки — **«показать
только строки с ошибками»** [V:GCJ6k3tD50A, 1:43:01]. Подробно — `../05-flows-journeys/`.

## 8. Действия

### 8.1 Действия строки

`[система]` + `[консенсус]`:
1. **1–2 частых действия — inline иконками** с подписью в tooltip и доступным именем; остальные — в меню строки.
2. Carbon: «когда в overflow-меню меньше трёх пунктов, выноси действия inline иконками — это экономит клик и
   делает доступные действия видимыми сразу» [S7].
3. Больше двух inline-действий приводит к одному из двух: **скученные иконки без подписей** (трудно попасть и
   трудно различить) или **спрятанные под наведение / в меню «Действия»** (плохая находимость, плохая
   доступность) [S1].
4. **Действия только по наведению** недоступны с тача и с клавиатуры. Carbon решает это тем, что определяет
   отсутствие hover у устройства и **оставляет меню видимым** [S7]. Правило базы: скрытые по наведению действия
   допустимы только при наличии парного видимого пути (меню строки, панель деталей, контекстное меню с клавиатуры).
5. **Место — последняя колонка справа**, одинаково во всех таблицах приложения
   (`../03-layout-placement/04-placement-conventions-and-redundancy.md` §7).
6. Меню «…» не должно становиться «junk drawer»: «эти подписи имеют низкий информационный запах и являются не чем
   иным, как ящиком для хлама… это ограничивает и находимость, и обнаруживаемость функций» [S30]. Практическое
   ограничение: **не больше 5–7 пунктов в меню строки**, сгруппированных, с деструктивным внизу отдельной группой.
7. Деструктивное действие не выносится inline рядом с частым безопасным
   (`../03-layout-placement/04-placement-conventions-and-redundancy.md` §5).
8. Антипаттерн Balsamiq: одинаковые кнопки «Просмотр»/«Удалить» в каждой строке становятся самым заметным
   элементом страницы и забирают внимание у данных [V:WJE3EDkiu0w].

### 8.2 Выбор строк и массовые действия

`[консенсус]` (Carbon, Polaris, NN/g 2025 совпадают):

**Выбор:**
- Чекбокс «выбрать всё» — **в левом верхнем углу шапки таблицы**; чекбокс в каждой строке [V:7MjvBqlRzCY].
- Чекбокс шапки имеет **три состояния**: checked, unchecked, **indeterminate** (частичный выбор) [S7].
- Выбранные строки отличаются визуально — заливкой или рамкой [V:7MjvBqlRzCY].
- Поддерживается **выбор диапазона с Shift** (в Polaris для этого у строки есть свойство `position`) [S14].
- Одиночный выбор — радиокнопка в первой колонке, действия для выбранного справа в тулбаре [S7].
- Антипримеры: заставлять искать «выбрать всё» по странице; прятать чекбоксы выбора и снятия [V:7MjvBqlRzCY].

**«Выбрать всё» против «выбрать все N»:**
- Чекбокс шапки выбирает **строки текущей страницы**.
- После этого появляется строка-предложение: «Выбраны все 20 на этой странице. **Выбрать все 4 312 записей?**» —
  отдельное явное действие. Обратное действие — «Снять выделение».
- Без этого различия массовое действие либо не масштабируется, либо тихо применяется не к тому набору.
- NN/g: «если применение действия ко всему набору — частая потребность, удобно иметь однокликовое "Select All"» [S1].

**Панель массовых действий:**
- Появляется **только после выбора**; до выбора её нет [V:7MjvBqlRzCY].
- Показывает **число выбранных** и «снять выделение».
- Содержит **только применимые к выбранному действия**: «если пять выбранных строк можно удалить, но нельзя
  редактировать массово, есть "удалить" и нет "редактировать"» [V:7MjvBqlRzCY].
- **Место — над таблицей или липкой полосой, следующей за прокруткой. Не внизу экрана**: низ приемлем для тач-,
  но на вебе и десктопе панель внизу «легко не заметить» [V:7MjvBqlRzCY].
- **В режиме массового выбора действия строки и overflow-меню строки отключаются** [S7].
- При большом выделении нужна **фильтрация внутри выделения** (например, по статусу) [V:GCJ6k3tD50A, 1:40:01].
- На узком экране массовые действия можно прятать (Polaris: ниже **490px**), но только если они несущественны для
  работы: «скрытие означает, что пользователь не может выбрать несколько объектов» [S14].
- Подписи массовых действий — по формуле **глагол + существительное** [S14].

### 8.3 Обратная связь и отмена

`[практика]` [V:7MjvBqlRzCY]:
1. **Необратимое** действие — диалог подтверждения с однозначной формулировкой того, что сейчас произойдёт (и с
   числом объектов).
2. Сразу после выполнения — **сообщение об успехе** (тост или алерт).
3. Для критичных действий **кнопка отмены помещается внутрь сообщения об успехе** — «хорошая страховка на случай,
   если действие выполнено по ошибке».
4. Таблица не должна дёргаться: «avoid jumpy or jarring updates», анимации сдержанные.
5. Имя действия одинаково в кнопке, подтверждении и сообщении (дефект F7.3 каталога).

Детали подтверждений, отмены и порогов «что подтверждать» — `../05-flows-journeys/03-*`.

## 9. Состояния таблицы

### 9.1 Матрица

| Состояние | Что показывать | Чего не делать |
|---|---|---|
| **Загрузка (первая)** | Скелет строк, повторяющий будущую структуру: ширины колонок, выравнивание, наличие ведущего значка | Спиннер по центру; «нет данных» |
| **Загрузка (обновление после фильтра/сортировки)** | Приглушение области данных + индикатор; **заголовки, тулбар и фильтры остаются активными** | Полная замена экрана скелетом; блокирующий оверлей |
| **Пусто: первый вход** | Заголовок, одно предложение о том, что здесь появится, **одно** первичное действие (или указание на элемент UI) | Пустая область; дубль primary-кнопки шапки |
| **Пусто: фильтр ничего не нашёл** | Текст с **повтором условий**, «сбросить фильтры», подсказка ослабить условие | Тот же текст, что при первом входе |
| **Ошибка загрузки** | Что произошло, что делать, кнопка «Повторить»; сохранённые фильтры не теряются | «Что-то пошло не так» |
| **Частичная загрузка** | Показать загруженное + явную отметку, что часть данных недоступна, с причиной | Молча показать неполный набор |
| **Нет прав** | Объяснение и путь запроса доступа | Пустая таблица |
| **Данные обновились в фоне** | Ненавязчивая отметка «обновлено N минут назад» и кнопка обновления | Автоперестроение под курсором |

### 9.2 Порядок состояний

**Сначала загрузка, потом пустое состояние.** Обратный порядок — отдельно вредный дефект: система показывает
«No records», а через несколько секунд заменяет его данными; «в лучшем случае пользователь дожидается и находит
контент, но получает стойкое недоверие к приложению; в худшем — нетерпеливые пользователи (то есть большинство)
никогда не увидят нужного» [S32] `[исследование]`.

### 9.3 Правила пустого состояния таблицы

- **Пустое состояние заменяет таблицу целиком**, включая заголовки колонок и футер: иначе «скринридер прочитает
  всю таблицу, прежде чем дойдёт до сообщения, что в ней ничего нет» [S12] `[система]`. То же для «ничего не
  найдено» [S12], [S24].
- Минимум — сообщение статуса, называющее условие: «Нет записей за выбранный период» [S32].
- Три роли пустого состояния: сообщить статус, обучить (что здесь будет и как это появляется), дать прямой путь к
  задаче [S32]. Приём: кнопка **плюс** ссылка «подробнее»; либо два пути — «добавить данные» и «загрузить демо-набор
  для безопасного исследования» [S32].
- Если пустых состояний на экране может быть несколько — использовать **третичные** кнопки и текст без иллюстраций
  [S12].
- Не уводить в тупик и не покрывать несколько вариантов сразу: «выбери самое важное действие» [S12].
- Полный разбор состояний — `../06-feedback-states-motion/`.

### 9.4 Много строк и живые данные

- Виртуализация — §6.6. Порог считать **по узлам DOM, а не по строкам**: Lighthouse предупреждает при > 800 узлов и
  считает ошибкой > 1 400 (`../09-mobile/03-mobile-content-tables-forms-dashboards.md`, выжимка п.28); таблица
  1 000 строк × 12 колонок — уже 12 000 узлов. Порог «> 1 000» в §2 — порог **серверных операций** (сортировка,
  фильтрация, «выбрать все N»), а не момент включения виртуализации.
- **Живое обновление** (операционные таблицы: очереди, мониторинг): новые строки не должны сдвигать то, что
  пользователь читает или редактирует. Рабочий приём — накапливать изменения и показывать полосу «N новых записей —
  показать», а не вставлять молча. `[практика]`
- Если строка исчезла из набора из-за фильтра после правки — сообщить об этом, а не просто убрать.
- При автообновлении **выделение и раскрытые строки сохраняются**.

## 10. Экспорт, печать, сохранённые виды, настройки

### 10.1 Экспорт и печать

- «Всегда позволяйте выгрузить сырые данные в CSV, если способ, которым вы спроектировали интерфейс, не отвечает
  их задаче. Это базовая вежливость к данным» [S19] `[практика]`.
- Экспорт учитывает **текущие фильтры, сортировку и набор колонок** и говорит об этом («Экспортировать 312
  отфильтрованных записей» против «Экспортировать все 4 312»).
- Действие экспорта живёт в тулбаре таблицы; при долгом экспорте — фоновая задача и уведомление, а не
  блокирующий спиннер.
- Печать в вебе редко нужна, но если нужна — печатается текущий фильтрованный срез без интерактивных контролов.

### 10.2 Сохранённые виды (saved views)

Состав вида `[система]` (Polaris реализует их вкладками над таблицей [S16]):
фильтры + поисковый запрос + сортировка + **набор и порядок колонок** + размер страницы (+ плотность).

Правила:
1. Виды показываются **вкладками или списком над таблицей**; первая вкладка — «Все» и она не удаляется (`isLocked`
   в Polaris) [S16].
2. Действия над видом: **переименовать, дублировать, изменить, удалить** [S16].
3. На вкладке «Все» первичное действие — **«Сохранить как…»** (создать новый вид); на своём виде — «Сохранить»
   (обновить) [S16].
4. Незафиксированные изменения фильтров показываются как «есть несохранённые изменения» с выбором «сохранить /
   отменить».
5. Имя вида даёт пользователь; система предлагает осмысленный черновик из условий («Просроченные, менеджер Иванов»).
6. Видимость: личные виды и общие для команды разделены; общие виды меняет только тот, у кого есть право.
7. Ролевые пресеты видов — **конфигурация одного компонента, а не форк таблицы под каждую роль**: «отдельный вид
   таблицы под каждую роль разваливается при сопровождении: функции одной роли начинают просить в другой»
   [V:WJE3EDkiu0w] `[практика]`.

### 10.3 Настройки таблицы на пользователя

Что запоминается: набор, порядок и ширины колонок; плотность; размер страницы; последний вид; состояние
свёрнутых панелей. Хранится «в сессии браузера или в учётной записи» [S17]; при входе с другого устройства
предпочтительнее учётная запись.
Обязателен **сброс к виду по умолчанию** [S17].

## 11. Узкий экран — только принципы

Подробно — волна 3, `../09-mobile/03-*`. Здесь три принципа, вытекающие из правил выше:

1. **Поддерживаются два сценария, а не «таблица целиком»**: сравнить все строки по одной колонке и открыть детали
   одной строки [V:GCJ6k3tD50A, 1:35:55]. Всё остальное — производные.
2. **Способы трансформации, по возрастанию потерь**: приоритетные колонки (2–4 поля в строке-карточке) →
   горизонтальная прокрутка с липкой первой колонкой → вкладки внутри таблицы (15 колонок → 3 по 5) → отдельный
   экран-деталь.
3. **Закрепление и строк, и колонок на узком экране съедает заметную долю площади** — это цена, которую надо
   считать [V:s7nvF1PuAWY].

Сохраняются в любом случае: идентификатор в первой позиции, сортировка (хотя бы в виде списка), фильтры
(в bottom sheet с кнопкой «Применить»), счётчик найденного и массовые действия, если они существенны.

## Частые ошибки

**Общие**

1. Первая колонка — технический ID [S30], [S1].
2. Колонки в порядке столбцов таблицы БД, а не по важности [S1].

4. Горизонтальная прокрутка без липкой первой колонки и без признака прокрутки [S25].
5. Числа выровнены влево или по центру, цифры пропорциональные [S17], [S24].
6. Заголовок колонки выровнен не так, как её содержимое [S17].
7. Одна колонка содержит несколько разных данных, и непонятно, по чему сортировка [S24].
8. Модалка поверх таблицы для просмотра или правки строки [S1], [S30].
9. Раскрытые аккордеоном строки, которые никто не закрывает [S1].

12. Пагинация сверху вместо низа или дублирование на таблице из 10 строк [S10].

## Чек-лист

Назначение и состав:
1. Заявлена ли задача экрана одной фразой и одна из четырёх задач таблицы?
2. Обоснован ли выбор «таблица», а не список, карточки или master-detail, по таблице §1.2?
3. Первая колонка — человекочитаемый идентификатор?
4. Колонки идут по важности, связанные рядом?
5. Каждая колонка — один тип данных, и заголовок его описывает?
6. Есть ли колонки, по которым не сортируют и не фильтруют, и можно ли их убрать?

Пороги:
7. Строк больше 50 → есть пагинация (или «показать ещё») и поиск/фильтр?
8. Колонок больше 8 → есть липкий заголовок, липкая первая колонка и управление колонками с индикатором «скрыто N»?
9. Строк больше 1000 → виртуализация или серверная пагинация, и серверные сортировка/фильтрация?
10. Каждая сортируемая колонка имеет `aria-sort`?

Поведение:
11. Сортировка по умолчанию осмысленна для этого типа данных, и это записано?
12. Есть ли многоуровневая сортировка там, где первичный ключ даёт много одинаковых значений?
13. Клик по строке — настоящая ссылка на карточку объекта; вложенные ссылки не конфликтуют?
14. Числа выровнены вправо, моноширинными цифрами; заголовки выровнены как содержимое?
15. Длинный текст переносится, а не обрезается; при обрезке есть tooltip с полным значением?
16. Пустые ячейки пусты (или их заполнитель скрыт от скринридера); `null` нигде нет?

Правка и действия:
17. Выбран способ редактирования по таблице §7.1, и модалки среди них нет?
18. Режим правки виден по четырём признакам (фон, поля, подписи кнопок, место кнопок)?
19. Действий строки не больше двух inline, остальные в меню; меню не длиннее 5–7 пунктов?
20. Есть ли для hover-действий парный видимый или клавиатурный путь?
21. Панель массовых действий появляется только при выборе, стоит над таблицей и показывает число выбранных?
22. Различены «выбрать всё на странице» и «выбрать все N»?
23. После массового действия есть сообщение об успехе и отмена внутри него?

Состояния:
24. Реализованы четыре состояния: загрузка, пусто (первый вход), пусто (фильтр), ошибка?
25. Пустое состояние заменяет таблицу вместе с заголовками колонок?
26. Состояние загрузки показывается **раньше** пустого, а не наоборот?
27. Скелет строк повторяет ширины и выравнивание будущих ячеек?

Состояние и память:
28. Фильтры, сортировка, страница, размер страницы и набор колонок живут в URL?
29. Позиция восстанавливается при возврате из карточки?
30. Настройки таблицы запоминаются на пользователя и есть сброс к умолчанию?
31. Есть сохранённые виды с переименованием, дублированием и удалением — если таблица используется в нескольких
    сценариях?
32. Есть экспорт текущего среза, и он честно сообщает, что именно экспортирует?

Проверка на реальности:
33. Таблица проверена на 0, 1, 500 и 5000 строк?
34. Проверена на граничных данных: очень длинное имя, отрицательное число, отсутствующее поле, все строки в одном
    статусе?
35. Проверена на ширине 1280 и 360 px?

## Открытые вопросы и противоречия

1. **Пустая ячейка: «пусто» или «—»** `[спорно]`. Primer запрещает символ-заполнитель из-за скринридеров [S24];
   практика админок ставит «—», чтобы отличать «нет значения» от «поле не загрузилось». Ни одного исследования по
   этому вопросу не найдено. Позиция базы (§3.7) — синтез, а не позиция источника.
2. **Склеивать ли колонки** `[спорно]`. Balsamiq рекомендует объединять данные, чтобы освободить место
   [V:WJE3EDkiu0w]; Primer прямо запрещает («Don't use a single column to show multiple pieces of data»), потому
   что заголовок перестаёт описывать содержимое и ломается сортировка [S24]. Разрешение базы: склеивать можно
   только то, что **никогда не сортируется и не фильтруется по отдельности** (имя+фамилия, город+улица), и
   заголовок должен описывать составное значение.
3. **Зебра** `[спорно]`. NN/g называет её помощником сканирования [S1]; практики 2026 года считают устаревшим
   дефолтом из-за конфликта состояний [S17]. Критерии §4.2 — мой синтез.
4. **Горизонтальная прокрутка** `[спорно]`. Разбор в §3.3; ни у одной стороны нет измерения, только утверждение
   NN/g «дороже вертикальной» без ссылки на исследование [V:23AQBZzDUIo].
5. **Плотность** `[спорно]`: Balsamiq за воздух, Friedman за плотность в экспертных средах. Разрешение §4.1.
6. **Число строк на странице**: единственный числовой ориентир — «20 строк — хорошая отправная точка» у Primer
   [S24] и порог «пагинация при более чем 50 объектах» у Polaris [S14]. Исследования, сравнивающего размеры
   страниц по времени задачи, я не нашёл. Это хороший кандидат на собственный замер.
7. **Пороговые таблицы §2 — синтез**, а не данные. Источники дают только два числа (50 и 20); пороги по колонкам
   (8, 12) и по строкам (200, 1000) выведены мной из правил о липких колонках, управлении колонками и
   производительности. Помечены `[мнение]` в самой таблице.
8. **Дефект F4.2 каталога остаётся частично неизмеренным.** Ни один найденный бенчмарк не проверяет сортировку,
   пагинацию, выбор строк и массовые операции как отдельный класс. §2 даёт проверяемые правила, но не данные о
   массовости дефекта.
9. **Айтрекинг «прыжок на восьмую страницу»** [V:GCJ6k3tD50A] — одна сессия одного пользователя. Приёмы steps
   pagination и scroll bar range interval стоит считать гипотезами.
10. **Не удалось прочитать**: Material 3 «Data tables» (m3.material.io — SPA, `r.jina.ai` вернул 403),
    Salesforce Lightning «Data tables» и «Record page» (SPA, архивы пустые), Fluent 2 DataGrid (сайт не отвечал),
    Ant Design «Table» (страница в кэше содержит только заголовок). Это заметный пробел: три из них задают
    конвенции корпоративных админок. Кандидаты доступа: npm-пакет документации Lightning, репозиторий
    `ant-design` с markdown-файлами компонентов, `render_fetch.py` из соседнего проекта `ui`.
11. **Расхождение с волной 1 не найдено.** Правила §3–§8 уточняют, но не переопределяют
    `../03-layout-placement/04-placement-conventions-and-redundancy.md` §7. Единственное уточнение: Carbon прямо
    запрещает пагинацию над таблицей [S10], тогда как B допускает дублирование сверху при длинных страницах; база
    сохраняет позицию B (дублирование — исключение для страниц длиннее 2–3 экранов), но отмечает, что одна из
    крупных систем этого не делает вовсе.
