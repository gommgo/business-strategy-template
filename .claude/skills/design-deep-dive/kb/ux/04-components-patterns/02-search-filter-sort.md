## Выжимка для агента

1. **Поиск, фильтры и сортировка — один блок инструментов, а не три компонента.** Пользователь не различает их;
   типичный порядок действий: поиск → фильтры → сортировка. → §1 `[мнение]`
2. **Прежде чем строить поиск, проверь, не чинишь ли ты им плохую навигацию.** Поиск — не замена структуре. → §2.1 `[практика]`
3. **Поле поиска видимо и просто**: поле, а не иконка; без подписи (лупа и плейсхолдер достаточны); плейсхолдер
   называет область поиска («Поиск по заказам», не «Введите текст»). → §2.2 `[система]`
4. **Три режима поиска различаются заранее**: basic (уводит на страницу результатов), active (фильтрует на месте
   после каждого символа), focused (результаты в своей области + расширение на всё). → §2.3 `[система]`
5. **Активный поиск по таблице — не то же, что глобальный поиск в шапке.** Они не заменяют друг друга и не
   дублируются. → §2.1 `[консенсус]`
6. **Подсказки появляются примерно с 3-го символа**, у каждой есть результаты, и подсветка зависит от механизма:
   дописываешь — подсвечивай дописанное; ищешь вхождение — подсвечивай введённое. → §2.4 `[исследование]`
7. **Подсказка, ведущая в ноль или в нерелевантное, хуже, чем отсутствие подсказок.** → §2.4 `[исследование]`
8. **Богатые подсказки с картинками почти не используются** (7 из 60 показов) и читаются как реклама; простые
   текстовые подсказки убирать нельзя. → §2.4 `[исследование]`
9. **Число результатов показывается всегда, включая ноль**, и для каждой области поиска отдельно. → §2.5 `[система]`
10. **«Ничего не найдено» — заметное сообщение в теле страницы + путь вперёд**: повтор запроса, поле с сохранённым
    запросом, исправление, совет сократить условия, сброс фильтров. Без юмора. → §2.6 `[исследование]`
11. **В админке поиск по точному идентификатору обязан находить объект без нечёткости**, а сценарий «убедиться,
    что ничего нет» должен быть возможен. → §2.7 `[практика]`
12. **Порог отклика: до 1 с — можно фильтровать мгновенно; дольше — «Применить» или явный индикатор.** → §3.5 `[исследование]`
13. **Запрос, фильтры, сортировка и страница живут в URL** — иначе нельзя поделиться, вернуться и восстановить
    состояние. → §6 `[консенсус]`
14. **Фасеты дороже фильтров**: они добавляют interaction cost и требуют метаданных. Не строить, пока не доказано,
    что нужны. → §3.1 `[консенсус]`
15. **Фильтр = свойство + отношение + значение.** Отношение чаще всего задаёт система, а не пользователь. → §3.2 `[практика]`
16. **Все данные, которые видны в записи, должны быть фильтруемыми** («видишь "изменено: дата" — жди фильтр по
    дате изменения»). → §3.2 `[практика]`
17. **Размещение: до 4–5 простых фильтров — строкой сверху; горизонтальная панель ломается после 6–8 типов;
    много многозначных фасетов — панель слева.** → §3.3 `[исследование]`
18. **Тип контрола выводится из типа данных**: один из многих — радио/селект, несколько — чекбоксы, булев —
    переключатель без дропдауна, число и дата — диапазон с пресетами. → §3.4 `[консенсус]`
19. **Выбор фильтра не должен закрывать панель, сбрасывать другие фильтры или прокручивать страницу**: люди
    выбирают 4–7 фильтров за сессию, в экспертном ПО до 28. → §3.5 `[практика]`
20. **Чипы применённых фильтров — над результатами**, а не в левой колонке: в колонке они меняют высоту блока и
    сбивают прицел мыши. → §3.6 `[практика]`
21. **Показывать только число применённых фильтров вместо самих фильтров — антипаттерн.** → §3.6 `[исследование]`
22. **Свёрнутая панель фильтров обязана показывать, что внутри есть выбор** (число), и давать сброс без
    разворачивания. → §3.6 `[система]`
23. **Сброс нужен и у отдельной категории, и глобальный.** «Сбросить всё» — ещё и напоминание, что фильтры
    применены. → §3.6 `[консенсус]`
24. **Счётчик результатов у каждого значения предотвращает нулевой результат**; конфликтующие значения
    дизейблятся. → §3.7 `[практика]`
25. **Значение фильтра не исчезает из панели после выбора** (97% сайтов это соблюдают). → §3.6 `[исследование]`
26. **Внутри категории: И между категориями, ИЛИ внутри категории** — и это объясняется текстом там, где важно. → §3.8 `[практика]`
27. **Порядок фильтров: общие сверху, специфические снизу; значения — по приоритету, если их мало, по алфавиту,
    если много.** → §3.9 `[исследование]`
28. **Ярлыки фильтров без жаргона и взаимоисключающие**; расплывчатые названия категорий («Тип элемента») —
    источник провалов в тестах. → §3.9 `[исследование]`
29. **Сохранённые фильтры (запросы) обязательны там, где одна и та же выборка повторяется.** → §3.10 `[практика]`
30. **Сортировка по умолчанию задаётся типом списка** (свежесть, срочность, релевантность, алфавит), и её меняют,
    только когда есть вторая осмысленная сортировка. → §4 `[консенсус]`
31. **Командная палитра — слой поверх работающей навигации, а не замена ей**; её главная проблема — находимость,
    а не ценность. → §5 `[практика]`

## 1. Один блок, а не три компонента

Практическое наблюдение: «пользователи не разделяют поиск, фильтрацию и сортировку — это одна задача; типичный
порядок: **поиск → фильтры → сортировка**. Проектируй их как один блок» [V:GCJ6k3tD50A, 1:08:12] `[мнение]`.

Подтверждение с другой стороны: в айтрекинге NN/g по таблице участник фиксируется туда-сюда **между данными и
фильтрами над ними** [S1] — то есть фильтры воспринимаются как часть таблицы, а не как отдельная панель.

Следствия для сборки экрана:
- инструменты сужения живут в одной зоне и в одинаковом порядке на всех экранах-списках приложения;
- поиск по разделу стоит рядом с фильтрами, а не в шапке приложения (там глобальный поиск — §2.1);
- результат любого из трёх действий отражается в одном и том же месте: счётчик найденного + чипы активных условий;
- сброс работает на весь блок («Сбросить всё»), а не только на фильтры.

Порядок сверху вниз на экране-списке (сводка с `../03-layout-placement/01-page-anatomy-templates.md` §4):
вкладки-виды → строка инструментов (поиск, фильтры, сортировка, вид, экспорт) → чипы применённых условий и счётчик
→ панель массовых действий (при выделении) → таблица → пагинация.

## 2. Поиск в приложении

### 2.1 Когда глобальный, когда локальный

| Тип | Где | Что ищет | Когда нужен |
|---|---|---|---|
| **Глобальный** | Верхняя полоса приложения | Объекты всех типов, разделы, настройки, документацию | Больше 3 типов объектов **или** больше 2 уровней навигации; пользователь часто приходит с известным идентификатором |
| **Локальный (по разделу)** | В строке инструментов над списком | Только объекты этого раздела | Всегда, если в списке больше ~50 объектов [S14] |
| **По таблице (active)** | В тулбаре таблицы | Фильтрует видимый набор по подстроке | Набор небольшой и умещается на клиенте, либо сервер выдерживает нагрузку [S9] |
| **Командная палитра** | Cmd/Ctrl+K | Действия и переходы | §5 |

Правила `[консенсус]`:
- Глобальный и локальный поиск **не дублируют друг друга**: у локального явно назван охват в плейсхолдере
  («Поиск по заказам»), у глобального — «Поиск» без уточнения либо с переключателем области.
- Дашборд может иметь **свой поиск как стартовую задачу**, а не дубль глобального: у турагента это «найти клиента»
  и «найти круиз» с выбором поля (номер брони / имя / телефон) [V:ZqNRywpO3bE, 18:25].
- Если пользователь не знает названия объекта, рядом с поиском нужен **просмотр по категориям**
  [V:ZqNRywpO3bE, 18:25].

**Предупреждение перед постройкой поиска** [S20] `[практика]`: «Иногда поиск используется как дешёвое решение
плохого UX — это одна из подпорок в корпоративном софте, которой заклеивают неприятный интерфейс. Спросите себя,
не плохая ли навигация лежит в основе желания сделать поиск». И: «Достаточно ли велик ваш продукт или объём
данных, чтобы поиск был нужен?»

**Scoped search** (поиск с областью) NN/g рекомендует «только на некоторых сайтах и только если реализован
хорошо» [S9-дополнение]. В Carbon правило конкретнее: в списке областей **всегда есть «Все»/«Любая», и она выбрана
по умолчанию**; выбранная область сохраняется на последующие поиски до сброса или новой сессии [S9] `[система]`.

### 2.2 Поле поиска

`[система]` + `[консенсус]`:
1. **Поле ввода, а не иконка и не ссылка.** Классическое правило NN/g «Search: Visible and Simple»
   (см. `../03-layout-placement/04-placement-conventions-and-redundancy.md` §1).
2. **Без подписи**: «Avoid adding a label to your search field. Users expect and understand search fields… A search
   icon along with useful placeholder text should clearly indicate that the field is intended for search» [S9].
   (Доступное имя для скринридера при этом обязательно — `aria-label`.)
3. **Плейсхолдер конкретный и называющий область**: «Search for networks or devices» [S9]; «search entire website
   vs. search items in table below» [S20]. У активного поиска плейсхолдер конкретнее, чем у обычного, и остаётся
   виден до начала ввода [S9].
4. **Иконка лупы** — универсальный признак поиска, в том числе между языками [S9]; у неё заметное состояние при
   наведении, и продумана горячая клавиша [S20].
5. **Кнопка очистки «×»** — обязательна в активном поиске; в обычном полезна.
6. Явное состояние фокуса [S20].
7. Для RTL раскладка поля зеркалится [S9].
8. Клавиатура: Tab в поле → ввод → Enter запускает; стрелки листают подсказки, Enter выбирает, **Esc закрывает
   подсказки без выбора** [S9].

### 2.3 Три режима поиска (таблица решений)

Carbon даёт готовую развилку [S9] `[система]`:

| Режим | Поведение | Когда применять |
|---|---|---|
| **Basic** | Запрос выполняется по Enter, пользователь попадает на **отдельную страницу результатов**. До запуска данные не запрашиваются | Поиск **дорогой** (много одновременных пользователей — запускать после каждого символа непрактично); поиск **медленный**; пространство данных **незнакомо пользователю** — «отдельная страница результатов даёт представление о структуре данных и доступных ресурсах» |
| **Active** | Запрос после каждого символа, результаты сразу под полем или прямо в списке; **нет кнопки «Найти»**, есть «×» | Небольшой набор (страница, таблица, каталог); пользователь знает, что ищет; сервер выдерживает нагрузку |
| **Focused** | Активные результаты внутри текущей области + внизу ссылка «искать во всём» | Поиск по задачам и данным текущего пользователя; надо ограничить нагрузку, но оставить возможность расширить |

Дополнительный приём для очень больших наборов: «дать выбрать общую корзину (bucket) до запуска поиска» [S20].

### 2.4 Автодополнение и подсказки

Определение: «recommended queries that appear in a dropdown as users type» [S21].

**Данные** `[исследование]`:
- Подсказки выбирались пользователями **в 23% случаев показа** (31 из 136, погрешность 7%) — то есть это ожидаемый,
  но не основной механизм; остальную пользу они приносят как справка: видно, что вообще есть, и как пишется
  сложный термин [S21].
- Обратная сторона: «если после первых символов названия товара подсказка не появилась, часть пользователей решает,
  что такого товара на сайте нет, и **уходит, не выполнив поиск**» [S21].
- **Обогащённые подсказки** (карточки товаров, категории, статьи) использованы **7 раз из 60 показов**; четыре
  причины провала: несовпадение с режимом «поиск» (пользователь не хочет исследовать), медленная загрузка
  (пользователь отправляет запрос раньше, чем догрузятся картинки), баннерная слепота (игнорируют графику даже при
  точном совпадении), чтение как рекламы [S22].

**Правила** `[исследование]` + `[практика]`:
1. **У каждой подсказки должны быть хорошие результаты.** «Подсказки, дающие ноль или нерелевантное, хуже, чем
   бесполезные: они уводят в сторону и прямо раздражают» [S21].
2. **Подсветка зависит от механизма** [S21]:
   - система **дописывает** к введённому → подсвечивать **дописанное**: `basketball h`**`oop`**;
   - система ищет **вхождение** введённого → подсвечивать **введённое**: **`basketball h`**`oodie`,
     `portable `**`basketball h`**`oop`.
3. **Область (scope) — третья часть строки**, визуально отличённая и **с отступом под запросом**: «water bottle» /
   «in Home & Kitchen» / «in Outdoor Recreation» [S21].
4. Появляются обычно **после 3 символов**; внутри — **заголовки категорий**, автофокус на первом результате,
   подсказки горячих клавиш, прокрутка, индикатор загрузки, **подсветка совпадений** [S20].
5. **Различать «вставить в запрос» и «выполнить поиск»**: клик по строке выполняет поиск, стрелка подставляет
   текст в поле для доуточнения. Приём полезный, но «его никто не понимает» — помечай подсказки-ключевые слова
   чипами или бейджами [V:GCJ6k3tD50A, 1:23:29].
6. **Не убирать простые текстовые подсказки** ради обогащённых; ограничить графику и динамику; **явно подписывать
   типы блоков** («Недавние», «Популярные», «Товары»), иначе они читаются как промо; **держать типы блоков на
   фиксированных местах**, а не менять раскладку от запроса к запросу [S22].
7. «Do not assume that regular site users will learn to use enriched search suggestions over time» — в исследовании
   не научились даже после нескольких поисков [S22].
8. **Список не должен прыгать под курсором**: при перестроении подсказок клик попадает не туда. Приём — на время
   движения мыши или табуляции не перестраивать список [S20].
9. На мобильном — только простые текстовые подсказки [S21].

### 2.5 Страница результатов

`[система]` + `[практика]`:
1. **Число результатов — всегда**, включая ноль; при наличии областей — число по каждой области [S9].
2. **Вкладки или группы по типам объектов**, если результаты разнородны [S20].
3. **Подсветка совпадений** в результатах — «облегчает мысленное сопоставление запроса и результата» [S20], [S17].
4. **Показывать, где именно совпало**, когда это неоднозначно: запрос «1232» может совпасть со штрихкодом, номером
   партии и ID образца — это разные вещи [S20].
5. Фильтры и сортировка на странице результатов обязательны; если фильтры хочется дать **до** поиска — это
   scope-фильтр в поле [S9].
6. Пагинация по правилам `01-data-tables.md` §6.
7. Сниппет результата строится по правилам списочной записи (`04-lists-cards-and-record-view.md` §2): 2–4
   приоритетных атрибута + тип объекта + путь/родитель для контекста.
8. Индикатор загрузки, если поиск дольше пары мгновений; для тяжёлых — прогресс с оценкой [S9].

### 2.6 «Ничего не найдено»

Три правила NN/g [S23] `[исследование]`: ясно сказать, что ничего не найдено; дать путь вперёд; не издеваться.

- **Сообщение должно быть в теле страницы и заметным.** Айтрекинг: мелкое светлое «Sorry, no matches found…»
  между логотипом и первым жирным заголовком **не получило ни одной фиксации взгляда**; пользователь ушёл читать
  то, что выглядело как основной контент [S23]. Причина — сильная ментальная модель «шапка сверху, результаты в
  теле».
- Что предлагать: повтор исходного запроса; **поле поиска с сохранённым запросом для правки**; похожие запросы,
  которые дают результаты; исправление опечаток; совет **сократить число слов** или ослабить условие [S23].
- Если ноль вызван **фильтрами**, а не запросом — сказать об этом и дать «сбросить фильтры» и «снять последнее
  условие».
- **Заменять контент, а не добавлять сообщение сверху**: пустое состояние занимает место таблицы [S12].
- **Не шутить**: «пользователь может не понять, смеётесь вы вместе с ним или над ним» [S23].
- Сценарий «убедиться, что ничего нет» — легитимный (§2.7): в нём «ничего не найдено» **и есть** правильный ответ,
  и формулировка не должна выглядеть как ошибка.

### 2.7 Поиск по идентификаторам и точным значениям в админках

`[практика]`, выведено из [S20] и из практики админок:
1. **Точное совпадение по идентификатору всегда выигрывает у нечёткого**: если пользователь ввёл номер заказа
   целиком, этот заказ — первый результат, а лучше — сразу переход на его карточку.
2. **Нечёткий поиск не должен «исправлять» идентификаторы**: «A-1042» не превращается в «A-1043».
3. Сценарий «найти ничего» (проверить, что дубля нет) обязан быть надёжным: результат «ничего не найдено» для
   точного запроса — это ответ, а не сбой.
4. Поиск по частичному идентификатору (последние 4 цифры) — частая потребность в поддержке; если поддерживается,
   об этом сказано в плейсхолдере или подсказке.
5. Поиск понимает **разные формы записи одного значения**: с пробелами и без, с дефисами и без, разный регистр,
   ведущие нули.
6. **Ветка «похоже на идентификатор»**: если введённое похоже на ID/номер/e-mail, показать точное совпадение
   отдельным блоком над остальными результатами.
7. Операторы для экспертов (кавычки для точной фразы, `поле:значение`, минус для исключения) — опционально, но
   если есть, то **синтаксис показан в подсказке под полем** и продублирован UI-конструктором (§3.8): «фильтр
   должен быть прозрачен пользователю» [S1].

### 2.8 Скорость и пороги отклика

| Время ответа | Что делать |
|---|---|
| < 0,1 с | Ничего; результат ощущается мгновенным |
| < 1 с | Можно обновлять результаты после каждого действия; индикатор не нужен, но допустим [S3] |
| 1–10 с | Спиннер или скелет; для фильтров — приглушить область результатов целиком и показать индикатор [S3], [S31] |
| > 10 с | Прогресс-бар с оценкой; для поиска — «ищем в N источниках» [S30], [S31] |
| Очень долго | Фоновая задача и уведомление по готовности |

Отдельно: **мерцание при мгновенной фильтрации** вредно само по себе — «flicker of an image swap will attract
attention… Flickering in the peripheral vision is annoying». Решение: затемнять **всю область результатов
целиком** и показывать один индикатор, чтобы менялась одна область, а не отдельные элементы [S3] `[исследование]`.

### 2.9 Запрос в URL и сохранение

- Поисковый запрос, область, фильтры, сортировка, страница и размер страницы — **параметры URL**; страница,
  открытая по такому адресу, воспроизводит состояние.
- Недавние запросы пользователя показываются при фокусе в пустом поле [S9].
- Сохранённые запросы — §3.10.

## 3. Фильтры

### 3.1 Фильтр и фасет

Определения NN/g [S2] `[консенсус]`:
- **Фильтр** — «всё, что анализирует набор контента и исключает часть элементов».
- **Фасетная навигация** — «несколько фильтров, которые исчерпывающе описывают набор контента», по одному на
  каждый аспект.

Разница «по степени, но важная»: фасеты дают структуру, из которой видно пространство данных и что вообще можно
искать. Цена: «значительно дороже создавать и поддерживать», метаданные нужны и у существующего, и у будущего
контента, и **фасеты увеличивают interaction cost** — «простой фильтр часто понятнее и быстрее» [S2].

**Правило:** не строить фасеты, пока не доказано, что одного-двух фильтров мало. Признак, что фасеты нужны:
пользователи регулярно комбинируют 3+ независимых условия (§3.5).

### 3.2 Анатомия фильтра

Полезный контракт из практики [S18] `[практика]`:

```
условие (variable) = идентификатор (identifier) + отношение (relative) + значение (value)
```

- **Идентификатор** — свойство или категория («Статус», «Сумма», «Дата изменения»).
- **Отношение** — «равно», «больше», «между x и y», «содержит», а также связка И/ИЛИ между условиями.
- **Значение** — конкретное значение или диапазон.

«Выбор отношения часто **не отдаётся пользователю** и должен быть продуман системой» [S18]. Пресеты диапазонов дат
(«эта неделя», «прошлый месяц», «с начала месяца») — способ упаковать отношение в одно значение.

Два правила отбора фильтров:
1. **Зеркалить данные**: «если в записи показано "Изменено: дата", пользователь ждёт, что сможет фильтровать по
   дате изменения» [S18]. Проверяемо: для каждого атрибута, видимого в строке списка или в карточке, должен быть
   ответ «фильтруется / сортируется / ни то ни другое, потому что …».
2. **Знать, когда остановиться**: «предлагать продвинутые фильтры для списка из 10 элементов — лишняя
   сложность… глубина фильтров должна соответствовать глубине и объёму самих данных» [S18].

### 3.3 Размещение (таблица решений)

| Признак | Строка сверху | Горизонтальная панель | Панель слева | Выдвижная панель / модалка | Фильтр в заголовке колонки |
|---|---|---|---|---|---|
| Число типов фильтров | 1–3 | **до 6–8** [S39] | много | много, но применяются редко | по одному на колонку |
| Значения надо видеть сразу | нет | нет | **да** | нет | нет |
| Нужны счётчики у значений | нет | нет | **да** | нет | нет |
| Фильтры действуют на всю страницу | да | да | **обязательно** | да | нет, на таблицу |
| На странице несколько блоков с разными данными | нет | да (над своей секцией) | **нет** | да | да |
| Масштабируемость | низкая | средняя | **высокая** | высокая | средняя |
| Контекст | высокий | гибридный | низкий (глобальный) | низкий | **самый высокий** |

Основания:
- Baymard: **24% сайтов используют горизонтальную панель фильтров**; она «может создавать трудности, если типов
  фильтров больше 6–8»; два её недостатка — значения не видны по умолчанию (нельзя оценить объём каталога и число
  совпадений) и кнопка «Все фильтры» **пропускается участниками тестов**. «Сайдбар — проверенная и привычная
  реализация, которая в целом устраивает большинство пользователей» [S39] `[исследование]`.
- Friedman: «фильтры **над** результатами обычно лучше, чем в левой колонке» [V:GCJ6k3tD50A, 1:14:18] `[мнение]` —
  это рекомендация для случая немногих фильтров и прямо конфликтует с Baymard при большом их числе.
- Pencil & Paper: сайдбар масштабируем, но **требует, чтобы фильтры влияли на всю страницу**, иначе путаница;
  inline-фильтры дают максимум контекста и минимум масштабируемости; горизонтальная панель — гибрид [S18].
- Carbon: «**несколько категорий фильтров никогда не кладут внутрь меню или дропдауна**» — только вертикально
  слева или горизонтально над данными [S8] `[система]`.
- Carbon и P&P: фильтр **в заголовке колонки** даёт «наивысший уровень контекста — результат меняется прямо под
  вводом» [S18].

**Разрешение конфликта Friedman vs Baymard** `[спорно]`: до 5–6 типов фильтров — сверху (Friedman прав: меньше
переводов взгляда, чипы и результаты рядом); от 7 и при многозначных значениях со счётчиками — слева (Baymard
прав: иначе значения не видны и часть фильтров теряется за «Ещё»). Совпадает с правилом волны 1
(`../03-layout-placement/04-placement-conventions-and-redundancy.md` §6).

**Продвинутые (promoted) фильтры** [S40] `[исследование]`: 2–3 самых частых значения выносятся прямо в список
над результатами; **61% сайтов этого не делают**, хотя «первое действие большинства участников при попадании в
список — искать подходящие фильтры». Условие: продвинутый фильтр **остаётся и на своём обычном месте** в панели.
На мобильном в строку влезает 2–3, дальше — горизонтальная прокрутка с обрезкой или индикаторами.

### 3.4 Типы контролов по типу данных

`[консенсус]` (Carbon, P&P, практика):

| Тип данных | Контрол | Замечания |
|---|---|---|
| Один из немногих взаимоисключающих (≤ 7) | Радиокнопки или сегментированный переключатель | Обязателен вариант «Все» |
| Один из многих | Селект с поиском | Поиск внутри — при более чем ~10 значениях, **с автофокусом** [S18] |
| Несколько из немногих (≤ 10) | Чекбоксы списком | Видны все значения и счётчики |
| Несколько из многих | Мультиселект с поиском + чипы выбранного | «Показать ещё» внутри категории |
| Булев («есть / нет») | **Чекбокс или переключатель, без дропдауна** [S18] | Формулировка положительная («Только с ошибками») |
| Число | Диапазон от–до полями ввода (+ слайдер как дополнение) | Поля ввода обязательны: слайдером не попасть в точное значение |
| Дата и период | Пресеты **и** произвольный выбор | §3.4.1 |
| Свободный текст | Поле с поиском по подстроке | Это уже поиск, см. §2 |
| Иерархия (категория → подкатегория) | Раскрывающиеся уровни внутри одной категории | Лучше, чем две конкурирующие плоские категории [S4] |
| Теги | Мультиселект с поиском | Чипы |

#### 3.4.1 Датапикер: минимальный контракт

[S18] `[практика]`:
1. **Пресеты и произвольный выбор одновременно**: «эта неделя», «прошлая неделя», «с начала месяца», «последние
   30 дней» + календарь.
2. **Быстрая обратная связь о порядке дат**: начало не может быть позже конца, и это видно до подтверждения.
3. **Выбранное видно текстом внутри пикера**, даже если календарь прокручен далеко.
4. Это текстовое поле — **редактируемое**: два способа ввода и полноценная работа с клавиатуры.
5. Формат ввода прощающий: принимать «01.02.2026», «1 фев 2026», «2026-02-01».
6. Часовой пояс и границы суток объявлены явно там, где они влияют на результат.

### 3.5 Мгновенно или по кнопке «Применить»

Ключевая развилка. Данные и правила:

**Два измерения** [S3] `[исследование]`:
1. Когда применять: **batch** (пользователь набирает несколько условий, потом один запрос) против **interactive**
   (результат после каждого значения).
2. Прокручивать ли результаты наверх или сохранять позицию.

**Таблица решений:**

| Условие | Мгновенно (interactive) | По кнопке (batch) |
|---|---|---|
| Режим пользователя | исследовательский: «выберу — посмотрю — придумаю следующее» | целевой: критерии уже в голове |
| Ответ сервера | **< 1 с** | ≥ 1 с или нестабильно |
| Число условий за сессию | 1–2 | 3+ |
| Мобильный | нет | **да** («это рекомендуемый подход на мобильных») |
| Категорий фильтров | одна | несколько |
| Риск нулевого результата | низкий (видно по счётчикам) | высокий → нужны счётчики и дизейбл |
| Цена ошибки | низкая | высокая (аналитика, отчёты) |

Обоснования [S3]:
- Интерактивная фильтрация связана с фасетами: после выбора появляются новые применимые фасеты; **счётчики у
  значений помогают избежать нулевого результата**.
- Batch: «самый большой минус — риск набрать комбинацию с нулём результатов… Плюс — экономит ожидание: вместо
  нескольких запросов пользователь ждёт один».
- «**Let users tell you when they're done selecting filters.** Это значит ошибаться в сторону batch и **включать
  кнопку "Применить"**… Это рекомендуемый подход на мобильных устройствах. Но так вы подводите исследовательских
  пользователей.»
- Третий путь — **детектировать активность**: движение мыши или фокус клавиатуры в зоне фильтров = пользователь
  ещё выбирает; уход к результатам = готов; **фолбэк по времени 1–2 секунды бездействия**, при немедленной
  обратной связи, что первый выбор принят.
- Скорость сайта как второй фактор: «если результат приходит меньше чем за секунду, интерактивная фильтрация
  безобидна даже в режиме поиска».

Промежуточный вариант из практики [S18]: **per-filter** — пользователь заканчивает работу внутри одного
мультиселекта (ищет, прокручивает, отмечает), и триггером служит закрытие дропдауна или inline-кнопка «Применить»
внутри него. Это лучший компромисс для мультиселектов с длинными списками.

Carbon формулирует то же через свои пять методов: batch — «когда пользователь делает несколько выборов в разных
категориях, которые требуют обдумывания», и при медленной отдаче данных; instant — «когда выбор идёт из одной
категории или ожидается один выбор» [S8].

**Чего нельзя ни в одном варианте** `[практика]` [V:GCJ6k3tD50A, 1:12:15]:
- закрывать панель фильтров после выбора одного значения («я никогда не видел человека, который хотел бы
  использовать ровно один фильтр за раз»);
- сбрасывать ранее выбранные фильтры при выборе нового;
- автоматически прокручивать страницу наверх, пока пользователь работает в зоне фильтров;
- блокировать интерфейс на время запроса.

Числа для калибровки: **типично 4–7 фильтров за сессию, в экспертном ПО до 28** [V:GCJ6k3tD50A, 1:12:15]
`[практика]`. Это прямой аргумент за batch или per-filter в админках.

**Прокрутка после применения** [S3]: прыжок наверх сбивает тех, кто ещё выбирает, и увеличивает шанс случайного
клика; но он полезен, когда релевантность резко падает вниз по списку **или** когда результатов стало мало и на
текущей позиции экран пуст (пример: отфильтровали до 6 рейсов, экран пуст — «это можно принять и за загрузку, и за
ноль результатов»). Правило: **не прокручивать, пока фокус или курсор в зоне фильтров; прокручивать, если после
применения видимая область оказалась пустой**.

### 3.6 Активные фильтры: чипы, индикаторы, сброс

**Зачем** [S38] `[исследование]`: без сводки применённых фильтров пользователь сталкивается с тремя проблемами —
нет подтверждения, что фильтры применены; нет быстрого способа их снять; **нет контекста списка**. «Сводка
применённых фильтров так же важна, как заголовок страницы или хлебные крошки… пользователи, пропустившие хотя бы
один применённый фильтр, скорее всего неверно поймут и тип, и диапазон того, что есть в системе». **28% сайтов
в бенчмарке Baymard вообще не показывают сводку.**

Сценарий отказа из тестов: 5 фильтров дают дюжину результатов; ничего не подошло; пользователь забыл, что
фильтровал три минуты назад, и решил, что нужного нет вовсе.

**Правила** `[консенсус]` (Baymard, Carbon, P&P, Polaris, Friedman):

1. **Три канала одновременно** [S18]:
   - активные значения остаются отмеченными **в исходном контексте** (внутри меню/секции);
   - на свёрнутом контроле — **индикатор с числом** («Фильтры (3)») и жирная подпись;
   - **отдельная сводка чипами**.
2. **Место чипов — над результатами** [V:GCJ6k3tD50A, 1:17:20] `[практика]`. Механизм поломки при размещении в
   левой колонке разобран прямо: растущий блок чипов меняет высоту сайдбара, позиции фильтров съезжают, и после
   каждого клика приходится заново наводить мышь. Baymard допускает три места (над результатами, над панелью
   фильтров, под горизонтальной панелью) и отмечает, что тестирование не выявило лучшего, **но у варианта «над
   панелью фильтров» есть тот же дефект: чипы выталкивают сами фильтры вниз** [S38].
3. **Перенос строк планируется заранее**: «часто чипы переносятся на 2 или даже 3 строки. Больше — стоит сделать
   "показать ещё / свернуть", чтобы прокрутка страницы не стала неприятной» [S18]. Baymard: лишние ряды **сдвигают
   список вниз**, поэтому второй и последующие ряды обрезают [S38].
4. **Показывать только число применённых фильтров без самих значений — антипаттерн**: «нет визуального напоминания
   о контексте списка», пользователю приходится открывать панель [S38].
5. **Свёрнутая панель фильтров обязана**: показать число применённых и дать **сброс без разворачивания** [S8]
   `[система]`.
6. **Сброс на двух уровнях**: у каждой категории — «очистить категорию», глобально — «сбросить всё» [S8], [S18].
   «Кнопка "Сбросить всё" — ещё и напоминание, что фильтры вообще применены» [S18].
7. **Значение не исчезает из панели после выбора**: 97% сайтов бенчмарка это соблюдают [S38].
8. **Текст чипа** [S15] `[система]`:
   - имя значения без категории, если оно однозначно: «Выполнен», не «Статус: Выполнен»;
   - с категорией, если значение неоднозначно: «Ширина: 90 см», «Высокий риск», не просто «90 см» и «Высокий»;
   - **нельзя показывать категорию у части чипов и не показывать у других** — «непоследовательно и трудно
     интерпретировать» [S38];
   - если тип нужен, ставить его **над значением** мелким серым (floating label), чтобы чип не расширялся и тип
     читался как вторичный [S38];
   - **чипы одной категории группируются вместе**: «(Не выполнен, Выполнен)», не «(Не выполнен) (Выполнен)» [S15];
   - если выбраны все значения категории — обрезать **посередине**: «Оплачен, ча… не оплачен» [S15].
9. Бюджет символов на чип решается заранее: «перечислить "Аристотель, Сократ, Платон, Эпикур" с лимитом 40
   символов — или писать "Авторы (4)" и дать открыть дропдаун» [S18].
10. Правило спецификационных vs визуальных каталогов [S38]: спецификационные (техника, оборудование) — **с типом
    фильтра**, визуальные (одежда, изображения) — без.
11. При inline-фильтрах (на уровне одного блока) **отдельная сводка не нужна** — они и так контекстны [S18].

### 3.7 Счётчики результатов и профилактика нуля

`[практика]` + `[исследование]`:
1. **Общее число найденного показывается всегда** — «это обратная связь о том, насколько эффективно сузился
   список» [S18]; в поиске — включая ноль [S9].
2. **Счётчик у каждого значения фильтра** — главное средство против нулевого результата: «фасеты часто показывают
   число элементов под каждым фильтром и тем помогают избежать нулевых результатов» [S3]; «размещая индикаторы
   того, сколько результатов даёт каждое свойство и значение, вы снижаете шанс, что пользователь осознанно выберет
   вариант, ведущий к нулю» [S18].
3. **Дизейбл конфликтующих значений** — второй механизм: «умные фильтры определяют, что значение конфликтует с уже
   выбранным, и делают опцию недоступной» [S18]. Дизейбленное значение остаётся видимым (иначе список прыгает).
4. Ограничение: при batch-фильтрации давать живые счётчики трудно — «задержка показа результатов затрудняет
   непрерывную обратную связь о доступности фильтров и числе результатов» [S3]. Компромисс: счётчики
   пересчитываются при открытии категории, а не после каждого клика.
5. Формат: «Статус: Просрочен (128)». Если счётчик дорог, показывать хотя бы наличие/отсутствие.

### 3.8 Логика И/ИЛИ, исключение, продвинутые фильтры

**Стандартная логика** `[практика]`: внутри одной категории значения объединяются по **ИЛИ** (статус = новый
**или** в работе), между категориями — по **И** (статус ∈ {…} **и** менеджер = Иванов). Это то, что ожидает
большинство пользователей, и то, что делают фасетные системы по умолчанию.

Правила:
1. Если реализована именно эта логика — **объяснять её не надо**; если реализована другая (И внутри категории:
   «объект имеет все выбранные теги») — **объяснять обязательно**, коротким текстом у категории («Показать объекты,
   у которых есть **все** выбранные теги»).
2. Там, где обе логики осмысленны (теги, метки, участники), дать **переключатель «любой из / все из»** у категории.
3. **Явное исключение**: приём с тремя состояниями значения — не включено → включено → **исключено** — полезен для
   «всё, кроме двух категорий»; в наблюдении Friedman он реализован отдельной иконкой у каждого значения и «не
   очевиден без объяснения» [V:GCJ6k3tD50A, 1:15:19] `[практика]`. Вводить только с подписью и легендой.
4. **Продвинутые фильтры как формулы** — для технических пользователей [S18]: пользователь управляет и отношением,
   и логикой; условия складываются в if/then; обязателен выбор «результаты должны соответствовать **всем / любому /
   ни одному** из условий». Примеры реализации: Google Drive (UI-форма), Jira (UI-форма **и** текстовый синтаксис)
   [S20].
5. Если есть текстовый синтаксис, он **двусторонний**: собранное в UI показывается как текст, и наоборот. Иначе
   пользователь не научится.

### 3.9 Порядок, именование и число фильтров

**Порядок категорий** [S4] `[исследование]`: «категории, стоящие выше в списке, получают больше внимания».
Правило: **общие и высокоуровневые сверху, специфические снизу**. Исключение — когда одна специфическая
характеристика решающая (объём стиральной машины важнее цвета), её поднимают. «Релевантность для пользователя —
финальный критерий приоритета.»

**Порядок значений внутри категории** [S4], [S18]:
- числовые — от меньшего к большему (цены, суммы) либо наоборот (рейтинг);
- словесные — **по алфавиту, если пользователь знает названия** (бренды, города);
- иначе — по приоритету пользователя; «статусы лучше упорядочивать по срочности, а список локаций — по алфавиту»
  [S18];
- при большом числе значений — алфавит плюс поиск внутри категории.

**Именование** [S4] `[исследование]`:
- **appropriate** — набор категорий настраивается под тип объекта; отсутствие критичного фильтра пользователи
  замечают и жалуются;
- **predictable** — пользователь должен предсказать, какие значения внутри. Антипример из теста: категории
  «Item Type» и «Style» не взаимоисключающие, участница искала «сандалии» в «Style», нашла только «Gladiator» и
  «Flip Flop» и ушла в поиск. Вывод: **избегать расплывчатых ярлыков** («Тип элемента», «Прочее»); лучше —
  иерархия значений внутри одной категории;
- **free of jargon** — антипример: категория «Поведение» со значениями «Фиолетовый», «Оранжевый», «Зелёный»
  (внутренний код). Для неизбежно сложных значений — иконка «i» с объяснением рядом с названием категории;
- **prioritized** — см. выше.

**Сколько показывать сразу:**
- Polaris: «не больше **2–3 продвинутых (promoted)** фильтров» в компактной строке [S15] `[система]`.
- Baymard: горизонтальная панель ломается **после 6–8 типов** [S39] `[исследование]`.
- Внутри категории: показывать несколько значений по умолчанию и «Показать все» [S18]; при длинном списке —
  поиск внутри категории с автофокусом.
- Остальные фильтры — под «Ещё фильтры», но помнить: **кнопку «Все фильтры» участники тестов пропускают** [S39],
  поэтому под ней не должно быть частых фильтров.

**Стартовое состояние категории** [S8] `[система]`: всё снято или всё выбрано — по тому, что типичнее. «Если
пользователь обычно хочет исключить один-два критерия, все фильтры выбраны на старте. Если обычно хочет видеть
только один критерий — все сняты.» При нескольких категориях старт может различаться.

### 3.10 Сохранённые фильтры и состояние в URL

- **Состояние в URL** — обязательное требование: `?q=&status=&assignee=&sort=&page=&per_page=` (плюс набор
  колонок и вид). Проверяется автотестом: применить условия → скопировать URL → открыть в новой вкладке →
  состояние совпадает.
- **Сохранённые запросы**: «пользователи регулярно приходят на страницу и повторяют одну и ту же
  последовательность фильтров. Это лишние усилия и потерянное время, если делать это вручную снова и снова» [S18]
  `[практика]`. Реализация — как сохранённые виды таблицы (`01-data-tables.md` §10.2): имя, переименование,
  дублирование, удаление, личные и общие.
- Возврат из карточки объекта восстанавливает и фильтры, и позицию (`01-data-tables.md` §6.4).
- Автоматически применённые фильтры (переход по промо-ссылке, по вкладке-виду, по клику в дашборде) **обязаны быть
  видимыми чипами**: иначе «пользователи неверно поймут диапазон и тип того, что есть в системе» [S38].

### 3.11 Фильтры на дашборде и в аналитике

Отличие: на дашборде фильтруется **не число элементов, а объём и срез данных** для графиков — период, аудитория,
набор метрик, диапазоны значений [S18].

Правила `[практика]`:
- **Период — один на весь экран**, в шапке (`../03-layout-placement/01-page-anatomy-templates.md` §3.2), кроме
  случаев, когда у блоков заведомо разные структуры данных — тогда фильтры инлайновые, на уровне блока [S18].
- Глобальные фильтры дашборда синхронизируют все блоки; частичная синхронизация («один график живёт своей
  жизнью») — источник ошибок интерпретации.
- Мощный приём аналитических экранов — **brushing**: выделение подмножества в одном графике подсвечивает его во
  всех остальных [S28].
- Подробнее — `03-dashboards-and-kpi.md`.

## 4. Сортировка как часть поиска

Устройство контрола сортировки в таблице — `01-data-tables.md` §5. Здесь — выбор умолчания и когда давать выбор.

**Сортировка по умолчанию по типу списка** `[консенсус]`:

| Тип списка | По умолчанию | Почему |
|---|---|---|
| Лента событий, журнал, история | Новые сверху | Смысл списка — «что произошло недавно» |
| Очередь работы (заявки, задачи, модерация) | **Срочность**: ближайший дедлайн, просроченные сверху | «Entries most needing action» [S17] |
| Список объектов (заказы, документы, клиенты) | Последнее изменение или создание | «Starting with the most recently created items» [S24] |
| Справочник, номенклатура, настройки | Алфавит по первой колонке | Предсказуемость поиска глазами |
| Результаты поиска | Релевантность | Иначе поиск теряет смысл |
| Результаты фильтрации без запроса | Как у списка объектов | Релевантности нет |

**Когда давать пользователю выбор сортировки** `[практика]`:
- если разные задачи выигрывают от разных порядков: «support sorting if the list can be long, and **especially if
  different merchant tasks benefit from different sort orders**» [S14];
- если в списке есть хотя бы одна количественная колонка, по которой осмысленно ранжировать (сумма, срок, объём);
- **не давать** выбор там, где порядок содержательно единственный (шаги процесса, приоритетная очередь с
  фиксированным правилом) — иначе пользователь получит бессмысленные срезы.

**Сортировка по релевантности** должна быть объяснима: если пользователь может переключиться на «по дате» и
обратно, у пункта «по релевантности» должно быть понятное имя и он должен быть первым.

**Смена сортировки не должна сбрасывать фильтры и не должна уводить на первую страницу без предупреждения**
(на практике — уводит всегда; тогда это сообщается счётчиком «показаны 1–20 из 312»).

## 5. Командная палитра и быстрые переходы

### 5.1 Что это и когда нужна

Определение: единая клавиатурная поверхность, из которой запускают **команды, переходы и недавние объекты**
[S42]. Вызов — Cmd/Ctrl+K; режим команд обычно отделяется префиксом (`>` в GitHub и VS Code) [S43].

**Когда уместна** `[практика]`:
- продукт **насыщен действиями**, а не только контентом;
- пользователи работают в нём ежедневно и подолгу;
- пространство действий растёт быстрее, чем навигация («breaks down as the action space grows» [S42]);
- есть смежные инструменты с той же конвенцией (редакторы кода, дизайн-инструменты) — перенос привычки.

**Когда вредна** [S42] `[практика]`:
- «Use a simpler visible navigation or single-page flow when the product surface is still small» — маленький
  продукт;
- «Avoid advanced interaction patterns if the team cannot support their state complexity well» — команда не
  потянет состояние и доступность (сложность реализации оценена как высокая);
- **«Do not introduce hidden power-user behavior before the plain path is already strong»** — палитра поверх
  сломанной навигации не чинит её, а прячет.

### 5.2 Что туда класть

Три варианта компоновки [S42] `[практика]`:
- **универсальный лаунчер** — переходы + создание + настройки в одной палитре (когда много разделов и много
  команд);
- **контекстная палитра** — только действия текущего объекта (когда глобальный поиск уже есть отдельно);
- **recent-first** — недавние команды и объекты выше результатов поиска (когда важнее скорость повтора, чем
  полнота).

Обязательные части: триггер (горячая клавиша **и видимая кнопка**), поле ввода с удержанием фокуса,
**сгруппированные результаты** (команды / страницы / объекты / недавнее — разными группами), элемент результата с
подписью, пояснением и шорткатом; желательно пустое состояние [S42].

Дополнительно `[практика]`:
- у каждой команды показывается её горячая клавиша — палитра **обучает** шорткатам;
- команды называются так же, как соответствующие кнопки в интерфейсе (иначе поиск по палитре не находит их);
- недоступные по правам команды не показываются;
- деструктивные команды из палитры требуют подтверждения так же, как из интерфейса.

### 5.3 Находимость — главная проблема

Единственные публичные данные о принятии `[практика]` [S43]:
- GitHub представил командную палитру в октябре 2021 как публичную бету; **три с половиной года она оставалась
  бетой и была выключена по умолчанию**, включалась в диалоге Feature Preview; в феврале 2024 её отключили даже у
  тех, кто включил;
- 16 июля 2025 GitHub объявил об удалении **«из-за низкого использования»**; через неделю решение отменено после
  сотен протестных комментариев: «ваша обратная связь показала, насколько эта функция встроена в рабочие процессы
  многих разработчиков»;
- типичный комментарий: «я узнал об этой функции пару недель назад и теперь пользуюсь постоянно; жаль, что не
  знал раньше»;
- GitHub классифицирует палитру **как функцию доступности**;
- палитра не равна поиску в шапке: «у командной палитры нет замены. Поиск наверху — дробовик по сравнению с
  лазером палитры».

**Вывод:** низкое использование объясняется находимостью, а не отсутствием ценности. Отсюда правила:
1. Палитра **включена по умолчанию**, а не спрятана в настройках.
2. Есть **видимый триггер** — кнопка или подсказка с шорткатом в поле поиска («Поиск… ⌘K»).
3. Подсказка показывается один раз при первом входе и вызывается снова из справки.
4. Шорткат стандартный (Cmd/Ctrl+K) и не конфликтует с браузерным; настраиваемость — плюс.
5. Метрика успеха — не доля пользователей, а доля **опытных** пользователей и время выполнения типовых переходов.

## 6. Контракт поведения (что проверяет автотест)

Каталог ошибок ИИ фиксирует, что фильтрация и поиск массово проваливают функциональные тесты (F4.2 и общий провал
Functional Testing). Ниже — проверяемый контракт; каждый пункт формулируется как тест.

| № | Проверка | Как проверить |
|---|---|---|
| 1 | Поиск запускается и меняет набор | Ввести запрос → число результатов изменилось или показано «ничего не найдено» |
| 2 | Запрос отражён в URL | После поиска URL содержит запрос; открытие URL в новой вкладке воспроизводит результат |
| 3 | Каждый фильтр меняет набор | Для каждого фильтра: применить → счётчик изменился |
| 4 | Активные фильтры видны чипами | После применения в DOM есть элементы-чипы с названиями значений |
| 5 | Чип снимается | Клик по «×» на чипе → условие снято, набор пересчитан, чип исчез |
| 6 | Есть глобальный сброс | Кнопка «Сбросить всё» присутствует при хотя бы одном активном условии и возвращает исходный набор |
| 7 | Счётчик результатов существует | На экране есть число найденного; при нуле — тоже |
| 8 | Ноль результатов имеет действие | В пустом состоянии есть хотя бы один интерактивный элемент (сброс, изменить запрос) и текст длиннее одной строки |
| 9 | Комбинация фильтров работает | Применить два условия из разных категорий → набор соответствует И между ними |
| 10 | Состояние переживает переход | Применить условия → открыть объект → «назад» → условия, сортировка и страница на месте |
| 11 | Сортировка работает | Кликнуть заголовок → порядок изменился, `aria-sort` обновился |
| 12 | Фильтры не ломают пагинацию | После применения номер страницы сброшен на 1, а счётчик показывает новый общий объём |
| 13 | Нет дублирования | Один и тот же фильтр не представлен одновременно в двух местах (панель + чипы — это не дубль; панель слева + та же панель сверху — дубль) |
| 14 | Клавиатура | Весь блок проходится с клавиатуры: поле → фильтры → значения → применить → результаты |

Дефект F4.2 закрывается пунктами 1–12; дефект F1.1 (выдуманные маршруты) — тем, что каждый чип и каждый пункт
сортировки соответствуют существующему параметру запроса.

## Частые ошибки

**Поиск**

1. Поиск сделан вместо того, чтобы починить навигацию [S20].
2. Иконка вместо поля там, где поиск — частая задача.
3. Плейсхолдер «Введите текст» вместо названия области поиска [S15], [S20].
4. Подпись над полем поиска, дублирующая иконку [S9].
5. Подсказки, ведущие в ноль или в нерелевантные результаты [S21].
6. Подсветка не того фрагмента: подсвечено введённое там, где система дописывает [S21].
7. Обогащённые подсказки с картинками вместо простых текстовых [S22].
8. Блоки подсказок меняют состав и место от запроса к запросу [S22].
9. Список подсказок перестраивается в момент клика [S20].
10. Нет числа результатов; нет числа по областям [S9].
11. «Ничего не найдено» мелким серым над списком рекомендаций [S23].
12. «Ничего не найдено» без поля с сохранённым запросом и без предложений [S23].
13. Шутка на экране неудачного поиска [S23].
14. Нечёткий поиск «исправляет» введённый идентификатор.
15. Поиск не понимает форму записи (пробелы, дефисы, регистр, ведущие нули).

**Фильтры**

16. Фасеты построены там, где хватало двух фильтров [S2].
17. Панель фильтров закрывается после выбора одного значения [V:GCJ6k3tD50A].
18. Выбор нового фильтра сбрасывает предыдущие [V:GCJ6k3tD50A].
19. Страница прокручивается наверх, пока пользователь работает с фильтрами [S3].
20. Мгновенная фильтрация при ответе сервера в несколько секунд [S3].
21. Мерцание отдельных элементов вместо приглушения всей области результатов [S3].
22. Чипы применённых фильтров внутри левой колонки — сдвигают сами фильтры [V:GCJ6k3tD50A], [S38].
23. Показано только число применённых фильтров, без значений [S38].
24. Свёрнутая панель без индикатора, что внутри есть выбор [S8].
25. Нет глобального «Сбросить всё» [S8], [S18].
26. Категория фильтров с расплывчатым названием («Тип элемента», «Прочее») [S4].
27. Две категории, которые не взаимоисключают друг друга [S4].
28. Внутренний жаргон в значениях фильтра [S4].
29. Нет счётчиков у значений, и пользователь регулярно попадает в ноль [S3], [S18].
30. Значение фильтра исчезает из панели после выбора [S38].
31. Тип фильтра показан у части чипов и не показан у других [S38].
32. Булев фильтр упакован в дропдаун с двумя значениями [S18].
33. Диапазон задаётся только слайдером, без полей ввода.
34. Датапикер без пресетов или без произвольного диапазона [S18].
35. Продвинутые фильтры вынесены наверх, но исчезли из основной панели [S40].
36. Фильтры не отражены в URL — нельзя поделиться результатом.
37. Атрибут виден в записи, но по нему нельзя фильтровать [S18].
38. Фильтры слева плюс те же фильтры чипами сверху плюс поиск в шапке — три способа сузить список
    (`../03-layout-placement/04-placement-conventions-and-redundancy.md` §11).

**Характерные для ИИ-генерации** (`../11-ai-generated-ui/01-failure-modes-catalog.md`)

39. **F4.2**: панель фильтров нарисована, но ни один фильтр не меняет набор данных.
40. **F4.3**: кнопка «Применить» без обработчика; «Сбросить всё» не сбрасывает.
41. **F6.3**: фильтры теряются при переходе в объект и обратно — самый массовый измеренный дефект.
42. **F4.4**: мультиселект реализован радиокнопками (или наоборот).
43. **F8.3**: на одном экране фильтр чипами, на другом — селектами; форматы дат разные.
44. **F5.2**: «Ничего не найдено» без действия и без сброса.
45. **F1.1**: значение фильтра ссылается на несуществующий параметр запроса.
46. **F12.2**: демо-данные подобраны так, что любой фильтр даёт результат; нулевой сценарий не проверен.

## Чек-лист

Поиск:
1. Решено, нужен ли глобальный поиск, или достаточно локального?
2. Проверено, что поиск не компенсирует плохую навигацию?
3. Поле видимое, без подписи, с конкретным плейсхолдером и доступным именем?
4. Выбран режим (basic / active / focused) и он соответствует объёму и скорости?
5. Подсказки появляются с 3-го символа, каждая даёт результаты, подсветка соответствует механизму?
6. Простые текстовые подсказки не заменены на карточки с картинками?
7. На странице результатов есть число найденного, группировка по типам и подсветка совпадений?
8. Точный идентификатор находится без нечёткого «исправления»?
9. Сценарий «ничего не найдено» — заметный, с полем правки запроса и предложениями?
10. Запрос и область живут в URL?

Фильтры:
11. Обосновано, фильтры это или фасеты?
12. Для каждого атрибута записи есть ответ, фильтруется он, сортируется или нет?
13. Размещение выбрано по таблице §3.3 (число типов, нужны ли счётчики, влияют ли на всю страницу)?
14. Тип контрола выведен из типа данных, а булевы — без дропдаунов?
15. Решено «мгновенно / по кнопке / per-filter» по таблице §3.5 и по реальному времени ответа?
16. Выбор фильтра не закрывает панель, не сбрасывает другие и не прокручивает страницу?
17. Активные условия видны чипами над результатами и снимаются по одному?
18. Есть сброс категории и глобальный сброс?
19. Свёрнутая панель показывает число применённых и даёт сброс?
20. Есть счётчик результатов и (по возможности) счётчики у значений?
21. Конфликтующие значения дизейблятся, а не исчезают?
22. Логика И/ИЛИ соответствует ожиданию, а нестандартная — объяснена?
23. Категории отсортированы «общие сверху», значения — по приоритету или алфавиту по правилу §3.9?
24. Ярлыки без жаргона, категории взаимоисключающие?
25. Частые фильтры не спрятаны за «Ещё фильтры»?
26. Стартовое состояние категории (всё выбрано / всё снято) выбрано осознанно?
27. Фильтры и сортировка в URL; есть сохранённые запросы, если выборка повторяется?

Сортировка и палитра:
28. Сортировка по умолчанию соответствует типу списка и записана с обоснованием?
29. Выбор сортировки дан там, где разные задачи требуют разного порядка?
30. Если есть командная палитра: включена по умолчанию, имеет видимый триггер, группирует результаты и показывает
    шорткаты?
31. Палитра не подменяет собой работающую навигацию?

Контракт:
32. Проходят ли все 14 проверок §6?

## Открытые вопросы и противоречия

1. **Фильтры сверху или слева** `[спорно]`. Friedman: «фильтры над результатами обычно лучше, чем в левой колонке»
   [V:GCJ6k3tD50A]. Baymard: горизонтальная панель ломается после 6–8 типов, значения не видны, «All Filters»
   пропускают; сайдбар — «проверенная и привычная реализация» [S39]. Разрешение §3.3 по числу типов — мой синтез.
   Кроме того, в файле волны 1 (`../03-layout-placement/04-placement-conventions-and-redundancy.md` §6) порог
   сформулирован как «до 4–5 сверху»; Baymard даёт 6–8. Расхождение небольшое, но его стоит свести в волне 4.
2. **Место сводки применённых фильтров** `[спорно]`. Baymard: три места равноценны, тестирование не выявило
   лучшего [S38]. Friedman: чипы в левой колонке ломают прицел мыши, механизм разобран [V:GCJ6k3tD50A]. База берёт
   позицию Friedman, отмечая, что у Baymard это не измерялось напрямую.
3. **Пустая ячейка/значение «—»** — см. `01-data-tables.md` §3.7; на чипах и в фильтрах та же проблема не возникает.
4. **Порог «3 символа» для подсказок** взят из практической статьи [S20]; исследования, подтверждающего именно
   это число, я не нашёл. Для коротких идентификаторов порог должен быть меньше.
5. **Данные о принятии командной палитры** — единственный источник журналистский [S43]; публичных исследований
   использования (Linear, Raycast, Superhuman) найти не удалось: компании публикуют маркетинговые материалы без
   цифр. Пробел, который стоит закрыть в волне 3 или в синтезе.
6. **Логика И/ИЛИ** описана как практика: ни одного исследования о том, как пользователи понимают комбинацию
   фильтров, в прочитанных источниках нет. Приём «явное исключение» имеет один источник и помечен как
   неочевидный автором.
7. **Не удалось прочитать**: Baymard «Sorting tool design» и «Allow applying multiple filter values» (пейволл —
   страницы вернули заглушку), NN/g «Mobile Faceted Search with a Tray» (не запрашивалась из-за лимитов),
   отчёт NN/g «Ecommerce Search (4-е издание, 80 гайдлайнов)» — платный. Часть количественных данных по фильтрам
   и сортировке осталась за пределами базы.
8. **Не проверено**: «как часто пользователи приложений начинают с поиска» (вопрос из отчёта B). Прямых данных по
   рабочим приложениям не нашлось; есть только наблюдение Baymard для ecommerce — «первое действие большинства
   участников при попадании в список — искать фильтры» [S40], то есть фильтры, а не поиск. Переносить это на
   админки нельзя.
