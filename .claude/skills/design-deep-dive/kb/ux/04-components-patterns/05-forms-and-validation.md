## Выжимка для агента

1. **Форма — самый слабый компонент у всех генеративных моделей.** Ни одна модель в FullFront не превысила 0.60 по
   компоненту Form; в WebGen-Bench операции с формами — самая массовая подкатегория функциональных тестов (134 из 339)
   при общей точности 17.1%. Поэтому правила ниже — обязательные, а не рекомендательные. → §1 `[исследование]`
2. **До генерации заполни контракт формы**: поле → тип контрола → обязательность → формат и маска → правила валидации
   → текст ошибки → состояния. Без контракта модель делает разметку без логики. → §1.1 `[консенсус]`
3. **Соблюдение базовых правил форм почти удваивает долю безошибочных отправок**: 78% против 42% (Seckler et al.,
   CHI 2014). → §0 `[исследование]`
4. **Одна колонка.** Несколько колонок «прерывают вертикальный импульс движения вниз по форме»; люди пропускают поля и
   потом не понимают, почему кнопка не срабатывает. → §2.1 `[консенсус]`
5. **Исключение из одной колонки одно: поля, образующие одно значение** (день/месяц/год, город/регион/индекс,
   номер карты/срок/CVV). Критерий: это части одного ответа, а не разные вопросы. → §2.2 `[консенсус]`
6. **Ширина поля равна ожидаемой длине ввода.** Индекс — узкое, адрес — широкое. Данные NN/g: 99,9% названий городов
   у 2130 человек укладываются в 19 символов → 19 символов и есть разумная ширина поля «город». → §2.3 `[исследование]`
7. **Подписи над полем.** Поле и подпись попадают в одну фиксацию, форма легче сканируется, помещаются длинные подписи
   и переводы. Подписи слева — только при дефиците вертикали. → §3.1 `[консенсус]`
8. **Подпись всегда ближе к своему полю, чем к соседнему.** Равноудалённая подпись — источник ошибок; это единственный
   признак принадлежности. → §3.1 `[консенсус]`
9. **Плейсхолдер не подпись и не хранит ничего важного.** Семь измеренных вредов, включая «поле с текстом выглядит
   заполненным и его пропускают». Требования к паролю, формат, пример — снаружи поля и постоянно. → §3.2 `[исследование]`
10. **Помечай обязательность так, чтобы её было видно до нажатия кнопки.** Правило по большинству: помечать меньшую
    группу — «(обязательное)» или «(необязательное)». Инструкцию «все поля обязательны» вверху формы не читают.
    → §3.4 `[спорно]`
11. **Прощающий ввод**: принимай пробелы, дефисы, скобки, точки, ведущие нули, названия месяцев словом; нормализуй
    сам. Данные GOV.UK: приём названий месяцев резко сократил число ошибок. → §3.5 `[исследование]`
12. **Inline-валидация окупается на полях, где ответ неочевиден**: +22% успешности, −22% ошибок, −42% времени,
    −47% зрительных фиксаций (LukeW + Etre, 22 участника). → §4.1 `[исследование]`
13. **По умолчанию проверять по отправке (сводка + сообщения у полей); там, где inline-валидация оправдана (§4.1, §4.3), —
    по уходу из поля, а не по мере набора.** «After» быстрее «while» на 7–10 секунд; «before and while» даёт худшее
    время, больше всего ошибок и худшую удовлетворённость. → §4.2, §4.3 `[исследование]`
14. **Машина состояний поля: reward early, punish late.** До порога символов — проверка только на blur; после порога —
    проверка идёт; очевидная ошибка показывается сразу; успех ставится только после перехода дальше; при правке
    невалидного поля проверка идёт на лету и ошибка снимается сразу. → §4.2 `[практика]`
15. **Успех показывать только для сложных полей** (доступность имени, сила пароля). «Не показывайте успех там, где
    единственное требование — заполненность.» → §4.7 `[консенсус]`
16. **Сообщение об ошибке — над полем (между подписью с подсказкой и полем), рядом и видно, пока человек чинит.**
    Это снимает нагрузку с рабочей памяти; под полем его перекрывают клавиатура и выпадающие списки. → §4.4 `[консенсус]`
17. **Сводка ошибок вверху — вместе с сообщениями у полей, никогда вместо них.** Фокус клавиатуры переводится на
    сводку; формулировки в сводке дословно совпадают с формулировками у полей; каждая строка — ссылка на поле.
    → §4.5 `[консенсус]`
18. **Не показывать ошибки тултипами**: иконку-алерт не замечают, человек не понимает, что сообщение есть.
    → §4.4 `[консенсус]`
19. **Не блокировать кнопку отправки до нажатия.** Disabled сообщает, что проблема есть, но не ведёт к решению, и при
    сбое скрипта запирает человека — «гарантированные 100% отказа». → §5.2 `[спорно]`
20. **Блокировать кнопку — только после нажатия**, чтобы предотвратить двойную отправку. → §5.3 `[консенсус]`
21. **Одна кнопка отправки на форму.** Не делать «Сохранить» у каждой секции, если секции не сохраняются независимо и
    это не видно. → §5.1 `[консенсус]`
22. **Reset и «Очистить» не делать никогда** в обычной форме: жмут по ошибке вместо отправки. → §5.4 `[консенсус]`
23. **Никогда не терять введённое**: при ошибке, при возврате на шаг назад, при обновлении страницы, при отказе
    сервера. Это проверяемое требование, а не пожелание. → §6.1 `[консенсус]`
24. **Автозаполнение — первое, что чинят в форме**: минус ≥30% времени заполнения; проставь `autocomplete` каждому полю.
    → §6.2 `[практика]`
25. **Tab-порядок совпадает с визуальным.** Переключение клавиатура↔мышь стоит ≈400 мс в одну сторону; на форме
    адреса из 8 полей табуляция быстрее примерно втрое. → §6.2 `[практика]`
26. **Не больше 6–7 полей ввода на одном шаге**; выше порога резко растёт воспринимаемая сложность. → §2.5 `[практика]`
27. **Длинную форму режь по принципу «одна смысловая группа на страницу»**, а не «одно поле на страницу».
    → §2.5 `[консенсус]`
28. **Аккордеон-форма ускоряет заполнение примерно на 10 секунд против одностраничной при равной конверсии** — но
    переход между секциями должен идти по кнопке внутри секции, а не по клику в заголовок. → §7.1 `[исследование]`
29. **Условные поля показывай после родительского контрола**, а не до и не сбоку. → §7.2 `[система]`
30. **Не спрашивай одно и то же дважды.** WCAG 2.2 «Redundant entry»; поле «повторите email» бессмысленно — ~70%
    нетехнических пользователей просто копируют введённое. → §3.5, §7.7 `[практика]`
31. **Перед отправкой большой формы — страница проверки** со всеми ответами и ссылками «Изменить»; «Изменить»
    возвращает сразу на страницу проверки, а не прогоняет сценарий заново. → §7.8 `[система]`
32. **Вход: не раскрывать, что именно неверно — логин или пароль**; 5–10 попыток до блокировки; не сохранять
    введённый пароль при неудачной попытке. → §7.7 `[система]`
33. **Пароль: показывать правила заранее и держать их видимыми; дать снять маскировку; показывать силу, а не прогресс
    по галочкам.** Минимум 8 символов, максимума не ставить, периодическую смену не требовать. → §7.7 `[консенсус]`
34. **Не блокировать вставку** ни в одно поле, включая пароль; не ставить `maxlength` без сообщения о лимите.
    → §3.5 `[консенсус]`
35. **Серверная валидация обязательна всегда**, даже при клиентской: клиентскую можно обойти, JS может не загрузиться.
    → §4.6 `[консенсус]`
36. **Каждая кнопка формы имеет действие, состояние и результат.** Кнопок без обработчика быть не должно — это
    проверяется по DOM. → §5.1, §1.3 `[исследование]`
37. **Имя действия не меняется по ходу потока**: кнопка «Опубликовать» → тост «Опубликовано» → статус «Опубликовано».
    → §5.1 `[система]`
38. **Форма в модалке — до пяти полей и без прокрутки.** Больше — боковая панель или страница. → §7.5 `[консенсус]`

## 0. Почему это стоит денег

**Данные CHI 2014** [S1]: Seckler, Heinz, Bargas-Avila, Opwis, Tuch (Google) сравнили формы, соблюдающие базовые
правила юзабилити, и формы, их нарушающие. Результат: время заполнения значимо падает, а доля отправок **без ошибок с
первого раза — 78% против 42%**. `[исследование]`

**Данные inline-валидации** [S7]: LukeW совместно с Etre, 22 участника 21–49 лет, 6 вариантов формы регистрации,
рандомизированный порядок, айтрекинг. Лучший inline-вариант против контроля (валидация только по кнопке):
успешность **+22%**, ошибки **−22%**, удовлетворённость **+31%**, время **−42%**, число фиксаций **−47%**. `[исследование]`

**Данные для генерации** [S29], [S30]: в FullFront ни одна модель не превысила 0.60 по компоненту Form (Claude 3.7
Sonnet 0.50, GPT-4.1 0.60, Gemini 2.5 Flash 0.45). В WebGen-Bench «Form Operations» — самая массовая подкатегория
функциональных тестов, 134 из 339, при точности Functional Testing 17.1% у лучшей связки. Вывод: **форма — то место,
где генерация ломается чаще всего, и требования к ней должны быть исполнимыми и проверяемыми**. `[исследование]`

## 1. Контракт формы

Контракт заполняется **до** проектирования и до генерации. Он закрывает дефекты F4.1 («формы без валидации и без
сообщений об ошибках») и F4.4 («не тот тип контрола») из `../11-ai-generated-ui/01-failure-modes-catalog.md`.

### 1.1 Таблица контракта

| Поле | Тип данных | Контрол | Обяз. | Формат / маска | Мин–макс | Валидация | Текст ошибки | Значение по умолчанию | autocomplete |
|---|---|---|---|---|---|---|---|---|---|
| Название компании | строка | text input | да | любые символы | 2–120 | непусто, ≤120 | «Введите название компании» | — | `organization` |
| Страна | перечисление | комбобокс с поиском | да | — | — | значение из справочника | «Выберите страну из списка» | по IP, если >90% клиентов из одной страны | `country-name` |
| Индекс | строка | text input, ширина 8 симв. | зависит от страны | цифры и буквы, пробелы игнорировать | по стране | по маске страны | «Индекс должен состоять из 6 цифр» | — | `postal-code` |
| Дата начала | дата | три поля день/месяц/год + календарь | да | принимать названия месяцев словом | не раньше сегодня | не в прошлом | «Дата начала не может быть в прошлом» | сегодня | — |
| Уведомления | булево | переключатель (мгновенно) | нет | — | — | — | — | включено | — |

Правила заполнения:
1. **Одна строка — одно поле формы.** Если поле составное (ФИО, адрес), в контракте оно раскладывается на реальные
   поля, и рядом фиксируется, почему оно разделено (см. §2.2).
2. **Столбец «Контрол» заполняется по таблице выбора из `06-input-controls.md` §1**, а не по привычке.
3. **Столбец «Текст ошибки» заполняется заранее**, а не оставляется на реализацию: это единственный способ не получить
   «Произошла ошибка». Формулировки — волна 3, `../07-ux-writing/`.
4. **Пустая ячейка «Значение по умолчанию» — тоже решение**, и его нужно обосновать (см. §6.3).

### 1.2 Профилирование поля: десять вопросов

Процедура Виталия Фридмана [V:qktwIWZNFY4, 38:32–41:36] `[практика]`: дизайнер и разработчик садятся вместе и до
вёрстки проходят по каждому полю. Протокол разговора ведётся в общем документе — «тогда критичные вопросы не всплывают
за два дня до релиза».

1. Обязательное или необязательное?
2. Можно ли предзаполнить (из профиля, из прошлого заказа, по IP, по геолокации)?
3. Какие символы допустимы? (ответ по умолчанию — любые)
4. Нужен ли адаптивный пример: для шведских клиентов «например, Volvo», для американских «например, Ford»?
5. Минимальная и максимальная длина? **Максимальная задаёт ширину поля.**
6. Нужна ли маска и автоформатирование?
7. Правила валидации и момент проверки?
8. Что писать в ошибке?
9. Нужна ли подсказка «зачем это поле»?
10. Что делать, если значения нет в справочнике (игнорировать, показать ошибку, дать ссылку на поддержку)?

### 1.3 Проверяемые требования к сгенерированной форме

Каждое проверяется автоматически по DOM или сценарием в headless-браузере:

| # | Требование | Как проверить |
|---|---|---|
| 1 | У каждого поля есть `<label>`, связанная с ним | DOM: `input` без `id`, на который ссылается `label[for]`, и без `aria-label`/`aria-labelledby` |
| 2 | Форма обёрнута в `<form>` | DOM |
| 3 | У каждого поля есть `autocomplete` (или явное обоснование его отсутствия) | DOM |
| 4 | Отправка пустой формы даёт сообщение и переводит фокус | сценарий |
| 5 | Отправка заведомо невалидной формы даёт сообщение у каждого проблемного поля | сценарий |
| 6 | Введённое сохраняется после ошибки | сценарий: заполнить, сломать одно поле, отправить, проверить остальные |
| 7 | Кнопка отправки не `disabled` до первого нажатия | DOM |
| 8 | Повторное нажатие кнопки во время отправки не создаёт второй запрос | сценарий с перехватом сети |
| 9 | Порядок табуляции совпадает с визуальным | сценарий: пройти Tab и сравнить с DOM-порядком |
| 10 | Нет плейсхолдера, дублирующего подпись | DOM: сравнить `placeholder` и текст `label` |
| 11 | Нет поля «повторите email»/«повторите пароль» без обоснования | DOM |
| 12 | Нет кнопки без обработчика, `href` и `type="submit"` | DOM |

## 2. Раскладка

### 2.1 Одна колонка

`[консенсус]` — на этом сходятся NN/g [S1], Carbon [S19] (прямо ссылаясь на исследование NN/g), Primer [S22],
Фридман [V:qktwIWZNFY4, 47:41] и короткое видео NN/g [V:nA7ildepUJU, 01:05].

Механизмы, названные источниками:
- «Несколько колонок **прерывают вертикальный импульс** движения вниз по форме; вместо того чтобы заставлять человека
  визуально переориентироваться, держите его в потоке» [S1].
- **Каждое поле — отдельный вопрос; вопросы задаются по одному, взгляд идёт единственным путём сверху вниз**
  [V:nA7ildepUJU].
- **Поля, вынесенные вбок, пропускают** — растёт риск незаполненного поля [V:nA7ildepUJU]; «люди пропускают поля и
  потом жмут на кнопку, которая "не работает"» [V:qktwIWZNFY4].
- Carbon: «многоколоночные формы чаще неверно интерпретируются» [S19].

**Формулировка правила:** по умолчанию одна колонка, поля друг под другом, действия внизу под последним полем.

### 2.2 Единственное исключение: части одного значения

Допустимо **2–3 поля в одной строке, если они образуют одно значение, а не разные вопросы** [S1], [S19],
[V:nA7ildepUJU]. Канонические группы:

- `[имя][отчество][фамилия]`
- `[номер карты][срок действия][код безопасности]`
- `[город][регион][индекс]`
- `[день][месяц][год]`

Критерий: **если человек произносит это одной строкой, это одно значение**. Обратный тест из [V:nA7ildepUJU]: «день,
месяц и год — три части одной даты, разносить их по трём строкам странно».

**Оговорка для энтерпрайза** [V:qktwIWZNFY4, 47:41] `[мнение]`: в формах, где полей объективно много, колонки
допустимы, но их нужно **развести далеко друг от друга**, чтобы взгляд не прыгал. Carbon формулирует то же иначе:
при большом числе полей вместо колонок лучше **многошаговая форма** [S19].

### 2.3 Ширина поля

**Ширина поля — это подсказка формата.** `[консенсус]`

- «Текстовые поля должны быть примерно того же размера, что и ожидаемый ввод: крайне ошибкоопасно, когда человек не
  видит свой ответ целиком» [S1].
- Данные [S1]: у 2130 участников конференции NN/g город проживания занимал от 3 символов (Leo, Indiana) до 22
  (San Pedro Garza Garcia, Mexico); **99,9% названий городов ≤19 символов → 19 символов — разумная ширина поля
  «город»**. Это готовый метод: взять реальное распределение длин значений и брать 99-й перцентиль.
- GOV.UK [S12]: **фиксированная ширина для контента известной длины** — поле индекса размером с индекс, поле телефона
  размером с телефон; по умолчанию поле тянется на всю ширину контейнера. Ширины GOV.UK рассчитаны под конкретное
  число символов и включают запас на иконки, которые вставляют браузеры (кнопка «показать пароль»).
- Фридман: **максимальная длина ввода, определённая при профилировании, и задаёт ширину** [V:qktwIWZNFY4, 56:48].

Антипример: все поля формы одинаковой ширины во всю колонку, включая «индекс» и «номер квартиры».

Числовые величины ширин по дизайн-системам — `../../ui/06-components-visual/`.

### 2.4 Группировка и заголовки групп

`[консенсус]` [S5], [S19], [V:nA7ildepUJU].

- **Группировать связанные поля.** Форма из 15 полей, разбитая на 3 группы по 4–6, воспринимается как три короткие
  формы [S5]. Заголовки групп не обязательны, но дают контекст.
- **Разделяет пространство, а не линии**: увеличенный интервал между группами — признак смены темы внутри формы
  (контактные данные / платёжные данные) [V:nA7ildepUJU, 01:45]. Правило «пространства между группами больше, чем
  внутри группы» — `../03-layout-placement/02-grid-spacing-density.md`.
- Ориентир Carbon [S19] `[система]`: если между полями 24px, то до первой группы и между секциями 32px; если между
  полями 32px — между секциями 40px; между последним полем и кнопками 48px. Полные шкалы —
  `../../ui/03-spacing-sizing/`.
- Семантика: группа радиокнопок или чекбоксов — `<fieldset>` с `<legend>`-вопросом [S9], [S12]; смысловая группа полей
  тоже размечается для скринридеров [S1].

### 2.5 Длина формы и разбиение на шаги

**Первое правило — сокращать, а не разбивать** [S1] `[консенсус]`: убирать поля, данные которых (а) можно вывести
иначе, (б) удобнее собрать позже, (в) можно не собирать вовсе. «Каждый раз, когда вы вырезаете поле, вы повышаете
конверсию». NN/g сократила свою форму с 6 полей до 2.

**Порог полей на шаг: 6–7** [V:qktwIWZNFY4, 33:27] `[практика]` — «выше порога резко растёт воспринимаемая сложность».
Сам автор допускает исключения для энтерпрайза; в базе это ориентир, не жёсткий предел.

**GOV.UK «one thing per page»** [S13] `[система]`: «Задавать по одному вопросу на страницу помогает пользователям
понять, что от них требуется, и сосредоточиться на конкретном вопросе и ответе». Фридман уточняет, что на практике это
означает **не одно поле на страницу, а один связный блок вопросов**: личные данные → доставка и оплата → платёж →
проверка [V:qktwIWZNFY4, 46:40].

Аргументы за многошаговую форму [V:qktwIWZNFY4]: людям проще; лучше работает на мобильных; проще обрабатываются
ошибки, ветвления, циклы и сохранение прогресса.

**Когда не дробить** — разрешение противоречия из отчёта W2 §5 `[спорно]`:

| Признак | Шаги (мастер, question pages) | Одна плотная страница с секциями |
|---|---|---|
| Частота задачи | редкая, разовая | ежедневная |
| Подготовка пользователя | неподготовленный, заходит однократно | эксперт, знает все поля |
| Порядок полей | задан, есть ветвления | произвольный |
| Нужно видеть уже сделанное | нет | **да** |
| Пример | подача заявления, регистрация, чекаут | карточка объекта в админке, настройки |

Обоснование правой колонки [V:P1CYZ65b5SA] `[мнение]`: «Сопротивляйтесь искушению использовать модалки и мастера в
сложных приложениях… чаще всего контекст — король»; сложность в экспертных инструментах не прячут. Обоснование левой —
GOV.UK [S13]. Подробно мастера — `../05-flows-journeys/02-task-flows-and-wizards.md`.

### 2.6 Порядок полей

`[консенсус]` [S1], [S22]:
1. **Стандартные последовательности не менять**: номер карты → срок → код безопасности; имя → фамилия.
2. **Порядок значений — по частоте**, самое частое первым, когда это уместно (доставка: стандартная → 2 дня → 1 день).
   Но у радиокнопок GOV.UK советует сортировать по алфавиту и менять порядок «с крайней осторожностью — это может
   закрепить предвзятость сервиса» [S9-radio].
3. **От известного к неизвестному, от лёгкого к трудному** — следствие данных LukeW [S7]: в первой половине формы
   (имя, email, страна, индекс) сообщения валидации заметили 30–50% участников, во второй (имя пользователя, пароль
   со строгими требованиями) — 80–100%. Люди уверены в начале и не уверены в конце.
4. Primer [S22]: сортировать по важности; держать связанные поля рядом; **держать рядом поля, требующие клавиатуры,
   чтобы человек не прыгал между клавиатурой и мышью**.
5. **Страна — одним из первых полей** [V:qktwIWZNFY4, 44:37] `[практика]`: от неё зависят до 18 параметров формы —
   валюта, формулировки и орфография подписей и кнопок, форматы дат и времени, маски, подсказки, «zip» против
   «postal code», city/state/county, плейсхолдеры, ширина поля индекса, расчёт налога и юридические требования
   (предотмеченный чекбокс рассылки допустим в США, но не в Калифорнии, Канаде и ЕС из-за GDPR).
6. **Email первым полем**, если нужна возможность напомнить о брошенной форме [V:qktwIWZNFY4, 1:11:03] `[практика]`.

## 3. Подписи, подсказки, плейсхолдеры

### 3.1 Размещение подписи

**Правило 1. Подпись обязательна у каждого поля и в большинстве случаев видима.** `[консенсус]` [S9], [S12], [S19],
[S22], [V:2juq00vrvl0, 23:39]. Единственный практический случай визуально скрытой подписи — **поле поиска**, и тогда
подпись всё равно передаётся скринридеру, а в макете это прямо отмечается для разработчика [V:2juq00vrvl0].

**Правило 2. По умолчанию подпись над полем.** `[консенсус]`
- NN/g [S5]: «Мы рекомендуем размещать подписи над соответствующими полями. Хотя это увеличивает общую длину формы,
  форму становится легче сканировать, потому что **поле и подпись попадают в одну фиксацию**. Верхнее размещение
  также позволяет использовать более длинные подписи, потому что горизонтальное место не ограничивает».
- Carbon [S19]: подписи сверху — единственная предлагаемая раскладка; преимущества — постоянный левый край, близость
  к полю, сканируемость, место под другие языки.
- M3 [S23]: подпись обязательна у каждого поля и всегда видима.

**Правило 3. Подпись ближе к своему полю, чем к любому другому.** `[консенсус]` [S1], [S5], [V:nA7ildepUJU, 00:37].
Это закон близости из гештальта; **проверять раскладку нужно именно на равноудалённость**: если подпись одинаково
далека от двух полей, это прямой источник ошибки [S1].

**Правило 4. Подписи слева — при дефиците вертикали и только одинаковой длины**, максимально близко к полю [S5].
Здесь источники расходятся `[спорно]`:
- NN/g [S5]: **выравнивание подписей по правому краю ухудшает сканируемость** (та же причина, что у меню, выровненных
  вправо).
- Фридман [V:qktwIWZNFY4, 48:41]: если подписи слева, **выравнивать их по правому краю**, чтобы сократить расстояние
  до поля.
- Разрешение для базы: левые подписи — вынужденная мера; в этом случае правое выравнивание лечит более тяжёлую
  болезнь (разрыв связи подписи и поля — антипример NN/g с формой пожертвований San Diego Zoo), но платит
  сканируемостью. **Если есть выбор — подписи сверху, и вопрос не возникает.**

**Правило 5. Текст подписи**: 1–3 слова (Carbon [S19]), не больше трёх слов (Primer [S22]), sentence case,
**без двоеточия** [S12], [S19]. Подпись — не вспомогательный текст.

### 3.2 Плейсхолдер

**Правило: плейсхолдер не заменяет подпись и не хранит ничего, что понадобится после начала ввода.**
`[исследование]` + `[консенсус]`.

Семь вредов [S2]:
1. Исчезающий текст нагружает кратковременную память; чтобы вспомнить требование, приходится стирать введённое и
   уходить из поля.
2. Без подписей нельзя проверить форму перед отправкой; автозаполнение браузера может подставить неверно, и это не видно.
3. При ошибке непонятно, как чинить — нужно возвращаться в каждое поле.
4. Раздражает при клавиатурной навигации: по Tab переходят быстро и не изучают поле заранее.
5. **Айтрекинг: взгляд притягивают пустые поля.** Заполненное поле ищут дольше или пропускают.
6. **Плейсхолдер принимают за подставленное значение и пропускают поле.**
7. Иногда плейсхолдер приходится удалять вручную.

Доступность [S2], [S12], [S22], [V:2juq00vrvl0, 51:17]:
- серый по умолчанию **часто не проходит WCAG 2.2 1.4.3 (контраст)** и стилизуется не во всех браузерах;
- не все скринридеры озвучивают плейсхолдер, а часть читает его неправильно;
- тёмный плейсхолдер выглядит как введённое значение;
- **заполненная плейсхолдерами форма выглядит уже заполненной** для людей с когнитивными особенностями.

Короткое видео NN/g формулирует правило жёстче всех [V:jrigp2L-P-0, 00:00]: «**Не помещайте ничего внутрь поля ввода.
Не делайте этого. Перестаньте, если делаете прямо сейчас.**» Стефани Вальтер: «я не вижу случая, где плейсхолдер не
был бы проблемой доступности или юзабилити» [V:2juq00vrvl0, 52:19].

**Что остаётся плейсхолдеру** (общий знаменатель всех источников): **пример значения формата**, продублированный
снаружи поля. Carbon [S19]: плейсхолдер — подсказка или пример (`YYYY-MM-DD`); поскольку он исчезает при вводе, он не
содержит важного; **для сложных требований (пароль) — не плейсхолдер, а infotip**; примеры анонимизировать.

**Плавающие подписи (floating labels)** `[спорно]`. NN/g [S2]: решают проблемы 1–4, **не решают 5 и 6**, проблемы
доступности сохраняются; плюсы — экономия вертикали на мобильном и видимая подпись во время набора; вывод: «если
место на экране есть, подпись и подсказка снаружи поля — по-прежнему лучший вариант». Фридман допускает их «при
аккуратной работе с доступностью» [V:qktwIWZNFY4, 55:47]. **Позиция базы: подписи снаружи; плавающие подписи —
компромисс только при жёстком дефиците вертикали на мобильном, с явной проверкой контраста и скринридером.**

### 3.3 Вспомогательный текст: helper, hint, tooltip

Различение Carbon [S19] `[система]`, совпадающее с NN/g [S24] и GOV.UK [S12]:

| Носитель | Виден | Для чего |
|---|---|---|
| **Helper / hint text** под подписью | **всегда, в том числе при фокусе** | информация «нужно знать»: формат, где взять данные, как они будут использованы |
| **Плейсхолдер** внутри поля | до начала ввода | пример значения, «приятно знать» |
| **Тултип** по наведению/фокусу | по требованию | дополнительное объяснение, «зачем это поле» |

Правила hint text [S12], [S13]:
- **одно короткое предложение без точки**;
- **никаких ссылок внутри подсказки**: скринридер прочитает текст ссылки, но не скажет, что это ссылка;
- если объяснение длинное, hint не подходит — тогда `h1`-утверждение, обычный текст с абзацами и списками, и уже под
  ним подпись с конкретным вопросом [S13];
- не повторять одно и то же под каждым полем (одна подсказка на одно правило).

Правила тултипа [S24], [S19]:
- **никогда не класть в тултип информацию, критичную для выполнения задачи** — требования к паролю в тултипе
  (антипример Amtrak) заставляют держать их в рабочей памяти;
- Carbon использует иконку «i», а не «?», именно чтобы обозначить «дополнительное, а не необходимое»;
- тултип обязан работать и по наведению мыши, и по клавиатурному фокусу.
Подробно — `07-overlays-modals-drawers-popovers.md` §5.

**Caption у Primer** [S22]: дополнительный контекст под подписью; **не должен дублировать подпись** («если caption
кажется избыточным, уберите его»); **при ошибке caption скрывается и заменяется сообщением об ошибке**, чтобы не
повторять одно и то же.

### 3.4 Обязательные и необязательные поля

Единственное место в файле, где два первичных источника дают прямо противоположные инструкции. `[спорно]`

| Источник | Правило |
|---|---|
| **NN/g** [S3] | **Помечать все обязательные** — звёздочкой (красной, привычной по закону Якоба) или словом «Required». Необязательные помечать не обязательно, но полезно |
| **GOV.UK** [S13] | **«Никогда не помечайте обязательные поля звёздочками.»** Помечать «(optional)» у необязательных |
| **Carbon** [S19] | **Правило по большинству**: если большинство полей обязательны — помечать только «(optional)»; если большинство необязательны — помечать только «(required)» |
| **Primer** [S22] | Обязательное поле визуально помечается и одновременно помечается в коде; исключение — формы входа, где и так всё обязательно |

Что у всех совпадает и потому идёт в правило `[консенсус]`:
1. **Обязательность видна до нажатия кнопки, а не после.** Антипример [V:2juq00vrvl0, 26:42]: форма регистрации, где
   подписи заменены плейсхолдерами, а обязательность не помечена, — «правила игры сообщают после того, как я проиграл».
2. **Инструкция «все поля обязательны» вверху формы не работает**: её не читают, а прочитав — забывают, особенно в
   длинной форме и при прерывании [S3].
3. **Помечать только необязательные, ничего не сказав про обязательные, — хуже всего**: аккуратные пользователи
   сканируют форму в поисках пометки, большинство просто предполагает («телефон им не нужен») и получает ошибку [S3].
4. **Сначала убрать необязательные поля.** NN/g [S1]: «оставляйте не больше 1–2 необязательных полей и явно помечайте
   их как необязательные». Carbon: избыток необязательных выносить в отдельную секцию.
5. **Пометка не низкоконтрастная** [S3].
6. **Паттерн консистентен по всему продукту**, а не по отдельной форме [S19]: «если из 100 форм свойств поля
   необязательны в 85, все 100 используют паттерн required».
7. **Отдельный чекбокс или радиокнопку нельзя пометить обязательными** — обязательна группа [S22].

**Рекомендация базы** (синтез, а не позиция одного источника): **правило по большинству Carbon**, потому что оно
одновременно удовлетворяет NN/g (в простых клиентских формах большинство полей обязательны → помечаются
необязательные, и их 1–2) и GOV.UK (в их сценарии на странице один вопрос, и звёздочка бессмысленна). Оформлять
пометку **словом в скобках**, а не только звёздочкой: слово читается скринридером и не требует легенды.

### 3.5 Форматы, маски, прощающий ввод

`[консенсус]` [S9], [S12], [V:qktwIWZNFY4, 32:26].

1. **Принимать любой разумный формат и нормализовать самим.** GOV.UK [S9]: игнорировать нежелательные символы —
   пробелы, невидимые символы, дефисы, скобки, тире, точки — (а) внутри номеров и кодов, (б) до и после ответа
   (скопировано случайно), (в) вставленные диктовкой (частое при диктовке чисел). «Если бы эти символы вызывали ошибку
   валидации, пользователю было бы трудно её увидеть и исправить».
2. **Данные о выигрыше** [S9-date] `[исследование]`: сервис Apply for teacher training обнаружил, что **сотни
   пользователей вводили месяц словом** и получали ошибку; после того как компонент стал принимать «january» и «jan»,
   **число ошибок резко упало**. Побочная польза: людям с дискалькулией трудно переводить название месяца в число.
3. **Объяснять требования формата до ошибки, а не после** [S1]. Антипример: Netgear показывает требования к паролю
   только как сообщение об ошибке.
4. **Убирать произвольные правила формата вовсе**: «смерть скобкам в коде города» [S1].
5. **Не блокировать копирование и вставку** ни в одном поле, включая пароль [S12], [S16].
6. **Избегать `maxlength`** [S12]: обрезка происходит без обратной связи (особенно при вставке и автозаполнении);
   ограничение мешает привычному форматированию (пробелы в индексе, запятые в числе); часть ассистивных технологий не
   сообщает о лимите, а голосовое управление может вставлять лишние пробелы. Если ограничение обязательно — сказать о
   нём в подсказке, разрешить ввести больше и дать ошибку, только если после нормализации значение всё ещё длиннее.
7. **Счётчик символов — не по умолчанию** [S18]: «сначала всегда протестируйте сервис без счётчика». Ставить только
   при данных, что люди пишут больше нужного, или при юридическом/техническом лимите. **Если пользователи постоянно
   упираются в лимит бэкенда — поднять лимит, а не ставить счётчик.** Счётчик **не мешает вводить больше лимита**:
   человек допечатывает или вставляет полный ответ и потом сокращает. Лимит ставить выше, чем нужно большинству; при
   лимите, до которого почти никто не доходит, показывать счётчик только после порога (например, 75%). Зрячие видят
   обновляющийся счётчик по мере набора, **скринридер озвучивает его, когда человек перестал печатать**.
8. **Не заставлять вводить одно и то же дважды** (WCAG 2.2 «Redundant entry») [V:2juq00vrvl0, 25:42], [S13]: чекбокс
   «адрес доставки совпадает с адресом оплаты» вместо второго набора полей; предзаполнение ранее введённого;
   исключение — требования безопасности.
9. **Отключать проверку орфографии** (`spellcheck="false"`) для референсов, имён, email, идентификаторов и пароля
   [S12], [S16]. Для пароля это ещё и защита от **spell-jacking**: часть проверяющих орфографию инструментов
   отправляла персональные данные и пароли третьим сторонам [S16].
10. **Целые числа — `inputmode="numeric"`**, а не `type="number"` (GOV.UK отказалась от него по итогам разбора
    браузерных проблем) [S12].
11. **Коды и последовательности** (номер заявки, номер счёта, код безопасности) визуально разделять на группы, чтобы
    человек мог сверить символы; для памятных данных (телефон, индекс) этого не делать [S12].

## 4. Валидация: механика

### 4.1 Где inline-валидация окупается

Данные [S7] `[исследование]`: **inline-валидация нужна полям, где ответ неочевиден**. В первой половине формы (имя,
фамилия, email, пол, страна, индекс) сообщения валидации заметили **30–50%** участников; во второй (имя пользователя,
пароль со строгими требованиями) — **80–100%**. Зелёная галочка на поле «имя» участников путала: «вы подтверждаете,
что имя валидно или что оно правильное?».

Риск обратного, который автор оставляет открытым: если успех показывать не везде, отсутствие галочки может читаться
как «невалидно». Практическое разрешение (совпадает с [S4]): **успех показывать только там, где он несёт информацию**
(§4.7).

### 4.2 Когда проверять: машина состояний поля

Три наивных варианта и их измеренная цена [S7] `[исследование]`:

| Момент проверки | Результат |
|---|---|
| **After** (on blur) | **быстрее «while» на 7 секунд и «before and while» на 10 секунд** |
| **While** (on keypress) | люди вводят по одному символу и ждут обновления сообщения |
| **Before and while** (on focus + on keypress) | **худшее время, самый высокий процент ошибок, худшая удовлетворённость**. Цитаты: «раздражает, что не успеваешь ничего ввести, а оно уже мигает красным»; «я нажал в поле "Имя", и оно сразу сказало, что имя слишком короткое. Разумеется! Я ещё не начал» |

**Рабочая машина состояний — «reward early, punish late»** (Mihael Konjević, в изложении Фридмана
[V:qktwIWZNFY4, 50:41]) `[практика]`. Для каждого типа поля задаётся пессимистичный порог символов (для email
порядка 7–8):

| Состояние поля | Событие | Действие |
|---|---|---|
| Пустое, не тронутое | фокус | ничего не показывать |
| Вводится, символов меньше порога | ввод | не проверять |
| Вводится, символов меньше порога | уход из поля (blur) | проверить, показать ошибку при провале |
| Вводится, порог достигнут | ввод | начать проверку; **очевидную ошибку показать сразу** (два символа `@`) |
| Валидное | уход из поля | **поставить отметку успеха только сейчас**, а не во время набора |
| Валидное | правка | снять отметку успеха, проверять по blur |
| **Невалидное** | правка | **проверять на лету и снимать ошибку сразу, как она исправлена** |

Та же логика у Primer [S22] `[система]`, сформулированная короче: «Если контрол валиден, проверка выполняется только
после того, как человек изменил ввод **и убрал фокус**. Не пытайтесь валидировать ввод до того, как человек закончил.
Проверка по мере набора допустима **только после первой проверки и только пока поле невалидно** — это даёт раннюю
положительную обратную связь, убирая ошибку, как только человек её исправил».

Carbon [S19] и NN/g [S4] независимо дают ту же опорную точку: **клиентская проверка срабатывает, как только поле
теряет фокус**.

Дополнительные условия:
- «Не показывайте ошибку, пока человек не закончил с полем и не перешёл к следующему» [S4]. Антипример BestBuy:
  возврат к правке email вызвал ошибку в поле телефона, где пользователь ещё не начинал печатать.
- Primer [S22]: **если проверка занимает больше 1 секунды, показать индикатор загрузки**.

### 4.3 Противоречие с GOV.UK

`[спорно]` — противоречие прямое, сглаживать нельзя.

GOV.UK [S9]: «**Не валидируйте, когда пользователь уходит из поля. Ждите, пока он попытается перейти к следующей части
сервиса — обычно нажатием кнопки внизу страницы.** Вообще избегайте валидации содержимого поля до того, как
пользователь закончил ввод: такая валидация вызывает проблемы, особенно у тех, кто печатает медленнее. Добавляйте её,
только если ваше исследование показывает, что в балансе она решает больше проблем, чем создаёт.» Плюс:
**отключить HTML5-валидацию** (`novalidate`) и **не ставить `required`** на поля.

Аргументы GOV.UK: трудно сообщать об ошибках одинаково во всех браузерах и ассистивных технологиях; правила клиентской
и серверной валидации могут конфликтовать; визуальный стиль, размещение и содержание нативных сообщений нельзя
привести к дизайн-системе.

Почему это не отменяет §4.2:
1. **Разные аудитории и сценарии.** GOV.UK проектирует однократные публичные сервисы для неподготовленных людей, где
   на странице один вопрос и «ждать кнопки» стоит дёшево. NN/g и LukeW мерили регистрацию и чекаут с формой из
   8+ полей, где ожидание кнопки означает возврат к началу.
2. **GOV.UK сама допускает исключение** — счётчик символов показывает ошибку при превышении лимита, «потому что важно,
   чтобы человек не потратил силы на ответ, который окажется слишком длинным» [S9].
3. Бесспорно одно: **пара «сводка вверху + сообщение у поля» обязательна независимо от момента проверки**.

**Позиция базы:** момент проверки выбирается по полю, а не по форме.

| Поле | Момент проверки |
|---|---|
| Ответ известен человеку (имя, город, телефон) | **по нажатию кнопки отправки** (GOV.UK) |
| Ответ неочевиден и зависит от системы (имя пользователя, промокод, ИНН с контрольной суммой) | **inline по blur**, плюс проверка на лету после первой ошибки |
| Есть жёсткое ограничение, о которое человек может потратить много труда (лимит символов, размер файла) | **на лету, с порогом** |
| Поле с форматом и маской (карта, дата) | **маска предотвращает ошибку; проверка по blur** |

### 4.4 Где показывать ошибку

`[консенсус]` [S4], [S9], [S11], [S19], [S22].

1. **Сообщение рядом с полем** — под подписью и подсказкой, **над самим полем** (GOV.UK) — позиция базы: под полем
   сообщение перекрывают экранная клавиатура, выпадающий список и автозаполнение
   (`../09-mobile/03-mobile-content-tables-forms-dashboards.md` §3.5). «Под полем» (Carbon, Primer) — только на десктопе
   в системах с этой конвенцией и при гарантии, что ничто не перекрывает; одно место на продукт
   (`../10-design-systems-consistency/02-consistency-rules.md` чек-лист 17).
   Главное — **сообщение видно, пока человек чинит**: это снимает нагрузку с рабочей памяти [S4].
2. **Красная рамка поля** визуально связывает сообщение с вопросом [S11]. **Не только цветом**: «обводка поля И
   красный текст И более жирное начертание — сейчас не время быть деликатным» [S1].
3. **Иконка слева от сообщения** помогает дальтоникам и сканированию; допустима лёгкая пульсация иконки, **но не
   анимировать текст** и не анимировать много иконок сразу [S4].
4. **Скрытый префикс «Ошибка:»** перед сообщением, чтобы скринридер произнёс «Ошибка: дата выдачи паспорта должна быть
   в прошлом» [S11]. `aria-invalid="true"` на поле и `aria-describedby` на сообщение [S22]; **если сообщение убрано из
   DOM, `aria-describedby` тоже убирается**.
5. **Не использовать тултипы для ошибок** [S4]: иконку-алерт плохо видно на плотном интерфейсе; человек не понимает,
   что сообщение вообще есть; нужны лишние действия ради критичной информации. Антипример Facebook.
6. **Не использовать модалку для ошибки формы** [S4], [S33]: «ошибку в форме показывать на странице рядом с полем, а
   не в модалке» — иначе сообщение приходится запоминать, потому что окно надо закрыть, чтобы чинить. Модалка
   допустима, если сообщение простое **или форму всё равно можно отправить как есть** (Gmail предупреждает о забытом
   вложении).
7. **Одно сообщение на группу**, а не на каждый элемент: у отдельного чекбокса или радиокнопки не должно быть своего
   сообщения и своего стиля ошибки — сообщение показывается для группы [S22].
8. **Live region для валидации не использовать** [S22]: всегда управление фокусом (на первую ссылку в сводке или на
   первое ошибочное поле) плюс правильная разметка.
9. **Не использовать нативную валидацию браузера** [S9], [S22]: сообщения недоступны скринридерам и визуально
   выбиваются из дизайн-системы.

### 4.5 Сводка ошибок

`[консенсус]` [S9], [S10], [S4], [S22], [V:qktwIWZNFY4, 51:41].

- **Сводка и сообщения у полей — вместе, никогда одно вместо другого.** «Сводка не должна быть единственным
  индикатором: она заставляет искать поле, и сообщение может уйти из вьюпорта, пока человек доходит до поля» [S4].
  Фридман: «одно из двух наверняка пропустят» [V:qktwIWZNFY4].
- **Показывать сводку всегда при ошибке валидации, даже если ошибка одна** [S10].
- **Переводить фокус клавиатуры на сводку** [S10], [S22].
- **Заголовок сводки — «Произошла ошибка» / «There is a problem»**; **каждая строка — ссылка на ошибочное поле**;
  **формулировки в сводке дословно совпадают с формулировками у полей** [S10].
- **Место сводки: вверху основного контейнера, ниже крошек и кнопки «Назад», но выше `<h1>`** [S10].
- Добавить `Error: ` в начало `<title>` страницы, чтобы скринридер произнёс это как можно раньше [S9].
- Порог Primer [S22] `[система]`: **сводку показывать при трёх и более ошибках**; если сводки нет — сфокусировать и
  прокрутить к первому ошибочному полю. GOV.UK порога не ставит и требует сводку всегда — расхождение `[спорно]`.
  Рекомендация базы: **форма длиннее экрана — сводка всегда; форма в один экран — достаточно фокуса на первое
  ошибочное поле**.
- Приём для случая, когда человек ушёл в другую вкладку на время долгой отправки [V:qktwIWZNFY4, 52:44] `[мнение]`:
  моргающий заголовок вкладки и смена фавикона при ошибке.

### 4.6 Клиент и сервер

`[консенсус]` [S9], [S19].

1. **Серверная валидация обязательна всегда**, даже при клиентской: клиентскую можно обойти, JS может не загрузиться.
2. **Всё, что можно проверить на фронте, проверять до отправки** [V:qktwIWZNFY4, 1:15:05] — иначе человек получает
   возврат на шаг назад с потерей данных.
3. **Серверная ошибка после отправки** показывается как inline-уведомление вверху формы **плюс** сообщения у полей,
   которые сервер отверг [S19]. После неудачной отправки Primer разрешает **переключиться на inline-валидацию**, чтобы
   дальше человек получал обратную связь быстрее [S22].
4. **Введённое сохраняется** и при серверной ошибке: страница показывается заново с заполненными полями [S9].
5. **Правила клиентской и серверной проверок обязаны совпадать** [S9]. Проверяемый антипример
   [V:qktwIWZNFY4, 52:44]: спецсимвол в фамилии проходит на бэкенде, но не проходит на фронте — при заблокированной
   кнопке человек оказывается заперт.

### 4.7 Индикация успеха

`[консенсус]` [S4], [S7], [S22].

- **Показывать успех только там, где он несёт информацию**: доступность имени пользователя, валидность промокода,
  сила пароля. «Не показывайте сообщение об успехе, если единственное требование к полю — быть заполненным: такое
  сообщение не даёт дополнительного контекста» [S4].
- Для сложных полей (новый пароль) допустима **мгновенная проверка по мере набора**, чтобы человек не гадал [S4].
- **Постоянные сообщения лучше исчезающих** [S7]: исчезающие пугают («я что-то сломал?») и их пропускают —
  подавляющее большинство участников печатали «hunt and peck», глядя на клавиатуру, а не на экран.
- Отметка успеха ставится **после перехода к следующему полю**, а не во время набора (§4.2).

### 4.8 Повторяющиеся ошибки

[S4] `[консенсус]`: **одна и та же ошибка три и более раз за одно заполнение — признак дефекта интерфейса, а не
пользователя**. Что делать: дать ссылку на поддержку прямо в форме; смотреть аналитику по паттернам ошибок; переписать
сообщение; упростить требование.

Практический приём, когда форму нельзя починить быстро [V:qktwIWZNFY4, 53:45] `[практика]`: рядом с кнопкой ставится
ссылка «не могу заполнить форму, свяжите меня с поддержкой», которая **отправляет уже введённые данные в поддержку**.

## 5. Кнопки формы

### 5.1 Одна главная кнопка

`[консенсус]` [S1], [S21], [S6], `../03-layout-placement/04-placement-conventions-and-redundancy.md` §11.

- **Одна кнопка отправки на форму.** Primer [S21]: «На странице должна быть только одна кнопка сохранения… Страницы
  с несколькими кнопками сохранения вызывают путаницу, какая из них что сохраняет. Несколько кнопок с одинаковой
  подписью путают пользователей скринридеров и голосового управления».
- Исключение: секции сохраняются **независимо**, и это явно видно (отдельные карточки со своим состоянием). Тогда у
  кнопки секции **вторичный вид**, а не primary [S21].
- **Подпись называет действие и объект**: «Создать», «Сохранить», «Удалить», «Обновить» [S21]; «Submit» создаёт
  впечатление, что форма шаблонная [S19]; «добавьте имя объекта в подпись, если иначе неясно, что меняется» [S21].
- **Имя действия не меняется по ходу потока**: кнопка «Опубликовать» → тост «Опубликовано» → статус «Опубликовано».
  Это закрывает дефект F7.3 каталога `../11-ai-generated-ui/01-failure-modes-catalog.md` §9.
- **Каждая кнопка имеет действие, состояние и результат.** Дефект F4.3 «кнопки без назначения» измерен в
  Interaction2Code: типы сбоя «Missing interactive element» и «No interaction» входят в четвёрку самых частых, и оба
  имеют usability rate ниже 10% — то есть взаимодействие полностью нерабочее. Проверка — §1.3 п. 12.
- **Не прикреплять кнопки к верху формы** [S19] `[система]`: предполагается, что человек прокручивает поля перед
  отправкой; «Назад» уже есть в крошках, в индикаторе шагов и в браузере, поэтому **«Назад» никогда не должна быть
  действием вторичной кнопки формы**; верхние кнопки создают неловкое отношение с контентом в момент готовности
  отправить.

### 5.2 Блокировать кнопку отправки или нет

`[спорно]` — одна из двух главных развилок файла.

| Источник | Позиция |
|---|---|
| **NN/g (видео 2025)** [V:uEjidraxhAw] | Не блокировать. Четыре вреда: обман («negative affordance» — подпись зовёт нажать); нечитаемая низкоконтрастная подпись; отсутствие обратной связи; **рост сложности — запрет на клик перекладывает всё на безошибочную инлайн-валидацию, и любая её ошибка запирает человека** |
| **Фридман** [V:qktwIWZNFY4, 52:44] | Не блокировать. «Disabled сообщает, что проблема есть, но не говорит какая; при ошибке скрипта человек заперт — **гарантированные 100% отказа**» |
| **Primer** [S21], [S22] | «**Не отключайте и не прячьте кнопку сохранения, даже если форма невалидна или не менялась.** Отключённые кнопки нельзя сфокусировать по Tab, а их стиль обычно низкоконтрастный и плохо читается» |
| **Carbon** [S19] | Блокировать **для коротких форм с серверной проверкой** до выполнения всех требований; **не блокировать для длинных**, потому что сообщения об ошибках и кнопка могут быть не видны одновременно |
| **Material 3** [S25] | **Отклоняющие действия никогда не блокируются**; подтверждающее можно заблокировать, пока не сделан обязательный выбор |

Дополнительный факт [V:uEjidraxhAw, 00:43]: **по WCAG элементы, с которыми нельзя взаимодействовать, не обязаны
соответствовать требованиям контраста** — формальная правота не делает решение хорошим.

**Правило базы:**

1. **По умолчанию кнопка активна всегда до первого нажатия.** Человек нажимает и получает объяснение — сводку ошибок
   и фокус на первом проблемном поле.
2. **Единственное бесспорное основание блокировать — после нажатия** (§5.3).
3. Если блокировка всё-таки применяется (легаси, требование безопасности), обязательны три вещи [V:uEjidraxhAw, 03:05]:
   элемент **остаётся фокусируемым** и объявляется скринридером; **рядом объясняется причина и способ продолжить**;
   активные кнопки визуально не похожи на заблокированные.
4. **Обходной путь** при невозможности снять блокировку: ссылка «не могу заполнить форму, свяжите с поддержкой»,
   отправляющая введённое (§4.8).

### 5.3 Двойная отправка и состояние загрузки

`[консенсус]` [S19], [V:uEjidraxhAw, 02:25].

1. **После нажатия кнопка блокируется, чтобы предотвратить дублирующие отправки.** Это не противоречит §5.2:
   «оправданный случай блокировки — после нажатия: действие обрабатывается или уже недоступно; тогда переход в
   disabled работает как микровзаимодействие, сообщающее об изменении состояния системы» [V:uEjidraxhAw].
   Пример: после запроса кода из SMS кнопка блокируется, чтобы не было серии повторных запросов.
2. **Действие выполняется немедленно; при короткой загрузке — индикатор внутри кнопки; при длительной — спиннер и
   оверлей поверх формы с отключённым содержимым** [S19].
3. **Если обработка занимает больше нескольких секунд — показывать прогресс, а не спиннер** [S19]. Пороги времени
   отклика — `../06-feedback-states-motion/02-system-status-and-waiting.md`.
4. Проверка (§1.3 п. 8): повторное нажатие во время отправки не создаёт второй запрос.

### 5.4 Отмена, Reset, «Очистить»

`[консенсус]` [S6], [S1].

**Reset / «Очистить» — не делать.** Три вреда [S6]: (1) жмут по ошибке вместо отправки, и вся работа пропадает;
(2) две кнопки внизу формы засоряют интерфейс и заставляют выбирать; (3) даже когда очистка нужна, выбор между
«править» и «очистить» стоит 1–2 секунды размышления. Антипример [S1]: у формы жалоб TSA кнопка «Clear Form» стоит
**ближе к полям**, чем кнопка отправки.

Два узких исключения [S6]: (а) форма заполняется одним человеком многократно **и** данные сильно отличаются от раза к
разу; (б) сложный диалог параметров с хорошими значениями по умолчанию — тогда Reset означает «вернуться к безопасным
значениям», а не «очистить».

**Предусловие отказа от Reset** [S6]: чтобы человек мог отменить выбор, **в группе радиокнопок должен быть явный
вариант по умолчанию или явный вариант «Ничего из перечисленного»**, а в выпадающем списке — выбираемый пункт по
умолчанию. Иначе радиогруппа без начального выбора становится ловушкой: снять выбор невозможно.

**Отмена**: в вебе доминирует кнопка «Назад» браузера, поэтому явная «Отмена» нужна не всегда [S6]. Она полезна, когда
человек боится, что уже на что-то подписался, и **в многошаговых процессах, где «Назад» уже не отменит сделанного на
предыдущих шагах**. Бэкенд обязан уметь обрабатывать брошенные многошаговые процессы. В формах с особо чувствительным
вводом (финансы) «Отмена» нужна, **но визуально заметно слабее кнопки отправки** [S1].

**Несохранённые изменения**: при уходе со страницы — предупреждение [S21]; современные браузеры не дают настроить
текст `beforeunload`, поэтому сообщение будет типовым. Внутри модалки и панели — `07-overlays-modals-drawers-popovers.md` §2.5.

### 5.5 Размещение и порядок кнопок

Решено агентом B, здесь только ссылка и выжимка:
`../03-layout-placement/04-placement-conventions-and-redundancy.md` §3–§4.

| Контекст | Размещение |
|---|---|
| Форма на странице | Внизу, **по левому краю полей**; primary первая, вторичная рядом, отмена — ссылка |
| Длинная форма (>2–3 экранов) | Липкая панель действий внизу окна; кнопки внизу страницы не дублируются |
| Диалог / модальное окно | Внизу справа группой; подтверждение справа, отмена слева |
| Боковая панель | Внизу панели; по левому краю её содержимого либо на всю ширину |

Основание — айтрекинг LukeW + Etre (6 вариантов, 23 участника): три лучших варианта ставили Submit и Cancel слева под
полями; вариант с изменённым размещением дал 6 ошибочных кликов по Cancel и +6 секунд; вариант, где кнопки не были
выровнены по левому краю полей, дал худшее движение глаз.

Единственное, что стоит добавить из источников этого файла: **Primer [S21] расходится с B в порядке внутри страничной
формы** — «по умолчанию кнопка отправки внизу слева, а кнопка отмены **справа от неё**» (в диалоге наоборот: отмена
слева от отправки). Расхождение вынесено в «Открытые вопросы». Позиция базы (волна 4): порядок B/GOV.UK — primary
первая по левому краю полей, отмена рядом вторичной кнопкой или ссылкой; продукт, построенный на Primer, держит порядок
Primer везде — консистентность выше конвенции (`../10-design-systems-consistency/02-consistency-rules.md` §3.3).

## 6. Сохранение введённого и умолчания

### 6.1 «Никогда не теряй введённое» как проверяемое требование

`[консенсус]` [S9], [S11], [S1], [S21], [V:qktwIWZNFY4], плюс Купер «considerate software» п. 12
(`../01-foundations/01-principles-and-laws.md` §5.5): «форма из 11 полей не должна терять 10 правильных из-за одного
неверного».

Четыре случая, каждый проверяется сценарием:

| Случай | Требование |
|---|---|
| Ошибка валидации | Страница показывается заново **со всеми введёнными значениями — и правильными, и неправильными** [S9], [S11] |
| Возврат на предыдущий шаг | Данные шага сохранены; в чекауте **возврат к правке адреса не должен обнулять данные карты** — страница не перезагружается [V:qktwIWZNFY4, 37:31] |
| Обновление страницы | Введённое восстанавливается [V:qktwIWZNFY4, 32:26] |
| Отказ сервера | Данные остаются в форме, человек получает объяснение [S21] |

GOV.UK формулирует пользу прямо [S11]: сохранение данных, вызвавших ошибку, помогает **увидеть, что пошло не так,
отредактировать прошлый ответ и не вводить информацию заново**.

Антипаттерн из списка раздражителей [V:qktwIWZNFY4, 21:12]: очистка всех полей при ошибке; перезагрузка страницы
после асинхронной проверки адреса.

Детально черновики и автосохранение — `../05-flows-journeys/05-saving-drafts-and-persistence.md`.

### 6.2 Автозаполнение и клавиатура

`[практика]` с числами из единичного источника [V:qktwIWZNFY4, 30:23–31:25], подтверждёнными по механизму у GOV.UK
[S12] и Carbon [S19]:

- **Автозаполнение браузера сокращает время заполнения минимум на 30%** — «это первое, что нужно чинить в форме,
  раньше валидации и красоты».
- **Переключение клавиатура↔мышь стоит ≈400 мс в одну сторону**; один вынужденный переход туда и обратно — почти
  секунда на каждое поле.
- **На форме адреса из 8 полей заполнение с табуляцией примерно втрое быстрее**, чем с мышью.
- Две вещи заставляют переключаться: **непредсказуемый tab-порядок, не совпадающий с раскладкой**, и **select-дропдаун**.

Следствия:
1. **Проставлять `autocomplete` каждому полю**: `postal-code`, `country-name`, `organization`, `new-password`,
   `current-password`, `bday-day`/`bday-month`/`bday-year` [S12], [S16], [S9-date].
2. **Проверять порядок табуляции** — он обязан совпадать с визуальным [S1].
3. **Учитывать менеджеры паролей**: не мешать им, не ставить `maxlength`, не блокировать вставку [S12], [S16], [S19].
4. **Держать рядом поля, требующие клавиатуры** [S22]; «дать человеку оставаться в одном способе ввода как можно
   дольше» [S19].
5. **После однозначного выбора переводить фокус на следующее поле** (выбрал страну — фокус в поле индекса)
   [V:qktwIWZNFY4, 43:37] `[мнение]`. Осторожно: автопереход между полями кода из SMS ломает часть скринридеров.

### 6.3 Значения по умолчанию

`[консенсус]` [S19], [S26], [S31].

Правило Carbon [S19]: «Убедитесь, что значение по умолчанию — то, которое и так обычно используется и **не вызовет
сбоя или ошибки, если человек забудет или решит его не менять**». Примеры хороших умолчаний: страна по геолокации
(оправдано, только если подавляющее большинство клиентов из одной страны [V:qktwIWZNFY4, 43:37]); минимальная квота
или лимит; название компании из профиля; **текущая дата как дата начала**.

Дефолт — сильный инструмент влияния [S31], поэтому:
- **не ставить дефолт, который выгоден бизнесу и невыгоден человеку** (предотмеченный чекбокс рассылки); в ЕС, Канаде
  и Калифорнии это ещё и незаконно [V:qktwIWZNFY4, 44:37];
- чекбокс согласия по умолчанию **пустой** — согласие только активным действием [S26];
- если подходящего дефолта нет, честнее его не ставить, чем ставить наугад (§3.4 и `06-input-controls.md` §4).

### 6.4 Предзаполнение и копирование из похожего объекта

`[консенсус]` [S13], `../01-foundations/01-principles-and-laws.md` §5.5 (Купер, «проявляет интерес»: помнит ли система,
что пользователь ей говорил, или спрашивает заново).

- **Спрашивать одно и то же один раз за сценарий** [S13]; если та же информация нужна ещё раз — предзаполнять поля
  или показывать ранее введённый ответ как вариант для выбора.
- **Дать переиспользовать уже загруженный файл** внутри одного сценария, если это не создаёт угрозы безопасности или
  приватности (фото прав для подтверждения личности и адреса) [S27]; учитывать публичные устройства при показе превью.
- **Копирование из похожего объекта** («Создать на основе», «Дублировать») — дешёвый способ убрать повторный ввод;
  конвенции именования — `10-actions-menus-bulk-shortcuts.md` §7.

## 7. Особые случаи

### 7.1 Длинные формы: секции, аккордеон, шаги

Четыре приёма в порядке возрастания разрыва потока:

| Приём | Когда | Источник |
|---|---|---|
| **Прогрессивное раскрытие** внутри страницы | редкие опции, ветвления | §7.2 |
| **Секции с заголовками + оглавление с якорями** | эксперт, ежедневная работа, нужно видеть всё | `../02-ia-navigation/02-navigation-patterns.md` §8 |
| **Аккордеон-форма** | длинная последовательная форма на одной странице | [S8] |
| **Многошаговая форма** | шаги обязательны, порядок задан, нужно сохранять прогресс | [S19], [S13] |

**Данные по аккордеон-формам** [S8] `[исследование]`: LukeW + Etre, **24 участника 19–48 лет**, 4 варианта типовой
формы чекаута (многостраничная, одностраничная, аккордеон с переходом по заголовкам, аккордеон с переходом по кнопке
внутри секции).
- **Конверсия одинаковая**: у всех четырёх вариантов 100% прохождения. Вывод автора: перенос той же формы в аккордеон
  **не повысит конверсию, но и не обрушит её** — «в отличие от большинства новых интерфейсных решений, которые обычно
  ухудшают конверсию, пока люди к ним не привыкнут».
- **Скорость**: быстрее всех **аккордеон с кнопками** — примерно **на 10 секунд быстрее даже одностраничной формы**.
- **Ключевая ошибка проектирования**: в варианте с переходом по заголовкам «очень немногие вообще додумались
  взаимодействовать с заголовками»; подавляющее большинство тянулось к заметной кнопке и жало её, **включая финальную
  кнопку «Оплатить и завершить заказ», ещё не введя данные карты** — это дало непреднамеренные ошибки.
- Формулировка урока: «даже когда вы придумываете новое, опирайтесь на конвенции»: клик по заметной кнопке для
  завершения формы — это привычка, и аккордеон должен на неё опираться.
- Оговорка автора: 24 человека, обобщённая форма e-commerce; проверять на своей аудитории.

Carbon добавляет предупреждение [S19]: **в аккордеон-формах возникает путаница, относится ли primary-кнопка к секции
или ко всей форме**; в диалоговых формах аккордеон не применять.

**Липкая панель действий** обязательна, если форма длиннее 2–3 экранов, и тогда кнопки внизу страницы не дублируются
(`../03-layout-placement/04-placement-conventions-and-redundancy.md` §9).

### 7.2 Условные поля (прогрессивное раскрытие)

`[консенсус]` [S9-checkbox], [S19], [S22], [V:qlKWPNgPjmw].

1. **Показывать вопрос только тем, кому он относится**: поле телефона появляется при выборе «связаться по телефону»;
   поля банковской карты не показываются, если выбран Apple Pay [V:qlKWPNgPjmw, 03:06].
2. **Раскрытое поле идёт сразу после родительского контрола**, визуально вложено под ним [S22], [S9-checkbox];
   для переключателя — **всегда после него** [S32].
3. **Подпись вложенного поля не конфликтует с подписью родителя**; если родитель даёт достаточный контекст, подпись
   можно визуально скрыть, но она обязана существовать для скринридера [S22].
4. **Ошибка показывается и для условно раскрытого вопроса**, если он не отвечен [S9-radio].
5. **Правило окупаемости** [V:qlKWPNgPjmw, 04:08]: цена прогрессивного раскрытия — одно-два лишних действия; она
   оправдана, **только если скрытое не нужно большинству**. Если нужно — прятать нельзя. Контрпример из отчёта W5:
   сокрытие двух ключевых функций стоило продукту кратной разницы в использовании.
6. GOV.UK и Primer обе отмечают, что **исследований условного раскрытия с пользователями ассистивных технологий
   мало** — это открытый вопрос обеих систем [S9-checkbox].

### 7.3 Повторяющиеся группы («добавить ещё»)

`[практика]` — сводка из [S19], [S14] и практики; отдельного исследования не найдено.

- Группа полей повторяется по кнопке «Добавить ещё …» с именем сущности («Добавить ещё участника»), а не «Добавить».
- **Каждый экземпляр удаляется отдельно**, кнопка удаления — у экземпляра, а не общая.
- **Удаление экземпляра с введёнными данными — подтверждение или undo** (§5.4,
  `../05-flows-journeys/03-destructive-actions-undo-confirmation.md`).
- При более чем 3–5 экземплярах переходить на **список с отдельной формой добавления** (страница или панель), иначе
  форма перестаёт сканироваться.
- Для проверки перед отправкой длинный список экземпляров сворачивается в **сводку** (GOV.UK summary cards: «когда
  нужно проверить несколько однотипных вещей» [S14]).

### 7.4 Таблица как форма: массовое и построчное редактирование

Граница с файлом D1 `01-data-tables.md` — здесь только правила формы.

- **Inline-редактирование**: Купер, AXIOM «разрешайте ввод везде, где есть вывод» и «не заставляйте идти в другое
  окно, чтобы выполнить функцию, влияющую на текущее окно» (`../01-foundations/01-principles-and-laws.md` §5.3)
  `[мнение]`. Carbon честно пишет, что **консолидированного руководства по inline-редактированию у них нет** [S19] —
  это зона без конвенций.
- **Одновременно активен один режим редактирования** [S21]: «разрешайте активировать только один режим правки за раз,
  если на странице есть несколько независимо редактируемых мест».
- **Кнопка сохранения при inline-правке ставится вплотную к полю**, чтобы связь была видна [S21].
- **Массовая правка нескольких строк** — не inline, а панель или диалог с предпросмотром последствий («будет изменено
  240 записей»); детально — `10-actions-menus-bulk-shortcuts.md` §3.
- **Валидация построчная**: сообщение у строки, сводка вверху таблицы с числом ошибочных строк и ссылками на них
  (перенос правила §4.5 на таблицу).

### 7.5 Формы в модалках и панелях

| Диалог / модалка | **менее пяти** [S19]; «до ~5» (B, §6.1) | Одна колонка, без прокрутки, **без аккордеонов и вкладок** [S19], без боковой навигации [S26p] |

### 7.7 Вход, регистрация, восстановление пароля

Анатомия экрана — `../03-layout-placement/01-page-anatomy-templates.md` §11. Здесь — правила формы.

**Регистрация** [S17] `[система]`:
1. **Не заводить аккаунты, если сервис можно оказать без них**: аккаунт — барьер и причина отвала. Для разовой
   операции достаточно уникального номера обращения плюс имя или email (номер выслать письмом или SMS — «его трудно
   запомнить»).
2. **Дать пользоваться сервисом как можно дольше до создания аккаунта.**
3. **Формулировки**: «Создать аккаунт», а не «Регистрация»; подписи полей **«Придумайте имя пользователя»,
   «Придумайте пароль»**, а не «Имя пользователя», «Пароль», — чтобы человек понял, что у него не спрашивают
   существующие.
4. **Явно различать «создать аккаунт» и «войти»: «показать варианты рядом недостаточно — люди могут пропустить один
   или не понять разницу».**
5. **Экран создания аккаунта посвящён только этой задаче**: никакого отвлекающего контента и ссылок.
6. **Избегать CAPTCHA**: это проверка когнитивных функций, трудная для части пользователей и зависящая от культуры и
   локали. Альтернативы [V:qktwIWZNFY4, 1:09:01] `[практика]`: фильтр спам-IP (Akismet), простой человеческий вопрос,
   **honeypot** (скрытое поле с правдоподобной подписью «phone»), доступный с клавиатуры слайдер, **временная ловушка
   3 секунды** (7 секунд — уже перебор). Оговорка: против современных ботов honeypot и тайм-трап слабее, чем в 2020;
   это первый слой, а не замена антифроду.
7. **Не спрашивать пароль на входе в сценарий** [V:qktwIWZNFY4, 35:29] `[практика]`: гостевое оформление по
   умолчанию, а после покупки — предложение задать пароль с выгодой («поставьте пароль — 15% на следующий заказ»),
   потому что всё остальное для аккаунта уже введено.
8. **Не форсировать вход, если введённый email уже есть в базе** [V:qktwIWZNFY4, 1:12:03] `[мнение]`: это выталкивает
   в восстановление пароля, которое часть людей не доводит до конца. Оговорка: у правила очевидный конфликт с
   безопасностью и антифродом — решать вместе с безопасниками.
9. **Поле «повторите email» не нужно**: ~70% нетехнических пользователей просто копируют введённое, то есть проверка
   не ловит ошибку [V:qktwIWZNFY4, 33:27]. Правильный момент подтверждения почты — экран проверки заказа перед
   оплатой и страница после оплаты, где человек сам ждёт письмо.

**Пароль** — сведение [S16], [S24], [V:2juq00vrvl0] `[консенсус]`:
1. **Показывать правила заранее** и держать их видимыми всё время, пока поле в фокусе. Ссылка «требования к паролю» не
   годится — её не заметят и не раскроют. **Требования не класть в плейсхолдер и не класть в тултип.**
2. **Дать снять маскировку.** Маскировка нагружает кратковременную память (человек придумывает строку на лету) и
   прячет опечатки; на маленьких экранах ошибок ввода больше (Von Zezschwitz et al., NordiCHI 2014).
   Расхождение `[спорно]`: NN/g [S24] советует **на мобильном показывать пароль по умолчанию** («экран легче прикрыть,
   и самые секретные аккаунты с телефона заводят реже»); GOV.UK [S16] требует **скрывать по умолчанию везде**
   («человек может быть не в приватном месте»). Рекомендация базы: **скрывать по умолчанию, кнопка «показать» рядом** —
   более безопасный вариант, разница в удобстве мала.
3. **Индикатор силы**, а не прогресс по галочкам: Egelman et al. (CHI 2013) — **индикаторы силы мотивируют создавать
   более сильные пароли** [S24]. Индикация прогресса по выполнению требований — не то же самое.
4. **Минимум 8 символов, максимума не ставить, не запрещать символы**; объяснять ограничения; не разрешать
   распространённые пароли [S16].
5. **Не требовать периодической смены пароля** [S16]: люди забывают, выбирают простые вариации предыдущего, хранят
   небезопасно. Смена — только при подозрении на компрометацию. Плюс данные Shay et al. (CHI 2014): «определённые
   комбинации требований к длинным паролям оказались одновременно надёжнее и удобнее традиционной сложной политики».
6. **Если нужна дополнительная безопасность — второй фактор, а не новые ограничения пароля** [S16].
7. **Ограничения одинаковы везде**, где пароль создаётся и вводится; при смене правил продолжать поддерживать старые
   пароли или просить сменить [S16].
8. **Поле «подтвердите пароль» не нужно**, особенно при наличии показа/скрытия [S16]. Если два поля пароля всё же
   есть, их подписи и переключатели показа обязаны различаться («Пароль» / «показать пароль», «Повторите пароль» /
   «показать повторный пароль»).

**Вход** [S16] `[система]`:
1. **Не раскрывать, что именно неверно — логин или пароль**: «раскрытие источника ошибки помогает мошенникам».
2. **Не сохранять введённый пароль при неудачной попытке.**
3. **5–10 попыток** до блокировки аккаунта или дополнительных проверок.
4. Ссылка «Забыли пароль» — **рядом с полем пароля**, не в подвале (B, §11).

**Восстановление** [S16] `[система]`:
1. **Ссылка или код с ограниченным сроком** на зарегистрированную почту или телефон.
2. **Никогда не отправлять пароль письмом.**
3. **Всегда уведомлять письмом о состоявшемся сбросе** — на случай, если его запустил не владелец.
4. **Не использовать секретные вопросы**: они либо слишком тёмные и такие же трудные для памяти, как пароль, либо
   легко узнаваемые («девичья фамилия матери»), либо меняются со временем («любимый цвет»).
5. **Не использовать «подсказку к паролю».**

### 7.8 Страница проверки ответов и страница подтверждения

`[система]` [S14], [S15] — паттерн GOV.UK, переносимый на любой длинный процесс.

**Страница проверки (check answers)** — перед отправкой:
- одна страница проверки непосредственно перед подтверждением для малых и средних процессов; для очень больших —
  проверка в конце каждой секции (полезно, когда секции заполняют разные люди);
- польза: **повышает уверенность** (видно, что всё заполнено) и **снижает уровень ошибок — второй шанс заметить и
  исправить до отправки**;
- **заголовок страницы говорит, что нужно сделать**, иначе кнопку внизу пропускают;
- ясно сказано, что процесс не завершён, пока не подтверждено;
- контент разбит на секции; **показываются только релевантные секции**;
- вопросы **переформулированы в утверждения** (не подписывать каждую строку адреса);
- **кнопка отправки называет действие** («Отправить заявление»), а не «Отправить»;
- **ссылка «Изменить» у каждой секции** со скрытым текстом, описывающим, что именно меняется;
- при возврате **данные предзаполнены, страницы выглядят как в прошлый раз, а «Продолжить» возвращает сразу на
  страницу проверки**, а не прогоняет весь сценарий заново;
- если новый ответ порождает новые вопросы — задать их до возврата;
- пропущенные необязательные поля показывать как **«Не указано»**.

**Страница подтверждения** — после отправки; обязана содержать [S15]: номер обращения (если есть); что произойдёт
дальше и когда; контакты сервиса; ссылки на то, что вероятно понадобится дальше; **способ сохранить запись о
транзакции** (например, PDF).
Отдельное наблюдение [S15]: **часть людей добавляет страницу подтверждения в закладки как квитанцию** — по возможности
разрешать возврат на неё, а если нельзя — осмысленно отвечать на переход по закладке («отследить заявку», «подать
новую», «к кому обратиться при проблеме»).
Предупреждение [S15]: интерактивные элементы внутри цветной панели подтверждения по умолчанию недоступны — контраст
фокуса не дотягивает до 3:1.

## 8. Доступность формы: минимум, который нельзя нарушать

Детально — `../08-accessibility/03-forms-tables-dynamic-content.md` (агент F2). Здесь только то, что относится к
устройству формы и проверяется на этапе проектирования.

1. Форма обёрнута в `<form>`; группы — в `<fieldset>` с `<legend>` [S19], [S9].
2. **У каждого поля видимая подпись, связанная программно**; визуально скрытая подпись — только у поиска, и об этом
   написано в макете для разработчика [V:2juq00vrvl0, 23:39].
3. **Главная трудность для незрячих — порядок табуляции** [S19]; он совпадает с визуальным порядком.
4. **Требования формы объявляются до входа в форму** [S19]; инструкции — в начале формы: «форма как настольная игра,
   правила объясняют до начала, иначе никто не выиграет» [V:2juq00vrvl0, 24:41].
5. Ошибка: `aria-invalid="true"` на поле, `aria-describedby` на сообщение, скрытый префикс «Ошибка:» [S11], [S22].
6. **Не полагаться на цвет**: рамка + иконка + текст [S1], [V:2juq00vrvl0, 03:09].
7. **Не блокировать кнопку** — заблокированный элемент не получает фокус по Tab [S21]; если блокировка неизбежна, он
   обязан оставаться фокусируемым и объяснять причину [V:uEjidraxhAw, 03:05].
8. **Размер цели ≥24×24 CSS-пикселя** (WCAG 2.2 2.5.8); проверка: круг 24 px вокруг каждой цели, круги соседних целей
   не пересекаются — иконки 20 px с зазором 4 px проходят, вплотную нет [V:2juq00vrvl0, 21:36].
9. **Состояния всех контролов нарисованы**: обычное, фокус, отмеченное, ошибка, отключённое [V:2juq00vrvl0, 27:43].
10. **Ошибки документируются на двух уровнях**: в дизайн-системе — общее состояние ошибки компонента (иконка и место
    сообщения); на макете страницы — конкретное условие и точный текст [V:2juq00vrvl0, 27:43].

## 9. Деградация формы

`[система]` [S22] — редкий случай, когда система описывает поведение при отказе.

| Ситуация | Что делать |
|---|---|
| Данные формы **нельзя сохранить** | **Не убирать и не блокировать поля и кнопку.** Сообщить, что форма в режиме «только чтение»; если человек всё же нажмёт отправку — диалог с объяснением |

## Чек-лист

1. Контракт формы заполнен: у каждого поля есть тип контрола, обязательность, формат, правило валидации, текст ошибки,
   значение по умолчанию, `autocomplete`.
2. Каждое поле обосновано: убрано всё, что можно вывести, спросить позже или не спрашивать.
3. Форма в одну колонку; исключения — только поля, образующие одно значение.
4. Ширина каждого поля отражает ожидаемую длину ввода.
5. Подписи над полями, ближе к своему полю, чем к соседнему; подпись 1–3 слова, без двоеточия.
6. Ни в одном поле плейсхолдер не несёт информации, которая понадобится после начала ввода.
7. Обязательность видна до нажатия кнопки; паттерн пометки одинаков во всём продукте.
8. Ввод принимается в любом разумном формате и нормализуется системой; вставка не блокируется; `maxlength` не режет молча.
9. Для каждого поля выбран момент проверки по таблице §4.3, а не один на всю форму.
10. Ошибка показана у поля и видна, пока человек чинит; используется не только цвет.
11. Сводка ошибок вверху есть для длинной формы; фокус переводится; формулировки совпадают; каждая строка — ссылка.
12. Успех показан только там, где он несёт информацию.
13. Кнопка отправки активна до первого нажатия и блокируется после него.
14. На форме одна кнопка отправки; её подпись называет действие и совпадает с именем действия в тосте и в статусе.
15. Кнопок «Очистить»/Reset нет.
16. Введённое сохраняется при ошибке, обновлении страницы, возврате на шаг назад и отказе сервера.
17. Порядок табуляции совпадает с визуальным; поля, требующие клавиатуры, стоят рядом.
18. На шаге не больше 6–7 полей ввода (или есть обоснование).
19. Условные поля появляются после родительского контрола и учитываются в валидации.
20. Форма в модалке — менее пяти полей, без прокрутки, без аккордеонов и вкладок.
21. Перед отправкой длинного процесса есть страница проверки ответов со ссылками «Изменить».
22. Для формы входа: ошибка не раскрывает, что именно неверно; есть ограничение попыток; пароль не сохраняется при
    неудаче.
23. Для формы с паролем: правила видны заранее, есть показ пароля, есть индикатор силы, нет требования периодической смены.
24. У каждого поля есть связанная подпись; форма обёрнута в `<form>`; группы размечены `fieldset/legend`.
25. Описано поведение формы при отказе сохранения, при недоступности всех данных и части данных.

## Открытые вопросы и противоречия

1. **Момент валидации: GOV.UK против NN/g, LukeW и Фридмана.** GOV.UK [S9] прямо запрещает валидацию по уходу из поля
   и требует ждать нажатия кнопки; NN/g [S4] требует «стремиться к inline-валидации всегда, когда возможно»; LukeW
   [S7] измерил выигрыш inline-валидации в 22–42%. Разрешение в §4.3 (выбор момента по типу поля) — **мой синтез, а не
   позиция какого-либо источника**. `[спорно]`
2. **Обязательные поля: GOV.UK «никогда не помечайте звёздочками» против NN/g «помечайте все обязательные
   звёздочкой».** [S13] vs [S3]. Рекомендация базы — правило по большинству Carbon [S19] — тоже синтез. `[спорно]`
3. **Предвыбор в радиогруппе.** NN/g [S28]: «выбирайте одну радиокнопку по умолчанию», потому что снять выбор нельзя и
   человек чувствует потерю контроля. GOV.UK [S9-radio]: «не предвыбирайте варианты — это повышает вероятность, что
   человек не заметит пропущенный вопрос и отправит неверный ответ». Обе стороны признают исходную проблему
   (невозможность вернуться к «ничего не выбрано») и решают её по-разному: NN/g — дефолтом, GOV.UK — обязательным
   вариантом «Ничего из перечисленного». Разбор — `06-input-controls.md` §4. `[спорно]`
4. **Выравнивание левых подписей**: NN/g [S5] против правого выравнивания, Фридман [V:qktwIWZNFY4] за. Данных ни у
   одной стороны нет. `[спорно]`
5. **Порядок кнопок в страничной форме**: агент B (`../03-layout-placement/04` §3) ставит primary первой слева, отмену
   рядом; Primer [S21] ставит отмену **справа** от кнопки отправки в страничной форме и **слева** в диалоге. GOV.UK
   ставит группу `[Сохранить и продолжить] [Сохранить черновик]` слева. Расхождение не разрешено; правило B остаётся
   позицией базы. `[спорно]`
6. **Порог сводки ошибок**: Primer [S22] — от трёх ошибок; GOV.UK [S10] — всегда. Порог «длиннее экрана» в §4.5 — мой
   вывод. `[мнение]`
7. **Маскировка пароля на мобильном**: NN/g [S24] — показывать по умолчанию; GOV.UK [S16] — скрывать. `[спорно]`
8. **Baymard не прочитан.** Статьи `baymard.com/blog/avoid-multi-column-forms` и `checkout-form-single-column` лежат в
   кэше, но отдают заглушку пейволла; количественные данные Baymard по одноколоночным формам, inline-валидации и
   пометке обязательных полей в базу не попали. Заметный пробел: Baymard — второй по цитируемости источник по формам
   после NN/g. Кандидаты доступа: браузерный агент (`claude-in-chrome`), archive.org.
9. **Порог «6–7 полей на шаг»** [V:qktwIWZNFY4] подан как опыт консультанта, без исследования; сам автор допускает
   исключения для энтерпрайза. `[мнение]`
10. **Числа 400 мс / ×3 / ≥30%** прочитаны Фридманом со слайда-сводки, первоисточники в докладе не названы. При
    переносе в продукт проверять. `[мнение]` из единичного источника.
11. **Inline-редактирование в таблицах — зона без конвенций**: Carbon прямо пишет, что консолидированного руководства
    у них нет [S19]. Тема для волны 3 (кандидаты: Airtable, Notion, Linear, Salesforce Lightning inline edit,
    Ant Design ProTable).
12. **Автопереход фокуса между полями** (страна → индекс, поля кода из SMS) рекомендован Фридманом и Тидвелл
    (`../01-foundations/01-principles-and-laws.md` §6.12), но известно, что он ломает часть скринридеров. Данных о
    масштабе проблемы не найдено.
13. **Условное раскрытие и ассистивные технологии**: и GOV.UK, и Primer отмечают нехватку исследований. Открытый
    вопрос обеих систем, не только базы.
14. **Расхождение с агентом B по порогу модалки не возникло**: B дал «до ~5 полей» как `[мнение]`, Carbon независимо
    даёт «менее пяти полей — диалог, более пяти — боковая панель» [S19]. Совпадение двух независимых источников
    поднимает уровень правила до `[консенсус]` — это уточнение к файлу B, а не противоречие.
