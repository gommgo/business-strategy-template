## Выжимка для агента

1. **Каркас приложения (app shell) = полосы (bars) + рейки (rails) + панели (panes).** Шапка и панель действий —
   полосы; навигация слева и инспектор справа — рейки; содержимое — панели. → §1 `[система]`
2. **Каркас одинаков на всех экранах.** Меняется только основная область. → §1 `[система]`
3. **Панель-инспектор (inspector panel) справа — общий регион, а не привилегия редакторов**: свойства и действия
   выбранного объекта в списке, карточке, дашборде, канвасе. → §1.3 `[система]`
4. **Шапка страницы (page header) — обязательная зона всех экранов кроме входа и канваса**: путь назад,
   заголовок, статус, действия. → §2 `[консенсус]`
5. **Одно главное действие страницы — primary-кнопка справа в шапке страницы.** Остальные — вторичные рядом или
   в меню «…». → §2 `[система]`
6. **Заголовок страницы-списка — имя типа объекта во множественном числе** («Заказы»). Заголовок карточки — имя
   объекта. → §2 `[система]`
7. **Дашборд — один экран без прокрутки или с одной прокруткой**, сверху 3–6 ключевых показателей, ниже
   динамика и списки требующего внимания. Не строить дашборд из круговых диаграмм и «спидометров». → §3 `[консенсус]`
   (число 3–6 не измерено)
8. **Список объектов (index): фильтры над таблицей или слева, массовые действия появляются над таблицей при
   выборе, пагинация под таблицей.** → §4 `[консенсус]`
9. **Колонки таблицы — по важности слева направо**; первая колонка — идентификатор и она липкая при
   горизонтальной прокрутке. → §4 `[мнение]`
10. **Не открывать модалку поверх таблицы для просмотра или правки строки** — она закрывает контекст, ради
    которого таблица и нужна; открывай боковую панель. Раскрытие строки аккордеоном — только для коротких таблиц:
    раскрытые строки не закрывают и они сдвигают соседей (NN/g 2022) — канон
    `../04-components-patterns/01-data-tables.md` §4.4. → §4, §6 `[мнение]`
11. **Карточка объекта: шапка (крошки/назад, имя, статус, действия) → вкладки → основная колонка + правая
    колонка метаданных.** → §5 `[консенсус]`
12. **Создание и редактирование: по умолчанию отдельная страница.** Модалка — только для короткого
    самодостаточного ввода (до ~5 полей) без нужды в контексте. Боковая панель — когда контекст нужен рядом. → §6 `[консенсус]`
13. **Мастер нужен, когда шаги обязательны, их порядок задан и процесс делается редко.** Иначе — одна страница с
    секциями. → §7 `[консенсус]`
14. **GOV.UK: одна вещь на страницу.** Один вопрос на экран снижает нагрузку и упрощает валидацию. → §7 `[система]`
15. **Настройки: левое подменю разделов, внутри — секции, «опасная зона» внизу отдельным блоком.** → §8;
    подробно — `../04-components-patterns/09-settings-permissions-admin.md` §4 `[система]`
16. **Master-detail (split view) применяй, когда пользователь перебирает много объектов подряд.** Пропорции по
    Material 3: medium — 50/50, expanded — фиксированная панель 360dp, large/XL — 412dp. → §9 `[система]`
17. **Редактор/канвас: инструменты слева, свойства справа, канвас в центре, режимы и файл сверху.** Канвас —
    единственная гибкая панель. → §10 `[система]`
18. **Вход и регистрация: одна колонка по центру, минимум полей, без маркетингового обвеса.** → §11 `[консенсус]`
19. **Не больше трёх панелей одновременно** (Material 3). → §1 `[система]`
20. **На узком экране: две панели → две страницы; инспектор → вниз или в bottom sheet; сайдбар → drawer или
    нижняя панель на 3–5 пунктов.** → §13 `[система]`
21. **Сложные приложения: контекст важнее чистоты.** «Resist the temptation to use modals and wizards on complex
    apps… context is king». → §6, §7 `[мнение]`
22. **Поддерживай безопасное исследование**: копия объекта, «что если», сравнение вариантов — без
    interaction cost. → §12 `[мнение]`
23. **Шапка страницы и вкладки не повторяют навигацию**: вкладки объекта — это представления объекта, а не копия
    разделов приложения. → §5 `[консенсус]`
24. **Всё содержимое живёт в панели** («All content must be in a pane»), и хотя бы одна панель должна быть
    гибкой по ширине. → §1 `[система]`

## 1. Каркас приложения (app shell)

### 1.1 Определение и регионы

**Каркас приложения (app shell)** — постоянная оболочка, одинаковая на всех экранах: навигация, шапка,
утилитарная зона, области содержимого. Material 3 называет эту конструкцию **scaffold** — «фундаментальная
структура дизайна UI, дающая стандартную платформу для сборки ключевых компонентов экрана» [S5]. `[система]`

M3 делит каркас на три типа регионов [S5]:

| Регион | Определение M3 | Что размещают |
|---|---|---|
| **Bars** (полосы) | Обрамляют экран и помогают навигировать; могут покрывать одну панель или всю ширину окна | App bar (заголовок и **1–2 существенных действия**), navigation bar (**3–5** основных представлений на узких экранах), нижняя панель действий |
| **Rails** (рейки) | Периметр вокруг панелей или плавающий над ними | Ведущая (левая) рейка — навигационная рейка; **замыкающая (правая) рейка — «поддерживающие контролы и действия, которые изменяют содержимое панели или относятся к нему»**; верх и низ — тулбары, поля ввода, FAB |
| **Panes** (панели) | Контейнеры содержимого: «**All content must be in a pane**» | Список, деталь, вспомогательная панель, инспектор |
| **Safety region** | Зоны системного UI (статус-бар, жестовая полоса) | «The safety region shouldn't contain primary content» |

Carbon перечисляет те же зоны в терминах «screen regions»: 1) Header, 2) Global sidenav, 3) Local sidenav,
4) Dropdown menu, 5) Content, 6) Footer, 7) Dialog — и подчёркивает: «В UI-раскладке пользователи ожидают
находить определённые типы контента в определённых местах. Особенно важно, чтобы эти зоны были консистентны
между устройствами и адаптировались на брейкпоинтах» [S4]. `[система]`

### 1.2 Карта каркаса веб-приложения

```
┌──────────────────────────────────────────────────────────────────────────────┐
│ ГЛОБАЛЬНАЯ ШАПКА (bar)                                                       │
│ логотип · переключатель контекста │ поиск │ уведомл. · помощь · профиль       │
├──────────────┬───────────────────────────────────────────┬───────────────────┤
│              │ ШАПКА СТРАНИЦЫ (page header)              │                   │
│ НАВИГАЦИЯ    │ крошки/назад · H1 · статус · действия     │ ПАНЕЛЬ-ИНСПЕКТОР  │
│ (левая рейка)│──────────────────────────────────────────-│ (правая рейка)    │
│              │ ВКЛАДКИ / ФИЛЬТРЫ (опционально)           │ свойства и        │
│ разделы,     │───────────────────────────────────────────│ действия для      │
│ группы,      │                                           │ ВЫБРАННОГО        │
│ настройки    │ ОСНОВНАЯ ОБЛАСТЬ (пане/панели)            │ объекта           │
│ внизу        │ список / карточка / канвас / деталь       │                   │
├──────────────┴───────────────────────────────────────────┴───────────────────┤
│ ЛИПКАЯ ПАНЕЛЬ ДЕЙСТВИЙ (bar) — только для длинных форм и редакторов          │
└──────────────────────────────────────────────────────────────────────────────┘
```

Обязательные регионы: глобальная шапка, навигация, основная область. Опциональные: шапка страницы (нет на
входе и на полноэкранном канвасе), вкладки, инспектор, нижняя панель действий, футер (в приложениях обычно
отсутствует или содержит только версию и правовые ссылки).

### 1.3 Панель-инспектор (inspector panel)

**Панель-инспектор** — правая панель со свойствами и действиями для **объекта, выбранного в основной области**.
Это общий регион каркаса, а не деталь редакторов: M3 описывает содержимое замыкающей рейки как «supporting
controls or actions that modify or relate to the content in a pane» [S5]. `[система]`

| Тип экрана | Что показывает инспектор |
|---|---|
| Список объектов | Сводка выделенной строки и быстрые действия без перехода на карточку |
| Карточка объекта | Метаданные: владелец, даты, теги, связанные объекты, история изменений |
| Дашборд | Настройки выбранного виджета, период, источник данных |
| Канвас / редактор | Свойства выделенного элемента, слои, стили |
| Таблица с массовым выбором | Что выбрано и какие операции доступны над выборкой |

**Правила** `[консенсус]` (сводка [S5], [S4], [S2]):

1. Инспектор **всегда справа**, навигация — слева; менять местами нельзя.
2. Инспектор привязан к **выделению**, а не к странице. Нет выделения — осмысленное пустое состояние
   («Выберите строку, чтобы увидеть детали»), а не пустая полоса.
3. Инспектор — **со-планарная** панель: «persistent utilities like tool panels should be co-planar with primary
   content» [S5]. Плавающими (floating) делают только временное — диалоги.
4. Ширина инспектора фиксированная, основная область — гибкая: «All layouts need at least one flexible pane» [S5].
5. Сворачивается; состояние запоминается между сессиями («persistent pane resizing» сохраняет предпочтение даже
   при смене брейкпоинта [S5]).
6. На узком экране уходит вниз под контент или в bottom sheet (стратегия reflow) [S5].
7. **Не больше трёх панелей одновременно**: «Don't use more than three panes» [S5].

### 1.4 Поведение панелей

Carbon различает три поведения вертикальных панелей [S4] `[система]`:

| Тип | Поведение |
|---|---|
| Flexible | Есть свёрнутое и развёрнутое состояние; при разворачивании либо сжимает контент и сетку, либо выталкивает контент за край окна |
| Fixed | Статическая ширина, не сворачивается, живёт вне адаптивной сетки |
| Floating | Плавает над контентом, не влияет на сетку, перекрывает элементы под собой и обязана закрываться пользователем |

M3 добавляет три способа показа нескольких панелей: **co-planar** (рядом), **floating** (поверх), **docked**
(прижата к краю, например bottom sheet), и три адаптивные стратегии перестроения: **show and hide**,
**levitate**, **reflow** [S5].

**Ключевое решение принимается один раз на всё приложение:** сворачивание сайдбара сжимает контент или наезжает
на него; инспектор сжимает контент или наезжает. Разное поведение на разных экранах ломает ожидания.

### 1.5 Каркас и брейкпоинты

Число панелей зависит от ширины окна [S5] `[система]`:

| Брейкпоинт M3 | Ширина (dp) | Рекомендуемое число панелей | Что это значит для каркаса |
|---|---|---|---|
| Compact | < 600 | 1 | Нижняя панель или drawer; инспектора нет |
| Medium | 600–839 | 1 (допустимо 2) | Рейка с иконками; две панели только для контента низкой плотности |
| Expanded | 840–1199 | 2 | Сайдбар + контент, либо контент + инспектор |
| Large | 1200–1599 | 2 | Сайдбар + контент + (инспектор при сворачивании сайдбара) |
| Extra-large | ≥ 1600 | 2, допустимо 3 | Сайдбар + контент + инспектор одновременно |

Практический вывод: **постоянный инспектор рядом с сайдбаром и контентом появляется примерно от 1440–1600px**;
ниже — либо сворачиваемый сайдбар, либо выдвижной инспектор.

## 2. Шапка страницы (page header)

Универсальная зона, одинаковая на всех экранах внутри приложения.

### 2.1 Состав

| Зона | Элемент | Обязательность |
|---|---|---|
| Строка над заголовком | Хлебные крошки **или** «Назад» (не оба) | Обязательно при иерархии; см. `../02-ia-navigation/02-navigation-patterns.md` §4 |
| Левая часть | **H1 — заголовок страницы** | Всегда |
| Сразу после заголовка | Статус объекта (бейдж) | Для карточек объектов |
| Под заголовком | Подзаголовок / краткое описание | Опционально |
| Правая часть | **Одна primary-кнопка** + 1–2 вторичных + меню «…» | Обычно |
| Под всем | Вкладки объекта | Опционально |

Состав подтверждается тремя системами независимо:
- Polaris `Page`: `backAction`, `title`, `titleMetadata` («важная информация о статусе, показанная сразу после
  заголовка»), `subtitle`, `primaryAction`, `secondaryActions`, `actionGroups`, `pagination` [S1]. `[система]`
- Primer `PageHeader`: «область заголовка вверху основной контентной зоны, которая показывает пользователю, где
  он находится. Может также содержать навигационные элементы — хлебные крошки или ссылку на уровень вверх»;
  слоты TitleArea, Description, Actions, Navigation [S6]. `[система]`
- Carbon: при drill-down «новая страница будет включать breadcrumb пути назад **над заголовком**» [S3]. `[система]`

### 2.2 Правила

1. **Заголовок обязателен всегда.** Polaris: «Always provide a title for the page header» [S1].
2. **Заголовок списка — имя типа объекта во множественном числе**: «For a list of orders, the page title should
   be "Orders"». Заголовок не обрезается [S1]. `[система]`
3. **Страница организуется вокруг одной главной активности**; если это одно действие — оно primary-кнопка в
   шапке страницы. Прочие действия уровня страницы — вторичные там же [S1]. `[система]`
4. **Подписи действий — {глагол}+{существительное}**: «Create order», не «Create». Если существительное
   совпадает с объектом страницы, допустим один глагол: на странице списка заказов — «Import», «Export». Без
   артиклей и лишних слов [S1].
5. **Breadcrumbs — когда у страницы есть родитель** [S1]; но не при иерархии в 1–2 уровня [S12].
6. **Пагинация по объектам того же типа** («предыдущий / следующий заказ») — в шапке карточки объекта, если
   пользователь просматривает объекты подряд [S1].
7. **Статус — сразу после заголовка**, не в теле страницы: это первое, что нужно знать об объекте [S1].
8. **Заголовок страницы не повторяется внутри контента** — см. `04-placement-conventions-and-redundancy.md`.

### 2.3 Антипримеры

- Заголовок страницы дублирует название активного пункта меню и ещё раз — заголовок первой карточки.
- Primary-кнопка внизу страницы, а в шапке — ничего: пользователь не видит главного действия без прокрутки.
- Три равнозначные кнопки в шапке: непонятно, что главное (см. `03-hierarchy-and-attention.md` §4).
- Вкладки над заголовком, а не под ним: заголовок теряет связь со страницей.
- Хлебные крошки и «Назад» одновременно.

## 3. Обзор / дашборд

### 3.1 Что такое дашборд

**Определение NN/g:** «Дашборды — наборы визуализаций данных, представленные в **одноэкранном виде**, дающие
информацию с одного взгляда, по которой пользователи могут быстро действовать» [S10]. Цель — не исследование
данных, а быстрое потребление с минимумом взаимодействия и когнитивной обработки. Дашборд ≠ портал (портал —
точка входа в набор ресурсов и инструментов). `[исследование]`

Два типа [S10]:

| Тип | Что делает | Примеры |
|---|---|---|
| **Операционный** | Даёт критичную информацию для действий прямо сейчас; данные непрерывно обновляются | Мониторинг серверов, витальные показатели, очередь обращений, диспетчеризация |
| **Аналитический** | Даёт обзор для анализа и решений без срочности | Продажи за период, маркетинговая аналитика |

### 3.2 Зоны и порядок

```
[Шапка страницы: «Обзор», период, действия]
[Строка ключевых показателей: 3–6 плиток]
[Динамика: 1–2 линейных/столбчатых графика]
[Требует внимания: короткие списки с переходом в раздел]
[Дополнительно: разбивки, вторичные метрики]
```

Правила `[консенсус]`:

1. **3–6 ключевых показателей вверху.** Верх экрана получает непропорционально много внимания: более 42% времени
   просмотра приходится на верхние 20% страницы, более 65% — на верхние 40% [S25]. Всё, что важно, ставится
   выше сгиба.
2. **Показатель = число + подпись + изменение.** Не украшать плитки кольцевыми диаграммами.
3. **Только длина и 2D-позиция кодируют величину** [S10]: столбчатые диаграммы, линейные графики, scatter plot.
   Круговые, кольцевые, tree map и «спидометры» «в целом не рекомендуются для быстрой передачи количественных
   отношений»; 3D искажает и площадь, и выравнивание. `[исследование]`
4. **Цвет и форма — для категорий, не для величин**: «люди не воспринимают разные цвета как упорядоченные» [S10].
   До 4.5% населения имеет нарушения цветовосприятия (~8% мужчин против ~0.5% женщин) [S10].
5. **Каждый блок ведёт в раздел** — дашборд это точка входа, а не тупик.
6. **Период — один на весь экран**, в шапке страницы, а не у каждого виджета.
7. **Дашборд плотнее обычного клиентского экрана.** Refactoring UI прямо разрешает: «если вы проектируете
   дашборд, где много информации должно быть видно одновременно, упаковать её так, чтобы всё влезло на один
   экран, может стоить того, чтобы дизайн ощущался более насыщенным» [S26]. `[мнение]`

### 3.3 Антипримеры

- Дашборд из восьми кольцевых диаграмм [S10].
- «Спидометры», занимающие много места и передающие одно число [S10].
- 20 плиток показателей без иерархии: «важно всё» = «важно ничего» (см. `03-hierarchy-and-attention.md`).
- Дашборд как первый экран приложения, где пользователю на самом деле нужен список работы на сегодня.
- Виджеты с собственными переключателями периода, не согласованными между собой.

## 4. Список объектов (index)

### 4.1 Зоны и порядок

```
[Шапка страницы: «Заказы» · [Создать заказ] · [⋯]]
[Вкладки-представления: Все | Новые | В работе]        (опционально)
[Строка инструментов: поиск · фильтры · вид · экспорт]
[Панель массовых действий]                              (появляется при выборе)
[ТАБЛИЦА: чекбокс | колонки по важности | действия строки]
[Пагинация]
```

### 4.2 Правила

1. **Главное действие — «Создать …» — primary в шапке страницы справа** [S1]. `[система]`
2. **Фильтры сверху, если их мало (до 4–5) и они простые**; **слева в панели, если их много, они многозначные и
   применяются подолгу** (фасеты). Primer описывает сайдбар с фильтрами как отдельный паттерн, который на узком
   экране сворачивается в меню (ориентир: до 15 пунктов в меню, дальше — bottom sheet) [S6]. `[система]`
3. **Чекбоксы выбора — первая колонка**, действия строки — последняя (см.
   `04-placement-conventions-and-redundancy.md`).
4. **Колонки по важности слева направо.** «Горизонтальная прокрутка (всё ещё) требует больше усилий, чем
   вертикальная… используйте хорошие дефолты: то, с чем пользователи взаимодействуют чаще всего, должно быть в
   видимой зоне без горизонтальной прокрутки» [V:23AQBZzDUIo]. `[мнение]`
5. **Сохраняй контекст при показе деталей** [V:23AQBZzDUIo]: липкие заголовки колонок при вертикальной прокрутке;
   **первая колонка следует за пользователем при горизонтальной прокрутке** (в ней уникальное имя или
   идентификатор). «Вместо модалок, закрывающих таблицу, для правки или просмотра деталей попробуйте раскрывать
   строку вертикально аккордеоном». `[мнение]`
6. **Говори по-человечески**: заменять автогенерируемые ID и коды на читаемое [V:23AQBZzDUIo].
7. **Массовые действия появляются над таблицей при выделении** и показывают, сколько выбрано; при снятии выбора
   панель исчезает.
8. **Пагинация под таблицей.** Дублировать сверху — только при очень длинных страницах (см.
   `04-placement-conventions-and-redundancy.md` §7).
9. **Состояние списка живёт в URL** (фильтры, сортировка, страница) и восстанавливается при возврате из
   карточки [S3].
10. **Для больших таблиц дай управление колонками**: скрытие ненужных и переупорядочивание, причём для таблиц со
    многими колонками — через **переупорядочиваемый список имён колонок**, а не drag-and-drop через несколько
    экранов [V:s7nvF1PuAWY]. `[мнение]`

### 4.3 Сколько данных влезает

Прямая формулировка NN/g: «Как отобразить большие таблицы при ограниченном экране? Ответ: **никак**. Видеть
таблицу целиком редко относится к задаче пользователя. Дизайнеру надо провести анализ задачи и дать инструменты
для её выполнения» [V:s7nvF1PuAWY]. Даже на восьми 24-дюймовых мониторах найдётся слишком большая таблица, и
всё равно «у человека не хватит объёма рабочей памяти, чтобы вместить всё это содержимое». `[мнение]`

### 4.4 Антипримеры

- Кнопка «Создать» внизу под таблицей или над фильтрами слева.
- Панель массовых действий, постоянно висящая с отключёнными кнопками.
- Модалка с деталями строки поверх таблицы [V:23AQBZzDUIo].
- 25 колонок по умолчанию без возможности скрыть.
- Фильтры, сбрасывающиеся при возврате из карточки объекта.

## 5. Карточка объекта (detail / record)

### 5.1 Зоны и порядок

```
[Крошки или «Назад к списку»]
[H1 — имя объекта] [бейдж статуса]     [Primary] [Вторичное] [⋯]
[Подзаголовок: тип, ключевой идентификатор]
[Вкладки: Обзор | Активность | Файлы | Настройки]
┌────────────────────────────────┬───────────────────────┐
│ ОСНОВНАЯ КОЛОНКА               │ БОКОВАЯ КОЛОНКА       │
│ ключевые блоки, таблицы,       │ метаданные, связанные │
│ формы, история                 │ объекты, участники    │
└────────────────────────────────┴───────────────────────┘
```

Пропорции основной и боковой колонок: **две трети / одна треть** — рекомендация GOV.UK для большинства типов
страниц [S7] `[система]`; M3 для supporting pane: «основная область занимает большую часть окна, обычно около
двух третей» [S5] `[система]`. Совпадение двух независимых систем делает это `[консенсус]`.

### 5.2 Правила

1. **Статус — рядом с заголовком** [S1].
2. **Одна primary-кнопка** — самое частое действие над объектом («Сохранить», «Опубликовать», «Подтвердить»).
3. **Вкладки — представления объекта, а не копия разделов приложения.** Смешивать типы вкладок нельзя [S11].
4. **Вкладок 2–7, один ряд, подписи 1–2 слова** [S11].
5. **Боковая колонка — метаданные, не действия.** Действия живут в шапке страницы и в строках блоков.
6. **Пагинация «предыдущий / следующий объект»** — если пользователь ходит по объектам подряд [S1].
7. **Не прячь ключевые данные за вкладку.** Содержимое невыбранных вкладок должно быть дополнительным, а не
   критичным [S11].
8. **Связанные объекты — ссылки, а не встроенные таблицы**, если их много.

### 5.3 Антипримеры

- Вкладки, дублирующие разделы главного меню.
- Статус объекта в правой колонке ниже сгиба.
- Десять вкладок в два ряда [S11].
- Кнопка «Удалить» рядом с «Сохранить» одинакового размера (см. `04-placement-conventions-and-redundancy.md` §5).
- Основная колонка на всю ширину 1920px с текстом в 200 символов на строку (см. `02-grid-spacing-density.md`).

## 6. Создание и редактирование: страница, модальное окно или боковая панель

### 6.1 Таблица решений

| Критерий | Страница | Модальное окно | Боковая панель |
|---|---|---|---|
| Полей | 6 и больше | до ~5 | 3–10 |
| Нужен контекст (данные под формой) | не обязателен | **не нужен** | **нужен** |
| Есть шаги / зависимые поля | да | нет | иногда |
| Действие частое, повторяется подряд | нет | иногда | **да** |
| Требуется прямая ссылка (URL) | **да** | нет | опционально |
| Загрузка файлов, длинные списки | **да** | нет | иногда |
| Есть вложенные диалоги | **да** (никогда не вкладывать модалки) | нет | нет |
| Мобильный | страница | полноэкранный диалог | нижняя шторка |

### 6.2 Обоснование

**Модальные окна дорого стоят** [S9] `[исследование]`: требуют немедленного внимания; прерывают рабочий процесс;
заставляют забыть контекст; добавляют лишнюю цель — закрыть окно; **закрывают контент позади**, из-за чего
иногда нечем ответить на вопрос диалога.

Когда модалка оправдана [S9]:
1. Важное предупреждение, предотвращение или исправление критической, необратимой ошибки. Критерий: станет ли
   проблему легче или труднее исправить, если увести внимание? **Ошибку в форме показывать на странице рядом с
   полем, а не в модалке.**
2. Запрос информации, критичной для продолжения начатого процесса.
3. Разбиение сложного процесса на шаги — **но**: «если для этого изначально требуется несколько шагов, это,
   вероятно, оправдывает выделение **целой страницы**».
4. Запрос информации, существенно сокращающей дальнейшую работу.
5. **Не** для несущественного вне текущего потока (подписки на рассылку — «visceral disdain» в тестах).
6. **Не** прерывать модалками процессы с высокими ставками (оформление заказа).

**Для сложных рабочих приложений правило жёстче** [V:P1CYZ65b5SA] `[мнение]`: «**Сопротивляйтесь искушению
использовать модалки и мастера в сложных приложениях.** Почему? Они прячут ту контекстную информацию, которая
поддерживает рабочую память пользователей… Хотя модалки и мастера иногда уместны, **чаще всего контекст —
король**». Вместо них — «паттерны, позволяющие редактировать или добавлять информацию **в контексте уже
существующих данных**». Формулировка, которую стоит держать в голове: «Приложение само работает как форма
внешней памяти для пользователя».

Иллюстрация оттуда же: настройку автоматического резервного копирования делают раз в квартал; пользователь хочет
посмотреть, как он делал это в прошлый раз, — модалка это скрывает.

### 6.3 Правила для каждого варианта

**Страница:**
- Своя шапка с заголовком («Новый заказ») и путём назад.
- Действия внизу формы, выровнены по левому краю полей (см. `04-placement-conventions-and-redundancy.md` §3).
  При длинной форме — липкая панель действий внизу.
- Форма в одну колонку (см. `02-grid-spacing-density.md`).

**Модальное окно:**
- Заголовок = действие («Переименовать проект»).
- Один экран без прокрутки по возможности; **никаких вложенных модалок**.
- Кнопки внизу справа (десктопная конвенция диалогов, см. `04-placement-conventions-and-redundancy.md` §4).
- Закрытие по Esc и по крестику; при несохранённых изменениях — подтверждение.

**Боковая панель:**
- Не перекрывает то, что редактируется; при необходимости сжимает контент.
- Имеет заголовок и явные «Сохранить»/«Отмена».
- Состояние ширины запоминается [S5].
- Подходит для повторяющихся правок подряд: панель остаётся, меняется выбранный объект.

### 6.4 Антипримеры

- Модалка на 20 полей с внутренней прокруткой.
- Модалка поверх таблицы, закрывающая строки, с которыми надо сверяться [V:23AQBZzDUIo].
- Боковая панель, которая закрывает сам объект, который редактируешь.
- Создание объекта в модалке, на которое потом нужно дать ссылку коллеге.

## 7. Мастер (wizard)

### 7.1 Когда нужен

| Нужен мастер | Не нужен мастер |
|---|---|
| Шаги обязательны и их порядок задан | Порядок произвольный |
| Процесс выполняется редко, пользователь не помнит его | Процесс ежедневный |
| Каждый следующий шаг зависит от предыдущего | Поля независимы |
| Нужно не дать пользователю отправить неполные данные | Черновик допустим |
| Пользователь — новичок в этой задаче | Пользователь — эксперт, знает все поля |

**Важное предупреждение для сложных приложений** [V:P1CYZ65b5SA]: мастера прячут уже сделанную работу; в
экспертных инструментах это вредит. Для эксперта лучше одна страница с секциями и оглавлением, где видно всё
сразу. `[мнение]`

**Аргумент в пользу мастера с другой стороны** — GOV.UK «одна вещь на страницу» [S8] `[система]`: «Задавать по
одному вопросу на страницу помогает пользователям понять, что от них требуется, и сосредоточиться на конкретном
вопросе и ответе». Это относится к сервисам, где пользователь неподготовлен и заходит однократно.

Разрешение противоречия: **мастер — для редких задач неподготовленных пользователей; одна страница с секциями —
для частых задач подготовленных.** `[спорно]` — источники смотрят на разные аудитории.

### 7.2 Анатомия

```
[Шапка: название процесса] [Выход / Сохранить черновик]
[Индикатор шагов: 1 ─ 2 ─ 3 ─ 4, текущий помечен, названы все]
[Содержимое шага — одна колонка]
[Назад]                                      [Далее / Завершить]
```

Правила:
1. **Шаги названы, а не только пронумерованы** — пользователь должен видеть, что впереди [S17: механизм «шаги»].
2. Индикатор шагов — горизонтально над содержимым либо вертикальным списком слева [S17].
3. **Выход без потери данных**: «Сохранить и вернуться позже» (формулировка GOV.UK [S8]).
4. Назад не теряет введённое.
5. Финальный шаг — **страница проверки** («Check answers») со всеми введёнными данными и ссылками «Изменить»
   к каждому блоку [S8].
6. Один вопрос или одна группа связанных полей на шаг [S8].
7. Заголовок шага не повторяется между шагами: «Do not use the same page heading across multiple pages» [S8].

## 8. Настройки

### 8.1 Зоны

```
[Шапка страницы: «Настройки»]
┌──────────────────┬───────────────────────────────────────┐
│ ЛОКАЛЬНОЕ МЕНЮ   │ [Секция: Профиль]                     │
│ Профиль          │  поля …                               │
│ Уведомления      │ [Секция: Безопасность]                │
│ Безопасность     │  поля …                               │
│ Команда          │                                       │
│ Биллинг          │ ─────────────────────────────────     │
│ Интеграции       │ [ОПАСНАЯ ЗОНА]                        │
│                  │  Удалить рабочее пространство         │
└──────────────────┴───────────────────────────────────────┘
```

### 8.2 Правила

1. **Локальное меню слева** — это конвенция: «Local navigation — вдоль левой стороны на десктопных сайтах» [S18].
   Каждый пункт меняет URL, поэтому это навигация, а не вкладки (NN/g не рекомендует вертикальные ряды вкладок
   [S11]).
2. **Внутри раздела — секции с заголовками**, отделённые пространством. Пространство вместо линий: «пространство
   обозначает группы связанной информации и создаёт логические секции без линий и прочих графических
   разделителей» [S16], то же у Carbon [S4] и Polaris [S2]. `[консенсус]`
3. **Сохранение: одна кнопка на страницу или автосохранение.** Кнопка «Сохранить» у каждой секции допустима
   только если секции сохраняются независимо и это видно (см. `04-placement-conventions-and-redundancy.md` §10).
4. **«Опасная зона» — внизу, отдельным блоком с рамкой, с деструктивными действиями**: удаление аккаунта,
   передача владения, отключение сервиса. Обоснование: GOV.UK — warning-кнопка «работает, только если
   использовать крайне редко», применяется «только для действий с серьёзными разрушительными последствиями,
   которые пользователь не может легко отменить», и **только на финальном подтверждении**, а первичный вызов —
   кнопка другого стиля [S19]. Отдельная зона внизу реализует и требование расстояния от безопасных кнопок
   (см. `04-placement-conventions-and-redundancy.md` §5). `[консенсус]`
5. **Настройки не смешиваются с рабочими разделами**: в главной навигации это отдельная группа внизу [S18].
6. **Длинный раздел настроек — с оглавлением и якорями** (см. `../02-ia-navigation/02-navigation-patterns.md` §8).
7. **Прогрессивное раскрытие**: редкие опции — в «Дополнительно», но не прятать то, чем пользуются регулярно [S15].

## 9. Master-detail (split view)

### 9.1 Когда применять

Применять, когда пользователь **перебирает много объектов подряд** и каждому нужен только беглый взгляд: почта,
чаты, файлы, обращения, логи, заявки на модерации. M3 перечисляет типовые пары: сообщения + переписка, файловый
браузер + открытая папка, исполнитель + альбом, **настройки + категория настроек**, входящие + выбранное
письмо [S5].

Не применять, когда: объект сложный и требует всей ширины; список короткий (проще одна таблица); переход в
объект редкий.

### 9.2 Пропорции и поведение

Material 3 [S5] `[система]`:

| Брейкпоинт | Видимые панели | Ширины |
|---|---|---|
| Compact (< 600dp) | 1 | Список **или** деталь |
| Medium (600–839) | 1 рекомендуется, допустимо 2 | При двух — по 50% ширины окна; кастомные ширины избегать; навигация переносится в нижнюю панель, чтобы не отнимать ширину |
| Expanded (840–1199) | 2 | Fixed-and-flexible: фиксированная панель по умолчанию **360dp** |
| Large (1200–1599) | 2 | Фиксированная панель **412dp** |
| Extra-large (≥ 1600) | 2 (допустима 3-я как side sheet, макс. 400dp) | Фиксированная **412dp** |

Поведение [S5]:
- **Кнопка «Назад» появляется в деталях только в однопанельной раскладке.**
- **Состояние «выбрано» показывается в списке только в двухпанельной раскладке.**
- При отсутствии выбора: одна панель показывает список; две панели показывают плейсхолдер в панели деталей.
- При переходе из двух панелей в одну обычно показывается деталь с app bar; «Consistency is key: если раскладка
  раньше показывала список, она должна вернуться к списку при возврате к одной панели».
- Состояние (прочитано/не прочитано, выделение) сохраняется при навигации между деталями.
- Разделитель между панелями — **drag handle**; поведение «persistent» запоминает ширину, в том числе после
  смены брейкпоинта.

### 9.3 Supporting pane — не то же самое

M3 разводит два паттерна [S5] `[система]`: **supporting pane** применяют, «когда вторичный контент осмыслен
только в связке с первичным» (комментарии к документу, очередь видео, палитра инструментов); **list-detail** —
когда между объектами отношение «родитель–ребёнок» и деталь осмысленна сама по себе.

| Признак | List-detail | Supporting pane |
|---|---|---|
| Смысл вторичной панели отдельно | Есть | Нет |
| Что в ней | Другой объект | Дополнение к текущему |
| Размещение на compact/medium | Заменяет список | **Под** основной панелью или bottom sheet |
| Размещение на expanded | Рядом, 2 панели | Сбоку, фиксированная 360dp |

## 10. Редактор / канвас

### 10.1 Зоны

```
[Верхняя полоса: файл/проект · режимы · отмена/повтор · поделиться · [Сохранить]]
┌────────┬─────────────────────────────────────┬──────────────────┐
│ ИНСТРУ-│                                     │ СВОЙСТВА         │
│ МЕНТЫ  │            КАНВАС                   │ выделенного      │
│ слои   │      (единственная гибкая панель)   │ элемента         │
│ (слева)│                                     │ (инспектор)      │
└────────┴─────────────────────────────────────┴──────────────────┘
[Нижняя полоса: масштаб, координаты, статус]
```

### 10.2 Правила

1. **Канвас — единственная гибкая панель**; боковые панели фиксированные [S5].
2. **Инструменты слева, свойства справа** — это частный случай общей карты каркаса (§1): ведущая рейка —
   навигация/инструменты, замыкающая — то, что «изменяет содержимое панели или относится к нему» [S5].
3. **Обе боковые панели сворачиваются**, состояние запоминается [S5].
4. **Верхняя полоса содержит только то, что относится ко всему документу**; всё, что относится к выделению, —
   в правой панели.
5. **Инспектор без выделения** показывает свойства документа или подсказку, а не пустоту.
6. **Поддерживай безопасное исследование** [V:P1CYZ65b5SA]: дублирование версии, «что если», сравнение вариантов
   «без interaction cost»; высший уровень — слияние вариантов. `[мнение]`
7. Плавающие панели допустимы только как временные (диалог); постоянные инструменты — со-планарные [S5].

## 11. Вход и регистрация

### 11.1 Анатомия

```
[Логотип]
[H1: «Вход» / «Создать аккаунт»]
[Поле: e-mail]
[Поле: пароль]                     ← с переключателем видимости
[ Войти ]                          ← primary, во всю ширину формы
[Забыли пароль?]                   ← вторичная ссылка
─────────── или ───────────
[Войти через SSO / провайдера]
[Нет аккаунта? Зарегистрироваться]
```

### 11.2 Правила `[консенсус]`

1. **Одна колонка по центру**, ширина формы фиксированная (ориентир — ширина комфортного поля ввода; числа см.
   `../../ui/05-layout-grid/`).
2. **Минимум полей.** Каждое поле должно быть обосновано: «убедитесь, что вы понимаете, зачем задаёте каждый
   вопрос, и просите только ту информацию, которая вам действительно нужна» [S8].
3. **Вход и регистрация — рядом и взаимно связаны ссылками**: NN/g про утилитарную навигацию — «Put Log In and
   Sign Up next to each other» [S18].
4. **Ошибки — на странице рядом с полем**, не в модалке [S9].
5. **Никакого маркетингового обвеса и лендинга**: экран входа — рабочий, а не рекламный (рамки проекта).
6. **Primary-кнопка одна.** «Войти через Google» — вторичного вида, чтобы не конкурировать.
7. **Не блокируй вставку в поле пароля** и не запрещай менеджеры паролей.
8. Ссылка «Забыли пароль» — рядом с полем пароля, а не в футере.

## 12. Пустой экран нового аккаунта

Только упоминание; подробно — волна 2, агент E, папка `06-feedback-states-motion/`.

Минимум, который относится к анатомии: пустое состояние занимает **основную область**, сохраняя шапку страницы и

страницы**, не два разных. Refactoring UI держит для этого отдельный раздел «Don't overlook empty states» [S26].

## 13. Трансформация шаблонов на узком экране — обзор

Подробно — волна 2, агент F, папка `09-mobile/`. Здесь — правила перестроения каркаса.

| Шаблон | Десктоп | Узкий экран |
|---|---|---|
| Каркас | Сайдбар + контент (+ инспектор) | Drawer или нижняя панель (3–5 пунктов); одна панель |
| Шапка страницы | Заголовок + действия справа | Заголовок; primary-действие — кнопка внизу или в app bar; остальное в «…» |
| Дашборд | Сетка плиток 3–4 в ряд | Одна колонка, порядок = приоритет |
| Список объектов | Таблица | Карточки-строки: 2–4 ключевых поля; фильтры в bottom sheet |
| Карточка объекта | Основная + боковая колонка | Боковая колонка уходит **под** основную |
| Master-detail | Две панели | Две страницы; «Назад» появляется в детали [S5] |
| Создание/редактирование | Страница или боковая панель | Страница; модалка → полноэкранный диалог [S5] |
| Инспектор | Правая панель | Bottom sheet или блок под контентом (reflow) [S5] |
| Настройки | Меню слева + контент справа | Список разделов → страница раздела (list-detail в одну панель) |
| Редактор | Инструменты слева, свойства справа | Панели по вызову, канвас на весь экран |

Три стратегии перестроения по M3 [S5]: **show and hide** (панели входят и выходят), **levitate** (панель
всплывает над контентом или прижимается к краю), **reflow** (панели переупорядочиваются, при нехватке ширины —
складываются вертикально). Fluent 2 называет пять техник: reposition, resize, reflow, show/hide,
re-architect [S16].

## Частые ошибки

**Общие**

1. Каркас меняется от экрана к экрану: где-то есть сайдбар, где-то нет.
2. Нет шапки страницы: заголовок H1 спрятан внутрь первой карточки.
3. Главное действие не в шапке страницы, а внизу или сбоку.
4. Две-три равнозначные primary-кнопки в шапке.
5. Модалка используется для всего подряд, включая длинные формы [S9].
6. Модалка поверх таблицы, закрывающая данные [V:23AQBZzDUIo].
7. Мастер там, где нужна одна страница с секциями (и наоборот) [V:P1CYZ65b5SA], [S8].
8. Дашборд из круговых диаграмм и «спидометров» [S10].
9. Боковая колонка метаданных превратилась в свалку виджетов.
10. Инспектор показывается пустым, когда ничего не выбрано.
11. Панелей одновременно больше трёх [S5].
12. Настройки без «опасной зоны»: удаление аккаунта рядом с «Сохранить».
13. Вкладки объекта дублируют разделы навигации.
14. Экран входа с лендингом и каруселью.

**Характерные для ИИ-генерации интерфейсов**

15. **Генерируется дашборд там, где нужен список работы.** «Dashboard» — дефолтный первый экран в обучающих
    данных, а не вывод из задачи.
16. **Все экраны одного типа** (карточки в сетке), независимо от того, список это, настройки или карточка
    объекта.
17. **Шапка страницы без пути назад** на вложенных экранах: генератор не отслеживает иерархию.
18. **Primary-кнопка повторяется и в шапке страницы, и в пустом состоянии, и внизу** — три раза одно действие.
19. **Инспектор нарисован, но ни к чему не привязан** — статичная колонка «Details» с выдуманными полями.
20. **Модалка внутри модалки** при генерации сложных сценариев.
21. **Мастер из трёх шагов для формы из четырёх полей.**
22. **Плитки показателей с кольцевыми диаграммами** — визуально «как на дашбордах», содержательно неверно [S10].
23. **Таблица с 15 колонками, ни одна из которых не липкая**, и без управления колонками [V:s7nvF1PuAWY].
24. **Пустое состояние, дублирующее заголовок страницы и главное действие дословно.**
25. **Канвас-редактор с инструментами справа и свойствами слева** — зеркальная раскладка, ломающая ожидание.

## Чек-лист

1. Каркас описан: какие регионы есть, какие обязательны, что меняется между экранами (ответ: только основная
   область).
2. Определено, есть ли инспектор, к чему он привязан и что показывает без выделения.
3. Панелей одновременно не больше трёх.
4. У каждого экрана есть шапка страницы с H1 и путём назад (кроме входа и полноэкранного канваса).
5. На каждом экране ровно одна primary-кнопка уровня страницы.
6. Заголовок списка — множественное число типа объекта; заголовок карточки — имя объекта.
7. Дашборд помещается в один-два экрана, показатели вверху, каждая плитка ведёт в раздел.
8. В списке: фильтры в одном месте, чекбоксы слева, действия строки справа, пагинация снизу.
9. Колонки таблицы отсортированы по важности; первая колонка — идентификатор; есть управление колонками.
10. Выбор способа создания/редактирования (страница / модалка / панель) обоснован по таблице §6.1.
11. Модалки не перекрывают данные, необходимые для ответа на вопрос модалки.
12. Мастер применён только там, где шаги обязательны и порядок задан.
13. В настройках есть «опасная зона» внизу, отдельно от безопасных действий.
14. Для master-detail заданы пропорции и поведение при сужении окна.
15. Определено, как каждый шаблон перестраивается на узком экране.
16. Состояние списка (фильтры, сортировка, страница) живёт в URL.

## Открытые вопросы и противоречия

1. **Мастер против одной страницы** — прямое противоречие источников. GOV.UK требует «одну вещь на страницу»
   [S8]; NN/g для сложных приложений требует не прятать контекст за мастерами [V:P1CYZ65b5SA]. Разрешение
   (редкие задачи неподготовленных пользователей → мастер; частые задачи экспертов → одна страница) —
   мой синтез, а не позиция источника. `[спорно]`
2. **NN/g «Wizards» и «Settings» прочитать не удалось**: сайт отдавал 503/таймаут при повторных обращениях
   (rate limit). Правила §7 и §8 собраны из смежных источников. Кандидаты для волны 2: nngroup.com/articles/wizards/,
   nngroup.com/articles/settings/, nngroup.com/articles/list-detail-pattern/.
3. **Пропорция «две трети / одна треть»** взята из GOV.UK (тип контентных страниц) и M3 (supporting pane).
   Для карточки объекта в админке эмпирических данных нет — это перенос по аналогии. `[мнение]`
4. **«Опасная зона» внизу настроек** — устоявшаяся практика (GitHub и далее), но первоисточника с исследованием
   я не нашёл; обоснование собрано из правил GOV.UK о warning-кнопках [S19] и правил разнесения деструктивных
   действий. Стоит проверить отдельно.
5. **Число полей как граница между модалкой и страницей (~5)** — ориентир из практики, не измерение. `[мнение]`
6. **Salesforce Lightning «Record page» и Ant Design Pro «ProLayout» прочитать не удалось**: страницы отдают
   пустой SPA-каркас. Это заметный пробел — обе системы задают сильные конвенции для карточки объекта и каркаса
   админки. Кандидаты: lightningdesignsystem.com (через их npm-пакет с документацией), pro.ant.design
   (репозиторий с markdown-документацией), архивные копии.
7. **Component Gallery показывает, что «page header», «split view», «inspector panel» не существуют как
   стандартизированные компоненты** [S27] — то есть в этой области меньше конвенций, чем кажется, и больше
   свободы (и больше риска несогласованности между экранами).
