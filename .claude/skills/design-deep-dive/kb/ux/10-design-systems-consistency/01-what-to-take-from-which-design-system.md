# Что брать из каких дизайн-систем (по UX-содержанию)

Волна 3 · Агент H · 22 сентября 2026 · проверено собственными запросами: каталог из 95 систем
(component.gallery), индексы паттернов GOV.UK / Carbon / Primer, наличие `llms.txt` у 17 систем, лицензии и
статус 14 репозиториев (GitHub API); плюс материалы, прочитанные агентами D1, D2, F2 по документации систем

Назначение: выбрать источник **UX-правил** (когда применять компонент, как он ведёт себя, что писать, как
проверять), а не источник визуальных величин. Числовые значения (цвет, типографика, отступы, радиусы, тени,
брейкпоинты, размеры компонентов) — в соседней базе `../../ui/10-design-systems-atlas/`; здесь они не
дублируются.

Главный вопрос файла: **у кого данная тема разобрана глубже всего и можно ли на этот источник сослаться**.

Уровни доказательности: `[данные]` (собственная проверка с датой), `[система]`, `[консенсус]`, `[практика]`,
`[мнение]`, `[не проверено]`.

## Выжимка для агента

1. **«Дизайн-система» по умолчанию означает библиотеку компонентов, а не руководство по UX.** Из 95 систем
   каталога только **55** документируют применение, **27** — доступность, **20** — тон, и лишь **2** приводят
   исследования. → §3 `[данные]`
2. **Ни одна система не описывает админочные экраны целиком**: настройки, матрица прав, аудит-лог,
   имперсонация, переключение организаций, командная палитра. Эти правила берутся из документации продуктов.
   → §5.3 `[данные]`
3. **Композиций уровня страницы в каталогах нет**: page header, app shell, split view, inspector,
   master-detail, settings page, record page. Их состав задаётся в брифе. → §3.3 `[данные]`
4. **Ранжируй источники: репозиторий > пакет > реальное приложение на этой системе > сайт документации >
   файлы и брендбук.** Сайт документации в одиночку даёт «скорее тему, чем систему». → §2 `[система]`
5. **Правило заземления**: если компонент, проп или токен нельзя подтвердить источником — не использовать.
   → §2 `[система]`
6. **Проверяй, жив ли источник.** На 22.09.2026 репозитории Salesforce Lightning и Shopify Polaris (React)
   **архивированы**, публичного репозитория Atlassian нет. → §2.2 `[данные]`
7. **GOV.UK — лучший источник по формам, вводу конкретных типов данных и типам служебных страниц**: 30
   паттернов, каждый с исследованием и историей изменений. → §4.1 `[данные]`
8. **Carbon — лучший источник по данным и по «универсальным паттернам»**: 14 паттернов с определением
   «паттерн — решение того, как пользователь достигает цели». → §4.2 `[данные]`
9. **Primer — единственный, кто документирует «деградированные состояния»** (страница работает при отказе
   необязательных зависимостей) и «сохранение». → §4.3 `[данные]`
10. **Material 3 — источник по адаптивности и мобильным конвенциям**, а не по продуктовым сценариям; с мая
    2026 «window size classes» называются breakpoints. → §4.4 `[система]`
11. **Apple HIG — источник платформенных конвенций и формулировок-запретов** (например, деструктивный стиль
    только для случайного разрушения), но не источник веб-правил. → §4.5 `[система]`
12. **Atlassian — источник по сообщениям, флагам и совместной работе**, с оговоркой: нет публичного
    репозитория и индекс паттернов не открывается программно. → §4.6 `[не проверено]`
13. **Ant Design — источник по CRUD и плотным формам**, самая большая аудитория (99,6 тыс. звёзд), есть
    `llms.txt`; но UX-обоснований мало, в основном API. → §4.7 `[данные]`
14. **shadcn/Radix — источник примитивов с доступностью, а не UX-правил**: у Radix документируется
    клавиатурный контракт, у shadcn — сборка. → §4.9 `[данные]`
15. **Spectrum — источник по доступности и сложным приложениям**, но сайт не отдаёт текст программно; брать
    через репозиторий `adobe/react-spectrum`. → §4.8 `[данные]`
16. **Component Gallery — инструмент выбора, а не источник правил**: по числу систем, документирующих
    компонент, видно, где есть конвенция, а где решение придётся принимать самим. → §3.2 `[данные]`
17. **Компонент из верхней части списка популярности имеет устойчивое имя и конвенцию** (Badge 123, Button
    118, Alert 108); из нижней — почти не стандартизован (Empty state 16, File 6, Rich text editor 5). → §3.2
    `[данные]`
18. **Синонимы компонентов — готовый словарь неймингов** и одновременно источник рассогласований внутри
    команды. → §3.4 `[данные]`
19. **Библиотека паттернов ≠ дизайн-система ≠ библиотека компонентов.** Различие практическое, а не
    терминологическое: у них разные артефакты и разные владельцы. → §6 `[консенсус]`
20. **Машиночитаемость системы проверяется одним запросом.** Реальный `llms.txt` (text/plain) на 22.09.2026
    есть у Atlassian, shadcn/ui, Carbon, Mantine, Ant Design, Untitled UI, Base UI; нет у Material 3, GOV.UK,
    Primer, MUI, Radix, Apple HIG, Salesforce. → §7 `[данные]`
21. **Каталоги паттернов (ui-patterns.com, Mobbin, PageFlows, Smart Interface Design Patterns) — источник
    гипотез, а не решений**: они показывают, как сделано, но не почему и не в каком контексте. → §8
    `[практика]`
22. **Копирование «как у всех» даёт коммодификацию**: популярные приложения одной категории почти идентичны,
    и их дизайн-системы «жутко похожи». → §8.2 `[мнение]`
23. **Чужой UI-фреймворк целиком стоит три вещи**: лишний вес, нехватка функциональности и **чужая система
    названий**. → §8.3 `[мнение]`
24. **Система не гарантирует качества**: экран, собранный целиком из её компонентов, может быть плохим
    экраном. Валидность по системе и качество — независимые измерения. → §9 `[практика]`
25. **Для генерации нужен не «лучший» источник, а один источник на потребность**: смесь систем ломает
    консистентность сильнее, чем слабость любой из них. → §9 `[практика]`

## 1. Как читать этот файл

Дизайн-система даёт четыре разных вещи, и их качество у одной и той же системы различается:

| Слой | Что это | Где искать в этом файле |
|---|---|---|
| **Токены и значения** | Цвет, типографика, отступы, радиусы | Не здесь — `../../ui/10-design-systems-atlas/` |
| **Компоненты** | Что есть, какие пропы, как выглядит | §3 (покрытие), §4 (по системам) |
| **Правила применения** | Когда применять, когда нет, что вместо | §4, главный предмет файла |
| **Паттерны и сценарии** | Как человек достигает цели, последовательности | §4, §5 |

Правило выбора: **берётся та система, у которой нужный вам слой разобран глубже**, и это может быть разная
система для разных слоёв одного продукта. Смешение допустимо на уровне **источников знаний** и недопустимо на
уровне **инвентаря компонентов** (§9).

## 2. Ранжирование источников и правило заземления

### 2.1 Порядок предпочтения

`[система]` — правило Vercel v0, забранное агентом C (`../11-ai-generated-ui/04` §1.3). По убыванию ценности:

1. **Репозиторий с кодом компонентов и документацией.**
2. **npm-пакет.**
3. **Реальное приложение, использующее систему** — показывает провайдеры, глобальные стили, шрифты, настройку
   темы и корректное употребление.
4. **Storybook или сайт документации.**
5. **Файлы макетов и брендбук.**

Прямое предупреждение: «A documentation website alone produces something closer to a theme than a true design
system with reusable components».

**Правило заземления (копировать дословно в контракт):** если компонент, проп или токен нельзя подтвердить
источником — не использовать.

**Слой, который обычно забывают**: заметки о том, чего нет в коде — устаревшие компоненты, антипаттерны,
подводные камни, какие конвенции предпочитать и каких избегать.

  **документация может иметь другую лицензию, чем код** (например, GOV.UK Design System — Open Government
  Licence на контент и MIT на код). Для генерации это существенно: копирование текстов гайдлайнов в свой
  продукт — отдельное решение.

### 2.3 Как цитировать

```
[Система] «Название страницы», версия/дата снятия, URL — что именно взято.
Пример: Carbon Design System, «Patterns → Overview», снято 22.09.2026,
        https://carbondesignsystem.com/patterns/overview/ — определение паттерна и список из 14 универсальных.
```

Правило: **дата снятия обязательна**. Системы меняются быстро (за 2026 год: M3 переименовал window size
classes в breakpoints, Polaris сменил технологию, Salesforce выпустил SLDS 2, Carbon добавил AI-компоненты).

## 3. Что показывает Component Gallery

`[данные]` — component.gallery, снято 22.09.2026. Каталог сводит один компонент по десяткам систем; он нужен
не как источник правил, а как **инструмент выбора и проверки полноты**.

### 3.1 Качество документации по каталогу

В каталоге **95 дизайн-систем**. Фильтр «Features» даёт прямую статистику:

| Признак | Сколько систем |
|---|---|
| Примеры кода | 79 |
| Открытый исходный код | 69 |
| **Руководство по применению (usage guidelines)** | **55** |
| **Доступность** | **27** |
| **Тон голоса** | **20** |
| Не поддерживается | 11 |
| Известные проблемы доступности | 4 |
| **Исследования** | **2** |

Вывод: **из 95 систем меньше двух третей объясняют, когда применять компонент, меньше трети говорят о
доступности, и только две приводят исследования**. Слово «дизайн-система» в 2026 году по умолчанию означает
библиотеку компонентов. Это же объясняет, почему UX-правила приходится собирать из разных источников, а не
брать из одной системы.

`[данные]`. В списке есть `Header` и `Footer` как элементы, но **нет ни одной композиции уровня страницы**:

## 4. Системы по темам: где сильна, где слаба

Оценка даётся **по UX-содержанию**, не по красоте и не по технологии. «Проверено» означает, что страницы
открывались в этом или предыдущих проходах проекта; «не проверено» — что источник недоступен программно.

### 4.1 GOV.UK Design System и Service Manual

**Сильна:** формы и ввод конкретных типов данных; служебные страницы; язык; доступность как процесс; наличие
исследования у каждого паттерна.

**Состав, проверенный 22.09.2026** — **30 паттернов**: адреса, банковские реквизиты, проверка ответов, проверка
пригодности услуги, выполнение нескольких задач, подтверждение email, подтверждение телефона, страницы
подтверждения, контакт с ведомством, страница cookie, создание аккаунта, создание имени пользователя, даты,
адреса электронной почты, сведения о равенстве, быстрый выход со страницы, страницы-прерывания, имена, номера
страхования, навигация по услуге, страницы 404, пароли, реквизиты карты, телефоны, страницы «проблема с
сервисом», страницы-вопросы, страницы «сервис недоступен», начало работы с услугой, пошаговая навигация,
валидация.

Это **единственный публичный источник такого рода**: паттерны не про компоненты, а про **типы данных и типы
страниц**. Аналогов нет ни у одной коммерческой системы.

**Слаба:** нет ничего про плотные таблицы, дашборды, массовые действия, права, многотенантность; визуальный
слой намеренно единый (государственный) и не переносится.

**Что брать:** структура вопроса-страницы; «одна вещь на страницу»; проверка ответов перед отправкой;
страница подтверждения; список задач (`../13-app-types/02-client-facing-app-playbook.md` §12); валидация и
сводка ошибок; формулировки служебных страниц; паттерны ввода имён, адресов, дат, телефонов.

**Лицензия:** код MIT (`alphagov/govuk-frontend`), контент — Open Government Licence. Цитировать с указанием
даты: система обновляется часто (на 27.08.2026 — GOV.UK Frontend v6.5.0, добавлены компоненты Feedback и

## 6. Библиотека паттернов, дизайн-система и библиотека компонентов

`[консенсус]` — Frost + Carbon + Worboys + Figma. Различие практическое: у трёх вещей разные артефакты, разные
владельцы и разная стоимость поддержки.

| | Библиотека компонентов | Библиотека паттернов | Дизайн-система |
|---|---|---|---|
| **Единица** | Компонент (кнопка, поле, таблица) | Паттерн: комбинация компонентов, решающая задачу пользователя | Всё вместе + правила + управление |
| **Отвечает на вопрос** | Что есть и как вызвать | **Как человек достигает цели** | Как мы работаем |
| **Артефакты** | Код, пропы, примеры | Паттерн + «почему» + когда не применять + примеры и антипримеры | Токены, компоненты, паттерны, тексты, доступность, процесс, метрики |
| **Кто владеет** | Разработка | Дизайн + разработка | Отдельная команда или роль |
| **Типовая ошибка** | «Приукрашенная библиотека компонентов», выдаваемая за систему | «Россыпь слабо организованных модулей» | Система, которая формирует культуру «что можно собрать из того, что есть» |

**Определение паттерна, взятое за рабочее** (Carbon): решение того, **как пользователь достигает цели**;
показывает переиспользуемые комбинации компонентов и шаблонов с последовательностями и потоками.

**Пять уровней Фроста** (atomic design) — атомы → молекулы → организмы → шаблоны → страницы — это **ментальная
модель, а не шаги 1-2-3**; все пять существуют одновременно. Важное для нас:
- **шаблон** фиксирует структуру контента (какой ширины изображение, какой длины заголовок в символах);
- **страница** — шаблон с настоящим контентом, и её главная функция — **проверка живучести нижележащих
  паттернов**: «выдерживают ли они реальный контент?». Сломалось — чинить на более атомарном уровне.

**Пять причин, по которым библиотеки паттернов не приживаются** `[V:W-h1FtNYim4, 10:18]`:
1. её делают как отдельный от проекта артефакт и не доделывают;
2. по ней не видно, где паттерн используется в реальном контексте;
3. она остаётся секретом дизайнеров и разработчиков от остальных дисциплин;
4. её создают после запуска и только под текущие сценарии;
5. она превращается в «россыпь слабо организованных модулей».

**Как агенту вести свою библиотеку паттернов** (минимальный формат записи):

```
## Паттерн: <имя>
Задача пользователя:        # «как человек достигает цели»
Когда применять:            # условия, лучше числами
Когда НЕ применять:         # и что вместо
Состав:                     # какие компоненты и в каком порядке
Поведение:                  # последовательность, состояния, ошибки
Почему именно так:          # ссылка на правило базы или на источник
Антипример:                 # что выглядит похоже и почему плохо
Происхождение (lineage):    # какие паттерны содержит и в какие включён
Где используется:           # список экранов
Доступность:                # клавиатура, объявления, фокус
Тексты:                     # что писать
Проверки:                   # что проверяется автоматически
```

Два требования из доклада Фроста, которые стоит соблюдать буквально:
- **аннотации живут в коде паттерна**, а не в PDF-вайрфрейме, который выбрасывают;
- **происхождение (lineage)** известно автоматически: для каждого паттерна видно, какие паттерны он содержит и
  в какие включён, — при правке сразу понятно, что перепроверять.

| Spectrum, Fluent 2, shopify.dev (`/llms.txt` → `/llms.md`) | Material 3, GOV.UK, Primer, MUI, Radix, Apple HIG, Salesforce Lightning |

**Как проверять** (одна команда):

```
curl -sIL "https://<домен>/llms.txt" | grep -i content-type
```

Код 200 с `text/html` означает, что сервер отдал страницу-заглушку, а не файл.

**Что внутри** (на примере Carbon): индекс ссылок по разделам (Getting Started, Foundations, Components,
Patterns) с одной строкой описания у каждой ссылки. То есть это карта, а не сама документация.

**Требования к «AI-ready» дизайн-системе**, сформулированные в практике `[V:aluBIa8aYYQ, 1:14:25]`
`[практика]`:
- не HTML-документация, а markdown/`llms.txt`;
- спецификация на каждый компонент: что держать в уме, пример, пропы, руководство по применению, тексты,
  доступность;
- **приоритеты вида «делай так; если нельзя — так»**;
- примеры «делай» и «не делай»;
- цикл с **обязательным аудитом на дрейф**: модель читает спеки → генерирует → аудит сравнивает с
  руководством → при несоответствии возврат к чтению, дальше не пропускать → выученное записывается обратно в
  спеки.

Оговорка оттуда же: дизайн-система всегда «comprehensive but incomplete» — полной её сделать нельзя, снежинки
остаются и **сбивают модель сильнее, чем помогают**. Отсюда практическое правило: спека должна явно называть,
чего в системе нет и что делать в этом случае.

## 8. Каталоги паттернов и примеров

### 8.1 Что это за источники

| Источник | Что даёт | Чего не даёт |
|---|---|---|
| **ui-patterns.com** | Каталог паттернов взаимодействия с описанием проблемы и решения | Данных о применимости; часть материала старая |
| **Mobbin** | Скриншоты реальных мобильных и веб-приложений по потокам | Контекста, целей, метрик; коммерческий |
| **PageFlows** | Видеозаписи реальных потоков (регистрация, отмена, оплата) | То же |
| **Smart Interface Design Patterns** (Friedman) | Набор чек-листов и разборов с примерами и антипримерами | Академической валидации; коммерческий |
| **component.gallery** | Сравнение одного компонента по 95 системам, синонимы | Правил применения |
| **checklist.design** | Чек-листы по компонентам | Обоснований |

### 8.2 Как использовать и как не использовать

**Использовать:**
- как **источник гипотез**: «так делают в N продуктах — стоит проверить, работает ли это в нашем контексте»;
- как **инвентарь вариантов**, чтобы не пропустить состояние или случай;
- как **аргумент о конвенции** (закон Якоба): если 8 из 10 продуктов категории делают так, отклонение надо
  обосновывать;
- как **источник антипримеров**.

**Не использовать:**
- как обоснование решения. Скриншот не содержит ни задачи, ни ограничений, ни результата;
- как замену объектной модели и сценариям: каталог показывает **как выглядит**, а не **из чего состоит наш
  продукт**;
- как источник числовых порогов.

**Риск коммодификации** `[мнение]` `[V:BQXTt-NZ2Bs, 10:13]`: популярные приложения в финансах, еде,
путешествиях, шопинге, фитнесе, коммуникациях и крипте почти идентичны, и их дизайн-системы «жутко похожи»;
«стремление к консистентности обходится нам коммодификацией». Отличие должно быть обосновано позицией
компании, а не желанием выделиться.

**Проверка на шаблонность** (из `../11-ai-generated-ui/`): силуэт экрана шириной 200 px рядом с силуэтами
конкурентов; и признак «у всех экранов продукта одинаковая структура».

### 8.3 Чужой UI-фреймворк целиком

`[мнение]` `[V:W-h1FtNYim4, 03:08]`. Три издержки, которые надо назвать явно, прежде чем брать Bootstrap-подобный
фреймворк как целое решение:
1. **лишнее** скачивается пользователем, даже если не используется;
2. **функциональности может не хватить**, и придётся писать своё рядом;
3. **вы принимаете чужую систему названий** — «подходит ли вашей организации слово Jumbotron?».

И отдельно: одинаковость. «Одна и та же раскладка снова и снова, потому что половина интернета использует
Bootstrap»; четыре конкурирующих бренда на одном фреймворке получатся похожими.

Целевая форма (формулировка Dave Rupert, приведённая Фростом): «tiny Bootstraps, for every client» — система
уровня Bootstrap, но **выкроенная** под задачи конкретного продукта.

## 9. Как этим пользоваться при генерации

1. **Один источник на потребность.** Инвентарь компонентов (`../13-app-types/04` §18) заполняется так, что у
   каждой потребности ровно один компонент и ровно один источник. Смесь систем ломает консистентность сильнее,
   чем слабость любой из них.
2. **Правило заземления** в контракте дословно (§2.1).
3. **Источник подаётся кодом**, а не ссылкой на сайт: «A documentation website alone produces something closer
   to a theme».
4. **Заметки о том, чего нет**, — обязательная часть подачи: устаревшие компоненты, антипаттерны, наши
   отклонения.
5. **Валидность по системе ≠ качество.** Экран, собранный целиком из компонентов системы, может быть плохим
   экраном: демонстрация Cash App на Config 2024 — крошечные ссылки, бессмысленный выпадающий список, огромное
   открытое поле для смены имени, всё из системы `[V:BQXTt-NZ2Bs, 15:20]`. Проверка по системе ставится
   **после** проверки по задаче, а не вместо неё.
6. **Проверка соответствия запускается после поиска решения**, а не вместо него: сначала спроектировать
   нужный опыт, затем перевести его в правила системы `[V:BQXTt-NZ2Bs, 06:08]`.
7. **Дата снятия источника фиксируется** в контракте: системы меняются быстро (§2.3).

## Частые ошибки

1. **Считать дизайн-систему источником UX-правил.** По каталогу: 55 из 95 документируют применение, 2 приводят
   исследования.
2. **Ссылаться на «Polaris» или «Lightning» без даты** — обе системы сменили форму в 2026 году, репозитории
   архивированы.
3. **Брать сайт документации как единственный источник** — получается тема, а не система.
4. **Ждать от системы страничных композиций** — их нет ни в одной.
5. **Смешивать системы в инвентаре компонентов** — два дейтпикера из разных систем в одном продукте.
6. **Принимать чужие названия** и получать «Jumbotron» в глоссарии.
7. **Копировать паттерн из каталога скриншотов** без задачи, ограничений и контекста.
8. **Считать соответствие системе критерием качества экрана.**
9. **Не проверять `llms.txt` на content-type** — три из семнадцати проверенных доменов отдают HTML с кодом 200.
10. **Игнорировать лицензию**: код и документация часто под разными лицензиями; «NOASSERTION» требует чтения.

## Чек-лист

Выбор источника:
1. Для каждой потребности выбран ровно один источник компонентов?
2. Проверено, что репозиторий источника активен (не архивирован)?
3. Записана дата снятия документации?
4. Проверена лицензия кода и отдельно — лицензия документации?
5. Источник подан кодом (репозиторий или пакет), а не только ссылкой на сайт?
6. Записаны заметки «чего в системе нет» и «что мы делаем иначе»?

Полнота:
7. Для компонентов из нижней части списка популярности (пустое состояние, дерево, загрузка файла, редактор)
   правила взяты из базы, а не «как у системы X»?
8. Состав страничных композиций задан явно в брифе?
9. Для админочных экранов (настройки, права, аудит, имперсонация) источники названы поимённо и помечены
   `[система]`?

Именование:
10. Из каждой строки словаря синонимов выбрано одно имя и записано в глоссарий?
11. Проверено, что имя компонента совпадает с общепринятым (по каталогу), а не изобретено?

Генерация:
12. В контракт вписано правило заземления?
13. Проверка соответствия системе запускается после поиска решения, а не вместо него?
14. Есть аудит на дрейф: результат сверяется со спекой, и дальше не пропускается при несоответствии?

## Открытые вопросы и противоречия

1. **Числа Component Gallery — счётчики каталога**, а не перепись индустрии: в каталоге 95 систем, а счётчик
   компонента доходит до 123, то есть считаются и варианты внутри систем. Порядок величин достоверен,
   абсолютные значения — нет. `[данные]` с оговоркой.
2. **Индекс паттернов Atlassian** не открылся ни одним из четырёх способов. Оценка системы по паттернам —
   `[не проверено]`; по компонентам — прочитано агентами D1/D2.
3. **Spectrum и Fluent 2** оценены по репозиториям и по страницам, прочитанным другими агентами; сайты
   программно не читаются. `[не проверено]` в части паттернов.
4. **Ant Design Pro** (шаблоны CRUD-страниц) не разобран: документация не открылась, репозиторий
   `ant-design/pro-components` не изучался. Кандидат на следующий проход.
5. **Salesforce Lightning Record Page** остаётся недоступным (§4.11) — это главный пробел базы по карточке
   объекта в CRM/ERP.
6. **«AI-ready дизайн-система»** описана по одному докладу и одному разбору стороннего автора; измерений
   эффекта (улучшает ли `llms.txt` качество генерации) нет. `[практика]`
7. **Противоречие о брейкпоинтах**: Фрост (2015) против фиксированных чисел устройств, Material 3 (2026)
   даёт именованные диапазоны. Разрешение — в `02-consistency-rules.md` §4.3.
8. **Русскоязычные системы** представлены одним источником (Контур); Яндекс, Т-Банк, Сбер, VK публичных
   UX-руководств в этом проходе не обнаружили. Кандидаты: публичные Figma-библиотеки и доклады конференций.
9. **Лицензии проверены через GitHub API** (поле `license.spdx_id`): для NOASSERTION реальный текст лицензии
   не читался. `[данные]` с оговоркой.
