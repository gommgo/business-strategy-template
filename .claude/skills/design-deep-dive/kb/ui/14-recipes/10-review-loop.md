# Рецепт 10. Цикл проверки: скриншот → чек-лист → правки

Волна 3 · агент I · 22 сентября 2026 · каркас из `[V03]` и `[V14]`, проверки из `13-evaluation-checklists/`

Вход: собранный экран (URL или HTML-файл). Выход: отчёт «правило → найдено → порог → вердикт» и очередь
правок в порядке, который даёт наибольший эффект за наименьшее время. Время цикла: 5 минут машинной части,
10–20 минут глазами.

**Главная установка цикла:** у модели должна появиться **измеримая цель**, а не пересказ промта. Возврат
отчёта «правило → найдено → порог» работает лучше, чем переписывание промта.

## Шаг 0. Порядок правок

Порядок из разбора сгенерированных интерфейсов `[V09 B 02:03]`: «модели плохо собирают сложные раскладки,
поэтому здесь наибольший эффект за наименьшее время». Порядок из живой работы `[V03 B 01:01]`: сначала
глобальные правки, затем самая сложная панель, затем перенос решения на остальные.

| Шаг | Что править | Проверка |
|---|---|---|
| 1 | **Каркас**: сайдбар, шапка, поля — из пресета | `ui_audit.py` J2, J3, J4 |
| 2 | **`max-width`** тексту и формам; снять у таблиц и канвасов | J1, H8 |
| 3 | **Убрать центрирование** везде, кроме пустых состояний, диалогов и входа | J7 |
| 4 | **Сетки на `minmax`** вместо `repeat(N, 1fr)` | J6 |
| 5 | **Правило внутреннего и внешнего**: секции 32/48, поля 12/20 | A6 + глазами |
| 6 | **Убрать вложенные карточки и лишние тени**, оставить одно средство группировки | D5, D6 |
| 7 | **Свести стили**: размеры шрифта, радиусы, толщины границ | H1, C1, C4 |
| 8 | **Sticky там, где нужно**, и проверить сумму полос | J4 |
| 9 | **Прогон на 1920 / 1280 / 390 / зум 400 %** | `--viewport`, `--touch` |
| 10 | **Только потом цвет и иконки** | I1–I7, B5, B6 |

Десятишаговый порядок наведения порядка в чужом макете `[V14]`, который ложится на тот же цикл: убрать
мусор → задать правило для повторяющегося элемента → починить правило внутреннего и внешнего → назначить
единый отступ между блоками → назначить внутренние поля → свести стили к минимуму → **убрать подложки и
проверить заново** → выровнять по левому краю всё, что было по центру → разнести ложные связи → и только в
конце выразительность.

## Шаг 1. Машинная часть: один прогон

```bash
python3 ../../scripts/ui/ui_audit.py http://localhost:3000/orders \
  --preset admin --tokens ./dist/tokens.json \
  --scheme both --reduced-motion --hover --tab 24 \
  --viewport 1440x900 --viewport 1280x800 --touch \
  --out ./audit --fail-on serious
```

Что покрывается: 14 групп проверок (отступы, размеры, форма, глубина, слои, цели, фокус, типографика, цвет,
раскладка, движение, сокращённое движение, состояния, антислоп), 81 проверка в каталоге, 55–66 срабатывают на одном прогоне (зависит от режима).

Дополнительно к нему, когда нужна официальная доступность:

```bash
npx pa11y --runner axe --runner htmlcs --standard WCAG2AA http://localhost:3000/orders
npx lighthouse http://localhost:3000/orders --only-categories=accessibility
```

Важно понимать границу инструментов: **axe не проверяет 1.4.11 (контраст нетекстовых элементов), 1.4.10
(reflow), 2.4.11 и 2.4.13 (фокус)** — правил с такими тегами в нём нет вовсе. `target-size` и
`color-contrast-enhanced` по умолчанию **выключены**. Любой градиент или фоновая картинка под текстом
переводит проверку контраста в статус `incomplete`, а не `fail`. Поэтому машинный прогон — фильтр, а не
вердикт.

## Шаг 2. Машинная часть: скриншоты

```bash
python3 ../../scripts/ui/ui_audit.py URL --scheme both --screenshot --out ./audit
```

Правила съёмки для последующего разбора глазами или моделью:

| Параметр | Значение | Почему |
|---|---|---|
| Ширины | 1440, 1280, 390 | 1440 — целевая, 1280 — где кончается контент, 390 — мобильная |
| Зум | 400 % на 1280 | эквивалент 320 CSS px, WCAG 1.4.10 |
| Темы | светлая и тёмная | половина дефектов контраста видна только в одной |
| Масштаб | `deviceScaleFactor: 1` для сверки пикселей, 2 для разбора глазами | при 2 числа в отчёте удваиваются |
| Анимации | `animations="disabled"` | иначе кадр случайный. В Python `page.screenshot` по умолчанию `animations="allow"` — ставить явно |
| Состояния | покой + открытый оверлей + состояние после Tab | скрипт снимает только покой |

## Шаг 3. Глазами: то, что скрипт не ловит

Пять приёмов, каждый занимает меньше минуты.

**1. Приложить линейку к четырём местам.**
- лейбл и поле в форме: 4–8 px (если 16 — иерархии близости нет);
- поле и следующее поле: 16–24 и обязательно **минимум вдвое больше** первого;
- padding карточки: 16 или 24, одинаковый у всех карточек экрана;
- высота кнопки и высота поля в одном ряду: должны совпасть.

Четыре замера отсеивают большинство машинных макетов.

**2. Прищуриться.** Размытие 6–10 px при ширине 1440. Что должно быть видно: группы как пятна с
промежутками, а не равномерная сетка; у главного блока больше воздуха, чем у соседей; линии не образуют
«клетку»; тени на этом уровне **не** должны быть заметны. «Simply squint your eyes and look at your design.
You should still be able to tell what the most important elements are» (Dannaway).

**3. Посчитать разнообразие по скриншоту.**

| Что считать | Норма на экран |
|---|---|
| Разных высот интерактивных элементов | 1–3 |
| Разных радиусов | 1–3 (медиана практики 3.5) |
| Элементов с тенью | 0–2 в админке, 0–5 в клиентском сервисе |
| Разных толщин линий | 1 (плюс фокус) |
| Разных цветов границ | 1–2 |
| Размеров шрифта | ≤ 8 (медиана практики 6) |
| Способов выделить блок | 1 |

**4. Убрать подложки.** Серый фон часто скрывает разные поля и невыровненные верхушки `[V14 51:22]`.
В DevTools: снять `background` у контейнеров и посмотреть на голую структуру.

**5. Пройти табом десять раз.** Виден ли фокус на каждом шаге, не обрезан ли он. Самая частая и самая
дешёвая в исправлении ошибка.

## Шаг 4. Критика моделью (необязательный шаг)

Промт и формат ответа — `../13-evaluation-checklists/02-rubrics-and-vlm-critic.md` §4. Коротко о том, что
известно про качество такой критики:

- Универсальная модель без примеров даёт **13 % валидных комментариев** (Gemini Pro Vision, 5927
  комментариев, валидны 776). Few-shot с визуально и задачно похожими примерами поднимает среднее качество
  комментария с 0.24 до 0.58 и точность рейтинга с 0 до 0.53; в слепой оценке шестью экспертами прирост
  качества комментария **+55 %** (0.31 → 0.48 при человеческом уровне 0.75).
- Локализация дефекта — главное слабое место: лучший результат на bbox среди всех моделей **IoU < 0.20**.
  Поэтому от модели просят **регион словами** («правая колонка, третья карточка»), а координаты берут из
  `ui_audit.py`.
- Рассуждающие модели преимущества не дают: в бенчмарке 2026 года GPT-o1, GPT-o3 и Gemini-2.5-Pro не
  выигрывают у своих нерассуждающих версий.
- **Критика всегда смотрит на отрендеренный экран, а не на разметку.** «A page can look fine in the code and
  be broken on screen, or the other way round, so judging layout, spacing or type from markup isn't honest».

## Шаг 5. Вернуть модели отчёт и повторить

```
| Правило                                | Найдено | Порог | Вердикт |
|----------------------------------------|---------|-------|---------|
| A1 Отступы из шкалы                    | 91.2 %  | 95 %  | FAIL    |
| A3 Уникальных gap                      | 11      | 6     | FAIL    |
| B2 Высоты контролов вне ряда           | 34, 38  | 0     | FAIL    |
| C1 Уникальных радиусов                 | 4       | 6     | OK      |
| D1 Уникальных теней                    | 9       | 7     | FAIL    |
| E1 z-index вне шкалы                   | 9999    | 0     | FAIL    |
| F1 Цели < 24px без зазора              | 6       | 0     | FAIL    |
| G2 Без индикатора фокуса               | 3       | 0     | FAIL    |
```

Требование к модели формулируется по нарушенным строкам, а не в общем виде: «приведи высоты контролов к
ряду 24/28/32/36/40/48 и убери z-index вне шкалы», а не «сделай аккуратнее».

Повторять, пока все строки OK. На практике 2–3 итерации закрывают машинную часть; композиция и иерархия
требуют глаз.

## Шаг 6. Ошибки самой починки

Мета-уровень: чем чаще всего портят интерфейс, пытаясь его исправить.

1. **Заменить «всё по центру» на «всё влево»**, включая пустые состояния, диалоги и страницу входа — там
   центр правильный.
2. **Поставить `max-width` всему подряд**, включая таблицы и канвасы.
3. **Уплотнить всё**: форма становится такой же плотной, как таблица, и число ошибок заполнения растёт.
   Плотность выбирается по типу страницы, а не по продукту.
4. **Убрать все тени**: пропадает различие между слоями, модалка не отделяется от страницы.
5. **Свести размеры шрифта к трём.** «Три кегля» — стартовое ограничение для обучения, реальная система
   требует 6–8 ролей.
6. **Выровнять высоты всех карточек по самой высокой**: появляется пустота внутри. Лечение — flex-колонки
   с `flex-grow`.
7. **Починить раскладку, не проверив на 1280.** На 1440 всё хорошо, на ноутбуке контента 550 px.
8. **Проверять только на десктопе.** Мобильные ошибки (модалка, цели, safe-area) остаются.
9. **Чинить числа, не вынося их в токены.** Следующая генерация повторит те же ошибки.
10. **Считать список маркеров вечным.** Он описывает модели 2026 года и устареет.

- `audit/<имя>.md` — отчёт по группам с примерами узлов;

## Проверки самого цикла

| Вопрос | Норма |
|---|---|
| Прогон делается на каждой сборке, а не раз в спринт? | да |
| Отчёт сохраняется вместе со сборкой? | да |
| Пороги лежат в конфиге (пресете), а не в голове? | да |
| Правки уходят в токены, а не в компоненты? | да |
| Есть прогон в тёмной теме? | да |
| Есть прогон с `prefers-reduced-motion`? | да |
| Есть прогон с эмуляцией тача (порог целей 44)? | да |
| Обход табом покрывает хотя бы 20 остановок? | да |
| Визуальная регрессия снимается в трёх режимах (светлая, тёмная, `forced-colors`) и двух ширинах? | да |
| Кто-то прошёл пять приёмов «глазами» после машинного прогона? | да |
