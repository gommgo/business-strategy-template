# Рецепт 06. Каркас приложения и анатомия страниц

Волна 3 · агент I · 22 сентября 2026 · собрано из `05-layout-grid/`

Вход: число разделов навигации, тип продукта, целевое окно. Выход: `grid-template-areas` каркаса, числа
всех зон, вертикальная схема страницы, брейкпоинты. Время: 15 минут.

---

## Шаги

### Шаг 1. Выбрать каркас по числу разделов, а не по вкусу

| Разделов навигации | Каркас | Схема |
|---|---|---|
| до 5 | верхняя навигация | topbar + контент |
| **5–15** | **левый сайдбар + контент** | самый частый выбор для веб-сервиса |
| больше 15 или два уровня | рейка + панель | рейка 48–72, панель 240–320 |
| объект и его детали | мастер-детали | список 320–400, детали — остаток |
| настройки | меню 200–240 внутри контента + контент 640–720 | меню настроек ≠ сайдбар приложения |
| полотно | боковые панели 240–300 плавают над канвасом | панели не влияют на сетку |

**Не больше трёх постоянных панелей.** Material 3: compact и medium — одна, expanded и large — две,
extra-large — до трёх. Четвёртая зона — ошибка каркаса.

### Шаг 2. Задать числа зон

| Зона | Плотная админка | Клиентский кабинет | Практика (медиана 24 продуктов) |
|---|---|---|---|
| Сайдбар | **240** | **264** (допустимо 288) | 276, центр 272–288, потолок 319 |
| Свёрнутый сайдбар | 48 | 48–56 | Carbon rail 48 |
| Верхняя панель | **48** | **64** | медиана 56, самое частое у приложений 48 |
| Правая панель | 288 | 360 | Primer 256/296/320, Atlassian 365 |
| Поля контента | 24 | 32 (16 на мобильном) | Ant Pro 40 |
| Пункт сайдбара | 32 | 40 | |
| Тулбар | 48 (контрол 32 + 2 × 8) | 56–64 | |
| Строка таблицы | 36 | 48 | медиана 40 |
| Шапка страницы | ≤ 60 | ≤ 64 | потолок 120 |

**Все вертикальные панели тянутся на полную высоту окна** (жёсткое правило Carbon); горизонтальные
(шапка, тулбар) — фиксированной высоты и резиновой ширины.

### Шаг 3. Проверить арифметику

Это не проверка задним числом, а шаг проектирования.

```
контент = ширина_окна − сайдбар − 2 × поля
```

| Окно | Админка (240 + 2 × 24) | Кабинет (264 + 2 × 32) |
|---|---|---|
| 1440 | **1152** | **1112** |
| 1280 | 992 | 952 |
| 1024 | 736 | 696 |
| 1280 + инспектор 288 | 704 (предел) | 664 |

**Контентной области всегда оставлять ≥ 640 px.** Primer формализует это как `--pane-max-width-diff`:
511 px при окне < 1280 и 959 px при ≥ 1280.

Вертикаль:

```
прилипшие зоны = шапка + шапка страницы + тулбар + шапка таблицы ≤ 192 px
строк на экране = (высота_окна − прилипшие) / высота_строки
```
Админка: (900 − 192) / 36 ≈ **19 строк**. Кабинет: (900 − 128) / 48 ≈ **13 строк**. Переход от плотного
каркаса к просторному стоит не ширины (−3.5 %), а высоты (**−32 % строк**).

**Каркас не обязан быть кратен 8.** Контент 1151 px у GitLab и 1144 у shadcn — нормальные измеренные числа;
кратность требуется от padding, gap и высот контролов, а не от ширин зон.

### Шаг 4. Записать каркас одним гридом

```css
.shell {
  display: grid;
  grid-template-columns: var(--size-panel-sidebar) 1fr;
  grid-template-rows: var(--size-panel-topbar) 1fr;
  grid-template-areas: "brand topbar" "sidebar main";
  min-height: 100vh;
}
```

Строки шаблона читаются как ASCII-схема, а порядок областей на узком экране переопределяется одним
свойством. Вложенные флексы такой читаемости не дают.

Решить один раз на весь продукт: **топбар перекрывает сайдбар или наоборот**. Оба варианта живут в
системах (Atlassian, Ant Pro, GitLab — топбар сверху; Grafana, Carbon — наоборот). Смешивать модели на
разных страницах нельзя.

### Шаг 5. Брейкпоинты

Приложению хватает **3–4**: mobile < 640, tablet 640–1023, desktop 1024–1439, wide ≥ 1440.

| Порог | Что происходит |
|---|---|
| **1280** | правая панель уходит в оверлей (раньше сайдбара: её отсутствие менее болезненно) |
| **1024** | сайдбар сворачивается в рейку |
| **768** | сайдбар только оверлеем `min(320px, 90 %)`; панель складывается над или под контентом |
| **640** | одна колонка; модалка становится листом; нижняя панель вкладок при 3–5 разделах |

Брейкпоинт считается **по ширине вьюпорта, а не по ширине области контента** (жёсткое правило Atlassian):
открытие сайдбара не меняет брейкпоинт. Для компонентов — container queries
(`container-type: inline-size`), медиазапросы остаются каркасу.

Все брейкпоинты из одной шкалы. Расхождение 992 / 1024 / 1040 историческое, а не содержательное.

Проектировать до **320 CSS px** (WCAG 1.4.10: контент читается без двумерной прокрутки при 320 px ширины;
320 px = вьюпорт 1280 при зуме 400 %). Исключения: таблицы данных, карты, видео.

### Шаг 6. Максимальные ширины по типу контента

| Контент | `max-width` |
|---|---|
| Абзац, описание | **640–720** (для русского ≤ 655 при 16 px) |
| Форма | **480–640**, одна колонка |
| Настройки | 640–720, прижаты влево |
| Страница объекта | 1200–1280, колонки 2/3 + 1/3 (правая 320–360) |
| Таблица, дашборд, канвас | **нет** `max-width`, минимальные ширины у колонок |
| Карточка входа | 400–440 по центру |

На 1920 и 2560 выбирается **одна из трёх стратегий Carbon**: центрировать (editorial), прижать влево при
наличии сайдбара (product and docs), тянуть на всю ширину и добавлять колонки по две (high-density).
Четвёртой нет. Сайдбар и панели при этом **не растут**.

**Выравнивание по левому краю при сайдбаре, центрирование без сайдбара.** Сайдбар уже задал левую
вертикаль; центрированный контент рядом с ним создаёт вторую ось.

### Шаг 7. Анатомия страницы

У каждой страницы одна вертикальная схема, меняется только содержимое полос:

```
шапка страницы (крошки → заголовок + действия → описание)  ≤ 120, цель 60
  ↓ 24 (плотно) / 32 (просторно)
[вкладки 36–48, внутри ширины контента]
  ↓
тулбар 48 (поиск 240–320, фильтры, вид)
  ↓ 16
контент (таблица / форма / карточки / дашборд)
  ↓ 16
пагинация 32–48
```

Между секциями 32 / 48. Над заголовком секции 24–32, под ним 8.

**Первичное действие одно и видно на первом экране.** Айтрекинг: 57 % времени просмотра приходится на
первый экран, 42 % — на верхние 20 % страницы, 74 % — на первые два экрана (до 2160 px).

Куда ставится первичное действие: правый верх шапки страницы (списки, объект), правый низ (диалоги), под
последним полем слева (формы в потоке страницы).

### Шаг 8. Числа по типам страниц

**Таблица.** Не растягивать ради ширины: «лучше пустое место справа, чем разрывы между колонками».
Минимальные ширины колонок по типу содержимого. Закрепить строку шапки и первую колонку, если таблица
больше экрана. Первая колонка — человекочитаемый идентификатор, а не UUID. Правку записи открывать
немодальной боковой панелью: в тестах пользователи постоянно подглядывают в соседние строки, модалка их
закрывает. Массовые действия — полоса над таблицей, появляется при выборе строк.

**Форма.** Одна колонка, `max-width` 480–640 (560 при базе 16 даёт 64–73 русских знака). Две колонки
только для коротких связанных полей (город + индекс, дата + время). Между секциями 32–48, между полями
12–20, лейбл → поле 4–8. Кнопки выровнены по левому краю полей. Число полей важнее числа шагов: средний
чекаут 11.3 поля при 5.1 шага, 17 % бросают из-за сложности.

**Дашборд.** Страница-сводка в один экран, а не жанр приложения. 49 % дашбордов используют
stratified-раскладку (сверху вниз по важности), 33 % grouped, 22 % open; 61 % — одна страница, 44 %
влезают без прокрутки. Аналитические дашборды не прокручивают: прокрутка мешает сравнивать визуализации.
Измеренные карточки: KPI **250–276 × 106–237**, половина ширины 507–568 × 367–486, полная ширина
1088–1096 × 392–477, gap 16–24, padding 16–24. Минимальная ширина карточки 280–320, сетка через
`repeat(auto-fill, minmax(280px, 1fr))`. Дашборд в приложении **один**.

**Страница объекта.** 2/3 + 1/3, правая колонка свойств 320–360. Вкладки — когда разделов 3–7 и они
равнозначны; при двух вкладки избыточны, при восьми нужен левый список.

**Пустое состояние.** Блок 320–400, иллюстрация 96–160, текст ≤ 420, одно действие. Проектируется
одновременно с основным состоянием, а не после. Три случая с разными текстами: пусто, не найдено, ошибка.

**Настройки.** Меню 200–240, контент 640–720, прижат влево. Пустота справа нормальна.

### Шаг 9. Оверлеи

| Слой | Ширина | Поведение |
|---|---|---|
| Модалка-подтверждение | 400 | — |
| Модалка-форма | 520–640 | `max-height: min(600px, 85vh)`, шапка и футер липкие |
| Модалка крупная | 800–960 | `max-width: calc(100vw − 32px)` |
| Дровер | 400–560 (`min(560px, 40vw)`) | на мобильном 100 % |
| Поповер | 240–320 | `sideOffset` 4–8 (по умолчанию 0 — ставить вручную) |
| Меню | `min-width` = ширине триггера, 160–280 | `max-height` из оставшегося места |
| Тултип | `max-width` 240–320 | задержка 300–500 мс, на тач нет |
| Тост | 320–400 (Sonner 356) | отступ от края 16–24, зазор 12–16, видимых 3, жизнь 4 с |

Порядок стратегий позиционирования: `offset` → `flip` → `shift`. `collisionPadding` ставить 8–16
(по умолчанию 0 — слой прилипает вплотную к краю окна).

Полноэкранные слои на `svh`/`dvh`, не `vh`. `env(safe-area-inset-*)` работает только при
`viewport-fit=cover` и добавляется к `padding`, а не к `margin`.

## Типичные ошибки

1. **Сайдбар 320–360 в админке.** Ни один из 10 измеренных продуктов не вышел за 319.
2. **Сайдбар 200 в русском интерфейсе.** «Настройки» — 170–180 px плюс иконка 16 плюс отступы не влезают.
   Ширины навигации считать с запасом **×1.45** на русский.
3. **Шапка приложения 80–120 px.** Измеренная мода — 48; высокая шапка это два ряда, и второй ряд должен
   принадлежать странице.
4. **Четвёртая постоянная зона.**
5. **Сайдбар, который кончается на середине экрана.**
6. **Шапка страницы вне контентной области** — две разные левые вертикали.
7. **Вкладки страницы прилеплены к шапке приложения**, а заголовок ниже.
8. **Три прилипшие полосы плюс прилипшая пагинация** — на окне 768 под данные остаётся меньше половины.
9. **Форма без `max-width` на широком экране**: поле для имени шириной 1152 px.
10. **`max-width` поставлен всему подряд**, включая таблицы и канвасы, которые обязаны быть резиновыми.
11. **Контент центрирован при наличии сайдбара.**
12. **Три одинаковые карточки в ряд** через `repeat(3, 1fr)` — визитная карточка генерации.
13. **Четыре одинаковых KPI на трёх экранах** и **приложение целиком из дашбордов**.
14. **Шапка-«хиро» в админке**: блок 200–400 px с крупным заголовком на странице списка.
15. **Таблица во всю ширину с разрывами между колонками по 200 px.**
16. **Пустое состояние на 80 px** вместо 320–400 с иллюстрацией и действием.
17. **Разные поля страницы на разных экранах** (24 на одной, 32 на другой).
18. **Шесть брейкпоинтов, из которых работают два**, или две шкалы в одном проекте (768 от Tailwind рядом
    с 992 от Bootstrap).
19. **Нет проверки на 320 px** — провал WCAG 1.4.10.
20. **`100vh` у полноэкранного слоя** — на мобильном низ уезжает под панель браузера.
