## Выжимка для агента

1. **Приложению хватает 3–4 брейкпоинтов**, а не 6: мобильный < 640, планшет 640–1023, десктоп 1024–1439,
   широкий ≥ 1440. GOV.UK обходится тремя (320 / 641 / 769) `[S11]`. → §3 `[консенсус]`
2. **Главный порог приложения — 1024 px**: ниже него сайдбар сворачивается и всплывает оверлеем. Так у
   Atlassian (прямо в документации), Tailwind `lg`, Polaris `lg` 1040. → §2, §3 `[консенсус]`
3. **Колоночная сетка нужна не везде.** Она полезна для дашбордов, каталогов карточек и страниц-описаний;
   в форме, таблице и настройках её заменяет одна колонка с `max-width` плюс flex/grid внутри блоков.
   Refactoring UI: «сетки переоценены» `[S30]`. → §1 `[спорно]`
4. **12 колонок, если сетка нужна**: делится на 2, 3, 4 и 6. Так у Bootstrap, Atlassian, Fluent 2, Hobday.
   Carbon — исключение с 16 колонками и делением надвое. Ant — 24. → §4 `[консенсус]`
5. **Гаттер 16 px на мобильном и планшете, 24 px на десктопе**; Carbon называет 32 px «wide» и 16 px
   «narrow, самый частый в продуктах», 1 px «condensed» для дашбордов. → §4 `[система]`
6. **Поля страницы 16 / 24 / 32–40** по брейкпоинтам — значение волны 1
   (`../03-spacing-sizing/01-spacing-scale.md` §6.1). Material 3: 16 на compact и 24 на всех остальных.
   Atlassian: 16 до 1024 и 32 выше. Ant Pro измеренный: 40. → §4 `[консенсус]`
7. **К сетке выравнивают только контейнеры верхнего уровня** (карточки, таблицы, формы, блоки текста).
   Кнопки, иконки и внутренности карточек — через шкалу отступов, а не через колонки `[S12]`. → §1 `[система]`
8. **Кратность 4/8 не распространяется на ширины контейнеров и колонок.** Контейнер фиксирован (1140, 1200,
   1280), колонки резиновые; ширина карточки 350.5 px — нормально `[V07]`. → §4 `[мнение]`
9. **Максимальная ширина контента приложения**: 1200–1280 для страниц с формами и текстом, 1440–1600 для
   рабочих областей, fluid без ограничения для таблиц, канвасов и досок. Atlassian: fixed-wide **1296**,
   fixed-narrow **864**, fluid без максимума. → §6 `[система]`
10. **Текстовая колонка 45–75 знаков.** Для русского при 16 px это **500–655 px**, при 14 px — **440–575 px**
    (измерено по файлам девяти шрифтов). Не ставь абзац шире 720 px. → §8 `[исследование]`
11. **Форма — одна колонка 480–640 px.** 560 px при базе 16 даёт 64–73 русских знака в строке лейбла или
    подсказки. → §8, `03-page-anatomy.md` §3 `[консенсус]`
12. **На 1920 и 2560 выбирай одну из трёх стратегий Carbon**: центрировать (editorial), прижать влево при
    наличии сайдбара (product and docs), тянуть на всю ширину и добавлять колонки по две (high-density).
    Четвёртой нет. → §7 `[система]`
13. **Не растягивай форму и текст на 1920.** Ограничивай `max-width`, а растягивай только таблицы, канвасы и
    сетки карточек. → §7 `[консенсус]`
14. **Выравнивание по левому краю при сайдбаре, центрирование без сайдбара.** Сайдбар уже задал левую
    вертикаль; центрированный контент рядом с ним создаёт вторую ось. → §7 `[система]`
15. **Container queries — дефолт для компонентов приложения в 2026.** `container-type: inline-size` на
    обёртке, `@container (min-width: …)` на потомках; в Tailwind 4 встроено (`@container`, `@sm:`).
    Медиазапросы оставь каркасу страницы. → §5 `[консенсус]`
16. **Контейнер не может стилизовать сам себя по своему размеру**: обёртка и стилизуемый блок — разные
    элементы `[S25]`. → §5 `[стандарт]`
17. **Проектируй до 320 CSS px.** WCAG 1.4.10: контент читается без двумерной прокрутки при 320 px ширины;
    320 px = вьюпорт 1280 px при зуме 400 %. Исключения: таблицы данных, карты, видео `[S27]`. → §3 `[стандарт]`
18. **Брейкпоинты в `rem`, а не в `px`**, если хочешь, чтобы раскладка реагировала на системный размер шрифта:
    так делают Tailwind 4 и Mantine. Bootstrap, Ant, Polaris, Atlassian — в px. → §2 `[спорно]`
19. **Ширина не равна брейкпоинту.** Брейкпоинт считается по ширине вьюпорта, а не по ширине области контента
    (жёсткое правило Atlassian): открытие сайдбара не меняет брейкпоинт. → §2 `[система]`
20. **Открытие и закрытие сайдбара не меняет число колонок**, колонки просто пересчитываются; выезжающая
    правая панель — уменьшает число колонок (Carbon grid influencers). → §4 `[система]`
21. **Сумма фиксированных ширин не должна съедать контент**: при сайдбаре 280 и инспекторе 400 на экране
    1280 остаётся 600 px. Правило: **контентная область ≥ 640 px**, иначе панель уходит в оверлей. → §6 `[мнение]`
22. **Сетка карточек задаётся не числом колонок, а `minmax`**: `repeat(auto-fill, minmax(280px, 1fr))`. Число
    колонок тогда выводится из ширины и не требует брейкпоинтов. → §1, §5 `[консенсус]`
23. **Порог схлопывания «сайдбар + контент» — 50 %**: «сайдбар перестаёт быть сайдбаром, когда он больше не
    самый узкий из двух элементов» `[S28]`. → §1 `[мнение]`
24. **Панели тянутся на всю высоту окна** (Carbon: «все вертикальные панели заполняют полную высоту»);
    горизонтальные (шапка, тулбар) — фиксированной высоты и резиновой ширины. → §4 `[система]`
25. **У раскладки должны быть видимые key lines** — вертикали и горизонтали, по которым выровнено несколько
    объектов `[S1]`. → §4, `04-alignment-whitespace-composition.md` §1 `[система]`
26. **Не смешивай две шкалы брейкпоинтов** в одном проекте: если берёшь Tailwind, не добавляй 992 от
    Bootstrap. Расхождение 992 / 1024 / 1040 — историческое, а не содержательное. → §2 `[консенсус]`

## 1. Когда колоночная сетка нужна, а когда мешает

### 1.1. Три режима раскладки

| Режим | Когда | Механика | Пример |
|---|---|---|---|
| **Колоночная сетка** | много разнородных блоков на одной странице, нужны повторяющиеся доли | 12 колонок, гаттер, поля; блоки занимают 3/6/12 колонок | дашборд, обзорная страница, каталог |
| **Одна колонка с `max-width`** | линейный контент: форма, статья, настройки, мастер | `max-width` + центрирование или прижатие влево | форма, страница настроек |
| **Каркас из фиксированных и резиновых зон** | приложение: сайдбар, панель, рабочая область | flex/grid с фиксированными ширинами панелей и `1fr` у контента | почта, трекер задач, редактор |

Refactoring UI формулирует это жёстко: **«сетки переоценены»** `[S30]`. Аргументы книги: не всё должно быть
резиновым, не надо сжимать элемент, пока это не понадобилось, сетка приносит порядок, но не обязана диктовать
каждое решение. Этому противостоит Carbon, у которого **вся** геометрия выведена из сетки `[S1]`. Разрешение
противоречия: сетка описывает **основную область контента**, а не приложение целиком — это прямая формулировка
Atlassian `[S12]`, и она же снимает спор.

### 1.2. Что выравнивают по сетке, а что нет

Правило Atlassian `[S12]`:

- **по колонкам**: контейнеры верхнего уровня — карточки, изображения, текстовые блоки, таблицы, формы;
- **не по колонкам**: мелкие элементы (кнопки, иконки), содержимое внутри контейнеров, оверлеи (модалки,
  тултипы, выпадающие меню — они плавают над страницей и живут вне сетки);
- **никогда**: контент не должен заходить в гаттеры и поля. «Это ломает визуальное выравнивание и делает
  раскладку непредсказуемой».

Carbon добавляет жёсткое правило типографики: **текст никогда не свешивается в гаттер**, даже ради выравнивания
`[S2]`. Компоненты с лейблами (поля ввода, выпадающие списки) обязаны использовать широкий гаттер 32 px.

### 1.3. Сетка без сетки: intrinsic-раскладки

Для сеток карточек колонки задаются не медиазапросами, а внутренними правилами:

```css
/* сетка карточек: число колонок выводится из ширины, брейкпоинты не нужны */
.cards {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(280px, 1fr));
  gap: 16px; /* 24px в просторном режиме */
}
```

`minmax(280px, 1fr)` даёт 4 колонки при 1200 px, 3 при 900, 2 при 620, 1 при 340. Минимум карточки
**280–320 px** — это же значение фигурирует у Primer как ширина панели и у Carbon как ширина плитки.

Каркас «сайдбар + контент» так же делается без медиазапросов `[S28]`:

```css
.with-sidebar { display: flex; flex-wrap: wrap; gap: 24px; }
.sidebar      { flex-basis: 280px; flex-grow: 1; }
.content      { flex-basis: 0; flex-grow: 999; min-inline-size: 50%; }
```

`flex-grow: 999` отдаёт всё свободное место контенту, `min-inline-size: 50%` задаёт **порог схлопывания**:
как только контенту достаётся половина или меньше, блоки становятся вертикальными. Обоснование автора: «сайдбар
перестаёт быть сайдбаром, когда он больше не является более узким из двух элементов».

### 1.4. Какую механику брать под задачу

| Нужно | Инструмент | Почему не другое |
|---|---|---|
| ряд из 3–5 KPI-карточек | `grid-template-columns: repeat(auto-fit, minmax(200px, 1fr))` | flex с `wrap` даст разную ширину в последнем ряду |
| сайдбар + контент | flex по рецепту выше или `grid-template-columns: 280px 1fr` | колоночная сетка не даст фиксированную панель |
| панель инструментов | flex с `gap` и `margin-inline-start: auto` у правой группы | сетка избыточна |
| дашборд с блоками разной ширины | 12-колоночный `grid` с `grid-column: span N` | flex не держит вертикальные линии |
| форма | одна колонка, `max-width`, вертикальный `gap` | сетка порождает лишние колонки |
| таблица | `table` или `grid` с `minmax` по колонкам | внешняя сетка страницы к таблице не применяется |

Наблюдения по таблице:

- **Порог «телефон / планшет»** расходится сильнее всего: 480 (Ant, Atlassian, Fluent), 576 (Bootstrap,
  Mantine), 600 (Material, MUI), 640 (Tailwind), 641 (GOV.UK), 672 (Carbon), 490 (Polaris).
- **Порог «планшет / десктоп»** сошёлся: **768 px** у Bootstrap, Tailwind, Polaris, Ant, Atlassian, Primer,
  Mantine. GOV.UK 769, Material 840, MUI 900. Это самое устойчивое число во всей таблице.
- **Порог «десктоп»**: 992 (Bootstrap, Ant, Mantine), 1012 (Primer), 1024 (Tailwind, Atlassian, Fluent),
  1040 (Polaris), 1056 (Carbon), 1200 (Material large, MUI lg). Расхождение историческое: 992 = 960 контента
  плюс поля, 1024 = разрешение старых экранов.
- **Порог «широкий экран»**: 1400 (Bootstrap, Primer), 1408 (Mantine), 1440 (Polaris, Atlassian), 1536
  (Tailwind, MUI), 1584 (Carbon), 1600 (Material, Ant), 1768 (Atlassian xl), 1920 (Fluent).
- **Единицы**: Tailwind 4 и Mantine задают брейкпоинты в `rem`/`em`, остальные в `px`. Разница проявляется,
  когда пользователь увеличил базовый шрифт браузера: rem-брейкпоинты сдвинутся, px-брейкпоинты нет.
  Mantine оговаривает, что CSS-переменные внутри медиазапросов не работают, поэтому значения приходится
  подставлять препроцессором.

### 2.2. Material 3: смена терминологии в мае 2026

Material 3 **переименовал window size classes в breakpoints** и «responsive layout» в «adaptive design»
`[S4]`. Старое название остаётся в Android API (`WindowSizeClass`). Диапазоны не изменились:

| Breakpoint | Ширина (dp) | Устройства | Панелей |
|---|---|---|---|
| Compact | < 600 | телефон в портрете | 1 |
| Medium | 600–839 | планшет в портрете, раскрытый фолдабл | 1 рекомендовано, 2 допустимо |
| Expanded | 840–1199 | телефон в ландшафте, планшет в ландшафте, десктоп | 2 рекомендовано |
| Large | 1200–1599 | десктоп | 2 рекомендовано |
| Extra-large | ≥ 1600 | десктоп, ультраширокие мониторы | 2 рекомендовано, до 3 |

Правило числа панелей — самое практичное, что даёт M3: **compact и medium — одна панель, expanded и large —
две, extra-large — до трёх, больше трёх не бывает**. Оговорка: «две панели на medium — только для контента
низкой плотности, например экрана настроек; при высокой плотности информации две панели снижают удобство».

### 2.3. Брейкпоинт считается по вьюпорту, а не по контенту

Жёсткое правило Atlassian `[S12]`: «брейкпоинты основаны на ширине вьюпорта, а не на ширине основной области
контента. Показ или скрытие боковой навигации или панели не меняет, какой брейкпоинт использует сетка».

Практическое следствие: если сайдбар 280 px открыт на экране 1440, область контента равна 1160 px, но правила
брейкпоинта `l` (1440) продолжают действовать — гаттер 16, поля 32. Если же компонент внутри контента должен
реагировать на реальные 1160 px, это задача **container query** (§5), а не медиазапроса.

## 3. Сколько брейкпоинтов нужно приложению

### 3.1. Рекомендация

**Три обязательных и один опциональный:**

| Имя | Диапазон | Что происходит |
|---|---|---|
| `mobile` | < 640 | одна колонка, сайдбар в оверлее, поля 16, таблицы → карточки, модалки → полноэкранные листы |
| `tablet` | 640–1023 | две колонки там, где их две по смыслу; сайдбар свёрнут в рейку или оверлей; поля 24 |
| `desktop` | 1024–1439 | полный каркас: сайдбар развёрнут, панель встроена; поля 32 |
| `wide` (опц.) | ≥ 1440 | шире поля или больше колонок; `max-width` контента вступает в силу |

Обоснования:

- **GOV.UK живёт на трёх** (`mobile: 320px, tablet: 641px, desktop: 769px` в
  `settings/_media-queries.scss`) `[S11]` — и это сервис государственного масштаба.
- **Atlassian требует минимум двух** из своих шести: «проектируй минимум для двух размеров из таблицы,
  желательно больше; мобильный (`xxs`) включай всегда» `[S12]`.
- **Material 3 даёт пять**, но при этом large и extra-large отличаются от expanded только шириной
  фиксированной панели (360 → 412 dp) и возможностью третьей панели `[S5]`, то есть реально переключателей
  раскладки три.
- Шесть брейкпоинтов Bootstrap и Ant — наследие адаптивных сайтов, где каждый брейкпоинт менял число колонок
  в резиновой сетке. В приложении с каркасом такой нужды нет.

### 3.2. Порог 1024 как главный

При **< 1024 px** ломается основной каркас приложения. Подтверждения:

| Система | Что происходит при < 1024 |
|---|---|
| Atlassian | «при `s`, `xs`, `xxs` (вьюпорт меньше 1024) сайдбар автоматически сворачивается, освобождая место контенту; открывается как оверлей». Правая панель тоже начинает накладываться `[S12]` |
| Polaris | навигация `position: fixed` и оверлей ниже `md` (768); правая колонка (sidebar Frame) включается только при `min-width: 1200` `[S9]` |
| Primer | панель складывается над или под контентом ниже 768; ширины панели 240/256/256 при ≥768 и 256/296/320 при ≥1012 `[S10]` |
| shadcn/ui | сайдбар отображается `md:flex`, то есть от 768; ниже — Sheet-оверлей `[S23]` |
| Material 3 | compact и medium — одна панель; две панели только с 840 dp `[S5]` |

Разброс 768 / 1024 / 1040 / 1200 объясняется тем, **какой именно сайдбар** сворачивается: узкая рейка 56–72
выживает и на 768, панель 280–320 требует 1024 и выше. Правило: **порог сворачивания = минимальная ширина
контента (640) + ширина сайдбара + поля**. При сайдбаре 280 и полях 2 × 24 это 976, округляется до 1024.

### 3.3. Нижняя граница: 320 CSS px и WCAG

`SC 1.4.10 Reflow` (уровень AA) требует, чтобы контент отображался **без прокрутки в двух направлениях** при
ширине, эквивалентной **320 CSS px** `[S27]`. Ключевое: **320 CSS px = вьюпорт 1280 px при зуме 400 %**, то
есть это требование не про телефоны, а про увеличение на десктопе. Проектируя раскладку до 320 px, вы
закрываете оба случая сразу.

Исключения, где двумерная прокрутка допустима: изображения, нужные для понимания (карты, схемы), видео, игры,
презентации, **таблицы данных** (но не отдельные ячейки), интерфейсы, где тулбар обязан оставаться видимым
при манипуляции контентом.

Не требуется схлопывать всё в одну колонку. Пример-«pass» из документа W3C: двухколоночное сравнение версий
кода, где каждая колонка влезает в 320 px, а между колонками работает горизонтальная прокрутка.

## 4. Колонки, гаттеры, поля

### 4.1. Число колонок

| Система | Колонок | Логика деления |
|---|---|---|
| Bootstrap, Atlassian, Fluent 2, Primer (де-факто), большинство продуктов | **12** | на 2, 3, 4, 6 |
| IBM Carbon | **16** (8 на medium, 4 на small) | делением надвое: 16 → 8 → 4 → 2 |
| Ant Design | **24** | на 2, 3, 4, 6, 8, 12 |
| GOV.UK | долями, не колонками | 1/4, 1/3, 1/2, 2/3, 3/4, 1 |

Anthony Hobday: «если используешь горизонтальную сетку, бери 12 колонок: 12 делится на 1, 2, 3 и 4, что даёт
много гибкости» `[S31]`. Steve Schoger в разборах: «12 колонок, потому что делится на 4, 3 и 2; навигация
занимает 1/4, контент 3/4» `[V03 A 09:10]`.

Carbon объясняет свой выбор 16 колонок концепцией «делить или умножать на 2» и прямо пишет, что 12 колонок —
легаси-вариант, который поддерживается, но не рекомендуется `[S2]`. При этом добавляет: **четырёхколоночная
структура — основа большинства интерфейсов IBM**, и даже в двух- и трёхколоночных блоках текст обычно сидит на
четырёх колонках.

### 4.2. Гаттеры

| Источник | Значение | Условие |
|---|---|---|
| Bootstrap `$grid-gutter-width` | **24 px** (1.5rem) | по 12 px padding с каждой стороны колонки |
| Atlassian | **12 px** до 1024, **16 px** от 1024 | `space.150` и `space.200` |
| Carbon, wide mode | **32 px** | по умолчанию; контейнер не заходит в гаттер; обязателен для полей ввода |
| Carbon, narrow mode | **16 px** | «самый частый выбор в продуктовой реализации»; контейнер заходит в гаттер на 16, текст нет |
| Carbon, condensed mode | **1 px** | дашборды и обзорные страницы; плиткам нужна граница 1 px темнее фона |
| Material 3 (spacer между панелями) | **24 dp** | на medium и выше |
| Бирман `[V14 47:13]` | 20–40 px | макет 1024, колонка 512 |

Рабочее правило: **16 px на мобильном и планшете, 24 px на десктопе, 32 px там, где в колонках лежат формы**.
Carbon отдельно предупреждает: «смешение гаттер-режимов будет правилом, а не исключением», потому что
компоненты с лейблами требуют 32, а карточки лучше смотрятся при 16 или 1.

### 4.3. Поля страницы

Значения из волны 1 (`../03-spacing-sizing/01-spacing-scale.md` §6.1), подтверждённые источниками этого файла:

| Ширина окна | Поле | Подтверждения |
|---|---|---|
| < 640 | **16** | Carbon margin 16, Material 3 compact 16, Atlassian `xxs`–`s` 16 |
| 640–1024 | **24** | Material 3 medium 24, практика |

Отдельные значения систем: Carbon margin по брейкпоинтам 0 / 16 / 16 / 16 / 24; Polaris `Page` padding
`--p-space-600` = **24**; Primer `--spacing-normal` = 16, а от 1012 px — **24**.

Измеренная практика (агент P, окно 1440): Ant Design Pro — 40 px, GitHub и GitLab — поля внутри блоков, у
самого `main` их нет.

### 4.4. Поведение элементов каркаса в сетке

Таблица из документации Carbon `[S1]`:

| Элемент | Ширина | Высота |
|---|---|---|
| Header | резиновая (по сетке) | фиксированная (кратна 8) |
| Toolbar | резиновая (по сетке) | фиксированная |
| **Side Panel** | **фиксированная** | резиновая (по сетке) |
| Menu | фиксированная | резиновая по контенту |
| Content | фиксированная | резиновая по контенту |
| **Data Table** | **резиновая (по сетке)** | резиновая по контенту |

Плюс правило панелей: **все вертикальные панели растягиваются на полную высоту окна**. Три типа панелей
Carbon:

- **flexible** — сворачиваемая; развёрнутое состояние фиксированной ширины, которую пользователь не меняет;
  при разворачивании либо сжимает контент и сетку, либо выталкивает контент за край окна;
- **fixed** — статичная ширина, не сворачивается, **живёт вне резиновой сетки**;
- **floating** — плавает над контентом, не влияет на сетку, обязана закрываться пользователем (сюда же
  попадают меню, выпадающие списки и тултипы).

**Grid influencers** (влияние каркаса на сетку) `[S2]`: открытие и закрытие левой навигации **не меняет число
колонок** — колонки плавно пересчитываются; появление выезжающей боковой панели **уменьшает число колонок**.

### 4.5. Key lines и соотношения сторон

Carbon: «независимо от того, как построена сетка, у раскладки должны быть видимые **key lines** — вертикальные
и горизонтальные линии, по которым выровнено несколько объектов. Горизонтальное и вертикальное выравнивание
одинаково критичны» `[S1]`.

Соотношения сторон блоков Carbon: **1:1, 2:1, 2:3, 3:2, 4:3, 16:9**. Пример расчёта из документации: блок 2:1
при базе 80 px даёт 320 × 160. Для дашбордов это даёт готовые высоты карточек: при ширине 1/3 от 1200 (то есть
384) карточка 16:9 имеет высоту 216, карточка 2:1 — 192.

### 4.6. Кратность 4/8 и ширины

Правило Tim Gabe `[V07 B 04:07]`, подтверждённое волной 1: **сетка 4/8 применяется к padding, gap, высотам
контролов и размерам иконок, но не к ширинам контейнеров и колонок**. Контейнер фиксирован (пример: 1140 px),
ширины внутри резиновые; если задать карточке ширину, кратную 8, колоночная раскладка сломается — в его примере
естественная ширина карточки 350.5 px.

Проверка на реальных числах: контейнер 1200 px, 12 колонок, гаттер 24 → колонка = (1200 − 11 × 24) / 12 =
78 px. Не кратно 8, и это нормально. Блок в 4 колонки = 4 × 78 + 3 × 24 = 384 px. Кратно 8 случайно.

## 5. Container queries против медиазапросов

### 5.1. Статус на 2026

Container queries — базовая возможность CSS, встроенная в Tailwind 4 (`@container`, варианты `@sm:`, `@max-md:`,
диапазоны `@sm:@max-md:`, именованные контейнеры `@container/main`) `[S7]`. Отдельный плагин больше не нужен.

### 5.2. Как разделить ответственность

| Уровень | Инструмент | Почему |
|---|---|---|
| Каркас страницы (сайдбар, панель, число панелей) | **медиазапросы** | зависит от окна целиком, а не от контейнера |
| Поля и гаттеры страницы | **медиазапросы** | то же |
| Карточка, строка списка, форма внутри панели | **container queries** | один и тот же компонент живёт и в контенте 1100 px, и в панели 320 px |
| Сетка карточек | `minmax` + `auto-fill` | число колонок выводится из ширины без запросов |
| Кегль в зависимости от контейнера | `cqi`-единицы | `font-size: max(1.5em, 1.23em + 2cqi)` (пример MDN) |

### 5.3. Техника

```css
/* обёртка объявляет контекст, потомок реагирует */
.panel { container: panel / inline-size; }

@container panel (min-width: 400px) {
  .card { display: grid; grid-template-columns: 96px 1fr; gap: 16px; }
}
@container panel (max-width: 399px) {
  .card { display: block; }
}
```

Ограничения, которые надо знать `[S25]`:

- **`container-type: inline-size` — рабочий вариант**; `size` требует определённости и по высоте и потому
  ломает блоки, растущие по контенту; `normal` отключает размерные запросы.
- **Контейнер не может стилизовать сам себя** по своим размерам: правила применяются только к потомкам.
  Поэтому обёртка-контейнер и стилизуемая карточка — обязательно разные элементы.
- Единицы контейнера: `cqw`, `cqh`, `cqi` (1 % inline-размера), `cqb`, `cqmin`, `cqmax`.

### 5.4. Когда container queries не нужны

- Компонент встречается ровно в одном месте раскладки (шапка страницы, глобальный тулбар).
- Компонент всегда шире порога (таблица в рабочей области 1000+ px).
- Достаточно `flex-wrap` или `minmax`: ряд фильтров, который переносится, не требует запросов вообще.

## 7. Поведение на 1920 и 2560

### 7.1. Три стратегии Carbon

Carbon формализовал выбор в виде **style models** `[S2]` — это самый полный ответ на вопрос, что делать с
лишней шириной:

| Модель | Что происходит выше максимального брейкпоинта | Для чего |
|---|---|---|
| **Editorial** | максимальная ширина сохраняется, сетка **центрируется** | маркетинговые страницы, продуктовые экраны низкой плотности (пример: чекаут) |
| **Product and docs** | максимальная ширина сохраняется, сетка **выравнивается по левому краю** | продуктовый UI с левой навигацией, документация |
| **High-density interface** | **вся ширина браузера**, колонки добавляются по две | сложные интерфейсы, каталоги, дашборды визуализации данных |

Выше максимального брейкпоинта (1584 px) «либо расширяются поля, либо добавляются колонки шагами по 2».

### 7.2. Что делать в веб-сервисе

| Зона | 1920 | 2560 |
|---|---|---|
| Сайдбар | не растёт (240–280) | не растёт |
| Верхняя панель | растягивается, содержимое прижато к краям | то же |
| Таблица | растягивается, но колонки держат `max-width`; пустое место справа | то же; при > 2000 стоит ограничить таблицу 1600–1920 |
| Дашборд | растягивается, колонки добавляются (4 → 5 → 6 карточек в ряд) | добавляются ещё колонки или растёт ширина карточек до 400 |
| Форма | **не растёт**: 480–640, прижата влево вместе с контентом | то же |
| Текст, описание | **не растёт**: 640–720 | то же |
| Страница объекта | контент 1200–1280, прижат влево при сайдбаре | то же |
| Канвас | растягивается полностью | растягивается полностью |

### 7.3. Слева или по центру

Правило, выводимое из Carbon и подтверждаемое измерениями:

- **Есть сайдбар → контент прижат к левому краю.** Сайдбар уже задал левую вертикаль; центрирование контента
  рядом с ним создаёт вторую, конкурирующую ось и оставляет «дыру» между сайдбаром и контентом. Это модель
  «product and docs».
- **Нет сайдбара → контент по центру.** Иначе на 1920 всё прижимается к левой трети экрана. Это модель
  «editorial». Polaris центрирует `Page` (`margin: 0 auto`) — и у Polaris навигация фиксирована слева, а
  контент центрируется в оставшейся области, то есть по центру **рабочей области**, а не окна.
- **Плотный рабочий интерфейс → полная ширина.** Модель «high-density».

Измеренная практика на 1440 (агент P): Ant Design Pro центрирует контент внутри 1184 px области с полями 40;
GitLab и GitHub тянут `main` на всю ширину; shadcn dashboard-01 тянет 1144 px.

Apple HIG добавляет частный случай для очень больших окон: «в visionOS на очень больших размерах держи контент
горизонтально по центру, чтобы его было удобно смотреть и трогать» `[S6]`.

### 7.4. Что растягивать нельзя ни при каких условиях

1. **Абзац текста** — нарушение WCAG 1.4.8 (не более 80 знаков) начинается уже около 800 px при 16 px.
2. **Форма в одну колонку** — 1920-пиксельное поле ввода имени выглядит как ошибка; правило Schoger:
   «ширина поля = ожидаемая длина значения» `[V01 15:22]`.
3. **Ряд из трёх карточек** — на 2560 три карточки по 800 px перестают читаться как карточки; либо
   добавляйте колонки, либо ограничивайте контейнер.
4. **Модалка** — потолок 90vw и абсолютный максимум 960 (см. `05-responsive-and-overlays.md` §2).

Отношение RU/EN совпадает с измерениями агента B (расхождение ≤ 0.02), то есть измерение воспроизводимо.

### 8.3. Готовые ширины для русского интерфейса

| Кегль | 50 знаков | 65 знаков | 75 знаков | Рабочий `max-width` |
|---|---|---|---|---|
| 14 px | 340–380 | **440–500** | 505–575 | **480** (≈ 63–70 знаков) или **560** (≈ 73–82, предел) |
| 16 px | 385–435 | **500–570** | 580–655 | **560** (≈ 64–73 знака) или **640** (≈ 73–83, предел) |

Проверочные числа:

- колонка **480 px** при 16 px — 55–62 русских знака: комфортно, годится для формы;
- колонка **640 px** при 16 px — 73–83 знака: верхняя граница WCAG 1.4.8 достигается;
- колонка **720 px** при 16 px — 82–94 знака: **нарушение**, так писать нельзя;
- колонка **1160 px** (контент при сайдбаре 240 на 1440) при 16 px — 133–151 знак: абзацу нужен свой
  `max-width` даже внутри узкой рабочей области.

### 8.4. Запас на расширение в других местах раскладки

Из волны 1 (`../02-typography/06-localization-and-ai-errors.md`): короткие надписи при переводе EN → RU растут
в **1.41–1.49 раза**, абзацы — на **13–18 %**. Что из этого следует для раскладки:

| Элемент | Английская ширина | Заложить для русского |
|---|---|---|
| Пункт навигации в сайдбаре | 120 | **170–180** (отсюда сайдбар 240, а не 200) |
| Кнопка в шапке страницы | 96 | **136–144** |
| Лейбл формы (горизонтальная раскладка) | 96–120 | **136–180**; лучше перейти на вертикальные лейблы |
| Заголовок колонки таблицы | 80 | **112–120**, иначе перенос в две строки |
| Вкладка | 80 | **112–120** |
| Плейсхолдер поиска | 160 | **226–238** (поиск 240 → 320) |

## Частые ошибки

1. **Колоночная сетка натянута на форму.** Форма — одна колонка с `max-width`, сетка в ней порождает лишние
   вертикали. Проверка: если в форме больше одной колонки полей, для этого должна быть причина (два коротких
   связанных поля, см. `03-page-anatomy.md` §3.4).
2. **Брейкпоинты посчитаны по ширине контента, а не окна.** Сайдбар открылся — «сломался» планшетный вид.
   Правило Atlassian: брейкпоинт всегда по вьюпорту; для контента — container query.
3. **Шесть брейкпоинтов, из которых работают два.** Лишние точки переключения стоят тестирования и порождают
   несогласованность. Оставить 3–4.
4. **Смешаны шкалы двух систем**: 768 от Tailwind рядом с 992 от Bootstrap. В интервале 768–992 раскладка
   ведёт себя непредсказуемо.
5. **Ширины подогнаны под кратность 8.** Колонка 78 px не кратна 8 и не должна быть; принудительное
   округление ломает сетку `[V07]`.
6. **`max-width` забыт совсем.** На 1920 абзац растягивается на 150 знаков, форма — на весь экран.
7. **`max-width` поставлен всему сразу**, включая таблицу и канвас, которые обязаны быть резиновыми.
8. **Контент центрирован при наличии сайдбара**: две конкурирующие оси и «дыра» слева.
9. **Разные поля страницы на разных экранах одного приложения**: на одной странице 24, на другой 32.
   Поле задаётся токеном на уровне каркаса, а не страницы.
10. **Текст свешивается в гаттер** ради выравнивания с соседним блоком (запрет Carbon).
11. **Контейнер и стилизуемый блок — один элемент**: container query молча не работает.
12. **Сумма фиксированных панелей съела контент**: сайдбар 280 + инспектор 400 на 1280 оставляют 552 px.
13. **Сетка применена к оверлеям**: модалка выровнена по колонкам страницы, хотя плавает над ней.
14. **Нет проверки на 320 px**: при зуме 400 % на десктопе появляется горизонтальная прокрутка — провал
    WCAG 1.4.10.

## Чек-лист

1. Брейкпоинтов в проекте **3 или 4**, и каждый действительно что-то меняет? Да / нет.
2. Все брейкпоинты взяты из одной шкалы (одной системы)? Да / нет.
3. Есть порог **1024**, на котором сайдбар сворачивается? Да / нет.
4. Раскладка проверена на **320 CSS px** (или на 1280 px при зуме 400 %) без горизонтальной прокрутки, кроме
   разрешённых исключений? Да / нет.
5. Поля страницы равны **16 / 24 / 32** по брейкпоинтам и заданы одним токеном на всё приложение? Да / нет.
6. Гаттер **16 или 24**, а в блоках с полями ввода — **32**? Да / нет.
7. Если есть колоночная сетка — **12 колонок** (или 16 по Carbon), и к ней выровнены только контейнеры
   верхнего уровня? Да / нет.
8. У абзацев и описаний есть `max-width` **640–720 px** (русский текст: ≤ 655 при 16 px)? Да / нет.
9. У формы есть `max-width` **480–640 px**? Да / нет.
10. Таблицы, канвасы и дашборды **не имеют** `max-width` или имеют его не меньше 1440? Да / нет.
11. На 1920 выбрана и применена одна стратегия: центр, левый край или полная ширина? Да / нет.
12. При открытом сайдбаре контент прижат к левому краю, а не центрирован? Да / нет.
13. Контентная область при всех открытых панелях **≥ 640 px** на 1280? Да / нет.
14. Компоненты, живущие и в контенте, и в узкой панели, используют container queries, а не медиазапросы?
    Да / нет.
15. Сетка карточек задана через `minmax(280px, 1fr)`, а не через фиксированное число колонок? Да / нет.
16. Ширины пунктов навигации, кнопок и заголовков колонок рассчитаны с запасом **×1.45** на русский текст?
    Да / нет.
17. У раскладки есть видимые key lines: минимум одна вертикаль, по которой выровнено 3+ блока? Да / нет.
18. Ширины контейнеров не подогнаны принудительно под кратность 8? Да / нет.

## Открытые вопросы и противоречия

1. **992 против 1024 против 1040.** Три «десктопных» порога у равно авторитетных систем. Содержательной
   разницы нет; различие историческое (960 + поля против разрешения экрана). Выбирать по тому, какую базу
   берёте целиком.
2. **12 против 16 колонок.** Carbon аргументирует 16 делением надвое и прямо называет 12 легаси; все
   остальные системы держат 12. Проверить эмпирически невозможно — это выбор языка, а не факт.
3. **Брейкпоинты в px или rem.** Tailwind 4 и Mantine перешли на rem/em ради реакции на системный размер
   шрифта; Bootstrap, Ant, Polaris, Atlassian остались в px. Сторонники px говорят о предсказуемости,
   сторонники rem — о доступности. Исследований, сравнивающих оба подхода, не найдено.
4. **Material 3: 412 dp против 400 dp.** Документация рекомендует фиксированную панель 412 dp на large и
   extra-large, но у side sheet максимальная ширина по умолчанию 400 dp — противоречие внутри самой системы,
   которое M3 оговаривает, но не разрешает.
5. **Максимальная ширина дашборда.** Ни одна система не даёт числа: Carbon говорит «вся ширина», Atlassian —
   «fluid без максимума», практика измерений даёт 1144–1440 на экране 1440. Число для 2560 остаётся вопросом
   вкуса; рекомендация 1600–1920 в этом файле выведена из правила «карточка не шире 400–480», а не из
   источника.
6. **Длина строки для кириллицы.** Все исследования (Ruder, Baymard, WCAG) сделаны на латинице. Переносится ли
   диапазон 50–75 знаков на русский без поправки, неизвестно; измерения дают только ширину в пикселях.
   Отмечено ещё агентом B и остаётся открытым.
7. **Spectrum (Adobe) не прочитан**: страница `spectrum.adobe.com/page/grid/` не отдала содержимое ни через
   fetch, ни через headless-браузер (пустой контейнер). Значения Spectrum по сетке в этой папке отсутствуют.
8. **Salesforce Lightning не прочитан**: новый сайт SLDS 2 редиректит на главную; шкала ширин
   48/96/192/240/320/400/640/960 взята из волны 1 (`../03-spacing-sizing/01-spacing-scale.md` §6.3), напрямую
   не проверена.
9. **Carbon UI Shell в числах**: страницы «style» отдают размеры только картинками. Значения 256 / 48 / 48
   взяты из волны 1, в исходниках не перепроверены.
