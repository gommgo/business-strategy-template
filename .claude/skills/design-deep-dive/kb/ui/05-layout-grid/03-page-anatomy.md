## Выжимка для агента

1. **У каждой страницы одна и та же вертикальная схема**: шапка страницы → (вкладки) → тулбар → контент →
   (пагинация). Меняется только содержимое полос, не порядок. → §1 `[консенсус]`
2. **Шапка страницы → контент: 24 (плотно) / 32 (просторно).** Между секциями 32 / 48. Тулбар → таблица 16.
   Таблица → пагинация 16. → §1.2 `[система]`
3. **Верх страницы получает 42 % времени просмотра**, верхние 40 % — 65 %; первый экран — 57 %, первые два
   экрана (до 2160 px) — 74 % `[S6]`. Всё важное выше 2160 px от начала страницы. → §1.3 `[исследование]`
4. **Тулбар списка 48 px** (контрол 32 + 2 × 8) в плотном режиме, 56–64 в просторном. Поиск в тулбаре
   240–320 (русский плейсхолдер требует 226–238 против 160 английского). → §2.2 `[система]`
5. **Таблицу не растягивают ради ширины.** «Лучше пустое место справа, чем разрывы между колонками» `[S1]`.
   Задавай минимальные ширины колонок по типу содержимого. → §2.3 `[мнение]`
6. **Закрепляй строку шапки таблицы и первую колонку**, если таблица больше экрана `[S3]`. → §2.3 `[консенсус]`
7. **Первая колонка — человекочитаемый идентификатор**, порядок колонок по важности, связанные рядом `[S3]`.
   → §2.3 `[консенсус]`
8. **Правку записи открывай немодальной боковой панелью, а не модалкой**: в тестах пользователи постоянно
   подглядывают в соседние строки, модалка их закрывает `[S3]`. → §2.5 `[исследование]`
9. **Массовые действия — полоса над таблицей** (или под ней), появляется при выборе строк `[S3]`. → §2.5
   `[консенсус]`
10. **Форма — одна колонка, `max-width` 480–640.** 560 при 16 px даёт 64–73 русских знака. Две колонки
    только для коротких связанных полей (город + индекс, дата + время). → §3 `[консенсус]`
11. **Ширина поля = ожидаемой длине значения** `[V01 15:22]`. Индекс не шире 96, год не шире 80, сумма не
    шире 160. → §3.3 `[мнение]`
12. **Между секциями формы 32–48, между полями 12–20, лейбл → поле 4–8.** Заголовок секции 16–20 px,
    над ним воздуха вдвое больше, чем под ним. → §3.4 `[система]`
13. **Кнопки формы выровнены по левому краю полей** (по той же вертикали, что и поля), первичная слева от
    вторичной в вебе. Sticky-футер — когда форма длиннее двух экранов. → §3.5 `[спорно]`
14. **Число полей важнее числа шагов**: средний чекаут 11.3 поля при 5.1 шага, 17 % бросают из-за сложности
    `[S10]`. Разбивай длинную форму на секции, а не только на шаги. → §3.6 `[исследование]`
15. **Страница объекта: 2/3 + 1/3**, правая колонка свойств 320–360, основная — остаток. GOV.UK: «для
    большинства типов страниц — two-thirds или two-thirds + one-third» `[S9]`. → §4 `[консенсус]`
16. **Вкладки на странице объекта — когда разделов 3–7 и они равнозначны**; при 2 разделах вкладки
    избыточны, при 8+ нужен левый список. → §4.3 `[мнение]`
17. **Дашборд — это одна страница-сводка, а не приложение.** NN/g: «набор визуализаций, представленный одним
    экраном» `[S5]`; поправка из комментариев `[V09]`. → §5.1 `[консенсус]`
18. **49 % дашбордов используют stratified-раскладку** (сверху вниз по важности), 33 % grouped, 22 % open,
    19 % table, 1 % schematic; 61 % — одна страница; 44 % влезают без прокрутки `[S4]`. → §5.2 `[исследование]`
19. **Аналитические дашборды не прокручивают**: прокрутка мешает сравнивать визуализации `[S4]`. → §5.7
    `[исследование]`
20. **Измеренные размеры карточек дашборда**: KPI **250–276 × 106–237**, половина ширины **507–568 ×
    367–486**, полная ширина **1088–1096 × 392–477**, gap **16–24**, padding **16–24** `[S17]`. → §5.4
    `[система]`
21. **Минимальная ширина карточки 280–320**, сетка через `repeat(auto-fill, minmax(280px, 1fr))`, а не через
    фиксированное число колонок. → §5.4 `[консенсус]`
22. **Три или пять KPI в ряд, а не четыре одинаковые**: четыре равных плитки читаются как «шаблон», ряд из
    3 или 5 требует выбора. Спорно: все измеренные дашборды дают именно 4. → §5.5 `[спорно]`
23. **Настройки: меню 200–240, контент 640–720, прижат влево.** Пустота справа нормальна. → §6 `[консенсус]`
24. **Пустое состояние: иллюстрация 96–160, текст ≤ 420, одна кнопка.** Проектируется одновременно с
    основным состоянием, а не после. → §7 `[консенсус]`
25. **Карточка входа 400–440 по центру**, вертикально по центру или со сдвигом вверх на 10–15 %; форма
    внутри 320–360. → §8 `[практика]`
26. **Первичное действие: правый верх шапки страницы** (списки, объект), **правый низ** (диалоги),
    **под последним полем слева** (формы в потоке страницы). → §10 `[спорно]`
27. **Одно первичное действие на экране.** Второе первичное действие обесценивает первое `[V09]`,
    `../91-videos/README.md` п. 17. → §10 `[консенсус видео]`
28. **Заголовок страницы 20–24 px в админке, 24–32 в клиентском сервисе** — значения из
    `../02-typography/02-type-scale.md` §7–8, не вводи своих. → §1.1 `[система]`

## 1. Общая вертикальная анатомия

### 1.1. Скелет страницы

Любая страница веб-сервиса собирается из одних и тех же полос. Меняется наполнение и то, какие полосы
присутствуют, но не их порядок:

```
 ┌─ рабочая область каркаса ─────────────────────────────────────────┐
 │ ←── поле 24/32 ──→                              ←── поле 24/32 ──→ │
 │                                                                    │
 │  Хлебные крошки                                       h = 20       │  ← опционально
 │  ↕ 2–4                                                             │
 │  H1 20–24 (админка) / 24–32 (кабинет)   [действия]    h = 32–40    │  ← всегда
 │  ↕ 4–8                                                             │
 │  Описание страницы, 14–16, max-width 640              h = 20–48    │  ← опционально
 │  ↕ 16–24                                                           │
 │  ─── вкладки ─────────────────────────────────────    h = 40–48    │  ← опционально
 │  ↕ 24 (плотно) / 32 (просторно)                                    │
 │  ┌ тулбар: поиск, фильтры, вид, действия ─────────┐   h = 48–64    │  ← для списков
 │  └──────────────────────────────────────────────── ┘               │
 │  ↕ 16                                                              │
 │  ┌ КОНТЕНТ ────────────────────────────────────────────────────┐   │
 │  │                                                              │   │
 │  └──────────────────────────────────────────────────────────────┘   │
 │  ↕ 16                                                              │
 │  Пагинация                                             h = 32      │  ← для списков
 │  ↕ 32–64 до низа области                                           │
 └────────────────────────────────────────────────────────────────────┘
```

Размеры заголовков берутся из пресетов волны 1 (`../02-typography/02-type-scale.md` §7–8): в плотной админке
H1 = `text-page-title` 20 px / 28, на странице объекта `text-page-title-lg` 24 px / 32; в клиентском сервисе
H1 = 24 px / 32, на главной кабинета 32 px / 40.

### 1.2. Вертикальные отступы

Значения зафиксированы в волне 1 (`../03-spacing-sizing/01-spacing-scale.md` §6.2). Повторяю их здесь как
рабочую таблицу, без изменений:

| Переход | Плотно | Просторно |
|---|---|---|
| Шапка приложения → шапка страницы | 24 | 32 |
| Шапка страницы → контент | **24** | **32** |
| Тулбар → таблица | 16 | 16 |
| Таблица → пагинация | 16 | 16 |
| Секция → секция | **32** | **48** |
| Заголовок секции → первый элемент | 8 | 16 |
| Последний блок → низ области | 32 | 64 |

Правило Бирмана для заголовков `[V14 1:10:50]`: **при увеличении кегля заголовка отступ под ним надо
пересчитывать**, иначе межстрочный просвет внутри заголовка оказывается больше внешнего отступа. В его
разборе отступ поднят с 20 до 30 px при переходе к крупному заголовку.

### 1.3. Сколько страницы реально смотрят

Данные айтрекинга NN/g на экране 1920 × 1080, 130 000+ фиксаций, 120 участников `[S6]`:

| Зона | Доля времени просмотра |
|---|---|
| Первый экран (above the fold) | **57 %** (в 2010 было 80 %) |
| Первые два экрана (до **2160 px**) | **74 %** |
| Первые три экрана | **81 %** |
| Верхние 20 % страницы | **42 %** |
| Верхние 40 % страницы | **65 %** |
| Верхняя половина первого экрана | **65 %** от времени на первом экране |

Что из этого следует для анатомии:

1. **Всё критичное — в первые 2160 px** от начала страницы. Ниже уходит четверть внимания на всё вместе.
2. **Первичное действие — в первом экране.** Прямая рекомендация статьи: «держите главные CTA above the
   fold».
3. **Ложное дно (false floor)** — реальная проблема минималистичных раскладок: если первый экран выглядит
   законченным, дальше не прокручивают. Лечение — обрезанный по нижнему краю блок, видимая часть следующей
   секции.
4. Важное наблюдение авторов, идущее против моды: «плотность информации в ранние годы веба была, вероятно,
   слишком высокой, но **сегодняшние страницы определённо слишком разрежены**».

### 2.2. Тулбар

| Параметр | Плотно | Просторно | Источник |
|---|---|---|---|
| Высота тулбара | **48** (контрол 32 + 2 × 8) | **56–64** (контрол 40 + 2 × 8–12) | `../03-spacing-sizing/03-control-and-panel-sizes.md` §5.8 |
| Поиск | 240 | 320 | там же; русский плейсхолдер 226–238 против 160 EN (`01-grids-breakpoints-containers.md` §8.4) |
| Зазор между контролами | 8 | 12 | волна 1 §8.1, §9.1 |
| Группа справа | `margin-inline-start: auto` | то же | — |
| Переключатель вида | иконочные кнопки 32 × 32 | 40 × 40 | волна 1 §2.4 |

Правило порядка внутри тулбара: **слева то, что сужает выборку** (поиск, фильтры), **справа то, что меняет
представление или запускает действие** (вид, настройки колонок, экспорт). Обоснование композиционное:
взгляд идёт слева направо, и естественный порядок «сузить → посмотреть» не должен требовать возврата к
началу строки `[S16]`.

Kole Jain формулирует требование к таблице жёстко: «таблица без поиска, фильтров и сортировки — это не
инструмент, а картинка» `[V09 A 06:05]`.

### 2.3. Таблица: ширины и поведение колонок

Главный антипаттерн, названный прямо `[S1]`: **растягивание**. «Таблицы с большим числом строк и малым
числом колонок обычно занимают 100 % доступной ширины; в результате между колонками появляются огромные
разрывы, что противоречит закону близости». Рецепт автора: задать разумные ширины колонок по умолчанию и
разрешить ручное изменение; **«при чтении таблицы лучше иметь пустое место справа, чем разрывы между
колонками»**.

Минимальные ширины колонок по типу содержимого (выведены из правила «ширина = ожидаемая длина значения»
`[V01 15:22]` и из измерений кириллицы `01-grids-breakpoints-containers.md` §8.2):

| Тип содержимого | Минимальная ширина | Комментарий |
|---|---|---|
| Чекбокс выбора | **40–48** | 16 чекбокс + 2 × 12–16 padding |
| Иконка типа, аватар | 40–56 | 16–32 иконка + padding |
| Короткий код, ID | 80–120 | моноширинный на 2 px мельче основного |
| Число, сумма | **100–160**, выравнивание по правому краю | табличные цифры обязательны |
| Дата | 120–140 | «12 сент. 2026» ≈ 96 px при 14 px |
| Относительное время | 120–140 | «2 часа назад» ≈ 100 px |
| Статус-бейдж | **120–160** | русские статусы в 1.45 раза длиннее английских |
| Имя, название | **200–280** | самая широкая колонка, ей же отдавать `1fr` |
| Email | 200–240 | — |
| Длинное описание | 240–320 с обрезкой в одну строку | либо перенос, если важно видеть целиком |
| Меню действий | **48–56** | иконочная кнопка 32 + padding |

Заголовок колонки на русском требует **112–120 px** против 80 английских, иначе перенос в две строки
(`../02-typography/06-localization-and-ai-errors.md`).

Правила NN/g для большой таблицы `[S3]`:

- **первая колонка — человекочитаемый идентификатор**, а не сгенерированный ID: по ней сканируют;
- **порядок колонок по важности**, связанные колонки рядом: «не заставляйте бегать глазами между колонкой 1
  и колонкой 20»;
- **закрепление (freeze) строки шапки и первой колонки**, если таблица больше экрана;
- границы, зебра и подсветка строки на hover — три средства «не потерять место» взглядом; Kole Jain
  добавляет: выбрать **одно** из трёх, не все сразу `[V09 A 06:05]`;
- скрытие и переупорядочивание колонок должно быть доступно и иметь видимый индикатор состояния («скрыто
  15 колонок»).

Измеренные высоты строк живых продуктов `[S17]`: 20 (Redmine), 36 (GitHub репозиторий, Matomo), 38.5
(Gravity UI), 39 (Ant Pro), 41, 48 ×2 (Radix, Carbon), 53 (shadcn), 87.5 (Discourse, двухстрочные). Значения
волны 1: плотно **36**, просторно **48** (`../03-spacing-sizing/03-control-and-panel-sizes.md` §6.1).

### 2.4. Пагинация и подвал списка

| Элемент | Значение |
|---|---|
| Высота полосы | **32** (плотно) / 40 (просторно) |
| Кнопка страницы | 32 × 32 / 40 × 40 |
| Счётчик «1–20 из 340» | слева, `text-caption` 11–12 px |
| Выбор размера страницы | справа, 80–120 по ширине |
| Отступ от таблицы | 16 |

Пагинация **не прилипает**: прилипшая полоса отнимает 32–40 px высоты у данных на каждом экране. Исключение —
бесконечный список, где счётчик заменяет пагинацию и живёт в тулбаре.

### 2.5. Действия над записями

| Способ | Размер | Когда |
|---|---|---|
| Inline в строке | 1–2 иконочные кнопки 32 × 32 | действий не больше двух, и они частые |
| Меню «три точки» | кнопка 32 × 32, меню 180–240 | 3+ действий; NN/g предупреждает о низкой обнаруживаемости `[S3]` |
| Полоса массовых действий | h = 48, над таблицей, появляется при выборе | `[S3]` |
| Боковая панель правки | **320–400**, немодальная | **рекомендуемый способ правки записи** `[S3]` |
| Модалка правки | 560–640 | только для коротких форм; закрывает соседние строки |

Прямое наблюдение из тестов NN/g `[S3]`: «мы регулярно видим, что пользователи смотрят на существующие
данные в других записях, пока редактируют запись», поэтому модалка для глубокой правки не рекомендуется.
Аккордеон внутри строки тоже плох: «пользователи не убирают за собой» и экран засоряется.

### 2.6. Где первичное действие на странице списка

**Правый верх шапки страницы.** Это единственное место, которое не конкурирует ни с фильтрами (левый верх
тулбара), ни с данными. Подтверждается структурой шапки Polaris (`PrimaryActionWrapper` — самый правый
элемент ряда действий `[S8]`) и Primer (`actions` — правый слот title bar `[S7]`).

Исключение: **пустой список**. Тогда первичное действие переезжает в центр пустого состояния (§7), а в шапке
дублируется или отсутствует.

| Значение | Ширина поля |

| Дата | 140–160 |
| Дата + время | 220–240 |
| Сумма, число | 160 |
| Телефон | 200–220 |
| Email, имя, название | **на всю ширину формы** |
| Адрес | на всю ширину |
| Текстовая область (описание) | на всю ширину, высота 3–5 строк |

Шкала ширин полей волны 1: `../03-spacing-sizing/03-control-and-panel-sizes.md` §4.2. Не вводить своих
значений.

### 3.4. Секции и две колонки

| Параметр | Плотно | Просторно |
|---|---|---|
| Между полями | **12** | **20** |
| Лейбл → поле | 4 | 8 |
| Поле → подсказка | 4 | 4 |
| Между секциями | **32** | **48** |
| Заголовок секции → первое поле | 8 | 16 |
| Над заголовком секции | 32 | 48 |

Две колонки в форме допустимы **только когда поля короткие и связанные**: город + индекс, дата + время,
имя + фамилия, ИНН + КПП. Условия: оба поля помещаются в 280 px каждое, между ними 16–24, и они читаются как
одно поле, разбитое на части. Во всех остальных случаях одна колонка.

Обоснование: Baymard называет однокоординатную (одноколоночную) форму базовым паттерном для мобильных и
десктопных чекаутов; переход на две колонки создаёт неоднозначность порядка заполнения. Refactoring UI
формулирует то же через «неоднозначные отступы»: при двух колонках вертикальное расстояние между полями
одной колонки и горизонтальное между колонками начинают спорить `[S15]`.

Дополнительное правило `[V03]`: **все поля выровнены по одной вертикали**, включая поля разной ширины. Левый
край поля = левый край лейбла = левый край заголовка секции = левый край кнопок.

### 3.5. Действия формы

| Вариант | Когда | Размеры |
|---|---|---|
| Кнопки в потоке под последним полем | форма короче полутора экранов | отступ сверху 32, выравнивание по левому краю полей |
| **Sticky-футер** | форма длиннее двух экранов | высота 64–72, граница сверху 1 px, фон страницы, кнопки прижаты влево или вправо по выбранному правилу |
| Кнопки в шапке страницы | форма-настройки с автосохранением | первичное действие справа |

Порядок кнопок — спорная точка. В вебе (Material, Polaris, Ant, Bootstrap) первичная кнопка идёт **первой
слева**; в macOS и Windows-диалогах — справа. Внутри одного продукта порядок должен быть один; детали
порядка и вида кнопок — у агента E, `../06-components-visual/`.

Выравнивание кнопок формы: **по левому краю полей**, если форма прижата влево (обычный случай страницы);
**по правому краю**, если форма живёт в модалке или дровере (там правый край — край поверхности, и кнопки
традиционно прижаты к нему).

### 3.6. Длина формы

Данные Baymard `[S10]`: средний чекаут содержит **11.3 поля** при **5.1 шага**; **17 %** пользователей
бросают оформление «из-за слишком долгого или сложного процесса». Вывод, который автор делает прямо:
**число полей важнее числа шагов**.

Для анатомии это значит: разбивать длинную форму на секции по 3–6 полей с заголовками (тогда работает
паттерн сканирования layer-cake, §6 файла 04), а не просто добавлять шаги мастера.

Расчёт долей при контенте 1152 и зазоре 32: основная колонка (1152 − 32) × 2/3 = **746**, боковая **374**.
Округлять не нужно; если хочется круглых чисел, возьмите фиксированную боковую 360 и основную `1fr` = 760.

### 4.2. Ширины колонок по системам

| Система | Доли | Значения |
|---|---|---|
| GOV.UK | two-thirds + one-third | 66.66 % / 33.33 % от 960 = 640 / 320 `[S9]` |
| Material 3 supporting pane | «основная примерно две трети» | зависит от брейкпоинта `[S11]` |
| Polaris `Layout` | primary 480–662, secondary 240–320 | `[S8]` |
| Primer `PageLayout` + `Pane` | контент 1fr, панель 256/296/320 | `[S22]` |
| Schoger `[V03 A 09:10]` | 3/4 + 1/4 для навигации, 2/3 + 1/3 для панели | — |

GOV.UK формулирует правило жёстко: «для большинства типов страниц используйте раскладку **two-thirds** или
**two-thirds + one-third**. Это не даёт строкам текста стать такими длинными, что страницу трудно читать на
десктопе. Обычно это значит не больше 75 знаков в строке. **Основной контент всегда в колонке two-thirds,
даже если соседней one-third нет**» `[S9]`.

Последняя фраза важна: при отсутствии боковой колонки контент **не растягивается** на всю ширину, а остаётся
в двух третях. Это же объясняет измеренную текстовую колонку GitHub на странице репозитория — **838 px** при
`main` 1440 `[S17]`.

### 4.3. Когда вкладки, когда одна колонка

| Структура | Условие |
|---|---|
| Вкладки | 3–7 равнозначных разделов объекта, между которыми переключаются; каждый раздел — самостоятельная страница по объёму |
| 2/3 + 1/3 | есть набор коротких свойств (10–20 пар «ключ: значение»), которые нужны постоянно |
| Одна колонка `max-width` 720 | объект в основном текстовый (статья, документ, задача с описанием); свойства уходят в шапку или в панель по кнопке |
| Левый список разделов | больше 8 разделов (тогда это уже каркас F, `02-app-shells.md` §2.6) |
| Правая панель каркаса | свойства нужны и на странице объекта, и в списке (каркас G) |

Антипаттерн: **вкладки при двух разделах**. Два раздела — это переключатель (segmented control) или просто
два блока на одной странице.

### 4.4. Шапка страницы объекта

Отличия от шапки списка `[S7]`:

- вариант заголовка **large** (для пользовательского контента: задача, обсуждение, запрос);
- **leading visual** (иконка типа, аватар) и **trailing visual** (статус, признак приватности) остаются
  видимыми **на всех вьюпортах**, в отличие от действий;
- под заголовком часто идёт строка метаданных (автор, дата, ID) размером `text-caption` 11–12 px;
- действия: 1 первичное + 1–2 вторичных + меню «ещё».

## 5. Дашборд

### 5.1. Что такое дашборд

Определение NN/g `[S5]`: «набор визуализаций данных, представленный **одним экраном (single-page view)**,
дающий информацию с одного взгляда, по которой можно быстро действовать». Прямо отделяется от портала
(«точка входа к разным задачам»).

Два типа, с разными требованиями к раскладке:

| Тип | Что | Требование к раскладке |
|---|---|---|
| **Операционный** | непрерывно обновляемые данные, срочные решения (мониторинг, диспетчеризация) | всё в одном экране без прокрутки, крупные значения, цветовые пороги |
| **Аналитический** | сводка для анализа, срочности нет | тоже один экран, но допустимы фильтры и drill-down |

Поправка, которую надо держать в голове при чтении популярных материалов: **дашборд — это страница внутри
приложения, а не всё приложение** (комментарий с 242 лайками под разбором Kole Jain `[V09 A]`). Приложение,
целиком состоящее из однотипных дашбордов, — отдельный маркер генерации (см. `06-ai-errors-and-checks.md`).

### 5.2. Паттерны раскладки: количественные данные

Систематический обзор **144 дашбордов** (Bach et al., IEEE VIS 2022) `[S4]`. Доли от корпуса; паттерны не
взаимоисключающие.

| Паттерн раскладки | Доля | Описание |
|---|---|---|
| **stratified** | **49 %** | сверху вниз по важности; «используется, чтобы выделить информацию наверху» |
| **grouped** | 33 % | два и более виджета под общим заголовком |
| **open** | 22 % | виджеты разных размеров без явного правила, выровнены по сетке, «ни у одного виджета нет приоритета» |
| **table** | 19 % | виджеты в осмысленных колонках и строках, повтор кодирования по фасетам |
| **schematic** | 1 % | схема, сеть, процесс |

| Использование площади | Доля |
|---|---|
| **screenfit** (всё влезает без прокрутки) | **44 %** |
| overflow (вертикальная прокрутка) | 22 % |
| detail on demand (тултипы, поповеры) | 47 % |
| parameterization (фильтры, слайдеры) | **52 %** |
| multiple pages | 42 % |

| Структура | Доля |
|---|---|
| **одна страница** | **61 %** |
| иерархическая (drill-down) | 19 % |
| параллельная (повтор раскладки для разных сущностей) | 16 % |
| открытая | 8 % |

Практические выводы:

1. **stratified — дефолт**: важное сверху, детали ниже. Это же согласуется с данными айтрекинга (§1.3): на
   верхние 20 % страницы приходится 42 % времени.
2. **open (22 %) — это не «нет раскладки»**, а осознанный выбор для случая, когда приоритета действительно
   нет. Если приоритет есть, а раскладка open — это ошибка.
3. **44 % влезают без прокрутки**, и авторы отдельно отмечают: «аналитические дашборды, как правило, не
   используют overflow-прокрутку, потому что **прокрутка мешает сравнивать визуализации**».
4. **52 % имеют параметризацию** (фильтры, период). Значит, полоса фильтров — штатная часть анатомии
   дашборда, а не дополнение.


(одинокая карточка не растягивается на 1152 px). Разница описана у Comeau `[S21]`.

### 5.5. Сколько KPI в ряду

Измеренная практика: **все четыре дашборда с KPI-рядом дают ровно 4 карточки** (shadcn, Ant Pro, MUI,
Grafana в одном из рядов). Это одновременно и практика, и маркер шаблонности: Kole Jain называет
«повторяющиеся блоки KPI — одни и те же четыре метрики на трёх экранах» первым признаком сгенерированного
интерфейса `[V09 B 01:01]`.

Разрешение противоречия: **число KPI не является проблемой, проблема — их одинаковость и повторяемость**.
Проверки:

- метрики на разных страницах приложения **различаются**;
- одна метрика в ряду выделена (размером карточки, цветом значения или позицией);
- у каждой метрики есть сравнение (динамика, план, прошлый период), иначе это просто число;
- ряд из 4 карточек по 262 при контенте 1152 оставляет 24 × 3 = 72 px на зазоры — проверить, что карточка
  не уже 240.

Для простого дашборда Kole Jain предлагает сетку **2 × 2** `[V09 A 02:03]`: два крупных блока сверху, два
снизу. Это тот же stratified-паттерн в минимальном виде.

### 5.6. Порядок и иерархия виджетов

| Правило | Обоснование |
|---|---|
| Важное — **слева сверху** | 42 % времени приходится на верхние 20 % страницы `[S6]`; приоритет верха и левого края `[V14 22:31]` |
| Виджеты **разного размера**, а не одинаковые | stratified и grouped вместе дают 82 % корпуса против 22 % open `[S4]` |
| Один общий фильтр периода **в шапке**, а не в каждой карточке | разбор ошибки редизайна `[V09]`: перенос периода внутрь карточек убрал возможность менять период для всех данных сразу |
| Длина и 2D-позиция вместо площади и угла | преаттентивная обработка: длину и позицию оценивают точно, площадь и угол — нет `[S5]` |
| Без 3D | 3D искажает и длину, и площадь `[S5]` |
| Цвет кодирует **категории**, не величины | до 4.5 % населения с нарушением цветовосприятия `[S5]`; детали в `../01-color/` |

### 5.7. Прокрутка дашборда

Аналитический дашборд **не прокручивают**: «прокрутка мешает сравнивать визуализации» `[S4]`, и 44 % корпуса
влезают в экран целиком. Если содержимое не влезает:

1. убрать виджеты (дашборд — не витрина всех метрик);
2. увеличить плотность: кегли мельче, шаги шкалы плотнее, чем на маркетинговой странице `[V09 A 01:01]`;
3. разделить на вкладки или страницы (42 % корпуса используют несколько страниц);
4. и только потом — вертикальная прокрутка (22 % корпуса).

Проверочная арифметика на окне 1440 × 900 при каркасе A (топбар 48, поля 24): под дашборд остаётся
**828 px**. Это шапка 40 + 24 + KPI 116 + 24 + графики 360 + 24 = 588, плюс 240 на начало таблицы. То есть
**KPI-ряд и один ряд графиков влезают, таблица начинается на границе экрана** — это нормальный «хвост»,
приглашающий прокрутить.

## 6. Страница настроек

Каркас и ширины — `02-app-shells.md` §2.6. Здесь только внутренняя анатомия:

```
 ┌─ меню 200–240 ─┐  ┌─ контент 640 ──────────────────────────────┐
 │ ▸ Профиль    ● │  │ H1 «Профиль» 20–24                         │
 │ ▸ Уведомления  │  │ ↕ 24                                       │
 │ ▸ Безопасность │  │ Личные данные          16px · 600          │
 │ ▸ Команда      │  │ ↕ 8                                        │
 │ ▸ Биллинг      │  │ [поля формы, ширина по значению]           │
 │ ▸ API          │  │ ↕ 32–48                                    │
 │                │  │ Аватар                 16px · 600          │
 │   h пункта 32  │  │ ↕ 8                                        │
 │   (40 просторно)│ │ [96 × 96] [Загрузить] [Удалить]            │
 └────────────────┘  └────────────────────────────────────────────┘
           ↔ 32–48
```

| Параметр | Значение |
|---|---|
| Меню настроек | 200–240, пункт 32/40 |
| Контент | **640–720** `max-width`, прижат влево |
| Между секциями | 32 / 48 |
| Ряд «настройка + переключатель» | высота 48–56, лейбл слева, контрол справа, разделитель 1 px |
| Описание настройки | 12–14 px, `max-width` 480, под лейблом |

Паттерн «строка настройки» (лейбл слева, контрол справа) — единственное место в интерфейсе, где
горизонтальное расположение лейбла и контрола оправдано: значения однотипные (переключатели), и правый край
образует собственную вертикаль. Для формы с разнородными полями это не работает.

Apple HIG добавляет два правила `[S14]`: «минимизируйте число настроек» и «настройки, влияющие только на
конкретную задачу, размещайте в самой задаче, а не в разделе настроек».

## 7. Пустая страница и пустое состояние

> Разрешение противоречия [C40]: 96–160 — иллюстрация в панели или карточке; полноэкранное пустое состояние 160–240, страница ошибки 240–320 (`../07-iconography-imagery/02-illustration-system-avatars-images.md` §4.1). См. `../CONTRADICTIONS.md`.

```
 ┌───────────────────────────────────────────────────────────────────────┐
 │ H1 «Клиенты» 20px                            [+ Добавить клиента]      │
 │ ↕ 24                                                                   │
 │ ┌───────────────────────────────────────────────────────────────────┐ │
 │ │                                                                   │ │
 │ │                        ┌─────────┐                                │ │
 │ │                        │иллюстра-│  96–160                        │ │
 │ │                        │  ция    │                                │ │
 │ │                        └─────────┘                                │ │
 │ │                          ↕ 16–24                                  │ │
 │ │                  Пока нет клиентов   16–20 · 600                  │ │
 │ │                          ↕ 8                                      │ │
 │ │        Добавьте первого клиента, чтобы начать работу              │ │
 │ │              текст 14, max-width 420, по центру                   │ │
 │ │                          ↕ 24                                     │ │
 │ │                   [+ Добавить клиента]  h 32/40                   │ │
 │ │                                                                   │ │
 │ └───────────────────────────────────────────────────────────────────┘ │
 │     высота блока: min-height 320–400, по центру области               │
 └───────────────────────────────────────────────────────────────────────┘
```

| Параметр | Значение | Источник |
|---|---|---|
| Иллюстрация | **96–160** | `../03-spacing-sizing/03-control-and-panel-sizes.md` §5.8 |
| Ширина текста | **≤ 420** | там же |
| Высота блока | 320–400 `min-height` | практика |
| Действий | **одно** первичное, максимум плюс одна ссылка | `[V09]` |

Пустое состояние — **единственный случай, где центрирование по горизонтали правильно** в приложении:
элементов один-три, и центр работает (Бирман: «центровка работает, пока элементов один-два, максимум
четыре» `[V14 20:28]`).

Три разных пустых состояния, которые часто путают:

| Состояние | Текст | Действие |
|---|---|---|
| **Ничего ещё не создано** | «Пока нет клиентов» | первичное: создать |
| **Ничего не нашлось по фильтру** | «Ничего не найдено по запросу “…”» | сбросить фильтры |
| **Нет доступа / ошибка** | код и описание | повторить, написать в поддержку |

Kole Jain: «проектируйте пустое состояние сразу; раскладка списком упрощает вставку пустого состояния по
сравнению с сеткой карточек» `[V09 A 03:03]`.

## 8. Страница входа

```
                          ┌──────────── 400–440 ────────────┐
                          │  padding 32                     │
                          │  ЛОГО 32                        │
                          │  ↕ 24                           │
        сдвиг сверху      │  Вход в систему   20–24 · 600   │
        10–15 % высоты    │  ↕ 24                           │
        окна, или         │  Email                          │
        вертикальный      │  [___________________] h 40     │
        центр             │  ↕ 16                           │
                          │  Пароль                         │
                          │  [___________________] h 40     │
                          │  ↕ 8   Забыли пароль? →         │
                          │  ↕ 24                           │
                          │  [      Войти      ] h 40 100%  │
                          │  ↕ 16                           │
                          │  ─── или ───                    │
                          │  [ Войти через SSO ] h 40 100%  │
                          └─────────────────────────────────┘
```

| Параметр | Значение | Уровень |
|---|---|---|
| Ширина карточки | **400–440** | `[практика]`: совпадает с `size.modal.confirm` = 400 волны 1 |
| Padding карточки | **32** (24 на мобильном) | `[практика]` |
| Ширина полей | 100 % карточки (336–376 при padding 32) | `[практика]` |
| Высота контролов | **40–48** (клиентский пресет) | волна 1 §9.2 |
| Вертикальное положение | центр или сдвиг вверх на 10–15 % высоты | `[практика]` |
| На мобильном | карточка во всю ширину минус 2 × 16, без тени и границы | `[практика]` |

Честная пометка: **источника с числом для ширины карточки входа не найдено**. 400–440 выведено из ширины
модалки-подтверждения (400, волна 1 §5.5) и из того, что поле ввода email при 16 px требует 320–360 px для
комфортного отображения адреса. Это практика, а не значение системы.

Что не делать на странице входа веб-сервиса: маркетинговый блок на половину экрана (это уже лендинг, вне
рамок базы), фоновое изображение с текстом поверх, карточку шире 480.

## 9. Страница с редактором или канвасом

Каркас — `02-app-shells.md` §2.8. Анатомия страницы:

| Зона | Размер | Поведение |
|---|---|---|
| Полотно | резиновое, без `max-width` | собственная система координат, зум |
| Плавающий тулбар | 40–56 по высоте, отступ от края 16–24 | плавает, не сжимает полотно |
| Панель слоёв / структуры | 240–300 | плавает или встроена |
| Панель свойств | 240–300 | плавает или встроена |
| Контролы зума | 120–160 × 32, левый нижний или правый нижний угол | плавают |
| Шапка приложения | 48–56 | может отсутствовать (Excalidraw, tldraw) |

Правило Apple HIG для macOS, применимое и к вебу `[S14]`: **не размещайте контролы и критичную информацию у
нижнего края окна** — окно часто сдвигают так, что нижняя кромка уходит за экран. Для веб-редактора это
значит: контролы зума в углу, но с отступом 16–24 от края, а не вплотную.

## 10. Размещение первичного действия

| Тип страницы или поверхности | Место | Обоснование |
|---|---|---|
| Список, таблица | **правый верх шапки страницы** | не конкурирует с фильтрами слева и данными ниже; Polaris `PrimaryActionWrapper` — самый правый `[S8]` |
| Страница объекта | **правый верх шапки** | то же |
| Форма в потоке страницы | **под последним полем**, по левому краю полей | естественный порядок «заполнил → нажал» `[S19]` |
| Форма в модалке или дровере | **правый низ поверхности** | правый край — край поверхности |
| Sticky-футер длинной формы | правый или левый край футера, одинаково во всём продукте | — |
| Диалог подтверждения | **правый низ** | — |
| Пустое состояние | **по центру блока**, под текстом | §7 |
| Дашборд | обычно нет первичного действия; фильтр периода — в шапке | §5.6 |
| Страница входа | **во всю ширину карточки** | §8 |

Композиционное обоснование порядка «поле → кнопка» `[S19]`: «естественный процесс — заполнить поле и нажать
кнопку; кнопка перед полем заставляет двигаться в одну сторону до конца, а потом возвращаться в начало».

Правило количества: **одно первичное действие на экране**. Если первичных действий два, ни одно не читается
как главное (`../91-videos/README.md` п. 17; `[V09]`). Вторичные действия — кнопки-обводки или ссылки;
редкие — в меню «ещё».

## Частые ошибки

1. **Форма без `max-width` на широком экране**: поле ввода имени шириной 1152 px. Проверка: `max-width`
   формы ≤ 640.
2. **Все поля формы одной ширины**, включая год и индекс. Проверка: ширина поля соответствует ожидаемой
   длине значения (§3.3).
3. **Таблица растянута на всю ширину при 4 колонках**: между колонками разрывы по 200 px. Проверка: сумма
   минимальных ширин колонок против ширины области; если меньше, оставить пустое место справа.
4. **Шапка таблицы не закреплена** при 50+ строках: на середине списка непонятно, что в колонке.
5. **Первая колонка — числовой ID** вместо названия.
6. **Правка записи в модалке** поверх таблицы: закрыты соседние строки, на которые пользователь смотрит.
7. **Три способа разделения строк сразу**: зебра плюс границы плюс подсветка.
8. **Вкладки при двух разделах** на странице объекта.
9. **Дашборд из четырёх одинаковых KPI-карточек**, повторяющихся на трёх экранах приложения.
10. **Фильтр периода внутри каждой карточки** вместо одного общего в шапке.
11. **Круговые диаграммы и датчики** вместо столбчатых и линейных: площадь и угол читаются неточно.
12. **Дашборд с вертикальной прокруткой на два экрана**: сравнивать виджеты невозможно.
13. **Пустое состояние придумано после основного**: блок на 80 px высоты с одной строкой «Нет данных».
14. **Карточка входа 560–720**: читается как форма, а не как вход.
15. **Два первичных действия в шапке страницы**.
16. **Первичное действие ниже первого экрана** при длинной странице (57 % времени приходится на первый
    экран).
17. **Настройки во всю ширину 1152**: ряды «лейбл — переключатель» растягиваются, связь между лейблом и
    контролом теряется.
18. **Описание страницы без `max-width`**: строка на 1152 px даёт 133–151 русский знак.

## Чек-лист

1. Вертикальный порядок полос соблюдён: шапка → вкладки → тулбар → контент → пагинация? Да / нет.
2. Отступ «шапка страницы → контент» равен **24 или 32** и одинаков на всех страницах? Да / нет.
3. Всё критичное умещается в первые **2160 px** страницы? Да / нет.
4. Первичное действие видно **на первом экране**? Да / нет.
5. Первичное действие **одно**? Да / нет.
6. У формы есть `max-width` **480–640**? Да / нет.
7. Ширина каждого поля соответствует ожидаемой длине значения? Да / нет.
8. Все поля, лейблы и кнопки формы выровнены по **одной левой вертикали**? Да / нет.
9. Две колонки в форме — только для коротких связанных полей? Да / нет.
10. Между секциями формы **32–48**, между полями **12–20**? Да / нет.
11. У таблицы заданы **минимальные ширины колонок**, а не только проценты? Да / нет.
12. Строка шапки таблицы и первая колонка закреплены при прокрутке? Да / нет.
13. Первая колонка — человекочитаемый идентификатор? Да / нет.
14. Правка записи открывается **боковой панелью**, а не модалкой поверх таблицы? Да / нет.
15. Выбран **один** способ разделения строк (зебра, границы или подсветка)? Да / нет.
16. Страница объекта построена как **2/3 + 1/3** или как одна колонка ≤ 720? Да / нет.
17. Дашборд помещается **в один экран** или явно разделён на страницы? Да / нет.
18. Виджеты дашборда **разного размера**, важнейший слева сверху? Да / нет.
19. KPI-карточки не уже **240** и имеют сравнение (динамика, план)? Да / нет.
20. Фильтр периода **один** и находится в шапке? Да / нет.
21. Графики используют длину и 2D-позицию, а не площадь и угол? Да / нет.
22. Пустое состояние спроектировано для всех трёх случаев (пусто, не найдено, ошибка)? Да / нет.
23. Текст пустого состояния ≤ **420 px**, действие одно? Да / нет.
24. Карточка входа **400–440**, форма внутри во всю ширину карточки? Да / нет.
25. Описание страницы имеет `max-width` **640**? Да / нет.

## Открытые вопросы и противоречия

1. **Четыре KPI в ряд: практика или шаблон.** Все измеренные дашборды дают ровно 4; одновременно это первый
   маркер сгенерированного интерфейса `[V09 B]`. Разрешение (§5.5) — эвристика, а не результат
   исследования.
2. **Высота карточки графика.** Ожидаемый по практике диапазон 280–360 не подтвердился измерениями:
   реальные значения 258–600, медиана около 400. Число 320–400 в §5.4 выведено из измерений, но разброс
   слишком велик для уверенной рекомендации.
3. **Порядок кнопок формы.** Веб-системы ставят первичную слева, десктопные ОС — справа. Единого правила
   нет; решать на уровне продукта. Детали — у агента E.
4. **Ширина карточки входа.** Источника с числом не найдено; 400–440 выведено из ширины
   модалки-подтверждения. Помечено `[практика]`.
5. **Ширина командной палитры** (560–640) — тоже практика: cmdk не задаёт размеров, они полностью на стороне
   потребителя. См. `05-responsive-and-overlays.md`.
6. **Baymard про формы не полностью применим**: данные собраны на чекаутах интернет-магазинов, а не на
   формах админок. Перенос вывода «число полей важнее числа шагов» на бэк-офис не проверен.
7. **Правило GOV.UK «основной контент всегда в two-thirds»** противоречит практике дашбордов и таблиц, где
   используется вся ширина. GOV.UK описывает контентные страницы государственных сервисов; для таблиц
   правило не применяется, и сам GOV.UK даёт класс `full`.
8. **Дашборд без прокрутки против реальных продуктов.** Bach et al. дают 44 % screenfit, но измеренные
   дашборды (Matomo — высота виджета 1712 px, Plausible — 477 + 4 × 430) прокручиваются на несколько
   экранов. Возможно, корпус исследования смещён в сторону публичных витринных дашбордов.
9. **Высоты строк таблиц разъезжаются сильнее, чем заявлено**: измеренные 20 … 87.5 при заявленных в волне 1
   36 / 48. Крайние значения — легаси-продукты (Redmine 20) и двухстрочные строки (Discourse 87.5).
