# Антипаттерны токенов и конвейер генеративной системы

Волна 2, агент F, 22 сентября 2026. Источников прочитано целиком: 38.

Чем ломаются наборы токенов, как это ловить автоматически, как устроена депрекация в четырёх системах и
какой конвейер нужен агенту, который выпускает интерфейс: бриф → токены → CSS и Tailwind → компоненты →
проверка.

## Выжимка для агента

1. **Взрыв компонентных токенов — главный способ убить набор.** Закон убывающей отдачи: чем больше
   компонентов, тем выше стоимость каждого и ниже его ценность. → §1.1 `[мнение]`
2. **Правило перехода: три и более компонента.** Пока значение нужно одному-двум, оно живёт в коде
   компонента, а не в общем наборе. → §1.1 `[мнение]`
3. **Псевдотокены вместо компонентных.** Uber заводит переменные уровня компонента, которые указывают
   на токены системы и **скрыты от публикации**. Набор не растёт, компонент всё равно параметризован. →
   §1.1 `[система]`
4. **Значение в имени семантического токена — отложенная ложь.** `color.blue.primary`, `space-16`,
   `radius-6`: любая смена ручки характера делает имя неверным. → §1.2 `[консенсус]`
5. **Четыре уровня алиасов — потолок читаемости.** На четвёртом звене ответ на вопрос «почему кнопка
   синяя» перестаёт помещаться в голову. → §1.3 `[консенсус]`
6. **Токен без описания применения мёртв через полгода.** Никто не помнит, чем `bg-component`
   отличается от `bg-subtle`. Лечится `$description` (Carbon) или расширением с `usage` и `rules`
   (Primer). → §1.4 `[система]`
7. **Несогласованность грамматики между категориями** (`bgColor.danger.emphasis` для цвета и
   `space-400` для отступов) заставляет держать в голове две системы вместо одной. → §1.5 `[мнение]`
8. **«Магическое» значение вне токенов — самая дешёвая в моменте и самая дорогая в итоге ошибка.**
   Авито при смене бренда нашли нетокенизированный логотип **более чем в 120 местах**. → §1.6
   `[система]`
9. **Мёртвый токен (ноль использований) — такой же дефект, как магическое значение.** Он занимает
   место в словаре, который читает человек или модель. → §1.7 `[мнение]`
10. **Цена нового значения измеряется месяцами, а не минутами.** В Яндекс Маркете добавление второго
    размера основного текста (14 к 16) обсуждали около двух месяцев. → §1.8 `[система]`
11. **Бритва Оккама как критерий приёмки:** число компонентов, цветов, стилей текста и теней —
    необходимый минимум. Антипример Wolt: столько теней, что нельзя выбрать между elevation 6 и 8. →
    §1.8 `[мнение]`
12. **Депрекация — это процесс из трёх шагов длиной около трёх месяцев**, а не удаление токена. → §2.1
    `[система]`
13. **Машиночитаемая замена важнее объяснения.** Spectrum пишет `lifecycle.replacedBy` с uuid нового
    токена; инструмент может переписать код автоматически. → §2.2 `[система]`
14. **`$deprecated` из стандарта не использует пока никто** из разобранных систем: Carbon пишет
    `carbon.layout.deprecated`, Spectrum — `lifecycle`, Atlassian — свои поля. → §2.3 `[спорно]`
15. **Проверки, которые ловят 90 % ошибок, — это пять грепов**: литералы цвета, числовые утилиты
    Tailwind, примитивы в компонентах, `z-index` вне шкалы, значения вне шкалы отступов. → §3.2
    `[мнение]`
16. **Каждую сборку токенов надо валидировать** (`tz check` или `ajv`) и прогонять проверки контраста.
    Ошибка в токенах дешевле всего стоит в момент сборки. → §3.1 `[консенсус]`
17. **Проверка «каждый примитив использован» ловит мёртвый код в токенах** и стоит десять строк. → §3.1
    `[мнение]`
18. **Конвейер генеративной системы: бриф → пресет → токены JSON → CSS + Tailwind → компоненты →
    проверка → правка токенов.** Правка всегда в токенах, никогда в компонентах. → §4 `[мнение]`
19. **Бриф превращается в семь ручек характера**, а не в двести решений. → §4.1 `[мнение]`
20. **Генератору картинок нужны не токены, а «карточка стиля»:** 6–10 hex, шрифт, радиус, плотность,
    тип теней, два-три слова о характере. Полный JSON в промт картинки не кладут. → §5 `[мнение]`
21. **Токены — граница между генерацией картинки и генерацией кода.** Картинка рисуется по карточке
    стиля, код собирается по токенам; сверяются они по одним и тем же числам. → §5 `[мнение]`
22. **Каждая правка визуала должна попадать в токены до попадания в компонент.** Иначе через три
    итерации набор и интерфейс расходятся. → §4.4 `[мнение]`

## 1. Антипаттерны

### 1.1. Взрыв компонентных токенов

Симптом: `button-primary-hover-background`, `button-primary-hover-border`,
`button-primary-hover-shadow`, `button-secondary-hover-background`… — по десятку токенов на компонент,
из которых девять указывают на один и тот же семантический токен.

Почему это происходит: компонентный токен кажется бесплатным. Он не бесплатен: каждый добавляет строку
в словарь, который читает человек или модель, и обязательство поддерживать его во всех темах.

Числа, которые стоит помнить:

| Наблюдение | Значение | Источник |
|---|---|---|
| Закон убывающей отдачи: стоимость компонента растёт, ценность падает | качественно | Nathan Curtis, доклад Config `[V16 A]` |
| Компонентов в системе Uber | 71, из них ~20 ядро | `[V16 B]` |
| Компонентных файлов токенов у Material 3 | ~90 (`md-comp-badge` 2.3 КБ … `md-comp-date-picker-modal` 15.6 КБ) | исходники |
| Токенов `color.chart` у Atlassian | 100 из 442 цветовых | `@atlaskit/tokens` |

Три лечения, в порядке предпочтения:

1. **Правило трёх компонентов** (Curtis): значение становится общим токеном, когда его используют три и
   более компонента. Процедура: добавить общий токен → заменить им локальный → удалить локальный →
   применить в остальных компонентах.
2. **Псевдотокены** (Uber): переменные уровня компонента, указывающие на токены системы и **скрытые от
   публикации** `[V16 B]`. Компонент параметризован, словарь системы не растёт.
3. **Вариант вместо токена**: `button[data-variant="danger"]` берёт `--danger-solid` напрямую, без
   промежуточного `--button-danger-background`.

Когда компонентный токен всё-таки нужен: значение не выводится из семантики и уникально для компонента.
Пример из Polaris — `space-table-cell-padding` = `space-150` (6px): решение «ячейка таблицы у нас 6, а
не 8» больше нигде не повторяется, и держать его в голове дороже, чем в токене.

### 1.2. Значения в именах

| Антипаттерн | Что сломается | Правильно |
|---|---|---|
| `color.blue.primary` | смена акцента на фиолетовый | `color.accent.solid` |
| `--text-grey-600` | смена нейтрали | `--fg-secondary` |
| `space-16` как семантический | режим `compact` | `space.md` |
| `radius-6` | смена характера на «мягкий» | `radius.md` |
| `font-14` как роль | переход на клиентский пресет 16px | `type.body` |
| `shadow-blue` | тень не про цвет | `elevation.raised` |

Детектор: **если после смены одной ручки характера имя становится неправдой — значение попало в имя.**

Исключение — примитивы. Там значение в имени и есть смысл: `size.16`, `neutral.600`, `duration.150`.
Примитивы при смене ручек не переименовываются, потому что заменяются целиком вместе с рампой.

Промежуточный случай — числовые шкалы Polaris (`size-400` = 16px, имена как сотые доли от 4px) и Carbon
(`spacing-05` = 16px). Формально значения в имени нет, фактически оно закодировано. Это работает, пока
база шкалы не меняется.

### 1.3. Слишком много уровней

Симптом: `--button-primary-background` → `--action-primary-background` → `--theme-color-primary` →
`--color-brand-blue-600` → `#155dfc`.

Позиция автора трёхуровневой модели: «this multi-tiered variable strategy **may be overkill** for some
systems, and can slow down the team's speed while the system is being created… we've started the project
with a leaner variable structure, then introduced additional tiers once the dust has settled».

Практический предел — **три звена**. Проверка: можно ли за один взгляд ответить, какое конечное значение
у токена. При четырёх звеньях нельзя.

Обратный антипаттерн тоже существует: **ноль уровней**, когда компонент берёт примитив напрямую
(`background: var(--palette-neutral-100)`). Формально работает, ломается при смене темы, потому что
примитив темой не меняется.

### 1.4. Токены без документации использования

Симптом: набор из 200 имён, к каждому из которых надо догадываться, где его применять. Через полгода
команда не помнит, чем `bg-component` отличается от `bg-subtle`, и оба применяются случайным образом.

Две живые реализации лечения:

**Carbon** — правило прямо в `$description`, в формате «что это — сколько px. Когда применять»:
«Spacing token — 16px. Standard spacing unit; use for typical component padding and gutters».
У **каждого** токена `layout.json` такое описание обязательно.

**Primer** — отдельное расширение `org.primer.llm` с полями `usage`, `rules`, `doNotUse`,
`alternatives`; 126 блоков в выборке, 100 % из них с полем `rules`. Формат разобран в
`04-reference-token-schema.md` §3.

Разница: Carbon адресует описание человеку и читает его глазами; Primer адресует машине и даёт
машиночитаемые метки (`usage: ['focus-indicator','selected-state']`). Для генеративного конвейера нужен
второй.

Третий признак того же тренда: README Carbon содержит разделы «Tip for agents», в корне Untitled UI
лежит `CLAUDE.md`, Adobe раздаёт `spectrum-design-data` как плагин для Claude Code и MCP-сервер. Системы
2026 года документируют себя для языковых моделей.

### 1.5. Несогласованность грамматики между категориями

Симптом: цвет назван `bgColor.danger.emphasis`, отступы `space-400`, радиусы `radius.lg`, движение
`motion.duration.xxshort`. Четыре грамматики в одном наборе.

Цена: модель, которая правильно угадала имя цветового токена, не угадает имя отступа. Человек держит в
голове четыре системы вместо одной.

Что должно совпадать во всём наборе:

| Что | Пример решения |
|---|---|
| разделитель | точка в путях JSON, дефис в CSS |
| вид шкалы | t-shirt везде, либо числовая везде |
| порядок частей | category → property → concept → modifier |
| конвенция пары «поверхность → передний план» | `-foreground` или `on-`, но одна |
| язык описаний | русский или английский, но один |

Живой пример расхождения: Atlassian одновременно использует числовые ступени для отступов
(`space.200` = 16px), t-shirt для радиусов (`radius.xsmall`…`radius.xxlarge`) и слова для длительностей
(`motion.duration.xxshort`). Работает, но требует помнить три словаря.

### 1.6. «Магические» значения вне токенов

Симптом: `padding: 13px`, `color: #f3f4f6`, `box-shadow: 0 2px 6px rgba(0,0,0,.09)` прямо в компоненте.

Числа, которые показывают цену:

- **Авито**: при смене бренда нетокенизированный логотип нашли **более чем в 120 местах** `[V18 B]`.
- **Доля отступов, кратных 4, в живых продуктах**: медиана 72 %, от 3.7 % (Gitea) до 98.1 % (Consta)
  (измерения агента P, `10-design-systems-atlas/04-live-products-measured.md` §4.6). То есть у
  половины продуктов четверть отступов не лежит на шкале.
- **Число различных `z-index` на странице**: у половины измеренных продуктов встречается значение ≥
  9999; в агрегате по всем страницам есть `100000` и `999999999`.

Механическая защита существует не везде. В Penpot при привязанном токене **drag-to-change у поля
отключается** — значение нельзя случайно подвинуть мышью. В коде аналога нет, остаются грепы (§3.2).

### 1.7. Мёртвые токены

Симптом: токен, на который никто не ссылается, и примитив, который не используется ни одним
семантическим токеном.

Почему это дефект, а не безобидный мусор: словарь токенов читают глазами (и подаёт в контекст модели).
Двести имён, из которых тридцать мертвы, — это тридцать ложных вариантов при каждом выборе.

Проверка автоматическая: собрать множество всех ссылок `{...}` и вычесть его из множества путей. В
эталонной схеме такая проверка встроена в генератор; исключение сделано только для полных рамп нейтрали
и акцента (`04-reference-token-schema.md` §1.2).

### 1.8. Слишком много значений в шкале

Симптом: 25 уровней тени (MUI), 16 длительностей (Material), 34 шага отступов (Chakra), 18 разных
кеглей на одном экране (витрина Radix, измерение агента P).

Формулировки из практики:

- **Бритва Оккама**: число компонентов, цветов, стилей текста и теней — необходимый минимум `[V18 A]`.
- **Ориентир Wolt**: «2–3 заголовка и 2 стиля основного текста за глаза»; антипример — столько теней,
  что нельзя выбрать между elevation 6 и 8 `[V18 A]`.
- **Цена нового значения**: в Яндекс Маркете добавление второго размера основного текста (14 к 16)
  обсуждали около **двух месяцев** `[V18 A]`.

Что показывает практика (измерения агента P по 24 продуктам):

| Величина | Медиана на экране | Диапазон |
|---|---|---|
| различных кеглей | 6 | 2–18 |
| различных радиусов | 3.5 | 0–17 |
| различных теней | 2.5 | 0–25 |
| различных `z-index` | 4.5 | 0–10 |

То есть **шкала из 6–8 кеглей, 4–6 радиусов и 4–5 теней покрывает то, что реально показывают на
экране**. Всё сверх этого — запас, который стоит денег и не виден.

### 1.9. Сводка антипаттернов

| # | Антипаттерн | Как ловить |
|---|---|---|
| 1 | компонентный токен под один компонент | счётчик использований |
| 2 | значение в имени семантики | греп по `blue`, `grey`, цифрам в именах семантического слоя |
| 3 | больше трёх звеньев алиаса | обход графа ссылок |
| 4 | токен без описания применения | доля токенов с `$description` или `rules` |
| 5 | разные грамматики в категориях | ручной обзор один раз |
| 6 | литерал в компоненте | греп по hex и `rgba(` |
| 7 | мёртвый токен | разность множеств путей и ссылок |
| 8 | раздутая шкала | число шагов против медианы практики |
| 9 | `z-index` вне шкалы | греп по `z-index:` с числом |
| 10 | примитив в компоненте | греп по префиксам `--palette-`, `--scale-` |

## 2. Депрекация и жизненный цикл

### 2.1. Процесс

Из доклада о системе Uber: депрекация в **три шага**, срок около **трёх месяцев** `[V16 B]`.

Обобщённый процесс, который согласуется со всеми четырьмя разобранными системами:

| Шаг | Что происходит | Срок |
|---|---|---|
| 1 | токен помечается устаревшим, в пометке указана замена; значение продолжает работать | день 0 |
| 2 | сборка выдаёт предупреждение при использовании; потребители мигрируют | день 0 … +3 мес. |
| 3 | токен удаляется в мажорной версии | +3 мес. |

Ключевое: **на шаге 1 обязательно указывается, чем заменить**. Пометка «устарел» без замены
перекладывает работу на каждого потребителя отдельно.

### 2.2. Как это записано в четырёх системах

**Adobe Spectrum** — самая машиночитаемая форма:

```json
"lifecycle": {
  "deprecatedIn": "14.3.0",
  "deprecatedComment": "Use semantic token base-padding-horizontal-medium instead. Updated to follow
   Spectrum Future Foundations spacing formula",
  "replacedBy": "52a75511-eb1b-4de2-a1bb-959365d8dc1a"
}
```

Три поля: версия, объяснение человеку, **uuid замены для машины**. Живые версии депрекаций в
выборке: 13.0.0, 14.3.0, 14.5.0; 273 токена из 597 в `layout` + `typography` имеют `lifecycle`.

**IBM Carbon** — собственный флаг плюс объяснение в описании:

```json
"layout": { "01": { "$value": 16, "$description": "Layout token — 16px. Replaced by spacing scale. Do not use in new work.",
  "$extensions": { "carbon.layout": { "deprecated": true } } } }
```

Вся группа `layout` (01 = 16px … 07 = 160px) помечена целиком: «Replaced by spacing scale».

**Atlassian** — собственные поля в `token-default-values.js`; в наборе одновременно живут
`atlassian-legacy-light/dark` и `atlassian-light/dark-brand-refresh`, то есть поколения языка вынесены в
ось темы (`03-theming-and-modes.md` §4.4).

**Ant Design** — депрекация значением: пресетный цвет `pink` помечен устаревшим в пользу `magenta`.

**Стандарт** даёт `$deprecated`: `true` | строка-объяснение | `false` (перебивает значение группы). Ни
одна из разобранных систем его пока не использует — все успели завести собственные поля до того, как
свойство появилось в спецификации.

### 2.3. Что делать своему набору

Минимум, который покрывает задачу:

```json
"layout": {
  "01": {
    "$value": {"value": 16, "unit": "px"},
    "$deprecated": "Replaced by space.md. Will be removed in 2.0.",
    "$extensions": {
      "org.design-deep-dive.llm": {
        "doNotUse": true,
        "alternatives": ["space.md"],
        "rules": "Deprecated. Use space.md instead."
      }
    }
  }
}
```

Стандартное поле для человека и инструмента, расширение — для модели, которая читает `doNotUse` и
`alternatives` машинно. Дублирование намеренное: инструмент, не знающий расширения, увидит
`$deprecated`; модель, читающая расширение, получит путь замены.

## 3. Проверки

### 3.1. На сборке токенов

| Проверка | Как | Что ловит |
|---|---|---|
| валидность формата | `npx tz check tokens.json` или `ajv validate -s <schema 2025.10>` | строковые размеры, отсутствующий `$type`, узел-токен-и-группа |
| все ссылки резолвятся | обход графа | опечатки в путях, удалённые токены |
| нет циклов в ссылках | обход графа с пометками | `a → b → a` |
| глубина цепочки ≤ 3 | обход графа | лишние уровни |
| каждый примитив использован | разность множеств | мёртвые примитивы |
| у каждого семантического токена есть `rules` | подсчёт | недокументированные токены |
| контраст всех пар | свой скрипт поверх `color.py` | нарушения WCAG 1.4.3 и 1.4.11 |
| ΔE палитры графиков в трёх симуляциях CVD | свой скрипт | неразличимые серии |
| произведение кегля на отношение целое | свой скрипт | дробный интерлиньяж |

Первые четыре умеет Terrazzo; остальные — свой скрипт на 100–200 строк. Пример полного набора проверок с
выводом — `04-reference-token-schema.md` §7 и генератор `../../scripts/ui/build_reference_tokens.py`.

### 3.2. На компонентах: пять грепов

```bash
# 1. литералы цвета в компонентах (должно быть пусто)
grep -rnE '#[0-9a-fA-F]{3,8}\b|rgba?\(' src/components/

# 2. числовые цветовые утилиты Tailwind (должно быть пусто)
grep -rnE '\b(bg|text|border|ring|fill|stroke)-(slate|gray|zinc|neutral|stone|blue|red|amber|green|…)-[0-9]{2,3}\b' src/

# 3. примитивы в компонентах (должно быть пусто: компоненты берут только семантику)
grep -rnE 'var\(--(palette|scale|font-size|curve|duration-[0-9])' src/components/

# 4. z-index вне шкалы (должно быть пусто)
grep -rnE 'z-index:\s*[0-9]+' src/ | grep -v 'var(--z-'

# 5. размеры вне шкалы: числа в px, не кратные 4 и не из списка исключений 1, 2, 6, 10, 14
grep -rnoE '\b[0-9]+px' src/components/ | awk -F'[:p]' '{print $NF}' | sort -n | uniq -c
```

Пятый грет даёт не «пусто», а список, который надо просмотреть: 1px (границы), 2px (фокус), 6px и 10px
(штатные исключения шкалы) допустимы, 13px и 17px — нет.

### 3.3. Что проверять на готовом экране

Это частично пересекается с задачей волны 3 (папка 13), поэтому здесь только то, что относится к
токенам:

1. Все цвета на экране принадлежат палитре набора (снять `getComputedStyle`, сравнить с множеством
   значений токенов).
2. Все радиусы принадлежат шкале.
3. Все отступы принадлежат шкале или списку исключений.
4. Высоты контролов принадлежат шкале.
5. Число различных теней на экране ≤ 5.
6. Число различных кеглей на экране ≤ 8.

Инструмент для первых четырёх — `../../scripts/ui/measure_ui.py` агента P: он снимает распределения с живой
страницы и показывает «чужие» значения с числом вхождений. Норма для сравнения — таблицы в
`10-design-systems-atlas/04-live-products-measured.md` §4.

### 3.4. Что проверками не ловится

- Семантическая правильность: `bg-subtle` применён там, где нужен `bg-component`. Значение из набора,
  правило нарушено. Ловится только описанием применения и ревью.
- Вкус: набор может быть безупречен формально и уродлив визуально.
- Несогласованность между токенами и макетом, если макет не привязан к токенам.

## 4. Конвейер генеративной системы

### 4.1. Схема

```
  бриф (текст заказчика)
      │  →  семь ручек характера: акцент, нейтраль, радиус, плотность, шрифт, тени, тема
      ▼
  пресет  ──────────────────────────────────────────────────────────┐
      │      «плотная админка» / «клиентский сервис» / …            │
      ▼                                                             │
  tokens.json (DTCG 2025.10)                                        │
      │   tz check + проверки контраста, ΔE, шкал                   │
      ▼                                                             │
  tokens.css  (:root + [data-theme] + [data-density])               │
  theme.css   (@theme inline + мост к shadcn)                       │
      │                                                             │
      ▼                                                             │
  компоненты (только семантические переменные)                      │
      │                                                             │
      ▼                                                             │
  проверка: пять грепов + измерение готового экрана                 │
      │                                                             │
      └──── правка → ВСЕГДА обратно в tokens.json ──────────────────┘
```

Ключевое правило конвейера: **обратная стрелка ведёт в токены, а не в компоненты.** Если правку
«кнопка слишком высокая» внести в CSS кнопки, через три итерации набор и интерфейс разойдутся, и набор
перестанет быть источником истины.

### 4.2. Шаг 1: бриф → семь ручек

Бриф — это текст: «финтех-админка для операторов, много таблиц, работают по 8 часов, корпоративный
синий, строгий вид». Превращается в семь значений:

| Ручка | Из чего берётся в брифе | Пример решения |
|---|---|---|
| акцент | «корпоративный синий» | blue Tailwind v4 |
| нейтраль | «строгий», «финтех» | slate (холодная) |
| радиус | «строгий вид» | 0 / 2 / 4 / 6 / 8 |
| плотность | «много таблиц», «8 часов» | default или compact |
| шрифт | не указан | Inter |
| тени | «строгий» | кольцо + минимальные тени |
| тема | не указана | светлая по умолчанию, тёмная как режим |

Всё остальное (185 семантических токенов) выводится из пресета и не требует решений. Это и есть смысл
пресета: **сократить число решений с двухсот до семи**.

### 4.3. Шаг 2: пресет → токены

Пресеты, которые уже есть в базе:

| Пресет | Где значения | База текста | Контрол | Радиус | Отступ карточки |
|---|---|---|---|---|---|
| Плотная админка | `03-spacing-sizing/03-control-and-panel-sizes.md` §8, `02-typography/02-type-scale.md` §7 | 14px | 32px | 6px | 16px |
| Клиентский сервис | `03-spacing-sizing/…` §9, `02-typography/…` §8 | 16px | 40px | 8–10px | 20–24px |

Готовый JSON, CSS и Tailwind-тема для первого — `04-reference-token-schema.md`. Второй собирается тем же
генератором с изменёнными константами.

### 4.4. Шаг 3–5: выпуск и проверка

```bash
python3 ../../scripts/ui/build_reference_tokens.py --out ./dist   # JSON + CSS + theme + report
grep '<<<' dist/report.txt                                     # непройденные пороги контраста
npx tz check dist/tokens.json                                  # валидность формата
# подключить в проект:
#   @import "tailwindcss"; @import "./tokens.css"; @import "./theme.css";
# собрать компоненты только на семантических переменных
bash checks.sh                                                  # пять грепов из §3.2
python3 ../../scripts/ui/measure_ui.py http://localhost:3000        # снять распределения с живого экрана
```

Критерий готовности набора: `report.txt` без строк `<<<`, `tz check` без ошибок, пять грепов пусты,
распределения измеренного экрана попадают в нормы из `10-design-systems-atlas/04-live-products-measured.md` §8.

## 5. Что из токенов нужно генератору картинок

Детали — волна 3, папка 12; здесь только граница ответственности.

**Полный JSON в промт генератора картинок не кладут.** Модель, рисующая изображение, не резолвит алиасы
и не считает контраст. Ей нужна «карточка стиля» — 10–15 строк:

```
Тип интерфейса: плотная админка веб-сервиса, десктоп 1440×900.
Палитра: фон #f8fafc, карточка #ffffff, текст #0f172b, вторичный текст #45556c,
  граница #e2e8f0, акцент #155dfc, текст на акценте #ffffff,
  успех #008236, предупреждение #e17100, ошибка #e7000b.
Шрифт: Inter. Базовый кегль 14px, заголовок страницы 20px, метрика 28px.
Форма: радиус 6px у кнопок и карточек, 4px у полей, границы 1px.
Плотность: высота кнопки 32px, строка таблицы 36px, padding карточки 16px, сайдбар 240px.
Глубина: карточки на границе 1px без тени; всплывающие слои с мягкой тенью и кольцом.
Характер: строгий, корпоративный, без декоративных элементов, без градиентов, без скруглённых пилюль.
```

Соответствие «токен → строка карточки стиля»:

| Что в карточке | Откуда |
|---|---|
| 8–10 hex | `color.bg.canvas`, `bg.surface`, `text.primary`, `text.secondary`, `border.subtle`, `accent.solid`, `text.on-accent`, `success/warning/danger.solid` |
| шрифт и 3 кегля | `primitive.font.family.sans`, `type.body`, `type.page-title`, `type.metric` |
| радиус и толщина границы | `radius.md`, `radius.sm`, `border.width.default` |
| четыре размера плотности | `size.control.md`, `size.row.table`, `space.inset.card`, `size.panel.sidebar` |
| описание глубины словами | `elevation.ring` против `elevation.raised` |
| 2–3 слова о характере | из брифа, не из токенов |

**Обратный маршрут — сверка.** Когда картинка сгенерирована, из неё снимают фактические цвета и размеры
и сравнивают с токенами. Расхождение означает либо что карточка стиля неполна, либо что картинку нельзя
брать за образец для кода.

Что генератору картинок **не нужно**: имена токенов, структура JSON, режимы, правила применения,
z-index, длительности. Всё это относится к коду.

## Частые ошибки

1. **Компонентный токен под один компонент.**
2. **Компонентный токен, который просто переименовывает семантический** (`--button-background:
   var(--accent-solid)` без единого исключения).
3. **Значение в имени семантического токена.**
4. **Четыре и больше звена в цепочке алиасов.**
5. **Примитив в компоненте вместо семантики.**
6. **Токен без описания применения.**
7. **Разные грамматики в разных категориях одного набора.**
8. **Литерал цвета или размера в компоненте.**
9. **`z-index` числом вместо токена.**
10. **Мёртвый токен.**
11. **Шкала из 25 теней или 34 отступов.**
12. **Удаление токена без периода депрекации.**
13. **Пометка «устарел» без указания замены.**
14. **Правка визуала в компоненте вместо токена.**
15. **Пересборка токенов без прогона проверок контраста.**
16. **Полный JSON токенов в промте генератора картинок.**
17. **Карточка стиля без hex-значений** («сине-серая палитра» вместо `#155dfc`).
18. **Смена акцента без перепроверки всех пар контраста.**

### Ошибки, типичные для нейросетей

- **Дописывание токена вместо использования существующего.** Модель, не найдя `--card-shadow`, заводит
  его, хотя есть `--elevation-raised`. Лечится подачей полного списка токенов в контекст и правилом «не
  создавать новых токенов без явной просьбы».
- **Литерал «на один раз».** Модель ставит `margin-top: 13px`, чтобы «поправить выравнивание». Это
  всегда признак того, что не сходится что-то другое (обычно интерлиньяж).
- **Копирование фрагмента чужой системы в середину файла.** В наборе на shadcn появляются
  `--md-sys-color-primary` или `bgColor.danger.emphasis`.
- **Игнорирование режима при правке.** Правится светлая тема, тёмная остаётся старой.
- **Раздувание шкалы под конкретный макет.** «Здесь нужен радиус 7» вместо выбора 6 или 8.
- **Перенос правила из одного пресета в другой.** Радиус 6 из админки в клиентском сервисе, где принято
  8–10.
- **Пересказ токенов словами вместо их применения.** В коде появляется комментарий `/* accent solid */`
  и литерал `#155dfc` рядом.
- **Потеря проверки после правки.** Изменили акцент, не прогнали контраст, получили 3.8:1 на кнопке.

## Чек-лист

1. Ни один компонентный токен не заведён под один компонент?
2. Все компонентные токены (если они есть) отличаются от семантических хотя бы одним значением?
3. Ни одно семантическое имя не содержит значения?
4. Максимальная глубина цепочки алиасов ≤ 3?
5. В файлах компонентов нет ссылок на примитивы (`--palette-*`, `--scale-*`)?
6. У каждого семантического токена есть описание применения?
7. Грамматика имён одинакова во всех категориях?
8. Греп по hex и `rgba(` в компонентах пуст?
9. Греп по числовым утилитам Tailwind пуст?
10. Греп по `z-index:` с числом пуст?
11. Список «чужих» значений размеров просмотрен и обоснован?
12. Каждый примитив вне полных рамп использован семантикой?
13. Число шагов в каждой шкале сопоставимо с медианой практики (кегли ≤ 8, радиусы ≤ 6, тени ≤ 5)?
14. Устаревшие токены помечены `$deprecated` с текстом и `alternatives`?
15. У депрекации назначен срок удаления?
16. Сборка токенов валидируется (`tz check` или `ajv`)?
17. Сборка прогоняет проверки контраста и печатает отчёт?
18. Отчёт не содержит непройденных порогов?
19. Правки визуала вносятся в токены, а не в компоненты?
20. Карточка стиля для генератора картинок содержит hex, шрифт, три кегля, радиус, четыре размера
    плотности и описание глубины?
21. Сгенерированная картинка сверена с токенами по фактическим цветам и размерам?

## Открытые вопросы и противоречия

1. **Правило трёх компонентов не проверено данными.** Это эвристика одного автора; исследования, что
   именно три, нет.
2. **Три месяца на депрекацию** — число из одного доклада. Другие системы срок не публикуют.
3. **`$deprecated` из стандарта не использует никто.** Все успели завести собственные поля. Переход
   на стандартное свойство потребует миграции инструментов, и неясно, произойдёт ли он.
4. **Замена по uuid против замены по имени.** Spectrum пишет uuid (машинно надёжно, человеком
   нечитаемо), остальные — имя. Общей практики нет.
5. **Сколько шагов в шкале «много».** Медианы практики (6 кеглей, 3.5 радиуса, 2.5 тени на экране) —
   это то, что показывают на одном экране, а не размер шкалы системы. Прямых данных «шкала из N шагов
   вредна» нет.
6. **Псевдотокены Uber не описаны публично в деталях.** Механизм известен из доклада, реализации в
   открытых системах нет.
7. **Граница между токеном и решением в коде.** Polaris кладёт `space-table-cell-padding` в токены,
   Carbon оставляет то же решение в компоненте. Критерия, кроме правила трёх, нет.
8. **Нет измерений, насколько проверки помогают.** Пять грепов из §3.2 выведены из антипаттернов, а не
   из данных о том, сколько дефектов они реально ловят.
9. **Карточка стиля для генератора картинок не проверена экспериментом.** Состав полей выведен из того,
   что модель картинки может воспроизвести, а не из сравнения результатов. Это задача волны 3, папка 12.
