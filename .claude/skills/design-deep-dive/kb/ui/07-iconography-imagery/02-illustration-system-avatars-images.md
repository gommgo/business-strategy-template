## Выжимка для агента

1. **Иллюстрация в продукте нужна в пяти местах:** пустое состояние, онбординг, ошибка (404/500/нет доступа), успех и веха, анонс. На рабочих экранах админки её нет. → §1.1 [консенсус]
2. **Лестница дешевизны Atlassian:** прежде чем ставить иллюстрацию, попробуй иконку, текст, фоновый паттерн. «Excessive illustrations increase cognitive load.» → §1.2 [система]
3. **Заполни «паспорт системы» до первой картинки.** Пятнадцать полей: палитра, насыщенность, свет, ракурс, линия, детализация, персонажи, фон, формат, размеры, тёмная тема, что изображаем, чего не изображаем, лицензия, источник. Шаблон — §3. → §3
4. **Цветов на одну картинку: 2–3 акцента плюс белый и серые.** Polaris: «individual illustrations use whites, grays, and two or three colors each». → §2.1 [система]
5. **Иллюстрация менее насыщена, чем интерфейс.** Polaris: «Colors are also less saturated than the surrounding UI, so they don't distract from core interactions». → §2.1 [система]
6. **Минимальная деталь не мельче 4 px** в готовом размере показа. Единственное найденное точное число нижнего предела. → §2.5 [система]
7. **Перспектива плоская, 2D.** Тень допускается как лёгкая подложка, не как объём. → §2.3 [система]
8. **Линия тоньше у мелких объектов, детальнее и кривее у крупных.** Толщину линии иллюстрации связывай со штрихом иконок: равная или на 0.5 px толще. → §2.4 [система + вывод]
9. **Вокруг иллюстрации всегда есть воздух**, и у всех картинок в одном слоте одинаковый оптический вес. → §2.3 [система]
10. **Три типа продуктовой иллюстрации (Atlassian):** spot (пятно, один концепт), low-fidelity UI (серые прямоугольники вместо скриншота), ambient pattern (фоновая текстура). Коллаж — только маркетинг. → §1.3 [система]
11. **Не показывай скриншоты внутри интерфейса**: получается «screen-within-screen». Вместо этого — низкодетальный UI из простых фигур, острых углов и серых тонов. → §1.3 [система]
12. **Размер в интерфейсе: 120–240 px в пустом состоянии, 48–96 в карточке и списке, 240–320 на странице ошибки.** → §4.1
13. **Граница иконка / пиктограмма / иллюстрация: до 32 px иконка, 48–96 пиктограмма, от 120 иллюстрация.** Carbon: «Don't use pictograms as a replacement for UI icons». → §4.2 [система]
14. **3D уместен в консьюмерском онбординге и маркетинге, не уместен в плотных рабочих инструментах.** Цена консистентности у 3D выше в разы. → §5 [консенсус]
15. **«Corporate Memphis» (плоские люди с длинными конечностями без лиц) — узнаваемый штамп 2018–2022**, сегодня читается как «дёшево и безлично». → §5.3 [мнение]
16. **unDraw лицензией запрещает использовать свои картинки для обучения и любой автоматической обработки моделями ИИ.** Humaaans и Open Peeps — CC0 без таких ограничений. → §6 [документация]
17. **Аватары: 16, 20, 24, 32, 40, 48, 64 (и 96/128 для профиля).** Primer: «start at 16px and increment by base-4 until 32px. At 32px, the scale switches to base-8 up to 48px. 64px is the largest». → §7.1 [система]
18. **Круг — человек, квадрат — сущность (проект, команда, бот), шестиугольник — ИИ-агент.** Совпадает у Primer и Atlassian. → §7.2 [консенсус]
19. **Радиус квадратного аватара растёт с размером:** 2 / 2 / 3 / 3 / 6 / 12 px у Atlassian для 16 / 24 / 32 / 40 / 96 / 128. → §7.2 [система]
20. **Инициалы: 1–2 буквы, 8–10 фоновых оттенков по хешу.** Готовые палитры с проверенным контрастом ≥ 4.5:1 — §7.3.
21. **Статус-точка 12 px на аватаре 24, 14 на 32, 15 на 40, 18 на 96**, с обводкой 2 px цветом поверхности. → §7.4 [система]
22. **Группа аватаров: наложение −8 px при размере 24–32, обводка 2 px цветом фона, не больше 5 плюс счётчик.** → §7.5
23. **Соотношения изображений: 16:9, 4:3, 3:2, 1:1.** `object-fit: cover`, радиус как у карточки минус padding, `aspect-ratio` вместо фиксированной высоты. → §8.1
24. **В тёмной теме изображения приглушаются на 10–20 %** (`filter: brightness(0.85)` либо наложение слоя 10 % фона). → §8.4 [консенсус]
25. **Эмодзи допустимы в пользовательском контенте (реакции, названия, статусы), запрещены как иконки интерфейса.** → §10 [консенсус]

## 1. Где иллюстрация нужна и где нет

### 1.1 Места

| Место | Нужна | Размер | Комментарий |
|---|---|---|---|
| **Пустое состояние** (первое посещение раздела) | да | 120–240 px | Polaris: «Merchants see an empty state illustration the first time they access a new part of the experience… It introduces what they can do here» [S38] |
| **Пустой результат поиска** | обычно нет | — | здесь хватает текста и кнопки «сбросить фильтры» |
| **Онбординг, туры по функциям** | да | 160–320 px | Atlassian: low-fidelity UI для объяснения workflow [S37] |
| **Ошибка 404 / 500 / нет доступа** | да | 200–320 px | одна картинка на весь класс ошибок |
| **Успех, завершение, веха** | да, экономно | 120–200 px | Atlassian: «celebrating big wins», цветные пятна [S37] |
| **Анонс новой функции** | да, экономно | 120–240 px | Polaris: «When the announcement celebrates a major merchant milestone» [S38] |
| **Карточка задачи настройки** | да, мелко | 48–96 px | Polaris: иллюстрация меняется при завершении задачи [S38] |
| **Рабочий экран: таблица, форма, дашборд** | **нет** | — | |
| **Шапка страницы** | **нет** | — | |
| **Фон блока «просто для красоты»** | **нет** | — | Atlassian: «Don't use collage-styled or purely decorative illustrations in product» [S37] |

### 1.2 Лестница дешевизны

Atlassian формулирует порядок выбора прямо: «**Consider icons, copy, ambient pattern, or other affordances before using illustrations**» [S37]. То есть:

1. **Текст** — если задача объясняется предложением;
2. **Иконка** — если нужен опознавательный знак;
3. **Фоновый паттерн** — если нужна атмосфера без конкретного образа;
4. **Иллюстрация** — если нужно показать то, чего ещё нет на экране.

Плюс два ограничивающих правила оттуда же:
- «Before you start choosing an illustration, decide if it is really necessary. Visuals in product should **always support the goal and context** for the user, rather than being purely decorative.»
- «Use illustration to support copy and surrounding elements. Illustration should **work with the message, not replace it**.»
- «**Excessive illustrations increase cognitive load.**»

Полярная позиция GOV.UK [S40]: «Avoid using images for unnecessary decoration. **Only use images if there's a real user need.** Services usually work best without relying on images… images should only be visual aids — **written content must contain all the information** the user needs.» Иллюстрация у GOV.UK допустима в двух случаях: показать физическое действие (сканирование паспорта) и показать, где на документе искать номер.

### 1.3 Три типа продуктовой иллюстрации

Полная таксономия есть только у Atlassian [S37], и она полезна как модель:

| Тип | Для чего | Правила |
|---|---|---|
| **Spot** (пятно) | пустые состояния, ошибки, «celebrating big wins» | у каждого пятна есть **цветная** и **нейтральная** версия: «Colorful spots add emphasis, while neutral spots work for more common tasks and less celebratory moments» |
| **Low-fidelity UI** | онбординг, туры, объяснение сложных workflow | «**Don't use actual screenshots in product**, which creates a screen-within-screen appearance that can be confusing. Instead, use **basic shapes, sharp corners, and mostly gray tones**» |
| **Ambient pattern** (фоновый паттерн) | сообщения и промо-блоки, которым нужен визуальный интерес без конкретного образа | текстура и характер бренда как фон |

И жёсткая граница между продуктом и маркетингом: «**Collage is for marketing landing pages and communications only — it's too visually busy for in-product use.**»

Правило «цветное пятно для праздника, нейтральное для рутины» переносится на любой продукт: одна и та же метафора рисуется дважды, и выбор версии зависит не от вкуса, а от значимости момента.

### 1.4 Что рисовать: один концепт

Polaris, принцип **Stay focused**: «Each illustration conveys **one thing**. The story is easy to understand, so merchants intuitively know how to accomplish whatever they came here to do» [S38].

Atlassian иллюстрирует это восемью вариантами одного концепта (security: ключи, замки, сейф, башня) — иллюстрация подбирается по смыслу, а не по красоте [S37].

Antiправило GOV.UK: «**Avoid depicting people** in illustrations. If you need to show people, think carefully about how you represent the people that use your service — do not only show one kind of person… only depicting people of a particular age, gender or ethnicity can exclude people and reinforce negative stereotypes» [S40].

## 2. Параметры системы

Пять параметров стиля Polaris — самый полный из найденных каркасов [S38]. Ниже они расширены до одиннадцати и дополнены значениями из Atlassian, Carbon и GOV.UK.

### 2.1 Палитра и насыщенность

| Правило | Значение | Источник |
|---|---|---|
| Цветов на одну картинку | **2–3 акцента + белый + 2–3 серых** | Polaris: «individual illustrations use whites, grays, and two or three colors each» [S38] |
| Насыщенность | **ниже, чем у интерфейса** | Polaris: «Colors are also less saturated than the surrounding UI, so they don't distract from core interactions» [S38] |
| Источник цветов | палитра продукта; при нехватке — **тинты той же палитры** | GOV.UK: «If you need more colours, try to use **tints of the colour palette**» [S40] |
| Заливка | **плоские блоки цвета**, без градиентов и теней | GOV.UK: «Use flat blocks of colour. Avoid using shadows or gradients, except when needed to show a distinctive feature of an object or to communicate layering or depth» [S40] |

Практический вывод для генеративной системы: **палитра иллюстраций выводится из палитры интерфейса**, а не придумывается отдельно. Берутся шаги 200–400 акцентной шкалы (светлее, чем 500–600, которые идут на кнопки) плюс нейтрали 100–400. Шкалы — `../01-color/01-color-models-and-scales.md`.

Нижняя граница насыщенности: если картинка сливается с фоном карточки, повысь хрому акцента на один шаг шкалы, а не добавляй новый цвет.

### 2.2 Свет

Одно направление света на всю систему. Значение задаётся как угол и фиксируется в паспорте: типично **сверху или сверху-слева** (совпадает с направлением теней интерфейса, см. `../04-shape-elevation/02-shadows-layers-depth.md` — «один источник света на страницу»).

Если система плоская (§2.3), света нет вовсе, и это тоже решение, которое пишется в паспорт: «света нет, объём передаётся только двумя тонами одного цвета».

### 2.3 Ракурс и пространство

Polaris [S38]: «The perspective is **flat and two-dimensional** so the entire area of the illustration is of equal importance. **Drop shadows give things subtle depth when necessary.** An additional side of an object can be added if things aren't easily recognizable from a single side.»

И про воздух: «Each illustration has **negative space around it** so it feels balanced in the place it lives, and so its **visual weight is the same as other illustrations that live in the same places**.»

Второе предложение — ключевое правило серии: у всех картинок в одном слоте (например, во всех пустых состояниях) **одинаковый оптический вес**. Проверяется так же, как у иконок: размыть две картинки и сравнить плотность пятна.

Варианты ракурса для паспорта:

| Ракурс | Когда | Цена |
|---|---|---|
| **Фронтальный, плоский** | админки, плотные интерфейсы, GOV.UK-подобные сервисы | низкая, легко держать серию |
| **3/4 без перспективы** | клиентские сервисы | средняя |
| **Изометрия** | схемы, инфраструктура, «как это устроено» | высокая: любая новая сцена требует того же угла |
| **Полная перспектива** | не применять в продуктовых иллюстрациях | очень высокая |

### 2.4 Линия

Polaris [S38]: «All illustrations have **smooth lines without texture**. **Smaller objects have straighter lines, while larger objects can have more detailed, curved lines.** Intersecting and continuous lines are a key element of the admin illustration style, but they aren't forced.»

GOV.UK требует согласованности прямо: «use consistent **colours, line widths and border radiuses** across them all» [S40]. То есть у GOV.UK параметры системы — это цвет + толщина линии + радиус, ровно три.

**Как связать со штрихом иконок.** Прямого правила в источниках нет, но есть надёжный вывод из масштабов: иконка рисуется на 24 px со штрихом 2, то есть отношение штриха к холсту **1:12**. Если иллюстрация показывается на 160 px, то же отношение даст линию 13 px, что заведомо слишком толсто. Работает другое соотношение:

| Размер показа | Толщина линии иллюстрации | Отношение |
|---|---|---|
| 48–96 px (мелкое пятно) | **1.5–2 px** | 1:32…1:48 |
| 120–160 px | **2–2.5 px** | 1:60…1:64 |
| 200–320 px | **3–4 px** | 1:70…1:80 |

Правило для паспорта: **толщина линии иллюстрации равна штриху иконок или на 0.5 px толще** в мелких размерах и растёт медленнее размера картинки. `[вывод]`

### 2.5 Детализация

Polaris [S38]: «Illustrations need some detail to make sense, but too much can be noisy. They have the **minimum amount of detail necessary** to make them feel realistic but still simple. **Fine details are rarely smaller than 4 px** in height or width.»

Это единственное найденное точное число нижнего предела детали. Практически: если в картинке на 160 px есть элемент мельче 4 px, он превратится в грязь при уменьшении до 96 и исчезнет в тёмной теме.

Проверка (тот же приём, что у Lucide для иконок): посмотреть на картинку в целевом размере и **размыть**; участки, которые стали тёмными пятнами, перегружены деталью.

### 2.6 Форма

Polaris [S38]: «Objects have **realistic proportions** so they're easy to recognize. Simple geometric shapes with **rounded corners** build images that are clear and approachable. **Representations of people use more organic shapes.**»

То есть в системе два языка формы: геометрический для предметов и органический для людей. Радиус скруглений в иллюстрации согласуется с радиусом интерфейса (`../04-shape-elevation/01-radius-and-borders.md`): строгая админка с радиусом 4–6 не сочетается с иллюстрацией, где всё скруглено на 24.

### 2.7 Персонажи

Три стратегии, каждая со своей ценой:

| Стратегия | Плюс | Минус |
|---|---|---|
| **Без людей** (предметы, схемы, абстракции) | нет вопросов репрезентации, дешевле серия, не устаревает | холоднее |
| **Люди без лиц** | не требует рисовать эмоции, легко варьировать | это и есть «corporate Memphis» (§5.3), штамп |
| **Люди с лицами и разнообразием** | тепло, человечно | дорого: каждый новый персонаж требует согласования, легко скатиться в стереотипы |

GOV.UK выбирает первую и объясняет почему [S40] (§1.4). Polaris допускает людей, но с оговоркой про органические формы [S38]. Atlassian использует людей в spot-иллюстрациях [S37].

Для генеративной системы первая стратегия безопаснее всего: **нейросети хуже всего держат консистентность именно на людях** (лица, пропорции, количество пальцев), и именно людей сложнее всего повторить в новой картинке той же серии.

### 2.8 Фон

| Вариант | Когда |
|---|---|
| **Без фона** (прозрачный, картинка ложится на поверхность) | по умолчанию; проще всего переносится в тёмную тему |
| **Цветное пятно** (круг, blob) под объектом | когда нужно отделить картинку от фона карточки |
| **Ambient pattern** | Atlassian: промо-блоки и сообщения [S37] |
| **Прямоугольная плашка с заливкой** | когда картинка используется как обложка |

Правило: **у картинок одного слота фон устроен одинаково.** Если у одного пустого состояния картинка на прозрачном фоне, а у другого — в цветном круге, серия распадается.

### 2.9 Формат файла

| Формат | Когда | Замечания |
|---|---|---|
| **SVG** | по умолчанию для плоских иллюстраций | масштабируется, поддаётся перекраске через `currentColor` или CSS-переменные; вес 5–40 КБ |
| **PNG** | когда в картинке градиенты, мягкие тени, 3D | нужны 1× и 2×, вес растёт |
| **WebP / AVIF** | растровые иллюстрации на клиенте | WebP экономит 25–35 % против PNG при том же качестве |

Перекрашиваемый SVG — важный приём: если в иллюстрации акцентный цвет вынесен в CSS-переменную, одна и та же картинка работает в светлой и тёмной теме и переживает ребрендинг.

### 2.10 Тёмная тема

Три способа, по убыванию качества:

1. **Отдельный вариант картинки** с перевёрнутой светлотой (нейтрали инвертируются, акценты остаются). Так делает Atlassian — у них у каждого баннера есть `hero.light` и `hero.dark` [S37].
2. **SVG с переменными цветами**: нейтрали через `currentColor` и CSS-переменные, акценты фиксированные.
3. **Приглушение**: `filter: brightness(0.85)` — годится только для фотографий, а не для плоских иллюстраций (§8.4).

Наблюдение волны 1 [V10]: монотонные иконки-иллюстрации на десатурированной палитре почти не требуют правок при переводе в тёмную тему. То есть чем ближе иллюстрация к монохрому, тем дешевле обе темы.

### 2.11 Что запрещено

Свод запретов из всех источников:

- **Фотореализм в продуктовой иллюстрации** — не встречается ни в одной изученной системе.
- **Стоковая фотография для абстрактных понятий** — GOV.UK: «Do not use photography to represent abstract concepts… Avoid using generic stock photography» [S40].
- **Скриншоты внутри интерфейса** — Atlassian: «screen-within-screen» [S37].
- **Коллаж и декоративные абстракции в продукте** — Atlassian [S37].
- **Текст внутри картинки** — GOV.UK: не масштабируется, не переводится, не читается скринридером; исключения (essential text) редки [S40].
- **Градиенты и тени в плоской системе** — GOV.UK, кроме случаев, когда они передают узнаваемую деталь объекта или слоистость [S40].

## 3. Паспорт системы иллюстраций (шаблон)

Заполняется **до** генерации первой картинки серии и хранится рядом с токенами. Всё, что не заполнено, нейросеть или подрядчик решит за вас и решит каждый раз по-разному.

  - карточка-задачи           # 64 px

  - рабочие экраны (таблицы, формы, дашборды)

  - декоративный фон блока

тени: "нет"                   # или "мягкая подложка 8 % чёрного, размытие 12"

# 4. Ракурс и пространство
ракурс: "фронтальный плоский"  # фронтальный | 3/4 | изометрия
перспектива: "нет"
воздух-вокруг: "не менее 8 % высоты картинки с каждой стороны"

# 7. Детализация

# 8. Персонажи

если-люди:
  пропорции: "реалистичные, голова 1/7 роста"

вес-файла-максимум: "40 КБ"

способ: "две версии файла"     # две версии | переменные цвета | приглушение
нейтрали-в-тёмной: ["#0f172b", "#314158", "#62748e", "#cad5e2"]

# 12. Что изображаем
список-метафор:
  пустой-список-заказов: "коробка с открытой крышкой"
  нет-доступа: "закрытая дверь"
  404: "карта с оторванным углом"
правило: "один концепт на картинку"

# 13. Чего не изображаем

  - стереотипные образы людей

# 14. Лицензия и происхождение
источник: "собственная генерация"   # собственная | unDraw | Storyset | Humaaans | подрядчик
лицензия: "—"
ограничения: "—"

  flat vector illustration, {объект}, 3 colors only: #155dfc, #8ec5ff, #e2e8f0,
  white background, no gradients, no shadows, no text, front view, flat perspective,
  2px rounded strokes, simple geometric shapes, minimal detail, centered composition,
  generous negative space
негативный-промт: >
  3d, photorealistic, gradient, drop shadow, text, watermark, people, faces,

Три правила работы с паспортом:

1. **Заполняется один раз и не меняется по ходу серии.** Смена любого поля означает перерисовку всей серии, а не одной картинки.
2. **Хранится рядом с токенами** (`09-design-tokens/`), потому что палитра и радиусы в нём — ссылки на токены продукта, а не отдельные значения.
3. **Серия генерируется за один сеанс** с одним seed и одним промт-шаблоном. Между сеансами модель дрейфует.

## 4. Размеры в интерфейсе

### 4.1 Таблица размеров

> Разрешение противоречия [C40]: в панели и карточке пустого состояния допускается 96–160 (`../05-layout-grid/03-page-anatomy.md` §7, `../06-components-visual/06-data-display-and-misc.md` §4); 120–240 — полноэкранное пустое состояние, 240–320 — страница ошибки. См. `../CONTRADICTIONS.md`.

| Слот | Размер картинки | Отступ до текста | Комментарий |
|---|---|---|---|
| Пустое состояние в карточке или панели | **120–160 px** | 16–24 | |
| Пустое состояние на всю страницу | **160–240 px** | 24 | |
| Страница ошибки 404/500 | **240–320 px** | 24–32 | |
| Онбординг, шаг мастера | **160–240 px** | 24 | |
| Карточка задачи настройки | **48–96 px** | 12–16 | Polaris: иллюстрация меняется при завершении задачи [S38] |
| Элемент списка | **32–48 px** | 12 | на грани с пиктограммой |
| Плашка анонса | **80–120 px** | 16 | |

Ширина текстового блока рядом с иллюстрацией — не больше **480 px** (см. `../02-typography/03-leading-tracking-measure.md` о длине строки). Картинка и текст выравниваются по центру блока, если композиция вертикальная.

### 4.2 Граница между иконкой, пиктограммой и иллюстрацией

| Класс | Размер | Штрих / детализация | Назначение |
|---|---|---|---|
| **Иконка интерфейса** | 12–32 px | штрих 1.5–2 при 24, монохром | действие, объект, статус в интерфейсе |
| **Пиктограмма** | **от 48 px** | детальнее иконки, может быть двухцветной | раздел, категория, карточка функции |
| **Иллюстрация** | **от 120 px** | сцена, 2–3 цвета, композиция | пустое состояние, ошибка, онбординг |

Carbon, единственная система с явной границей [S39]:
- «Pictograms are used in a range of sizes, the **minimum being 48 px**.»
- «Treat pictograms as illustrations with sufficient sizing.»
- «**Don't use pictograms as a replacement for UI icons, that is not their purpose.**»
- «Don't use productive pictograms as **logos** or in a lockup for product headers, merchandise or events.»

Правила Carbon для пиктограмм, переносимые на любую систему:
- **Выравнивание:** «optically aligned to the **center of the icon grid** within the boundary box».
- **Контейнеры:** только **круг или квадрат**, «Don't create new shapes for containers», не кадрировать, оптически центрировать.
- **Клиренс:** «minimum padding based on **1/4 of the scaled grid size**», увеличивается шагами по 1/4. Для сетки 48 это минимум 12 px.
- **Две личности:** productive («illustrative and simple», основной вариант) и expressive («gradients, layering and transparency… should be used **selectively**»).

### 4.3 Цвет и фон пиктограммы

Carbon даёт числовую таблицу соответствия фона и варианта пиктограммы (шкала цвета Carbon 10–100) [S39]:

| Значение фона | Тема пиктограммы |
|---|---|
| White, 10–20 | Light |
| 30–50 | Monochromatic light (чёрная) |
| 50–70 | Monochromatic dark (белая) |
| 80–100, Black | Dark |

И общее правило: «Dark background colors should range between values **70–100** while light backgrounds should not exceed values **10–20**» — то есть пиктограмма не ставится на фон из середины шкалы, где контраста не хватит ни светлому, ни тёмному варианту. Запрещены также градиентные пиктограммы на градиентных фонах.

Переносимое правило: **у картинки должно быть не больше двух вариантов (светлый и тёмный), и фон под ней выбирается из краёв шкалы светлоты, а не из середины.**

## 5. Стили и 2D против 3D

### 5.1 Каталог стилей

| Стиль | Признаки | Уместен | Риск |
|---|---|---|---|
| **Line / контурная** | только контур, 1–2 цвета, без заливок | админки, документация, GOV.UK-подобные сервисы | выглядит бедно на крупных размерах |
| **Flat / плоская заливка** | плоские фигуры, 2–3 цвета, без объёма | большинство веб-сервисов | самый распространённый, то есть самый безликий |
| **Flat + лёгкая тень** | плоские фигуры плюс мягкая подложка | клиентские сервисы | Polaris: «Drop shadows give things subtle depth **when necessary**» [S38] |
| **Изометрия** | угол 30°, объём без перспективы | схемы, инфраструктура, «как это устроено» | дорого держать серию: каждая новая сцена в том же углу |
| **«Corporate Memphis»** | плоские люди без лиц, удлинённые конечности, яркие несочетаемые цвета | нигде в 2026 | §5.3 |
| **3D clay** | пластилиновые объёмы, мягкий свет, скруглённые формы | консьюмерский онбординг, маркетинг | §5.2 |
| **3D реалистичный** | рендер с материалами и освещением | маркетинг | не применять в продукте |
| **Рисованная / hand-drawn** | неровная линия, видна рука | нишевые продукты с авторским характером | почти невозможно повторить серией |
| **Фотореализм** | фото | превью документов, товары | не иллюстрация; GOV.UK: только когда нужна достоверная картинка реального объекта [S40] |

### 5.2 Когда 3D

| За | Против |
|---|---|
| Консьюмерский продукт, где картинка часть впечатления | Плотный рабочий инструмент: 3D тормозит взгляд |
| Онбординг и маркетинговые экраны внутри продукта | Цена консистентности: каждая новая сцена требует того же освещения, материалов, камеры |
| Один-два «героя» на продукт | Вес файлов: PNG вместо SVG, 2× для Retina |
| Есть 3D-конвейер (Blender), а не разовая генерация | Тёмная тема: рендер под светлый фон на тёмном выглядит вырезанным |

Правило: **3D оправдан, только если есть воспроизводимый конвейер** (сцена, свет, материалы, камера сохранены в файле и переиспользуются). Разовая генерация 3D-картинок нейросетью даёт серию, которая разваливается на третьей картинке: свет, материал и пропорции дрейфуют.

Карбоновская формулировка про expressive-пиктограммы применима и к 3D: «Due to their **visual complexity**… should be used selectively and **only in scenarios that call for a graphic with strong presence**» [S39].

### 5.3 «Corporate Memphis» и его репутация

Стиль плоских людей с удлинёнными конечностями, без лиц, в ярких несочетаемых цветах, массово распространившийся в 2018–2022 (Alegria от Facebook, затем unDraw, Humaaans и десятки клонов).

Почему сегодня читается как «дёшево и безлично»:
- **Насыщенность.** Стиль применялся одновременно сотнями продуктов, и картинка перестала что-либо сообщать о конкретном сервисе.
- **Отсутствие лиц** задумывалось как инклюзивность, но на практике даёт эффект безличности.
- **Непропорциональность** (длинные руки, маленькие головы) заметна и не мотивирована содержанием.

Это `[мнение]`: систематического исследования репутации стиля найти не удалось, и в дизайн-системах он не упоминается вовсе. Подробнее о стилях и их старении — `../11-styles-trends/` (волна 3, агент G).

Практический вывод для генеративной системы: **если стиль выбирается автоматически, ни unDraw, ни его производные не должны быть дефолтом.** Они узнаются мгновенно и сообщают «сделано быстро и без бюджета».

### 5.4 Редакционная иллюстрация — другой жанр

Интервью Intercom Brand Studio [S59] полезно как контрпример. Их фильтр отбора художников один: «**Does this look like it has been created by a human being?** We tend to stay away from super clean, vector illustrations… We try to keep it a lot more **organic, loose and expressive**.» Процесс намеренно не систематизирован: «We generally just send the illustrator a draft of the blog post and let them have at it… **We don't get prescriptive**.»

Это работает, потому что речь о **блоге**, а не о продукте. Редакционная иллюстрация живёт за счёт авторской руки и разнообразия; продуктовая — за счёт предсказуемости и единого паспорта. **Смешивать жанры в одном продукте нельзя**: авторская картинка в пустом состоянии рядом с системной выглядит как ошибка.

### 5.5 Style Tiles как инструмент брифа

Style Tiles (Samantha Warren) — промежуточный артефакт между мудбордом и макетом [S47]:

- «Style Tiles are a design deliverable consisting of **fonts, colors and interface elements** that communicate the essence of a visual brand for the web.»
- «Style tiles are for when a **moodboard is too vague and a comp is too literal**. Style tiles establish a direct connection with actual interface elements **without defining layout**.»
- Метафора: «similar to the **paint chips and fabric swatches** an interior designer gets approval on before designing a room».
- Шкала фидельности: **moodboard → style tile → mockup**.
- Процесс: Listen (опросить) → Interpret (**агрегировать прилагательные**, выделить темы) → Define a Visual Language (сопоставить прилагательные со стилями) → Iterate.
- Почему «style», а не «mood»: слово выбрано, чтобы перекликаться с «cascading stylesheets».

Для генеративной системы Style Tile — это ровно тот артефакт, который надо собрать перед генерацией: палитра + шрифт + 3–5 элементов интерфейса + 1–2 пробные иллюстрации, без раскладки. Он дешевле макета и конкретнее мудборда, и его можно показать заказчику до того, как потрачен бюджет на серию.

Связанная цитата Ethan Marcotte оттуда же: статичные макеты в адаптивном дизайне — это «a **catalog of assumptions**».

### 6.2 Лицензионная ловушка для генеративной системы

**unDraw прямо запрещает использовать свои картинки для ИИ** [S42], дословно:

> «this license explicitly prohibits the use of unDraw assets, vectors, and images for **training, fine-tuning, or developing artificial intelligence, machine learning models**… Using the assets as training data for generative AI models; Incorporating the assets into machine learning datasets; Fine-tuning a machine learning model; Using the assets to train, validate, or test AI systems; **Any automated processing of the assets for AI/ML model development**.»

Плюс запрет на «compile assets… to replicate a similar or competing service» и на массовое автоматическое скачивание.

Практический вывод: **unDraw можно поставить в интерфейс вручную, но нельзя скормить модели как референс стиля или как обучающий материал.** Для системы, которая генерирует картинки нейросетью, это значит: unDraw не годится ни как style reference, ни как источник для векторизации.

Storyset (Freepik): Terms запрещают «robots, spiders or any other mechanism… to access, copy or control any part of the Website» — автоматическая выкачка коллекции запрещена [S43].

**Humaaans и Open Peeps под CC0** — единственные из перечисленных, где таких ограничений нет. Но именно они и задали визуальный штамп (§5.3).

### 6.3 Когда брать готовое, когда рисовать своё

| Готовое | Своё |
|---|---|
| Внутренний инструмент, админка для своих | Продукт с видимым брендом |
| Прототип, MVP, проверка гипотезы | Продукт, который будет жить годы |
| Нужно 3–5 картинок | Нужно 20+ картинок и новые будут появляться |
| Бюджета на иллюстратора нет | Есть |

Atlassian формулирует ту же развилку внутри своей системы: «**Most cases call for using existing brand assets.** For big launches or complex new features requiring unique stories, custom illustrations may be needed. These require **more time and usually involve working with creative and motion teams**» [S37]. То есть новая иллюстрация — это проект, а не задача на час.

```js
AVATAR_SIZES  = { xxsmall: 16, xsmall: 16, UNSAFE_xsmall: 20, small: 24,
                  medium: 32, large: 40, xlarge: 96, xxlarge: 128 }
```

Привязка к контексту:

| Контекст | Размер |
|---|---|
| Инлайн в тексте, в бейдже | 16 |
| Строка таблицы, компактный список | **24** |
| Строка списка, комментарий, шапка | **32** |
| Карточка пользователя | 40–48 |
| Страница профиля | 64–96 |

Пресеты волны 1 дают аватары 20/24/32 для плотной админки (`../03-spacing-sizing/03-control-and-panel-sizes.md` §8).

### 7.2 Форма и радиус

| Форма | Что означает | Источник |
|---|---|---|
| **Круг** | человек | Primer: «Circle Avatars represent individual people»; Atlassian: «Use circle avatars to represent a person» |
| **Квадрат со скруглением** | сущность: проект, репозиторий, команда, организация, бот | Primer: «Square Avatars represent non-human entities, such as bots, AI agents, teams, or organizations» |
| **Шестиугольник** | ИИ-агент | Atlassian: «Use hexagon avatars to represent an agent entity, such as Rovodev or other AI-powered entities» |

Соответствие у двух независимых систем делает правило «круг = человек, квадрат = сущность» `[консенсус]`. Шестиугольник для ИИ пока только у Atlassian, `[система]`.

**Радиус квадратного аватара растёт с размером** [S50]:

| Размер | 16 | 20 | 24 | 32 | 40 | 96 | 128 |
|---|---|---|---|---|---|---|---|
| Радиус | 2 | 2 | 2 | **3** | **3** | **6** | **12** |

Это редкий пример применения правила «радиус пропорционален размеру элемента» внутри одного компонента (`../04-shape-elevation/01-radius-and-borders.md` §3). Отношение радиуса к стороне держится в коридоре 1:8…1:13.

Дополнительная константа Atlassian: `ACTIVE_SCALE_FACTOR = 0.9` — нажатый аватар ужимается до 90 % [S50].

### 7.3 Инициалы и цвет по хешу

Когда фотографии нет, аватар рисуется из инициалов на цветной плашке.

| Параметр | Значение |
|---|---|
| Число букв | **1–2** (имя + фамилия; для одного слова — первая буква) |
| Регистр | прописные |
| Кегль | **≈ 40 % размера аватара**: 10 при 24, 13 при 32, 16 при 40, 19 при 48, 26 при 64 |
| Вес | 500–600 |
| Трекинг | 0 или +0.01em |
| Число фоновых оттенков | **8–10** |
| Выбор оттенка | детерминированный хеш от идентификатора (не от имени: имя меняется) |
| Контраст текста к фону | **≥ 4.5:1** |

Алгоритм:

```js
function avatarPaletteIndex(userId, paletteSize = 10) {
  let h = 0;
  for (const ch of String(userId)) h = (h * 31 + ch.codePointAt(0)) >>> 0;
  return h % paletteSize;
}
```

Хеш берётся от **идентификатора**, а не от отображаемого имени: иначе смена фамилии меняет цвет аватара, и пользователь перестаёт себя узнавать в списках.

### 7.4 Статус и присутствие

Исходники Atlassian (`presence-wrapper.compiled.css`, `status-wrapper.compiled.css`) [S50]:

| Размер аватара | Размер индикатора | Доля | Смещение (круглый) | Смещение (квадратный) |
|---|---|---|---|---|
| 24 (small) | **12 × 12** | 50 % | bottom 0, right 0 | −4, −4 |
| 32 (medium) | **14 × 14** | 44 % | bottom 0, right 0 | −4, −4 |
| 40 (large) | **15 × 15** | 37.5 % | bottom 1, right 1 | −4, −4 |
| 96 (xlarge) | **18 × 18** | 19 % | bottom 7, right 7 | −4, −4 |

Позиции: **присутствие — снизу-справа, статус — сверху-справа** (в CSS статуса те же размеры, но `inset-block-start` вместо `bottom`).

Обводка: точка нарисована в `viewBox 8 8` с «прорезью» цвета `--ds-surface-overlay`, то есть кольцо вокруг точки — это цвет поверхности, а не отдельная граница. Константа `BORDER_WIDTH = 2` [S50].

Практическое правило для своей системы: **видимая точка 8–10 px плюс обводка 2 px цветом поверхности**, итого габарит 12–14 на аватарах 24–32. На аватарах меньше 24 индикатор не помещается — вместо него показывай статус текстом или отдельной колонкой.

Цвета состояний (Atlassian, из исходника): available зелёный, busy `--ds-icon-danger` `#C9372C`, focus `--ds-icon-discovery` `#AF59E1`, offline `--ds-text-subtlest` `#6B6E76`. Форма тоже различается (круг, круг с «вырезом», кольцо, полый круг) — это важно: **статус не должен кодироваться только цветом**.

### 7.5 Группа аватаров

| Параметр | Значение |
|---|---|
| Наложение | **−8 px** при размере 24–32, −10…−12 при 40–48 |
| Обводка | **2 px** цветом фона-подложки |
| Максимум видимых | **3–5**, дальше счётчик `+N` |
| Счётчик | тот же размер и форма, фон `bg.component`, текст `text.secondary` |
| Порядок | первым — текущий пользователь, если он в группе |
| z-index | первый аватар сверху, остальные под ним (или наоборот, но одинаково во всём продукте) |

Обводка обязательна: без неё круги сливаются в неразличимую ленту. Ширина 2 px совпадает с `BORDER_WIDTH` Atlassian и с правилом волны 1 о границах 2 px (`../04-shape-elevation/01-radius-and-borders.md` §9).

### 7.6 Фотография в аватаре

- `object-fit: cover`, `object-position: center` (или `top` для портретов: лица чаще в верхней трети кадра).
- Обрезка по форме через `border-radius`, а не через `clip-path`: дешевле и корректно работает с `overflow`.
- Плейсхолдер на время загрузки — плашка с инициалами, не серый квадрат: так не будет скачка.
- При ошибке загрузки — инициалы, при отсутствии имени — нейтральная иконка человека 60 % размера аватара.

## 8. Изображения

### 8.1 Соотношения и обрезка

| Соотношение | Когда |
|---|---|
| **16:9** | превью видео, обложки, баннеры, скриншоты интерфейсов |
| **4:3** | фотографии общего назначения, превью документов |
| **3:2** | фотографии с камеры |
| **1:1** | товары, аватары, плитки галереи |
| **21:9** | широкие баннеры (редко) |

```css
.media {
  aspect-ratio: 16 / 9;      /* вместо фиксированной высоты: нет сдвига раскладки */
  width: 100%;
  object-fit: cover;
  object-position: center;
  border-radius: var(--radius-md);
  background: var(--color-bg-subtle);   /* видно, пока картинка грузится */
}
```

Правила:
- **`aspect-ratio` вместо `height`**: место резервируется до загрузки, нет сдвига раскладки (Cumulative Layout Shift).
- **`object-fit: cover` по умолчанию**, `contain` — только для логотипов и скриншотов, где важно видеть всё.
- **Радиус картинки внутри карточки = радиус карточки − padding** (правило вложенных радиусов, `../04-shape-elevation/01-radius-and-borders.md` §2). Если картинка прилегает к краю карточки без padding, радиус равен радиусу карточки, и у неё скругляются только верхние углы.
- **`loading="lazy"` для всего ниже первого экрана**, `decoding="async"`, явные `width` и `height` в атрибутах.

### 8.2 Плейсхолдеры

| Тип | Когда | Как |
|---|---|---|
| **Скелетон** | список карточек, галерея | плашка `bg.subtle` с шиммером 1.8 s (`../08-motion/02-what-to-animate-in-apps.md` §3.7) |
| **Доминирующий цвет** | превью, где цвет известен заранее | однотонная заливка вместо серого |
| **BlurHash / LQIP** | фотогалереи | размытая миниатюра 20–30 байт |
| **Иконка-заглушка** | нет картинки вообще | иконка 24–32 в центре плашки, цвет `icon.subtle` |

Плейсхолдер обязан иметь те же габариты, что и итоговая картинка, иначе смысла нет.

### 8.3 Скриншоты интерфейса

Отдельный случай, потому что его делают чаще всего неправильно.

- **Внутри продукта скриншоты не используются** — Atlassian: «screen-within-screen appearance that can be confusing» [S37]. Вместо них — low-fidelity UI из простых фигур и серых тонов.
- В документации и справке скриншоты уместны; тогда: `object-fit: contain`, рамка 1 px `border.default`, радиус как у карточки, обязательная подпись.
- Текст внутри скриншота не читается скринридером и не переводится — рядом должно быть текстовое описание (GOV.UK, раздел про «images of text» [S40]).

### 8.4 Тёмная тема

| Что | Как |
|---|---|
| Фотографии | приглушить на **10–20 %**: `filter: brightness(0.85)` или наложение слоя фона с альфой 0.08–0.12 |
| Плоские иллюстрации | **отдельная версия файла** или переменные цвета, фильтром не лечится |
| Скриншоты светлого интерфейса | отдельный скриншот тёмной темы; приглушение делает его грязным |
| Логотипы | монохромный вариант (§9) |
| Рамка | в тёмной теме картинка без рамки сливается с фоном: добавь `1px` кольцо `rgb(255 255 255 / .08)` |

Наблюдение волны 1 [V10] (Material dark theme): монотонные иконки-иллюстрации на десатурированной палитре почти не требуют правок при переводе в тёмную тему. Чем меньше в иллюстрации цветов и чем ближе она к монохрому, тем дешевле обе темы.

Подробности про светлоты поверхностей — `../01-color/04-dark-theme.md`.

### 8.5 Фотография: когда она вообще нужна

GOV.UK даёт самое строгое правило [S40]:
- **Да:** «when it's important to show a lifelike representation of something. For example, showing a preview of a document a user has uploaded».
- **Нет:** «to represent abstract concepts, such as to convey an impression or emotion to the user. **Avoid using generic stock photography** in your service».

В веб-сервисах фотография уместна в четырёх местах: превью загруженного файла, карточка товара, фото пользователя, карта или снимок объекта. Везде остальном она либо стоковая, либо декоративная.

## 9. Логотипы в интерфейсе

| Параметр | Значение |
|---|---|
| Высота в шапке | **20–32 px** (24 при шапке 48, 28–32 при шапке 64) |
| Высота в свёрнутом сайдбаре | 24–28, обычно только знак без надписи |
| Safe zone | поле вокруг логотипа не меньше **высоты знака × 0.5** |
| Варианты | полный (знак + надпись), только знак, монохромный светлый, монохромный тёмный |
| Формат | SVG; PNG только если в логотипе растровые эффекты |
| Выравнивание | по оптическому центру, а не по боксу: у логотипов с выносными элементами бокс врёт |

Логотипы чужих брендов (интеграции, способы оплаты, поставщики):
- **выравнивание по оптической площади, а не по высоте**: квадратный знак и вытянутый логотип при равной высоте выглядят разновеликими; нормализуй по площади;
- в списке интеграций держи один размер бокса (например 32 × 32) и вписывай логотип с `object-fit: contain` и полем 4 px;
- в тёмной теме у многих чужих логотипов нет светлого варианта: ставь их на светлую плашку с радиусом, а не инвертируй;
- не перекрашивай чужой логотип: это нарушение бренд-гайдов.

Ограничение Apple, полезное как общий принцип: **иконки набора нельзя использовать как логотип** [S32]; то же у Carbon для пиктограмм: «Don't use pictograms as logos or in a lockup for product headers, merchandise or events» [S39].

## 10. Эмодзи

| Где допустимы | Где запрещены |
|---|---|
| Реакции на сообщения и комментарии | Иконки интерфейса |
| Пользовательские названия (страницы, каналы, теги) | Кнопки и пункты меню |
| Статусы, которые ставит сам пользователь | Заголовки разделов |
| Контент, введённый пользователем | Системные уведомления |
| Пикер эмодзи как отдельный компонент | Пустые состояния |

Почему эмодзи нельзя как иконку:
1. **Рендерится шрифтом операционной системы** — выглядит по-разному на Windows, macOS, Android, Linux; иногда не отрисовывается вовсе.
2. **Не подчиняется `currentColor`** — не адаптируется к теме и к состоянию (disabled, hover).
3. **Не соответствует сетке набора** — другой оптический вес, другие поля, другая базовая линия.
4. **Не масштабируется по правилам** — при 16 px мелкие эмодзи превращаются в цветные пятна.
5. **Имеет собственное значение**, часто не то, которое подразумевал автор, и меняющееся между платформами.

Технические правила, если эмодзи всё же есть:
- задай стек `font-family: "Apple Color Emoji", "Segoe UI Emoji", "Noto Color Emoji", sans-serif` для контейнеров с эмодзи, иначе текстовый шрифт подменит часть символов;
- фиксируй размер: эмодзи по умолчанию крупнее букв того же кегля;
- в реакциях эмодзи 16–20 px, счётчик рядом тем же кеглем, что и текст.

Отдельно: **эмодзи-искорка ✨ как символ ИИ** — самый заметный маркер сгенерированного интерфейса 2024–2026. Если в продукте есть ИИ-функция, дай ей одну иконку из набора и не повторяй её в каждом блоке (см. `01-icons.md` §8.2).

## 11. Генерация иллюстраций нейросетью: визуальные параметры

Конвейер целиком (инструменты, промты, векторизация, контроль качества) — `../12-ai-generated-ui/` (волна 3, агент H). Здесь только то, что надо зафиксировать в паспорте до генерации.

### 11.1 Что дрейфует между картинками

| Параметр | Как проявляется дрейф | Чем лечится |
|---|---|---|
| **Толщина линии** | первая картинка 2 px, пятая 3.5 px | явно в промте, плюс проверка измерением после векторизации |
| **Палитра** | появляются оттенки, которых нет в палитре | перечислить hex прямо в промте, потом заменить цвета скриптом по ближайшему |
| **Свет и тени** | тень то есть, то нет, то с другой стороны | «no shadows» в промте; тень добавляется в редакторе одинаково |
| **Ракурс** | часть картинок фронтальные, часть в перспективе | «front view, flat perspective» |
| **Пропорции персонажей** | главный источник расхождений | не рисовать людей (§2.7) |
| **Плотность детали** | одна картинка пустая, другая перегружена | «minimal detail», проверка размытием |
| **Поля и композиция** | объект то в центре, то в углу | «centered composition, generous negative space» |

### 11.2 Приёмы удержания серии

1. **Один сеанс на всю серию.** Между сеансами модель дрейфует даже при одинаковом промте.
2. **Один seed** и фиксированные параметры (модель, размер, шаги).
3. **Промт-шаблон с подстановкой только объекта.** Всё остальное — константы из паспорта.
4. **Референс стиля** — первая принятая картинка серии, не сторонняя библиотека (§6.2: unDraw лицензией это запрещает).
5. **Постобработка палитры скриптом**: после векторизации все цвета заменяются на ближайшие из палитры паспорта. Это дешевле, чем добиваться точных цветов от модели.
6. **Векторизация** (Recraft, Illustrator Image Trace, vtracer) с последующей нормализацией: одинаковый `viewBox`, толщина штриха, радиусы.
7. **Приёмка серией, а не по одной.** Выложить все картинки рядом в целевом размере и размыть: пятна должны быть одного веса.

### 11.3 Признаки «сгенерированной» иллюстрации

- Ассиметричная ерунда в мелких деталях (лишние линии, оборванные контуры);
- текст-абракадабра внутри картинки;
- руки и пальцы;
- градиент там, где в паспорте написано «плоская заливка»;
- «почти симметричный» объект (замок, часы, коробка) с заметным перекосом;
- лишняя тень с другой стороны, чем у соседних картинок;
- слишком много оттенков: 12 цветов вместо трёх.

Проверка простая и быстрая: **открыть SVG и посчитать уникальные заливки.** Если их больше пяти, картинка не из системы.

## 12. Частые ошибки

### 12.1 Общие

1. **Иллюстрация на рабочем экране** (в шапке таблицы, рядом с формой).
2. **Разные стили в одной серии**: одна картинка линейная, другая с заливкой.
3. **Разный оптический вес** в одном слоте: одна картинка плотная, другая воздушная.
4. **Слишком много цветов** (больше 3 акцентов на картинку).
5. **Насыщенность выше интерфейсной** — картинка перетягивает внимание с кнопки.
6. **Деталь мельче 4 px**, исчезающая при уменьшении.
7. **Скриншот внутри продукта** вместо low-fidelity UI.
8. **Текст внутри картинки.**
9. **Стоковая фотография** для абстрактного понятия.
10. **Нет варианта для тёмной темы**, картинка остаётся светлым пятном.
11. **Аватары разного размера в одном списке.**
12. **Инициалы без проверки контраста**: белый текст на светло-жёлтой плашке.
13. **Цвет аватара берётся от имени**, а не от идентификатора: смена фамилии меняет цвет.
14. **Группа аватаров без обводки** — круги сливаются.
15. **Статус кодируется только цветом**, без формы.
16. **Картинка без `aspect-ratio`** — сдвиг раскладки при загрузке.
17. **Радиус картинки не согласован с радиусом карточки.**
18. **Чужой логотип перекрашен** или выровнен по боксу, а не оптически.
19. **Эмодзи вместо иконок интерфейса.**
20. **Иллюстрация есть, а текста нет**: картинка не объясняет, что делать дальше.

### 12.2 Характерные для нейросетей

21. **Каждое пустое состояние получает свою уникальную иллюстрацию** вместо одной-двух на продукт.
22. **unDraw по умолчанию** — узнаётся мгновенно и нарушает лицензию, если использован как референс для модели (§6.2).
23. **«Corporate Memphis» как дефолтный стиль** (§5.3).
24. **Иллюстрация в шапке каждой страницы** — паттерн лендинга.
25. **Градиентные абстрактные пятна на фоне** админки.
26. **3D-рендеры, сгенерированные по одной**, без общей сцены: разный свет и материалы.
27. **Аватары-заглушки из сервисов вроде `i.pravatar.cc`** остаются в боевом коде.
28. **Изображения из `unsplash.com/random`** в продуктовом интерфейсе.
29. **Иконка-искорка ✨ у любой ИИ-функции**, повторённая пять раз на экране.
30. **Картинка 512 × 512 PNG весом 800 КБ** там, где нужен SVG на 8 КБ.
31. **Фотографии людей в интерфейсе B2B-инструмента** без всякой причины.
32. **Плейсхолдер с текстом «Image»** или серый прямоугольник, оставшийся в продакшене.

## 13. Чек-лист

**Система иллюстраций**
1. Заполнен ли паспорт системы (§3) до генерации первой картинки?
2. Иллюстрации стоят только в разрешённых слотах (пусто, ошибка, онбординг, успех, анонс)?
3. На рабочих экранах иллюстраций нет?
4. Прежде чем поставить иллюстрацию, рассмотрены иконка, текст и паттерн?
5. У всех картинок одного слота одинаковый оптический вес (проверено размытием)?
6. Не больше 3 акцентных цветов на картинку плюс нейтрали?
7. Насыщенность иллюстрации ниже интерфейсной?
8. Палитра иллюстраций выведена из палитры продукта?
9. Минимальная деталь не мельче 4 px в целевом размере?
10. Толщина линии согласована со штрихом иконок?
11. Радиусы скруглений согласованы с радиусом интерфейса?
12. Есть вариант для тёмной темы (отдельный файл или переменные цвета)?
13. Нет текста внутри картинок?
14. Нет скриншотов интерфейса внутри продукта?
15. Лицензия использованных библиотек проверена, включая запрет на обработку моделями ИИ?

**Аватары**
16. Размеры из ряда 16 / 24 / 32 / 40 / 48 / 64?
17. Круг для людей, квадрат для сущностей, и это соблюдается везде?
18. Радиус квадратного аватара растёт с размером?
19. Инициалы 1–2 буквы, кегль ≈ 40 % размера аватара?
20. Цвет плашки берётся по хешу идентификатора, а не имени?
21. Контраст текста инициалов к плашке не ниже 4.5:1?
22. Статус-индикатор имеет обводку 2 px цветом поверхности и различается формой, а не только цветом?
23. В группе аватаров есть обводка и счётчик `+N` после 3–5 элементов?

**Изображения и логотипы**
24. У каждого изображения задан `aspect-ratio`, а не фиксированная высота?
25. `object-fit: cover` везде, кроме логотипов и скриншотов?
26. Радиус изображения согласован с радиусом контейнера?
27. Есть плейсхолдер тех же габаритов?
28. Изображения ниже первого экрана грузятся лениво?
29. В тёмной теме фотографии приглушены на 10–20 %, а иллюстрации заменены, а не отфильтрованы?
30. Логотип в шапке высотой 20–32 px с safe zone?
31. Чужие логотипы выровнены оптически и не перекрашены?
32. В интерфейсе нет эмодзи вместо иконок?

## 14. Открытые вопросы и противоречия

1. **У Material 3 раздела об иллюстрациях нет вообще** (проверено на двух путях: `m3.material.io/styles/illustration/*` отдаёт 404). Иллюстрация осталась в Material 2 (`material.io/design/communication/`). Для системы, задающей стандарты мобильного дизайна, это заметный пробел; в базе Material по иллюстрациям не представлен.
2. **Раздел иллюстраций Fluent 2 закрыт**: `fluent2.microsoft.design/illustration` отдаёт 404 и «Microsoft employee? Sign in to see internal-only content». Внешним данные недоступны.
3. **Mailchimp** описать по первоисточнику не удалось: `ux.mailchimp.com/patterns/illustration` отдаёт 503, снимка в web.archive нет. В файл ничего из Mailchimp не внесено.
4. **Dropbox**: `dropbox.design/article/dropbox-brand-illustration` отдаёт только заголовки, контент за JavaScript и не извлёкся ни `fetch.py`, ни через рендеринг.
5. **Действующая версия иллюстраций Polaris недоступна**: живой URL редиректит на страницу о поверхностях приложений, а архивная версия 2023 года помечена «This section is currently being reworked to provide better guidance aligned with Polaris v12». То есть §2 опирается на официальный, но устаревающий документ. `[спорно]`
6. **Связь толщины линии иллюстрации со штрихом иконок** (§2.4) — мой вывод из соотношений масштабов, прямого правила в источниках нет. `[вывод]`
7. **Репутация «corporate Memphis»** (§5.3) — `[мнение]`: систематического исследования нет, в дизайн-системах стиль не обсуждается.
8. **Наложение −8 px в группе аватаров** (§7.5) — практика, подтверждённая только визуально; числовых значений в исходниках Atlassian и Primer для стопки аватаров найти не удалось.
9. **Приглушение изображений в тёмной теме на 10–20 %** — `[консенсус]` по практике, точного числа ни одна из изученных систем не называет.
10. **Кегль инициалов ≈ 40 % размера аватара** — мой расчёт от типичных пропорций, а не значение из системы. `[вывод]`
11. **Число слотов для иллюстраций** (пять) — обобщение по Atlassian и Polaris; другие системы дают другие наборы.
12. **Границы 48 и 120 px между иконкой, пиктограммой и иллюстрацией** — нижняя граница 48 взята у Carbon, верхняя 120 выведена из размеров пустых состояний. `[вывод]`
