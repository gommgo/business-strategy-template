## Выжимка для агента

1. **Ни один бенчмарк не измеряет «красиво».** Все измеряют одно из трёх: похожесть на эталон, наличие
   заранее внесённого дефекта, соответствие правилу из свода. Метрики «эстетика» в готовом виде нет.
   → §7.1 `[консенсус]`
2. **Универсальная VLM без дообучения на попарном сравнении качества UI работает на уровне монетки:
   GPT-4V — 51,58 %**, при этом отказывается отвечать на ~10 % примеров. Специализированная модель на
   CLIP B/32 — 75,12 %. → §2.1 `[исследование]`
3. **На рубрике с описанными критериями VLM внезапно надёжна**: Пирсон **0,9892** между тремя
   VLM-судьями и средним четырёх экспертов (GEBench, 100 образцов на модель). Разница с п. 2 — в форме
   вопроса: не «какой лучше», а «оцени по пяти измерениям 0–5». → §6.1 `[исследование]`
4. **Zero-shot критика дизайна в основном мусор: валидны 13,1 % замечаний Gemini** (776 из 5 927).
   Few-shot по близости задачи и картинки плюс визуальный промт даёт **+55 %**. → §2.2 `[исследование]`
5. **Больше замечаний — хуже, а не лучше.** Zero-shot выдал 45 комментариев при оценке 0,24; few-shot —
   меньше и качественнее. Многословная критика — признак галлюцинаций. → §2.2 `[исследование]`
6. **Модель не может показать, где проблема.** IoU рамки замечания: **0,004** по голому скриншоту,
   **0,186** с координатной разметкой по краям, **0,222** с пронумерованной сеткой патчей. Сетка линий
   делает хуже (1,1e-5). → §2.2 `[исследование]`
7. **Критику и локализацию надо разводить по разным вызовам.** Объединение улучшает рамки, но ухудшает
   сами замечания («task overload»). → §2.2, §6.3 `[исследование]`
8. **Лучший результат на судействе эстетики — 0,7252 при случайном уровне 0,50** (GPT-5, AesEval-Bench,
   вопрос «есть ли дефект, да/нет»). Локализация дефекта bbox: **IoU ниже 0,20 у всех**. → §2.3 `[исследование]`
9. **Рассуждающие модели не лучше обычных** в оценке эстетики; модели, обученные на эстетике фотографий,
   **хуже всех** («substantial gap between design aesthetics and image aesthetics»). → §2.3 `[исследование]`
10. **Картинка незаменима, метаданные помогают локализации.** Абляция входа: удаление изображения даёт
    наибольшее падение; JSON с раскладкой, цветом и шрифтом сильнее всего влияет на точность bbox.
    → §2.3, §6.4 `[исследование]`
11. **Объяснение критерия нужно ровно для субъективных пунктов.** Для «баланса» описание почти не влияет,
    для «релевантности» и «психологии цвета» — критично. → §2.3, §6.2 `[исследование]`
12. **Текст воспроизводится почти идеально, позиция и цвет — нет**: 98,2 / 85,5 / 84,1 у лучшей модели
    (Design2Code). У Claude 3 Opus цвет 71,4. → §3.1 `[исследование]`
13. **Люди (и значит арены) смотрят только на верхний уровень**: в регрессии по 435 парным предпочтениям
    текстовое сходство имеет **отрицательный и наименее значимый** коэффициент. → §3.1 `[исследование]`
14. **Самокритика без измерителя вредит слабым моделям**: block-match 39,7 → 30,1 и 46,7 → 12,3.
    → §3.1 `[исследование]`
15. **В сгенерированном коде нарушений в 5,6 раза больше**, чем в человеческом, при сопоставимой
    сложности: 9,8 против 1,74 на проект. → §3.3 `[исследование]`
16. **Мягкие правила («рекомендуется») чинятся заметно хуже жёстких («делай / не делай»): 70,4 % против
    92,3 % recall.** Бриф должен быть в форме запретов и чисел. → §3.3 `[исследование]`
17. **Самостоятельное обнаружение визуального дефекта — 0,2714 в среднем по девяти моделям.** Дефект
    надо называть. → §3.2 `[исследование]`
18. **Компонентный подход не возникает сам: 0,24 % страниц на React.** Отсюда расползание значений.
    → §3.2 `[исследование]`
19. **Бриф раскладывается на четыре уровня** — Product, Design System, Feature, Component — по
    тематическому анализу 907 фрагментов руководств шести инструментов. Структурированный ввод даёт
    **p = 0,002, r = 0,87** против чата. → §4 `[исследование]`
20. **Первое впечатление предсказывается двумя величинами** — цветностью и визуальной сложностью; вместе
    с демографией они объясняют около половины дисперсии оценки после **500 мс** показа. Это ровно те две
    величины, которые генератор раздувает. → §5.1 `[исследование, по аннотации]`
21. **Готовая рубрика из 12 индикаторов** (layout: balance, layering, whitespace, alignment; color:
    harmony, contrast, appeal, psychology; font: legibility, hierarchy; graphics: quality, relevance) —
    берётся целиком из AesEval-Bench. → §6.2 `[исследование]`
22. **Готовая рубрика из 5 измерений для последовательностей экранов** (GOAL, LOGIC, CONS, UI, QUAL,
    шкала 0–5) — из GEBench. → §6.2 `[исследование]`

## 2. Оценка визуального качества

### 2.1. UIClip: сколько стоит «просто спросить модель» `[S2]`

Jason Wu, Yi-Hao Peng, Amanda Li, Amanda Swearngin, Jeffrey P. Bigham, Jeffrey Nichols (CMU + Apple),
arXiv:2404.12500, UIST 2024.

**Данные.** `JitterWeb` — 2,3 млн примеров: ~300 000 страниц обойдены headless Chrome, к каждой применены
до трёх «jitter-функций» из девяти, выведенных из принципов **CRAP** (contrast, repetition, alignment,
proximity):

| Группа | Функции |
|---|---|
| Цвет | Color Swap (перемешать цвета элементов), Color Noise (шум в RGB) |
| Шрифт | Font Size swap (поменять местами размеры ролей), Text Noise |
| Контраст | Text Color (приблизить текст к фону), Background Color (приблизить фон к тексту) |
| Отступы | шум в `margin` и `padding` |
| Сложность | случайное удаление изображений, текста и оформления |
| Раскладка | смена направления потока |

`BetterApp` — 1,2 тыс. оценок **12 дизайнеров** (попарные сравнения, ~1,5 часа, ≥ 100 экранов на человека).

**Результаты** (точность выбора лучшего экрана в паре):

| Модель | Точность |
|---|---|
| **UIClip (CLIP B/32 + jitter web + web pairs)** | **75,12 %** (на веб-дефектах 87,1 %) |
| UIClip + человеческие пары | 73,88 % |
| UIClip (только CLIP-objective) | 65,42 % |
| LLaVA-1.6-13B | 54,59 % |
| **GPT-4V** | **51,58 %**, **отказ отвечать на ~10 % примеров** |
| CLIP B/32 (база) | худший результат; ассоциировал тёмные нечитаемые фоны с «хорошим дизайном» |

**Подсказки по дизайну.** LVLM перечисляют все четыре принципа CRAP почти в каждом ответе: recall Gemini
87,11 %, GPT-4V 84,57 %. После поправки на правильность выбора — **49,17 % и 46,58 %**. Это тот же эффект,
что в UICrit: **многословность не есть качество**.

**Retrieval.** MRR базового CLIP 0,2534 / 0,1466 → UIClip с CLIP-objective **0,3851 / 0,4085**. Вариант с
попарной функцией потерь обрушивает retrieval до 0,0962: задачи «сравнить два экрана» и «найти похожий»
тянут модель в разные стороны. **Для конвейера это значит: судья и поисковик по образцам — разные модели.**

**Применение, которое работает.** Best-of-n: LLM генерирует n = 5 вариантов HTML/CSS, каждый рендерится,
UIClip ранжирует. В примере лучший по UIClip был третьим в выдаче LLM.

**Ограничение, важное для практики.** Модель говорит «плохой контраст текста», но не может указать, где
именно: описание привязано ко всему скриншоту, координат в данных нет.

### 2.2. UICrit: как заставить критику быть полезной `[S3]`

Peitong Duan (UC Berkeley), Chin-Yi Chen, Gang Li, Yang Li (Google DeepMind), Bjoern Hartmann.
arXiv:2407.08850v3, UIST 2024. Данные: github.com/google-research-datasets/uicrit.

**Датасет.** 3 059 критик и оценок для **983 мобильных экранов**, собраны у **7 опытных дизайнеров**.
У каждой критики bounding box, у каждого экрана три числовые оценки (эстетика, юзабилити, общее качество).

**Главное число.** Из 5 927 комментариев, сгенерированных Gemini, валидными признаны **776 — 13,1 %**.
В итоговом датасете 74,6 % критик от людей, 8,3 % от Gemini, 17,1 % от обоих.

**Пять тем критики** (кластеризация SentenceBERT + K-means, k = 5 по методу локтя):

| Тема | Размер кластера |
|---|---|
| Layout (позиционирование, выравнивание, иерархия, группировка, простота) | 696 |
| Color Contrast (контраст текста, иконок, кнопок с фоном) | 655 |
| Usability of Buttons | 601 |
| Learnability (ясность иконок, зон, подписей) | 601 |
| Text Readability (кегль и вес) | 591 |

**Четыре из пяти кластеров — визуальный слой.** Это прямое обоснование того, почему рубрика критики
должна начинаться с раскладки и контраста.

**Локализация.** Средний IoU рамки замечания:

| Способ | IoU |
|---|---|
| только скриншот | **0,004** |
| скриншот с наложенной сеткой линий | **1,1e-5** (хуже: линии добавляют визуальный шум) |
| скриншот с координатными подписями по краям | 0,186 |
| **скриншот с пронумерованными патчами** (модель возвращает номера) | **0,222** |

**Разделение вызовов.** Объединение генерации критики и локализации в один вызов улучшает рамки, но
ухудшает качество критик — «task overload on the LLM». Рабочая схема: вызов 1 — критики и оценки,
вызов 2 — рамки по готовым критикам.

**Прирост.** Few-shot по совместной визуальной и задачной близости плюс визуальный промт даёт
**+0,17 в нормированной оценке, то есть +55 %** относительно zero-shot (p = 5e-4). Эксперты предпочли
few-shot-набор zero-shot-набору в **67 %** случаев, человеческий набор — набору модели в **81 %**.

**Zero-shot многословен и плох.** 45 комментариев при оценке 0,24; распределение оценок смещено к
«невалидно». Few-shot уменьшил и число, и долю галлюцинаций.

**Согласие людей между собой низкое.** Fleiss' Kappa 0,29–0,31 («fair») на оценке критик и 0,55 на
ранжировании наборов. У участников от 5 до 30 лет опыта. **Оценка дизайна субъективна в принципе**, и
требовать от модели согласия выше человеческого бессмысленно.

**Оценка экрана не связана с рейтингом приложения в сторе**: Пирсон 0,007 (эстетика), 0,022 (юзабилити),
0,023 (общее). При этом внутри одного приложения оценки согласованы: SD 0,60–0,65 против общей 1,13–1,25.

**Известная слабость LLM-критики** (из предшествующей работы Duan et al. 2024, на которую опираются
авторы): **плохое знание популярных конвенций дизайна и неумение расставить приоритет, когда гайдлайны
конфликтуют.**

### 2.3. AesEval-Bench: рубрика из 12 индикаторов `[S17]`

Arctanx An (Peking University), Shizhao Sun, Danqing Huang, Mingxi Cheng и др. (Microsoft Research Asia),
arXiv:2603.01083v1, март 2026. github.com/arctanxarc/AesEval-Bench.

**Структура.** Четыре измерения и двенадцать индикаторов:

| Измерение | Индикаторы |
|---|---|
| **Layout** | balance, layering, whitespace, alignment |
| **Color** | harmony, contrast, appeal, psychology |
| **Font** | legibility, hierarchy |
| **Graphics** | quality, relevance |

Три задачи, все полностью квантифицируемые:
1. **aesthetic judgment** — есть ли дефект по данному индикатору (да/нет);
2. **region selection** — выбрать из четырёх кандидатов, включая None;
3. **precise localization** — вернуть bbox или None.

**Данные.** 1200–1500 профессиональных макетов из Crello, к которым применены **1–3 контролируемые
пертурбации** (сдвиг элемента, смена шрифта, смена цвета) на уровне JSON-метаданных и перерендерены.
Разметка — люди, большинством голосов. Всего 4500 базовых пар «вопрос-ответ», каждая инстанцирована по
двенадцати индикаторам.

**Результаты (10 моделей).**

| Модель | Judgment (случайный 0,50) | Localization, выбор None | Localization, IoU bbox |
|---|---|---|---|
| **GPT-5** | **0,7252** | **0,6090** | **0,1993** |
| Gemini-2.5-Pro | — | 0,6047 | 0,0977 |
| GPT-o3 | — | 0,5800 | 0,1418 |
| GPT-4o | — | 0,5680 | 0,1712 |
| GPT-o1 | — | 0,5295 | 0,1286 |
| Qwen-VL-7B | — | 0,5192 | 0,0514 |
| LLaVA-13B | — | 0,4455 | 0,0559 |
| AesExpert-7b (эстетика фото) | — | 0,3377 | 0,0327 |

Четыре вывода:
1. **Даже сильнейшая модель на бинарном вопросе берёт 0,73 при случайном уровне 0,50.**
2. **Рассуждающие модели не дают преимущества**: «generic reasoning provides little benefit in this domain».
3. **Модели, обученные на эстетике фотографий, хуже всех**: «substantial gap between design aesthetics and
   image aesthetics». Оценщик красоты фотографии для макета бесполезен.
4. **Точная локализация не решена: IoU ниже 0,20 у всех.**

**Абляция входа** (GPT-4o): вход состоит из вопроса с описанием индикатора, изображения и метаданных в JSON.
- **Удаление изображения даёт наибольшее падение** на всех задачах — картинка незаменима.
- **Описание индикатора** почти не влияет на «интуитивные» индикаторы (balance) и критично для
  субъективных (relevance, psychology).
- **Метаданные** (раскладка, цвет, шрифт в JSON) сильнее всего влияют на точность bbox: они дают явную
  информацию о положении элементов.

**Дообучение.** 30 тыс. пар с «indicator-grounded reasoning» (рассуждение, явно привязанное к bbox
конкретного элемента) на Qwen2.5-VL-7B дало прирост **5,97 %, 2,70 % и 17,17 %** по трём задачам.

## 3. Дизайн → код: где ломается визуальный слой

### 3.1. Design2Code `[S21]`

Chenglei Si и др. (Stanford), arXiv:2403.03163v3. 484 реальные страницы; пять метрик: **Block-Match**
(воспроизведены ли все блоки и нет ли выдуманных), **Text** (посимвольное сходство),
**Position** (нормированное расстояние центров), **Color** (CIEDE2000 по цвету текста), **CLIP**.

| Модель, режим | Block | Text | Position | Color | CLIP |
|---|---|---|---|---|---|
| GPT-4o Direct | **93,0** | **98,2** | **85,5** | **84,1** | **90,4** |
| GPT-4V Direct | 85,8 | 97,4 | 80,5 | 73,3 | 86,9 |
| Claude 3 Opus Direct | 90,2 | 97,5 | 77,9 | 71,4 | 87,0 |
| Gemini 1.0 Pro Vision Direct | 80,2 | 94,6 | 72,3 | 66,2 | 84,4 |
| WebSight VLM-8B (дообучена) | 55,9 | 86,6 | 77,3 | 79,4 | 87,6 |
| Design2Code-18B (дообучена) | 78,5 | 96,4 | 74,3 | 67,0 | 85,8 |

**Разрыв Text → Position → Color: 98,2 → 85,5 → 84,1 у лучшей и 97,5 → 77,9 → 71,4 у Claude 3 Opus.**
Формулировка авторов: «models mostly lag in recalling visual elements from the input webpages and
generating correct layout designs».

**Text-augmented prompting** (подать распознанный текст отдельным списком) поднимает block-match и
текстовое сходство у моделей, слабых в распознавании: в примере с 0,25 до 0,84.

**Self-revision** — разбор в `02-codegen-tools-and-default-look.md` §4.3: помогает GPT-4V и Claude 3,
не помогает Gemini Pro Vision, **обрушивает** DeepSeek-VL (39,7 → 30,1) и Idefics2 (46,7 → 12,3).

**Люди смотрят на верхний уровень.** Логистическая регрессия по 435 парным предпочтениям (точность
79,9 % на отложенной половине) даёт **отрицательный и наименее значимый коэффициент у текстового
сходства**; все остальные меры — положительные и значимые. Вывод авторов: «human evaluation should not be
blindly trusted as the oracle here due to their cognitive bias to only consider "principle components"».
Следствие для нас: **арена и вопрос «какой скриншот лучше» систематически не замечают содержательных
ошибок**; такой сигнал нельзя использовать как единственный.

**Design2Code-HARD**: 80 сложных примеров (26 % длиннее 500 HTML-тегов, 19 % не на английском).
Фронтир-модели **не воспроизводят 30–40 % блоков**. Число тегов — сильный предиктор сложности;
неанглийские страницы сложнее «probably due to the limited pretraining data» — прямое основание проверять
русский интерфейс отдельно.

### 3.2. DesignBench `[S4]`

Jingyu Xiao и др. (CUHK + SMU), arXiv:2506.06251v1, июнь 2025. 900 образцов, три фреймворка
(React, Vue, Angular) плюс vanilla HTML/CSS, три задачи: **Design Generation** (430), **Design Edit** (359),
**Design Repair** (111). Девять моделей.

**Распределение дефектов UI в задаче repair** (что вообще ломается на реальных страницах):

| Дефект | Доля |
|---|---|
| **alignment** | **42,2 %** |
| crowding | 18,7 % |
| occlusion | 18,1 % |
| overflow | 11,4 % |
| прочее | 9,6 % |

**Больше 40 % визуальных дефектов — выравнивание.** Это подтверждает приоритет раскладки в порядке правок
(`02-…` §7.1) и совпадает с самым крупным кластером критик в UICrit (Layout, 696).

**Распределение правок в задаче edit**: Change 55,8 %, Add 38,1 %, Delete 6,1 %. По визуальному типу:
компонент 27,9 %, текст 17,1 %, позиция 16,0 %, цвет 15,2 %, форма 13,4 %, размер 10,4 %.

**Пять чисел, меняющих поведение агента:**

1. **Точность обнаружения UI-дефекта: 0,2714** в среднем (React 0,2972, Vue 0,2205, Angular 0,2275,
   Vanilla 0,3403); лучшая модель GPT-4o — 0,3951. Рекомендация авторов дословно: «explicitly stating the
   problems allows models to focus on targeted solutions rather than inaccurate independent diagnosis».
2. **Локализация правки — узкое место**: Code Modification Similarity у Claude-3.7 0,3439–0,6829 (edit) и
   0,2287–0,5719 (repair) при компиляции выше 0,9. Рекомендация: **давать точное место правки**.
3. **Компонентный подход почти отсутствует**: доля страниц, собранных из компонентов, —
   **0,24 % (React), 5 % (Vue), 19 % (Angular)**. Пример: список новостей BBC из одинаковых карточек
   сгенерирован захардкоженным повтором вместо `v-for`. **Это механическое объяснение того, почему
   значения у соседних карточек расходятся: они написаны отдельно.**
4. **Vanilla HTML/CSS лучше фреймворков**: CLIP > 0,72 и 100 % компиляции; Angular худший (компиляция
   0,6–0,7, CLIP 0,45–0,55).
5. **Код как вход сильнее картинки, комбинация не помогает**: Design Edit 8,40–8,43 (код) против
   7,37–7,67 (картинка); Design Repair 6,53–6,70 против 5,47–5,81. Вывод авторов: «MLLMs currently
   underutilize visual information».

**Деградация по сложности:** Design Generation падает умеренно (CLIP 0,79–0,83 → 0,69–0,73 при росте
макета с < 1000 × 1000 до > 2000 × 2000 px), Design Edit сильнее (8,64–9,05 → 7,51–8,19), Design Repair
катастрофически (7,21 → 4,19 у Gemini-2.0 при правке > 30 строк). **Дели макет и правки на части.**

### 3.3. DesignRepair `[S18]`

Mingyue Yuan и др., arXiv:2411.01606v2, декабрь 2024. База знаний из Material Design 3, разбитая на два
уровня:

- **KB-Comp** (компоненты): 24 типа; **228 жёстких ограничений (113 «делай», 115 «не делай») и
  399 мягких (рекомендаций)**. По аспектам: anatomy 43,2 %, placement 5,9 %. Самые «нагруженные»
  компоненты: кнопки (109 правил) и навигация (95); чекбокс — 6.
- **KB-System** (система): 12 аспектов, 7 свойств, 15 отношений; знания записаны тройками
  `<аспект, свойство, отношение>`. Семь групп свойств: **Group, Clickable, Spacing, Platform, Label,
  Text, Color**.

**Разделение на жёсткие (do/don't) и мягкие (рекомендации) ограничения — прямой прототип раздела
«Do's and Don'ts» в брифе** (`04-…` §2.4).

**Сравнение сгенерированного и человеческого кода:**

| Показатель | 20 проектов v0 | 6 популярных проектов GitHub |
|---|---|---|
| компонентов и групп свойств на файл | 33,45 | 27 |
| **нарушений гайдлайнов на проект** | **9,8** | **1,74** |
| доля нарушений по компонентам | 76 % | 52 % |
| доля нарушений жёстких ограничений | 86 % | 87 % |

Разметка: 669 компонентов и групп свойств, 3 765 применимых правил, 196 нарушены; **в среднем
188,25 применимых правил на проект**.

**Эффективность подхода:** обнаружение нарушений recall 92,9 % / precision 90,1 % (базовая линия
UIS-Hunter: 32,3 % / 55,4 %); извлечение компонентов recall 96,7 %; починка компонентных нарушений
recall 89,9 %, свойственных 87,2 %.

**Ключевая асимметрия: мягкие ограничения чинятся хуже жёстких — 70,4 % против 92,3 % recall.**
Прямое следствие для брифа: формулировать числом и запретом, а не пожеланием.

**Побочное наблюдение:** при починке «LLMs tend to predict larger values to ensure accessibility, which
can compromise page consistency» — модель завышает размеры ради доступности и ломает согласованность.
Это объясняет измеренную кнопку 50 px (`02-…` §5.2).

### 3.4. Prototype2Code и DeclarUI: два приёма, которые стоит заимствовать

**Prototype2Code** (arXiv:2405.04975, 08.05.2024). Генерация кода из прототипа с **design linting внутри
конвейера**: детекция фрагментированных элементов и перцептивных групп до генерации кода, оптимизация
иерархии, распознавание типов элементов, flexbox как основная модель раскладки ради адаптивности.
Сравнение с CodeFun и Screenshot-to-code на GPT-4V по SSIM, PSNR и MSE: у Prototype2Code минимальные
ошибки. Пользовательское исследование с пятью опытными фронтендерами: выше по читаемости,
пригодности и сопровождаемости.
**Что заимствовать: линтинг макета до генерации кода**, а не после.

**DeclarUI** (arXiv:2409.11667, 18.09.2024). Связка компьютерного зрения, MLLM и итеративной оптимизации
под компилятор: точная сегментация компонентов, **Page Transition Graph** для межэкранных связей,
итеративная доводка. На React Native: **96,8 % покрытия PTG и 98 % успешной компиляции**; относительно
базовых MLLM — **+123 % покрытия PTG, до +55 % визуального сходства, +29 % компиляции**.
**Что заимствовать: сегментацию компонентов зрением до генерации** и явный граф переходов вместо
надежды на то, что модель свяжет экраны сама.

## 4. Структура брифа: что именно надо сказать

**Bridging Gulfs in UI Generation through Semantic Guidance** `[S19]`, Seokhyeon Park и др.
(Seoul National University, HCIL), arXiv:2601.19171v2, CHI '26.

**Метод.** Тематический анализ руководств по промтам шести ведущих инструментов — **Vercel v0, Google
Stitch, Figma Make, Uizard, Lovable, Relume**: **907 фрагментов = 601 правило + 306 примеров промтов**,
трое авторов, итеративное кодирование.

**Результат — четырёхуровневая иерархия семантик:**

| Уровень | Элементы |
|---|---|
| **Product** | Description (что строим), Target User (для кого), Goal (зачем) |
| **Design System** | Design Style (эстетика), **Color** (палитра и схема), **Typography** (шрифты, размеры, иерархии), **Visual Properties** (тени, радиус, отступы), **Visual Mood** (эмоциональный тон), Tone of Voice |
| **Feature** | Function (что делает экран), Content (что показывает), Information Architecture (как структурировано и приоритизировано) |
| **Component** | Type, **Interactivity** (hover, клики, переходы), **State** (active, disabled, loading), Content, Properties |

Три типа действий (creation, modification, analysis) × три масштаба (приложение, экран, элемент).
Семантики связаны **вертикально и горизонтально**: изменение одного элемента каскадом идёт по остальным.

Отдельное наблюдение: **interactivity и state «часто отсутствуют в статических таксономиях UI», но в
генеративном контексте становятся значимыми семантиками**. Бриф обязан содержать состояния.

**Сравнительное исследование.** 14 участников (8 UI/UX-дизайнеров, 3 разработчика и др.), парный дизайн,
7-балльные шкалы. Структурированный семантический ввод значимо лучше чат-базовой линии по всем измерениям:

| Измерение | Базовая линия | Семантический ввод | Значимость |
|---|---|---|---|
| Intent Reflection | M = 4,43 | **M = 6,00** | **p = 0,002, r = 0,87** |
| «Think Through» | M = 3,71 | **M = 6,00** | r = 0,80 |
| Modification Reflection | M = 3,86 | M = 5,64 | p = 0,032 |

**Пять участников из 14 в чат-условии прямо описали «ripple effect»** — правка одного элемента расползается
по остальному интерфейсу. Независимое подтверждение совета Lovable «скажи, что не трогать».

## 5. Классические метрики эстетики: что из них живо

### 5.1. Reinecke, Yeh, Miratrix, Mardiko, Zhao, Liu, Gajos. CHI 2013 `[S27]`

**Полный текст открыть не удалось** (Harvard DASH отдаёт 405, ACM DL за платным доступом); изложено по
аннотации и вторичным описаниям, поэтому помечено `[исследование, по аннотации]`.

**450 сайтов, 548 участников**; собраны оценки colorfulness, visual complexity и visual appeal.
Вычислительные модели двух первых величин вместе с демографией (образование, возраст) объясняют
**около половины дисперсии** оценок привлекательности после показа страницы **всего 500 мс**.

Значение для нашей темы: **две величины, предсказывающие первое впечатление, — это ровно те две величины,
которые генератор раздувает**. Градиенты, стекло, восемь кеглей, 34 карточки на экране, максимальный
кегль 96 px — это рост и цветности, и визуальной сложности одновременно. Отсюда практическое правило:
считать их до показа, а не после.

### 5.2. Miniukovich & De Angeli (tLight) — по вторичному описанию

Восемь автоматических метрик визуальной эстетики графических интерфейсов, применимых к десктопу и
мобильным. Упоминается в UIClip `[S2]` как предшествующая работа. **Первоисточник не открывался**;
здесь только факт существования и роль: набор метрик, чьи выходы «still require interpretation and cannot,
for example, be used to compare the quality of two candidate designs» — это и была причина появления
UIClip.

Аналогично **Aalto Interface Metrics (AIM)** (Oulasvirta et al., 2018): пакет метрик, который UIClip
рассматривал как базовую линию и **исключил, потому что нет однозначного способа превратить эти метрики в
оценку дизайна**. Это важный урок: набор метрик без правила агрегации не заменяет рубрику.

## 6. VLM как судья визуального качества

### 6.1. Когда VLM надёжна, а когда нет

Три числа, которые надо сопоставить:

| Форма вопроса | Результат | Источник |
|---|---|---|
| «Какой из двух экранов лучше?» (попарно, без рубрики) | **51,58 %** у GPT-4V при случайном 50 % | UIClip `[S2]` |
| «Есть ли дефект по индикатору X?» (да/нет, с описанием индикатора) | **0,7252** у GPT-5 при случайном 0,50 | AesEval-Bench `[S17]` |
| «Оцени по пяти измерениям от 0 до 5 с описанными критериями» | **Пирсон 0,9892** с людьми (0,9926 и 0,9833 по моделям) | GEBench `[S1]` |

Разница не в моделях, а в **форме задачи**. Согласие 0,99 в GEBench получено на **подробной рубрике из
пяти измерений с описанными критериями, тремя независимыми судьями (Gemini-3-Flash-Native, GPT-4o,
Qwen3-VL-235B-thinking), тремя прогонами и усреднением оценок четырёх экспертов** на 100 образцах на
модель. Это не «VLM понимает красоту», это «VLM надёжно применяет подробный чек-лист».

Тот же вывод независимо получает DesignBench: MLLM-as-a-judge с «detailed guideline of evaluation
criteria» показал точность выше 90 % при сверке с людьми `[S4]`.

**Практическое правило: судья без рубрики — шум; судья с рубрикой, несколькими прогонами и несколькими
моделями — инструмент.**

Дополнительные данные о надёжности LLM-судьи в UX-задачах (13,6 % переворотов при повторе, 25 % смены
вердикта от перефразировки рубрики, 11 прогонов для устойчивого решения) — в
`../../ux/11-ai-generated-ui/02-research-and-benchmarks.md` §4.3. Они не противоречат
приведённым: там измерялся вердикт «какой лучше», здесь — оценка по описанным измерениям.

### 6.2. Две готовые рубрики

**Для одного экрана — 12 индикаторов AesEval-Bench** (§2.3): layout (balance, layering, whitespace,
alignment), color (harmony, contrast, appeal, psychology), font (legibility, hierarchy), graphics
(quality, relevance).

**Для последовательности экранов — 5 измерений GEBench** (шкала 0–5 каждое, агрегат = среднее × 20):

| Измерение | Что оценивает |
|---|---|
| **GOAL** | достигнута ли заявленная цель, полон ли результат |
| **LOGIC** | объясним ли переход реальным действием пользователя |
| **CONS** | сохранились ли нетронутые области и стабильны ли элементы между кадрами |
| **UI** | структурная связность, отсутствие галлюцинированных и физически невозможных элементов |
| **QUAL** | читаемость текста, чёткость иконок, отсутствие артефактов |

Третья рубрика, из UICrit, — тематическая: пять тем критики с распределением (§2.2). Она полезна не как
шкала, а как **проверка полноты**: если в ответе модели нет ни одного замечания по раскладке или
контрасту, ответ неполон.

Сборка рабочей рубрики из этих трёх — `04-steering-brief-prompts-pipeline.md` §4.2.

### 6.3. Протокол вызова критики

Собран из трёх работ:

1. **Разделить вызовы.** Критика отдельно, локализация отдельно (UICrit: объединение вызывает «task
   overload»).
2. **Дать описание каждого критерия.** Обязательно для субъективных, необязательно для очевидных
   (AesEval-Bench, абляция).
3. **Дать картинку.** Её удаление — самое сильное падение (AesEval-Bench).
4. **Дать метаданные.** JSON с раскладкой, цветами и шрифтами сильнее всего помогает локализации
   (AesEval-Bench). В нашем случае это выгрузка `measure_ui.py`.
5. **Для локализации наложить пронумерованные патчи**, а не просить координаты и не рисовать сетку линий
   (UICrit: 0,222 против 0,186 против 1,1e-5).
6. **Few-shot по близости задачи и внешнего вида**, а не случайный (UICrit: +55 %).
7. **Несколько прогонов и несколько судей** (GEBench: три судьи, три прогона).
8. **Ограничить число замечаний.** Многословность коррелирует с галлюцинациями (UICrit, UIClip).

### 6.4. Чего судья не заменяет

- **Расчёт.** Контраст, ΔE, кратность, принадлежность шкале считаются кодом, а не моделью. Это и дешевле,
  и точнее.
- **Локализацию.** IoU 0,20 на лучшей модели — это не «где», а «примерно там».
- **Вкус.** Fleiss' Kappa людей 0,29–0,31: согласия нет даже между экспертами.
- **Семантическую правильность.** `bg-subtle` вместо `bg-component` — значение из набора, правило
  нарушено; ловится только описанием применения и ревью (`../09-design-tokens/05` §3.4).

|---|---|---|
| GEBench | границы применимости картинок; рубрика из 5 измерений; доказательство, что VLM-судья на рубрике надёжен | шаг «генерация картинки», шаг «критика» |

### 7.2. Три числа, которые стоит помнить наизусть

- **0,2714** — точность самостоятельного обнаружения визуального дефекта моделью. Поэтому дефекты
  называем мы, а не она.
- **0,004 → 0,222** — IoU локализации замечания без помощи и с пронумерованными патчами. Поэтому
  локализацию делаем разметкой, а не просьбой.
- **9,8 против 1,74** — нарушений гайдлайна на проект в сгенерированном и человеческом коде. Поэтому
  проверка обязательна, а не опциональна.

## Частые ошибки при чтении этой литературы

1. **Путать «похоже на эталон» с «хорошо».** Design2Code измеряет воспроизведение макета, а не качество
   дизайна. Высокий CLIP при уродливом эталоне — высокий CLIP.
2. **Путать «красиво» с «работает».** GEBench прямо показывает: высокий QUAL при галлюцинированных
   виджетах.
3. **Брать результат бенчмарка как характеристику модели вообще.** GEBench мерил GPT-image-1.0 и 1.5;
   на 2.5 результаты не переносятся.
4. **Сравнивать агрегат с одним измерением.** «Nano Banana Pro лучшая по тексту» и «GPT-image-1.5 выше по
   GE-Score на английском» — оба утверждения верны и не противоречат друг другу.
5. **Считать человеческое предпочтение золотым стандартом.** Отрицательный вес текстового сходства
   в регрессии Design2Code — прямое доказательство когнитивного смещения.
6. **Ожидать от модели согласия выше человеческого.** Fleiss' Kappa экспертов 0,29–0,31.
7. **Переносить метрики эстетики фотографий на интерфейс.** AesExpert-7b — худший результат в
   AesEval-Bench.
8. **Считать «рассуждающую» модель лучшим судьёй.** Преимущества нет.
9. **Читать recall починки как «стало лучше».** Ни одна из работ не мерила, сколько новых нарушений
   вносит починка.
10. **Цитировать числа без выборки.** «9,8 нарушений» — это 20 проектов v0, размеченных вручную по
    Material Design, а не универсальная константа.

## Чек-лист выбора метрики

1. Что измеряется: похожесть на эталон, наличие внесённого дефекта или соответствие правилу?
2. Есть ли у метрики случайный уровень и указан ли он (0,50 для да/нет, 0,25 для выбора из четырёх)?
3. Если метрика — оценка VLM, есть ли рубрика с описанными критериями?
4. Сколько прогонов и сколько судей? Один прогон одной модели — шум.
5. Сверена ли рубрика с людьми, и на какой выборке (GEBench: 100 образцов на модель, 4 эксперта)?
6. Какое согласие у самих людей? Если Kappa ниже 0,4 — верхняя граница качества модели тоже низкая.
7. Локализуется ли замечание, и каким способом (номера патчей, координаты, ничего)?
8. Входит ли в вход и картинка, и метаданные?
9. Считается ли то, что можно посчитать (контраст, ΔE, кратность), кодом, а не моделью?
10. Измеряется ли число новых нарушений после правки, а не только число исправленных?

## Открытые вопросы и противоречия

1. **Нет бенчмарка визуального качества именно веб-приложений за авторизацией.** UICrit — мобильные
   экраны из RICO, AesEval-Bench — графический дизайн из Crello, Design2Code и DesignBench — публичные
   страницы. Админки и личные кабинеты не представлены ни в одном.
2. **Нет данных по русскому интерфейсу.** Design2Code отмечает, что неанглийские страницы сложнее, и на
   этом всё. Типографические ошибки кириллицы (`../02-typography/06` §4) никем не измерены.
3. **Согласие 0,9892 в GEBench выглядит аномально высоким** для задачи с человеческой субъективностью.
   Вероятное объяснение: пять измерений с жёсткими критериями оставляют мало места для разногласий, и
   усреднение четырёх экспертов дополнительно сглаживает. Проверить независимо не удалось.
4. **Противоречие по «рассуждающим» моделям.** AesEval-Bench: преимущества нет. GEBench использует
   Qwen3-VL-thinking как одного из судей и не сообщает, отличается ли он от нерассуждающих.
5. **Никто не измерял, ухудшает ли починка визуальный слой.** DesignRepair мерил recall починки, но не
   число новых нарушений. В UX-проекте есть данные, что итеративная починка вносит новые нарушения
   доступности; для визуальных величин аналога нет.
6. **Первоисточники по метрикам эстетики не открыты.** Miniukovich & De Angeli, Oulasvirta (AIM),
   Reinecke & Gajos — все по аннотациям и вторичным описаниям. Это единственный раздел файла с таким
   уровнем доказательности; относиться соответственно.
7. **Prototype2Code и DeclarUI разобраны по аннотациям**, полный текст не читан: их числа
   (96,8 % PTG, +55 % визуального сходства) приведены как заявления авторов.
8. **Неизвестно, переносится ли рубрика из 12 индикаторов с графического дизайна на интерфейс.**
   Crello — это постеры и баннеры. Индикаторы «psychology» и «appeal» для админки сомнительны;
   «legibility», «hierarchy», «alignment», «contrast», «whitespace» переносятся очевидно.
9. **Число 188,25 применимых правил на проект** относится к Material Design; для свода на shadcn/Tailwind
   порядок величины неизвестен.
10. **Все результаты по моделям устаревают за месяцы.** Из моделей, названных в разобранных работах,
    к сентябрю 2026 актуальны единицы. Устойчивы выводы про **форму задачи**, а не про модели.

## Источники

- `[S1]` Haodong Li и др. (StepFun AI). **GEBench: Benchmarking Image Generation Models as GUI
  Environments.** arXiv:2602.09007v2, 09–10.02.2026. https://arxiv.org/abs/2602.09007 — 700 задач,
  GE-Score из пяти измерений, 12 моделей, три VLM-судьи, Пирсон 0,9892 с экспертами. Первичное исследование.
- `[S2]` Jason Wu и др. (CMU, Apple). **UIClip: A Data-driven Model for Assessing User Interface Design.**
  arXiv:2404.12500, UIST 2024. https://arxiv.org/abs/2404.12500 — 2,3 млн синтетических пар, 12 дизайнеров,
  75,12 % против 51,58 % у GPT-4V, best-of-n. Первичное исследование.
- `[S3]` Peitong Duan, Chin-Yi Chen, Gang Li, Bjoern Hartmann, Yang Li. **UICrit: Enhancing Automated
  Design Evaluation with a UI Critique Dataset.** arXiv:2407.08850v3, UIST 2024.
  https://arxiv.org/abs/2407.08850 — 3 059 критик, 983 экрана, 7 дизайнеров, 13,1 % валидных замечаний
  Gemini, IoU 0,004 → 0,222, +55 % от few-shot. Первичное исследование.
- `[S4]` Jingyu Xiao и др. **DesignBench.** arXiv:2506.06251v1, 06.2025. https://arxiv.org/abs/2506.06251

- `[S17]` Arctanx An и др. (PKU, MSRA). **Can Vision–Language Models Assess Graphic Design Aesthetics?**
  arXiv:2603.01083v1, 03.2026. https://arxiv.org/abs/2603.01083 — AesEval-Bench: 4 измерения,
  12 индикаторов, 3 задачи, GPT-5 0,7252, IoU < 0,20, абляция входа.

  https://arxiv.org/abs/2411.01606 — 228 жёстких и 399 мягких ограничений, 9,8 против 1,74 нарушений,
  мягкие чинятся хуже жёстких.

  arXiv:2601.19171v2, CHI '26. https://arxiv.org/abs/2601.19171 — 907 фрагментов руководств шести
