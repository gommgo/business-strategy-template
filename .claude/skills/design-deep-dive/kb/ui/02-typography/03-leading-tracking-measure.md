## Выжимка для агента

1. **Интерлиньяж (line-height, leading) основного текста 1.4–1.5**: Material `body-medium` 14/20 = 1.43,
   Carbon `body-01` 14/20 = 1.43, Fluent Body 1 14/20 = 1.43, Atlassian 14/20 = 1.43, Radix 16/24 = 1.5,
   Tailwind base 16/24 = 1.5. → §1.1 `[консенсус]`
2. **Заголовки 1.1–1.3.** Atlassian: 32/36 = 1.125, 24/28 = 1.17, 20/24 = 1.2. Material: 32/40 = 1.25,
   57/64 = 1.12. → §1.2 `[консенсус]`
3. **Чем крупнее кегль, тем меньше относительный интерлиньяж.** Untitled UI формулирует прямо: «There is an
   inverse relationship between font size and appropriate line height» `[S32]`. → §1.3 `[консенсус]`
4. **И наоборот: чем мельче кегль, тем больше относительный интерлиньяж.** Primer рекомендует `relaxed` 1.625
   именно для 12–13 px, `loose` 1.75 для самого мелкого `[S7]`. Ant Design: 12 px → 1.667. → §1.3 `[система]`
5. **Простейшая исполнимая формула: `line-height(px) = font-size(px) + 8`** (Ant Design `[S35]`). Для плотных
   таблиц `+6`, для длинного чтения `+10`. → §1.4 `[система]`
6. **Однострочные лейблы, кнопки, бейджи: 1.0–1.25.** Primer: `tight` 1.25 — «for single-line text in compact
   UI elements like labels, badges, buttons… Not recommended for multi-line body text» `[S7]`.
   Polaris `body-xs` 11/12 = 1.09 `[S6]`. → §1.5 `[консенсус]`
7. **Задавай `line-height` в пикселях/rem там, где нужен вертикальный ритм**, и безразмерным там, где размер
   элемента может меняться. Material, Carbon, Fluent, Atlassian, Radix, GOV.UK задают в абсолютных единицах;
   Primer, Tailwind, Mantine, MUI — безразмерным. → §1.6 `[спорно]`
8. **Округляй line-height к 4 px** (Material — все значения; Atlassian, Radix, Tailwind — почти все);
   у GOV.UK кратность 5 px под свою сетку. → §1.7 `[система]`
9. **Трекинг (letter-spacing) отрицательный у крупных кеглей, положительный у мелких.** Radix:
   +0.0025em на 12 px → −0.025em на 60 px `[S18]`. Material: +0.5px на 11–12 px, 0 на 22–36 px,
   −0.25px на 57 px `[S5]`. → §2.1 `[консенсус]`
10. **Порядок величин**: заголовки 20–32 px → −0.01…−0.015 em; 36–60 px → −0.02…−0.025 em; тело 14–16 px → 0;
    подписи 11–12 px → +0.01…+0.02 em; капс-лейблы → +0.05…+0.1 em. → §2.2
11. **Не переноси значения трекинга между гарнитурами.** Прямо в коде MUI: «The letter spacing was designed
    for the Roboto font-family. Using the same letter-spacing across font-families can cause issues with the
    kerning» `[S36]`. → §2.4 `[система]`
12. **У SF Pro трекинг отрицательный именно в диапазоне тела (13–23 pt), минимум −26/1000 em на 17 pt**,
    и снова положительный ниже 12 pt и выше 24 pt `[S4]`. Это опровергает «народное» правило «чем крупнее,
    тем отрицательнее» в его абсолютной форме. → §2.3 `[исследование]`
13. **Длина строки 45–75 знаков.** Baymard: 50–75, WCAG 1.4.8 — не более 80 `[S23]`; Butterick: 45–90 `[S26]`;
    Erik Kennedy: 50–75 `[S12]`; Practical UI: 40–80 `[S31]`. → §3.1 `[исследование]`
14. **`max-width: 65ch` для абзацев** — 520 px при 14 px и 640 px при 16 px. В таблицах, формах и панелях
    ограничение не применяется. → §3.2 `[консенсус]`
15. **Русский текст той же длины в знаках шире английского на 13–18 %** `[S24]`: `65ch` для русского даёт
    строку, визуально соответствующую примерно 58 английским знакам. Не уменьшай `ch` дополнительно.
    → §3.3 `[исследование]`
16. **Отступ между абзацами 0.75–1.0 em** (Atlassian: 16 px при теле 16, 12 px при 14, 8 px при 12 `[S10]`).
    WCAG 1.4.12 требует, чтобы интерфейс пережил `2em`. → §4.1 `[система]`
17. **Над заголовком отступ вдвое больше, чем под ним** (правило близости). Практическое значение:
    32/8 px для заголовка секции, 40/12 px для H1. → §4.2 `[мнение]`
18. **Выравнивание только по левому краю.** Fluent: «generally stick to left-alignment for LTR languages»;
    центрирование — «to call attention to a small piece of copy»; выключка по формату (`justify`) в
    интерфейсе не применяется никогда. → §5 `[консенсус]`
19. **Числа в таблице — по правому краю, с табличными цифрами**; текст — по левому; заголовок колонки
    выравнивается так же, как её содержимое. → §5.3 `[консенсус]`
20. **`text-wrap: balance` для заголовков и коротких подписей** (до 6 строк в Chromium, 10 в Firefox),
    `text-wrap: pretty` для абзацев. Подробности и границы применимости — в
    `05-numbers-rhythm-opentype.md` §4. `[система]`
21. **Предел отрицательного трекинга проверяй словом «ухо»**: уменьшай значение, пока буквы не соприкоснулись;
    предыдущее — предел (Королькова `[V15]`). → §2.3a `[мнение]`
22. **Мелкому тексту нужен положительный трекинг, крупному — отрицательный**, потому что одни и те же
    промежутки кажутся большими при крупном кегле и тесными при мелком (Королькова `[V15]`). → §2.3a `[исследование]`
23. **Абзац длиннее трёх строк — только по левому краю; выравнивания в одном блоке не смешивать**
    (Tim Gabe `[V07]`). → §5.1 `[консенсус]`
24. **Отступ между заголовком и его текстом 1×, до предыдущего блока 2×** (Tim Gabe `[V07]`): 16 и 32 px при
    базе 16 px. → §4.2 `[консенсус видео]`

  общепринятой `[спорно]`.

с текстом 16 px.

### 1.3. Правило обратной зависимости

Untitled UI `[S32]`: «There is an inverse relationship between font size and appropriate line height — the
larger the text, the smaller the line height should be.»
Butterick `[S26]`: «fonts that run small will need less line spacing, and vice versa» (про кажущийся размер);
и «As you reduce point size, also reduce line spacing and line length».
Primer `[S7]` формулирует нижнюю часть кривой: `relaxed` 1.625 — «for longer-form content, smaller text sizes
(12-13px)», `loose` 1.75 — «very small text… footnotes, legal text».

Steve Schoger `[V02 28:16]` формулирует то же и сразу с оговоркой: «нет одного значения на все случаи,
потому что влияют кегль и длина строки»; безопасная отправная точка для основного текста — **16 px / 1.5**,
крупнее кегль → плотнее межстрочный.
Александра Королькова `[V15 06:09]` добавляет, что **генераторы шкал применяют коэффициент тупо**: «чем крупнее
кегль и короче строка, тем меньше интерлиньяж, иногда меньше кегля». То есть для дисплейных размеров
допустим `line-height < 1.0`, чего нет ни в одной из изученных систем (минимум — GOV.UK 48/50 = 1.04).

Собранная кривая (из значений Material 3, Carbon, Radix, Ant Design, Tailwind):

| кегль | ratio | line-height в px |
|---|---|---|
| 11 px | 1.45 | 16 px |
| 12 px | 1.33–1.67 | 16–20 px |
| 13 px | 1.54 | 20 px |
| 14 px | 1.29–1.57 | 18–22 px |
| 16 px | 1.375–1.50 | 22–24 px |
| 18 px | 1.44–1.56 | 26–28 px |
| 20 px | 1.20–1.40 | 24–28 px |
| 24 px | 1.25–1.33 | 30–32 px |
| 28 px | 1.14–1.29 | 32–36 px |
| 32 px | 1.125–1.25 | 36–40 px |
| 36 px | 1.11–1.33 | 40–48 px |
| 48 px | 1.04–1.17 | 50–56 px |
| 60 px | 1.00–1.16 | 60–70 px |

Заметь «горб» в районе 12–18 px: самая мелкая подпись получает *относительно* большой интерлиньяж, тело —
средний, а дальше кривая монотонно падает.

### 1.4. Формулы

| формула | источник | результат для 14 px | для 16 px | для 24 px |
|---|---|---|---|---|
| `lh = size + 8` | Ant Design `[S35]` | 22 px (1.57) | 24 px (1.5) | 32 px (1.33) |
| `lh = size + 6` | вывод из Carbon `body-01` и Material | 20 px (1.43) | 22 px (1.375) | 30 px (1.25) |
| `lh = size + 4` | вывод из Carbon `body-compact-01` | 18 px (1.29) | 20 px (1.25) | 28 px (1.17) |
| `lh = round4(size × 1.45)` | усреднение | 20 px | 24 px | 36 px — уже много |

**Рекомендация для генератора**: `lh = size + 6`, округление до ближайших 4 px для размеров ≥ 20 px.
Проверка: 11→16(+5, округл. 16), 12→18→16, 14→20, 16→22, 20→26→28, 24→30→32, 28→34→36, 32→38→40.
Совпадает с Material 3 почти везде.

### 1.5. Однострочные элементы

| элемент | line-height | источник |
|---|---|---|
| кнопка | 1.25–1.43, или равен высоте контрола | Material `label-large` 14/20 = 1.43 `[S5]`; Primer `tight` 1.25 `[S7]` |
| бейдж, чип | 1.0–1.25 | Primer `tight` «badges» `[S7]`; Polaris `body-xs` 11/12 = 1.09 `[S6]` |
| подпись поля | 1.33 | Carbon `label-01` 12/16 `[S2]` |
| заголовок колонки таблицы | 1.33 | Carbon `label-01` `[S2]` |
| пункт меню | 1.43 | Material `label-large` `[S5]` |
| инлайновый код | равен кеглю (1.0) | Atlassian: «line height is equal to the font size» `[S10]` |

Primer прямо предупреждает `[S7]`: `tight` 1.25 «Not recommended for multi-line body text due to reduced
readability». То есть плотный интерлиньяж допустим только там, где строка гарантированно одна.

Практика: в кнопках и контролах интерлиньяж часто не задают вовсе, а центрируют текст по высоте контрола
флексом. Это надёжнее, потому что не зависит от гарнитуры.

### 1.6. Абсолютный или безразмерный

> Разрешение противоречия [C36]: в токенах — отношение (DTCG требует `number`), подобранное под целые px и кратность 4 (`../09-design-tokens/04-reference-token-schema.md` §2.5); в CSS — шестизначное отношение, округлённое вверх (`1.428572` для 20 / 14); интерлиньяж задаётся вместе с кеглем в роли и не наследуется в блок с другим кеглем. См. `../CONTRADICTIONS.md`.

| система | как задаёт |
|---|---|
| Material 3 `[S5]`, Carbon `[S2]`, Fluent `[S3]`, Atlassian `[S10]`, Radix `[S18]`, GOV.UK `[S8]`, Polaris `[S6]` | **абсолютно** (px / rem) |
| Primer `[S7]`, Tailwind `[S9]`, Mantine `[S37]`, MUI `[S36]`, Ant Design `[S35]` | **безразмерно** (множитель) |
| Butterick `[S26]` | безразмерно: «preferably with a unitless value, so 130 % would become 1.3» |

`[спорно]`. Разбор:

- **Абсолютное значение** даёт вертикальный ритм: все строки укладываются в сетку 4 px, высоты строк таблицы
  предсказуемы, отступы считаются арифметикой. Минус: при наследовании в дочерний элемент с другим кеглем
  значение не масштабируется.
- **Безразмерное** наследуется как множитель и безопасно для вложенных элементов. Минус: при кегле 13 px и
  множителе 1.45 получается 18.85 px, полпикселя уезжает, ритм ломается.

**Практическое решение**: задавай пары «размер + интерлиньяж» как единые роли в абсолютных единицах (как
Material, Carbon, Radix) и не наследуй интерлиньяж отдельно. На корневом элементе задай безразмерное значение
как страховку (`body { line-height: 1.5 }`), чтобы элементы без роли выглядели прилично.

### 1.7. Кратность

| система | кратность line-height | примеры отклонений |
|---|---|---|
| Material 3 `[S5]` | 4 px, все без исключений | — |
| Carbon `[S2]` | 2 px | 18, 22, 50 px — кратны 2, не 4 |
| Atlassian `[S10]` | 4 px | — |
| Radix `[S18]` | 2 px | 18, 22, 26, 30 px |
| Tailwind `[S9]` | 4 px | — |
| Fluent `[S3]` | 2 px | 14, 22, 26 px |
| GOV.UK `[S8]` | **5 px** | 20, 25, 30, 35, 40, 50, 55, 80 px |
| Ant Design `[S35]` | нет кратности | 20, 22, 24, 28, 32, 38, 46, 54, 64, 76 px |

**Для генератора**: выбери 4 px, допусти 2 px для плотных пар (14/18). Смешивать кратности внутри одного
продукта нельзя: это ровно то, что делает ритм «дрожащим».

tighter −0.05em, tight −0.025em, normal 0, wide +0.025em, wider +0.05em, widest +0.1em.

#### MUI `[S36]`

h1 −0.01563em, h2 −0.00833em, h3 0, h4 +0.00735em, h5 0, h6 +0.0075em, subtitle1 +0.00938em,
subtitle2 +0.00714em, body1 +0.00938em, body2 +0.01071em, button +0.02857em, caption +0.03333em,
overline +0.08333em.

### 2.2. Рабочие значения

Свод `[консенсус]`:

| контекст | кегль | трекинг |
|---|---|---|
| капс-лейбл, small caps | 10–12 px | **+0.05…+0.1 em** |
| подпись, мета | 11–12 px | +0.01…+0.04 em |
| тело | 13–16 px | **0** (или +0.01 em для Carbon-подобной подачи) |
| заголовок карточки, секции | 16–20 px | −0.005…−0.01 em |
| заголовок страницы | 20–28 px | −0.01…−0.015 em |
| крупный заголовок | 32–48 px | −0.015…−0.02 em |
| display | 57–96 px | −0.02…−0.025 em |
| KPI-число | 28–40 px | −0.02 em |
| моноширинный | любой | 0…−0.007 em |

### 2.3. Что делает SF Pro и почему это важно

Apple публикует полные таблицы трекинга `[S4]`. Ключевые точки для SF Pro:

| кегль pt | трекинг 1/1000 em | в pt |
|---|---|---|
| 10 | +12 | +0.12 |
| 11 | +6 | +0.06 |
| 12 | 0 | 0 |
| 13 | −6 | −0.08 |
| 14 | −11 | −0.15 |
| 15 | −16 | −0.23 |
| 16 | −20 | −0.31 |
| **17** | **−26** | **−0.43** |
| 20 | −23 | −0.45 |
| 23 | −4 | −0.10 |
| 24 | +3 | +0.07 |
| 28 | +14 | +0.38 |
| 34 | +12 | +0.40 |
| 48 | +8 | +0.35 |
| 80 и выше | 0 | 0 |

То есть у SF Pro **трекинг отрицательный ровно в диапазоне основного текста (13–23 pt), с минимумом
−0.026 em на 17 pt**, а на мелких и на крупных кеглях положительный. Это прямо противоречит правилу «чем
крупнее, тем плотнее» в его абсолютной форме `[исследование]`.

Для New York (serif) картина другая: трекинг отрицательный начиная с 16 pt и монотонно растёт по модулю
до −0.018 em. Для SF Pro Rounded — положительный на всех размерах до 76 pt.

Вывод: **кривая трекинга — свойство конкретной гарнитуры, а не универсальный закон**. Правила из §2.2 —
приближение для «обычного» интерфейсного гротеска, не подогнанного под кегль.

Апдейт от Apple: «In a running app, the system font dynamically adjusts tracking at every point size. To
produce an accurate interface mockup… you might need to adjust the tracking» `[S4]`. В вебе этой автоматики
нет, поэтому значения задаются вручную.

### 2.3a. Как найти предел отрицательного трекинга: тест «ухо»

Александра Королькова `[V15 19:26]`–`[25:33]` объясняет механику и даёт проверку.

**Почему трекинг вообще нужен.** Оптическая иллюзия: одни и те же промежутки кажутся большими при крупном
кегле и тесными при мелком. Отсюда исторические оптические размеры: у шрифтов Бодони для 6-го кегля
«гигантские межбуквенные расстояния» и часть штрихов упрощена.

**Правило компенсации, если у гарнитуры нет оптических размеров** `[V15 23:31]`:
- крупно → **небольшой отрицательный трекинг**;
- мелко → **небольшой положительный трекинг** и расширение **на 5 %, не больше**.
  Цитата: «вам везде будут писать: не растягивайте и не сжимайте шрифты. В обычных условиях — не растягивайте.
  Но если надо набрать очень мелко, растяните на 5 %». `[спорно]` для интерфейсов: надёжнее взять гарнитуру с
  текстовым оптическим размером, чем растягивать (см. `01-font-selection.md` §8.1).

**Тест «ухо»** `[V15 24:32]`. При рисовании шрифта треугольным буквам («у», «х», «А», «V») задают минимальные
боковые поля, потому что между ними и так дыра. Как только трекинг уходит в минус, две такие буквы подряд
«втыкаются» друг в друга. Практическая проверка: набрать гарнитурой слово **«ухо»** и уменьшать трекинг до
момента, когда буквы соприкоснутся; **предыдущее значение — предел**.

Альтернатива от разработчиков шрифтов: отдельная линейка с плотным набором вместо кручения трекинга. Пример —
**Inter Tight** Расмуса Андерсона: тот же рисунок, другие расстояния `[V15 24:32]`, `[S13]`.

Tim Gabe `[V07 A 03:02]`–`[A 04:05]` даёт тот же порядок величин с другой стороны: трекинг заголовков
**−1…−2 %** («та самая хрусткость крупных заголовков на хороших сайтах»), основному тексту отрицательный
трекинг не ставить, при сомнении брать меньшее по модулю значение.

### 2.4. Трекинг не переносится между гарнитурами

Прямая цитата из исходника MUI `[S36]`: «The letter spacing was designed for the Roboto font-family. Using
the same letter-spacing across font-families can cause issues with the kerning.» В коде это реализовано как
условие: трекинг применяется, **только если семейство осталось дефолтным Roboto**.

Untitled UI `[S32]` добавляет практическую ловушку: Figma задаёт letter-spacing в процентах, CSS — в px или
em, и при передаче в разработку значения нужно пересчитывать (1 % = 0.01 em).

**Правило**: при смене гарнитуры обнули трекинг и подбери заново, начиная от нуля. Шрифты, оптимизированные
для интерфейса (Inter, Golos Text, Onest, Geist), обычно уже хорошо отспейсены на 14–16 px и требуют только
подтяжки крупных заголовков.

### 2.5. Капс и разрядка

Верхний регистр в мелком кегле требует **положительного трекинга +0.05…+0.1 em**: прописные нарисованы
для соседства со строчными, и в сплошном капсе просветы кажутся слишком тесными.

MUI `overline`: 12 px, `+0.08333 em`, UPPERCASE `[S36]`. Tailwind `widest` = +0.1em `[S9]`.
Steve Schoger `[V02 39:40]` формулирует причину: «заглавные буквы не имеют разнообразия форм, поэтому слово
хуже опознаётся», отсюда правило — **при любом uppercase добавлять трекинг, вплоть до аббревиатур внутри
текста**.

Но: **Fluent 2 прямо не советует капс** `[S3]`: «Don't use all caps to get a user's attention because it's
difficult to read.» Для русского это тем более верно: в кириллице прописные ближе по рисунку друг к другу
(много прямоугольных форм), капс читается хуже, чем в латинице.

Итог `[спорно]`: капс-лейблы (12 px / 600 / +0.06 em / UPPERCASE) остаются в ходу в некоторых системах, но
для русского интерфейса безопаснее заменить их на 12 px / 500–600 + цвет `secondary` без смены регистра.
Подробнее в `04-weight-hierarchy-color.md` §5.

## 3. Длина строки (measure)

### 3.1. Значения по источникам

| источник | диапазон | тип |
|---|---|---|
| Baymard `[S23]` | **50–75 знаков**, «optimal» | юзабилити-тесты, e-commerce |
| Emil Ruder, «Typographie» (через Baymard `[S23]`) | 50–60 знаков | классика |
| WCAG 1.4.8 (через Baymard `[S23]`) | **не более 80** (40 для CJK) | стандарт |
| Butterick `[S26]` | 45–90 знаков, «2–3 строчные азбуки» | книга-справочник |
| Erik Kennedy `[S12]` | 50–75 знаков | практик |
| Practical UI (Adham Dannaway) `[S31]` | **40–80 знаков** | книга |
| Tim Gabe `[V07 A 06:07]` | 50–75 знаков; при кегле ~18 px это **≈ 600 px** на десктопе | практик, ссылается на Baymard |
| Refactoring UI (Wathan, Schoger) `[S40]` | 45–75 знаков (20–35 em) | книга |

**Пересечение всех: 50–75 знаков.** Нижняя граница 40 (Practical UI) нужна для узких колонок и мобильных;
верхняя 80 — жёсткий потолок из WCAG.

Почему границы такие:
- слишком длинная: «the line length makes it difficult to gauge where the line starts and ends… it can be
  difficult to continue onto the correct line» `[S23]`;
- слишком короткая: «the eye will have to travel back too often, breaking the reader's rhythm. Too-short
  lines also tend to stress readers, making them begin on the next line before finishing the current one»
  `[S23]`.

Baymard приводит наблюдения из тестов: пользователи, увидев длинные строки, «immediately go back to a
previous page» `[S23]` `[исследование]`.

### 3.2. Как задавать

Baymard `[S23]` предлагает `max-width` около `70ch` или `34em`. Единица `ch` = ширина глифа «0» в текущем
шрифте, то есть приблизительно совпадает со средней шириной знака.

Практические значения:

| кегль | `65ch` | `70ch` | примерная ширина в px (Inter) |
|---|---|---|---|
| 14 px | ~520 px | ~560 px | цифра «0» Inter ≈ 0.57 em = 8 px |
| 16 px | ~595 px | ~640 px | |
| 19 px (GOV.UK) | ~710 px | ~760 px | |

Альтернатива без `ch`: `max-width: 40em` для 45–75 знаков — грубее, но не зависит от конкретного шрифта.

### 3.3. Поправка на русский

Измерено `[S24]`: **кириллическая строчная в среднем на 12–20 % шире латинской в том же шрифте** (PT Sans
1.120, Golos Text 1.128, Inter 1.147, IBM Plex Sans 1.173, Roboto 1.196). На связном тексте разница по
фактической ширине составила **+13…+18 %** при почти одинаковом числе знаков (+2.6 %).

Следствия:
- `65ch` для русского текста визуально ближе к 58 английским знакам по *ширине блока*, но по *числу знаков в
  строке* это по-прежнему 65 — а именно число знаков определяет удобство чтения. Значит **`ch` и дальше
  правильная единица, уменьшать её не нужно**.
- Зато колонка с русским текстом займёт на 13–18 % больше пикселей, чем такая же английская. Это надо
  закладывать в раскладку (см. `05-layout-grid/` волны 2).

### 3.4. Где measure не применяется

| контекст | почему |
|---|---|
| ячейка таблицы | ширина задаётся колонкой, текст обычно короткий или усекается |
| поле формы и его значение | ширина задаётся типом данных |
| элементы навигации, вкладки, кнопки | одна строка |
| панель фильтров, сайдбар | ширина панели уже ограничена (240–320 px) |
| код | ширина определяется содержимым, перенос по словам недопустим |

Где применяется всегда: абзацы описаний, тексты пустых состояний, тексты ошибок и подтверждений,
справочные блоки, соглашения, письма в предпросмотре.

## 4. Абзац и вертикальные отступы вокруг текста

### 4.1. Отступ между абзацами

| источник | значение |
|---|---|
| Atlassian `font.body.large` (16 px) `[S10]` | 16 px = **1.0 em** |
| Atlassian `font.body` (14 px) `[S10]` | 12 px = 0.857 em |
| Atlassian `font.body.small` (12 px) `[S10]` | 8 px = 0.667 em |
| WCAG 1.4.12 (минимум настраиваемости) `[S23]` | **2 em** должно быть поддержано без поломки |

Закономерность Atlassian: **чем мельче текст, тем меньше относительный отбив**. Логика та же, что у
интерлиньяжа наоборот: мелкий текст обычно короткий, ему не нужен большой «разрыв смысла».

Tim Gabe `[V07 A 09:12]` формулирует общее правило расстояний по силе связи: если между заголовком и его
текстом **1× = 16 px**, то до предыдущего блока **2× = 32 px**.

Sajid `[V05 09:10]` предлагает более жёсткий приём: **использовать `line-height` как встроенный нижний
отступ текстового блока**, а `margin` у заголовков и абзацев обнулять. Топ-комментарий под видео уточняет
практику: «Always reset margin and padding on h1–h6 and p to 0. Try to rely on line height for consistent
spacing». `[мнение]` Приём экономит решения, но ломается при смене гарнитуры (полулидинг разный), поэтому
надёжнее задавать отступы явно и обрезать полулидинг через `text-box-trim` (см.
`05-numbers-rhythm-opentype.md` §3.3).

Рабочее правило `[система]`: отбив = **0.75–1.0 em**, и обязательно кратен 4 px.
База 14 px → 12 px. База 16 px → 16 px. Подпись 12 px → 8 px.

Антиправило: не используй и отступ, и красную строку одновременно (классическая типографика выбирает одно);
в интерфейсах красная строка не применяется вообще.

### 4.2. Заголовок и текст под ним

Правило близости (Gestalt): заголовок принадлежит тексту под ним, значит отступ **сверху должен быть
заметно больше, чем снизу**. Типичное соотношение **2:1 … 4:1**; нижнюю границу подтверждает Tim Gabe
`[V07 A 09:12]` числом: **1× между заголовком и его текстом (16 px), 2× до предыдущего блока (32 px)**
`[консенсус видео]`. В документации дизайн-систем это соотношение не задано, но оно согласуется с тем, как
устроены отступы в Atlassian и Carbon.

Отдельное предупреждение Бирмана `[V14]`: **увеличив кегль заголовка, не увеличивай автоматически отступ
под ним** — иначе заголовок отрывается от своего текста и начинает читаться как относящийся к предыдущему
блоку.

Рабочие значения (согласуются со шкалой отступов 4/8, см. `03-spacing-sizing/`):

| роль | отступ сверху | отступ снизу | соотношение |
|---|---|---|---|
| H1 страницы | 0 (первый элемент) | 12–16 px | — |
| Заголовок секции (16–20 px) | 32 px | 8–12 px | 3:1 … 4:1 |
| Заголовок подсекции (14–16 px) | 24 px | 8 px | 3:1 |
| Заголовок карточки | 0 (первый в карточке) | 8 px | — |
| Между секциями (без заголовка) | 24–40 px | — | — |

### 4.3. Оптическая поправка: полулидинг

Интерлиньяж распределяется поровну над и под строкой (half-leading). Для заголовка 32 px с интерлиньяжем
40 px это 4 px сверху и 4 px снизу, которые визуально добавляются к заданным отступам. Из-за этого заголовок
с `margin-top: 32px` выглядит так, будто отступ 36 px.

Два решения:
1. **Вычитать полулидинг руками**: `margin-top: calc(32px - (40px - 32px) / 2)` = 28 px.
2. **`text-box-trim`** — CSS-свойство, ставшее Baseline в августе 2026 `[S22]`. Подробности в
   `05-numbers-rhythm-opentype.md` §3.

До `text-box-trim` системы решали задачу токенами: Radix Themes хранит
`--default-leading-trim-start: 0.42em` и `--default-leading-trim-end: 0.36em`, а для заголовков —
свои значения `[S18]`.

## 5. Выравнивание

### 5.1. Горизонтальное

Fluent 2 `[S3]`: «When aligning text horizontally, generally stick to left-alignment for left-to-right (LTR)
languages… Use right-alignment for right-to-left (RTL) languages… or to distinguish a short text element in
English, like a side note. Don't right-align long blocks of text in LTR languages. Use the same discretion
when centering text. It should call attention to a small piece of copy.»

Carbon `[S2]` про `body-01` и `body-02`: «It is always left-aligned.»

| контекст | выравнивание |
|---|---|
| весь текст интерфейса | **по левому краю** |
| пустое состояние (иллюстрация + 1 заголовок + 1–2 строки) | по центру |
| диалог подтверждения с одной короткой фразой | по центру допустимо |
| экран входа / регистрации | по центру допустимо |
| текст ошибки под полем | по левому краю |
| числа в таблице | по правому краю |
| короткая боковая заметка справа от контента | по правому краю допустимо |
| длинный абзац | **никогда не по центру и не по правому краю** |

Tim Gabe `[V07 A 05:06]` добавляет два порога:
- **больше трёх строк — только левый край**; центрированный абзац заставляет каждый раз искать начало
  следующей строки;
- **никогда не смешивай выравнивания**: заголовок по центру плюс текст по левому краю (и наоборот).

Refactoring UI `[S40]`: «Left align most text, right align numbers in tables. **Justify only with
hyphenation**» — то есть выключка по формату допустима только вместе с переносами, а без них не применяется.

**Выключка по формату (`text-align: justify`) в интерфейсе не применяется никогда** `[консенсус]`:
без переносов и тонкой настройки она даёт «реки» из пробелов, особенно заметные в узких колонках и в русском
тексте с длинными словами.

### 5.2. Вертикальное

Fluent 2 `[S3]`: «Fluent uses baseline alignment to distribute vertical space. This creates a consistent
visual rhythm within a layout.»

Практика для веба: базовые линии соседних элементов разной величины (иконка 16 px и текст 14 px, поле ввода
и его подпись) выравниваются либо по центру блока (`align-items: center`), либо по первой базовой линии
(`align-items: first baseline`). Второе точнее для текста, первое — для текста с иконками.

### 5.3. Таблицы

| тип колонки | выравнивание | комментарий |
|---|---|---|
| текст, имена, описания | влево | |
| числа, суммы, проценты | **вправо**, `font-variant-numeric: tabular-nums` | разряды выстраиваются друг под другом |
| даты и время | влево или вправо, но единообразно | при формате `ISO` или `ДД.ММ.ГГГГ` влево читается лучше |
| статусы, бейджи | влево | |
| действия | вправо | |
| заголовок колонки | **как содержимое** | заголовок числовой колонки тоже вправо |

Подробности о цифрах — в `05-numbers-rhythm-opentype.md` §1.

### 5.4. Переносы в русском

`hyphens: auto` работает только при указанном языке:

```html
<html lang="ru">
```
```css
.prose { hyphens: auto; hyphenate-limit-chars: 6 3 3; }
```

Где включать: узкие колонки (< 45 знаков), карточки, мобильная версия, текст в сайдбаре.
Где не включать: заголовки, кнопки, ячейки таблиц, ссылки, идентификаторы.

Для русского это особенно полезно: слова длиннее английских (среднее слово русского текста примерно на
1.5 знака длиннее), в узкой колонке без переносов появляются большие дыры.

Подробнее о русских правилах переноса и неразрывных пробелах — в `06-localization-and-ai-errors.md` §2.

## Частые ошибки

### Общие

1. **`line-height: 1` у абзаца.** Строки слипаются. Минимум для многострочного текста — 1.4.
2. **`line-height: 1.5` глобально на всё**, включая заголовки 32 px (получается 48 px) и бейджи.
3. **`line-height: normal`.** Даёт разброс 1.17–1.42 в зависимости от шрифта `[S24]`; при подмене шрифта
   вёрстка прыгает.
4. **Дробные значения интерлиньяжа** (19.6 px): полупиксельные строки, неровный ритм в таблице.
5. **Одинаковый трекинг на всех кеглях.** Заголовок 32 px с тем же `letter-spacing: 0.02em`, что и подпись
   11 px, выглядит разреженным.
6. **Отрицательный трекинг на теле.** `letter-spacing: -0.02em` на 14 px делает текст «слипшимся»; ни одна
   система так не делает: на 14–16 px все ставят 0 или плюс.
7. **Трекинг, скопированный вместе со шкалой из другой системы, при другой гарнитуре** `[S36]`.
8. **Абзац шириной во весь экран** (1400 px = ~180 знаков при 16 px). Нарушает WCAG 1.4.8.
9. **Центрированный длинный текст** в пустом состоянии или в модалке.
10. **`text-align: justify`** в интерфейсе.
11. **Одинаковый отступ сверху и снизу у заголовка.** Заголовок «плавает» между блоками, непонятно, к чему
    относится.
12. **Отступ между абзацами задан `<br><br>`** вместо `margin`.
13. **`hyphens: auto` без `lang="ru"`.** Не работает или переносит по английским правилам.

### Характерные для нейросетей

14. **`leading-relaxed` (1.625) на заголовке и `leading-tight` (1.25) на абзаце** — перепутанные местами
    утилиты Tailwind. Проверка: у любого блока длиннее 2 строк ratio ≥ 1.4; у любого заголовка ≤ 1.3.
15. **`tracking-tight` на всём подряд.** Модель «слышала», что у современных интерфейсов плотный трекинг,
    и вешает −0.025em и на заголовок, и на подпись 11 px.
16. **Отсутствие `max-width` у абзацев** в сгенерированной раскладке: контент растягивается на всю ширину
    контейнера 1440 px.
17. **Разные значения интерлиньяжа для одинаковых по роли блоков** на соседних страницах.
18. **`text-align: center` у всей карточки** вместо центрирования одного заголовка.
19. **Копирование `line-height` в px без пересчёта при смене кегля**: было 14/20, стало 16/20 (ratio 1.25,
    слишком плотно для тела).

## Чек-лист

1. Интерлиньяж основного текста в диапазоне 1.4–1.5? Да / нет.
2. Интерлиньяж заголовков в диапазоне 1.1–1.3 и уменьшается с ростом кегля? Да / нет.
3. Мелкие подписи (11–12 px) получили *больший* относительный интерлиньяж (1.33–1.6)? Да / нет.
4. Все значения `line-height` — целые пиксели, кратные 4 (допустимо 2)? Да / нет.
5. `line-height: normal` нигде не используется? Да / нет.
6. Трекинг: 0 на теле, отрицательный только с 18–20 px, положительный только на 11–12 px и на капсе? Да / нет.
7. Значения трекинга подобраны под текущую гарнитуру, а не скопированы из чужой системы? Да / нет.
8. У абзацев есть `max-width` в диапазоне 45–75 знаков (`60ch`–`70ch`)? Да / нет.
9. Ни одна строка текста не превышает 80 знаков (WCAG 1.4.8)? Да / нет.
10. Отступ между абзацами 0.75–1.0 em и кратен 4 px? Да / нет.
11. Отступ над заголовком в 2–4 раза больше, чем под ним? Да / нет.
12. Весь текст выровнен по левому краю, кроме чисел в таблицах (вправо) и коротких блоков пустых состояний
    (по центру)? Да / нет.
13. `justify` не встречается нигде? Да / нет.
14. Числовые колонки таблиц выровнены вправо вместе с их заголовками? Да / нет.
15. Интерфейс не ломается при `line-height: 1.5`, `letter-spacing: 0.12em`, `word-spacing: 0.16em`,
    отступе абзаца `2em` (WCAG 1.4.12)? Да / нет.
16. `hyphens: auto` включён только там, где колонка уже 45 знаков, и установлен `lang="ru"`? Да / нет.

## Открытые вопросы и противоречия

1. **Абсолютный против безразмерного `line-height`** `[спорно]`. Системы делятся примерно поровну; аргументы
   в §1.6. Прямого сравнения последствий ни один источник не приводит.
2. **Mantine с растущим интерлиньяжем** (1.4 → 1.65 на кеглях 12 → 20 px) `[S37]` противоречит остальным.
   Объяснения в исходниках нет.
3. **Соотношение отступов над и под заголовком** я нигде не нашёл в виде числа. 2:1 … 4:1 — вывод из
   практики и принципа близости, а не из источника. `[мнение]`
4. **Ширина строки для русского**: все найденные исследования (Ruder, Baymard, WCAG) сделаны на латинице.
   Переносится ли диапазон 50–75 знаков на кириллицу без поправки — неизвестно. Мои измерения говорят только
   о ширине в пикселях, не о скорости чтения. Кандидат на отдельное исследование.
5. **Капс в русском интерфейсе** `[спорно]`: Fluent запрещает капс вообще, MUI держит его в `button` и
   `overline`, Material 3 от капса кнопок отказался при переходе с M2 на M3. Количественных данных по
   кириллице нет.
6. **Значение `+0.16 px` трекинга у Carbon на 14 px** (= +0.011 em) — единственная система, добавляющая
   трекинг к телу. Связано ли это со свойствами IBM Plex или это общий приём, неизвестно.
7. **`hyphenate-limit-chars` для русского**: значения 6 3 3 — общепринятая практика, но подтверждения в
   открытых мной источниках нет. `[мнение]`
