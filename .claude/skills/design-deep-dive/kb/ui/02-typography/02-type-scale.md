# Типографическая шкала интерфейса: размеры, роли, база 14 или 16

Волна 1, агент B, 22 сентября 2026. Источников прочитано целиком: 37. Сквозная нумерация источников по всей
папке `02-typography/`, полный список в `README.md`.

## Выжимка для агента

1. **Не изобретай шкалу — возьми готовый пресет** из §7 (плотная админка, база 14 px) или §8 (клиентский сервис,
   база 16 px) и меняй только то, что мешает. → §7, §8 `[система]`
2. **База 14 px для админок и бэк-офиса, 16 px для клиентских сервисов.** Это не вкус: Carbon прямо разделяет
   productive (14) и expressive (16), Fluent 2 web Body 1 = 14, Ant Design seed = 14, Atlassian body = 14;
   Material 3 body-large = 16, Radix Themes default = 16, Mantine md = 16. → §2 `[консенсус]`
3. **Поля ввода на страницах, которые открывают с телефона, — минимум 16 px**, иначе Safari на iOS зумит поле
   при фокусе. Если тело 14 px, то у `input`, `textarea`, `select` всё равно ставь `font-size: 16px` на
   ширинах < 768 px. → §5.2 `[консенсус]`
4. **Размеров должно быть 5–7, ролей 8–12.** Роли переиспользуют размеры (14/400 body и 14/600 заголовок
   карточки — это один размер и две роли). Erik Kennedy: даже плотной странице хватает ~4 размеров. → §3 `[консенсус]`
5. **Ряд размеров для интерфейса: 11, 12, 13, 14, 16, 18, 20, 24, 28, 32, 36, 40.** Всё, что крупнее 40 px,
   в приложении не нужно: display-роли — для маркетинга. → §1, §4 `[консенсус]`
6. **Не ставь 15, 17, 19, 21, 22, 23 px** без причины: соседние ступени должны различаться минимум на 2 px,
   иначе иерархия не читается, а кода становится больше. Исключение: Radix step 8 = 35 px, Carbon 42 px.
   → §4 `[консенсус]`
7. **Никогда не бери размер «на глаз» из соседнего компонента.** Один раз объяви токены `--font-size-*`
   и `--line-height-*` и используй только их. → §6 `[консенсус]`
8. **Минимум 12 px для любого читаемого текста, 11 px — только для служебных подписей** (Material label-small
   11 px, Polaris body-xs 11 px, Apple iOS минимум 11 pt, macOS минимум 10 pt). Ниже 11 px в вебе не опускайся.
   → §5.1 `[консенсус]`
9. **Задавай размеры в `rem`, а не в `px`**, чтобы работало системное укрупнение шрифта: так делают Atlassian
   («rem units… allow users to adjust the size of text»), Carbon, GOV.UK, Primer. Базу `html` не трогай
   (16 px), масштаб задавай токенами. → §6.2 `[консенсус]`
10. **Проверяй интерфейс при зуме 200 %** (WCAG 1.4.4): при `rem` вёрстка должна пережить это без потери
    контента. → §6.2 `[консенсус]`
11. **Fluid type (`clamp()`) в приложениях не нужен.** Его придумали для маркетинговых страниц. Carbon прямо
    делит: productive-заголовки fixed, expressive — fluid, и запрещает fluid внутри контейнеров. В админке
    используй 2 брейкпоинта и фиксированные размеры. → §9 `[система]`
12. **На мобильных меняются только заголовки, тело остаётся.** GOV.UK: body 19 px на обоих экранах, а
    heading-xl 48 → 32 px. Обратный случай тоже бывает: GOV.UK v6 специально *увеличил* мелкий текст на
    маленьких экранах. → §9.2 `[система]`
13. **Заголовок страницы в админке 20–24 px, в клиентском сервисе 24–32 px.** Не 36 и не 48: Butterick прямо
    называет удвоение кегля для заголовков «silly». → §3.3 `[консенсус]`
14. **Крупный заголовок не требует жирности, а жирный — крупности.** Carbon с heading-03 (20 px) переходит на
    вес 400, дальше 300. Если заголовок 32 px и вес 700 — он почти всегда слишком тяжёлый. → §3.3 `[система]`
15. **Модульная шкала с одним коэффициентом (1.125, 1.2, 1.25) для интерфейса плохо работает**: даёт дробные
    значения (14 → 15.75 → 17.72) и слишком частые ступени внизу. Все крупные системы используют ручной ряд
    целых чисел или формулу с округлением к чётным (Ant Design) или к 4 px. → §4.2 `[консенсус]`
16. **Round к 4 px, где можешь.** Material 3: все line-height кратны 4. Carbon: кратны 2, почти все 4.
    GOV.UK: кратны 5 (у них шаг сетки 5 px). Выбери одну кратность и держись её. → §4.3 `[система]`
17. **Между соседними ступенями сверху коэффициент 1.2–1.33, снизу 1.1–1.17.** У Tailwind: 12→14 = 1.167,
    16→18 = 1.125, 24→30 = 1.25, 36→48 = 1.33. Одинаковый коэффициент по всей шкале — признак теоретической,
    а не рабочей шкалы. → §4.2 `[консенсус]`
18. **Не копируй шкалу вместе со сменой гарнитуры.** При одном `font-size` визуальный размер разных шрифтов
    отличается до 13 % (измеренный x-height: Source Sans 3 — 0.486 em, Inter — 0.546 em). После смены шрифта
    пересобери шкалу по x-height. → §10 `[исследование]`
19. **Если шкалу нужно вывести самому — бери формулу Ant Design:** размеры `base * e^(i/5)`, округлённые до
    чётных, интерлиньяж `(размер + 8) / размер`, то есть интерлиньяж в px = кегль + 8 px. Для базы 14 это
    12/20, 14/22, 16/24, 20/28, 24/32, 30/38, 38/46. → §4.4 `[система]`
20. **Одна шкала — один продукт.** Если в приложении есть и «плотная» таблица, и «спокойная» страница
    настроек, не заводи две шкалы: заведи один набор ролей и два набора отступов (см. `03-spacing-sizing/`).
    → §3.4 `[мнение]`
21. **Книги (Refactoring UI, Practical UI) дают правила без чисел, дизайн-системы дают числа без объяснений.**
    Сопоставление тех и других — в §11; пресеты §7 и §8 собраны именно из этой связки. → §11 `[мнение]`
22. **Практики в докладах сходятся на ещё более жёстком ограничении, чем системы**: «трёх кеглей достаточно
    для 99 % приложений» (Sajid `[V05]`), «три размера шрифта на макет» (Бирман `[V14]`). Это не противоречие:
    они считают размеры, системы перечисляют роли. → §4.5 `[спорно]`
23. **У дашборда кегли мельче и шаги шкалы плотнее, чем у лендинга** `[V09]`. → §4.5 `[мнение]`

## 2. База 14 против 16: кто и почему

### 2.1. Аргументы за 14 px

- **Carbon говорит прямо**: «The productive type set uses a base type size of 14px, while the expressive type
  set uses a base type size of 16px» `[S2]`. Productive — это продукт, где «users benefit from a more condensed
  treatment of content to maintain focus on tasks»; expressive — редакционные и маркетинговые страницы.
- **Fluent 2** для веба даёт Body 1 = 14/20 px `[S3]`; 16 px там уже Subtitle 2.
- **Ant Design 5**: `fontSize: 14` в seed-токенах, вся шкала выводится из этого числа `[S35]`.
- **Atlassian**: `font.body` (default) = 14/20 px, 16 px — это `font.body.large` «для длинных текстов,
  например блогов» `[S10]`.
- **Material 3**: `body-medium` (14/20) — основной размер текста компонентов, `body-large` (16/24) — для
  длинного чтения `[S5]`.
- **Primer** описывает `sm` (14 px) как «Default body text size for UI», а `md` (16 px) как «Large body text
  and small titles» `[S7]`.
- **Polaris идёт дальше всех: `body-md` = 13 px** `[S6]`. Это база админки Shopify.
- **Apple macOS**: системный Body = 13 pt, дефолтный размер платформы 13 pt, минимум 10 pt `[S4]`. Десктопное
  приложение на macOS плотнее веба по умолчанию.
- Практический аргумент: в таблице на 12 колонок каждый лишний пиксель кегля даёт ~8 % ширины строки
  (измерено: средняя ширина строчной латиницы 0.50–0.55 em, см. §10).

### 2.2. Аргументы за 16 px

- **Material 3** `body-large` 16/24 — рекомендованный размер для основного чтения `[S5]`.
- **Radix Themes**: `--default-font-size: var(--font-size-3)` = 16 px, `--default-line-height: 1.5` `[S18]`.
- **Mantine**: `fontSizes.md = 16` — дефолт компонентов `[S37]`.
- **Untitled UI**: «Most modern UI and web design uses a base font size of 16px» `[S32]`.
- **GOV.UK идёт ещё дальше: база 19 px / 25 px** `[S8]`, обоснована исследованиями доступности; на маленьких
  экранах шкалу в v6.0.0 специально увеличили.
- **Butterick**: тело в вебе 15–25 px `[S26]`. 14 px по его меркам — уже мелко.
- **Erik Kennedy**: «interaction-heavy» страницы 14–20 px, «text-heavy» 18–24 px `[S12]`.
- **Зум полей на iOS**: любое поле ввода с `font-size < 16px` вызывает автозум Safari `[S12]`. Если тело 16 px,
  проблема не возникает нигде.
- Доступность: чем крупнее база, тем меньше людей с возрастной дальнозоркостью будут ломать вёрстку зумом.

### 2.3. Решающее правило

> Разрешение противоречия [C4]: правило подтверждено измерением (14 px у 14 продуктов из 24); второй по частоте вариант — 12 px как база плотных списков (GitHub, GitLab), а не 16; 16 у Schoger [V03 B] относится к клиентскому продукту. См. `../CONTRADICTIONS.md`.

| тип продукта | база | обоснование |
|---|---|---|
| Админка, бэк-офис, CRM, биллинг, аналитика с таблицами | **14 px** | Carbon productive, Fluent web, Ant Design, Atlassian `[консенсус]` |
| Сверхплотная админка с 10+ колонками (Shopify-класс) | **13 px** | Polaris `body-md` `[система]`, только с высоким x-height (Inter, Golos Text) |
| Личный кабинет, SaaS с формами и карточками, сервис самообслуживания | **16 px** | Material, Radix, Mantine, Untitled UI `[консенсус]` |
| Госуслуги, сервис для широкой и пожилой аудитории | **16–19 px** | GOV.UK `[исследование]` |
| Мобильная версия любого из перечисленного | **16 px минимум для полей** | автозум iOS `[консенсус]` |

**Антиправило**: не делай базу 15 px «как компромисс». Ни одна система такого не делает; 15 px попадает мимо
всех отлаженных пар размер/интерлиньяж и мимо кратности 4.

## 3. Роли: сколько их и как раскладывать

### 3.1. Минимальный набор ролей приложения

| роль | что это | типичный размер (база 14) | типичный размер (база 16) |
|---|---|---|---|
| `caption` | мета, таймстемпы, «показано 1–20 из 340» | 11–12 px | 12 px |
| `helper` | подсказка под полем, текст ошибки | 12 px | 14 px |
| `label` | подпись поля, заголовок колонки, бейдж | 12–14 px / 500 | 14 px / 500 |
| `body` | основной текст, ячейки таблиц, значения полей | 14 px | 16 px |
| `body-strong` | выделенное значение, имя объекта в строке | 14 px / 600 | 16 px / 600 |
| `button` | текст кнопок и пунктов меню | 14 px / 500 | 14–16 px / 500 |
| `subtitle` | заголовок карточки, группы полей, модалки | 14–16 px / 600 | 18 px / 500–600 |
| `section` | заголовок секции страницы | 16–18 px / 600 | 20 px / 600 |
| `page-title` | H1 страницы | 20–24 px / 600 | 24–32 px / 600 |
| `metric` | KPI-число на дашборде | 28 px / 600 | 32 px / 600 |
| `code` | моноширинный: id, ключи, фрагменты кода | 12 px | 14 px |

Одиннадцать ролей на **семь размеров** (11/12/14/16/20/24/28 или 12/14/16/18/20/24/32).

### 3.2. Почему ролей больше, чем размеров

Роль = размер + интерлиньяж + вес + трекинг + назначение. Carbon эксплуатирует это буквально: `body-01`
(14/20/400) и `heading-01` (14/20/600) отличаются только весом, `body-compact-01` (14/18) и `body-01` (14/20) —
только интерлиньяжем `[S2]`. Атлассиан так же: `font.heading.xsmall` = 14/20/Bold против `font.body` =
14/20/Regular `[S10]`.

**Правило**: новую роль заводи, только если она отличается хотя бы двумя параметрами или имеет отдельное
назначение, которое агент сможет назвать словом. Иначе это дубль.

### 3.3. Заголовки: где остановиться

- Butterick: «Also silly is the web's tradition of enormous point sizes for headings. This habit started with
  the default formatting of `<h1>` tags… which is about 200 % of the default point size of body text. There is
  no typographic universe in which you need to double the point size to achieve emphasis» `[S26]` `[мнение]`.
- Carbon: с `heading-03` (20 px) вес падает до 400, с `heading-06` (42 px) — до 300 `[S2]`. Крупный размер сам
  по себе даёт иерархию, добавлять к нему жирность — перебор.
- Atlassian: XXL (32) и XL (28) «suitable for brand and marketing content»; **для заголовков страниц
  приложения рекомендованы XL и L (28 и 24 px)**, M (20 px) — для крупных компонентов вроде модалок `[S10]`.
- Material 3: `title-large` 22/28 при весе 400 — это заголовок верхней панели, `headline-*` уже 24–32 px `[S5]`.

Итоговая таблица «где заголовок страницы»:

| контекст | размер | вес | системы, подтверждающие |
|---|---|---|---|
| админка, страница списка/таблицы | 20 px / 28 px | 600 | Carbon heading-03, Fluent Subtitle 1, Ant H4, Radix 5 |
| админка, страница объекта или дашборд | 24 px / 32 px | 600 | Fluent Title 3, Material headline-small, Polaris heading-xl, Ant H3 |
| клиентский сервис, обычная страница | 24 px / 32 px | 600 | те же |
| клиентский сервис, главная кабинета | 32 px / 40 px | 600 | Material headline-large, Fluent Title 1, Atlassian XXL |
| маркетинг (вне рамок этой базы) | 40–60 px | 600–700 | Fluent Large Title, Radix 9, GOV.UK 48 |

### 3.4. Не заводи вторую шкалу под плотность

Radix Themes решает вопрос плотности множителем `--scaling`, который умножает сразу все размеры и отступы
`[S18]`; Carbon решает его двумя *наборами токенов* с одинаковым ритмом `[S2]`. Обе стратегии дешевле, чем
две независимые шкалы. Для генератора проще первая: одна шкала + множитель 0.9 / 1.0 / 1.1.

### 4.2. Модульная шкала против ручного ряда

Модульная шкала — это `размер(n) = база × k^n`. Популярные k: 1.125 (major second), 1.2 (minor third),
1.25 (major third), 1.333 (perfect fourth).

Что получается при базе 16 и k = 1.25: 16 → 20 → 25 → 31.25 → 39.06 → 48.83. Дробные значения приходится
округлять, и «чистота» пропорции теряется сразу.

Что реально делают системы:

| система | одинаковый ли коэффициент | комментарий |
|---|---|---|
| Material 3 | нет | 11/12/14/16/22/24/28/32/36/45/57; коэффициенты 1.09…1.27 |
| Carbon | нет, но по формуле | шаг растёт ступенями: +2, +2, +2, +2, +4, +4, +4, +4, +6… |
| Tailwind | нет | 1.167 → 1.143 → 1.125 → 1.111 → 1.2 → 1.25 → 1.2 → 1.333 |
| Ant Design | **да, e^(1/5) ≈ 1.2214**, но с округлением до чётных | единственная система с честной геометрической шкалой |
| Radix | нет | 12/14/16/18/20/24/28/35/60 |
| Polaris | нет | 11/12/13/14/20/24/30/36 |

Вывод `[консенсус]`: **для интерфейса ручной ряд целых чисел лучше модульной шкалы.** Причины: нужен контроль
над мелким концом (11–16 px, где ступени должны быть ровно по 1–2 px), нужна кратность сетке, нужны целые
значения для `line-height`.

Модульная шкала полезна как *стартовая точка*: сгенерировать ряд с k = 1.2, округлить к ближайшему чётному,
а внизу вручную добавить 11, 12, 13, 14.

### 4.3. Кратность и вертикальная сетка

| система | кратность line-height | шаг шкалы отступов |
|---|---|---|
| Material 3 | 4 px (все без исключения) | 4 px |
| Carbon | 2 px (почти все 4) | 8 px, с половинками |
| Atlassian | 4 px | 4 px |
| Radix Themes | 2 px (16/18/20/22/24/26/28/30/36/40/60) | 4 px |
| Tailwind | 4 px | 4 px |
| GOV.UK | **5 px** | 5 px |
| Ant Design | line-height = кегль + 8 px, в px не всегда кратно 4 (22, 38, 46, 54, 76) | 8 px |

**Правило для генератора**: выбери 4 px и округляй все вычисленные line-height к ближайшим 4 px. Исключение
только для 14 px в плотных таблицах: там допустим 18 px (кратен 2), как у Carbon `body-compact-01`.

### 4.4. Формула, если шкалу нужно вывести с нуля

Самая простая исполнимая формула — из Ant Design `[S35]`:

```
размер(i) = round_even( база × e^(i/5) ),  i = −1, 0, 1, 2, …
line-height(px) = размер + 8
```

Проверка на базе 14: 12, 14, 16, 20, 24, 30, 38 — совпадает с реальными токенами Ant Design.
Проверка на базе 16: 14, 16, 18, 22, 28, 34, 42.

Правило `line-height = кегль + 8 px` даёт: 12 → 20 (1.67), 14 → 22 (1.57), 16 → 24 (1.5), 20 → 28 (1.4),
24 → 32 (1.33), 32 → 40 (1.25), 40 → 48 (1.2). Это **автоматически убывающий относительный интерлиньяж**,
ровно то, чего требуют Material 3, Carbon, Radix, Untitled UI и Butterick.

Ограничение: для текстов длиннее 4 строк при 14 px формула даёт 22 px (1.57), это немного просторнее, чем
Carbon (20 px) и Material (20 px). Для плотных таблиц используй `кегль + 6 px` (14 → 20), для длинного
чтения `кегль + 8 px`.

### 4.5. Что советуют практики в докладах: «три кегля» против 15 ролей

> Разрешение противоречия [C6]: практики считают несущие кегли, системы — роли; норма генератора 6–8 кеглей на экране (медиана практики 6), из них три несут 77 % текста. См. `../CONTRADICTIONS.md`.

`[V05]`, `[V02]`, `[V14]`, `[V09]` — дайджесты в `../91-videos/digests/`.

**Sajid, «The 80 % of UI Design — Typography» (2024, 354 тыс. просмотров)** `[V05]`:
- «**Трёх кеглей достаточно** для 99 % приложений». Доказательство на экране: в интерфейсе YouTube почти весь
  текст — **14 px**, кроме заголовка ролика и названия канала `[07:08]`, `[08:08]`.
- Схема построения: взять базу **14 или 16 px**, regular, самый светлый цвет текстовой шкалы; пытаться сделать
  весь интерфейс этой базой; когда без разницы в кегле не обойтись — **шаг ±2 px**; записать в глобальные
  переменные `[08:08]`.
- Показаны два антипримера: длинная модульная шкала («не стоит делать такую») и шкала из двух значений
  («такая тоже не поможет») `[08:08]`.
- Кегли задавать в `rem` ради пользовательской настройки размера `[09:10]`.
- «Code for document hierarchy, but style for visual hierarchy»: не каждый `<h1>` — самый крупный текст на
  экране `[10:13]`.
- Если крупный жирный текст «бьёт по глазам», **снижай вес, а не кегль** `[10:13]`.

**Steve Schoger (Laracon 2018)** `[V02 15:12]`: шкала кеглей — классическая типографская из полиграфии с двумя
поправками: **20 px вместо 21** («странно иметь одно нечётное число в середине ряда ровных») и добавленный
**30 px** между 24 и 36; выше 36 — кратно 12. Оговорка автора: «я не строг к этому, размеры в итоге выбираются
глазом, но шкала — безопасная отправная точка».

**Илья Бирман** `[V14]`: разбор студенческой работы, где в верхней части экрана насчитано **16 текстовых
стилей**, ещё не дойдя до меню. Норма, которую он ставит: **три размера шрифта**, один способ выделить плашку,
один стиль иконок, одна толщина линии на весь макет `[13:19]`.

**Kole Jain (дашборды и «AI slop»)** `[V09]`: у дашборда «типографическая шкала состоит из **мелких кеглей с
небольшими шагами**», в отличие от лендинга, и сетка соблюдается строже.

**Как это соотносится с системами.** «Три кегля» — не противоречие моим 6–7 размерам, а другой способ считать:
Sajid говорит о *размерах*, системы перечисляют *роли*. В пресете §7 действительно три кегля несут почти весь
текст (12, 14, 16 px), а 20, 24 и 28 px встречаются по одному разу на экран. Противоречие возникает только с
Material 3 (11 размеров) и Carbon (9 размеров), и оно объясняется масштабом: системе нужны роли на все
продукты компании, одному приложению — нет. `[спорно]`

Общее у всех четверых практиков и у всех систем: **шкала задаётся один раз и в переменных, кегль не
подбирается у каждого компонента заново**.

### 5.2. Поля ввода и автозум iOS

Safari на iOS зумит страницу при фокусе на поле с `font-size < 16px`, обрезая правую часть поля `[S12]`
`[консенсус]`.

```css
/* админка с базой 14 px */
:root { --font-size-body: 0.875rem; }        /* 14 px */
input, textarea, select { font-size: var(--font-size-body); }

@media (max-width: 768px) {
  input, textarea, select { font-size: 1rem; }  /* 16 px, отключает автозум */
}
```

Альтернатива (жёстче, но проще): база 16 px во всём клиентском сервисе — тогда проблема не возникает нигде.

### 5.3. Масштабирование и `rem`

- WCAG 1.4.4 Resize Text: текст должен масштабироваться до 200 % без потери контента и функциональности.
- WCAG 1.4.12 Text Spacing: интерфейс не должен ломаться, если пользователь выставит `line-height: 1.5`,
  отступ между абзацами `2em`, межсловный интервал `0.16em`, межбуквенный `0.12em` `[S23]`.
- Atlassian формулирует причину перехода на rem: «rem are relative units that adjust according to the root
  element (html) size. Using rem units allow users to adjust the size of text depending on their needs» `[S10]`.
- GOV.UK отдаёт CSS в относительных единицах, а px в документации приводит «so it's easier to understand» `[S8]`.

**Правило**: `font-size` и `line-height` (если задан в единицах) — в `rem`; отступы могут быть в `px` или
`rem` (см. `03-spacing-sizing/`); базовый `html { font-size }` не переопределяй.

Перевод px → rem при базе 16: 11 = 0.6875rem, 12 = 0.75rem, 13 = 0.8125rem, 14 = 0.875rem, 16 = 1rem,
18 = 1.125rem, 20 = 1.25rem, 24 = 1.5rem, 28 = 1.75rem, 32 = 2rem, 36 = 2.25rem, 40 = 2.5rem.

```css
.text-body      { font: var(--fw-regular) var(--text-sm)/var(--lh-sm) var(--font-sans); letter-spacing: 0; }
.text-page-title{ font: var(--fw-semibold) var(--text-lg)/var(--lh-lg) var(--font-sans); letter-spacing: var(--tracking-tight); }
```

Предупреждение прямо из исходников Material 3 `[S5]`: составной токен `font` не умеет передавать трекинг,
поэтому `letter-spacing` всегда объявляется отдельным свойством.

### 6.2. px, rem, em

| единица | где | почему |
|---|---|---|
| `rem` | `font-size`, `line-height` при задании в единицах, `max-width` текстовых блоков | масштабируется с настройками браузера; так делают Atlassian, Carbon, GOV.UK, Primer, Tailwind, Mantine |
| `px` | толщины границ, иконки, точные позиции | не должно масштабироваться |
| `em` | `letter-spacing`, отступы внутри текстового блока | значение привязано к кеглю самого элемента |
| безразмерный | `line-height` там, где размер элемента может меняться | наследуется как множитель, а не как готовое значение |
| `ch` | `max-width` абзаца | прямо выражает длину строки в знаках (см. `03-leading-tracking-measure.md`) |

**Про округление**: если вычисленное значение даёт дробь (0.875rem × 1.4 = 1.225rem = 19.6 px), округляй
line-height до целого пикселя, а лучше до 4 px. Дробные line-height дают неровный вертикальный ритм и
полупиксельные границы у строк таблицы.

## 9. Адаптация к экрану и fluid type

### 9.1. Нужен ли `clamp()` в приложениях

Нет `[система]`, `[мнение]`. Аргументы:

- **Carbon разделяет прямо**: productive-заголовки fixed, «Product pages have a higher density of information
  housed inside containers for space efficiency, and in these situations fixed type styles are a must»;
  expressive-заголовки fluid, и про них сказано: «Do not use these styles inside a container» `[S2]`.
- Плавный размер ломает вертикальную сетку: если заголовок 24.3 px, его line-height 32.4 px, и отступы
  перестают быть кратны 4.
- В админке ширина контента редко меняется плавно: она скачкообразно зависит от ширины сайдбара и наличия
  правой панели.
- В таблицах и формах размер текста вообще не должен зависеть от ширины окна: иначе одна и та же колонка на
  двух мониторах выглядит по-разному.

Где `clamp()` уместен: страницы входа и регистрации, пустые состояния во весь экран, приветственные и
маркетинговые страницы внутри продукта, страницы ошибок 404/500. То есть там, где текста мало, а
композиция дисплейная.

### 9.2. Что менять на узких экранах

| что | как | источник |
|---|---|---|
| тело, лейблы, подсказки | **не менять** | GOV.UK: 19/25 на обоих экранах; Carbon productive fixed `[S8]`, `[S2]` |
| заголовок страницы | уменьшить на 1 ступень (24 → 20, 32 → 28) | GOV.UK: 48 → 32, 36 → 27, 24 → 21 `[S8]` |
| display-роли | уменьшить на 2 ступени (40 → 32, 60 → 40) | GOV.UK: 80 → 53 `[S8]` |
| поля ввода | увеличить до 16 px, если было меньше | автозум iOS `[S12]` |
| мелкий текст | **возможно, увеличить** | GOV.UK v6.0.0 «includes an updated type scale to increase the size of text on small screens, improving legibility and accessibility» `[S8]` |

Брейкпоинт для переключения шкалы: GOV.UK использует 640 px (tablet) `[S8]`. Одного брейкпоинта достаточно,
двух хватает с запасом: 640 px и 1024 px.

Пример на CSS-переменных (без `clamp()`, значения целые):

```css
:root { --text-page-title: 1.5rem; --lh-page-title: 2rem; }       /* 24/32 */
@media (max-width: 640px) {
  :root { --text-page-title: 1.25rem; --lh-page-title: 1.75rem; } /* 20/28 */
}
```

### 9.3. Dynamic Type и системное укрупнение

Apple переводит тело с 14 pt (xSmall) до 23 pt (xxxLarge) без учёта accessibility-размеров, то есть в
**1.64 раза** `[S4]`. На вебе аналог — системный масштаб и зум браузера. Отсюда практические требования:

- Не фиксируй высоту контейнеров под текст: используй `min-height` и `padding`.
- Не полагайся на то, что подпись поместится в одну строку.
- Apple: «Keep text truncation to a minimum as font size increases»; «Consider adjusting your layout at large
  font sizes… consider using a stacked layout where text appears above secondary items»; «Reduce the number of
  columns when the font size increases» `[S4]`.

## 10. Почему шкалу нельзя переносить между гарнитурами

Собственное измерение по файлам шрифтов (fontTools, TTF из Google Fonts, подмножество latin + cyrillic)
`[S24]`. Отношение x-height к кегельной площадке (em) определяет, насколько крупным *выглядит* текст при
одном и том же `font-size`:

| шрифт | x-height / em | визуальный размер при `font-size: 16px` |
|---|---|---|
| JetBrains Mono | 0.550 | 8.80 px |
| Inter, Inter Tight | 0.546 | 8.73 px |
| Manrope | 0.540 | 8.64 px |
| Noto Sans | 0.536 | 8.58 px |
| Open Sans | 0.535 | 8.56 px |
| Geist, Golos Text | 0.530 | 8.48 px |
| Roboto | 0.528 | 8.45 px |
| Fira Sans, Onest | 0.527 | 8.43 px |
| Montserrat | 0.525 | 8.40 px |
| Rubik | 0.520 | 8.32 px |
| Ubuntu Sans | 0.518 | 8.29 px |
| IBM Plex Sans | 0.516 | 8.26 px |
| PT Sans | 0.500 | 8.00 px |
| Commissioner | 0.496 | 7.94 px |
| Wix Madefor Text | 0.492 | 7.87 px |
| Nunito Sans, Source Sans 3 | 0.486 | 7.78 px |

Разброс **0.486–0.550, то есть 13 %**. Source Sans 3 при 16 px выглядит примерно как Inter при 14.2 px.

Butterick про то же `[S26]`: «Two fonts set at the same point size will appear to be different sizes if one
occupies less space on its em». Его метод подбора: набрать один и тот же блок обоими шрифтами и менять кегль
нового, пока строки не начнут ломаться в тех же местах.

**Практическое правило для агента** `[исследование]`:

```
новый_размер ≈ старый_размер × (x-height_старого / x-height_нового)
```

Пример: шкала настроена на Inter (0.546), меняем на IBM Plex Sans (0.516) → коэффициент 1.058, значит база
14 px превращается в 14.8 px, то есть **шкалу надо сдвинуть на ступень вверх**: 14 → 16 для тела, если
плотность позволяет; если не позволяет — оставить 14 и увеличить интерлиньяж на 2 px, компенсируя меньший
рост строчных большим воздухом.

Обратный случай: шкала на Source Sans 3 (0.486), меняем на Inter (0.546) → коэффициент 0.89, размеры можно
уменьшить: 16 → 14.2 ≈ 14 px.

В CSS есть готовый механизм: `font-size-adjust` (подгонка по x-height) и дескриптор `size-adjust`
в `@font-face` `[S27]`, но они применяются к подмене шрифта, а не к пересборке шкалы.

## 11. Refactoring UI и Practical UI: правила с объяснением «почему»

Две книги-справочника, на которые чаще всего опираются разработчики без дизайнерского образования. Обе платные,
полные тексты я не открывал: правила ниже взяты из открытых страниц книг (оглавление с названиями глав, образец
правила целиком) и из подробных конспектов читателей `[S31]`, `[S39]`, `[S40]`. Помечаю соответствующе.

### 11.1. Что говорит Refactoring UI (Adam Wathan, Steve Schoger)

Раздел «Designing Text» состоит из восьми глав; их названия сами по себе формулируют правила `[S39]`:
«Establish a type scale», «Use good fonts», «Keep your line length in check», «Baseline, not center»,
«Line-height is proportional», «Not every link needs a color», «Align with readability in mind»,
«Use letter-spacing effectively». Плюс раздел «Hierarchy is Everything» с главами «Size isn't everything»,
«De-emphasize to emphasize», «Labels are a last resort», «Balance weight and contrast»,
«Separate visual hierarchy from document hierarchy».

Содержание правил по конспекту `[S40]` `[мнение]`:

| правило | объяснение «почему» |
|---|---|
| **Заведи ограниченную типографическую шкалу, строгую модульную не используй** | шкала ускоряет решения и даёт консистентность; строгий коэффициент даёт дробные пиксели и слишком редкие ступени наверху |
| **Для интерфейса подбирай значения шкалы руками, а не формулой** | интерфейсу нужен контроль над мелким концом, где ступени по 1–2 px |
| **Единицы — `px` или `rem`, но не `em`** | `em` наследуется и «уплывает» от шкалы во вложенных элементах |
| **Шрифт с пятью и более весами, оптимизированный под читаемость** | много весов — признак проработанной гарнитуры; совпадает с критерием Untitled UI `[S32]` |
| **Если не уверен — бери системный стек** | приводится стек `-apple-system, Segoe UI, Roboto, Noto Sans, Ubuntu, Cantarell, Helvetica Neue` |
| **Длина строки 45–75 знаков (20–35 em)** | совпадает с Butterick `[S26]` и Baymard `[S23]` |
| **Выравнивай тексты разного кегля по базовой линии, а не по центру** | при выравнивании по центру разнокегельные надписи «плавают» |
| **Мелкому тексту — больший интерлиньяж, крупному — меньший** | то же правило обратной зависимости, что у Untitled UI `[S32]` и Ant Design `[S35]` |
| **Иерархию делай весом и цветом, а не только размером** | размеров в шкале мало, а вес и цвет бесплатны |
| **Ограничься 2–3 цветами и 2–3 весами** | больше — иерархия перестаёт читаться |
| **Понижай второстепенное вместо того, чтобы повышать главное** | «de-emphasize to emphasize» |
| **На цветном фоне не делай текст серым**: бери тот же тон с меньшей насыщенностью и светлотой | серый на цветном выглядит грязным |
| **Подписи — вспомогательный контент**: мельче, ниже контраст, легче вес; а лучше обойтись без них | «Labels are a last resort»; вместо «In stock: 12» писать «12 left in stock» |
| **Не давай HTML-семантике диктовать визуальный стиль** | `<h1>` не обязан быть самым крупным текстом на экране |
| **Заголовок приложения не должен быть огромным** | пример из конспекта `[S41]`: в Gmail `h1` не 72 px, «a giant h1 just takes up space»; совпадает с критикой Butterick `[S26]` |
| **Текст влево, числа в таблицах вправо; выключка по формату — только с переносами** | совпадает с Fluent 2 `[S3]` и Carbon `[S2]` |
| **Длинный текст не центрируй** | |
| **Заголовкам, набранным текстовой гарнитурой, трекинг поджимай; капсу — распускай** | совпадает с Radix `[S18]` и Apple `[S4]` |
| **Ссылки в интерфейсе не обязаны быть яркими** | в интерфейсе и так много интерактивного |

### 11.2. Что говорит Practical UI (Adham Dannaway)

Заявленный метод: «Use a system of logical guidelines, rather than just gut feeling… every design detail has a
logical purpose behind it» `[S31]`. Глава 5 целиком про типографику.

| правило | объяснение «почему» |
|---|---|
| **Длина строки 40–80 знаков с пробелами** (единственное правило, приведённое на сайте целиком) | «If lines are too long, it makes it harder for people to gauge where the line starts and ends. If lines are too short, your eyes get stressed from having to travel back too often.» |
| **Выбирай типографическую шкалу, а не отдельные кегли** | убирает произвольные решения |
| **Ограниченный набор отступов** (2 px, 4 px и кратные 8 px) | меньше решений, консистентнее результат |
| **Кнопка не меньше 48×48 px** | попадание указателем и пальцем |
| **Иерархию кнопок делай не только цветом** (заливка / обводка / без фона) | для пользователей с дальтонизмом |

В комплект книги входит Figma-стартер с токенами цвета, **сеткой 4 px** и типографическими стилями,
а также отдельный раздел «10 лучших бесплатных гарнитур для UI» `[S31]`.

### 11.3. Сравнение с Material 3 и Carbon

| вопрос | Refactoring UI `[S40]` | Practical UI `[S31]` | Material 3 `[S5]` | Carbon `[S2]` |
|---|---|---|---|---|
| как строится шкала | руками, ограниченный набор; строгие модульные шкалы отвергаются | «выбери шкалу» (в конспекте упоминается калькулятор модульных шкал) | ручной ряд 11/12/14/16/22/24/28/32/36/45/57 | формула `Xn = Xn−1 + {INT[(n−2)/4]+1} × 2`, y₀ = 12 |
| база | не задаётся | не задаётся (рекомендация 16 px в смежных материалах) | 14 px (`body-medium`) и 16 px (`body-large`) | **14 px productive, 16 px expressive** |
| единицы | `px` или `rem`, **не `em`** | — | `rem` в токенах | `rem` в токенах |
| число размеров | «ограниченный набор» | «шкала» | 11 размеров на 15 ролей | 9 размеров на 20+ ролей |
| длина строки | **45–75 знаков (20–35 em)** | **40–80 знаков** | не задаётся | не задаётся |
| интерлиньяж | мелкому больше, крупному меньше | — | 1.33–1.5 тело, 1.12–1.33 заголовки | 1.29–1.43 тело, 1.19–1.40 заголовки |
| веса | 2–3 веса, шрифт с 5+ весами | — | 400 / 500 / 700 | 300 / 400 / 600 |
| иерархия | вес и цвет, не только размер | — | вес 500 у label и title, цвет через роли `on-surface-variant` | цвет нейтральный в тексте, синий для ссылок |
| трекинг | поджимать заголовки, распускать капс | — | +0.5 px на 11–12 px, 0 на 22–36, −0.25 px на 57 | +0.32 px на 12 px, +0.16 на 14, 0 на 16+ |
| выравнивание | текст влево, числа вправо | — | не задаётся | body всегда влево |

**Где книги и системы расходятся**:
- Refactoring UI отвергает модульные шкалы, а Ant Design `[S35]` строит шкалу ровно по геометрической формуле
  `base × e^(i/5)`. Противоречие снимается тем, что Ant округляет результат до чётных целых — то есть на выходе
  всё равно получается «ручной» ряд. `[спорно]`
- Refactoring UI запрещает `em` для `font-size`, Radix Themes `[S18]` и Atlassian `[S10]` задают трекинг в `em`.
  Это не противоречие: запрет касается размера шрифта, а трекинг в `em` как раз и должен масштабироваться
  вместе с кеглем.
- Книги дают правила без чисел для базы и интерлиньяжа, системы дают числа без объяснений. Связка «правило +
  значение» получается только их сопоставлением, что и сделано в пресетах §7 и §8.

## Частые ошибки

### Общие

1. **Пятнадцать размеров вместо шести.** Признак: в CSS встречаются 13, 15, 17, 19, 21, 22, 23 px.
   Проверка: `grep -oE "font-size: *[0-9.]+(px|rem)" | sort -u | wc -l` должно дать ≤ 8.
2. **Размер подобран «на глаз» у каждого компонента.** Признак: заголовок карточки 15 px, а заголовок
   модалки 17 px, хотя роль одна.
3. **Заголовок страницы 36–48 px в админке.** Butterick: удвоение кегля ради акцента не нужно `[S26]`.
4. **`font-size` в `px` вместо `rem`.** Ломает системное укрупнение и зум 200 % (WCAG 1.4.4).
5. **`clamp()` на теле и лейблах приложения.** Ломает вертикальную сетку и делает одну и ту же таблицу
   разной на двух мониторах.
6. **Перенос шкалы при смене гарнитуры без пересчёта.** См. §10.
7. **База 12 px «чтобы влезло больше».** Ни одна система не опускает базу ниже 13 px; при 12 px на не-Retina
   мониторе текст теряет читаемость.
8. **Одинаковый интерлиньяж на всех размерах** (`line-height: 1.5` глобально). Заголовок 32 px получает
   48 px интерлиньяжа — визуально распадается на несвязанные строки.
9. **Поля ввода 14 px в мобильной версии.** Автозум iOS `[S12]`.
10. **Дробные line-height** (19.6 px, 22.4 px). Даёт неровный ритм и полупиксельные границы.

### Характерные для нейросетей

11. **Смешение шкал из разных систем в одном файле.** Модель «помнит» и Tailwind (12/14/16/18/20/24/30/36),
    и Material (11/12/14/16/22/24/28/32), и выдаёт гибрид, где рядом стоят 18 и 22 px без роли для каждого.
    Проверка: выпиши все размеры и назови роль каждого; если роли нет — размер лишний.
12. **Дефолты Tailwind как «дизайн».** `text-sm` для всего мелкого и `text-3xl` (30 px) для заголовка страницы
    админки — типичный генеративный след. 30 px для H1 админки велико: системы дают 20–24 px.
13. **Дефолты MUI без переопределения.** h1 96 px, кнопка UPPERCASE, вес 300 у заголовков — это Material 2
    `[S36]`, устаревшая на 2026 год картина.
14. **Копирование шкалы Material 3 в админку целиком**, включая роли display (36–57 px), которые в приложении
    не нужны.
15. **Каждая новая секция получает новый размер.** У модели нет памяти о том, что 20 px уже занято ролью
    «заголовок секции», и появляется 21 px «заголовок подсекции».
16. **`text-base` (16 px) в ячейках таблицы на 12 колонок.** Таблица не помещается, начинается горизонтальный
    скролл; в плотной админке ячейка — 14 px, а то и 13 px.

## Чек-лист

1. Сколько уникальных значений `font-size` в проекте? Должно быть **≤ 8** (в админке 6–7). Да / нет.
2. Каждому размеру соответствует названная роль? Размеров без роли быть не должно. Да / нет.
3. База: 14 px для админки, 16 px для клиентского сервиса, 13 px только для сверхплотных таблиц. Да / нет.
4. Ни один читаемый текст не мельче 12 px; 11 px только для подписей в 1–3 слова. Да / нет.
5. Все `font-size` заданы в `rem`? `html { font-size }` не переопределён? Да / нет.
6. Все `line-height` — целые пиксели, кратные 4 (допустимо 2 для 14/18)? Да / нет.
7. Относительный интерлиньяж убывает с ростом кегля: 12 px → 1.33, 16 px → 1.5, 24 px → 1.33, 32 px → 1.25?
   (Обрати внимание: у самых мелких он снова растёт.) Да / нет.
8. Поля ввода на ширинах < 768 px имеют `font-size: 16px`? Да / нет.
9. Интерфейс не ломается при зуме 200 % (WCAG 1.4.4)? Да / нет.
10. Интерфейс не ломается при `line-height: 1.5`, `word-spacing: 0.16em`, `letter-spacing: 0.12em`,
    отступе абзаца `2em` (WCAG 1.4.12)? Да / нет.
11. Заголовок страницы: 20–24 px в админке, 24–32 px в кабинете. Не 36 и не 48. Да / нет.
12. `clamp()` не применяется к телу, лейблам и ячейкам таблиц? Да / нет.
13. На узких экранах уменьшены только заголовки, тело не тронуто? Да / нет.
14. При смене гарнитуры шкала пересчитана по x-height (§10)? Да / нет.
15. Есть ли в шкале «дырка» для роли, которая точно понадобится (заголовок карточки между 14 и 20 px)?
    Да / нет.
16. Заголовки не тяжелее 600 при размере ≥ 24 px? Да / нет.

## Открытые вопросы и противоречия

1. **13 против 14 px в плотных админках.** Polaris `[S6]` ставит базу 13 px, Carbon `[S2]` и Ant `[S35]` —
   14 px, Apple macOS `[S4]` — 13 pt. Прямого сравнительного исследования читаемости 13 против 14 px на
   мониторах 2024–2026 я не нашёл. Вероятно, 13 px безопасен только при x-height ≥ 0.53 em (Inter, которым
   и набран Polaris).
2. **GOV.UK 19 px против всех остальных.** База 19 px обоснована собственным исследованием доступности
   (designnotes.blog.gov.uk, декабрь 2022), которое я не открывал (страница не проверялась). Насколько этот
   результат переносится на коммерческие сервисы — неизвестно.
3. **Mantine против всех по интерлиньяжу**: у неё он растёт с кеглем (1.4 → 1.65 на 12 → 20 px) `[S37]`,
   у остальных падает. Возможное объяснение: весь диапазон Mantine — «тело», а не заголовки; но явного
   объяснения в исходниках и документации нет. `[спорно]`
4. **Нужна ли отдельная роль для чисел.** Atlassian `[S10]` её выделяет (`metric`), остальные системы — нет.
   Данных о влиянии на скорость считывания дашборда не нашёл.
5. **Material 3 в документации против исходников.** Значения я брал из исходников `material-web` v0.192;
   страница m3.material.io не отдаётся скриптом (SPA), сверить с документацией не удалось. Вероятность
   расхождения низкая, но она есть.
6. **Tailwind v4 убрал конкретные шрифты из `--font-sans`** `[S9]`, оставив `ui-sans-serif, system-ui`.
   Насколько это меняет вид интерфейса на старых Windows, я не проверял.
7. **Нет данных о читаемости при базе 14 против 16 для пользователей 50+.** Все найденные рекомендации по
   крупному тексту для широкой аудитории опираются на GOV.UK и общие соображения, а не на сравнительный
   эксперимент.
