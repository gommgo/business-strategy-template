# job-graph-deep-dive

Сборка **графа работ** выбранного сегмента по методологии **Advanced
JTBD** (Иван Замесин): что за работы выполняет сегмент, как они связаны
(вверх через «чтобы», по последовательности, вниз шагами), что он
**нанимает** на эти работы, где **трётся** с решениями и какие **механики
ценности** из графа вырастают в возможности продукта. Канон —
`docs/ajtbd/README.md`. Слой **discovery** между «кто этот бизнес»
(`docs/business/`) и «какую проблему решаем» (реестр проблем
`docs/business/business-problem.md`, SWOT `docs/swot/`, Карта гипотез
`docs/hypothesis-map/`).

Скилл владеет файлами `docs/ajtbd/{job.md, job-graph.md, solution.md,
segment-problem.md}`. **Сегментами он не владеет** — их заводит и скорит
`/segment-deep-dive`; здесь сегмент только **выбирается** как контур
работы. Без сегмента граф не собрать: работа всегда тегирована сегментом,
граф собирается вокруг его целевой Core-работы.

Скилл ведёт сеанс через 9 фаз, структурированные вопросы
(`AskUserQuestion`), фиксирует контекст в `state/`, **не выдумывает
работы, решения, трения и мотивации**. Методология графа — `references/methodology.md`;
многоволновой рой — `references/research-waves.md`.

## Разведочная рамка (держать в голове всю сессию)

Слой ищет **known-unknown** — работы и решения сегмента, которых мы ещё
не знаем. Поэтому здесь нет метрик-обязательств (это слой
`business-problem`) — здесь **карта спроса**. Три сущности **не
смешиваются**: работа ⟂ решение ⟂ проблема. Проблема **никогда не
существует сама по себе** — она следствие конкретного `solution`,
нанятого на конкретную `job`; поэтому `segment-problem` всегда висит на
паре. Работа доказывается **прошлым поведением** (затраты времени / денег
/ энергии), не мнением и не гипотетикой. Скилл **никогда** не выдаёт
гипотетику за работу.

## Точки входа

| вызов | поведение |
|---|---|
| `/job-graph-deep-dive` | пикер сегмента → сводка по фазам выбранного + следующий шаг |
| `/job-graph-deep-dive <segment-slug>` | работать по графу этого сегмента: сводка фаз + следующий шаг |
| `/job-graph-deep-dive <segment-slug> <kind>` | завести новую сущность типа kind в этом сегменте (режим A) |
| `/job-graph-deep-dive <segment-slug> <kind>:<slug>` | углубить существующую запись (режим C) |
| `/job-graph-deep-dive <segment-slug> <slug>` | найти slug; одиночный → C; конфликт kind → переспросить |
| `/job-graph-deep-dive <segment-slug> <свободный текст / транскрипт>` | сырьё → разбор (режим B) |
| `/job-graph-deep-dive <segment-slug> --phase <name>` | принудительно работать в фазе |

`kind` ∈ {`job`, `job-graph`, `solution`, `segment-problem`}.

`phase` ∈ {`intake`, `target-job`, `graph-up`, `graph-sequence`,
`graph-down`, `solutions`, `frictions`, `value`, `cohesion`}.

**Сегмент обязателен.** Если `<segment-slug>` не задан — пикер по
`docs/ajtbd/segment.md` (`AskUserQuestion`: по опции на каждый сегмент,
показывая Score и статус). Если сегментов нет вовсе — сказать, что граф
работ собирается внутри сегмента, и предложить запустить
`/segment-deep-dive`. Скилл сам его **не вызывает**.

## Что делать сразу при запуске

1. Прочитать `docs/ajtbd/README.md` — освежить канон 5 kind (своими
   владеет 4), методологические инварианты и anti-patterns слоя.
2. Определить сегмент (из args или пикер по `segment.md`). Весь сеанс
   работает **внутри одного сегмента**.
3. Прочитать `references/phases.md` — карту 9 фаз.
4. Открыть `references/methodology.md` (граф работ: уровни, типы, два
   навигационных вопроса, непрерывность «чтобы», CPR, 11 механик).
   Разобранные графы целиком — `references/examples.md` (последовательный,
   частотный, иерархия уровней).
5. При многоволновом research — `references/research-waves.md`.
6. Если args (после сегмента) пустые — **сводка по фазам сегмента** (см.
   ниже) + `AskUserQuestion` с выбором следующего шага.
7. Если args указывают на сущность — определить kind и режим (A/B/C) по
   `references/workflow-patterns.md`.
8. Если `--phase` — открыть карту фазы.

## Сводка состояния (без kind-args, сегмент выбран)

Скилл всегда даёт аналитику **карту, где он в графе работ сегмента**, не
просто список draft-записей.

1. Прочитать `segment.md` (выбранную строку — `core-jobs`, `big-job`,
   `success-criteria`, `score`), затем `job.md`, `job-graph.md`,
   `solution.md`, `segment-problem.md` — отфильтровать записи **этого
   сегмента** (по `job.segment` / `solution.by-segment` /
   `segment-problem.segment` / `job-graph.segment`).
2. Прочитать свою ветку `../entrypoint/state/ajtbd/` (+ read-only
   остальное дерево — см. «Единый контекст») — собрать
   `**blocker**`-вопросы.
3. Определить текущую фазу по дереву (на записях этого сегмента):
   - нет ни одной `job`, нет сырья → `intake`;
   - есть сырьё / нет целевой Core-работы → `target-job`;
   - целевая есть, цепочка вверх до Big не дотянута → `graph-up`;
   - вверх есть, не размечены предыдущие/последовательные → `graph-sequence`;
   - последовательность есть, нет низкоуровневых шагов → `graph-down`;
   - граф есть, у целевой нет ни одного `solution` → `solutions`;
   - решения есть, не сняты трения → `frictions`;
   - трения есть, нет `job-graph` (CPR + типы + механики) → `value`;
   - всё заполнено, но есть draft/blocker → `cohesion`.
4. Вывести карту фаз (как в `references/phases.md`, раздел «Сводка фаз»)
   по выбранному сегменту.
5. Через `AskUserQuestion` предложить: продолжить текущую фазу /
   перепрыгнуть фазу / разобрать сырьё / запустить рой research /
   переключиться на другой сегмент.

## Фазы проработки

Скилл **проактивно** ведёт через 9 фаз **в пределах одного сегмента**.
Полная карта — `references/phases.md`. По порядку методологии (целевая →
вверх → последовательность → вниз → решения → трения → синтез):

| фаза | цель | артефакты |
|---|---|---|
| `intake` | приём сырья (материалы / транскрипты JTBD-интервью / находки роя), выбор/подтверждение сегмента | — (state) |
| `target-job` | целевая Core-работа сегмента (точка входа в граф) | `job.md` |
| `graph-up` | работы выше уровнем через «чтобы» до Big Job (непрерывность: `so-that` нижней = `want` верхней) | `job.md` |
| `graph-sequence` | предыдущие / последовательные работы (= маркетинговая воронка) | `job.md` |
| `graph-down` | низкоуровневые работы-шаги (важны для UX, не для сегментации) | `job.md` |
| `solutions` | что сегмент «нанимает» на работы (satisfaction · price · price-value-fit · maps-to) | `solution.md` |
| `frictions` | трения сегмента с решениями (сила 1–10, драйверы, барьеры) — всегда на паре solution+job | `segment-problem.md` |
| `value` | синтез `job-graph`: целевая, CPR без разрывов, разметка типов, кандидаты-механики из 11 | `job-graph.md` |
| `cohesion` | целостность графа сегмента + повышение draft → stable + передача наверх/вниз | все |

**Целевая Core-работа — рекомендуемый, но не единственный вход.** Если
бизнес/research принёс яркое **решение** (что нанимают) или **трение** —
можно стартовать с него и навигацией восстановить работу: «на какую
работу это нанято / какой результат недостижим?» (см. `references/phases.md`,
«Перепрыгивание»). Строится **набегающей волной** (неточно → уточняем),
не водопадом.

## Три режима

См. `references/workflow-patterns.md`. Зеркалит project-deep-dive:

- **A. Новая сущность.** Args = `<segment> <kind>` или
  `<segment> <kind>:<новый-slug>`. Батч `AskUserQuestion` по
  `Критерии <kind>` из md-файла; опции — anti-patterns из `Что <kind>
  НЕ`; значения (тексты работ/решений/трений) — через Other. Каждая
  сущность наследует **выбранный сегмент** (`job.segment` /
  `solution.by-segment` / `segment-problem.segment` / `job-graph.segment`).
- **B. Сырьё.** Args = транскрипт JTBD-интервью / заметки / находки роя.
  Извлечь кандидатов по типам (job / solution / segment-problem),
  показать план, по подтверждению завести stub-записи, углубить через C.
  Авто-залив **запрещён** — только через `AskUserQuestion`.
- **C. Углубление.** Args = `<kind>:<slug>`. Точечные вопросы по дырам и
  методологическим подозрениям (непрерывность «чтобы», тип работы,
  ложная работа, решение без оценок, трение без пары); чек-лист
  `draft → stable`.

## Стиль вопросов

См. `references/workflow-patterns.md`. Краткий канон:

- **Всегда через `AskUserQuestion`**, до 4 вопросов в раунде.
- **Опции** — для: anti-patterns из `Что <kind> НЕ`; enum
  (`job.level`, `job.type`, `solution.kind`); выбора существующего slug
  соседа (родительская работа, предыдущая работа, целевая работа,
  решение, конкурент/офер для `maps-to`); навигационных развилок
  (вверх / последовательность / вниз); проверочного вопроса на ложную
  работу; теста-критерия (✅/❌).
- **Свободная форма (Other)** — для значений: `name`, `description`,
  шаблон работы `when`/`want`/`success-criteria`/`so-that`, описание
  решения, описание трения, `drivers`/`barriers`, `motivation`-сигналы,
  оценки (satisfaction / price-value-fit / strength), частоты.
- **Никогда** не выдумывать работы, решения, трения и мотивации.
  Anti-patterns как опции — да; сами тексты — нет. Это **священная
  экспертиза** сегмента (см. `CLAUDE.md` §3); добывается из research /
  транскриптов / аналитика, не из головы модели.

## Многоволновой рой research

См. `references/research-waves.md`. Запускается **только** по решению
аналитика (или по его «да» на предложение скилла). Рой 5–10 агентов ×
2–5 волн; каждая волна **засевается находками прошлой** (новые работы →
новые угла поиска решений и трений); стоп — когда **две волны подряд** не
приносят новых работ/решений. Кандидаты складываются в
`../entrypoint/state/ajtbd/research/<тема>-<UTC-ts>.md`; promotion в
`docs/ajtbd/` — **только через `AskUserQuestion`**. Авто-залив из веба запрещён. Рой — через
инструмент **Agent** (параллельные подагенты в одном message-блоке), не
через Workflow.

## Память (state)

Заметки лежат в общей ветке AJTBD единого дерева оркестратора —
`../entrypoint/state/ajtbd/` (делит её с `segment-deep-dive`): per-kind
заметки `<kind>/<slug>.md` (kind ∈ {job, job-graph, solution,
segment-problem}), находки роя — `research/<тема>-<ts>.md`. Транскрипты,
разбираемые в intake, приходят от `/jtbd-interview` в ветку
`../entrypoint/state/ajtbd/_interview/` — скилл их read-only читает.
Формат и жизненный цикл заметки (три опциональные секции
`## Открытые вопросы` с опц. `**blocker**`, `## Доменные решения`,
`## Что копать дальше`; forward-only; пустые удаляются) — единый канон
`../entrypoint/references/state-model.md`.

**Единый контекст (read-only):** чтобы картина была общей, скилл
подтягивает всё дерево `../entrypoint/state/` (соседние слои business/
swot/hypothesis-map и проектные ветки) плюс клиентский дом
`../entrypoint-for-business/state/`. **Своя ветка `ajtbd/` — rw; чужие
ветки и клиентский дом — read-only**, в них никто не пишет. При чтении
клиентского дома маркер `**жду аналитика**` — blocker-кандидат
(эквивалент `**blocker**`).

## Методологические инварианты (семантические, не slug-grep)

Связи **не валидируются slug-целостностью** — они семантические, как в
business-problem и project. Инварианты считаются **в пределах одного
сегмента**. Их ловит рой `/ajtbd-audit`. Скилл **в процессе** держит их в
голове и поднимает при углублении и cohesion:

- **Сегмент держится на бандле.** У сегмента ровно одна `big-job` и ≥1
  `core-job` (живут в `segment.md`; здесь — следим, что граф к ним
  сходится).
- **Непрерывность «чтобы».** `job.so-that` нижней работы = `want`
  верхней (как «5 почему»); цепочка `core`/`low` ведёт вверх до
  `big`-работы сегмента.
- **Работа тегирована сегментом.** Каждая `job` несёт `segment`.
- **У целевой работы есть решение.** У `core`-работы ≥1 `solution` с
  оценками `satisfaction` и `price-value-fit` — иначе Score сегмента не
  вычислить.
- **Проблема — следствие решения.** `segment-problem` висит на реальной
  паре `solution` + `job`. Трение без решения запрещено.
- **Граф размечен по типам.** В `job-graph` у работ проставлен `type`;
  CPR без разрывов.
- **Ложные работы помечены.** Подозрительная работа проверена вопросом
  «двигает ли она к ценности?» и при необходимости помечена
  `type: ложная`.

Сам скилл — **не аудитор**; в конце сессии предложит `/ajtbd-audit`
(инварианты слоя роем) или `/cross-audit` (стыки с соседями).

## Контракт `draft → stable`

См. `references/draft-stable.md`. Чек-лист после каждой правки:
обязательные слоты заполнены · `Критерии <kind>` подтверждены аналитиком
· `Что <kind> НЕ` не нарушены · `Тест-критерий` ✅ · нет `**blocker**` в
state · факт прослежен до research или транскрипта (не гипотетика). Все
✅ → предложить повышение через `AskUserQuestion`. Скилл **не повышает
сам**.

## Stub-сущности

Если копаемая сущность ссылается на ещё не существующий slug (работа
упомянула родительскую работу, которой нет; решение нанято на работу, не
заведённую): завести stub-запись (`slug + name + segment + status=draft`,
прочее `—`), записать state-заметку «заведён как stub в контексте
`<откуда>` — докопать в фазе `<phase>`», вернуться к исходной.

**Тяга гипотез из сегмента.** Сегмент в `segment.md` несёт `core-jobs` и
`big-job` — это slug-рефы на работы. Часто их завели как **stub** ещё в
`/segment-deep-dive` (имя есть, шаблон работы пуст). При входе в
`target-job` / `graph-up` скилл подтягивает эти stub-работы из выбранного
сегмента и **доводит их до полноценных** `job` (шаблон когда→хочу→чтобы,
уровень, тип, непрерывность). Если работы-stub из сегмента ещё нет в
`job.md` — завести её и связать.

## Удаление сущности (каскад)

1. Прочитать все 4 файла + ветку `../entrypoint/state/ajtbd/` — найти
   семантические упоминания slug: `job.parent-job`, `job.prev-jobs`,
   `solution.hired-for`,
   `segment-problem.solution`/`job`, `job-graph.target-job`/`cpr`,
   `segment.core-jobs`/`big-job` (в `segment.md` — **не правим сами**,
   подсвечиваем для `/segment-deep-dive`).
2. Показать каскад. Через `AskUserQuestion` по каждому месту: «заменить
   на другой slug» / «удалить упоминание» / «оставить».
3. Применить пакетом. Удалить запись из файла и
   `../entrypoint/state/ajtbd/<kind>/<slug>.md`.
4. Если удалена работа, на которой висели трения/решения — спросить, не
   удалить ли осиротевшие `solution` (без `hired-for`) и
   `segment-problem` (без пары). Если удалена единственная Core-работа
   сегмента — предупредить: граф остался без целевой; предложить
   пересмотр через `/segment-deep-dive`.

## Завершение сессии

1. Перечислить затронутые сущности (заведены / углублены / удалены /
   повышены), по сегменту.
2. Перечислить нерешённые `**blocker**`-вопросы.
3. Назвать текущую фазу и логичный следующий шаг.
4. Через `AskUserQuestion` предложить:
   - `/ajtbd-audit` (инварианты методологии слоя роем);
   - `/cross-audit` (стыки с business / swot / hypothesis-map / projects);
   - `/jtbd-interview` (если работ/решений не хватает — добыть живым
     интервью; кладёт транскрипты + кандидатов в state → разбираем через
     intake, режим B);
   - `/business-deep-dive business-problem` (трения → проблема бизнеса в
     реестре) и `/swot-deep-dive` (трения → SWOT-факторы);
   - `/project-deep-dive` (механики ценности → `capability` продукта).

## Запреты

- Не редактировать таблицы вслепую — всегда сначала `Read`.
- Не работать без сегмента — граф собирается внутри сегмента.
- Не править `docs/ajtbd/segment.md` — он у `/segment-deep-dive`
  (подсвечивать нужное, не трогать).
- Не выдумывать работы, решения, трения, мотивации, оценки. Anti-patterns
  как опции — да; сами тексты — нет.
- Не выдавать **гипотетику** за работу — работа доказывается прошлым
  поведением (затраты времени/денег/энергии).
- Не путать `job` с фичей/решением, `segment-problem` (трение клиента) с
  `business/business-problem` (проблема бизнеса), `segment` (рынок) с
  `user` (пользователь продукта).
- Не оставлять `segment-problem` без пары `solution` + `job`.
- Не повышать `draft → stable` без явного подтверждения аналитика; не
  понижать сам.
- Не авто-заливать web-research или транскрипты в артефакты — promotion
  только через `AskUserQuestion`.
- Не аккумулировать историю в state — forward-only.
- Писать только в свою ветку `../entrypoint/state/ajtbd/`; чужие ветки
  дерева и клиентский дом `../entrypoint-for-business/state/` — read-only.
- Не пушить и не коммитить. Коммит/push — гейт аналитика.
- Не вызывать другие скилы — предложить аналитику запустить руками.
