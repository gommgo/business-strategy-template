# Многоволновой web-research через рой агентов

Способ наполнить граф работ сегмента находками о его работах, нанятых
решениях и трениях, когда аналитик не знает рынок наизусть. Воспроизводит
норматив полноты AJTBD: **итерации, пока два цикла подряд не приносят
новых работ**. **Никогда** не запускается автоматически — только по
решению аналитика (или по его «да» на предложение скилла).

## Чем отличается от одноволнового роя

Граф работ — **known-unknown**: мы не знаем заранее, какие работы и решения
есть у сегмента. Один заход роя их не вычерпывает. Поэтому здесь —
**волны**: каждая следующая **засевается находками прошлой** (новая работа
→ новые угла «какие решения нанимают на эту работу» и «где трутся»). Стоп —
по нормативу насыщения, а не по фиксированному числу заходов.

## Когда

| фаза | повод |
|---|---|
| `target-job` / `graph-up` / `graph-down` | найти, как реально звучат работы сегмента (отзывы, форумы, обзоры «как я выбирал/делал»). |
| `solutions` | вычерпать **все** нанятые решения на работы графа — включая DIY, субституты, бездействие, неожиданных конкурентов. |
| `frictions` | собрать трения с решениями (жалобы, «что бесит», «почему ушёл»), драйверы и барьеры перехода. |

> baseline-оценки удовлетворённости/цены берём из research как **сигнал**,
> уточняем интервью; не выдаём найденное за факт без подтверждения.

## Параметры запуска (один раунд = одна волна)

1. Аналитик попросил research, или скилл предложил после артефакта.
2. `AskUserQuestion`:
   - **Сколько углов в волне?** «5 — дефолт», «7 — шире», «10 — широкая
     разведка».
   - **Фокус волны** (Other) — одной фразой: на работы / на решения / на
     трения и под какой сегмент.
3. Скилл генерит N углов под тему и **сегмент** (см. шаблоны ниже).
4. Спавнит N агентов **параллельно** — все вызовы в **одном**
   message-блоке, через инструмент **Agent** (`subagent_type:
   general-purpose`, WebSearch/WebFetch). **Не** через Workflow.
5. Ждёт всех. Каждый возвращает структурированный markdown-отчёт.
6. Сводит волну в `state/research/<тема>-<UTC-ts>.md` с секциями
   `## <угол>` + финальной `## Кандидаты` по kind (job / solution /
   segment-problem).
7. **Засев следующей волны:** из находок этой волны выделить новые
   работы/решения, под них сгенерить новые угла → предложить аналитику
   запустить следующую волну.

## Критерий остановки (норматив насыщения)

Считаем **новые** работы/решения, появившиеся в волне (которых не было в
прошлых отчётах и в `docs/ajtbd/`).

- Волна дала **новые** работы/решения → засеять следующую их углами.
- **Две волны подряд** без новых работ/решений → **стоп**: граф по этому
  фокусу насыщен. Зафиксировать в state «насыщение по фокусу ⟨X⟩ —
  ⟨сколько⟩ волн».
- Жёсткий потолок — **5 волн** (защита от бесконечного копания); дальше —
  только по явному решению аналитика.
- Между волнами `AskUserQuestion`: «волна ⟨n⟩ дала ⟨k⟩ новых работ /
  ⟨m⟩ решений. Запустить следующую (засев: ⟨угла⟩) / остановиться /
  сменить фокус?».

## Шаблоны углов

**Работы (фазы target-job / graph / down):**
1. как сегмент описывает свою задачу своими словами (отзывы, форумы,
   Reddit/VC/профильные сообщества);
2. «как я выбирал / делал ⟨работа⟩» — пошаговые рассказы (что делали →
   = низкоуровневые работы);
3. «зачем мне это» — высокоуровневые мотивы (→ работы выше уровнем);
4. триггеры и контекст (когда возникает работа);
5. соседние/предыдущие работы в цепочке (= воронка перед целевой).

**Решения (фаза solutions):** + (6) прямые продукты-конкуренты; (7)
сервисы / «сделаю руками» (DIY); (8) субституты (решают потребность
иначе); (9) бездействие (почему ничего не делают); (10) неожиданные
решения из высокоуровневой работы.

**Трения (фаза frictions):** + жалобы и «что бесит» по конкретному
решению; «почему ушёл / не перешёл»; страхи и сомнения перед сменой
решения (барьеры); что удерживает на текущем (драйверы).

## Промпт для одного агента

```
Сегмент (из segment.md): <кто это, бандл работ, критерии успеха>
Тема волны: <фокус аналитика — работы / решения / трения>
Угол: <один из шаблонных или custom>
Слой: job / solution / segment-problem (укажи, что ищем)
Уже известно (засев из прошлых волн): <работы/решения, чтобы не дублировать>

Найди наблюдаемое из веба по этому углу. Ищи ДЕЙСТВИЯ и затраты
(время/деньги/энергия) — они доказывают работу, а не мнения и не
гипотетику. Для каждой находки:
- если работа (job): черновое название + шаблон «когда/хочу/чтобы», на
  каком уровне (big/core/low) кажется, чем доказана (какие затраты);
- если решение (solution): что нанимают, kind (product/service/diy/
  substitute/inaction), на какую работу, признаки удовлетворённости и
  цены, ссылка-источник;
- если трение (segment-problem): с каким решением на какой работе, сила
  негатива, драйверы (что держит) и барьеры (что мешает уйти);
- 2-3 источника (url) на каждую находку.

Не выдумывай. Пусто по углу → пустой список + одна фраза почему.
Наблюдаемое, не маркетинг. Ответ — markdown.
```

## Promotion в артефакты

Только через `AskUserQuestion`, по кандидату: «принять в `<kind>` как
`<slug>`» / «отбросить» / «доработать (Other)». До 4 в раунде. При
приёме работы — довести до шаблона когда→хочу→чтобы (если данных не
хватает — завести `draft` + `**blocker**` в state). Авто-залив
**запрещён**.

## Что НЕ делать

- ❌ Авто-вписывать в `docs/ajtbd/`. Promotion только через
  `AskUserQuestion`.
- ❌ Останавливаться на одной волне, если она дала новые работы — норматив
  насыщения требует продолжить.
- ❌ Терять отчёты — `state/research/<тема>-<ts>.md` остаётся по каждой
  волне.
- ❌ Выдавать найденную гипотетику за работу — работа доказывается
  действиями (затраты), не словами «хотел бы».
- ❌ Брать оценки satisfaction/price-value-fit из веба как факт —
  это сигнал, уточняется интервью.
- ❌ Запускать рой через Workflow — только параллельные подагенты (Agent)
  в одном message-блоке.
- ❌ Смешивать research с intake (материалами/транскриптами) в одном
  заходе.
