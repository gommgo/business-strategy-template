# Режим B: разбор сырья

«Сырьё» — любая входящая форма, по которой нужно понять, какие
сущности заводить:

- **картинка** (скриншот чужого бота-референса, переписка с ботом
  конкурента, мокап сообщения, фото эскиза сценария);
- **текст** (описание сценария бота словами «клиент жмёт /start, видит
  меню, выбирает услуги…», транскрипт интервью, заметки по итогам
  встречи);
- **URL** (бот конкурента `t.me/…`, статья с разбором бота, лендинг с
  описанием сценария);
- **комбинация** — типично: «вот скрины бота и описание, чего хотим».

Скилл переходит в режим B, когда:

- args содержат свободный текст без kind/slug-сигналов;
- в сообщении пользователя есть приложение (картинка или файл
  отдельным content-блоком);
- args начинаются с URL.

## Алгоритм разбора

### Шаг 1. Изучить материал

**Картинка**: посмотреть содержательно. Что за шаг бота — меню,
выбор из списка, ввод, подтверждение? Какие кнопки видны (подписи,
ряды, ссылки наружу)? Это ответ бота на действие или сообщение,
которое бот прислал первым? Есть ли пагинация, «Назад», deep-link?

**Текст**: прочитать. Выделить сущности, упомянутые явно («после
/start меню», «напоминание за час») и выводимые («раз выбор копится до
подтверждения — диалог с накоплением»). Глаголы участника — кандидаты
в виджеты; глагол-действие, дёргающее домен и стейт («отправить»,
«создать», «сохранить»), — кандидат в use-case бота; «бот присылает
сам» — кандидаты в notification.

**URL**: `WebFetch` — получить описание. В живой бот скилл не ходит;
если нужны скрины — попросить аналитика приложить.

### Шаг 2. Извлечь кандидатов

Применить фильтр по `Что <kind> НЕ` из канонов
`docs/projects/_template/telegram-bot-flow/_template/`. Кандидаты —
только то, что прошло фильтр.

| вижу в материале | kind-кандидат |
|---|---|
| завершённый сценарий из нескольких шагов («оформить заказ») | dialog (= фича) |
| один шаг: сообщение + кнопки/ввод | window |
| действие, оркеструющее вызов домена и стейт («отправить заказ», «сохранить выбор») | use-case (бота) — внутри фичи |
| `/start`, `/help`, deep-link из QR/рекламы/уведомления | command (корень) |
| сообщение, которое бот шлёт первым (напоминание, статус) | notification (корень) |
| серия сообщений как «один шаг» | НЕ window — несколько окон или пагинация |
| кнопка «Далее» внутри шага | НЕ command — виджет окна |
| «после нажатия бот отвечает…» | НЕ notification — следующее окно |
| «если доставка — спросить адрес» | НЕ логика окна — исход use-case бота (`when`), требование домену |
| вложенный сценарий внутри сценария | НЕ второй диалог в фиче — отдельная фича, вход `start:<feature>` |
| эмодзи-стиль, форматирование, «красивые карточки» | НЕ артефакт — облик, забота кода |

Заодно пометить, что из материала уезжает в **interface** (новые роли,
ситуации, блоки, атомы — если их там нет) и в **домены сервисов**
(`services/*/domains/` — операции и
события, на которые обопрутся action/trigger) — эти кандидаты скилл
**не заводит** (см. anti-patterns ниже).

### Шаг 3. Показать план

Через чат:

```
Из материала вижу:

фичи / dialog-кандидаты (фича = диалог):
  - booking — оформление заказа: услуги → гости → адрес → подтверждение
  - main-menu — корневое меню (root)

window-кандидаты (по фичам):
  - booking/menu — приветствие + кнопки разделов
  - booking/services — multiselect услуг + «Далее»/«Назад»
  - booking/confirm — сводка заказа + «Подтвердить»

use-case-кандидаты (бота, по фичам):
  - booking/submit-booking (op SubmitBooking) — собрать draft, дёрнуть
    домен, вернуть «нужен адрес»/«готово»

command-кандидаты (корень):
  - start-menu — /start → feature:main-menu, сброс стека

notification-кандидаты (корень):
  - order-confirmed — «бот пишет первым» при подтверждении; нужен
    триггер-событие домена и идемпотентность — уточним

Мимо слоя (предложу соседям):
  - interface: блока под «сводку заказа» не вижу в block.md
  - домены сервисов: операции SetServices/SubmitOrder — требования
    (попадут в Dependencies bot UC submit-booking)

Картинку → сохранить как
  features/booking/assets/services/competitor-bot.png? (y/n)

Так?
```

### Шаг 4. Подтвердить через AskUserQuestion

Раунд до 4 вопросов:

- «Кандидаты dialog/window/use-case/command/notification корректные?»
  (опции: «да, все правильные» / «убрать какие-то» (Other) / «добавить
  какие-то» (Other));
- «Сохранить картинку как референс?» (по политике ассетов SKILL.md);
- «Какую сущность углубить первой?» (опции: по одной на каждый
  кандидат + «другую» (Other));
- (если URL) «WebFetch посмотреть страницу для дополнительного
  контекста?» (опции: «да» / «нет, в материале хватает»).

### Шаг 5. Завести stub'ы

Для каждого подтверждённого кандидата (внутри фичи —
`docs/projects/<project-slug>/telegram-bot-flow/<surface>/features/<feature>/`):

1. dialog — файл `dialog.md` фичи (заведение заводит и папку фичи) с
   минимальным frontmatter (`slug`, `name`, `description`,
   `status: draft`; `states-group` скилл предлагает сразу, с контролем
   одной строкой; обязательные поля без значения — `—` или пустые
   массивы). window — секция `## <slug>` в `window.md` фичи со
   `status: draft` и минимально осмысленными значениями всех мета-полей
   (у окна `—` в мета-полях не допускается; дыры — вопросами в
   state-заметке); use-case
   бота — секция `## <slug>` в `use-case.md` фичи (`name`/`operation` +
   `status: draft` + пустые/`—` H3-секции). command/notification —
   строка таблицы реестра корня с `—` в незаполненных колонках
   (notification без `idempotency` не записывается даже как stub —
   спросить ключ или оставить кандидата в state-заметке).
2. Тело — пустое или скелет из материала (`message.text` — только
   если дословно есть в материале; виджеты — только подтверждённые).
3. State-заметка с секцией `## Открытые вопросы`:
   - «извлечено из сырья — уточнить <конкретно что>»;
   - `**blocker**`'ы по ключевым неопределённостям (например,
     «`**blocker**`: не определён interface-block окна»).

### Шаг 6. Углубить выбранную через C

Точечные раунды по `field-checklists.md`.

## Естественный порядок углубления

dialog → window → use-case → command → notification. Объясняется так:

- window живёт секцией в `window.md` фичи — без диалога (фичи) окно не
  заводится;
- use-case бота заводится, **когда окну нужен action** к домену — он
  следует за окном (action виджета ссылается на секцию `use-case.md`
  той же фичи), а его `Dependencies` уже мостятся к домену;
- command ссылается на фичу (`starts` → `feature:<slug>`) — фича должна
  существовать хотя бы stub'ом;
- notification ссылается на команду-deep-link или фичу (`action`) и
  доменное событие — её удобно добивать последней, когда входы готовы.

Параллельно при углублении окон копится зеркало
`dialog.transitions` — после прохода по окнам фичи вернуться в её диалог
и подтвердить сводный граф (тупики, путь к `done`); `when` переходов
сверяются с исходами use-case'ов бота фичи.

## Anti-patterns режима B

- ❌ Заводить кандидата, который не подтверждён аналитиком —
  кандидаты до подтверждения это **гипотезы**, не сущности.
- ❌ Угадывать тексты сообщений, подписи кнопок, условия переходов,
  ключи идемпотентности по скриншоту — только структуру. Текст с
  чужого скрина — референс, не контент нашего бота.
- ❌ «Это, наверное, корневой диалог (`launch-mode: root`)» — нет,
  спросить.
- ❌ Сохранять картинку без согласия (политика ассетов SKILL.md).
- ❌ Лезть в web без явной просьбы.
- ❌ Заводить interface-сущности или доменные артефакты из сырья — это
  домены `interface-deep-dive` и `domain-deep-dive`. Если из материала
  видны новые блоки/ситуации/атомы или операции/события — предложить
  аналитику запустить соответствующий скилл, доменные требования
  зафиксировать в state (см. `domain-bridge.md`). Use-case **бота** —
  наша сущность (секция в `use-case.md` фичи), его заводим; доменную
  операцию, которую он дёргает, — нет (она в `Dependencies` как
  семантический реф / требование).
- ❌ Цеплять доменную операцию из сырья прямо на `widget.action` (с
  точкой) — действие окна ссылается на use-case бота фичи (без точки),
  а доменная операция живёт в его `Dependencies`.
- ❌ Переносить «как у конкурента» в инварианты: если чужой бот шлёт
  ленту сообщений — наш канон всё равно «одно окно = одно сообщение».
