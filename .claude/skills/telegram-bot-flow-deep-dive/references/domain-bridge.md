# Мост к domains

Бот — **фронтенд в Telegram**: доменных решений в слое нет, есть рёбра
к ним. Вся бизнес-логика живёт в `docs/projects/<project-slug>/domains/`
(по bounded-context, surface-агностично). Скилл читает домены
read-only: предлагает существующие операции и события как опции, но
**не пишет** в `domains/` — это домен `domain-deep-dive`.

Рёбра **семантические** (slug-валидации нет; несостыковки сводит
`/cross-audit`):

| telegram-bot-flow | → ссылается на → | domains |
|---|---|---|
| `widget.action` (`use-case:<ctx>.<Operation>`) | M:1 | `domains/<ctx>/use-cases/<Operation>.md` |
| `getter.*.source` (`use-case:…`) | M:1 | `domains/<ctx>/use-cases/<Operation>.md` |
| `notification.trigger` (`event:<ctx>.<Event>`) | M:1 | `domains/<ctx>/events/<Event>.md` |
| условие перехода `when` | — | исход use-case (его `## Outputs` / `## Errors`) |

## Заведение action / getter.source

Когда виджету нужен `action` или ключу getter'а — `source` с чтением
из домена:

1. Просканировать `docs/projects/<project-slug>/domains/*/use-cases/`
   (исключая `_shared` и `_templates`).
2. Раунд `AskUserQuestion`: опции — существующие операции в форме
   `use-case:<ctx>.<Operation>` (короткое «что делает» из файла —
   деталь опции; релевантные по смыслу окна — первыми), плюс:
   - `—` — чистая навигация (для `action`) / другой `source`
     (`dialog-data`, `start-data`, `const`) — для getter'а;
   - «нужна новая операция» (Other — аналитик называет смысл,
     **не** имя в формате; имя `<ctx>.<Operation>` предлагает скилл
     одной строкой для контроля).
3. По «нужна новая» — см. «Когда домена нет» ниже.

`action` дёргает домен; «кнопка сама сохраняет в базу» — anti-pattern:
действие либо ссылается на use-case, либо отсутствует.

## Условие перехода `when`

`when` — **исход use-case**, не правило, придуманное окном. Алгоритм:

1. Если операция `action` существует в доменах — прочитать её
   `## Outputs` и `## Errors`, показать аналитику как контекст:
   «операция возвращает такие исходы — какие куда маршрутизируем?»
2. Формулировка `when` — слова аналитика (Other), на русском, в духе
   «use-case вернул „нужен адрес"». Скилл не сочиняет исходы.
3. Если в исходах операции нет нужной ветки — это сигнал домену:
   зафиксировать в state-заметке окна (`## Доменные решения`)
   требование «use-case `<ctx>.<Operation>` должен различать исход
   <какой> — для перехода <куда>» и предложить
   `/domain-deep-dive <project-slug> <ctx>`.

Бизнес-правило в `when` («если сумма > 1000 — скидка») не
записывается: скилл объясняет, что ветвление решает домен, и
переформулирует вопрос через исход операции.

## Заведение notification.trigger

1. Просканировать `docs/projects/<project-slug>/domains/*/events/`.
2. Раунд `AskUserQuestion`: опции — существующие события
   `event:<ctx>.<Event>` (короткий смысл — деталь) + `schedule:`
   (Other — расписание по-русски: «за час до брони») +
   `integration:<slug>` (опции из `integration.md` проекта) + «нужно
   новое событие» (Other).
3. Для выбранного `event:` — прочитать его `## Payload` и сверить
   плейсхолдеры `content`: каждый `{…}` должен быть обеспечен полем
   payload. Дыры показать аналитику (поправить текст / расширить
   требование к событию).

## Когда домена нет (или нет нужной части)

Слой `domains/` опционален — его отсутствие **не блокирует** работу и
stable. Связь семантическая: имя фиксируется как **требование**.

1. В артефакте реф пишется как есть:
   `action: use-case:booking.SetGuests`,
   `trigger: event:booking.OrderConfirmed`.
2. В state-заметке сущности (`## Доменные решения`) — строка-требование:
   - «нужен `use-case:<ctx>.<Operation>` — <что должен делать, какие
     исходы различать> (для <виджет/ключ getter>)»;
   - «нужен `event:<ctx>.<Event>` — payload минимум: <поля под
     плейсхолдеры content>».
3. Имя `<ctx>` — если контексты уже есть, выбрать из существующих;
   если доменов нет вовсе, аналитик называет смысл контекста, скилл
   предлагает slug одной строкой.
4. Предложить аналитику (не запускать самому):
   `/domain-deep-dive <project-slug> <ctx>` — довести требование до
   спроектированного use-case / event.
5. В завершении сессии — перечислить накопленные доменные требования
   отдельным списком.

## Что НЕ делать

- Не писать в `docs/projects/<project-slug>/domains/` — ни файлов, ни
  правок. Только read-only чтение и предложение `domain-deep-dive`.
- Не выдумывать исходы, inputs и payload'ы операций/событий — читать
  из файлов домена; чего нет — спросить аналитика и зафиксировать как
  требование.
- Не блокировать stable отсутствующим доменом — требование в state
  достаточно; сверку ведёт `/cross-audit`.
- Не превращать `when` в бизнес-правило и не позволять `action`
  «работать без домена» молча.
- Не придумывать имена `<ctx>.<Operation>` за спиной аналитика — имя
  предлагается одной строкой для контроля, смысл называет аналитик.
