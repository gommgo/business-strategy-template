# Мост к domains

Бот — **фронтенд в Telegram**: доменных решений в слое нет, есть рёбра
к ним. Но окно касается домена **не напрямую**, а через **use-case
бота** фичи — мост двухуровневый:

1. **Окно → use-case бота** — внутри слоя, **в пределах фичи**,
   **slug-валидируемо**: `widget.action` и `getter.*.source` ссылаются на
   секцию `## <uc-slug>` в `use-case.md` той же фичи (`use-case:<uc-slug>`,
   без точки).
2. **Use-case бота → домен** — **семантически** (slug-валидации нет): bot
   UC в своих `### Dependencies` ссылается на доменный use-case
   (`use-case:<ctx>.<Operation>`, с точкой), а уведомление — на доменное
   событие. Несостыковки сводит `/cross-audit`.

Точка различает уровни: реф **без точки** — use-case бота, **с точкой** —
доменный. Бизнес-логики (валидация по правилу, инвариант, policy) в слое
нет: bot UC её **вызывает** у домена, не повторяет — он лишь оркеструет
(собрать ввод → дёрнуть доменный use-case → разобрать исход → апдейт
`dialog-data` → вернуть исход окну). Скилл читает домены read-only:
предлагает существующие операции и события как опции, но **не пишет** в
`domains/` — это домен `domain-deep-dive`.

| ребро | уровень | → ссылается на → | как валидируется |
|---|---|---|---|
| `widget.action` (`use-case:<uc-slug>`) | окно → bot UC | секция `## <uc-slug>` в `use-case.md` **той же фичи** | slug, в пределах фичи |
| `getter.*.source` (`use-case:<uc-slug>`) | окно → bot UC | секция `## <uc-slug>` в `use-case.md` **той же фичи** | slug, в пределах фичи |
| `use-case.Dependencies` (`use-case:<ctx>.<Operation>`) | bot UC → домен | `domains/<ctx>/use-cases/<Operation>.md` | семантически |
| `notification.trigger` (`event:<ctx>.<Event>`) | реестр корня → домен | `domains/<ctx>/events/<Event>.md` | семантически |
| условие перехода `when` | — | исход bot UC (его `### Outputs` / `### Errors`) | смысловое |

## Заведение action / getter.source (окно → bot UC)

Когда виджету окна нужен `action` или ключу getter'а — `source` через
оркестрацию (а не «чистая навигация» / `dialog-data` / `start-data` /
`const`):

1. Прочитать `use-case.md` **текущей фичи** — собрать список её use-case'ов
   бота.
2. Раунд `AskUserQuestion`: опции —
   - существующие use-case бота фичи в форме `use-case:<uc-slug>`
     (короткое «что оркеструет» — деталь опции; релевантные по смыслу
     окна — первыми);
   - `—` — чистая навигация (для `action`) / другой `source`
     (`dialog-data`, `start-data`, `const`) — для getter'а;
   - «нужен новый bot UC» (Other — аналитик называет смысл действия,
     **не** имя в формате; `slug` + `operation` (PascalCase) предлагает
     скилл одной строкой для контроля).
3. По «нужен новый bot UC» — завести секцию `## <uc-slug>` в `use-case.md`
   фичи (мета-блок + H3-секции), затем внутри неё выбрать доменный
   use-case для `### Dependencies` (см. «Заведение Dependencies bot UC»).

`action` дёргает домен **через bot UC**; «кнопка сама сохраняет в базу» —
anti-pattern: действие либо ссылается на use-case бота, либо отсутствует.
Доменного use-case на самом виджете быть не может — он живёт в
`Dependencies` bot UC.

## Заведение Dependencies bot UC (bot UC → домен)

Внутри секции use-case бота, при заполнении `### Dependencies`:

1. Просканировать `docs/projects/<project-slug>/domains/*/use-cases/`
   (исключая `_shared` и `_templates`).
2. Раунд `AskUserQuestion`: опции — существующие доменные операции в форме
   `use-case:<ctx>.<Operation>` (короткое «что делает» из файла — деталь
   опции; релевантные по смыслу bot UC — первыми), плюс «нужна новая
   операция» (Other — аналитик называет смысл, **не** имя в формате; имя
   `<ctx>.<Operation>` предлагает скилл одной строкой для контроля).
3. По «нужна новая» — см. «Когда домена нет» ниже.
4. В `### Dependencies` рядом с доменными use-case фиксируются строки
   стейта `dialog-data:<key>` (read | write) — что bot UC читает/пишет в
   контракт накопления (JSON-примитивы).

## Условие перехода `when`

`when` — **исход use-case бота**, не правило, придуманное окном. Алгоритм:

1. Если use-case бота `action` существует — прочитать его `### Outputs` и
   `### Errors`, показать аналитику как контекст: «bot UC возвращает такие
   исходы — какие куда маршрутизируем?»
2. Формулировка `when` — слова аналитика (Other), на русском, в духе
   «use-case бота вернул „нужен адрес"». Скилл не сочиняет исходы.
3. Если в исходах bot UC нет нужной ветки — проследить её к домену:
   зафиксировать в state-заметке bot UC (`## Доменные решения`)
   требование «доменный use-case `<ctx>.<Operation>` должен различать
   исход <какой> — для перехода <куда>» и предложить
   `/domain-deep-dive <project-slug> <ctx>`.

Бизнес-правило в `when` («если сумма > 1000 — скидка») не записывается:
скилл объясняет, что ветвление решает домен, и переформулирует вопрос
через исход bot UC (а тот — через исход доменного use-case).

## Заведение notification.trigger

1. Просканировать `docs/projects/<project-slug>/domains/*/events/`.
2. Раунд `AskUserQuestion`: опции — существующие события
   `event:<ctx>.<Event>` (короткий смысл — деталь) + `schedule:`
   (Other — расписание по-русски: «за час до брони») +
   `integration:<slug>` (опции из `integration.md` проекта) + «нужно
   новое событие» (Other).
3. Для выбранного `event:` — прочитать его `## Payload` и сверить
   плейсхолдеры `content`: каждый `{…}` должен быть обеспечен полем
   payload. Дыры показать аналитику (поправить текст / расширить
   требование к событию).

Уведомление триггерится доменным событием **напрямую** (это реестр корня,
вне фич) — оно не проходит через use-case бота.

## Когда домена нет (или нет нужной части)

Слой `domains/` опционален — его отсутствие **не блокирует** работу и
stable. Доменная связь семантическая: имя фиксируется как **требование**
на уровне bot UC (или реестра уведомлений).

1. В артефакте реф пишется как есть:
   - в `### Dependencies` bot UC: `use-case:booking.SetGuests`;
   - в `notification.trigger`: `event:booking.OrderConfirmed`.
2. В state-заметке сущности (`## Доменные решения`) — строка-требование:
   - для bot UC: «нужен `use-case:<ctx>.<Operation>` — <что должен делать,
     какие исходы различать> (для bot UC <slug>)»;
   - для уведомления: «нужен `event:<ctx>.<Event>` — payload минимум:
     <поля под плейсхолдеры content>».
3. Имя `<ctx>` — если контексты уже есть, выбрать из существующих;
   если доменов нет вовсе, аналитик называет смысл контекста, скилл
   предлагает slug одной строкой.
4. Предложить аналитику (не запускать самому):
   `/domain-deep-dive <project-slug> <ctx>` — довести требование до
   спроектированного use-case / event.
5. В завершении сессии — перечислить накопленные доменные требования
   отдельным списком.

## Что НЕ делать

- Не давать `widget.action` ссылаться на доменный use-case напрямую (с
  точкой) — окно ходит в домен **только через use-case бота фичи** (без
  точки); доменный use-case живёт в `Dependencies` bot UC.
- Не писать в `docs/projects/<project-slug>/domains/` — ни файлов, ни
  правок. Только read-only чтение и предложение `domain-deep-dive`.
- Не выдумывать исходы, inputs и payload'ы операций/событий — читать
  из файлов домена; чего нет — спросить аналитика и зафиксировать как
  требование.
- Не блокировать stable отсутствующим доменом — требование в state
  достаточно; сверку ведёт `/cross-audit`.
- Не превращать `when` или `Steps` bot UC в бизнес-правило и не позволять
  `action` «работать без домена» молча.
- Не придумывать имена `<ctx>.<Operation>` и `operation` bot UC за спиной
  аналитика — имя предлагается одной строкой для контроля, смысл называет
  аналитик.
