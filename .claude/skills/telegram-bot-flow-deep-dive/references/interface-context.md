# Синтез из interface и зеркала

Слой telegram-bot-flow **синтезируется** из UX-слоя **той же
поверхности** того же проекта —
`docs/projects/<project-slug>/interface/<surface>/` (канон interface
един для всех типов поверхностей; bot-поверхность получает те же 7
файлов). Скилл читает interface read-only: предлагает кандидатов
оттуда, держит зеркала сходящимися, но **не правит** — это домен
`interface-deep-dive`.

## Поверхность и фича — структурные оси

Поверхность не хранится отдельным полем артефакта — она **задана
папкой** `telegram-bot-flow/<surface>/`. Внутри неё фичевые kind
(`dialog`/`window`/`use-case`) **заданы папкой фичи**
`features/<feature>/` — окно и use-case бота уже принадлежат своему
диалогу структурно. Скилл **не задаёт** вопрос «на какой поверхности
живёт диалог»: ответ — `<surface>`, выбранная при запуске; принадлежность
окна/use-case фиче — её папка. Ссылки на сущности другой поверхности или
другой фичи запрещены (изоляция двухуровневая).

## Маппинг: что чем проявляется

| interface | → | telegram-bot-flow | связь |
|---|---|---|---|
| `zone` (смысловая область UX) | → | `feature` / `dialog` | смысловая рифма (зона ≈ фича = её диалог); семантическая, сверяет `/cross-audit` |
| `block` (блок взаимодействия) | → | `window` | авторское ребро `window.interface-block` (M:1) |
| `ux-substrate` (атом) | → | виджет / текст окна | зеркало `window.ux-substrates` + покрытие виджетами |
| `situation` (ситуация) | → | `window.situations` | M:N |
| `who` (роль) | → | `dialog.who` / `window.who` / `use-case.who` / `command.who` / `notification.to` | M:N |
| `data-items` (словарь данных) | → | `getter.*.data` (`data:<slug>`) | M:1, surface-локально |

`use-case` бота в этой таблице **нет**: он не синтезируется напрямую из
interface, а **выводится из потребности окна в действии** — когда виджету
нужен `action` к домену (`widget.action`) или getter'у нужен источник из
домена (`getter.*.source`). interface даёт атом `команда`/`ввод`/`выбор`,
а решение «этому действию нужен оркестратор бота» рождается на шаге
заведения виджета (см. `domain-bridge.md` «Окно → bot UC»), не из зоны
или блока.

## Соответствие атомов виджетам

`ux-substrate.type` подсказывает состав `widgets` и текста окна;
соответствие проверяется аудитом:

| атом (`type`) | роль | проявление в окне |
|---|---|---|
| `команда` | участник запускает действие | `button` (с `action` и/или `transition`) |
| `ввод` | свободные данные сообщением | `text-input` (`value-type`, `validation`) |
| `выбор` | вариант(ы) из предложенных | `select` / `multiselect` / `calendar` |
| `инфо` | система предъявляет значение | плейсхолдер `{…}` в `message.text` |
| `список` | система предъявляет коллекцию | `items` виджета либо `{…}`-сводка в тексте |

Выбор между `select` / `multiselect` / `calendar` — по смыслу атома
(одиночный/множественный выбор, дата); скилл предлагает опции, решает
аналитик. Ссылка наружу без обработчика — `url` (атому обычно
соответствует `команда`-навигация наружу).

## Кандидаты на синтез

### Заведение dialog / фичи (режим A)

Заведение диалога заводит и **папку фичи** `features/<feature>/` (фича =
диалог), куда лягут его окна (`window.md`) и use-case'ы бота
(`use-case.md`).

1. Прочитать `…/interface/<surface>/zone.md`. Раунд `AskUserQuestion`:
   «Какая зона — источник этой фичи (её диалога)?»
   - по опции на зону (имя; slug — деталь), приоритет — зоны, ещё не
     проявленные фичами;
   - «без зоны-источника» (Other) — допустимо, связь семантическая.
2. Если зона выбрана — её блоки (`zone` у строк `block.md`) становятся
   очередью кандидатов-окон; `windows` диалога собирается из них
   (каждый блок → окно-секция в `window.md` фичи через режим A в window).
3. Решение «фича ← зона <slug>» — в state-заметку диалога
   (`## Доменные решения`).

### Заведение window (режим A)

Окно заводится секцией `## <slug>` в `window.md` своей фичи.

1. `window.interface-block` — обязательное ребро. Опции — блоки из
   `…/interface/<surface>/block.md` (приоритет — блоки зоны-источника
   фичи-владельца и блоки, ещё не воплощённые окнами) + «нужен новый»
   (Other → предложить запустить
   `interface-deep-dive <project-slug> <surface> block:<slug>`,
   `**blocker**` в state до его появления).
2. `ux-substrates` — автоматически предложить весь набор
   `ux-substrates` выбранного блока (зеркало по умолчанию).
3. Состав `widgets` и плейсхолдеров — скилл раскладывает выбранные
   атомы по таблице соответствия и предлагает скелет («атом
   `svc-select` (`выбор`) → multiselect; атом `svc-next` (`команда`) →
   button»). Тексты `label` и `message.text` — формулировки аналитика
   (Other), скелет — лишь структура.
4. Если у виджета-`команды` есть действие к домену — это сигнал завести
   **use-case бота** фичи и сослаться на него в `widget.action` (см.
   `domain-bridge.md`); use-case не выводится из атома, а рождается из
   потребности действия.
5. `situations` — предложить ситуации выбранных субстратов
   (`ux-substrate.situation`) по умолчанию.

### Сводка (без args)

В сводке состояния поверхности скилл показывает **дыры синтеза**:

- зоны interface без фичи-проявления;
- блоки interface, не указанные ни в одном `window.interface-block`;
- атомы `команда`-навигации наружу без проявления (кандидаты в `url`);
- виджеты-`команды` с действием к домену, но без `action` на use-case
  бота фичи.

Это кандидаты на углубление, не автоматические заведения: каждое —
через подтверждение аналитика.

## Зеркало `ux-substrates`

Живёт в двух слоях одной поверхности: `block.ux-substrates`
(interface) и `window.ux-substrates` (мета-блок секции окна в
`window.md`). Канонического источника нет. Политика при расхождении —
SKILL.md «Зеркала interface ↔ telegram-bot-flow»: показать diff, спросить
источник правды, interface руками не править.

Дополнительная проверка покрытия (внутри окна): каждый объявленный
`ux-substrate` представлен в теле — виджетом или плейсхолдером (по
таблице соответствия). Атом без проявления — вопрос аналитику; виджет
без атома — подозрение «окно делает больше, чем анализировал interface»
(предложить дополнить блок через `interface-deep-dive`).

## Если interface поверхности пуст

Если папки `…/interface/<surface>/` нет или таблицы пусты — синтез
невозможен: окна не к чему привязать (`interface-block` обязателен).
Скилл говорит:

> «UX-слой поверхности `<surface>` пуст. Слой бота синтезируется из
> него — сначала наполни `interface/<surface>/` через
> `/interface-deep-dive <project-slug> <surface>` (хотя бы who,
> situation, zone, block, ux-substrate), потом возвращайся.»

Команды и уведомления без окон заводить можно (реестры не требуют
блоков), но `who`/`to` всё равно ссылаются на `who.md` — без него и
они не закрываются до stable.

## Cross-audit

Смысловую сторону рёбер (зона ↔ диалог, покрытие возможностей
поверхности диалогами, словарь данных между поверхностями) сверяет
`/cross-audit` — скилл в конце сессии упоминает это рядом с
предложением `/telegram-bot-flow-audit`.
