# Режимы ведения сеанса

Режим выбирается по тому, что есть в слоях-источниках **той же поверхности
того же проекта**: `interface/<surface>/`, `screens/<surface>/`,
`services/<svc>/domains/`.

## A. С аналитикой

**Сигнал**: в `interface/<surface>/situation.md` есть ситуации; экраны в
`screens/<surface>/screen.md` и/или домены в `services/<svc>/domains/`
заведены.

1. Освежить канон: `docs/projects/_template/fsd/README.md`.
2. Прочитать источники: `situation.md`, `data-items.md`, `screen.md`,
   `block.md`, `services/service.md` + домены сервисов, которые
   обслуживают поверхность.
3. Мапить напрямую в порядке inside-out: агрегат/сущность домена (или
   data-item) → entity; ситуация → feature; экран → page; блок с
   повторением на ≥2 экранах → widget.
4. Каждый кандидат — через волну `AskUserQuestion` (до 4): подтвердить /
   отбросить / переименовать. Не выдумывать слайсы, которых нет в
   источнике.
5. Открытые места — в ветку state (`## Открытые вопросы`, `**blocker**`
   для блокирующих).

## B. С эскизом

**Сигнал**: слои-источники пусты или тонки, но архитектор принёс эскиз
экранов / набросок сценариев / описание UI.

1. Прочитать материал, извлечь кандидатов и привязать к слоям (действие →
   feature, данные → entity, маршрут → page, повторяемый блок → widget).
2. Показать план в чат, подтвердить волной `AskUserQuestion`.
3. Завести подтверждённое как `draft`-строки; дыры по обязательным
   слотам — `**blocker**` в state.
4. Предложить довести аналитику: ситуации — `/interface-deep-dive`,
   экраны — `/screen-deep-dive`, домены — `/domain-deep-dive`. Stable
   требует источников: колонки `situation`/`screen`/`source` должны
   заполниться до промоушна.

Извлечённое из эскиза — кандидаты до подтверждения, не факты.

## C. С нуля

**Сигнал**: ни аналитики, ни эскиза.

1. Волна базовых вопросов про сценарии и данные поверхности (3–4).
2. Из ответов — минимальный набор `draft`-записей; остальное — «Что
   копать дальше» в state.
3. Предупредить: без слоёв-источников карта останется в `draft`; вести
   аналитика в deep-dive'ы источников.

## Каскады удаления

Запись удаляется не в одиночку:

- удалить **entity** → снять её из `features.entities`, `pages.entities`,
  `widgets.entities`, из покрытия `shared-api.md`;
- удалить **feature** → снять из `pages.features` / `widgets.features`;
- удалить **page** → пересчитать зеркало `widgets.pages`; widget,
  оставшийся с <2 референсами, — кандидат на возврат в page-слайс
  (pages-first), спросить;
- удалить **widget** → снять из `pages.widgets`, пересчитать зеркало.

После каскада — прогнать чек-лист `references/draft-stable.md` по
затронутым записям.

## Стиль вопросов

- Волна — до 4 вопросов, не 10. Дизайн-решения — через `AskUserQuestion`.
- Имена слайсов — из источника (`situation.name`, имя агрегата,
  `screen.name`), транслит slug'а делает скилл.
- Не предлагать «оптимизации» нарезки сверх того, что диктует источник.
- Не закрывать сессию без чек-листа `draft-stable.md` хотя бы по одной
  правленой записи.
