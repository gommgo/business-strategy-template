# Режимы ведения сеанса

Режим выбирается по тому, что есть в слоях-источниках **той же поверхности
того же проекта**: `interface/<surface>/`, `screens/<surface>/`,
`services/<svc>/domains/`.

## A. С аналитикой

**Сигнал**: в `interface/<surface>/situation.md` есть ситуации; экраны в
`screens/<surface>/screens/` и/или домены в `services/<svc>/domains/`
заведены.

1. Освежить канон: `docs/projects/_template/fsd/README.md`.
2. Прочитать источники: `situation.md`, `data-items.md`, экраны
   `screens/<surface>/screens/*/index.md`, блоки
   `screens/<surface>/blocks/*/index.md`, реестр текстов
   `screens/<surface>/texts.md`, `services/service.md` + домены
   сервисов, которые обслуживают поверхность.
3. Мапить напрямую в порядке inside-out: агрегат/сущность домена (или
   data-item) → entity; ситуация → feature; экран → page; блок с
   повторением на ≥2 экранах → widget; тип `ui:`, реально
   переиспользуемый на экранах поверхности, → shared-ui.
4. Поля, у которых источник — экраны, не спрашиваются, а выводятся и
   показываются строкой для контроля:
   - `pages.path` — маршрут (`route`) экрана `pages.screen` с его
     параметрами (`params`); экран с маршрутом `modal:<имя>` — не page;
   - `pages.guard` — доступ (`access`) экрана: `public`,
     `authenticated` или роли — `who` экрана при `access: roles`;
   - `shared-ui.ui-type` — тип словаря компонентов или расширения
     проекта, который реализует слайс; слайс заводится только при
     переиспользовании, тип без слайса реализует компонент дизайн-системы;
   - сценарии данных `shared-api` — `empty` и `populated` всегда, а
     `partial-few`, `overflow-many`, `loading-initial`, `error-load`,
     `no-permission` — когда эти состояния есть в обязательных наборах
     экранов поверхности (имена — ключи словаря состояний экрана);
     значения — производный демо-набор экранов, своих фикстур нет;
   - `shared-lib`, i18n — список локалей: язык `default` — колонка `text`
     реестра текстов, каждая `supported` — колонка `text-<locale>`;
     строки и их ключи живут в реестре.
5. Каждый кандидат — через волну `AskUserQuestion` (до 4): подтвердить /
   отбросить / переименовать. Не выдумывать слайсы, которых нет в
   источнике.
6. Открытые места — в ветку state (`## Открытые вопросы`, `**blocker**`
   для блокирующих).

## B. С эскизом

**Сигнал**: слои-источники пусты или тонки, но архитектор принёс эскиз
экранов / набросок сценариев / описание UI.

1. Прочитать материал, извлечь кандидатов и привязать к слоям (действие →
   feature, данные → entity, маршрут → page, повторяемый блок → widget).
2. Показать план в чат, подтвердить волной `AskUserQuestion`.
3. Завести подтверждённое как `draft`-строки; дыры по обязательным
   слотам — `**blocker**` в state.
4. Предложить довести аналитику: ситуации — `/interface-deep-dive`,
   экраны — `/screen-deep-dive`, домены — `/domain-deep-dive`. Stable
   требует источников: колонки `situation`/`screen`/`source` должны
   заполниться до промоушна, а сверки `path`, `guard` и `ui-type`
   включаются, когда появляются экраны.

Извлечённое из эскиза — кандидаты до подтверждения, не факты.

## C. С нуля

**Сигнал**: ни аналитики, ни эскиза.

1. Волна базовых вопросов про сценарии и данные поверхности (3–4).
2. Из ответов — минимальный набор `draft`-записей; остальное — «Что
   копать дальше» в state.
3. Предупредить: без слоёв-источников карта останется в `draft`; вести
   аналитика в deep-dive'ы источников.

## Каскады удаления

Запись удаляется не в одиночку:

- удалить **entity** → снять её из `features.entities`, `pages.entities`,
  `widgets.entities`, из покрытия `shared-api.md`;
- удалить **feature** → снять из `pages.features` / `widgets.features`;
- удалить **page** → пересчитать зеркало `widgets.pages`; widget,
  оставшийся с <2 референсами, — кандидат на возврат в page-слайс
  (pages-first), спросить;
- удалить **widget** → снять из `pages.widgets`, пересчитать зеркало.

После каскада — прогнать чек-лист `references/draft-stable.md` по
затронутым записям.

## Стиль вопросов

- Волна — до 4 вопросов, не 10. Дизайн-решения — через `AskUserQuestion`.
- Имена слайсов — из источника (`situation.name`, имя агрегата,
  `screen.name`), транслит slug'а делает скилл.
- Не предлагать «оптимизации» нарезки сверх того, что диктует источник.
- Не закрывать сессию без чек-листа `draft-stable.md` хотя бы по одной
  правленой записи.

## Привести к канону

Файлы папки поверхности расходятся с формой слоя — например, форк обновил
шаблон поверх заполненного проекта. Тогда карта приводится к канону
`docs/projects/_template/fsd/`: восемь файлов, колонки и их порядок — как в
форме, стыки с экранами — как в разделе «Связи» канона. Цель — чтобы
`/scaffold` фронт-форка читал карту по одной форме, не потеряв ни одного
решения архитектора.

**Когда.** При запуске скилл сверяет папку с формой: у `pages` `path` и
`guard` совпадают с маршрутом и доступом экранов; у `shared-ui` есть
колонка `ui-type`; сценарии `shared-api` названы по наборам состояний
экранов; `shared-lib` держит список локалей, а строки — реестр текстов
экранов. Расхождения видит и `/fsd-audit`. Их мало — правятся по ходу, в
режиме C; много — скилл первым пунктом сводки предлагает пакет.

**Сначала экраны.** `path`, `guard`, наборы состояний и ключи текстов
приходят из экранов поверхности (`/screen-deep-dive`): у экранов нет
маршрута, доступа или набора — скилл называет этот скилл первым шагом, а в
заметке пишет долг.

**Механические правки** скилл делает сам после одного подтверждения,
показав различие по каждому файлу: `path` и `guard` — из маршрута и
доступа экрана-источника; недостающие колонки — на своё место по форме,
значения колонок вне канона — в колонки канона, где у их смысла есть
место; сценарий данных, чьё состояние есть в наборах экранов, — строка с
ключом словаря; строки локализации — в реестр текстов экранов через
`/screen-deep-dive`, в `shared-lib` остаётся список локалей.

**Пустое — не прочерк.** Новая ячейка `ui-type`, которую экраны не
подсказывают однозначно, остаётся пустой до ответа архитектора: какой
тип реализует слайс — его решение.

**Смысловые правки** — архитектору (`CLAUDE.md` §3): какой тип
реализует слайс, нужен ли слайс вовсе (тип без слайса реализует компонент
дизайн-системы), что лежит в сценариях данных.

**Статусы.** Stable-записи скилл не понижает — понижение делает только
архитектор. Пустой обязательный слот stable-записи и расхождение с
экранами — находки `/fsd-audit`, их список — список работ перевода.

**Порядок — по зависимостям.** Продукт → interface → экраны → FSD-карта
(этот скилл) → стыки мобильного приложения и бота. Заметки держат открытые
вопросы перевода, а не его историю.
