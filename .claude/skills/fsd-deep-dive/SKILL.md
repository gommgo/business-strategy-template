# fsd-deep-dive

Проектирование FSD-карты **одной SPA-поверхности** проекта в
`docs/projects/<project-slug>/fsd/<surface>/`. Канон формы —
`docs/projects/_template/fsd/README.md`. Скилл ведёт сеанс через
структурированные вопросы, фиксирует контекст в своей ветке единого дерева
state оркестратора (`../entrypoint/state/projects/<project-slug>/fsd/<surface>/`),
не выдумывает слайсы и craft.

Слой — мост «аналитика → фронт-код»: источники — `interface/<surface>/`
(ситуации, данные), `screens/<surface>/` (экраны, блоки),
`services/<svc>/domains/<ctx>/` (доменные сущности) **того же проекта**.
Потребитель — форк `<org>/frontend`: его `/scaffold` и `/de-template`
читают stable-записи cross-repo и сами выводят `src/<layer>/<slice>/` из
kind + slug. `src/`-пути и библиотеки в артефактах не появляются.

Использовать как **единственную точку входа** в fsd-слой: заведение,
углубление, разбор сырья, переход `draft → stable`, удаление с каскадом.

## Выбор проекта и поверхности

Скилл работает в контексте **одного** проекта и **одной** его
SPA-поверхности. Аргументы позиционны — `<project-slug>` первый,
`<surface>` второй:

| вызов | проект · поверхность |
|---|---|
| `/fsd-deep-dive <project-slug> <surface> …` | взять `<project-slug>` и `<surface>` |
| `/fsd-deep-dive <project-slug> …` (без surface) | проект задан; поверхность — `AskUserQuestion`-пикер **по именам** SPA-поверхностей из `surface.md` |
| `/fsd-deep-dive …` (без slug) | пикеры **по именам**: сначала проект, затем поверхность |

Алгоритм определения при запуске:

1. **Проект.** Если первый аргумент совпадает с именем подпапки
   `docs/projects/` (кроме `_template`) — это `<project-slug>`. Иначе —
   пикер по именам проектов. Если проектов нет — «сначала заведи проект
   через `/project-deep-dive`», выйти.
2. **Поверхность.** Прочитать реестр
   `docs/projects/<project-slug>/surface.md`; кандидаты — только строки с
   `type: web | admin | desktop | embed` (для `type: bot` слой —
   `telegram-bot-flow/`, для `type: mobile` — `mobile/`, для `api` слоя
   нет). Если следующий аргумент
   совпадает со `slug` такой строки — это `<surface>`. Иначе — пикер по
   именам SPA-поверхностей. Реестр пуст или SPA-поверхностей нет —
   «сначала заведи поверхность в `surface.md` через `/project-deep-dive`»,
   выйти. Поверхность вне реестра не принимается.
3. **Scaffold.** Если папки `docs/projects/<project-slug>/fsd/<surface>/`
   ещё нет — первый заход: создать её, скопировав форму из
   `docs/projects/_template/fsd/_template/` (8 файлов), очистив таблицы от
   строк-образцов (остаётся канон-проза + пустой заголовок таблицы).
   Каталог руками не создавать в обход скила.
4. Все дальнейшие чтения/записи скоупятся в выбранную поверхность и ветку
   state `../entrypoint/state/projects/<project-slug>/fsd/<surface>/`.

## Точки входа

После того как `<project-slug>` и `<surface>` определены, остаток args
задаёт режим:

| вызов | поведение |
|---|---|
| `/fsd-deep-dive <project-slug> <surface>` | сводка состояния поверхности + топ-3 кандидата на углубление |
| `/fsd-deep-dive <project-slug> <surface> <kind>` | завести новую запись kind'а (режим A) |
| `/fsd-deep-dive <project-slug> <surface> <kind>:<slug>` | углубить существующую запись (режим C) |
| `/fsd-deep-dive <project-slug> <surface> <slug>` | найти slug; одиночный → C; конфликт kind → переспросить |
| `/fsd-deep-dive <project-slug> <surface> <свободный текст / приложение>` | сырьё (эскиз, набросок сценариев) → разбор (режим B) |

`kind` ∈ {`entities`, `features`, `pages`, `widgets`, `app`, `shared-ui`,
`shared-api`, `shared-lib`}.

## Что делать сразу при запуске

1. Определить `<project-slug>` и `<surface>`, при первом заходе — scaffold
   папки.
2. Прочитать `docs/projects/_template/fsd/README.md` — освежить канон формы.
3. Прочитать источники поверхности: `interface/<surface>/situation.md` +
   `data-items.md`, `screens/<surface>/screen.md` + `block.md`, реестр
   `services/service.md` и `services/<svc>/domains/` (если сервисный слой
   есть) — из них берутся кандидаты. Пустота источников — не ошибка, а
   сигнал режима (см. `references/workflow-patterns.md`).
4. Если остаток args пуст — сводка (см. ниже) + `AskUserQuestion`-выбор.
5. Если указывает на запись — определить kind и режим (A/B/C), применить
   маршрут из `references/workflow-patterns.md`.

## Сводка состояния (без args)

1. Прочитать все 8 файлов поверхности.
2. Подсчитать `draft` / `stable` по каждому kind.
3. Прочитать свою ветку state (если есть), собрать открытые вопросы;
   `**blocker**` приоритетны.
4. Топ-3 кандидата: blocker-записи → записи с пустыми обязательными
   слотами → draft-записи, на которые ссылаются stable-соседи → слои без
   единой записи в порядке inside-out (entities → features → pages →
   widgets → app → shared-*).
5. Сводка в чат + `AskUserQuestion`-выбор.

## Порядок проектирования — inside-out

`entities` → `features` → `pages` → `widgets` → `app` → `shared-ui` →
`shared-api` → `shared-lib`. Не догма обхода, а приоритет при пустом слое:
сначала данные и сценарии, потом маршруты, потом переиспользование.

## Три режима

Детали и примеры вопросов — `references/workflow-patterns.md`.

- **A. Новая запись.** Args = `<kind>` или `<kind>:<новый-slug>`.
  Кандидаты — из источников (ситуация → feature, экран → page, агрегат →
  entity, повторяемый блок → widget); батч `AskUserQuestion` по
  `Критерии <kind>`; опции — anti-patterns из `Что <kind> НЕ`.
- **B. Сырьё.** Args = свободный текст / приложение (эскиз, набросок).
  Извлечь кандидатов, показать план, по подтверждению завести stub-строки,
  погрузиться через режим C. Извлечённое — кандидаты, не факты.
- **C. Углубление.** Args = `<kind>:<slug>` или выбор из сводки. Точечные
  вопросы по дырам; чек-лист `draft → stable` после каждой правки.

## Стиль вопросов

- **Всегда через `AskUserQuestion`**, до 4 вопросов в раунде.
- **Опции** — для anti-patterns (`Что <kind> НЕ`), тест-критерия (✅/❌) и
  структурных перечислений (guard, роль локали).
- **Свободная форма** (через Other) — для значений: `name`, `description`,
  `результат`, `состояние`, `семантика`.
- Имена слайсов предлагать **только из источника** (`situation.name`, имя
  агрегата, `screen.name`) — не изобретать аббревиатуры. Слайс без
  источника — сначала спросить, вести ли аналитика в
  `/interface-deep-dive` / `/screen-deep-dive` / `/domain-deep-dive`.

## Память: своя ветка единого дерева state

Скилл не держит своего `state/`. Заметки — в ветке
`../entrypoint/state/projects/<project-slug>/fsd/<surface>/<kind>/<slug>.md`
(для секционных записей app/shared-api/shared-lib slug = slug строки).
Формат — канон `../entrypoint/references/state-model.md`: frontmatter
`kind` · `slug` · `ref`; секции `## Открытые вопросы` (опц. `**blocker**`),
`## Доменные решения`, `## Что копать дальше`; пусто → удалить файл;
forward-only, не журнал.

Единый контекст: read-only видимость всего дерева `../entrypoint/state/`
(проектные ветки — только текущего `<project-slug>`) и клиентского дома
`../entrypoint-for-business/state/`; rw — только своя ветка
`projects/<project-slug>/fsd/<surface>/`. Маркер `**жду аналитика**` —
blocker-кандидат.

## Зеркало

`widgets.pages` — **производное** поле; канонический источник —
`pages.widgets` (M:N). После любой правки `pages.widgets` — пересчитать
`widgets.pages` автоматически, без подтверждения. Инвариант pages-first:
widget с <2 page-референсами (и без явной пометки зоны каркаса) — blocker
для его stable.

## Контракт `draft → stable`

См. `references/draft-stable.md`. Чек-лист после каждой правки:

1. Обязательные слоты заполнены (опциональные могут быть `—`).
2. Ссылки на источники валидны: `situation`/`screen`/`block` существуют в
   слоях поверхности, `source` — в `services/<svc>/domains/<ctx>/` или
   `data-items.md`.
3. Внутрислойные ссылки валидны (entities/features/widgets/pages),
   зеркало `widgets.pages` консистентно, cross-feature отсутствует.
4. Тест-критерий из md подтверждён архитектором в этой сессии.
5. В ветке state нет `**blocker**`-вопросов.

Все 5 ✅ → предложить «Готов к stable, повышаем?»; повышение — только по
подтверждению. Понижение `stable → draft` — только аналитик руками.

## Stub-записи

Ссылка на не существующий slug **той же поверхности** (feature → entity,
page → widget): завести stub-строку (`slug + name + description +
status=draft`, остальное `—`), заметку в state «заведён как stub в
контексте `<откуда>` — докопать», вернуться к исходной записи. Stub'ы в
слоях-источниках (situation, screen, домен) не заводятся — это работа
их deep-dive-скиллов; фиксируй blocker.

## Удаление записи (каскад)

1. Прочитать все 8 файлов поверхности + свою ветку state — найти ссылки
   на удаляемый slug.
2. Показать каскад: «ссылаются X, Y — вот что сломается» (widget при
   удалении page может потерять ≥2 референса — это тоже каскад).
3. `AskUserQuestion` по каждому месту: заменить slug / `—` / удалить
   ссылающуюся запись.
4. По подтверждению — все правки одним пакетом, запись удалить, заметку
   state удалить, зеркало пересчитать.

## Завершение сессии

1. Перечислить затронутые записи (заведены / углублены / удалены).
2. Перечислить нерешённые открытые вопросы.
3. Предложить: «Прогнать `/fsd-audit`?» — по «да» сказать «Запусти
   `/fsd-audit`», сам не вызываю.

## Запреты

- Не редактировать таблицы вслепую — всегда сначала `Read`.
- Не выдумывать слайсы без источника и не писать продуктовые/UX-формулировки
  от себя — это работа deep-dive-скиллов слоёв-источников.
- Не вписывать `src/`-пути, имена файлов, импорты, библиотеки — карта
  слайсов, не код (`Generates` — сторона `<org>/frontend`).
- Не выдумывать craft (облик, размеры, варианты) — screens + `@stit/ui`.
- Не выносить FSD-имена в артефакты других слоёв (R-SEM-003 остаётся).
- Не повышать `draft → stable` без явного подтверждения архитектора; не
  понижать сам.
- Не оставлять зеркало `widgets.pages` рассинхронным.
- Не писать в чужие ветки дерева state и в клиентский дом — rw только
  своя ветка.
- Не работать сразу с несколькими проектами/поверхностями — скоуп один.
- Не ссылаться из одной поверхности в сущность другой — изоляцию сводит
  `/cross-audit`.
