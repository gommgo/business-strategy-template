# Конвейер приёма сырья (intake)

Оркестратор рассчитан на сырьё **любого объёма и разнородности**:
3-часовой транскрипт созвона, разрозненные заметки, ссылка на сайт,
выгрузка, сигнал «из жизни». Задача intake — ничего не потерять и развести
по слоям, не подменяя экспертизу исполнителей.

Конвейер — пять шагов: **ingest → сегментация → классификация →
предложение маршрута → делегирование**.

## 1. ingest — забрать содержимое

| источник | как берём |
|---|---|
| вставленный текст / заметки | как есть |
| путь к файлу (PDF/deck/выгрузка/транскрипт) | `Read` |
| ссылка (сайт/лендинг/соцсети) | `WebFetch` |
| несколько источников разом | по очереди, помечая, что откуда |

Не угадывать содержимого, которого в источнике нет. Чувствительные данные
(ПДн, коммерческая тайна) дальше не тиражируются — в маршрут идут только
**бизнес-факты**, сами файлы остаются по своему пути.

## 2. сегментация — разбить на тематические чанки

Большой транскрипт почти всегда покрывает **несколько слоёв сразу**:
кусок про профиль бизнеса, кусок про боли клиентов, кусок про метрику,
кусок про то, что продукт должен уметь. Разбить поток на смысловые чанки
— один чанк = одна тема, тяготеющая к одному слою/kind.

Признаки границы чанка: смена темы, смена адресата («а вот наши клиенты…»
→ ajtbd; «нам важно дойти до…» → hypothesis-map/goal; «в боте продукт
должен…» → project/`capability/<surface>`). Чанк может быть и одной фразой,
и абзацем.

Не терять «висящие» куски: если фрагмент явно важен, но слой неясен —
оставить как чанк с пометкой «слой под вопрос», разрешить на шаге
классификации.

## 3. классификация — чанк → слой + kind

Каждый чанк сопоставить со слоем и kind по сигнальной таблице
`routing.md`. Для проектных слоёв — определить **какой проект**
(`<project-slug>`), а для `interface`/`screens`/`fsd`/`telegram-bot-flow`/
`mobile`/`capability`, слоя страницы и облика поверхности — ещё и **какую
поверхность** (`<surface>`) и её род: слой страницы — только у `web` рода
`landing` и `site`, экраны и FSD-карта — у кабинета; если непонятно — это
вопрос аналитику, не догадка.

Эвристики (полная таблица — `routing.md`):

- «чем бизнес занимается / как зарабатывает / конкуренты / текущие KPI» →
  `business`;
- «какую боль бизнеса решаем / граница гарантии» → `business/business-problem`;
- «кто в бизнесе принимает решение / спонсор / держит бюджет / блокирует /
  на кого влияет / куда хочет вести» → `business` (stakeholder / stakeholder-map);
- «кто наши клиенты по работам / что они делают / чем пользуются / где им
  тяжело» → `ajtbd` (segment / job-graph);
- «сильные-слабые стороны, тренды-угрозы / за счёт чего сделаем шаг» →
  `swot`;
- «к чему стремимся / по какому числу поймём / на чьё поведение влияем /
  если…то…потому что» → `hypothesis-map`;
- «зачем продукт и для кого / какие поверхности / что умеет на поверхности
  / с чем интегрируется» → `projects/<slug>` (project; возможности —
  `capability/<surface>`, на какой поверхности?);
- «продукт обменивается с соседним продуктом бизнеса» → `projects/<slug>`
  (integration `target: sibling-project` → ребро `projects/project-map`);
- «с какими вещами работает пользователь / как их называет / что с ними
  делает» → `projects/<slug>` (object / action);
- «как пользователь взаимодействует / сценарий задачи / из каких экранов и
  что на экране / подписи кнопок кабинета» → `projects/<slug>` (interface /
  screens — на какой поверхности?);
- «сайт / лендинг / посадочная / тексты для сайта / воронка / заявки с
  сайта / редизайн сайта» → `projects/<slug>/site/<surface>` (какая
  поверхность? род `landing` или `site`); проекта или поверхности нет —
  быстрый путь (`routing.md`, «Быстрый путь и вход с середины»);
- «цифры, отзывы, кейсы, гарантии для сайта / как мы говорим, тон» →
  уровень продукта: факты и голос (`/design-deep-dive <slug>`);
- «стиль / бренд / логотип / цвета и шрифты / референсы / картинки /
  иконки / 3D / видео / анимация» → `projects/<slug>/design` (продукт или
  поверхность);
- «макет / холст / вайрфрейм / правки макета / проверь или прими макет» →
  `projects/<slug>/design/<surface>` (этапы холста — какая поверхность?);
- «кабинет / личный кабинет / сервис / SaaS / админка» → маршрут кабинета:
  продукт → interface → экраны → FSD, облик — `design`; «как выглядит» у
  кабинета — облик (`design`), «что на экране и где» — экраны;
- «как фронт нарезан по слоям FSD / какие слайсы у веб-фронта» → `projects/<slug>`
  (fsd — какая фронтовая поверхность?);
- «как бот ведёт диалог / окна и кнопки / команды / уведомления бота» →
  `projects/<slug>` (telegram-bot-flow — какая bot-поверхность?);
- «мобильное приложение: экраны, push и напоминания, ссылки, разрешения,
  голос, виджеты, фон, офлайн» → `projects/<slug>` (mobile — какая
  мобильная поверхность?);
- «бизнес-код бэкенда / агрегаты / инварианты» →
  `projects/<slug>/services/<svc>/domains/<ctx>` (по bounded-context, внутри
  сервиса-владельца); сервисная топология и инфраструктура — классы
  «архитектура приложения» (`projects/<slug>/services`) и «ИТ-периметр»
  (`projects/infrastructure`).

Неоднозначный чанк → опция в `AskUserQuestion` на следующем шаге, не
самовольный выбор слоя. Для `interface`/`screens`/`fsd`/`telegram-bot-flow`/
`mobile`/`capability`, слоя страницы и облика поверхности неясная
**поверхность** — тоже вопрос, не догадка (поверхность — ось продукта).

## 4. предложение маршрута

Свести классификацию в **план маршрутов** и показать аналитику. Для
каждого чанка: слой → исполнитель → сущность(kind) → режим.

```
Из сырья вижу (5 тем):
  1. «сеть клиник, выручка ОМС + платные»        → business / profile        · наполнить
  2. «платные пациенты не возвращаются»          → business / business-problem · наполнить
  3. «отток платных 8% за Q1»                    → hypothesis-map / metric (baseline ← current-metric) · наполнить
  4. «хотим, чтобы пациенты возвращались сами»   → hypothesis-map / goal      · наполнить
  5. «запись и напоминания в приложении»         → projects/<?> / capability[поверхность?] · наполнить (какой проект? какая поверхность?)
  6. «лендинг под акцию, заявки уходят в CRM»    → projects/<?> / site[поверхность?] · наполнить (быстрый путь: минимум продукта → /design-deep-dive, этап выберет исполнитель)

Веду по порядку через исполнителей? (темы 5 и 6 — в какой проект и на какую поверхность?)
```

Строка «быстрый путь» появляется, когда сайт или лендинг просят сразу, а
проекта или поверхности с родом нет: первым в плане идёт
`/project-deep-dive` (минимум продукта), вторым — `/design-deep-dive` с
поверхностью; пропущенные верхние слои исполнители запишут долгом
(`routing.md`, «Быстрый путь и вход с середины»).

Подтверждение — батч `AskUserQuestion` (до 4 вопросов в раунде; если тем
больше — несколько раундов): принять маршрут / поправить слой / уточнить
проект / уточнить поверхность / отложить чанк. Неоднозначные слои,
`<project-slug>` и `<surface>` (для interface/screens/fsd/telegram-bot-flow/
mobile/capability) — обязательно через вопрос.

## 5. делегирование

По подтверждению каждого маршрута:

1. Записать строку в открытую нить `state/threads/<slug>.md` (чанк →
   слой/kind/исполнитель → ждёт) — см. `state-model.md`.
2. **Активировать исполнителя** с аргументами и чанком как сырьём
   (исполнитель войдёт в свой режим B «сырьё»). Проектный слой — первым
   аргументом `<project-slug>`; `interface`/`screens`/`fsd`/
   `telegram-bot-flow`/`mobile` — вторым аргументом `[<surface>]` (без него
   исполнитель сам предложит пикер поверхностей); слой страницы и облик
   поверхности — `/design-deep-dive <project-slug> <surface>`; факты, голос,
   бренд и дизайн-система — уровень продукта: их этапы идут внутри
   маршрута поверхности, которой они нужны, поэтому при известной
   поверхности — тот же вызов с поверхностью, без неё —
   `/design-deep-dive <project-slug>` (поверхности нет или нужен только
   уровень продукта). Этап оркестратор не называет: первый этап с готовым
   входом выбирает исполнитель.
3. Исполнитель добивает формулировки **сам** через свой `AskUserQuestion`
   — оркестратор доменный текст не подставляет.
4. По возвращении — убрать закрытый чанк из нити, предложить следующий.

## Что НЕ делать

- Не смешивать intake (сырьё аналитика/клиента) и web-research в одном
  заходе — research запускает исполнитель (`*-deep-dive --research`)
  отдельно, с пометкой источника. Сначала разложить сырьё, потом research.
- Не заводить артефакты напрямую — только через исполнителя.
- Не выдумывать кандидатов, которых в сырье нет.
- Не выбирать слой/проект за аналитика при неоднозначности — спросить.
- Не терять чанки: всё, что не разложено в этой сессии, остаётся открытой
  нитью в `state/threads/`.
