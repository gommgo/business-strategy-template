# Восходящий поток `project → business` (reconcile-up)

Дозревший продукт меняет реальность бизнеса: он сам становится офером,
приносит новые baseline-метрики, может сдвинуть профиль, а рынок, который
был разведкой (`prospective`), становится обслуживаемым (`served`).
`reconcile-up` — процедура, которой `entrypoint` **сверяет** дозревший
продукт с верхним слоем `docs/business/` (и связанными `docs/ajtbd/`).

**Оркестратор ведёт сверку сам, но не пишет в `docs/` напрямую.** Каждое
изменение наверху уезжает через делегирование исполнителю:

- `business/offering`, `business/current-metric`, `business/profile`,
  `business/business-problem.served` → `/business-deep-dive`;
- `ajtbd/segment.served` → `/segment-deep-dive`.

Всё — через `AskUserQuestion` (оркестратора при сборе кандидатов и
исполнителя при записи). **Авто-записи нет**: оркестратор предлагает, человек
подтверждает, исполнитель формализует. Факты о бизнесе не выдумываются —
они вытекают из дозревшего продукта (`vision`, `capability`, `user`,
новые числа), но формулировку наверху добивает исполнитель (экспертиза
священна, `CLAUDE.md` §3).

## Триггер

`reconcile-up` запускается, когда:

- оркестратор замечает переход `vision.lifecycle → stable` (при сводке «где
  мы» видит проект на `lifecycle: stable`, по которому восходящая сверка ещё
  не проведена), **или**
- аналитик явно просит сверить продукт с бизнесом
  (`/entrypoint --upstream <slug>`).

## Подготовка

Перед предложением шагов оркестратор собирает контекст (read-only):

1. **`vision` проекта** `docs/projects/<slug>/vision.md` — оси `audience` /
   `intent` / `market-maturity`, `lifecycle`, разделы `Problem` / `Success`,
   массив `addresses-problem` (на какие строки `business/business-problem`
   продукт целит).
2. **Что продукт даёт как ценность** — `capability/<surface>.md` (по
   поверхности), `user.md` проекта: кандидаты на офер и на адресата.
3. **Новые числа продукта** — наблюдаемые baseline (из `success`/метрик
   продукта, из state проекта): кандидаты в `current-metric`.
4. **Связанные сущности наверху** — по семантике (не по slug-валидации):
   `business/offering`, `business/current-metric`, `business/business-problem`
   (особенно строки из `addresses-problem`), `ajtbd/segment` (через
   `offering.for-segment` / адресуемые проблемы). Помечает, какие из них
   `served=prospective`.

Заводит/держит нить `state/threads/upstream-<slug>.md` — маршрут сверки
(шаги-кандидаты как открытые строки; закрытый шаг удаляется, forward-only).

## Четыре шага сверки

Шаги независимы — не все применимы к каждому продукту. По каждому
оркестратор предлагает кандидата через `AskUserQuestion`; по согласию
делегирует исполнителю, который записывает с провенансом.

### 1. Продукт как офер

Дозревший продукт — это услуга/продукт, который бизнес теперь продаёт.

- **Предложить** новую или обновлённую запись `business/offering` с
  `from-project = <slug>`.
- **Кандидаты** — из `vision.Success` + `capability/<surface>` (что
  продукт даёт рынку на своих поверхностях), адресат — из `user` /
  адресуемого сегмента.
- **Пишет** `/business-deep-dive` (режим A — новый офер, или C — углубление
  существующего), проставляя `from-project` `<slug>`.

### 2. Профиль

Продукт мог сдвинуть «как бизнес зарабатывает / кого обслуживает».

- **Если** дозревший продукт изменил модель заработка или адресата —
  **предложить** правку `docs/business/profile.md` (раздел `Модель` или
  `Бизнес`).
- Профиль описывает бизнес **как он есть** — правка только когда продукт
  уже стал частью реальности бизнеса, не «как будет».
- **Пишет** `/business-deep-dive` (фаза `profile`).

### 3. Метрики

Продукт приносит новые наблюдаемые числа — кандидаты в baseline.

- **Предложить** новые записи `business/current-metric` с
  `from-project = <slug>` (число + дата + источник).
- Это baseline-кандидаты для целевых метрик `docs/hypothesis-map/`, не
  цель-гарантия.
- **Пишет** `/business-deep-dive` (фаза `metrics`), проставляя
  `from-project`.

### 4. Проспективное → обслуживаемое

Если продукт целил в новый рынок (`vision.market-maturity: prospective`) и
дозрел — этот рынок бизнес теперь обслуживает.

- **Предложить** повысить `served`: `prospective → served` у связанных
  - `ajtbd/segment.served` — **пишет** `/segment-deep-dive`, проставляя
    `from-project = <slug>`;
  - `business/business-problem.served` — **пишет** `/business-deep-dive`,
    проставляя `from-project = <slug>`.
- Связь «какой сегмент / какая проблема» — из `vision.addresses-problem` и
  адресуемого сегмента; неоднозначность → вопрос аналитику, не угадывание.
- Повышение **только** когда рынок действительно стал обслуживаемым;
  оставшаяся разведка остаётся `prospective` (не «висяк»).

## Делегирование и нить

1. Подтверждён шаг → оркестратор записывает строку в
   `state/threads/upstream-<slug>.md` (что → какому исполнителю → ждёт).
2. **Активирует исполнителя** (`/business-deep-dive` или
   `/segment-deep-dive`) с чанком-кандидатом; исполнитель ведёт запись по
   своим фазам и пишет per-kind заметку в свою ветку дерева `state/`.
3. По возвращении оркестратор убирает закрытый шаг из нити и предлагает
   следующий. Нить без открытых шагов — удаляется.

## Границы

- **Без авто-записи** — каждое изменение наверху проходит через
  `AskUserQuestion` исполнителя; оркестратор только предлагает и
  маршрутизирует.
- **Провенанс делает контур наблюдаемым** — поля `*.from-project`
  (offering, current-metric, business-problem, segment) показывают, какой
  продукт что породил. **Обратную сторону** (по проекту — что он породил,
  замкнут ли контур, консистентен ли `from-project`) сводит `/cross-audit`
  (угол `provenance-upstream`).
- **Контур процессный, не структурный** — он не превращает downstream-чтение
  в двустороннюю запись: форки-соседи **только читают** `docs/`. Восходит
  **внутри** репо стратегии.
- **Экспертиза священна** — оркестратор не формулирует офер/проблему/метрику
  из своей головы; кандидаты вытекают из дозревшего продукта, текст добивает
  исполнитель через `AskUserQuestion`.
