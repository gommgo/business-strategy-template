# Перекрёстная видимость (read-only)

Оркестратор аналитика видит **весь** state системы read-only, чтобы
сводка «где мы» была единой. Пишет **только в свой** state
(`entrypoint/state/`).

## Что читает

| источник | зачем |
|---|---|
| `../entrypoint-for-business/state/` | клиентский оркестратор: что клиент наработал, его `**жду аналитика**` |
| `../business-deep-dive/state/` · `../business-deep-dive-for-business/state/` | картина бизнеса + реестр проблем (аналитик и клиент) |
| `../segment-deep-dive/state/` · `../segment-deep-dive-for-business/state/` | сегменты по работам |
| `../job-graph-deep-dive/state/` · `../job-graph-deep-dive-for-business/state/` | граф работ, трения, решения |
| `../swot-deep-dive/state/` | факторы и ставки |
| `../hypothesis-map-deep-dive/state/` | цели, метрики, субъекты, гипотезы |
| `../project-deep-dive/state/<slug>/` · `../project-deep-dive-for-business/state/<slug>/` | продукт (по каждому проекту) |
| `../interface-deep-dive/state/<slug>/` · `../screen-deep-dive/state/<slug>/` · `../domain-deep-dive/state/<slug>/` | UX / композиция / домены проекта |

Каталоги создаются по требованию — читать те, что существуют; отсутствие
не ошибка.

## Anti-leak — на стороне аналитика не ограничивает

Аналитик видит **сырое**: открытые вопросы, черновые гипотезы, доменные
решения, `slug/draft/stable` — всё. Anti-leak (перевод в бизнес-язык,
сокрытие кухни) — забота **клиентского** оркестратора
(`../entrypoint-for-business/`), не этого. Здесь правило одно:

> **В чужой state не писать.** Только read-only.

## Маркеры `**жду аналитика**` — входящая очередь

Клиентские скиллы (оркестратор `entrypoint-for-business` и
`*-for-business`-исполнители) помечают застрявшие места
`**жду аналитика**` и `**отправлено в ветку client (<ts>)**`. Для
аналитика это **входящая очередь**:

1. В сводке «где мы» оркестратор поднимает все `**жду аналитика**` из
   клиентского state.
2. Предлагает разобрать — через нужного исполнителя (правка артефактов в
   `main`) и/или прямой ответ.
3. Ответ уходит в `main` (артефакты + свой state). Клиент подхватит его,
   когда его ветка `client` перебазируется на свежий `main` (обычная
   git-механика; ветку `client` ведёт клиентская сторона).

Оркестратор аналитика **не пишет** в клиентский state и **не трогает**
ветку `client` — он отвечает в `main`, клиент синхронизируется сам.

## Изоляция проектов

Проектные слои читать **по нужному `<project-slug>`** — не смешивать
разные продукты в одной сводке без явной развёртки. Это сохраняет
изоляцию продуктов при единой картине.
