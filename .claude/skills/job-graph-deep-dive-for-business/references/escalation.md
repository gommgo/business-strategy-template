# Эскалация и передача аналитику

Два формата: **мягкая** (клиент застрял на вопросе — фиксируем, идём
дальше) и **полная** (`--share` — весь материал по выбранной группе
уезжает аналитику в ветку).

В этом слое (разведка клиентов) эскалация особенно частая на **глубокой
сборке** и **рынке**: собрать весь путь клиента целиком, проставить
оценки удовлетворённости/болезненности по-настоящему, посмотреть
конкурентов и тренды роем помощников — это дисциплина аналитика, не
клиента.

## Мягкая эскалация (`**жду аналитика**`)

### Когда

- клиент трижды Other без сходящегося ответа;
- явное «не знаю / надо спросить самих клиентов»;
- вопрос требует дисциплины (сборка всего пути клиента, реальные оценки
  удовлетворённости/болезненности вместо «на глаз», классификация);
- клиент просит «посмотреть рынок / конкурентов / тренды» (это поиск
  роем — аналитик);
- клиент попросил «давай пропустим».

### Что делает

1. `AskUserQuestion`:
   > «Похоже, это лучше дождаться аналитика — у него есть инструменты,
   > чтобы это прояснить (а где-то — поговорить с вашими клиентами
   > вживую). Зафиксируем вопрос для него и пойдём дальше?»
   - «Да, отложим до аналитика»;
   - «Нет, ещё попробуем»;
   - «Лучше передам сразу» (`--share`).
2. По «да» — в state-заметку (под нужной группой):
   ```markdown
   ## Открытые вопросы
   - (**жду аналитика**) <вопрос в языке клиента>
   ```
3. «Записал. Когда отправим, аналитик увидит и ответит. Идём дальше?»

### Не делает

Не угадывает ответ; не блокирует другие блоки; не запускает поиск по
рынку сам; не отправляет ничего наружу (копится до `--share`).

## Полная передача (`--share`)

### Когда

Явное «передай аналитику» / `--share`; закрыт логичный блок; накопилось
3+ `**жду аналитика**`.

### Подтверждение (обязательно)

> «Я подготовлю для аналитика по группе ⟨название⟩:
>   — что вы рассказали про этих клиентов (черновики: что делают, чем
>     пользуются, где мучаются);
>   — наши заметки и открытые вопросы;
>   — короткий пересказ что сделали и где остановились;
>   — полный текст нашей сессии (мои вопросы и ваши ответы).
>
> Всё поедет в **отдельную папку проекта**, чтобы аналитик посмотрел, не
> трогая основную работу. Отправляем?»

Опции: «Да, отправляем» / «Сначала покажи, что поедет» (`--share
--preview`) / «Нет, отменим».

### Что упаковывается

1. Изменения в `docs/ajtbd/` (черновики клиента по выбранной группе:
   `job.md`, `solution.md`, `segment-problem.md`, при наличии —
   `job-graph.md`; набросок строки группы в `segment.md`, если заводили).
2. Изменения в `state/<segment-slug>/` (заметки, `**жду аналитика**`,
   `## Что я имел в виду`).
3. `client-handoff/summary.md` (живой срез, держится актуальным).
4. `client-handoff/transcripts/<YYYY-MM-DD>--<HH-MM>--<тема>.md`
   (человекочитаемое имя; полный лог сессии с предложенными вариантами).

**Не** упаковывается: `state/_session-log/` (уже в transcripts); файлы
вне перечисленного; ключи/.env (`git add` адресный, не `-A`).

### Настройка доступа к репозиторию (один раз)

Push требует логин/пароль — но клиента спрашиваем **ровно один раз на
устройстве**, дальше git помнит сам. Перед первым push проверить,
сохранён ли уже доступ:

```bash
host=$(git remote get-url origin | sed -E 's#https?://([^/@]*@)?([^/]+)/.*#\2#')
[ "$(git config --global credential.helper)" = "store" ] \
  && grep -q "@$host" ~/.git-credentials 2>/dev/null && echo ДОСТУП-ЕСТЬ
```

- Печатает `ДОСТУП-ЕСТЬ` → доступ уже сохранён: ничего не спрашиваем,
  сразу к Git-механике.
- Иначе — **один раз** запросить логин и пароль (или токен доступа, если
  выдали) через `AskUserQuestion` бизнес-языком: «Чтобы отправлять без
  повторных вопросов, нужно один раз ввести доступ к репозиторию — логин
  и пароль (или токен). Сохраню локально на вашем компьютере, больше не
  спрошу.» Логин и пароль клиент вводит через Other (два поля). Затем
  сохранить стандартным механизмом git (не редактировать файл руками):

  ```bash
  git config --global credential.helper store
  printf 'protocol=https\nhost=%s\nusername=%s\npassword=%s\n' \
    "$host" "<логин>" "<пароль>" | git credential approve
  ```

  После этого push идёт молча — и сейчас, и во всех будущих сессиях.

**Логин и пароль клиента — секрет.** Никогда не писать их в transcript,
summary, state, commit или в обычный текст чата после ввода. Этот шаг в
лог сессии не попадает.

### Синхронизация с main (старт и перед push)

`main` — канон аналитика, он уходит вперёд (аналитик мёржит черновики,
дописывает разбор). Чтобы клиент всегда работал поверх свежей аналитики,
ветку `client` держим перебазированной на `main` — и на старте сессии, и
перед каждым push.

**На старте сессии (до работы):**

1. `git fetch origin` — узнать, ушёл ли `main` вперёд (всегда безопасно).
2. Рабочее дерево чистое (нет несохранённых черновиков)?
   - Да → лечь поверх свежего `main`:
     ```bash
     git switch client 2>/dev/null || git switch -c client origin/main
     git pull --rebase origin client 2>/dev/null   # свои коммиты с другого устройства
     git rebase origin/main
     ```
     Клиенту бизнес-языком: «Подтянул свежие обновления, можно работать».
   - Нет (есть несохранённые черновики) → дерево **не трогать**; сказать,
     что обновления подтянутся при отправке, и работать дальше (rebase на
     `main` всё равно случится в Git-механике после коммита).

**Конфликт rebase** — не угадывать. Через `AskUserQuestion`
бизнес-языком: «Свежие правки пересеклись с вашими черновиками — это
лучше развести аккуратно. Поставлю на паузу для аналитика?» →
зафиксировать `**жду аналитика**`, дерево не ломать. Конфликты
разруливает аналитик.

### Git-механика

1. Доступ настроен (см. «Настройка доступа»).
2. Встать на единую ветку `client` — одна на все сессии, новые не плодим:
   `git switch client 2>/dev/null || git switch -c client origin/main`.
3. Перезаписать `client-handoff/summary.md` под актуальное состояние
   (живой срез, без мусора) и записать
   `client-handoff/transcripts/<YYYY-MM-DD>--<HH-MM>--<тема>.md` (с
   предложенными вариантами) — форматы ниже.
4. `git add` адресно (`docs/ajtbd/`,
   `.claude/skills/job-graph-deep-dive-for-business/state/<segment-slug>/`,
   `client-handoff/`).
5. `git commit -m "docs(handoff): ajtbd client session <UTC-ts>"`
   (Conventional Commits — пройти хук).
6. Лечь поверх свежего `main` и запушить: `git fetch origin && git rebase
   origin/main`. Первый push — `git push -u origin client`; последующие
   (rebase переписал историю) — `git push --force-with-lease origin
   client` (безопасный force: откажется, если на remote есть чужие
   коммиты). Remote-ветка ушла вперёд (другое устройство) → `git pull
   --rebase origin client`, снова `git rebase origin/main`, повторить
   push.
7. Удалить локально `state/<segment-slug>/_session-log/<этой-ts>.md`.

### Если git-hook падает

**Не** `--no-verify`. Поймать сообщение, через `AskUserQuestion`:
«Возникла техническая загвоздка: <текст>. Попробовать исправить, или
пауза — аналитик разберётся?» — «свяжусь с аналитиком» / «попробуй
автоматически» / «откатить». По «попробуй» — починить корректно
(переформатировать commit message) и повторить.

### После push

1. К каждой `**жду аналитика**` добавить `**отправлено в ветку client
   (<UTC-ts>)**`.
2. Удалить `_session-log/<ts>.md`.
3. Дать клиенту текст для пересылки (3-5 строк, бизнес-языком, от его
   лица): про какую группу клиентов разговор, что выяснили, где
   остановились, что нужно от аналитика (часто — «помоги собрать весь
   путь клиента» или «нужно поговорить с клиентами вживую / посмотреть
   рынок»).

## Формат `client-handoff/summary.md`

`summary.md` — **живой срез** для аналитика, не журнал. На каждом
`--share` **перезаписывается** под текущее состояние: закрытые вопросы
уходят из «Открытых», устаревшее «где остановились» заменяется, решённое
не копится. Forward-only — без «было/стало» и следов прошлых сессий.
Цель: аналитик с одного взгляда видит актуальную картину по каждой
группе клиентов, без мусора.

```markdown
# Передача аналитику — разведка клиентов

Обновлено: <YYYY-MM-DD> · Ветка: `client`

## Группы клиентов
- <список групп, по каждой — закрыта / в работе>

## Что обсудили
- <бизнес-формулировки тем, с указанием группы>

## Что выяснили
- <без жаргона, по группам: что клиент пытается сделать, чем пользуется,
  где мучается; насколько доволен/болезненно — если из реальных слов>

## Где остановились
- <текущая тема — только актуальное>

## Открытые вопросы для аналитика
- <в бизнес-форме; сборка пути целиком, оценки «на глаз», рынок/
  конкуренты — сюда чаще всего; только не закрытые>

## Где смотреть
- `docs/ajtbd/` — черновики
- заметки: `.claude/skills/job-graph-deep-dive-for-business/state/<группа>/`
- логи сессий: `client-handoff/transcripts/`
```

## Формат transcript

Имя файла — **человекочитаемое**:
`transcripts/<YYYY-MM-DD>--<HH-MM>--<тема>.md` (напр.
`2026-06-05--14-25--dachniki.md`). Три части — дата, время, тема —
разделены **двойным тире** `--` для читаемости; внутри части — одинарный
дефис. Время в имени через дефис (`14-25`, `:` запрещён в именах на
Windows), в заголовке транскрипта — через двоеточие (`14:25`). Тема —
короткий слаг обсуждаемой группы клиентов; дата-время делают имя
уникальным.

Транскрипт — **верный лог сессии**: пишется последовательно, не
редактируется (в отличие от summary). Каждый блок несёт и **варианты,
которые скилл предлагал** (клиент их обычно теряет — а аналитику ценно
видеть, из чего выбирали), и итоговый ответ:

```markdown
# Сессия <YYYY-MM-DD> <HH:MM> · <тема> (группа: <бизнес-название>)

## <бизнес-название блока>
**Вопрос:** <текст вопроса>
**Что предлагал:**
- <вариант 1>
- <вариант 2>
- <вариант 3>
- свой ответ
**Выбрано:** <вариант или свой текст клиента> — <пояснение, если было>

## <следующий блок>
…
```

Варианты берутся из буфера `_session-log` (там они уже записаны как
`### Опции`). Последовательно, forward-only.
