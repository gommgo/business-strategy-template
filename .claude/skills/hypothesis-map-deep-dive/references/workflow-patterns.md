# Три режима ведения сеанса

Скилл выбирает режим по виду args.

## A. Новая сущность

**Сигнал:** args = `<kind>` или `<kind>:<новый-slug>`.

1. Прочитать `docs/hypothesis-map/README.md` (`Критерии`, `Anti-patterns`,
   форма ячеек). Освежить `methodology.md`; для metric — `metric-spine.md`.
2. Раунд 1 `AskUserQuestion` — фундамент: `slug` (Other), `name` (Other),
   `description` (Other; для hypothesis вместо него — четыре части). Здесь
   же спросить `business-problem` (к какой проблеме(ам) относится; опции —
   существующие строки реестра `docs/business/business-problem.md` +
   «новая проблема»; M:N). Реестр пуст — сначала завести проблему через
   `/business-deep-dive business-problem`.
3. Записать строку со `status=draft`, `business-problem` проставлен, прочее `—`.
4. Раунд 2+ — батч по доменным слотам kind (см. `field-checklists.md`).
   До 4 вопросов. Перемежать опции (anti-patterns / enum / выбор проблемы /
   соседи / сегмент для subject / метрика для «тогда») и Other (значения).
5. Ссылка на несуществующий slug → **stub** (см. SKILL.md), продолжить.
6. Чек-лист `draft-stable.md`. Все ✅ → предложить stable.
7. Записать `../entrypoint/state/hypothesis-map/<kind>/<slug>.md`, если есть что.
8. Предложить следующий шаг по `phases.md`.

## B. Сырьё

**Сигнал:** args = транскрипт интервью / заметки бизнеса.

1. Прочитать материал внимательно.
2. Определить, **о какой проблеме(ах)** материал — если в реестре
   подходящей строки нет, предложить завести проблему первой (через
   `/business-deep-dive business-problem`).
3. Извлечь кандидатов **только то, что прямо названо** (не угадывать),
   проставив каждому `business-problem`:
   - goal — какой результат/успех назван;
   - metric — какие числа/KPI упомянуты;
   - subject — чьё поведение хотят изменить;
   - hypothesis — какая причинная идея «если/то» прозвучала;
   - task — какие проверки/эксперименты названы.
4. Показать план в чате, `AskUserQuestion` — подтвердить/поправить
   (в том числе привязку к проблеме).
5. Завести **stub'ы** с `business-problem`, создать state-заметки «извлечено из
   сырья — уточнить ⟨что⟩».
6. `AskUserQuestion` — какую углубить первой (по логике фаз) → режим C.

### Что НЕ делать в B

- Не объявлять извлечённое «зафиксированным» (это кандидаты).
- Не угадывать `motivation`, части гипотезы, поля метрики — только
  `name`/`description` близко к языку аналитика/бизнеса.
- Не выдумывать кандидатов, которых в материале нет.
- Не оставлять кандидата без `business-problem` — если проблема неясна, спросить.

## C. Углубление

**Сигнал:** args = `<kind>:<slug>` существующей записи.

1. Прочитать строку + `../entrypoint/state/hypothesis-map/<kind>/<slug>.md`.
   Отметить её `business-problem` — все проверки соседей идут в пределах этих
   проблем.
2. Прочитать соседей семантически **в пределах проблем записи** (для
   hypothesis — её subject и metric той же проблемы; для metric — её goal
   и какие гипотезы той же проблемы бьют).
3. Найти: пустой/невалидный `business-problem`; пустые обязательные слоты;
   подозрения по anti-patterns; методологические тупики в пределах
   проблемы (метрика без влияния, задача без гипотезы, «тогда» без метрики
   той же проблемы, субъект без сегмента).
4. Раунд `AskUserQuestion` (до 4): дыры → Other; anti-pattern → «да/нет
   почему»; тупик → «связать с ⟨варианты⟩ / оставить, потому что Other».
5. Применить ответы; обновить state.
6. Чек-лист `draft-stable.md`. Все ✅ → предложить stable.
7. Осталась дыра/подозрение → следующий раунд.

## Стиль вопросов

### Когда давать опции

| ситуация | формат |
|---|---|
| anti-pattern | две опции «соответствует / не соответствует (Other почему)» |
| enum (`metric.kind`, `metric.direction`, `subject.kind`) | по опции на значение |
| привязка к проблеме (`business-problem`) | по опции на каждую строку реестра (можно несколько) + «новая проблема» (Other) |
| выбор существующего slug соседа | по опции на каждого + «нужен новый» (Other) |
| сегмент для `subject.segments` | по опции на каждый `ajtbd/segment` + «другой/без» |
| работа для `hypothesis.jobs` | по опции на каждый `ajtbd/job` + «нет» |
| метод атрибуции метрики | опции из списка `metric-spine.md` |
| перепрыгивание фазы | две-три опции «потому что X/Y/Other» |

### Когда только Other (значения)

`name`, `description`, текст цели, четыре части гипотезы, `motivation`
субъекта, поля метрики `source`/`attribution`/`acceptance`/`evidence`,
любой ещё не существующий slug. **Это священная экспертиза бизнеса — не
выдумывать.**

### Чего не делать

- Не предлагать «образцы» доменных формулировок от себя. Примеры в README —
  иллюстрация канона, не варианты для текущего проекта.
- Не более 4 вопросов в раунде.
- Не закрывать сессию без чек-листа хотя бы по одной правленой сущности.
