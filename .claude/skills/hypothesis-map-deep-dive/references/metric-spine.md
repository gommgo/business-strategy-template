# Хребет метрики (фаза `metric`)

Метрика — **ядро** слоя и самое сложное. Методология даёт измерительный
каркас; этот файл достраивает дисциплину **честного измерения** под наши
условия (best-effort таргет, не гарантия; ради общей ясности, не суда).

## Что даёт методология

Карта гипотез: метрика = параметр + **желаемое + текущее**; деление
**опережающая/запаздывающая**; **балансирующие** («не сделали хуже» —
удерживаем); **запрет бинарных**; требование объективной измеримости;
«метрик столько, чтобы однозначно определить достижение цели».

## Чего методологии не хватает — достраиваем в полях `metric.md`

| поле | зачем (риск без него) |
|---|---|
| `current` (baseline + дата + окно) | от чего считаем шаг; без даты заказчик двигает старт, без окна аномальный день идёт за базу. Берётся из `business/current-metric.md` |
| `target` (+ тип: absolute/delta/relative — в тексте) | «на 20%» vs «до 20%» — классический спор |
| `direction` (`up`/`down`/`hold`) | при «снизить отток» рост без direction выдают за успех |
| `source` (источник истины) | две системы → два числа → спор о «настоящем» |
| `attribution` | главный вопрос: как доказать НАШ вклад, а не сезон/рынок |
| `acceptance` (предикат + окно + порог) | однозначное «сдвинулось/нет», без «примерно/существенно» |
| `evidence` (протокол замера) | кто снимает, как, где хранится; устное «померили» — не доказательство |
| `kind` (`leading`/`lagging`/`balancing`) | leading в таргете без lagging = целимся в индикатор, не в результат |

## Атрибуция (от сильного к слабому)

Главный риск best-effort модели — приписать (или не приписать) сдвиг
нашему проекту. Один основной метод фиксируется в `attribution`:

1. **Рандомизированный A/B** — случайные тест/контроль; вычитает сезон и
   рынок. Сильнейшее.
2. **Контрольная группа** без рандомизации — сопоставимый сегмент/филиал
   без внедрения.
3. **Difference-in-Differences** — «разница разниц», отсекает стартовое
   неравенство и общий тренд.
4. **Baseline-период (before/after)** — слабый; усиливать год-к-году,
   рыночным бенчмарком, удлинённым окном.
5. **Изоляция фактора** — заказчик не запускает параллельных инициатив на
   ту же метрику в окне (зафиксировать в `business/business-problem.md`/state).

Правило: слабый метод допустим только с расширенным разделом
«вне контроля» (`out-of-control`) в `business/business-problem.md` и
пониженной планкой притязаний.

## Guardrail (балансирующие)

Целевую **двигаем**, guardrail **удерживаем в коридоре**, чтобы «улучшили
одно — сломали другое» не прошло (конверсия демпингом ↔ обрушенная маржа).
В `metric.md`: `kind=balancing`, `direction=hold`, в `target` — порог
коридора. Каждая целевая несёт ≥1 guardrail **в пределах своей проблемы**,
закрывающую очевидный способ «сжульничать». Метрика тегируется проблемой
через `problem` (массив, обычно те же проблемы, что у её цели).

## Leading vs lagging

- **lagging** — итоговый бизнес-результат (отток, выручка, конверсия в
  деньги). Это то, во что целимся по существу.
- **leading** — опережающий индикатор (частота визитов, открытие
  напоминаний). Полезен как ранний сигнал по ходу и как метрика гипотезы
  (`hypothesis.so`), но не подменяет lagging-цель.

## Вопросы фасилитации метрики (раунды AskUserQuestion)

1. «Какие метрики однозначно покажут достижение цели?» (Other)
2. «Текущее значение и на какую дату? Откуда берём (источник истины)?»
   (`current` — кандидат из `business/current-metric.md`)
3. «Опережающая или запаздывающая?» (опции `leading`/`lagging`)
4. «Что НЕ должны ухудшить, пока двигаем эту? (guardrail)» (Other)
5. «Как докажем, что сдвинул именно проект, а не сезон/рынок?» (опции
   методов атрибуции из списка выше)
6. «Что считаем приёмкой — однозначное правило „сдвинулось“?» (Other:
   предикат + окно + порог)

## Анти-паттерны (для секции `Anti-patterns` README и аудита)

- Бинарная метрика как результат («запущен модуль»).
- Метрика без формулы/источника (спорный термин рушит приёмку).
- Нет `current` (нет точки отсчёта).
- Обязательство без атрибуции (сдвиг припишут сезону).
- leading вместо lagging как существо цели.
- Целевая без guardrail (в пределах её проблемы).
- Метрика без `problem` (вне реестра — непонятно, какой проблемы касается).
- Размытый критерий приёмки («существенно вырастет», точечный замер без
  окна).
- **Метрика подана как гарантия** — нарушает юр-рамку
  (`business/business-problem.md`).
