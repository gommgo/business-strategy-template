# 6 фаз Карты гипотез

Скилл ведёт аналитика по фазам как по карте: всегда видно, где мы, что
закрыто. **Порядок — рекомендация, не закон.** Порядок следует методологии:
`goal` → `metric` → `subject` → `hypothesis` → `task` → `cohesion`.
Строим **набегающей волной** — неточно, потом уточняем.

Слой **многопроблемный**: реестр проблем — `docs/business/business-problem.md`.
Фазы считаются **в пределах одной проблемы**: сначала выбираем, по какой
идём, потом смотрим её дерево. Каждая заводимая запись тегируется
проблемой(ами) через `business-problem` (массив строк реестра, M:N).

## Карта фаз

### 1. `goal` — цели карты

**Триггер:** у выбранной проблемы нет целей (нет `goal` с её `business-problem`).

**Цель:** критерий успеха **без цифр**, выросший из приоритетной ставки
SWOT (`swot/bet.promoted-to = goal:...`).

**Что копать:** «по каким критериям поймём, что достигли?» + шатание
(утрировать, отбросить часть, щупать границу, «зачем вам этот результат?»).
Откуда пришла цель (`from-bet`).

**Анти-паттерны:** цифра внутри цели; задача вместо цели; цель без метрики.

**Переходы после:** `metric` — навесить измеримость.

### 2. `metric` — метрики цели

**Триггер:** есть цель, нет метрик. Ядро слоя — см. `metric-spine.md`.

**Цель:** метрики, однозначно показывающие достижение цели: baseline +
target, источник истины, атрибуция, критерий приёмки, guardrail. `business-problem`
метрики обычно совпадает с проблемой её цели.

**Что копать:** «какие метрики однозначно покажут достижение? текущее/
желаемое? опережающая/запаздывающая? что нельзя ухудшить (balancing)? откуда
число? как докажем наш вклад? что считаем приёмкой?». `current` берётся из
`business/current-metric.md`.

**Анти-паттерны:** бинарная; без baseline; без источника; без guardrail
(в пределах проблемы); **метрика как гарантия**.

**Переходы после:** `subject` — через чьё поведение двигаем.

### 3. `subject` — субъекты влияния

**Триггер:** есть метрики, нужно понять, чьё поведение их двигает.

**Цель:** субъекты (носители самодвижения) + мотивация (боли/желания) +
связь с сегментом (`segments` — обяз. для `positive`, опц. для
`negative`). Негативный субъект — если есть противодействие.

**Что копать:** «чьё поведение изменить, чтобы двинулась метрика?» (не
исполнитель). «Какие боли/желания?» + пять «ну и что?» до корневой.

**Связь с AJTBD-сегментом (read-only).** Субъект влияния семантически
вырастает из `ajtbd/segment` — группы клиентов по бандлу работ. Заводя или
углубляя субъект, заглянуть в `docs/ajtbd/segment.md` (read-only) и через
`AskUserQuestion` связать субъект с конкретным сегментом (`segments` —
обяз. для `positive`, опц. для `negative`; опции — существующие сегменты +
«другой/без сегмента»); мотивация опирается на success-criteria сегмента и
его трения (`segment-problem.drivers`/`barriers`), не выдумывается. Нет
сегментов — подсказать `/segment-deep-dive`. Сегмент ≠ субъект.
Негативный субъект (конкурент, регулятор) сегмента не требует — `—`. Опц.
`users` — связь с `projects/<slug>/user`.

**Анти-паттерны:** исполнитель вместо субъекта; субъект без мотивации;
система без воли; **позитивный** субъект без сегмента (`segments` пуст;
негативному сегмент не нужен).

**Переходы после:** `hypothesis` — на каждую боль/желание гипотеза.

### 4. `hypothesis` — гипотезы

**Триггер:** есть субъект с мотивацией, нет гипотез.

**Цель:** гипотезы в 4 частях (если·то·потому что·тогда→metric).

**Что копать:** «„если“ — принцип или уже задача? „то“ — поведение
субъекта? „потому что“ на его боли? „тогда“ — на какую метрику и как?». На
какую работу сегмента целит (`jobs`, опц.).

**Анти-паттерны:** конкретная задача в «если»; «тогда» не о метрике;
пустое «потому что»; запрос на анализ вместо гипотезы.

**Переходы после:** `task` — под приоритетные гипотезы задачи.

### 5. `task` — задачи проверки

**Триггер:** есть гипотезы, нет задач.

**Цель:** активности, которыми проверяем гипотезы. Каждая привязана к
гипотезе (сирота запрещена).

**Что копать:** «чем проверим эту гипотезу? эксперимент/замер/пилот? к
какой гипотезе крепится?».

**Анти-паттерны:** задача-сирота; инженерный тикет реализации; задача как
цель.

**Переходы после:** `cohesion`.

### 6. `cohesion` — целостность

**Триггер:** все kinds выбранной проблемы имеют записи, фокус —
целостность её карты.

**Цель:** проверить инварианты методологии **в пределах проблемы** (см.
README слоя), повысить проходящие чек-лист записи `draft → stable`,
подсветить подозрения (проблема без цели, цель без метрики, метрика без
влияния, позитивный субъект без сегмента), предложить `/hypothesis-map-audit` и
`/cross-audit`, передать цель/метрику/субъект в проект(ы)
`docs/projects/<slug>/` (связь проблема↔проект — M:N, авторски на стороне
продукта через `vision.addresses-problem`).

**Анти-паттерны:** принудительный stable у незрелых; «красный путь» брошен
на полпути; проблема, оставшаяся без единой цели.

## Сводка фаз для UI

Сводка — **по выбранной проблеме**; для остальных проблем даём строку
«закрыта / в работе».

```
Проблема: paid-outflow (1 из 2)
Фазы:
  ✅ goal        — 1 цель stable
  🔄 metric      — 1 draft (текущая)
  ⏳ subject
  ⏳ hypothesis
  ⏳ task
  ⏳ cohesion

Прочие проблемы:
  🔄 slow-onboarding — в работе (фаза goal)
```

✅ — закрыта (≥1 stable, нет blocker); 🔄 — текущая; ⏳ — не начата.

## Перепрыгивание

Цель — рекомендуемый вход, но если бизнес принёс ясную метрику-таргет без
оформленной цели — `AskUserQuestion`: «Завести цель под эту метрику?». Даже
при перепрыгивании запись тегируется `business-problem`. Ответ →
`../entrypoint/state/hypothesis-map/goal/_phase-jump.md` как доменное
решение.
