# hypothesis-map-deep-dive

Формализация **Карты гипотез** заказчика: `goal` · `metric` · `subject` ·
`hypothesis` · `task`. Канон — `docs/hypothesis-map/README.md`. Между SWOT
(`docs/swot/`) и продуктом (`docs/projects/`): стратегическая ставка
(`swot/bet.promoted-to`) дотягивается до измеримой цели и причинной цепи, а
цель/метрика становятся тем, во что целит `vision.Success`.

Слой **многопроблемный**: реестр проблем — `docs/business/business-problem.md`
(одна строка = одна проблема), а каждая запись 5 kind несёт колонку
`business-problem` — массив slug-рефов на строки реестра (M:N). **Проблема —
первичное измерение группировки**: заводя запись, скилл всегда тегирует её
проблемой(ами). Все методологические инварианты считаются **в пределах
одной проблемы**. Связь с продуктом тоже M:N и ведётся авторски на стороне
продукта (`projects/<slug>/vision.addresses-problem`).

Скилл ведёт сеанс через 6 фаз, структурированные вопросы
(`AskUserQuestion`), фиксирует контекст в своей ветке единого дерева
state оркестратора (`../entrypoint/state/hypothesis-map/`), **не выдумывает
бизнес-логику**. Глубинная логика Карты гипотез — `references/methodology.md`;
дисциплина метрик-обязательств — `references/metric-spine.md`.

## Юридическая рамка (держать в голове всю сессию)

Мы гарантируем **доставку проекта на 100% по scope** — твёрдо. Метрики —
**совместный с бизнесом best-effort таргет**, не гарантия исхода. Поэтому
строгость метрик — ради **общей ясности и честного измерения**, не ради
суда. Граница «гарантируем / целимся / вне контроля» живёт в реестре
проблем `docs/business/business-problem.md`. Скилл подаёт метрику только
как таргет: обещание результата нарушило бы юридическую рамку.

## Связь с соседними слоями (read-only)

- **Вход из SWOT.** Ставка `swot/bet.promoted-to = goal:...`/`hypothesis:...`
  — зародыш цели/гипотезы. Read-only заглянуть в `docs/swot/bet.md`: какие
  ставки доведены сюда. Ставка изоморфна зародышу гипотезы («действие» →
  «если», «ценность» → «тогда»).
- **Baseline из бизнеса.** `metric.current` берётся из
  `business/current-metric.md` (read-only) — текущий KPI становится
  baseline целевой.
- **Субъект из сегмента AJTBD.** `subject.segments` связывает субъект
  влияния с `ajtbd/segment` — обяз. для `positive` (мотивация субъекта
  опирается на success-criteria сегмента и его трения `segment-problem`,
  не выдумывается); для `negative` (конкурент, регулятор, внешняя сила)
  сегмент опц. Опц. `subject.users` — связь с пользователем продукта.
- **Гипотеза в работу.** `hypothesis.jobs` (опц.) — на какую работу
  сегмента (`ajtbd/job`) целит гипотеза.
- **Стейкхолдеры бизнеса.** Лицо-решатель внутри заказчика
  (`business/stakeholder.md`) может быть тем же человеком, что `subject` —
  через `stakeholder.manifests-as = subject:<slug>`; согласуй мотивации
  (один человек — один портрет). Властный внутренний `blocker`/`skeptic`
  — кандидат в `subject.kind: negative` там, где его поведение двигает
  метрику. И `goal` не должна **противоречить** `strategic-stance`
  властного (`power: high`) лица — иначе стратегия мертва на старте.
  Стейкхолдеров не выдумывает (заводятся в `business`); сквозная сверка —
  `/cross-audit` (`stakeholder-subject` · `stakeholder-strategy`).

**Сегменты, трения, ставки, стейкхолдеров не выдумывает**; перенос их
смысла — через `AskUserQuestion`. Автозалива нет.

## Точки входа

| вызов | поведение |
|---|---|
| `/hypothesis-map-deep-dive` | сводка по фазам + ходы на выбор |
| `/hypothesis-map-deep-dive <kind>` | завести новую сущность типа kind (режим A) |
| `/hypothesis-map-deep-dive <kind>:<slug>` | углубить существующую запись (режим C) |
| `/hypothesis-map-deep-dive <slug>` | найти slug; одиночный → C; конфликт kind → переспросить |
| `/hypothesis-map-deep-dive <свободный текст / транскрипт>` | сырьё → разбор (режим B) |
| `/hypothesis-map-deep-dive --phase <name>` | принудительно работать в фазе |

`kind` ∈ {`goal`, `metric`, `subject`, `hypothesis`, `task`}.

`phase` ∈ {`goal`, `metric`, `subject`, `hypothesis`, `task`, `cohesion`}.

## Что делать сразу при запуске

1. Прочитать `docs/hypothesis-map/README.md` — освежить канон 5 kinds,
   юр-рамку и методологические инварианты.
2. Прочитать `references/methodology.md` (Карта гипотез) и `references/phases.md`.
   При работе с `metric` — `references/metric-spine.md`.
3. **Прочитать реестр проблем** `docs/business/business-problem.md` —
   строки-проблемы, по которым скоупятся записи. Нет ни одной проблемы →
   подсказать завести через `/business-deep-dive business-problem`.
4. Если args пустые — **сводка по фазам** + `AskUserQuestion` с выбором
   хода.
5. Если args указывают на сущность — определить kind и режим (A/B/C) по
   `references/workflow-patterns.md`.

Как говорить о ходе, словах и вариантах — `.claude/rules/guiding.md`;
условия работы, названные человеком, читаются до первого вопроса.

## Сводка состояния (без args)

1. Прочитать все 5 табличных файлов + реестр проблем
   `docs/business/business-problem.md`.
2. Перечислить **проблемы** (строки реестра); подсчитать `draft`/`stable`
   по каждому kind, разложив записи по `business-problem` (массив-реф).
3. Прочитать свою ветку `../entrypoint/state/hypothesis-map/` и read-only
   остальное дерево (см. «Единый контекст») — собрать `**blocker**`-вопросы.
4. **Фазы считаются в пределах проблемы.** Если проблем несколько —
   сначала выбрать, по какой идём (`AskUserQuestion`), затем определить её
   текущую фазу по дереву (на записях, чей `business-problem` содержит выбранную):
   - нет целей с этой проблемой → `goal`;
   - нет метрик → `metric`;
   - нет субъектов → `subject`;
   - нет гипотез → `hypothesis`;
   - нет задач → `task`;
   - всё заполнено, но есть draft/blocker → `cohesion`.
5. Вывести карту фаз (как в `references/phases.md`, раздел «Сводка фаз») —
   по выбранной проблеме; для остальных — краткая сводка «закрыта/в работе».
6. Через `AskUserQuestion` предложить: продолжить фазу / переключиться на
   другую проблему / перепрыгнуть фазу / разобрать сырьё.

## Фазы проработки

Скилл **проактивно** ведёт через 6 фаз. Полная карта — `references/phases.md`.
Фазы считаются **в пределах одной проблемы**; каждая заводимая запись
тегируется проблемой(ами) через `business-problem`:

| фаза | цель | артефакты |
|---|---|---|
| `goal` | цели карты (критерий успеха без цифр), из ставки SWOT | `goal.md` |
| `metric` | измеримые метрики цели (baseline/target/атрибуция/приёмка) | `metric.md` |
| `subject` | субъекты влияния + мотивация, связь с сегментом | `subject.md` |
| `hypothesis` | гипотезы (если·то·потому что·тогда) | `hypothesis.md` |
| `task` | задачи проверки гипотез | `task.md` |
| `cohesion` | целостность карты проблемы + повышение draft → stable | все |

Строится **набегающей волной** (неточно → уточняем), не водопадом
(см. `methodology.md`, «красный путь»).

## Три режима

См. `references/workflow-patterns.md`; обязательные поля и порядок
заполнения по kind — `references/field-checklists.md` (открыть в раундах
по слотам):

- **A. Новая сущность.** Args = `<kind>` или `<kind>:<новый-slug>`.
  Батч `AskUserQuestion` по `Критерии <kind>` из `docs/hypothesis-map/<kind>.md`;
  опции — anti-patterns из `Что <kind> НЕ` того же файла и `Anti-patterns`
  README слоя; значения — через Other. Всегда спросить **к какой
  проблеме(ам) относится** (`business-problem`; опции — существующие
  строки реестра + «новая»).
- **B. Сырьё.** Args = транскрипт / заметки. Извлечь кандидатов
  (goal/metric/subject/hypothesis/task), определить, **о какой проблеме(ах)**
  материал, показать план, по подтверждению завести stub'ы с `business-problem`,
  углубить через C.
- **C. Углубление.** Args = `<kind>:<slug>`. Точечные вопросы по дырам и
  методологическим подозрениям (всё — в пределах проблем записи); чек-лист
  `draft → stable`.

## Стиль вопросов

См. `references/workflow-patterns.md`. Краткий канон:

- **Всегда через `AskUserQuestion`**, до 4 вопросов в раунде.
- **Опции** — для: anti-patterns; enum (`metric.kind`, `metric.direction`,
  `subject.kind`); выбора существующего slug соседа (метрика для «тогда»,
  субъект для гипотезы, сегмент для `subject.segments`, работа для
  `hypothesis.jobs`); **выбора проблемы(ам)** для `business-problem`; метода
  атрибуции метрики.
- **Свободная форма (Other)** — для значений: `name`, `description`, текст
  цели, четырёх частей гипотезы (`if`/`then`/`because`/`so`), мотивации
  субъекта, полей метрики (`source`/`attribution`/`acceptance`).
- Бизнес-формулировки (текст цели, части гипотезы, мотивация, поля
  метрики) даёт аналитик: это экспертиза бизнеса (`CLAUDE.md` §3), и
  догаданная формулировка стала бы ложным основанием для решений.
  Anti-patterns как опции — да; сами тексты — нет.

## Память — своя ветка единого дерева

Весь аналитический state — **одно дерево** у оркестратора. Скилл своего
`state/` не держит: per-kind заметки пишет в **свою ветку**
`../entrypoint/state/hypothesis-map/<kind>/<slug>.md`
(`goal` · `metric` · `subject` · `hypothesis` · `task`). Формат — канон
`../entrypoint/references/state-model.md`. Три опциональные секции:
`## Открытые вопросы` (опц. `**blocker**` — блокирует `draft → stable`),
`## Доменные решения`, `## Что копать дальше`. Forward-only. Файл/ветка
создаются по требованию; пустые секции — удалить.

**Единый контекст (read-only).** Скилл видит **всё дерево**
`../entrypoint/state/` — SWOT (`swot/` — ставки, доведённые сюда),
бизнес-слой (`business/` — реестр проблем, current-metric, стейкхолдеры:
лицо ↔ субъект через `manifests-as`, властный блокер ≈ negative-субъект,
стойка властного лица как рамка целей), разведку
AJTBD (`ajtbd/` — сегменты и работы), проект
(`projects/<slug>/`), срез оркестратора (`index.md`/`threads/`) — плюс
клиентский дом `../entrypoint-for-business/state/` (правила —
`cross-read.md`). **Своя ветка — rw, чужое — read-only; в чужое не
пишет.**

## Методологические инварианты (семантические, не slug-grep)

Связи **не валидируются slug-целостностью** — они семантические. Все
инварианты считаются **в пределах одной проблемы** (`business-problem`).
Методологические инварианты ловит рой `/hypothesis-map-audit`. Скилл **в
процессе** держит их в голове и поднимает при углублении и cohesion:

- каждая запись 5 kind несёт непустой `business-problem` (массив строк реестра);
- у каждой проблемы (строки реестра) есть ≥1 `goal` — иначе она повисла;
- у каждой `goal` есть ≥1 `metric`;
- задача-сирота (`task` без `hypothesis`) запрещена (ресурсный фильтр);
- `hypothesis.so` бьёт в конкретную `metric` той же проблемы; `because`
  опирается на `subject.motivation`; «если» — наше воздействие-принцип,
  «то» — поведение субъекта;
- целевая `metric` без влияющей гипотезы (в пределах её проблемы) —
  мёртвая; у каждой целевой есть ≥1 `balancing` в той же проблеме;
- субъект — носитель самодвижения, не исполнитель;
- **метрика никогда не подана как гарантия**.

Сам скилл — **не аудитор**; в конце сессии предложит `/hypothesis-map-audit`
или `/cross-audit`.

## Контракт `draft → stable`

См. `references/draft-stable.md`. Чек-лист после каждой правки: обязательные
слоты заполнены · `Критерии <kind>` подтверждены аналитиком · `Anti-patterns`
не нарушены · нет `**blocker**` в state. Все ✅ → предложить повышение через
`AskUserQuestion`. Скилл **не повышает сам**.

## Stub-сущности

Если копаемая сущность ссылается на ещё не существующий slug (гипотеза
упомянула метрику, которой нет): завести stub-строку (`slug + name +
description/части + business-problem + status=draft`, прочее `—`; `business-problem` обычно
наследует проблему(ы) сущности-инициатора), записать state-заметку
«заведён как stub в контексте `<откуда>` — докопать в фазе `<phase>`»,
вернуться к исходной.

## Удаление сущности (каскад)

1. Прочитать все 5 файлов + свою ветку `../entrypoint/state/hypothesis-map/`
   — найти семантические упоминания slug (`metric.goal`,
   `hypothesis.subject`/`metric`, `task.hypothesis`).
2. Показать каскад. Через `AskUserQuestion` по каждому месту: «заменить на
   другой slug» / «удалить упоминание» / «оставить».
3. Применить пакетом. Удалить запись из файла и
   `../entrypoint/state/hypothesis-map/<kind>/<slug>.md`.
4. Если удалена единственная метрика цели — спросить, не пора ли
   пересмотреть `goal`. Если удалена строка реестра проблем (сущность
   чужого слоя `docs/business/`) — у записей, чей `business-problem` ссылался
   только на неё, спросить, к какой проблеме переотнести или удалить.

## Завершение сессии

1. Перечислить затронутые сущности (заведены/углублены/удалены/повышены).
2. Перечислить нерешённые `**blocker**`-вопросы.
3. Назвать текущую фазу и ходы дальше — два-три, один рекомендован.
4. Через `AskUserQuestion` предложить: `/hypothesis-map-audit` (инварианты
   Карты гипотез роем, по каждой проблеме) / `/cross-audit` (стыки с
   business — в т.ч. стейкхолдеры: `stakeholder-subject`/`stakeholder-strategy`
   — swot, ajtbd и проектами) / передать цель/метрику/субъект в
   проект(ы) `docs/projects/<slug>/` (связь проблема↔проект — M:N,
   авторски на стороне продукта через `vision.addresses-problem`).
5. Если субъект не опёрт на сегмент или метрике не хватает baseline —
   подсказать, что сегменты собираются в `docs/ajtbd/`
   (`/segment-deep-dive`), а baseline — в `business/current-metric`
   (`/business-deep-dive`).

Скилл **сам не вызывает** другие скилы — аналитик запускает.

Как говорить о ходе, словах и вариантах — `.claude/rules/guiding.md`:
итог сессии, ходы дальше и строка «как продолжить» идут по нему.

## Границы

- Метрика — best-effort таргет, не гарантия (см. «Юридическая рамка»).
- Факторы и ставки живут в `docs/swot/` (`/swot-deep-dive`), строки реестра
  проблем — в `docs/business/` (`/business-deep-dive business-problem`);
  сюда приходят `bet.promoted-to` и ссылки через колонку
  `business-problem`.
- Статус записи меняет аналитик: `draft → stable` — по его подтверждению,
  `stable → draft` скилл только подсвечивает.
- Пишет скилл в `docs/hypothesis-map/` и свою ветку
  `../entrypoint/state/hypothesis-map/`; остальное дерево state и клиентский
  дом — только чтение.
