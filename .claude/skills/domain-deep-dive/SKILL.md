# Skill: domain-deep-dive

Проектирование бизнес-домена. Превращает минимальные драфты артефактов
(frontmatter + properties + методы по имени) в полные `status: stable`
артефакты, сверенные с канон-формой и явно подтверждённые архитектором.

Домены живут **внутри проекта**: данные — в
`docs/projects/<project-slug>/domains/<context>/`, форма-канон и шаблоны —
один раз в `docs/projects/_canon/domains/`. Сессия всегда идёт в контексте
**одного проекта**: скилл принимает `<project-slug>` первым аргументом, без
него — предлагает пикер по папкам `docs/projects/` (кроме `_canon`). Все
чтения и записи скоупятся в `domains/` выбранного проекта.

Это **source of truth** проектирования (design-time): артефакты — чистая
язык-агностичная аналитика домена. Канон артефактов и обязательных секций —
`docs/projects/_canon/domains/README.md`; скилл его не дублирует, а исполняет.
Маппинг DDD → конкретный код (Go-раскладка `internal/domain/<ctx>/`) живёт
не здесь, а в соседнем backend-репо (`<org>/backend`, форк
`go-backend-template`), его `docs/reference/domain-mapping.md` — он
потребитель этих stable-артефактов.

Этот слой — опциональный и **завершается на stable-артефакте**. Что с ним
делают соседние форки (scaffold доменов в код) — забота тех репо, не этого
скилла.

## Главный ритм: AskUserQuestion

Скилл — **интервьюер архитектора**, не редактор. Партнёр по диалогу —
архитектор сервиса (тот, кто проектирует домены и стек); его решения
дословно ложатся в артефакт, скилл их **не сочиняет**. Каждый шаг
сеанса — раунд `AskUserQuestion` (до 4 вопросов за раунд, иначе
следующий раунд) → получаем ответ → пишем в артефакт через `Edit` →
следующий раунд.

**Никаких альтернатив этому ритму нет.** В частности:

- ❌ Длинный prose-ответ «вот как я бы спроектировал X» вместо вопросов.
- ❌ «По умолчанию» применить решение, потому что «обычно делают так».
- ❌ Молча достроить пропущенные секции, потому что они «очевидны».
- ❌ Один большой `AskUserQuestion` с попыткой влезть >4 вопросов —
  лимит инструмента, инструмент режет молча.
- ❌ Скопить ответы «запишу в конце волны» — пиши после **каждого**
  раунда, иначе теряется при `/clear`.
- ✅ Сомневаешься, чего хочет архитектор → лишний раунд вопросов, а не
  догадка.

Бизнес-решения скилл **не выдумывает**. Он формулирует falsifiable-
вопрос и пишет ответ архитектора дословно. Anti-pattern'ы из канона — даёт
как опции; тексты доменных полей (инварианты, preconditions, имена,
описания) — только через свободную форму (Other).

## Выбор проекта

Сессия всегда скоупится в **один проект**. До любой работы определи
`<project-slug>`:

- `<project-slug>` передан первым аргументом
  (`/domain-deep-dive <slug> …`) — берём его.
- Аргумент отсутствует — `AskUserQuestion`-пикер по подкаталогам
  `docs/projects/` **кроме `_canon`** (это образец формы, не проект). Одна
  опция на проект + Other. Без выбора проекта сессия не идёт.

Дальше в этом файле `<P>` = `docs/projects/<project-slug>` для краткости:
данные доменов — `<P>/domains/<ctx>/`, форма-канон и шаблоны — один раз в
`docs/projects/_canon/domains/`.

## Точки входа

`<slug>` — slug проекта (если опущен в любом вызове — пикер, см. выше).

| вызов | поведение |
|---|---|
| `/domain-deep-dive <slug>` | сводка состояния всех контекстов проекта + топ-3 кандидата на углубление |
| `/domain-deep-dive <slug> <ctx>` | сводка по контексту + AskUserQuestion: что углубить / что завести |
| `/domain-deep-dive <slug> <ctx>:<kind>` | завести новую сущность типа `kind` в контексте `ctx` (режим **A**) |
| `/domain-deep-dive <slug> <ctx>:<kind>:<Name>` | углубить существующий артефакт (режим **C**); если `Name` не существует — режим A с заданным именем |
| `/domain-deep-dive <slug> <свободный текст / приложение>` | сырьё → разбор (режим **B**) |

`kind` ∈ {`aggregate`, `entity`, `event`, `use-case`, `policy`, `vo`}
(`vo` — только для `_shared/`; внутри-контекстный VO живёт inline в
aggregate-файле и kind-ом отдельно не заводится).

## Что делать сразу при запуске

1. Определить `<project-slug>` (см. § Выбор проекта).
2. Прочитать `docs/projects/_canon/domains/README.md` — освежить канон
   (kinds, обязательные H2, anti-patterns).
3. Прочитать `docs/projects/_canon/project/README.md` +
   `references/project-context.md` — освежить связи с продуктовым слоем
   **того же проекта** (domain ↔ capability, adapter ↔ integration).
4. Если args (после slug) пустые — сделать сводку (см. ниже) и через
   `AskUserQuestion` предложить выбор: что копать / что заводить.
5. Если args указывают на контекст/сущность — определить kind и режим
   (A/B/C), применить маршрут из `references/workflow-patterns.md`.

## Сводка состояния

1. `ls <P>/domains/` — список контекстов проекта.
2. На каждый контекст: пройтись по `<ctx>/*.md`, `<ctx>/events/*.md`,
   `<ctx>/use-cases/*.md`, `<ctx>/policies/*.md`; для каждого артефакта
   считать `status`, `kind` и **сколько обязательных H2-секций заполнено**
   (см. `references/field-checklists.md`).
3. Сверить артефакты с канон-формой (`docs/projects/_canon/domains/README.md`
   + `references/field-checklists.md`) вручную: frontmatter, обязательные H2,
   ref-целостность. Если всё `stable` и без дыр — выйти: «спроектировано,
   делать нечего». Committed-валидатора в этом репо нет — проверка ручная,
   по чек-листу (см. `references/draft-stable.md`).
4. Прочитать свою ветку
   `../entrypoint/state/projects/<project-slug>/domains/` (если есть) —
   секции `## Открытые вопросы`; пометки `**blocker**` приоритетны.
5. Выявить топ-3 «горячих» кандидата на углубление:
   - draft-артефакты с `**blocker**`-вопросами;
   - draft-артефакты с большим числом пустых обязательных H2;
   - draft-артефакты, на которые ссылаются stable-соседи (`relations`,
     `emits`, `consumes`) — блокируют корректность соседа.
6. Сжатая карта в чат:

   ```
   ## Состояние <P>/domains/<ctx>

   | артефакт | kind | status | H2 заполнено | дыры |
   |---|---|---|---|---|
   | User.md | aggregate | draft | 6/12 | Invariants, Lifecycle, Events, Relations, VOs, Use Cases |
   | events/UserRegistered.md | event | draft | 1/4 | Payload, Consumers, Delivery |
   ```

7. Через `AskUserQuestion` — что копать дальше (опции = кандидаты + «другой»).

## Три режима

Детали — `references/workflow-patterns.md`. Краткая семантика:

- **A. Новая сущность.** Args = `<ctx>:<kind>` или `<ctx>:<kind>:<новый-Name>`.
  Скилл копирует шаблон из `docs/projects/_canon/domains/_templates/<kind>.md`
  в нужный путь под `<P>/domains/`, заполняет frontmatter, заводит минимум
  (имя + одна фраза описания) и погружается в режим C.
- **B. Сырьё.** Args = свободный текст / приложение (транскрипт интервью,
  ER-диаграмма, набросок кода, заметки). Извлекает кандидатов на агрегаты /
  методы / события / use-case'ы, показывает план, по подтверждению — заводит
  stub-артефакты с открытыми вопросами и переходит в режим C по каждому.
- **C. Углубление.** Args = `<ctx>:<kind>:<Name>` существующего артефакта
  либо выбор из сводки. Точечные вопросы по дырам и подозрениям; волны
  inside-out; чек-лист `draft → stable` после каждой правки.

## Inside-out волны (порядок копания)

Режим C идёт волнами; порядок запомнен, у архитектора не спрашивается:

1. **Properties (детали)** — constraints/default/source каждого property всех aggregate'ов.
2. **Methods (детали)** — params/returns/preconditions/postconditions/events для каждого метода.
3. **Invariants** — собрать falsifiable-список и привязать каждый к owning method.
4. **Lifecycle** — таблица переходов (stateful aggregate) или `_N/A (stateless)_`.
5. **Identity** — ID type, mutability, visibility.
6. **Boundary / VOs / Contained Entities / Spanning Invariants** — границы агрегата.
7. **Events** — `events/*.md`: Trigger, Payload, Consumers, Delivery.
8. **Use Cases** — Actor, Inputs, Outputs, Dependencies, Steps, Called methods, Events, Errors.
9. **Policies** — Kind, Inputs, Rules, Outcomes.
10. **Relations** — связи между артефактами + cross-context (по ID, не composition).
11. **Context README / Ubiquitous Language** — финальный роллап.

Юзеру при старте волн в новом контексте — короткое: «иду inside-out, начну
с Properties во всех aggregate'ах этого контекста; скажи если хочешь
прыгнуть в конкретную волну».

## Стиль вопросов

См. `references/workflow-patterns.md § Стиль вопросов`. Кратко — это
**главная дисциплина скилла**:

- **Всегда через `AskUserQuestion`**, до 4 вопросов в одном раунде
  (лимит инструмента).
- **Опции** только для:
  - anti-patterns из секции **Anti-patterns** в
    `docs/projects/_canon/domains/README.md` и из шаблонов («Это I/O-метод
    агрегата вместо use-case?» / «Spanning invariant между двумя
    aggregate'ами?»);
  - enum-поля (`kind`, `Visibility`, `Mutable`, `Channel`, `Source`,
    `Delivery`, `Type of decision`);
  - тест-критерий kind'а (см. `references/draft-stable.md § Тест-критерий`)
    с примерами ✅/❌;
  - выбор существующего соседа (`relations`, `emits` → существующий
    `<ctx>.<Name>` + «нужен новый» через Other).
- **Свободная форма** (через Other) — только для **значения**: `name`,
  `description`, `goal`, имена полей, типы, тексты инвариантов,
  бизнес-семантика.
- **Никогда** не предлагать конкретные тексты доменных полей от себя.
  Anti-patterns как опции — да. Сама формулировка инварианта /
  preconditions / business rule — нет.
- Falsifiable: «Может ли существовать `User` с `Status=blocked` и
  `EmailVerified=false`?» — да. «Какие инварианты у `User`?» — нет.

## Память: своя ветка единого дерева state

Скилл не держит своего `state/`. Per-kind заметки пишутся в **свою ветку**
единого дерева state оркестратора, разложенную по проекту и контексту:

```
../entrypoint/state/projects/<project-slug>/domains/<ctx>/<kind>/<slug>.md
```

Формат заметки — канон `../entrypoint/references/state-model.md`. Кратко:

- `slug` = basename файла артефакта без `.md` (например `User`,
  `UserRegistered`, `RegisterUser`).
- Файл существует, пока есть хоть одна непустая секция.
- Frontmatter: `kind` · `slug` · `ref` (путь к артефакту).
- Три возможные секции (любая может отсутствовать):
  - `## Открытые вопросы` (опц. префикс/суффикс `**blocker**` —
    блокирует переход в stable);
  - `## Доменные решения` (неочевидные смысловые решения, не лезущие
    в `description` / комментарии артефакта);
  - `## Что копать дальше` (локальные next-step'ы по этому артефакту).
- Если все секции пусты — заметку удалить.
- **Forward-only**: не аккумулировать «было/стало», даты сессий,
  «обсуждено такого-то». Только текущее состояние знания. См. правило
  `.claude/rules/forward-only.md`.

Ветка **коммитится** вместе с деревом оркестратора — это общая проектная
память между сессиями и архитекторами. Forward-only (никакого
«было/стало») держит `git log` чистым. Это **не** часть канона
`docs/projects/_canon/domains/` (зафиксированные решения уходят в
`<P>/domains/`, не открытые вопросы), но это часть проектного знания о
домене — клон репо несёт с собой все висящие `**blocker**`-вопросы, на
которые тимейт может ответить.

### Единый контекст: read-only видимость дерева

Для единой картины скилл **read-only** подтягивает всё дерево state
оркестратора `../entrypoint/state/` (срез `index.md`, открытые нити
`threads/`, верхнеуровневые слои `business/`, `ajtbd/`, `swot/`,
`hypothesis-map/`) и клиентский дом `../entrypoint-for-business/state/`.
Проектные ветки `projects/<…>/` читаются **только по текущему
`<project-slug>`** (изоляция продуктов сохраняется). Своя ветка
`projects/<project-slug>/domains/` — **rw**, всё остальное дерево и
клиентский дом — **read-only**: в чужое не писать. При чтении клиентского
дома маркер `**жду аналитика**` трактуется как blocker-кандидат.

## Контракт `draft → stable`

См. `references/draft-stable.md`. Чек-лист после каждой правки артефакта
(все 5 одновременно ✅ → предложить промоушн через AskUserQuestion):

1. **Обязательные H2 заполнены** (см. `references/field-checklists.md`
   по kind). Опциональные могут быть `_N/A_` / `_нет_`.
2. **Все cross-ref'ы валидны** — `relations`, `emits`, `consumes` указывают
   на существующие `<ctx>.<Name>`; `stable` может ссылаться на `draft`
   (это допустимо, не блокирует).
3. **Форма консистентна (ручная сверка)** — frontmatter полон
   (`id`/`kind`/`context`/`name`/`status`), `id` = `<context>.<Name>`,
   basename файла = `name`, все обязательные H2 для kind присутствуют и
   непусты, `relations`/`emits`/`consumes` указывают на существующие
   `<ctx>.<Name>`. Committed-скрипта-валидатора в репо нет — сверяешь по
   `references/field-checklists.md` и `references/draft-stable.md`.
4. **Тест-критерий kind'а явно подтверждён** в этой сессии. См.
   `references/draft-stable.md § Тест-критерий по kind`. Скилл предъявляет
   ✅/❌-пример через AskUserQuestion, архитектор соотносит свою запись.
5. **State чист по `**blocker**`-вопросам.** Другие открытые вопросы при
   stable допустимы (они описывают «хорошо бы узнать», не «здесь смысл
   сломан»).

Все 5 ✅ → через `AskUserQuestion` предложить «Готов к stable, повышаем?»
с опциями «Да, повысить» / «Нет, ещё не уверен» (через Other — что именно
смущает). По «Да» — `Edit`'ом `status: draft → stable`. **Скилл не повышает
сам**, даже при всех ✅.

Понижение `stable → draft` — только архитектор руками (либо явная команда через
AskUserQuestion со смыслом «эту запись надо пересмотреть»). Скилл максимум
может подсветить и предложить.

## Stub-сущности

Если копаемый артефакт ссылается (`relations` / `emits` / `consumes` /
методы) на ещё не существующий `<ctx>.<Name>`:

1. В соответствующем пути (по kind, под `<P>/domains/`) — новая запись
   через шаблон из `docs/projects/_canon/domains/_templates/<kind>.md`:
   `id`, `kind`, `context`, `name` заполнены; `status: draft`; обязательные
   H2-заголовки оставлены пустыми или с заглушкой `_TBD_`.
2. В `../entrypoint/state/projects/<project-slug>/domains/<ctx>/<kind>/<Name>.md`
   — секция `## Открытые вопросы` с записью «Заведён как stub в контексте
   `<откуда сослались>` — докопать» с пометкой `**blocker**`.
3. Возврат в исходный артефакт, копание продолжается. Stub-сосед не
   блокирует stable у исходника: ссылка на `draft`-соседа при stable
   допустима (см. чек-лист `draft → stable`, п. 2).

## Удаление артефакта (каскад)

1. Прочитать все `<P>/domains/**/*.md` +
   `../entrypoint/state/projects/<project-slug>/domains/` — найти все
   ссылки на удаляемый `<ctx>.<Name>` (frontmatter
   `relations|emits|consumes`, markdown-ссылки `[...](...)`).
2. Показать каскад: «ссылаются X, Y, Z — вот что сломается».
3. Через `AskUserQuestion` по каждому месту: «удалить ссылку» / «заменить
   на другой `<Name>`» / «оставить (станет битой → state-note)».
4. По подтверждению — выполнить все правки одним пакетом через `Edit`.
5. Удалить файл артефакта.
6. Удалить
   `../entrypoint/state/projects/<project-slug>/domains/<ctx>/<kind>/<Name>.md`.
7. Если удалён последний артефакт контекста — спросить через
   `AskUserQuestion`: «контекст `<ctx>` пуст, удалить каталог целиком
   вместе с README?».

## Завершение сессии

1. Перечислить затронутые артефакты (заведены / углублены / промоутнуты /
   удалены).
2. Перечислить нерешённые открытые вопросы по артефактам (читая
   `../entrypoint/state/projects/<project-slug>/domains/`).
3. Свериться с канон-формой ещё раз (ручная проверка по
   `references/field-checklists.md` + `references/draft-stable.md`) —
   подтвердить, что форма консистентна и stable-инварианты держатся.
4. Предложить следующий шаг:
   - **Внутри docs**: добить остальные контексты/use-case'ы этого проекта
     (`/domain-deep-dive <slug> <ctx>`), либо прогнать `/cross-audit`
     (lenses `capability-domain`, `integration-domain`) — не повисла ли
     capability без бизнес-кода или integration без адаптера.
   - **Cross-repo (текстовая ссылка, не локальный chain)**: когда домены
     `stable`, их потребляет соседний `<org>/backend` (форк
     `go-backend-template`) — там `/scaffold` (вариант domain) разворачивает
     Go-код по этим артефактам. Это шаг **в другом репо**, не запускается
     отсюда.

## Запреты

- Не редактировать артефакты вслепую — всегда сначала `Read`.
- Не выдумывать значения доменных полей. Anti-patterns как опции — да;
  тексты инвариантов, business rules, preconditions, имена методов — нет.
- Не повышать `draft → stable` без явного подтверждения архитектора, даже при
  всех 5 ✅.
- Не понижать `stable → draft` сам — только подсветить и предложить.
- Не оставлять висящих cross-ref'ов после удаления (каскад обязателен).
- Не аккумулировать историю в своей ветке state — forward-only.
- Не создавать
  `../entrypoint/state/projects/<project-slug>/domains/<ctx>/<kind>/<slug>.md`,
  если все секции были бы пустыми — заметка появляется только когда есть
  что записать.
- Не писать в чужие ветки дерева `../entrypoint/state/` и в клиентский дом
  `../entrypoint-for-business/state/` — только read-only; rw только своя
  ветка `projects/<project-slug>/domains/`.
- Не задавать >4 вопросов одним AskUserQuestion (инструмент режет).
- Не копить ответы «запишу в конце волны» — пиши сразу через `Edit`, иначе
  теряется при `/clear`.
- Не смешивать проекты: чтения, записи, сверка формы и state — строго в
  скоупе выбранного `<project-slug>`.
- Не дублировать здесь правила `docs/projects/_canon/domains/README.md` и
  шаблонов — они source of truth канона, скилл их **исполняет**, не
  пересказывает.
