## 1. Ширины приёмки и брейкпоинты

Четыре понятия, которые базы смешивают (GL-37), и где живёт число каждого:

| понятие | что это | где число |
|---|---|---|
| ширина приёмки | ширина, на которой результат смотрят и принимают | `kb/common/acceptance-widths.yaml` (NU-01) |
| брейкпоинт | ширина окна, на которой меняется раскладка | токены `breakpoint.*` ДС проекта (NU-04, NU-08) |
| вьюпорт (`viewport`) | класс окна потока и экрана screens: desktop, mobile, any | граница класса — первый брейкпоинт ДС (NU-02) |
| артборд | кадр холста одной ширины | основные — 1440 и 390 (NU-01) |

Сопоставление систем (по числу панелей и навигации, не по пикселям) и попадание ширин приёмки в диапазоны:

| класс M3 (dp) | эталон ui (px) | каталог блоков site | ключ `responsive` screens | ширины приёмки |
|---|---|---|---|---|
| compact < 600 | mobile < 640 | < 40rem | xs | 390, 360; вылет 320 |
| medium 600–839 | tablet 640–1023 | 40–60rem | sm | 768 |
| expanded 840–1199, large 1200–1599 | desktop 1024–1439 | > 60rem | md | 1024, 1280 |
| extra-large ≥ 1600 | wide ≥ 1440 | > 60rem | lg (xl — при четвёртой границе ДС) | 1440 |

### NU-01 · Ширины приёмки — один набор (new-norm, закрыто)

- **Стороны.** Р28: «Основные артборды холста — 1440 и 390, остальные ширины — проверкой HTML-копий»; Р46 добавил 1280.
  cd `06-design-process/04-checks.md` §1: «1440, 1280, 1024, 768, 390, 360 + вылет на 320» — тот же набор; cd `07`
  шаблон мобильного раунда: «кадры 390, 360, 768, 1440» — подмножество. site `09-ai-generation-evaluation/02-site-checklist.md`
  SITE-OUT-02: «Все пункты B этого чек-листа пройдены на 1440×900, 390×844 и 360×800». ui `14-recipes/10-review-loop.md`:
  «1440 — целевая, 1280 — где кончается контент, 390 — мобильная», плюс зум 400 %. ux `12-evaluation-checklists/03-automated-checks.md`
  §6.2а и UX-MOB-01: 320 / 360 / 390–430 / 600 / 768 / 840 / 1024–1280 / 1440 / 1920; ux `13-app-types/04` §24:
  «Проверять надо на произвольных ширинах, а не на списке моделей устройств».
- **Решение.** Одна норма для артбордов, HTML-копий и сборки (страница сайта и экран приложения): ширины 1440, 1280,
  1024, 768, 390, 360 и проверка вылета на 320; тёмная тема — на тех же ширинах, если есть в ДС; основные артборды —
  1440 и 390. Набор меняет только заказчик. Наборы ux с 600, 840 и 1920 — это проверка перестроения (NU-05), а не
  приёмка; наборы site и ui — подмножества. Кадры для судьи рубрики (ui 13/02 §4.4: 1440, 1280, 390) — законное
  подмножество, его задаёт владелец рубрики (узел JU).
- **Почему `kb/common/`.** У нормы нет базы-владельца: её задал заказчик для скилла целиком, а четыре базы держат
  свои наборы. cd 06/04 §1 уже записывает решение, но процессная часть `06-design-process` переписывается в
  `references/` скилла (Р118) — канон там сдвинется. Утилиты (`kit/shot.py`, `mockup_checks.py`, `ui_audit.py`,
  `marketing_audit.py`, `page_accept.py`) держат ширины в коде (`1440x900`, `390x844`); одно машиночитаемое место
  убирает эти копии в Ф8.
- **Канон:** `common/acceptance-widths.yaml`. **Копии к правке (Ф10):** cd 06/04 §1, 06/01 §6, 06/02 §4 D1 — ссылкой;
  cd 06/07 — кадры на всех ширинах; site SITE-OUT-02 и «Устройства» чек-листа — ширины приёмки, окна первого экрана
  остаются у site; ux UX-MOB-01 (id прежний, Р49), 12/03 §6.2а и §5.1, 09/01 §4.3; ui 14/10, 05/06 — ширины приёмки
  плюс проверка перестроения.

### NU-02 · Поле `viewport` ↔ ширины приёмки (gap, позиция)

- **Стороны.** screens `_template/flow.md`, `screen.md`: `viewport` — desktop, mobile, any; мобильная декомпозиция —
  серия экранов потока. Глоссарий: вьюпорт — класс окна, не ширина. На каких ширинах принимать экран какого класса —
  нигде не сказано.
- **Решение.** Экран `mobile` принимают на ширинах приёмки ниже первого брейкпоинта ДС и вылетом на 320, `desktop` — на
  остальных, `any` — на всех. С эталоном ui (640): mobile — 390, 360, 320; desktop — 1440, 1280, 1024, 768. Граница —
  брейкпоинт проекта, а не число в файле: при другой ДС 768 может уйти к мобильной композиции.
- **Канон:** `common/acceptance-widths.yaml#by_viewport`. **Позиция:** формы flow и screen перепишет Ф7.

### NU-03 · Ключи `shell.responsive` ↔ брейкпоинты ДС (gap, позиция)

- **Стороны.** screens `_template/shell.md`: «Допустимые `breakpoint`: `xs`, `sm`, `md`, `lg`, `xl` (канон слоя)» —
  границ нет, пиксели запрещены. Схема ui 09/04 §1.3: `tablet` 640, `desktop` 1024, `wide` 1440 — четыре диапазона.
- **Решение.** Ключи `responsive` — имена диапазонов, границы — токены `breakpoint.*` ДС проекта: с эталоном ui xs < 640,
  sm 640–1023, md 1024–1439, lg ≥ 1440; xl — только при четвёртой границе ДС. Пиксели в screens не пишутся — ключи
  читают код-репо, переименование не нужно.
- **Канон:** ui 09/04 §1.3. **Позиция:** таблица сопоставления в README screens — Ф7; ДС объявляет границы до экранов — Ф6.

### NU-04 · Брейкпоинты приложения: M3 против эталона ui (conflict, закрыто)

- **Стороны.** ux `09-mobile/01-responsive-strategy.md` §4.1: три системы классов не совпадают, «По умолчанию брать M3»

- **Решение.** Границы — токены `breakpoint.*` ДС, одна шкала на продукт; эталон приложения — ui 640 / 1024 / 1440,

### NU-05 · Проверка перестроения (duplicate, закрыто)

- **Стороны.** ux `10-design-systems-consistency/02` §4.3: «Проверка: скриншоты на 8–12 случайных ширинах внутри каждого

## 2. Цели нажатия и плотность

### NU-09 · Цели нажатия (conflict, закрыто)

- **Стороны.** Р52: «минимум 24×24 везде, 44×44 — на таче». ux `08-accessibility/01` §12.4, правило выбора: «Любой
  контрол на тач-экране или в клиентском сервисе | ≥ 44×44», основное, деструктивное и навигация — ≥ 44 без
  оговорки указателя; README правило 46: «Основные и деструктивные действия на таче — 44×44»; UX-A11-14: «Каждая цель
  ≥ 24×24 px или имеет зазор; основные и деструктивные ≥ 44×44»; handoff §3: «ни одна высота … в клиентском сервисе
  < 44». ui C11: 24 на десктопе, 44–48 на тач, с плотностью не меняется; C16: контрол 32 / 40, «зона нажатия
  добирается padding или псевдоэлементом». site В-07: «44×44 — практика для главных на телефоне»; SITE-A11Y-08 и
  `blocks.yaml` `target-size` — 44 главным призывам, полям и «Меню». `marketing_audit.py`: «390×844 тач (… цели 24 px
  по WCAG 2.5.8 — не 44)». Hallmark (через site): 44 — «AA».
- **Решение.** Каждая цель ≥ 24×24 CSS px или зазор (2.5.8) — везде. На таче каждая цель ≥ 44×44 — зоной нажатия;
  видимый контрол может быть меньше (C16). Так и на странице сайта, кроме исключений 2.5.8 (ссылка в абзаце,
  эквивалент, системный контрол). С мышью 44 не требуется: рабочие высоты 32 / 40 — пресеты ui. Плотность цель не
  меняет. 44 — уровень AAA (2.5.5), не AA.
- **Почему.** Р52 решил спор «всегда или на таче» в пользу тача; строки 08/01 §12.4 «в клиентском сервисе» и «основное
  … ≥ 44» без указателя — копии, которые Р52 правит. Для страницы сайта отдельного Р-решения нет, а брифом Р52 задан как
  норма скилла; зона ≥ 44 на таче достижима отступами у любой цели, ссылки в тексте исключены стандартом. Если
  оркестратор читает Р52 только для приложения, строка делится на две: приложение — как здесь, сайт — профиль site
  (44 главным целям).
- **Канон:** ux 08/01 §12.4. **Копии (Ф10):** 08/01 §12.4 (две строки правила выбора), README правило 46, UX-A11-14 и
  AC-LAY-03 (id прежние), handoff §3 («зона, не высота»), site `target-size`, SITE-A11Y-08, 08/03; схема ui — правило
  `size.control.lg` «every control on touch screens» при высоте 40: на таче зона ≥ 44. **Ф8:** перегенерировать YAML
  чек-листа и профиль site; `marketing_audit.py` — на таче 44 (S) поверх 24.

### NU-10 · Что считать тачем (conflict, закрыто)

- **Стороны.** ux `09-mobile/01` §5.2: «`any-pointer: coarse` — достаточное основание увеличить цели; `pointer: fine` —
