# 09. JU — судья, рубрики, метки доказательности: отчёт узла

Рабочий документ журнала Ф4. Узел заменяет правило баз «судья — модель другого семейства» одним протоколом судьи на Opus
и сводит девять легенд меток доказательности в одну. Строки — `09-JU.tsv` (47). Пути баз — от
`.claude/skills/design-deep-dive/kb/`, пути кода, набора и журнала — от корня репозитория. Цитаты — не длиннее 15 слов, с
путём.

Правки существующих файлов делают следующие фазы (Р114): тексты баз — Ф10, код и данные, которые читает код, — Ф8, этапы
скилла — Ф6, калибровка — Ф9. Существующие файлы `kb/`, `scripts/` и `docs/` не правились. Новые файлы —
`kb/common/judge.md` и `kb/common/evidence.md`. Утилиты не запускались; код судьи `scripts/ai-media/asset_audit.py`
(задания, разбор, согласие) прочитан, калибровочный набор — только разметка `assets/calibration/index.yaml`.

## Как решалось

- **Одна модель вместо «другого семейства».** Р27 снимает правило базы, Р47 запрещает оценочные модели кроме Opus, Р55
  переводит VLM-судью кода на Opus, Р60 требует штрафа за избыточность и решающего голоса человека. Протокол собран из
  норм, которые базы уже держат: отдельная сессия (ux 12/01 §7.1), два порядка и победа при совпадении (ux, site, text,
  creative, blender), атомарные вопросы с доказательством (ai-media 11/02 §2.1, text, site), пороги доверия (ai-media
  X25), чистые контексты на вызов (blender 11/06 §6), судья-Opus и «решает человек» (cd 06/04 §6, 06/06 §7). Новое —
  штраф за избыточность, режимы машинного отчёта, число прогонов без «11 для решения», калибровка набором.
- **Параметры выборки.** Базы задают судье температуру 0 и seed (ai-media, creative, text). У сессии Opus их нет —
  устойчивость дают повторы и два порядка; поля рубрик уходят в Ф8.
- **Где остаётся «та же фирма».** В чтении внешних сравнений моделей правило ai-media «судья той же фирмы, что лидер, —
  класс ниже» (13/02 §3) верно и остаётся: оно про чужие бенчмарки, не про нашего судью. Для нашего судьи самый рискованный
  случай — сравнение своей работы с чужими образцами (референсы класса creative): вердикт в пользу своей работы
  подтверждает человек (judge.md §2).
- **Легенда как словарь перевода.** Метки баз не переименовываются (как термины у GL): Р132 требует, чтобы ужатие сохраняло
  метки, а контракт тройки собирался привести синонимы к общим меткам на сводке S2, которой не было. Легенда задаёт, как
  читать каждую форму, и какую метку пишет скилл. Снимаются только пометки журнала `[поправка …]` — их убирает Ф10 по
  forward-only.
- **Сила — группами.** Базы ставят меткам разный порядок: у ux `[исследование]` — «самая сильная метка», у ai-media и
  blender легенда начинается с `[проверено]`.
  Порядок внутри группы решает близость выборки к поверхности, её размер и свежесть; свой опыт на нужной поверхности
  сильнее чужого исследования на другой. Это даёт CN правило «при равенстве — где доказательство сильнее» (PLAN, п. 3).
- **Чтение.** Слоями: легенды и разделы «Что ненадёжно» баз целиком; файлы судьи — выжимки и нужные разделы (ai-media 11/02,
  cd 06/06, blender 11/06 — целиком); рубрики JSON и YAML — разбором скриптом (ключи, блоки `judge`, `calibration`,
  `run_protocol`, `vlm_judge`); места «другого семейства» — греп по всем базам с разметкой по разделам; метки — скрипт по
  всем md, YAML, JSON баз (счёт по слову до двоеточия).

### JU-03 · Поточечно или попарно (text X40) (conflict, закрыто)

### JU-04 · Число прогонов (conflict, закрыто)
| база | что пишет | путь |
|---|---|---|
| ux | «Минимум — 5 прогонов для черновой сортировки, 11 для решения» | ux 11/04 §5.2; 12/03 §8.2 AC-JDG-01, AC-JDG-02 |
| site | «3 — черновая сортировка, 11 — решение, 15 — при большом разбросе» | site 09/03 §5.1, выжимка п. 15; `site-rubric.json` `run_protocol.runs` |
| text | «3 повтора, спорное — до 11 или человеку» | text 09/03 §4.3 п. 4; COPY-C-23; P7 п. 6 |
| cd | «3 прогона, находка — из ≥ 2» | cd 06/04 §6 |
| ui | «Для скрининга хватает одного» | ui 13/02 §4.7 п. 5 |

Решение: три прогона — поиск находок и второе мнение (находка — из ≥ 2, пара — большинством, иначе «неразличимы»); пять —
сортировка трёх и более вариантов, только на уровне «сортировать»; 11 и 15 не нужны: вердикт судьи ничего не решает, спорное
уходит человеку. Один прогон — черновая подсказка внутри итерации, не оценка (ux 11/04 «Частые ошибки» п. 4). Почему три,
а не пять: при 13,6 % переворотов большинство трёх воспроизводит вердикт примерно в 95 % случаев (расчёт узла: 0,864³ +
3 · 0,864² · 0,136 ≈ 0,95 при независимых прогонах), а вопросы с высоким разбросом протокол отдаёт человеку, а не в прогоны;
число переворотов — из текстовых задач (оговорка ux README). Для сортировки пять — минимум ux 11/04 §5.2. Канон judge.md §5.
Копии (Ф10): AC-JDG-01 и AC-JDG-02 (id не меняются), ux README правило 58, site 09/03 и README п. 7 и 56,
`site-rubric.json` `run_protocol.runs`, text COPY-C-23 и P7, ui 13/02 §4.7 п. 5. Ф8: строка UX-OUT-11 в
`scripts/site/build_profile.py` («3 прогона для сортировки, 11 для решения») — перегенерировать `ux-marketing-profile.tsv`.
