# Ф4 — сверка баз: план

Рабочий документ журнала (`research/design-build/`). Общий план — `../PLAN.md`, решения — `../DECISIONS.md` (Р114–Р117 — устройство
этой фазы), что сверять — `../phase-2/SYNTHESIS.md` §9 (22 пункта), §5 (реестры, таблицы канонов, владение форматами), §2.2 (узлы
межбазовых связей), §6.4 (разнобой терминов), §6.12 (противоречия между документами). База — `.claude/skills/design-deep-dive/kb/`
(дальше — `kb/`).

## Цель и готовность
Одна норма — одно место. У каждой нормы, которую повторяют или по-разному трактуют несколько баз, — одно каноническое место;
межбазовые противоречия закрыты или помечены (что их закроет: данные, пилот, заказчик).
Готово, когда: (1) каждая межбазовая строка карты входов (`inputs/rows.tsv`) покрыта строкой сводного реестра — проверка скриптом;
(2) у каждой нормы реестра ровно одно каноническое место, и оно существует; (3) файлы `kb/common/` проходят проверку ссылок и
forward-only; (4) открытые пункты — списком с тем, что их закроет.

## Что Ф4 делает и чего не делает (Р114)
- Делает: решает расхождения, выбирает каноническое место каждой нормы, пишет новые общие нормы в `kb/common/`, составляет
  реестр действий для следующих фаз.
- Не делает: не правит существующие файлы `kb/<база>/` и `scripts/`. Выравнивание копий и сжатого слоя — Ф10 (тексты, Р48),
  код — Ф8, слой проекта — Ф6/Ф7. Причина: правило forward-only грузится при правке любого md, а базы до уборки полны журнальных
  частей; попутная уборка размоет сверку.

## Где живёт результат (Р115, Р116)
- **Нормы с владельцем темы** остаются в базе-владельце («норма живёт у владельца темы»: контракт тройки §2, отчёт X site §2).
  Ф4 фиксирует место и решение; правку текста делает Ф10.
- **Нормы без владельца** — новая папка `kb/common/`: `README.md` (что здесь и старшинство), `glossary.md`, `components.yaml`,
  `judge.md`, `evidence.md`, межбазовый `CONTRADICTIONS.md`, `canon.tsv` (норма → место; генерируется из реестра). Состав
  уточняют узлы; новый файл в `kb/common/` появляется, только когда у нормы нет базы-владельца.
- **Старшинство:** `kb/common/` → реестр противоречий базы → текст базы → сжатый слой («Выжимки», «Частые ошибки», чек-листы, YAML).
- **Рабочие артефакты** — здесь, в `phase-4/`: `inputs/` (карта входов), `nodes/<NN>-<код>.md` и `.tsv` (отчёт и строки узла),
  `CHAIN.md` (передача между агентами), `registry.tsv` (сводный реестр, собирает скрипт), `REPORT.md` (итог), `tools/`.

## Строки узла (`nodes/<NN>-<код>.tsv`)
TSV, UTF-8, первая строка — заголовок; одна строка — одна норма или расхождение:

| колонка | что |
|---|---|
| `id` | `<код>-NN`, например `TR-07` |
| `node` | код узла |
| `kind` | `conflict` — нормы баз противоречат; `duplicate` — одна норма в нескольких местах без противоречия; `gap` — нормы нет или ожидание одной стороны не выполнено; `id-sync` — id, ссылки, схемы, ключи; `term` — термин; `new-norm` — новая общая норма |
| `topic` | тема, до 80 символов |
| `sides` | стороны: `база:путь §…`, через `; ` (пути — от `kb/`) |
| `positions` | позиции сторон коротко: `site: …; blender: …` |
| `resolution` | решение — сама норма, до 300 символов (подробно — в md узла) |
| `basis` | на чём стоит: метки доказательности, строки реестров, Р-номера |
| `canon` | одно каноническое место: `путь §…` или `путь#ключ` |
| `copies` | где норму повторяют или противоречат ей, через `; ` |
| `action` | что сделать и в какой фазе: `Ф10: …; Ф8: …; Ф7: …; Ф6: …` |
| `status` | `закрыто` · `позиция` (решено с условием) · `открыто` (что закроет — в `action`) · `заказчику` |
| `source` | откуда строка: `§9 п. N`, id строк `inputs/rows.tsv` (`IN-…`) через `; ` |

Проверка и сборка — `tools/registry.py` (пишет агент IN): схема строк, уникальность `id`, одно `canon` на норму, существование путей,
покрытие строк `inputs/rows.tsv`.

## Общие правила для агентов узлов
1. Решения `../DECISIONS.md` обязательны. Если норма базы спорит с Р-решением, действует Р-решение, а место в базе — копия к правке.
2. Реестр противоречий базы главнее её сжатого слоя (Р48): устаревшая «Выжимка» — копия к правке, не довод.
3. Каноническое место выбирается так: владелец темы по контракту тройки и таблицам канонов баз; числа — в одном машиночитаемом месте
   (токены ui — Р42, YAML-пороги баз); при равенстве — где доказательство сильнее (метки `[проверено: …]`, `[консенсус]` и т. п.).
4. Чтение слоями: README базы → «Выжимка для агента» файла → нужный раздел. Большие файлы целиком не грузить. Отчёты Ф2
   (`phase-2/light/`, `phase-2/ux/`) — путеводитель, но решения проверяются по самим файлам базы.
5. Существующие файлы `kb/` и `scripts/` не правятся (Р114). Писать можно: свои файлы в `phase-4/`, свой новый файл в `kb/common/`
   (если узлу он назначен), запись в `CHAIN.md`.
6. Идентификаторы заморожены: UX-*, AC-*, K3-*, F-*, неймспейс `org.ui-research.*`, URN схем, ключи `ALLOW_KEYS` (Р49, Р62, Р86);
   переименования — только строкой `action` (Р76 п. 25).
7. Не решается по базе — статус `открыто` и что закроет (данные, пилот); `заказчику` — только вкус или бизнес.
8. Тексты `kb/common/` — по стандарту `../phase-3/SKILL-MAP.md` §7 и forward-only: без дат, истории и «было / стало»; ограничения —
   спокойно и с причиной.
9. Контекст подходит к ≈ 800 тыс. токенов — остановиться, записать сделанное и раздел «что не прочитано».
10. Файлы результата — рабочие артефакты заказчика. Если записать файл не получается, вернуть его текст в ответе.

## Проверка узла оркестратором
После каждого агента: `tools/registry.py check` по строкам узла; сводка md узла; выборочная сверка 2–3 решений с источниками; решения
узла — одной строкой в DECISIONS (принято, поправки); правки плана и брифа следующего узла — по «передаче дальше».
