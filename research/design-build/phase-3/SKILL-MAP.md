## 2. Правила раскладки

### 2.1. Базы (`kb/`)
- Имена баз — без суффикса `-research`: `ux`, `ui`, `site`, `text`, `creative`, `ai-media`, `blender`, `claude-design`.
- Переносятся 1:1 по относительным путям: корневые `README.md`, `CONTRADICTIONS.md`, `PLAN.md` и тематические папки `NN-*`
  (кроме `90-sources`, `91-videos`, `99-raw`) — классы инвентаря prose, data, code, root-doc. Внутренняя структура не меняется, поэтому
  короткие адреса «NN/MM» и «→ §» остаются верными.
- `PLAN.md` баз едет файлом: нормы из него извлекаем, журнальные части убираем при уборке. Позиция SYNTHESIS §3.4 «PLAN файлом не
  переносим» снята: снаружи мы больше не работаем, а без файла нормы потеряются.
- Эталонный код (примеры рецептов, HTML-экраны ui, исходники артефактов Claude Design, код сцен) остаётся в kb рядом с текстом.
  Утилиты, которые лежат в тематике (`kit`), уходят в `scripts/`.
- Не переносим по решениям: `measurements.tsv`, `corpus.tsv` text (Р32); `lab/`, `effect_bench.py`, данные `03-live-sites-measured/`
  creative (Р39; md `03/01–02` остаются); 63 карточки моделей и `routing.v0/v1` ai-media (Р54); `skills-map.md` site, text, creative
  (противоречат Р6); примеры site v0 (Р76 п. 19); `routerai_models.json` (Р76 п. 15). Остальные кандидаты «не переносим сверх
  умолчания» из SYNTHESIS §3.1 спецификация выписывает списком с источником; без решения — на решение оркестратора.

### 2.2. Код (`scripts/`)
- Источники: `<база>/99-raw/tools/`, модули и шаги из `99-raw/experiments/`, принятые исключениями (Р33, Р37, Р54, Р57, Р66, Р62),
  `kit`, инструменты обслуживания из `_skill-build/tools/`.
- Одна каноническая копия на утилиту (колонка «канон» SYNTHESIS §4.1, сверка md5); дубли не переносятся, ссылки на них ведут к канону.
  `scripts/<база>/` — по базе-канону утилиты. Модули, которые импортируют утилиты разных доменов, — в `scripts/lib/`.
- Не берём — SYNTHESIS §4.2.
- При переносе код правится только механически: корни и пути — через `kbpaths`, импорты соседей — через `lib/` и `kbpaths`, абсолютные
  пути `/home/mm/…` — через `kbpaths` и переменные окружения, блокировки браузера и выходы — в кэш. Смысловая адаптация (судья → Opus,
  Kimi-ветки, схемы v1, жанр «интерфейс», демо-факты) — позже, внутри шаблона.
- Цель переноса по коду: каждая утилита импортируется и отвечает на `--help` (или самопроверку) в новой раскладке; исключения —
  списком с причиной.

### 2.3. Машинные файлы
Схемы, YAML, JSON, TSV, реестры — нормы: остаются в kb рядом с текстом, код читает их через `kbpaths`. Пути внутри них (`$ref`,
`source_file`, колонки путей) переписывает скрипт по правилу §3.

### 2.4. `99-raw` в kb — «к разбору»
- Утилиты и модули, которые исполняет код, — в `scripts/`.
- Файлы, которые читает только код и которые человек не читает как норму (эталонные иконки `lucide-ref`, HDRI для `gltf_diff`,
  фикстуры самопроверок), — в `scripts/<база>/data/`.
- Всё остальное отобранное — в `kb/<база>/99-raw/<старый путь>`: отчёты аудита X целиком (нормы извлекаем положениями позже),
  `handoff-to-neighbours.md` (вход сверки), `_common.md` creative, контракт тройки и `ac-profile.tsv` site, `temp-vocabulary-v0.yaml`
  text, формат заданий генерации ai-media, исходники рецептов 13–17 blender и др. — полный список даёт спецификация.
- При уборке `99-raw` в kb опустошается: нормы переезжают в тематику, реестры и таблицы канонов, остальное уходит.

### 2.5. Ассеты
Только исключения: калибровочный набор → `assets/calibration/` (Р16, Р56, Р95); минимальные ассеты эталонов creative L0–L2 (Р41) и
blender (Р57, вариант А) — на своих местах в kb; `lucide-ref` и HDRI — `scripts/<база>/data/`. Бинарники, модели и библиотеки — не в git,
ставит `install.sh` (версии, sha256).

### 2.6. Журнал сборки (`research/design-build/`)
- Зеркало `_skill-build/` без `phase-2/inventory/{files,links}.tsv`, `freeze/inventory/{files,links}.tsv`, полного
  `freeze/manifest.tsv.gz`, `__pycache__`, временной папки сборки.
- Внутри журнала `_skill-build/` в старых текстах = сама эта папка; пути к базам app-design переводит `path-map.tsv` (старый путь →
  новый путь → sha256 источника) — он же запись заморозки для перенесённых файлов.
- `STATE.md`, `PLAN.md`, `NEXT-SESSION-PROMPT.md` перед переносом переписываются под работу внутри шаблона.
- Журнал живёт только в ветке; строки о нём в `CLAUDE.md` нет (он грузится во все сессии, в том числе у клиентов).

### 2.7. Окружение
Всё тяжёлое — вне репозитория, в `~/.cache/design-deep-dive/` (переопределяется `DDD_HOME`): venv, `node_modules`, бинарники, модели
ONNX, браузеры Playwright, выходы утилит, блокировки. Одно окружение на машину для всех форков шаблона. Ключи API — переменные
окружения или файл вне репозитория (Р53). Blender, Brave, ffmpeg — системные, путь через переменные окружения или PATH.

## 3. Переписывание путей
- Правило «разрешить → сопоставить»: токен переписывается, только если он разрешается (от файла, от корня базы или от корня app-design —
  как в `inventory.py`) в реальный файл источника, у которого есть новое место; путь пересчитывается относительно нового места файла,
  где стоит ссылка.
- Где ищем: md — ссылки `[..](..)`, пути в обратных кавычках, голые пути с расширением; машинные файлы — строковые значения и `$ref`;
  код — только через правки механики (§2.2), общим переписыванием код не трогаем.
- Не разрешился — не трогаем и считаем. Ссылки на непереносимое остаются (их убирает уборка); их число не больше, чем до переноса.
- Идентификаторы не трогаем никогда: неймспейс `org.ui-research.*`, URN схем, id `UX-*`, `AC-*`, `K3-*`, `F-*`, «K3» в ui, имена баз в
  прозе. Смена `x-research` → `x` — только в сегментах разрешённых путей.

## 4. Что создаётся при переносе (overlay)

(из tools-map), `requirements.txt`, `package.json`, `install.sh`, `scripts/tests/`, `.gitignore` скилла, `assets/calibration/` с
`index.yaml`, `research/design-build/README.md` (как читать журнал и старые пути), абзац-исключение в `forward-only.md`. Исходники
overlay лежат в `phase-3/migration/overlay/`, скрипт копирует их как есть.

## 5. Как переносим
1. Заморозка — сделано: `../freeze/` (манифест sha256 58 156 файлов, свежий инвентарь). Перед каждым прогоном — `freeze.py --verify`.
2. Калибровочный набор — агент: ≈ 40 кадров из 50 кандидатов SYNTHESIS §11 и добора → `phase-3/calibration/` (кадры, `index.yaml`,
   страница-контактный лист) → утверждение заказчиком за один проход.
3. Спецификация — агент: `phase-3/migration/SPEC.md`, `manifest-rules.yaml`, `tools-map.tsv` из этой карты, SYNTHESIS §3–4,
   DECISIONS и свежего инвентаря; спорное — списком на решение.
4. `migrate.py` — агент: собирает во временную папку из (замороженная база + правила + overlay), детерминированно; проверки; запись
   только в управляемые пути (`.claude/skills/design-deep-dive/`, `research/design-build/`, строка в `forward-only.md`); повторный
   запуск откажет, если там правили руками после прошлого прогона.
5. Проверки: источник не менялся с заморозки; каждый файл цели учтён в `path-map.tsv` и наоборот; нет файлов из `99-raw/cache`, kimi,
   мусора; в kb и scripts нет `CLAUDE.md`, `AGENTS.md`, `SKILL.md` (кроме нашего), `.claude/`, `.mcp.json`, `.git` — Claude Code
   подхватил бы их как инструкции; нет секретов и закрытых текстов; битых ссылок не больше, чем до переноса; 0 путей `/home/mm` в
   `scripts/`; смоук утилит; отчёт о размере и токенах по частям.
6. Ветка `feat/design-deep-dive` от `main`, коммиты по Conventional Commits в стиле forward-only; только локально, push — по слову
   заказчика. Дальше работаем только внутри шаблона.

## 6. Потом — внутри шаблона (порядок; подробно — `../PLAN.md`)
1. Сверка баз (Р67, Р105): одна норма — одно место, единый глоссарий, словарь компонентов, WEB-01/WEB-04.
2. Карта знаний `kb/INDEX.md` и навигатор `SKILL.md` — по сведённым нормам.
3. Blueprint: workflow (сайт / лендинг / SaaS, этапы, тексты, единый вход Claude Design), модель слоя проекта (UX-дельта, слой
   страницы), устройство `design-deep-dive` и `design-audit`, агенты, бюджеты контекста.
4. Реализация: слой проекта (`CLAUDE.md` §3, ≈ 35 файлов), маршруты и ужатие базы, `references/`, формы, `design-audit`, агенты,
   ветка `entrypoint`; сокращение описаний скиллов под листинг.
5. Адаптация кода: судья → Opus, Kimi из кода, валидаторы под схемы v1, жанр «интерфейс», демо-факты, установка окружения.
6. Пилоты: лендинг, многостраничник, SaaS; тесты T-1…T-6.
7. Финальная уборка (SYNTHESIS §10, Р82) → prompt-audit всех текстов → журнал из ветки убираем → слияние по слову заказчика.

## 7. Стандарт текстов скилла (`/claude-api prompt-audit`, кратко)
- Контекст — аудитория, продукт, среда, планка качества, причины ограничений — не бывает лишним.
- Без давления (MUST, NEVER, CRITICAL капсом) и без «думай пошагово»; ограничение — спокойно и с причиной; глубина — через effort.
- Цель и способ проверки вместо хореографии шагов; точные шаги — только для хрупких операций (публикация «прочитать → слить →
  опубликовать», перенос, установка окружения).
- Запреты — только реальные и с причиной, стиль — позитивно. Исключение: бан-лист конкретных дефолтов дизайна (кремовый фон,
  курсивные акценты, «01/02/03», моноширинные подписи, пилюли) — рабочая форма для Opus 5.5, его сохраняем и расширяем.
- `SKILL.md` читается за один присест; каждая информация — в одном месте; без зашитых путей и версий; без истории; описание скилла —
  категории намерений, а не перечень фраз-триггеров (в описании допустима выверенная настойчивость).
- Детерминированное — скриптами, суждение — модели; таблицы, баллы, расчёты — в данных и коде.
- Примеры — несколько разных, помеченных как иллюстрация.
