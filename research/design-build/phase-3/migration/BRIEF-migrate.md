## Что сделать — `_skill-build/phase-3/migration/migrate.py` (+ свои модули рядом, если нужно)
1. **`build`** → `phase-3/migration/.staging/` — полное дерево управляемых путей: `.claude/skills/design-deep-dive/…`,
   `research/design-build/…` и новая версия `.claude/rules/forward-only.md` (текущий файл шаблона из `main` + абзац, только чтение шаблона).
   - сверка источника с заморозкой (sha256 взятых файлов против `freeze/manifest.tsv.gz`);
   - содержимое по правилам (`rules_eval`), код по `tools-map.tsv` (его строка главнее правила содержимого, §2 SPEC) с правками
     `apply_patches`, overlay, калибровка, журнал (оживший `_skill-build/` на момент сборки, исключения — §6 SPEC и Р110: overlay в журнал
     не идёт);
   - переписывание путей по SPEC §7.1, включая каталоги (Р110); идентификаторы не трогать;
   - `kb/INDEX.md` — заготовка карты знаний: базы → заголовок и первая строка их README → тематические папки с числом файлов; в одном
     месте скажи, что это заготовка, которую заменит карта знаний;
   - `research/design-build/phase-3/migration/path-map.tsv`: старый путь → новый путь → sha256 источника → вид (copy | alias |
     rewritten | patched) → число замен; строки — и для kb, и для кода, и для журнала;
   - детерминированно: тот же вход → побайтно то же дерево; печатай отпечаток дерева.
2. **`check`** — все проверки SPEC §8 и SPEC-code (смоук утилит — `scripts/tests/smoke.py` на `.staging`, уже с настоящим kb, без
   симлинков; 0 вхождений `/home/mm` в `scripts/`), размер и токены по частям. Итог — `phase-3/migration/reports/check.json` и короткая
   человекочитаемая сводка `reports/check.txt`. Жёсткие проверки (запретное, файлы-инструкции, секреты, битые ссылки на перенесённое,
   идентификаторы, состав, калибровка) — ненулевой код выхода; базовые числа — предупреждения с цифрами.
3. **`apply --repo <путь> [--dry-run]`** — только после зелёного `check`. Защита: репозиторий git; текущая ветка
   `feat/design-deep-dive`; рабочее дерево чистое; управляемые пути либо отсутствуют (первый перенос), либо совпадают с деревом из
   прошлой отметки `research/design-build/phase-3/migration/applied.json` — иначе отказ с перечнем расхождений (в шаблоне правили руками).
   Копирует `.staging` в управляемые пути, дописывает абзац в `forward-only.md`, пишет отметку. Ничего в репозитории не удаляет: если
   в `.staging` нет файла, который есть в управляемых путях, — отказ с перечнем. Git-команды — только чтение (статус, ветка); коммитит
   оркестратор.
4. **Прогон:** `build` → `check` до зелёного (исключения — с причиной в отчёте) → `apply` на временном клоне шаблона
   (`git clone --local` в `phase-3/migration/.staging-apply/`, ветка `feat/design-deep-dive` там) → второй `build` даёт тот же отпечаток,
   второй `apply` ничего не меняет. Настоящий шаблон — только чтение.
5. **`MIGRATE.md`** рядом: как запускать, что делает каждый шаг, какие отчёты читать, что делать при отказе `apply`.

## Файлы — рабочие артефакты заказчика
`migrate.py`, модули, отчёты, `MIGRATE.md` — заказанные заказчиком рабочие артефакты сборки; их запись — сама задача, а не отчёт о
работе. Если среда всё же не даст записать какой-то файл, верни его полный текст в ответе — оркестратор сохранит.

## Границы
- Базы, настоящий шаблон, файлы агентов A и B — только чтение. Если в их файлах ошибка — обойди в своём коде, если можно, и опиши
  в отчёте; иначе — в «На решение». Писать — только в `_skill-build/phase-3/migration/` (свои файлы и папки `.staging*`, `reports/`).
- Ничего не удалять, кроме пересоздания своих временных папок `.staging` и `.staging-apply` (их можно чистить целиком перед
  сборкой); `.staging-code` агента B не трогать.
- Браузеры не запускать; перед тяжёлым — `free -g`, нужно ≥ 3 ГБ доступной.
- Итог в ответе — не длиннее 15 строк: отпечаток дерева, итог проверок, размер, что на решение.
