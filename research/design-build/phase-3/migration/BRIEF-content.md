# Бриф: спецификация переноса — содержимое (агент A)

Исполнитель — один агент на Claude Opus 5.5. После тебя агент B делает часть «код» (`tools-map.tsv`), затем агент C пишет
`migrate.py`. Твой результат — вход для обоих: пиши так, чтобы по нему можно было собрать перенос без повторного исследования базы.

## Контекст
База знаний (8 ресерчей в `/home/mm/Документы/app-design/<база>-research/`) заморожена и переезжает в репозиторий-шаблон
`/home/mm/git/stit-core/business-strategy-template` внутрь скилла `.claude/skills/design-deep-dive/`. Устройство скилла и правила

данные для кода), должно уехать внутрь, а лишнее — не уехать.

Все пути `_skill-build/…` — от `/home/mm/Документы/app-design/`.

## Что сделать
1. **`_skill-build/phase-3/migration/manifest-rules.yaml`** — упорядоченные правила для содержимого (первое совпадение решает):
   `match` (glob от корня app-design), `action` (`take` | `skip`), `dest` (шаблон пути в шаблоне; по умолчанию — `kb/<база>/<тот же
   путь>`), `purpose` (`kb` | `raw-norm` | `build-input` | `ref-code` | `asset-min` | `code-data` | `journal` | `calibration`),
   `why` (Р-номер или раздел SYNTHESIS; без решения — `open`). Плюс заголовок: соответствие имён баз, классы по умолчанию, мусор,
   корни. Формат можешь уточнить — опиши его в SPEC.md.
   Охват: всё, что не исполняемый код утилит: тематика 1:1 и сверх-умолчания исключения; некодовое из `99-raw` «к разбору» (SKILL-MAP
   §2.4); эталонный код из `99-raw` (исходники рецептов 13–17 blender — только финальные, Р76 п. 16; creative `J/04/src/scene.js`);
   минимальные ассеты эталонов (Р41, Р57 вариант А) и данные кода (`lucide-ref`, HDRI → `scripts/<база>/data/`); калибровочный набор
   (утверждён заказчиком, Р109: `_skill-build/phase-3/calibration/frames/` + `index.yaml` → `assets/calibration/`; `_superseded/` и
   `tools/` набора в скилл не идут); журнал (`_skill-build/` → `research/design-build/` без больших TSV, полного манифеста,
   `__pycache__`, временной папки сборки `phase-3/migration/.staging/`, кадров калибровки и `phase-3/calibration/_superseded/`).
2. **`_skill-build/phase-3/migration/rules_eval.py`** — применяет правила к замороженной базе (инвентарь + манифест) и пишет
   `expected-content.tsv` (source, dest, purpose, why, bytes, tokens_est, sha256) и итоги по базам и `purpose`. Детерминированно,
   без записи куда-либо ещё; `migrate.py` потом его импортирует.
3. **Сканы для переписывания путей** (скриптами, результаты — в SPEC.md и, если длинно, в `scan-*.tsv`):
   - защищённые идентификаторы: где имена баз с `-research` встречаются не как путь (неймспейсы вроде `org.ui-research.*`, URN схем,
     `$id`, ключи) — шаблоны и число вхождений по базам;
   - поля машинных файлов (YAML, JSON, TSV, CSV), значения которых разрешаются в файлы, — по имени поля или колонки, с числом;
     вывод: безопасно ли общее правило «разрешить → сопоставить» для всех строковых значений или нужен список полей;
   - ссылки из переносимого по новой политике: сколько ведут на перенесённое (после переноса обязаны разрешаться), сколько — на
     непереносимое (останутся битыми до уборки), сколько не разрешаются и сейчас. Это базовые числа проверок.
4. **`_skill-build/phase-3/migration/SPEC.md`** (часть «Содержимое»): итог в цифрах (файлы, МБ, токены — по базам и по purpose); по
   каждой базе — что сверх умолчания не берём и почему, что берём из `99-raw` и зачем, минимальные ассеты; журнал; правила
   переписывания путей с результатами сканов; проверки с базовыми значениями; раздел «Передача агенту B» — исполняемый код, который
   в kb не идёт (утилиты в тематике вроде `kit`, копии утилит в `06-design-process/stand/`, модули и шаги из `99-raw/experiments`,
   принятые исключениями, `99-raw/tools/README.md`), с путями; раздел «На решение» — пункты без решения, у каждого твоя рекомендация
   и цена (МБ, токены).

## Файлы — рабочие артефакты заказчика
`SPEC.md`, `manifest-rules.yaml`, `rules_eval.py`, `scan-*.tsv` — заказанные заказчиком рабочие артефакты сборки, их запись в
`_skill-build/phase-3/migration/` — сама задача, а не отчёт о работе. Если среда всё же не даст записать какой-то файл, верни
его полный текст в ответе — оркестратор сохранит.

## Границы
- В базе и в шаблоне ничего не менять. Писать только в `_skill-build/phase-3/migration/`. Ничего не удалять; свой файл при
  необходимости — перезаписать.
- Решения из DECISIONS не пересматривать; если факт в базе им противоречит — записать в «На решение», не решать молча.
- Итог в ответе — не длиннее 15 строк: главные цифры, число правил, что на решение.
