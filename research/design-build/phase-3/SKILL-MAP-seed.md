## 2. Правила раскладки
- База — 1:1: тематика, README, CONTRADICTIONS, PLAN (журнальные части PLAN убираются при финальной уборке). Суффикс `-research`
  у баз убираем; межбазовые пути `../x-research/` переписывает скрипт.
- Код — из `99-raw/tools` и нужных модулей `99-raw/experiments` — в `scripts/<домен>/`; одна каноническая копия на утилиту (дубли по
  md5 — одна); ссылки на старые пути в тексте базы переписывает скрипт по таблице «старый путь → новый».
- Эталонный код (примеры рецептов, HTML-экраны ui, исходники артефактов Claude Design) остаётся в kb рядом с содержимым; их
  минимальные ассеты (creative L0–L2, blender) — рядом с ними.
- Абсолютных путей в коде нет: всё через `scripts/lib/kbpaths.py`; блокировки браузера и кэши — в каталоге пользователя; ключи API —
  переменные окружения или файл вне репозитория.
- Не переносим: служебное (90, 91, остальное 99), ассеты (кроме калибровки и минимумов эталонов), мусор (venv, node_modules, dist,
  кэши), kimi (в корзине), закрытые тексты claude-design (`99-raw/cache`).
- Все исключения — по `DECISIONS.md` (сводно — `phase-2/SYNTHESIS.md` §3–4).

## 3. Что создаётся при переносе
`SKILL.md`-навигатор, заготовка `kb/INDEX.md`, `scripts/lib/kbpaths.py`, `scripts/README.md`, `requirements.txt`, `package.json`,
`install.sh`, смоук-тесты, `.gitignore` (`.venv`, `node_modules`, кэши, выходы утилит), `assets/calibration/` с разметкой, журнал
`research/design-build/`. Обсудить: одна строка в `CLAUDE.md` шаблона — где журнал сборки (CLAUDE.md грузится всегда).

## 4. Как переносим
Заморозка app-design (манифест sha256, пересчёт `inventory.py`) → отбор калибровочного набора (агент, из 50 кандидатов SYNTHESIS §11) →
спецификация переноса (агент: `manifest-rules.yaml`, `tools-map.tsv` из SYNTHESIS §3–4 и DECISIONS) → `migrate.py` (идемпотентный) →
проверки: битых ссылок не больше, чем до переноса; смоук всех утилит; нет секретов, kimi, закрытых текстов; отчёт о размере и токенах →
коммиты в ветку шаблона (например, `design/kb-import`), в main не мержим.

## 5. Потом — внутри шаблона (черновик порядка)
1. Карта знаний `kb/INDEX.md` + навигатор `SKILL.md`.
2. Сверка баз — одна норма в одном месте.
3. Blueprint: workflow (сайт / лендинг / SaaS; этапы; тексты; единый вход Claude Design), модель слоя проекта (UX-дельта + слой
   страницы), устройство `design-deep-dive` и `design-audit`, агенты.
4. Реализация: слой проекта (`CLAUDE.md` §3, ≈ 35 файлов), workflow, шаблоны артефактов, `design-audit`, агенты, ветка `entrypoint`;
   сокращение описаний скиллов под листинг.
5. Адаптация кода: судья → Opus, Kimi из кода, валидаторы под схемы v1, жанр «интерфейс» у линтера, демо-факты и др.
6. Пилоты: лендинг, многостраничник, SaaS; тесты T-1…T-6.
7. Финальная уборка (абстрагироваться от внешнего, выровнять сжатый слой по реестрам, замены ссылок kimi, id `LOOK-*`/`HON-*`) →
   prompt-audit всех текстов → слияние.

## 6. Стандарт текстов скилла (`/claude-api prompt-audit`, кратко)
- Контекст — аудитория, продукт, среда, планка качества, причины ограничений — не бывает лишним.
- Без давления (MUST, NEVER, CRITICAL капсом) и без «думай пошагово»; ограничение — спокойно и с причиной; глубина — через effort.
- Цель и способ проверки вместо хореографии шагов; точные шаги — только для хрупких операций (публикация «прочитать → слить →
  опубликовать», перенос, установка окружения).
- Запреты — только реальные и с причиной, стиль — позитивно. Исключение: бан-лист конкретных дефолтов дизайна (кремовый фон,
  курсивные акценты, «01/02/03», моноширинные подписи, пилюли) — рабочая форма для Opus 5.5, его сохраняем и расширяем.
- `SKILL.md` читается за один присест; каждая информация — в одном месте; без зашитых путей и версий; без истории; описание скилла —
  категории намерений, а не перечень фраз-триггеров (в описании допустима выверенная настойчивость).
- Детерминированное — скриптами, суждение — модели; таблицы, баллы, расчёты — в данных и коде.
- Примеры — несколько разных, помеченных как иллюстрация.
