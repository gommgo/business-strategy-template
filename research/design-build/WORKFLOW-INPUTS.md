# Вводные к будущему workflow (не проект, а сырьё для Ф3)

Собираются по ходу работы: что говорил заказчик и что по этому поводу говорит база. Workflow проектируем только после выжимок Ф2.

## 1. Вход и маршрут (заказчик, 25–26.09)
- Проектировать можно начать почти с любого места. Тип продукта (сайт / лендинг / SaaS) определяет маршрут `entrypoint` и поведение
  скилла; «хочу просто сайт» → сразу в дизайн.
- Для сайтов и лендингов появится новый слой проектирования (один или два): тексты, маркетинг, воронки.
- Workflow поэтапный, в несколько сессий, вдумчивый; читает базу выборочно, по маршрутам.

## 2. Порядок этапов дизайна (заказчик, 26.09 — набросок «примерно так»)
Бриф и анализ того, что есть в репозитории → мудборды и референсы (Behance, Dribbble, Dprofile…) → ассеты и их генерация, решение
«генерировать или нет», нужен ли Blender → общий визуал → дизайн-система в Claude Design → вайрфреймы → дизайн-система поверх
вайрфреймов → слоями: 3D / видео / анимации / креатив / уровень амбиций.

Что говорит база (оркестратор, по дайджестам):
- уровень амбиций L0–L2 решается рано (бриф, страница, секция): от него бюджеты и допустимые эффекты; поздно накладываются только
  сами эффекты (creative);
- ассеты генерируются после дизайн-системы и структуры: план ассетов берётся из слотов страницы, «паспорт визуала» — из токенов ДС до
  первой картинки (ai-media);
- ДС — до экранов; эстетика согласуется 2–4 направлениями, а не выбирается молча (claude-design, ui);
- Claude Design: ДС — артефакт Design System, холст — артефакт Design (направления → вайрфрейм → макет с твиками и прототипом);
  исходники в репозитории, «прочитать → слить → опубликовать».

## 3. Тексты (заказчик, 26.09)
Тексты надо писать, раскладывать по структуре и проводить через аудит и ревью — для сайта, лендинга и SaaS. Набросок заказчика:
после вайрфреймов → тексты → аудит текстов → «натянуть» на дизайн. Куда вставить — решить при проектировании workflow.

Что говорит база:
- факты раньше слов: числа, имена, цены, гарантии — только из `facts.yaml`; нет факта — видимая заглушка и вопрос заказчику (text);
- смысл (позиционирование, осведомлённость, иерархия сообщений, возражения) — до текстов и до макета (text 02);
- тексты раскладываются по слотам страницы: `copy-slots.yaml` (длины, обязательность факта), copy deck — файл текстов страницы с
  фактами, вариантами, статусами и проверками (text 04, 10); слоты приходят из плана страницы (site `page-plan`);
- «текст пишется до макета» (ux 07); в Claude Design на вход — реальные тексты и данные, недостающее — видимые заглушки (claude-design);
  русский длиннее английского на 10–30 % — вёрстка должна выдерживать реальные длины (ux, ui);
- аудит текстов: факты и право → линтер жанра → длины и мета → судья (сигнал, не арбитр) → человек; правка по находкам, ≤ 3 прохода
  (text 09);
- для SaaS — микрокопи интерфейса (кнопки, ошибки, пустые состояния) идёт вместе с экранами и состояниями (ux 07, S01–S22).
- Из выжимки text (26.09): стыка «тексты → макет Claude Design» в базе нет (среди потребителей copy deck Claude Design не значится —
  `text 10/README` «Куда уходят поля»); связь `page-plan` ↔ copy deck только объявлена (поле `copy_deck` у плана, поля `site_*` в deck
  пусты), код её не проверяет; роли секций: 28 у text, 40 у site — сверка не проведена. Это надо спроектировать в Ф3.
- (вывод) Вероятная точка: смысл и факты — на этапе брифа; черновик текстов по слотам — вместе со структурой (вайрфреймом) и до
  чистового макета; аудит текстов — до чистового макета; финальная шлифовка — после.

## 3а. Процесс макета в Claude Design (из выжимки «Kimi → Claude Design», 26.09)
- claude-design-research процесса не несёт: бриф и ≤ 7 вопросов одним сообщением, пакет задачи, цикл правок и стоп, проверки, стенд
  и правило решения тестов лежали в kimi — их надо написать под Claude Design (основа — kimi 07/01, 07/02, 08/01–03, 09).
- Совпадают со страницами холста: направления, мобильная версия. Частично: ДС, бриф, факты, проверки, цикл итераций. Нет аналога у
  типа артефакта: формат референсов, проверка «изменилось только названное» (она есть в `kit`).
- Единый вход холста и ДС вместо стыков «тексты и бриф → исполнитель» — спроектировать.

## 4. Принцип использования (заказчик, 26.09)
Во время создания дизайна агент видит карту всех знаний и смешивает нормы разных баз в цельную идею; референсы скилла связаны между
собой. Сейчас — только файловые связи.

## 5. Набросок слоёв лендинга (оркестратор, 26.09, на обсуждение с заказчиком)
Опора: site 01–10 (бриф, типы и словарь, структура, блоки и план, воронки, ворота), text 02/04/09/10, creative (уровни, мудборд,
направления), ai-media (план ассетов из слотов, паспорт визуала), решения Р24, Р76 п. 1–5.
- Над страницей (есть в шаблоне): AJTBD (сегмент, работа, барьеры и драйверы) → карта гипотез (что проверяем лендингом; метрика
  воронки = критерий гипотезы — предложение, вывод) → vision-минимум + поверхность с родом «лендинг»; interface лендингу не нужен.
- Слой страницы `site/<поверхность>/` (на месте screens): `brief` (оффер, одно целевое действие, трафик и осведомлённость, уровень,
  юрисдикция, пробелы) → `meaning` (позиционирование, иерархия сообщений, возражения) → `facts` (с источниками, демо-метка) → `funnel`
  (источник → посадочная → действие: форма / квиз / мессенджер → «спасибо» → CRM; события и цели; честная срочность, цена) →
  `page-plan` (каркас по типу × осведомлённости, 8–12 секций, роли → блоки → слоты, первый экран, бюджет уровня) → `copy-deck`.
  Карта сайта — только у многостраничника.
- Слой дизайна `design/<поверхность>/` (craft легален только здесь): мудборд и направление подачи, план ассетов, исходники ДС и холста
  Claude Design, реестр ссылок на артефакты, последний результат проверок.
- Порядок по базе: бриф → смысл и факты → воронка → структура → тексты по слотам и аудит → мудборд и 2–4 направления → ДС → ассеты →
  холст (вайрфрейм с реальными текстами → макет 1440/390 → прототип) → проверки по постоянной просьбе.
- Развилки с наброском заказчика (§2–3): ассеты до или после ДС; тексты до или после вайрфрейма; уровень амбиций в брифе или последним
  слоем. Живую страницу собирает отдельный репозиторий кода по спроектированному в стратегии (Р99): пакет на выходе
  дизайна должен быть полным и машиночитаемым; ворота скорости и аудит живой страницы — там.
- Расхождение баз к сверке: creative — «лендинги L1», site — «L0 для лидогенерации».
- Решено заказчиком 26.09 (Р100–Р102): ассеты до ДС, ДС — по ассетам; тексты — по базе, до вайрфрейма; уровень амбиций — в брифе.
  Порядок лендинга для blueprint: слой страницы (бриф с уровнем → смысл и факты → воронка → структура → тексты и аудит) → слой дизайна
  (мудборд → направление → ключевые ассеты → ДС по ассетам → вайрфрейм → макет → слои движения, 3D, видео → проверки).
