# План: design-deep-dive в business-strategy-template

Живой документ журнала сборки (`research/design-build/`). Решения — `DECISIONS.md` (Р-номер = номер строки), текущее положение —
`STATE.md`, устройство скилла — `phase-3/SKILL-MAP.md`. Прежняя редакция плана — `phase-3/archive/PLAN-before-phase-3.md`.

## Цель
Репозиторий-проектировщик business-strategy-template получает полную систему проектирования и дизайна:
- скилл `design-deep-dive` с базой знаний внутри (8 баз: ux, ui, site, text, creative, ai-media, blender, claude-design), утилитами,
  схемами, данными и калибровочным набором; пара `design-audit`; агенты — консультант по базе и критик свежим контекстом;
- workflow: вход почти с любого места; тип продукта (сайт / лендинг / SaaS) задаёт маршрут `entrypoint`; «просто сайт» → сразу в дизайн;
- слой проекта переписан сверху вниз: vision (шире) → capabilities (строже) → interfaces → screens → FSD; для сайта и лендинга — слой
  страницы (бриф, карта, план, факты, copy deck, воронки);
- макет — Claude Design в сессии Claude Code: холст — тип артефакта Design, дизайн-система — тип Design System, исходники в репозитории,
  синхронизация «прочитать → слить → опубликовать»; `kit` — автопроверки и запасной путь.

Принцип (заказчик): при создании дизайна агент видит карту всех знаний и смешивает нормы разных баз в цельную идею; references
связаны между собой, а не разложены по ресерчам.

Ограничения: всё внутри репозитория (он не знает о внешних); не плагин; только Claude Opus 5.5; модели не от Claude — только для
генерации картинок и видео (Р47); экономия контекста — прогрессивная загрузка, роутинг, скрипты, субагенты.

## Сквозные правила работы
1. Работа в шаблоне — на GitHub (gommgo/business-strategy-template): в облаке — ветка сессии `claude/…` (remote `origin`),
   слияние в main и PR — по слову заказчика (Р152); в локальном клоне — main, remote `github` (`origin` там —
   git.stit.tech, не трогаем); каждый принятый шаг — коммит и сразу push (Р143, Р165).
2. Главная сессия — дирижёр: тяжёлое чтение делают субагенты на Opus 5.5 по одному, цепочкой; отчёты — в файлы, в чат — резюме.
3. Каждая сессия начинает со `STATE.md` и `DECISIONS.md` и заканчивает их обновлением; решения — только дописываем в конец.
4. Механика — скриптами (перенос, пути, подсчёт, проверки): повторяемо, без токенов, проверяемо. Суждение — модели.
5. Каждый шаг измеряем (токены по калибровке Opus 5.5, размер, покрытие правил, битые ссылки), а не оцениваем на глаз.
6. Ничего не удаляем насовсем: только в корзину и по команде заказчика.
7. Тексты скилла — по стандарту `/claude-api prompt-audit` (SKILL-MAP §7).

## Готовность по фазам
- **После Ф7 — ручной режим.** Маршрут, этапы, формы и скиллы на месте, но вход холста, приёмку и ДС агент собирает по
  формам сам, без утилит: медленно и с риском потерять поле. Для внутренней пробы, не для клиента.
- **После Ф8 — технически рабочий.** Утилиты по файлам проекта, адаптированный код баз, окружение и самопроверки; нормы базы
  практикой не проверены, пороги не откалиброваны.
- **После Ф9 — боевой, плюс-минус.** Три продукта доведены до принятого макета и аудита, судья откалиброван голосами
  заказчика, находки внесены в шаблон; можно брать клиентский проект. Если один из пилотов — реальный клиентский проект,
  боевой режим наступает внутри Ф9.
- **После Ф10 — чистый, готовый к бою.** Без журнала сборки и хвостов ресерчей, база выровнена и ужата, тексты прошли
  prompt-audit. Массовые форки — отсюда: форк копирует шаблон целиком и без общей истории, всё лежащее в шаблоне уедет к клиенту.

## Риски
- Правила базы не проверены практикой → пилоты; пороги почти везде не откалиброваны.
- Opus-судья тянет к «богаче» → калибровочный набор, рубрика штрафует избыточность, решает человек (Р60).
- Окружение тяжёлое (Chromium, ffmpeg, Blender, ONNX; ≥ 3 ГБ памяти; `kit --min-free-gb 2`) → `install.sh` и смоук.
- Глобальный CLAUDE.md заказчика грузится в каждого субагента → у консультанта по базе отключить.
- Claude Design — бета с серверными флагами → снимок версий и проверка дрейфа; нет типов в среде → `kit`.
- Тип Design запрещает самопроверку без просьбы → постоянная просьба на проект (Р64).
- Контекст шаблона всегда ≈ 22 тыс. токенов, листинг скиллов переполнен → описания сокращаем, навигатор скрыт от автовызова.
- Правило forward-only грузится при правке любого md, а kb до уборки полна журнальных частей → уборку не делать попутно, только в Ф10.
- Размер шаблона ≈ 45–50 МБ (принят, Р96).
