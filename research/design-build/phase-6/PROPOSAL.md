# Ф6 — как проводим: предложение к встрече с заказчиком (Р144)

Рабочий документ журнала. План — `../PLAN.md` «Ф6», решения — `../DECISIONS.md`. Готовность Ф6 — заказчик утвердил
blueprint одной страницей (Р106).

## 1. Что получится на выходе
- **Страница решений (одна) — её утверждаете вы.** Каждое решение — 1–2 строки: что решено и почему; вверху — маршруты по
  роду продукта, внизу — что меняется в шаблоне и чего это стоит.
- **Приложение-спецификация — для Ф7, без утверждения.** Каждое из 71 действия Ф6 сверки (`phase-4/actions.tsv`) получает
  ответ и место, где его реализуют (файл формы, этап, раздел `references/`). Сюда же — контракты этапов «вход → выход →
  проверка → кто утверждает» (Р118).

## 2. Что решает blueprint (группы)
| группа | главные вопросы |
|---|---|
| A. Маршруты | лендинг, многостраничник, SaaS (+ бот и мобильное — что из дизайна им нужно); вход с любого места и «просто сайт → сразу в дизайн» (`_phase-jump.md`); где маршрут выбирает `entrypoint` |
| B. Слой страницы | состав (бриф, смысл, факты, воронка, план, copy deck; карта сайта — у многостраничника), папка в `docs/projects/_template/`, кто ведёт: этапы `design-deep-dive` или свой исполнитель |
| C. Слой дизайна | мудборд и направления, арт-дирекция, план ассетов и паспорт визуала, ДС (артефакт Design System + токены DTCG + «тип → компонент»), холст, проверки; craft легален только здесь (Р76 п. 1) |
| D. Спорные узлы порядка | «ключевые ассеты → ДС по ассетам» (Р100; нормы в базах нет — паспорт сайта из арт-дирекции, SaaS из токенов); этап ассетов у SaaS; живая 3D-сцена после макета; место текстов интерфейса SaaS |
| E. Вход холста и приёмка | раскладка входа (TR-44 и ещё ≈ 15 действий), проекции брифа, фактов, текстов, голоса и движения; раунд правок (стоп после отказа публикации: «ещё один» в cd 05/01 §6 против «третий» в cd 06/03 §1, §5); проверки по постоянной просьбе (Р64); судья |
| F. Слой проекта для SaaS | UX-дельта (SYNTHESIS §7): vision шире, реестр capability, модель объектов, сценарии, ИА, состояния S01–S24 и `ui:` в screens, карта экранов |
| G. Пакет для репозитория кода | состав и форматы (Р99), ворота исходов и утилиты «после сборки» (GT-03) |
| H. Устройство скиллов | `design-deep-dive` (этапы и роутер), `design-audit`, агенты (консультант по базе, критик), ветки `entrypoint` и клиент-режима, место в роутере `CLAUDE.md` §2 и листинге скиллов |

## 3. Как проводим — предлагаемый порядок
1. **Встреча (сейчас).** Согласуем способ и ответы на вопросы §5.
2. **Каркас страницы — оркестратор; затем остановка: заказчик смотрит список решений до агентов (Р149).** Список решений по группам A–H с вариантами и рекомендацией; входы читаю сам
   (PLAN Ф6, REPORT §7, `actions.tsv` Ф6, WORKFLOW-INPUTS §5, SYNTHESIS §7–§8, Р99–Р102, Р118, Р138–Р140, Р146–Р148,
   карта, находки Ф5 для Ф7 — `phase-5/check/grade.md` §5).
3. **Агенты-темы — по одному, цепочкой через `phase-6/CHAIN.md`.** Каждый читает реальные файлы шаблона и базы, пишет свой
   раздел спецификации и 5–10 строк страницы с вариантами:
   - T1 — слой страницы и маршрут сайта и лендинга (B, A, часть D);
   - T2 — слой дизайна, ДС, ассеты, вход холста и проверки (C, D, E);
   - T3 — слой проекта для SaaS и стыки с FSD, mobile, ботом (F, часть A);
   - T4 — устройство скиллов, агенты, `entrypoint` и клиент-режим, пакет для кода (H, G).
   T1 и T3 независимы — можно параллельно. Решения по структуре принимаю я и записываю в DECISIONS (Р23, Р106).
4. **Сборка страницы — оркестратор.**
5. **Сухой прогон — свежий агент.** Три сквозных сценария по blueprint: лендинг услуг, многостраничный сайт, SaaS — от
   входа до пакета для кода. Ищет дыры, этапы без входа или проверки, противоречия с DECISIONS и `canon.tsv`.
6. **Утверждение — вы, одна страница.** Правки — и снова сухой прогон, если они затрагивают маршрут.

Объём: ≈ 4–6 агентов по 25–35 минут; одна-две сессии.

## 5. Вопросы на встречу — отвечены: способ — Р149, UX-дельта в этой сборке — Р150, X-59 (а) — Р151; пилоты — позже
1. **Способ проведения** (§3): так, или иначе (например, всё сам без агентов-тем, или меньше тем).
2. **Объём UX-дельты для SaaS (F).** Она меняет существующие слои проекта (vision, capability, interface, screens) — по
   `CLAUDE.md` §5 это правка накопленной продуктовой модели и контракта всех слоёв. Варианты: (а) в этой сборке, вместе с
   лендингом и сайтом; (б) сначала сайт и лендинг, SaaS — отдельным треком после их пилотов; (в) для SaaS в этой сборке только
   слой дизайна поверх текущих screens, дельта — после.
3. **X-59 — референсы с Dribbble, Dprofile, FWA** (`phase-4/REPORT.md` §5): (а) вы листаете, агент пишет ссылку и значения
   текстом, без автора и превью — рекомендуем, действует сейчас; (б) как (а) плюс поле автора; (в) скрипт поиска и библиотека
   превью вне репозитория — риск по условиям площадок ваш.
4. **Пилоты (Ф9)** — можно ответить позже: реальные продукты или учебные; бюджет на генерацию ассетов (PLAN «Открытые
   решения»).
