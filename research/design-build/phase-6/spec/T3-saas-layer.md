# T3 — слой проекта для SaaS и стыки с FSD, mobile, ботом: спецификация Ф6

Рабочий документ журнала (Ф6, Р149, Р156). Тема — UX-дельта слоя проекта для SaaS (Р150): vision, роли и постуры,
поверхности и их род, модель объектов, capability, сценарии, ИА, экраны (карта, маршруты, состояния, `ui:`, тексты),
контракт генерации экранов, бриф приложения, стыки с FSD, mobile и ботом, перевод заполненных проектов форков.

Пути шаблона — от корня репозитория; `_template/` = `docs/projects/_template/`; короткие адреса базы — по `kb/INDEX.md`
§1 п. 3 («ux 13/04 §14»). Кандидаты проверок из журнала Ф2 (`phase-2/ux/ux-верх.md` §3.3 — CAP, MX, RL, GL, SC, IA, VS;
`ux-низ.md` §3.1–§3.5 — ST, RT, CP, TX, AX, MB, GC) пересекаются по имени с id узлов Ф4 (GL-*, ST-*, TX-*): в этом
файле они названы «кандидат ux-верх GL-01» и т. п.; в Ф7 правила аудитов получают свои id `R-*`.

Итог против каркаса: принято 8, изменено 8, новых 2 (раздел 1). Главное: колонка рода — `web-kind` (не `kind`);
дизайн SaaS входит дважды — после сценариев (бриф на вид, карточки стиля, токены) и после stable-экранов (компоненты ДС,
макет); объекты и действия — до capability; мобильные сценарии пишутся в vision, бриф их проецирует; контракт генерации
ux 11/04 §7.3 — 10 разделов, не 9; `shared-ui` не обязан покрывать все `ui:` (CM-10); карта экранов и реестр маршрутов —
поля экрана и свод `screens/<surface>/map.md`; тексты интерфейса — реестр `screens/<surface>/texts.md`; путь перевода
форков — режим «перевод формы» у исполнителей.

## 1. Решения

### A1. Род поверхности — изменено (имя колонки, правила, каскад)

- **Решение.** В реестре `surface.md` — колонка `web-kind` (род веб-поверхности), только у `type: web`: `landing` ·
  `site` · `app`; у остальных типов — `—`, маршрут задаёт сам `type`: `admin`, `desktop`, `embed` — маршрут SaaS;
  `mobile` — слой `mobile/`; `bot` — `telegram-bot-flow/`; `api`, `other` — без композиции. Значения `type` не
  меняются. Колонка встаёт перед `status` (последняя колонка — всегда `status`, `_template/project/README.md` «Принципы
  оформления»). Производная сводка рода продукта — раздел vision `Name` (Р76 п. 2, F1).
- **Почему.** `type` читают код-репо и хаб: фронтовые типы `web · admin · desktop · embed` задают FSD-карту
  (`_template/fsd/README.md`), `<org>/infra` читает `surface.md` (`docs/README.md` «Что docs отдаёт соседям»); новые
  значения `type` каскадят в пикеры, маршрутизацию, `/cross-audit` и привязку `surface` в `docs/stack/service.md`
  код-репо (Ф1 05 §3, вариант Б). Тонкий тип сайта — не колонка, а поле брифа `site_type` (`kb/site/02-site-types/
  vocabulary.yaml#site_type`, T1): `landing` ↔ `landing-site`, `site` ↔ многостраничные `site_type`, `app` ↔ `web-app`
  («веб-сервис после входа… ux-research и ui-research», там же, `status: out-of-scope` для site).
- **Имя.** `web-kind`, а не `kind`: «kind» в шаблоне — тип сущности (`<kind>:<slug>`, «7 kind», `CLAUDE.md` §7), колонка
  `kind` у поверхности читалась бы как «kind поверхности»; приставка `web-` называет, у какого `type` колонка живёт.
  Прецедент колонки-перечисления `kind` есть (`constraint.kind`), но там путаницы с маршрутизацией нет.
- **Каскад.** `surface.md`: критерий «род веб-поверхности» и тест; `/project-deep-dive` фаза `surface` спрашивает род
  у `web`; `/project-audit`: `web-kind` пуст у `type: web` при stable или задан у другого типа — error, значение вне
  перечня — error (R-STRUCT-003); `entrypoint` «Выбор поверхности»: `web` + `landing`/`site` → слой страницы (T1),
  `web` + `app` → interface → screens → FSD (T4); клиентский пикер мест делит «web-сайт» на «сайт или лендинг» и
  «веб-сервис, кабинет» (H6, T4); углы `/cross-audit` `surface-*` учитывают род (A9 — T1, T4).
- **Варианты.** (а) колонка у `web` — рекомендация; (б) колонка у всех поверхностей — лишняя: у `admin`, `mobile`, `bot`
  род однозначен; (в) новые значения `type` — ломают контракт с код-репо.
- **Ф7.** `_template/project/surface.md` (колонка, критерий, тест, пример), `_template/project/README.md` (таблица
  файлов), `docs/projects/README.md`, `docs/README.md` (строка handoff: `surface.md` несёт `web-kind`),
  `.claude/skills/project-deep-dive/references/{field-checklists,phases}.md`, `.claude/skills/project-audit/references/
  rules.md`; маршрутизация и клиентский пикер — T4.

### A4. SaaS: когда начинается дизайн — изменено (два входа, бриф в два приёма)

- **Решение.** Дизайн SaaS идёт рядом с экранами и входит дважды.
  - **Вход Д1 — после этапа «сценарии»** (артефакты шагов 1–11 ux 13/04 stable: vision, роли и постуры, поверхности,
    объекты и действия, capability, сценарии хабов): бриф на вид — ядро (тип приложения и постуры, плотность по
    умолчанию, роли статусов объектов, ИИ-слой, язык, указатель, темы, бренд, цель доступности, мобильный объём) →
    2–3 карточки стиля (ui 11/02 §2.4, VI-46) → выбор заказчика → токены ДС по семи ручкам (ui 14/09 шаг 2) → паспорт
    визуала из токенов (ai-media 06/01 §3) → иконки (ui 07/01).
  - **Вход Д2 — после stable-экранов поверхности** (шаги 13–24): дополнение брифа (состояния с визуальным кодом из
    наборов экранов, плотность по областям из карты экранов, каркас и ширины, инвентарь `ui:`) → сопоставление «тип →
    компонент ДС» и покрытие каждого названного типа (Р29, C5 — T2a) → иллюстрации мест из ui 07/02 §1.1 (пустое
    состояние, ошибка, успех, онбординг) → вайрфрейм с черновыми текстами → макет экранов по контракту генерации (F8) →
    чистовой макет — после утверждения текстов (D5) → проверки → пакет для `<org>/frontend`.
- **Почему.** «Ничего не рисуй, пока не заполнены артефакты шагов 1–13» (ux 13/04 выжимка п. 1, §1) говорит об
  экранах; карточка стиля — не экран: её делают «параллельно с UX, а не после него» (ui 11/02 §1.4) и «до того, как
  нарисован хоть один экран» (ui 11/02 §1.1). Поля брифа ux 13/04 §25 делятся по источникам: тип, постуры, статусы
  объектов, тема, бренд — шаги 3–6; состояния с визуальным кодом, плотность по зонам, каркас и ширины — шаги 14–23;
  поэтому бриф собирается в два приёма. Токены нужны экранам до макета: `maxlen` текстов выводится из ширины
  компонентов ДС (ux 07/05 §4.6, TX-18). Макет без stable-экранов переделывается, контракт генерации собирается только
  из stable-артефактов (кандидат ux-низ GC-01; ux 13/04 §26).
- **Шаг 13 против шага 11.** Каркас ставил вход после шага 13. В шаблоне шаг 12 (реальные данные) — производный
  демо-набор (F9), шаг 13 (что переживает переход) — таблица экранов `map.md` (F6); стилю они не нужны, поэтому вход
  Д1 — после шага 11.
- **Шаги ux 13/04 → этапы шаблона** (раздел 3 — контракты):

| шаги | этап шаблона | где артефакт |

- **Ф7.** `references/phases.md` скилла `design-deep-dive` (таблица маршрутов и этапы Д1, Д2 — T2a, T4), поля брифа

### A6. Бот и мобильное в этой сборке — принято (только стыки)

- **Решение.** Маршрута макета для `mobile` и `bot` в этой сборке нет (Р150 называет сайт, лендинг и SaaS; Р156 п. 4).
  Стыки записываются в каноны их слоёв, контракт с код-репо меняется только добавлениями.
- **mobile берёт:** токены ДС проекта — источник значений темы `<org>/mobile` (G2); голос продукта (text 05/01 §2,
  TX-30); тексты жанра `interface` с ролями по полям (TX-45); соответствие ключей `states` словарю S01–S24 — ключи не
  переименовываются (ST-01, Р125); паритет по умолчанию и урезание с основанием (ST-20, F11); у типов на поверхности
  `mobile` состояние `hover` не требуется (`kb/common/components.yaml`, шапка, правило 4); тема по умолчанию `system` в
  `shell.md#Theme & locale` согласована с CN-104 (две темы — умолчание по системе).
- **бот берёт:** голос продукта; тексты жанра `interface` с ролями полей (TX-43, TX-45); разведение пусто и отказа у
  ключа getter'а (ST-24); путь к человеку (ST-19, раздел 4.2); S18, S23, S24 в окне — текстом ролей `title`, `body`,
  `status` (TX-43); медиа сообщений по паспорту визуала — после пилотов.
- **Почему только стыки.** Слои mobile и бота строже верха цепочки (Ф1 00 п. 2), их ключи — handoff-контракт
  (`CLAUDE.md` §8); стык со словарями состояний, текстов и голоса нужен уже сейчас, чтобы продукт с веб-кабинетом,
  приложением и ботом говорил одним голосом и одними словами.
- **Ф7.** `_template/mobile/README.md` (разделы «Стык с дизайном», «Состояния экрана и словарь», «Тексты: роли и
  жанр», ссылка на норму паритета), `_template/mobile/_template/shell.md` (запрет «значения токенов темы — код-репо» →
  «значения — токены ДС проекта»), `_template/telegram-bot-flow/README.md` (разделы «Путь к человеку», «Тексты: роли и
  жанр», «Состояния окна»), формы бота — раздел 4.2.

### D3. SaaS: ассеты — принято

- **Решение.** Этапа ключевых ассетов до ДС у SaaS нет: ДС первой, паспорт визуала — из токенов, иконки и иллюстрации —
  по ним (Р140). Иллюстрации в продукте — только в местах ui 07/02 §1.1 (пустое состояние, онбординг, ошибка, успех и
  веха, анонс), на рабочих экранах админки их нет; метафору иллюстрации пустого состояния экран называет из списка
  паспорта (VI-55, F7). 3D в кабинете обычно не нужен (blender 01/02 §7; `kb/INDEX.md` §5 «SaaS и кабинет»).
- **Почему.** Конвейер ai-media 06/01 §1: «квиз/бриф → style tile + токены → паспорт визуала → спецификация ассета →
  генерация»; правила вывода паспорта из токенов — ai-media 06/01 §3 (`vlm_to_dna.py from-tokens`); паспорт
  иллюстраций заполняется «до первой картинки» (ui 07/02 выжимка п. 3). Нормы «ключевые ассеты до ДС» для приложения
  в базах нет — она решение заказчика для сайта (Р100) и в базах тоже не записана (Р140).
- **Вариант (б)** «как у сайта, если у кабинета своя иллюстративная система» — отклонён: существующий стиль иллюстраций
  бренда входит в бриф ограничением бренда (ux 13/04 §25 «Ограничения бренда»), а паспорт всё равно выводится из
  токенов и бренда.
- **Для T2a.** Смешанный продукт: у сайта с двумя мирами — два паспорта, маркетинговый и продуктовый, «а не один
  средний» (ai-media 06/01 §1); ДС одна (A5).
- **Ф7.** `references/phases.md` `design-deep-dive` (маршрут SaaS, этапы ДС → паспорт → иконки → иллюстрации — T2a);
  `screens` — атрибут `illustration` у `ui:EmptyState` (раздел 4.3).

### D5. Тексты интерфейса SaaS — принято (форма уточнена)

- **Решение.** Тексты интерфейса поверхности живут в реестре `screens/<surface>/texts.md`; дерево экрана держит ключ
  `text:<key>`, а не литерал. Строка реестра: `key` (ux 07/05 §3.1: `{раздел}.{экран}.{элемент}.{роль}`) · `role`
  (закрытый список ux 07/06 §7.2, 32 роли — Р127) · `text` (язык по умолчанию; ICU для чисел и плюрализации — ux 07/05
  §4.4) · `maxlen` (знаков, из ширины компонента ДС; до ДС — ориентиры ux 07/05 §4.6) · `action` (словарь действий) ·
  `object` (глоссарий объектов) · `group` (меню, набор статусов объекта) · `context` (смысл строки для автора и
  переводчика, ux 07/05 §3.2) · `status` (`assumption` → `approved`). Второй язык — колонка `text-<locale>` по
  `shared-lib#i18n` FSD.
- **Цепочка.** Черновик пишет агент «допущением» (`assumption`, Р25) из глоссария, словаря действий, голоса продукта
  (TX-31) и правил ux 07/02; линтер `copy_lint.py` в жанре `interface` с ролью строки как входом (TX-04, TX-05; Ф8) и
  межстрочные проверки ux 07/06 §7.3 (TX-21; Ф8) — до утверждения; `maxlen` — ворота, длина по роли в словах — сигнал
  (TX-18); утверждает владелец продукта (Р25) — статус `approved`.
- **Когда.** Stable-экран требует, чтобы каждый его ключ был в реестре и проходил линтер (0 error); утверждение
  владельцем не требуется для stable-экрана — оно требуется до чистового макета (Д2) и до манифеста готовности для
  `<org>/frontend` (G1 — T4). Так структура экранов не ждёт утверждения каждой строки, а на холст и в код идут только
  утверждённые тексты (Р101 для сайта — та же логика).
- **Роль части компонента** — из `kb/common/components.yaml#text_roles` (текст под `ui:Button` — `action`, под
  `ui:Field.Error` — `error`); роль ключа ≠ роль части — error. Тексты состояний — роли TX-43 (S01–S03 — `empty` и
  `action`; S13 — `error`, `inline-message` или `banner`; S07, S24 — `status`; S18, S23 — `title`, `body`, `action`).
- **Почему здесь, а не в слое дизайна (вариант б).** Текст — узел дерева экрана (кандидат ux-низ TX-01…TX-08), ключ
  строится по экрану и роли; линтер и `maxlen` — проверки структуры до макета (07/01 §13.1 «текст пишется до
  макета»); холст получает литералы утверждённых строк проекцией (E1 — T2b), второго источника нет.
- **Статусы.** Реестр интерфейса — два значения Р25 и TX-45 (`assumption`, `approved`); copy deck сайта — схема text
  (`draft · checked · approved · rejected`, `copy-deck.schema.json#/$defs/status`). Свести словарь статусов — стык с
  T1 (раздел 6).
- **Ф7.** Новый `_template/screens/_template/texts.md`; `_template/screens/README.md` (раздел «Тексты интерфейса»,
  префикс `text:`); `screen-deep-dive` (`SKILL.md`, `references/field-checklists.md`, `references/draft-stable.md`,
  `references/tree-notation.md`); `screen-audit/references/rules.md`; правка `CLAUDE.md` §3 (строка владельцев текстов
  интерфейса) — T4.

### F1. vision — принято (разделы, минимум, механизм «допущения»)

- **Решение.** `vision.md` расширяется в самом файле (Р19) до 12 разделов; имена H2 — английские, как у уже

### F2. Роли и постуры — изменено (место уточнения постуры)

- **Решение.** Постура — у пользователя продукта (`user`), второй таблицей `## Постура` в `user.md` (прецедент двух
  таблиц — `integration.md`): `user` · `surface` · `hours` · `return` · `main-work` · `posture` · `density` ·
  `accelerators` · `learning` — восемь колонок ux 13/04 §4 плюс `surface`. Строка с `surface: —` — постура пользователя
  на всех его поверхностях, пишется на этапе «роли и постуры» до реестра поверхностей (Р22); строка с `surface: <slug>`
  — только когда на этой поверхности постура другая (менеджер в админке — суверенная, в приложении — транзитная).
  `who` в interface постуры не несёт: уточнение по поверхности живёт в той же таблице, одно место.
- **Перечни.** `return`: `daily` · `weekly` · `monthly` · `rare`; `main-work`: `yes` · `no`; `posture`: `sovereign` ·
  `transient` · `auxiliary` · `mixed` (01/01 §5.1; `mixed` — «смешанная постура» клиентского кабинета, 13/04 §4);
  `density`: `high` · `medium` · `low` — поведенческая потребность, числа — ДС; `learning`: `expected` · `minimal` ·
  `excluded` (13/04 §5); `hours` — число или диапазон; `accelerators` — частые операции или `—`.
- **Почему не у `who` (вариант каркаса «`who` уточняет»).** `who` рождается в interface после capability, а постура
  нужна до поверхностей: решение о разделении админки и клиентской части принимается по постурам (13/04 §17 п. 3) на
  этапе поверхностей (Р22; ux-верх §3.6). Отдельный kind `role` — пятое понятие адресата рядом с `who ≠ user ≠ segment ≠
  subject` (ux-верх §3.6); глоссарий уже переводит роль ux в слой проекта как «участник (who)» и «пользователь (user)»
  (`kb/common/glossary.md` §Роль).
- **Проверки.** `/project-audit`: у пользователя поверхности маршрута SaaS при `stable` строка постуры заполнена
  целиком, нет пользователя «все пользователи» (кандидат ux-верх RL-01, error@stable); на одной поверхности пользователи
  с `sovereign` и `transient` без записанного решения о разделении (state поверхности, «Доменные решения») — warning
  (RL-02).
- **Ф7.** `_template/project/user.md` (раздел «Постура»: колонки, критерии, тест), `_template/project/README.md`,

### F3. capability — принято (реестр 10 колонок, паспорт, проверки)

- **Реестр** `capability/<surface>.md` (Р76 п. 9, ≤ 10 колонок): `slug` · `name` · `description` · `value` · `user` ·
  `object` · `action` · `priority` · `trace` · `status`.
  - `object` — ровно один объект глоссария, `action` — ровно одно действие словаря (Г1; обязательны при `stable`,
    `—` в `draft` — F12);
  - `priority`: `hub` («идеальный шторм»: частота × сложность × фрустрация) · `critical` (редкая, но критичная) ·
    `regular` (ux 13/04 §7);
  - `trace` — трасса вверх: `job:<slug>` (`ajtbd/job`) и `hypothesis:<slug>` (`hypothesis-map/hypothesis`) одним
    массивом или `—`; заменяет колонки `jobs` и `hypotheses` — иначе реестр выходит за 10 колонок; направление ребра
    (capability → вверх, авторски снизу) не меняется;
  - вхождение в MVP — не колонка: список MVP живёт в vision (`MVP`), второе место разошлось бы.
- **Паспорт** — раздел `## Паспорта`, подраздел `### <slug>` на возможность, строки «поле: значение»: `need`
  (потребность ≠ задача) · `trigger` (когда и откуда, точки входа) · `outcome` (какой объект появится или в какой статус
  перейдёт) · `acceptance` (1–3 проверяемых утверждения + задача для теста) · `frequency` (`hours-daily` · `daily` ·
  `weekly` · `monthly` · `rare` · `once`) · `error-cost` (`low` · `medium` · `high` + кто платит) · `reversibility`
  (`undo` · `soft-delete` · `confirm` · `irreversible`; по умолчанию — из словаря действий) · `scope` (`own` · `team` ·
  `all`) · `posture-exception` (транзитная функция внутри суверенной) · `depends-on` (`integration`, `constraint`) ·
  `metric` · `justification` (если `trace` пуст и возможности нет в MVP) · `ai` (`no` или блок ux 13/03 §1.4:
  автоматизация или аугментация, точность, цена ошибки, путь без ИИ, данные, чего модель не делает, кто отвечает,
  метрики). Паспорт обязателен у `hub`, `critical` и у любой ИИ-функции; у `regular` — по желанию (каркас, Р76 п. 9).
  Форма раздела — как секции окон и use-case бота (`_template/telegram-bot-flow/README.md` «Форма трёх файлов фичи»).
- **Урезание** — раздел `## Урезание` у поверхности, где ценности другой поверхности сознательно нет (прежде всего
  `mobile`): `slug` · `capability` (`<surface>:<slug>` ценности на другой поверхности) · `why` (основание — данные об
  аудитории) · `review` (когда пересмотреть) · `status` (ST-20; ux README № 57).
- **Критерии** (раздел «Критерии capability» переписывается): прежние 1–5 + гранулярность Г1–Г7 ux-верх §3.2 — одна
  тройка ядра; имя ≤ 4 слов «глагол + объект» без «и» и зонтичных глаголов (управлять, вести, администрировать, работать
  с); не ниже шага (≥ 1 ситуация со своей целью); не выше шага карты историй (ситуации складываются в один путь к одному
  исходу); одна частота и одна обратимость; ориентиры количества (≥ 10 задач у продукта средней сложности, 3–5 хабов —
  hint); без слов UI и техники.
- **Двустороннее покрытие** (Р76 п. 9): stable-возможность ⇒ ≥ 1 ситуация той же поверхности с `situation.capabilities
  ∋ slug`; `hub` и `critical` ⇒ ≥ 1 сценарий (F5); экран называет главную задачу ссылкой на возможность (F6).

### F4. Модель объектов и словарь действий — принято (формы)

- **Решение** (Р21, Р76 п. 10). Два файла продуктового слоя рядом с vision: `object.md` — глоссарий объектов,
  `action.md` — словарь действий; канон — `_template/project/object.md`, `_template/project/action.md`; ведёт
  `/project-deep-dive` (новые kind `object`, `action`, фаза `objects` — F12), проверяет `/project-audit`.
- **`object.md`**, таблица объектов (01/03 §13, 13/04 §6): `slug` · `name` (единственное число, как видит
  пользователь) · `description` (определение одной фразой) · `examples` (2–3 реальных экземпляра — из материалов
  клиента) · `purpose` (зачем в системе и когда появляется) · `statuses` (статусы объекта — жизненный цикл; слово
  «состояние» занято состояниями экрана и элемента, `kb/common/glossary.md` §Состояние) · `aliases` (другие названия,
  они же запрещённые синонимы в текстах) · `creates` · `deletes` (пользователи или `system`, 01/03 §6) · `status`.
  Вторая таблица `## Атрибуты`: `object` · `slug` · `name` · `rank` (1–3 узнают экземпляр, 01/03 §5.3) · `type`
  (`text` · `number` · `money` · `date` · `datetime` · `enum` · `bool` · `file` · `ref:<object>`) · `required` ·
  `length` (мин / типичная / макс в знаках, ux 06/01 §6.3) · `values` (перечень для `enum`). Связи объектов — атрибуты
  `ref:<object>`, объект-связка — отдельный объект (13/04 §9).
- **Представления** (13/04 §10) вычисляются из рангов — все контексты «усечения одного порядка атрибутов» (01/03 §2.3):
  строка — 1–5, карточка — 1–3, результат поиска — 1–3 и родитель, строка выбора — 1–2, уведомление — 1–2 и что
  изменилось, крошки — 1, инлайн-ссылка — 1, страница — все. Третья таблица `## Представления` — только исключения:
  `object` · `context` (`row` · `card` · `search` · `option` · `notification` · `breadcrumb` · `inline` · `page`) ·
  `attributes` · `why`. Маркер типа («иконка, форма, цвет») — облик, слой дизайна (ux-верх §4, T2a).
- **`action.md`** (13/04 §6): `slug` · `name` (каноническое действие) · `description` · `verb` (глагол на кнопке) ·
  `past` (прошедшее время для тоста и журнала) · `banned` (запрещённые синонимы, непусто) · `reversibility` (`undo` ·
  `soft-delete` · `confirm` · `irreversible`, ux 04/10 §1.1) · `objects` · `status`.
- **Кто ссылается.** `capability.object`, `capability.action`; `data-items.object` (interface); `zone.object`;
  `screen.object`, `screen.key-action`, атрибут `action=` у `ui:Button` и `ui:Menu.Item`; `texts.object`,
  `texts.action`; `scenario` — «что меняется» (объект и статус).
- **Матрица «роль × объект × действие»** — вычисляемый вид отчёта `/project-audit` из capability (`user` × `object` ×
  `action`, `scope` — из паспортов) и `object.creates`/`deletes`; ручной таблицы нет (ux-верх §3.6). Колонки базы
  «контейнер · подтверждение · журнал» (13/04 §8) — контейнер и подтверждение — экраны, журнал — сценарий.
- **Проверки** (кандидаты ux-верх GL-01…05, в Ф7 — id `R-*`): у объекта определение, 2–3 примера, статусы, создатель и
  удалитель — error@stable; запрещённый синоним в `name` возможности, зоны, ситуации, блока — warning (07/01 §10.1); у
  действия один глагол, одна форма прошедшего, `banned` непусто — error; у объекта помечены три идентифицирующих
  атрибута — warning; коллекции и представления («каталог», «календарь», «дашборд», «отчёт») объектами — warning
  (стоп-лист + модель).
- **Почему не в `data-items` (вариант б).** «Одно понятие — одно слово» на весь продукт (07/01 §10.1), а `data-items`
  локален поверхности и без полей (`_template/interface/_template/data-items.md`); `data-items` остаётся словом
  участника на поверхности и ссылается на объект — это закрывает `data:<slug>.<field>` (ux-низ дельта № 7).

### F5. Сценарии — принято (kind `scenario` в interface)

- **Решение** (GL-07, Р79). Пользовательский сценарий ux — kind `scenario` в `interface/<surface>/scenario.md`: секция

  меняется), `### Ошибки` (шаг · что не сработало · что видит — id состояния S13, S14, S17, S18, S21… · как выйти),

  что видят остальные · при бездействии — срок, эскалация), `### Что меняется` (объекты и статусы — ссылки на глоссарий;

  `value` — формой словаря), `fills` (у каркаса); у `layout:` — `gap` (размер намерения = имя токена `space.*` ДС,
  NU-17), `justify`, `align`, `wrap`, `columns`, `areas`, `fill`, `span`, `fills`. `variant` и `size` у `ui:` уходят —
  облик решает ДС; атрибут вне списка — warning (кандидат ux-низ, дельта № 17).
- **Ссылки дерева:** `block:<slug>`; `data:<data-item>[.<атрибут>]` — атрибут объекта, на который ссылается
  `data-items.object` (F4); `text:<key>` — строка `texts.md` (D5); `icon:<имя>` — набор иконок ДС (сверяет слой дизайна).
- **Нотация** — валидный YAML в компактной форме (грамматика — раздел 4.3): узел без детей — строка-голова
  (`ui:Pagination`), узел с детьми — словарь из одного ключа-головы со списком детей (`ui:Button level=primary:`),
  узел со структурными атрибутами — словарь атрибутов (`items`, `columns`, `areas`, `fill`, `children`); голова —
  `<префикс>:<имя>[.<часть>]` и атрибуты `имя=значение`; `(fills: $slot)` → `fills=$slot`.
  - **Почему так.** (а) Нынешняя отступная запись не парсится (PyYAML: `ScannerError` на дереве блока, `ParserError` на
    каркасе, в `states` дети склеиваются — Ф1 03 §4.2), а README обещает детерминированную карту экранов; (б) явная
    форма `{ui: Button, level: primary, children: […]}` удобна схеме, но втрое длиннее и требует переписать все деревья;
    (в) компактная форма читается как прежняя, перевод механический (двоеточие у узла с детьми, `fills=`), голова
    разбирается одной регуляркой. Проверено в Ф6 на трёх образцах (дерево блока, дерево каркаса, `states`):
    `yaml.safe_load` (PyYAML 6.0.1) — без ошибок. Грамматика живёт один раз — в README screens; разбор и проверку делает
    скрипт (Ф8), JSON-схемы в `_template/` нет.
- **Слова канона** (GL-02, GL-04, GL-09): «внутренние области блока» (идентификаторы `block-*` не меняются), «слот
  каркаса», «компонент (тип закрытого словаря)». **Ширины и брейкпоинты** (NU-02, NU-03): `viewport` экрана и потока →
  ширины приёмки `kb/common/acceptance-widths.yaml`; ключи `shell.responsive` `xs…xl` — имена токенов `breakpoint.*` ДС,
  таблица сопоставления в README screens.
- **Проверки** (`/screen-audit`, скрипт Ф8): дерево парсится — error; `ui:` вне словаря и расширения, часть вне `parts`
  — error; атрибут вне списка — warning; ключ `states` вне словаря — error; обязательный набор не покрыт — warning,
  error@stable (замещает R-SEM-011 «6 канон-состояний»); у блока `source: own` нет S07 и S13 — error@stable; `text:`
  ключа нет в реестре, роль ключа ≠ роль части — error; литерал текста в дереве при `stable` — error.
- **Ф7.** `_template/screens/README.md` (Naming узлов, атрибуты, грамматика, состояния, приоритет, тексты, ширины),

  `screen-deep-dive/references/{tree-notation,field-checklists,draft-stable,raw-input}.md`, `screen-deep-dive/SKILL.md`

### F10. Стык с FSD — изменено (`shared-ui` не покрывает все `ui:`)

- **`pages.path`** — маршрут экрана `pages.screen` (`route` с параметрами); не совпал — error `/fsd-audit`; экран с

  error. Мост «роль-участник — роль доступа» проходит через `access` маршрута, а не через `who` как ACL (ux-верх §2,
  «матрица · модель прав»).
- **`shared-ui`** — колонка `ui-type` (тип `components.yaml` или расширения проекта); тип вне словаря — error. Правило
  каркаса «`shared-ui` ⊇ `ui:`» не принимается: слайс поднимается «при реальном переиспользовании», а тип может жить без
  слайса — компонентом ДС напрямую (CM-10, Р124; `_template/fsd/_template/shared-ui.md` «Критерии»). Покрытие каждого
  названного в экранах типа компонентом проверяет ДС (Р29; C5 — T2a, `design-audit` — T4). Запрет «Дизайн-токены и облик
  … живёт в коде фронт-форка» переписывается: токены — ДС проекта (слой дизайна), фронт выпускает из них тему.
- **`shared-api`** (ST-25) — сценарии данных покрывают обязательные состояния экранов поверхности: `empty` (S01),
  `populated` (идеальное) — имена контракта остаются; новые — slug словаря: `partial-few` (S04), `overflow-many` (S05),

  данные — демо-набор (F9).
- **`shared-lib`** — ключи строк i18n — ключи `texts.md` (ux-низ §3.7).
- **Ф7.** `_template/fsd/README.md`, `_template/fsd/_template/{pages,shared-ui,shared-api,shared-lib}.md`,

### F12. Порядок этапов слоя проекта SaaS — новое

- **Решение.** Маршрут SaaS со стороны слоя проекта: **vision → роли и постуры → поверхности → объекты и действия →
  capability → сценарии → interface → экраны → тексты интерфейса → FSD** (контракты — раздел 3). Против каркаса: объекты
  и действия — до capability; тексты интерфейса — отдельный этап после экранов.
- **Почему объекты раньше.** ux 13/04: шаги 5–6 (объекты, глоссарий, словарь) — до шага 7 (каталог задач); 01/03 §15:
  «объекты → связи → действия по ролям → сценарии → карта экранов»; «начинай с языка, а не с интерфейса» (13/04 выжимка
  п. 17); ядро capability — ссылки на объект и действие (CAP-02). Вход с capability не запрещён: в `draft` `object` и
  `action` — `—`, в словарях — stub-записи (раздел 3, «вход с середины»).
- **Почему тексты отдельно.** Этап «тексты интерфейса» назван узлом TX (TX-45); ключ строки строится по экрану (ux
  07/05 §3.1), `maxlen` — по ширине компонента ДС (§4.6); утверждение владельцем — до чистового макета, не до stable
  экрана (D5).
- **Фазы `/project-deep-dive`:** `discovery` · `user` («роли и постуры») · `surface` · `objects` (новая: `object.md`,
  `action.md`) · `capability` · `integration` · `constraint` · `market` · `cohesion`; сводка фаз и «логичные переходы»
  — по новому порядку; «порядок — рекомендация, не закон» остаётся (`references/phases.md`). Этапы «сценарии» и
  «interface» ведёт `/interface-deep-dive` (сценарий — первый kind на поверхности с хабами).
- **Ф7.** `project-deep-dive` (`SKILL.md` «Фазы проработки», «Сводка состояния»; `references/phases.md`),
  `interface-deep-dive/SKILL.md` («Сводка состояния»: сценарии хабов — первыми), таблица маршрутов `references/phases.md`
  `design-deep-dive` (T4).

### F13. Перевод заполненных проектов форков — новое

- **Решение.** Каноны меняются только вперёд: в `_template/` — одна текущая форма, без пометок о прежней. Данные форков
  переводят исполнители слоёв каскадом (F3 (а)): узкие аудиты находят записи не по канону, исполнитель предлагает
  пакет правок, человек подтверждает (`CLAUDE.md` §5 — правка накопленной продуктовой модели). Порядок — по
  зависимостям: продукт (vision, постура, род поверхностей, объекты и действия, capability) → interface (объектные
  ссылки данных, ИА-поля зон, сценарии хабов) → screens (нотация, ключи состояний, типы `ui:`, атрибуты, тексты в
  реестр, поля экрана, `map.md`) → FSD (`ui-type`, `path` и `guard`, сценарии данных) → стыки mobile и бота
  (добавочные поля).
- **Механика.** Раздел «Привести к канону» в `references/workflow-patterns.md` исполнителей (`project-deep-dive`,
  `interface-deep-dive`, `screen-deep-dive`, `fsd-deep-dive`) и шаг в «Что делать сразу при запуске»: скилл сверяет
  файлы поверхности с каноном; расхождений много — предлагает пакет: механические правки (скилл делает сам после одного
  подтверждения, показав различие) и смысловые (заводит `—` и открытые вопросы в своей ветке state). Текст — в
  терминах текущих правил, без прежних имён (`.claude/rules/forward-only.md`): «дерево не парсится — нормализовать»,
  «имя из `aka` — тип словаря», «ключ `states` вне словаря — ближайший slug по таблице ключей mobile», «колонки вне
  канона — разложить по колонкам канона».
- **Механические правки** (скрипты-нормализаторы Ф8 принимают вольный вход и выдают канон; таблица соответствий
  «прежнее → новое» — в этом журнале, раздел 4.5, а не в скиллах): дерево — в компактный YAML; `(fills: $x)` → `fills=$x`;
  `aka` → тип; `variant=accent|outline|ghost` → `level=primary|secondary|tertiary`, `size` — снять; ключи `states` → slug
  словаря; литералы текстов → строки `texts.md` (ключ по 07/05 §3.1, роль по `text_roles`, статус `assumption`);
  `jobs` и `hypotheses` capability → `trace`; `transitions-to-screen: [a]` → `[{to: a}]`; новые колонки — `—`.
- **Смысловые правки** — владельцу формулировки (`CLAUDE.md` §3): новые разделы vision, постура, объекты и действия,
  ядро capability (`object`, `action`, `priority`), паспорта хабов, сценарии, ИА-поля, тип, объект, главная задача и
  ключевое действие экрана, обязательные наборы состояний, `maxlen`, род поверхности `web`.
- **Статусы.** Stable-записи скилл не понижает (понижение — только аналитик, `_template/project/README.md` «Статус
  записи»): узкий аудит показывает у них error «обязательный слот пуст при stable» — это и есть список работ перевода;
  аналитик добивает запись или понижает её сам. Код-репо читают stable-записи как раньше: новые поля — аналитика слоя
  проекта, контракт кода (FSD, mobile, бот) меняется только добавлениями (`ui-type`, сценарии `shared-api`, ключ
  `empty` у getter'а бота).
- **Почему так.** Каскад исполнителей — уже принятый путь (F3, Р150); отдельный «скрипт миграции» с прежними именами
  нарушил бы forward-only в скиллах, а удалённый при уборке журнала (Ф10) — не дошёл бы до форков, которые подтянут
  шаблон позже.
- **Ф7.** `references/workflow-patterns.md` и `SKILL.md` четырёх исполнителей; нормализаторы — Ф8 (H10 — T4).
