## 3. Отступления от плана и спецификации

1. **Второй общий модуль `layer.py`.** Бриф называет один общий модуль (формат находок, коды, печать) — это `findings.py`.
   Разбор файлов проекта (md-таблицы, frontmatter, блоки YAML, interface, продукт, словарь компонентов) нужен всем
   четырём утилитам и их читателям (C5, C6, C11, C13), поэтому вынесен в `layer.py`, а не повторён. Решает оркестратор;
   предлагаю оставить.
2. **Правила сверх названных брифом.** `tree` проверяет и другие детерминированные R-STRUCT и R-TX (бриф это допускает):
   R-STRUCT-001, 002, 010, 011, 012, 013, 023, 025, R-TX-002, 004, 005, 006; R-STRUCT-001/002/023 — в части узлов
   дерева и контрактов блока (`block.data`, `form`, `tiles`, колонки реестра), ссылки полей экрана в продукт (object,
   тип параметра, main-task, key-action) проверяет `screen_map` под R-STRUCT-023, `screen.shell`, `blocks`, `who`,
   `zone`, `situations` — не проверяются (R-MIRROR и frontmatter-ссылки — чтением `/screen-audit`). `screen_map`
   проверяет ещё R-STRUCT-006. Ссылки в interface и продукт — только когда файл-источник есть.
3. **«Работа без сети» и «живые данные» — чтением.** Канон выводит `offline` и `stale` из решений поверхности
   (раздел «Решения» `map.md`), а у раздела нет машинного поля: решение — проза. `states` эти состояния не требует,
   а показывает в `show` пунктом «чтением» с текстом строки «Решений» (у `stale` — ещё у дашборда). Варианты: (а) так;
   (б) поле или строка-метка в «Решениях» (правка канона — C17 или Ф10). Сделано (а).
4. **`no-permission` из строки матрицы — только при `access: roles`.** Строка «Экран или маршрут целиком» держит S18
   обязательным, а сам S18 — «база для систем с ролями»; README экранов переводит это в `access: roles`. Без этого
   каждый экран (и служебный, и публичный) требовал бы `no-permission`. Канонический пример master-detail формы
   `screen.md` совпадает с набором утилиты ровно при таком чтении.
5. **Строки присутствия в своде — под R-RT-008, не R-RT-001.** Оба правила называют «каждый маршрут экрана — строка
   «Маршрутов» и наоборот»; одна проверка — одно правило: присутствие строк сверяет R-RT-008, R-RT-001 — уникальность
   маршрута на вьюпорте и строку-запрет. Иначе один дефект давал бы две находки.
6. **Выводимые колонки свода, которых канон не расписал.** `density` — самая высокая плотность постуры пользователей
   экрана (роли → `who.users` → «Постура»), с потолком типа: формы (`edit`, `settings`, `auth`) — не выше средней,
   мастер — низкая; без постуры — по типу (`scripts/project/data/screens.yaml`). `entry-points` — `старт`, `навигация` и входящие
   экраны; прочие пункты ячейки — слова аналитика, сборка их сохраняет. «Навигация» — строка на пункты одного уровня
   с одинаковой видимостью; `active` и `narrow` — слова аналитика, сохраняются. Порядок строк: «Карта экранов» — по
   `slug`, «Маршруты» — по маршруту. Решает оркестратор; все правила — в справке `screen_map` и данных.
7. **Достижимость по навигации** (R-COV-003) — буквально по правилу: пункт навигации делает достижимыми все экраны
   своей зоны, в том числе экран с параметром объекта. Строже — только экраны без параметров маршрута; не сделано.
8. **Нормализатор: литерал → ключ.** Раздел ключа — корневая зона записи (у каркаса и экрана без зоны — `app`), экран —
   `slug` без префикса раздела, элемент — действие узла, атрибут колонки или ключ состояния, иначе тип компонента;
   роль — первая роль части по `text_roles`, вне компонента — по правилу «Тексты состояний» (в `no-permission` и
   `not-found` первый текст — `title`, дальше — `body`), иначе `body`. Строка с тем же ключом и текстом
   переиспользуется, иначе ключ получает суффикс. Синонимы входа T3 §4.5 (`variant` → `level`) — в коде без слов
   «прежнее / новое»; ключи состояний — по таблице README mobile (читается из канона), неоднозначный ключ — первое
   состояние строки и пункт владельцу. Блок, который после правок не разбирается, остаётся как был — пунктом
   владельцу (канонической перевыдачи дерева нет: правки построчные, чтобы сохранить отступы и комментарии аналитика).
9. **`kind` находки — открытое слово.** Контракт перечисляет виды записей слоя экранов, но утилиты слоя дизайна (C5,
   C11, C13) будут писать свои (`system`, `ready` …): `findings` проверяет форму slug, а не закрытый список.
10. **R-SEM-015 механически — две проверки из пяти:** главная кнопка шапки блока, повторённая главной в пустом
    состоянии; два и больше пустых состояния, видимых одновременно (в одной дельте или в блоках своего источника), —
    только текст и третичные кнопки. «`not-found` об архиве», «`generating` без остановки», «дельта `offline` без
    доступного и отложенного» — чтением; состояние приложения в `states` экрана показывает R-STRUCT-022 с отсылкой к
    разделу каркаса.
11. **R-TX-004 — одна находка на ключ.** Правило считается по stable-экранам вместе с блоками их слотов и каркасом;
    строка `assumed` в каркасе дала бы находку на каждом экране. Находка ставится в месте употребления ключа и
    перечисляет stable-экраны.
12. **Фикстура — три папки:** манифест собирает слои подряд, поэтому «чистый», «дефекты» и «вольная форма» — фикстуры
    `cabinet`, `cabinet-defects` и `cabinet-freeform` (две последние — `extends: [cabinet]`).

## 4. Для следующих зон

- **Контракт находок (C5, C6, C11, C13 — первым пишет C3).** Модуль `scripts/project/findings.py`; подключение —
  `sys.path.insert(0, <папка project>)`, `import findings as F` (из другого домена — `kbpaths.use("project")`).
  - Строка JSON, поля по порядку `rule, severity, surface, kind, ref, path, message, fix`:
    `{"rule": "R-STRUCT-021", "severity": "error", "surface": "office", "kind": "shell", "ref":
    "app-shell#/tree/0/layout:stack/0", "path": "docs/projects/otves-office/screens/office/shells/app-shell/index.md",
    "message": "`ui:Navbar` — имя из aka словаря компонентов; тип словаря — TopBar", "fix": "заменить на `ui:TopBar` —
    /screen-deep-dive otves-office office shell:app-shell"}`.
  - `rule` — id правила `R-…` реестра аудита; `severity` — `error` · `warning` · `hint` (тяжесть по статусу —
    `F.severity_for(status, draft=…, stable=…)`); `surface` — slug поверхности или `null`; `kind` — вид записи словом-slug
    (у экранов `screen` · `block` · `shell` · `flow` · `map` · `texts`, у поверхности — `surface`; C5, C11, C13 — вид
    своей записи); `ref` — `<slug>` или `<slug>#<место>`: в дереве — JSON Pointer в разобранном YAML тела
    (`request-card#/states/not-found`, голова узла — сегмент пути), в своде — `map#<раздел>/<ключ строки>`
    (`map#Маршруты//requests`, `map#Карта экранов/requests-list`), в реестре — `texts#<ключ>`, у поверхности — её slug;
    `path` — `docpaths.rel(файл, repo)`; `fix` — что сделать и каким скиллом или пусто.
  - Коды выхода: 0 — нет `error`, 1 — есть (у `normalize check` — есть правки), 2 — ошибка вызова или окружения
    (`docpaths.parse` → `ap.error`; `F.ToolError` — битые данные утилиты или базы).
  - `check --json` печатает только строки находок; читатель — `F.parse_lines(stdout)` (чужая строка — `ValueError`).
    Сборка — `F.Report().add(...)`, печать — `F.print_findings(items, as_json=call.json)`, код — `F.exit_code(items)`.
  - Проверить файл строк — `python3 scripts/project/findings.py --validate FILE`.
- **Вызов утилит экранов.** `tree check|show`, `states check|show`, `screen_map build|check`, `normalize check|build`:
  `<команда> <slug> [<surface>] [--repo DIR] [--json]`; без `<surface>` — все поверхности кабинета (`web` рода `app`,
  `admin`, `desktop`, `embed`), поверхность другого рода — код 2. `screen_map build --out DIR` → `DIR/<surface>/map.md`;
