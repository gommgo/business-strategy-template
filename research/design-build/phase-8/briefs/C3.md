## Зона
Первые утилиты `scripts/project/` — по файлам слоя экранов проекта: разбор дерева, наборы состояний, свод `map.md` с
проверками маршрутов и приведение заполненного проекта к канону. Их зовут `screen-deep-dive`, `screen-audit`,
`design_audit` (C13) и сборщик входа холста кабинета (C11); разбор дерева читают покрытие ДС (C5) и контракт генерации
(C6). Ты — первый писатель контракта находок утилит `project/` (`PLAN.md` §4): его точная форма из твоего отчёта станет
образцом для C5, C6, C11, C13.

| файл | что |
|---|---|
| `scripts/project/tree.py` (новый) | разбор компактной YAML-нотации дерева по грамматике README экранов; проверка узлов, атрибутов, `ui:`, `text:`, `gap` |
| `scripts/project/states.py` (новый) | обязательные наборы состояний экрана и блока по правилам канона; проверка набора и ключей `states` |
| `scripts/project/screen_map.py` (новый) | генерируемые разделы свода `map.md` (`build` / `check`) и проверки карты экранов и маршрутов |
| `scripts/project/normalize.py` (новый) | приведение заполненного проекта к канону: без `--write` — дифф |
| общий модуль `scripts/project/` (имя — твоё) | формат находок, коды выхода, печать таблицей и `--json` — одна копия для всех утилит `project/` |
| `scripts/tests/fixtures/<кабинет>/` (новая) | фикстура кабинета: продукт, interface, экраны, `map.md`, `texts.md`; слои с дефектами и «вольной формой» |
| `scripts/tests/smoke/project-screens.tsv` | строки четырёх утилит (help и `--selftest`) |

## Что сделать
- **`tree.py`** (H10-screens, NU-17, ST-01 — часть). Грамматика — `_template/screens/README.md` («Нотация дерева»,
  «Узлы», «Атрибуты»; управляемая копия — `.claude/skills/screen-deep-dive/references/tree-notation.md`, при
  расхождении прав README). Узлы и головы `<префикс>:<имя>` с атрибутами `атрибут=значение`, префиксы `ui`, `layout`,
  `block`, `data`, `text`, `icon`; корни экрана, блока, каркаса; закрытый список атрибутов и значений; `ui:<Тип>` и
  `ui:<Тип>.<Часть>` — по `kb/common/components.yaml` (`types`, `parts`, `aka`) и расширениям проекта (`extensions`
  карты решений `design/system.yaml`, если файл есть); `text:<ключ>` — строка реестра `texts.md` той же поверхности;
  `gap` — имя токена группы `space` ДС (есть `design/system.tokens.json` — сверка с ним, нет — только форма имени).
  Выход: дерево в JSON для соседних утилит (Python-функция и подкоманда вывода) и находки правил `screen-audit`:
  R-STRUCT-020, R-STRUCT-021 (у имени из `aka` находка называет тип словаря), R-SEM-014, R-TX-001, R-TX-003 (и другие
  R-TX и R-STRUCT, если проверка детерминирована и её правило это описывает).
- **`states.py`** (ST-05, ST-06, ST-12, ST-01 — часть). Набор экрана — объединение условий канона
  (`_template/screens/README.md` «Состояния экрана», «Обязательный набор», «Частные правила», «Приоритет»; правило
  R-SEM-011): загрузка данных, коллекция, поиск и фильтр, строки типа экрана и «Экран или маршрут целиком» матрицы,
  строки компонентов с `screen_states`, `access: roles`, `params`, работа без сети (раздел «Решения» `map.md`), живые
  данные, отказы ситуаций экрана, `duration: background` возможности; у блока с `source: own` — свой набор. Словарь,
  приоритет и матрицу читай из YAML C2 (в код не копируй). Приоритет — правило канона, у экрана его не требуй (ST-06).
  Выход: набор с причиной каждого состояния («почему в наборе»), находки R-SEM-011 (тяжесть по статусу), R-STRUCT-022,
  механическая часть R-SEM-015, если она детерминирована.
- **`screen_map.py`** (ST-07, ST-15, ST-16, F7-Z2-1 — часть). Генерируемые разделы `map.md` по форме
  `_template/screens/_template/map.md` (какие разделы собираются из экранов, какие пишет аналитик — по форме): `build`
  пишет только генерируемые разделы, `check` сверяет без записи. Проверки карты — правила R-RT-001…R-RT-009 и R-COV-003
  `screen-audit/references/rules.md` (номера правил — по `rules.md`, а не по кандидатам журнала `RT-0N`).
- **`normalize.py`** (F7-Z7b-2, T3-scripts — часть; Р183 п. 8). Вход — вольная запись заполненного проекта, выход —
  канон: тип по `aka` словаря, ключи состояний mobile и прежние ключи экрана — по таблице соответствия README mobile и
  словарю, литерал текста → ключ реестра `texts.md` (строка реестра со статусом `assumed` и ролью по части компонента),
  атрибуты — на свои места. Соответствия — из данных канона (`aka`, таблица README mobile) и таблицы
  `phase-6/spec/T3-saas-layer.md` §4.5 — в коде как синонимы входа, без слов «прежнее / новое». Смысловые поля
  (главная задача, объект, роль, сценарий) нормализатор не заполняет — оставляет пустыми для владельца и перечисляет.
  Без `--write` — только дифф; с `--write` — правка файлов проекта по месту.
- **Контракт находок** (первый писатель, `PLAN.md` §4): строки JSON `{rule, severity, surface, kind, ref, path,
  message, fix}`, тяжесть `error | warning | hint`; код выхода 0 — ошибок нет, 1 — есть, 2 — вызов или окружение;
  вызов `<команда> <slug> [<surface>] [--repo DIR] [--out …] [--json]`, команды `build` и `check`, `--selftest` на
  встроенной фикстуре. Разбор вызова и пути — через `docpaths` (C1). Точную форму (поля, значения `kind` и `ref`,
  пример строки) запиши в отчёт §4.
- **Фикстура кабинета** (ENV-6 — часть C3). Свои файлы (примеров кабинета в базах нет), иллюстрация: `example: true` в
  машинных файлах, пометка в md. Состав: продукт (`vision.md` с `MVP` и `Devices and accessibility`, `surface.md` с
  поверхностью `web` рода `app`, `user.md` с двумя ролями, `object.md` и `action.md` — два объекта), interface
  поверхности (зоны, ситуации с `refusals`, один сценарий, блоки), экраны поверхности (основной каркас с состояниями
  приложения; экраны: список с фильтром и коллекцией, карточка объекта с `params`, форма создания, дашборд с плиткой
  показателя, служебный `not-found`), блоки, `map.md`, `texts.md`. Слои манифеста: чистый; «дефекты» (поверх чистого,
  таблица ниже); «вольная форма» (для нормализатора).
