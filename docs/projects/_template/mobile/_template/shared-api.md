# shared-api

> Контракт данных поверхности: какие ресурсы бэкенда и операции нужны приложению, кто ими
> владеет, идемпотентность и офлайн-кэш; плюс **сценарии данных** для работы без бэкенда
> (mock/demo/тесты). Клиент, генератор моделей, заголовки — платформа код-репо
> (`docs/stack/api.md`). Из записи выводятся `<Resource>Api` и фикстуры `mock/fixtures/`.

## Контракт данных

Форма каждой сущности задаётся её записью в `entities.md`; контракт покрывает **все** entities
с `source ≠ local` — сущность без ресурса здесь — blocker для stable этого файла. Операции
существуют в `api/openapi.yaml` бэкенда (advisory-проверка `/mobile-audit` через `backend-path`
код-репо); отсутствующие — BACKEND-HANDOFF, не выдумываются.

## Критерии ресурса

1. **Владелец известен** — домен/сервис бэкенда (`services/<svc>`).
2. **Операции перечислены** методом и путём как в спеке (`GET /todos`, `PATCH /todos/{id}`).
3. **Идемпотентность мутаций** осознанна (`Idempotency-Key` — дефолт код-репо).
4. **Офлайн-кэш** согласован с `entities.cache`.

## Что shared-api НЕ

- ❌ Выбор клиента, генератора, заголовки, ретраи — `docs/stack/api.md`.
- ❌ Дубль полей сущностей — форма живёт в `entities.md`.
- ❌ Тест-фикстуры конкретных тестов — исполнительная сторона; здесь — сценарии.

## Ресурсы

- `ресурс` — имя ресурса · `kebab-case` · обяз.
- `операции` — массив `<METHOD> <path>` · обяз.
- `владелец` — домен/сервис бэкенда · реф `services/<svc>` · обяз.
- `идемпотентность` — `да` \| `нет` для мутаций · обяз.
- `offline-кэш` — `да` \| `нет` (⇔ `entities.cache ≠ none`) · обяз.
- `status` — зрелость записи · `draft` \| `stable` · обяз.

| ресурс | операции | владелец | идемпотентность | offline-кэш | status |
|---|---|---|---|---|---|
| `auth` | [`POST /api/auth/login`, `POST /api/auth/refresh`, `POST /api/auth/logout`, `GET /api/auth/sessions`] | `backend/auth` | да | нет | `draft` |
| `app` | [`GET /api/app/requirements`] | `backend/app` | — | да (последний ответ) | `draft` |
| `devices` | [`PUT /api/v1/devices`, `DELETE /api/v1/devices/{id}`] | `backend/device` | да | нет | `draft` |
| `<ресурс>` | [`<METHOD> <path>`] | `<svc>/<ctx>` | `да` \| `нет` | `да` \| `нет` | `draft` \| `stable` |

## Сценарии данных

Продуктовые состояния данных поверхности для mock/demo и тестов. Набор покрывает обязательные
состояния экранов поверхности (канон слоя, раздел «Состояния экрана и словарь»): `empty` и
`populated` — всегда; `error` и `loading-initial` — у поверхности с сетью; `partial-few` — у
экранов с коллекцией; `overflow-many` — где коллекция бывает кратно больше расчётной;
`no-permission` — когда доступ к экранам ограничен ролями.

Имена `empty`, `populated`, `authenticated`, `error` — контракт с код-репо и не переименовываются;
остальные сценарии называются ключами словаря состояний экрана, как сценарии FSD-карты веба
(`error` приложения соответствует `error-load` веба).

- `slug` — идентификатор · обяз. · `name` · `description` · `состояние` — данные по сущностям · `status`.

| slug | name | description | состояние | status |
|---|---|---|---|---|
| `empty` | Пусто | <что видно без данных> | все сущности пустые; сессия есть | `draft` |
| `populated` | Наполнено | <реалистичная картина> | <какие сущности чем наполнены> | `draft` |
| `authenticated` | Авторизован | <seed-сессия без данных> | сессия есть; остальное пусто | `draft` |
| `error` | Ошибка | <все операции отвечают 500> | — | `draft` |
| `loading-initial` | Долгий ответ | <что видно, пока данные в пути> | <ответы задержаны> | `draft` |
| `partial-few` | Мало | <экраны с одной-тремя записями в коллекциях> | <в коллекциях по одной-три записи> | `draft` |
| `overflow-many` | Много | <экраны с объёмом кратно больше расчётного> | <какие коллекции и насколько велики> | `draft` |
| `no-permission` | Нет прав | <что видит роль без прав> | <сессия роли без прав на объекты> | `draft` |
