# Артефакты телеграм-бота

Слой композиции **bot-поверхности**, партиционированный по поверхности
(surface): из аналитических артефактов
`docs/projects/<project-slug>/interface/<surface>/` синтезируется карта
диалогов бота в родных понятиях Telegram — **диалог (dialog) · окно
(window) · виджет · команда (command) · уведомление (notification)**. Для
поверхности с `type: bot` из реестра `surface.md` этот слой встаёт **на
место `screens/<surface>/`**: web-поверхность получает экраны, бот —
диалоги. Этот файл — **канон слоя**; форма одной папки поверхности лежит
рядом в `_template/`. Данные каждого проекта живут в
`docs/projects/<project-slug>/telegram-bot-flow/<surface>/`.

Бот — **фронтенд в Telegram**: его окна показывают данные и принимают
действия, а вся бизнес-логика живёт в `domains/` того же проекта. Слой
фиксирует мост явно: действие кнопки и источник данных окна ссылаются на
`use-case` домена, исходящее уведомление триггерится доменным `event`.

## Воркфлоу

```
interface/<surface>/ → синтез → telegram-bot-flow/<surface>/ → код бота
 (бизнес)                        (диалоги, окна,                (<org>/<bot> —
                                  переходы, данные)              форк telegram-bot-template)
```

1. В `docs/projects/<project-slug>/interface/<surface>/` заведены и
   углублены сущности bot-поверхности (через `interface-deep-dive`;
   канон interface един для всех типов поверхностей).
2. На их базе через скилл `telegram-bot-flow-deep-dive <slug> [<surface>]`
   создаются артефакты в
   `docs/projects/<project-slug>/telegram-bot-flow/<surface>/` — каждый
   ссылается на свой источник в interface той же поверхности через `slug`.
   Консистентность слоя (зеркала, граф, контракты данных) сверяет
   `telegram-bot-flow-audit <slug>`; сквозные рёбра с interface и domains —
   `/cross-audit` (углы `surface-botflow` · `botflow-domain`).
3. Stable-артефакты слоя читает код-репо бота (форк
   `telegram-bot-template`): по диалогам и окнам он разворачивает
   `StatesGroup`, окна, виджеты, getter'ы и обработчики. Имена файлов,
   `.ftl`-ключи i18n и конкретные виджет-классы `aiogram_dialog` — забота
   код-репо, не этого слоя.

## 4 kind

| kind | сущность | один-в-одно про |
|---|---|---|
| [`dialog`](_template/dialogs/README.md) | сценарий из окон поверх одной группы состояний | состав окон + входы + накопление данных |
| [`window`](_template/windows/README.md) | один шаг диалога: сообщение + виджеты + данные | что показано, что нажимается, куда ведёт |
| [`command`](_template/command.md) | точка входа: команда или deep-link | что запускает какой диалог |
| [`notification`](_template/notification.md) | исходящее сообщение от бота | бот пишет первым по событию домена |

Понятия зеркалят модель `aiogram_dialog`: диалог (dialog) — контейнер окон
с собственным стеком, окно (window) — одно состояние FSM с одним
сообщением, виджеты — кнопки/выбор/ввод внутри окна. Слой при этом —
**аналитика композиции**, не код: он описывает «что и куда», а не «каким
классом».

## Структура папок

Канон формы (этот README + 2 kind-README + 2 табличных канона) живёт один
раз в `docs/projects/_template/telegram-bot-flow/`; подпапка `_template/`
описывает **одну папку поверхности**:

```
docs/projects/_template/telegram-bot-flow/
├── README.md                       (этот файл — канон слоя)
└── _template/                      (форма одной папки поверхности)
    ├── dialogs/README.md           (канон dialog)
    ├── windows/README.md           (канон window)
    ├── command.md                  (канон-таблица command)
    └── notification.md             (канон-таблица notification)
```

Данные живут в папке поверхности проекта
`docs/projects/<project-slug>/telegram-bot-flow/<surface>/` (одна папка на
каждую bot-поверхность из реестра `surface.md`):

```
docs/projects/<project-slug>/telegram-bot-flow/
└── <surface>/
    ├── command.md                  (реестр точек входа)
    ├── notification.md             (реестр исходящих)
    ├── dialogs/
    │   └── <slug>/index.md
    ├── windows/
    │   └── <slug>/index.md
    └── assets/
        └── <kind>/<slug>/          (референсы: скриншоты ботов-аналогов, мокапы сообщений)
```

Диалог (dialog) и окно (window) — папки с `index.md` (место для add-on, как
в screens); команда (command) и уведомление (notification) — плоские
таблицы (один файл = один kind, как в interface). Поверхности изолированы:
ссылки внутри `telegram-bot-flow/<surface>/` и зеркала с
`interface/<surface>/` — в пределах одной поверхности.

## Форма артефакта (dialog, window)

```markdown
---
slug: <kebab-case>
name: <человекочитаемое имя>
description: <одна фраза о сущности>
status: draft | stable
<доменные поля по kind>
---

# <slug>

<одна-две поясняющие фразы>

​```yaml
<message | widgets | getter | dialog-data | transitions>
​```
```

Маркеры `<>` — заполняемые места. `status` — зрелость записи относительно
критериев своего kind (как в каноне `docs/projects/_template/interface/`).
Связи — слаг-рефами в бэктиках (форма ячеек — как в interface).
Frontmatter — YAML, структура — fenced ```yaml```-блок в теле.

## Язык контракта

Структурные идентификаторы, которые читает код-репо бота, — **английские**
и не переименовываются:

- `states-group` диалога — PascalCase (`Booking`);
- `state` окна — UPPER_SNAKE (`SERVICES`); полный адрес окна в коде —
  `<states-group>.<state>`;
- `id` виджета — snake_case, уникален в пределах окна (из него код строит
  callback-данные);
- ключи getter'а — snake_case (`services`, `selected_summary`) — они же
  плейсхолдеры `{…}` в тексте сообщения.

Всё остальное — **русский контент**: тексты сообщений, подписи кнопок,
описания, условия переходов. Превращение текстов в `.ftl`-ключи Fluent —
работа код-репо.

## Виджет-язык (для тела window)

| `widget` | роль | ключевые поля |
|---|---|---|
| `button` | команда участника (нажал — действие и/или переход) | `id`, `label`, `action`, `transition` |
| `url` | кнопка-ссылка наружу (без обработчика) | `id`, `label`, `url` |
| `select` | одиночный выбор из вариантов | `id`, `items`, `label`, `action`, `transition` |
| `multiselect` | множественный выбор (копится в окне) | `id`, `items`, `label`, `selected-label` |
| `text-input` | свободный ввод сообщением | `id`, `value-type`, `validation`, `action`, `transition` |
| `calendar` | выбор даты | `id`, `action`, `transition` |

Соответствие атомам interface очевидно и проверяется аудитом: `команда` →
`button`, `ввод` → `text-input`, `выбор` → `select`/`multiselect`/
`calendar`, `инфо`/`список` — текст сообщения и `items`. Группировка
кнопок в ряд — узлом `row:`. Облик (эмодзи-стиль, форматирование Markdown/
HTML) — забота кода, не артефакта.

`action` — слаг-реф `use-case:<ctx>.<Operation>` на use-case домена
(`domains/<ctx>/use-cases/`) либо `—` (чистая навигация). `transition` —
`<window-slug>` того же диалога, `back`, `done` (закрыть диалог) или
`start:<dialog-slug>` (вложенный диалог); условные переходы — списком
`{ to, when }`, где `when` — **исход use-case**, не правило, придуманное
окном.

## Данные окна (getter)

Каждый плейсхолдер `{…}` сообщения и каждый `items` виджета обеспечен
ключом в секции `getter` тела окна:

```yaml
getter:
  services:
    source: use-case:catalog.ListServices
    data: data:service
    fallback: пустой список — окно живо, «Далее» доступна
```

- `source` — откуда значение: `use-case:<ctx>.<Operation>` (чтение из
  домена), `dialog-data` (накоплено диалогом), `start-data` (передано при
  старте), `const` (статика).
- `data` — опц. реф `data:<slug>` на словарь данных interface
  (`data-items.md` той же поверхности); доступ к полю — `data:<slug>.<поле>`.
- `fallback` — обязателен: что показывает окно, когда источник недоступен.
  Окно не падает никогда.

## Модель Telegram (инварианты слоя)

- **Одно окно = одно сообщение.** Бот редактирует одно сообщение стека, а
  не шлёт ленту: большие коллекции — пагинация внутри окна, не серия
  сообщений.
- **Стек диалогов.** `start:` растит стек (вложенный диалог), `done`
  сворачивает к родителю. Команда со `stack: reset` (обязательна для
  `/start`) очищает стек целиком.
- **Накопление — JSON.** Контракт `dialog-data` диалога — только
  JSON-примитивы (строки, числа, списки, словари): хранилище состояний
  сериализует контекст.
- **Протухшие кнопки.** Сообщение живёт в чате вечно, диалог — нет; нажатие
  на старую кнопку обрабатывает общий recovery код-репо. Окно описывает
  только свои содержательные ошибки (`errors`).
- **Бот пишет первым.** Исходящее сообщение — всегда запись реестра
  `notification.md` с доменным триггером и идемпотентностью, не «сообщение
  из обработчика».

## Связь с `interface/<surface>/` проекта

Источник синтеза — UX-слой **той же поверхности** того же проекта (канон
interface для bot-поверхности не меняется):

| telegram-bot-flow | → ссылается на → | interface |
|---|---|---|
| `dialog.who` / `window.who` | M:N | `who.md` |
| `window.interface-block` | M:1 | `block.md` |
| `window.ux-substrates` | M:N | `ux-substrate.md` (зеркало interface) |
| `window.situations` | M:N | `situation.md` |
| `getter.*.data` (`data:<slug>`) | M:1 | `data-items.md` |

Смысловая рифма (семантическая, сверяет `/cross-audit`): зона (zone)
interface обычно проявляется как диалог (dialog), блок (block) — как окно
(window). Когда сущность interface удаляется — каскадно удаляются ссылки
здесь (правило forward-only).

## Связь с `domains/` проекта

Бот — фронтенд: доменных решений в слое нет, есть рёбра к ним
(семантические, сверяет `/cross-audit`):

| telegram-bot-flow | → ссылается на → | domains |
|---|---|---|
| `widget.action` (`use-case:<ctx>.<Operation>`) | M:1 | `domains/<ctx>/use-cases/` |
| `getter.*.source` (`use-case:…`) | M:1 | `domains/<ctx>/use-cases/` |
| `notification.trigger` (`event:<ctx>.<Event>`) | M:1 | `domains/<ctx>/events/` |
| условие перехода `when` | — | исход use-case (его `Outputs`/`Errors`) |

Ветвление сценария — следствие исхода use-case («адрес нужен, если
выбрана доставка» — решает домен), окно лишь маршрутизирует исходы.

## Связь с кодом

Stable-артефакты слоя — **вход** для форка `telegram-bot-template`
(`<org>/<bot>`): его скиллы проектирования и генерации читают диалоги,
окна, команды и уведомления и разворачивают их в код (группы состояний,
окна, виджеты, getter'ы, обработчики, точки регистрации). Контракт
read-only и односторонний, как у остальных соседей (`docs/README.md § Что
docs отдаёт соседям`). Mini-app Telegram (WebApp) — **отдельная
поверхность** реестра (`type: web` или `embed`) со своим
`screens/<surface>/`; этот слой её не описывает.

## Anti-patterns

- ❌ Код в артефактах: имена python-файлов, классов виджетов, `.ftl`-ключи,
  callback-строки. Слой — аналитика, маппинг на код делает код-репо.
- ❌ Несериализуемое в `dialog-data` (даты-объекты, сущности домена) —
  только JSON-примитивы.
- ❌ Команда `/start` без `stack: reset`.
- ❌ Доменное решение в окне: ветвление по бизнес-правилу описывается как
  исход use-case (`when`), а не как логика виджета.
- ❌ Окно-сирота (нет входящих переходов и не первое в диалоге), диалог без
  `started-by`, тупиковое окно (нет ни перехода, ни `done`).
- ❌ Исходящее сообщение вне реестра `notification.md` или уведомление без
  идемпотентности.
- ❌ Серия сообщений как «экран» (одно окно = одно сообщение).
- ❌ Битый slug-реф (на несуществующее окно/диалог/команду/data-item).
- ❌ Ссылка из папки одной поверхности в сущность другой поверхности —
  поверхности изолированы.
- ❌ Расхождение зеркал interface ↔ telegram-bot-flow: если у
  `interface-block` объявлены `ux-substrates`, тот же набор — в frontmatter
  соответствующего окна (window).
- ❌ `telegram-bot-flow/<surface>/` для поверхности, которой нет в реестре
  `surface.md` или у которой `type` не `bot`.
