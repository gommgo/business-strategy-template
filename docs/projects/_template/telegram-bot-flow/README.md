# Артефакты телеграм-бота

Слой композиции **bot-поверхности**, партиционированный по поверхности
(surface): из аналитических артефактов
`docs/projects/<project-slug>/interface/<surface>/` синтезируется карта
диалогов бота в родных понятиях Telegram — **диалог (dialog) · окно
(window) · виджет · команда (command) · уведомление (notification)** — плюс
**use-case бота**, оркестрирующий действия окон. Для поверхности с
`type: bot` из реестра `surface.md` этот слой встаёт **на место
`screens/<surface>/`**: web-поверхность получает экраны, бот — диалоги.
Внутри поверхности диалог, его окна и его use-case'ы собраны в **фичу
(feature)** — `features/<feature>/{dialog.md, window.md, use-case.md}`;
команды и уведомления лежат сквозными реестрами на корне поверхности. Этот
файл — **канон слоя**; форма одной папки поверхности лежит рядом в
`_template/`. Данные каждого проекта живут в
`docs/projects/<project-slug>/telegram-bot-flow/<surface>/`.

Бот — **фронтенд в Telegram**: его окна показывают данные и принимают
действия, а вся бизнес-логика живёт в доменах сервисов того же проекта
(`services/*/domains/`). Между
окнами и доменом стоит **оркестратор бота** — `use-case` слоя: он собирает
ввод, дёргает доменные `use-case` через backend и работает со стейтом
диалога, **не держа бизнес-правил**. Слой фиксирует мост явно: действие
кнопки и источник данных окна ссылаются на `use-case` бота, а тот в своих
зависимостях — на `use-case` домена; исходящее уведомление триггерится
доменным `event`.

## Воркфлоу

```
interface/<surface>/ → синтез → telegram-bot-flow/<surface>/ → код бота
 (бизнес)                        (диалоги, окна,                (<org>/<bot> —
                                  переходы, данные)              форк telegram-bot-template)
```

1. В `docs/projects/<project-slug>/interface/<surface>/` заведены и
   углублены сущности bot-поверхности (через `interface-deep-dive`;
   канон interface един для всех типов поверхностей).
2. На их базе через скилл `telegram-bot-flow-deep-dive <slug> [<surface>]`
   создаются артефакты в
   `docs/projects/<project-slug>/telegram-bot-flow/<surface>/` — каждый
   ссылается на свой источник в interface той же поверхности через `slug`.
   Консистентность слоя (зеркала, граф, контракты данных) сверяет
   `telegram-bot-flow-audit <slug>`; сквозные рёбра с interface и services —
   `/cross-audit` (углы `surface-botflow` · `botflow-domain` ·
   `botflow-service`).
3. Stable-артефакты слоя читает код-репо бота (форк
   `telegram-bot-template`): по диалогам и окнам он разворачивает
   `StatesGroup`, окна, виджеты, getter'ы и обработчики. Имена файлов,
   `.ftl`-ключи i18n и конкретные виджет-классы `aiogram_dialog` — забота
   код-репо, не этого слоя.

## Фича + 5 kind

Организующая ось внутри поверхности — **фича (feature)**: один диалог + его
окна + его use-case'ы в папке `features/<feature>/`. 5 kind:

| kind | где живёт | один-в-одно про |
|---|---|---|
| [`dialog`](_template/features/dialog.md) | `features/<feature>/dialog.md` (один на фичу) | состав окон + входы + накопление данных |
| [`window`](_template/features/window.md) | `features/<feature>/window.md` (секция на окно) | что показано, что нажимается, куда ведёт |
| [`use-case`](_template/features/use-case.md) | `features/<feature>/use-case.md` (секция на UC) | что делает кнопка/getter, чем оркеструет, какие исходы |
| [`command`](_template/command.md) | `command.md` (корень поверхности) | что запускает какую фичу |
| [`notification`](_template/notification.md) | `notification.md` (корень поверхности) | бот пишет первым по событию домена |

Диалог · окно · виджет зеркалят модель `aiogram_dialog`: диалог (dialog) —
контейнер окон с собственным стеком, окно (window) — одно состояние FSM с
одним сообщением, виджеты — кнопки/выбор/ввод внутри окна. Use-case бота —
**application-слой** поверх них: то, что вызывают виджеты и getter'ы, чтобы
сходить в домен и поработать со стейтом. Фича собирает эту тройку в связную
единицу; команды и уведомления — сквозные точки входа и исходящие. Слой при
этом — **аналитика композиции**, не код: он описывает «что и куда», а не
«каким классом».

## Структура папок

Канон формы (этот README + канон фичи + 2 табличных канона) живёт один раз
в `docs/projects/_template/telegram-bot-flow/`; подпапка `_template/`
описывает **одну папку поверхности**:

```
docs/projects/_template/telegram-bot-flow/
├── README.md                       (этот файл — канон слоя)
└── _template/                      (форма одной папки поверхности)
    ├── features/                    (канон фичи)
    │   ├── README.md                (общая часть: изоляция · мост к домену · виджет-язык · инварианты)
    │   ├── dialog.md                (форма диалога)
    │   ├── window.md                (форма окна)
    │   └── use-case.md              (форма use-case бота)
    ├── command.md                  (канон-таблица command, корень)
    └── notification.md             (канон-таблица notification, корень)
```

Данные живут в папке поверхности проекта
`docs/projects/<project-slug>/telegram-bot-flow/<surface>/` (одна папка на
каждую bot-поверхность из реестра `surface.md`):

```
docs/projects/<project-slug>/telegram-bot-flow/
└── <surface>/
    ├── command.md                  (реестр точек входа — сквозной, корень)
    ├── notification.md             (реестр исходящих — сквозной, корень)
    └── features/
        └── <feature>/              (= один диалог + его окна + его use-case'ы)
            ├── dialog.md           (один диалог фичи)
            ├── window.md           (все окна — H2-секция на окно)
            ├── use-case.md         (все use-case'ы бота — H2-секция на UC)
            └── assets/<slug>/      (референсы: мокапы сообщений, скриншоты ботов-аналогов)
```

Фича — папка из трёх файлов; команда (command) и уведомление (notification)
— плоские таблицы корня (один файл = один kind, как в interface).
**Изоляция двухуровневая**: поверхности изолированы между собой, а внутри
поверхности изолированы и **фичи** — ссылки внутри `features/<feature>/`
(окно ↔ диалог ↔ use-case) резолвятся в пределах своей фичи; между фичами —
только `start:<feature>` и сквозные реестры корня (`feature:<slug>`).
Зеркала с `interface/<surface>/` — в пределах одной поверхности.

## Форма трёх файлов фичи

Полные формы — в файлах-формах канона фичи (`_template/features/{dialog,window,use-case}.md`). Кратко:

- **`dialog.md`** — один диалог: frontmatter YAML (`slug` · `name` ·
  `description` · `states-group` · `windows` · `started-by` · `launch-mode`
  · `start-data` · `who` · `status`) + тело fenced ```yaml``` (`dialog-data`
  · `transitions`).
- **`window.md`** — все окна фичи **секциями** `## <window-slug>`: каждая —
  мета-блок ```yaml``` (`name` · `state` · `interface-block` ·
  `ux-substrates` · `situations` · `who` · `status`) + тело (`message` ·
  `widgets` · `getter` · `errors`).
- **`use-case.md`** — все use-case'ы бота **секциями** `## <uc-slug>`:
  каждая — мета-блок ```yaml``` (`name` · `operation` · `who` · `status`) +
  **H3-секции** `### Actor` · `### Inputs` · `### Outputs` ·
  `### Dependencies` · `### Steps` · `### Errors`, зеркалящие доменный
  use-case (`services/_templates/use-case.md`) без доменных-only секций.

`status` — зрелость **каждой** секции/файла относительно критериев своего
kind. Связи — слаг-рефами в бэктиках (форма ячеек — как в interface).

## Язык контракта

Структурные идентификаторы, которые читает код-репо бота, — **английские**
и не переименовываются:

- `states-group` диалога — PascalCase (`Booking`);
- `state` окна — UPPER_SNAKE (`SERVICES`); полный адрес окна в коде —
  `<states-group>.<state>`;
- `operation` use-case бота — PascalCase (`SubmitBooking`); из него код
  строит имя сервиса/handler'а оркестрации;
- `id` виджета — snake_case, уникален в пределах окна (из него код строит
  callback-данные);
- ключи getter'а — snake_case (`services`, `selected_summary`) — они же
  плейсхолдеры `{…}` в тексте сообщения;
- поля формы окна — как в форме `_template/features/window.md`: у ключа
  getter'а `source`, `data`, `empty`, `fallback`; `errors` с
  `backend-unavailable`, `invalid-input`; `escalate` у виджета `text-input`.

Всё остальное — **русский контент**: тексты сообщений, подписи кнопок,
описания, условия переходов. Превращение текстов в `.ftl`-ключи Fluent —
работа код-репо.

## Виджет-язык (для тела window)

| `widget` | роль | ключевые поля |
|---|---|---|
| `button` | команда участника (нажал — действие и/или переход) | `id`, `label`, `action`, `transition` |
| `url` | кнопка-ссылка наружу (без обработчика) | `id`, `label`, `url` |
| `select` | одиночный выбор из вариантов | `id`, `items`, `label`, `action`, `transition`, опц. `paginated` |
| `multiselect` | множественный выбор (копится в окне) | `id`, `items`, `label`, `selected-label`, опц. `paginated` |
| `text-input` | свободный ввод сообщением | `id`, `value-type`, `validation`, `action`, `transition`, опц. `escalate` |
| `calendar` | выбор даты | `id`, `action`, `transition` |

Соответствие атомам interface очевидно и проверяется аудитом: `команда` →
`button`, `ввод` → `text-input`, `выбор` → `select`/`multiselect`/
`calendar`, `инфо`/`список` — текст сообщения и `items`. Группировка
кнопок в ряд — узлом `row:`. Облик (эмодзи-стиль, форматирование Markdown/
HTML) — забота кода, не артефакта.

`value-type` у `text-input` — `str | int | float | date | phone | email`
(`str` — по умолчанию, поле можно опустить). `escalate` (опц.) у
`text-input` — `start:<feature>` фичи передачи человеку: куда ведёт
предложение человека, когда ввод не удался подряд (раздел «Путь к
человеку»). `paginated: true` (опц.) у
виджета с `items` — большая коллекция листается внутри окна, носитель
инварианта «одно окно = одно сообщение». Медиа сообщения
(`message.media`) — типизировано: `type` ∈ `photo | video | document |
animation` + `source` (путь ассета `assets/<window-slug>/…` или реф
`data:<slug>.<поле>`), либо `—`.

`action` — слаг-реф `use-case:<slug>` на **use-case бота** той же фичи
(секция `## <slug>` в `use-case.md`) либо `—` (чистая навигация). Bot UC
оркеструет вызов домена; реф **без точки** — bot UC, **с точкой**
(`use-case:<ctx>.<Operation>`) — доменный (он живёт в `Dependencies` bot
UC, не на виджете). `transition` — `<window-slug>` **той же фичи**, `back`,
`done` (закрыть диалог) или `start:<feature>` (войти в диалог другой фичи —
вложенный диалог); условные переходы — списком `{ to, when }`, где `when` —
**исход use-case бота**, не правило, придуманное окном.

## Данные окна (getter)

Каждый плейсхолдер `{…}` сообщения и каждый `items` виджета обеспечен
ключом в секции `getter` тела окна:

```yaml
getter:
  services:
    source: use-case:list-services
    data: data:service
    empty: услуг пока нет — окно живо, «Назад» доступна
    fallback: список не загрузился — причина и «Повторить»
```

- `source` — откуда значение: `use-case:<slug>` (чтение через **use-case
  бота**, тот ходит в домен), `dialog-data` (накоплено диалогом),
  `start-data` (передано при старте), `const` (статика).
- `data` — опц. реф `data:<slug>` на словарь данных interface
  (`data-items.md` той же поверхности); доступ к полю — `data:<slug>.<поле>`.
- `empty` — обязателен у ключа-коллекции: что показывает окно, когда
  источник ответил, а данных нет, — причина пустоты и следующий шаг
  (`empty-first-run`, `empty-filtered`, `empty-cleared`; ux 06/01 §4.3).
- `fallback` — обязателен у каждого ключа: что показывает окно, когда
  источник недоступен, — причина и повтор (`error-load`). Окно не падает
  никогда; пустой список вместо отказа источника — дефект.

Виджет с `items` берёт коллекцию из такого ключа (значение `items` — имя
ключа-коллекции в `getter`). Контракт элемента списка: каждый item несёт
`id` (из него строятся callback-данные выбора) и поля, которые
`label`/`selected-label` виджета подставляют через `{item.<поле>}`
(`label: '{item.name} — {item.price}'`); `empty` ключа-коллекции описывает
пустое состояние, `fallback` — отказ источника.

## Модель Telegram (инварианты слоя)

- **Одно окно = одно сообщение.** Бот редактирует одно сообщение стека, а
  не шлёт ленту: большие коллекции — пагинация внутри окна (атрибут
  `paginated` у виджета с `items`), не серия сообщений.
- **Стек диалогов.** `start:<feature>` растит стек (вложенный диалог
  другой фичи), `done` сворачивает к родителю. Команда со `stack: reset`
  (обязательна для `/start`) очищает стек целиком.
- **Накопление — JSON.** Контракт `dialog-data` диалога — только
  JSON-примитивы (строки, числа, списки, словари): хранилище состояний
  сериализует контекст.
- **Протухшие кнопки.** Сообщение живёт в чате вечно, диалог — нет; нажатие
  на старую кнопку обрабатывает общий recovery код-репо. Окно описывает
  только свои содержательные ошибки (`errors`).
- **Бот пишет первым.** Исходящее сообщение — всегда запись реестра
  `notification.md` с доменным триггером и идемпотентностью, не «сообщение
  из обработчика». Плейсхолдеры `{…}` его текста — поля `Payload`
  события-триггера: PascalCase-поле в snake_case (`OrderID` → `{order_id}`).

## Состояния окна

Словарь состояний экрана один на веб, приложение и бота — ux 06/01 §2
(S01–S24; ключи словаря — канон экранов `../screens/README.md`, раздел
«Состояния экрана»). Окно бота — одно состояние машины состояний и одно
сообщение, поэтому своих ключей состояний у слоя нет: состояние словаря
выражает поле окна, исход use-case бота или сам клиент Telegram. Приоритет
состояний окну не нужен — окно показывает одно сообщение.

| где в слое | состояния словаря |
|---|---|
| окно с данными getter'а | идеальное |
| `getter.<ключ>.empty` ключа-коллекции | S01 `empty-first-run`, S02 `empty-filtered` (окно с поиском), S03 `empty-cleared` |
| `getter.<ключ>.fallback` | S13 `error-load`; ключи окна падают порознь — S15 `partial-failure` |
| `paginated: true` у виджета с `items` | S05 `overflow-many`, S09 `loading-more` — листание внутри окна |
| `errors.backend-unavailable`, `errors.invalid-input` | S14 `error-action` |
| исход use-case бота (`### Outputs`, `### Errors`) и переход окна по `when` | S12 `success`, S15 `partial-failure`, S17 `timeout`, S19 `locked`, S20 `archived-deleted`, S21 `limit-reached`, S23 `not-found` (объекта из `start-data` нет) |
| исход «принято» и запись `notification.md` о завершении | S10 `in-progress-background` |
| `who` команды, диалога и окна | S18 `no-permission` — вход закрыт; S22 `read-only` — виджетов правки нет |
| метка свежести в тексте сообщения | S06 `stale` — у живых данных |
| не проектируется: рисует клиент Telegram | S07 `loading-initial`, S11 `saving` (индикатор кнопки), S16 `offline` (связь) |
| не применимо: одно сообщение | S04 `partial-few`, S08 `loading-refresh` |
| окно ответа ИИ | S24 `generating` |

Три состояния бот показывает текстом окна с ролями (раздел «Тексты: роли и
жанр»):

- **`no-permission` и `not-found`** — окно-исход use-case, когда домен не
  пустил или объекта нет: заголовок роли `title` (что случилось),
  пояснение роли `body` (почему и что делать) и кнопка выхода с подписью
  роли `action`; отказ не маскируется пустым списком.
- **`generating`** — окно ответа ИИ: пока ответ идёт, текст сообщения несёт
  признак незавершённости роли `status`, в окне есть кнопка остановки
  (виджет `button`, подпись роли `action`); норма потокового ответа —
  ux 13/03 §6.

Состояния приложения (плановые работы, сервис недоступен) окнами не
проектируются: ответ на них — общий обработчик код-репо.

## Тексты: роли и жанр

Тексты бота — жанр `interface` и голос продукта (профиль голоса — файл
уровня продукта, `../site/README.md`, раздел «Уровень продукта»). Реестра
текстов, как у экранов веба, у бота нет: роль строки задаёт поле, в котором
она живёт. Роль — из закрытого списка ролей текста ux 07/06 §7.2 или
`body`; по ней линтер текстов выбирает правила.

| поле | роль |
|---|---|
| `message.text` окна | `body` |
| текст окна `no-permission` и `not-found` | `title` — что случилось, `body` — почему и что делать |
| текст окна ответа ИИ, пока ответ идёт (`generating`) | `status` |
| `label` виджета `button` | `action` |
| `label` виджета `url` | `link` |
| `label` виджета `select` | `label` |
| `label` и `selected-label` виджета `multiselect` | `checkbox-label` |
| `getter.<ключ>.empty` | `empty` |
| `getter.<ключ>.fallback` | `error` |
| `errors.backend-unavailable`, `errors.invalid-input` | `error` |
| `content` уведомления (`notification.md`) | `push` |

Роль подписи виджета — роль текстовой части типа словаря компонентов,
которому виджет соответствует (`kb/common/components.yaml`, разделы
`crosswalk` и `text_roles`).

## Путь к человеку

Бот не удерживает человека, который просит живого собеседника: явная
просьба — путь к человеку сразу, неявный провал — предложение человека
после трёх неудачных попыток ввода или непонятых запросов подряд
(ux 13/03 §16.2; `kb/ux/README.md § Реестр разрешённых противоречий`,
№ 49). Путь собирается из частей слоя:

- **фича передачи** — диалог, который принимает обращение и передаёт
  разговор человеку; её use-case называет исход «передано человеку» в
  `### Outputs`, а use-case, который не довёл задачу сам и отдаёт разговор
  человеку, — строкой `### Errors`;
- **команда** — запись `command.md`, которая запускает фичу передачи в
  любой момент: явная просьба не ждёт провала;
- **кнопка** — виджет `button` с переходом `start:<feature>` фичи передачи
  в окнах, где просьба ожидаема: меню, помощь, окно отказа;
- **`escalate` у `text-input`** — `start:<feature>` фичи передачи: после
  трёх неудачных вводов подряд окно предлагает человека, а не повторяет
  вопрос;
- **оператор узнаёт о передаче** — запись `notification.md` с адресатом-ролью
  оператора и доменным событием передачи или функция интеграции, когда
  обращения принимает внешняя система поддержки (строка `integration.md`
  проекта).

Бот со свободным вводом (`text-input`) или ответами ИИ без пути к человеку —
предупреждение `/telegram-bot-flow-audit`, кнопочный бот — подсказка.

## Связь с `interface/<surface>/` проекта

Источник синтеза — UX-слой **той же поверхности** того же проекта (канон
interface для bot-поверхности не меняется):

| telegram-bot-flow | → ссылается на → | interface |
|---|---|---|
| `dialog.who` / `window.who` | M:N | `who.md` |
| `window.interface-block` | M:1 | `block.md` |
| `window.ux-substrates` | M:N | `ux-substrate.md` (зеркало interface) |
| `window.situations` | M:N | `situation.md` |
| `getter.*.data` (`data:<slug>`) | M:1 | `data-items.md` |

Смысловая рифма (семантическая, сверяет `/cross-audit`): зона (zone)
interface обычно проявляется как диалог (dialog), блок (block) — как окно
(window). Когда сущность interface удаляется — каскадно удаляются ссылки
здесь (правило forward-only).

## Связь с `use-case` бота (внутри слоя)

Действия и данные окон проходят через **оркестратор бота** — это рёбра
**внутри слоя**, slug-валидируемы в пределах поверхности:

| telegram-bot-flow | → ссылается на → | use-case бота |
|---|---|---|
| `widget.action` (`use-case:<slug>`) | M:1 | секция `## <slug>` в `use-case.md` **той же фичи** |
| `getter.*.source` (`use-case:<slug>`) | M:1 | секция `## <slug>` в `use-case.md` **той же фичи** |
| условие перехода `when` | — | исход bot UC (его `Outputs`/`Errors`) |

## Связь с доменами сервисов проекта

Бизнес-логики в слое нет; домена касается только **use-case бота** (через
свои `Dependencies`) и реестр уведомлений. Рёбра семантические (домен
опционален), сверяет `/cross-audit`:

| telegram-bot-flow | → ссылается на → | services (домены) |
|---|---|---|
| `use-case.Dependencies` (`use-case:<ctx>.<Operation>`) | M:N | `services/*/domains/<ctx>/use-cases/` |
| `notification.trigger` (`event:<ctx>.<Event>`) | M:1 | `services/*/domains/<ctx>/events/` |

Ветвление сценария — следствие исхода доменного use-case, который bot UC
возвращает окну («адрес нужен, если выбрана доставка» — решает домен);
окно лишь маршрутизирует исход bot UC.

В сервисной топологии бот — сервис `type: bot` реестра `service.md`
(оркестратор без бизнес-правил). Сервис-владелец контекста выводится из
пути `services/*/domains/<ctx>/`; чтобы уведомление дошло, его
событие-триггер должно публиковаться в брокер — строка `produces` в
`## Messaging` паспорта сервиса-владельца (сверяет `/cross-audit`, угол
`botflow-service`).

## Связь с кодом

Stable-артефакты слоя — **вход** для форка `telegram-bot-template`
(`<org>/<bot>`): его скиллы проектирования и генерации читают фичи (диалоги,
окна, use-case'ы бота), команды и уведомления и разворачивают их в код
(группы состояний, окна, виджеты, getter'ы, сервисы-оркестраторы,
обработчики, точки регистрации). Контракт
read-only и односторонний, как у остальных соседей (`docs/README.md § Что
docs отдаёт соседям`). Mini-app Telegram (WebApp) — **отдельная
поверхность** реестра (`type: web` или `embed`) со своим
`screens/<surface>/`; этот слой её не описывает.

## Anti-patterns

- ❌ Код в артефактах: имена python-файлов, классов виджетов, `.ftl`-ключи,
  callback-строки. Слой — аналитика, маппинг на код делает код-репо.
- ❌ Несериализуемое в `dialog-data` (даты-объекты, сущности домена) —
  только JSON-примитивы.
- ❌ Команда `/start` без `stack: reset`.
- ❌ Доменное решение в окне или в `Steps` use-case бота: ветвление по
  бизнес-правилу описывается как исход use-case (`when`), а не как логика
  виджета или шаг оркестрации.
- ❌ `action` мимо use-case бота («кнопка сама сохраняет в базу») — действие
  ссылается на use-case или отсутствует.
- ❌ Несколько диалогов в одной фиче — вложенный сценарий выносится в
  отдельную фичу, вход через `start:<feature>`.
- ❌ Окно-сирота (нет входящих переходов и не первое в диалоге), диалог без
  `started-by`, тупиковое окно (нет ни перехода, ни `done`).
- ❌ Исходящее сообщение вне реестра `notification.md` или уведомление без
  идемпотентности.
- ❌ Серия сообщений как «экран» (одно окно = одно сообщение).
- ❌ Пусто и отказ одним текстом: ключ-коллекция без `empty` или `fallback`,
  который прячет отказ источника за пустым списком.
- ❌ Бот удерживает человека: при свободном вводе или ответах ИИ пути к
  человеку нет, просьбу соединить с человеком бот откладывает.
- ❌ Битый slug-реф (на несуществующее окно/use-case/фичу/команду/data-item).
- ❌ Ссылка из одной фичи в окно/use-case другой минуя `start:`/`command`,
  или из папки одной поверхности в сущность другой — изоляция двухуровневая
  (поверхности и фичи).
- ❌ Расхождение зеркал interface ↔ telegram-bot-flow: если у
  `interface-block` объявлены `ux-substrates`, тот же набор — в мета-блоке
  соответствующего окна (window).
- ❌ `telegram-bot-flow/<surface>/` для поверхности, которой нет в реестре
  `surface.md` или у которой `type` не `bot`.
