# feature

> Feature (фича) — связная единица бота: **один диалог** (dialog) + его
> **окна** (window) + его **use-case'ы** (use-case бота), собранные в одну
> папку. Это композиционный аналог зоны (zone) interface и flow слоя
> экранов. Феатура живёт в `features/<feature>/` и держит три файла:
> `dialog.md` (один диалог), `window.md` (все окна — секцией на окно),
> `use-case.md` (все оркестраторы — секцией на use-case). Точки входа
> (command) и исходящие (notification) лежат **выше**, на корне поверхности
> — они сквозные.

```
features/<feature>/
├── dialog.md       (один диалог фичи)
├── window.md       (все окна — H2-секция на окно)
├── use-case.md     (все use-case'ы бота — H2-секция на use-case)
└── assets/<slug>/  (референсы: мокапы сообщений, скриншоты ботов-аналогов)
```

## Feature = один диалог

Феатура несёт **ровно один** диалог. Поэтому slug фичи (имя папки) — это и
есть slug её диалога: `features/booking/` ⇒ диалог `booking`. Окна и
use-case'ы фичи — те, что нужны именно этому диалогу. Вложенный сценарий
(стек растёт через `start:`) — это **другая фича**, в которую входят
кросс-фичевым переходом, а не второй диалог внутри той же папки.

## Жёсткая изоляция (как поверхности)

Феатуры изолированы так же, как поверхности. Внутри-фичевые рёбра
(`window` ↔ `dialog` ↔ `use-case`) резолвятся **только внутри своей фичи**;
slug окна/use-case уникален **в пределах фичи** (одинаковый slug в разных
фичах — не дубль). Между фичами — только два моста:

- `start:<feature>` на виджете окна — войти в диалог другой фичи (стек
  растёт, вложенный диалог);
- сквозные реестры корня — `command` (вход извне) и `notification`
  (исходящее), которые ссылаются на фичу через `feature:<feature>`.

| ребро | форма | где резолвится |
|---|---|---|
| `dialog.windows` | `[<window-slug>]` | окна **этой** фичи (`window.md`) |
| `widget.transition` | `<window-slug>` \| `back` \| `done` \| `start:<feature>` | окно этой фичи; `start:` — диалог другой фичи |
| `widget.action` | `use-case:<uc-slug>` \| `—` | use-case **этой** фичи (`use-case.md`) |
| `getter.*.source` | `use-case:<uc-slug>` \| `dialog-data` \| `start-data` \| `const` | use-case этой фичи |
| `dialog.started-by` | `[command:<slug> \| notification:<slug> \| feature:<feature>]` | команда/уведомление корня; `feature:` — другая фича, входящая через `start:` |
| `command.starts` (корень) | `feature:<feature>` \| `—` | диалог фичи |
| `notification.action` (корень) | `command:<slug>` \| `feature:<feature>` \| `—` | команда корня / диалог фичи |

Ссылка из одной фичи в окно/use-case другой (минуя `start:`/`command`) —
нарушение изоляции, ловит аудит. Общее между фичами (как и между
поверхностями) сводит `/cross-audit`.

## Мост к домену (через use-case бота)

Бизнес-логики в фиче нет. Действие виджета и источник данных getter'а
ссылаются на **use-case бота** (`use-case:<uc-slug>`, внутри фичи); сам
use-case бота в секции `Dependencies` ссылается на **доменный** use-case
(`use-case:<ctx>.<Operation>`, `services/*/domains/<ctx>/use-cases/`). Точка различает
уровни: реф **без точки** — use-case бота, **с точкой** — доменный.
Доменные рёбра семантические (домен опционален), их сверяет `/cross-audit`
(угол `botflow-domain`). Уведомления (`notification.trigger`) триггерятся
доменными `event` — это тоже семантическое ребро корневого реестра.

## Язык контракта (структурные идентификаторы)

Идентификаторы, которые читает код-репо бота (форк `telegram-bot-template`),
— **английские** и не переименовываются:

- `states-group` диалога — PascalCase (`Booking`);
- `state` окна — UPPER_SNAKE (`SERVICES`); полный адрес окна в коде —
  `<states-group>.<state>`;
- `operation` use-case бота — PascalCase (`SubmitBooking`); из него код
  строит сервис/handler оркестрации;
- `id` виджета — snake_case, уникален в пределах окна (callback-данные);
- ключи getter'а — snake_case (`services`, `selected_summary`) — они же
  плейсхолдеры `{…}` в тексте сообщения.

Всё остальное — **русский контент**: тексты сообщений, подписи кнопок,
описания, условия переходов. Превращение текстов в `.ftl`-ключи Fluent,
имена python-файлов и классы `aiogram_dialog` — работа код-репо.

## Виджет-язык (для секции `widgets` окна)

| `widget` | роль | ключевые поля |
|---|---|---|
| `button` | команда участника (нажал — действие и/или переход) | `id`, `label`, `action`, `transition` |
| `url` | кнопка-ссылка наружу (без обработчика) | `id`, `label`, `url` |
| `select` | одиночный выбор из вариантов | `id`, `items`, `label`, `action`, `transition` |
| `multiselect` | множественный выбор (копится в окне) | `id`, `items`, `label`, `selected-label` |
| `text-input` | свободный ввод сообщением | `id`, `value-type`, `validation`, `action`, `transition` |
| `calendar` | выбор даты | `id`, `action`, `transition` |

Соответствие атомам interface (проверяет аудит): `команда` → `button`,
`ввод` → `text-input`, `выбор` → `select`/`multiselect`/`calendar`, `инфо`/
`список` — текст сообщения и `items`. Группировка кнопок в ряд — узлом
`row:`. Облик (эмодзи-стиль, форматирование) — забота кода, не артефакта.

## Инварианты модели Telegram

- **Одно окно = одно сообщение.** Бот редактирует одно сообщение стека:
  большие коллекции — пагинация внутри окна, не серия сообщений.
- **Стек диалогов.** `start:<feature>` растит стек (вложенный диалог),
  `done` сворачивает к родителю. Команда со `stack: reset` (обязательна для
  `/start`) очищает стек целиком.
- **Накопление — JSON.** `dialog-data` — только JSON-примитивы (строки,
  числа, списки, словари).
- **Протухшие кнопки.** Сообщение живёт вечно, диалог — нет; нажатие на
  старую кнопку обрабатывает общий recovery код-репо. Окно описывает только
  свои содержательные ошибки (`errors`).
- **Бот пишет первым.** Исходящее — всегда запись реестра `notification.md`
  корня с доменным триггером и идемпотентностью.

# Форма `dialog.md`

> Диалог (dialog) — единственный сценарий фичи из её окон поверх одной
> группы состояний: завершённая задача участника (who) от входа до
> результата. Frontmatter — YAML, тело — fenced ```yaml```-блок.

## Критерии dialog

1. **Одна задача участника.** Завершённый сценарий («оформить заказ»), не
   произвольная пачка окон и не весь бот.
2. **Состав окон упорядочен.** `windows` перечисляет окна `window.md` в
   порядке шагов (= порядок состояний группы, по нему автопереход).
3. **Входы объявлены.** `started-by` — откуда стартует: команда корня
   (`command:<slug>`), уведомление корня (`notification:<slug>`) или другая
   фича (`feature:<slug>`, входящая через `start:<эта-фича>`). Диалог без
   входа недостижим.
4. **Накопление — контракт.** `dialog-data` тела: ключ → что лежит
   (JSON-примитивы).
5. **Граф без тупиков.** Из каждого окна есть путь к `done` или явному
   переходу; сводный `transitions` — зеркало переходов виджетов окон.

### Frontmatter

| поле | тип | обяз | смысл |
|---|---|---|---|
| `slug` | string | yes | kebab-case = имя папки фичи |
| `name` | string | yes | человекочитаемое имя |
| `description` | string | yes | одна фраза о сценарии |
| `states-group` | string (PascalCase, англ.) | yes | имя группы состояний — структурный идентификатор для кода |
| `windows` | `[window-slug]` | yes | окна по порядку шагов (= порядок состояний) |
| `started-by` | `[command:<slug> \| notification:<slug> \| feature:<slug>]` | yes | точки входа |
| `launch-mode` | `standard \| root \| single-top \| exclusive` | yes | режим запуска (root — главное меню) |
| `start-data` | string | optional | что передаётся при старте (JSON-примитивы), `—` если ничего |
| `who` | `[who-slug]` | yes | роли interface, для которых сценарий существует |
| `status` | `draft \| stable` | yes | зрелость записи |

### Тело — `dialog-data` и `transitions`

```yaml
dialog-data:
  draft: черновик заказа — services (список), guests (число), address (строка)
  draft_id: идемпотентный ключ отправки, выдаётся на старте

transitions:   # сводное зеркало; источник правды — transition на виджетах окон
  - { from: services, to: guests,  when: 'кнопка «Далее»' }
  - { from: guests,   to: address, when: 'use-case бота вернул «нужен адрес»' }
  - { from: guests,   to: confirm, when: 'адрес не нужен' }
  - { from: confirm,  to: done,    when: 'заказ отправлен' }
```

### Что dialog НЕ

- ❌ Не окно (window): один шаг — секция в `window.md`.
- ❌ Не команда: `/start` и deep-link — реестр `command.md` корня.
- ❌ Не зона interface: зона — UX-анализ; диалог — её воплощение (связь
  семантическая).
- ❌ Не «несколько диалогов в фиче»: вложенный сценарий — отдельная фича,
  вход через `start:<feature>`.

### Тест-критерий

«Завершённая задача участника из последовательности окон с явными входами
и контрактом накопления?» — «Оформление заказа: услуги → гости → адрес →
подтверждение» ✅; «Окно выбора услуг» — window ❌; «/start» — command ❌.

# Форма `window.md`

> Окно (window) — один шаг диалога: **одно сообщение** бота (текст + медиа)
> с виджетами, контрактом данных (`getter`) и переходами. Одно окно = одно
> состояние (`state`) группы. Реализует блок (block) interface той же
> поверхности. Все окна фичи лежат в `window.md` — **по H2-секции на
> окно**: `## <window-slug>` + мета-блок + тело.

## Критерии window

1. **Одно сообщение.** Всё, что участник видит на шаге, — один текст (с
   плейсхолдерами `{…}`) + опц. медиа + клавиатура из виджетов.
2. **Принадлежит диалогу фичи.** `state` уникален в группе диалога фичи.
3. **Каждый плейсхолдер обеспечен.** Любой `{ключ}` и каждый `items` имеет
   запись в `getter` с источником и `fallback`.
4. **Действия — к use-case бота, переходы — к окнам.** `action` виджета
   ссылается на use-case бота фичи (`use-case:<uc-slug>`); `transition` —
   окно этой фичи, `back`, `done` или `start:<feature>`. Условные переходы
   (`when`) маршрутизируют **исходы use-case бота**, не правила окна.
5. **Зеркалит interface.** `interface-block` указывает блок-источник;
   `ux-substrates` повторяет его набор атомов.

### Форма секции окна

```markdown
## <window-slug>

> <одна фраза об окне>

​```yaml
name: <человекочитаемое имя>
state: <UPPER_SNAKE>
interface-block: <block-slug>
ux-substrates: [<ux-substrate-slug>]
situations: [<situation-slug>]
who: [<who-slug>]
status: draft | stable

message:
  text: |
    <текст с плейсхолдерами {…}>
  media: —                       # или assets/<window-slug>/…, или data:<slug>.<поле>

widgets:
  - widget: <button|url|select|multiselect|text-input|calendar>
    id: <snake_case>
    ...
    action: use-case:<uc-slug>   # use-case бота этой фичи, или опустить
    transition: <window-slug>|back|done|start:<feature>

getter:
  <ключ>:
    source: use-case:<uc-slug> | dialog-data | start-data | const
    data: data:<slug>            # опц., словарь interface
    fallback: <что показывает окно при недоступном источнике>

errors:
  backend-unavailable: <текст или —>
  invalid-input: <текст или —>
​```
```

- Обязательные мета-поля: `name`, `state`, `interface-block`,
  `ux-substrates`, `situations`, `who`, `status` (`slug` — заголовок H2).
- Условный переход — списком исходов use-case бота:
  `transition: [{ to: address, when: 'use-case бота вернул «нужен адрес»' }, { to: confirm, when: 'иначе' }]`.
- `errors` — канон-ключи `backend-unavailable`, `invalid-input` (текст или
  `—`); технический recovery — в код-репо.

### Что window НЕ

- ❌ Не диалог (сценарий из шагов) и не блок interface (UX-анализ).
- ❌ Не уведомление: окно отвечает на действие; исходящее первым — реестр
  `notification.md` корня.
- ❌ Не носитель бизнес-правил: ветвление и валидацию решает домен через
  use-case бота; окно показывает и маршрутизирует.
- ❌ Не код: классы виджетов, `.ftl`-ключи, callback-строки.

### Тест-критерий

«Один шаг диалога — одно сообщение с виджетами, данными и переходами?» —
«Выбор услуг: приглашение + multiselect + Далее/Назад» ✅; «Оформление
заказа целиком» — dialog ❌; «Напоминание за час» — notification ❌.

# Форма `use-case.md`

> Use-case бота — **оркестратор** одного действия: собрать ввод, дёрнуть
> доменный use-case через backend, поработать со стейтом и вернуть исход.
> **Бизнес-правил не держит** (они в доменах сервисов). Все use-case'ы фичи лежат
> в `use-case.md` — **по H2-секции на use-case**, форма секции зеркалит
> доменный use-case (`services/_templates/use-case.md`) на уровне H3, без
> доменных-only секций (`Called aggregate methods`, `Events emitted`,
> `Side effects`).

## Критерии use-case

1. **Оркестрация, не правило.** Валидация формата ввода → вызов доменного
   use-case → разбор исхода → апдейт `dialog-data` → возврат исхода окну.
   Бизнес-решение принимает **домен**.
2. **Опирается на домен.** `### Dependencies` перечисляет доменные use-case
   (`use-case:<ctx>.<Operation>`); чистая навигация use-case'а не требует.
3. **Исходы объявлены.** `### Outputs` называет исходы, на которые
   ссылаются `when` переходов окон.
4. **Стейт — контракт.** Что читает/пишет в `dialog-data` — в
   `### Dependencies` (JSON-примитивы).
5. **Фичевый.** slug уникален в фиче; рефы `use-case:<uc-slug>` (без точки)
   внутри фичи.

### Форма секции use-case

```markdown
## <uc-slug>

​```yaml
name: <человекочитаемое имя>
operation: <PascalCase>
who: [<who-slug>]
status: draft | stable
​```

<одна-две фразы об оркестрации>

### Actor
- **Role:** <who> · **Trigger:** виджет `<id>` окна `<window-slug>` | вход диалога | system

### Inputs
| field | source | required | description |
|---|---|---|---|
| `<Field>` | `widget:<id>` \| `dialog-data:<key>` \| `start-data:<key>` | yes | <смысл> |

### Outputs
- **On success:** <исход> (на него смотрит `when` окна)
- **On failure:** см. Errors

### Dependencies
| dependency | kind | purpose |
|---|---|---|
| `use-case:<ctx>.<Operation>` | domain use-case | <что делает домен> |
| `dialog-data:<key>` | state (read \| write) | <что лежит, JSON-примитив> |

### Steps
1. **Validate input:** формат (бизнес-валидация — в домене).
2. **Call domain:** `use-case:<ctx>.<Operation>`.
3. **Map outcome:** исход домена → исход bot UC.
4. **Update state:** `dialog-data:<key>`.
5. **Return outcome:** исход окну.

### Errors
| outcome | when | реакция окна |
|---|---|---|
| `backend-unavailable` | backend недоступен | `errors.backend-unavailable` окна |
| `<domain-failure>` | домен вернул отказ | переход/сообщение по `when` |
```

### Что use-case НЕ

- ❌ Не носитель бизнес-правил: инвариант, бизнес-валидация, policy — в
  доменов сервисов (`services/*/domains/`). Bot UC их **вызывает**, не повторяет.
- ❌ Не доменный use-case: реф на доменный — с точкой
  (`use-case:<ctx>.<Operation>`), на bot UC — без точки.
- ❌ Не окно: UC обрабатывает действие и возвращает исход, показ — окно.
- ❌ Не код: класс сервиса, метод API-клиента, формат запроса, ретраи.

### Тест-критерий

«Оркестрация бота — собрать ввод, дёрнуть доменный use-case, разрулить
исход и стейт?» — «submit-booking: собрать draft, вызвать
`booking.CreateOrder`, вернуть «нужен адрес»/«готово»» ✅; «Проверить, что
гостей ≤ вместимости» — бизнес-правило домена ❌; «Окно подтверждения» —
window ❌.

# Anti-patterns (вся фича)

- ❌ Несколько диалогов в одной фиче — вложенный сценарий выносится в
  отдельную фичу, вход через `start:<feature>`.
- ❌ Ссылка из фичи в окно/use-case другой фичи минуя `start:`/`command` —
  фичи изолированы.
- ❌ `action` мимо use-case бота («кнопка сама сохраняет в базу») —
  действие ссылается на use-case или отсутствует.
- ❌ Бизнес-правило в `when` или в `Steps` use-case бота («если сумма >
  1000») — решает домен, bot UC маршрутизирует исход.
- ❌ Реф на доменный UC без точки или на bot UC с точкой — точка различает
  уровни.
- ❌ Несериализуемое в `dialog-data` (объект даты, сущность домена) —
  только JSON-примитивы.
- ❌ Окно-тупик (ни перехода, ни `done`), диалог без `started-by`,
  плейсхолдер без ключа `getter`, ключ без `fallback`.
- ❌ `/start` без `stack: reset`; уведомление без идемпотентности; серия
  сообщений как «окно».
- ❌ Код/облик в артефактах: классы виджетов, `.ftl`-ключи, callback-строки,
  HTML/эмодзи-оформление как требование.
- ❌ Рассинхрон зеркал interface ↔ окно: `window.ux-substrates` обязан
  совпадать с `ux-substrates` его `interface-block`.
