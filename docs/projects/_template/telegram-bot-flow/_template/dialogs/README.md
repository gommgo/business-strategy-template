# dialog

> Диалог (dialog) — сценарий бота из окон (window) поверх одной группы
> состояний: завершённая задача участника (who) от входа до результата.
> Держит состав окон, точки входа (`started-by`), режим запуска и контракт
> накопления данных (`dialog-data`) между окнами. Смысловой аналог зоны
> (zone) interface и flow слоя экранов.

## Критерии dialog

1. **Одна задача участника.** Диалог (dialog) — завершённый сценарий
   («оформить заказ», «выбрать язык»), не произвольная пачка окон и не
   весь бот целиком.
2. **Состав окон упорядочен.** `windows` перечисляет окна (window) в
   содержательном порядке шагов — этот порядок и есть порядок состояний
   группы (по нему работает автопереход «следующее окно»).
3. **Входы объявлены.** `started-by` перечисляет, откуда диалог стартует:
   команда (`command:<slug>`), кнопка другого диалога (`window:<slug>`) или
   уведомление (`notification:<slug>`). Диалог без входа недостижим.
4. **Накопление — контракт.** Всё, что окна передают друг другу, описано в
   `dialog-data` тела: имя ключа + что лежит (JSON-примитивы).
5. **Граф без тупиков.** Из каждого окна есть путь к завершению (`done`)
   или явному переходу; сводный граф `transitions` в теле — зеркало
   переходов, авторски заданных на виджетах окон.

## Что dialog НЕ

- ❌ Не окно (window): один шаг с сообщением и кнопками — это window.
- ❌ Не команда (command): `/start` и deep-link — точки входа, реестр
  `command.md`.
- ❌ Не зона (zone) interface: зона — смысловая область UX-анализа; диалог
  — её композиционное воплощение в боте (связь семантическая).
- ❌ Не бот целиком: бот — это поверхность; диалогов в ней много.
- ❌ Не код: имя python-файла, класс `Dialog`, регистрация роутера — забота
  код-репо.

## Тест-критерий

«Это завершённая задача участника из последовательности окон с явными
входами и контрактом накопления — а не один шаг, не точка входа и не вся
поверхность?»

- «**Оформление заказа**»: выбор услуг → гости → адрес → подтверждение ✅
- «**Окно выбора услуг**» — это window ❌
- «**/start**» — это command, вход в диалог `main-menu` ❌

## Форма frontmatter

| поле | тип | обязательность | смысл |
|---|---|---|---|
| `slug` | string | yes | kebab-case идентификатор |
| `name` | string | yes | человекочитаемое имя |
| `description` | string | yes | одна фраза о сценарии |
| `states-group` | string (PascalCase, англ.) | yes | имя группы состояний — структурный идентификатор для кода |
| `windows` | `[window-slug]` | yes | окна по порядку шагов (= порядок состояний) |
| `started-by` | `[command:<slug> \| window:<slug> \| notification:<slug>]` | yes | точки входа |
| `launch-mode` | `standard \| root \| single-top \| exclusive` | yes | режим запуска: обычный, корневой (главное меню), без дублей на вершине, единственный |
| `start-data` | string | optional | что передаётся при старте (контракт, JSON-примитивы), `—` если ничего |
| `who` | `[who-slug]` | yes | роли interface, для которых сценарий существует |
| `status` | `draft \| stable` | yes | зрелость записи |

## Тело: dialog-data и transitions

```yaml
dialog-data:
  draft: черновик заказа — services (список), guests (число), address (строка)
  draft_id: идемпотентный ключ отправки, выдаётся на старте

transitions:   # сводное зеркало; канон — transition на виджетах окон
  - { from: services, to: guests,  when: 'кнопка «Далее»' }
  - { from: guests,   to: address, when: 'use-case вернул «нужен адрес»' }
  - { from: guests,   to: confirm, when: 'адрес не нужен' }
  - { from: address,  to: confirm, when: 'адрес принят' }
  - { from: confirm,  to: done,    when: 'заказ отправлен' }
```

`dialog-data` — контракт накопления: ключ → что лежит (по-русски, с
указанием JSON-формы). `transitions` — выводимая сводка графа окон для
чтения целиком; источник правды — поля `transition` виджетов в окнах,
рассинхрон ловит аудит слоя.

## Пример

```markdown
---
slug: booking
name: 'Оформление заказа'
description: 'От выбора услуг до подтверждения с номером заказа'
states-group: Booking
windows: [services, guests, address, confirm]
started-by: [command:start-menu, window:menu]
launch-mode: standard
start-data: —
who: [client]
status: draft
---

## Anti-patterns

- ❌ Диалог без `started-by` (недостижим) или окно в `windows`, которого
  нет в `windows/` поверхности.
- ❌ `dialog-data` с несериализуемым содержимым (сущности домена,
  даты-объекты) — только JSON-примитивы.
- ❌ `transitions`, расходящийся с `transition` виджетов окон (зеркало
  обязано сходиться).
- ❌ Окно одного диалога в `windows` другого: окно (window) принадлежит
  ровно одному диалогу (`window.dialog`).
- ❌ Глубокая матрёшка `start:` без `done` на каждом уровне — стек должен
  сворачиваться.
- ❌ Два диалога с одним `states-group` — имя группы уникально в пределах
  поверхности.
