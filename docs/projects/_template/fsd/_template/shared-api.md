# shared-api

> Контракт данных поверхности: как фронт разговаривает с бэком на уровне
> смысла — какие сущности покрыты контрактом и какие **сценарии данных**
> нужны для работы без бэка (мок/демо/разработка). Выбор HTTP-клиента,
> либы мока и формат схем — платформа фронт-форка (`docs/stack/`).

## Контракт данных

Форма каждой сущности задаётся её записью в `entities.md` (колонка `поля` +
источник в домене). Контракт покрывает **все** entities поверхности:
сущность без покрытия — blocker для stable этого файла.

## Критерии сценария данных

1. **Продуктовое состояние.** Сценарий описывает осмысленное состояние
   данных поверхности (пусто / наполнено / ошибка / авторизован), а не
   техническую фикстуру.
2. **Полнота.** Сценариев достаточно, чтобы показать поверхность без бэка:
   как минимум `empty` и `populated`.

## Что shared-api НЕ

- ❌ Выбор клиента/библиотек, заголовки, эндпоинты — `docs/stack/`
  фронт-форка.
- ❌ Дубль схем сущностей — форма живёт в `entities.md`.
- ❌ Тест-фикстуры конкретных тестов — это исполнительная сторона.

## Сценарии данных

- `slug` — идентификатор сценария · строка-идентификатор · обяз.
- `name` — человекочитаемое имя · строка · обяз.
- `description` — что демонстрирует сценарий · строка · обяз.
- `состояние` — состояние данных по сущностям · свободный текст · обяз.
- `status` — зрелость записи · `draft | stable` · обяз.

| slug | name | description | состояние | status |
|---|---|---|---|---|
| `empty` | Пусто | <что видно без данных> | <все сущности пустые> | `draft` |
| `populated` | Наполнено | <реалистичная картина> | <какие сущности чем наполнены> | `draft` |
| `<slug>` | <имя> | <что демонстрирует> | <состояние> | `draft` \| `stable` |
