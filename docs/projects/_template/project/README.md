# Артефакты продукта

Продуктовый слой проекта живёт в `docs/projects/<project-slug>/`. Этот файл — **канон формы** (`_template/project/`);
данные каждого проекта живут в его папке. Состав слоя:

- **1 singleton** `vision.md` — корневой документ продукта: двенадцать разделов у продукта с поверхностью маршрута
  приложения, минимум — у продукта из сайтов и лендингов.
- **реестр-хребет** `surface.md` — поверхности продукта с типом и родом веб-поверхности. Его slug'и — **ключи
  партиционирования**: каждая поверхность получает свой файл возможностей и свои папки слоёв по типу и роду (раздел
  «Поверхность — хребет продукта»).
- **папка возможностей** `capability/<surface>.md` — реестр возможностей одной поверхности с паспортами и урезанием (по
  файлу на поверхность).
- **7 плоских кросс-поверхностных таблиц** `user.md` (пользователи и их постура), `object.md` (глоссарий объектов),
  `action.md` (словарь действий), `integration.md`, `boundary.md`, `constraint.md`, `market.md`.
- **файлы уровня продукта** — машинные файлы по схемам базы текстов: факты, голос, голос клиента (раздел «Файлы уровня
  продукта»); их ведёт исполнитель слоя страницы.

Связи между записями — через `slug`; что проверяется структурно, а что семантически — раздел «Связи».

Чистая продуктовая аналитика. На код, FSD и компонент не мапится — это вход для соседних слоёв того же проекта,
**вложенных в его папку**: `<slug>/interface/<surface>/` (UX по поверхности, `/interface-deep-dive`),
`<slug>/screens/<surface>/` (карта экранов, состояния, тексты интерфейса, `/screen-deep-dive`), `<slug>/fsd/<surface>/`
(FSD-карта фронтовой поверхности — мост к коду `<org>/frontend`, `/fsd-deep-dive`), `<slug>/site/<surface>/` (слой
страницы сайта и лендинга — мост к коду `<org>/site`, `/design-deep-dive`), `<slug>/telegram-bot-flow/<surface>/`
(композиция диалогов bot-поверхности), `<slug>/mobile/<surface>/` (карта мобильного приложения — композиция и мост к
коду `<org>/mobile`, `/mobile-deep-dive`), `<slug>/design/` (облик продукта, `/design-deep-dive`), `<slug>/services/`
(сервисная топология бэкенда, `/service-deep-dive`; домены по bounded-context внутри сервисов — surface-агностичны,
`/domain-deep-dive`).

## Поверхность — хребет продукта

Продукт состоит из **поверхностей** (сайт, лендинг, веб-кабинет, мобильное приложение, бот, API, админка …) — точек,
где он встречает пользователя. `surface.md` — реестр поверхностей. Каждая поверхность описывается сверху вниз в слоях,
которые задают её `type` и род `web-kind`, и все они партиционируются по её slug:

```
docs/projects/<slug>/
├── vision.md                 singleton продукта
├── surface.md                РЕЕСТР-ХРЕБЕТ: объявляет поверхности (type, web-kind)
├── user.md  object.md  action.md          плоские кросс-поверхностные таблицы
├── integration.md  boundary.md  constraint.md  market.md
├── facts.yaml  voice.yaml  voc.yaml       файлы уровня продукта (ведёт слой страницы)
├── capability/
│   ├── <surface-1>.md        возможности поверхности 1
│   └── <surface-2>.md        возможности поверхности 2
├── interface/
│   └── <surface>/            who · stage · situation · scenario · zone · block · ux-substrate · data-items  (кроме web рода landing и site)
├── screens/
│   └── <surface>/            map.md · texts.md · flows · screens · blocks · shells · assets  (web рода app, admin, desktop, embed)
├── fsd/
│   └── <surface>/            entities · features · pages · widgets · app · shared-*  (web рода app, admin, desktop, embed)
├── site/
│   └── <site-surface>/       site-brief · meaning · site-map · hierarchy · plans · copy  (web рода landing и site — вместо interface, screens, fsd)
├── telegram-bot-flow/
│   └── <bot-surface>/        command.md · notification.md · features/<feature>/{dialog.md,window.md,use-case.md}  (для type: bot — вместо screens)
├── mobile/
│   └── <mobile-surface>/     entities · screens · flows · features · shell · entry-points · permissions · system-actions · widgets · background-tasks · shared-*  (для type: mobile — вместо screens)
├── design/                   облик продукта: бренд, дизайн-система, бриф на вид, паспорт визуала, ассеты
│   └── <surface>/            облик поверхности сайта или приложения: арт-дирекция, ассеты, холст, приёмка
└── services/                 service.md + platform.md + architecture.md + _shared/
                              + <service-slug>/ (паспорт + domains/<ctx>/)
```

Одна ценность, доступная на двух поверхностях («смотреть статус» на web и в боте), описывается **двумя записями** —
каждая в файле своей поверхности, со своим воплощением. Дубль — осознанный: воплощение ценности на разных поверхностях
разное. Понятия и слова — наоборот, одни на продукт: объект, действие, факт и голос заводятся один раз.

## Порядок этапов

Продукт описывается до экранов: экраны строятся от объектов и сценариев, а не от списка функций (ux 13/04 §1).
Маршрут поверхности задают её `type` и род `web-kind`:

| поверхность | этапы со стороны слоя проекта | исполнители |
|---|---|---|
| `web` рода `app`; `admin`, `desktop`, `embed` | vision → роли и постуры → поверхности → объекты и действия → возможности → сценарии → interface → экраны → тексты интерфейса → FSD | `/project-deep-dive` → `/interface-deep-dive` → `/screen-deep-dive` → `/fsd-deep-dive` |
| `web` рода `landing`, `site` | vision (минимум) → пользователь → поверхность с родом → слой страницы | `/project-deep-dive` → `/design-deep-dive` |
| `mobile`, `bot` | как у приложения до interface включительно, дальше — карта приложения или диалоги бота | … → `/mobile-deep-dive` или `/telegram-bot-flow-deep-dive` |

- **Роли и постуры — до поверхностей.** Поверхности выводятся из ролей, а решение, делить ли админку и клиентскую
  часть, принимается по постурам (ux 13/04 §17).
- **Объекты и действия — до возможностей.** Ядро возможности — ссылка на объект и действие; язык продукта задают до
  списка задач (ux 13/04 §6–§7).
- **Сценарии — до экранов.** Сценарий пишется для каждой возможности `hub` и `critical`; на поверхности с хабами это
  первый kind interface (ux 13/04 §11).
- **Тексты интерфейса — свой этап после экранов.** Ключ строки строится по экрану, длина — по ширине компонента
  дизайн-системы.
- **Дизайн входит в маршрут приложения дважды.** После сценариев — бриф на вид, карточки стиля, дизайн-система, паспорт
  визуала и иконки; после готовых экранов — компоненты, иллюстрации и макет (слой `design/`, `/design-deep-dive`). Сайт
  и лендинг приходят в дизайн из слоя страницы.

Порядок — рекомендация, не закон. Войти можно с любого этапа: исполнитель находит первый этап с готовым входом, а
пропуск пишет в `…/_phase-jump.md` своей ветки state с долгом. Например, возможности, заведённые со списка функций до
объектов, держат `object` и `action` = `—` в `draft`, а названные объекты и действия ложатся stub-строками в
`object.md` и `action.md`. Долг не блокирует работу, но `stable` требует того, что пропущено.

## Файлы уровня продукта

Рядом с `vision.md` живут машинные файлы по схемам базы текстов — одни на продукт: сайт, кабинет, мобильное
приложение и бот говорят одними фактами и одним голосом.

| файл | что | форма | «закрыто» | кто закрывает |
|---|---|---|---|---|
| `<slug>/facts.yaml` (второй язык — `facts.<lang>.yaml` с теми же id) | белый список фактов продукта: каждое число, цена, срок, гарантия — с источником; `never_claim` — чего продукт не обещает | `kb/text/02-strategy-messaging/facts.schema.yaml` | `status: confirmed` | заказчик |
| `<slug>/voice.yaml` | профиль голоса бренда: где действует (`scope`), принципы, карта тона | `kb/text/05-voice-editorial/voice.schema.yaml` | `status: approved` | заказчик, владелец продукта |
| `<slug>/voice.product.yaml` | профиль голоса продукта — интерфейс за входом, мобильное приложение, бот: принципы и карта тона по ситуациям интерфейса (ux 07/01 §7.1); на него ссылается `scope.product_voice_ref` профиля бренда | та же схема | `status: approved` | владелец продукта |
| `<slug>/voc.yaml` | голос клиента: слова клиентов с источником — интервью, отзывы; по желанию | `kb/text/02-strategy-messaging/voc.schema.yaml` | — | — |

- **Кто ведёт.** Исполнитель слоя страницы `/design-deep-dive` — и у продукта без сайта: тексты интерфейса и бота
  читают те же факты и голос. `/project-deep-dive` их читает, но не правит; md-файлы продуктового слоя, наоборот,
  ведёт только он.
- **Факт — только с источником.** Сообщение, документ, система заказчика, реестр, интервью, договор; модель источником
  не бывает. Статус факта `confirmed` ставит заказчик.
- **Голос продукта обязателен** у проекта с интерактивной поверхностью — кабинетом, мобильным приложением, ботом.
  Раздел `Voice` vision ссылается на оба профиля.
- **Канон формы** — схемы базы; где файлы лежат, как читаются и кто пишет тексты по ним — канон слоя страницы
  [`../site/README.md`](../site/README.md), раздел «Уровень продукта».

## Облик продукта — папка `design/`

Облик продукта — бренд, дизайн-система, бриф на вид приложения, паспорт визуала продукта, ассеты — живёт в папке
`design/` проекта; у поверхности сайта или приложения (`web`, `admin`, `desktop`, `embed`) — своя папка
`design/<surface>/`. Её ведёт `/design-deep-dive`, канон — [`../design/README.md`](../design/README.md). В md-файлах
продуктового слоя облика нет: бриф на вид берёт из него проекции — тип приложения, постуры, статусы объектов, мобильный
объём, цель доступности.

## Принципы оформления

Зеркалит канон `docs/projects/_template/interface/`. Один файл — один kind (vision — singleton). Табличный файл держит
основную таблицу своего kind; где форма это называет, рядом живут подтаблицы и секции того же kind: провайдеры и
функции `integration.md`, постура `user.md`, атрибуты и представления `object.md`, паспорта и урезание
`capability.md`. Структура табличного файла:

```markdown
# <имя файла>

> Одна-две фразы о сущности (что это в продукте, что чем ссылается).

## Критерии <kind>
…

## Что <kind> НЕ
…

## Тест-критерий
…

| slug | name | description | <relation columns> | status |
|---|---|---|---|---|
| `<slug>` | <имя> | <описание> | … | `draft` |
```

H1 = имя файла = kind. Frontmatter не нужен — kind определяется именем файла. Файл возможностей берёт имя поверхности
(`capability/<surface>.md`), H1 внутри — `capability`. Русское слово, являющееся переводом строгого термина,
сопровождается его `slug` в скобках при каждом вхождении: «пользователь (user)», «возможность (capability)»,
«поверхность (surface)», «объект (object)», «действие (action)».

### Форма ячеек (та же что в interface)

| тип значения | формат | пример |
|---|---|---|
| одиночный slug-реф | в бэктиках | `` `analyst` `` |
| массив slug-рефов | питон-стиль с бэктиками внутри | `` [`analyst`, `business-owner`] `` |
| ссылка в чужой слой или на другую поверхность | префикс и slug в бэктиках | `` `job:<slug>` ``, `` `web:send-referral` `` |
| пустое опциональное поле | em-dash | `—` |
| enum (`type`, `web-kind`, `priority`, `posture`, `reversibility`, `direction`, `kind`, `target`, `status`) | в бэктиках | `` `web` `` |
| свободный текст | без кавычек, одна строка | «снижение времени до первой ценности» |

У основной таблицы первые три колонки одни и те же: `slug` · `name` · `description`; последняя колонка — `status`
(enum `draft` \| `stable`). Подтаблица начинается ссылкой на запись основной таблицы (`user`, `object`) и своего
`status` не держит: её полноту проверяет переход записи в `stable`.

## Статус записи

- `draft` — заведена, но не прошла полный чек-лист зрелости (часть слотов пустая, есть открытые вопросы в ветке
  state скилла, тест-критерий не подтверждён, ссылается на не существующие сущности).
- `stable` — прошла все критерии файла-канона (`Критерии <kind>`, `Что <kind> НЕ`, `Тест-критерий`), все обязательные
  слоты заполнены, все семантические связи внятные, открытых вопросов нет.
- Дефолт у новой записи — `draft`. Повышение в `stable` — через скилл `/project-deep-dive` (аналитик; в клиент-режиме
  продукт ведёт единый вход `/entrypoint-for-business`), по подтверждению аналитика.
- Понижение `stable → draft` — только аналитик руками, когда нашёл несостыковку.
- Машинные файлы уровня продукта держат статус по своей схеме: у фактов — `confirmed`, у голоса — `approved`.

## Связи

Внутри продуктового слоя структурно проверяются поверхность и ссылки ядра: `/project-audit` ловит файлы и папки для
поверхностей вне реестра, неразрешённые `user`, `object`, `action` возможности, `integration.surface` в пустоту. Смысл
связей и связи с другими слоями — **семантические**: их сверяет `/cross-audit` роем агентов, а не ссылочной
целостностью.

**Поверхность — структурная ось.** Файл `capability/<surface>.md` и папки `interface/<surface>/`,
`screens/<surface>/`, `fsd/<surface>/`, `site/<surface>/`, `telegram-bot-flow/<surface>/`, `mobile/<surface>/`,
`design/<surface>/` обязаны соответствовать поверхности из реестра `surface.md`, и каждая — своему типу и роду:

- `interface/` — у всех поверхностей, кроме `web` рода `landing` и `site`;
- `screens/` и `fsd/` — у `web` рода `app`; `admin`, `desktop`, `embed`;
- `site/` — только у `web` рода `landing` и `site`; файл возможностей такой поверхности — по желанию;
- `telegram-bot-flow/` и `mobile/` — только у `type: bot` и `type: mobile` соответственно;
- `design/<surface>/` — у `web`, `admin`, `desktop`, `embed`; облик мобильного приложения и бота — токены
  дизайн-системы продукта и голос.

Внутри `docs/projects/<slug>/` ожидаются связи:

- **user → surface**: user работает через одну+ поверхность (`surface.user` — кого она обслуживает).
- **user → capability**: user получает ценность от одной+ возможности (`capability/<surface>.md` → колонка `user`).
- **capability → object, action**: ядро возможности — один объект глоссария и одно действие словаря.
- **capability → surface**: связь **структурная** — возможность лежит в файле своей поверхности. `/project-audit`
  ловит файл возможностей для поверхности вне реестра и поверхность маршрута приложения без файла возможностей.
- **object → user**: `object.creates`, `object.deletes` — кто создаёт и удаляет экземпляры (или `system`); вместе с
  ядром возможностей это матрица «пользователь × объект × действие», которую собирает отчёт `/project-audit`.
- **action → object**: `action.objects` — к каким объектам применимо действие.
- **vision → остальные kind**: `Users` — пользователи, `MVP` — возможности `<surface>:<slug>`, `Positioning` —
  `market`, `Constraints` — `constraint`, `Non-goals` — slug записей `boundary`; сводки `Name` и `Users` выводятся из
  `surface.md` и постуры `user.md`.
- **integration → surface**: интеграция обслуживает одну+ поверхность (колонка `surface` — массив slug-рефов в
  реестр). Лендинг без своего бэкенда отдаёт заявки во внешние системы — строками интеграций с этой поверхностью.
- **integration ↔ capability**: интеграция обычно обслуживает возможность (не фиксируется отдельным полем —
  `/cross-audit`; паспорт возможности называет её в `depends-on`).
- **integration → соседний проект**: при `target: sibling-project` — колонка `sibling-project` ссылается на slug
  соседнего проекта бизнеса (стык фиксируется здесь, сводится в `../project-map.md`).
- **constraint ↔ surface / integration**: ограничение часто привязано к поверхности или интеграции (152-ФЗ → web; SLA
  партнёра → integration). Не фиксируется полем.
- **market ↔ capability**: конкурент покрывает наши возможности — это смысл сопоставления, проверяет `/cross-audit`.

Связь с соседними слоями (тоже семантическая; соседи живут **в той же папке проекта** `docs/projects/<slug>/` или в
общих слоях стратегии):

- `vision.addresses-problem` ↔ `business/business-problem.md` — какие проблемы закрывает продукт (M:N; авторская
  сторона связи — здесь); `Success` целит в метрики `hypothesis-map/metric.md`.
- `user.segments` → `ajtbd/segment.md` — пользователь сводится к сегменту(ам) рынка (опц.; авторски здесь).
- `capability.trace` → `ajtbd/job.md` (`job:<slug>`) и `hypothesis-map/hypothesis.md` (`hypothesis:<slug>`) —
  возможность целит в работу сегмента и реализует гипотезу (опц.; авторски здесь).
- `user` ↔ `<slug>/interface/<surface>/who` — каждая роль в `interface` должна семантически соответствовать одной из
  user проекта (авторски `who.users`); постуру роль берёт у пользователя.
- `capability/<surface>` ↔ `<slug>/interface/<surface>/situation` и `scenario` / `<slug>/screens/<surface>` (поле
  экрана `main-task`) / `<slug>/services/<svc>/domains/<область>` — возможность поверхности реализуется через ситуации
  и сценарии той же поверхности (UX), экраны и домены (бэкенд).
- `object` и `action` ← interface и screens той же папки проекта: `data-items.object`, `zone.object`, поля экрана
  `object` и `key-action`, атрибут `action=` узлов дерева, колонки `object` и `action` реестра текстов интерфейса.
  `aliases` объектов и `banned` действий — запрещённые синонимы для текстов страницы и интерфейса.
- `surface` ↔ `<slug>/interface/<surface>/zone` — зоны интерфейса живут в папке своей поверхности.
- `vision`, постура `user.md`, `surface.md`, статусы `object.md` → бриф на вид приложения в `design/` — проекции,
  которые слой дизайна не переписывает.
- `integration` ↔ `<slug>/services/` — внешняя интеграция в коде существует как доменный адаптер; межпроектная
  интеграция — как порт/клиент к соседнему проекту (клиент интеграции в `services/_shared/`, потребление —
  `services/_templates/use-case.md`); какой сервис ходит наружу — видно по паспорту (`Dependencies`/`Fronts`). У
  поверхности без своего сервиса (лендинг, сайт) архитектор записывает это решением `services/architecture.md`.

## Workflow

```
/project-deep-dive            — единая точка входа аналитика в продуктовый слой: vision, пользователи и постуры,
                                поверхности, объекты и действия, возможности, интеграции, ограничения, рынок.
/design-deep-dive             — файлы уровня продукта (факты, голос), слой страницы и облик продукта (design/).
/entrypoint-for-business      — режим «домашнее задание» для клиента
                                (бизнес-язык, единый вход, эскалация в ветку).
/project-audit                — узкий аудит внутри project-слоя.
/cross-audit                  — сквозной семантический аудит
                                project ↔ interface ↔ services/domain ↔ screen
                                + межпроектные стыки (project-map).
```

Скилы заводят новые сущности, углубляют частичные, разбирают сырьё (транскрипт интервью клиента, заметки,
web-research), ведут переход `draft → stable`. Прямой правки артефактов руками избегаем — скилл держит state и
предлагает переходы через `AskUserQuestion`.

## Anti-patterns

- ❌ Frontmatter в файлах (kind определяется именем файла — как в `interface/`).
- ❌ Каталоги-по-сущностям (папка `users` с файлом на запись). Один табличный файл = один kind. Поверхность —
  единственная ось партиционирования: `capability/<surface>.md` — это таблица, не каталог записей.
- ❌ Файл возможностей или папка слоя для поверхности, которой нет в реестре `surface.md`. Хребет ведёт реестр.
- ❌ Папка слоя не по типу и роду поверхности: `interface/`, `screens/`, `fsd/` у `web` рода `landing` или `site` (на их
  месте слой страницы), `site/` у рода `app`, `web` без рода.
- ❌ Несколько vision в **одном проекте**. Один проект (папка `docs/projects/<slug>/`) = один продукт = один
  `vision.md`. Разные продукты — разные папки проектов.
- ❌ Второе слово для одного понятия: синоним объекта или действия в имени возможности, зоны, ситуации или блока.
  Другие названия — в `aliases` объекта и `banned` действия.
- ❌ Перенос продукт-аналитики в `<slug>/interface/` (UX-слой) или в `<slug>/services/` (топология и бэкенд) — это
  разные слои. project = «зачем и для кого», interface = «как взаимодействует», domain = «какой бизнес-код».
- ❌ Облик и продающий текст в md-файлах продуктового слоя: облик — `design/`, продающий текст — тексты страницы слоя
  страницы.
- ❌ Правка файлов уровня продукта — фактов, голоса, голоса клиента — из продуктового слоя: их ведёт исполнитель
  слоя страницы.
- ❌ Жёсткие slug-валидации между project и соседями. Связи — семантические; ловит `/cross-audit`, а не grep.
- ❌ Авто-вписывание результатов web-research в артефакты. Рой агентов кладёт кандидатов в ветку
  `projects/<slug>/project/research/` state оркестратора `/entrypoint` — promotion в
  `market.md` / `constraint.md` только через `AskUserQuestion` аналитика.
- ❌ Промоушн `stable` руками без чек-листа — это работа скилла.
