# surface

> Поверхность (surface) — точка, где продукт «торчит наружу» и встречает пользователя (user): сайт, лендинг,
> web-приложение, мобильное приложение, публичное API, админка, телеграм-бот, embed-виджет. Поверхность принадлежит
> одному типу (`type`) и обслуживает одного+ пользователя (user); у веб-поверхности есть ещё род (`web-kind`).
>
> Этот файл — **реестр-хребет** продукта: он объявляет поверхности, а их slug'и — **ключи партиционирования**
> остальных слоёв. Какие слои получает поверхность, решают её `type` и род:
>
> - `web` рода `app`, `admin`, `desktop`, `embed` — маршрут приложения: файл возможностей `capability/<surface>.md`,
>   интерфейс `interface/<surface>/`, экраны `screens/<surface>/` и FSD-карта `fsd/<surface>/`;
> - `web` рода `landing` или `site` — слой страницы `site/<surface>/` на месте интерфейса, экранов и FSD-карты; файл
>   возможностей — по желанию;
> - `mobile` — интерфейс и карта приложения `mobile/<surface>/`; `bot` — интерфейс и диалоги
>   `telegram-bot-flow/<surface>/`; у `api` и `other` композиции (экранов, диалогов, карты приложения) нет.
>
> Облик поверхности сайта и приложения (`web`, `admin`, `desktop`, `embed`) — папка `design/<surface>/` слоя дизайна.
> Завести строку здесь — значит открыть поверхности место во всех её слоях; `/project-audit` ловит файлы и папки для
> поверхностей вне реестра и поверхности реестра без слоёв. Сводку поверхностей с типом и родом держит раздел `Name`
> файла `vision.md` — она выводится из этого реестра.

## Критерии surface

1. **Точка встречи с user.** Поверхность существует, потому что через неё user получает ценность от продукта. Если ни
   один user не пользуется — поверхность мёртвая.
2. **Один тип, одно «где».** `type` (web / mobile / api / admin / bot / desktop / embed / …) — один. `lives-at` —
   конкретное «где» (домен, store-app, мессенджер, embedding-host). Двух типов на одной surface не бывает — это две
   разные surface.
3. **Самодостаточна.** User может закрыть основной job-to-be-done, не выходя за пределы поверхности. Если для базовой
   задачи нужна другая поверхность — это или одна поверхность, или зависимость нужно явно зафиксировать.
4. **Поверхность ≠ канал нотификации.** Email/SMS/push, через которые мы только уведомляем — это **integration**, не
   surface. Surface — где user **действует**, а не только получает сигнал.
5. **Мобильное приложение — одна поверхность со всеми своими входами.** `type: mobile` — нативное приложение
   (Android / iOS). Его уведомления, виджеты, ярлыки, голосовые команды и фоновая работа — не отдельные поверхности, а
   части той же (то же «где» — то же приложение); они проектируются в слое `mobile/<surface>/`, код живёт в
   `<org>/mobile`. Отдельной поверхностью становится только самостоятельное «где»: часы, автомобиль, голосовой
   сценарий, целиком проходящий вне приложения (`type: other`).
6. **У веб-поверхности назван род.** `web-kind` говорит, что это за веб-поверхность и какой репозиторий кода её
   поднимет:
   - `landing` — сайт из одной посадочной страницы со своим «где», своей шапкой и воронкой; код — `<org>/site`;
   - `site` — многостраничный сайт: одна карта, одна шапка и подвал, один порядок сборки; код — `<org>/site`;
   - `app` — веб-сервис или кабинет: работа за входом, объекты и сценарии; код — `<org>/frontend`.

   Посадочная под платный трафик внутри многостраничного сайта — страница этого сайта, а не отдельная поверхность;
   отдельный `landing` — только при своём «где», своей шапке и воронке. Кабинет за входом на сайте — отдельная
   поверхность рода `app`. У остальных типов рода нет (`—`): маршрут задаёт сам `type`, а значения `type` читают
   репозитории кода и хаб `<org>/infra`, поэтому род — колонка, а не новый тип.

## Что surface НЕ

- ❌ Технологический стек («React-фронт», «Go-API»). Это стек, не поверхность. Поверхность — `web`, реализованная на
  чём угодно.
- ❌ Канал уведомлений без обратного действия (email-рассылка, push без deep-link). Это `integration`.
- ❌ Виджет, уведомление или голосовая команда мобильного приложения как отдельная поверхность. Это входы и
  представления той же `mobile`-поверхности (слой `mobile/<surface>/`).
- ❌ Внутренний интерфейс команды (логи, мониторинг, k8s-dashboard). Это эксплуатация, не продукт.
- ❌ Поверхность без user. Surface, на которую никто из user не заходит — либо неправильно очерчен user, либо surface
  лишняя.
- ❌ Страница сайта как поверхность: лендинг акции внутри сайта, страница тарифов, блог — страницы поверхности рода
  `site`, их порядок держит карта сайта слоя страницы.

## Тест-критерий

«Может ли user, **зайдя только сюда**, закрыть хотя бы один свой job-to-be-done?» — и для `type: web`: «какой
репозиторий кода её поднимет и какой слой проектирует её композицию?»

- `web-clinic` (web-кабинет медсестры, `web-kind: app`) → ✅ (заходит, передаёт направление, готово; экраны и FSD).
- `promo-checkup` (лендинг акции со своим доменом и формой заявки, `web-kind: landing`) → ✅ (оставляет заявку; слой
  страницы).
- `tg-bot-status` (телеграм-бот с уведомлениями о статусе записи) → если только показывает — это `integration`; если
  можно отменить / переподтвердить → ✅ как surface.
- `internal-monitoring` → ❌ (внутренний инструмент команды, не продуктовая поверхность).
- `web` без рода → ❌ (неизвестно, поднимать `<org>/site` или `<org>/frontend`).

## Колонки

- `slug` — устойчивый идентификатор записи · `kebab-case` · обяз.
- `name` — короткое имя поверхности · текст · обяз.
- `description` — одно предложение, что это за точка встречи · текст · обяз.
- `type` — тип поверхности (один) · `web` \| `mobile` \| `api` \| `admin` \| `bot` \| `desktop` \| `embed` \| `other` ·
  обяз.
- `lives-at` — конкретное «где»: домен / app-id в магазине приложений либо «личная установка» / мессенджер /
  embedding-host · текст · обяз.
- `user` — ссылки на пользователей (`user`), которых поверхность обслуживает · `` [`user-slug`, …] `` · обяз.
- `web-kind` — род веб-поверхности; у остальных типов — `—` · `landing` \| `site` \| `app` \| `—` · обяз. у
  `type: web`
- `status` — зрелость записи · `draft` \| `stable` · обяз.

| slug | name | description | type | lives-at | user | web-kind | status |
|---|---|---|---|---|---|---|---|
| `<slug>` | <короткое имя> | <одно предложение> | `web` \| `mobile` \| `api` \| `admin` \| `bot` \| `desktop` \| `embed` \| `other` | <домен / app-id / messenger / host> | `` [`user-1`, …] `` | `landing` \| `site` \| `app` \| `—` | `draft` |

> Заполняется под проект. Пример (иллюстрация): `web-partner` · «Веб для медсестры» · «Кабинет медсестры партнёрской
> клиники» · `web` · «`partner.example.com`» · `` [`nurse-partner`] `` · `app` · `draft`.
