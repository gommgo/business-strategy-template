# surface

> Поверхность (surface) — точка, где продукт «торчит наружу» и встречает
> пользователя (user): web-приложение, мобильное приложение, публичное API,
> админка, телеграм-бот, embed-виджет. Поверхность принадлежит одному
> типу (`type`) и обслуживает одного+ пользователя (user).
>
> Семантически ↔ `interface/zone.md` — зоны интерфейса принадлежат
> поверхности. Жёсткой ссылки нет — `/cross-audit` ловит зоны без
> поверхности и поверхности без зон.

## Критерии surface

1. **Точка встречи с user.** Поверхность существует, потому что
   через неё user получает ценность от продукта. Если ни один
   user не пользуется — поверхность мёртвая.
2. **Один тип, одно «где».** `type` (web / mobile / api / admin / bot /
   desktop / embed / …) — один. `lives-at` — конкретное «где» (домен,
   store-app, мессенджер, embedding-host). Двух типов на одной surface
   не бывает — это две разные surface.
3. **Самодостаточна.** User может закрыть основной job-to-be-done,
   не выходя за пределы поверхности. Если для базовой задачи нужна
   другая поверхность — это или одна поверхность, или зависимость
   нужно явно зафиксировать.
4. **Поверхность ≠ канал нотификации.** Email/SMS/push, через которые
   мы только уведомляем — это **integration**, не surface. Surface — где
   user **действует**, а не только получает сигнал.

## Что surface НЕ

- ❌ Технологический стек («React-фронт», «Go-API»). Это стек, не
  поверхность. Поверхность — `web`, реализованная на чём угодно.
- ❌ Канал уведомлений без обратного действия (email-рассылка, push без
  deep-link). Это `integration`.
- ❌ Внутренний интерфейс команды (логи, мониторинг, k8s-dashboard).
  Это эксплуатация, не продукт.
- ❌ Поверхность без user. Surface, на которую никто из user не
  заходит — либо неправильно очерчен user, либо surface лишняя.

## Тест-критерий

«Может ли user, **зайдя только сюда**, закрыть хотя бы один свой
job-to-be-done?»

- `web-clinic` (web для медсестры) → ✅ (заходит, передаёт направление,
  готово).
- `tg-bot-status` (телеграм-бот с уведомлениями о статусе записи) →
  если только показывает — это `integration`; если можно отменить /
  переподтвердить → ✅ как surface.
- `internal-grafana` → ❌ (внутренний tool, не продуктовая
  поверхность).

## Колонки

- `slug` — устойчивый идентификатор записи · `kebab-case` · обяз.
- `name` — короткое имя поверхности · текст · обяз.
- `description` — одно предложение, что это за точка встречи · текст · обяз.
- `type` — тип поверхности (один) · `web` \| `mobile` \| `api` \| `admin` \| `bot` \| `desktop` \| `embed` \| `other` · обяз.
- `lives-at` — конкретное «где»: домен / app-id / мессенджер / embedding-host · текст · обяз.
- `user` — ссылки на пользователей (`user`), которых поверхность обслуживает · `` [`user-slug`, …] `` · обяз.
- `status` — зрелость записи · `draft` \| `stable` · обяз.

| slug | name | description | type | lives-at | user | status |
|---|---|---|---|---|---|---|
| `<slug>` | <короткое имя> | <одно предложение> | `web` \| `mobile` \| `api` \| `admin` \| `bot` \| `desktop` \| `embed` \| `other` | <домен / app-id / messenger / host> | `` [`user-1`, …] `` | `draft` |

> Заполняется под проект. Пример: `web-partner` · «Веб для медсестры» ·
> «SPA для медсестры партнёрской клиники» · `web` · «`partner.example.com`»
> · `` [`nurse-partner`] `` · `draft`.
