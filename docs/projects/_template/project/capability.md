# capability

> Возможность (capability) — бизнес-возможность продукта верхнего уровня,
> сформулированная в терминах «что продукт умеет для **кого**», а не «как
> это реализовано». Возможность ссылается на пользователя (user), для
> которого она ценна.
>
> Семантически ↔ `interface/situation.md` (через какие ситуации
> реализуется) и `domain/<область>` (какой бизнес-код её несёт). Жёсткой
> ссылки нет — связь ловит `/cross-audit`. `hypotheses` (опц.) связывает
> возможность с гипотезами Карты гипотез (`hypothesis-map/hypothesis`),
> `jobs` (опц.) — с работами сегмента (`ajtbd/job`), в которые она целит.

## Критерии capability

1. **Глагол + объект в языке user.** «Передать направление», «увидеть
   статус», «согласовать слот». Если возможность звучит как
   технологическая фича («Postgres-репликация», «JWT-аутентификация»)
   — это не capability, это домен/инфра.
2. **Кому ценность.** У каждой возможности есть один+ пользователь (user),
   который получает ценность. Если ценность «всем» — возможность плохо
   очерчена.
3. **Самодостаточна.** Возможность можно описать одним предложением
   ценности без отсылки к другой возможности. «Передать направление»
   — да. «Управлять направлениями» — нет (управлять = передать +
   отменить + переподтвердить, это группа).
4. **Не вход для реализации.** Возможность — **что**, не **как**.
   Конкретные шаги UX живут в `interface/situation.md`, бизнес-логика
   — в `domain/`. Здесь должна быть карта **умений** продукта, не их
   декомпозиция.
5. **Сквозные рёбра (опц.).** `hypotheses` — какие гипотезы Карты гипотез
   реализует возможность (`hypothesis-map/hypothesis`); `jobs` — в какие
   работы сегмента она целит (`ajtbd/job`). Оба авторские (capability →
   вверх), прочерк допустим.

## Что capability НЕ

- ❌ Фича-эпик в бэклоге («v2.0 — поиск по тегам»). Capability —
  устойчивая способность продукта, не тикет.
- ❌ Технологическая способность («продукт умеет в OAuth»). Это слой
  ниже — domain / integration.
- ❌ Группа возможностей под одним зонтом («управление пользователями»).
  Раскладывается на отдельные capability.
- ❌ Возможность без пользователя (user). Если ни один user не
  пользуется capability — она мёртвая, либо user ещё не добавлен.
- ❌ UI-элемент / экран / кнопка. «Кнопка отмены» — не capability;
  «отменить запись» — да.

## Тест-критерий

«Эта возможность (capability) формулируется в **одно предложение
ценности** для **конкретного пользователя (user)**, без слов о технологии?»

- «Медсестра передаёт направление без звонков» → ✅ (user + ценность,
  без «как»).
- «Авторизация по SMS» → ❌ (это `how`, не `what`; ценность не названа).
- «Управление пациентами» → ❌ (зонтичная, разложится на 3-5 capability).

## Колонки

- `slug` — устойчивый идентификатор записи · `kebab-case` · обяз.
- `name` — короткое имя, глагол + объект в языке user · текст · обяз.
- `description` — одно предложение, что продукт умеет · текст · обяз.
- `value` — ценность для user, в его языке · текст · обяз.
- `user` — ссылки на пользователей (`user`), которым возможность ценна · `` [`user-slug`, …] `` · обяз.
- `hypotheses` — ссылки на гипотезы `hypothesis-map/hypothesis`, которые возможность реализует (авторское ребро capability → вверх); иначе `—` · `` [`hyp-slug`, …] `` \| `—` · опц.
- `jobs` — ссылки на работы сегмента `ajtbd/job`, в которые возможность целит (авторское ребро capability → вверх); иначе `—` · `` [`job-slug`, …] `` \| `—` · опц.
- `status` — зрелость записи · `draft` \| `stable` · обяз.

| slug | name | description | value | user | hypotheses | jobs | status |
|---|---|---|---|---|---|---|---|
| `<slug>` | <короткое имя> | <одно предложение, что продукт умеет> | <ценность для user, в его языке> | `` [`user-1`, …] `` | `` [`hyp-1`, …] `` \| `—` | `` [`job-1`, …] `` \| `—` | `draft` |

> Заполняется под проект. Пример: `send-referral` · «Передать направление»
> · «Медсестра отправляет направление пациента в принимающую клинику»
> · «Один клик вместо 20-минутного звонка» · `` [`nurse-partner`] `` ·
> `—` · `—` · `draft`.
