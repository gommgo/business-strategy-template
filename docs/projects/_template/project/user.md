# user

> Пользователь (user) — тип адресата продукта: сегмент людей / клиентов,
> объединённых общим контекстом, jobs-to-be-done и болевыми точками.
> Не лицо, не должность в штатном расписании — а **тип адресата** боли,
> к которой прикасается продукт.
>
> На `slug` пользователя (user) ссылаются `surface.user`,
> `capability.user` и (семантически, не структурно) роли в
> `docs/projects/<slug>/interface/who.md`. `segments` (опц.) связывает
> пользователя с сегментами рынка (`ajtbd/segment`).

## Критерии user

1. **Адресат боли продукта.** Пользователь (user) — тот, чьё поведение
   изменится, если продукт сработает. Если изменение его ничему не
   меняет — это не пользователь (user).
2. **Контекст устойчивый.** Где он находится, в каком процессе, под
   каким давлением — описывается так, чтобы можно было воспроизвести
   ситуацию его жизни. Без контекста user — абстракция.
3. **Jobs-to-be-done в его языке.** То, ради чего он готов что-то
   сделать (или перестать делать). Не «фичи», а **зачем** ему результат.
4. **Боли наблюдаемые.** Что его сейчас раздражает / отнимает время /
   стоит денег / создаёт риск. Если боль не наблюдаема, user
   спекулятивен.
5. **Свой критерий успеха.** Что для **него лично** будет «полегчало».
   Может отличаться от vision.success — vision говорит про продукт в
   целом, user — про конкретный сегмент.
6. **Сегменты (`segments`, опц.).** Если пользователь сводится к
   сегмент(ам) рынка — `segments` ссылается на `ajtbd/segment`; иначе `—`.
   Связь авторская (user → ajtbd).

## Что user НЕ

- ❌ Должность в штатке («junior backend developer») без привязки к боли
  продукта.
- ❌ Демография ради демографии («женщины 25-40, доход выше среднего»)
  — это маркетинговый сегмент, не пользователь (user). Допустимо, если
  демография реально меняет контекст.
- ❌ Внутренняя роль команды («наш PM», «наш дизайнер») — если только
  продукт не сделан для самой команды.
- ❌ «Идеальный пользователь» из методичек. Берём реального адресата,
  даже если он неудобный.
- ❌ Системный актор (планировщик, ML-агент). Это не пользователь (user);
  если ему нужны интересы — он попадает в `interface/who.md` как
  системный актор, не в project.

## Тест-критерий

«Если этот пользователь (user) **исчезнет**, имеет ли продукт смысл?»

- «Медсестра партнёрской клиники, передающая направление» → ✅ (без
  неё нечего передавать).
- «Любой пользователь интернета» → ❌ (слишком широко, исчезновение
  ничего не меняет).
- «Маркетолог продукта» → ❌ (внутренняя роль; продукт не для него).

## Колонки

- `slug` — устойчивый идентификатор записи · `kebab-case` · обяз.
- `name` — имя сегмента-адресата · текст · обяз.
- `description` — одно предложение, кто это · текст · обяз.
- `context` — где живёт, в каком процессе, под каким давлением · текст · обяз.
- `jobs` — jobs-to-be-done в его языке: зачем ему результат · текст · обяз.
- `pains` — что сейчас раздражает / отнимает время / стоит денег / создаёт риск · текст · обяз.
- `success` — что для него лично будет «полегчало» · текст · обяз.
- `segments` — ссылки на сегменты рынка `ajtbd/segment` (связь авторская user → ajtbd); иначе `—` · `` [`segment-slug`, …] `` \| `—` · опц.
- `status` — зрелость записи · `draft` \| `stable` · обяз.

| slug | name | description | context | jobs | pains | success | segments | status |
|---|---|---|---|---|---|---|---|---|
| `<slug>` | <имя сегмента> | <одно предложение, кто это> | <где живёт, под каким давлением> | <jobs-to-be-done в его языке> | <что раздражает / отнимает> | <что для него лично «полегчало»> | `` [`segment-1`, …] `` \| `—` | `draft` |

> Заполняется под проект. Пример: `nurse-partner` · «Медсестра партнёрской
> клиники» · «Сотрудница чужой клиники, передающая направление
> пациента» · «Между приёмами, на телефоне, в формализованной
> переписке» · «Передать направление без ошибок и без переспросов» ·
> «20-30 минут на уточнения формата» · «Один клик — направление ушло» ·
> `—` · `draft`.
