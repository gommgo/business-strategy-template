## Exposes

> Бизнес-каталог функций, которые сервис отдаёт наружу (sync) — внутреннее
> зеркало `## Функции` продуктового `integration.md`. По этим `slug`'ам
> функции потребляют use-case'ы других сервисов (порт `service:<этот-slug>`
> в их `## Dependencies`). Без протоколов и endpoint'ов — это материализация
> кода. `audience`: `` `surface:<slug>` `` — зовёт поверхность (через входной
> api-gateway), `` `service:<slug>` `` — соседний сервис,
> `` `integration:<slug>` `` — внешняя система зовёт нас (inbound webhook
> терминируется здесь). `backed-by` — какой доменный use-case обслуживает
> функцию (`—` для сервисов без доменов).

## Messaging

> Асинхронный обмен через брокер. `broker` — реф в `../platform.md`
> (`type: message-broker`); `topic` — сквозной идентификатор: пара
> `(broker, topic)` у консьюмера обязана существовать у продюсера с тем же
> событием. `event` — payload-контракт, реф на доменное событие; produces

## Workers

> Фоновые воркеры **внутри** сервиса — процессы того же деплой-юнита
> (консьюмер топика, периодическая задача). Это не отдельный сервис: код и
> данные общие, деплоится вместе; отдельный деплой-юнит на событиях — это
> сервис `type: worker` в реестре. Здесь — **реестр-таблица**; полное
> описание каждого воркера (Trigger · Handles — какие доменные use-case'ы
> дёргает · Semantics — идемпотентность/retry→DLQ/ordering/батчинг ·
> On failure) — файлом [`workers/<slug>.md`](workers/) по форме
> `_templates/worker.md`. Воркер с `trigger: topic:<t>` требует парной
> строки `consumes` в `## Messaging`.
