# service

> Сервис (service) — деплой-юнит бэкенда: то, что мы **проектируем и пишем**,
> собираем и запускаем отдельно от соседей. У сервиса есть смысловая начинка —
> домены (bounded context), оркестрация или фасад с нормализацией — и паспорт
> (`<service-slug>/README.md`).
>
> Этот файл — **реестр-хребет** бэкенда (зеркало `surface.md` для фронта):
> он объявляет сервисы, а их slug'и — ключи партиционирования слоя. Каждый
> сервис из реестра получает папку `services/<service-slug>/` с паспортом и
> (для доменных типов) папкой `domains/`. Завести строку здесь — значит
> открыть сервису место в слое; `/service-audit` ловит папки вне реестра и
> строки без папки.

## Критерии service

1. **Отдельный деплой-юнит.** Сервис можно собрать, задеплоить и сломать,
   не трогая соседей. Если два «сервиса» всегда деплоятся вместе и делят
   данные — это один сервис.
2. **Своя смысловая начинка.** У сервиса есть что проектировать в этом репо:
   домены, оркестрация, фасад. Готовая инфраструктура, которую мы только
   конфигурируем (брокер, входной api-gateway, CDN), — `platform.md`,
   не сервис.
3. **Один тип.** `type` описывает роль сервиса в топологии; сервис с двумя
   ролями — кандидат на разделение (или на честное признание монолитом
   `api`).
4. **Владение данными.** Каждый ресурс (`Resources` паспорта) принадлежит
   ровно одному сервису. Сервис, читающий чужую БД, — анти-паттерн.

## Что service НЕ

- ❌ Bounded context. Контекст — единица **доменной** модели и живёт внутри
  сервиса; сервис может владеть несколькими контекстами (монолит — многими).
- ❌ Платформенный ресурс (брокер, входной api-gateway, CDN, object storage,
  IDP). Это `platform.md`: берём готовое и конфигурируем, не проектируем.
- ❌ Поверхность (surface). Поверхность — где user действует; сервис — что
  её обслуживает. Связь — колонка `surfaces`.
- ❌ Внешняя система или соседний проект. Это `integration` продуктового
  слоя; фасад к ней — наш сервис `type: gateway`.

## Тест-критерий

«Можно ли задеплоить и сломать его, не трогая соседей?»

- `orders` (домены заказов, своя БД, своё API) → ✅ сервис.
- `ai-gateway` (наш фасад к LLM-провайдеру, нормализует ответы) → ✅ сервис
  (`type: gateway`).
- «Postgres под заказы» → ❌ не сервис: ресурс в `Resources` паспорта
  `orders`.
- «Traefik на входе» → ❌ не сервис: запись `platform.md`
  (`type: api-gateway`).

## Типы сервисов

| type | смысл | домены | типовой пример |
|---|---|---|---|
| `api` | доменный сервис: владеет контекстами, отдаёт sync-API поверхностям и/или сервисам | да | `orders`, `billing`; монолит — один `api` со многими контекстами |
| `worker` | консьюмер/обработчик: живёт на событиях брокера и расписаниях, публичного API не имеет | может | `notifications-worker` |
| `gateway` | фасад к **внешней системе**: фронтит интеграцию из `integration.md`, нормализует её для остальных сервисов | нет | `ai-gateway`, `crm-gateway` |
| `edge` | edge/BFF: терминирует поверхность(и), агрегирует вызовы api-сервисов, своих контекстов не имеет | нет | `web-bff` |
| `bot` | bot-backend: оркестратор диалогов bot-поверхности (читает `telegram-bot-flow/<surface>/`), бизнес-правил не держит | нет | `tg-bot` |

«Монолит» — это `api`. Отдельные типы под cron/ETL/CDC не нужны: это
воплощение, не смысл. Фоновый процесс **внутри** сервиса (консьюмер,
периодическая задача того же деплой-юнита) — не отдельный сервис, а строка
`## Workers` его паспорта; `type: worker` — только когда это отдельный
деплой-юнит, живущий целиком на событиях/расписании.

## Колонки

- `slug` — устойчивый идентификатор сервиса (= имя папки) · `kebab-case` · обяз.
- `name` — короткое имя · текст · обяз.
- `description` — одно предложение, какую часть продукта несёт · текст · обяз.
- `type` — роль в топологии (одна) · `api` \| `worker` \| `gateway` \| `edge` \| `bot` · обяз.
- `surfaces` — какие поверхности обслуживает (slug-рефы в `surface.md`) · `` [`surface-slug`, …] `` \| `—` · обяз. (для `worker`/`gateway` обычно `—`)
- `status` — зрелость записи · `draft` \| `stable` · обяз.

Ребро **surface → service** авторится здесь (единственное место); паспорт его
не дублирует. Через что фронт физически ходит к сервису (входной
api-gateway) — запись `platform.md`; маршруты и хосты — runtime, не
моделируются.

| slug | name | description | type | surfaces | status |
|---|---|---|---|---|---|
| `<slug>` | <короткое имя> | <одно предложение> | `api` \| `worker` \| `gateway` \| `edge` \| `bot` | `` [`web`, …] `` \| `—` | `draft` |

> Заполняется под проект. Пример: `orders` · «Заказы» · «Домены заказов и
> оплат, API для web и бота» · `api` · `` [`web`, `tg-bot`] `` · `draft`.
