# Артефакты интерфейса

UX-слой проекта **партиционируется по поверхности (surface)**: на каждую поверхность из реестра `surface.md` — своя
папка `docs/projects/<project-slug>/interface/<surface>/` с 8 md-файлами (семь таблиц сущностей одного типа и файл
сценариев). Этот файл — **канон слоя**; форма одной папки поверхности (те самые 8 файлов) лежит рядом в
[`_template/`](_template/) — её копируют под каждый slug поверхности.

У `type: web` interface есть только у рода `app`: у рода `landing` и `site` на его месте слой страницы
`site/<surface>/` (канон — [`../site/README.md`](../site/README.md)), и экранов и FSD-карты у такой поверхности нет. У
остальных типов поверхности interface есть всегда.

## Структура

Канон формы живёт один раз в `docs/projects/_template/interface/` и описывает **одну папку поверхности**:

```
docs/projects/_template/interface/
├── README.md          ← этот файл (канон слоя)
└── _template/         ← форма одной папки поверхности (копируется под surface)
    ├── who.md
    ├── stage.md
    ├── situation.md
    ├── scenario.md
    ├── zone.md
    ├── block.md
    ├── ux-substrate.md
    └── data-items.md
```

Данные интерфейса живут в папке поверхности проекта `docs/projects/<project-slug>/interface/<surface>/` (одна папка на
поверхность из реестра `surface.md`):

```
docs/projects/<project-slug>/interface/
└── <surface>/
    ├── who.md
    ├── stage.md
    ├── situation.md
    ├── scenario.md
    ├── zone.md
    ├── block.md
    ├── ux-substrate.md
    └── data-items.md
```

Все ссылки между сущностями — через `slug`, **в пределах одной поверхности**:
who/stage/situation/scenario/zone/block/ux-substrate/data-items одной папки ссылаются только друг на друга. Вверх, в
продуктовый слой той же папки проекта, ссылаются участник (`who.users` → `user`), ситуация и сценарий
(`capabilities`, `capability` → `capability/<surface>.md`), зона и данные (`object` → глоссарий объектов
`object.md`). `data-items` surface-локален — правило «один датум, один slug» действует **внутри поверхности**; один и
тот же бизнес-датум на web и в боте — две записи в разных папках, их сверяет `/cross-audit` (hint, не error), а
понятие за ними одно — объект глоссария.

**Чистая аналитика**: на код (FSD-слои, компоненты) артефакты напрямую не мапятся — переход к коду идёт через
`docs/projects/<project-slug>/screens/<surface>/` (карта экранов, состояния, компоненты, тексты интерфейса; для
поверхности с `type: bot` — `telegram-bot-flow/<surface>/`, с `type: mobile` — `mobile/<surface>/`: композиция и
карта кода приложения, мост к `<org>/mobile`) и, для фронтовых поверхностей, через FSD-карту `fsd/<surface>/`
(артефакт-мост к коду `<org>/frontend`, читает ситуации и данные этого слоя как источник).

## Порядок

Интерфейс поверхности начинается со сценариев: для каждой возможности `hub` и `critical` поверхности маршрута
приложения сценарий пишется до экранов (ux 13/04 §11), и его шаги заводят ситуации — сначала stub-строками. Затем —
участники, этапы, ситуации с частотой и отказами, зоны информационной архитектуры, блоки, субстраты, данные. После
сценариев хабов в работу может войти слой дизайна: бриф на вид приложения и дизайн-система не ждут экранов.

## Файлы

| файл | сущность | поля |
|---|---|---|
| [`who.md`](_template/who.md) | участник системы | slug · name · description · users · status |
| [`stage.md`](_template/stage.md) | этап бизнес-процесса (порядок строк = порядок этапов) | slug · name · description · status |
| [`situation.md`](_template/situation.md) | ситуация: кто/когда/что/ради чего/с какими данными, как часто, чем может не закончиться | slug · name · description · stage · who · when · action · goal · entry-data · exit-data · using-what · ux-substrate · block · jobs · capabilities · hypotheses · frequency · refusals · status |
| [`scenario.md`](_template/scenario.md) | пользовательский сценарий одной задачи — **секция на сценарий** | `## <slug>` + мета: name · capability · who · goal · frequency · expertise · preconditions · trigger · context-needed · reversibility · status; подразделы Happy path · Ветвления · Ошибки · Конечные состояния · Чей ход · Что меняется · Приёмка |
| [`zone.md`](_template/zone.md) | зона интерфейса — раздел информационной архитектуры | slug · name · description · parent-zone · order · object · status |
| [`block.md`](_template/block.md) | блок (узел навигации + контейнер субстратов) | slug · name · description · zone · who · ux-substrates · entrypoint · transition-to-block · transition-from-zone · status |
| [`ux-substrate.md`](_template/ux-substrate.md) | UX-субстрат: `type` + `name`, принадлежит ситуации | slug · name · description · type · situation · status |
| [`data-items.md`](_template/data-items.md) | элемент данных в языке участника (entry/exit ситуации, опц.) | slug · name · description · object · status |

## Принципы оформления

Один файл — одна таблица сущностей одного типа. Исключение — `scenario.md`: **секция на запись** (`## <slug>` +
мета-блок YAML + подразделы), как окна и use-case'ы бота, потому что у сценария упорядоченные шаги и ветки. Структура
табличного файла:

```markdown
# <имя файла>

> Одна фраза о сущности (что это в проекте, что чем ссылается).

| slug | name | description | <relation columns> |
|---|---|---|---|
| `<slug>` | <имя> | <описание> | `<other_slug>` |
```

H1 = имя файла = kind. Под H1 — одна-две поясняющие фразы, при необходимости секции `Критерии <kind>` / `Что <kind> НЕ`
/ `Тест-критерий` (чем сущность является и чем — нет, с разделяющим вопросом и примерами ✅/❌), и одна таблица.
Frontmatter не нужен — kind определяется именем файла.

Русское слово, являющееся переводом строгого термина, сопровождается его `slug` в скобках при каждом вхождении:
«участник (who)», «способ действия (action)», «цель (goal)», «данные (data-items)», «сценарий (scenario)». Так перевод
и канонический идентификатор остаются однозначно связаны.

### Форма ячеек (единая по проекту)

| тип значения | формат | пример |
|---|---|---|
| одиночный slug-реф | в бэктиках | `` `doctor` `` |
| массив slug-рефов | питон-стиль с бэктиками внутри | `` [`doctor`, `nurse`] `` |
| пустое опциональное поле | em-dash | `—` |
| bool | как в коде | `true` \| `false` |
| enum (`status`, `frequency`, `type`) | в бэктиках | `` `draft` `` \| `` `stable` `` |
| свободный текст | без кавычек, одна строка | подпись бумажного направления |

Первые три колонки везде одни и те же: `slug` · `name` · `description`. Дальше — связи и доменные поля. **Последняя
колонка** во всех табличных файлах — `status` (enum `draft` \| `stable`): зрелость записи относительно своих
критериев; у сценария `status` — поле мета-блока секции.

## Статус записи

- `draft` — заведена, но не прошла полный чек-лист зрелости (часть слотов пустая, есть открытые вопросы,
  тест-критерий не подтверждён, или ссылается на ещё не существующие сущности).
- `stable` — прошла все критерии файла-канона (`Критерии <kind>`, `Что <kind> НЕ`, `Тест-критерий`), все обязательные
  слоты заполнены, все ссылки валидны, зеркала консистентны, открытых вопросов нет.
- Дефолт у новой записи — `draft`. Повышение в `stable` — через скилл `/interface-deep-dive`, по подтверждению
  аналитика.
- Понижение `stable → draft` — только аналитик руками, когда нашёл несостыковку.
- `stable` может ссылаться на `draft`: это «эта запись прошла свои критерии», не «вся цепочка зрелая».
  `/interface-audit` подсветит hint, не блокирует.

## Связи и выводимые поля

- **ситуация → этап** (M:1): `situation.stage`.
- **ситуация → участник** (M:1): `situation.who`.
- **ситуация ↔ данные** (M:N, опционально): `situation.entry-data`, `situation.exit-data` → `data-items`. Оба поля
  могут быть `—` (например, ситуация открытия экрана без явных входных данных). data-items — в **языке участника**
  (`who`), не в понятиях реализации; определение и критерии — в [`data-items.md`](_template/data-items.md).
- **ситуация → состояния отказа** (M:N): `situation.refusals` — ключи словаря состояний экрана (канон экранов
  [`../screens/README.md`](../screens/README.md), раздел «Состояния экрана»); отказы ситуаций экрана входят в его
  обязательный набор состояний.
- **сценарий → ситуации** (упорядоченно): шаги раздела «Happy path» и цели ветвлений — ситуации той же поверхности.
- **сценарий → возможность** (M:1): `scenario.capability` — возможность **той же поверхности**; у каждой `hub` и
  `critical` — хотя бы один сценарий.
- **сценарий → участники** (M:N): `scenario.who`; при двух и больше — раздел «Чей ход».
- **субстрат → ситуация** (M:1): `ux-substrate.situation` — канонический источник.
- **ситуация → субстраты** (1:N): `situation.ux-substrate` — **зеркало для наглядности**; должно соответствовать
  фильтру `ux-substrate.situation == <ситуация>`.
- **блок ↔ субстраты** (M:N): `block.ux-substrates` — канонический источник.
- **блок ↔ ситуация** (M:N): `situation.block` — **зеркало для наглядности**; должно соответствовать join'у через
  субстраты (`situation → ux-substrate.situation → block.ux-substrates`).
- **зона → родительская зона** (M:1): `zone.parent-zone`. Цикл запрещён.
- **блок → зона** (M:1): `block.zone`.
- **блок → блоки** (M:N исходящие): `block.transition-to-block`.
- **блок ← зоны** (M:N входящие): `block.transition-from-zone` — из этих зон можно попасть в этот блок. Внутри одной
  зоны блоки достижимы взаимно неявно: пишутся только нестандартные/межзонные переходы.
- **глобальный entrypoint**: `block.entrypoint = true` — стартовый блок системы (их может быть несколько, например по
  разным `who`). Каждый stable-блок достижим от стартового через зоны и переходы.

Межслойные сквозные рёбра (семантические, опц., авторски на стороне interface; ловит `/cross-audit`):

- **ситуация → работа** (M:N): `situation.jobs` → `ajtbd/job.md` — какие работы сегмента обслуживает шаг.
- **ситуация → возможность** (M:N): `situation.capabilities` → `projects/<slug>/capability/<surface>` — какие
  возможности **той же поверхности** шаг реализует.
- **ситуация → гипотеза** (M:N): `situation.hypotheses` → `hypothesis-map/hypothesis.md` — какие гипотезы шаг
  проверяет.
- **участник → пользователь** (M:N): `who.users` → `projects/<slug>/user` — какому пользователю продукта соответствует
  роль; постуру роль берёт у пользователя (`user.md`, раздел «Постура»).
- **данные → объект** (M:1): `data-items.object` → `projects/<slug>/object` — какой объект глоссария или его атрибут
  стоит за датумом.
- **зона → объект** (M:1): `zone.object` → `projects/<slug>/object` — вокруг какого объекта построен раздел.

## Информационная архитектура

Зона — раздел информационной архитектуры поверхности. Навигация приложения собирается из зон: пункты уровня 1 —
корневые зоны по `order`, уровня 2 — их дочерние зоны; вкладки объекта — уровень 3, внутри экрана. Экран связывает
раздел с маршрутом полем `zone` (канон экранов). Имена разделов — существительные без свалок «Разное» и «Прочее»,
категории соседей не пересекаются, глубина дерева и число корневых зон — по ux 02/01 §3.2–§3.3; критерии — в
[`zone.md`](_template/zone.md).

## Workflow

```
/interface-deep-dive — единая точка входа.
```

Скилл заводит новые сущности, углубляет частичные, разбирает сырьё (транскрипт интервью, заметки, скрин UI), ведёт
переход `draft → stable`. В конце сессии предлагает прогнать `/interface-audit` — полный аудит консистентности
(тупики, рассинхрон зеркал, битые ссылки, семантические подозрения).

## Anti-patterns

- ❌ Несколько таблиц в одном файле (один файл = один kind; у сценариев — секция на запись).
- ❌ Ссылки прозой или на несуществующий slug.
- ❌ Один датум под разными `data-items` slug'ами (реестр сквозной **в пределах поверхности**).
- ❌ Расхождение зеркал у ситуации: `situation.ux-substrate` не соответствует фильтру по `ux-substrate.situation`, или
  `situation.block` не соответствует join'у через субстраты.
- ❌ Цикл `parent-zone` в `zone.md`.
- ❌ Явный `transition-to-block` внутри одной зоны (внутризонная связность — по умолчанию).
- ❌ Блок без `ux-substrates` или без `who`.
- ❌ Сценарий из шагов, которых нет среди ситуаций поверхности, или сценарий, остановленный на основном пути.
- ❌ Экранные поля в сценарии: маршрут шага, фокус и сохранение введённого — поля экрана и карта экранов
  (`screens/<surface>/`).
- ❌ Код, FSD, компонент и облик в артефактах. Композиция — `screens/<surface>/` (для bot-поверхности —
  `telegram-bot-flow/<surface>/`, для мобильной — `mobile/<surface>/`), карта кода — FSD-карта `fsd/<surface>/`,
  облик — слой дизайна `design/`; в interface облика нет.
- ❌ `interface/<surface>/` у поверхности `web` рода `landing` или `site`: на его месте слой страницы.
- ❌ Ссылка из папки одной поверхности в сущность другой поверхности. Поверхности изолированы; общее (один user, один
  датум на разных поверхностях) сводит `/cross-audit`.
