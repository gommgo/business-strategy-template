# integration

> Интеграция (integration) — внешняя система, с которой продукт
> обменивается данными или поручениями. Платёжный шлюз, CRM, ERP,
> мессенджер, IDP, маркетинг-сток, BI-приёмник, регистратор событий,
> SSO-провайдер. Каждая интеграция — отдельная запись.
>
> Семантически ↔ `domain/<адаптер>` (в коде живёт как доменный адаптер).
> Жёсткой ссылки нет — `/cross-audit` ловит интеграции без домена и
> «дикие» адаптеры в коде без записи здесь.

## Критерии integration

1. **Граница ответственности.** За что отвечает внешняя система, за что
   мы. «`description`» — про то, **зачем** интегрируемся; `payload` —
   **что** передаём/получаем; `direction` — **кто инициирует**.
2. **Один провайдер — одна запись.** Если CRM — это записываем CRM
   (Bitrix24 / Pipedrive / самописная) одним slug. Если по той же
   системе есть две сильно разные интеграции (синхронизация + webhook
   нотификации) — это две записи.
3. **Направление честно.** `in` — внешняя система пишет к нам; `out` —
   мы пишем во внешнюю; `duplex` — двунаправленно (нужна явная
   синхронизация). Не путаем «пишем в API провайдера» (это out) с
   «получаем webhook от провайдера» (это in).
4. **`owner` — кто инициирует обмен.** `we` — обмен начинается с нашей
   стороны (POST, polling); `partner` — с их стороны (webhook,
   subscription). Бывает `both` — phone home + webhook.
5. **Чувствительные данные.** Если payload пересекает PII / финансы /
   медицинские данные — это автоматический повод завести `constraint`
   (152-ФЗ / PCI-DSS / HIPAA).

## Что integration НЕ

- ❌ Surface. Email-рассылка как продуктовая поверхность для user —
  тут граница тонкая, но критерий простой: если user **действует**
  через канал — это `surface`; если только получает сигнал — `integration`.
- ❌ Внутренний сервис продукта (Postgres / Redis / собственный
  бэкенд). Это инфра / domain, не интеграция.
- ❌ Библиотека / SDK без побочных эффектов в чужой системе.
  «Используем lodash» — не интеграция. «Зовём Stripe SDK, который
  создаёт чарж у Stripe» — да.
- ❌ Маркетинговая аналитика без передачи данных наружу. Если только
  читаем — это integration `in`; если ничего не происходит — нечего
  заводить.

## Тест-критерий

«Если эта внешняя система **уйдёт в офлайн на час** — что **сломается** в
продуктовом experience user?»

- Stripe уйдёт → user не сможет оплатить → ✅ critical integration.
- BI-receiver уйдёт → внутренние дашборды устареют, user ничего не
  заметит → ✅ low-criticality integration (но всё равно фиксируем).
- Внутренний Postgres уйдёт → ничего не работает → ❌ это не
  integration, это база.

|---|---|---|---|---|---|---|
| `<slug>` | <короткое имя провайдера> | <зачем интегрируемся, в одном предложении> | `in` \| `out` \| `duplex` | <что передаём/получаем, в языке бизнеса> | `we` \| `partner` \| `both` | `draft` |
