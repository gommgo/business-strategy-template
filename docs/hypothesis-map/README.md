# Артефакты Карты гипотез

Слой **Карты гипотез**: стратегическая ставка (`docs/swot/bet`)
дотягивается до измеримой **цели** и причинной цепи «**воздействие →
поведение субъекта → метрика**». Стоит между SWOT (`docs/swot/`) и
продуктом (`docs/projects/`): отсюда берутся цель и метрика, в которые
целит `vision.Success`.

Пять kind в порядке ветки:

1. **`goal`** — вершина ветки: критерий успеха **без цифр**.
2. **`metric`** — измеримый параметр цели: baseline + target + обвязка
   честного измерения (источник, атрибуция, приёмка). Best-effort таргет,
   **не гарантия**.
3. **`subject`** — носитель самодвижения, чьё поведение двигаем (не
   исполнитель).
4. **`hypothesis`** — четыре части «**если** · **то** · **потому что** ·
   **тогда**»; «тогда» бьёт в `metric`.
5. **`task`** — активность, которой проверяем гипотезу (задача-сирота
   запрещена).

Слой **строгий** (методология Карты гипотез) и **многопроблемный**:
каждая запись принадлежит одной+ проблеме (M:N) через колонку `business-problem` —
ссылку на строки `business/business-problem.md`.

## Юридическая рамка (читать до заполнения)

Мы **гарантируем доставку проекта на 100% по scope** — это твёрдое
обязательство. Метрики этого слоя — **совместный с бизнесом best-effort
таргет**: проектируем решение, которое с максимальной вероятностью на них
повлияет, но **не гарантируем** исход (есть факторы вне нашего контроля).
Строгость метрик нужна не как щит в суде, а ради **общей ясности и
честного измерения** — чтобы обе стороны одинаково видели «сдвинулось /
нет» и чей это вклад. Граница «гарантируем / целимся / вне контроля»
живёт в `business/business-problem.md`.

## Файлы

| файл | сущность | поля |
|---|---|---|
| [`goal.md`](goal.md) | цель карты гипотез (без цифр) | slug · name · description · **business-problem** · from-bet · deadline · status |
| [`metric.md`](metric.md) | измеримый параметр цели (best-effort таргет) | slug · name · **business-problem** · goal · current · target · direction · kind · source · attribution · acceptance · evidence · status |
| [`subject.md`](subject.md) | субъект, чьё поведение меняем | slug · name · description · **business-problem** · kind · motivation · segments · users · status |
| [`hypothesis.md`](hypothesis.md) | гипотеза (если · то · потому что · тогда) | slug · name · **business-problem** · if · then · because · so · subject · metric · jobs · priority · status |
| [`task.md`](task.md) | задача проверки гипотезы | slug · name · description · **business-problem** · hypothesis · status |

`business-problem` везде — массив slug-рефов на строки `business/business-problem.md`
(M:N).

## Принципы оформления

Зеркалит канон `docs/projects/_template/project/`. Один файл — одна таблица.
H1 = имя файла = kind, без frontmatter. Русское слово-перевод строгого
термина сопровождается `slug` в скобках: «цель (goal)», «метрика
(metric)», «субъект (subject)», «гипотеза (hypothesis)», «задача (task)».

**Исключение для `hypothesis`:** вместо одиночного `description` несёт
четыре структурные части `if` · `then` · `because` · `so` — это и есть
тело гипотезы по методологии.

### Форма ячеек

| тип значения | формат | пример |
|---|---|---|
| одиночный slug-реф | в бэктиках | `` `paid-churn` `` |
| массив slug-рефов | питон-стиль с бэктиками | `` [`paid-outflow`] `` |
| пустое опциональное поле | em-dash | `—` |
| enum (`kind`, `direction`, `status`) | в бэктиках | `` `lagging` `` |
| приоритет | целое, 1 = высший | `1` |
| свободный текст | без кавычек, одна строка | «удержать платных пациентов» |

Последняя колонка везде — `status` (enum `draft` \| `stable`).

## Статус записи

- `draft` — заведена, не прошла чек-лист зрелости.
- `stable` — прошла критерии файла-канона, обязательные слоты заполнены,
  методологические инварианты соблюдены, открытых вопросов нет.
- Дефолт — `draft`. Повышение — через `/hypothesis-map-deep-dive` по
  подтверждению аналитика. Понижение — аналитик руками.

## Связи и методологические инварианты (семантические)

Связи **не валидируются slug-целостностью** — они семантические. Все
инварианты считаются **в пределах одной проблемы** (`business-problem`).
Методологические инварианты Карты гипотез ловит **рой агентов**
`/hypothesis-map-audit` — смыслом, не grep:

- **Задача-сирота запрещена.** Каждая `task` привязана к `hypothesis`.
  Не привязана — не берём в работу (ресурсный фильтр методологии).
- **«Тогда» бьёт в метрику.** `hypothesis.so` ссылается на конкретную
  `metric` цели той же проблемы. Нет ссылки — гипотезу нельзя оценить.
- **«Потому что» опирается на мотивацию.** `hypothesis.because`
  коррелирует с `subject.motivation`. Нет опоры — гипотеза без шанса.
- **Метрика без влияния.** Целевая `metric`, в которую (в пределах её
  проблемы) не бьёт ни одна гипотеза, — мёртвая.
- **Целевая без guardrail.** У каждой целевой метрики проблемы есть хотя
  бы одна балансирующая (`kind: balancing`), закрывающая способ
  «сжульничать».
- **Цель без метрики.** У каждой `goal` есть ≥1 `metric` — иначе нечем
  измерить достижение.
- **Исполнитель вместо субъекта.** `subject` — носитель самодвижения, а
  не тот, кто делает задачу.

Связь с соседними слоями (тоже семантическая, ловит `/cross-audit`):

- `swot.bet.promoted-to` → `goal` / `hypothesis` — ставка дотягивается до
  карты.
- `business.current-metric` → `metric.current` — текущий KPI становится
  baseline целевой метрики.
- `goal` / `metric` → `projects/<slug>/vision.Success` — успех продукта
  целит в ту же метрику.
- `subject.segments` → `ajtbd/segment` — субъект влияния вырастает из
  сегмента рынка (обяз. для `positive`; для `negative` — опц., конкурент
  или регулятор не обязан быть нашим сегментом).
- `subject.users` → `projects/<slug>/user` — субъект влияния ↔ пользователь
  продукта (опц.).
- `hypothesis.jobs` → `ajtbd/job` — гипотеза целит в работу(ы) сегмента (опц.).
- `business-problem` → `business/business-problem.md` — каждая запись питает одну+
  строку реестра проблем; строка без единой `goal` — повисла.

## Workflow

```
/hypothesis-map-deep-dive — единая точка входа аналитика.
/hypothesis-map-audit     — рой агентов: инварианты Карты гипотез.
/cross-audit              — сквозная проверка с business / swot / project.
```

## Anti-patterns

- ❌ Метрика как **гарантия** («гарантируем рост на 20%»). Best-effort
  таргет (см. `business/business-problem.md`).
- ❌ Бинарная метрика («запущен модуль») как результат.
- ❌ Цель с цифрой внутри (цифра — в `metric`).
- ❌ Задача вместо цели / задача-сирота без гипотезы.
- ❌ «Если» гипотезы как конкретная задача (преждевременная
  конкретизация); «тогда» не о метрике цели; «потому что» не о мотивации
  субъекта.
- ❌ Исполнитель вместо субъекта (субъект — носитель самодвижения).
- ❌ Запись без `business-problem` (непонятно, какой проблемы касается).
- ❌ Frontmatter / каталоги под kind.
- ❌ Жёсткие slug-валидации. Инварианты ловит рой, не grep.
