# Артефакты AJTBD (сегменты и граф работ)

Слой **discovery** между «кто этот бизнес» (`docs/business/`) и «какую
проблему решаем» (реестр `business-problem` в `docs/business/`). По
методологии **Advanced JTBD** (Иван Замесин): кто наш сегмент — **по
работам, а не по демографии**, как устроен его **граф работ**, что он
«нанимает» на работы и где **трётся** с этими решениями. Источник
истины — **рой web-research** (многоволновой) и опционально
**JTBD-интервью**, не проекция аналитика.

Слой **строгий** (своя методология и свой аудит), но **разведочный** по
характеру: ищет known-unknown — сегменты и работы, которых мы ещё не
знаем. Поэтому метрик-обязательств здесь нет (это слой Карты гипотез
`docs/hypothesis-map/`); здесь — карта спроса, на которой строится проблема
бизнеса и продукт.

Слой **один на бизнес** (как `business`), не per-project. Питает обоих
соседей: вверх — реестр проблем бизнеса (`business/business-problem`)
(трения сегмента доказывают проблему бизнеса), вниз — `docs/projects/<slug>/`
(граф работ и механики ценности подсказывают возможности продукта).

## Ядро методологии (читать до заполнения)

- **Работа ⟂ Решение ⟂ Проблема — три разные сущности.** Людям не нужны
  продукты; они хотят достигать целей и лучше себя чувствовать. Проблема
  **никогда не существует сама по себе** — она следствие конкретного
  **решения**, нанятого на **работу**. Поэтому `segment-problem` всегда
  висит на паре `solution` + `job`.
- **Сегмент = люди, объединённые общей работой**, не демографией. Один
  сегмент держится на **бандле Core Jobs** + ровно **одной Big Job** +
  общих **критериях успеха**.
- **Уровни работ.** `big` — верхняя мотивация (не меняется десятилетиями);
  `core` — то, за что платят, что продукт завершает целиком; `low` —
  низкоуровневые работы-шаги (важны для UX, не для сегментации).
- **Типы работ** определяют продуктовую стратегию: разовые ·
  последовательные · частотные (двигатель LTV) · виральные · налоговые
  (издержки, которые можно «убить») · ложные (85 lvl — нужен проверочный
  вопрос).
- **Score сегмента** = важность × частотность × размер ×
  (10 − удовлетворённость текущим решением). Чем хуже текущее решение —
  тем проще принести ценность.
- **CPR** (Critical Path of Results) — упорядоченный must-do путь работ к
  Big Job; разрыв CPR убивает результат. Разрывы CPR — кандидаты в
  возможности продукта.
- **11 механик создания ценности** выводятся прямо из графа работ (растить
  Benefits / снижать Cost / будить спящие / убить низкоуровневую / забрать
  у конкурента / …). В `job-graph` живут как кандидаты-механики → `capability`.

## Принципы оформления

Зеркалит канон `docs/business/`. Один файл —
одна таблица сущностей одного типа. H1 = имя файла = kind, без
frontmatter. Русское слово-перевод строгого термина сопровождается `slug`
в скобках при каждом вхождении: «сегмент (segment)», «работа (job)»,
«решение (solution)», «трение / проблема сегмента (segment-problem)»,
«граф работ (job-graph)».

### Форма ячеек

| тип значения | формат | пример |
|---|---|---|
| одиночный slug-реф | в бэктиках | `` `dacha-owner` `` |
| массив slug-рефов | питон-стиль с бэктиками | `` [`buy-gear`, `plan-trip`] `` |
| упорядоченный путь (CPR) | питон-стиль, порядок значим | `` [`step-1`, `step-2`, `step-3`] `` |
| пустое опциональное поле | em-dash | `—` |
| enum (`kind`, `level`, `type`, `status`) | в бэктиках | `` `core` `` |
| оценка 1–10 | целое | `7` |
| свободный текст | без кавычек, одна строка | «когда промок в прошлый раз» |

Первые две колонки везде — `slug` · `name`. Последняя — `status` (enum
`draft` \| `stable`).

## Статус записи

- `draft` — заведена, не прошла чек-лист зрелости (часть слотов пустая,
  факт не подтверждён research/интервью, есть открытые вопросы в `state/`).
- `stable` — прошла критерии файла-канона, обязательные слоты заполнены,
  методологические инварианты соблюдены (см. ниже), факт прослежен до
  research или транскрипта интервью.
- Дефолт — `draft`. Повышение — через `/segment-deep-dive` или
  `/job-graph-deep-dive` по подтверждению аналитика. Понижение — аналитик
  руками.

## Связи и методологические инварианты (семантические)

Связи **не валидируются slug-целостностью** — они семантические, как в
`swot`/`hypothesis-map` и `project`. Методологические инварианты ловит **рой
агентов** `/ajtbd-audit` — смыслом, не grep:

- **Сегмент держится на бандле.** У `segment` ровно одна `big-job` и ≥1
  `core-job`. Ноль Big Job или несколько — не сегмент.
- **Непрерывность «чтобы».** `job.so-that` нижней работы = `want` верхней
  (как «5 почему»); цепочка ведёт вверх до `big`-работы сегмента.
- **Работа тегирована сегментом.** Каждая `job` несёт `segment`.
- **У целевой работы есть решение.** У `core`-работы ≥1 `solution` с
  оценками `satisfaction` и `price-value-fit` — иначе Score не вычислить.
- **Проблема — следствие решения.** `segment-problem` висит на реальной
  паре `solution` + `job`. Трение без решения запрещено.
- **Score вычислим.** У `segment` есть компоненты (важность · частотность
  · размер · удовлетворённость) — иначе остаётся `draft`.
- **Граф размечен по типам.** В `job-graph` у работ проставлен `type`; CPR
  без разрывов.
- **Ложные работы помечены.** Подозрительная работа проверена вопросом и
  при необходимости помечена `type: ложная`.

Связь с соседними слоями (тоже семантическая, ловит `/cross-audit`):

- `segment` ↔ `projects/<slug>/user` — сегмент рынка ↔ пользователь
  продукта (разные сущности: сегмент — клиент/рынок, пользователь —
  адресат нашего решения; авторски `user.segments`).
- `job` (`big`/`core`) → `projects/<slug>/vision.Success` — успех
  продукта целит в Big/Core Job сегмента.
- `segment-problem` → `business/business-problem` (доказательство проблемы
  бизнеса; опц. явная ссылка `feeds-problem`) и → `projects/<slug>/vision.Problem`.
- `segment` ↔ `hypothesis-map/subject` — субъект влияния вырастает из
  сегмента (авторски `subject.segments`).
- `segment.score` / `segment-problem` → `swot/factor` —
  сильное трение при низкой удовлетворённости питает SWOT-фактор.
- `job` ← `hypothesis-map/hypothesis.jobs`, `projects/<slug>/capability.jobs`,
  `interface/situation.jobs` — работа сегмента, в которую целят гипотеза,
  возможность и ситуация (авторски снизу-вверх).
- `solution` ↔ `business/competitor` / `business/offering` — нанятое
  решение часто и есть конкурент или собственный офер бизнеса (`maps-to`).
- `job-graph.value-mechanics` → `projects/<slug>/capability` — механика
  ценности из графа становится возможностью продукта.
- `business/offering.for-segment`, `business/channel.serves-segment` →
  `ajtbd/segment` — оферы и каналы бизнеса обслуживают эти сегменты.

## Workflow

```
/segment-deep-dive               — поиск/скоринг сегментов (рой, многоволновой).
/segment-deep-dive-for-business  — клиент описывает своих клиентов (бизнес-язык).
/job-graph-deep-dive             — сборка графа работ выбранного сегмента (рой).
/job-graph-deep-dive-for-business— клиент описывает работы/решения своими словами.
/jtbd-interview                  — опц. тяжёлый процесс: рекрут → скрипт → интервью → конспект.
/ajtbd-audit                     — рой: методологические инварианты слоя.
/cross-audit                     — сквозная проверка с business / business-problem / projects.
```

Поток discovery: `business` (профиль готов) → `segment-deep-dive` (выбран
сегмент по Score) → `job-graph-deep-dive` (граф, решения, трения) →
`business-problem` (трения → проблема) и/или `project` (механики →
capability). `jtbd-interview` запускается из любой фазы по явному решению,
кладёт сырьё (транскрипты + кандидаты в `state/`), которое
`*-deep-dive`-скил разбирает через intake. Рой кладёт кандидатов в
`state/research/`; promotion в артефакты — только через `AskUserQuestion`.
Авто-залив из веба и из транскриптов запрещён.

## Anti-patterns

- ❌ **Демография как сегмент** («женщины 25–35»). Сегмент — общий бандл
  работ + критерии успеха, а не возраст/пол/«SMB».
- ❌ **Проблема без решения.** `segment-problem` без `solution` — нарушение
  ядра: проблема всегда следствие конкретного нанятого решения.
- ❌ **Работа = задача/фича/решение.** `job` — цель + желаемое состояние,
  не «нажать кнопку» и не наш будущий продукт.
- ❌ **Сегмент без Big Job или с несколькими.** Ровно одна Big Job на
  сегмент.
- ❌ Путать `segment-problem` (трение **клиента** с решением) с
  `business/business-problem` (проблема **бизнеса**). Первое питает второе.
- ❌ Путать `ajtbd/segment` (клиент/рынок) с `projects/<slug>/user`
  (пользователь нашего решения) — соседние слои.
- ❌ Граф работ без разметки типов и без CPR.
- ❌ Слово «pain» / «боль» вместо работ, критериев и мотиваций.
- ❌ Frontmatter / каталоги под kind / несколько файлов одного kind.
- ❌ Автозалив web-research или транскриптов интервью в артефакты без
  подтверждения аналитика.
