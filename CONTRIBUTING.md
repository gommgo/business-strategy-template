# Вклад в business-strategy-template

Это форкаемый **шаблон бизнес-стратегии** — методология и каркас аналитики:
бизнес → проблемы → AJTBD → SWOT → Карта гипотез (терминал — `task`), а продукт
(`projects/` → интерфейс / домены / экраны) — опциональный исход, когда стратегия
требует его. Вклад полезен, когда он делает методологию, каноны формы или
deep-dive-скиллы чище и понятнее — не когда он зашивает данные конкретного
заказчика.

## С чего начать

- Прочитай `README.md` (карта репозитория и воркфлоу) и `CLAUDE.md` (роль репо,
  роутер слоёв, принципы). Каноны формы — в `docs/projects/_template/` и README
  каждого слоя.
- Сборки здесь нет — артефакты это чистая аналитика: markdown, а у слоёв страницы и
  дизайна — YAML и JSON по схемам базы скилла `design-deep-dive`. «Запуск» репозитория —
  это прохождение слоёв через оркестратор `/entrypoint` или напрямую deep-dive-скиллы
  (`/business-deep-dive`, `/swot-deep-dive`, `/hypothesis-map-deep-dive`,
  `/project-deep-dive <slug>`, и т.д.).

## Принципы

- **Артефакты — source of truth.** Бизнес — верх (профиль + реестр проблем); под ним
  AJTBD, SWOT и Карта гипотез; продукты — опциональный исход (когда проблему не
  закрывает задача `task`); всё растёт сверху вниз. На код напрямую не мапятся.
- **Канон формы — один раз в `docs/projects/_template/`**, данные — в папках проектов;
  канон не дублируется в проект.
- **Экспертиза священна.** Доменные и продуктовые формулировки приходят от
  бизнеса, аналитика и архитектора через `AskUserQuestion`, не из головы агента;
  облик — только в слое дизайна, утверждает владелец продукта. Неоднозначность
  вне покрытия — вопрос человеку, не угадывание.
- **Метрика — best-effort таргет, не гарантия.** Гарантируем доставку проекта по
  scope; на метрику целимся совместно с бизнесом.
- **Связи между слоями семантические**, не slug-валидируемые. Расхождения ловит
  `/cross-audit` (рой агентов), не grep.
- **Forward-only.** Все артефакты — «что есть сейчас и куда идём», без changelog'ов в
  prose, дат, «было/стало». История живёт в `git log`.
- **`.claude/rules/` расширяем.** Каталог правил для агента — открытый: потребитель
  форка добавляет туда собственные `<topic>.md`-правила (path-scoped инварианты своего
  проекта: `paths:` во frontmatter), не ограничиваясь поставляемыми `forward-only.md`
  и `naming.md`.

## Форк, issue, PR

- **Issue** — для багов методологии и предложений: что в каноне/скилле неясно или
  ломается, как воспроизвести, ожидаемое поведение.
- **PR** — форкни репозиторий, заведи ветку, открой pull request с понятным описанием
  «зачем». Держи PR сфокусированным; не подмешивай несвязанные правки. Один sweep =
  одна непересекающаяся зона.
- Правка, способная сломать накопленную продуктовую модель или раскатиться вширь
  (контракт артефактов всех слоёв, таксономия) — опиши обоснование в PR отдельно.

## Перед PR

Сборки нет — gate здесь это **аудиты** соответствующего слоя (у слоёв страницы и
дизайна — вместе с валидаторами и линтерами скилла `design-deep-dive`):

- узкий аудит каждого тронутого слоя — по таблице слоёв в `CLAUDE.md` §2
  (`/project-audit <slug>`, `/interface-audit <slug>`, `/screen-audit <slug>`,
  `/fsd-audit <slug>`, `/design-audit <slug>`, `/telegram-bot-flow-audit <slug>`,
  `/mobile-audit <slug>`, `/service-audit <slug>`, `/infrastructure-audit`; `/swot-audit` ·
  `/hypothesis-map-audit` — по каждой проблеме, `/ajtbd-audit` — по каждому сегменту);
- `/cross-audit` — сквозная семантика между всеми слоями и проектами (прогнать,
  если трогал несколько слоёв).

- **Conventional Commits** (конвенция формата; git-хук не поставляется): `<type>(<scope>)?: <subject>`,
  subject ≤72. Типы: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `meta`.
  Пример: `docs(canon): clarify hypothesis-map metric attribution`.

## Стиль

Спокойно и по делу, без хайпа. По-русски; технические идентификаторы (имена файлов,
slug, kind) — как есть. Английский в backticks — для устоявшегося канона (`a11y`,
FSD-слои, DDD-термины) и структурных идентификаторов handoff-контракта
(`CLAUDE.md` §8), не для полу-калек. Каноны терминов — в README каждого слоя.

Описание скилла (`description` во frontmatter `SKILL.md`) — до 600 знаков: главный
случай первой фразой, дальше — категории намерений и граница с соседним скиллом, без
перечня фраз-триггеров и пересказа устройства скилла. Листинг скиллов Claude Code
держит имена всех скиллов, а описания при переполнении бюджета
(`skillListingBudgetFraction` в `.claude/settings.json`) снимает у реже вызываемых.
